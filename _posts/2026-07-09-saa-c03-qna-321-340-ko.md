## QUESTION 321

**문제**: 솔루션 설계자는 Amazon S3 버킷에 업로드되는 모든 객체가 반드시 암호화되도록 강제해야 한다. 어떻게 해야 하는가?

**보기**
- A. PutObject 요청에 `s3:x-amz-acl` 헤더가 설정되어 있지 않으면 거부하도록 버킷 정책을 업데이트한다(ACL 헤더는 접근 제어용이며 암호화 여부와는 무관).
- B. PutObject 요청에 `private`로 설정된 `s3:x-amz-acl` 헤더가 없으면 거부하도록 버킷 정책을 업데이트한다(마찬가지로 ACL은 공개/비공개 접근 범위를 지정할 뿐 암호화를 강제하지 않음).
- C. PutObject 요청에 `true`로 설정된 `aws:SecureTransport` 헤더가 없으면 거부하도록 버킷 정책을 업데이트한다(이는 전송 중 암호화, 즉 HTTPS 사용 여부를 강제할 뿐 저장 시 암호화와는 별개).
- D. **PutObject 요청에 `x-amz-server-side-encryption` 헤더 세트가 없으면 거부하도록 버킷 정책을 업데이트한다.**

**정답: D**

**해설**
버킷 정책의 `Deny` 조건에서 `s3:x-amz-server-side-encryption` 헤더가 없는 PutObject 요청을 거부하도록 설정하면, 클라이언트가 서버 측 암호화 헤더(SSE-S3 또는 SSE-KMS)를 명시하지 않은 업로드 자체가 실패하게 되어 버킷에 저장되는 모든 객체가 예외 없이 암호화됩니다. 이는 **저장 시 암호화(encryption at rest)**를 정책 수준에서 강제하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: `s3:x-amz-acl` 헤더는 객체의 접근 권한(ACL)을 지정하는 것으로 암호화와는 관계가 없습니다.
- B: 마찬가지로 ACL을 private로 강제하는 것은 접근 제어이지 암호화 강제가 아닙니다.
- C: `aws:SecureTransport`는 HTTPS를 통한 전송, 즉 전송 중 암호화를 강제하는 조건으로 저장 시 암호화 요구 사항을 충족하지 못합니다.

> 💡 **시험 꿀팁**: **"업로드되는 모든 객체를 암호화하도록 강제"**하라는 조건이 나오면 버킷 정책에서 **`x-amz-server-side-encryption` 헤더가 없는 PutObject를 거부**하는 방식이 표준 정답입니다.

## QUESTION 322

**문제**: 솔루션 설계자가 회사의 다중 계층 애플리케이션을 설계하고 있다. 사용자는 모바일 기기에서 이미지를 업로드하며, 애플리케이션은 각 이미지의 썸네일을 생성한 뒤 업로드 성공을 알리는 메시지를 사용자에게 반환한다. 썸네일 생성에는 최대 60초가 걸릴 수 있지만, 회사는 원본 이미지가 수신되었음을 더 빠르게 사용자에게 알리고 싶어 하며 서로 다른 애플리케이션 계층 간 요청을 비동기식으로 전달하는 구조를 원한다. 이 요구 사항을 충족하려면 어떻게 해야 하는가?

**보기**
- A. 사용자 지정 AWS Lambda 함수로 썸네일을 생성하고 사용자에게 알리며, 이미지 업로드 프로세스를 이벤트 소스로 사용해 Lambda를 호출한다(업로드 프로세스가 곧바로 Lambda를 호출·처리하는 구조라 계층 간 비동기 분리가 이루어지지 않고, 대량 업로드 시 동시 실행 문제도 발생할 수 있음).
- B. AWS Step Functions 워크플로를 생성해 애플리케이션 계층 간 오케스트레이션을 처리하고, 썸네일 생성이 완료되면 사용자에게 알린다(썸네일 생성 완료까지 기다렸다가 알리는 구조라 "빠른 응답"이라는 요구를 충족하지 못하고 오케스트레이션에 따른 지연·복잡성이 추가됨).
- C. **Amazon SQS 메시지 대기열을 생성한다. 이미지가 업로드되면 썸네일 생성을 위해 SQS 대기열에 메시지를 넣고, 이미지가 수신되었음을 애플리케이션 메시지로 즉시 사용자에게 알린다.**
- D. Amazon SNS 알림 주제와 두 개의 구독을 생성해, 업로드 완료 후 썸네일을 생성하고 완료 시 푸시 알림을 보낸다(SNS는 팬아웃 알림 서비스로 처리 작업을 대기열에 넣어 분리하는 용도가 아니며, 두 구독 체인이 추가적인 지연과 복잡성을 유발).

**정답: C**

**해설**
**Amazon SQS**는 업로드 처리 계층과 썸네일 생성 계층을 메시지 대기열로 분리(decouple)하는 완전관리형 서비스입니다. 이미지가 업로드되면 즉시 SQS에 작업 메시지를 넣고 사용자에게 수신 확인을 반환할 수 있으므로, 썸네일 생성이 끝날 때까지 기다릴 필요 없이 빠른 응답 시간을 제공합니다. 동시에 대기열이 버퍼 역할을 하여 업로드가 몰려도 뒷단 처리 계층이 자체 속도로 소비할 수 있어 확장성과 안정성이 향상됩니다.

**왜 다른 보기는 오답인가**
- A: 업로드 이벤트가 곧바로 Lambda를 트리거하는 구조는 비동기 디스패치를 위한 중간 버퍼가 없어 대량 업로드 시 동시성 문제가 발생하고, 응답을 빠르게 반환하는 별도 메커니즘도 없습니다.
- B: Step Functions는 단계별 오케스트레이션에는 유용하지만, 이 시나리오에서는 썸네일 생성 완료 후에야 사용자에게 알리도록 구성되어 빠른 응답 요구에 부합하지 않고 불필요한 복잡성을 더합니다.
- D: SNS는 발행-구독 알림 서비스로, 작업을 순차적으로 버퍼링·처리하는 대기열 역할을 하지 않으며 두 단계 구독 체인이 오히려 지연과 복잡도를 늘립니다.

> 💡 **시험 꿀팁**: **"빠른 응답 + 계층 간 비동기 처리"**가 필요하면 **Amazon SQS로 작업을 큐잉하고 즉시 확인 메시지를 반환**하는 패턴이 표준 정답입니다.

## QUESTION 323

**문제**: 회사 시설의 모든 출입구에 배지 판독기가 있으며, 배지를 스캔하면 판독기가 HTTPS로 메시지를 보내 누가 해당 출입구에 접근을 시도했는지 알린다. 솔루션 설계자는 이 센서 메시지를 처리할 시스템을 설계해야 하며, 솔루션은 고가용성을 갖추고 보안 팀이 분석할 수 있도록 결과를 제공해야 한다. 어떤 아키텍처를 추천해야 하는가?

**보기**
- A. Amazon EC2 인스턴스를 시작해 HTTPS 엔드포인트 역할을 하며 메시지를 처리하고, 결과를 Amazon S3 버킷에 저장한다(단일 EC2 인스턴스는 자체적으로 고가용성을 보장하지 않으며, S3에 쌓인 원시 결과는 보안 팀이 바로 분석하기에 적합한 질의형 저장소가 아님).
- B. **Amazon API Gateway로 HTTPS 엔드포인트를 만들고, AWS Lambda 함수를 호출해 메시지를 처리한 뒤 결과를 Amazon DynamoDB 테이블에 저장한다.**
- C. Amazon Route 53으로 들어오는 센서 메시지를 AWS Lambda 함수로 직접 보낸다(Route 53은 DNS 서비스로 HTTPS 메시지를 수신·라우팅해 Lambda를 호출하는 엔드포인트 역할을 하지 않음).
- D. Amazon S3용 게이트웨이 VPC 엔드포인트를 만들고, 시설 네트워크에서 VPC로 Site-to-Site VPN을 구성해 센서 데이터를 S3에 직접 기록한다(배지 판독기는 HTTPS로 메시지를 보내는 외부 디바이스이며, VPC 게이트웨이 엔드포인트는 VPC 내부 리소스가 S3에 프라이빗하게 접근하기 위한 것이라 이 시나리오에 맞지 않음).

**정답: B**

**해설**
**Amazon API Gateway**는 관리형 HTTPS 엔드포인트를 손쉽게 제공하며 자동으로 확장되어 대량의 센서 메시지를 안정적으로 수신할 수 있습니다. 여기에 **AWS Lambda**를 연결해 서버 관리 없이 메시지를 처리하고, 처리 결과를 저지연 조회가 가능한 **Amazon DynamoDB**에 저장하면 보안 팀이 필요할 때 즉시 데이터를 조회·분석할 수 있습니다. 이 조합은 완전관리형 서비스들로만 구성되어 있어 별도의 인프라 운영 없이도 고가용성을 확보합니다.

**왜 다른 보기는 오답인가**
- A: EC2 인스턴스 하나로 엔드포인트를 구성하면 고가용성 확보를 위해 별도의 다중 AZ 구성과 오토스케일링을 직접 설계·운영해야 하며, S3는 실시간 분석용 조회 저장소로는 적합하지 않습니다.
- C: Route 53은 DNS 라우팅 서비스일 뿐이며 HTTPS 요청을 받아 Lambda를 호출하는 애플리케이션 엔드포인트 기능이 없습니다.
- D: 이 구조는 VPC 내부 리소스가 인터넷 경유 없이 S3에 접근할 때 쓰는 것으로, 외부 배지 판독기가 보내는 HTTPS 메시지를 수신하는 용도에 맞지 않습니다.

> 💡 **시험 꿀팁**: **다수의 외부 디바이스가 보내는 HTTPS 메시지를 고가용성으로 수신·처리하고 결과를 조회 가능하게 저장**해야 한다면 **API Gateway + Lambda + DynamoDB** 조합이 표준 정답입니다.

## QUESTION 324

**문제**: 회사가 온프레미스 파일 스토리지 볼륨에 대한 재해 복구 계획을 구현하려 한다. 이 볼륨은 로컬 스토리지 서버의 iSCSI 장치에서 마운트되며 수백 테라바이트의 데이터를 보유한다. 회사는 최종 사용자가 대기 시간 없이 온프레미스 시스템의 모든 파일 유형에 즉시 접근할 수 있기를 원하며, 기존 인프라 변경은 최소화하고자 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. 온프레미스 가상 머신으로 Amazon S3 파일 게이트웨이를 프로비저닝하고 로컬 캐시를 10TB로 설정하며, NFS 프로토콜로 파일에 접근하도록 기존 애플리케이션을 수정한다(iSCSI 대신 NFS를 쓰도록 애플리케이션을 바꿔야 해 "최소 변경" 요구에 위배되고, 10TB 캐시만으로는 수백 TB 전체에 대한 무지연 접근을 보장할 수 없음).
- B. AWS Storage Gateway 테이프 게이트웨이를 프로비저닝하고 데이터 백업 솔루션으로 가상 테이프 라이브러리에 백업한다(테이프 게이트웨이는 장기 아카이브 백업용으로, 최종 사용자가 파일에 실시간으로 즉시 접근하는 운영 스토리지 용도가 아님).
- C. AWS Storage Gateway 볼륨 게이트웨이의 캐시 볼륨을 프로비저닝하고 로컬 캐시를 10TB로 설정한 뒤, iSCSI로 기존 파일 서버에 마운트해 모든 파일을 복사한다(캐시 볼륨은 자주 쓰는 데이터만 로컬에 캐싱하고 나머지는 S3에서 가져오므로, 전체 데이터에 대한 "지연 없는 즉시 접근" 요구를 충족하지 못함).
- D. **기존 파일 스토리지 볼륨과 동일한 용량으로 AWS Storage Gateway 볼륨 게이트웨이의 저장 볼륨(Stored Volume)을 프로비저닝하고, iSCSI로 기존 파일 서버에 마운트해 모든 파일을 복사한다. 스토리지 볼륨의 예약된 스냅샷을 구성하고, 재해 발생 시 스냅샷을 EBS 볼륨으로 복원해 EC2 인스턴스에 연결한다.**

**정답: D**

**해설**
**볼륨 게이트웨이의 저장 볼륨(Stored Volume)**은 전체 데이터 세트를 온프레미스 로컬 스토리지에 그대로 유지하면서, 동시에 그 데이터를 Amazon S3에 비동기적으로 예약 스냅샷 형태로 백업합니다. 이렇게 하면 최종 사용자는 기존과 동일하게 iSCSI로 온프레미스에서 모든 파일에 대기 시간 없이 접근할 수 있고, 애플리케이션이나 프로토콜 변경도 필요 없으며, 재해 발생 시에는 S3에 저장된 스냅샷을 EBS 볼륨으로 복원해 EC2에서 복구할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: NFS로 접근 방식 자체를 바꿔야 해 애플리케이션 수정이 불가피하고, 10TB 캐시만으로는 수백 TB 전체 데이터에 대한 무지연 접근을 보장할 수 없습니다.
- B: 테이프 게이트웨이는 백업·아카이브 목적의 가상 테이프 라이브러리로, 실시간 파일 접근용 운영 스토리지로는 적합하지 않습니다.
- C: 캐시 볼륨은 데이터 대부분을 S3에 두고 일부만 로컬에 캐싱하는 구조라, 캐시에 없는 파일에 접근할 때 지연이 발생해 요구 사항에 맞지 않습니다.

> 💡 **시험 꿀팁**: **전체 데이터에 대한 온프레미스 무지연 접근을 유지하면서 S3로 백업**해야 한다면 **볼륨 게이트웨이의 저장 볼륨(Stored Volume)**, 반대로 자주 쓰는 데이터만 로컬에 캐싱해도 된다면 **캐시 볼륨(Cached Volume)**이 정답이라는 차이를 기억하세요.

## QUESTION 325

> 💡 **시험 꿀팁**: **Cognito 인증 사용자가 AWS 리소스에 접근하지 못하는 문제**는 대부분 **자격 증명 풀에 연결된 IAM 역할의 권한 부족**이 원인이며, 이 역할을 수정하는 것이 표준 정답입니다.

## QUESTION 326

**문제**: 이미지 호스팅 회사가 대용량 자산을 Amazon S3 Standard 버킷에 멀티파트 업로드로 병렬 업로드하며, 동일 객체가 재업로드되면 덮어쓴다. 업로드 후 처음 30일 동안은 자주 접근하지만, 30일 이후에는 접근 빈도가 줄어들면서도 객체별 접근 패턴이 일정하지 않다. 저장된 자산의 고가용성과 복원력을 유지하면서 S3 스토리지 비용을 최적화하려면 어떤 조합을 권장해야 하는가? (2개 선택)

**보기**
- A. **30일 후 자산을 S3 Intelligent-Tiering으로 이동한다.**
- B. **불완전한 멀티파트 업로드를 정리하도록 S3 수명 주기 정책을 구성한다.**

- E. 30일 후 자산을 S3 One Zone-IA로 이동한다(단일 가용 영역에만 저장되어 "고가용성 유지"라는 요구 사항 자체를 위반하며, 접근 패턴이 불규칙할 때 검색 비용 부담도 커짐).

**해설**
**S3 Intelligent-Tiering**은 접근 빈도를 자동으로 모니터링해 가장 비용 효율적인 계층으로 객체를 이동시키는 스토리지 클래스로, 접근 패턴을 예측할 수 없는 이번 시나리오에 정확히 들어맞으며 검색 비용이나 성능 저하 없이 고가용성과 복원력을 그대로 유지합니다. 또한 멀티파트 업로드를 병렬로 사용하고 있으므로, 중단되거나 완료되지 않은 멀티파트 업로드 조각이 남아 불필요한 스토리지 비용을 유발할 수 있습니다. **수명 주기 정책으로 불완전한 멀티파트 업로드를 자동 정리**하면 이런 낭비 비용을 없앨 수 있습니다.

- D: Standard-IA는 접근 빈도가 낮고 예측 가능한 데이터에 적합하며, 이번처럼 접근 패턴이 일정하지 않은 경우 검색 비용이 누적되어 비용이 오히려 늘어날 수 있습니다.
- E: One Zone-IA는 단일 AZ에만 저장되어 고가용성 요구 사항을 충족하지 못하며, IA 계열과 동일하게 불규칙한 접근 시 검색 비용 부담이 큽니다.

> 💡 **시험 꿀팁**: **접근 패턴을 예측할 수 없는 데이터의 비용 최적화**에는 **S3 Intelligent-Tiering**이 표준 정답이며, **멀티파트 업로드를 사용하는 환경**에서는 항상 **불완전한 멀티파트 업로드 정리 수명 주기 규칙**을 함께 고려해야 합니다.

**문제**: 솔루션 설계자가 매우 민감한 데이터를 다루며 프라이빗 서브넷에서 실행되는 EC2 인스턴스를 보호해야 한다. 회사 정책상 이 인스턴스는 인터넷의 승인된 타사 소프트웨어 리포지토리 URL에만 접근해 제품 업데이트를 받을 수 있어야 하며, 그 외 모든 인터넷 트래픽은 차단되어야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. **아웃바운드 트래픽을 AWS Network Firewall로 라우팅하도록 프라이빗 서브넷의 라우팅 테이블을 업데이트하고, 도메인 목록 규칙 그룹을 구성한다.**
- B. AWS WAF 웹 ACL을 설정하고 소스/대상 IP 주소 범위 기반의 사용자 지정 규칙으로 트래픽을 필터링한다(WAF는 인바운드 웹 트래픽을 검사하는 서비스이며, EC2의 아웃바운드 인터넷 트래픽을 도메인 단위로 제어하는 용도가 아님).
- C. 엄격한 인바운드 보안 그룹 규칙을 구현하고, URL을 지정해 승인된 리포지토리로만 나가는 아웃바운드 규칙을 구성한다(보안 그룹은 IP/CIDR와 포트 기반으로만 동작하며 URL·도메인 단위 필터링을 지원하지 않음).

- B: AWS WAF는 웹 애플리케이션으로 들어오는 인바운드 HTTP(S) 요청을 필터링하는 서비스로, EC2의 아웃바운드 트래픽을 도메인 기준으로 제어하지 못합니다.
- C: 보안 그룹은 IP 주소와 포트 기반의 상태 저장 방화벽으로 URL이나 도메인 이름을 직접 지정할 수 없어 요구 사항을 구현할 수 없습니다.
- D: ALB는 인바운드 트래픽을 대상 그룹에 분산하는 서비스이며, 인스턴스에서 나가는 아웃바운드 인터넷 접속을 중계·필터링하는 용도로 사용되지 않습니다.

> 💡 **시험 꿀팁**: **특정 도메인(URL)으로만 아웃바운드를 허용하고 나머지는 차단**해야 한다면 **AWS Network Firewall의 도메인 목록 규칙**이 표준 정답입니다(보안 그룹/WAF는 도메인 기반 필터링을 지원하지 않는다는 점을 기억하세요).

## QUESTION 328

**보기**
- A. 동적 콘텐츠에 CloudFront 배포를 추가하고, 트래픽 증가에 대응해 EC2 인스턴스 수를 늘린다(동적 콘텐츠는 CloudFront 캐싱의 효과가 제한적이며, 수동으로 인스턴스 수를 늘리는 방식은 급격한 트래픽 폭증에 즉각 대응하지 못함).
- B. 정적 콘텐츠에 CloudFront 배포를 추가하고, Auto Scaling 그룹에 EC2 인스턴스를 배치해 네트워크 트래픽 기준으로 새 인스턴스를 시작한다(오토스케일링은 반응형이라 스케일 아웃이 완료되기 전 폭증 구간에서 요청이 유실될 위험이 남아 있어 "모든 요청의 성공적 처리"를 보장하지 못함).
- C. 동적 콘텐츠에 CloudFront 배포를 추가하고, ALB 앞에 ElastiCache 인스턴스를 두어 API가 처리할 트래픽을 줄인다(판매 요청 생성과 같은 쓰기 위주의 트랜잭션은 캐싱으로 처리량을 줄이기 어려워 이 시나리오에 맞지 않음).

**왜 다른 보기는 오답인가**
- A: 동적 콘텐츠는 캐시 적중률이 낮아 CloudFront의 효과가 제한적이고, 수동 인스턴스 증설은 급격한 스파이크에 실시간으로 대응하기 어렵습니다.
- B: 트래픽 기반 오토스케일링은 스케일 아웃까지 지연이 있어 그 사이에 발생하는 요청이 처리되지 못하고 실패할 위험이 있습니다.
- C: ElastiCache는 읽기 위주 데이터의 조회 부하를 줄이는 데 효과적이며, 판매 주문 생성처럼 매번 새로운 쓰기가 발생하는 요청 처리량을 줄이는 데는 적합하지 않습니다.

> 💡 **시험 꿀팁**: **트래픽 폭증 시 모든 요청의 유실 없는 처리**가 관건이라면 **SQS로 요청을 버퍼링해 백엔드가 자체 속도로 소비**하게 하는 패턴이 표준 정답입니다.

**문제**: 보안 감사 결과 Amazon EC2 인스턴스가 정기적으로 패치되지 않는 것으로 나타났다. 솔루션 설계자는 대규모 EC2 인스턴스 전체에 대해 정기적인 보안 스캔을 수행하고, 정기적으로 패치를 적용하며, 각 인스턴스의 패치 상태 보고서를 제공하는 솔루션을 마련해야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. Amazon Macie를 설정해 EC2 인스턴스의 소프트웨어 취약점을 스캔하고, 각 EC2 인스턴스에서 cron 작업으로 정기 패치를 수행한다(Macie는 S3의 민감 데이터를 탐지하는 서비스로 EC2 취약점 스캔 기능이 없으며, cron 기반 개별 패치는 중앙화된 보고서를 제공하지 못함).
- B. Amazon GuardDuty를 활성화해 소프트웨어 취약점을 스캔하도록 구성하고, Systems Manager Session Manager로 정기 패치를 수행한다(GuardDuty는 로그 기반 위협 탐지 서비스로 소프트웨어 취약점 스캔 기능이 없으며, Session Manager는 원격 셸 접속 도구일 뿐 패치 관리·보고 기능을 제공하지 않음).
- C. Amazon Detective를 설정해 소프트웨어 취약점을 스캔하고, EventBridge 예약 규칙으로 정기 패치를 수행한다(Detective는 보안 사고 발생 후 근본 원인을 분석하는 조사 도구로 취약점 스캔 기능이 없으며, EventBridge 규칙만으로는 패치 적용과 상태 보고가 이루어지지 않음).
- D. **계정에서 Amazon Inspector를 활성화해 EC2 인스턴스의 소프트웨어 취약점을 스캔하도록 구성하고, AWS Systems Manager Patch Manager로 정기적인 일정에 따라 인스턴스를 패치한다.**

**정답: D**

**해설**
**Amazon Inspector**는 EC2 인스턴스와 컨테이너 이미지의 소프트웨어 취약점 및 네트워크 노출을 자동으로 지속 스캔하는 서비스이며, **AWS Systems Manager Patch Manager**는 정의된 패치 기준선과 유지 관리 기간에 따라 대규모 인스턴스 플릿에 패치를 자동 적용하고 패치 준수 상태 보고서를 제공합니다. 두 서비스를 결합하면 정기 취약점 스캔, 자동 패치, 상태 보고라는 세 가지 요구 사항을 모두 관리형 서비스로 충족할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Macie는 S3에 저장된 민감 데이터를 식별·분류하는 서비스로 EC2 취약점 스캔과는 무관하며, cron 기반 개별 패치는 중앙 집중적인 상태 보고를 제공하지 못합니다.
- B: GuardDuty는 CloudTrail·VPC 흐름 로그 등을 분석해 이상 행위를 탐지하는 위협 탐지 서비스이지 소프트웨어 취약점 스캐너가 아니며, Session Manager는 패치 관리 기능이 없습니다.
- C: Detective는 이미 발생한 보안 이벤트의 근본 원인을 시각적으로 분석하는 도구로 사전 취약점 스캔 기능이 없으며, EventBridge 규칙만으로는 실제 패치 적용과 준수 보고가 이루어지지 않습니다.

> 💡 **시험 꿀팁**: **EC2 취약점 스캔은 Amazon Inspector, 정기 패치 적용과 준수 보고는 Systems Manager Patch Manager**라는 조합을 기억해 두면 이런 유형의 문제에 바로 대응할 수 있습니다.

## QUESTION 330

**문제**: 회사가 Amazon RDS DB 인스턴스에 데이터를 저장할 계획이며, 미사용(저장) 데이터를 암호화해야 한다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. **AWS KMS에서 키를 생성하고, DB 인스턴스에 대해 암호화를 활성화한다.**
- B. 암호화 키를 생성해 AWS Secrets Manager에 저장하고, 이 키로 DB 인스턴스를 암호화한다(Secrets Manager는 암호·자격 증명 등의 시크릿을 안전하게 저장·교체하는 서비스이며, RDS 저장 데이터 암호화에 사용하는 키 관리 서비스가 아님).
- C. AWS Certificate Manager에서 인증서를 생성해 DB 인스턴스에서 SSL/TLS를 활성화한다(SSL/TLS는 클라이언트와 DB 간 전송 중 암호화를 제공할 뿐 저장 데이터 자체를 암호화하지 않음).
- D. IAM에서 인증서를 생성해 DB 인스턴스에서 SSL/TLS를 활성화한다(IAM은 인증서 발급 기능을 제공하지 않으며, SSL/TLS 역시 전송 중 암호화이지 저장 시 암호화가 아님).

**정답: A**

**해설**
Amazon RDS의 저장 데이터 암호화는 **AWS KMS**와 통합되어 동작합니다. KMS에서 키를 생성(또는 AWS 관리형 키 사용)한 뒤 DB 인스턴스 생성 시 암호화를 활성화하면, RDS는 해당 키로 기본 스토리지뿐 아니라 자동 백업, 읽기 전용 복제본, 스냅샷까지 모두 암호화합니다. 이는 미사용 데이터 암호화 요구 사항을 충족하는 표준적이고 가장 간단한 방법입니다.

**왜 다른 보기는 오답인가**
- B: Secrets Manager는 데이터베이스 자격 증명이나 API 키 같은 시크릿을 저장·순환하는 서비스로, RDS 스토리지 암호화에 사용되는 키 관리 메커니즘이 아닙니다.
- C: ACM 인증서로 활성화하는 SSL/TLS는 클라이언트-DB 간 통신 구간을 암호화하는 전송 중 암호화이며, 디스크에 저장된 데이터 자체는 암호화하지 않습니다.
- D: IAM은 인증서 발급 서비스가 아니며(그 역할은 ACM의 몫), 설령 인증서를 적용해도 SSL/TLS는 여전히 전송 중 암호화에 해당해 저장 데이터 암호화 요구를 충족하지 못합니다.

> 💡 **시험 꿀팁**: **RDS의 "미사용(저장) 데이터 암호화"** 요구에는 **AWS KMS 키 기반의 DB 인스턴스 암호화 활성화**가 표준 정답이며, SSL/TLS는 전송 중 암호화라는 별개의 개념임을 구분해야 합니다.

## QUESTION 331

**문제**: 회사가 30일 이내에 데이터 센터에서 AWS 클라우드로 20TB의 데이터를 마이그레이션해야 한다. 회사의 네트워크 대역폭은 15Mbps로 제한되며 사용률이 70%를 초과할 수 없다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. **AWS Snowball을 사용한다.**
- B. AWS DataSync를 사용한다(DataSync 역시 기존 네트워크 회선을 통해 데이터를 전송하므로 15Mbps×70%의 제한된 대역폭 안에서는 20TB를 30일 내에 옮기기 사실상 불가능).
- C. 안전한 VPN 연결을 사용한다(VPN도 결국 동일한 제한된 네트워크 대역폭을 사용하는 방식이라 전송 속도 문제를 해결하지 못함).

가용 대역폭(15Mbps × 70% = 10.5Mbps)으로 20TB를 전송하면 이론적으로 수개월이 걸려 30일이라는 기한을 지킬 수 없습니다. **AWS Snowball**은 물리적 디바이스에 데이터를 적재해 오프라인으로 운송하는 방식이므로 제한된 네트워크 대역폭과 무관하게 대량의 데이터를 정해진 기한 내에 안전하게 옮길 수 있어 이 시나리오에 가장 적합합니다.

**왜 다른 보기는 오답인가**
- B: DataSync는 네트워크를 통해 데이터를 전송하는 서비스로, 제한된 대역폭 환경에서는 마찬가지로 기한 내 전송이 어렵습니다.
- C: VPN 연결도 결국 동일한 제한된 회선 대역폭을 사용하므로 전송 속도 문제 자체를 해결하지 못합니다.
- D: Transfer Acceleration은 인터넷 경로를 최적화해 업로드 속도를 높이는 기능이지만, 클라이언트가 내보낼 수 있는 물리적 대역폭 상한(10.5Mbps)을 초과할 수는 없습니다.

> 💡 **시험 꿀팁**: **제한된 네트워크 대역폭으로 대용량 데이터를 정해진 기한 내에 옮겨야 한다**는 조건이 나오면, 대역폭으로 계산했을 때 기한을 못 맞춘다는 것을 확인한 뒤 **AWS Snowball(오프라인 전송)**을 선택하는 것이 표준 패턴입니다.

## QUESTION 332

**문제**: 회사가 직원들에게 기밀 및 민감한 파일에 대한 안전한 접근을 제공해야 하며, 권한이 있는 사용자만 파일에 접근하고 파일이 직원 장치에 안전하게 다운로드되어야 한다. 파일은 온프레미스 Windows 파일 서버에 저장되어 있지만, 원격 사용량 증가로 파일 서버의 용량이 부족한 상황이다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. 파일 서버를 퍼블릭 서브넷의 EC2 인스턴스로 마이그레이션하고, 인바운드 트래픽을 직원 IP 주소로 제한하도록 보안 그룹을 구성한다(퍼블릭 서브넷 배치는 불필요하게 노출 표면을 늘리며, 원격 근무자의 IP는 유동적인 경우가 많아 IP 기반 제한만으로는 안전하고 유연한 접근 제어가 어려움).
- B. **파일을 Amazon FSx for Windows File Server 파일 시스템으로 마이그레이션하고, 온프레미스 Active Directory와 통합한 뒤 AWS Client VPN을 구성한다.**
- C. 파일을 Amazon S3로 마이그레이션하고 프라이빗 VPC 엔드포인트를 생성한 뒤, 다운로드를 허용하는 서명된 URL을 만든다(S3로 옮기면 기존 Windows 파일 서버의 NTFS 권한 체계와 SMB 기반 워크플로가 그대로 유지되지 않아 애플리케이션·운영 방식의 큰 변경이 필요함).
- D. 파일을 Amazon S3로 마이그레이션하고 퍼블릭 VPC 엔드포인트를 생성한 뒤, 직원이 IAM Identity Center로 로그인하도록 허용한다(퍼블릭 엔드포인트 사용은 "안전한 접근"이라는 요구에 부합하지 않으며, 마찬가지로 기존 파일 서버 체계와의 정합성이 떨어짐).

**정답: B**

**해설**
**Amazon FSx for Windows File Server**는 완전관리형 Windows 파일 시스템으로, 온프레미스 **Active Directory**와 통합해 기존과 동일한 NTFS 권한 및 사용자/그룹 기반 접근 제어를 그대로 유지할 수 있습니다. 여기에 **AWS Client VPN**을 구성하면 원격 직원이 안전한 암호화 터널을 통해 파일 시스템에 접속해 권한이 있는 파일만 안전하게 다운로드할 수 있으며, 온프레미스 서버의 용량 문제도 클라우드로 이전함으로써 해결됩니다.

**왜 다른 보기는 오답인가**
- A: 파일 서버를 퍼블릭 서브넷에 두는 것은 불필요하게 공격 표면을 넓히며, IP 기반 접근 제한은 재택·이동 근무 환경에서 IP가 자주 바뀌는 직원에게는 실용적이지 않습니다.
- C: S3로 이전하면 기존 Windows 파일 서버의 SMB 프로토콜과 NTFS 세밀한 권한 구조를 유지할 수 없어, 애플리케이션과 운영 절차 전반의 재설계가 필요합니다.
- D: 퍼블릭 VPC 엔드포인트는 트래픽을 인터넷에 노출시킬 수 있어 "안전한 접근"이라는 핵심 요구 사항과 배치되며, S3 자체의 파일 서버 대체 한계도 동일하게 적용됩니다.

> 💡 **시험 꿀팁**: **온프레미스 Windows 파일 서버를 AD 권한 체계를 유지한 채 클라우드로 이전**해야 한다면 **Amazon FSx for Windows File Server + AD 통합 + Client VPN**이 표준 정답입니다.

## QUESTION 333

**문제**: 회사의 애플리케이션이 ALB 뒤에서 여러 가용 영역에 걸친 EC2 Auto Scaling 그룹으로 실행된다. 매월 1일 자정에 월말 재무 계산 일괄 처리가 실행되면 애플리케이션이 크게 느려지며, EC2 인스턴스의 CPU 사용률이 즉시 100%에 도달해 애플리케이션이 중단된다. 애플리케이션이 이 워크로드를 처리하고 다운타임을 방지하려면 솔루션 설계자는 무엇을 권장해야 하는가?

**보기**
- A. ALB 앞에 CloudFront 배포를 구성한다(CloudFront는 콘텐츠 캐싱·전송 최적화 서비스로, 배치 작업으로 인한 EC2의 CPU 연산 부하 문제 자체를 해결하지 못함).
- B. CPU 사용률 기반의 EC2 Auto Scaling 단순 조정 정책을 구성한다(배치가 시작되자마자 CPU가 즉시 100%에 도달하는 상황이라, 사용률 지표가 임계값을 넘은 뒤 반응하는 방식으로는 스케일 아웃이 완료되기 전에 이미 애플리케이션이 중단됨).
- C. **월별 일정을 기반으로 EC2 Auto Scaling 예약 조정 정책을 구성한다.**
- D. EC2 인스턴스에서 일부 워크로드를 덜어내도록 Amazon ElastiCache를 구성한다(월말 재무 계산과 같은 배치 연산 부하는 단순 캐싱으로 줄일 수 있는 성격의 작업이 아님).

**정답: C**

**해설**
배치 작업이 시작되는 시점(매월 1일 자정)이 이미 정확히 예측 가능하므로, **예약 조정 정책(Scheduled Scaling)**을 사용해 배치 실행 몇 시간 전에 미리 인스턴스 수를 늘려두면 CPU 사용률이 급증하기 전에 이미 충분한 컴퓨팅 용량을 확보할 수 있습니다. 배치가 끝난 뒤에는 다시 인스턴스 수를 줄여 비용도 절감할 수 있어, 다운타임 방지와 비용 효율을 동시에 만족합니다.

**왜 다른 보기는 오답인가**
- A: CloudFront는 정적/동적 콘텐츠 전송을 가속하는 서비스일 뿐, 서버 내부에서 발생하는 연산 집약적 배치 작업의 CPU 부하를 줄이지 못합니다.
- B: 사용률 기반 조정은 CPU가 임계값을 초과한 뒤에야 반응하는 사후 대응 방식이라, 이 시나리오처럼 부하가 순식간에 100%까지 치솟는 경우 스케일 아웃이 완료되기 전에 이미 서비스 중단이 발생합니다.
- D: ElastiCache는 반복 조회되는 데이터의 캐싱에 효과적이지만, 매월 실행되는 재무 계산 배치처럼 매번 새로운 연산이 필요한 워크로드의 부하를 줄여주지는 못합니다.

> 💡 **시험 꿀팁**: **예측 가능한 일정(정기 배치 등)으로 부하가 급증**하는 경우에는 반응형 조정이 아니라 **예약 조정 정책(Scheduled Scaling)으로 사전에 용량을 늘려두는 것**이 표준 정답입니다.

## QUESTION 334

**문제**: 회사가 고객이 온프레미스 Microsoft Active Directory를 사용해 Amazon S3에 저장된 파일을 다운로드할 수 있도록 하려 한다. 고객의 애플리케이션은 SFTP 클라이언트로 파일을 다운로드한다. 운영 오버헤드를 최소화하고 고객 애플리케이션을 변경하지 않으면서 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. **Amazon S3용 SFTP로 AWS Transfer Family를 설정하고, 통합된 Active Directory 인증을 구성한다.**
- B. 온프레미스 클라이언트를 S3와 동기화하도록 AWS DMS를 설정하고, 통합된 AD 인증을 구성한다(DMS는 데이터베이스 마이그레이션·복제 전용 서비스로, SFTP 프로토콜을 통한 파일 다운로드 인터페이스를 제공하지 않음).
- C. IAM Identity Center를 사용해 온프레미스 위치와 S3 위치 간 동기화를 하도록 AWS DataSync를 설정한다(DataSync는 스토리지 간 데이터 전송·동기화 도구로, 고객이 SFTP 클라이언트로 직접 접속해 다운로드할 수 있는 엔드포인트를 제공하지 않음).
- D. Windows EC2 인스턴스에 SFTP를 설정해 온프레미스 클라이언트를 S3와 연결하고 IAM을 통합한다(직접 EC2에서 SFTP 서버를 구축·패치·운영해야 해 "운영 오버헤드 최소화" 요구에 정면으로 위배됨).

**정답: A**

**해설**
**AWS Transfer Family**는 완전관리형 SFTP(FTPS/FTP 포함) 엔드포인트를 제공해 S3를 백엔드 스토리지로 그대로 사용하면서도, 고객의 SFTP 클라이언트 사용 방식을 전혀 바꿀 필요가 없습니다. 여기에 **온프레미스 Active Directory와의 통합 인증**을 구성하면 기존 AD 자격 증명으로 그대로 로그인해 파일을 다운로드할 수 있어, 서버 인프라를 직접 구축·운영하지 않고도 운영 오버헤드를 최소화하면서 요구 사항을 충족합니다.

**왜 다른 보기는 오답인가**
- B: AWS DMS는 관계형 데이터베이스 등의 마이그레이션·복제를 위한 서비스로, 고객에게 SFTP 인터페이스를 제공하는 기능이 없습니다.
- C: DataSync는 스토리지 시스템 간 대량 데이터 전송·동기화 도구이며, 최종 고객이 SFTP로 직접 접속해 파일을 내려받는 프런트엔드 역할을 하지 않습니다.
- D: EC2에 SFTP 서버를 직접 구축하면 운영체제 패치, 서버 관리, 고가용성 확보 등을 모두 직접 책임져야 해 운영 오버헤드가 오히려 커집니다.

> 💡 **시험 꿀팁**: **기존 SFTP 클라이언트를 바꾸지 않고 S3를 SFTP로 노출**해야 한다면 **AWS Transfer Family(SFTP) + AD 통합 인증**이 표준 정답입니다.

## QUESTION 335

**문제**: 회사에 수요가 갑자기 증가해 AMI로부터 대규모 EC2 인스턴스를 Auto Scaling 그룹에서 프로비저닝해야 한다. 회사는 최소한의 초기화 대기 시간을 제공하는 솔루션이 필요하다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. `aws ec2 register-image` 명령으로 스냅샷에서 AMI를 생성하고, AWS Step Functions로 Auto Scaling 그룹의 AMI를 교체한다(스냅샷에서 곧바로 생성한 볼륨은 최초 접근 시 블록을 S3에서 지연 로드(lazy-loading)하므로, 새 인스턴스 시작 초기에 I/O 지연이 발생해 "최소 초기화 대기 시간" 요구를 충족하지 못함).
- B. **스냅샷에서 Amazon EBS 빠른 스냅샷 복원(Fast Snapshot Restore)을 활성화하고, 이 스냅샷으로 AMI를 프로비저닝한 뒤 Auto Scaling 그룹의 AMI를 새 AMI로 교체한다.**
- C. Amazon Data Lifecycle Manager에서 AMI 생성을 활성화하고 수명 주기 규칙을 정의하며, Auto Scaling 그룹의 AMI를 수정하는 Lambda 함수를 만든다(DLM은 스냅샷/AMI 생성 자동화·수명 주기 관리 도구일 뿐, EBS 볼륨의 초기화 지연 문제 자체를 해결하지 않음).
- D. EventBridge로 AMI를 프로비저닝하는 AWS Backup 수명 주기 정책을 호출하고, Auto Scaling 그룹 용량 제한을 이벤트 소스로 구성한다(AWS Backup은 백업 관리 서비스로 이런 방식의 AMI 프로비저닝에 사용되지 않으며, 초기화 지연 문제도 해결하지 못하는 불필요하게 복잡한 구성).

**정답: B**

**해설**
새 EBS 볼륨을 스냅샷에서 생성하면 기본적으로 데이터 블록이 처음 접근될 때 S3에서 지연 로드되어 초기 I/O 성능이 저하됩니다. **EBS 빠른 스냅샷 복원**을 활성화하면 스냅샷의 모든 블록을 미리 초기화해 두어, 이 스냅샷으로 생성한 볼륨(및 AMI)은 최초 접근부터 완전한 성능을 제공합니다. 이렇게 준비된 AMI로 Auto Scaling 그룹을 교체하면 급증하는 수요에 맞춰 새 인스턴스가 초기화 지연 없이 빠르게 기동됩니다.

**왜 다른 보기는 오답인가**
- A: 빠른 스냅샷 복원 없이 생성한 AMI는 여전히 지연 로딩 문제를 겪어 신규 인스턴스의 초기 성능이 저하됩니다.
- C: DLM은 스냅샷과 AMI 생성·보존을 자동화하는 수명 주기 관리 기능으로, 볼륨 초기화 지연이라는 근본 문제와는 무관합니다.
- D: AWS Backup은 백업 데이터 관리에 특화된 서비스로 이런 용도의 AMI 프로비저닝에 적합하지 않으며, 구성도 불필요하게 복잡합니다.

> 💡 **시험 꿀팁**: **스냅샷 기반 AMI로 인스턴스를 빠르게 기동하면서 초기화 지연을 없애야** 한다면 **EBS 빠른 스냅샷 복원(Fast Snapshot Restore)**이 표준 정답입니다.

## QUESTION 336

**문제**: 회사가 Amazon Aurora MySQL DB 클러스터를 스토리지로 사용하는 다중 계층 웹 애플리케이션을 호스팅하며, 애플리케이션 계층은 EC2 인스턴스에서 실행된다. 회사의 IT 보안 지침에 따라 데이터베이스 자격 증명을 암호화하고 14일마다 교체해야 한다. 최소한의 운영 노력으로 이 요구 사항을 충족하려면 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. **새 AWS KMS 암호화 키를 생성한다. AWS Secrets Manager를 사용해 해당 KMS 키로 암호화된 새 시크릿을 적절한 자격 증명과 함께 생성하고, 이를 Aurora DB 클러스터와 연결한 뒤 14일 주기의 사용자 지정 순환 기간을 구성한다.**
- B. Systems Manager Parameter Store에 사용자 이름(문자열)과 암호(SecureString, KMS 암호화)를 위한 매개변수 두 개를 생성해 애플리케이션이 로드하도록 하고, 14일마다 암호를 교체하는 Lambda 함수를 직접 구현한다(Parameter Store에는 RDS/Aurora 자격 증명을 자동으로 교체하는 내장 기능이 없어 순환 로직을 직접 개발·유지해야 해 운영 부담이 큼).

- D. 자격 증명 파일을 KMS로 암호화된 S3 버킷에 저장하고 애플리케이션이 주기적으로 파일을 다운로드하도록 하며, 14일마다 자격 증명을 교체해 S3에 업로드하는 Lambda 함수를 구현한다(마찬가지로 자격 증명 배포·동기화·교체 로직을 모두 직접 구현·관리해야 해 운영 오버헤드가 큼).

**정답: A**

**해설**
**AWS Secrets Manager**는 Amazon Aurora(및 RDS)용 자격 증명 교체 기능을 기본 내장하고 있어, 시크릿을 KMS 키로 암호화해 저장하고 DB 클러스터와 연결한 뒤 원하는 순환 주기(이 경우 14일)만 지정하면 별도의 커스텀 Lambda 코드를 작성하지 않아도 자동으로 자격 증명이 교체됩니다. 이는 암호화와 정기 교체라는 두 요구 사항을 모두 최소한의 운영 노력으로 충족하는 방법입니다.

**왜 다른 보기는 오답인가**
- B: Parameter Store는 Secrets Manager와 달리 데이터베이스 자격 증명에 대한 자동 교체 기능을 제공하지 않아, 순환 로직을 담은 Lambda 함수를 직접 개발하고 유지 보수해야 합니다.
- C: EFS에 자격 증명 파일을 두고 Lambda로 직접 교체·배포하는 방식은 접근 제어, 동기화, 오류 처리 등을 모두 자체적으로 설계해야 하는 고비용 커스텀 솔루션입니다.
- D: S3에 자격 증명 파일을 두고 주기적으로 다운로드·교체하는 방식 역시 배포 및 교체 로직을 직접 구현·관리해야 하므로 운영 부담이 큽니다.

> 💡 **시험 꿀팁**: **DB 자격 증명의 암호화 저장 + 정기 자동 교체**가 필요하면, RDS/Aurora와의 **내장 자동 교체 기능을 제공하는 AWS Secrets Manager**가 최소 운영 노력의 표준 정답입니다.

## QUESTION 337

**문제**: 회사가 AWS에 배포한 웹 애플리케이션의 백엔드로 기본 DB 인스턴스와 5개의 읽기 전용 복제본을 둔 Amazon RDS for MySQL을 사용한다. 읽기 전용 복제본은 기본 DB 인스턴스보다 1초 이상 뒤처지면 안 되며, 데이터베이스는 정기적으로 예약된 저장 프로시저를 실행한다. 트래픽이 증가하면서 피크 부하 시간대에 복제본의 지연이 커지고 있다. 솔루션 설계자는 애플리케이션 코드 변경과 운영 오버헤드를 최소화하면서 복제 지연을 최대한 줄여야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. **데이터베이스를 Amazon Aurora MySQL로 마이그레이션한다. 읽기 전용 복제본을 Aurora 복제본으로 교체하고 Aurora Auto Scaling을 구성하며, 저장 프로시저를 Aurora MySQL 기본 함수로 대체한다.**
- B. 데이터베이스 앞에 Redis용 Amazon ElastiCache 클러스터를 배포하고, 애플리케이션이 쿼리 전에 캐시를 확인하도록 수정하며, 저장 프로시저를 AWS Lambda 함수로 대체한다(캐시 확인 로직 추가와 저장 프로시저의 Lambda 전환은 애플리케이션 코드를 대폭 수정해야 하는 작업으로 "코드 변경 최소화" 요구에 위배).
- C. 데이터베이스를 EC2 인스턴스에서 실행되는 MySQL로 마이그레이션하고, 모든 복제본 노드에 컴퓨팅 최적화 대형 인스턴스를 선택하며 저장 프로시저는 EC2 인스턴스에 그대로 유지한다(자체 관리형 MySQL로 전환하면 엔진 패치·백업·복제 구성까지 직접 운영해야 해 운영 오버헤드가 오히려 커지고, 복제 메커니즘 자체는 여전히 표준 MySQL 비동기 복제라 근본적인 지연 개선이 제한적).
- D. 데이터베이스를 Amazon DynamoDB로 마이그레이션하고, 필요한 처리량을 위해 많은 RCU를 프로비저닝하며 저장 프로시저를 DynamoDB 스트림으로 대체한다(관계형 스키마와 저장 프로시저 로직을 NoSQL 데이터 모델로 전면 재설계해야 하는 대규모 애플리케이션 변경이 불가피해 요구 사항에 정면으로 위배).

**정답: A**

**해설**
**Amazon Aurora MySQL**은 스토리지 계층에서 복제를 처리하는 구조 덕분에 기존 RDS for MySQL의 논리적 바이너리 로그 복제보다 훨씬 짧은 복제 지연을 제공합니다. 읽기 전용 복제본을 **Aurora 복제본**으로 바꾸고 **Aurora Auto Scaling**을 적용하면 피크 시간대에도 필요한 만큼 복제본을 자동으로 늘려 지연을 최소화할 수 있으며, MySQL 호환성 덕분에 저장 프로시저 로직 대부분을 Aurora MySQL 기본 함수로 손쉽게 대체할 수 있어 애플리케이션 코드 변경도 최소화됩니다.

**왜 다른 보기는 오답인가**
- B: 캐시 조회 로직 추가와 저장 프로시저를 Lambda로 전면 재작성하는 작업은 애플리케이션 코드를 대규모로 수정해야 해 요구 사항에 맞지 않습니다.
- C: 자체 관리형 EC2 MySQL로 옮기면 엔진 운영·복제 구성·패치를 모두 직접 책임져야 해 운영 오버헤드가 커지며, 복제 메커니즘 자체가 개선되지 않아 근본적인 지연 문제가 해결되지 않습니다.
- D: DynamoDB로의 전환은 데이터 모델과 저장 프로시저 로직을 완전히 새로 설계해야 하는 대규모 재작성을 요구해 코드 변경 최소화 요구와 정면으로 배치됩니다.

> 💡 **시험 꿀팁**: **RDS 읽기 복제본의 지연을 최소화하면서 코드 변경을 최소화**해야 한다면 **Amazon Aurora로의 마이그레이션(스토리지 계층 복제 + Aurora Auto Scaling)**이 표준 정답입니다.

## QUESTION 338

**문제**: 솔루션 설계자가 대용량 SaaS 플랫폼의 재해 복구 계획을 세워야 한다. 플랫폼의 모든 데이터는 Amazon Aurora MySQL DB 클러스터에 저장되며, DR 계획은 데이터를 보조 AWS 리전으로 복제해야 한다. 가장 비용 효율적으로 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. 보조 리전의 Aurora 클러스터에 MySQL 바이너리 로그 복제를 사용하고, 보조 리전에 Aurora 클러스터용 DB 인스턴스 1개를 프로비저닝한다(바이너리 로그 기반 복제는 Aurora의 네이티브 스토리지 계층 복제보다 관리가 번거롭고 지연도 더 커, Aurora가 기본 제공하는 글로벌 복제 기능을 활용하지 않는 비효율적인 방식).
- B. DB 클러스터에 대해 Aurora 글로벌 데이터베이스를 설정한 뒤, 설정이 끝나면 보조 리전의 DB 인스턴스를 제거한다(Aurora 글로벌 데이터베이스의 스토리지 기반 복제가 지속되려면 보조 리전에 최소 하나의 DB 인스턴스가 필요하며, 인스턴스를 제거하면 정상적인 복제·장애 조치 구조가 깨짐).
- C. AWS DMS로 데이터를 보조 리전의 Aurora 클러스터에 지속적으로 복제하고, 보조 리전의 DB 인스턴스를 제거한다(DMS 복제 역시 데이터를 받아 쓸 대상 DB 인스턴스가 있어야 동작하므로, 인스턴스를 제거하면 복제 자체가 성립하지 않음).
- D. **DB 클러스터에 대해 Aurora 글로벌 데이터베이스를 설정하고, 보조 리전에 최소 하나의 DB 인스턴스를 유지한다.**

**정답: D**

**해설**
**Aurora 글로벌 데이터베이스**는 기본 클러스터에서 보조 리전으로의 복제를 데이터베이스 엔진이 아닌 Aurora의 전용 스토리지 계층에서 처리하기 때문에, 일반적으로 1초 미만의 낮은 복제 지연을 제공하면서도 별도의 MySQL 바이너리 로그 복제 구성이나 관리가 필요 없습니다. 다만 이 스토리지 기반 복제 구조가 유지되고 장애 조치 시 곧바로 승격할 수 있으려면 **보조 리전에 최소 한 개의 DB 인스턴스**가 존재해야 하므로, 이를 유지하는 D가 가장 비용 효율적이면서도 올바르게 동작하는 DR 솔루션입니다.

**왜 다른 보기는 오답인가**
- A: 수동 바이너리 로그 복제는 Aurora가 기본 제공하는 저지연 스토리지 복제를 활용하지 않아 설정·운영 부담이 더 크고 복제 지연도 상대적으로 큽니다.
- B: 보조 리전의 DB 인스턴스를 제거하면 Aurora 글로벌 데이터베이스의 복제 및 장애 조치 메커니즘이 정상적으로 동작하지 않습니다.
- C: DMS 복제도 데이터를 기록할 대상 DB 인스턴스가 필요하므로, 인스턴스를 제거하면 복제 자체가 이루어질 수 없습니다.

> 💡 **시험 꿀팁**: **Aurora 클러스터의 리전 간 DR 복제**에는 **Aurora 글로벌 데이터베이스**가 표준 정답이며, 이때 **보조 리전에 최소 하나의 DB 인스턴스를 반드시 유지**해야 한다는 점을 함께 기억하세요.

## QUESTION 339

**문제**: 회사에 Amazon RDS MySQL DB 인스턴스에서 정보를 조회하는 사용자 지정 애플리케이션이 있으며, 자격 증명이 코드에 내장되어 있다. 경영진은 최소한의 프로그래밍 노력으로 애플리케이션을 더 안전하게 만들라고 요청했다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. AWS KMS로 키를 생성하고, 애플리케이션이 KMS에서 데이터베이스 자격 증명을 로드하도록 구성하며 자동 키 순환을 활성화한다(KMS는 암호화 키 관리 서비스로 임의의 애플리케이션 자격 증명을 저장·조회하는 용도가 아니며, 키 자동 순환이 DB 사용자 자격 증명 교체를 의미하지도 않음).
- B. RDS for MySQL 데이터베이스에 애플리케이션용 자격 증명을 생성해 Secrets Manager에 저장하고, 애플리케이션이 이를 로드하도록 구성한 뒤 자격 증명을 교체하는 Lambda 함수를 직접 생성한다(Secrets Manager는 RDS MySQL용 자격 증명 교체 기능을 이미 내장 제공하므로, 커스텀 Lambda를 직접 작성하는 것은 불필요한 추가 개발 작업).
- C. **RDS for MySQL 데이터베이스에 애플리케이션용 자격 증명을 생성해 Secrets Manager에 저장하고, 애플리케이션이 이를 로드하도록 구성한 뒤 Secrets Manager의 기능을 이용해 RDS for MySQL 자격 증명 교체 일정을 설정한다.**
- D. RDS for MySQL 데이터베이스에 애플리케이션용 자격 증명을 생성해 Systems Manager Parameter Store에 저장하고, 애플리케이션이 이를 로드하도록 구성한 뒤 Parameter Store로 자격 증명 교체 일정을 설정한다(Parameter Store에는 RDS 자격 증명을 자동으로 교체하는 내장 기능이 없어, 교체 로직을 직접 개발해야 해 프로그래밍 노력이 늘어남).

**정답: C**

**해설**
**AWS Secrets Manager**는 Amazon RDS(MySQL 포함)와 사전 통합되어 있어, 자격 증명을 시크릿으로 저장하고 애플리케이션이 SDK를 통해 하드코딩 없이 이를 조회하도록 바꾸는 것만으로도 보안이 크게 개선됩니다. 게다가 RDS용으로 사전 구축된 교체 템플릿(Lambda 함수 자동 생성)을 이용해 자격 증명 교체 일정을 설정할 수 있어, 별도로 순환 로직을 직접 개발할 필요 없이 최소한의 프로그래밍 노력으로 요구 사항을 충족합니다.

**왜 다른 보기는 오답인가**
- A: KMS는 암호화 키 자체를 관리하는 서비스이며, 애플리케이션의 데이터베이스 자격 증명을 저장·조회하거나 DB 사용자 계정을 교체하는 기능을 제공하지 않습니다.
- B: Secrets Manager는 RDS용 자격 증명 교체 기능을 이미 내장 제공하므로, 별도의 커스텀 Lambda 함수를 직접 작성하는 것은 "최소한의 프로그래밍 노력"이라는 요구에 불필요하게 반하는 추가 작업입니다.
- D: Parameter Store는 SecureString으로 안전하게 값을 저장할 수는 있지만 RDS 자격 증명을 자동으로 교체하는 내장 기능이 없어, 이를 구현하려면 별도의 개발이 필요합니다.

> 💡 **시험 꿀팁**: **DB 자격 증명 보안 강화 + 최소한의 개발 노력**이라는 조합에는 **RDS/Aurora용 내장 자동 교체 기능을 갖춘 AWS Secrets Manager**가 표준 정답입니다.

## QUESTION 340

**문제**: 미디어 회사가 AWS에서 웹사이트를 호스팅한다. 웹사이트 애플리케이션 아키텍처는 ALB 뒤의 EC2 인스턴스 플릿과 Amazon Aurora에서 호스팅되는 데이터베이스로 구성된다. 회사의 사이버 보안 팀은 애플리케이션이 SQL 주입에 취약하다고 보고했다. 회사는 이 문제를 어떻게 해결해야 하는가?

**보기**
- A. **ALB 앞에서 AWS WAF를 사용한다. 적절한 웹 ACL을 AWS WAF와 연결한다.**
- B. SQL 주입에 고정 응답으로 대응하는 ALB 리스너 규칙을 생성한다(ALB 리스너 규칙은 경로·호스트·헤더 등의 조건으로 라우팅을 결정할 뿐 SQL 주입 패턴을 탐지하는 기능이 없음).
- C. AWS Shield Advanced에 가입해 모든 SQL 주입 시도를 자동으로 차단한다(Shield Advanced는 DDoS 공격 방어에 특화된 서비스로 애플리케이션 계층의 SQL 인젝션 같은 공격 페이로드를 탐지·차단하지 않음).
- D. Amazon Inspector를 설정해 모든 SQL 주입 시도를 자동으로 차단한다(Inspector는 EC2·컨테이너·Lambda의 소프트웨어 취약점을 스캔하는 평가 도구로, 실시간 웹 요청의 공격 페이로드를 차단하는 기능이 없음).

**정답: A**

**해설**
**AWS WAF**는 웹 애플리케이션 앞단에서 HTTP(S) 요청을 검사해 SQL 인젝션, 크로스 사이트 스크립팅 등 알려진 웹 공격 패턴을 탐지·차단하는 웹 애플리케이션 방화벽입니다. ALB에 WAF를 연결하고 SQL 인젝션을 탐지하는 관리형 규칙 그룹이 포함된 **웹 ACL**을 적용하면, 악성 쿼리가 담긴 요청이 EC2 애플리케이션 계층에 도달하기 전에 차단되어 SQL 주입 취약점을 효과적으로 완화할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: ALB의 리스너 규칙은 요청 경로나 헤더 등의 조건에 따라 트래픽을 라우팅하거나 고정 응답을 반환하는 기능일 뿐, 요청 본문의 SQL 인젝션 패턴을 분석하는 보안 검사 기능이 없습니다.
- C: Shield Advanced는 네트워크/전송 계층 및 일부 애플리케이션 계층의 DDoS 공격으로부터 보호하는 서비스로, SQL 인젝션 같은 애플리케이션 로직을 노린 공격은 탐지 대상이 아닙니다.
- D: Amazon Inspector는 인스턴스나 컨테이너 이미지의 알려진 소프트웨어 취약점을 스캔하는 사전 평가 도구이며, 실시간으로 들어오는 웹 요청의 공격 페이로드를 차단하는 기능은 제공하지 않습니다.

> 💡 **시험 꿀팁**: **애플리케이션이 SQL 인젝션 같은 웹 공격에 취약**하다는 문제에는 **ALB/CloudFront 앞단에 AWS WAF와 웹 ACL을 배치**하는 것이 표준 정답입니다.
