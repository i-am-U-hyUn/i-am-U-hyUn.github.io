## QUESTION 501

**문제**: 회사가 미션 크리티컬 애플리케이션을 us-east-1의 Aurora MySQL 클러스터에서 운영 중이며, 리전 전체 장애 발생 시에도 RPO 1초 미만, RTO 1분 이내로 다른 리전에서 서비스를 복구해야 하는 엄격한 요구사항이 있다. 일반적인 크로스 리전 리드 리플리카는 비동기 복제 지연이 수 초를 넘어설 수 있어 이 요구사항을 충족하지 못할 위험이 있다. 솔루션은?

**보기**
- A. 표준 Aurora MySQL 크로스 리전 리드 리플리카를 생성해두고 장애 시 수동으로 승격(promotion)(일반 크로스 리전 리플리카는 비동기 복제로 인해 지연이 수 초 이상 발생할 수 있어 1초 미만의 엄격한 RPO를 안정적으로 보장하기 어려움).
- B. **Amazon Aurora Global Database를 사용해, 전용 인프라 기반의 스토리지 레벨 복제로 리전 간 복제 지연을 일반적으로 1초 미만으로 유지하고, 리전 장애 시 보조 리전을 수 분 이내에 쓰기 가능한 프라이머리로 승격.**
- C. AWS DMS로 지속적 복제(ongoing replication) 작업을 구성해 다른 리전의 별도 Aurora 클러스터에 동기화(DMS 기반 지속 복제도 가능하지만 별도의 복제 인스턴스 운영이 필요하고 Aurora Global Database의 스토리지 레벨 복제만큼 낮고 안정적인 지연을 보장하도록 설계되지 않음).
- D. 각 리전에 독립적인 Aurora 클러스터를 두고 애플리케이션 레벨에서 이중 쓰기(dual write)를 구현(애플리케이션 이중 쓰기는 두 클러스터 간 트랜잭션 일관성을 보장하기가 매우 어렵고 구현/운영 복잡도가 지나치게 높음).

**정답: B**

**해설**
**Amazon Aurora Global Database**는 하나의 프라이머리 리전과 최대 5개의 보조(secondary) 리전으로 구성되며, 일반적인 논리 복제가 아닌 **전용 인프라를 통한 스토리지 레벨 복제**를 사용해 리전 간 복제 지연을 통상 1초 미만으로 유지합니다. 리전 전체 장애가 발생하면 보조 리전 중 하나를 수 분 이내에 쓰기 가능한 프라이머리로 승격(managed planned failover 또는 unplanned failover)할 수 있어, 엄격한 RPO/RTO 요구사항을 가진 미션 크리티컬 워크로드의 표준 크로스 리전 DR 솔루션입니다.

**왜 다른 보기는 오답인가**
- A: 표준 크로스 리전 리드 리플리카는 비동기 복제 지연이 수 초 이상이 될 수 있어 1초 미만 RPO를 안정적으로 보장하지 못합니다.
- C: DMS 지속 복제는 가능한 대안이지만 별도 운영 부담이 크고 Aurora Global Database만큼 낮은 지연을 보장하지 않습니다.
- D: 애플리케이션 레벨 이중 쓰기는 트랜잭션 일관성 보장이 매우 어려운 고위험 접근입니다.

> 💡 **시험 꿀팁**: 크로스 리전으로 **RPO 1초 미만, RTO 분 단위**의 엄격한 DR 요구사항을 가진 Aurora 워크로드에는 **Aurora Global Database**가 표준 정답입니다.

## QUESTION 502

**문제**: 회사가 VPC 내부의 프라이빗 서브넷에 있는 EC2 인스턴스에서 S3 버킷에 자주 접근하는데, 현재는 NAT 게이트웨이를 경유해 인터넷을 통해 S3에 접근하고 있어 NAT 게이트웨이의 데이터 처리 비용이 상당히 발생하고 있다. 트래픽이 인터넷을 거치지 않고 AWS 네트워크 내부에서만 S3에 도달하도록 하면서 NAT 게이트웨이 비용도 절감하고 싶다. 솔루션은?

**보기**
- A. NAT 게이트웨이를 더 큰 인스턴스 유형으로 교체(NAT 게이트웨이는 인스턴스 유형 개념이 없고, 처리량에 따른 데이터 비용 구조 자체는 유형 교체로 해결되지 않음).
- B. 모든 프라이빗 서브넷 인스턴스에 퍼블릭 IP를 할당해 인터넷 게이트웨이로 직접 접근(퍼블릭 IP 할당은 보안 노출 위험을 높이고, 애초에 프라이빗 서브넷으로 설계한 목적에 반함).
- C. **VPC에 S3용 게이트웨이 VPC 엔드포인트(Gateway VPC Endpoint)를 생성해, 라우팅 테이블을 통해 S3로 향하는 트래픽이 NAT 게이트웨이나 인터넷을 거치지 않고 AWS 네트워크 내부에서 직접 S3에 도달하도록 구성(추가 비용 없이 NAT 데이터 처리 비용 절감).**
- D. S3 버킷을 VPC와 동일한 계정의 다른 리전으로 이전(리전 이전은 NAT 경유 여부나 비용 구조와 무관하며 문제의 핵심 요구사항을 해결하지 못함).

**정답: C**

**해설**
**S3용 게이트웨이 VPC 엔드포인트**는 VPC의 라우팅 테이블에 S3 프리픽스 목록(prefix list)을 대상으로 하는 경로를 추가해, 프라이빗 서브넷의 인스턴스가 인터넷 게이트웨이나 NAT 게이트웨이를 거치지 않고 **AWS 네트워크 내부 경로로 직접 S3에 접근**하도록 합니다. 게이트웨이 엔드포인트 자체는 시간당 요금이나 데이터 처리 요금이 없어, NAT 게이트웨이를 경유하던 S3 트래픽을 엔드포인트로 전환하면 NAT 데이터 처리 비용을 절감하면서 보안성도 향상시킬 수 있습니다.

**왜 다른 보기는 오답인가**
- A: NAT 게이트웨이는 인스턴스 유형 개념이 없으며 비용 구조 문제를 해결하지 못합니다.
- B: 퍼블릭 IP 할당은 보안 위험을 높이고 프라이빗 서브넷 설계 목적에 반합니다.
- D: 리전 이전은 문제의 핵심(NAT 경유 및 비용)과 무관합니다.

> 💡 **시험 꿀팁**: 프라이빗 서브넷에서 **NAT 게이트웨이 비용 없이 S3에 AWS 네트워크 내부로 직접 접근**하려면 **게이트웨이 VPC 엔드포인트**가 표준 정답입니다.

## QUESTION 503

**문제**: 회사가 여러 사업부(BU)가 공유하는 AWS 계정에서 리소스를 사용하는데, 각 사업부별로 실제 사용한 만큼 비용을 내부적으로 청구(chargeback)하고 싶다. 리소스에는 이미 비용 배분 태그(cost allocation tag)로 사업부명을 태깅해두었지만, 여러 태그 값과 서비스에 걸친 비용을 사업부 단위로 유연하게 그룹화해서 정기적으로 보고서를 받고 싶다. 솔루션은?

**보기**
- A. **AWS Cost Categories를 사용해 비용 배분 태그, 계정, 서비스 등 다양한 차원을 조합한 규칙으로 비용을 사업부 단위로 그룹화하고, Cost Explorer나 예산 보고서에서 이 카테고리 기준으로 지속적으로 조회.**
- B. 각 사업부마다 완전히 별도의 AWS 계정을 만들어 청구서 자체를 분리(계정 분리도 유효한 장기 전략이지만, 이미 태그로 구분된 공유 계정 환경에서 즉시 청구 그룹화를 원하는 요구에는 과도한 재구성이 필요).
- C. CloudTrail 로그를 분석해 API 호출 주체 기준으로 비용을 수동 추정(CloudTrail은 API 호출 이력을 기록할 뿐 실제 비용 데이터나 사업부별 그룹화 기능을 제공하지 않음).
- D. 모든 리소스 이름에 사업부명을 접두사로 붙이고 청구서를 수동으로 파싱(수동 파싱은 확장성이 없고 비용 배분 태그라는 기존 자산을 활용하지 못함).

**정답: A**

**해설**
**AWS Cost Categories**는 비용 배분 태그, 연결된 계정, 서비스, 청구 항목 등 다양한 차원을 규칙으로 조합해 비용과 사용량 데이터를 원하는 비즈니스 단위(예: 사업부, 프로젝트, 팀)로 매핑하는 기능입니다. 한 번 규칙을 정의해두면 Cost Explorer, 예산(Budgets), 비용 및 사용 보고서(CUR)에서 이 카테고리를 하나의 그룹화 차원으로 지속적으로 활용할 수 있어, 이미 태깅된 공유 계정 환경에서도 유연하게 사업부별 chargeback 보고서를 생성할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 계정 완전 분리는 유효한 전략이지만 이 문제의 즉각적인 요구(기존 태그 활용한 유연한 그룹화)에는 과도합니다.
- C: CloudTrail은 비용 데이터를 제공하지 않습니다.
- D: 수동 파싱은 확장성이 없고 비효율적입니다.

> 💡 **시험 꿀팁**: 비용 배분 태그 등 여러 차원을 조합해 **비즈니스 단위로 비용을 그룹화하고 지속적으로 chargeback 보고**하려면 **AWS Cost Categories**가 표준 정답입니다.

## QUESTION 504

**문제**: 회사가 50개의 VPC(여러 계정에 분산)를 운영하며, 이들 간에 서로 통신이 필요한 경우가 늘어나면서 VPC 피어링 연결 수가 기하급수적으로 증가해 관리가 매우 복잡해졌다(피어링은 전이적 라우팅을 지원하지 않아 완전 메시 구조 필요). 온프레미스 데이터센터와의 Direct Connect 연결도 모든 VPC에서 공유하고 싶다. 네트워크 아키텍처를 단순화하려면?

**보기**
- A. 모든 VPC를 하나의 거대한 VPC로 통합(다른 팀/계정이 소유한 VPC를 하나로 통합하는 것은 격리 요구사항을 해치고 대규모 재설계가 필요해 현실적이지 않음).
- B. 피어링 연결 수를 줄이기 위해 통신이 꼭 필요한 VPC 쌍만 최소한으로 남기고 나머지는 애플리케이션 레벨에서 우회(우회 설계는 아키텍처를 오히려 복잡하게 만들고 근본적인 확장성 문제를 해결하지 못함).
- C. 모든 VPC 간 통신을 API Gateway를 경유하도록 강제(API Gateway는 HTTP API 앞단의 관리형 게이트웨이이며, VPC 간 네트워크 레벨 라우팅을 대체하는 도구가 아님).
- D. **AWS Transit Gateway를 허브로 두고 모든 VPC와 Direct Connect 연결을 Transit Gateway에 연결하는 허브-스포크(hub-and-spoke) 구조로 전환해, VPC 간 피어링을 개별적으로 관리할 필요 없이 중앙에서 라우팅을 관리하고 Direct Connect도 모든 연결된 VPC가 공유.**

**정답: D**

**해설**
**AWS Transit Gateway**는 여러 VPC와 온프레미스 네트워크(Direct Connect, VPN)를 하나의 중앙 허브에 연결하는 **허브-스포크 아키텍처**를 제공합니다. 각 VPC는 Transit Gateway에 한 번만 연결하면 되며, VPC 간 통신은 Transit Gateway의 라우팅 테이블을 통해 중앙에서 관리됩니다. 이를 통해 VPC 수가 늘어나도 개별 피어링 연결을 기하급수적으로 추가할 필요가 없고, Direct Connect Gateway와 결합하면 온프레미스 연결도 연결된 모든 VPC가 공유할 수 있어 대규모 멀티 VPC 환경의 네트워크 복잡도를 크게 낮춥니다.

**왜 다른 보기는 오답인가**
- A: VPC 통합은 격리 요구사항을 해치고 현실적인 재설계 범위를 벗어납니다.
- B: 우회 설계는 근본적인 확장성 문제를 해결하지 못합니다.
- C: API Gateway는 네트워크 레벨 VPC 간 라우팅 도구가 아닙니다.

> 💡 **시험 꿀팁**: 다수의 VPC 간 통신과 Direct Connect 공유를 **피어링 없이 중앙에서 단순하게 관리**하려면 **AWS Transit Gateway** 허브-스포크 구조가 표준 정답입니다.

## QUESTION 505

**문제**: 회사가 초당 수만 건씩 발생하는 IoT 센서 이벤트를 처리하는 워크플로우를 Step Functions로 구축하려 한다. 각 워크플로우 실행은 수 초 이내로 완료되는 짧은 처리(간단한 검증, 변환, DynamoDB 저장)이며, 실행 이력을 장기간 상세히 보관할 필요는 없고 비용 효율이 가장 중요하다. 이런 대량, 짧은 실행에 적합한 Step Functions 워크플로우 유형은?

**보기**
- A. 표준(Standard) 워크플로우를 사용(Standard 워크플로우는 실행당 상태 전이(state transition) 횟수 기준으로 과금되며 모든 실행 이력을 장기간 상세히 보관하도록 설계되어, 초당 수만 건의 짧은 실행에는 비용 효율이 떨어짐).
- B. **Express 워크플로우를 사용해, 요청 수와 실행 시간(duration) 및 메모리 사용량 기준으로 과금되는 방식으로 대량의 짧은 이벤트 처리 워크플로우를 비용 효율적으로 실행(비동기 Express는 최대 5분까지 지원).**
- C. Step Functions 대신 모든 로직을 단일 거대 Lambda 함수에 순차적으로 구현(단일 함수 구현은 가능하지만 문제가 명시적으로 Step Functions 기반 워크플로우 유형을 묻고 있으며, 시각적 워크플로우 관리와 재시도/에러 처리 이점을 포기하게 됨).
- D. SQS 표준 큐만 사용하고 Step Functions는 아예 사용하지 않음(SQS만으로는 여러 단계의 조건부 로직과 상태 관리를 표현하는 오케스트레이션 기능을 제공하지 않음).

- A: 인스턴스 업그레이드는 비용만 늘리고 동시성이 더 커지면 문제가 재발합니다.

- D: 엔진 전환만으로는 연결 풀링 문제가 자동으로 해결되지 않습니다.

## QUESTION 512

**문제**: 회사가 온프레미스 데이터센터와 AWS 간에 Direct Connect 전용선을 구축해 안정적인 대역폭과 낮은 지연 시간을 확보했다. 하지만 이 전용선 자체나 연결된 통신사 회선에 장애가 발생할 경우를 대비한 백업 경로가 없어, 단일 장애점(SPOF)에 대한 우려가 크다. 완전한 이중화 없이도 비용 효율적으로 복원력을 높이려면?

- B. 모든 계정에서 IAM 사용자의 관리자 권한(AdministratorAccess) 정책 연결을 금지하는 규칙만 수동으로 검토(관리자 권한을 막아도 위임된 다른 권한으로 여전히 위험한 작업이 가능할 수 있고, 계정별 수동 검토는 확장성이 없음).
- C. 각 계정에서 IAM 권한 경계(permission boundary)를 개별적으로 설정해 사용자별 최대 권한을 제한(권한 경계는 계정 내에서 개별 IAM principal 단위로 적용되며, 계정 자체의 루트 사용자를 포함해 조직 전체에 걸쳐 획일적으로 강제되는 것은 아니어서 계정마다 개별 설정/유지보수가 필요).
- D. **AWS Organizations의 서비스 제어 정책(Service Control Policy, SCP)을 관리 계정에서 정의해 대상 OU에 적용함으로써, 해당 OU 하위 모든 계정의 모든 IAM principal(루트 사용자 포함)에 대해 특정 작업을 계정 내 권한 설정과 무관하게 조직 차원에서 원천적으로 차단(허용 가능한 최대 권한의 상한선 역할).**

**정답: D**

**해설**
**AWS Organizations의 서비스 제어 정책(SCP)**은 조직 또는 특정 OU 단위로 적용되는 정책으로, 대상 범위 내 **모든 계정의 모든 IAM 사용자/역할(심지어 계정 루트 사용자 포함)**이 가질 수 있는 **허용 가능한 최대 권한의 상한선**을 정의합니다. SCP에서 명시적으로 거부(Deny)한 작업은 해당 계정의 IAM 정책이 아무리 관대하게(심지어 관리자 권한으로) 허용하더라도 절대 수행할 수 없어, 계정별 IAM 설정에 의존하지 않는 조직 차원의 강제적 가드레일을 구현하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 문서 기반 가이드라인은 강제성이 없습니다.
- B: 관리자 권한만 막는 것으로는 다른 위임 권한을 통한 위험 작업을 막지 못하고 확장성도 없습니다.
- C: 권한 경계는 계정 내 개별 principal 단위로 적용되며 조직 전체에 걸친 획일적 강제가 아닙니다.

> 💡 **시험 꿀팁**: 계정 내 권한 설정과 무관하게 **조직 전체에 걸쳐 특정 작업을 원천 차단**하는 가드레일에는 **AWS Organizations SCP**가 표준 정답입니다.

## QUESTION 520

**문제**: 회사가 수백 개의 EC2 인스턴스를 운영하는데, 많은 인스턴스가 실제 CPU/메모리 사용률에 비해 과도하게 큰 인스턴스 유형으로 프로비저닝되어 있어 비용 낭비가 의심된다. 수동으로 CloudWatch 지표를 하나씩 분석해 적정 크기를 판단하는 대신, 과거 사용률 데이터를 기반으로 각 인스턴스에 대한 구체적인 다운사이징/유형 변경 권장 사항을 자동으로 받고 싶다. 솔루션은?

**보기**
- A. AWS Budgets로 예산 초과 알림만 설정(Budgets는 예산 대비 지출 여부를 알려줄 뿐, 개별 리소스 단위의 사용률 기반 최적 인스턴스 유형 추천 기능은 제공하지 않음).
- B. 모든 인스턴스를 가장 작은 인스턴스 유형으로 일괄 축소한 뒤 문제가 생기면 다시 늘림(무작위 일괄 축소는 실제 사용률을 고려하지 않아 성능 저하나 장애를 유발할 위험이 크고 비체계적).
- C. **AWS Compute Optimizer를 사용해, 각 EC2 인스턴스의 과거 CloudWatch 사용률 지표(CPU, 메모리 등)를 머신러닝으로 분석하고, 인스턴스별로 구체적인 적정 크기(다운사이징 또는 유형 변경) 권장 사항과 예상 비용 절감 효과를 자동으로 제공.**
- D. Systems Manager Inventory로 설치된 소프트웨어 목록만 수집해 수동 판단 자료로 사용(Inventory는 설치된 소프트웨어/구성 정보를 수집할 뿐 사용률 기반 적정 크기 분석 기능은 제공하지 않음).

**정답: C**

**해설**
**AWS Compute Optimizer**는 EC2 인스턴스, Auto Scaling 그룹, EBS 볼륨, Lambda 함수 등의 과거 CloudWatch 사용률 지표(CPU, 메모리(에이전트 설치 시), 네트워크 등)를 **머신러닝으로 분석**해, 리소스가 과다 프로비저닝(over-provisioned)되었는지 과소 프로비저닝(under-provisioned)되었는지 판단하고 구체적인 **인스턴스 유형 변경 권장 사항과 예상 비용 절감액**을 자동으로 제시합니다. 수백 개 인스턴스를 수동으로 하나씩 분석할 필요 없이 데이터 기반의 rightsizing 의사결정을 지원하는 표준 도구입니다.

**왜 다른 보기는 오답인가**
- A: Budgets는 예산 초과 여부만 알려주며 리소스별 사용률 분석 기능이 없습니다.
- B: 무작위 일괄 축소는 실제 사용률을 고려하지 않아 위험합니다.
- D: Systems Manager Inventory는 소프트웨어/구성 정보 수집 도구이며 사용률 분석 기능이 없습니다.

> 💡 **시험 꿀팁**: 과거 사용률 데이터를 기반으로 **EC2 등 리소스의 rightsizing(다운사이징) 권장 사항**을 자동으로 받으려면 **AWS Compute Optimizer**가 표준 정답입니다.
