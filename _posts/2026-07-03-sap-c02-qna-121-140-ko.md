## QUESTION 121

**문제**: 금융 회사가 웹 앱을 온프레미스에서 AWS EC2(전용 VPC, ASG)로 마이그레이션합니다. 15년간 써온 서드파티 보안 도구(클라우드 버전 없음)로 VPC의 모든 인바운드·아웃바운드 패킷을 **실시간으로, 성능 저하 없이** 검사해야 합니다. 리전 내 고가용성도 필요합니다. (2가지 선택)

**보기**
- A. **기존 VPC에 새 Auto Scaling 그룹을 만들어 EC2 인스턴스에 보안 도구 배포**
- B. Network Load Balancer 뒤에 웹 애플리케이션 배포
- C. 보안 도구 인스턴스 앞에 Application Load Balancer 배포
- D. **각 가용 영역에 Gateway Load Balancer를 프로비저닝해 트래픽을 보안 도구로 리디렉션**
- E. VPC 간 통신을 위한 전송 게이트웨이 프로비저닝

**정답: A, D**

**해설**
**Gateway Load Balancer(GWLB)**는 정확히 이런 상황—레거시(클라우드 네이티브가 아닌) 서드파티 어플라이언스를 트래픽 경로에 투명하게 삽입해야 하는 경우—을 위해 설계된 서비스입니다. 각 AZ에 GWLB를 두어 트래픽을 보안 도구 인스턴스(A)로 리디렉션하면, 도구 자체를 클라우드에 맞게 바꾸지 않고도 확장성·고가용성을 확보할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 웹 앱을 NLB 뒤에 두는 것은 이 문제의 핵심(보안 도구를 트래픽 경로에 삽입하는 것)과 무관합니다.
- C: 보안 도구 앞에 ALB를 두는 것은 GWLB 기반 트래픽 검사 아키텍처의 표준 방식이 아닙니다.
- E: 전송 게이트웨이는 VPC 간 통신용이지, 단일 VPC 내 트래픽 검사 어플라이언스 삽입과는 무관합니다.

> 💡 **시험 꿀팁**: 레거시 서드파티 보안/검사 어플라이언스를 트래픽 경로에 투명하게 삽입하면서 고가용성·성능을 확보하려면 **Gateway Load Balancer(AZ당 하나)**를 떠올리세요. AWS의 표준 정답 패턴입니다.

## QUESTION 122

**문제**: 회사가 여러 공급업체의 가전제품(각각 IoT 센서)을 구매했습니다. 각 센서는 공급업체별 독점 형식으로 상태 정보를 레거시 앱에 보내 JSON으로 파싱하지만, 공급업체마다 형식이 다릅니다. 앱은 하루 한 번 모든 JSON을 파싱해 관계형 DB에 저장합니다. 더 빠르고 비용 최적화된 새 데이터 분석 솔루션은?

**보기**
- A. **IoT 센서를 AWS IoT Core에 연결, 규칙으로 Lambda를 호출해 파싱 후 S3에 .csv 저장, AWS Glue로 분류, Athena+QuickSight로 분석**
- B. 앱 서버를 Fargate로 마이그레이션 + Redshift에 저장
- C. AWS Transfer for SFTP 생성 + IoT 센서 코드를 SFTP 전송용으로 업데이트
- D. Snowball Edge로 로컬 분석 + 주기적으로 Redshift에 수집

**정답: A**

**해설**
**AWS IoT Core**로 다양한 형식의 IoT 데이터를 수집하고, **Lambda**로 공급업체별 파싱을 처리하며, **Glue+Athena+QuickSight**로 완전 서버리스 분석을 구성하는 것이, 매일 한 번 배치로 처리하던 기존 방식보다 훨씬 빠르고 비용 최적화된 재설계입니다.

**왜 다른 보기는 오답인가**
- B: 앱 서버를 Fargate로 옮겨도 여전히 동일한(수신→파싱→저장) 구조를 유지하며, 상시 실행되는 Redshift 클러스터 비용도 발생해 "빠르고 비용 최적화"라는 목표에 부합하지 않습니다.
- C: 다양한 공급업체의 독점 IoT 센서 코드를 직접 업데이트하는 것은 현실적으로 어렵고, IoT Core의 네이티브 수집 기능을 활용하지 못합니다.
- D: Snowball Edge는 대량 일회성 전송용이지, 지속적인 실시간 센서 데이터 파이프라인 용도가 아닙니다.

> 💡 **시험 꿀팁**: 공급업체별로 형식이 다른 지속적인 IoT 센서 데이터 파이프라인에는 **IoT Core(수집) + Lambda(파싱) + S3+Glue+Athena/QuickSight(서버리스 저장·분석)** 조합이 표준입니다.

## QUESTION 123

**문제**: 회사가 앱을 AWS로 마이그레이션하며 네트워킹·보안 전략을 빠르게 확정하려 합니다. 중앙 네트워크 계정에 Direct Connect가 있으며, 가까운 미래에 **수백 개**의 계정·VPC를 가질 것으로 예상합니다. 회사 네트워크는 모든 VPC와 원활히 통신해야 하고, **클라우드 리소스의 인터넷 트래픽을 온프레미스 데이터센터를 통해 라우팅**하려 합니다. (3가지 선택)

**보기**
- A. 계정 ID와 VGW를 사용한 "연결 제안" 방식으로 DX 게이트웨이 구성
- B. **중앙 네트워크 계정에 Direct Connect 게이트웨이와 Transit Gateway 생성, 전송(Transit) VIF로 TGW를 DXGW에 연결**
- C. 인터넷 게이트웨이 프로비저닝 + 서브넷 연결 + 인터넷 트래픽 허용
- D. **전송 게이트웨이를 다른 계정과 공유, VPC를 TGW에 연결**
- E. 필요에 따라 VPC 피어링 프로비저닝
- F. **프라이빗 서브넷만 프로비저닝, TGW·고객 게이트웨이에 경로를 열어 AWS의 아웃바운드 인터넷 트래픽이 데이터센터의 NAT 서비스를 거치도록 함**

**정답: B, D, F**

**해설**
**DXGW+TGW(전송 VIF)** 조합으로 확장성 있는 온프레미스-다중 VPC 연결을 구성하고(B), **TGW를 RAM으로 공유**해 수백 개의 VPC를 연결하며(D), **프라이빗 서브넷만 사용**하고 아웃바운드 인터넷 트래픽이 온프레미스 NAT를 거치도록 경로를 구성합니다(F, "온프레미스를 거쳐 인터넷으로" 요구 사항 충족).

**왜 다른 보기는 오답인가**
- A: 계정ID+VGW 기반의 오래된 DX 공유 방식은 "수백 개 계정·VPC" 규모에 적합하지 않습니다.
- C: 인터넷 게이트웨이로 직접 인터넷에 나가는 것은 "온프레미스를 거쳐 인터넷으로 라우팅"이라는 요구 사항에 정면으로 위배됩니다.
- E: VPC 피어링을 "필요에 따라" 맺는 방식은 수백 개 VPC 규모에서 확장성이 없습니다(전이적이지도 않음).

> 💡 **시험 꿀팁**: 수백 개의 계정·VPC 규모에서는 **DXGW+TGW(전송 VIF) + RAM 공유**가 표준이며, 인터넷 트래픽을 온프레미스로 우회시키려면 **프라이빗 서브넷만 사용**하고 TGW/고객 게이트웨이 경로를 온프레미스 NAT로 향하게 구성하세요.

## QUESTION 124

**문제**: 수백 개 계정을 가진 회사가 예약 인스턴스(RI) 구매·수정을 전담 팀을 통한 중앙 프로세스로 바꾸려 합니다(기존엔 각 사업부가 자율적으로 구매). 가장 안전하게 새 프로세스를 시행하려면? (2가지 선택)

**보기**
- A. **모든 계정이 "모든 기능이 활성화된" AWS Organizations 조직에 속하는지 확인**
- B. AWS Config로 RI 관련 작업을 거부하는 IAM 정책 연결 여부를 "보고"
- C. 각 계정에서 개별적으로 RI 관련 작업을 거부하는 IAM 정책 생성
- D. **RI 구매·수정 작업을 거부하는 SCP 생성, 조직의 각 OU에 적용**
- E. 모든 계정이 "통합 결제 기능만" 사용하는 조직에 속하는지 확인

**정답: A, D**

**해설**
SCP가 작동하려면 Organizations의 **"모든 기능(All Features)"**이 활성화되어 있어야 합니다(A, 자주 간과되는 전제 조건). 그 위에 **RI 구매·수정 작업을 거부하는 SCP**를 조직 전체 OU에 적용(D)하면 가장 중앙집중적이고 안전하게 시행할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: AWS Config로 "보고"하는 것은 사후 감지일 뿐, 실제 차단(예방)이 아닙니다.
- C: 수백 개 계정 각각에 동일한 IAM 정책을 만드는 것은 SCP 하나보다 훨씬 유지보수 부담이 크고 일관성도 떨어집니다.
- E: SCP에는 **"모든 기능"**이 필요하며, "통합 결제 기능"만으로는 부족합니다.

> 💡 **시험 꿀팁**: **SCP는 Organizations의 "모든 기능(All Features)"이 활성화되어야만 작동**합니다("통합 결제 기능"만으로는 안 됨). 여러 계정에 걸친 제한은 개별 IAM 정책보다 **조직 전체 SCP** 하나로 시행하는 것이 더 안전하고 유지보수가 쉽습니다.

## QUESTION 125

**문제**: 중요 앱이 RDS for MySQL 다중 AZ를 사용하는데, 최근 장애 조치 테스트로 **40초** 중단이 발생했습니다. 이를 **20초 미만**으로 줄이려면? (3가지 선택)

**보기**
- A. 데이터베이스 앞에 ElastiCache for Memcached
- B. 데이터베이스 앞에 ElastiCache for Redis
- C. **데이터베이스 앞에 RDS 프록시 사용**
- D. **데이터베이스를 Amazon Aurora MySQL로 마이그레이션**
- E. **Aurora 복제본 생성**
- F. RDS for MySQL 읽기 전용 복제본 생성

**정답: C, D, E**

**해설**
**Aurora는 표준 RDS 다중 AZ보다 훨씬 빠른 자체 장애 조치**를 제공하며, **Aurora 복제본**을 두면 승격 대상이 항상 준비되어 있어 장애 조치가 더 빨라집니다. 여기에 **RDS 프록시**를 앞단에 두면 장애 조치 시 연결 재수립을 프록시가 대신 처리해 애플리케이션이 체감하는 다운타임도 줄어듭니다.

**왜 다른 보기는 오답인가**
- A, B: ElastiCache(캐시)는 읽기 부하를 줄여줄 수는 있지만, **장애 조치 자체의 소요 시간**(쓰기 가용성 공백)과는 무관합니다.
- F: **RDS for MySQL의 읽기 전용 복제본은 Aurora 복제본과 달리 자동 장애 조치 대상이 아니며 수동 승격이 필요**해, 자동 장애 조치 시간 단축에 직접 기여하지 않습니다.

> 💡 **시험 꿀팁**: 다중 AZ 데이터베이스의 **장애 조치 시간을 줄이려면 Aurora로 마이그레이션 + Aurora 복제본 + RDS 프록시** 조합을 기억하세요. 캐시는 장애 조치 시간과 무관하고, 일반 RDS 읽기 복제본은 자동 장애 조치 대상이 아닙니다.

## QUESTION 126

**문제**: AWS 파트너(org1)가 별도 조직(org2)에 속한 고객 계정의 리소스에 API/CLI로 최소 권한 접근해야 합니다. 가장 안전한 방법은?

**보기**
- A. 고객이 계정 액세스 키를 파트너에 직접 제공
- B. 고객이 IAM 사용자를 만들어 자격 증명을 파트너에 공유
- C. 고객이 IAM 역할을 만들고, 파트너가 역할 ARN만으로 접근
- D. **고객이 IAM 역할을 만들고, 파트너가 역할 ARN + 신뢰 정책의 외부 ID(External ID)를 함께 사용해 접근**

**정답: D**

**해설**
이는 **교차 계정 역할 수임 + 외부 ID(External ID)** 표준 패턴으로, 특히 **서드파티(파트너)가 여러 무관한 고객 계정에 접근**해야 하는 SaaS/파트너 시나리오에 AWS가 명시적으로 권장하는 방식입니다. External ID는 "혼동된 대리인(confused deputy)" 문제—파트너가 실수로/악의적으로 다른 고객의 역할에 접근하게 되는 상황—를 방지하는 핵심 장치입니다.

**왜 다른 보기는 오답인가**
- A, B: 계정 액세스 키나 IAM 사용자 자격 증명을 외부에 직접 공유하는 것은 범위를 좁힐 수 없고 회수도 어려운 심각한 보안 안티패턴입니다.
- C: External ID 없이 ARN만 사용하는 것은, 파트너가 여러 고객 계정을 다루는 상황에서 "혼동된 대리인" 문제에 취약합니다.

> 💡 **시험 꿀팁**: **서드파티 파트너가 여러 고객 계정에 접근**해야 하는 SaaS 통합 패턴에서는 **역할 ARN + 고유한 External ID**를 신뢰 정책에 포함하는 것이 AWS 권장 표준입니다. External ID가 없으면 "혼동된 대리인" 문제에 노출됩니다.

## QUESTION 127

**문제**: 배송 회사가 서드파티 경로 계획 앱(공용 레지스트리 Docker 이미지)을 마이그레이션합니다. 배송 구역을 허브 기준으로 나누고, 구역별로 고유한 설정의 컨테이너 세트를 사용합니다. 실행 중인 컨테이너 수에 따라 비용 효율적으로 리소스를 할당해야 하며 최소 운영 오버헤드가 필요합니다.

**보기**
- A. EC2의 EKS 클러스터 + EKS CLI `--tags`로 포드에 태그
- B. Fargate의 EKS 클러스터 + `tag-resource` API로 포드 태그
- C. EC2의 ECS 클러스터 + `--tags`로 작업(task)에 태그
- D. **AWS Fargate의 ECS 클러스터, `run-task` 명령에 `enableECSManagedTags=true` 설정, `--tags`로 작업에 커스텀 태그 할당**

**정답: D**

**해설**

- A, C: **자체 관리 SMTP 서버(EC2)를 다시 구축**하는 것은 마이그레이션으로 없애려던 바로 그 서버 관리 부담을 재도입하는 것입니다.
- B: SES는 쓰지만 템플릿을 **S3에 별도 저장**하고 **커스텀 Lambda로 수동 병합**하는 것은, SES가 이미 네이티브로 제공하는 템플릿 저장·렌더링 기능을 불필요하게 재구현하는 것입니다.

> 💡 **시험 꿀팁**: **Amazon SES는 파라미터가 있는 이메일 템플릿을 직접 저장하고 `SendTemplatedEmail` API로 발송**할 수 있습니다. "이메일 템플릿에 고객 데이터를 병합해서 보낸다"는 요구 사항이 나오면 별도의 S3 저장이나 커스텀 병합 로직 없이 이 네이티브 기능을 먼저 떠올리세요. 자체 관리 SMTP 서버 재구축은 거의 항상 오답입니다.
