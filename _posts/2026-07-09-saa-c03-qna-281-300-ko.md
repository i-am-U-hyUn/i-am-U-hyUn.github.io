## QUESTION 281

**문제**: 회사는 PostgreSQL DB 인스턴스용 Amazon RDS로 웹 서버 플릿을 운영합니다. 정기 컴플라이언스 점검 후, 회사는 모든 프로덕션 데이터베이스에 대해 1초 미만의 복구 지점 목표(RPO)를 만족해야 한다는 표준을 새로 수립했습니다. 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. **DB 인스턴스에 대해 다중 AZ(Multi-AZ) 배포를 활성화한다.**
- B. 단일 가용 영역에서 DB 인스턴스에 대해 Auto Scaling을 활성화한다. (컴퓨팅 용량만 조정할 뿐 데이터를 다른 AZ로 복제하지 않아 요구 사항을 충족하지 못함)
- C. 단일 가용 영역에서 DB 인스턴스를 구성하고 별도 AZ에 다수의 읽기 전용 복제본을 생성한다. (읽기 전용 복제본은 비동기 복제를 사용해 지연이 발생할 수 있음)
- D. 단일 가용 영역에서 DB 인스턴스를 구성하고 AWS DMS(AWS Database Migration Service) CDC 작업을 구성한다. (DMS CDC도 비동기 복제 방식이라 지연이 발생할 수 있음)

**정답: A**

**해설**
Amazon RDS **다중 AZ 배포**는 기본(Primary) 인스턴스의 트랜잭션을 대기(Standby) 인스턴스로 **동기식으로 복제**합니다. 두 인스턴스가 항상 동기화 상태를 유지하므로 장애 발생 시 데이터 손실이 사실상 없는, 즉 RPO 0에 가까운 수준의 복구가 가능합니다. 이는 문제에서 요구하는 1초 미만 RPO를 만족하는 유일한 옵션입니다.

**왜 다른 보기는 오답인가**
- B: Auto Scaling은 부하에 따라 컴퓨팅 용량을 조정하는 기능일 뿐, 데이터를 다른 AZ로 복제하지 않으므로 RPO 개선과 무관하다.
- C: 읽기 전용 복제본은 비동기 복제를 사용하여 기본 인스턴스보다 지연될 수 있다.
- D: DMS CDC 역시 비동기 방식으로 데이터를 캡처·적용하므로 실시간 동기화를 보장하지 못한다.

> 💡 **시험 꿀팁**: "RPO를 최소화해야 한다"는 조건이 나오면 동기식 복제를 제공하는 Multi-AZ 배포가 표준 정답입니다.

## QUESTION 282

**문제**: 회사는 VPC의 프라이빗 서브넷에 있는 Amazon EC2 인스턴스에 웹 애플리케이션을 배포했습니다. 퍼블릭 서브넷에 걸쳐 있는 ALB(Application Load Balancer)가 웹 트래픽을 이 EC2 인스턴스로 전달합니다. 회사는 ALB에서 EC2 인스턴스로 향하는 인바운드 트래픽만 허용하고, 프라이빗 서브넷 내부 또는 외부의 다른 어떤 소스로부터의 접근도 차단하는 보안 조치를 새로 구현하려고 합니다. 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. 인터넷에서 EC2 인스턴스의 프라이빗 IP 주소로 트래픽을 보내도록 라우팅 테이블 경로를 구성한다. (프라이빗 IP는 인터넷에서 라우팅될 수 없으며 오히려 접근을 확대하는 잘못된 방향의 조치)
- B. **ALB의 보안 그룹에서 오는 트래픽만 허용하도록 EC2 인스턴스의 보안 그룹을 구성한다.**
- C. EC2 인스턴스를 퍼블릭 서브넷으로 이동하고 탄력적 IP를 할당한다. (인스턴스를 인터넷에 직접 노출시켜 요구 사항과 정반대의 결과를 낳음)
- D. 모든 포트에서 모든 TCP 트래픽을 허용하도록 ALB의 보안 그룹을 구성한다. (ALB 자체의 노출면만 넓힐 뿐 EC2 인스턴스 접근 제한과는 무관함)

**정답: B**

**해설**
보안 그룹은 소스로 다른 보안 그룹을 지정할 수 있습니다. EC2 인스턴스의 보안 그룹 인바운드 규칙에서 허용 소스를 **ALB의 보안 그룹**으로 지정하면, ALB를 거친 트래픽만 인스턴스에 도달할 수 있고 그 외의 어떤 IP나 서브넷에서 직접 접근하는 트래픽은 모두 차단됩니다. 이는 프라이빗 서브넷의 백엔드 인스턴스를 로드밸런서로만 접근하도록 보호하는 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- A: 프라이빗 IP는 인터넷에서 라우팅될 수 없으며, 이런 시도는 오히려 설계 원칙에 위배된다.
- C: 인스턴스를 퍼블릭 서브넷으로 옮기고 EIP를 부여하면 인터넷에 직접 노출되어 요구 사항과 반대되는 결과를 낳는다.
- D: ALB 보안 그룹을 모든 트래픽에 개방하면 ALB의 노출면만 커질 뿐 EC2 인스턴스로의 접근 제한과는 관련이 없다.

> 💡 **시험 꿀팁**: "로드밸런서 뒤 인스턴스로의 접근을 로드밸런서로만 제한하라"는 요구에는 대상 보안 그룹의 소스를 로드밸런서 보안 그룹으로 지정하는 것이 표준 정답입니다.

## QUESTION 283

**문제**: 한 연구 회사는 시뮬레이션 애플리케이션과 시각화 애플리케이션으로 구동되는 실험을 수행합니다. Linux에서 실행되는 시뮬레이션 애플리케이션은 5분마다 NFS 공유에 중간 데이터를 출력하고, SMB 파일 시스템이 필요한 Windows 데스크톱 시각화 애플리케이션이 그 결과를 표시합니다. 현재 두 개의 동기화된 파일 시스템을 별도로 유지하고 있어 데이터 중복과 비효율적인 리소스 사용이 발생합니다. 회사는 애플리케이션 코드를 변경하지 않고 AWS로 마이그레이션해야 합니다. 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. 두 애플리케이션을 모두 AWS Lambda로 마이그레이션하고, 애플리케이션 간 데이터 교환용 Amazon S3 버킷을 생성한다. (Lambda로의 전환은 애플리케이션 재작성을 요구해 "코드 변경 없이" 조건에 위배됨)
- B. 두 애플리케이션을 모두 Amazon ECS로 마이그레이션하고, 스토리지용 Amazon FSx File Gateway를 구성한다. (컨테이너화 자체가 재구성을 요구하며, FSx File Gateway는 온프레미스에서 AWS 스토리지에 캐시로 접근하는 용도라 이 시나리오와 맞지 않음)
- C. 시뮬레이션 앱은 Linux EC2로, 시각화 앱은 Windows EC2로 마이그레이션하고, 두 앱 간 데이터 교환에 Amazon SQS를 구성한다. (SQS는 메시지 큐 서비스로 NFS/SMB 파일 공유 자체를 대체할 수 없음)
- D. **시뮬레이션 앱은 Linux EC2로, 시각화 앱은 Windows EC2로 마이그레이션하고, 스토리지용으로 Amazon FSx for NetApp ONTAP를 구성한다.**

**정답: D**

**해설**
**Amazon FSx for NetApp ONTAP**는 단일 파일 시스템에서 NFS와 SMB 프로토콜을 동시에 지원하는 완전관리형 스토리지입니다. Linux 시뮬레이션 애플리케이션은 NFS로, Windows 시각화 애플리케이션은 SMB로 동일한 볼륨에 접근할 수 있어, 기존처럼 두 개의 별도 동기화된 파일 시스템을 유지할 필요 없이 애플리케이션 코드를 변경하지 않고도 데이터 중복 문제를 해결할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Lambda로의 마이그레이션 자체가 애플리케이션 재작성을 전제로 하므로 "코드 변경 없이"라는 조건에 어긋난다.
- B: ECS 컨테이너화도 애플리케이션 재구성이 필요하며, FSx File Gateway는 온프레미스-AWS 간 캐시 게이트웨이 용도로 이 시나리오와 맞지 않다.
- C: SQS는 메시지 큐 서비스이지 파일 시스템이 아니므로 NFS/SMB 기반 파일 공유를 요구하는 두 애플리케이션에는 사용할 수 없다.

> 💡 **시험 꿀팁**: "리눅스는 NFS, 윈도우는 SMB를 동시에 써야 한다"는 요구에는 FSx for NetApp ONTAP가 표준 정답입니다(FSx for Windows File Server는 SMB만 지원).

## QUESTION 284

**문제**: 예산 계획을 위해 경영진은 사용자별로 구분된 AWS 청구 항목 보고서를 원합니다. 이 데이터는 부서별 예산 수립에 사용됩니다. 솔루션 설계자는 이 보고서를 가장 효율적으로 얻는 방법을 결정해야 합니다. 어떤 솔루션이 이 요구 사항을 충족합니까?

**보기**
- A. Amazon Athena로 쿼리를 실행하여 보고서를 생성한다. (S3에 적재된 Cost and Usage Report 데이터를 가리키는 테이블을 별도로 구성해야 해 추가 비용과 복잡성이 발생함)
- B. **Cost Explorer에서 보고서를 생성하고 다운로드한다.**
- C. 청구 대시보드에서 청구서 세부 정보에 접근하여 청구서를 다운로드한다. (청구 대시보드는 전체 비용의 상위 수준 요약만 제공할 뿐 사용자별 항목을 구분해 주지 않음)
- D. Amazon SES로 알리도록 AWS Budgets의 비용 예산을 수정한다. (Budgets는 예산 초과 여부를 알리는 용도일 뿐 사용자별 상세 보고서를 만들어 주지 않음)

**정답: B**

**해설**
**AWS Cost Explorer**는 비용 할당 태그(예: 사용자 이름 태그)를 필터·그룹화 기준으로 사용해 사용자별 비용 내역을 시각화하고, 이를 CSV로 다운로드할 수 있는 기능을 기본 제공합니다. 별도의 데이터 파이프라인 구축 없이 콘솔에서 몇 번의 클릭만으로 원하는 보고서를 만들 수 있어 가장 효율적인 방법입니다.

**왜 다른 보기는 오답인가**
- A: Athena로 이런 보고서를 만들려면 S3에 Cost and Usage Report를 적재하고 테이블을 정의한 뒤 쿼리를 작성해야 하므로 Cost Explorer보다 훨씬 번거롭다.
- C: 청구 대시보드는 계정 전체의 비용 개요만 보여주며 사용자 단위로 분리된 내역을 제공하지 않는다.
- D: AWS Budgets는 예산 초과(또는 초과 예상) 시 알림을 보내는 도구로, 사용자별 상세 보고서 생성 기능이 아니다.

> 💡 **시험 꿀팁**: "태그·사용자 기준으로 비용을 분석하고 다운로드해야 한다"는 요구에는 Cost Explorer가 표준 정답입니다.

## QUESTION 285

**문제**: 한 회사는 Amazon S3로 정적 웹 사이트를 호스팅하고 있으며, 이름·이메일·전화번호·메시지를 입력받는 동적 서버 측 연락처 양식을 웹 페이지에 추가하려고 합니다. 이 사이트는 매월 100회 미만의 방문만 예상됩니다. 이 요구 사항을 가장 비용 효율적으로 충족하는 솔루션은 무엇입니까?

**보기**
- A. Amazon ECS에서 동적 문의 양식 페이지를 호스팅하고, 타사 이메일 공급자에 연결하도록 Amazon SES를 설정한다. (ECS는 컨테이너를 상시 실행해야 해 월 100회 미만의 방문에는 과도한 비용이 발생함)
- B. **Amazon SES를 호출하는 AWS Lambda 백엔드로 Amazon API Gateway 엔드포인트를 생성한다.**
- C. Amazon Lightsail을 배포해 정적 페이지를 동적으로 전환하고, 클라이언트 측 스크립팅으로 양식을 만들어 Amazon WorkMail과 통합한다. (Lightsail은 트래픽과 무관하게 고정 월 요금이 부과되는 상시 가동 인스턴스라 비효율적)
- D. t2.micro EC2 인스턴스에 LAMP 스택을 배포해 웹 페이지를 호스팅하고, 클라이언트 측 스크립팅으로 양식을 만들어 Amazon WorkMail과 통합한다. (EC2 인스턴스 역시 상시 과금되는 자원이라 저트래픽 대비 비용 효율이 떨어짐)

**정답: B**

**해설**
**Amazon API Gateway**와 **AWS Lambda**는 완전 서버리스 조합으로, 요청이 들어올 때만 과금되고 유휴 상태에서는 비용이 발생하지 않습니다. 사용자가 양식을 제출하면 API Gateway가 이를 받아 Lambda 함수를 호출하고, Lambda가 Amazon SES를 통해 이메일을 전송합니다. 월 100회 미만의 저트래픽 환경에서는 상시 가동되는 서버(ECS, Lightsail, EC2)보다 서버리스 구조가 압도적으로 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- A: ECS는 컨테이너를 계속 실행 상태로 유지해야 하므로 낮은 트래픽 대비 불필요한 상시 비용이 발생한다.
- C: Lightsail도 트래픽량과 무관하게 고정 월 요금이 청구되는 상시 가동형 인스턴스이므로 비효율적이다.
- D: EC2 인스턴스에 LAMP 스택을 구성해 운영하는 것 역시 24시간 상시 과금되며, 서버 유지관리 부담까지 추가된다.

> 💡 **시험 꿀팁**: "트래픽이 매우 적고 비용 효율이 핵심"이라는 조건에는 API Gateway + Lambda(+ SES) 서버리스 조합이 표준 정답입니다.

## QUESTION 286

**문제**: 한 회사는 Amazon S3 앞단에 Amazon CloudFront를 둔 정적 웹 사이트를 운영합니다. Git 리포지토리와 S3 간 CI/CD 파이프라인의 webhook 설정과 배포 성공 메시지를 모두 확인했음에도, 웹 사이트가 Git 리포지토리의 최신 업데이트를 반영하지 않습니다. 솔루션 설계자는 웹 사이트에 최신 업데이트가 표시되도록 해야 합니다. 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. Application Load Balancer를 추가한다. (정적 콘텐츠를 S3+CloudFront로 서빙하는 구조에는 ALB가 필요 없으며 콘텐츠 갱신 문제와도 무관함)

- D. AWS Certificate Manager(ACM)로 웹 사이트의 SSL 인증서를 확인한다. (SSL 인증서 문제는 콘텐츠 갱신 여부와 관계가 없음)

- D: SSL 인증서는 HTTPS 통신의 신뢰성과 관련이 있을 뿐 콘텐츠 갱신 여부와는 무관하다.

> 💡 **시험 꿀팁**: "CI/CD 배포는 성공했는데 CloudFront 뒤 사이트가 갱신되지 않는다"는 상황에는 캐시 무효화가 표준 정답입니다.

## QUESTION 287

**문제**: 한 회사가 Windows 기반 애플리케이션을 온프레미스에서 AWS 클라우드로 마이그레이션하려고 합니다. 이 애플리케이션은 애플리케이션 계층, 비즈니스 계층, Microsoft SQL Server 기반 데이터베이스 계층의 3계층 구조입니다. 회사는 네이티브 백업 및 데이터 품질 서비스(Data Quality Services)와 같은 SQL Server 고유 기능을 계속 사용하려고 하며, 계층 간에는 처리를 위한 파일 공유도 필요합니다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 아키텍처를 어떻게 설계해야 합니까?

**보기**
- A. Amazon EC2 인스턴스에서 세 계층을 모두 호스팅하고, 계층 간 파일 공유에 Amazon FSx File Gateway를 사용한다. (FSx File Gateway는 온프레미스에서 FSx 스토리지에 캐시 방식으로 접근하는 게이트웨이 어플라이언스로, 완전히 클라우드로 이전한 이 구성에는 맞지 않음)
- B. **Amazon EC2 인스턴스에서 세 계층을 모두 호스팅하고, 계층 간 파일 공유에 Amazon FSx for Windows File Server를 사용한다.**
- C. 애플리케이션 계층과 비즈니스 계층은 EC2에서, 데이터베이스 계층은 Amazon RDS에서 호스팅하고, 계층 간 파일 공유에 Amazon EFS를 사용한다. (RDS for SQL Server는 OS 접근이 제한되어 일부 네이티브 기능을 쓸 수 없고, EFS는 NFS만 지원해 Windows 환경과 맞지 않음)
- D. 애플리케이션 계층과 비즈니스 계층은 EC2에서, 데이터베이스 계층은 RDS에서 호스팅하고, 계층 간 파일 공유에 프로비저닝된 IOPS(io2) EBS 볼륨을 사용한다. (RDS의 기능 제약 문제는 C와 동일하고, EBS 볼륨은 기본적으로 단일 인스턴스에만 연결되어 다중 계층 파일 공유에 부적합함)

**정답: B**

**해설**
SQL Server의 네이티브 백업이나 데이터 품질 서비스 같은 기능은 관리형 RDS가 아닌, **OS 수준 접근이 가능한 EC2에 SQL Server를 직접 설치**해야 온전히 사용할 수 있습니다. 따라서 세 계층 모두 EC2에서 호스팅해야 합니다. 계층 간 파일 공유는 Windows 환경에 최적화된 완전관리형 SMB 파일 시스템인 **Amazon FSx for Windows File Server**를 사용하면, 별도의 파일 서버 구축 없이 여러 EC2 인스턴스에서 동일한 파일 공유에 접근할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: FSx File Gateway는 온프레미스에서 AWS 스토리지에 저지연 캐시 접근을 제공하기 위한 게이트웨이로, 완전히 클라우드로 이전한 이 시나리오와는 목적이 다르다.
- C: Amazon RDS for SQL Server는 관리형 서비스 특성상 OS 접근이 제한되어 일부 SQL Server 네이티브 기능을 지원하지 않으며, EFS는 NFS 전용이라 Windows 파일 공유 요구와 맞지 않다.
- D: RDS의 기능 제약은 C와 동일하며, EBS 볼륨은 원칙적으로 하나의 EC2 인스턴스에만 연결되므로 다중 계층 간 파일 공유 용도로는 부적합하다.

> 💡 **시험 꿀팁**: "SQL Server의 네이티브 기능을 그대로 써야 한다"는 조건이 나오면 RDS가 아닌 EC2 직접 설치 구성이 정답이며, Windows 파일 공유에는 FSx for Windows File Server가 표준 정답입니다.

**문제**: 한 회사가 Linux 기반 웹 서버 그룹을 AWS로 마이그레이션하고 있습니다. 웹 서버는 일부 콘텐츠를 위해 공유 파일 스토리지에 접근해야 하며, 회사는 애플리케이션을 변경할 수 없습니다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 합니까?

- B. Amazon S3 버킷을 오리진으로 사용하는 Amazon CloudFront 배포를 구성한다. (CloudFront는 콘텐츠 전송을 가속화하는 CDN일 뿐 다중 서버 간 공유 파일 접근 방식을 제공하지 않음)

- D: EBS 볼륨은 기본적으로 단일 EC2 인스턴스에만 연결 가능해 여러 서버 간 동시 공유에는 사용할 수 없다.

> 💡 **시험 꿀팁**: "여러 Linux 서버가 애플리케이션 변경 없이 파일을 공유해야 한다"는 조건에는 Amazon EFS가 표준 정답입니다.

**문제**: 한 회사에 동일한 AWS 계정 내 Amazon S3 버킷에 대한 읽기 접근 권한이 필요한 AWS Lambda 함수가 있습니다. 가장 안전한 방식으로 이 요구 사항을 충족하는 솔루션은 무엇입니까?

- B. **Lambda 함수에 IAM 역할을 적용하고, 해당 역할에 S3 버킷 읽기 접근 권한을 부여하는 IAM 정책을 연결한다.**
- C. Lambda 함수 코드에 액세스 키와 비밀 키를 직접 하드코딩하여 S3 접근 권한을 부여한다. (코드에 자격 증명을 하드코딩하면 유출·노출 위험이 커지고 키 순환 관리도 어려워짐)

**해설**

**왜 다른 보기는 오답인가**
- A: 버킷 정책으로 권한을 부여하면 Lambda 함수 외의 다른 보안 주체도 접근할 수 있는 범위로 설정되기 쉬워 세밀한 최소 권한 제어가 어렵다.
- C: 액세스 키를 코드에 하드코딩하면 소스 코드 유출 시 자격 증명이 그대로 노출되며, 키 순환도 수동으로 관리해야 하는 위험한 방식이다.
- D: 계정의 모든 S3 버킷에 대한 읽기 권한은 실제 필요한 범위를 벗어난 과도한 권한으로, 최소 권한 원칙에 위배된다.

> 💡 **시험 꿀팁**: "Lambda가 특정 AWS 리소스에 안전하게 접근해야 한다"는 조건에는 항상 IAM 역할 + 최소 권한 정책 조합이 표준 정답입니다.

> 💡 **시험 꿀팁**: "장기 약정 없이 비용을 최적화하라"는 조건에는 온디맨드 + 스팟 혼합 구성이 표준 정답입니다(예약 인스턴스·Savings Plans는 약정이 필요하므로 제외).

**문제**: 한 미디어 회사가 공개적으로 제공되는 스트리밍 비디오 콘텐츠에 Amazon CloudFront를 사용하고 있습니다. 이 회사는 Amazon S3에 호스팅된 비디오 콘텐츠에 대해 접근 권한이 있는 사용자만 제어하여 콘텐츠를 보호하려고 합니다. 일부 사용자는 쿠키를 지원하지 않는 커스텀 HTTP 클라이언트를 사용하고, 일부 사용자는 접근에 사용하는 하드코딩된 URL을 변경할 수 없습니다. 사용자에게 미치는 영향을 최소화하면서 이 요구 사항을 충족하는 서비스 또는 방법은 무엇입니까? (2개 선택)

**보기**
- A. **서명된 쿠키(Signed Cookies)**
- B. **서명된 URL(Signed URLs)**
- C. AWS AppSync (GraphQL API를 위한 관리형 서비스로, CloudFront 콘텐츠에 대한 서명 기반 접근 제어 기능을 제공하지 않음)
- D. JSON 웹 토큰(JWT) (CloudFront와 네이티브로 통합되는 콘텐츠 접근 제어 메커니즘이 아니며 별도의 검증 로직 구축이 필요함)
- E. AWS Secrets Manager (비밀 값을 안전하게 저장·순환하는 서비스일 뿐, 콘텐츠 배포 접근을 직접 제어하는 기능은 없음)

**정답: A, B**

**해설**
CloudFront는 콘텐츠 접근을 제한하는 두 가지 방법으로 **서명된 URL**과 **서명된 쿠키**를 제공합니다. 쿠키를 지원하지 않는 커스텀 HTTP 클라이언트를 쓰는 사용자에게는 요청 URL 자체에 서명 정보를 담는 서명된 URL을 발급하면 쿠키 없이도 인증된 요청만 허용할 수 있습니다. 반대로 하드코딩된 URL을 바꿀 수 없는 사용자에게는 URL은 그대로 두고 별도의 서명된 쿠키를 발급해 인증 정보를 쿠키에 담으면, URL 변경 없이 접근을 제어할 수 있습니다. 두 방법을 병행하면 서로 다른 제약을 가진 두 사용자 그룹 모두에 최소한의 영향으로 접근 제어를 적용할 수 있습니다.

**왜 다른 보기는 오답인가**
- C: AppSync는 GraphQL API 관리 서비스로 CloudFront 배포 콘텐츠에 대한 서명 기반 접근 제어와는 관련이 없다.
- D: JWT는 자체적으로 유효한 인증 토큰 포맷일 뿐, CloudFront가 기본 제공하는 서명 검증 메커니즘이 아니므로 별도의 검증 인프라를 구축해야 한다.
- E: Secrets Manager는 데이터베이스 자격 증명 등 비밀 정보를 저장·순환하는 서비스로, 콘텐츠 배포 자체의 접근 제어 기능은 제공하지 않는다.

> 💡 **시험 꿀팁**: "쿠키를 못 쓰는 사용자와 URL을 못 바꾸는 사용자가 섞여 있다"는 조건이 나오면 서명된 URL과 서명된 쿠키를 함께 사용하는 것이 표준 정답입니다.

**보기**
- A. AWS Snowball을 사용해 온프레미스에서 Amazon S3로 데이터를 마이그레이션하고, 로컬 접근을 위해 Snowball S3 엔드포인트를 온프레미스 시스템에 마운트하도록 구성한다. (물리 장치를 주고받아야 하는 일회성 대량 전송 방식이라 자동화된 지속적 백업에 적합하지 않음)

- C: 캐시형 볼륨 게이트웨이는 원본 데이터가 S3에 있고 자주 쓰는 데이터의 일부만 로컬에 캐싱되므로, "모든 데이터"에 대한 로컬 접근을 제공하지 못한다.

> 💡 **시험 꿀팁**: "모든 데이터를 로컬에 유지하면서 AWS에도 자동 백업해야 한다"는 조건에는 저장형(Stored) 볼륨 게이트웨이가, "자주 쓰는 일부만 로컬에 캐싱해도 된다"면 캐시형(Cached) 볼륨 게이트웨이가 정답이라는 점을 구분해서 기억해야 합니다.

## QUESTION 294

**문제**: Amazon EC2 인스턴스에서 호스팅되는 애플리케이션이 Amazon S3 버킷에 접근해야 하며, 이 트래픽은 인터넷을 거치면 안 됩니다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 접근을 어떻게 구성해야 합니까?

**보기**
- A. Amazon Route 53으로 프라이빗 호스팅 영역을 생성한다. (VPC 내부 리소스에 대한 사용자 지정 DNS 이름을 제공할 뿐, 인터넷 게이트웨이나 NAT 없이 S3로의 연결 경로 자체를 만들어 주지는 않음)
- B. **VPC에서 Amazon S3에 대한 게이트웨이 VPC 엔드포인트(Gateway VPC Endpoint)를 설정한다.**
- C. NAT 게이트웨이를 사용해 S3 버킷에 접근하도록 EC2 인스턴스를 구성한다. (NAT 게이트웨이는 프라이빗 서브넷의 인스턴스가 인터넷 경로로 나가는 아웃바운드 연결을 위한 것으로, 결국 인터넷 경로를 사용하게 되어 요구 사항을 충족하지 못함)

**정답: B**

**해설**

**왜 다른 보기는 오답인가**
- A: Route 53 프라이빗 호스팅 영역은 VPC 내부용 DNS 이름을 제공하는 기능일 뿐, S3로의 네트워크 경로 자체를 인터넷 없이 열어주지는 않는다.
- C: NAT 게이트웨이는 프라이빗 서브넷의 아웃바운드 트래픽이 인터넷 게이트웨이를 거쳐 나가도록 중계하는 서비스이므로, 트래픽이 사실상 인터넷 경로를 사용하게 되어 요구 사항에 부합하지 않는다.
- D: Site-to-Site VPN은 온프레미스와 VPC 사이의 연결을 위한 것으로, S3 같은 AWS 서비스와의 연결에는 적용할 수 없는 방식이다.

> 💡 **시험 꿀팁**: "EC2에서 S3로 가는 트래픽이 인터넷을 거치면 안 된다"는 조건에는 게이트웨이 VPC 엔드포인트가 표준 정답입니다.

**S3 Object Lambda**는 S3에서 객체를 반환하기 직전에 Lambda 함수를 통해 실시간으로 데이터를 가공할 수 있는 기능입니다. 원본 데이터는 하나의 S3 버킷에 단일 사본으로만 유지하면서, PII 처리가 허용된 애플리케이션에는 원본 그대로, 나머지 두 애플리케이션에는 PII를 마스킹·제거한 형태로 각각 다르게 반환하도록 Object Lambda 함수를 구성할 수 있습니다. 데이터 복제나 별도 프록시 계층 구축 없이 요청 시점에 처리되므로 운영 오버헤드가 가장 낮습니다.

**왜 다른 보기는 오답인가**
- A: 요청을 가로채 처리하는 프록시 계층을 직접 설계·구현·운영해야 하므로 관리형 서비스 조합보다 운영 부담이 훨씬 크다.
- C: 애플리케이션마다 변환된 데이터를 별도로 저장하면 테라바이트 규모의 데이터가 중복되어 스토리지 비용이 늘고, 원본이 갱신될 때마다 3곳을 모두 동기화해야 하는 부담이 생긴다.
- D: C와 동일한 데이터 중복·동기화 문제가 있으며, 테라바이트급 데이터를 다수의 DynamoDB 테이블로 중복 관리하는 것은 비용과 설계 측면 모두에서 비효율적이다.

> 💡 **시험 꿀팁**: "원본은 하나만 유지하면서 요청자에 따라 다르게 가공된 데이터를 돌려줘야 한다"는 조건에는 S3 Object Lambda가 표준 정답입니다.

## QUESTION 296

**문제**: 개발 팀이 개발용 VPC 내부의 Amazon EC2 인스턴스에서 새 애플리케이션을 출시했습니다. 솔루션 설계자는 동일한 계정에 새 VPC를 생성하고, 이 새 VPC를 개발용 VPC와 피어링해야 합니다. 개발용 VPC의 CIDR 블록은 192.168.0.0/24입니다. 솔루션 설계자는 개발용 VPC와의 VPC 피어링 연결에 유효한, 새 VPC의 CIDR 블록 중 가장 작은 것을 선택해야 합니다. 이 요구 사항을 충족하는 CIDR 블록은 무엇입니까?

**보기**
- A. 10.0.1.0/32 (VPC CIDR 블록의 허용 크기는 /16~/28 사이인데 /32는 이 범위를 벗어나 VPC에 할당할 수 없는 크기임)
- B. 192.168.0.0/24 (개발용 VPC의 CIDR 블록과 완전히 동일해 겹치므로, VPC 피어링 연결 시 CIDR이 중복되지 않아야 한다는 조건을 위반함)
- C. 192.168.1.0/32 (개발용 VPC와는 겹치지 않지만, /32 역시 VPC CIDR 허용 범위(/16~/28)를 벗어나 유효하지 않은 크기임)
- D. **10.0.1.0/24**

**정답: D**

**해설**
VPC의 CIDR 블록 크기는 **/16(가장 큼)에서 /28(가장 작음) 사이**여야 하며, VPC 피어링 연결을 맺으려는 두 VPC의 CIDR 블록은 서로 겹치지 않아야 합니다. 보기 중 /32 크기의 블록(A, C)은 애초에 VPC에 할당할 수 없는 크기이고, 192.168.0.0/24(B)는 기존 개발용 VPC의 CIDR과 완전히 겹칩니다. 따라서 겹치지 않으면서 동시에 유효한 VPC CIDR 크기 범위 안에 있는 10.0.1.0/24가 요구 사항을 만족하는 가장 작은(그리고 유일하게 유효한) 선택입니다.

**왜 다른 보기는 오답인가**
- A: /32는 호스트 하나만을 가리키는 크기로, VPC의 최소 CIDR 크기인 /28보다도 작아 VPC에 할당할 수 없다.
- B: 개발용 VPC의 CIDR 블록과 동일해 완전히 겹치므로 피어링 연결에 사용할 수 없다.
- C: 겹치지는 않지만 A와 마찬가지로 /32 크기는 VPC CIDR로 허용되지 않는다.

> 💡 **시험 꿀팁**: "VPC 피어링용 CIDR을 고르라"는 문제에서는 항상 (1) VPC CIDR은 /16~/28 범위여야 하고 (2) 피어링 대상과 겹치면 안 된다는 두 조건을 함께 확인해야 합니다.

- C: Auto Scaling 그룹의 용량 범위만 설정하고 조정 정책이 없으면, 인스턴스 수는 CPU 사용률 변화와 무관하게 고정되어 자동 확장이 이뤄지지 않는다.
- D: 경보와 알림까지는 자동화되지만 실제 인스턴스 수 조정은 사람이 로그인해 수동으로 처리해야 하므로 완전한 자동화라고 볼 수 없다.

> 💡 **시험 꿀팁**: "비용 최적화와 급증 대응을 동시에 자동화하라"는 조건에는 대상 추적 조정 정책 기반의 Auto Scaling(예: ASGAverageCPUUtilization 목표값 설정)이 표준 정답입니다.

## QUESTION 298

**문제**: 한 회사가 ALB 뒤의 Amazon EC2 인스턴스에서 중요한 비즈니스 애플리케이션을 운영하고 있습니다. EC2 인스턴스는 Auto Scaling 그룹에서 실행되며 Amazon RDS DB 인스턴스에 접근합니다. EC2 인스턴스와 DB 인스턴스가 모두 단일 가용 영역에 있어 설계가 운영 검토를 통과하지 못했습니다. 솔루션 설계자는 두 번째 가용 영역을 활용하도록 설계를 변경해야 합니다. 애플리케이션의 가용성을 높이는 솔루션은 무엇입니까?

**보기**
- A. 각 가용 영역에 서브넷을 하나씩 프로비저닝하고, 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성한다. DB 인스턴스는 각 네트워크에 연결되도록 구성한다. (RDS DB 인스턴스를 "각 네트워크에 대한 연결"로 구성하는 것은 RDS의 표준 고가용성 메커니즘이 아니며, Multi-AZ 배포를 사용하지 않음)
- B. 두 가용 영역에 걸쳐 확장되는 두 개의 서브넷을 프로비저닝하고, 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성한다. DB 인스턴스는 각 네트워크에 연결되도록 구성한다. (서브넷은 하나의 가용 영역에만 속할 수 있어 "두 가용 영역에 걸쳐 확장되는 서브넷"이라는 전제 자체가 AWS VPC 구조상 불가능함)
- C. **각 가용 영역에 서브넷을 하나씩 프로비저닝하고, 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성한다. DB 인스턴스는 Multi-AZ 배포로 구성한다.**
- D. 두 가용 영역에 걸쳐 확장되는 서브넷을 프로비저닝하고, 두 가용 영역에 EC2 인스턴스를 배포하도록 Auto Scaling 그룹을 구성한다. DB 인스턴스는 Multi-AZ 배포로 구성한다. (B와 마찬가지로 서브넷이 여러 가용 영역에 걸쳐 있을 수 있다는 전제 자체가 잘못됨)

**해설**
Amazon VPC에서 서브넷은 반드시 **하나의 가용 영역에만** 속하도록 생성되며, 여러 가용 영역에 걸쳐 있는 서브넷은 만들 수 없습니다. 따라서 두 번째 가용 영역을 사용하려면 각 가용 영역마다 별도의 서브넷을 프로비저닝해야 합니다. Auto Scaling 그룹을 두 가용 영역의 서브넷 모두에 걸치도록 구성해 EC2 인스턴스를 분산 배치하고, RDS DB 인스턴스는 **Multi-AZ 배포**로 전환해 다른 가용 영역에 동기식으로 복제되는 대기 인스턴스를 두면, 애플리케이션 계층과 데이터베이스 계층 모두에서 가용 영역 장애에 대한 내성을 확보할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: RDS 고가용성은 Multi-AZ 배포 기능을 통해 구현해야 하며, "각 네트워크에 대한 연결"이라는 구성 방식은 RDS가 제공하는 표준 장애 조치 메커니즘이 아니다.
- B: 서브넷은 하나의 가용 영역에 종속되는 리소스이므로 "두 가용 영역에 걸쳐 확장되는 서브넷"은 애초에 생성할 수 없다.
- D: B와 동일하게 서브넷이 여러 가용 영역에 걸칠 수 있다는 전제가 AWS VPC 구조에 맞지 않아 실현 불가능한 설계다.

> 💡 **시험 꿀팁**: "서브넷이 여러 가용 영역에 걸쳐 있다"는 표현이 보기에 나오면 그 보기는 항상 오답입니다 — 서브넷은 하나의 가용 영역에만 속합니다. RDS의 표준 고가용성 솔루션은 Multi-AZ 배포입니다.

## QUESTION 299

**문제**: 한 연구소가 약 8TB 규모의 데이터를 처리해야 하며, 스토리지 하위 시스템에 1밀리초 미만의 지연 시간과 최소 6GBps의 처리량이 필요합니다. Amazon Linux를 실행하는 수백 대의 EC2 인스턴스가 데이터를 배포하고 처리합니다. 이 성능 요구 사항을 충족하는 솔루션은 무엇입니까?

**Amazon FSx for Lustre**는 수백~수천 대의 컴퓨팅 인스턴스가 동시에 접근하는 고성능 컴퓨팅(HPC) 워크로드를 위해 설계된 병렬 파일 시스템으로, SSD 기반 스토리지를 사용하면 밀리초 미만의 지연 시간과 수 GBps급의 높은 처리량을 제공합니다. S3를 데이터 리포지토리로 연결하면 원시 데이터를 파일 시스템으로 가져오고, 처리 결과를 다시 S3로 내보낼 수 있습니다. **영구(Persistent) SSD** 배포 유형을 선택하면 파일 시스템이 중지되더라도 데이터가 디스크에 안전하게 보존됩니다.

**왜 다른 보기는 오답인가**
- A: 계층화 정책 ALL은 콜드 데이터를 자동으로 저비용 스토리지 계층으로 옮기는 기능으로, 오히려 접근 지연을 늘릴 수 있어 초저지연·고처리량 요구에 반한다.
- C: HDD 기반 스토리지는 SSD보다 지연 시간이 길고 처리량도 낮아 1밀리초 미만 지연, 6GBps 이상 처리량이라는 엄격한 성능 목표를 만족하기 어렵다.
- D: FSx for NetApp ONTAP는 다양한 프로토콜을 지원하는 범용 NAS에 강점이 있지만, 수백 대 규모의 컴퓨팅 노드가 병렬로 접근하는 HPC급 워크로드에서 요구하는 초고처리량 확보에는 FSx for Lustre만큼 최적화되어 있지 않다.

> 💡 **시험 꿀팁**: "수백 대의 컴퓨팅 인스턴스가 동시에 접근하며 밀리초 미만 지연·초고처리량이 필요하다"는 조건에는 FSx for Lustre(영구 SSD)가 표준 정답입니다.

## QUESTION 300

**문제**: 한 회사가 하드웨어 용량 제약으로 인해 온프레미스 데이터 센터의 레거시 애플리케이션을 AWS 클라우드로 마이그레이션해야 합니다. 이 애플리케이션은 연중무휴 24시간 실행되며, 데이터베이스 스토리지 사용량은 시간이 지남에 따라 계속 증가합니다. 이 요구 사항을 가장 비용 효율적으로 충족하기 위해 솔루션 설계자는 무엇을 해야 합니까?

**보기**
- A. 애플리케이션 계층을 Amazon EC2 스팟 인스턴스로, 데이터 스토리지 계층을 Amazon S3로 마이그레이션한다. (스팟 인스턴스는 언제든 회수될 수 있어 24시간 연속 운영이 필수인 워크로드에 부적합하며, S3는 객체 스토리지로 관계형 데이터베이스 스토리지 계층을 대체할 수 없음)
- B. 애플리케이션 계층을 Amazon EC2 예약 인스턴스로, 데이터 스토리지 계층을 Amazon RDS 온디맨드 인스턴스로 마이그레이션한다. (24시간 상시 운영되는 데이터베이스에도 예약 인스턴스를 적용하면 더 큰 비용 절감이 가능한데, 온디맨드로만 유지해 절감 기회를 놓치게 됨)
- C. **애플리케이션 계층을 Amazon EC2 예약 인스턴스로, 데이터 스토리지 계층을 Amazon Aurora 예약 인스턴스로 마이그레이션한다.**
- D. 애플리케이션 계층을 Amazon EC2 온디맨드 인스턴스로, 데이터 스토리지 계층을 Amazon RDS 예약 인스턴스로 마이그레이션한다. (애플리케이션 계층 역시 24시간 연속 실행되는 예측 가능한 워크로드이므로 온디맨드보다 예약 인스턴스가 더 비용 효율적인데 이 기회를 놓침)

**정답: C**

**해설**
애플리케이션이 24시간 365일 예측 가능하게 계속 실행되는 스테디 스테이트(steady-state) 워크로드이므로, 1년·3년 단위로 약정해 큰 폭의 할인을 받는 **예약 인스턴스**가 EC2 애플리케이션 계층에 가장 비용 효율적입니다. 데이터베이스 계층은 스토리지가 계속 증가하는 관계형 워크로드이므로, MySQL·PostgreSQL 호환 완전관리형 서비스인 **Amazon Aurora**를 예약 인스턴스로 사용하면 RDS 대비 더 높은 처리 성능과 스토리지 자동 확장(최대 128TiB)을 제공받으면서도 예약을 통해 비용을 절감할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 스팟 인스턴스는 회수 시 애플리케이션이 중단될 수 있어 24시간 상시 가동이 필요한 레거시 애플리케이션에 적합하지 않고, S3는 객체 스토리지라 관계형 데이터베이스 스토리지 계층을 대체할 수 없다.
- B: 데이터 스토리지 계층을 RDS 온디맨드로 유지하면, 예측 가능한 24시간 워크로드임에도 예약을 통한 할인 기회를 살리지 못해 비용 효율이 떨어진다.
- D: 애플리케이션 계층을 온디맨드로 유지하면 마찬가지로 예측 가능한 상시 워크로드에 대한 예약 할인 기회를 놓치게 된다.

> 💡 **시험 꿀팁**: "24시간 연중무휴로 실행되는 예측 가능한 워크로드"라는 조건에는 온디맨드가 아닌 예약 인스턴스(또는 Savings Plans)가 표준 정답이며, 스토리지가 계속 증가하는 관계형 워크로드에는 Aurora가 RDS보다 흔히 더 적합한 선택입니다.
