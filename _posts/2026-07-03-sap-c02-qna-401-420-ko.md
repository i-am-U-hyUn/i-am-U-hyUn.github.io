## QUESTION 401

**문제**: 회사가 지사에 서드파티 SD-WAN 어플라이언스를 운영 중이며, 이 어플라이언스를 통해 다수의 지사 네트워크를 AWS의 Transit Gateway에 **GRE 터널 기반으로 동적 라우팅(BGP)과 함께 직접 연결**하고 싶다. VPN 연결이 아닌, SD-WAN 벤더의 가상 어플라이언스와 네이티브하게 통합되는 방법을 원한다. 솔루션은?

**보기**
- A. 각 지사에서 Transit Gateway로 표준 Site-to-Site VPN 연결 구성(표준 VPN도 가능하지만, SD-WAN 어플라이언스와의 네이티브 GRE 통합이라는 요구에는 맞지 않으며 SD-WAN 벤더 생태계와의 최적화된 통합을 제공하지 않음).
- B. **Transit Gateway Connect를 사용해, GRE 터널을 통해 SD-WAN 어플라이언스를 Transit Gateway에 연결하고, Transit Gateway Connect 피어를 통한 BGP 동적 라우팅을 구성.**
- C. 각 지사에 Direct Connect를 개별적으로 구축(SD-WAN 벤더 어플라이언스와의 통합이 목적이 아니라 전용 회선 자체를 새로 구축하는 것으로, 비용과 구축 기간이 크게 늘어나며 이 문제의 요구와 다름).
- D. 지사 네트워크를 각각 VPC로 간주해 VPC 피어링으로 Transit Gateway 없이 직접 연결(피어링은 SD-WAN 어플라이언스와의 GRE 기반 동적 라우팅 통합을 지원하지 않으며, 다수 지사 규모에는 확장성도 없음).

**정답: B**

**해설**
**Transit Gateway Connect**는 기존 VPN 연결이 아닌 **GRE 터널**을 통해 서드파티 SD-WAN 어플라이언스를 Transit Gateway에 직접 연결할 수 있게 해주는 기능입니다. Transit Gateway Connect 피어를 통해 **BGP 동적 라우팅**을 구성하면, SD-WAN 벤더의 가상 어플라이언스와 네이티브하게 통합되어 대역폭도 표준 VPN보다 높은 처리량을 지원합니다. 다수의 지사를 SD-WAN 어플라이언스 경유로 Transit Gateway에 연결하는 표준적인 방법입니다.

**왜 다른 보기는 오답인가**
- A: 표준 VPN은 가능한 연결 방식이지만 SD-WAN 어플라이언스와의 네이티브 GRE 통합이라는 특정 요구에는 맞지 않습니다.
- C: Direct Connect는 전용 회선 구축이 목적이며, SD-WAN 어플라이언스 통합이라는 이 문제의 핵심과 무관합니다.
- D: VPC 피어링은 GRE 기반 동적 라우팅 통합이나 다수 지사 확장성을 지원하지 않습니다.

> 💡 **시험 꿀팁**: 서드파티 **SD-WAN 어플라이언스를 GRE 터널 기반으로 Transit Gateway에 네이티브 통합**하려면 **Transit Gateway Connect**가 표준 정답입니다.

## QUESTION 402

**문제**: 회사가 레거시 상용 데이터베이스 애플리케이션을 RDS로 마이그레이션하고 싶은데, 이 애플리케이션은 데이터베이스 **운영체제 수준의 접근**(커스텀 에이전트 설치, 레지스트리 설정 변경, 서드파티 백업 도구 등)이 필요해 표준 RDS의 관리형 제약(OS 접근 불가)으로는 요구를 충족할 수 없다. 그럼에도 RDS 수준의 자동화된 백업, 패치, 고가용성 같은 관리형 이점은 최대한 누리고 싶다. 솔루션은?

**보기**
- A. 표준 RDS 인스턴스를 사용하고 애플리케이션 요구사항을 포기(OS 수준 접근이 필요한 애플리케이션 요구사항 자체를 충족하지 못해 마이그레이션이 불가능해짐).
- B. **RDS Custom을 사용해, 기본 운영체제와 데이터베이스 인스턴스에 대한 SSH/RDP 접근 권한을 확보하고 커스텀 설정을 적용하면서도, RDS의 자동화된 백업·모니터링·고가용성 같은 관리형 기능은 그대로 활용.**
- C. EC2에 데이터베이스를 자체 설치해 완전한 자체 관리형으로 전환(OS 접근은 확보되지만, RDS가 제공하는 자동화된 백업/패치/고가용성 관리 기능을 모두 포기하고 직접 구현/관리해야 함).
- D. Aurora로 전환해 RDS Custom for Aurora 없이 표준 Aurora 사용(표준 Aurora도 OS 수준 접근을 허용하지 않아 애플리케이션의 커스텀 요구사항을 충족하지 못함).

**정답: B**

**해설**
**RDS Custom**은 표준 RDS와 완전 자체 관리형 EC2 데이터베이스의 중간 지점을 제공하는 서비스로, 기본 운영체제와 데이터베이스 인스턴스에 대한 **SSH/RDP 접근**을 허용해 커스텀 에이전트 설치나 레지스트리 설정 변경 같은 OS 수준 커스터마이징을 가능하게 하면서도, RDS의 **자동화된 백업, 패치, 모니터링, 고가용성** 같은 관리형 기능의 상당 부분을 그대로 유지합니다. 레거시 상용 애플리케이션의 특수한 OS 수준 요구사항과 RDS의 관리형 이점을 동시에 얻고자 할 때 사용하는 표준 서비스입니다.

**왜 다른 보기는 오답인가**
- A: 표준 RDS는 OS 접근 자체를 허용하지 않아 애플리케이션 요구사항을 충족하지 못합니다.
- C: EC2 자체 관리형 전환은 OS 접근은 얻지만 RDS의 모든 관리형 이점을 포기해야 합니다.
- D: 표준 Aurora도 RDS와 마찬가지로 OS 수준 접근을 제공하지 않습니다.

> 💡 **시험 꿀팁**: **OS 수준 커스터마이징이 필요한 레거시 데이터베이스 애플리케이션**을 RDS의 관리형 이점(백업/패치/고가용성)을 유지하며 마이그레이션하려면 **RDS Custom**이 표준 정답입니다.

## QUESTION 403

**문제**: 보안 팀이 조직의 200개 계정에 흩어진 ALB와 CloudFront 배포에 **동일한 AWS WAF 규칙 세트**를 중앙에서 적용하고, 신규로 생성되는 리소스에도 자동으로 이 규칙이 적용되도록 강제하고 싶다. 각 계정의 관리자가 WAF 설정을 개별적으로 변경하거나 규칙 적용을 우회하지 못하도록 하려면?

**보기**
- A. 각 계정 관리자에게 표준 WAF 규칙 세트를 배포하고 적용하도록 안내(안내만으로는 강제력이 없어 계정별로 규칙이 누락되거나 다르게 적용될 위험이 큼).
- B. **AWS Firewall Manager를 사용해 조직 차원의 WAF 정책을 정의하고, 이를 조직 내 모든 계정(및 신규 계정)의 대상 리소스(ALB, CloudFront 등)에 자동으로 적용하며, 개별 계정에서의 규칙 변경/우회를 중앙에서 지속적으로 강제 및 교정.**
- C. 각 계정에서 개별적으로 WAF 웹 ACL을 생성한 뒤 CloudFormation StackSets로 배포(StackSets로 초기 배포는 가능하지만, 이후 개별 계정에서 규칙이 변경/삭제되는 것을 지속적으로 감지하고 자동으로 재교정하는 기능은 Firewall Manager가 전용으로 제공).
- D. SCP로 WAF 관련 API 호출 자체를 모두 차단(WAF API 호출을 전면 차단하면 정당한 규칙 관리 작업까지 막혀버리며, 중앙 정책을 적용하는 것이 아니라 단순히 모든 사용을 막는 것이므로 목적에 부합하지 않음).

**정답: B**

**해설**
**AWS Firewall Manager**는 Organizations와 통합해 **조직 차원의 보안 정책**(WAF 규칙, Shield Advanced 보호, 보안 그룹 등)을 중앙에서 정의하고, 이를 조직 내 모든 계정과 리소스(기존 및 신규)에 **자동으로 적용**합니다. 개별 계정에서 정책이 변경되거나 리소스가 정책 범위를 벗어나면 Firewall Manager가 이를 지속적으로 감지해 **자동으로 재교정(remediation)**하므로, 계정 관리자가 임의로 규칙을 우회하는 것을 중앙에서 효과적으로 방지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 안내만으로는 강제력이 없어 일관된 적용을 보장하지 못합니다.
- C: StackSets는 초기 배포에는 유용하지만, 이후 지속적인 감지/재교정 기능은 Firewall Manager가 전용으로 제공하는 강점입니다.
- D: WAF API 전면 차단은 정당한 관리 작업까지 막아 실용적이지 않으며 중앙 정책 배포라는 목적과 다릅니다.

> 💡 **시험 꿀팁**: 다중 계정에 **WAF/보안 정책을 중앙에서 적용하고 신규 계정/리소스에도 자동 강제 및 지속적으로 재교정**하려면 **AWS Firewall Manager**가 표준 정답입니다.

## QUESTION 404

**문제**: 회사가 S3 버킷에 대해 얼마 전 교차 리전 복제(CRR) 규칙을 새로 설정했는데, 이 규칙은 **설정 시점 이후에 업로드된 객체에만** 적용된다는 사실을 알게 되었다. 규칙 설정 이전부터 이미 버킷에 존재하던 수백만 개의 기존 객체도 소급해서 다른 리전으로 복제하고 싶다. 솔루션은?

**보기**
- A. 복제 규칙을 삭제했다가 다시 생성(규칙을 재생성해도 여전히 재생성 시점 이후의 신규 객체에만 적용되며, 기존 객체를 소급 복제하는 기능은 아님).
- B. **S3 배치 복제(S3 Batch Replication)를 사용해, 복제 규칙 생성 이전부터 존재하던 기존 객체들을 대상으로 일회성 복제 작업을 실행해 대상 리전으로 소급 복제.**
- C. 모든 기존 객체를 다운로드한 뒤 다른 리전의 버킷에 직접 재업로드(수백만 개 객체를 수동으로 다운로드/재업로드하는 것은 시간과 비용이 막대하며 비효율적).
- D. 라이프사이클 정책으로 기존 객체를 다른 스토리지 클래스로 전환(스토리지 클래스 전환은 리전 간 복제와는 무관한 별개의 기능).

**정답: B**

**해설**
표준 S3 복제 규칙은 규칙이 **활성화된 시점 이후에 업로드/변경된 객체**에만 적용됩니다. 규칙 생성 이전부터 존재하던 기존 객체까지 복제하려면 **S3 배치 복제(S3 Batch Replication)**를 사용해야 하며, 이는 S3 Batch Operations를 기반으로 기존 객체 목록에 대한 일회성 복제 작업을 대규모로 실행해, 수백만 개에 달하는 기존 객체도 효율적으로 대상 리전에 소급 복제할 수 있게 해줍니다.

**왜 다른 보기는 오답인가**
- A: 규칙을 재생성해도 소급 적용되지 않으며 여전히 향후 신규 객체에만 적용됩니다.
- C: 수동 다운로드/재업로드는 대량 객체에서 매우 비효율적입니다.
- D: 라이프사이클 정책은 스토리지 클래스 전환용이며 리전 간 복제 기능이 아닙니다.

> 💡 **시험 꿀팁**: S3 복제 규칙 설정 **이전부터 존재하던 기존 객체를 소급해서 복제**하려면 **S3 배치 복제(S3 Batch Replication)**가 표준 정답입니다.

## QUESTION 405

**문제**: Auto Scaling 그룹에서 인스턴스가 스케일 인(축소)으로 종료되기 전에, 해당 인스턴스에 남아있는 애플리케이션 로그를 중앙 로그 저장소로 완전히 전송(드레이닝)한 뒤에 종료되도록 하고 싶다. 로그 전송이 끝나기 전에 인스턴스가 갑자기 종료되면 로그 유실이 발생한다. 솔루션은?

**보기**
- A. 인스턴스의 종료 방지(termination protection)만 활성화(종료 방지는 실수로 인한 수동 종료를 막는 기능이며, Auto Scaling의 정상적인 스케일 인 프로세스에 의한 종료를 제어하거나 지연시키는 기능은 아님).
- B. **Auto Scaling 수명 주기 후크(lifecycle hook)를 종료(Terminating) 상태에 구성해, 인스턴스가 실제로 종료되기 전 대기 상태에서 로그 드레이닝 스크립트를 실행할 시간을 확보하고, 완료 후 CompleteLifecycleAction을 호출해 종료를 진행.**
- C. 인스턴스 종료 시 자동으로 실행되는 UserData 스크립트만 작성(UserData는 인스턴스가 시작될 때 실행되는 것이 표준이며, 종료 시점에 실행을 보장하는 표준 메커니즘이 아니고, Auto Scaling의 종료 프로세스와 통합된 대기/완료 신호 체계도 없음).
- D. CloudWatch 이벤트로 종료 예정 인스턴스를 감지해 별도 Lambda가 사후에 로그를 수집(인스턴스가 이미 종료된 후에는 로그에 접근할 수 없어 사후 수집이 불가능함).

**정답: B**

**해설**
**Auto Scaling 수명 주기 후크(lifecycle hook)**를 **Terminating** 상태에 구성하면, 인스턴스가 실제로 종료되기 전에 **정의된 시간 동안 대기 상태**를 유지합니다. 이 대기 시간 동안 로그 드레이닝 스크립트(예: SSM Run Command나 인스턴스 내 에이전트를 통해)를 실행해 남은 로그를 완전히 전송한 뒤, **CompleteLifecycleAction** API를 호출하면 그제서야 인스턴스 종료가 진행됩니다. 이는 스케일 인 시 데이터 유실 없이 정상적인 정리 작업을 보장하는 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- A: 종료 방지는 수동 종료 실수를 막는 기능이며 Auto Scaling의 자동 스케일 인 프로세스와는 무관합니다.
- C: UserData는 시작 시점 실행이 표준이며, 종료 시점의 대기/완료 신호 체계를 제공하지 않습니다.
- D: 인스턴스가 이미 종료된 후에는 로그 데이터에 접근할 수 없어 사후 수집이 불가능합니다.

> 💡 **시험 꿀팁**: Auto Scaling **스케일 인 시 인스턴스가 종료되기 전에 정리 작업(로그 드레이닝 등)을 완료**시키려면 **수명 주기 후크(lifecycle hook, Terminating 상태)**가 표준 정답입니다.

## QUESTION 407

**문제**: 보안 팀이 사내 EC2 인스턴스나 컨테이너가 알려진 악성 도메인이나 최근 등록된 의심스러운 도메인으로 DNS 조회를 시도할 경우, 이를 **DNS 계층에서 자동으로 차단**하고 싶다. 애플리케이션이나 인스턴스별로 개별 설정을 하지 않고 VPC 전체에 걸쳐 이를 강제하려면?

**보기**
- A. 각 인스턴스의 로컬 hosts 파일에 알려진 악성 도메인을 수동으로 등록해 차단(수동 관리이며 악성 도메인 목록이 계속 갱신되어야 하므로 확장성이 없고, 인스턴스별 개별 설정이 필요해 요구사항에 반함).
- B. **Route 53 Resolver DNS Firewall을 사용해, VPC 수준에서 도메인 목록 기반의 규칙(AWS 관리형 위협 목록 포함)을 구성해 악성/의심 도메인에 대한 DNS 쿼리를 자동으로 차단하거나 알림 처리.**
- C. 보안 그룹 아웃바운드 규칙으로 특정 IP 대역 차단(악성 도메인은 IP가 계속 바뀔 수 있어 IP 기반 차단만으로는 비효율적이며, 이는 DNS 계층이 아닌 네트워크 계층의 통제).
- D. 각 인스턴스에 서드파티 DNS 필터링 소프트웨어를 개별 설치(인스턴스마다 개별 설치/관리가 필요해 VPC 전체에 걸친 중앙 강제라는 요구에 반함).

**정답: B**

**해설**
**Route 53 Resolver DNS Firewall**은 VPC 수준에서 DNS 쿼리에 대한 필터링 규칙을 정의할 수 있는 기능으로, AWS가 관리하는 **위협 인텔리전스 기반 도메인 목록**(악성코드, 봇넷 등)을 규칙에 연결하거나 커스텀 도메인 목록을 만들어 특정 도메인에 대한 DNS 조회를 **차단(BLOCK), 허용(ALLOW), 알림(ALERT)** 처리할 수 있습니다. 이를 VPC의 리졸버 규칙 그룹에 연결하면 개별 인스턴스 설정 없이 VPC 전체에 일괄 적용되어, DNS 계층에서 악성 도메인 통신을 원천 차단하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 수동 hosts 파일 관리는 확장성이 없고 인스턴스별 개별 작업이 필요합니다.
- C: 보안 그룹은 IP 기반 통제이며, 악성 도메인의 IP가 자주 바뀌는 특성상 비효율적이고 DNS 계층의 통제가 아닙니다.
- D: 서드파티 소프트웨어의 개별 설치는 VPC 전체 중앙 강제라는 요구에 반합니다.

> 💡 **시험 꿀팁**: VPC 전체에서 **악성/의심 도메인에 대한 DNS 쿼리를 중앙에서 자동 차단**하려면 **Route 53 Resolver DNS Firewall**이 표준 정답입니다.

**문제**: 모바일 앱 개발팀이 오프라인 상태에서도 앱을 사용할 수 있어야 하고(오프라인 중 변경 사항을 로컬에 저장했다가 온라인 복귀 시 자동 동기화), 특정 데이터가 변경될 때 연결된 모든 클라이언트에게 실시간으로 알려주는(실시간 구독) 기능도 필요하다. GraphQL 기반의 유연한 API를 선호한다. 이 모든 요구를 관리형으로 충족하는 서비스는?

**보기**

**AWS AppSync**는 관리형 **GraphQL** 서비스로, DynamoDB·Lambda·RDS 등 여러 데이터 소스를 하나의 GraphQL API로 통합해 유연하게 쿼리할 수 있게 해줍니다. 특히 모바일/웹 SDK를 통해 **오프라인 상태에서의 로컬 데이터 캐싱과 온라인 복귀 시 자동 동기화(충돌 해결 포함)**를 기본 지원하며, GraphQL **구독(subscription)** 기능으로 특정 데이터 변경을 연결된 모든 클라이언트에게 실시간으로 푸시할 수 있습니다. 이는 모바일 앱의 오프라인 우선(offline-first) 및 실시간 요구사항을 모두 관리형으로 충족하는 표준 서비스입니다.

- C: Amazon MQ는 메시지 브로커이며 GraphQL API나 내장 오프라인 동기화 기능이 없습니다.
- D: 정적 캐싱은 동적 쿼리, 실시간, 오프라인 쓰기 동기화 요구를 전혀 충족하지 못합니다.

> 💡 **시험 꿀팁**: 모바일 앱에 **GraphQL API + 오프라인 데이터 동기화 + 실시간 구독**이 모두 필요하면 **AWS AppSync**가 표준 정답입니다.

> 💡 **시험 꿀팁**: EC2/ECR/Lambda에 대한 **자동화된 지속적 CVE 취약점 스캔과 위험 점수 산정**이 필요하면 **Amazon Inspector**가 표준 정답입니다.

**Direct Connect 게이트웨이**는 하나의 Direct Connect 연결(특정 리전에 위치한 프라이빗 가상 인터페이스)을 **전 세계 여러 리전에 있는 다수의 VPC**(각 VPC의 가상 프라이빗 게이트웨이나 Transit Gateway를 통해)와 연결할 수 있게 해주는 글로벌 리소스입니다. 이를 통해 리전마다 별도의 값비싼 Direct Connect 연결을 구축할 필요 없이, 단일 연결로 전 세계에 분산된 다수의 VPC와 온프레미스 네트워크를 효율적으로 연결할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 리전마다 개별 연결을 구축하는 것은 문제에서 이미 비용이 너무 크다고 밝힌 접근입니다.
- C: 모든 VPC를 단일 리전으로 통합하는 것은 다중 리전 아키텍처 요구 자체를 제한하는 불필요한 조치입니다.
- D: 인터넷 기반 VPN은 Direct Connect의 이점을 포기하는 것이며, 기존 Direct Connect 활용이라는 문제의 취지와 다릅니다.

> 💡 **시험 꿀팁**: 하나의 Direct Connect 연결을 **여러 리전에 있는 다수의 VPC와 연결**하려면 **Direct Connect 게이트웨이(Direct Connect Gateway)**가 표준 정답입니다.

## QUESTION 411

**문제**: 전자상거래 회사가 DynamoDB의 주문 테이블에 새 주문이 추가되거나 상태가 변경될 때마다, 이를 실시간으로 감지해 재고 시스템 업데이트, 이메일 알림 발송 같은 후속 처리를 이벤트 기반으로 트리거하고 싶다. 별도의 폴링 없이 테이블의 변경 사항 자체를 이벤트 소스로 사용하는 방법은?

**보기**
- A. 애플리케이션이 주기적으로 테이블을 스캔(Scan)해 이전 상태와 비교(폴링 기반 스캔은 비용이 크고 지연이 발생하며 실시간성이 떨어지고, 대규모 테이블에서는 매우 비효율적).
- B. **DynamoDB 스트림(Streams)을 활성화해, 테이블의 항목 수준 변경 사항(삽입/수정/삭제)을 캡처하는 스트림을 Lambda 함수의 이벤트 소스로 연결해, 변경 발생 시 실시간으로 Lambda가 트리거되어 후속 처리 수행.**

**정답: B**

**해설**
**DynamoDB 스트림**은 테이블의 항목이 삽입, 수정, 삭제될 때마다 그 변경 사항을 시간순으로 캡처하는 기능입니다. 이 스트림을 **Lambda 함수의 이벤트 소스**로 연결하면, 폴링 없이 테이블 변경이 발생하는 즉시 Lambda가 자동으로 트리거되어 재고 업데이트, 알림 발송 같은 이벤트 기반 후속 처리를 실시간으로 수행할 수 있습니다. 이는 DynamoDB 기반의 변경 데이터 캡처(CDC) 패턴을 구현하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 주기적 스캔은 실시간성이 떨어지고 대규모 테이블에서 비용/성능 부담이 매우 큽니다.
- C: 관계형 DB로의 마이그레이션은 불필요한 재설계이며, DynamoDB 자체에서 스트림 기능을 제공합니다.
- D: CloudTrail은 API 호출 감사에 특화되어 있으며 항목 수준 실시간 변경 처리에는 DynamoDB Streams가 더 적합합니다.

> 💡 **시험 꿀팁**: DynamoDB 테이블의 **항목 수준 변경 사항을 실시간 이벤트로 감지해 후속 처리를 트리거**하려면 **DynamoDB 스트림(Streams) + Lambda**가 표준 정답입니다.

## QUESTION 414

**문제**: 배치 처리 워크로드가 Spot Instance를 광범위하게 사용하는데, 특정 하나의 인스턴스 유형에만 의존하다 보니 해당 유형의 스팟 용량이 부족해지면 전체 작업이 중단되는 문제가 반복된다. 여러 인스턴스 유형에 걸쳐 스팟 용량을 다양화하면서, 중단 가능성이 낮은 용량 풀을 우선적으로 선택하도록 하려면?

**보기**
- A. Auto Scaling 그룹에서 단일 인스턴스 유형만 계속 사용하되 여러 리전에 그룹을 복제(여러 리전 복제는 관리 복잡도를 높이며, 이 문제의 핵심인 "여러 인스턴스 유형에 걸친 스팟 다양화" 요구를 직접 해결하지 못함).
- B. **Auto Scaling 그룹에서 혼합 인스턴스 정책(mixed instances policy)을 구성해 여러 개의 호환 가능한 인스턴스 유형을 지정하고, 스팟 할당 전략을 용량 최적화(capacity-optimized)로 설정해 중단 가능성이 낮은 용량 풀에서 우선적으로 스팟 인스턴스를 시작.**
- C. 스팟 할당 전략을 최저가(lowest-price)로만 설정(최저가 전략은 비용은 최소화할 수 있지만 특정 저렴한 유형에 요청이 몰려 오히려 중단 가능성이 높아질 수 있음 — 중단 최소화가 목표라면 용량 최적화가 더 적합).
- D. 모든 인스턴스를 On-Demand로 전환(스팟의 비용 이점을 완전히 포기하는 것이며, 문제는 스팟 사용을 유지하면서 다양화하는 방법을 묻고 있음).

**정답: B**

**해설**
Auto Scaling 그룹의 **혼합 인스턴스 정책(mixed instances policy)**을 사용해 여러 호환 가능한 인스턴스 유형(크기가 비슷한 다양한 패밀리 등)을 지정하면, 스팟 용량을 여러 유형/풀에 걸쳐 다양화할 수 있어 특정 하나의 유형에서 용량이 부족해져도 다른 유형에서 계속 용량을 확보할 수 있습니다. 여기에 스팟 할당 전략을 **용량 최적화(capacity-optimized)**로 설정하면, 단순히 가장 저렴한 풀이 아니라 **현재 중단 가능성이 가장 낮은 용량 풀**에서 우선적으로 인스턴스를 시작해, 중단 빈도를 최소화하면서도 스팟의 비용 이점을 유지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 여러 리전 복제는 관리 복잡도만 늘릴 뿐 단일 유형 의존이라는 근본 문제를 해결하지 못합니다.
- C: 최저가 전략은 특정 저렴한 유형에 수요가 몰려 오히려 중단 위험이 커질 수 있습니다.
- D: On-Demand 전환은 스팟의 비용 이점을 포기하는 것으로 문제의 취지와 다릅니다.

> 💡 **시험 꿀팁**: Spot Instance의 **중단 가능성을 최소화하면서 여러 인스턴스 유형에 걸쳐 다양화**하려면 **혼합 인스턴스 정책 + 용량 최적화(capacity-optimized) 할당 전략**이 표준 정답입니다.

- C. 각 계산 노드에 로컬 인스턴스 스토어만 사용하고 노드 간 데이터 공유는 애플리케이션에서 직접 구현(로컬 스토어는 노드 간 공유가 안 되어 병렬 HPC 워크로드의 공유 파일 시스템 요구 자체를 충족하지 못함).
- D. S3를 파일 시스템처럼 직접 마운트해 사용(S3는 객체 스토리지이며 POSIX 파일 시스템 시맨틱이나 이 정도의 낮은 지연시간을 기본적으로 제공하지 않아 HPC 스크래치 워크로드에 부적합).

**정답: B**

**해설**
**Amazon FSx for Lustre**는 HPC, 머신러닝 같은 컴퓨팅 집약적 워크로드를 위해 설계된 고성능 병렬 파일 시스템으로, 초당 수백 GB의 처리량과 낮은 지연시간을 제공하며 **POSIX 호환**입니다. S3와 네이티브로 연동되어, S3의 데이터를 파일 시스템으로 지연 로딩(lazy loading)하고, 계산이 끝난 결과를 다시 S3로 내보낼 수 있어, 컴퓨팅 노드 간 공유 스크래치 공간이 필요한 HPC 워크로드에 최적화된 표준 서비스입니다.

**왜 다른 보기는 오답인가**
- A: EFS도 POSIX 호환 공유 파일 시스템이지만, 이 정도 규모의 초고성능(수백 GB/s) HPC 스크래치 요구에는 FSx for Lustre가 특화되어 있습니다.
- C: 로컬 인스턴스 스토어는 노드 간 공유가 불가능해 병렬 워크로드의 공유 파일 시스템 요구를 충족하지 못합니다.
- D: S3는 객체 스토리지로 POSIX 시맨틱을 기본 제공하지 않아 HPC 스크래치 용도로 직접 사용하기에는 부적합합니다.

> 💡 **시험 꿀팁**: HPC 워크로드에 **초고성능(수백 GB/s), 낮은 지연시간의 POSIX 호환 공유 스크래치 파일 시스템(S3 연동 포함)**이 필요하면 **Amazon FSx for Lustre**가 표준 정답입니다.

**왜 다른 보기는 오답인가**
- A: 개별 cron 설정은 중앙 관리나 통합된 준수 현황 가시성을 제공하지 못합니다.
- C: 수동 순차 접속 패치는 이 문제가 개선하고자 하는 비효율적인 현재 방식 그대로입니다.
- D: AMI 교체 방식은 무상태 인스턴스에 적합하며, 이 문제의 패치 관리/준수 확인이라는 목적과는 접근 방식이 다릅니다.

> 💡 **시험 꿀팁**: 대규모 EC2 플릿의 **패치 적용을 자동화하고 준수 현황을 중앙에서 확인**하려면 **AWS Systems Manager Patch Manager**(패치 기준선 + 유지 관리 기간)가 표준 정답입니다.

## QUESTION 420

**문제**: IT 운영 팀이 자주 반복되는 표준 운영 작업(예: "디스크 공간 부족 인스턴스에서 로그 정리 후 서비스 재시작", "특정 태그가 붙은 인스턴스의 보안 그룹 규칙 감사")을 **매번 수동 스크립트 실행이 아닌, 승인된 반복 가능한 절차(runbook)**로 표준화하고, 실행 이력을 감사 추적할 수 있게 하고 싶다. 솔루션은?

**보기**
- A. 각 작업을 개별 셸 스크립트로 작성해 필요할 때마다 담당자가 수동으로 실행(수동 실행 방식 자체는 유지되며, "표준화된 절차"와 "실행 이력 감사 추적"이라는 요구를 충족하지 못함).
- B. **AWS Systems Manager Automation을 사용해, 반복 작업을 문서(런북)로 정의하고 사전 승인된 절차로 표준화하며, 실행 시마다 파라미터·실행 단계·결과가 기록되어 감사 추적이 가능하도록 구성.**
- C. 각 작업을 Lambda 함수로 재작성해 수동으로 호출(Lambda로 재작성하는 것도 가능한 방법이지만, 표준화된 운영 런북 형식, 승인 워크플로우 통합, 각 단계별 상세 실행 기록 같은 SSM Automation의 운영 특화 기능은 제공하지 않음).
- D. 모든 작업 절차를 위키 문서로만 작성해 사람이 수동으로 따라하도록 안내(문서화만으로는 실행 자체가 자동화되지 않고, 실행 이력에 대한 시스템적인 감사 추적도 제공되지 않음).

**정답: B**

**해설**
**AWS Systems Manager Automation**은 반복적인 운영 작업을 **문서(런북)**로 정의해 표준화하고, 필요시 승인 워크플로우와 연계해 실행할 수 있는 서비스입니다. 런북이 실행될 때마다 사용된 파라미터, 각 실행 단계의 상태, 최종 결과가 자동으로 기록되어, 감사관이나 운영 팀이 언제 누가 어떤 절차를 실행했는지 **감사 추적**할 수 있습니다. 이는 수동 스크립트 실행을 표준화되고 감사 가능한 운영 절차로 전환하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 개별 스크립트의 수동 실행은 표준화나 감사 추적 요구를 충족하지 못합니다.
- C: Lambda 재작성도 가능한 방법이지만, SSM Automation이 제공하는 운영 특화 런북 형식과 상세 실행 기록/감사 기능을 기본 제공하지는 않습니다.
- D: 문서화만으로는 실행 자동화나 시스템적인 감사 추적이 이루어지지 않습니다.

> 💡 **시험 꿀팁**: 반복적인 운영 작업을 **승인된 표준 절차(런북)로 표준화하고 실행 이력을 감사 추적**하려면 **AWS Systems Manager Automation**이 표준 정답입니다.
