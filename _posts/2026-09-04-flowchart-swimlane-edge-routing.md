## 1. 전체 통합 맵에서 선을 다 그리면 안 되는 이유

레이아웃 코드에는 원래 "Airflow DAG처럼 연결선을 그리는 전제로 배치한다"는 주석이 남아있다. 즉 처음 접근은 모든 엣지를 실제 선으로 이어서, DAG 도구처럼 좌→우로 흐르는 그림을 그리는 것이었다.

문제는 스윔레인(부서/시스템별 가로 구획) 통합 맵에서는 **레인을 넘나드는 분기·반려 엣지가 유독 많다**는 점이었다. 딜 유형을 세 갈래로 나누는 분기, 검토 반려로 이전 단계로 되돌아가는 롤백, macro 단계에서 하위 상세 그룹으로 진입하는 계층 엣지까지 전부 선으로 그리면, 노드 20개짜리 작은 그래프인데도 선이 교차하며 뒤엉켜 정작 중요한 순차 흐름조차 눈에 안 들어왔다.

해결한 방향은 **엣지 종류에 따라 "그리는 방식"을 다르게 하는 것**이었다.

- **순차(sequence) 엣지**: 실선으로 그린다 (레인 안에서 흐르는 정상 흐름)
- **분기(branch) / 반려(rollback) / 계층(hierarchy) 엣지**: 화면에 선을 그리지 않고, 출발 노드에 "다음 →" **뱃지(라벨)**로 붙인다

```ts
// 화면엔 선을 안 그리지만(프론트가 렌더 생략), hover 하이라이트용으로 엣지는 내려준다
src.branches.push({ label: e.label ?? "", target: tgt.label, targetId: e.to });
```

실제 엣지 데이터 자체는 API 응답에 그대로 포함시켜서 hover 하이라이트에는 쓰되, 전체 맵 렌더링에서는 선 대신 텍스트 뱃지로 대체한 것이다. Detail/Step처럼 노드 수가 적은 뷰에서는 분기·반려도 선으로 그리고, 노드가 많이 몰리는 전체 통합 맵에서만 뱃지 방식을 쓰도록 나눴다.

## 2. 도형 판별에서 반려 엣지를 빼야 했던 이유

1편에서 다룬 `decideShape`가 실제로 맞아떨어지려면, 차수(진입/진출) 계산 단계에서부터 반려 엣지를 제외해야 했다.

```ts
for (const e of edges) {
  if (e.kind === "rollback") continue; // 롤백은 정상 흐름 차수에서 제외
  ...
}
```

반려는 "정상 검토 완료 → 다음 단계"가 아니라 "문제가 있어서 이전 단계로 되돌아가는" 예외 흐름이다. 이걸 일반 진출 엣지와 똑같이 세면, 실제로는 흐름의 끝(terminator)인 노드도 반려 경로 하나 때문에 진출 차수가 1 이상으로 잡혀 도형이 틀어진다. 반려는 도형 판별에서는 없는 셈 치고, 화면에는 별도로 빨간 점선 + "반려" 뱃지로 표시하는 쪽으로 역할을 분리했다.

## 3. 레이아웃: 외부 엔진 대신 직접 짠 위상정렬

프론트엔드에는 `@dagrejs/dagre`, `elkjs` 같은 그래프 레이아웃 엔진이 이미 의존성으로 들어 있었지만, 실제 노드 배치 로직은 이 라이브러리들을 쓰지 않고 직접 구현했다. 코드에 남긴 이유는 이렇다.

> 레이아웃 계산 (외부 엔진 없이 순수 위상정렬 기반 — 예측 가능/안정적)

범용 그래프 레이아웃 엔진은 강력하지만 그래프 구조가 조금만 바뀌어도 배치가 크게 흔들릴 수 있다. 이 프로젝트는 "시스템/부서별 레인은 항상 같은 위치, 흐름은 항상 좌→우"라는 강한 제약이 있는 도메인이라, 범용 엔진의 자유도가 오히려 예측 불가능성으로 돌아왔다. 그래서 필요한 만큼만 직접 짰다.

```ts
// 컬럼 = 전역 위상 레벨 (레인 무관, 흐름 순서 그대로)
// → 레인별로 컬럼을 재부여하지 않으므로 A→B 선은 항상 좌→우로 흐른다
const level = computeLevels(nodes, forwardEdgesOnly); // rollback/hierarchy 제외
```

- **X(컬럼)**: 반려·계층 엣지를 뺀 순방향 그래프로 위상정렬한 전역 레벨 — 레인과 무관하게 흐름 순서 그대로
- **Y(레인)**: 시스템/부서별로 고정된 가로 구획
- 같은 (레벨, 레인)에 여러 노드가 몰리면 서브행(subRow)으로 세로 분리해 겹침 방지
- 노드에 분기 뱃지가 여러 개 붙으면 카드 높이가 늘어나는 걸 감안해서, 레인 본문 높이를 노드 실제 렌더 높이 기준으로 재계산

## 4. 그래도 남는 문제 — 핸들 자동 선택과 예외 하드코딩

레인과 컬럼으로 큰 틀을 잡아도, 두 노드 사이에 다른 노드가 끼어 있으면 직선으로 이으면 선이 그 노드를 관통한다. 그래서 경로가 막혔는지(`pathBlocked`) 판단해 막혀 있으면 아래로 우회(`detour`)시키는 핸들 선택 로직을 따로 뒀다.

```ts
const pathBlocked = () => {
  const loX = Math.min(s.x, t.x) + NODE_WIDTH * 0.5;
  const hiX = Math.max(s.x, t.x) + NODE_WIDTH * 0.5;
  return others.some((o) => {
    const cx = o.x + NODE_WIDTH / 2, cy = o.y + NODE_HEIGHT / 2;
    return cx > loX + 5 && cx < hiX - 5 && Math.abs(cy - (s.y + NODE_HEIGHT / 2)) < NODE_HEIGHT;
  });
};
```

인접한 레인을 세로로 넘나드는 우회선은 꺾이는 지점(`centerY`)을 두 레인 사이 여백의 정중앙에 고정해서, 어느 쪽 레인 경계선과도 겹치지 않게 했다. 우회선이 여러 개 몰릴 때도 출발/도착 노드별로 순번을 매겨 offset을 차등 적용해 선끼리 겹치지 않게 했다.

그런데도 자동 로직만으로는 안 풀리는 케이스가 하나 남았다. 특정 두 노드(견적 제출 단계 → 계약서 작성 단계) 사이 연결은 일반 규칙대로 처리하면 레인을 한 단계 건너뛰며 수직으로 꺾이는 부자연스러운 모양이 나왔다. 이건 규칙을 더 정교하게 다듬는 대신, **그 한 쌍만 예외로 명시적으로 하드코딩**해서 오른쪽에서 나와 왼쪽으로 들어가는 자연스러운 형태로 고정했다.

```ts
// 특정 연결: 레인을 내려가는 수직 꺾임 대신, 오른쪽에서 나와 왼쪽으로 들어가는 형태로 표시
if (e.id === "D5->C1:sequence") {
  return { e, pick: { sourceHandle: "r", targetHandle: "l" } };
}
```

일반화된 규칙으로 모든 케이스를 커버하려는 대신, 규칙이 안 맞는 소수의 예외는 코드에 그대로 드러내 놓고 관리하는 쪽을 택한 것이다. 그래프가 22개 엣지 규모로 작았기 때문에 가능했던 실용적인 판단이었다.

## 5. 자동 배치가 안 예쁘면, 결국 사람이 고칠 수 있게

레이아웃 알고리즘과 예외 처리를 아무리 다듬어도 100% 만족스러운 배치가 나오지 않는 경우는 남는다. 그래서 마지막 안전판으로 **엣지를 직접 드래그해서 수정할 수 있는 편집 모드**를 만들었다.

- 편집 모드를 켜야만 선의 관절(waypoint)과 시작/끝 앵커가 드래그 가능해짐 (실수로 건드리는 걸 방지)
- 드래그 제스처가 "시작"할 때만 이전 상태를 스택에 쌓아 `Ctrl+Z` 실행취소 지원 (마우스 이동마다 쌓으면 한 번의 undo로 거의 안 움직여서 무의미)
- "저장" 버튼을 눌러야만 서버(`layout.json`)로 반영되고, 그 전까지는 로컬 상태
- 저장할 때마다 덮어쓰기 전 상태를 이력(`layout.history.json`, 최근 20개)에 남겨서, 저장한 뒤에도 "이전 버전" 버튼으로 되돌릴 수 있게 함

레이아웃 알고리즘이 커버 못 하는 나머지는 소프트웨어로 완전히 자동화하기보다, 사람이 마지막 미세조정을 할 수 있는 도구를 주는 쪽으로 실용적으로 타협한 것이다.

## 6. 정리

작은 그래프(노드 20개, 엣지 22개)라도 "부서/시스템별 스윔레인 + 순차/분기/반려/계층이 섞인 흐름"이라는 조건이 붙으면 렌더링 난이도가 확 올라간다는 걸 이번에 체감했다. 이번에 적용한 원칙을 정리하면:

1. 엣지 종류별로 표현 방식을 다르게 한다 (순차=선, 분기/반려/계층=뱃지)
2. 도형 판별 같은 그래프 알고리즘에는 역방향(rollback) 엣지를 명시적으로 제외한다
3. 도메인에 강한 제약(레인 고정, 좌→우 흐름)이 있으면 범용 레이아웃 엔진보다 직접 짠 규칙이 더 예측 가능하다
4. 규칙으로 안 풀리는 소수의 예외는 숨기지 않고 코드에 명시적으로 남긴다
5. 그래도 안 되는 부분은 자동화 대신 사람이 고칠 수 있는 도구(편집 모드 + undo + 이력)로 넘긴다
