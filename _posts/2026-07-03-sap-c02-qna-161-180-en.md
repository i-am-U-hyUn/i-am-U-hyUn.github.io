## QUESTION 161

**Question**: A telecom company connected to on-premises via Direct Connect. Application on EC2 (multiple AZs) behind an internal ALB (TLS terminates at the ALB, path-based routing). The company plans to deploy an on-premises firewall using an **IP address-based allow list**. Design a solution allowing traffic while keeping client access.

**Choices**
- A. Configure the existing ALB to use a static IP + assign IPs across AZs + add ALB IPs to the firewall (ALBs don't support static IPs).
- B. **Create an NLB, associate it with one static IP per AZ, create an ALB-type target group on the NLB and add the existing ALB, add the NLB's IP to the firewall, and update clients to connect to the NLB.**
- C. Create an NLB, add existing target groups directly to the NLB, delete the ALB (loses the ALB's path-based routing capability).
- D. Create a Gateway Load Balancer, add the ALB as a target group (GWLB is for traffic inspection, mismatched purpose here).

**Correct Answer: B**

**Explanation**
**ALBs do not support static/fixed IPs.** When a fixed IP is needed for an IP allow list, the standard solution is placing an **NLB (which supports static IPs) in front of the ALB, connecting the existing ALB via an ALB-type target group** on the NLB. This preserves the ALB's path-based routing.

**Why the other choices are wrong**
- A: ALBs cannot be assigned static IPs.
- C: Deleting the existing ALB loses path-based routing (multiple target groups) functionality.
- D: Gateway Load Balancer is for inserting traffic inspection appliances — a different purpose than obtaining a static IP.

> 💡 **Exam tip**: **ALBs cannot have static IPs.** When a static IP is required, remember the pattern: **place an NLB in front and connect the ALB as a target group.**

## QUESTION 162

**Question**: A private-subnet EC2 fleet behind an internet-facing ALB, which is the origin for a CloudFront distribution with an AWS-managed-rules WAF web ACL attached. The company needs internet traffic to be unable to reach the ALB **directly.** Minimal operational overhead solution?

**Choices**
- A. Create a new web ACL with the same rules and attach it to the ALB.
- B. Attach the existing web ACL to the ALB (only inspects requests — doesn't block direct access).
- C. **Add a security group rule to the ALB allowing traffic only from the AWS-managed prefix list for CloudFront.**
- D. Manually list CloudFront IP ranges and add allow rules to the ALB's security group.

**Correct Answer: C**

**Explanation**
Using the **AWS-managed prefix list for CloudFront origin traffic** in a security group rule allows only traffic from CloudFront while blocking direct internet access — with AWS automatically keeping the list updated, minimizing operational overhead.

**Why the other choices are wrong**
- A, B: Web ACLs inspect request content — they don't block direct network access to the ALB itself.
- D: Manually managing CloudFront's IP ranges requires updating whenever they change — high operational overhead.

> 💡 **Exam tip**: To restrict an origin (ALB/EC2) to **CloudFront-only access**, use the **AWS-managed prefix list (com.amazonaws.global.cloudfront.origin-facing)** in the security group — the minimal-overhead standard answer.

## QUESTION 163

**Question**: ElastiCache for Redis (encryption at rest is configured) used as a caching layer. **In-transit encryption is not configured**, and users can access it without authentication. Require authentication and switch to end-to-end encryption.

**Choices**
- A. Generate an AUTH token + store in Parameter Store (encrypted parameter) + create a **new cluster**.
- B. **Generate an AUTH token + store in Secrets Manager + configure the existing cluster with the AUTH token and in-transit encryption. Look it up from Secrets Manager and use it for authentication when needed.**
- C. Generate an SSL certificate + store in Secrets Manager + create a new cluster (Redis auth uses AUTH tokens, not SSL certificates).
- D. SSL certificate + Parameter Store + update existing cluster (same certificate misconception).

**Correct Answer: B**

**Explanation**
ElastiCache for Redis authentication uses **AUTH tokens** (not SSL certificates), and storing them in **AWS Secrets Manager** (purpose-built for sensitive credential management) while **updating the existing cluster** to configure AUTH and in-transit encryption is correct.

**Why the other choices are wrong**
- A: Parameter Store can also store encrypted parameters, but Secrets Manager is more suited to credential/secret management, and there's no need to create a new cluster — the existing one can be updated.
- C, D: Redis's authentication mechanism is an **AUTH token**, not an SSL certificate — a conceptual error.

> 💡 **Exam tip**: **ElastiCache for Redis user authentication uses AUTH tokens** (not SSL certificates), and best practice stores the token in **Secrets Manager.** The existing cluster can be updated with AUTH + in-transit encryption.

## QUESTION 164

**Question**: A compute workload runs on Spot Instances in an Auto Scaling group (launch template, 2 placement groups, single instance type). Recent monitoring shows instance launch failures causing increased wait times for system users. Improve overall workload reliability.

**Choices**
- A. Replace the launch template with a launch configuration and use attribute-based instance type selection (launch configurations are an older feature that don't support attribute-based selection).
- B. **Create a new launch template version using attribute-based instance type selection. Configure the Auto Scaling group to use the new launch template version.**
- C. Update the launch template's Auto Scaling group to increase the number of placement groups (unrelated to the single-instance-type Spot availability issue).
- D. Update the launch template to use a larger instance type (leaves the single-type dependency problem unchanged).

**Correct Answer: B**

**Explanation**
Relying on a single instance type causes launch failures when that type's Spot capacity runs short. **Attribute-Based Instance Type Selection (ABIS)** lets Auto Scaling automatically choose from a pool of instance types matching required attributes (vCPU, memory, etc.), making it far more resilient to capacity shortages for any single type.

**Why the other choices are wrong**
- A: Launch configurations are an older feature and don't support modern features like ABIS.
- C: Increasing placement groups is unrelated to the Spot capacity/launch failure issue.
- D: Switching to a larger single instance type still leaves the root problem — dependence on a single type.

> 💡 **Exam tip**: Spot Instance launch failures caused by **dependence on a single instance type** are best solved with **Attribute-Based Instance Type Selection (ABIS)**, leveraging a pool of multiple types.

## QUESTION 165

**Question**: A Linux document processing server (generating ~5 documents/second, cannot be immediately updated to support the S3 API — a legacy constraint) needs **fast local access** to files it creates, and after processing, files must be publicly downloadable from S3 within 30 minutes. Minimal-effort solution?

**Choices**
- A. Migrate the application to Lambda (violates the constraint that the legacy server can't be immediately rewritten).
- B. **Set up an Amazon S3 File Gateway and configure a file share connected to document storage. Mount the file share on the EC2 instance via NFS. Trigger a RefreshCache API call to update the S3 File Gateway when changes occur.**
- C. Configure FSx for Lustre (import/export policy, linked to S3) + install Lustre clients and mount via NFS (Lustre uses its own Lustre protocol, not NFS — a conceptual error).
- D. Configure AWS DataSync connected to the EC2 instance + sync generated files to S3 (File Gateway better suits the requirement for immediate local-like access and automatic reflection).

**Correct Answer: B**

**Explanation**
**Amazon S3 File Gateway** is purpose-built for exactly this scenario: the legacy server accesses files quickly as if local (via NFS/SMB), while the gateway automatically syncs data to S3 in the background — requiring zero server code changes.

**Why the other choices are wrong**
- A: Immediately migrating the server to Lambda violates the "cannot be immediately updated for S3 API support" constraint.
- C: FSx for Lustre uses its own Lustre client/protocol, not NFS, so it doesn't match "mount using NFS."
- D: DataSync is closer to batch-style syncing; File Gateway is more natural for scenarios needing immediate, local-filesystem-like access.

> 💡 **Exam tip**: When a **legacy server can't support the S3 API but needs fast local-file-like access**, the standard answer is **Storage Gateway (S3 File Gateway)** — the server mounts it via NFS/SMB like a local filesystem, while it syncs to S3 in the background.

## QUESTION 166

**Question**: A serverless shipping solution with multiple microservices; a central user service stores critical data in DynamoDB, while other microservices store copies of sensitive data in their own storage. When a user is deleted, **all** microservices must immediately delete their copies too.

**Choices**
- A. DynamoDB Streams → publish to SQS via Lambda → each microservice polls the queue (a single queue delivers each message to only one consumer — unsuitable for fan-out).
- B. DynamoDB event notification → SNS topic → each microservice subscribes (DynamoDB tables don't have a native "event notification" feature like this — must go through Streams).
- C. **Configure the central user service to publish an event to a custom EventBridge event bus when deleting a user. Create an EventBridge rule per microservice (matching the delete event pattern) that invokes each microservice's own deletion logic.**
- D. Publish a message to an SQS queue + use SQS "event filters" for each microservice to delete (SQS's single-consumer model is unsuitable for fanning out to multiple microservices).

**Correct Answer: C**

**Explanation**
Fanning a single event out to **multiple independent microservices** is exactly what **Amazon EventBridge** (publish-subscribe model, each service subscribing via its own rule) is designed for. SQS is fundamentally a single-consumer (competing consumers) model, unsuitable for fanning the same event out to multiple services.

**Why the other choices are wrong**
- A, D: SQS queues deliver each message to only one consumer by default, failing the requirement that multiple microservices receive the same delete event simultaneously (an SNS fan-out pattern would be needed).
- B: DynamoDB tables themselves don't natively publish "event notifications" — this requires DynamoDB Streams.

> 💡 **Exam tip**: To **fan a single event out to multiple independent microservices**, use **EventBridge (or SNS)** — a single SQS queue is unsuitable for fan-out (though SNS+SQS combined works).

## QUESTION 167

**Question**: A VPC web application (ALB+WAF) must provide external customers with an **IP address** (presumably for their firewall allow lists). Minimal operational overhead solution?

**Choices**
- A. Replace the ALB with an NLB + assign an Elastic IP (loses the ALB's WAF/L7 features).
- B. Assign an Elastic IP directly to the ALB (ALBs cannot be assigned an EIP directly).
- C. **Create an AWS Global Accelerator standard accelerator. Designate the ALB as an endpoint. Provide the accelerator's static IP addresses to customers.**
- D. Configure a CloudFront distribution + ping the DNS name to determine the distribution's public IP addresses to give customers (CloudFront's IPs are numerous and not fixed).

**Correct Answer: C**

**Explanation**
**ALBs cannot have static IPs.** Placing **AWS Global Accelerator** in front of the ALB provides customers with **fixed static Anycast IP addresses** from the accelerator, while keeping the ALB (and its WAF) unchanged behind it.

**Why the other choices are wrong**
- A: Replacing with an NLB loses the AWS WAF functionality attached to the ALB.
- B: ALBs cannot be directly assigned an Elastic IP.
- D: CloudFront's edge IPs are numerous and not fixed, unsuitable for "give the customer a specific IP."

> 💡 **Exam tip**: When an ALB needs a **fixed IP** while retaining its L7 features (WAF, etc.), the standard answer is **AWS Global Accelerator** (providing fixed Anycast IPs).

## QUESTION 168

**Question**: Several development AWS accounts exist; production applications are about to move to AWS. EBS encryption at rest must apply **only to current and future production accounts.** A solution with built-in blueprints and guardrails is needed. (Choose three.)

**Choices**
- A. Use CloudFormation StackSets to deploy AWS Config rules to production accounts (not a guardrail/blueprint-based approach).
- B. Create a new AWS Control Tower landing zone from an existing developer account (landing zones must be created in the management/master account).
- C. **Create a new AWS Control Tower landing zone in the company's master (management) account. Add production and development accounts to respective OUs.**
- D. **Invite existing accounts to join the organization in AWS Organizations. Create SCPs to ensure compliance.**
- E. Create a guardrail in the master account to detect EBS encryption (guardrails must be applied at the OU level to scope to a specific OU).
- F. **Create a guardrail for the production OU to detect EBS encryption.**

**Correct Answer: C, D, F**

**Explanation**
The phrase "built-in blueprints and guardrails" points directly at **AWS Control Tower.** Create the landing zone in the **master account** (C), bring existing accounts into the Organizations/OU structure with SCPs enforcing compliance (D), and apply a guardrail detecting EBS encryption **only to the production OU** (F) — exactly matching "current and future production accounts only."

**Why the other choices are wrong**
- A: StackSets+Config is a valid approach but doesn't satisfy the explicit requirement for "built-in blueprints and guardrails" (a Control Tower-specific feature).
- B: A Control Tower landing zone must be created from the organization's **management (master) account** — not a regular developer account.
- E: Applying a guardrail at the master account level itself affects all OUs, failing "production accounts only."

> 💡 **Exam tip**: When you see "built-in blueprints/guardrails," **AWS Control Tower** is the answer's core. The landing zone must be created in the **management (master) account**, and guardrails are applied at the **specific OU level** to scope them.

## QUESTION 169

**Question**: A stateful web application (ALB behind 2 Linux EC2 + RDS MySQL). DNS records in Route 53. Goals: application layer RPO 2min/RTO 30min, database layer RPO 5min/RTO 30min. No major architecture changes, and optimal latency guaranteed post-failover.

**Choices**
- A. **Configure EC2 instances to use AWS Elastic Disaster Recovery + create a cross-Region read replica for RDS + create an ALB in the second Region + create a Global Accelerator endpoint associated with the ALB + update DNS to point to the Global Accelerator endpoint.**
- B. Use DLM to snapshot EBS volumes + configure RDS automated backups (cross-Region copy) + second-Region ALB + Global Accelerator (snapshot cycles too slow to meet RPO/RTO).
- C. AWS Backup (EC2+RDS) + cross-Region copy + second-Region ALB + CloudFront (backup-based, fails RPO requirement).
- D. DLM snapshots + RDS cross-Region read replica + second-Region ALB + Global Accelerator (uses snapshots instead of DRS for the EC2 layer — fails the 2-minute RPO).

**Correct Answer: A**

**Explanation**
Meeting a short 2-minute application-layer RPO requires **AWS Elastic Disaster Recovery (DRS)**'s continuous block-level replication (snapshot-based approaches are too slow). The database's 5-minute RPO is met with an **RDS cross-Region read replica**, and **AWS Global Accelerator** guarantees optimal network routing (latency) even after failover.

**Why the other choices are wrong**
- B, D: EBS snapshot (DLM)-based approaches replicate too infrequently to meet a few-minutes-scale RPO.
- C: AWS Backup is also fundamentally snapshot/backup-based, similarly struggling to meet a 2-minute RPO, and CloudFront isn't as suited to "guaranteed optimal latency" as Global Accelerator in this scenario (it's more focused on static content caching).

> 💡 **Exam tip**: For EC2 workloads needing a **short, minutes-scale RPO**, the answer is continuous replication via **AWS Elastic Disaster Recovery (DRS)**, not snapshots (DLM). For optimal post-failover latency, **AWS Global Accelerator** is the standard answer.

## QUESTION 170

**Question**: Optimize cost and rightsize EC2 instances in a single AWS account based on CPU/memory/network metrics. (Choose two.)

**Choices**
- A. Purchase Business/Enterprise Support (not strictly required just to see recommendations).
- B. Turn on Trusted Advisor and review "low-utilization Amazon EC2 instances" recommendations (memory metrics aren't included by default).
- C. **Install the CloudWatch agent and configure memory metric collection on EC2 instances.**
- D. **Configure AWS Compute Optimizer on the AWS account to receive findings and optimization recommendations.**
- E. Create EC2 Instance Savings Plans covering regions/families/OS of interest (a pricing discount tool, unrelated to rightsizing).

**Correct Answer: C, D**

**Explanation**
By default, CloudWatch **does not collect EC2 memory metrics**, so a **CloudWatch agent** must be installed for memory-based optimization (C). **AWS Compute Optimizer** then comprehensively analyzes CPU/network/memory (including this collected memory data) to provide concrete rightsizing recommendations (D).

**Why the other choices are wrong**
- A: Compute Optimizer is a free service — a paid support plan isn't required.
- B: Trusted Advisor's low-utilization instance check is useful but doesn't include memory metrics, and some checks require Enterprise/Business support — Compute Optimizer better fits this scenario's core need (memory-inclusive optimization).
- E: Savings Plans are a pricing discount program, unrelated to instance "size" optimization.

> 💡 **Exam tip**: EC2 **memory metrics** aren't collected by CloudWatch by default — requiring a **CloudWatch agent install** — and comprehensive rightsizing recommendations come from **AWS Compute Optimizer.**

## QUESTION 171

**Question**: CodeCommit repository data must be stored as a backup copy in a **second Region.**

**Choices**
- A. Configure AWS Elastic Disaster Recovery to replicate the repository (DRS is for server/volume replication, unrelated to CodeCommit repositories).
- B. Use AWS Backup to back up the CodeCommit repository hourly + create a cross-Region copy in the second Region (AWS Backup doesn't support CodeCommit as a resource type).
- C. **Create an EventBridge rule that invokes CodeBuild when code is pushed to the repository. Use CodeBuild to clone the repository, create a .zip file of the contents, and copy the file to an S3 bucket in the second Region.**
- D. Create a Step Functions workflow on an hourly schedule to create "snapshots" of the CodeCommit repository (no such snapshot concept exists for CodeCommit).

**Correct Answer: C**

**Explanation**
**AWS CodeCommit is not a supported resource for AWS Backup, nor does it natively offer cross-Region replication.** So a practical solution is a custom pipeline: **trigger CodeBuild via an EventBridge rule on code push, have CodeBuild clone the repo and zip it, then store the archive in an S3 bucket in the second Region.**

**Why the other choices are wrong**
- A: Elastic Disaster Recovery is for server/block volume replication, unrelated to Git repository replication.
- B: CodeCommit is not in AWS Backup's list of supported resources.
- D: There's no "snapshot" concept for CodeCommit.

> 💡 **Exam tip**: **CodeCommit is not supported by AWS Backup/DRS.** For cross-Region backup, the standard custom pipeline is **EventBridge (code-push trigger) + CodeBuild (clone/zip) + S3 (in another Region).**

## QUESTION 172

**Question**: Multiple business units, each with a separate account and multiple VPCs with **overlapping** CIDR ranges. The marketing team's new internal application must be accessible from all other business units (private IPs only). Minimal operational overhead solution?

**Choices**
- A. Add unique secondary CIDR ranges to each VPC + peer + private NAT (when CIDRs already overlap, peering itself is often impossible or highly complex).
- B. Create a virtual appliance EC2 instance in the marketing account + Site-to-Site VPN + NAT (heavy operational burden managing VPN/NAT translation).
- C. **Create an AWS PrivateLink endpoint service to share the marketing application. Grant connection permission to specific accounts. Create interface VPC endpoints in each account for private-IP access.**
- D. NLB + API Gateway private integration + IAM authorization (a more complex workaround than PrivateLink).

**Correct Answer: C**

**Explanation**
**VPC peering is not possible between VPCs with overlapping CIDR ranges** (making A largely infeasible in practice). **AWS PrivateLink (VPC endpoint service)** allows a consumer VPC to access the provider's service via private IPs through just an interface endpoint, regardless of CIDR overlap — exactly matching this scenario with minimal overhead.

**Why the other choices are wrong**
- A: When CIDRs overlap, VPC peering connections are technically impossible or severely limited.
- B: Directly building/managing a virtual appliance and VPN is far more operational burden than PrivateLink.
- D: Working around with API Gateway/NLB when the native PrivateLink feature exists is unnecessarily complex.

> 💡 **Exam tip**: To share a specific service via private IPs **between VPCs with overlapping CIDRs** (where peering is impossible), the standard answer is **AWS PrivateLink (interface VPC endpoint service).**

## QUESTION 173

**Question**: Audit the security posture of a newly acquired AWS account. Notification is needed **only when an S3 bucket becomes publicly exposed.** An SNS topic with the data security team's email already subscribed exists.

**Choices**
- A. Create S3 event notifications for isPublic events on all S3 buckets (no such "isPublic" event type exists for S3 event notifications).
- B. **Create an analyzer in IAM Access Analyzer. Create an EventBridge rule for the "Access Analyzer Finding" event type filtered on "isPublic: true". Set the SNS topic as the target.**
- C. Create an EventBridge rule filtered on CloudTrail "PutBucketPolicy" API calls (a policy change alone doesn't necessarily mean the bucket became public — inaccurate).
- D. Enable Config with the cloudtrail-s3-dataevents-enabled rule (checks CloudTrail data event logging status, not bucket public exposure — mismatched purpose).

**Correct Answer: B**

**Explanation**
**IAM Access Analyzer** continuously analyzes whether resources including S3 buckets are **exposed publicly**, publishing results ("Access Analyzer Finding") as EventBridge events. Using an `isPublic: true` filter sends an SNS notification precisely at the moment of public exposure.

**Why the other choices are wrong**
- A: No "isPublic" event type exists for S3 event notifications.
- C: Detecting the PutBucketPolicy API call itself is separate from whether the bucket actually became public — prone to false positives/negatives.
- D: The cloudtrail-s3-dataevents-enabled Config rule checks whether CloudTrail data event logging is enabled, unrelated to detecting bucket public exposure.

> 💡 **Exam tip**: To **continuously detect S3 bucket public exposure**, use **IAM Access Analyzer**, wiring its finding events to **EventBridge (`isPublic: true` filter) + SNS** — the standard pattern.

## QUESTION 174

**Question**: Evaluate the application/database portfolio of a newly acquired company (poorly documented on-premises data center) to build a migration business case. The number of existing applications/databases isn't immediately known. Traffic is variable (including month-end batch jobs). Understand the portfolio better before starting migration.

**Choices**
- A. Use SMS+DMS to assess migration + Service Catalog to understand dependencies (SMS/DMS are migration execution tools, not discovery/assessment tools).
- B. Use Application Migration Service + on-premises agent + Migration Hub + Storage Gateway to assess storage/database dependencies (Storage Gateway is a storage gateway service, not a dependency assessment tool).
- C. **Use Migration Evaluator to build a server inventory and generate a business-case report. Use Migration Hub to view the portfolio. Use AWS Application Discovery Service to understand application dependencies.**
- D. Use Control Tower in the target account to build the application portfolio + SMS for a deeper report and business case (Control Tower is an account governance tool, unrelated to portfolio discovery).

**Correct Answer: C**

**Explanation**
When documentation is poor and **you don't even know what exists**, the right combination is: **AWS Application Discovery Service** (agent/agentless discovery of servers, network, and process dependencies) to understand the actual infrastructure, **AWS Migration Evaluator** to build a business case (TCO) from this data, and **AWS Migration Hub** to view the overall portfolio and progress in one place.

**Why the other choices are wrong**
- A, B, D: SMS, Application Migration Service, Storage Gateway, and Control Tower are all tools for the migration execution/governance stage — not suited to the initial discovery stage when you don't even know what exists.

> 💡 **Exam tip**: When on-premises infrastructure is **undocumented and asset inventory is unknown**, the standard trio is **AWS Application Discovery Service (discovery) + Migration Evaluator (business case/TCO) + Migration Hub (portfolio view).**

## QUESTION 175

**Question**: An application running as a ReplicaSet on an EKS cluster (multiple AZs) generates **many small files** that must be accessible from all running instances. Files must be backed up and retained for 1 year. Solution providing the **fastest storage performance** while meeting these requirements?

**Choices**
- A. **Create an EFS file system + mount targets in each subnet (including nodes). Configure the ReplicaSet to mount EFS. Use AWS Backup to retain for 1 year.**
- B. Create an EBS volume + enable EBS Multi-Attach + mount to the ReplicaSet (Multi-Attach only works within the same AZ — violates the multi-AZ requirement).
- C. Create an S3 bucket and "mount" it like a filesystem (S3 isn't a filesystem and is unsuitable for low-latency random access to many small files).
- D. Configure each pod to store files using local storage + back up the EKS cluster with a third-party tool for 1 year (fails the shared-access requirement across instances).

**Correct Answer: A**

**Explanation**
A shared file system accessed simultaneously by **multiple pods spanning multiple Availability Zones** calls for **Amazon EFS.** Create mount targets in each AZ (subnet) to make it accessible from all nodes, and use **AWS Backup** to retain EFS data for 1 year.

**Why the other choices are wrong**
- B: EBS Multi-Attach is only supported **within the same Availability Zone**, failing this requirement of shared access across nodes spanning multiple AZs.
- C: S3 is object storage, not a filesystem, and unsuitable for low-latency random access to many small files.
- D: Pod-local storage fails the basic requirement that "all running instances" must be able to access the files.

> 💡 **Exam tip**: For a file store needing **simultaneous shared access from multiple containers/pods across multiple AZs**, **Amazon EFS** is the answer. Remember EBS Multi-Attach is limited to a single AZ.

## QUESTION 176

**Question**: A call center (phone answering + bidirectional text message surveys) must migrate from aging on-premises hardware to AWS for improved reliability. Minimal operational overhead solution?

**Choices**
- A. **Replace call center hardware with Amazon Connect + send text message surveys using Amazon Pinpoint.**
- B. Amazon Connect + send texts via Amazon SNS (SNS suits simple notifications, but Pinpoint is better suited to managing bidirectional conversational survey campaigns).

- B: SNS suits simple notification sending, but Pinpoint is more specialized for campaign-style messaging that receives and processes responses, like a "bidirectional" survey.

## QUESTION 177

**Question**: A DR strategy across AWS Regions for an Amazon Connect call center (dozens of contact flows, hundreds of users, dozens of claimed phone numbers). Which solution provides the **lowest RTO**?

**Choices**
- A. Availability-check Lambda (every 5 min) → notify ops team on failure → team manually provisions a new instance via the console (fully manual, high RTO).
- B. Pre-provision users in the second Region + availability-check Lambda (every 5 min) → deploy flows/phone numbers via CloudFormation on issue (phone number provisioning takes time).
- C. Pre-provision flows/phone numbers in the second Region + Route 53 health check/CloudWatch alarm → Lambda deploys **users** via CloudFormation (phone numbers already exist, but user provisioning takes time).
- D. **Pre-provision users and flows in the second Region (excluding phone numbers) + Route 53 health check/CloudWatch alarm → Lambda deploys only the claimed phone numbers via CloudFormation.**

**Correct Answer: D**

**Explanation**
Claimed phone numbers are often a uniquely-allocated resource that **cannot pre-exist simultaneously in two Regions** — making them the one element that can't be pre-provisioned. Since users and flows **can** be pre-provisioned, the lowest RTO comes from having everything ready in advance except automatically deploying **only the phone numbers** (the slowest, non-pre-provisionable piece) at failure time.

**Why the other choices are wrong**
- A: A fully manual process has the highest RTO.
- B: Deploying flows/phone numbers only at failure time is slower than pre-provisioning users alone (phone number provisioning is the bottleneck).
- C: Deploying users only at failure time is less efficient than pre-provisioning phone numbers/flows in advance — deferring the actual bottleneck (phone numbers), as in D, is better.

> 💡 **Exam tip**: For Amazon Connect DR, **users and contact flows can be pre-provisioned**, but **claimed phone numbers** are a resource that's tricky to pre-provision — automatically deploying them **only at failure time** is the key to the lowest RTO.

## QUESTION 178

**Question**: After ETL, data is stored in Redshift and delivered via FTP to multiple data customers, but the growing customer count makes management difficult. Switch to AWS Data Exchange, needing **customer identity verification** before sharing data, and customers must have access to **the latest data immediately upon publish.** Minimal operational overhead solution?

**Choices**
- A. Data Exchange for APIs + Redshift-API Gateway Data API integration + subscription verification (unnecessarily complex added API layer).
- B. **Create an AWS Data Exchange data share directly connecting AWS Data Exchange to the Redshift cluster in the data-producing account. Configure subscription verification. Require customers to subscribe to the data product.**
- C. Periodically download Redshift → S3 + Data Exchange for S3 + subscription verification (periodic downloads fail the "latest data upon publish" requirement).

- C: "Periodically" downloading from Redshift to S3 inevitably introduces delay, failing the "latest data upon publish" requirement.

> 💡 **Exam tip**: To share Redshift data with external customers in real time with identity verification, the answer is **AWS Data Exchange's Redshift data share integration + subscription verification** — a file-extraction/copy approach (via S3) fails the freshness requirement.

## QUESTION 179

**Question**: An event-processing solution must scale up/down based on incoming event volume. **When a processing error occurs, the event must move to a separate queue** for review.

**Choices**
- A. **Send event details to an SNS topic. Configure a Lambda function as a subscriber to process events. Add an on-failure destination to the function, set to an SQS queue.**
- B. Publish events to an SQS queue + an EC2 Auto Scaling group (scaling based on ApproximateAgeOfOldestMessage) + configure the application to write failed messages directly to a DLQ (directly managed EC2, more operational overhead than Lambda).
- C. Write events to a DynamoDB table + configure DynamoDB Streams → invoke a Lambda function (a valid event-processing pattern, but no clear built-in "move to a separate queue on error" path).
- D. Publish to an EventBridge event bus + create/run the application on EC2 in an Auto Scaling group behind an ALB (as target) + configure retries + write to a DLQ on failure (EC2-based, more operational overhead, and using an ALB as an event bus target isn't typical).

**Correct Answer: A**

**Explanation**
Lambda natively supports an **on-failure destination** for asynchronous invocations, automatically routing an event to a specified SQS queue (or SNS, EventBridge) when function execution fails. An SNS→Lambda setup scales fully managed, with no need to build separate failure-handling logic.

**Why the other choices are wrong**
- B, D: EC2-based processing carries far more operational overhead than Lambda's fully managed scaling and failure-handling.
- C: The DynamoDB Streams+Lambda combination is valid, but lacks a clear native mechanism for "move to a separate queue on error" (A's explicit Lambda on-failure destination is more precise).

> 💡 **Exam tip**: When a Lambda function must **automatically route events to a separate queue on processing failure**, use Lambda's **asynchronous invocation on-failure destination** feature (can target SQS/SNS/EventBridge).

## QUESTION 180

**Question**: Millions of devices across European logistics centers send data to a processing engine via a RESTful API to compute a sustainability index. The API experiences unpredictable traffic surges. **No data loss is allowed.**

**Choices**
- A. ALB + SQS (directly connecting SQS as a target group isn't supported — ALB target groups only support EC2/IP/Lambda) + Fargate ECS to process queue messages.
- B. **Create an Amazon API Gateway HTTP API implementing the RESTful API. Create an SQS queue. Create an API Gateway-SQS service integration (direct integration). Create a Lambda function to process queue messages.**
- C. API Gateway REST API + Auto Scaling EC2 fleet + API Gateway-Auto Scaling group proxy integration (this kind of direct proxy integration isn't typical and lacks a scalability buffer).
- D. CloudFront + Kinesis Data Streams (directly setting a data stream as a distribution origin isn't a typical architecture) + Lambda consumption.

**Correct Answer: B**

**Explanation**
API Gateway supports **direct service integration with SQS**, allowing incoming requests to be safely queued immediately without any backend compute resource. SQS acts as a buffer absorbing traffic surges, enabling **loss-free** processing at a controlled rate, while Lambda polls the queue and automatically scales with throughput.

**Why the other choices are wrong**
- A: ALB target groups cannot directly target SQS (only EC2/IP/Lambda).
- C: Direct proxy integration between API Gateway and an Auto Scaling group isn't a typical pattern, and lacks a buffer to absorb traffic surges, risking data loss.
- D: Placing CloudFront directly in front of Kinesis Data Streams is a mismatched architecture for this RESTful API ingestion scenario.

> 💡 **Exam tip**: To ingest API requests **without data loss amid unpredictable traffic surges**, the standard pattern is **API Gateway's direct SQS service integration** to immediately queue requests, with Lambda processing asynchronously.
