## QUESTION 221

**문제**: Organizations로 계정 관리. CPU/메모리 사용률이 낮은 모든 EC2 인스턴스 목록과 크기 축소 권장 사항 필요. 최소 노력 솔루션은?

**보기**
- A. AWS Marketplace 모니터링 도구 설치 + S3 저장 + Python 스크립트로 직접 분석(직접 구현이라 노력이 큼).
- B. **Systems Manager로 모든 EC2에 CloudWatch 에이전트 설치. 조직의 마스터 계정에 있는 AWS Cost Explorer에서 리소스 최적화 권장 사항 조회. 이를 이용해 조직 전체 계정의 저활용 인스턴스 크기 축소.**
- C. CloudWatch 에이전트 설치 + 각 계정의 Cost Explorer에서 개별 조회(마스터 계정에서 조직 전체를 한 번에 보는 것이 더 효율적 — 계정별 개별 조회는 비효율).
- D. CloudWatch 에이전트 설치 + Lambda로 지표 추출 + S3 저장 + Athena로 분석(직접 구현이라 노력이 큼).

**정답: B**

**해설**
**AWS Cost Explorer의 리소스 최적화(Rightsizing) 권장 사항**은 CloudWatch 에이전트가 수집한 메모리 지표를 포함해 CPU/메모리 사용률 기반의 구체적인 인스턴스 축소 권장을 자동으로 제공합니다. **조직의 마스터 계정**에서 조회하면 조직 전체 계정에 대한 통합 뷰를 한 번에 확인할 수 있어 최소 노력으로 요구사항을 만족합니다.

**왜 다른 보기는 오답인가**
- A, D: 자체 스크립트/Lambda/Athena로 분석 로직을 직접 구현하는 것은 Cost Explorer의 기본 제공 기능을 재발명하는 것으로 불필요하게 많은 노력이 듭니다.
- C: 각 계정에서 개별적으로 확인하는 것보다 마스터 계정에서 조직 전체를 한 번에 확인하는 것이 훨씬 효율적입니다.

> 💡 **시험 꿀팁**: 조직 전체의 **EC2 저활용 인스턴스 식별 및 크기 축소 권장**에는 **CloudWatch 에이전트(메모리 지표) + 마스터 계정의 AWS Cost Explorer 리소스 최적화 권장 사항**이 최소 노력 표준 정답입니다.

## QUESTION 222

**문제**: CloudFormation으로 배포된 Auto Scaling 그룹(3개 EC2)에서 사용자 지정 네트워크 분석 소프트웨어 실행, 트래픽 검사용 네트워크 라우팅 구성됨. 분석 소프트웨어가 멈추면 ASG가 인스턴스를 교체하지만 **네트워크 경로가 업데이트되지 않는** 문제. 해결 조합은? (3개 선택)

**보기**
- A. EC2 상태 확인 지표 기반 경보로 ASG가 실패 인스턴스 교체하도록 함(이미 ASG가 교체하고 있음 — 문제는 교체 후 라우팅 업데이트가 안 되는 것).
- B. **CloudFormation 템플릿 업데이트해 EC2에 CloudWatch 에이전트 설치. 애플리케이션 프로세스 지표를 CloudWatch로 전송하도록 구성.**
- C. Systems Manager Agent 설치 + 프로세스 메트릭 전송(CloudWatch 에이전트가 지표 수집의 표준 방법이며, SSM Agent는 이 용도가 아님).
- D. **실패 시나리오에 대해 CloudWatch에서 사용자 지정 지표 경보 생성. SNS 주제에 메시지를 게시하도록 경보 구성.**
- E. **SNS 메시지에 응답하는 Lambda 함수 생성해 서비스에서 인스턴스 제거, 교체 인스턴스를 가리키도록 네트워크 경로 업데이트.**
- F. CloudFormation 템플릿에 조건 작성해 대체 인스턴스 시작 시 네트워크 경로 업데이트(CloudFormation 자체는 런타임 이벤트에 반응해 스택 리소스를 동적으로 갱신하는 방식에 적합하지 않음 — Lambda+EventBridge/SNS 방식이 표준).

**정답: B, D, E**

**해설**
**CloudWatch 에이전트로 애플리케이션 프로세스 지표를 수집**하고(B), 이를 기반으로 **사용자 지정 지표 경보를 만들어 SNS로 알림**을 보내며(D), **Lambda가 이 SNS 메시지를 받아 실패한 인스턴스를 서비스에서 제거하고 새 인스턴스로 네트워크 경로를 업데이트**하는(E) 흐름이 "애플리케이션 프로세스 실패 → 자동 감지 → 라우팅 자동 갱신"을 완전히 자동화하는 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- A: 문제는 이미 ASG가 인스턴스를 교체하고 있다는 데 있는 것이 아니라, 교체 후 **네트워크 경로가 갱신되지 않는다**는 것이므로 이 보기는 핵심을 다루지 않습니다.
- C: 프로세스 지표 수집의 표준 도구는 CloudWatch 에이전트이며, Systems Manager Agent는 이 용도에 맞지 않습니다.
- F: CloudFormation 템플릿 자체의 정적 조건으로는 런타임에 발생하는 인스턴스 교체 이벤트에 동적으로 반응해 라우팅을 갱신할 수 없습니다 — 이벤트 기반 Lambda가 필요합니다.

> 💡 **시험 꿀팁**: **Auto Scaling으로 교체된 인스턴스에 맞춰 네트워크 경로를 자동 업데이트**해야 할 때는 **CloudWatch 사용자 지정 지표(애플리케이션 프로세스 상태) → 경보 → SNS → Lambda(라우팅 업데이트)**의 이벤트 기반 자동화 체인이 표준 정답입니다.

## QUESTION 223

**문제**: 마이크로서비스 기반 VOD 앱, 출시 시 500만 사용자 → 6개월 후 3천만 사용자. ECS(Fargate), HTTPS 사용. **블루/그린 배포**로 업데이트해야 하며, 로드 밸런서로 각 ECS 서비스에 트래픽 분산, CloudWatch 경보에 따라 **작업 수 자동 조정**.

**보기**
- A. 블루/그린 + NLB + 서비스 할당량 증가 요청(NLB는 HTTPS/L7 라우팅에 적합하지 않고, 할당량 증가는 자동 조정이 아님).
- B. 블루/그린 + NLB + Cluster Autoscaler(Cluster Autoscaler는 EKS/Kubernetes 개념이며 ECS와는 다름 — 개념 오류, NLB도 부적합).
- C. 블루/그린 + ALB + Cluster Autoscaler(Cluster Autoscaler는 ECS의 네이티브 기능이 아님 — 개념 오류).
- D. **블루/그린 배포 유형 + Application Load Balancer 사용하도록 ECS 서비스 구성. 각 ECS 서비스에 대해 Service Auto Scaling 구현.**

**정답: D**

**해설**
HTTPS 기반 트래픽 분산에는 **ALB**(L7 라우팅 지원)가 적합하며, ECS의 블루/그린 배포는 CodeDeploy와 함께 ALB를 사용하는 것이 표준입니다. 작업 수를 CloudWatch 경보에 따라 자동 조정하는 것은 ECS의 네이티브 기능인 **Service Auto Scaling**(Application Auto Scaling)입니다.

**왜 다른 보기는 오답인가**
- A, B: NLB는 L4(TCP) 로드 밸런서로, HTTPS 트래픽에 대한 세밀한 라우팅에는 ALB가 더 적합하며 블루/그린 ECS 배포의 표준 조합도 ALB입니다.
- B, C: **Cluster Autoscaler는 Kubernetes(EKS)의 개념**으로, ECS에는 해당 기능명이 존재하지 않습니다 — ECS는 Service Auto Scaling을 사용합니다.

> 💡 **시험 꿀팁**: **ECS의 블루/그린 배포**에는 **ALB**(NLB 아님)가 표준이며, 작업 수 자동 조정에는 **ECS Service Auto Scaling**을 사용하세요 — "Cluster Autoscaler"는 EKS/Kubernetes 용어로 ECS와 혼동하면 안 됩니다.

## QUESTION 224

**문제**: ECS(EC2, ASG)+ECR 컨테이너 애플리케이션. 새 이미지 태그마다 일반적 취약점(CVE) 스캔 필요. **심각도 높음/치명적 결과가 있는 이미지 태그는 자동 삭제**해야 하고, 삭제 시 개발 팀에 알려야 함.

**보기**
- A. **리포지토리 푸시 시 스캔 구성. 스캔 완료(치명적/높음 결과) 시 EventBridge로 Step Functions 상태 머신 호출. Step Functions로 해당 이미지 태그 삭제 + SNS로 개발 팀 알림.**
- B. 푸시 시 스캔 + SQS 큐로 결과 전송 + Lambda 호출 + Lambda로 태그 삭제 + SES로 알림(가능한 방법이지만 SES는 이벤트 트리거가 아닌 단순 이메일 발송 API — A의 EventBridge+Step Functions+SNS 조합이 더 표준적인 이벤트 기반 아키텍처).
- C. 매시간 수동 스캔 예약(Lambda) + 완료 시 EventBridge로 두 번째 Lambda 호출 + 태그 삭제 + SNS 알림(정기 예약 방식은 "새 이미지 버전 업로드 시" 즉시 스캔이라는 요구보다 지연이 발생 — 푸시 시 스캔이 더 적합).
- D. 주기적 이미지 스캔 + SQS + Step Functions + SES 알림(주기적 스캔은 즉시성이 떨어지고, SES는 이벤트 트리거 서비스가 아님).

**정답: A**

**해설**
ECR의 **"푸시 시 스캔(scan on push)"** 기능으로 새 이미지가 업로드될 때마다 즉시 스캔하고, 스캔 완료 이벤트(치명적/높음 결과 포함)를 **EventBridge**로 감지해 **Step Functions**를 호출, 이미지 태그 삭제와 **SNS 알림**까지 오케스트레이션하는 것이 이 요구사항(즉시성+자동 삭제+알림)을 정확히 만족하는 완전 이벤트 기반 서버리스 흐름입니다.

**왜 다른 보기는 오답인가**
- B, D: **Amazon SES는 이메일 발송 API**이지 이벤트를 구독/라우팅하는 서비스가 아니므로, "완료되면 알림을 보낸다"는 흐름에 직접 연결하기에 적합하지 않습니다(SNS가 표준).
- C, D: 매시간/주기적 스캔은 "새 이미지 버전이 업로드되면"이라는 즉시성 요구보다 늦게 반응합니다 — 푸시 시 스캔(scan on push)이 더 정확합니다.

> 💡 **시험 꿀팁**: ECR의 **푸시 시 스캔(scan on push) + EventBridge(스캔 완료 이벤트) + Step Functions(삭제 오케스트레이션) + SNS(알림)**가 이미지 취약점 자동 삭제/알림의 표준 정답입니다. SES는 이벤트 트리거가 아닌 단순 발송 API임을 기억하세요.

## QUESTION 225

**문제**: Organizations로 여러 계정 관리, EC2/Fargate/Lambda 워크로드. 일부 워크로드는 수요 예측 불가(월별 사용량 변동). 향후 3년 컴퓨팅 비용 최적화. 6개월 평균 사용량 기준. 조직 전체 컴퓨팅 사용에 가장 큰 비용 절감을 주는 솔루션은?

**보기**
- A. 회원 계정의 가장 흔한 EC2 인스턴스 크기/수에 맞춰 예약 인스턴스 구매(RI는 특정 인스턴스 유형/계열에 종속되어, 예측 불가능한 다양한 워크로드[EC2+Fargate+Lambda]에는 유연성이 부족).
- B. **마스터 계정 수준 권장 사항을 사용해 마스터 계정에서 조직의 Compute Savings Plan 구매.**
- C. 지난 6개월 데이터 기반, 사용량 많은 멤버 계정별로 개별 RI 구매(계정별 개별 구매는 조직 전체 최적화보다 비효율적이며, RI는 인스턴스 유형에 종속).
- D. 마스터 계정에서 각 멤버 계정에 대한 EC2 Instance Savings Plan 개별 구매(EC2 Instance SP는 인스턴스 계열에 종속되어 Compute SP보다 유연성이 낮음).

**정답: B**

**해설**
**Compute Savings Plans**는 EC2, Fargate, Lambda **전반**에 걸쳐 사용량(시간당 $ 약정)에 대해 할인을 적용하며 인스턴스 유형/계열/리전에 종속되지 않아 예측 불가능하고 다양한 워크로드에 가장 큰 유연성과 절감을 제공합니다. **조직의 마스터 계정**에서 조직 전체 권장 사항을 기반으로 구매하면, 조직 내 모든 계정의 사용량이 하나의 약정에 통합되어 활용도가 극대화됩니다.

**왜 다른 보기는 오답인가**
- A, C: 예약 인스턴스(RI)는 특정 인스턴스 유형/계열에 대한 약정이라 Fargate/Lambda를 포함한 혼합 워크로드나 예측 불가능한 수요 변화에 유연하게 대응하지 못합니다.
- D: EC2 Instance Savings Plan은 Compute Savings Plan보다 특정 인스턴스 계열에 더 종속적이며, 계정별로 개별 구매하는 것도 조직 전체 통합 최적화보다 비효율적입니다.

> 💡 **시험 꿀팁**: **EC2+Fargate+Lambda가 혼합**되고 **수요가 예측 불가능**한 조직 환경에서 최대 비용 절감을 원한다면 **Compute Savings Plans**(가장 유연함)를 **조직의 마스터 계정에서 조직 전체 단위로** 구매하는 것이 표준 정답입니다.

## QUESTION 226

**문제**: 수백 개 AWS 계정, Organizations(모든 기능 켜짐). 재무 팀은 조직의 AWS 비용이 할당 예산의 **80%를 초과**하면 이메일 알림 필요. 비용 추적/알림 솔루션은?

**보기**
- A. **조직의 마스터 계정에서 AWS Budgets로 일일 기간의 예산 생성. 경고 임계값 80% 설정. SNS로 재무 팀에 알림.**
- B. Trusted Advisor 조직 보기 + 비용 최적화 보고서 + 80% 임계값 설정(Trusted Advisor는 예산 초과 여부에 대한 이런 실시간 임계값 알림 기능을 제공하지 않음 — 개념 오류).
- C. Control Tower 등록 + 선택적 비용 제어 가드레일 활성화 + 80% 설정(Control Tower의 가드레일은 주로 정책 준수용이며 예산 초과 알림 전용 기능이 아님).
- D. 일일 비용 보고서를 S3에 저장 + EventBridge로 Athena 쿼리 예약 + CloudWatch 알림(직접 구현해야 하는 부분이 많아 AWS Budgets 대비 노력이 훨씬 큼).

**정답: A**

**해설**

- A. Site-to-Site VPN(중앙 VPC) + 중앙 VPC에서 다른 모든 VPC로 피어링(VPN은 대역폭 처리량이 제한적이고, VPC 피어링은 비전이적이라 다수 VPC 연결에 비효율).
- B. **Direct Connect 연결 + 전송 VIF 프로비저닝해 Direct Connect 게이트웨이에 연결 + 각 리전에서 전송 게이트웨이로 DXGW를 다른 모든 VPC에 연결.**
- C. Site-to-Site VPN(중앙 VPC) + 동적 라우팅 있는 전송 게이트웨이로 다른 모든 VPC 연결(VPN은 DX보다 대역폭/일관성이 낮음).
- D. Direct Connect + 각 리전의 모든 VPC 간 VPN 연결 + 중앙 VPC에서 피어링(VPN을 추가로 쓰는 것과 비전이적 피어링 모두 비효율적).

> 💡 **시험 꿀팁**: **다중 리전 VPC의 전이적 라우팅 + 높은 대역폭 + 일관된 네트워크 경험 + 낮은 비용**이 모두 필요하면 **Direct Connect + 전송 VIF + Direct Connect Gateway + (리전별) Transit Gateway** 조합이 표준 정답입니다.

- D. IoT Core 배포 + EC2에서 Kafka 서버 호스팅 + IoT Core가 데이터를 EC2로 전달(여전히 자체 관리형 Kafka를 유지해야 해서 근본적 해결책이 아님).

**정답: C**

**해설**
**Amazon MSK**는 관리형 Apache Kafka 서비스로, 기존 Kafka 기반 아키텍처(변환 로직, 프로토콜 등)를 그대로 유지하면서 브로커의 고가용성/장애 복구를 AWS가 관리하게 만듭니다. **NLB + 상태 확인**을 브로커 앞에 두면 안정적인 연결 지점을 제공하면서 가용성 문제(서버 충돌로 인한 데이터 손실)를 근본적으로 해결합니다.

**왜 다른 보기는 오답인가**
- A, D: 여전히 자체 관리형 Kafka 서버를 유지하는 방식이라, 근본적인 단일 소프트웨어 장애 위험(관리 부담, 패치, 장애 복구 등)이 남습니다.
- B: IoT Core+Firehose+Lambda로 완전히 재설계하는 것도 가능하지만, 기존 Kafka 기반 변환 로직/생태계를 그대로 활용하고 싶다면(문제에서 시사) MSK로의 마이그레이션이 더 자연스럽고 변경 폭이 적습니다.

> 💡 **시험 꿀팁**: **온프레미스 Kafka의 가용성/확장성 문제**를 해결하면서 기존 Kafka 생태계(코드/도구)를 유지하려면 **Amazon MSK**(관리형 Kafka) + **NLB(상태 확인 포함)**로 마이그레이션하는 것이 표준 정답입니다.

## QUESTION 238

**문제**: EC2+EFS+RDS 워크로드. 백업 요구사항: ① 캡처 직후 다른 리전으로 복제, ② 전체 환경의 **단일 백업 상태 소스** 제공, ③ 백업 실패 시 **즉시 알림**. 최소 운영 오버헤드로. (3개 선택)

**보기**
- A. **각 보존 요구사항에 대한 백업 규칙을 사용하는 AWS Backup 계획 생성.**
- B. **백업을 다른 리전으로 복사하도록 AWS Backup 계획 구성.**
- C. 다른 리전 복제 + 실패 시 알림을 보내는 Lambda 함수 직접 구현(AWS Backup의 네이티브 기능을 재구현하는 것으로 불필요하게 복잡).
- D. **백업 계획에 SNS 주제를 추가해 BACKUP_JOB_COMPLETED가 아닌 상태(즉, 실패 등)의 완료된 작업에 대해 알림.**
- E. 각 보존 요구사항에 대해 DLM 스냅샷 수명 주기 정책 생성(DLM은 EBS 전용이며 RDS/EFS를 포괄하는 "단일 백업 상태 소스"를 제공하지 못함).
- F. 각 데이터베이스에 RDS 스냅샷 개별 설정(RDS 자체 스냅샷 기능만 사용하면 EC2/EFS를 포괄하는 통합 백업 관리가 안 되고, AWS Backup의 "단일 소스" 요구를 만족 못함).

**정답: A, B, D**

**해설**
**AWS Backup**은 EC2/EFS/RDS를 포함한 여러 AWS 리소스 유형에 대해 하나의 통합된 백업 계획(A)으로 백업하고, 다른 리전으로의 **자동 복사**(B)를 지원하며, **SNS 알림**을 백업 작업의 상태(성공이 아닌 모든 상태, 즉 실패 포함)에 연결(D)할 수 있어, 이 세 가지 요구사항(즉시 복제, 단일 소스, 실패 알림)을 모두 관리형으로, 최소 운영 오버헤드로 만족합니다.

**왜 다른 보기는 오답인가**
- C: AWS Backup이 이미 네이티브로 제공하는 리전 간 복사/실패 알림 기능을 Lambda로 직접 재구현하는 것은 불필요한 노력입니다.
- E, F: DLM(EBS 전용)이나 RDS 자체 스냅샷 기능만으로는 EC2+EFS+RDS를 포괄하는 "**단일 백업 상태 소스**"라는 핵심 요구사항을 만족하지 못합니다 — AWS Backup 같은 통합 서비스가 필요합니다.

> 💡 **시험 꿀팁**: **여러 리소스 유형(EC2/EFS/RDS)에 대한 통합 백업 관리 + 크로스 리전 복제 + 실패 알림**이 모두 필요하면 **AWS Backup**(백업 계획 + 리전 간 복사 + SNS 알림)이 최소 운영 오버헤드의 표준 정답입니다. DLM이나 서비스별 개별 스냅샷 기능만으로는 "단일 소스"를 만족할 수 없습니다.

## QUESTION 239

**문제**: 유전자 보고 장치가 초당 8KB의 게놈 데이터를 데이터 플랫폼에 푸시. 요구사항: ① 인바운드 데이터의 **실시간에 가까운 분석**, ② 유연/병렬/내구성 있는 데이터 처리, ③ 결과를 **데이터 웨어하우스**로 전달. 전략은?

**보기**
- A. Kinesis Data Firehose로 수집 + Kinesis 클라이언트로 분석 + RDS에 저장(Firehose는 실시간 스트림 처리[커스텀 분석]보다는 배치성 전송에 가깝고, RDS는 "데이터 웨어하우스"가 아님 — 두 가지 개념 오류).
- B. **Kinesis Data Streams로 수집. Kinesis 클라이언트로 데이터 분석. Amazon EMR을 사용해 Amazon Redshift 클러스터에 결과 저장.**
- C. S3로 수집 + SQS에서 Kinesis로 분석(SQS와 Kinesis를 이런 방식으로 연결하는 것은 일반적인 실시간 분석 패턴이 아님) + Redshift 저장.
- D. API Gateway로 요청을 SQS에 넣고 + Lambda로 분석 + EMR로 Redshift에 저장(SQS는 실시간 스트리밍 분석보다는 비동기 작업 큐잉에 적합 — 실시간 스트림에는 Kinesis가 더 자연스러움).

**정답: B**

**해설**
**Kinesis Data Streams**는 실시간 스트리밍 데이터 수집에 최적화되어 있고, **Kinesis 클라이언트 라이브러리(KCL)**로 실시간에 가까운 분석을 수행할 수 있습니다. 분석 결과는 **Amazon EMR**을 통해 처리한 뒤 **Amazon Redshift**(데이터 웨어하우스)에 저장하는 것이 "실시간 분석 + 유연/병렬/내구성 + 데이터 웨어하우스 전달"이라는 세 요구사항을 모두 만족하는 표준 빅데이터 파이프라인입니다.

**왜 다른 보기는 오답인가**
- A: Kinesis Data Firehose는 주로 배치성 전송(대상에 자동 전달)에 가까워 커스텀 실시간 분석 로직에는 Data Streams가 더 적합하며, Amazon RDS는 "데이터 웨어하우스"가 아니라 트랜잭션 처리용 관계형 DB입니다.
- C, D: S3나 SQS를 이 방식으로 수집/연결하는 것은 "실시간에 가까운" 분석 요구에 비해 지연이 발생하기 쉬운 비표준적인 조합입니다.

> 💡 **시험 꿀팁**: **실시간에 가까운 스트리밍 데이터 분석 후 데이터 웨어하우스 저장**이 필요하면 **Kinesis Data Streams(수집) + KCL(분석) + EMR(처리) + Redshift(웨어하우스)**가 표준 파이프라인입니다. RDS는 데이터 웨어하우스가 아니라는 점을 기억하세요.

## QUESTION 240

**문제**: 웹+앱+NoSQL 3계층 애플리케이션 참조 아키텍처. 요구사항: ① 리전 내 고가용성, ② 재해 복구를 위해 **1분 이내** 다른 리전으로 장애 조치, ③ 사용자 경험 영향 최소화하며 가장 효율적인 솔루션. (3개 선택)

**보기**
- A. 두 리전에 100/0 Route 53 가중치 라우팅 + TTL 1시간(가중치 라우팅은 장애 조치 목적이 아니고, TTL 1시간은 전환에 최대 1시간이 걸릴 수 있어 "1분 이내" 요구를 명백히 위반).
- B. **기본 리전→DR 리전 Route 53 장애 조치 라우팅 정책. TTL 30초.**
- C. **선택한 두 리전에서 데이터 접근 가능하도록 DynamoDB 글로벌 테이블 사용.**
- D. DynamoDB에서 60분마다 데이터 백업 후 S3에 씀 + S3 CRR로 DR 리전에 복사 + DR 시나리오에서 스크립트로 DynamoDB에 가져오기(60분 백업 주기와 수동 가져오기 스크립트는 1분 RTO/데이터 최신성 요구를 전혀 만족하지 못함).
- E. **웹/앱 계층에 대해 여러 AZ에서 Auto Scaling 그룹으로 상시 대기(웜 스탠바이) 모델 구현. 최소 서버 수는 리전 예약 인스턴스, 추가 리소스는 온디맨드 사용.**
- F. 웹/앱 계층에 대해 여러 AZ Auto Scaling 그룹 + 필요 리소스에 스팟 인스턴스 사용(스팟은 중단 위험이 있어 재해 복구 대상 리전의 "즉시 가용" 웜 스탠바이 요건과 상충).

**정답: B, C, E**

**해설**
**Route 53 장애 조치 라우팅 + 짧은 TTL(30초)**(B)로 1분 이내의 빠른 DNS 전환을 달성하고, **DynamoDB 글로벌 테이블**(C)로 두 리전에서 항상 최신 데이터에 접근 가능하게 하며, **웜 스탠바이**(여러 AZ Auto Scaling, 최소 용량은 예약 인스턴스+추가는 온디맨드)(E)로 평상시 비용을 절감하면서도 장애 시 즉시 확장 가능한 상태를 유지하는 것이 세 요구사항 모두를 만족하는 가장 효율적인 조합입니다.

**왜 다른 보기는 오답인가**
- A: 가중치 라우팅은 트래픽 분산용이지 장애 조치 메커니즘이 아니며, 1시간 TTL은 "1분 이내" 요구에 크게 못 미칩니다.
- D: 60분 주기 백업과 수동 스크립트 기반 복원은 1분 RTO나 최신 데이터 요구를 전혀 만족할 수 없습니다.
- F: 스팟 인스턴스는 언제든 회수될 수 있어, 재해 발생 시 "즉시 사용 가능해야 하는" DR 대상 리전의 웜 스탠바이 용도에는 부적합합니다.

> 💡 **시험 꿀팁**: **1분 이내 리전 간 장애 조치**를 위해서는 **Route 53 장애 조치 라우팅 + 짧은 TTL**, 데이터 계층에는 **DynamoDB 글로벌 테이블**, 컴퓨팅 계층에는 **웜 스탠바이(예약+온디맨드 혼합)**를 조합하는 것이 표준 정답입니다. 스팟 인스턴스는 DR 대상 리전의 즉시 가용성 요건과 상충한다는 점에 유의하세요.
