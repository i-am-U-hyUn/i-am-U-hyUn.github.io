## QUESTION 41

**Question**: An app's DynamoDB table has RCU/WCU sized for expected peak load. Peak load occurs once a week for 4 hours and is double the average, while the rest of the week runs near average load. Writes outnumber reads. How can table cost be minimized?

**Choices**
- A. Use **AWS Application Auto Scaling** to increase capacity during the peak period, and **purchase Reserved RCU/WCU capacity** matched to the average load.
- B. Configure the table with On-Demand capacity mode.
- C. Configure DynamoDB Accelerator (DAX) in front of the table, and reduce provisioned read capacity to match the new peak load.
- D. Configure DAX in front of the table, and configure On-Demand capacity mode.

**Correct Answer: A**

**Explanation**
Since the load pattern is predictable (mostly average, with a short weekly spike), pairing **Reserved Capacity** (discounted rate for the average-load baseline) with **Application Auto Scaling** (handling the brief peak) is generally cheaper than On-Demand pricing for this kind of sustained, predictable workload.

**Why the other choices are wrong**
- B: On-Demand mode charges per request, and for this kind of predictable, sustained load pattern, it's typically more expensive than a Reserved Capacity + Auto Scaling combination.
- C, D: **DAX is a read-only cache.** Since the stated access pattern has more writes than reads, DAX provides no benefit here at all.

> 💡 **Exam tip**: For a DynamoDB workload with a **predictable baseline load plus periodic brief spikes**, combining **Reserved Capacity (baseline) + Application Auto Scaling (peaks)** is often cheaper than On-Demand mode. Also remember DAX only helps read-heavy workloads.

## QUESTION 42

**Question**: An on-premises media processing app is being migrated. A web server saves files to NAS and notifies a processing server via a message queue. Each file can take up to an hour to process. The backlog of pending files is much larger during business hours and drops sharply afterward. What is the most cost-effective migration recommendation?

**Choices**
- A. Use SQS. Configure the web servers to publish to the new queue. Invoke a **Lambda function** when there's a message in the queue, to pull requests and process files, storing them in S3.
- B. Use Amazon MQ. Configure the web servers to publish to the new queue. When a message arrives, create a new EC2 instance to pull from the queue and process it, storing processed files in EFS, terminating the instance after the job.
- C. Use Amazon MQ. Configure the web servers to publish to the new queue. Invoke a Lambda function to process files, storing them in EFS.
- D. Use **SQS**. Configure web servers to publish to the new queue. Use EC2 instances in an **Auto Scaling group** to pull requests and process files, **scaling based on SQS queue length**, storing processed files in **S3**.

**Correct Answer: D**

**Explanation**
Since processing can take **up to an hour**, and **Lambda's maximum execution duration is 15 minutes**, using Lambda (A, C) is technically infeasible from the start. For a simple point-to-point queueing need, **SQS** is simpler and cheaper than Amazon MQ, and **scaling an EC2 Auto Scaling group based on SQS queue length** naturally follows the backlog's business-hours surge and after-hours drop.

**Why the other choices are wrong**
- A, C: Using Lambda (15-minute limit) for a task that can take up to an hour is technically impossible.
- B: Amazon MQ, better suited to migrating existing brokered messaging protocols, is more costly/complex than SQS for this simple queueing need, and manually spinning up instances (instead of queue-length-based auto scaling) is less efficient.

> 💡 **Exam tip**: If a task might take **longer than 15 minutes**, rule out Lambda from the start (its execution duration limit). For simple point-to-point queueing, **SQS** is the default choice over Amazon MQ.

## QUESTION 43

**Question**: An OpenSearch Service cluster (10 data nodes) loads data from S3 Standard. Data resides in the cluster for one month for read-only analysis, then the index is deleted. For compliance, **a copy of all input data must be retained.** What is the most cost-effective solution?

**Choices**
- A. Replace all data nodes with UltraWarm, immediately transitioning input data from S3 Standard to **Glacier Deep Archive** as it's loaded.
- B. **Reduce data nodes to 2**, **add UltraWarm nodes**, configure indices to transition to UltraWarm as data is ingested, and **use an S3 lifecycle policy to transition data to Glacier Deep Archive after one month.**
- C. Reduce data nodes to 2, add UltraWarm nodes plus cold storage nodes, and **delete the input data from S3 after one month.**
- D. Reduce data nodes to 2, add **instance-backed** data nodes, immediately transitioning input data to Glacier Deep Archive as it's loaded.

**Correct Answer: B**

**Explanation**
**UltraWarm** is a cost-effective S3-backed storage tier in OpenSearch Service for infrequently accessed "warm" data, letting you shrink the number of expensive hot data nodes while still meeting the one-month analysis window. Since compliance requires **retaining, not deleting**, all input data, use an S3 lifecycle policy to transition it to the cheapest long-term storage class, **Glacier Deep Archive**, after one month.

**Why the other choices are wrong**
- A: Replacing all nodes with UltraWarm leaves no hot nodes for fresh incoming ingestion, mismatching the standard hot+warm architecture.
- C: Adding a cold storage tier is excessive, and critically, **deleting the input data from S3 after one month directly violates** the "retain all input data" compliance requirement.
- D: Using **instance-backed data nodes** instead of UltraWarm is significantly more expensive for warm/infrequently queried data.

> 💡 **Exam tip**: **UltraWarm** in OpenSearch Service is a low-cost, S3-backed "warm" storage tier. When compliance requires permanent data retention, use an **S3 lifecycle policy to transition — not delete — data to Glacier Deep Archive.**

## QUESTION 44

**Question**: 10 accounts under Organizations (Prod/NonProd OUs), each with AWS Config configured. An EventBridge rule per account notifies via SNS whenever a security group inbound rule with source `0.0.0.0/0` is created. For all NonProd OU accounts, the security team needs to make it **impossible to create such a rule** in the first place. With minimal operational overhead:

**Choices**
- A. Modify the EventBridge rule to invoke a Lambda function that removes the rule and publishes to SNS.
- B. Add the `vpc-sg-open-only-to-authorized-ports` AWS Config managed rule to the NonProd OU.
- C. Configure an SCP that **Allows** `ec2:AuthorizeSecurityGroupIngress` when `aws:SourceIp` is **not** `0.0.0.0/0`.
- D. Configure an SCP that **denies** `ec2:AuthorizeSecurityGroupIngress` **when the `aws:SourceIp` condition key value is `0.0.0.0/0`**, and apply it to the NonProd OU.

**Correct Answer: D**

**Explanation**
"Impossible to create" implies a **preventive control**. The existing EventBridge+SNS notification, and AWS Config rules (B), are **detective controls** that act only after the fact. To truly block a specific dangerous action pattern up front, use an **explicit Deny SCP with a condition key**.

**Why the other choices are wrong**
- A: Removing the rule via Lambda after it's created is still a reactive (detect-then-remediate) approach, leaving a window of vulnerability.
- B: An AWS Config managed rule is fundamentally a **detective** mechanism; even with auto-remediation, it's not as immediate a preventive block as an SCP.
- C: Expressing the exception via an "Allow" SCP doesn't align with how SCPs actually evaluate (see Question 32's tip), and isn't as decisive as a direct explicit Deny (D) targeting the exact dangerous pattern.

> 💡 **Exam tip**: To genuinely **block** an action at the organization/OU level (rather than just detecting it afterward), use an **explicit Deny SCP with a condition key**. EventBridge/Lambda remediation and Config rules are detective/reactive controls that act after the risky resource already exists.

## QUESTION 45

**Question**: An on-premises Git repository calls an AWS-hosted function via webhooks. Webhook logic currently runs on EC2 (Auto Scaling group) behind an ALB. The company wants to move to serverless with minimal operational overhead.

**Choices**
- A. Create individual **Lambda function URLs** for each webhook, and update the Git server to call each one.
- B. Create an **API Gateway HTTP API**. Implement each webhook's logic in a **separate Lambda function**. Update the Git server to call the API Gateway endpoint.
- C. Deploy the webhook logic to AWS App Runner with an ALB in front.
- D. Containerize the webhook logic, run it on ECS Fargate, and connect it via an API Gateway REST API.

**Correct Answer: B**

**Explanation**
An **API Gateway HTTP API** (cheaper/simpler than REST API when its advanced features aren't needed) fronting **a separate Lambda function per webhook** is far more centrally manageable than scattered individual function URLs, and much leaner operationally than a container-based approach.

**Why the other choices are wrong**
- A: As the number of webhooks grows, managing individual function URLs separately doesn't scale as well as a single unified API Gateway.
- C: App Runner + ALB is container-based, not as lightweight as a fully event-driven serverless (Lambda) architecture, and requires additional infrastructure (ALB).
- D: Containerizing and running on ECS Fargate plus a REST API carries far more operational overhead (image builds, ECS service management).

> 💡 **Exam tip**: To move an EC2/ALB-hosted webhook processor to a low-ops serverless architecture, the standard combo is **API Gateway (HTTP API) + one Lambda function per webhook** — leaner than scattered function URLs or a container-based approach (App Runner/ECS).

## QUESTION 46

**Question**: Migrating 1,000 on-premises servers (VMware clusters). Need to collect CPU details, RAM usage, OS information, and **running processes**, then query and analyze the data.

**Choices**
- A. Deploy the **Agentless Discovery Connector** + Migration Hub + AWS Glue ETL + query with S3 Select.
- B. Manually export VM performance info only, import into Migration Hub, manually update missing info, and query with QuickSight.
- C. A custom script + `put-resource-attributes` CLI to manually push data into Migration Hub, and query directly in the console.
- D. Deploy the **AWS Application Discovery Agent** on each server, configure data exploration in Migration Hub, and **run predefined queries with Amazon Athena** against the data in S3.

**Correct Answer: D**

**Explanation**
The requirement to collect **running processes** is key. The **agentless** connector (works via vCenter API, outside the VM) can't see inside the guest OS to report process-level detail, failing this requirement. You must use the **in-guest Application Discovery Agent**, whose collected data flows through Migration Hub into S3, queryable via serverless SQL with **Amazon Athena**.

**Why the other choices are wrong**
- A: The agentless connector cannot collect in-guest process information, failing the requirement outright.
- B, C: Manually exporting or pushing data via CLI is neither as complete nor as efficient as the automated agent-based collection.

> 💡 **Exam tip**: Whenever deep in-guest detail like **running processes** is needed, use the (not agentless) **Application Discovery Agent**. Collected data landing in S3 is typically queried directly with **Amazon Athena**.

## QUESTION 47

**Question**: A serverless app built on VPC-attached Lambda functions needs to integrate with an external provider's new service. The provider only supports requests from an allow-listed **public IPv4 address**, and the company must provide **a single public IP** in advance. Which solution provides the app access to the new service?

**Choices**
- A. **Deploy a NAT Gateway**, **associate an Elastic IP** with it, and configure the VPC to use it.
- B. Associate an Elastic IP with an "egress-only internet gateway."
- C. Associate an Elastic IP with an internet gateway and configure the Lambda function to use that internet gateway.
- D. Set up an internet gateway with an Elastic IP and a public route table default route.

**Correct Answer: A**

**Explanation**
A VPC-attached Lambda function's outbound traffic routes through a NAT device in a private subnet. Configuring outbound traffic through a **NAT Gateway with an assigned Elastic IP** means all outbound requests appear to originate from this one fixed public IP, satisfying the "provide a single public IP in advance" requirement.

**Why the other choices are wrong**
- B: **Egress-only internet gateways are IPv6-only** and don't support IPv4 Elastic IP association at all — this option describes a nonexistent configuration.
- C, D: A VPC-attached Lambda function cannot be configured to "use an internet gateway" directly this way — private-subnet-based outbound traffic must go through a NAT device. These configurations aren't technically valid.

> 💡 **Exam tip**: For a VPC-attached Lambda function needing a **single fixed public outbound IP**, think **NAT Gateway with an assigned Elastic IP**. Remember egress-only internet gateways are IPv6-only.

## QUESTION 48

**Question**: A web app: API Gateway (regional endpoint, since consumers are all near the deployed Region) + Lambda queries Aurora MySQL with 3 read replicas. Under high load, the app opens an excessive number of database connections, failing performance requirements. (Choose two.)

**Choices**
- A. Use the Aurora database's cluster endpoint.
- B. **Use RDS Proxy to set up a connection pool against Aurora's reader endpoint.**
- C. Use Lambda provisioned concurrency.
- D. **Move the code that opens database connections outside the Lambda event handler.**
- E. Change the API Gateway endpoint to edge-optimized.

**Correct Answer: B, D**

**Explanation**
The standard two-part fix for a Lambda-to-RDS "too many connections" problem: ① Use **RDS Proxy** for connection pooling (targeting the reader endpoint, since the workload is read-heavy), drastically reducing the actual number of connections reaching the database. ② **Move the connection-opening code outside the handler** (into the global/initialization scope) so a warm Lambda execution environment reuses existing connections instead of opening a new one every single invocation.

**Why the other choices are wrong**
- A: The cluster endpoint always points to the writer, so it doesn't help distribute read load across the 3 replicas or address the connection explosion.
- C: Provisioned concurrency reduces cold-start latency but doesn't reduce the number of database connections opened.
- E: Since consumers are explicitly all near the deployed Region already, an edge-optimized endpoint (which benefits geographically dispersed users) is irrelevant here.

> 💡 **Exam tip**: The standard fix for a Lambda↔RDS/Aurora "too many connections" problem is **① RDS Proxy (connection pooling) + ② moving DB connection code outside the handler (global/init scope).**

## QUESTION 49

**Question**: A company wants load balancing across an EC2 instance group, with **end-to-end encryption** between client and web server as a security requirement.

**Choices**
- A. Place EC2 instances behind an ALB, provision an SSL certificate via ACM and associate it with the ALB, then **export that ACM certificate** and install it on each EC2 instance.
- B. Associate EC2 instances with a target group, provision an ACM certificate, create a CloudFront distribution using it, and **set the target group as the origin**.
- C. Place EC2 instances behind an ALB, associate an ACM certificate with the ALB, and install a **separate third-party SSL certificate** on each EC2 instance. Configure the ALB to listen on port 443 and forward to the instances' port 443.
- D. Place EC2 instances behind an NLB, and install a third-party certificate on both the NLB and each EC2 instance.

**Correct Answer: C**

**Explanation**
**ACM-issued certificates cannot be exported.** They're only usable with directly integrated AWS services like ALB and CloudFront — not installable on your own EC2 instances. For end-to-end encryption, use ACM for the client-to-ALB leg, and install a **separate (third-party) certificate on the instances** to encrypt the ALB-to-instance leg as well.

**Why the other choices are wrong**
- A: **ACM certificates cannot be exported** — this scenario is technically impossible as described.
- B: A "target group" isn't a valid CloudFront origin type, and this doesn't address the ALB-to-instance encryption leg the requirement calls for.
- D: Manually installing a third-party certificate on both the NLB and instances could technically work, but it's more operationally cumbersome than leveraging ALB + ACM for the client-facing leg, as in C.

> 💡 **Exam tip**: **ACM certificates cannot be exported** — they're exclusive to directly integrated AWS services (ALB, CloudFront, etc.). If you need a certificate installed on your own EC2 instances, you need a **separate (third-party or self-signed) certificate.**

## QUESTION 50

**Question**: Migrating a data analytics environment (two Node.js apps — one ingests sensor data into MySQL, the other aggregates reports) to AWS. Some load jobs fail when the aggregation job runs. The migration must fix the loading issue with **no downtime or visible changes for customers.**

**Choices**
- A. Set up Aurora as a replication target of the on-premises database, create an Aurora Replica and move aggregation to it, and once synced, **restart the replica as the primary instance** to cut over.
- B. Use **AWS DMS** for continuous replication, but run the aggregation job **on the primary Aurora instance itself.**
- C. Use **AWS DMS** for continuous replication, **create an Aurora Replica for the aggregation job**, set the ingestion endpoint to Lambda + RDS Proxy, **cut over by switching a DNS record**, and disable DMS afterward.
- D. Use Kinesis Data Streams + Firehose for ingestion, and cut over by restarting a replica as the primary.

**Correct Answer: C**

**Explanation**
The standard zero-downtime migration pattern is: keep **AWS DMS** running for continuous replication, and once ready, **switch a DNS record** to cut over traffic, disabling the DMS task only after confirming the cutover succeeded. The original problem (aggregation interfering with ingestion) is fixed by physically separating the aggregation workload onto its **own Aurora Replica.**

**Why the other choices are wrong**
- A: Cutting over by "restarting a replica as the primary" carries a brief interruption risk during the restart, making it less stable than C's DNS-switch approach.
- B: Running aggregation on the **same primary (write) instance** reproduces the exact same interference problem the company had on-premises.
- D: Introduces an unnecessarily complex Kinesis-based architecture for this scenario, and uses the same riskier "replica promotion" cutover as A.

> 💡 **Exam tip**: For a **zero-downtime database migration**, remember the pattern: **AWS DMS (continuous replication) + DNS record switch (cutover) + disable DMS only after confirming cutover.** Any workload (like aggregation) that was interfering with writes should get its own **separate read replica**, not just move onto the same instance in the new environment.

## QUESTION 51

**Question**: PII stored in S3 is currently encrypted with SSE-S3. A new requirement states all current and future objects must be encrypted with **a key managed by the company's security team.** Bucket versioning is not enabled.

**Choices**
- A. Change default encryption to "SSE-S3 using a customer-managed key," re-upload all objects via CLI, and deny unencrypted PutObject requests via bucket policy.
- B. Change default encryption to **SSE-KMS**, set a bucket policy **denying unencrypted PutObject requests**, and **re-upload all existing objects via the CLI.**
- C. Change default encryption to SSE-KMS, and set a bucket policy that "automatically encrypts" objects on GetObject/PutObject requests.
- D. Change default encryption to "AES-256 using a customer-managed key," attach a policy, and re-upload objects via CLI.

**Correct Answer: B**

**Explanation**
Since the security team must "manage" the key, this requires **SSE-KMS with a customer-managed key** (SSE-S3 always uses an AWS-owned key that customers can never manage). Also, since **changing default encryption only affects newly-uploaded objects**, existing objects must be explicitly re-encrypted by re-uploading them (e.g., via CLI).

**Why the other choices are wrong**
- A, D: The combination "SSE-S3/AES-256 with a customer-managed key" is **technically impossible** — SSE-S3/AES-256 always uses an AWS-managed key; customer-managed keys are only possible via SSE-KMS.
- C: A bucket policy can only **allow/deny** requests — it has no capability to "automatically apply encryption" to a request. This describes a feature bucket policies don't have.

> 💡 **Exam tip**: **SSE-S3 always uses an AWS-owned key and can never be paired with a customer-managed key.** Any requirement that a security/company team must manage the encryption key always means **SSE-KMS with a customer-managed key.** Also: **changing default encryption only affects new objects** — existing objects need to be explicitly re-uploaded/copied to re-encrypt.

## QUESTION 52

**Question**: A dynamic web app on EC2 (ASG, target group) behind an ALB is distributed globally via CloudFront (origin = ALB), with a Route 53 `www.example.com` A record pointing at CloudFront. The company needs high availability and fault tolerance.

**Choices**
- A. Provision a full secondary deployment in another Region, and update the **Route 53 A record to a Failover record** with **both CloudFront distributions** as values.
- B. **Provision an ALB, ASG, and EC2 in another Region.** **Add a second origin to the same CloudFront distribution**, and configure an **Origin Group** with one origin primary and one secondary.
- C. Provision an ASG and EC2 in another Region, and register them as a **second target on the same ALB** in the original Region, with a failover routing algorithm on the ALB.
- D. Provision a full secondary deployment in another Region, create a **second CloudFront distribution**, and use **AWS Global Accelerator** to combine both distributions as endpoints.

**Correct Answer: B**

**Explanation**
Provisioning a fully redundant deployment (ALB + ASG + EC2) in another Region, then **adding it as a second origin to the same CloudFront distribution**, grouped into an **Origin Group** (primary/secondary), lets CloudFront automatically fail over to the secondary origin if the primary fails — the most direct, standard native CloudFront failover pattern.

**Why the other choices are wrong**
- A: Combining two separate CloudFront distributions via a Route 53 Failover record is an unnecessarily layered approach compared to using CloudFront's own native Origin Group failover (B).
- C: **An ALB is a regional resource** — you cannot register targets from a different Region directly. This configuration is architecturally invalid.
- D: Two separate CloudFront distributions plus Global Accelerator is more complex and costly than using a single distribution's Origin Group.

> 💡 **Exam tip**: For **cross-Region fault tolerance** on a CloudFront-fronted app, the simplest standard pattern is: add a second regional origin to the **same CloudFront distribution**, grouped into an **Origin Group** for automatic primary/secondary failover.

## QUESTION 53

**Question**: A "transit account" owns a Transit Gateway shared with every other account in the organization, connected to global offices via Site-to-Site VPN. The networking team needs to **centrally manage** a list of internal IP address ranges belonging to global offices, which developers reference for secure application access. Minimal operational overhead?

**Choices**
- A. Host a JSON file in S3, trigger SNS on updates, and have a Lambda subscriber update all relevant security group rules across all accounts.
- B. Create an AWS Config managed rule containing all internal IP ranges, checking security groups for compliance and auto-remediating.
- C. **Create a VPC prefix list in the transit account** with all internal IP ranges, **share it via AWS RAM** with every other account, and use the shared prefix list in security group rules elsewhere.
- D. Create a security group in the transit account, and reference it from other accounts via "nested security group references."

**Correct Answer: C**

**Explanation**
**Managed prefix lists** are AWS's purpose-built feature for maintaining a centrally-managed, reusable set of CIDR ranges that can be shared and referenced directly in security group and route table rules across accounts (via **AWS RAM**). Updates to the list propagate automatically everywhere it's referenced, minimizing ongoing operational effort.

**Why the other choices are wrong**
- A: A custom Lambda-based sync reimplements what a managed prefix list already provides natively — unnecessary complexity.
- B: An AWS Config rule detects and remediates compliance — it doesn't provide a referenceable "list object" for developers to use directly in security group rules.
- D: **Cross-account security group references require actual network connectivity (like VPC peering)** between the referencing and referenced VPCs — simply naming a security group ID from an unrelated account doesn't work.

> 💡 **Exam tip**: For a CIDR list that must be shared and centrally managed across accounts, use a **managed prefix list shared via AWS RAM.** Updates propagate automatically everywhere referenced — no custom sync scripts or misuse of Config/security-group cross-referencing needed.

## QUESTION 54

**Question**: An app runs on S3 (static site) + CloudFront + API Gateway REST API + per-method Lambda. The company wants a biweekly CSV report showing recommended memory config, recommended cost, and the price gap between current config and the recommendation, for each Lambda function, saved to S3, with **minimal development time.**

**Choices**
- A. Build a custom Lambda function that extracts metrics directly from CloudWatch Logs, formats a table, and saves it to S3, scheduled via EventBridge every two weeks.
- B. **Opt in to AWS Compute Optimizer.** Create a Lambda function that calls the **`ExportLambdaFunctionRecommendations`** operation, exporting a CSV to S3. **Schedule it via an EventBridge rule every two weeks.**
- C. Opt in to Compute Optimizer, and schedule a recurring CSV export "within the Compute Optimizer console" every two weeks.
- D. Purchase an AWS Business Support plan, opt in to Compute Optimizer for Trusted Advisor checks, and schedule a cost-optimization CSV export from the Trusted Advisor console.

**Correct Answer: B**

**Explanation**
**AWS Compute Optimizer** is the AWS-native service that generates exactly this kind of Lambda memory/cost recommendation, with a built-in **`ExportLambdaFunctionRecommendations`** API to export it directly to S3 as CSV. Wrapping this single API call in a thin Lambda function scheduled via EventBridge completes the requirement with minimal development.

**Why the other choices are wrong**
- A: Manually computing recommendations from raw CloudWatch metrics reimplements what Compute Optimizer already provides, far exceeding "minimal development time."
- C: Compute Optimizer's console doesn't have a native built-in recurring export-to-S3 schedule feature — the actual automation mechanism is the API/CLI operation triggered by EventBridge, as in B.
- D: Requires purchasing a paid support plan unnecessarily, and Trusted Advisor's broader cost checks don't provide the specific per-Lambda-function memory recommendation this requirement calls for.

> 💡 **Exam tip**: **AWS Compute Optimizer** natively provides Lambda memory/cost right-sizing recommendations, exportable to S3/CSV via its `ExportLambdaFunctionRecommendations` API — pair it with an EventBridge schedule for the minimal-development way to automate a recurring report.

## QUESTION 55

**Question**: 20+ factory/automation apps (across EC2/ECS/RDS) in a single VPC are owned by 3 engineering teams, with resources tagged by app and team. The company needs to (1) attribute monthly AWS bill costs per app/team, and (2) generate reports comparing the past 12 months of cost and forecasting the next 12 months. (Choose three.)

**Choices**
- A. **Activate user-defined (custom) cost allocation tags** representing app and team.
- B. Activate **AWS-generated** cost allocation tags representing app and team.
- C. **Create Cost Categories in Billing and Cost Management** for each application.
- D. Enable IAM access to Billing and Cost Management.
- E. Create cost budgets.
- F. **Activate Cost Explorer.**

**Correct Answer: A, C, F**

**Explanation**
Since the company's own custom tags are used, activate **user-defined cost allocation tags** (A). Grouping costs meaningfully per application requires **Cost Categories** (C). Both historical comparison AND future forecasting are provided by **Cost Explorer** (F).

**Why the other choices are wrong**
- B: "AWS-generated" tags are a different category from the company's own custom tags — since this scenario uses custom tags, A is correct instead.
- D: Enabling IAM access is an access-control concern, not something that itself provides cost attribution or forecasting.
- E: Cost budgets provide spending threshold alerts, not historical comparison or future forecasting.

> 💡 **Exam tip**: For attributing costs to apps/teams plus historical comparison and forecasting, remember the trio: **① user-defined (custom) cost allocation tags + ② Cost Categories + ③ Cost Explorer (which includes forecasting).** Budgets don't provide forecasting or comparison.

## QUESTION 56

**Question**: An on-premises app fetches data from a third-party API behind a firewall; the third party only allow-lists **one public CIDR block** per client. After migrating to AWS (ALB in a public subnet, EC2 in private subnets, NAT gateway), the app must still be able to call the third-party API.

**Choices**
- A. Attach the customer-owned public IP block to the VPC and enable public IP addressing on the public subnet.
- B. **Register the customer-owned public IP block (BYOIP)** with the AWS account, **create an Elastic IP from that block, and assign it to the VPC's NAT Gateway.**
- C. Create an Elastic IP from the customer-owned IP block and assign it to the **ALB.**
- D. Register the BYOIP block, and set up **AWS Global Accelerator** with the ALB as an endpoint.

**Correct Answer: B**

**Explanation**
Requests to the third-party API are **outbound traffic from private-subnet EC2 instances, routed through the NAT Gateway.** Using **BYOIP** to bring the already-allow-listed public IP range into AWS, and assigning an Elastic IP from it to the **NAT Gateway**, keeps the outbound source IP unchanged — the third party needs no changes at all.

**Why the other choices are wrong**
- A: Assigning public IPs to the public subnet has nothing to do with the **outbound** path from private-subnet EC2 instances.
- C, D: The ALB and Global Accelerator both handle **inbound** traffic to the app — a different direction than the app's own **outbound** calls to the third party.

> 💡 **Exam tip**: To pin an application's **outbound** (external API call) source IP to a specific, already-allow-listed range, think **BYOIP + assigning an Elastic IP to the NAT Gateway.** ALB/Global Accelerator handle inbound traffic instead.

## QUESTION 57

**Question**: An administrator's SCP has two statements — `"AllowsAllActions"` (Allow on all actions) and `"DenyCloudTrail"` (Deny on cloudtrail:* actions) — attached to the OU containing account `1111-1111-1111`. Developers in that account complain they can't create S3 buckets. How should this be fixed?

**Choices**
- A. Add an "Allow" statement for `s3:CreateBucket` to the SCP.
- B. Remove the account from the OU and attach the SCP directly to account `1111-1111-1111`.
- C. **Instruct developers to add Amazon S3 permissions to their IAM entity.**
- D. Remove the SCP from the account.

**Correct Answer: C**

**Explanation**
This SCP only explicitly denies CloudTrail — **everything else is already allowed.** Since **SCPs never grant permissions, only set a ceiling**, if the SCP already permits S3 and developers still can't create a bucket, the actual cause must be that their **IAM identity-based policy lacks the `s3:CreateBucket` permission** entirely.

**Why the other choices are wrong**
- A: The SCP already allows S3 actions (Allow-all except CloudTrail), so adding another Allow statement is redundant and doesn't address the real cause (a missing IAM grant).
- B, D: Neither changing where the SCP is attached nor removing it addresses the actual problem, since the SCP was never blocking S3 in the first place.

> 💡 **Exam tip**: **SCPs never grant permissions — they only set a ceiling on what IAM policies can grant.** If an SCP allows (or doesn't deny) an action but a user still can't perform it, the SCP isn't the problem — check the user's **IAM identity-based policy** for the missing grant instead.

## QUESTION 58

**Question**: A business-critical monolithic application runs on Amazon Linux 2 EC2. Legal requires backing up data from the encrypted EBS volume to S3, but the application team has **no SSH key pair** for the instance. The app must keep serving users continuously.

**Choices**
- A. **Attach a role with S3 write permissions to the instance**, and use **AWS Systems Manager Session Manager** to access the instance and run a command copying data to S3.
- B. Create an image with the reboot option turned on, launch a new instance from it, attach a role with S3 write permissions, and run the copy command.
- C. Use Amazon Data Lifecycle Manager to create a snapshot of the EBS volume, then copy the data to S3.
- D. Create an image, launch a new EC2 instance from it, attach a role with S3 write permissions, and run the copy command.

**Correct Answer: A**

**Explanation**
**AWS Systems Manager Session Manager** provides access to an instance without needing an SSH key pair (using IAM permissions and the SSM Agent instead), and works directly on the **existing running instance** without a reboot or new instance — satisfying both the "no SSH key" and "no service interruption" constraints.

**Why the other choices are wrong**
- B: Creating an image "with the reboot option on" actually **reboots the instance**, violating the requirement to keep serving continuously.
- C: An EBS snapshot is a block-level backup — a different form than "copying data (files) to S3," and Data Lifecycle Manager doesn't itself copy data into S3.
- D: Creating an image and launching a new instance just to run the copy is unnecessarily roundabout compared to accessing the existing instance directly via Session Manager.

> 💡 **Exam tip**: When you need to access an EC2 instance with **no SSH key pair**, think **AWS Systems Manager Session Manager** — it accesses a running instance directly, without requiring a reboot or new instance.

## QUESTION 59

**Question**: Data must be copied from an S3 bucket in one AWS account to a new S3 bucket in a new AWS account, using the AWS CLI. Which three-step combination succeeds?

**Choices**
- A. A source bucket policy allowing the source bucket to list, put objects, and set ACLs on the destination bucket.
- B. **A bucket policy on the source bucket allowing the destination account's user to list and read objects from the source bucket.**
- C. An IAM policy created in the source account (for a source-account user).
- D. **An IAM policy created in the destination account**, allowing the destination account's user to list/get from the source bucket and list/put/set-ACL on the destination bucket, attached to that user.
- E. Run `aws s3 sync` as a source-account user.
- F. **Run `aws s3 sync` as a destination-account user.**

**Correct Answer: B, D, F**

**Explanation**
This is the **"destination account pulls"** cross-account copy pattern: ① a bucket policy on the source grants the destination account's user read access (B), ② an IAM policy **in the destination account** grants that user permission to read from source and write to destination (D), and ③ the actual `aws s3 sync` is **run as the destination account's user** (F).

**Why the other choices are wrong**
- A, E: These belong to the alternative "source account pushes" pattern and can't be mixed with the "destination pulls" combination used in the correct answer.
- C: An IAM policy in the source account also belongs to the "push" direction, inconsistent with the "pull" direction of the correct combination.

> 💡 **Exam tip**: For a cross-account S3 copy via CLI, pick ONE consistent direction — **"destination pulls"** (destination IAM policy + source bucket policy granting read + run `sync` as the destination user) or **"source pushes"** (the opposite). Don't mix elements from both directions.

## QUESTION 60

**Question**: A Lambda-based application deployed via CloudFormation suffered a several-minute outage during its last production release. How should the deployment process be adjusted to support **canary releases**?

**Choices**
- A. Create an **alias** for each newly deployed Lambda function version, and use the **AWS CLI `update-alias` command with a routing configuration parameter** to distribute load.
- B. Deploy the application to a new CloudFormation stack and distribute load via Route 53 weighted routing.
- C. Create a version for each newly deployed function, and use the `update-function-configuration` command with a routing configuration parameter to distribute load.
- D. Configure AWS CodeDeploy using the `CodeDeployDefault.OneAtATime` deployment configuration to distribute load.

**Correct Answer: A**

**Explanation**
Lambda's native canary release mechanism is built on **Lambda aliases with weighted routing configuration.** The `update-alias` CLI command with a routing configuration parameter is the direct way to gradually shift traffic between the old and new versions.

**Why the other choices are wrong**
- B: Deploying an entirely new stack and distributing via DNS is far heavier and more complex than simply using Lambda's built-in alias-based canary mechanism.
- C: `update-function-configuration` changes a function's **settings** (memory, timeout, etc.) — it has no routing configuration parameter for traffic splitting; this describes a capability that doesn't exist for this command.
- D: `CodeDeployDefault.OneAtATime` is a deployment configuration typically used for **EC2/on-premises** deployments (one instance at a time), not a Lambda canary configuration (Lambda uses configs like `LambdaCanary10Percent5Minutes`).

> 💡 **Exam tip**: Lambda's native canary release uses **aliases + weighted routing configuration** (`update-alias --routing-config`, or SAM+CodeDeploy's `LambdaCanary*`/`LambdaLinear*` deployment types). Watch for mismatched deployment-config names (`OneAtATime` is an EC2 concept) and unrelated CLI commands (`update-function-configuration` changes settings, not routing) as classic distractors.
