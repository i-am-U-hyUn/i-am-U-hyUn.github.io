## QUESTION 441

**Question**: An online gaming company needs to connect players to game server instances worldwide, but instead of standard load balancing (evenly distributing to the nearest healthy endpoint), it needs to **route each player to the exact instance/port running the specific game session they're already part of** (session stickiness, custom routing logic). They still want the benefit of a static Anycast IP and globally optimal routing. What's the solution?

**Choices**
- A. Use a standard AWS Global Accelerator (a standard accelerator automatically distributes traffic to healthy endpoints based on health checks, and doesn't let the application directly control custom routing logic mapping specific clients to specific instances/ports).
- B. **Use AWS Global Accelerator's custom routing accelerator, letting the application directly control a routing table mapping specific client IP/port combinations to specific target EC2 instances' IP/port, while still leveraging the static Anycast IP and optimal routing via AWS's global network.**
- C. Create a new DNS record for every session in Route 53 (DNS-based routing isn't suited to fine-grained, per-session port/instance mapping, incurs delay from DNS caching, and creating/managing a record every time isn't practical).
- D. Use ALB target-group stickiness (sticky sessions) (ALB stickiness is a cookie-based mechanism for reusing the same target and doesn't support a UDP-based custom protocol or arbitrary client-instance mapping like a game server needs).

**Correct Answer: B**

**Explanation**
Unlike a standard accelerator, **AWS Global Accelerator's custom routing accelerator** lets the application directly control a routing table that **maps a specific client (source IP/port) to a specific target EC2 instance's specific destination IP/port**. This gives the application fine-grained control over exactly which instance/port a specific client (like a game session) should connect to, while still fully benefiting from Global Accelerator's static Anycast IP and globally optimal routing via AWS's global network.

**Why the other choices are wrong**
- A: A standard accelerator is optimized for automatic distribution to healthy endpoints and doesn't support custom routing logic where the application arbitrarily controls client-instance mapping.
- C: A DNS-based approach isn't suited to fine-grained, per-session routing and carries caching delay and management burden.
- D: ALB stickiness is cookie-based and doesn't apply to a game server's UDP/custom-protocol session routing.

> 💡 **Exam tip**: To let the application control **custom routing directly mapping specific clients to specific instances/ports** while keeping a static IP and globally optimal path, **Global Accelerator's custom routing accelerator** is the standard answer.

## QUESTION 442

**Question**: A company wants to analyze Aurora MySQL transaction data in near real time on Redshift, but previously had to build/maintain a separate ETL pipeline for this (continuous replication via DMS or a custom Lambda). They want Aurora's data changes to automatically, near-real-time reflect on Redshift with no ETL pipeline to build. What's the solution?

**Choices**
- A. Configure a continuous replication task with DMS (DMS is also viable, but still incurs the ETL pipeline operational burden of configuring/monitoring/managing a separate replication task — the question wants to eliminate this).
- B. **Use Aurora zero-ETL integration with Amazon Redshift, natively configured so Aurora's data changes are automatically replicated to Redshift within seconds, with no separate ETL pipeline to build.**
- C. Export Aurora data to S3 every night and load via a Redshift COPY command (a daily batch approach falls far short of the "near real time" requirement and still requires building/managing a pipeline).
- D. Query Aurora snapshot data directly via Redshift Spectrum (Redshift Spectrum is for querying external tables in an S3 data lake, not for directly querying an operational database like Aurora — a conceptual error).

**Correct Answer: B**

**Explanation**
**Aurora zero-ETL integration** is a native integration feature between Aurora (MySQL-compatible) and Amazon Redshift, where Aurora's transaction data changes are **automatically replicated to Redshift within seconds**, with no separate ETL pipeline to build or manage, enabling near-real-time analysis. This is the modern standard solution completely eliminating the burden of building/maintaining a custom pipeline for moving data between an operational database and a data warehouse.

**Why the other choices are wrong**
- A: DMS is viable, but still leaves the burden of configuring/operating a separate replication task.
- C: A daily batch approach falls far short of the real-time-ness requirement.
- D: Redshift Spectrum targets S3 data and isn't a feature for directly querying Aurora.

> 💡 **Exam tip**: To **analyze Aurora data on Redshift in near real time with no separate ETL pipeline**, **Aurora zero-ETL integration** is the standard answer.

## QUESTION 443

**Question**: A retail chain wants AWS-native compute resources at each store for inventory management/POS processing, but store space is very limited, leaving no room for a standard Outposts rack (full rack size). What smaller-form-factor AWS Outposts option fits a small store environment?

**Choices**
- A. Install a standard Outposts rack scaled down (an Outposts rack is a fixed rack-size form factor and can't be arbitrarily scaled down — a conceptual error).
- B. **Use AWS Outposts servers (1U or 2U form factor), a compact option installable even in a small space with no need for a full rack, providing AWS-native compute/storage at the store.**
- C. Use AWS Snowball Edge as standing installed infrastructure (Snowball Edge is mainly for data transfer/temporary edge processing; Outposts servers are better suited as standing infrastructure for a continuous production workload).
- D. Build a generic on-premises server at each store and connect to AWS via VPN (gives up Outposts's core benefit of using native AWS APIs/tools as-is, and takes on the burden of building/managing generic servers yourself).

**Correct Answer: B**

**Explanation**
**AWS Outposts servers** are a compact Outposts option in **1U or 2U form factor**, designed for small spaces (retail stores, branch offices, etc.) that don't need a full rack. They can be installed in a much smaller physical footprint than a standard Outposts rack, while still performing low-latency local processing (inventory management, POS, etc.) at the store using the same AWS-native APIs, services, and management tools.

**Why the other choices are wrong**
- A: An Outposts rack is a fixed, large form factor and isn't an option that can be arbitrarily scaled down.
- C: Snowball Edge is more suited to data transfer/temporary processing; Outposts servers are the standard for standing infrastructure supporting a continuous production workload.
- D: Building generic on-premises servers gives up Outposts's core native-AWS-integration benefit.

> 💡 **Exam tip**: For **AWS-native compute at a space-constrained small site (a store, etc.)**, a compact **AWS Outposts server (1U/2U)** is the standard answer.

## QUESTION 444

**Question**: The security team wants to automatically find whether the organization's S3 buckets, IAM roles, KMS keys, etc. have any **resource-based policy that unintentionally allows access to an external account (outside the organization) or the public**. Manually reviewing each resource policy is impractical at this scale. What's the solution?

**Choices**
- A. Ask each team to review its own resource policies (manual review is impractical and inconsistent at a large organization's scale and easily misses mistakes).
- B. **Use IAM Access Analyzer to analyze the policies of supported resources — S3, IAM roles, KMS keys, Lambda, etc. — automatically identifying findings that unintentionally allow access from outside the organization or publicly, with continuous monitoring.**
- C. Scan all resource policies with Macie (Macie specializes in detecting sensitive information [PII, etc.] in data stored in S3; analyzing whether resource policies allow external access is Access Analyzer's role).
- D. Detect all external-access patterns using only Config rules (some specific conditions can be built with Config rules, but comprehensively, automatically analyzing policy logic itself across various resource types to identify unintended external/public access is a dedicated feature Access Analyzer provides).

**Correct Answer: B**

**Explanation**
**IAM Access Analyzer** uses logical reasoning (automated reasoning) technology to **analyze resource-based policies** on S3 buckets, IAM roles, KMS keys, SQS queues, Lambda functions, etc., automatically identifying as **findings** whether a policy unintentionally allows access to entities outside the trust zone (organization/account) or to the public. It continuously analyzes whenever a new policy is created/changed, letting you continuously monitor unintended external exposure organization-wide with no manual review.

**Why the other choices are wrong**
- A: Manual review is impractical and inconsistent at a large organization's scale.
- C: Macie specializes in detecting sensitive information in data content; analyzing whether policies themselves allow external access is Access Analyzer's role.
- D: Config rules can partially help, but comprehensive automated analysis of policy logic across resource types is Access Analyzer's dedicated feature.

> 💡 **Exam tip**: To **automatically find whether resource policies unintentionally allow access from outside the organization/publicly**, **IAM Access Analyzer** is the standard answer.

## QUESTION 445

**Question**: A regulatory requirement mandates guaranteeing and monitoring that an S3 bucket's objects **must** finish replicating to another Region within a defined time (SLA) after upload. Standard CRR has a "most within a few minutes" goal, but doesn't provide a guaranteed SLA or replication-lag monitoring metrics. What's the solution?

**Choices**
- A. Use only standard cross-region replication (CRR) with no additional measures (standard CRR provides no guaranteed SLA for replication time, failing to meet the regulatory "guaranteed within a defined time" requirement).
- B. **Enable Replication Time Control (RTC) on the S3 replication rule, applying an SLA guaranteeing 99.99% of objects replicate within 15 minutes, and monitor replication lag with CloudWatch metrics (S3 Replication metrics).**
- C. Have the application synchronously upload directly to a second Region immediately after uploading an object (application-level dual upload requires directly implementing separate error handling, retries, and consistency management for two Regions — significantly increased complexity).
- D. Manually check replication status via an hourly batch job (manual batch checking isn't near-real-time, doesn't prevent an SLA violation in advance, and only discovers issues after the fact).

**Correct Answer: B**

**Explanation**
**S3 Replication Time Control (RTC)** is a feature addable to standard CRR that provides an explicit SLA guaranteeing **99.99% of objects replicate within 15 minutes**. It also provides dedicated **CloudWatch metrics** showing the number of objects pending replication and replication time, letting you monitor replication status in real time — meeting both the regulatory requirement for guaranteed within-time replication and ongoing visibility into compliance.

**Why the other choices are wrong**
- A: Standard CRR has no guaranteed SLA, failing the regulatory requirement.
- C: Application-level dual upload significantly increases complexity and operational burden.
- D: Manual batch checking lacks real-time-ness and only discovers issues after the fact — not proactive SLA assurance.

> 💡 **Exam tip**: For S3 cross-region replication needing a **guaranteed within-time replication SLA and lag monitoring**, **Replication Time Control (RTC)** is the standard answer.

## QUESTION 446

**Question**: The operations team wants to continuously detect, **proactively before users report a problem**, whether a customer-facing website's core user flows (login, checkout, etc.) actually work correctly. They want periodic testing from multiple Regions using synthetic traffic that mimics actual browser behavior, and to be alerted on failure. What's the solution?

**Choices**
- A. Only monitor server-side error rate via CloudWatch metrics (server-side error-rate monitoring is useful, but doesn't detect whether the actual user flow [the entire process from login through checkout] works correctly from the client's perspective, or whether UI elements load properly).
- B. **Use Amazon CloudWatch Synthetics, writing a canary script that reproduces the actual user flow, scheduled to run periodically from multiple Regions/locations, alerting proactively via a CloudWatch alarm on failure.**

Only collect real user browser performance data (RUM, Real User Monitoring) (real-user data collection is a useful after-the-fact analysis tool, but data is only generated after users actually visit — doesn't fit the "proactively before users report" goal; synthetic monitoring is more suitable).
- D. Periodically manually review server logs (manual log review isn't proactive, lacks real-time-ness, and doesn't scale).

**Correct Answer: B**

**Explanation**
**Amazon CloudWatch Synthetics** is a synthetic monitoring service where you write a **canary script** that reproduces actual user behavior (login, page navigation, checkout, etc.), automatically running it on a regular schedule from multiple Regions or locations. If the canary fails (e.g., a specific UI element doesn't load, or response time exceeds a threshold), a CloudWatch alarm lets the operations team **proactively detect and respond to the problem before users actually experience and report it**.

**Why the other choices are wrong**
- A: Server-side error rate alone doesn't reveal whether the full user flow works correctly from the client's perspective.
- C: RUM only generates data once real users actually visit — synthetic monitoring (Synthetics) is more suitable for the proactive-detection goal.
- D: Manual log review isn't proactive and doesn't scale.

> 💡 **Exam tip**: To **continuously, proactively monitor core user flows with synthetic traffic** before users report a problem, **Amazon CloudWatch Synthetics** (canaries) is the standard answer.

## QUESTION 448

**Question**: The security team wants to go a step beyond AWS Config detecting compliance violations like "S3 bucket public access not blocked" — when a violation is found, they want an **automatic corrective action (remediation)** performed (e.g., enabling public access block on that bucket) with no human intervention. What's the solution?

**Choices**
- A. Periodically check Config rule findings and have staff manually remediate (manual remediation contradicts the "automatic, no human intervention" requirement and responds slowly).
- B. **Attach a remediation action based on an AWS Systems Manager Automation document to the Config rule, so that when a non-compliant resource is detected, the linked Automation runbook automatically runs to remediate the violation.**
- C. Reconfigure GuardDuty to detect the same compliance violation (GuardDuty specializes in threat/anomaly detection; detecting resource-configuration compliance and linking to auto-remediation is Config's role and strength).
- D. Use an EventBridge rule to monitor all S3 API calls and implement remediation logic directly in Lambda (viable, but Config already provides compliance evaluation and remediation-action linkage out of the box, so building this from scratch is unnecessary duplication).

**Correct Answer: B**

**Explanation**
**AWS Config** provides a feature to directly attach a **remediation action** to a rule. When a non-compliant resource is detected, the linked **AWS Systems Manager Automation document** (e.g., a runbook enabling public access block on an S3 bucket) **automatically runs**, remediating the violation with no human intervention. This is the standard automated compliance-remediation approach, integrating detection (Config rule) and remediation (SSM Automation) into a single pipeline.

**Why the other choices are wrong**
- A: Manual remediation contradicts the automation requirement and is slow.
- C: GuardDuty specializes in threat detection; resource-configuration compliance and auto-remediation linkage is Config's domain.
- D: A custom EventBridge+Lambda implementation unnecessarily reinvents functionality Config already provides.

> 💡 **Exam tip**: To **automatically (with no human intervention) remediate non-compliant resources**, linking a **Config rule + an SSM-Automation-based remediation action** is the standard answer.

## QUESTION 449

**Question**: A company uses Aurora Global Database with the primary in Region A and the secondary in Region B. An application server located in Region B occasionally needs to perform **write** operations, but they don't want to implement logic in the application code that switches connections directly to the primary endpoint in Region A. They want write requests sent to the same local endpoint in Region B to be automatically handled. What's the solution?

**Choices**
- A. Implement logic in the application to distinguish read/write operations, always routing writes to the Region A endpoint and reads to the Region B endpoint (exactly the approach the question wants to avoid — implementing Region-switching logic directly in the application).
- B. **Enable Aurora Global Database's write forwarding feature, so write requests coming into the secondary Region (B)'s cluster endpoint are automatically internally forwarded by Aurora to the primary Region (A) for processing, with the result returned.**
- C. Configure a fully independent, separately writable Aurora cluster in the secondary Region too (Global Database's secondary Region is read-only by default; configuring a fully independent separate write cluster contradicts Global Database's architecture and data-consistency model).
- D. Store all secondary-Region write requests in an SQS queue and batch-send them to Region A (an SQS batch approach can't return an immediate write result, mismatching a synchronous application requirement, and is unnecessarily complex).

**Correct Answer: B**

**Explanation**
Enabling Aurora Global Database's **write forwarding** feature means that even if the secondary Region's application sends a write request to the secondary Region's **local cluster endpoint**, Aurora **automatically forwards** it internally to the primary Region for processing and returns the result. The application doesn't need to implement logic to switch endpoints by Region — it can always just use the local (nearest) endpoint, simplifying development.

**Why the other choices are wrong**
- A: Implementing Region-specific endpoint-switching logic directly in the application is exactly the approach this question wants to avoid.
- C: An independent write cluster in the secondary Region doesn't fit Global Database's structure and data-consistency model.
- D: An SQS batch approach doesn't fit a scenario needing a synchronous write response and is overly complex.

> 💡 **Exam tip**: To have Aurora Global Database's **secondary Region also handle writes via its local endpoint (automatically forwarded internally to the primary)**, **write forwarding** is the standard answer.

## QUESTION 451

**Question**: Multiple business units each run their own Redshift cluster in their own AWS account, and one business unit (B) wants to query data in another business unit (A)'s cluster **in real time, without physically copying the data**. Each cluster must continue to operate/scale independently (they don't want to consolidate into one large shared cluster). What's the solution?

**Choices**
- A. UNLOAD/COPY business unit A's data to business unit B's cluster every night (a batch-copy approach lacks real-time-ness, physically duplicates data, contradicting "without copying," and incurs duplicate storage cost).
- B. **Use Amazon Redshift's data sharing feature, configuring business unit A's cluster to share a specific database/schema/table with business unit B's cluster. Business unit B queries directly in real time with no physical data copy, while each cluster continues to operate/scale independently.**
- C. Consolidate both business units into a single large Redshift cluster (directly contradicts the requirement to avoid consolidating into one shared cluster, and loses each business unit's independent operation/scaling requirement).
- D. Have business unit A export data to S3 and business unit B query it as an external table via Redshift Spectrum (viable, but the export step to S3 adds delay, failing to provide true real-time-ness, and lags behind native data sharing — Redshift's native data sharing is the standard method for real-time inter-cluster sharing).

**Explanation**

> 💡 **Exam tip**: To **share data in real time without physically copying it** across multiple Redshift clusters/accounts, **Redshift data sharing** is the standard answer.

## QUESTION 452

**Question**: A company receives SFTP uploads via AWS Transfer Family, and wants to **automatically virus-scan uploaded files, encrypt files that pass the scan, and move them to a final destination S3 bucket**, while moving infected files to a quarantine bucket. How do you automatically trigger this multi-step follow-up processing on every file upload (without directly managing separate custom orchestration code)?

**Choices**
- A. Detect uploads via S3 event notifications, trigger Lambda, and directly implement the entire scan/encrypt/move logic as one function inside Lambda (viable, but carries the burden of implementing/managing the orchestration of each step [scan, conditional branch, encrypt, move] directly inside a single custom Lambda function).
- B. **Use AWS Transfer Family's managed workflows feature, automatically running a workflow declaratively configured with multiple steps — scan, conditional branch (tagging), encrypt, copy/move — triggered by file upload.**
- C. Build a separate application that periodically polls uploaded files for batch processing (polling-based batch processing isn't triggered immediately on upload — introduces delay, and building/operating a separate application is a heavy burden).
- D. Design the entire pipeline directly with Step Functions (a viable alternative, but requires directly designing/implementing everything from the upload-event integration to custom state definitions for each step — more implementation burden than Transfer Family's built-in managed workflow for SFTP upload follow-up processing).

**Correct Answer: B**

**Explanation**
**AWS Transfer Family's managed workflows** feature triggers off the moment a file is uploaded via SFTP/FTPS/FTP, letting you automatically run a declaratively defined workflow with multiple steps — **virus scanning, conditional tagging/branching, encryption, file copy/move, custom Lambda invocation**. Conditionally branching a file to a destination or quarantine bucket based on scan results can also be configured within the workflow, with no need to directly manage complex custom orchestration code.

**Why the other choices are wrong**
- A: Implementing all logic directly in a single custom Lambda function unnecessarily reinvents functionality Transfer Family already provides.
- C: Polling-based batch processing isn't an immediate trigger and carries the burden of building a separate application.
- D: Directly designing with Step Functions is viable, but carries more implementation burden than Transfer Family's managed workflow.

> 💡 **Exam tip**: To **automate multi-step follow-up processing (scan, conditional branch, encrypt, move) after an SFTP upload**, **AWS Transfer Family's managed workflows** is the standard answer.

## QUESTION 454

**Question**: A company's application uses an API key for a third-party payment API, and wants to regularly automatically rotate this key. Since this API key isn't an RDS credential, they can't use Secrets Manager's built-in RDS rotation feature. What's the solution?

**Choices**
- A. Conclude that Secrets Manager only offers rotation for RDS credentials, so this API key can't use rotation, and rotate it manually (this conclusion is inaccurate — rotation can be used for non-RDS secrets too).

**Explanation**

Implementing the logic to call the third-party provider's key-reissuance API (following the create-test-replace steps) in this custom function and attaching it to a rotation schedule lets even a non-RDS secret be regularly automatically rotated.

**Why the other choices are wrong**
- A: This conclusion is inaccurate — Secrets Manager can rotate non-RDS secrets too via a custom Lambda.
- C: Notification alone doesn't achieve automatic rotation.
- D: Never rotating contradicts security best practice.

> 💡 **Exam tip**: To **automatically rotate a non-RDS secret like a third-party API key**, **Secrets Manager + a custom Lambda rotation function** is the standard answer.

## QUESTION 455

**Question**: A bug in the message-processing logic for a standard SQS queue caused some messages to repeatedly fail processing and move to the dead-letter queue (DLQ). After fixing the bug, they want to move the messages accumulated in the DLQ back to the original source queue for reprocessing. How do you do this without manually copying messages one by one?

**Choices**
