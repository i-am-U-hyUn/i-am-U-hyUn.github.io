## QUESTION 101

**문제**: 솔루션 설계자가 퍼블릭 서브넷과 프라이빗 서브넷으로 구성된 VPC를 설계하고 있다. VPC와 서브넷은 IPv4 CIDR 블록을 사용하며, 고가용성을 위해 3개의 가용 영역(AZ) 각각에 퍼블릭 서브넷 1개와 프라이빗 서브넷 1개를 둔다. 인터넷 게이트웨이가 퍼블릭 서브넷의 인터넷 액세스를 제공한다. 프라이빗 서브넷의 EC2 인스턴스는 소프트웨어 업데이트를 다운로드할 수 있도록 인터넷에 액세스할 수 있어야 한다. 프라이빗 서브넷에 대한 인터넷 액세스를 활성화하려면 어떻게 해야 하는가?

**보기**
- A. **각 AZ의 퍼블릭 서브넷마다 하나씩 총 3개의 NAT 게이트웨이를 생성한다. 각 AZ의 비 VPC 트래픽을 해당 AZ의 NAT 게이트웨이로 전달하도록 프라이빗 라우팅 테이블을 구성한다.**
- B. 각 AZ의 프라이빗 서브넷마다 하나씩 3개의 NAT 인스턴스를 생성한다(NAT 인스턴스는 직접 관리해야 하는 EC2 기반 방식으로, 고가용성 구성과 패치·스케일링을 사용자가 떠안아야 해 AWS가 더 이상 권장하지 않는 방식).
- C. 프라이빗 서브넷 중 하나에 두 번째 인터넷 게이트웨이를 생성한다(인터넷 게이트웨이는 퍼블릭 IP가 있는 리소스와 인터넷을 직접 연결하는 용도로, 프라이빗 서브넷에 붙인다고 해서 아웃바운드 인터넷 액세스가 생기지 않는다).
- D. 퍼블릭 서브넷 중 하나에 송신 전용 인터넷 게이트웨이를 생성한다(송신 전용 인터넷 게이트웨이는 IPv6 전용 아웃바운드 트래픽을 위한 구성 요소이며, IPv4 기반 아웃바운드 인터넷 액세스에는 사용할 수 없다).

**정답: A**

**해설**
프라이빗 서브넷의 인스턴스가 아웃바운드로만 인터넷에 접근하려면 **NAT 게이트웨이**를 퍼블릭 서브넷에 배치하고, 프라이빗 서브넷의 라우팅 테이블에서 인터넷행 트래픽(0.0.0.0/0)을 이 NAT 게이트웨이로 향하게 해야 합니다. 고가용성을 위해서는 AZ마다 독립된 NAT 게이트웨이를 두고 같은 AZ의 프라이빗 서브넷이 자신의 AZ에 있는 NAT 게이트웨이만 사용하도록 라우팅해야, 특정 AZ 장애가 다른 AZ의 인터넷 액세스에 영향을 주지 않습니다.

**왜 다른 보기는 오답인가**
- B: NAT 인스턴스는 레거시 방식으로 대역폭 확장, 고가용성 구성, 패치 관리를 모두 직접 해야 하므로 관리형 NAT 게이트웨이보다 운영 부담이 큽니다.
- C: 인터넷 게이트웨이는 퍼블릭 서브넷의 리소스와 인터넷 간 양방향 라우팅을 담당할 뿐, 프라이빗 서브넷의 아웃바운드 인터넷 접근을 제공하지 못합니다.
- D: 송신 전용 인터넷 게이트웨이(Egress-Only Internet Gateway)는 IPv6 트래픽 전용이며, 이 시나리오는 IPv4 CIDR을 사용하므로 해당되지 않습니다.

> 💡 **시험 꿀팁**: **프라이빗 서브넷에서 아웃바운드 인터넷 액세스**가 필요하다는 조건이 나오면, AZ마다 하나씩 배치한 **NAT 게이트웨이**가 표준 정답입니다.

## QUESTION 102

**문제**: 회사가 온프레미스 데이터 센터를 AWS로 마이그레이션하려고 한다. 데이터 센터는 NFS 기반 파일 시스템에 데이터를 저장하는 SFTP 서버를 운영하며, 전송해야 할 데이터는 200GB이다. 이 서버는 Amazon EFS 파일 시스템을 사용하는 EC2 인스턴스에서 호스팅되어야 한다. 솔루션 설계자는 이 작업을 자동화하기 위해 어떤 단계 조합을 취해야 하는가? (2개를 선택하세요.)

**보기**
- A. **EFS 파일 시스템과 동일한 가용 영역에서 EC2 인스턴스를 시작한다.**
- B. **온프레미스 데이터 센터에 AWS DataSync 에이전트를 설치한다.**
- C. 데이터를 저장할 EC2 인스턴스에 보조 EBS 볼륨을 생성한다(EBS는 블록 스토리지로 NFS 프로토콜을 지원하지 않으며, 대상이 EFS인 이 시나리오와 맞지 않는다).
- D. 운영체제의 복사 명령을 수동으로 사용해 데이터를 EC2 인스턴스로 옮긴다(수동 작업은 "자동화"라는 요구 사항에 위배되며 반복 가능성과 안정성이 떨어진다).
- E. AWS DataSync를 사용해 온프레미스 SFTP 서버에 대한 위치(location) 구성을 생성한다(DataSync는 SFTP 프로토콜이 아니라 NFS, SMB, S3, EFS, FSx 등의 위치 유형을 지원하므로, SFTP 서버 자체를 위치로 구성할 수 없다).

**정답: A, B**

**해설**
**AWS DataSync**는 온프레미스와 AWS 스토리지 서비스 간 데이터 전송을 자동화·검증·암호화하는 관리형 서비스입니다. 온프레미스에는 데이터를 읽어 전송할 **DataSync 에이전트**(VM 또는 EC2 인스턴스)를 설치해야 하며, 이 시나리오처럼 NFS 기반 파일 시스템에서 Amazon EFS로 옮기는 작업에 적합합니다. 전송 후 EFS를 마운트할 EC2 인스턴스는 EFS와 같은 가용 영역에 두면 지연 시간이 최소화되고 마운트 대상 선택이 단순해집니다.

**왜 다른 보기는 오답인가**
- C: EFS가 아닌 EBS에 데이터를 저장하면 NFS 파일 시스템 요구 사항 자체를 충족하지 못합니다.
- D: 수동 복사는 자동화 요구 사항에 정면으로 위배됩니다.
- E: DataSync 위치는 NFS 공유 자체(온프레미스의 NFS 파일 시스템)를 가리켜야 하며, SFTP 서버 프로토콜을 대상으로 위치를 구성할 수 없습니다. SFTP 프로토콜 자체를 옮기는 용도라면 AWS Transfer Family가 더 적합합니다.

> 💡 **시험 꿀팁**: 온프레미스 NFS/SMB 데이터를 EFS/S3로 **자동 마이그레이션**해야 한다는 조건이 나오면 **DataSync 에이전트 설치 + DataSync 작업 구성**이 표준 정답입니다.

## QUESTION 103

**문제**: 회사에 매일 같은 시간에 실행되는 AWS Glue ETL 작업이 있다. 이 작업은 Amazon S3 버킷의 XML 데이터를 처리하며, 매일 새로운 데이터가 버킷에 추가된다. 솔루션 설계자는 Glue가 매 실행마다 모든 데이터를 다시 처리하고 있음을 발견했다. 오래된 데이터의 재처리를 막으려면 어떻게 해야 하는가?

**보기**
- A. **작업 북마크(Job bookmark)를 사용하도록 작업을 편집한다.**
- B. 데이터가 처리된 후 삭제되도록 작업을 편집한다(원본 데이터를 삭제하면 재처리 문제와 무관하게 데이터 손실 위험이 생기고, 다른 목적의 재사용도 불가능해진다).
- C. NumberOfWorkers 필드를 1로 설정한다(이는 작업에 할당되는 워커 수, 즉 처리 용량을 조정하는 설정일 뿐 처리 대상 데이터 범위와는 무관하다).
- D. FindMatches 머신러닝 변환을 사용한다(FindMatches는 중복 레코드를 찾아 매칭하는 ML 변환으로, 이미 처리된 데이터를 추적하는 기능과는 관계가 없다).

**정답: A**

**해설**
**AWS Glue 작업 북마크**는 이전 실행에서 이미 처리한 데이터(파일, 파티션, 테이블 등)에 대한 상태 정보를 유지하는 기능입니다. 북마크를 활성화하면 Glue는 다음 실행 시 새로 추가된 데이터만 식별해 처리하고, 이미 처리된 오래된 데이터는 건너뛰므로 매일 반복 실행되는 ETL 작업에서 중복 처리를 방지할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 원본 삭제는 재처리 방지의 정석적인 방법이 아니며 데이터 무결성과 재사용성을 해칩니다.
- C: 워커 수 조정은 성능/비용에 관한 설정으로, 처리 범위(전체 vs 신규 데이터)를 제어하지 않습니다.
- D: FindMatches는 레코드 중복 제거·매칭을 위한 ML 변환으로 실행 이력 추적과 무관합니다.

> 💡 **시험 꿀팁**: Glue ETL 작업이 **매번 전체 데이터를 재처리**하는 문제가 나오면 **작업 북마크(Job Bookmark)** 활성화가 표준 정답입니다.

## QUESTION 104

**문제**: 솔루션 설계자가 웹사이트를 위한 고가용성 인프라를 설계해야 한다. 이 웹사이트는 EC2 인스턴스에서 실행되는 Windows 웹 서버로 구동된다. 솔루션 설계자는 수천 개의 IP 주소에서 발생하는 대규모 DDoS 공격을 완화할 수 있어야 하며, 다운타임은 허용되지 않는다. 웹사이트를 이러한 공격으로부터 보호하기 위해 어떤 조치를 취해야 하는가? (2개를 선택하세요.)

**보기**
- A. **AWS Shield Advanced를 사용해 DDoS 공격을 완화한다.**
- B. 공격자를 자동으로 차단하도록 Amazon GuardDuty를 구성한다(GuardDuty는 계정·워크로드에 대한 악성 활동을 탐지하는 위협 탐지 서비스로, 자체적으로 DDoS 트래픽을 완화하는 기능은 제공하지 않는다).
- C. **정적·동적 콘텐츠 모두에 Amazon CloudFront를 사용하도록 웹사이트를 구성한다.**
- D. Lambda 함수로 VPC 네트워크 ACL에 공격자 IP를 자동 추가한다(수천 개의 분산된 IP를 일일이 차단 목록에 추가하는 방식은 확장성이 없고 대응 속도도 느려 대규모 DDoS에는 비효율적이다).
- E. 80% CPU 사용률 기준의 대상 추적 조정 정책과 함께 스팟 인스턴스로 구성된 Auto Scaling 그룹을 사용한다(오토스케일링은 정상적인 트래픽 증가에 대응하는 수단이며, 대규모 DDoS 트래픽 자체를 흡수·차단하는 보안 대책이 아니다).

**정답: A, C**

**해설**
**AWS Shield Advanced**는 상시 트래픽 모니터링과 자동 완화 기법으로 대규모 네트워크/전송 계층 DDoS 공격에 대응하며, 애플리케이션 계층 공격 탐지와 대응팀(DRT) 지원까지 제공합니다. 여기에 **Amazon CloudFront**를 앞단에 두면 AWS의 글로벌 엣지 네트워크가 트래픽을 분산 흡수하고 캐싱을 통해 오리진 부하를 줄여, 정적 콘텐츠뿐 아니라 동적 콘텐츠 요청에 대해서도 DDoS 복원력을 크게 높일 수 있습니다.

**왜 다른 보기는 오답인가**
- B: GuardDuty는 위협 탐지·가시성 제공 서비스이며 DDoS 트래픽을 직접 차단하는 완화 서비스가 아닙니다.
- D: 좀비 PC 수천~수만 대에서 오는 IP를 건별로 ACL에 추가하는 방식은 규모 면에서 실효성이 없습니다.
- E: Auto Scaling은 정상 트래픽 증가에 대한 확장 대응이지, 악의적인 대규모 DDoS 트래픽 자체를 막는 방어 수단이 아닙니다.

> 💡 **시험 꿀팁**: **대규모 DDoS 공격 완화**가 요구 사항으로 나오면 **AWS Shield Advanced + CloudFront(엣지 네트워크 분산)** 조합이 표준 정답입니다.

## QUESTION 105

**문제**: 회사가 새로운 서버리스 워크로드를 배포하려고 한다. 솔루션 설계자는 최소 권한 원칙에 따라 AWS Lambda 함수 실행에 필요한 권한을 구성해야 하며, Amazon EventBridge(CloudWatch Events) 규칙이 이 함수를 호출한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. lambda:InvokeFunction을 작업으로, *를 보안 주체로 사용해 함수에 실행 역할을 추가한다(보안 주체를 *로 지정하면 누구나 함수를 호출할 수 있게 되어 최소 권한 원칙에 정면으로 위배된다).
- B. lambda:InvokeFunction을 작업으로, Service: lambda.amazonaws.com을 보안 주체로 사용해 함수에 실행 역할을 추가한다(보안 주체가 EventBridge가 아닌 Lambda 서비스 자신으로 잘못 지정되어 있고, 애초에 함수를 호출할 권한은 함수의 "실행 역할"이 아니라 리소스 기반 정책으로 부여해야 한다).
- C. lambda:*를 작업으로, Service: events.amazonaws.com을 보안 주체로 사용해 리소스 기반 정책을 함수에 추가한다(lambda:*는 함수 호출뿐 아니라 삭제·수정 등 모든 Lambda 작업 권한까지 부여하므로 최소 권한 원칙에 위배된다).
- D. **lambda:InvokeFunction을 작업으로, Service: events.amazonaws.com을 보안 주체로 사용해 리소스 기반 정책을 함수에 추가한다.**

**정답: D**

**해설**
EventBridge 규칙이 Lambda 함수를 호출하도록 허용하려면 함수에 **리소스 기반 정책(resource-based policy)**을 추가해, 보안 주체를 EventBridge 서비스(`events.amazonaws.com`)로, 허용 작업을 함수 호출에 필요한 최소 권한인 `lambda:InvokeFunction`으로 한정해야 합니다. 이는 "함수를 실행하는 데 필요한 IAM 역할"이 아니라 "누가 이 함수를 호출할 수 있는가"를 정의하는 정책이며, 필요한 서비스와 필요한 작업만 정확히 명시하는 것이 최소 권한 원칙에 부합합니다.

**왜 다른 보기는 오답인가**
- A: 보안 주체를 와일드카드(*)로 열어두면 누구나 함수를 호출할 수 있어 최소 권한을 완전히 위반합니다.
- B: 보안 주체가 EventBridge가 아닌 Lambda 서비스로 잘못 설정되어 있어, EventBridge 규칙의 호출을 허용하는 목적을 달성하지 못합니다.
- C: `lambda:*`는 호출뿐 아니라 함수 삭제, 구성 변경 등 불필요하게 광범위한 권한까지 부여해 최소 권한 원칙에 어긋납니다.

> 💡 **시험 꿀팁**: **다른 AWS 서비스가 Lambda 함수를 호출**하도록 허용해야 한다면, 함수의 **리소스 기반 정책**에 해당 서비스 보안 주체(`Service: xxx.amazonaws.com`)와 `lambda:InvokeFunction`만 최소한으로 부여하는 것이 표준 정답입니다.

## QUESTION 108

**문제**: 자동차 판매 웹사이트가 Amazon RDS 데이터베이스에 매물 목록을 저장한다. 자동차가 판매되면 웹사이트에서 목록을 제거해야 하고, 이 변경 사항을 여러 대상 시스템으로 전달해야 한다. 솔루션 설계자는 어떤 설계를 추천해야 하는가?

**보기**
- A. RDS 데이터베이스가 업데이트될 때 트리거되는 Lambda 함수를 생성해, 대상이 소비할 SQS 대기열로 정보를 보낸다(단일 SQS 대기열은 하나의 컨슈머 그룹이 메시지를 나눠 가져가는 구조이므로, 동일한 이벤트를 "여러" 독립적인 대상 시스템에 각각 전달하는 팬아웃 요구에는 적합하지 않다).
- B. 위와 동일하되 SQS FIFO 대기열을 사용한다(FIFO 큐 역시 순서 보장에 초점을 둔 단일 대기열 구조로, 여러 대상 시스템에 대한 팬아웃 배포 문제를 해결하지 못한다).
- C. RDS 이벤트 알림을 구독하고, 여러 SNS 주제로 팬아웃하는 SQS 대기열을 하나 두어 Lambda로 대상을 업데이트한다(SNS로 팬아웃하려면 SNS 주제가 먼저 있어야 하고 그 아래에 각 대상별 SQS 대기열을 구독시켜야 하는데, 이 보기는 순서가 뒤바뀌어 있어 다중 독립 구독 구조를 만들지 못한다).
- D. **RDS 이벤트 알림을 구독하고, SNS 주제를 여러 SQS 대기열로 팬아웃한다. Lambda 함수로 각 대상을 업데이트한다.**

**해설**
하나의 이벤트를 **여러 독립적인 대상 시스템**에 동시에 전달하려면 **SNS의 팬아웃(fan-out) 패턴**이 표준적인 해법입니다. RDS 이벤트 알림을 SNS 주제에 게시하고, 이 주제를 여러 SQS 대기열이 각각 구독하도록 구성하면 각 대상 시스템이 독립적인 큐에서 자신의 속도에 맞춰 메시지를 처리할 수 있고, Lambda가 각 큐를 폴링해 최종 대상 시스템을 업데이트합니다.

**왜 다른 보기는 오답인가**
- A, B: 하나의 SQS 대기열(FIFO 여부와 무관)만으로는 동일 메시지를 여러 독립적인 소비 시스템에 각각 전달할 수 없고, 하나의 컨슈머 그룹이 메시지를 나눠 가져가는 구조가 됩니다.
- C: SNS로 팬아웃하려면 SNS 주제 하나에 여러 SQS 대기열을 구독시키는 구조가 되어야 하는데, 이 보기는 SQS를 먼저 두고 그 뒤에 여러 SNS 주제로 보내는 구조로 순서가 잘못되어 있어 다중 대상 배포에 적합하지 않습니다.

> 💡 **시험 꿀팁**: 하나의 이벤트를 **여러 독립적인 대상 시스템**에 전달해야 한다는 요구가 나오면 **SNS → 여러 SQS 대기열 팬아웃** 패턴이 표준 정답입니다.

**문제**: 회사가 Amazon S3에 데이터를 저장하며 데이터가 변경되지 않도록 해야 한다. 새로 업로드된 객체는 회사가 수정을 결정할 때까지 일정하지 않은(정해지지 않은) 기간 동안 변경 불가 상태를 유지해야 하며, 계정 내 특정 사용자만 객체를 삭제할 수 있어야 한다. 솔루션 설계자는 무엇을 해야 하는가?

- B. S3 객체 잠금과 버전 관리를 활성화하고 보존 기간을 100년으로 설정한 거버넌스 모드를 기본 보존 모드로 사용한다(고정된 보존 기간을 미리 설정하는 방식은 "일정하지 않은 기간 동안" 유지되다가 회사가 임의 시점에 수정을 결정한다는 요구 사항과 맞지 않는다).

S3 **객체 잠금(Object Lock)**의 **법적 보존(Legal Hold)** 기능은 보존 기간을 미리 정하지 않고도 객체 버전의 덮어쓰기·삭제를 막을 수 있으며, `s3:PutObjectLegalHold` 권한을 가진 사용자가 보존을 해제하기 전까지 무기한 유지됩니다. 이는 "회사가 수정을 결정할 때까지 정해지지 않은 기간" 동안 불변 상태를 유지해야 한다는 요구에 정확히 부합하며, 해당 권한을 특정 IAM 사용자에게만 부여함으로써 접근 제어 요구 사항도 함께 충족합니다.

**왜 다른 보기는 오답인가**

- B: 보존 기간(retention period)을 고정값(100년)으로 설정하는 방식은 "정해지지 않은 기간"이라는 조건과 어긋나며, 법적 보존과 달리 특정 시점에 자유롭게 해제할 수 있는 구조가 아닙니다.
- C: 사후에 CloudTrail 알림을 받고 복원하는 방식은 애초에 변경 자체를 막지 못하는 사후 대응이며 운영 오버헤드도 큽니다.

> 💡 **시험 꿀팁**: 보존 **기간을 정할 수 없고** 회사가 임의 시점에 해제하기 전까지 객체를 불변 상태로 유지해야 한다면 S3 객체 잠금의 **법적 보존(Legal Hold)**이 표준 정답입니다.

- C. **미리 서명된 URL(presigned URL)을 사용해 각 사용자의 브라우저에서 S3로 이미지를 직접 업로드하도록 애플리케이션을 구성한다.**
- D. **이미지가 업로드될 때 Lambda 함수를 호출하도록 S3 이벤트 알림을 구성하고, 이 함수로 이미지 크기를 조정한다.**
- E. 업로드된 이미지 크기 조정을 위해 EventBridge 규칙으로 Lambda 함수를 일정에 따라 호출한다(스케줄 기반 실행은 업로드 시점과 리사이즈 사이에 지연이 발생하고, 새로 업로드된 파일을 식별하는 로직도 별도로 필요해 비효율적이다).

**정답: C, D**

**해설**
**미리 서명된 URL**을 사용하면 사용자의 브라우저가 웹 서버를 거치지 않고 S3에 직접 이미지를 업로드할 수 있어, 웹 서버의 부하와 애플리케이션 내 결합도를 크게 줄이면서 업로드 성능도 개선됩니다. 이후 **S3 이벤트 알림**으로 업로드 완료 시점에 **Lambda** 함수를 트리거해 리사이징을 수행하면, 이미지 처리 작업을 웹 서버에서 완전히 분리해 서버리스로 확장성 있게 처리할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Glacier는 즉시 조회가 필요한 사용자 업로드 이미지에 적합한 스토리지 클래스가 아닙니다.
- B: 웹 서버가 여전히 업로드 경로에 남아 있어 느린 업로드 문제와 결합도 문제를 해결하지 못합니다.
- E: 스케줄 기반 실행은 업로드 이벤트와 실시간으로 연동되지 않아 지연이 발생하고, 처리 대상 신규 이미지를 식별하는 추가 로직이 필요합니다.

> 💡 **시험 꿀팁**: **업로드로 인한 웹 서버 부하와 결합도**를 줄여야 한다면 **미리 서명된 URL로 S3 직접 업로드 + S3 이벤트 알림 기반 Lambda 처리** 조합이 표준 정답입니다.

## QUESTION 111

**문제**: 한 회사가 메시지 처리 시스템을 AWS로 마이그레이션했다. 시스템은 EC2에서 실행되는 ActiveMQ 대기열로 메시지를 수신하고, EC2에서 실행되는 소비자 애플리케이션이 메시지를 처리해 EC2의 MySQL 데이터베이스에 결과를 기록한다. 회사는 낮은 운영 복잡성으로 고가용성을 확보하고 싶다. 가장 높은 가용성을 제공하는 아키텍처는 무엇인가?

**보기**
- A. 다른 AZ에 두 번째 ActiveMQ 서버, 소비자 EC2 인스턴스를 추가하고 MySQL 데이터베이스를 다른 AZ에 복제한다(자체 관리형 ActiveMQ와 자체 관리형 MySQL 복제를 직접 운영해야 하므로 페일오버 자동화가 없고 운영 복잡성이 크다).
- B. Amazon MQ의 두 AZ 활성/대기 브로커를 사용하고, 다른 AZ에 소비자 EC2 인스턴스를 추가하며 MySQL을 다른 AZ에 복제한다(메시지 브로커는 관리형으로 개선되었지만, MySQL을 EC2에서 자체 관리·복제하는 부분은 여전히 페일오버 자동화가 없어 운영 부담이 남는다).
- C. Amazon MQ의 활성/대기 브로커와 다중 AZ RDS for MySQL을 사용하되, 소비자는 단순히 다른 AZ에 EC2 인스턴스를 추가하는 방식이다(소비자 인스턴스가 Auto Scaling 그룹으로 관리되지 않아 장애 시 자동 교체·확장이 되지 않으므로 D보다 가용성이 낮다).
- D. **두 AZ에 활성/대기 브로커로 구성된 Amazon MQ, 두 AZ에 걸친 소비자 EC2 Auto Scaling 그룹, 다중 AZ가 활성화된 Amazon RDS for MySQL을 사용한다.**

**정답: D**

**해설**
**Amazon MQ**의 활성/대기 브로커 배포는 브로커 장애 시 자동으로 대기 인스턴스로 전환해 메시지 브로커 계층의 고가용성을 관리형으로 제공합니다. 소비자 계층은 여러 AZ에 걸친 **Auto Scaling 그룹**으로 구성해 인스턴스 장애 시 자동 교체와 수요에 따른 확장을 보장하고, 데이터베이스 계층은 **다중 AZ RDS for MySQL**을 사용해 동기 복제와 자동 페일오버를 관리형으로 확보합니다. 이 세 계층 모두를 관리형 고가용성 기능으로 구성하는 것이 운영 복잡성을 최소화하면서 가용성을 극대화하는 방법입니다.

**왜 다른 보기는 오답인가**
- A: 자체 관리형 ActiveMQ와 MySQL 복제는 페일오버를 수동/커스텀 스크립트로 처리해야 해 운영 복잡성이 매우 큽니다.
- B: 메시지 브로커는 개선되었지만 MySQL을 EC2에서 자체 복제하는 방식은 자동 페일오버가 없어 D에 비해 가용성과 운영 효율이 떨어집니다.
- C: 다중 AZ RDS까지는 맞지만 소비자 계층이 Auto Scaling으로 구성되지 않아 인스턴스 장애 시 자동 복구가 되지 않습니다.

> 💡 **시험 꿀팁**: 브로커·컴퓨팅·데이터베이스 각 계층에서 고가용성을 확보해야 한다면 **Amazon MQ 활성/대기 + Auto Scaling 그룹 + 다중 AZ RDS**처럼 계층마다 관리형 HA 기능을 적용하는 조합이 표준 정답입니다.

## QUESTION 112

**문제**: 회사가 온프레미스 서버에서 컨테이너화된 웹 애플리케이션을 호스팅하고 있으며, 요청량이 급증해 온프레미스 서버가 감당하지 못하고 있다. 회사는 최소한의 코드 변경과 개발 노력으로 애플리케이션을 AWS로 옮기고 싶어한다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. **Amazon ECS에서 AWS Fargate를 사용해 Service Auto Scaling으로 컨테이너화된 웹 애플리케이션을 실행하고, Application Load Balancer로 수신 요청을 분산한다.**
- B. 두 개의 EC2 인스턴스로 컨테이너화된 애플리케이션을 호스팅하고 ALB로 요청을 분산한다(EC2 인스턴스와 그 위의 컨테이너 런타임/클러스터를 직접 프로비저닝하고 패치해야 하므로 Fargate 대비 운영 오버헤드가 크다).
- C. 지원 언어로 새 코드를 작성해 여러 Lambda 함수로 부하를 감당하고 API Gateway를 진입점으로 사용한다(기존 컨테이너화된 애플리케이션을 Lambda 함수 코드로 다시 작성해야 하므로 "최소한의 코드 변경"이라는 요구 사항에 정면으로 위배된다).

**정답: A**

**해설**
**AWS Fargate**를 사용하면 서버나 클러스터를 직접 프로비저닝·관리할 필요 없이 컨테이너 이미지를 그대로 **Amazon ECS**에서 실행할 수 있어, 기존 컨테이너화된 애플리케이션을 코드 변경 없이 옮길 수 있습니다. **Service Auto Scaling**으로 트래픽 증가에 맞춰 태스크 수를 자동 조정하고, **Application Load Balancer**로 요청을 여러 태스크에 분산하면 온프레미스의 용량 한계를 해소하면서도 운영 오버헤드를 최소화할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: EC2 기반 호스팅은 인스턴스 프로비저닝, 패치, 컨테이너 오케스트레이션 구성까지 직접 관리해야 해 Fargate보다 운영 부담이 큽니다.
- C: Lambda로 옮기려면 컨테이너 애플리케이션을 함수 코드로 재작성해야 하므로 최소 코드 변경 요구를 위반합니다.
- D: ParallelCluster는 HPC 클러스터 관리 도구로 일반 웹 트래픽 처리 시나리오와 목적이 다릅니다.

> 💡 **시험 꿀팁**: **컨테이너화된 애플리케이션을 코드 변경 최소화**하며 AWS로 옮기고 확장해야 한다면 **ECS + Fargate + ALB** 조합이 표준 정답입니다.

## QUESTION 113

**문제**: 회사가 보고용 50TB 데이터를 온프레미스에서 AWS로 이전하려고 한다. 온프레미스의 사용자 지정 애플리케이션은 매주 데이터 변환 작업을 실행하며, 이 작업은 데이터 이전이 끝나는 대로 최대한 빨리 AWS에서 계속 실행되어야 한다. 데이터 센터에는 추가 워크로드에 쓸 네트워크 대역폭이 없다. 최소한의 운영 오버헤드로 데이터 전송과 변환 작업 이전을 모두 충족하는 솔루션은 무엇인가?

**보기**
- A. AWS DataSync로 데이터를 이동하고 AWS Glue로 변환 작업을 새로 만든다(DataSync는 네트워크를 통해 전송하는 서비스인데, 데이터 센터에 추가 워크로드용 네트워크 대역폭이 없다는 제약 조건과 정면으로 충돌한다).
- B. AWS Snowcone 디바이스로 데이터를 이동하고 디바이스에 변환 애플리케이션을 배포한다(Snowcone은 최대 8TB/14TB 수준의 소용량 디바이스로 50TB를 처리하기에 용량이 부족하다).
- C. **AWS Snowball Edge Storage Optimized 디바이스를 주문해 데이터를 복사하고, AWS Glue로 변환 작업을 새로 구성한다.**
- D. 컴퓨팅이 포함된 Snowball Edge Storage Optimized 디바이스로 데이터를 옮기고, AWS에서 새 EC2 인스턴스를 만들어 변환 애플리케이션을 실행한다(변환 애플리케이션을 EC2에서 별도로 운영·관리해야 하므로 관리형 서비스인 Glue를 쓰는 C보다 운영 오버헤드가 크다).

**정답: C**

**해설**
네트워크 대역폭이 없다는 제약 때문에 온라인 전송 서비스를 쓸 수 없으므로, 오프라인 물리 배송 방식인 **AWS Snowball Edge Storage Optimized**가 적합합니다. 이 디바이스는 최대 80TB 수준의 대용량 스토리지를 제공해 50TB 데이터를 감당할 수 있습니다. 전송 후 AWS 클라우드에서는 완전관리형 ETL 서비스인 **AWS Glue**로 변환 작업을 구성하면, 별도의 서버 운영 없이 서버리스로 매주 반복되는 변환 작업을 이어갈 수 있어 운영 오버헤드가 가장 낮습니다.

**왜 다른 보기는 오답인가**
- A: DataSync는 네트워크 기반 전송 서비스이므로 대역폭이 없는 이 시나리오의 제약과 맞지 않습니다.
- B: Snowcone은 소규모(8~14TB) 데이터 전송용 디바이스로 50TB에는 용량이 부족합니다.
- D: EC2에서 변환 애플리케이션을 직접 운영하면 인스턴스 관리, 패치, 확장까지 회사가 떠안아야 해 Glue를 사용하는 방식보다 운영 부담이 큽니다.

> 💡 **시험 꿀팁**: **네트워크 대역폭이 없는 대용량(수십 TB) 데이터 이전**에는 **Snowball Edge**, 이후 변환 작업은 **AWS Glue** 같은 서버리스 관리형 서비스로 이어가는 조합이 표준 정답입니다.

## QUESTION 114

**문제**: 사용자가 사진을 업로드하고 이미지에 액자를 씌울 수 있는 이미지 분석 애플리케이션이 있다. 사용자는 이미지와 프레임을 지정하는 메타데이터를 함께 업로드하며, 애플리케이션은 단일 EC2 인스턴스와 DynamoDB로 메타데이터를 저장한다. 사용자 수와 동시 접속자 수의 변동 폭이 커지고 있어, 애플리케이션이 이러한 증가하는 요구 사항에 맞춰 확장 가능해야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. Lambda로 사진을 처리하고, 사진과 메타데이터를 모두 DynamoDB에 저장한다(DynamoDB는 항목 크기 제한이 있는 NoSQL 데이터베이스로, 이미지와 같은 대용량 바이너리 객체를 저장하는 용도로는 비효율적이고 비용도 높아진다).
- B. Kinesis Data Firehose로 사진을 처리하고 사진과 메타데이터를 저장한다(Kinesis Data Firehose는 스트리밍 데이터를 캡처해 S3/Redshift 등으로 전달하는 서비스로, 사진 업로드·리사이즈 같은 요청-응답형 처리에는 적합하지 않다).
- C. **Lambda로 사진을 처리하고 Amazon S3에 사진을 저장하며, DynamoDB는 그대로 메타데이터 저장용으로 유지한다.**
- D. EC2 인스턴스를 3개로 늘리고, 프로비저닝된 IOPS SSD(io2) EBS 볼륨에 사진과 메타데이터를 저장한다(EC2 인스턴스 수를 고정으로 늘리는 방식은 변동성이 큰 동시 접속자 수에 자동으로 대응하지 못하고, EBS는 특정 인스턴스에 종속된 블록 스토리지라 여러 인스턴스에서 공유하기에도 적합하지 않다).

**정답: C**

**해설**
이미지 같은 대용량 객체는 내구성과 확장성이 뛰어난 **Amazon S3**에 저장하고, 이미지 처리는 수요에 따라 자동으로 확장/축소되는 **AWS Lambda**로 오프로드하는 것이 적합합니다. 메타데이터는 이미 사용 중인 **DynamoDB**에 계속 저장하면 되는데, DynamoDB는 트래픽 변동에도 일관된 성능을 제공하는 완전관리형 NoSQL 데이터베이스이기 때문입니다. 이 조합은 EC2 인스턴스를 직접 확장·관리할 필요 없이 각 계층을 그 목적에 맞는 서비스로 분리해 변동성 큰 트래픽에 자동으로 대응합니다.

**왜 다른 보기는 오답인가**
- A: DynamoDB에 이미지 바이너리를 저장하면 항목 크기 제한과 비용 문제가 발생해 이미지 저장소로 적합하지 않습니다.
- B: Kinesis Data Firehose는 스트리밍 데이터 전달용이며 사용자 업로드 이미지를 처리·저장하는 워크플로우에는 맞지 않습니다.
- D: 고정된 수의 EC2 인스턴스와 EBS 볼륨은 변동성 큰 동시 접속자 수에 자동으로 확장되지 않고, EBS는 여러 인스턴스가 동시에 접근하기 어려운 구조입니다.

> 💡 **시험 꿀팁**: 사용자 업로드 **이미지 저장 + 변동성 큰 트래픽 확장**이 요구되면 **Lambda(처리) + S3(이미지 저장) + DynamoDB(메타데이터)** 조합이 표준 정답입니다.

## QUESTION 115

**문제**: 의료 기록 회사가 EC2 인스턴스에서 애플리케이션을 호스팅하며, 이 애플리케이션은 S3에 저장된 고객 데이터 파일을 처리한다. EC2 인스턴스는 퍼블릭 서브넷에 있고 인터넷을 통해 S3에 접근하며, 그 외 다른 네트워크 액세스는 필요 없다. 새로운 요구 사항으로 파일 전송 트래픽이 인터넷을 거치지 않고 프라이빗 경로를 사용해야 한다. 솔루션 설계자가 권장해야 할 네트워크 아키텍처 변경은 무엇인가?

**보기**
- A. NAT 게이트웨이를 생성하고 퍼블릭 서브넷의 라우팅 테이블이 NAT 게이트웨이를 거쳐 S3로 트래픽을 보내도록 구성한다(NAT 게이트웨이를 거쳐도 트래픽은 여전히 인터넷 경로를 통해 S3의 퍼블릭 엔드포인트로 나가므로 "인터넷을 통하지 않는" 요구 사항을 충족하지 못한다).
- B. S3 접두사 목록(prefix list)에 대한 트래픽만 허용하도록 EC2 보안 그룹의 아웃바운드를 제한한다(트래픽을 필터링할 뿐 경로 자체를 인터넷에서 프라이빗 경로로 바꾸지는 못한다).
- C. **EC2 인스턴스를 프라이빗 서브넷으로 옮기고, Amazon S3용 VPC 엔드포인트(게이트웨이 엔드포인트)를 생성해 프라이빗 서브넷의 라우팅 테이블에 연결한다.**
- D. VPC에서 인터넷 게이트웨이를 제거하고 AWS Direct Connect 연결을 설정해 S3로 트래픽을 라우팅한다(Direct Connect는 온프레미스와 AWS 간의 전용 회선 연결로, 이미 AWS 내부에 있는 EC2와 S3 간 통신 경로 문제와는 무관하며 구축 비용과 기간도 과도하다).

**정답: C**

**해설**
S3 이외의 네트워크 액세스가 필요 없다는 조건은 **S3 게이트웨이 VPC 엔드포인트**의 전형적인 사용 사례입니다. EC2 인스턴스를 인터넷 게이트웨이 경로가 없는 **프라이빗 서브넷**으로 옮기고, 해당 서브넷의 라우팅 테이블에 S3용 게이트웨이 엔드포인트를 연결하면 S3로 향하는 트래픽이 AWS 내부의 프라이빗 네트워크 경로만 사용하게 되어 인터넷을 전혀 거치지 않습니다.

**왜 다른 보기는 오답인가**
- A: NAT 게이트웨이는 아웃바운드를 인터넷을 통해 내보내는 구성 요소이므로 프라이빗 경로 요구 사항과 반대 방향입니다.
- B: 보안 그룹은 트래픽의 허용 여부를 필터링할 뿐 실제 라우팅 경로(인터넷 vs 프라이빗)를 바꾸지 않습니다.
- D: Direct Connect는 온프레미스-AWS 간 연결을 위한 것으로, AWS 내부의 EC2-S3 통신에는 해당되지 않고 구성 비용과 기간도 과도합니다.

> 💡 **시험 꿀팁**: EC2에서 **S3로만** 접근하면서 트래픽이 **인터넷을 거치지 않아야** 한다면, 프라이빗 서브넷 + **S3 게이트웨이 VPC 엔드포인트** 조합이 표준 정답입니다.

- C: 연 4회만 갱신되는 정적 콘텐츠에 Lambda 기반 콘텐츠 관리 로직을 만드는 것은 불필요한 개발·운영 부담입니다.

## QUESTION 118

**문제**: 회사가 여러 AZ의 EC2 인스턴스에서 실행되는 웹 애플리케이션을 구축 중이며, 약 900TB 규모의 텍스트 문서 저장소에 접근을 제공한다. 수요가 많은 기간이 예상되며, 스토리지 구성 요소가 항상 요구 사항을 충족하도록 확장 가능해야 한다. 회사는 전체 비용도 우려하고 있다. 어떤 스토리지 솔루션이 이 요구 사항을 가장 비용 효율적으로 충족하는가?

**보기**
- A. Amazon EBS(EBS는 특정 EC2 인스턴스에 연결되는 블록 스토리지로 개별 볼륨 크기와 확장에 한계가 있어, 900TB 규모의 다중 인스턴스 공유 저장소로는 비용·운영 면에서 비효율적이다).

- D. **Amazon S3**

**Amazon S3**는 사실상 무제한으로 확장되는 객체 스토리지로, 900TB 같은 대규모 데이터를 저장하면서도 높은 내구성과 가용성을 제공하고 저장 용량에 대한 과금 구조가 단순해 대용량 데이터 저장에 가장 비용 효율적입니다. 또한 여러 AZ의 EC2 인스턴스에서 웹 애플리케이션을 통해 텍스트 문서에 접근하는 시나리오에서, S3는 별도의 서버·볼륨 프로비저닝 없이 필요한 만큼 자동으로 확장되므로 수요 변동에도 유연하게 대응합니다.

**왜 다른 보기는 오답인가**
- A: EBS는 인스턴스 단위로 연결되는 블록 스토리지라 여러 인스턴스가 공유하는 대용량 문서 저장소로 확장하기에 비용과 구조 면에서 불리합니다.
- B: EFS도 확장 가능한 공유 파일 스토리지이지만, 순수 문서/객체 저장 용도에서는 S3보다 GB당 비용이 높습니다.
- C: OpenSearch Service는 검색·분석에 특화된 서비스로 대용량 원본 문서의 기본 저장소로는 적합하지 않습니다.

> 💡 **시험 꿀팁**: 수백 TB급 **대용량 데이터를 비용 효율적으로 저장·확장**해야 한다면 **Amazon S3**가 표준 정답입니다.

**왜 다른 보기는 오답인가**
- A: WAF 자체는 SQL 인젝션/XSS 방어에 적합하지만, 여러 계정에 개별적으로 설정해야 한다면 계정 수가 늘어날수록 관리 노력이 비례해서 커집니다.
- C, D: AWS Shield는 DDoS 공격에 대응하는 서비스로, SQL 인젝션·XSS 같은 애플리케이션 계층 공격 패턴 탐지는 WAF의 역할이며 Shield만으로는 이 요구 사항을 충족할 수 없습니다.

> 💡 **시험 꿀팁**: **여러 AWS 계정/리전**에 걸쳐 WAF 규칙을 **중앙에서 일관되게 관리**해야 한다면 **AWS Firewall Manager**가 표준 정답입니다.

## QUESTION 120

**문제**: 한 회사가 us-west-2 리전의 Network Load Balancer(NLB) 뒤에 있는 3개의 EC2 인스턴스에 자체 관리형 DNS 솔루션을 구현했다. 사용자 대부분은 미국과 유럽에 있으며, 회사는 솔루션의 성능과 가용성을 개선하고 싶어한다. 회사는 eu-west-1 리전에도 3개의 EC2 인스턴스를 시작하고 새 NLB의 대상으로 추가했다. 트래픽을 모든 EC2 인스턴스로 라우팅하기 위해 회사가 사용할 수 있는 솔루션은 무엇인가?

**보기**
- A. 두 NLB 중 하나로 요청을 라우팅하는 Route 53 지리적 위치 라우팅 정책을 만들고 CloudFront 배포를 생성해 Route 53 레코드를 오리진으로 사용한다(이미 자체 관리형 DNS 솔루션이 있는 상황에서 Route 53으로 전환하는 것은 추가 비용/변경이 필요하고, 정적 콘텐츠 캐싱이 목적이 아닌 이 시나리오에 CDN을 끼워 넣을 근거도 없다).
- B. **AWS Global Accelerator에서 표준 액셀러레이터를 생성하고, us-west-2와 eu-west-1에 엔드포인트 그룹을 만들어 두 NLB를 각 엔드포인트 그룹의 엔드포인트로 추가한다.**
- C. 6개의 EC2 인스턴스에 탄력적 IP를 연결하고, 이 중 하나로 요청을 라우팅하는 Route 53 지리적 위치 라우팅 정책을 만든 뒤 CloudFront 배포를 생성해 Route 53 레코드를 오리진으로 사용한다(인스턴스가 늘어날 때마다 개별 탄력적 IP를 일일이 관리해야 해 확장성이 떨어지고, Global Accelerator처럼 NLB 단위로 엔드포인트를 묶어 관리하는 방식보다 비효율적이다).
- D. 2개의 NLB를 2개의 ALB로 교체하고, 둘 중 하나로 요청을 라우팅하는 Route 53 지연 시간 라우팅 정책을 만든 뒤 CloudFront 배포를 생성해 Route 53 레코드를 오리진으로 사용한다(자체 관리형 DNS를 이미 사용 중인 상황에서 로드밸런서 종류까지 교체할 이유가 없고, A와 마찬가지로 불필요한 CDN 계층을 추가하게 된다).

**정답: B**

**해설**
**AWS Global Accelerator**는 두 개 이상의 리전에 있는 **Network Load Balancer**를 엔드포인트로 등록해, 사용자의 위치와 애플리케이션 상태에 따라 AWS 글로벌 네트워크를 통해 가장 가까운/정상적인 리전으로 트래픽을 라우팅합니다. 회사가 이미 자체 DNS 솔루션과 NLB 기반 아키텍처를 갖추고 있으므로, DNS나 로드밸런서 교체 없이 Global Accelerator의 엔드포인트 그룹에 두 리전의 NLB를 그대로 추가하기만 하면 되어 변경 폭이 가장 작으면서도 성능과 가용성을 함께 개선할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 이미 자체 DNS 솔루션이 있는데 Route 53으로 전환할 이유가 없고, 정적 콘텐츠 캐싱 요구가 없는 상황에 CloudFront를 추가하는 것도 불필요합니다.
- C: EC2 인스턴스마다 탄력적 IP를 개별 관리해야 해서, 인스턴스가 늘어날수록 관리 부담이 커지고 Global Accelerator의 NLB 단위 엔드포인트 관리보다 비효율적입니다.
- D: NLB를 ALB로 바꿀 이유가 없고, A와 마찬가지로 불필요한 CDN 계층까지 추가하게 됩니다.

> 💡 **시험 꿀팁**: **여러 리전의 NLB/ALB로 트래픽을 성능 기반으로 라우팅**해 가용성을 높이고 싶다면 **AWS Global Accelerator**가 표준 정답입니다.
