## QUESTION 381

**문제**: 방송사가 특정 대도시 권역의 시청자에게 실시간 4K 영상 렌더링/트랜스코딩 서비스를 제공해야 하며, 가장 가까운 AWS 리전도 왕복 지연시간이 실시간 방송 요구사항(한 자릿수 밀리초)에는 너무 멀다. 해당 도시에만 서비스를 제공하면 되고, 별도 데이터센터를 구축하고 싶지는 않다. 솔루션은?

**보기**
- A. 가장 가까운 리전에 배포하고 CloudFront로 캐싱(CloudFront 캐싱은 정적 콘텐츠 전송에는 유효하지만, 실시간 렌더링/트랜스코딩 같은 동적 컴퓨팅 워크로드 자체를 그 도시 근처로 옮겨주지는 못함).
- B. **AWS 로컬 존(Local Zones)을 사용해 해당 대도시 권역에 EC2, EBS 등 컴퓨팅/스토리지 인프라를 배치하고, 나머지 관리 기능(제어 플레인 등)은 상위 리전을 그대로 활용.**
- C. 해당 도시에 자체 데이터센터를 구축하고 Direct Connect로 AWS와 연결(자체 데이터센터 구축은 하고 싶지 않다는 요구에 정면으로 반함).
- D. AWS Wavelength를 사용해 통신사 네트워크 엣지에 배포(Wavelength는 통신사 5G 네트워크를 이용하는 모바일 최종 사용자 대상 초저지연에 특화되어 있으며, 이 시나리오처럼 특정 대도시 권역에 일반적인 저지연 컴퓨팅 인프라를 두는 목적에는 로컬 존이 더 적합).

**정답: B**

**해설**
**AWS 로컬 존(Local Zones)**은 대도시 권역 근처에 AWS 컴퓨팅, 스토리지, 데이터베이스, 기타 서비스를 배치하는 인프라 배포 옵션으로, 별도의 데이터센터 구축 없이도 해당 지역 사용자에게 한 자릿수 밀리초의 초저지연을 제공합니다. 상위 리전과 동일한 API/도구/콘솔을 그대로 사용하면서, 관리 기능은 상위 리전에 두고 실제 실시간 처리가 필요한 컴퓨팅 자원만 로컬 존에 배치할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: CloudFront는 정적 콘텐츠 캐싱에 효과적이지만, 실시간 렌더링/트랜스코딩 같은 동적 컴퓨팅 워크로드의 물리적 위치를 옮겨주지는 못합니다.
- C: 자체 데이터센터 구축은 이 문제가 원하지 않는다고 명시한 방식입니다.
- D: Wavelength는 통신사 네트워크 엣지의 모바일 사용자 대상이며, 이 시나리오의 목적(특정 대도시 권역 일반 저지연 인프라)에는 로컬 존이 표준입니다.

> 💡 **시험 꿀팁**: 특정 **대도시 권역에 한 자릿수 밀리초의 초저지연 컴퓨팅**이 필요하고 자체 데이터센터를 구축하고 싶지 않다면 **AWS 로컬 존(Local Zones)**이 표준 정답입니다.

## QUESTION 382

**문제**: 데이터 웨어하우스 워크로드가 Aurora PostgreSQL에서 매우 많은 양의 스토리지 I/O(초당 수백만 건의 읽기/쓰기)를 발생시키며, I/O 요청량에 따라 청구되는 표준 Aurora 요금 구조로는 **매월 비용이 크게 변동**해 예산 수립이 어렵다. 워크로드의 컴퓨팅/스토리지 요구사항 자체는 바꾸지 않고 비용 예측 가능성을 높이려면?

**보기**
- A. 데이터 웨어하우스를 Redshift로 전면 마이그레이션(마이그레이션 자체가 큰 작업이며, 문제는 기존 Aurora 워크로드의 비용 구조 개선 방법을 묻고 있음).
- B. **Aurora I/O-Optimized 스토리지 구성으로 전환해, I/O 요청 건별 과금 대신 컴퓨팅+스토리지에 대한 고정 요금 구조로 변경, I/O가 많은 워크로드의 비용을 예측 가능하게 만듦.**
- C. 읽기 전용 복제본을 늘려 I/O를 분산(복제본을 늘려도 전체 I/O 요청 자체가 줄어들지 않으며, 오히려 복제본마다 발생하는 I/O 요금이 추가되어 비용이 더 커질 수 있음).
- D. Aurora Serverless v2로 전환해 자동 확장(Serverless v2도 컴퓨팅 용량에 대한 과금이며, I/O 요청 건별 과금 구조 자체를 바꾸는 기능은 아님 — I/O 비용 예측 가능성 문제는 별도로 존재).

**정답: B**

**해설**
**Aurora I/O-Optimized**는 기존의 I/O 요청 건별 과금 방식 대신, 컴퓨팅과 스토리지에 대해 **더 높지만 고정된 요금**을 청구하는 대안 요금 구조입니다. I/O 집약적인 워크로드(요청량이 많고 변동이 큰 경우)에서는 이 구성이 전체 비용을 낮추면서도 매월 청구액의 **예측 가능성**을 크게 높여줍니다.

**왜 다른 보기는 오답인가**
- A: Redshift로의 전면 마이그레이션은 이 문제가 묻는 기존 Aurora 워크로드 개선 범위를 벗어나는 큰 작업입니다.
- C: 복제본 추가는 I/O 요청 자체를 줄이지 않으며 오히려 복제본별 I/O 요금이 추가될 수 있습니다.
- D: Serverless v2는 컴퓨팅 자동 확장 기능이며 I/O 과금 구조 자체를 바꾸지는 않습니다.

> 💡 **시험 꿀팁**: I/O가 많고 **비용 예측 가능성이 필요한 Aurora 워크로드**에는 **Aurora I/O-Optimized** 스토리지 구성이 표준 정답입니다.

## QUESTION 383

**문제**: 회사가 배포하는 Lambda 함수와 IoT 디바이스 펌웨어에 대해, 배포 전에 **코드가 승인된 빌드 프로세스를 거쳤고 변조되지 않았음을 암호학적으로 검증**하고 싶다. 서명되지 않았거나 서명이 유효하지 않은 코드는 배포/실행 자체가 거부되어야 한다. 솔루션은?

**보기**
- A. 코드 리포지토리에 대한 접근을 IAM으로 엄격히 제한(접근 제어는 유효하지만, 배포되는 아티팩트 자체의 암호학적 무결성을 검증하고 서명되지 않은 코드의 배포/실행을 기술적으로 차단하는 기능은 아님).
- B. **AWS Signer를 사용해 Lambda 함수 코드와 IoT 펌웨어에 대한 코드 서명 작업을 구성하고, Lambda의 코드 서명 구성(code-signing configuration) 또는 IoT의 서명된 작업(signed job)을 통해 서명되지 않았거나 무효한 서명의 코드는 배포/설치를 거부하도록 강제.**
- C. S3에 업로드된 배포 패키지에 대해 체크섬만 수동으로 비교(수동 체크섬 비교는 자동화된 강제 메커니즘이 아니며, 배포 파이프라인에서 서명되지 않은 코드를 자동으로 거부하는 기능을 제공하지 않음).
- D. CodePipeline의 승인 단계에서 담당자가 육안으로 코드를 검토(수동 육안 검토는 암호학적 무결성 검증이 아니며 확장성도 없고 실수 가능성도 큼).

**정답: B**

**해설**
**AWS Signer**는 Lambda 함수 코드나 IoT 디바이스 펌웨어에 대해 **디지털 서명**을 생성하고 관리하는 완전관리형 서비스입니다. Lambda의 **코드 서명 구성**을 사용하면, 함수 배포 시 신뢰할 수 있는 서명 프로파일로 서명되지 않았거나 서명이 유효하지 않은 코드는 배포 자체가 **자동으로 거부**됩니다. IoT의 경우 **서명된 작업(signed job)**을 통해 디바이스가 펌웨어를 설치하기 전에 서명을 검증하도록 강제할 수 있어, 승인된 빌드 프로세스를 거친 변조되지 않은 코드만 배포/실행되도록 암호학적으로 보장합니다.

**왜 다른 보기는 오답인가**
- A: IAM 접근 제어는 리포지토리 접근을 제한할 뿐, 배포되는 아티팩트 자체의 암호학적 무결성 검증과는 다른 계층입니다.
- C: 수동 체크섬 비교는 자동화된 강제가 아니며 배포 파이프라인에 통합되어 있지 않습니다.
- D: 수동 육안 검토는 확장성이 없고 암호학적 검증을 대체할 수 없습니다.

> 💡 **시험 꿀팁**: Lambda 함수나 IoT 펌웨어 배포 시 **코드 서명을 암호학적으로 검증하고 서명되지 않은 코드의 배포를 강제로 차단**하려면 **AWS Signer**(Lambda 코드 서명 구성/IoT 서명된 작업)가 표준 정답입니다.

## QUESTION 384

**문제**: 회사가 온프레미스 NFS 파일 서버의 페타바이트급 데이터를 S3로 **최초 대량 이관(initial bulk transfer)**한 뒤, 이관이 끝난 이후에도 온프레미스에서 계속 발생하는 변경 사항(신규/수정 파일)을 **지속적으로 증분 동기화**하고 싶다(완전한 컷오버 전까지 온프레미스 시스템도 계속 운영). 하나의 도구로 초기 대량 이관과 이후 지속적 증분 동기화를 모두 처리하려면?

**보기**
- A. 초기 이관은 Snowball Edge로, 이후 증분 동기화는 별도로 rsync 스크립트 구현(서로 다른 두 개의 도구를 조합해야 하고, 증분 동기화 부분은 자체 스크립트 구현/유지 부담이 발생).
- B. **AWS DataSync를 사용해, 초기 대량 이관 작업을 실행한 뒤 동일한 DataSync 태스크를 반복/예약 실행해 이후 변경분만 효율적으로(변경된 파일만 감지) 지속적으로 증분 동기화.**
- C. 초기 이관은 DataSync로, 이후 증분 동기화는 Storage Gateway 파일 게이트웨이로 전환(전환 시 별도의 관리 체계와 접근 방식으로 바뀌어야 해서 "하나의 도구로 모두 처리"하려는 요구에 반함).
- D. 모든 데이터를 매번 처음부터 다시 전체 복사(전체 재복사는 페타바이트급 데이터에서 매우 비효율적이며 대역폭과 시간을 크게 낭비).

**정답: B**

**해설**
**AWS DataSync**는 초기 대량 데이터 이관뿐 아니라, 이후 동일한 태스크를 반복 실행하면 **변경된 파일만 효율적으로 감지해 전송**하는 증분 동기화도 지원합니다. 하나의 도구로 최초 대량 이관과 이후 지속적인 증분 동기화(변경 사항만 반영)를 모두 처리할 수 있어, 완전한 컷오버 전까지 온프레미스와 S3 간 데이터를 계속 최신 상태로 유지하는 데 적합합니다.

**왜 다른 보기는 오답인가**
- A: 서로 다른 두 도구를 조합하는 것은 "하나의 도구로 모두 처리"하려는 목표에 반하며 자체 스크립트 유지 부담도 있습니다.
- C: 중간에 도구를 전환하는 것도 마찬가지로 하나의 통합된 도구 사용 요구에 반합니다.
- D: 매번 전체를 재복사하는 것은 페타바이트급 데이터에서 매우 비효율적입니다.

> 💡 **시험 꿀팁**: 온프레미스에서 S3로 **초기 대량 이관 후 지속적인 증분 동기화**까지 하나의 도구로 처리하려면 **AWS DataSync**(반복 실행으로 변경분만 효율적으로 전송)가 표준 정답입니다.

## QUESTION 385

**문제**: 회사가 특정 가용 영역(AZ)에서 트래픽 급증 시 필요한 만큼의 EC2 용량을 **반드시 확보**해야 하며(다른 고객의 용량 소진으로 인한 "용량 부족" 오류를 피하고 싶음), 동시에 장기 사용에 대한 비용 할인 혜택도 받고 싶다. 이 두 요구를 함께 충족하는 조합은?

**보기**
- A. Savings Plans만 구매(Savings Plans는 요금 할인을 제공하지만 특정 AZ에서의 물리적 용량 확보를 보장하지는 않음 — 할인과 용량 확보는 서로 다른 메커니즘).
- B. **온디맨드 용량 예약(On-Demand Capacity Reservation)으로 특정 AZ에 필요한 용량을 예약해 확보하고, 이 예약된 용량에 대해 Savings Plans(또는 예약 인스턴스)를 별도로 구매해 결합함으로써 용량 확보와 요금 할인을 동시에 획득.**
- C. 예약 인스턴스(리전 범위)만 구매(리전 범위 예약 인스턴스는 요금 할인 혜택은 제공하지만 특정 AZ에 대한 물리적 용량 확보를 보장하지 않음 — 용량 확보에는 AZ 범위의 용량 예약이 필요).
- D. 스팟 인스턴스로 필요한 용량을 미리 확보(스팟 인스턴스는 용량이 부족하면 언제든 회수될 수 있어 "반드시 확보"라는 요구와 정반대).

**정답: B**

**해설**
**용량 예약(Capacity Reservation)**은 특정 AZ에 대해 EC2 용량을 물리적으로 예약해, 다른 고객의 수요와 무관하게 필요할 때 해당 용량을 확실히 사용할 수 있도록 보장합니다. 용량 예약 자체는 요금 할인을 제공하지 않으므로, 이 예약된 용량과 일치하는 **Savings Plans**(또는 예약 인스턴스)를 함께 구매하면, 예약을 통한 **용량 확보**와 약정을 통한 **비용 할인**을 동시에 얻을 수 있습니다.

**왜 다른 보기는 오답인가**
- A, C: Savings Plans와 리전 범위 예약 인스턴스는 요금 할인 메커니즘일 뿐, 특정 AZ의 물리적 용량을 보장하지 않습니다.
- D: 스팟 인스턴스는 용량 회수 가능성이 있어 "반드시 확보"라는 요구와 상충합니다.

> 💡 **시험 꿀팁**: 특정 AZ에서 **용량을 확실히 확보하면서 동시에 비용 할인**도 받으려면 **용량 예약(Capacity Reservation) + Savings Plans(또는 예약 인스턴스)**의 결합이 표준 정답입니다.

## QUESTION 386

**문제**: 기업이 Control Tower 랜딩존을 운영 중인데, 특정 팀에서 "S3 버킷을 퍼블릭으로 만들 수 없다"는 예방적(preventive) 가드레일 외에, "만약 실수로 퍼블릭 버킷이 생성되면 이를 탐지해 보안 팀에 알리는" 탐지적(detective) 가드레일도 함께 원한다. Control Tower의 가드레일 체계에서 이 두 종류를 구분해 이해하려면?

**보기**
- A. 예방적 가드레일과 탐지적 가드레일 모두 SCP로만 구현됨(SCP는 예방적 통제(특정 API 호출 자체를 차단)에 사용되는 메커니즘이며, 사후 탐지 및 알림 같은 탐지적 통제는 SCP의 역할이 아님 — 개념 오류).
- B. **Control Tower는 예방적 가드레일을 SCP로, 탐지적 가드레일을 AWS Config 규칙으로 구현. 예방적 가드레일(예: "퍼블릭 액세스 차단을 비활성화할 수 없음")은 특정 행위 자체를 원천 차단하고, 탐지적 가드레일(예: "S3 버킷이 퍼블릭 액세스를 허용하는지 식별")은 규정 위반 리소스를 지속적으로 스캔해 비준수 상태로 표시.**
- C. 예방적 가드레일과 탐지적 가드레일 모두 GuardDuty로만 구현됨(GuardDuty는 위협/이상 행위 탐지에 특화되어 있으며, Control Tower의 가드레일 체계는 GuardDuty가 아닌 SCP와 Config 규칙을 기반으로 함).
- D. 탐지적 가드레일이 예방적 가드레일보다 우선 적용되어 항상 먼저 확인됨(두 가드레일 유형은 목적과 작동 시점이 다를 뿐 우선순위 개념으로 비교되는 것이 아니며, 예방적 가드레일은 애초에 행위 시점에 차단하고 탐지적 가드레일은 사후에 지속적으로 평가하는 별개의 메커니즘).

**정답: B**

**해설**
**AWS Control Tower**의 가드레일은 크게 두 유형으로 나뉩니다. **예방적(preventive) 가드레일**은 내부적으로 **SCP**를 사용해 특정 행위(예: 퍼블릭 액세스 차단 비활성화) 자체를 API 호출 시점에 원천 차단합니다. **탐지적(detective) 가드레일**은 내부적으로 **AWS Config 규칙**을 사용해 이미 존재하는 리소스가 규정을 준수하는지 지속적으로 평가하고, 비준수 리소스를 식별해 대시보드에 표시합니다. 이 두 계층을 함께 사용하면 사전 예방과 사후 탐지를 모두 갖춘 다층적 거버넌스를 구현할 수 있습니다.

**왜 다른 보기는 오답인가**
- A, C: 각 가드레일 유형이 사용하는 실제 기반 메커니즘(SCP vs Config 규칙)을 정확히 반영하지 못했습니다.
- D: 두 가드레일은 우선순위로 비교되는 것이 아니라 목적(사전 차단 vs 사후 탐지)과 작동 시점이 다른 별개의 보완적 메커니즘입니다.

> 💡 **시험 꿀팁**: Control Tower 가드레일에서 **예방적 가드레일은 SCP 기반(행위 자체 차단)**, **탐지적 가드레일은 AWS Config 규칙 기반(사후 비준수 식별)**이라는 차이를 기억하세요.

**보기**
- A. 네트워크 팀 계정에 VPC를 만들고, 각 애플리케이션 팀에게 그 계정에 대한 전체 관리자 IAM 역할 부여(전체 관리자 권한 위임은 최소 권한 원칙에 위배되며, 애플리케이션 팀이 네트워크 리소스까지 변경할 수 있게 되어 "네트워크는 중앙에서만 관리"하려는 목적에 반함).

**VPC 공유(AWS Resource Access Manager 기반)**를 사용하면, VPC(및 서브넷)를 소유한 계정(네트워크 팀)이 이를 조직 내 다른 계정(애플리케이션 팀들)과 공유할 수 있습니다. 공유받은 계정은 해당 서브넷에 자신의 리소스(EC2, RDS 등)를 배포할 수 있지만, **서브넷 생성/삭제, 라우팅 테이블, NACL 같은 네트워크 인프라 자체에 대한 관리 권한은 소유 계정(네트워크 팀)에만 남아** 있습니다. 이는 중앙 집중식 네트워크 관리와 팀별 리소스 배포 자율성을 동시에 만족하는 표준 멀티 계정 네트워킹 패턴입니다.

> 💡 **시험 꿀팁**: 네트워크를 **중앙에서 소유/관리하면서 여러 계정이 그 네트워크 안에 자신의 리소스를 배포**하도록 하려면 **VPC 공유(VPC sharing, AWS RAM)**가 표준 정답입니다.

**문제**: 회사가 수천 개의 서로 다른 예약(특정 날짜/시간의 일회성 실행, 타임존을 고려한 반복 실행 등)을 관리해야 하는데, 기존 EventBridge 규칙(cron/rate 표현식) 방식으로는 대량의 스케줄을 개별 규칙으로 관리하기가 번거롭고 UTC 외 타임존 처리도 직접 계산해야 한다. 대량의 유연한 스케줄을 더 쉽게 관리하는 서비스는?

## QUESTION 389

**문제**: 회사가 S3 기반 데이터 레이크에 대한 접근 권한을, 사전에 IAM 역할/정책을 일일이 만들지 않고 회사의 **기존 ID 공급자(예: Okta, Microsoft Entra ID)의 사용자/그룹 신원**에 직접 매핑해 세밀하게(디렉터리 접두사 단위) 부여하고 싶다. 데이터 사용자가 늘어나도 IAM 역할을 추가로 만들지 않으면서 이를 구현하는 방법은?

**보기**
- A. ID 공급자의 각 사용자마다 대응하는 IAM 역할을 개별적으로 사전 생성(사용자 수만큼 IAM 역할을 미리 만들어야 해서 "IAM 역할을 추가로 만들지 않고"라는 요구에 정면으로 반하며 확장성도 없음).
- B. **S3 Access Grants를 사용해, IAM Identity Center와 통합된 기존 ID 공급자의 사용자/그룹에게 S3 버킷/접두사 단위의 세분화된 접근 권한(읽기/쓰기 등)을 동적으로 부여. 사용자는 자격 증명 연동을 통해 임시 자격 증명을 받아 부여된 범위만 접근.**
- C. 모든 데이터 사용자에게 동일한 하나의 광범위한 IAM 역할을 공유(모든 사용자가 동일한 광범위 권한을 갖게 되어 세분화된 접근 제어라는 요구에 반하며 최소 권한 원칙 위반).
- D. 버킷 정책에 모든 개별 사용자의 ARN을 나열(수많은 개별 사용자를 버킷 정책에 직접 나열하는 것은 정책 크기 제한에 부딪힐 수 있고, ID 공급자와의 동적 연동이 아니라 수동 유지보수 부담이 큼).

**정답: B**

**해설**
**S3 Access Grants**는 S3 데이터에 대한 접근 권한을, 사전에 정의된 IAM 역할이 아니라 **ID 공급자(IAM Identity Center와 연동된 Okta, Entra ID 등)의 사용자/그룹 신원**에 직접, 동적으로 매핑해 부여하는 기능입니다. 데이터 소유자가 버킷/접두사 단위로 특정 신원에게 읽기/쓰기 권한을 부여(grant)하면, 사용자는 자격 증명 연동을 통해 그 권한 범위에 맞는 **임시 자격 증명**을 받아 접근합니다. 새로운 데이터 사용자가 추가되어도 IAM 역할을 새로 만들 필요 없이 ID 공급자 측 신원에 권한을 부여하기만 하면 되어 확장성이 뛰어납니다.

**왜 다른 보기는 오답인가**
- A: 사용자마다 IAM 역할을 사전 생성하는 것은 확장성이 없고 요구사항에 반합니다.
- C: 동일한 광범위 역할 공유는 세분화된 접근 제어와 최소 권한 원칙에 반합니다.
- D: 버킷 정책에 개별 사용자를 나열하는 것은 정책 크기 제한과 유지보수 부담 문제가 있습니다.

> 💡 **시험 꿀팁**: 기존 **ID 공급자의 신원에 직접 매핑해 S3 데이터에 세분화된 접근 권한을 동적으로 부여**하려면(IAM 역할을 추가로 만들지 않고) **S3 Access Grants**가 표준 정답입니다.

**문제**: 제조 공장의 IoT 센서 데이터를 실시간으로 분석해 이상 징후를 감지해야 하는데, 공장의 인터넷 연결이 **간헐적으로 끊기는** 환경이다. 인터넷 연결이 끊긴 동안에도 로컬에서 계속 머신러닝 추론과 기본적인 데이터 처리가 이루어져야 하며, 연결이 복구되면 자동으로 클라우드와 동기화되기를 원한다. 솔루션은?

## QUESTION 392

**문제**: 회사가 현재 리전 A에서 운영 중인 애플리케이션을 새로운 리전 B로 점진적으로 마이그레이션하려 한다. 하루아침에 전체 트래픽을 전환하는 대신, **몇 주에 걸쳐 트래픽 비율을 점진적으로 리전 B로 늘려가며** 문제가 없는지 모니터링하고 싶다. 두 리전 모두 애플리케이션이 배포되어 있다는 가정하에 솔루션은?

**보기**
- A. Route 53 페일오버 라우팅 정책 사용(페일오버 라우팅은 능동-대기 구조로 한쪽이 완전히 다운되었을 때만 전환되는 방식이며, 이 문제가 원하는 "점진적인 비율 조정을 통한 트래픽 이전"과는 다른 목적).
- B. **Route 53 가중치 기반 라우팅 정책을 사용해, 리전 A와 리전 B의 엔드포인트에 가중치를 부여하고 몇 주에 걸쳐 리전 B의 가중치를 점진적으로 높여가며 트래픽 비율을 조정.**

**정답: B**

**해설**
**Route 53 가중치 기반 라우팅**은 여러 엔드포인트(리전 A, 리전 B)에 상대적인 가중치를 지정해, 그 비율에 따라 트래픽을 분산시킵니다. 몇 주에 걸쳐 리전 B의 가중치를 점진적으로(예: 10% → 30% → 50% → 100%) 높여가면서 모니터링하면, 문제가 발생할 경우 즉시 가중치를 되돌릴 수 있는 안전한 점진적 리전 마이그레이션을 구현할 수 있습니다. **왜 다른 보기는 오답인가**
- A: 페일오버 라우팅은 완전한 장애 상황에서의 전환에 최적화되어 있으며, 점진적 비율 조정 목적과는 다릅니다.
- D: 즉시 전면 전환은 점진적 마이그레이션이라는 요구에 정면으로 반합니다.

> 💡 **시험 꿀팁**: 두 리전 간 트래픽을 **몇 주에 걸쳐 점진적으로 비율 조정하며 전환**하려면 **Route 53 가중치 기반 라우팅**이 표준 정답입니다.

## QUESTION 393

**문제**: 회사가 자체 관리하는 Apache Cassandra 클러스터(와이드 컬럼 NoSQL, 높은 쓰기 처리량, 낮은 지연시간 요구)를 운영 중이며, 클러스터 패치/스케일링/장애 복구 등 운영 부담을 줄이고 싶다. 기존 Cassandra Query Language(CQL) 기반 애플리케이션 코드는 그대로 유지하고 싶다. 솔루션은?

**보기**
- A. DynamoDB로 전면 마이그레이션(DynamoDB는 강력한 NoSQL 서비스이지만 CQL이 아닌 자체 API를 사용하므로, 기존 CQL 기반 애플리케이션 코드를 대폭 재작성해야 함).
- B. **Amazon Keyspaces(Apache Cassandra용, 서버리스)로 마이그레이션해, 기존 CQL 드라이버와 애플리케이션 코드를 거의 그대로 사용하면서 서버 프로비저닝/패치/스케일링 없는 완전관리형 서비스로 전환.**
- C. Cassandra 클러스터를 EC2에 그대로 유지하되 인스턴스 유형만 상위로 업그레이드(운영 부담(패치, 스케일링, 장애 복구 등) 자체는 여전히 자체적으로 관리해야 해서 근본적인 운영 부담 절감 목표를 달성하지 못함).
- D. RDS for PostgreSQL로 마이그레이션 후 JSONB 컬럼으로 와이드 컬럼 데이터 모델링(관계형 데이터베이스로의 전환은 CQL 기반 코드와 데이터 모델을 완전히 재작성해야 하며, Cassandra 수준의 쓰기 처리량/지연시간 특성과도 맞지 않음).

**정답: B**

**해설**
**Amazon Keyspaces(Apache Cassandra용)**는 Cassandra Query Language(CQL) API와 호환되는 **서버리스, 완전관리형** 와이드 컬럼 NoSQL 데이터베이스 서비스입니다. 기존 CQL 기반 드라이버와 애플리케이션 코드를 대부분 그대로 사용하면서, 서버 프로비저닝, 패치, 스케일링, 장애 복구 같은 운영 부담을 AWS가 대신 처리하도록 전환할 수 있어, 이 문제의 두 요구(운영 부담 절감 + 코드 유지)를 모두 충족합니다.

**왜 다른 보기는 오답인가**
- A: DynamoDB는 CQL이 아닌 자체 API를 사용해 애플리케이션 코드의 대대적인 재작성이 필요합니다.
- C: 자체 EC2 클러스터를 유지하는 한 패치/스케일링/장애 복구 부담이 그대로 남습니다.
- D: 관계형 데이터베이스로의 전환은 데이터 모델과 코드를 완전히 재설계해야 하며 성능 특성도 다릅니다.

> 💡 **시험 꿀팁**: 자체 관리형 **Apache Cassandra의 운영 부담을 없애면서 기존 CQL 코드를 그대로 유지**하려면 **Amazon Keyspaces**가 표준 정답입니다.

## QUESTION 394

**문제**: 리전 재해 발생으로 DR 리전에서 애플리케이션을 성공적으로 페일오버해 운영 중이다. 이제 원래 프라이머리 리전이 복구되어, **원래 리전으로 다시 안전하게 페일백(failback)**하고 싶다. 페일백 시 DR 기간 동안 변경된 데이터(장애 중 DR 리전에서 발생한 신규 거래 등)의 유실을 방지하려면 어떤 접근이 필요한가?

**보기**
- A. 원래 프라이머리 리전이 복구되는 즉시 DNS를 그쪽으로 즉시 재전환(DR 기간 동안 DR 리전에서 발생한 데이터 변경 사항이 원래 리전에 전혀 반영되지 않은 채로 즉시 전환하면 데이터 유실이 발생 — 역방향 동기화 없이 성급한 전환).

- D. 페일백 없이 DR 리전을 영구적으로 새로운 프라이머리로 사용(가능한 선택지일 수 있으나, 문제가 명시적으로 원래 리전으로의 페일백을 원한다고 했으므로 이 시나리오의 요구에 맞지 않음).

**해설**

**왜 다른 보기는 오답인가**
- A: 역방향 동기화 없이 즉시 전환하면 DR 기간 중 데이터가 유실됩니다.
- C: 재해 발생 시점 백업으로 복원하는 것은 그 이후의 모든 변경 사항을 잃게 되는 심각한 데이터 손실을 야기합니다.
- D: 문제가 명시적으로 원래 리전으로의 페일백을 요구하고 있어 이 옵션은 시나리오에 맞지 않습니다.

> 💡 **시험 꿀팁**: DR 이벤트 이후 **원래 리전으로 안전하게 페일백**하려면, 먼저 현재 활성 리전에서 원래 리전으로 **역방향 복제로 데이터를 완전히 동기화**한 뒤 트래픽을 전환하는 순서가 표준 정답입니다.

> 💡 **시험 꿀팁**: 두 리소스 간 **네트워크 연결 문제의 정확한 원인(어느 보안 그룹/NACL/라우팅 항목)을 자동으로 진단**하려면 **Amazon VPC Reachability Analyzer**가 표준 정답입니다.

- A. 각 도구(MGN 콘솔, DMS 콘솔, 서드파티 도구 대시보드)를 개별적으로 열어 확인 후 수동으로 종합 보고서 작성(여러 도구를 오가며 수동으로 취합해야 해서 비효율적이고 실시간성도 떨어짐).
- B. **AWS Migration Hub를 사용해, MGN·DMS 등 AWS 마이그레이션 도구는 물론 지원되는 서드파티 마이그레이션 도구의 진행 상황까지 하나의 중앙 대시보드에서 애플리케이션 그룹 단위로 통합 추적.**
- C. CloudWatch 커스텀 대시보드를 만들어 각 도구의 지표를 수동으로 통합(각 도구에서 마이그레이션 진행 상황 지표를 CloudWatch로 내보내는 통합 작업을 직접 구현해야 해서, Migration Hub가 기본 제공하는 통합 추적 기능을 불필요하게 재구현하는 것).
- D. 마이그레이션이 끝난 후에만 최종 결과를 보고(진행 중 상태를 실시간으로 파악하고 싶다는 요구에 반하며, 문제 발생 시 조기에 대응할 기회를 놓침).

**정답: B**

**해설**
**AWS Migration Hub**는 AWS Application Migration Service(MGN), AWS DMS 같은 AWS 네이티브 마이그레이션 도구뿐 아니라, 지원되는 **서드파티 마이그레이션 도구**의 진행 상황까지 통합해 하나의 중앙 대시보드에서 **애플리케이션 그룹 단위**로 추적할 수 있게 해주는 서비스입니다. 사용하는 마이그레이션 도구가 여러 개 섞여 있어도, 경영진이나 프로젝트 관리자가 전체 마이그레이션 프로젝트의 진행 상황을 도구에 관계없이 한눈에 파악할 수 있는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 여러 도구를 개별적으로 확인하고 수동 취합하는 것은 비효율적이고 실시간성이 떨어집니다.
- C: 자체 통합 대시보드 구축은 Migration Hub가 이미 제공하는 기능을 불필요하게 재구현하는 것입니다.
- D: 마이그레이션 종료 후에만 보고하는 것은 실시간 가시성 요구에 반하고 문제 조기 대응 기회를 놓칩니다.

> 💡 **시험 꿀팁**: 여러 도구(MGN, DMS, 서드파티 등)를 사용하는 **대규모 마이그레이션 프로젝트의 진행 상황을 하나의 화면에서 통합 추적**하려면 **AWS Migration Hub**가 표준 정답입니다.

## QUESTION 400

**문제**: 회사가 여러 부서의 EC2 사용량을 표준 오픈소스 소프트웨어 스택으로 실행 중이며, x86에서 Graviton(ARM)으로 전환을 검토하되, 전환 전에 **애플리케이션이 실제로 ARM 아키텍처에서 문제없이 작동하는지 검증**하고, 전환 시 예상되는 비용 절감액도 미리 추정하고 싶다. 이런 마이그레이션 평가/검증 과정을 지원하는 AWS 도구/서비스 조합은?

**보기**
- A. 별도 도구 없이 바로 프로덕션 인스턴스를 Graviton으로 전환한 뒤 문제가 생기면 대응(사전 검증 없이 프로덕션에 바로 적용하는 것은 호환성 문제 발생 시 서비스 영향이 크고 위험함).
- B. **AWS Compute Optimizer로 Graviton 전환 시 예상되는 비용/성능 개선을 먼저 추정하고, 비프로덕션 환경에서 Graviton 기반 인스턴스를 시작해 애플리케이션 테스트 스위트를 실행하며 호환성을 검증한 뒤, 문제가 없으면 점진적으로 프로덕션에 롤아웃.**
- C. Trusted Advisor 검사만으로 Graviton 전환 가능 여부를 판단(Trusted Advisor는 일반적인 모범 사례 점검 도구이며, Graviton 전환에 특화된 상세한 비용/성능 예측이나 애플리케이션 호환성 검증 기능을 제공하지 않음).
- D. 모든 x86 인스턴스를 동시에 Graviton으로 교체한 뒤 결과를 관찰(사전 검증이나 점진적 롤아웃 없이 전체를 한 번에 바꾸는 것은 호환성 문제 발생 시 광범위한 서비스 장애로 이어질 위험이 매우 큼).

**정답: B**

**해설**
Graviton으로의 안전한 전환은 여러 단계를 거치는 것이 표준입니다. 먼저 **AWS Compute Optimizer**로 현재 워크로드에 대해 Graviton 전환 시 예상되는 **비용 절감과 성능 개선을 데이터 기반으로 추정**합니다. 그다음 **비프로덕션 환경**에서 실제로 Graviton 기반 인스턴스를 시작해 애플리케이션의 테스트 스위트를 실행하고 커스텀 네이티브 바이너리 등 호환성 문제가 없는지 검증한 뒤, 문제가 없다고 확인되면 프로덕션에 **점진적으로** 롤아웃하는 것이 리스크를 최소화하는 표준 마이그레이션 접근입니다.

**왜 다른 보기는 오답인가**
- A, D: 사전 검증 없이 바로 프로덕션 전체를 전환하는 것은 호환성 문제 발생 시 리스크가 매우 큽니다.
- C: Trusted Advisor는 Graviton 전환에 특화된 상세 평가 기능을 제공하지 않습니다.

> 💡 **시험 꿀팁**: **Graviton(ARM) 전환을 안전하게 평가/검증**하려면 **Compute Optimizer(비용/성능 추정) → 비프로덕션 환경 테스트(호환성 검증) → 점진적 프로덕션 롤아웃**의 단계적 접근이 표준 정답입니다.
