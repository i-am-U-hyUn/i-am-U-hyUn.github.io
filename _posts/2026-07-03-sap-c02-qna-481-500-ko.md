## QUESTION 481

**문제**: 회사가 온프레미스 데이터센터에서 AWS로 마이그레이션하는 대규모 프로젝트를 진행 중이며, 수백 개의 애플리케이션을 웨이브(wave) 단위로 나누어 이관해야 한다. 각 애플리케이션의 마이그레이션 전략(리호스트, 리플랫폼, 리팩터 등)과 우선순위를 데이터 기반으로 결정하고 싶고, 프로젝트 전체의 진행 상황을 추적하고 싶다. Discovery 데이터를 이미 수집한 상태에서, 이를 활용해 마이그레이션 계획을 수립하는 단계에 적합한 서비스는?

**보기**
- A. AWS Application Discovery Service만 계속 사용(Discovery Service는 데이터 수집 단계의 도구이며, 수집된 데이터를 기반으로 마이그레이션 전략을 그룹화하고 계획을 수립하며 진행 상황을 추적하는 기능은 별도 서비스의 역할).
- B. **AWS Migration Hub를 사용해, Discovery Service가 수집한 서버 데이터를 애플리케이션 단위로 그룹화하고 각각에 마이그레이션 전략을 할당(리호스트/리플랫폼/리팩터 등)하며, 여러 마이그레이션 도구(MGN, DMS 등)를 사용하는 웨이브별 진행 상황을 중앙에서 추적.**
- C. AWS Well-Architected Tool로 마이그레이션 계획 수립(Well-Architected Tool은 기존 워크로드의 아키텍처 모범 사례 준수 여부를 검토하는 도구이며, 마이그레이션 웨이브 계획이나 애플리케이션 그룹화, 다중 도구 진행 상황 추적 기능을 제공하지 않음).
- D. Trusted Advisor로 마이그레이션 우선순위 결정(Trusted Advisor는 기존 AWS 계정 내 리소스에 대한 일반적인 모범 사례 검사 도구이며, 온프레미스 마이그레이션 계획 수립과는 무관).

**정답: B**

**해설**
**AWS Migration Hub**는 마이그레이션 프로젝트의 계획 수립 및 추적 단계에 특화된 서비스입니다. Application Discovery Service가 수집한 서버 데이터를 **애플리케이션 단위로 그룹화**하고, 각 애플리케이션에 적합한 마이그레이션 전략(6R: 리호스트, 리플랫폼, 리팩터, 재구매, 유지, 은퇴)을 할당해 계획을 수립할 수 있습니다. 또한 MGN, DMS 등 실제 마이그레이션에 사용되는 여러 도구의 진행 상황을 애플리케이션/웨이브 단위로 **중앙에서 추적**할 수 있어, 대규모 마이그레이션 프로젝트의 계획-실행-추적 전 과정을 지원합니다.

**왜 다른 보기는 오답인가**
- A: Discovery Service는 데이터 수집 단계이며, 이를 기반으로 한 계획 수립/그룹화/추적은 Migration Hub의 역할입니다.
- C: Well-Architected Tool은 아키텍처 모범 사례 검토 도구이며 마이그레이션 웨이브 계획과는 목적이 다릅니다.
- D: Trusted Advisor는 기존 AWS 리소스 점검용이며 온프레미스 마이그레이션 계획과 무관합니다.

> 💡 **시험 꿀팁**: Discovery 데이터를 기반으로 **애플리케이션을 그룹화하고 마이그레이션 전략을 할당하며 여러 도구의 진행 상황을 추적**하려면 **AWS Migration Hub**가 표준 정답입니다.

## QUESTION 482

**문제**: 회사가 EC2 Auto Scaling 그룹에서 스케일 아웃 시 새 인스턴스가 시작되고 몇 초 이내에 헬스 체크를 통과해야 하는데, 인스턴스 부트스트랩(사용자 데이터 스크립트로 소프트웨어 설치)에 시간이 걸려 헬스 체크가 조기에 실패해 인스턴스가 불필요하게 재시작되는 문제가 반복된다. 부트스트랩이 완료될 때까지 헬스 체크를 유예하려면?

**보기**
- A. 헬스 체크 자체를 비활성화(헬스 체크를 완전히 끄면 실제로 비정상적인 인스턴스도 탐지하지 못하게 되어 가용성에 위험을 초래).
- B. **Auto Scaling 그룹의 헬스 체크 유예 기간(health check grace period)을 인스턴스 부트스트랩에 필요한 시간보다 길게 설정해, 이 기간 동안에는 헬스 체크 실패로 인한 인스턴스 교체가 발생하지 않도록 구성.**
- C. 헬스 체크 간격(interval)만 매우 길게 설정(체크 간격을 늘리는 것은 전체적인 헬스 체크 빈도를 줄일 뿐, 부트스트랩 초기 기간 동안의 조기 실패 자체를 근본적으로 막지는 못함 — 유예 기간이 이 목적에 더 정확히 맞음).
- D. 사용자 데이터 스크립트 실행을 완전히 제거하고 사전에 모든 소프트웨어가 설치된 커스텀 AMI만 사용(가능한 개선 방향이지만, 문제는 유예 기간 설정이라는 Auto Scaling의 기본 기능으로 해결하는 방법을 묻고 있으며, AMI 사전 빌드가 항상 가능하거나 필요한 것은 아님).

**정답: B**

**해설**
**Auto Scaling 그룹의 헬스 체크 유예 기간**은 새로 시작된 인스턴스가 헬스 체크 대상이 되기까지 기다려주는 시간을 설정하는 기능입니다. 이 유예 기간을 인스턴스의 부트스트랩(사용자 데이터 스크립트 실행)에 필요한 시간보다 충분히 길게 설정하면, 부트스트랩이 진행 중인 동안 발생하는 일시적인 헬스 체크 실패로 인해 Auto Scaling이 인스턴스를 불필요하게 교체하는 것을 방지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 헬스 체크를 완전히 끄는 것은 실제 장애 인스턴스도 탐지하지 못하게 되는 위험한 조치입니다.
- C: 체크 간격 조정만으로는 부트스트랩 초기의 조기 실패 문제를 근본적으로 해결하지 못합니다.
- D: 사전 빌드된 AMI 사용도 도움이 되지만, 이 문제는 Auto Scaling의 유예 기간 기능으로 해결하는 표준 방법을 묻고 있습니다.

> 💡 **시험 꿀팁**: Auto Scaling에서 **인스턴스 부트스트랩 시간 동안 헬스 체크 실패로 인한 불필요한 교체를 방지**하려면 **헬스 체크 유예 기간(health check grace period)**이 표준 정답입니다.

## QUESTION 483

**문제**: 회사가 AWS Organizations의 여러 계정에서 발생하는 CloudTrail 로그를 하나의 중앙 계정의 S3 버킷에 통합하고 싶다. 각 계정에서 개별적으로 CloudTrail을 활성화하고 각자의 S3 버킷에 저장한 뒤 별도로 통합하는 복잡한 방식 대신, 처음부터 조직 전체에 걸쳐 하나의 추적(trail)으로 관리하고 싶다. 솔루션은?

**보기**
- A. 각 계정에서 개별 CloudTrail 추적을 생성하고 크로스 계정 S3 복제로 통합(개별 추적을 만든 뒤 사후에 복제로 통합하는 것은 이 문제가 피하고자 하는 "처음부터 하나의 추적으로 관리"라는 요구에 반하며 더 복잡함).
- B. **AWS Organizations의 관리 계정에서 조직 추적(organization trail)을 생성해, 조직 내 모든 기존 및 신규 계정의 CloudTrail 이벤트가 자동으로 지정된 중앙 계정의 S3 버킷에 통합 전달되도록 구성.**
- C. 각 계정에서 CloudWatch Logs로 CloudTrail 이벤트를 전송한 뒤 중앙 계정에서 구독 필터로 수집(가능한 방법이지만, 계정마다 개별 설정이 필요하고 신규 계정 자동 포함도 안 되어 Organizations 조직 추적보다 운영 부담이 큼).
- D. CloudTrail Lake만 사용하고 S3 통합은 하지 않음(CloudTrail Lake는 유용한 쿼리 기능을 제공하지만, 문제가 명시적으로 요구하는 "하나의 S3 버킷으로 통합"이라는 목표에는 조직 추적이 더 직접적).

**정답: B**

**해설**
**Organizations 조직 추적(organization trail)**은 관리 계정에서 한 번 생성하면, 조직 내 **모든 기존 계정과 향후 추가되는 신규 계정**의 CloudTrail 이벤트가 자동으로 지정된 중앙 계정의 S3 버킷으로 전달되도록 구성됩니다. 각 계정에서 개별적으로 추적을 활성화하고 사후에 통합할 필요 없이, 처음부터 조직 전체에 걸쳐 하나의 통합된 로깅 파이프라인을 구축하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 개별 추적을 만들고 사후 복제로 통합하는 것은 더 복잡하고 이 문제가 원하는 처음부터의 통합 관리와 다릅니다.
- C: CloudWatch Logs 구독 방식도 가능하지만 계정마다 개별 설정이 필요해 운영 부담이 큽니다.
- D: CloudTrail Lake는 쿼리에 특화되어 있으며, S3 통합이라는 명시적 목표에는 조직 추적이 더 적합합니다.

> 💡 **시험 꿀팁**: 조직의 **모든 계정(신규 포함) CloudTrail 로그를 하나의 중앙 S3 버킷으로 자동 통합**하려면 **Organizations 조직 추적(organization trail)**이 표준 정답입니다.

## QUESTION 484

**문제**: 회사가 API Gateway로 제공하는 공개 API에 대해, 특정 국가/리전에서의 접근만 허용하거나 차단하고 싶다(지리적 제한, geo-blocking). API Gateway 자체는 이런 지리적 필터링 기능을 기본 제공하지 않는다는 것을 알게 되었다. 솔루션은?

**보기**
- A. API Gateway 리소스 정책에서 IP 대역을 국가별로 나열해 직접 차단(국가별 IP 대역은 매우 방대하고 지속적으로 변경되어 리소스 정책에서 수동으로 관리하는 것은 비현실적).
- B. **AWS WAF를 API Gateway에 연결하고, WAF의 지리 일치(geo match) 규칙을 사용해 특정 국가 코드 기반으로 요청을 허용하거나 차단.**
- C. Lambda 함수 내부에서 요청 IP를 조회해 국가를 확인한 뒤 로직으로 거부(가능한 방법이지만, 모든 요청이 일단 Lambda까지 도달한 후 처리되어 비효율적이며, WAF의 관리형 지리 데이터베이스를 재구현하는 불필요한 작업).
- D. Route 53 지리 근접 라우팅으로 API Gateway 엔드포인트 접근 제어(지리 근접 라우팅은 DNS 응답을 사용자 위치에 따라 다르게 반환하는 트래픽 분산 기능이며, 특정 국가의 접근을 명시적으로 차단하는 보안 필터링 기능이 아님).

**정답: B**

**해설**
**AWS WAF**의 **지리 일치(geo match) 규칙**은 요청의 출발지 국가를 기반으로 API Gateway, CloudFront, ALB에 대한 접근을 허용하거나 차단할 수 있게 해주는 기능입니다. WAF 웹 ACL을 API Gateway에 연결하고 지리 일치 규칙을 구성하면, 국가별 IP 대역을 직접 관리할 필요 없이 AWS가 유지하는 지리 데이터베이스를 기반으로 특정 국가의 트래픽을 API Gateway 계층에 도달하기 전에 효율적으로 필터링할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 국가별 IP 대역을 수동으로 관리하는 것은 매우 비현실적입니다.
- C: Lambda 내부 로직 구현은 이미 Lambda까지 요청이 도달한 후 처리되어 비효율적이며 WAF 기능을 불필요하게 재구현합니다.
- D: Route 53 지리 근접 라우팅은 트래픽 분산용이며 명시적인 국가 차단 기능이 아닙니다.

> 💡 **시험 꿀팁**: API Gateway/CloudFront/ALB에 대해 **특정 국가의 접근을 허용/차단(지리적 제한)**하려면 **AWS WAF의 지리 일치(geo match) 규칙**이 표준 정답입니다.

## QUESTION 485

**문제**: 데이터 팀이 여러 부서에서 생성하는 Glue 데이터 카탈로그의 테이블 수가 수만 개에 달해, 특정 컬럼명이나 설명(description)을 포함하는 테이블을 검색하는 것이 매우 어렵다. 비즈니스 사용자가 사람이 읽을 수 있는 용어(비즈니스 용어집)로 데이터를 검색하고 발견할 수 있는 데이터 카탈로그/거버넌스 도구가 필요하다. 솔루션은?

**보기**
- A. Glue 콘솔에서 테이블 이름으로 수동 검색(Glue 콘솔의 기본 검색은 대규모 카탈로그에서 비즈니스 용어 기반의 의미론적 검색이나 데이터 계보(lineage) 추적 같은 고급 발견 기능을 제공하지 않음).
- B. **Amazon DataZone을 사용해, 비즈니스 용어집(business glossary), 데이터 자산에 대한 메타데이터 태깅, 검색/탐색 인터페이스를 통해 비즈니스 사용자가 조직 전체의 데이터를 발견하고 접근 요청할 수 있는 데이터 포털을 구축.**
- C. 모든 테이블 이름을 표준화된 명명 규칙으로 강제 변경(명명 규칙 표준화는 도움이 될 수 있지만, 수만 개 테이블에 대한 근본적인 검색/발견 경험을 제공하는 전용 카탈로그 도구가 필요하며, 이름 변경만으로는 부족).
- D. 모든 테이블에 대한 설명을 담은 위키 페이지를 수동으로 작성(수동 위키 관리는 수만 개 테이블 규모에서 최신 상태 유지가 불가능하고 확장성이 없음).

**정답: B**

**해설**
**Amazon DataZone**은 조직의 데이터 자산(Glue 카탈로그의 테이블 등 포함)에 대한 **비즈니스 용어집**을 구축하고, 데이터에 비즈니스 컨텍스트를 담은 메타데이터를 연결하며, 비즈니스 사용자가 기술적 세부사항 없이도 **비즈니스 용어로 데이터를 검색/발견**하고 접근을 요청할 수 있는 데이터 포털을 제공하는 데이터 거버넌스 서비스입니다. 수만 개 규모의 테이블에서 발견 가능성(discoverability)을 향상시키는 표준 솔루션입니다.

**왜 다른 보기는 오답인가**
- A: Glue 콘솔의 기본 검색은 대규모 카탈로그의 의미론적 검색/발견에는 한계가 있습니다.
- C: 명명 규칙 표준화만으로는 근본적인 검색/발견 도구를 대체하지 못합니다.
- D: 수동 위키 관리는 수만 개 규모에서 확장성이 없습니다.

> 💡 **시험 꿀팁**: 대규모 데이터 카탈로그에서 **비즈니스 용어 기반으로 데이터를 검색/발견하고 접근을 요청**할 수 있는 포털이 필요하면 **Amazon DataZone**이 표준 정답입니다.

## QUESTION 486

**문제**: 회사가 Lambda 함수에서 외부 서드파티 API를 호출하는데, 이 API가 가끔 일시적인 오류(5xx)를 반환한다. 단순 재시도만으로는 동일한 순간적 장애 상황에서 재시도가 계속 실패할 수 있어, 재시도 간격을 점진적으로 늘리면서(exponential backoff) 약간의 무작위성(jitter)도 추가하고 싶다. 이 로직을 Lambda 코드에 직접 매번 구현하고 싶지 않다면?

**보기**
- A. Lambda의 기본 재시도 설정만 사용(동기 호출 기본 재시도는 매우 제한적이며 exponential backoff나 jitter 같은 세밀한 재시도 전략을 커스터마이징하는 기능은 아님).
- B. **AWS SDK(예: Boto3, AWS SDK for JavaScript 등)에 내장된 재시도 모드(예: adaptive 또는 standard 재시도 모드)를 활용하거나, AWS SDK가 지원하지 않는 경우 서드파티 재시도 라이브러리(예: 특정 언어의 backoff/retry 데코레이터 라이브러리)를 사용해 exponential backoff와 jitter를 표준화된 방식으로 적용.**
- C. 실패 시 동일한 Lambda 함수를 무한정 즉시 재귀 호출(즉시 재귀 호출은 backoff 개념이 없어 동일한 순간적 장애 상황에서 계속 실패할 위험이 크고, 무한 재귀는 비용 폭증과 스택 문제를 일으킬 수 있음).
- D. Lambda 함수 제한 시간(timeout)을 최대로 늘려 단일 호출 내에서 계속 대기(제한 시간을 늘리는 것은 backoff 재시도 전략 자체를 구현하는 것이 아니며 단순히 대기 시간을 늘리는 것에 불과함).

**정답: B**

**해설**
AWS SDK는 대부분의 언어에서 **내장 재시도 메커니즘**을 제공하며, 최신 SDK들은 **adaptive retry mode** 같은 옵션을 통해 exponential backoff와 jitter를 자동으로 적용합니다. 서드파티 API 호출처럼 SDK가 직접 지원하지 않는 경우에도, 검증된 재시도 라이브러리(각 언어의 백오프/재시도 데코레이터/헬퍼)를 사용하면 매번 직접 backoff/jitter 로직을 구현하지 않고도 신뢰성 있는 재시도 전략을 표준화된 방식으로 적용할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Lambda 자체의 기본 재시도는 제한적이며 세밀한 backoff/jitter 커스터마이징을 제공하지 않습니다.
- C: 즉시 재귀 호출은 backoff가 없어 동일 장애에서 계속 실패할 위험이 크고 비용/스택 문제를 유발합니다.
- D: 제한 시간만 늘리는 것은 backoff 전략 자체가 아닙니다.

> 💡 **시험 꿀팁**: 서드파티 API 호출에 **exponential backoff + jitter 기반의 표준화된 재시도**를 적용하려면 **AWS SDK의 내장 재시도 모드(또는 검증된 재시도 라이브러리)**를 활용하는 것이 표준 정답입니다.

- D: 파티션 단위 삭제/재생성은 DynamoDB의 개념과 맞지 않습니다.

> 💡 **시험 꿀팁**: DynamoDB 항목을 **프로비저닝된 용량 소비 없이 일정 기간 후 자동으로 삭제**하려면 **DynamoDB TTL(Time to Live)**이 표준 정답입니다.

- A: 수동 SSH 접속은 증거 무결성 훼손 위험이 있고 자동화/확장성 요구에 반합니다.
- C: 정기 전체 백업은 사고 발생 시점의 정확한 상태를 이벤트 기반으로 캡처하지 못합니다.
- D: 즉시 종료는 휘발성 메모리 증거를 영구히 잃게 되어 포렌식 조사 자체를 불가능하게 만듭니다.

- A: 사용자 데이터에 평문 시크릿을 포함하는 것은 심각한 보안 위험입니다.
- C: SSH 키 배포와 사전 파일 복사는 시크릿을 정적으로 여러 곳에 두어 관리/순환이 어렵습니다.
- D: AMI에 시크릿을 하드코딩하는 것은 AMI 공유/유출 시 시크릿도 함께 노출되는 매우 위험한 방식입니다.

> 💡 **시험 꿀팁**: EC2 인스턴스가 부팅 시 **하드코딩 없이 안전하게 시크릿을 가져오도록** 하려면 **IAM 역할(인스턴스 프로파일) + Secrets Manager/Parameter Store**가 표준 정답입니다.

- A. 매번 실제로 전체 페일오버를 실행해 문제가 있는지 확인(실제 페일오버는 프로덕션 트래픽에 영향을 줄 위험이 크고, 매번 전체 페일오버를 반복하는 것은 비용과 리스크가 매우 큼).
- B. **AWS Resilience Hub의 지속적인 복원력 평가(assessment) 기능을 정기적으로 실행해, DR 관련 인프라 구성(리소스 존재 여부, 구성 일치 등)이 정의된 정책과 실제로 부합하는지 지속적으로 검증하고 드리프트나 격차를 사전에 식별.**
- C. DR 문서를 분기별로 담당자가 수동으로 읽고 실제 콘솔과 대조(수동 대조는 대규모 인프라에서 시간이 오래 걸리고 누락되기 쉬우며 지속적인 자동 검증이 아님).
- D. CloudFormation 템플릿 코드만 검토하고 실제 배포 상태는 확인하지 않음(코드 검토만으로는 실제 배포된 인프라가 코드와 일치하는지, 혹은 수동 변경으로 드리프트가 발생했는지 확인할 수 없음).

**정답: B**

**해설**
**AWS Resilience Hub**는 애플리케이션의 복원력 정책(RTO/RPO 등)을 정의한 뒤, 정기적으로(또는 인프라 변경 시마다) **평가(assessment)**를 실행해 실제 리소스 구성이 정의된 복원력 요구사항을 충족하는지 지속적으로 검증합니다. DR 관련 리소스가 실제로 존재하는지, 구성이 프로덕션과 일치하는지 등의 격차나 드리프트를 실제 페일오버 실행 전에 사전에 식별할 수 있어, 값비싸고 위험한 전체 페일오버 테스트를 매번 반복하지 않고도 DR 준비 상태를 지속적으로 검증하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 매번 전체 페일오버를 실행하는 것은 비용과 리스크가 매우 큽니다.
- C: 수동 대조는 시간이 오래 걸리고 지속적인 자동 검증이 아닙니다.
- D: 코드 검토만으로는 실제 배포 상태나 드리프트를 확인할 수 없습니다.

> 💡 **시험 꿀팁**: 실제 페일오버 없이 **DR 관련 인프라 구성이 요구사항과 부합하는지 지속적으로 사전 검증**하려면 **AWS Resilience Hub의 지속적인 평가(assessment)**가 표준 정답입니다.

## QUESTION 500

**문제**: 회사가 지금까지 여러 AWS 서비스(마이그레이션, 네트워킹, 보안, 데이터베이스, 서버리스, 컨테이너, 거버넌스, 비용 최적화 등)에 걸친 복잡한 아키텍처 결정을 내려왔는데, 새로운 팀원이 합류할 때마다 이런 결정들의 배경과 근거를 매번 구두로 설명해야 해서 비효율적이다. 아키텍처 결정 사항과 그 근거를 체계적으로 문서화해 팀 전체가 참조할 수 있게 하고 싶다. 이는 특정 AWS 서비스라기보다는 실천(practice)에 가까운데, AWS Well-Architected 프레임워크에서 이런 관행을 무엇이라고 부르며 어떻게 실천을 권장하는가?

**보기**
- A. AWS Config로 모든 아키텍처 결정을 자동 기록(Config는 리소스 구성 변경 이력을 기록하지만, "왜" 그런 아키텍처 결정을 내렸는지에 대한 맥락과 트레이드오프 논의 자체를 담는 도구는 아님).
- B. **Well-Architected 프레임워크의 운영 우수성(Operational Excellence) 기둥이 권장하는 아키텍처 결정 기록(Architecture Decision Records, ADR) 관행을 도입해, 각 주요 아키텍처 결정의 배경, 고려한 대안, 선택 근거, 트레이드오프를 문서(코드 리포지토리와 함께 버전 관리되는 경우가 많음)로 남겨 팀이 지속적으로 참조.**
- C. CloudTrail 로그만으로 모든 결정 근거를 파악(CloudTrail은 "무엇이" 변경되었는지의 API 호출 이력을 기록할 뿐, 결정의 배경/근거/트레이드오프 같은 맥락 정보는 담지 않음).
- D. AWS Support에 문의해 과거 결정 사항을 요청(AWS Support는 AWS 서비스 자체에 대한 지원을 제공하며, 고객 자신의 내부 아키텍처 결정 이력을 보관/제공하는 서비스가 아님).

**정답: B**

**해설**
**아키텍처 결정 기록(Architecture Decision Records, ADR)**은 AWS Well-Architected 프레임워크의 **운영 우수성** 기둥에서 권장하는 실천 관행으로, 주요 아키텍처 결정이 내려질 때마다 그 **배경(context), 고려했던 대안들, 최종 선택과 그 근거, 트레이드오프**를 간결한 문서로 기록해 코드 리포지토리 등과 함께 버전 관리합니다. 이를 통해 새로운 팀원이 합류하거나 시간이 지난 후에도 "왜 이런 결정을 내렸는가"에 대한 맥락을 구두 설명 없이도 언제든 참조할 수 있어, 조직의 아키텍처 지식을 체계적으로 축적하고 전수하는 표준 관행입니다.

**왜 다른 보기는 오답인가**
- A: Config는 리소스 구성 변경 이력을 기록할 뿐 결정의 맥락/근거를 담지 않습니다.
- C: CloudTrail은 API 호출 이력만 기록하며 결정 배경은 담지 않습니다.
- D: AWS Support는 고객 내부 결정 이력을 보관하는 서비스가 아닙니다.

> 💡 **시험 꿀팁**: 아키텍처 결정의 **배경과 근거를 체계적으로 문서화**하는 Well-Architected(운영 우수성) 권장 관행은 **아키텍처 결정 기록(Architecture Decision Records, ADR)**입니다.
