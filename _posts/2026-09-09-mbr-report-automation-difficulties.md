## 3. 기술적 난점과 해결

### HTML 웹앱은 외부에서 읽을 수 없다

Apps Script의 HTML 서비스는 실제 화면을 별도 iframe에 담아 전달한다. 바깥에서 URL을 호출하면 껍데기만 오고 표와 숫자는 따라오지 않는다. 텍스트를 그대로 반환하는 콘텐츠 서비스로 별도 엔드포인트(1편의 `mode` 분기)를 만들어 우회했다.

### 스프레드시트 직접 연동은 불가

시트를 외부에서 읽으려면 웹 게시가 필요한데, 그건 사내 데이터를 공개하는 것과 같다. 이미 승인된 계정 권한으로 실행되는 웹앱을 통로로 삼아, 데이터를 공개하지 않고도 접근을 확보했다.

### 권한 스코프의 함정

문서를 읽기만 해도 읽기 전용 스코프로는 열리지 않는 경우가 있었다. 캘린더·문서·드라이브 각각의 최소 스코프를 실패 로그로 역추적해 확정했다.

```json
{
  "oauthScopes": [
    "https://www.googleapis.com/auth/calendar.readonly",
    "https://www.googleapis.com/auth/documents",
    "https://www.googleapis.com/auth/drive.readonly",
    "https://www.googleapis.com/auth/script.container.ui"
  ]
}
```

`documents`는 `.readonly`가 아니다. 읽기만 하는데도 `DocumentApp.openByUrl()`이 쓰기 스코프를 요구했기 때문이다. `script.container.ui`는 메뉴에서 모달 UI(5장의 취합 도구)를 띄우는 데 별도로 필요했다.

### 누적 이력에서 최신 결론 판별

시트의 논의 이력 열은 여러 달의 기록이 한 셀에 누적된다. 폐기된 안과 확정된 안이 섞여 있어서 앞부분만 읽으면 틀린 결론을 쓰게 된다. **회의록이 있으면 시트보다 우선**이라는 규칙을 세워 해결했다 — 시트 이력은 참고만 하고, 같은 안건에 회의록이 있으면 그쪽을 근거로 삼는다.

### 수집 속도

초기 구현은 안건마다 시트 전체를 다시 읽어서, 안건 수만큼 호출이 발생했다. 한 번 읽은 데이터를 재사용하도록 바꿔 호출을 1회로 줄였다.

```js
// Before — 안건마다 piMinutes_(taskNo)를 호출 → 시트 재조회 N번
tasks.forEach(t => bundle.push(piMinutes_(t.taskNo)));

// After — piDocsFromRow_ 추가, 이미 읽은 row를 그대로 넘겨 재조회 0번
const rows = piRows_(month); // 시트 조회 1회
tasks.forEach(t => {
  const row = rows.find(r => r.taskNo === t.taskNo);
  bundle.push(piDocsFromRow_(row)); // row에 이미 있는 링크로 문서만 읽음
});
```

문서 읽기 자체는 병렬 요청으로 처리해, 안건 수가 늘어도 전체 소요 시간이 크게 늘지 않게 했다.

## 4. 본문 생성 규칙 — 요약만 LLM에 맡긴다

숫자와 표는 코드가 확정 출력하므로 생성 과정에서 값이 변형될 여지가 없다. [PI 포털의 안건 자동 분류](/posts/pi-portal-apps-script/)에 썼던 것과 같은 Vertex AI Gemini를 이번엔 회의록 요약에 썼다. 요약에는 아래 규칙을 적용하는데, 전부 실제 작성·검수를 반복하며 오류가 나온 지점마다 하나씩 추가된 것이다.

**내용 판단**

- 회의록이 최우선 근거다. 시트 이력과 어긋나면 회의록을 따른다.
- 반려·폐기된 안은 합의사항에 넣지 않고 별도 항목으로 분리한다.
- 원문에 없는 수치·금액·날짜·인명을 추론해 쓰지 않는다.
- "검토 필요"를 "진행합니다"로 격상하지 않는다. 확정 수준을 유지한다.
- 제기된 의견과 확정된 결론을 구분해 서술한다.
- 작성 시점 이후 회의는 예정으로 표시하고 결과를 쓰지 않는다.

**형식**

- 모든 문장을 서술형으로 끝낸다. 명사형 종결을 쓰지 않는다.
- 안건 상세는 배경 → 문제 → 합의사항 → 반려·우려사항 → Next Step 순이다.
- 개인명은 기재하지 않고 부서 단위로 표기한다.
- 건수에는 전체 대비 비율을 함께 표기한다.
- 각 안건 하단에 근거 회의록 링크를 배치한다.

## 5. 운영 방식

두 가지 경로를 병행한다.

- **경로 A · 대화형** — 엔드포인트를 직접 조회해 Vertex AI Gemini로 보고서를 작성한다. 월 지정 한 줄로 실행되며, 검수 피드백을 즉시 반영할 수 있다. 현재 주 경로다.
- **경로 B · 취합 도구** — 스프레드시트 메뉴 버튼으로 해당 월 원자료를 한 문서에 모은다. 사람이 원자료를 직접 검토할 때 쓴다.

산출물은 화면용 문서, 인쇄용 PDF, 편집 가능한 Word 파일로 내보낸다. Word 변환은 표·불릿·하이퍼링크를 유지하도록 문서 형식을 직접 생성하는 방식을 썼다. 복사·붙여넣기로는 레이아웃이 유지되지 않았기 때문이다.

## 6. 결과와 남은 과제

| | |
|---|---|
| 자동 연동 데이터 소스 | 4개 |
| 수기 전사 항목 | 0개 |
| 월간 실행 명령 | 1줄 |

숫자와 표는 원본과 항상 일치한다. 회의록이 갱신되면 해당 안건만 다시 읽어 부분 갱신할 수 있고, 회차가 바뀌어도 규칙은 그대로 재사용된다.

남은 과제는 이렇다.

- 완료 시점 열이 시트에 없어 특정 월에 완료된 안건을 자동 식별할 수 없다. 열 추가가 필요하다.
- Tier와 상태의 교차 집계는 기존 집계 로직에 없어 두 분포를 분리해 기재하고 있다.
- PDF·이미지 첨부는 링크로만 연결된다. 본문 내용까지 반영하려면 변환 단계가 추가로 필요하다.
- 완전 무인 실행은 요약 품질 편차 때문에 도입하지 않았다. 검수 단계를 유지하는 편이 안전하다고 판단했다.

> 판단이 필요한 구간과 계산으로 끝나는 구간을 먼저 나눈다. 계산 구간은 코드가 확정 출력하고, 판단 구간만 LLM에 맡긴다. 이렇게 하면 검수 범위가 좁아지고, 틀렸을 때 어디를 고쳐야 하는지 분명해진다.
