## Q1. 엣지 로케이션(Edge Location)의 특징

모서리 위치(엣지 로케이션)의 특징은 다음과 같습니다.

- A. 사용자와 더 가까운 호스트 Amazon EC2 인스턴스
- B. 사용자의 대기 시간을 줄이고 성능을 향상시킵니다.
- C. 원본 서버에 도달하지 않고 자주 변경되는 데이터를 캐시합니다.
- D. 매일 데이터를 새로 고칩니다.

**정답: B**

✅ **B. 사용자의 대기 시간을 줄이고 성능을 향상시킵니다.**: 엣지 로케이션은 Amazon CloudFront CDN의 핵심 구성 요소로, 전 세계 사용자에게 콘텐츠를 빠르게 전달하기 위해 지리적으로 분산된 위치에 배치됩니다. 사용자와 가까운 곳에서 콘텐츠를 제공함으로써 네트워크 지연(latency)을 크게 줄이고 성능을 향상시키는 것이 핵심 목적입니다.

❌ **A. 사용자와 더 가까운 호스트 Amazon EC2 인스턴스**: 엣지 로케이션은 EC2 인스턴스를 호스팅하는 곳이 아닙니다. EC2는 AWS 리전(Region)의 가용 영역(AZ)에서 실행됩니다.

❌ **C. 원본 서버에 도달하지 않고 자주 변경되는 데이터를 캐시합니다.**: 엣지 로케이션은 자주 변경되지 않는(정적) 콘텐츠를 캐싱하는 데 최적화되어 있습니다. 자주 변경되는 데이터는 캐싱 효율이 낮습니다.

❌ **D. 매일 데이터를 새로 고칩니다.**: 캐시 갱신은 TTL(Time To Live) 설정에 따라 이루어지며, 반드시 매일 새로 고침이 되는 것이 아닙니다. 무효화(Invalidation) 작업을 통해 수동으로도 가능합니다.

💡 **시험 꿀팁**: 엣지 로케이션 = CloudFront + 지연 시간 감소 + 콘텐츠 캐싱. 엣지 로케이션 수(400개 이상)는 리전 수(30개 이상)보다 훨씬 많습니다. "지연 시간 감소", "글로벌 콘텐츠 전송" 키워드가 나오면 CloudFront와 엣지 로케이션을 떠올리세요.

## Q2. S3 버킷 액세스 제한

다음 중 특정 사용자에 대한 Amazon 스토리지 서비스(Amazon S3) 버킷 액세스를 제한할 수 있는 항목은 무엇입니까?

- A. 공개 및 개인 키 쌍
- B. Amazon 검사관 (Amazon Inspector)
- C. AWS IAM(Identity and Access Management) 정책
- D. 보안 그룹

**정답: C**

✅ **C. AWS IAM 정책**: IAM 정책은 특정 사용자, 그룹, 역할에 대해 S3 버킷 및 객체에 대한 액세스 권한을 세밀하게 제어할 수 있습니다. S3 버킷 정책(Bucket Policy)과 IAM 정책을 함께 사용하여 "누가(Who) 무엇을(What) 할 수 있는지" 정의합니다.

❌ **A. 공개 및 개인 키 쌍**: 퍼블릭/프라이빗 키 쌍은 EC2 인스턴스 SSH 접속에 사용되며, S3 버킷 액세스 제어와는 관련이 없습니다.

❌ **B. Amazon 검사관 (Amazon Inspector)**: Amazon Inspector는 EC2 인스턴스 및 컨테이너 이미지의 취약점을 자동으로 검사하는 보안 서비스입니다. S3 버킷 액세스를 제한하는 기능이 없습니다.

❌ **D. 보안 그룹**: 보안 그룹(Security Group)은 EC2 인스턴스 등 VPC 내 리소스의 인바운드/아웃바운드 트래픽을 제어하는 가상 방화벽입니다. S3는 VPC 외부의 관리형 서비스로, 보안 그룹으로 액세스를 제한할 수 없습니다.

💡 **시험 꿀팁**: S3 접근 제어 = IAM 정책 + S3 버킷 정책 + ACL(Access Control List). "특정 사용자 액세스 제한" 키워드 → IAM 정책. 보안 그룹은 EC2/VPC 전용, Inspector는 취약점 스캔 전용으로 구분하세요.

## Q3. 무료로 이용할 수 있는 보안 관련 조치

다음 중 무료로 이용할 수 있는 보안 관련 조치는 무엇입니까?

- A. AWS 지원 요청
- B. 워크샵을 요청하기 위해 AWS 프로페셔널 서비스에 연락
- C. 포럼, 블로그 및 백서 액세스
- D. 지역 대학의 AWS 강의에 참석

**정답: C**

✅ **C. 포럼, 블로그 및 백서 액세스**: AWS는 AWS 공식 문서, 보안 백서(Whitepapers), 개발자 포럼, 공식 블로그 등을 무료로 제공합니다. AWS Well-Architected Framework, AWS 보안 모범 사례 등 다양한 보안 관련 자료를 비용 없이 열람할 수 있습니다.

❌ **A. AWS 지원 요청**: AWS 지원 플랜(Support Plan)은 Basic(무료), Developer, Business, Enterprise 등 단계가 있으며, 기술 지원을 받으려면 유료 플랜 가입이 필요합니다.

❌ **B. 워크샵을 요청하기 위해 AWS 프로페셔널 서비스에 연락**: AWS Professional Services는 유료 컨설팅 서비스로, 엔터프라이즈 고객이 클라우드 전환 및 최적화를 위해 별도 비용을 지불하고 이용합니다.

❌ **D. 지역 대학의 AWS 강의에 참석**: 대학 강의는 AWS가 제공하는 서비스가 아니며 별도의 교육 비용이 발생합니다.

💡 **시험 꿀팁**: AWS 무료 리소스 = 공식 문서 + 백서(Whitepaper) + 포럼 + AWS 블로그 + AWS 기술 FAQ. AWS Basic 지원 플랜은 무료이지만 기술 지원 담당자 접근은 제한적입니다. "무료"를 묻는 문제에서는 항상 공식 문서/백서/포럼이 답입니다.

## Q4. 속성 변경이 가능한 예약 인스턴스(RI) 유형

교환을 통해 동일하거나 더 큰 가치의 RI가 창출되는 한 RI의 속성을 변경할 수 있는 예약 인스턴스(Reserved Instance) 가격 모델은 무엇입니까?

- A. 전용 RI (Dedicated RI)
- B. 예약된 RI (Scheduled RI)
- C. 컨버터블 RIs (Convertible RIs)
- D. 표준 RIs (Standard RIs)

**정답: C**

✅ **C. 컨버터블 RIs**: Convertible Reserved Instance는 약정 기간 동안 인스턴스 패밀리, 운영 체제, 테넌시, 결제 옵션 등을 변경(교환)할 수 있는 유연한 RI 유형입니다. 단, 교환 시 동일하거나 더 높은 가치의 RI로만 교환이 가능하며, Standard RI보다 할인율이 약간 낮습니다.

❌ **A. 전용 RI (Dedicated RI)**: 전용 RI는 물리적으로 격리된 전용 하드웨어에서 실행되는 인스턴스를 예약하는 방식으로, 속성 변경과 관련된 별도 유형이 아닙니다.

❌ **B. 예약된 RI (Scheduled RI)**: Scheduled RI는 특정 시간대(예: 매일 오전 9시~오후 6시)에만 사용하는 방식으로, 현재는 더 이상 제공되지 않는 레거시 옵션입니다.

❌ **D. 표준 RIs (Standard RIs)**: Standard RI는 가장 높은 할인율(최대 72%)을 제공하지만, 인스턴스 패밀리 등 주요 속성을 변경할 수 없습니다. AZ(가용 영역) 변경 정도만 가능합니다.

💡 **시험 꿀팁**: Standard RI = 높은 할인율(~72%) + 속성 변경 불가 / Convertible RI = 낮은 할인율(~54%) + 속성 변경 가능. "유연하게 변경", "교환 가능" 키워드 → Convertible RI. 1년 또는 3년 약정 선택 가능합니다.

## Q5. 총 소유 비용(TCO) 절감을 위한 AWS 기능

고객의 총 소유 비용(TCO)을 절감할 수 있는 AWS 기능은 무엇입니까?

- A. 공유 책임 보안 모델
- B. 단일 테넌시 (Single Tenancy)
- C. 탄성 컴퓨팅 (Elastic Computing)
- D. 암호화

**정답: C**

✅ **C. 탄성 컴퓨팅**: AWS의 탄력적 컴퓨팅(Elastic Computing)은 실제 사용량에 따라 리소스를 자동으로 확장하거나 축소할 수 있습니다. 온프레미스처럼 최대 부하를 예상하여 과잉 프로비저닝할 필요 없이, 필요한 만큼만 사용하고 비용을 지불하므로 총 소유 비용(TCO)을 크게 절감합니다.

❌ **A. 공유 책임 보안 모델**: 공유 책임 모델은 AWS와 고객 간의 보안 책임 범위를 정의하는 개념으로, 직접적인 TCO 절감 기능이 아닙니다.

❌ **B. 단일 테넌시**: 단일 테넌시(Dedicated Host/Instance)는 물리적으로 격리된 전용 서버를 사용하는 방식으로, 일반 공유 테넌시보다 비용이 더 높아 TCO를 증가시킵니다.

❌ **D. 암호화**: 암호화는 데이터 보안을 위한 기능이며, 직접적인 비용 절감과는 관련이 없습니다.

💡 **시험 꿀팁**: TCO 절감의 핵심 = 탄력성(Elasticity) + 종량제(Pay-as-you-go) + 규모의 경제(Economies of Scale). "총 소유 비용 절감" 키워드 → 자본 지출(CapEx)을 운영 지출(OpEx)로 전환, 필요 시에만 사용하는 탄력적 컴퓨팅이 핵심입니다.

## Q6. 웹 트래픽 증가에 따라 자동으로 확장되는 서비스

다음 중 웹 트래픽의 예상 증가에 따라 자동으로 확장되는 서비스는 무엇입니까?

- A. AWS 코드 파이프라인 (AWS CodePipeline)
- B. 탄성 부하 분산 (Elastic Load Balancing)
- C. Amazon EBS
- D. AWS Direct Connect

**정답: B**

✅ **B. 탄성 부하 분산 (Elastic Load Balancing)**: ELB(Elastic Load Balancing)는 들어오는 트래픽을 여러 EC2 인스턴스, 컨테이너, IP 주소 등에 자동으로 분산시키며, 트래픽 증가에 따라 자동으로 확장됩니다. Auto Scaling과 함께 사용하면 트래픽 급증 시 새 인스턴스를 자동으로 추가하고 부하를 분산할 수 있습니다.

❌ **A. AWS 코드 파이프라인 (AWS CodePipeline)**: CodePipeline은 CI/CD(지속적 통합/지속적 배포) 파이프라인을 자동화하는 서비스입니다. 트래픽 처리 및 확장과는 관련이 없습니다.

❌ **C. Amazon EBS**: Amazon Elastic Block Store(EBS)는 EC2 인스턴스에 연결하는 블록 스토리지 서비스입니다. 웹 트래픽에 따라 자동으로 확장되는 기능이 없으며, 수동으로 볼륨 크기를 조정해야 합니다.

❌ **D. AWS Direct Connect**: Direct Connect는 온프레미스 데이터 센터와 AWS를 전용 네트워크 회선으로 연결하는 서비스입니다. 트래픽 자동 확장과는 관련이 없습니다.

💡 **시험 꿀팁**: 자동 확장 콤비 = ELB(부하 분산) + Auto Scaling(인스턴스 수 조정). "자동 확장", "트래픽 분산" 키워드 → ELB. ELB 유형: ALB(HTTP/HTTPS), NLB(TCP/UDP 고성능), GLB(방화벽 어플라이언스).

## Q7. AWS 준수 문서(SOC 1 보고서) 위치

SOC 1 보고서와 같은 AWS 준수 문서는 어디에 있습니까?

- A. Amazon 조사관 (Amazon Inspector)
- B. AWS CloudTrail
- C. AWS 아티팩트 (AWS Artifact)
- D. AWS 인증서 관리자 (AWS Certificate Manager)

**정답: C**

✅ **C. AWS 아티팩트 (AWS Artifact)**: AWS Artifact는 AWS 보안 및 규정 준수 보고서에 대한 온디맨드 액세스를 제공하는 셀프 서비스 포털입니다. SOC 1, SOC 2, SOC 3, PCI DSS, ISO 인증서, HIPAA 관련 문서 등 다양한 컴플라이언스 문서를 무료로 다운로드할 수 있습니다.

❌ **A. Amazon 조사관 (Amazon Inspector)**: Amazon Inspector는 EC2 인스턴스 및 컨테이너의 보안 취약점을 자동으로 검사하는 서비스입니다. 규정 준수 보고서를 제공하지 않습니다.

❌ **B. AWS CloudTrail**: CloudTrail은 AWS 계정 내 API 호출 이력을 기록하고 감사하는 서비스입니다. SOC 보고서 같은 외부 규정 준수 문서를 제공하지 않습니다.

❌ **D. AWS 인증서 관리자 (AWS Certificate Manager)**: ACM은 SSL/TLS 인증서를 프로비저닝, 관리, 배포하는 서비스입니다. 규정 준수 보고서와 관련이 없습니다.

💡 **시험 꿀팁**: AWS Artifact = 규정 준수 보고서 저장소(SOC, PCI, ISO 등) + 무료 + 셀프 서비스. "컴플라이언스 문서", "감사 보고서", "SOC", "PCI DSS" 키워드 → AWS Artifact를 떠올리세요.

## Q8. 공유 책임 모델에서 고객의 책임 (두 개 선택)

AWS 공유 책임 모델에서 다음 중 고객의 책임은 무엇입니까? (두 개를 선택합니다.)

- A. Amazon RDS용 운영 체제 구성요소 패치
- B. 클라이언트측 데이터 암호화
- C. 데이터 센터 직원 교육
- D. 네트워크 액세스 제어 목록(ACL) 구성
- E. 데이터 센터 내 환경 제어 유지

**정답: B, D**

✅ **B. 클라이언트측 데이터 암호화**: 클라이언트 측(고객 측)에서 데이터를 암호화하는 것은 전적으로 고객의 책임입니다. AWS는 암호화 도구(KMS 등)를 제공하지만, 암호화를 적용하고 키를 관리하는 것은 고객이 결정합니다.

✅ **D. 네트워크 ACL 구성**: 보안 그룹, 네트워크 ACL 등 네트워크 수준의 접근 제어 설정은 고객의 책임입니다. AWS는 네트워크 인프라를 제공하지만, 고객이 트래픽 규칙을 직접 구성해야 합니다.

❌ **A. Amazon RDS용 운영 체제 구성요소 패치**: RDS는 AWS의 완전관리형 서비스(Managed Service)입니다. 운영 체제 패치 및 데이터베이스 엔진 업데이트는 AWS가 담당합니다. (EC2에 직접 DB를 설치한 경우에는 고객 책임)

❌ **C. 데이터 센터 직원 교육**: 데이터 센터의 물리적 보안, 직원 관리 및 교육은 AWS의 책임입니다.

❌ **E. 데이터 센터 내 환경 제어 유지**: 데이터 센터의 온도, 습도, 전력 등 물리적 환경 제어는 AWS의 책임입니다.

💡 **시험 꿀팁**: 공유 책임 모델 구분법 — AWS 책임("클라우드의 보안"): 물리적 인프라, 데이터 센터, 관리형 서비스 OS 패치 / 고객 책임("클라우드에서의 보안"): 데이터 암호화, IAM, 네트워크 ACL, 보안 그룹, 애플리케이션 패치(EC2). RDS는 관리형 → OS 패치는 AWS!

## Q9. 고가용성 아키텍처 설계 패턴

AWS에서 고가용성 아키텍처를 설계할 때 권장되는 패턴은 무엇입니까?

- A. 구성요소의 네트워크 연결 지연 시간이 짧은지 확인합니다.
- B. 최대 부하에서 작동하기에 충분한 Amazon EC2 인스턴스 실행
- C. 응용프로그램이 단일 구성요소의 고장을 수용하도록 설계되었는지 확인합니다.
- D. 모든 작업을 처리하는 단일 애플리케이션을 사용합니다.

**정답: C**

✅ **C. 응용프로그램이 단일 구성요소의 고장을 수용하도록 설계되었는지 확인합니다.**: 고가용성(HA, High Availability) 설계의 핵심은 단일 장애점(SPOF, Single Point of Failure)을 제거하는 것입니다. 하나의 구성요소가 실패해도 전체 시스템이 계속 운영될 수 있도록 다중화(Redundancy), 자동 장애 조치(Failover), 다중 AZ 배포를 통해 내결함성(Fault Tolerance)을 확보해야 합니다.

❌ **A. 구성요소의 네트워크 연결 지연 시간이 짧은지 확인합니다.**: 낮은 지연 시간은 성능 최적화에 해당하며, 고가용성을 보장하는 설계 패턴이 아닙니다.

❌ **B. 최대 부하에서 작동하기에 충분한 Amazon EC2 인스턴스 실행**: 이는 온프레미스 방식의 과잉 프로비저닝(Over-provisioning)으로 비효율적입니다. AWS에서는 Auto Scaling으로 동적으로 조정하는 것이 모범 사례입니다.

❌ **D. 모든 작업을 처리하는 단일 애플리케이션을 사용합니다.**: 단일 모놀리식 애플리케이션은 SPOF를 만들어 고가용성에 역행합니다. 마이크로서비스 아키텍처나 분산 설계가 권장됩니다.

💡 **시험 꿀팁**: 고가용성 = 단일 장애점(SPOF) 제거 + 다중 AZ 배포 + 자동 장애 조치(Failover). AWS Well-Architected Framework의 안정성(Reliability) 원칙과 일치합니다. "고가용성" → 다중 AZ, ELB, Auto Scaling, RDS Multi-AZ를 떠올리세요.

## Q10. AWS 클라우드 애플리케이션 설계 모범 사례

모범 사례에 따르면 AWS 클라우드에서 애플리케이션을 실행하려면 어떻게 설계해야 합니까?

- A. 단단히 결합된 구성 요소를 사용합니다. (Tightly Coupled)
- B. 느슨하게 결합된 부품을 사용합니다. (Loosely Coupled)
- C. 간헐적으로 결합된 구성 요소를 사용합니다.
- D. 자주 결합되는 구성 요소를 사용합니다.

**정답: B**

✅ **B. 느슨하게 결합된 부품을 사용합니다.**: 느슨한 결합(Loose Coupling)은 AWS Well-Architected Framework의 핵심 설계 원칙입니다. 각 구성 요소가 독립적으로 운영되어 하나의 구성 요소가 실패해도 다른 구성 요소에 영향을 주지 않습니다. Amazon SQS(메시지 큐), SNS(알림), API Gateway 등이 느슨한 결합을 구현하는 데 사용됩니다.

❌ **A. 단단히 결합된 구성 요소를 사용합니다.**: 긴밀한 결합(Tight Coupling)은 하나의 구성 요소 장애가 연쇄적으로 다른 구성 요소에도 영향을 미칩니다. 확장성과 내결함성이 낮아 클라우드 환경에 부적합합니다.

❌ **C. 간헐적으로 결합된 구성 요소를 사용합니다.**: 이는 실제 AWS 설계 패턴에서 사용되는 개념이 아닙니다.

❌ **D. 자주 결합되는 구성 요소를 사용합니다.**: 이 역시 표준 AWS 아키텍처 원칙이 아닙니다.

💡 **시험 꿀팁**: 느슨한 결합(Loose Coupling) 구현 서비스 = Amazon SQS(대기열) + SNS(알림) + API Gateway. "마이크로서비스", "독립적 확장", "장애 격리" 키워드 → 느슨한 결합. AWS Well-Architected Framework 5대 원칙 중 운영 우수성(Operational Excellence)과 안정성(Reliability)의 핵심입니다.

## Q11. IAM 사용자에게 보안 추가 방법 (두 개 선택)

AWS는 다음 중 IAM(Identity and Access Management) 사용자에게 보안을 추가하는 방법을 지원합니까? (두 개를 선택합니다.)

- A. Amazon Rekognition 구현
- B. AWS Shield 보호 리소스 사용
- C. Security Group을 통한 액세스 차단
- D. MFA(Multi-Factor Authentication) 사용
- E. 암호 보안 수준 및 만료 적용

**정답: D, E**

✅ **D. MFA(Multi-Factor Authentication) 사용**: MFA는 패스워드 외에 추가 인증 요소(OTP, 하드웨어 토큰 등)를 요구하여 IAM 사용자 계정 보안을 크게 강화합니다. 루트 계정과 권한이 높은 IAM 사용자에게는 MFA 적용이 강력히 권장됩니다.

✅ **E. 암호 보안 수준 및 만료 적용**: IAM 패스워드 정책(Password Policy)을 통해 최소 길이, 특수 문자 요구, 정기적인 패스워드 만료 등을 강제하여 IAM 사용자의 계정 보안을 강화할 수 있습니다.

❌ **A. Amazon Rekognition 구현**: Rekognition은 이미지 및 영상에서 객체, 얼굴, 텍스트를 인식하는 AI/ML 서비스입니다. IAM 사용자 보안 강화와는 관련이 없습니다.

❌ **B. AWS Shield 보호 리소스 사용**: AWS Shield는 DDoS(분산 서비스 거부 공격)로부터 AWS 리소스를 보호하는 서비스입니다. IAM 사용자 개인 계정 보안과는 관련이 없습니다.

❌ **C. Security Group을 통한 액세스 차단**: 보안 그룹은 EC2 등 네트워크 수준의 접근 제어를 위한 것으로, IAM 사용자 인증 보안 강화와 무관합니다.

💡 **시험 꿀팁**: IAM 보안 강화 3종 세트 = MFA(다단계 인증) + 강력한 패스워드 정책 + 최소 권한 원칙(Least Privilege). "루트 계정 보호" → MFA 반드시 활성화. IAM 자격 증명 보고서(Credential Report)로 MFA 미적용 사용자를 확인할 수 있습니다.

## Q12. 지속적으로 변경되는 데이터의 읽기/쓰기 서비스 (두 개 선택)

지속적으로 변경되는 데이터의 읽기/쓰기에 사용해야 하는 AWS 서비스는 무엇입니까? (두 개를 선택합니다.)

- A. 아마존 빙하 (Amazon Glacier / S3 Glacier)
- B. Amazon RDS
- C. AWS 스노우볼 (AWS Snowball)
- D. Amazon Redshift
- E. Amazon EFS

**정답: B, E**

✅ **B. Amazon RDS**: Amazon Relational Database Service(RDS)는 관계형 데이터베이스로, OLTP(온라인 트랜잭션 처리) 워크로드에 최적화되어 있습니다. 지속적으로 변경되는 데이터(INSERT, UPDATE, DELETE)를 실시간으로 처리하는 데 적합합니다.

✅ **E. Amazon EFS**: Amazon Elastic File System(EFS)은 여러 EC2 인스턴스가 동시에 읽고 쓸 수 있는 완전관리형 공유 파일 시스템입니다. 지속적으로 변경되는 파일 데이터를 여러 인스턴스에서 동시에 액세스해야 하는 경우에 적합합니다.

❌ **A. 아마존 빙하 (Amazon S3 Glacier)**: S3 Glacier는 장기 보관(아카이브) 목적의 저비용 스토리지입니다. 데이터 검색에 수분~수시간이 걸리므로 지속적인 읽기/쓰기에 부적합합니다.

❌ **C. AWS 스노우볼**: Snowball은 대용량 데이터를 물리적으로 AWS로 이전하기 위한 데이터 마이그레이션 장치입니다. 온라인 실시간 데이터 처리 서비스가 아닙니다.

❌ **D. Amazon Redshift**: Redshift는 페타바이트급 데이터 웨어하우스 서비스로, OLAP(온라인 분석 처리)에 최적화되어 있습니다. 대용량 분석 쿼리에 적합하지만, 지속적인 소규모 읽기/쓰기 트랜잭션에는 부적합합니다.

💡 **시험 꿀팁**: 스토리지 목적별 구분 — 실시간 읽기/쓰기: RDS, DynamoDB, EFS / 분석(OLAP): Redshift / 아카이브(장기 보관): S3 Glacier / 데이터 이전: Snowball. "지속적 변경", "실시간 트랜잭션" → RDS 또는 DynamoDB!

## Q13. Amazon RDS의 장점 (세 개 선택)

Amazon RDS(Amazon Relational Database Service)의 장점 중 하나는 무엇입니까? (3가지 선택)

- A. 관계형 데이터베이스 관리 작업을 단순화합니다.
- B. 99.999999999%의 신뢰성과 내구성을 제공합니다.
- C. 부하에 따라 데이터베이스의 크기를 자동으로 조정합니다.
- D. 사용자가 CPU 및 RAM 리소스를 동적으로 조정할 수 있도록 했습니다.

**정답: A, C, D**

✅ **A. 관계형 데이터베이스 관리 작업을 단순화합니다.**: RDS는 완전관리형(Fully Managed) 서비스로, 데이터베이스 설치, 패치, 백업, 복구, 모니터링 등의 관리 작업을 AWS가 대신 처리합니다. 개발자는 데이터베이스 관리보다 애플리케이션 개발에 집중할 수 있습니다.

✅ **C. 부하에 따라 데이터베이스의 크기를 자동으로 조정합니다.**: RDS Storage Auto Scaling 기능을 통해 스토리지 사용량이 임계치에 도달하면 자동으로 스토리지 용량을 확장합니다. 또한 RDS는 읽기 전용 복제본(Read Replica)을 통해 읽기 부하를 분산할 수 있습니다.

✅ **D. 사용자가 CPU 및 RAM 리소스를 동적으로 조정할 수 있도록 했습니다.**: RDS 인스턴스 유형을 변경하여 CPU, 메모리(RAM) 등의 컴퓨팅 리소스를 필요에 따라 조정할 수 있습니다(수직 확장, Vertical Scaling).

❌ **B. 99.999999999%의 신뢰성과 내구성을 제공합니다.**: 99.999999999%(11 9s)의 내구성은 Amazon S3의 특성입니다. RDS는 Multi-AZ 구성 시 99.95% SLA의 가용성을 제공하지만, 11 9s 내구성은 RDS의 공식 사양이 아닙니다.

💡 **시험 꿀팁**: 99.999999999%(11 Nine) 내구성은 오직 Amazon S3만 해당합니다. RDS 장점 키워드 = 완전관리형(자동 패치/백업) + 스토리지 자동 확장 + Multi-AZ 고가용성 + 읽기 전용 복제본(Read Replica). S3와 RDS를 혼동하는 문제가 자주 출제됩니다!

## Q14. 쉽게 확장할 수 있는 MySQL 데이터베이스 서비스

고객은 쉽게 확장할 수 있는 MySQL 데이터베이스를 실행해야 합니다. 어떤 AWS 서비스를 사용해야 합니까?

- A. 아마존 오로라 (Amazon Aurora)
- B. Amazon Redshift
- C. 아마존 다이너모DB (Amazon DynamoDB)
- D. Amazon ElastiCache

**정답: A**

✅ **A. 아마존 오로라 (Amazon Aurora)**: Amazon Aurora는 MySQL 및 PostgreSQL과 호환되는 완전관리형 관계형 데이터베이스 서비스입니다. 표준 MySQL 대비 최대 5배의 성능을 제공하며, 스토리지가 자동으로 최대 128TB까지 확장됩니다. 읽기 전용 복제본을 최대 15개까지 추가하여 읽기 확장성을 제공합니다.

❌ **B. Amazon Redshift**: Redshift는 데이터 웨어하우스(OLAP) 서비스로, MySQL 호환 관계형 데이터베이스가 아닙니다. 대용량 분석 쿼리에 특화되어 있습니다.

❌ **C. 아마존 다이너모DB**: DynamoDB는 NoSQL(키-값, 문서) 데이터베이스 서비스입니다. MySQL 같은 관계형(SQL) 데이터베이스가 아니므로, SQL 쿼리를 기반으로 한 기존 애플리케이션에는 적합하지 않습니다.

❌ **D. Amazon ElastiCache**: ElastiCache는 인메모리 캐싱 서비스(Redis, Memcached)로, 주로 데이터베이스 성능 향상을 위한 캐시 레이어로 사용됩니다. 독립적인 주 데이터베이스 역할을 하지 않습니다.

💡 **시험 꿀팁**: Aurora = MySQL/PostgreSQL 호환 + 고성능(MySQL 대비 5배) + 자동 확장(최대 128TB) + 서버리스 옵션. "MySQL", "PostgreSQL", "관계형", "확장 가능" → Aurora. DynamoDB = NoSQL, Redshift = 데이터 웨어하우스로 명확히 구분하세요.

## Q15. 가용 영역(AZ)의 정의

다음 중 짧은 지연 시간 링크를 통해 상호 연결된 하나 이상의 개별 데이터 센터로 구성된 AWS Global Infrastructure 구성 요소는 무엇입니까?

- A. 가용성 영역 (Availability Zone)
- B. 가장자리 위치 (Edge Location)
- C. 지역 (Region)
- D. 프라이빗 네트워킹

**정답: A**

✅ **A. 가용성 영역 (Availability Zone)**: 가용 영역(AZ)은 하나 이상의 물리적 데이터 센터로 구성되며, 동일 리전 내 다른 AZ와 저지연(Low Latency)의 고속 전용 네트워크로 연결되어 있습니다. 각 AZ는 독립적인 전력, 냉각, 네트워킹 인프라를 갖추고 있어 한 AZ의 장애가 다른 AZ에 영향을 주지 않습니다.

❌ **B. 가장자리 위치 (Edge Location)**: 엣지 로케이션은 CloudFront CDN의 캐싱 서버가 위치한 곳으로, 데이터 센터 집합체가 아닙니다.

❌ **C. 지역 (Region)**: 리전은 2개 이상의 가용 영역(AZ)을 포함하는 더 큰 지리적 영역입니다. 서울 리전(ap-northeast-2)은 4개의 AZ로 구성됩니다.

❌ **D. 프라이빗 네트워킹**: 프라이빗 네트워킹은 AWS 글로벌 인프라의 구성 요소 분류가 아닙니다. VPC 내 프라이빗 서브넷과 연관된 개념입니다.

💡 **시험 꿀팁**: AWS 인프라 계층 구조 = 리전(Region) > 가용 영역(AZ) > 데이터 센터. AZ = 1개 이상의 데이터 센터 + 저지연 연결. 리전 = 2개 이상의 AZ. 엣지 로케이션은 리전/AZ와 별개로 전 세계에 분산. "짧은 지연", "데이터 센터 집합" → AZ!

## Q16. 고객과 AWS 간의 공유 제어

다음 중 고객과 AWS 간의 공유 제어는 무엇입니까?

- A. Amazon S3 클라이언트측 암호화를 위한 키 제공
- B. Amazon EC2 인스턴스 구성
- C. 물리적 AWS 데이터 센터의 환경 제어
- D. 인식 및 교육 (Awareness and Training)

**정답: D**

✅ **D. 인식 및 교육**: 보안 인식 및 교육은 공유 책임 모델에서 공유 제어(Shared Control)에 해당합니다. AWS는 AWS 직원에 대한 보안 인식 교육을 실시하고, 고객은 자사 직원과 개발자에 대한 보안 인식 및 AWS 사용 교육을 실시해야 합니다. 양측 모두 각자의 영역에서 교육 책임이 있습니다.

❌ **A. Amazon S3 클라이언트측 암호화를 위한 키 제공**: 클라이언트 측 암호화 키 관리는 고객의 단독 책임입니다. AWS는 클라이언트 측에서 어떤 키를 사용하는지 알 수 없습니다.

❌ **B. Amazon EC2 인스턴스 구성**: EC2 인스턴스의 운영 체제, 애플리케이션, 방화벽 설정 등의 구성은 고객의 단독 책임입니다.

❌ **C. 물리적 AWS 데이터 센터의 환경 제어**: 데이터 센터의 물리적 보안(잠금장치, 경비원, 온도/습도 제어 등)은 AWS의 단독 책임입니다.

💡 **시험 꿀팁**: 공유 제어(Shared Controls) 3가지 = 패치 관리(Patch Management) + 구성 관리(Configuration Management) + 인식 및 교육(Awareness & Training). AWS와 고객 모두 각자의 영역에서 이 세 가지를 수행해야 합니다. "공유 제어" 키워드 → 교육/패치/구성 관리!

## Q17. 고가용성을 위한 최소 가용 영역 수

고가용성을 달성하기 위해 컴퓨팅 리소스를 몇 개의 가용성 영역에 걸쳐 프로비저닝해야 합니까?

- A. 최소 1개
- B. 최소 2개
- C. 최소 3개
- D. 최소 4개 이상

**정답: B**

✅ **B. 최소 2개**: 고가용성(High Availability)을 달성하려면 최소 2개의 가용 영역(AZ)에 리소스를 분산 배포해야 합니다. 하나의 AZ에 장애가 발생해도 다른 AZ에서 서비스를 계속 제공할 수 있습니다. ELB와 Auto Scaling을 함께 사용하여 트래픽을 자동으로 정상 AZ로 전환합니다.

❌ **A. 최소 1개**: 단일 AZ 배포는 해당 AZ 장애 시 서비스 중단이 발생합니다. 이는 단일 장애점(SPOF)을 가진 구성으로 고가용성이 아닙니다.

❌ **C. 최소 3개**: 3개 이상의 AZ 배포는 더 높은 가용성을 제공하지만, AWS에서 고가용성의 최소 요건은 2개입니다. 3개 배포는 일부 기업의 내부 정책이나 특수 요건에 해당합니다.

❌ **D. 최소 4개 이상**: 현실적으로 대부분의 AWS 리전이 3~4개의 AZ를 제공하며, 최소 4개는 고가용성의 일반적 최소 기준이 아닙니다.

💡 **시험 꿀팁**: 고가용성 최소 구성 = 2개 AZ + ELB + Auto Scaling. AWS는 각 리전에 최소 3개 AZ를 보유하며(일부 리전 예외), RDS Multi-AZ는 자동으로 2개 AZ에 배포합니다. "고가용성 최소" → 2개 AZ!

## Q18. 온프레미스에서 AWS로 전환 시 이점

사내 데이터 센터에서 AWS 클라우드로 인프라를 전환할 때 얻을 수 있는 이점 중 하나는 다음과 같습니다.

- A. IT 비용을 없앨 수 있습니다.
- B. 기업은 각 고객의 데이터 센터에 서버를 배치할 수 있습니다.
- C. 비즈니스가 비즈니스 활동에 집중할 수 있도록 합니다.
- D. 서버를 패치하지 않은 상태로 둘 수 있습니다.

**정답: C**

✅ **C. 비즈니스가 비즈니스 활동에 집중할 수 있도록 합니다.**: AWS 클라우드로 전환하면 서버 구매, 데이터 센터 유지 관리, 네트워크 장비 관리 등의 IT 인프라 운영 부담을 AWS에 위임할 수 있습니다. 이를 통해 기업은 핵심 비즈니스 혁신과 차별화에 더 많은 시간과 자원을 집중할 수 있습니다.

❌ **A. IT 비용을 없앨 수 있습니다.**: AWS로 전환해도 IT 비용이 완전히 사라지지는 않습니다. 자본 지출(CapEx)이 운영 지출(OpEx)로 전환되며, 올바른 아키텍처 설계를 통해 비용을 최적화할 수 있을 뿐입니다.

❌ **B. 기업은 각 고객의 데이터 센터에 서버를 배치할 수 있습니다.**: AWS 클라우드는 공유 인프라를 사용하므로, 개별 고객의 데이터 센터에 서버를 배치하는 방식이 아닙니다. (AWS Outposts는 예외적으로 온프레미스에 AWS 인프라를 배치하는 서비스)

❌ **D. 서버를 패치하지 않은 상태로 둘 수 있습니다.**: EC2 등 IaaS 서비스의 경우 운영 체제 패치는 여전히 고객의 책임입니다. 보안 패치를 소홀히 하는 것은 보안 취약점을 만들 수 있어 절대 권장되지 않습니다.

💡 **시험 꿀팁**: 클라우드 전환의 핵심 이점 = 민첩성(Agility) + 비용 효율화 + 비즈니스 집중 + 글로벌 확장. "IT 관리 부담 감소", "핵심 비즈니스 집중" → 클라우드의 대표 이점. CapEx(자본 지출) → OpEx(운영 지출) 전환이 핵심 비용 이점입니다.

## Q19. 즉각적 검색을 위한 저렴하고 내구성 높은 스토리지

즉각적인 검색을 위해 데이터베이스 백업을 보존하기 위한 가장 저렴하고 내구성이 뛰어난 스토리지 옵션은 무엇입니까?

- A. 아마존 S3 (Amazon S3)
- B. 아마존 빙하 (Amazon S3 Glacier)
- C. Amazon EBS
- D. Amazon EC2 인스턴스 저장소

**정답: A**

✅ **A. 아마존 S3**: Amazon S3는 99.999999999%(11 9s)의 내구성을 제공하는 객체 스토리지 서비스입니다. 데이터를 즉시 액세스(밀리초 단위)할 수 있으며, EBS나 EC2 인스턴스 스토어보다 훨씬 저렴합니다. 데이터베이스 백업, 로그, 미디어 파일 등의 장기 보존에 이상적입니다.

❌ **B. 아마존 빙하 (Amazon S3 Glacier)**: S3 Glacier는 S3보다 더 저렴하지만, 데이터 검색에 수분(Glacier Instant Retrieval)에서 수시간(Glacier Deep Archive)이 소요됩니다. "즉각적인 검색"이라는 조건에 부합하지 않습니다.

❌ **C. Amazon EBS**: EBS는 EC2 인스턴스에 연결되는 블록 스토리지로, 인스턴스에 종속적이며 S3보다 비용이 높습니다. 데이터베이스 백업 장기 보존보다는 실행 중인 인스턴스의 OS/데이터 볼륨에 적합합니다.

❌ **D. Amazon EC2 인스턴스 저장소**: 인스턴스 스토어는 EC2 인스턴스에 물리적으로 연결된 임시 스토리지입니다. 인스턴스가 중지되거나 종료되면 데이터가 삭제되므로 내구성이 매우 낮습니다.

💡 **시험 꿀팁**: S3 스토리지 클래스 선택 기준 — 즉각 접근 필요 + 저비용: S3 Standard 또는 S3-IA / 즉각 접근 필요 + 최저비용: S3 Glacier Instant Retrieval / 장기 보관 + 가끔 접근: S3 Glacier / 장기 보관 + 거의 접근 안 함: S3 Glacier Deep Archive. "즉각적 검색" + "저렴" + "내구성" → Amazon S3!

## Q20. AWS CLI를 통한 서비스 접근을 위한 IAM 기능

개발자가 AWS CLI를 통해 AWS 서비스에 액세스할 수 있는 AWS IAM 기능은 무엇입니까?

- A. API 키
- B. 액세스 키 (Access Keys)
- C. 사용자 이름/암호
- D. SSH 키

**정답: B**

✅ **B. 액세스 키 (Access Keys)**: AWS CLI, SDK, API를 통해 AWS 서비스에 프로그래밍 방식으로 접근할 때는 IAM 액세스 키를 사용합니다. 액세스 키는 액세스 키 ID(Access Key ID)와 시크릿 액세스 키(Secret Access Key) 두 부분으로 구성됩니다. `aws configure` 명령어로 설정하여 사용합니다.

❌ **A. API 키**: AWS IAM에서 공식적으로 사용하는 용어는 "액세스 키(Access Keys)"입니다. "API 키"는 일반적인 용어로 혼용되기도 하지만, AWS IAM의 정확한 명칭은 액세스 키입니다.

❌ **C. 사용자 이름/암호**: 사용자 이름과 암호는 AWS 관리 콘솔(웹 UI) 로그인에 사용됩니다. CLI, SDK, API 접근에는 사용할 수 없습니다.

❌ **D. SSH 키**: SSH 키 쌍은 EC2 인스턴스에 SSH로 직접 접속할 때 사용됩니다. AWS CLI를 통한 AWS 서비스 API 호출에는 사용하지 않습니다.

💡 **시험 꿀팁**: AWS 접근 방식 구분 — 콘솔(웹 브라우저): 사용자 이름 + 암호 (+ MFA) / CLI/SDK/API: 액세스 키 ID + 시크릿 액세스 키 / EC2 SSH 접속: SSH 키 쌍(Key Pair). 보안 모범 사례: 루트 계정 액세스 키는 절대 생성하지 말고, IAM 역할(Role)로 EC2/Lambda 등에서 AWS 서비스에 접근하는 것을 권장합니다.
