[1편](/posts/docx-process-flowchart-elt/), [2편](/posts/flowchart-swimlane-edge-routing/)에서 다룬 플로우차트는 "프로세스가 어떤 순서로 흘러가는지"는 잘 보여줬지만, 실제로 화면을 시연했을 때 돌아온 질문은 다른 방향이었다. "이 단계, 누가 책임지나요?", "이 문제가 얼마나 심각한 건가요?" — 도형과 화살표만으로는 답할 수 없는 질문들이었다. 그래서 노드를 클릭하면 열리는 상세 패널을 별도로 설계했다.

> 이 글도 1·2편과 동일한 마스킹 기준을 따른다 — 회사명·조직 식별자는 담지 않았고, 프로세스 이름은 역할 기반으로 일반화했다.

## 1. 요구사항: 청중마다 알고 싶은 게 달랐다

시연을 반복하면서 알게 된 건, "이 프로세스 좀 자세히 보여줘"라는 요청이 사람마다 다른 걸 원한다는 점이었다.

- 경영진/기획: 이 단계 담당은 누구고, 목표 대비 실제 소요시간(Lead time gap)이 얼마나 벌어져 있는지
- 실무자: 세부 단계별로 RACI(누가 실무를 하고, 누가 최종 책임지는지)가 어떻게 나뉘는지
- 개선 논의: 이 프로세스에 어떤 Pain Point가 있고, 그중 뭐가 제일 급한지

이 세 갈래 요구를 패널 하나에 다 욱여넣지 않고, **개요 / 단계 / 이슈** 3개 탭으로 나눴다. 처음엔 한 화면에 다 넣었는데 "그래서 지금 제일 급한 문제가 뭐야"가 스크롤 없이는 안 보였고, 탭으로 쪼갠 뒤에야 이슈 탭 하나만 눌러도 우선순위가 바로 보이게 됐다.

## 2. Pain Point 우선순위 스코어 — 공식은 데이터로, 등급 기준도 데이터로

Pain Point마다 `frequency`(빈도) × `business_impact`(영향도)로 계산한 `priority_score`를 저장해뒀는데, 점수 하나만 숫자로 던지면 "37점이 높은 건지 낮은 건지" 바로 안 와닿는다. 그래서 점수 구간(band)마다 라벨과 조치를 매핑하는 기준을 별도 컬렉션(`priority_score_scale`)으로 분리했다.

```ts
function bandForScore(score: number | null, bands?: { range: string; label: string }[]) {
  if (score == null || !bands) return null;
  for (const b of bands) {
    const [lo, hi] = b.range.split("-").map(Number);
    if (score >= lo && score <= hi) return b.label;
  }
  return null;
}
```

이렇게 분리해두면 "몇 점 이상은 긴급"이라는 등급 기준 자체가 바뀌어도 코드를 안 건드리고 시드 데이터의 `bands` 배열만 고치면 된다. 화면에는 점수와 라벨을 같이 보여준다(예: `37 · 긴급`) — 숫자만 있을 때보다 판단이 훨씬 빨라졌다.

## 3. RACI 코드를 코드 그대로 보여주지 않기

`steps` 컬렉션에는 단계별 RACI(Responsible/Accountable/Consulted/Informed)가 `R`/`A`/`C`/`I` 코드로 그대로 들어있는데, 이니셜만 봐서는 매번 무슨 뜻인지 다시 떠올려야 했다. 그래서 이니셜 → 역할명 → 설명 매핑 테이블을 프론트에 두고, hover하면 툴팁으로 전체 설명이 뜨게 했다.

```ts
const RACI_MEANING: Record<string, { role: string; desc: string }> = {
  R: { role: "실무", desc: "Responsible · 실제 업무를 수행" },
  A: { role: "책임", desc: "Accountable · 최종 승인·책임" },
  C: { role: "협의", desc: "Consulted · 의견을 구함" },
  I: { role: "통보", desc: "Informed · 결과를 통보받음" },
};
```

값이 없거나 `"-"`인 항목은 렌더링에서 아예 뺀다. "담당자 없음"이라고 굳이 표시하는 대신, 없는 항목은 화면에서 조용히 사라지게 했다 — 빈 칸이 많아 보이는 것보다 있는 정보만 깔끔하게 보이는 쪽이 우선순위 판단에 더 도움이 됐다.

## 4. 분기하는 "다음 프로세스" — 단일 값과 배열을 한 로직으로

프로세스 연결 관계(이전 → 현재 → 다음)를 보여줄 때 까다로웠던 부분은 "다음 프로세스"가 항상 하나가 아니라는 점이었다. 딜 유형 분류처럼 분기가 있는 프로세스는 다음 단계가 여러 개다. 그래서 타입 자체를 `ProcessContextRef | ProcessContextRef[]`로 열어두고, 프론트에서 배열/단일 값 여부를 흡수한다.

```ts
const nextRefs = Array.isArray(ctx?.next_process)
  ? ctx?.next_process
  : ctx?.next_process
  ? [ctx.next_process]
  : [];
```

화면에는 항상 배열로 정규화한 뒤 이어붙여서 보여주고, 분기가 없는 프로세스는 자연스럽게 배열 길이 1로 처리된다 — 분기 여부에 따라 컴포넌트를 따로 만들지 않고 하나의 로직으로 두 케이스를 다 커버했다.

## 5. 데이터 품질 문제를 숨기지 않고 그대로 노출

원본 정의서를 정제하다 보면 "이 항목은 정의서에 없어서 추정했다"거나 "문서 간 내용이 서로 다르다" 같은 이슈가 나온다. 이런 걸 조용히 덮어쓰는 대신 `data_quality_flags` 컬렉션에 그대로 남겨서, 이슈 탭에 "데이터 품질 플래그"로 노출한다.

```tsx
{detail.data_quality_flags.map((f, i) => (
  <div key={i} className="flag">
    <b>{f.flag}</b>: {f.detail}
  </div>
))}
```

정제된 데이터를 보여주는 도구일수록 "이 부분은 확신 없다"는 신호를 감추기 쉬운데, 오히려 이걸 그대로 드러내는 쪽이 신뢰를 얻는 데 낫다고 판단했다. 데이터를 보는 사람이 어느 부분을 곧이곧대로 믿어도 되는지 스스로 판단할 수 있게 하는 게 목적이었다.

---

## 6. 정리

플로우차트는 "무슨 일이 어떤 순서로 일어나는가"를 보여주는 데는 강하지만, "누가 책임지는가", "뭐가 제일 급한가", "이 데이터를 얼마나 믿어도 되는가" 같은 질문에는 약하다. 상세 패널을 설계하면서 잡은 원칙은:

1. 청중마다 원하는 정보가 다르면, 한 화면에 다 넣지 말고 탭으로 쪼갠다
2. 점수 하나로 끝내지 않고, 등급 기준을 데이터(설정)로 분리해 코드 수정 없이 바뀔 수 있게 한다
3. 빈 값은 숨기고, 있는 정보만 보여준다
4. 스키마가 "하나 또는 여러 개"를 다 표현해야 하면, 프론트에서 항상 배열로 정규화해 로직을 하나로 합친다
5. 데이터의 불확실성은 감추지 않고 명시적으로 노출한다
