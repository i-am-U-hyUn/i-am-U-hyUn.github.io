## Q1. 관리형 NoSQL 데이터베이스 서비스

어떤 AWS 서비스가 관리형 NoSQL 데이터베이스입니까?

- A. Amazon Redshift
- B. Amazon DynamoDB
- C. Amazon Aurora
- D. Amazon RDS for MariaDB

**정답: B**

✅ **B. Amazon DynamoDB**: DynamoDB는 AWS의 완전 관리형 서버리스 NoSQL 키-값 및 문서 데이터베이스입니다. 어떤 규모에서도 고성능, 저지연 애플리케이션을 위해 설계되었으며 AWS가 하드웨어 프로비저닝, 설정 및 구성을 포함한 모든 인프라 관리를 처리합니다.

❌ **A. Amazon Redshift**: Redshift는 관리형 데이터 웨어하우스(SQL/관계형)이며 NoSQL 데이터베이스가 아닙니다. 분석 워크로드(OLAP)에 최적화되어 있습니다.

❌ **C. Amazon Aurora**: Aurora는 MySQL 및 PostgreSQL과 호환되는 완전 관리형 관계형(SQL) 데이터베이스 엔진이며 NoSQL 데이터베이스가 아닙니다.

❌ **D. Amazon RDS for MariaDB**: Amazon RDS for MariaDB는 관리형 관계형 SQL 데이터베이스이며 NoSQL 서비스가 아닙니다.

💡 **시험 꿀팁**: AWS에서 NoSQL = DynamoDB. 키-값/문서, 서버리스, 한 자릿수 밀리초 지연 시간, 완전 관리형. Redshift = 데이터 웨어하우스(SQL/OLAP). Aurora = 관계형(MySQL/PostgreSQL 호환).

## Q2. 청구 알람 생성에 사용해야 하는 AWS 서비스

청구 알람을 생성하는 데 어떤 AWS 서비스를 사용해야 합니까?

- A. AWS Trusted Advisor
- B. AWS CloudTrail
- C. Amazon CloudWatch
- D. Amazon QuickSight

**정답: C**

✅ **C. Amazon CloudWatch**: CloudWatch를 사용하면 예상 AWS 요금을 모니터링하여 청구 알람을 생성할 수 있습니다. 요금이 정의된 임계값을 초과하면 CloudWatch가 Amazon SNS를 통해 알림을 트리거하여 예상치 못한 비용을 방지합니다.

❌ **A. AWS Trusted Advisor**: Trusted Advisor는 비용, 보안, 내결함성, 성능 및 서비스 한도에 대한 모범 사례 권장 사항을 제공하지만 청구 알람을 생성하지 않습니다.

❌ **B. AWS CloudTrail**: CloudTrail은 감사 목적으로 API 호출 및 계정 활동을 기록합니다. 청구 알람 기능을 제공하지 않습니다.

❌ **D. Amazon QuickSight**: QuickSight는 비즈니스 인텔리전스(BI) 및 데이터 시각화 서비스입니다. 청구 알람 생성에는 사용하지 않습니다.

💡 **시험 꿀팁**: 청구 알람 = CloudWatch + SNS. 청구 알람을 생성하기 전에 계정의 청구 기본 설정에서 "청구 알림 받기"를 활성화해야 합니다. AWS Budgets를 통해서도 예산 알림을 설정할 수 있습니다.

## Q3. EC2에서 Docker 컨테이너를 실행할 때 AWS의 책임

회사가 Amazon EC2의 Docker 컨테이너에서 웹 애플리케이션을 호스팅하고 있습니다. 다음 중 AWS의 책임은 무엇입니까?

- A. Docker를 사용하여 개발된 웹 애플리케이션 및 서비스 확장
- B. 가용성을 유지하기 위해 클러스터에서 실행 중인 컨테이너 프로비저닝 또는 예약
- C. AWS 클라우드를 실행하는 AWS 시설에서 하드웨어 유지 관리 수행
- D. 업데이트 및 보안 패치를 포함한 게스트 운영 체제 관리

**정답: C**

✅ **C. AWS 클라우드를 실행하는 AWS 시설에서 하드웨어 유지 관리 수행**: AWS 공유 책임 모델에 따르면 AWS는 서버, 네트워킹 및 시설(데이터 센터)을 포함한 물리적 인프라의 보안 및 유지 관리를 담당합니다. 이 하드웨어 수준의 책임은 항상 AWS에 속합니다.

❌ **A. Docker를 사용하여 개발된 웹 애플리케이션 및 서비스 확장**: 애플리케이션 확장 로직은 고객의 책임입니다. 고객은 Auto Scaling 정책을 구성하고 컨테이너화된 앱이 확장되는 방식을 관리합니다.

❌ **B. 클러스터에서 실행 중인 컨테이너 프로비저닝 또는 예약**: 컨테이너 오케스트레이션 및 예약(예: ECS 작업 또는 Kubernetes 파드 관리)은 EC2 인스턴스에서 컨테이너를 실행할 때 고객의 책임입니다.

❌ **D. 게스트 운영 체제 관리(업데이트 및 보안 패치 포함)**: EC2를 사용할 때 고객은 보안 패치 및 업데이트 적용을 포함하여 게스트 OS를 관리할 책임이 있습니다.

💡 **시험 꿀팁**: 공유 책임 모델 — AWS는 "클라우드의 보안"(하드웨어, 물리적 시설, 글로벌 인프라)을 관리합니다. 고객은 "클라우드에서의 보안"(OS, 앱, 데이터, 네트워크 구성)을 관리합니다. EC2 = 고객이 OS를 관리합니다.

## Q4. 글로벌 웹사이트의 지연 시간 감소

전 세계 고객 기반을 갖춘 웹사이트에서 연결 시 지연 시간이 보고되고 있습니다. 고객 경험을 개선하고 지연 시간을 줄이는 AWS 서비스는 무엇입니까?

- A. Amazon CloudFront
- B. AWS Direct Connect
- C. Amazon EC2 Auto Scaling
- D. AWS Transit Gateway

**정답: A**

✅ **A. Amazon CloudFront**: CloudFront는 전 세계 엣지 로케이션에서 콘텐츠를 캐싱하여 최종 사용자와 더 가까운 위치에서 제공하는 AWS의 콘텐츠 전달 네트워크(CDN)입니다. 가장 가까운 엣지 로케이션에서 콘텐츠를 제공함으로써 전 세계 사용자의 지연 시간을 크게 줄입니다.

❌ **B. AWS Direct Connect**: Direct Connect는 온프레미스에서 AWS로의 전용 프라이빗 네트워크 연결을 제공합니다. 온프레미스에서 AWS로의 트래픽 지연 시간을 줄일 수 있지만, 전 세계 최종 사용자에게 웹사이트 콘텐츠를 더 빠르게 전달하는 데 도움이 되지 않습니다.

❌ **C. Amazon EC2 Auto Scaling**: Auto Scaling은 수요에 따라 EC2 인스턴스를 추가하거나 제거합니다. 용량 및 가용성을 다루며 지리적 지연 시간이 아닙니다.

❌ **D. AWS Transit Gateway**: Transit Gateway는 여러 VPC와 온프레미스 네트워크를 연결합니다. 내부 네트워크 간 트래픽 라우팅을 위한 네트워크 허브이며, 공용 콘텐츠에 접근하는 전 세계 사용자의 지연 시간을 줄이는 솔루션이 아닙니다.

💡 **시험 꿀팁**: 글로벌 지연 시간 감소 = CloudFront(CDN) + 엣지 로케이션. CloudFront는 전 세계적으로 정적/동적 콘텐츠를 캐싱합니다. 상태 확인을 기반으로 지역 엔드포인트로 라우팅하려면 AWS Global Accelerator(Anycast IP + AWS 백본)를 생각하세요.

## Q5. AWS IAM 모범 사례 (2개 선택)

다음 중 AWS IAM을 사용하는 데 있어 모범 사례를 나타내는 조치는 무엇입니까? (2개 선택)

- A. 강력한 비밀번호 정책 구성
- B. 동일한 리전의 AWS 계정 사용자 간에 보안 자격 증명 공유
- C. 액세스 키를 사용하여 AWS 관리 콘솔에 로그인
- D. 정기적으로 액세스 키 교체
- E. 권한 위임을 위해 IAM 역할 사용 지양

**정답: A, D**

✅ **A. 강력한 비밀번호 정책 구성**: 최소 길이, 복잡성, 만료 등을 포함한 강력한 비밀번호를 강제하는 것은 무차별 대입 또는 추측 공격을 통한 무단 접근으로부터 계정을 보호하는 기본적인 IAM 모범 사례입니다.

✅ **D. 정기적으로 액세스 키 교체**: 액세스 키를 정기적으로 교체하면 손상된 키가 무단 접근에 사용될 위험이 줄어듭니다. AWS는 일정에 따라 키를 교체하고 미사용 키를 제거할 것을 권장합니다.

❌ **B. 보안 자격 증명 공유**: 자격 증명 공유는 심각한 보안 위반입니다. 각 사용자는 고유한 자격 증명을 가져야 합니다. 공유하면 감사가 불가능해지고 노출 위험이 증가합니다.

❌ **C. 액세스 키를 사용하여 AWS 관리 콘솔에 로그인**: 액세스 키(액세스 키 ID + 시크릿 액세스 키)는 프로그래밍 방식 접근(CLI, SDK)에 사용되며, AWS 관리 콘솔 로그인에는 사용하지 않습니다. 콘솔 로그인에는 사용자 이름과 비밀번호를 사용합니다.

❌ **E. 권한 위임을 위해 IAM 역할 사용 지양**: 이것은 모범 사례의 반대입니다. IAM 역할은 장기 자격 증명 공유 없이 서비스, 애플리케이션 및 교차 계정 접근에 권한을 안전하게 위임하는 권장 방식입니다.

💡 **시험 꿀팁**: IAM 모범 사례 — 루트 및 IAM 사용자에 MFA 활성화, 자격 증명 공유 대신 역할 사용, 정기적으로 액세스 키 교체, 강력한 비밀번호 정책 강제, 최소 권한 적용, 일상적인 작업에 루트 절대 사용 금지.

## Q6. VPC 트래픽 정보를 캡처하는 AWS 기능

AWS VPC 인프라의 인바운드 및 아웃바운드 트래픽에 대한 정보를 캡처하는 데 사용할 수 있는 AWS 기능 또는 서비스는 무엇입니까?

- A. AWS Config
- B. VPC Flow Logs
- C. AWS Trusted Advisor
- D. AWS CloudTrail

**정답: B**

✅ **B. VPC Flow Logs**: VPC Flow Logs는 VPC의 네트워크 인터페이스를 드나드는 IP 트래픽에 대한 정보를 캡처합니다. 로그는 소스/대상 IP, 포트, 프로토콜 및 트래픽 수락 또는 거부 여부를 기록하여 네트워크 모니터링, 보안 분석 및 문제 해결에 유용합니다.

❌ **A. AWS Config**: AWS Config는 시간 경과에 따른 AWS 리소스의 구성을 기록하고 평가합니다. 네트워크 패킷/플로우 데이터를 캡처하지 않습니다.

❌ **C. AWS Trusted Advisor**: Trusted Advisor는 비용, 보안, 내결함성, 성능 및 서비스 한도에 대한 모범 사례를 확인합니다. 네트워크 트래픽을 캡처하지 않습니다.

❌ **D. AWS CloudTrail**: CloudTrail은 감사를 위해 AWS API 호출 및 관리 이벤트를 로그합니다. AWS 계정에서 "누가 무엇을 했는지"를 기록하며, 네트워크 수준 IP 트래픽 플로우는 기록하지 않습니다.

💡 **시험 꿀팁**: 네트워크 트래픽 캡처 = VPC Flow Logs. CloudWatch Logs 또는 S3에 저장됩니다. IP 수준 메타데이터를 캡처하지만 패킷 내용은 아닙니다. CloudTrail = API 호출 로그. Config = 리소스 구성 기록.

## Q7. 애플리케이션 엔드포인트 상태 모니터링 및 트래픽 라우팅 서비스

회사가 AWS 서비스를 사용하여 애플리케이션 엔드포인트의 상태를 모니터링하고 정상 리전 엔드포인트로 트래픽을 라우팅하여 애플리케이션 가용성을 개선하려 합니다. 이러한 요구 사항을 지원하는 서비스는 무엇입니까?

- A. Amazon Inspector
- B. Amazon CloudWatch
- C. AWS Global Accelerator
- D. Amazon CloudFront

**정답: C**

✅ **C. AWS Global Accelerator**: Global Accelerator는 애플리케이션 엔드포인트의 상태를 지속적으로 모니터링하고 AWS 글로벌 네트워크 백본을 사용하여 사용자 트래픽을 가장 가까운 정상 엔드포인트로 자동 라우팅합니다. 이를 통해 지연 시간을 줄이고 엔드포인트가 비정상 상태가 될 때 즉시 정상 리전으로 장애 조치하여 가용성을 향상시킵니다.

❌ **A. Amazon Inspector**: Inspector는 EC2 인스턴스 및 컨테이너 이미지를 위한 보안 취약점 평가 서비스입니다. 트래픽을 라우팅하거나 가용성을 위해 엔드포인트 상태를 모니터링하지 않습니다.

❌ **B. Amazon CloudWatch**: CloudWatch는 지표, 로그를 모니터링하고 알람을 설정합니다. 비정상 상태를 감지할 수 있지만 정상 리전 엔드포인트로 트래픽을 자동으로 라우팅하지 않습니다.

❌ **D. Amazon CloudFront**: CloudFront는 지연 시간을 줄이기 위해 엣지 로케이션에서 콘텐츠를 캐싱하는 CDN입니다. Global Accelerator와 같은 방식으로 여러 리전 엔드포인트에 걸쳐 활성 상태 기반 라우팅을 제공하지 않습니다.

💡 **시험 꿀팁**: AWS Global Accelerator = 상태 기반 라우팅 + Anycast 정적 IP + AWS 백본 네트워크. 정상 엔드포인트로 재라우팅하여 가용성을 향상시킵니다. CloudFront = 콘텐츠 캐싱/CDN. 둘 다 지연 시간을 줄이지만 사용 사례가 다릅니다.

## Q8. AWS Well-Architected Framework에서 안정성 달성을 위한 변경 관리 단계 (2개 선택)

AWS Well-Architected Framework에 따르면 AWS 클라우드에서 안정성을 달성하기 위해 어떤 변경 관리 단계를 수행해야 합니까? (2개 선택)

- A. AWS Config를 사용하여 AWS 리소스 인벤토리 만들기
- B. 서비스 한도를 사용하여 사용자가 AWS 리소스를 생성하거나 변경하지 못하도록 방지
- C. AWS CloudTrail을 사용하여 감사 가능한 로그 파일에 AWS API 호출 기록
- D. AWS Certificate Manager를 사용하여 승인된 AWS 리소스 및 서비스를 화이트리스트에 추가
- E. Amazon GuardDuty를 사용하여 AWS 리소스의 구성 변경 확인

**정답: A, C**

✅ **A. AWS Config를 사용하여 AWS 리소스 인벤토리 만들기**: AWS Config는 리소스 구성을 지속적으로 모니터링하고 기록하여 변경 사항을 추적하고, 규정 준수를 평가하고, 정확한 인벤토리를 유지할 수 있게 합니다. 이것은 안정성 기둥의 변경 관리에 필수적입니다.

✅ **C. AWS CloudTrail을 사용하여 감사 가능한 로그 파일에 AWS API 호출 기록**: CloudTrail은 누가 변경했는지, 언제, 어디서 했는지를 기록하는 완전한 API 호출 감사 추적을 제공합니다. 이것은 무단 또는 의도치 않은 변경을 탐지할 수 있게 해주므로 변경 관리에 매우 중요합니다.

❌ **B. 서비스 한도를 사용하여 사용자가 리소스를 생성하거나 변경하지 못하도록 방지**: 서비스 할당량(한도)은 변경 관리 도구가 아닙니다. 리소스 수를 제한하지만 변경 거버넌스를 강제하도록 설계되지 않았습니다.

❌ **D. AWS Certificate Manager를 사용하여 승인된 AWS 리소스 화이트리스트 추가**: AWS Certificate Manager(ACM)는 SSL/TLS 인증서를 관리합니다. 리소스 화이트리스트 또는 변경 관리에는 사용하지 않습니다.

❌ **E. Amazon GuardDuty를 사용하여 구성 변경 확인**: GuardDuty는 ML을 사용하여 의심스러운 활동을 식별하는 위협 탐지 서비스입니다. 구성 변경을 추적하지 않습니다. 그것은 Config의 역할입니다.

💡 **시험 꿀팁**: Well-Architected 안정성 기둥 변경 관리 = AWS Config(리소스 인벤토리 + 규정 준수) + AWS CloudTrail(API 감사 로그). Config는 "무엇이 변경되었는지"를 추적하고 CloudTrail은 "누가 변경했는지"를 추적합니다.

## Q9. 루트 사용자 로그인 이벤트 모니터링 서비스

AWS 계정 루트 사용자 AWS 관리 콘솔 로그인 이벤트를 모니터링하고 알림을 받는 데 사용할 수 있는 서비스는 무엇입니까?

- A. Amazon CloudWatch
- B. AWS Config
- C. AWS Trusted Advisor
- D. AWS IAM

**정답: A**

✅ **A. Amazon CloudWatch**: CloudTrail의 루트 사용자 로그인 이벤트를 감지하고 SNS 알림을 트리거하는 CloudWatch Events(EventBridge) 규칙을 생성할 수 있습니다. 이것이 루트 계정 콘솔 로그인을 모니터링하고 보안 팀에 알리는 AWS 권장 접근 방식입니다.

❌ **B. AWS Config**: Config는 AWS 리소스의 구성 변경을 추적합니다. 콘솔 로그인 이벤트를 직접 모니터링하거나 알림을 보내지 않습니다.

❌ **C. AWS Trusted Advisor**: Trusted Advisor는 모범 사례에 대한 권장 사항을 제공하지만 로그인 이벤트를 모니터링하거나 루트 사용자 로그인에 대한 실시간 알림을 보내지 않습니다.

❌ **D. AWS IAM**: IAM은 사용자, 역할 및 권한을 관리합니다. 로그인 이벤트를 위한 내장 이벤트 모니터링 또는 알림 기능이 없습니다.

💡 **시험 꿀팁**: 루트 사용자 로그인 모니터링 = CloudTrail(이벤트 기록) + CloudWatch Events/EventBridge(감지) + SNS(알림 전송). AWS Security Hub와 GuardDuty도 비정상적인 루트 사용을 감지할 수 있습니다.

## Q10. AWS 클라우드에서 설계 시 고려해야 할 설계 원칙

AWS 클라우드에서 설계할 때 고려해야 할 설계 원칙은 무엇입니까?

- A. 서버를 일회용 리소스로 취급
- B. 서비스의 동기식 통합 사용
- C. 느슨하게 결합된 컴포넌트 설계
- D. 보안 그룹에 최소한의 허용 규칙 구현

**정답: A**

✅ **A. 서버를 일회용 리소스로 취급**: 이것은 핵심 AWS 클라우드 설계 원칙입니다. 오래 실행되는 서버를 구성하는 대신 서버를 자동으로 종료하고 교체할 수 있도록 시스템을 설계해야 합니다. 이를 통해 자동화, 빠른 복구 및 불변 인프라 패턴을 가능하게 합니다.

❌ **B. 서비스의 동기식 통합 사용**: AWS 모범 사례는 비동기식, 느슨하게 결합된 통합(예: SQS, SNS, EventBridge 사용)을 선호합니다. 동기식 호출은 강한 의존성을 만들고 내결함성을 줄입니다.

❌ **C. 느슨하게 결합된 컴포넌트 설계**: 이것도 유효한 AWS 설계 원칙이지만, 이 문제의 단일 답변 버전에서는 "서버를 일회용으로 취급"이 가장 클라우드 네이티브한 답변입니다. 느슨한 결합도 맞지만 시험 버전에 따라 기대하는 단일 답변이 다를 수 있습니다.

❌ **D. 보안 그룹에 최소한의 허용 규칙 구현**: 이것은 보안 모범 사례(최소 권한)를 설명하지만 AWS Well-Architected Framework의 운영 설계 원칙에서 논의하는 기본 클라우드 설계 원칙 중 하나가 아닙니다.

💡 **시험 꿀팁**: AWS 클라우드 설계 원칙 — 일회용 리소스(가축, 애완동물 아님), 느슨한 결합, 장애를 위한 설계, 탄력성, 자동화, 데이터 기반 아키텍처. "서버를 가축으로, 애완동물이 아닌 것으로 취급" = 일회용/교체 가능으로 취급합니다.

## Q11. 온프레미스 데이터 센터에서 AWS로 데이터를 이동하는 서비스 (2개 선택)

온프레미스 데이터 센터에서 AWS로 데이터를 이동하는 데 사용할 수 있는 AWS 서비스는 무엇입니까? (2개 선택)

- A. AWS Snowball
- B. AWS Lambda
- C. AWS ElastiCache
- D. AWS Database Migration Service(AWS DMS)
- E. Amazon API Gateway

**정답: A, D**

✅ **A. AWS Snowball**: Snowball은 디바이스를 배송함으로써 대량의 데이터(페타바이트 규모)를 AWS로 이동할 수 있는 물리적 데이터 전송 디바이스입니다. 인터넷 대역폭이 데이터 마이그레이션에 충분하지 않거나 너무 느릴 때 이상적입니다.

✅ **D. AWS Database Migration Service(AWS DMS)**: AWS DMS는 온프레미스(또는 다른 클라우드 환경)에서 AWS로 데이터베이스를 마이그레이션합니다. 동종 및 이종 마이그레이션을 지원하며 다운타임을 최소화하기 위한 지속적인 복제를 처리할 수 있습니다.

❌ **B. AWS Lambda**: Lambda는 서버를 프로비저닝하거나 관리하지 않고 코드를 실행하는 서버리스 컴퓨팅 서비스입니다. 온프레미스에서 AWS로 데이터를 전송하지 않습니다.

❌ **C. AWS ElastiCache**: ElastiCache는 인메모리 캐싱 서비스(Redis/Memcached)입니다. 데이터 마이그레이션 또는 전송 서비스가 아닙니다.

❌ **E. Amazon API Gateway**: API Gateway는 API를 생성, 게시 및 관리합니다. 온프레미스 환경에서 AWS로 데이터를 전송하지 않습니다.

💡 **시험 꿀팁**: 데이터 마이그레이션 도구 — AWS Snowball/Snowmobile(물리적, 대규모), AWS DMS(데이터베이스 마이그레이션), AWS DataSync(온라인 파일 전송), Storage Gateway(하이브리드 스토리지). Lambda/ElastiCache/API Gateway는 컴퓨팅/캐시/API 도구이며 마이그레이션 도구가 아닙니다.

## Q12. 점점 늘어나는 배치 워크로드를 위한 최적 아키텍처

Amazon EC2의 배치 워크로드가 완료하는 데 5시간이 걸립니다. 처리할 데이터 양은 매달 두 배가 되고 처리 시간도 비례하여 증가합니다. 이 지속적으로 증가하는 수요를 해결하기 위한 최적의 클라우드 아키텍처는 무엇입니까?

- A. 더 큰 EC2 인스턴스 크기에서 애플리케이션 실행
- B. 배치 요구 사항에 더 적합한 EC2 인스턴스 패밀리로 전환
- C. 여러 EC2 인스턴스에 애플리케이션을 분산하고 병렬로 실행
- D. 베어 메탈 EC2 인스턴스에서 애플리케이션 실행

**정답: C**

✅ **C. 여러 EC2 인스턴스에 애플리케이션을 분산하고 병렬로 실행**: 수평 확장(여러 인스턴스에서 워크로드를 병렬로 실행)은 최적의 클라우드 네이티브 접근 방식입니다. 데이터가 매달 두 배가 됨에 따라 더 많은 인스턴스를 추가하면 처리 시간이 비례하여 증가하는 대신 일정하게 유지됩니다. 이것은 비용 효율적이며 클라우드 탄력성 원칙을 따릅니다.

❌ **A. 더 큰 EC2 인스턴스 크기에서 애플리케이션 실행**: 수직 확장(스케일 업)에는 한계가 있으며 점점 더 비싸집니다. 데이터가 계속 두 배가 되면 결국 가장 큰 인스턴스 크기에 도달하여 장기적으로 지속 불가능합니다.

❌ **B. 배치 요구 사항에 더 적합한 EC2 인스턴스 패밀리로 전환**: 더 적절한 인스턴스 패밀리(예: 컴퓨팅 최적화)를 선택하는 것은 유효한 최적화이지만 지속적으로 두 배로 증가하는 데이터의 근본적인 문제를 해결하지 못합니다. 처리 시간은 여전히 비례하여 증가할 것입니다.

❌ **D. 베어 메탈 EC2 인스턴스에서 애플리케이션 실행**: 베어 메탈 인스턴스는 특수한 요구 사항을 위한 직접 하드웨어 접근을 제공하지만 확장 문제를 본질적으로 해결하지 못합니다. 데이터 볼륨이 두 배가 됨에 따라 처리 시간은 여전히 증가할 것입니다.

💡 **시험 꿀팁**: 수평 확장(스케일 아웃) = 여러 인스턴스에 분산 + 병렬 실행. 이것은 탄력적이고 비용 효율적이며 실질적인 상한이 없기 때문에 배치 워크로드에 대한 수직 확장(스케일 업)보다 선호됩니다. AWS Batch 또는 EC2 + 병렬 처리를 생각하세요.

## Q13. 부서 거버넌스 중앙화 및 결제 통합

각 부서에 독립적인 AWS 계정과 결제 방법이 있습니다. 새 기업 리더십이 부서 거버넌스를 중앙화하고 결제를 통합하려 합니다. AWS 서비스 및 기능을 사용하여 이를 어떻게 달성할 수 있습니까?

- A. 각 계정의 월별 청구서를 전달한 다음 IAM 역할을 생성하여 교차 계정 접근 허용
- B. 새 AWS 계정을 생성한 다음 AWS Organizations를 구성하고 모든 기존 계정을 초대하여 가입
- C. 각 기존 계정에서 AWS Organizations를 구성한 다음 모든 계정을 연결
- D. Cost Explorer를 사용하여 모든 계정의 비용을 결합한 다음 IAM 정책을 계정 전체에 복제

**정답: B**

✅ **B. 새 AWS 계정을 생성한 다음 AWS Organizations를 구성하고 모든 기존 계정을 초대하여 가입**: AWS Organizations는 거버넌스 중앙화 및 청구 통합을 위한 올바른 서비스입니다. 관리(마스터) 계정을 생성하고 AWS Organizations를 설정하고 기존 멤버 계정을 초대합니다. Organizations의 통합 청구는 모든 계정을 단일 결제로 결합하고, 서비스 제어 정책(SCP)은 중앙화된 거버넌스를 가능하게 합니다.

❌ **A. 청구서 전달 후 교차 계정 접근을 위한 IAM 역할 생성**: 수동으로 청구서를 전달하는 것은 통합 청구가 아니며, 교차 계정 접근을 위한 IAM 역할은 조직 수준에서 중앙화된 거버넌스 또는 결제 통합을 다루지 않습니다.

❌ **C. 각 기존 계정에서 AWS Organizations 구성 후 연결**: AWS Organizations는 단일 관리 계정에서 관리됩니다. 각 계정에서 구성하고 연결할 수 없습니다. 모든 멤버 계정을 관리하는 하나의 관리 계정이 있습니다.

❌ **D. Cost Explorer로 모든 계정의 비용을 결합 후 IAM 정책 복제**: Cost Explorer는 비용 가시성을 제공하지만 실제 청구를 통합하지 않습니다. IAM 정책을 수동으로 복제하는 것은 오류가 발생하기 쉽고 중앙 거버넌스를 제공하지 않습니다.

💡 **시험 꿀팁**: 다중 계정 거버넌스 = AWS Organizations. 핵심 기능: 통합 청구(단일 결제), 거버넌스를 위한 서비스 제어 정책(SCP), 그룹화를 위한 조직 단위(OU). 관리 계정이 멤버 계정을 초대하며, 반대 방향이 아닙니다.

## Q14. AWS 클라우드 가치 제안에서 수평 확장의 예

수요에 따라 Amazon EC2 인스턴스를 수평으로 확장하는 능력은 AWS 클라우드 가치 제안에서 어떤 개념의 예입니까?

- A. 규모의 경제
- B. 탄력성
- C. 고가용성
- D. 민첩성

**정답: B**

✅ **B. 탄력성**: 탄력성은 수요에 맞게 리소스를 자동으로 확장하거나 축소하는 능력입니다. EC2 인스턴스의 수평 확장(수요가 증가할 때 인스턴스를 추가하고 수요가 감소할 때 제거)은 클라우드 탄력성의 교과서적 정의입니다.

❌ **A. 규모의 경제**: 규모의 경제는 AWS가 수백만 명의 고객에게 인프라 비용을 분산시킴으로써 더 낮은 가격을 제공하는 능력을 의미합니다. 비용 절감에 관한 것이지 리소스를 확장하는 능력에 관한 것이 아닙니다.

❌ **C. 고가용성**: 고가용성은 장애에도 불구하고 운영을 유지하도록 시스템을 설계하는 것을 의미하며, 일반적으로 여러 AZ에 걸쳐 중복성을 사용합니다. 확장 자체가 가용성에 기여할 수 있지만, 확장 행위 자체는 탄력성입니다.

❌ **D. 민첩성**: 민첩성은 조직이 혁신할 수 있는 속도(수 분 내에 리소스 프로비저닝, 빠른 실험, 시장 출시 속도)를 의미합니다. 수평 확장은 특히 탄력성이며 민첩성이 아닙니다.

💡 **시험 꿀팁**: 탄력성 = 수요에 따라 자동으로 확장/축소. 민첩성 = 혁신/배포 속도. 규모의 경제 = AWS의 방대한 구매력으로 인한 낮은 비용. 고가용성 = 다중 AZ, 내결함성, 중복성.

## Q15. 다가오는 쇼핑 시즌에 트래픽 급증에 대비하는 서비스

e-commerce 회사가 곧 다가올 인기 쇼핑 시즌 두 번에 웹 트래픽이 크게 증가할 것으로 예상합니다. 이 수요 변화에 맞게 리소스를 동적으로 조정하도록 구성할 수 있는 AWS 서비스 또는 기능은 무엇입니까?

- A. AWS CloudTrail
- B. Amazon EC2 Auto Scaling
- C. Amazon Forecast
- D. AWS Config

**정답: B**

✅ **B. Amazon EC2 Auto Scaling**: EC2 Auto Scaling은 정의된 확장 정책(예: 목표 추적, 예약된 확장 또는 단계별 확장)에 따라 EC2 인스턴스를 자동으로 추가하거나 제거합니다. 쇼핑 시즌과 같이 예측 가능한 급증의 경우 트래픽 급증 전에 사전에 용량을 추가하는 예약된 확장 작업을 설정할 수 있습니다.

❌ **A. AWS CloudTrail**: CloudTrail은 감사를 위해 API 호출을 기록합니다. 수요에 따라 인프라 리소스를 조정하지 않습니다.

❌ **C. Amazon Forecast**: Amazon Forecast는 시계열 수요 예측을 위한 기계 학습 서비스입니다. 수요를 예측할 수 있지만 리소스를 직접 확장하지 않습니다. 예측을 제공하지만 자동화된 확장이 아닙니다.

❌ **D. AWS Config**: AWS Config는 규정 준수를 위한 리소스 구성을 기록하고 평가합니다. 트래픽에 따라 리소스를 동적으로 확장하지 않습니다.

💡 **시험 꿀팁**: 동적 확장 = EC2 Auto Scaling. 유형: 예약됨(예측 가능한 부하), 목표 추적(CPU 50%와 같은 지표 유지), 단계별 확장(지표가 임계값을 초과할 때 X 인스턴스 추가). 확장된 인스턴스로 트래픽을 분산하기 위해 Elastic Load Balancing과 함께 작동합니다.

## Q16. 공용 인터넷을 통해 AWS 리소스에 안전하게 연결하는 서비스

어떤 AWS 서비스를 사용하면 공용 인터넷을 통해 AWS 리소스에 안전하게 연결할 수 있습니까?

- A. Amazon VPC 피어링
- B. AWS Direct Connect
- C. AWS VPN
- D. Amazon Pinpoint

**정답: C**

✅ **C. AWS VPN**: AWS 가상 사설망(VPN)은 온프레미스 네트워크(또는 클라이언트 디바이스)와 AWS VPC 간에 공용 인터넷을 통해 암호화된 보안 터널을 만듭니다. 전용 물리적 연결 없이 보안 연결을 제공합니다.

❌ **A. Amazon VPC 피어링**: VPC 피어링은 AWS 네트워크 내에서 두 VPC를 프라이빗으로 연결합니다. AWS 외부에서 공용 인터넷을 통한 연결을 제공하지 않습니다. 두 VPC 모두 AWS 내에 있어야 합니다.

❌ **B. AWS Direct Connect**: Direct Connect는 온프레미스 데이터 센터와 AWS 간에 전용 프라이빗 네트워크 연결을 설정하여 공용 인터넷을 완전히 우회합니다. "공용 인터넷을 통한" 솔루션이 아닙니다.

❌ **D. Amazon Pinpoint**: Pinpoint는 고객 참여 및 마케팅 통신 서비스(이메일, SMS, 푸시 알림)입니다. 네트워크 연결 서비스가 아닙니다.

💡 **시험 꿀팁**: 인터넷을 통한 AWS에 대한 보안 연결 = AWS VPN(공용 인터넷을 통한 암호화 터널). 전용 프라이빗 연결 = AWS Direct Connect(인터넷 완전 우회). VPC 피어링 = AWS 내 VPC 간. 사이트 간 VPN vs. 클라이언트 VPN: 사이트 간은 온프레미스 네트워크를 연결하고 클라이언트 VPN은 개별 사용자를 연결합니다.

## Q17. AWS 지출을 예측하는 도구

AWS 지출을 예측하는 데 사용하는 도구는 무엇입니까?

- A. AWS Trusted Advisor
- B. AWS Organizations
- C. Cost Explorer
- D. Amazon Inspector

**정답: C**

✅ **C. Cost Explorer**: AWS Cost Explorer는 AWS의 과거 지출 및 사용량을 상세하게 시각화하고 과거 추세를 기반으로 미래 비용을 예측하는 예측 기능을 포함합니다. 지출 패턴을 이해하고 예산을 계획하는 데 도움이 됩니다.

❌ **A. AWS Trusted Advisor**: Trusted Advisor는 모범 사례에 대한 AWS 환경을 확인하고 일부 비용 최적화 제안을 포함한 권장 사항을 제공합니다. 하지만 미래의 AWS 지출을 예측하지 않습니다.

❌ **B. AWS Organizations**: AWS Organizations는 통합 청구로 여러 AWS 계정을 중앙에서 관리합니다. 지출 예측을 제공하지 않습니다.

❌ **D. Amazon Inspector**: Inspector는 EC2 및 컨테이너를 위한 자동화된 보안 취약점 평가 서비스입니다. 비용 예측 기능이 없습니다.

💡 **시험 꿀팁**: 비용 예측 = Cost Explorer(과거 분석 + 예측). 비용 예산 = AWS Budgets(임계값 설정 + 알림). 비용 최적화 권장 사항 = Trusted Advisor + Cost Explorer 적절한 크기 조정. 비용 분류 = 상세 분석을 위한 비용 및 사용 보고서(CUR).

## Q18. 글로벌 사용자를 위해 정적 콘텐츠를 더 가까이 캐싱하는 서비스

회사가 유럽에 호스팅된 e-commerce 애플리케이션을 실행합니다. 전 세계 다른 지역에서 웹사이트에 접근하는 사용자의 지연 시간을 줄이기 위해 자주 접근하는 정적 콘텐츠를 사용자와 더 가까운 위치에 캐싱하려 합니다. 이 요구 사항을 지원하는 AWS 서비스는 무엇입니까?

- A. Amazon ElastiCache
- B. Amazon CloudFront
- C. Amazon Elastic File System(Amazon EFS)
- D. Amazon Elastic Block Store(Amazon EBS)

**정답: B**

✅ **B. Amazon CloudFront**: CloudFront는 전 세계 400개 이상의 엣지 로케이션이 있는 AWS의 글로벌 콘텐츠 전달 네트워크(CDN)입니다. 최종 사용자와 가장 가까운 엣지 로케이션에서 정적 콘텐츠(이미지, CSS, JavaScript, 동영상)를 캐싱하여 원본 서버가 어디에 호스팅되든 전 세계 방문자의 지연 시간을 크게 줄입니다.

❌ **A. Amazon ElastiCache**: ElastiCache는 데이터베이스 쿼리 결과 또는 세션 데이터를 캐싱하기 위해 VPC 내에 배포된 인메모리 캐싱 서비스(Redis 또는 Memcached)입니다. 엣지 로케이션에서 전 세계 최종 사용자에게 콘텐츠를 배포하지 않습니다.

❌ **C. Amazon Elastic File System(Amazon EFS)**: EFS는 AWS 내의 EC2 인스턴스를 위한 관리형 네트워크 파일 시스템입니다. 공유 스토리지 솔루션이지 전 세계 사용자를 위한 CDN 또는 콘텐츠 전달 메커니즘이 아닙니다.

❌ **D. Amazon Elastic Block Store(Amazon EBS)**: EBS는 개별 EC2 인스턴스에 연결된 블록 스토리지 볼륨을 제공합니다. 로컬 영구 스토리지이며 전 세계 사용자에게 콘텐츠를 캐싱하거나 전달할 수 없습니다.

💡 **시험 꿀팁**: 글로벌 정적 콘텐츠 캐싱 = CloudFront(CDN + 엣지 로케이션). ElastiCache = VPC 내 데이터베이스/세션 캐싱. EFS = AWS 내 공유 파일 스토리지. EBS = 단일 EC2 인스턴스에 연결된 블록 스토리지. 질문에 "전 세계 사용자" + "캐시" + "지연 시간"이 언급되면 답은 거의 항상 CloudFront입니다.

## Q19. AWS 글로벌 인프라의 구성 요소

다음 중 AWS 글로벌 인프라의 구성 요소는 무엇입니까?

- A. Amazon Alexa
- B. AWS 리전
- C. Amazon Ray
- D. AWS Organizations

**정답: B**

✅ **B. AWS 리전**: AWS 리전은 AWS가 데이터 센터를 클러스터하는 전 세계의 지리적으로 구별된 위치입니다. 각 리전은 여러 가용 영역(AZ)으로 구성되며 엣지 로케이션 및 로컬 존도 포함하는 AWS 글로벌 인프라의 기본 구성 요소입니다.

❌ **A. Amazon Alexa**: Amazon Alexa는 음성 어시스턴트 서비스/플랫폼입니다. AWS 제품/서비스이지 글로벌 인프라 자체의 구성 요소가 아닙니다.

❌ **C. Amazon Ray**: "Amazon Ray"는 실제 AWS 서비스가 아닙니다. AWS 글로벌 인프라의 구성 요소가 아닙니다.

❌ **D. AWS Organizations**: AWS Organizations는 여러 AWS 계정을 통합하는 데 도움이 되는 계정 관리 서비스입니다. AWS 서비스이지 물리적 인프라 구성 요소가 아닙니다.

💡 **시험 꿀팁**: AWS 글로벌 인프라 구성 요소 = 리전 + 가용 영역(AZ) + 엣지 로케이션(CloudFront PoP) + 로컬 존 + 웨이브렝스 존. 리전에는 2개 이상의 AZ가 포함됩니다. AZ는 리전 내의 별도 데이터 센터입니다. 엣지 로케이션은 CloudFront CDN 트래픽을 제공합니다.

## Q20. EC2 인스턴스의 CPU 용량이 충분한지 확인하는 서비스

어떤 AWS 서비스가 사용자가 애플리케이션을 실행하는 Amazon EC2 인스턴스의 CPU 용량이 충분한지 확인하는 데 도움이 됩니까?

- A. Amazon CloudWatch
- B. AWS Config
- C. AWS CloudTrail
- D. Amazon Inspector

**정답: A**

✅ **A. Amazon CloudWatch**: CloudWatch는 EC2 CPU 사용률(CPUUtilization 지표)을 포함하여 AWS 리소스에 대한 지표를 수집하고 모니터링합니다. CPU 사용량 그래프를 보고, CPU가 임계값을 초과할 때 알람을 설정하고, 이 데이터를 사용하여 인스턴스가 과소 프로비저닝되어 있는지 과잉 프로비저닝되어 있는지 확인할 수 있습니다.

❌ **B. AWS Config**: AWS Config는 AWS 리소스의 구성 변경 사항을 기록하고 규정 준수 여부를 평가합니다. CPU 사용률과 같은 실시간 성능 지표를 모니터링하지 않습니다.

❌ **C. AWS CloudTrail**: CloudTrail은 감사 목적으로 API 호출 및 계정 활동을 기록합니다. 관리 수준 이벤트(누가 무엇을 했는지)를 추적하지 않으며, 애플리케이션 또는 인프라 성능 지표는 추적하지 않습니다.

❌ **D. Amazon Inspector**: Inspector는 EC2 인스턴스 및 컨테이너 이미지에서 취약점과 의도하지 않은 네트워크 노출을 확인하는 보안 평가 서비스입니다. CPU 용량이나 성능 지표를 모니터링하지 않습니다.

💡 **시험 꿀팁**: EC2 성능 모니터링 = Amazon CloudWatch. 주요 EC2 지표: CPUUtilization, NetworkIn/Out, DiskReadOps/WriteOps, StatusCheckFailed. 메모리 및 디스크 지표(기본적으로 이용 불가)의 경우 EC2 인스턴스에 CloudWatch 에이전트를 설치하세요. CloudWatch 알람은 Auto Scaling 또는 SNS 알림을 트리거할 수 있습니다.
