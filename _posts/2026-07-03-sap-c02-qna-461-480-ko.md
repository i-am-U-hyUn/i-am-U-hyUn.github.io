## QUESTION 461

**문제**: 회사가 여러 계정에 걸쳐 EC2 인스턴스를 실행 중인데, 특정 소프트웨어 라이선스 규정상 인스턴스가 물리적으로 어느 국가/리전에서 실행되는지 **암호학적으로 증명 가능한 방식**으로 확인해야 한다. 단순히 리전 설정값을 신뢰하는 것이 아니라 하드웨어 수준에서 검증하고 싶다. 솔루션은?

**보기**
- A. 인스턴스의 리전 태그와 메타데이터만 확인(태그나 메타데이터는 소프트웨어적으로 설정되는 값이라 위변조 가능성이 있어 "암호학적으로 증명 가능"이라는 엄격한 요구를 충족하지 못함).
- B. **AWS Nitro 시스템 기반 인스턴스에서 제공하는 첨부 증명(attestation) 기능을 활용해, 인스턴스가 실행 중인 Nitro 하드웨어의 암호학적 증명서를 통해 물리적 실행 위치를 포함한 신뢰할 수 있는 하드웨어 근원(root of trust) 정보를 검증.**
- C. CloudTrail 로그에서 인스턴스 시작 시 지정된 리전 파라미터만 확인(CloudTrail은 API 호출 시 사용자가 지정한 리전 파라미터를 기록할 뿐이며, 이것이 실제 물리적 실행 위치를 암호학적으로 증명하지는 않음).
- D. 각 리전에 있는 온프레미스 검증 서버로 인스턴스가 직접 접속해 위치를 스스로 보고하도록 구현(인스턴스 자체가 자신의 위치를 보고하는 방식은 소프트웨어 계층의 자기 보고이며, 하드웨어 수준의 암호학적 증명이 아님).

**정답: B**

**해설**
**AWS Nitro 시스템**은 하드웨어 기반 보안 모델을 사용하며, Nitro 카드와 Nitro 보안 칩을 통해 인스턴스가 실행되는 하드웨어에 대한 **암호학적 증명(attestation)** 체계를 제공합니다(Nitro Enclaves의 증명 기능이 대표적 사례). 이를 통해 소프트웨어 계층의 설정값(태그, 메타데이터)을 신뢰하는 것이 아니라, 하드웨어 근원(root of trust)에 기반한 신뢰할 수 있는 검증을 수행할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 태그/메타데이터는 소프트웨어적으로 설정되는 값이라 위변조 가능하며 암호학적 증명이 아닙니다.
- C: CloudTrail은 API 호출 파라미터를 기록할 뿐 물리적 실행 위치의 하드웨어 수준 증명을 제공하지 않습니다.
- D: 인스턴스의 자기 보고는 소프트웨어 계층의 신뢰에 의존하며 하드웨어 기반 증명과는 다릅니다.

> 💡 **시험 꿀팁**: 인스턴스의 물리적 실행 환경을 **암호학적으로, 하드웨어 수준에서 증명**해야 한다면 **AWS Nitro 시스템의 증명(attestation)** 기반 검증이 표준 정답입니다.

## QUESTION 462

**문제**: 회사가 여러 AWS 계정에서 실행 중인 EC2 인스턴스의 소프트웨어 인벤토리(설치된 애플리케이션, 버전)를 중앙에서 조회하고, 특정 소프트웨어(예: 취약점이 있는 특정 라이브러리 버전)가 설치된 모든 인스턴스를 신속하게 찾고 싶다. 각 인스턴스에 개별 접속해 확인하지 않고 이를 수행하려면?

**보기**
- A. 각 인스턴스에 SSH로 접속해 설치된 패키지 목록을 수동으로 확인(수백~수천 대 규모에서 수동 확인은 매우 비효율적이고 시간이 오래 걸림).
- B. **AWS Systems Manager 인벤토리(Inventory) 기능을 사용해, SSM 에이전트를 통해 각 인스턴스의 설치된 애플리케이션/버전 정보를 자동으로 수집하고, Systems Manager 콘솔이나 Athena 쿼리로 특정 소프트웨어가 설치된 인스턴스를 중앙에서 신속하게 검색.**
- C. Config 규칙으로 설치된 소프트웨어 목록을 추적(Config는 주로 AWS 리소스의 구성 상태를 추적하며, 인스턴스 내부에 설치된 애플리케이션 인벤토리 수집에는 SSM Inventory가 전용 기능).
- D. Trusted Advisor로 소프트웨어 인벤토리 확인(Trusted Advisor는 일반적인 모범 사례 검사를 제공하며 인스턴스 내부의 상세 소프트웨어 인벤토리 수집 기능은 제공하지 않음).

**정답: B**

**해설**
**AWS Systems Manager 인벤토리**는 SSM 에이전트가 설치된 인스턴스로부터 애플리케이션, 파일, 네트워크 구성 등의 메타데이터를 자동으로 수집해 중앙에서 조회할 수 있게 해주는 기능입니다. 수집된 인벤토리 데이터는 콘솔에서 직접 검색하거나 S3로 내보내 Athena로 쿼리할 수 있어, 특정 취약한 라이브러리 버전이 설치된 모든 인스턴스를 여러 계정에 걸쳐 신속하게 식별할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 대규모 환경에서 수동 개별 확인은 매우 비효율적입니다.
- C: Config는 AWS 리소스 구성 추적에 중점을 두며, 인스턴스 내부 소프트웨어 인벤토리는 SSM Inventory의 전용 영역입니다.
- D: Trusted Advisor는 일반 모범 사례 검사 도구이며 상세 소프트웨어 인벤토리 수집 기능이 없습니다.

> 💡 **시험 꿀팁**: 다수의 EC2 인스턴스에 대해 **설치된 소프트웨어 인벤토리를 중앙에서 수집/검색**하려면 **AWS Systems Manager 인벤토리(Inventory)**가 표준 정답입니다.

## QUESTION 463

**문제**: 회사가 Amazon MQ(ActiveMQ 엔진)를 사용해 레거시 JMS 기반 애플리케이션과 메시징을 처리하는데, 브로커 인스턴스에 장애가 발생해도 메시지 손실 없이 자동으로 장애 조치되기를 원하며, 액티브-스탠바이 방식보다 더 높은 가용성(여러 노드가 동시에 활성 상태)을 원한다. 솔루션은?

**보기**
- A. Amazon MQ의 액티브/스탠바이 브로커만 사용(액티브/스탠바이는 한 번에 하나의 브로커만 활성 상태이며, 이 문제가 원하는 "여러 노드가 동시에 활성 상태"인 더 높은 가용성 구성과는 다름).
- B. **Amazon MQ for RabbitMQ의 클러스터 배포(cluster deployment)를 사용해, 여러 브로커 노드가 동시에 활성 상태로 동작하는 클러스터를 구성(단, 애플리케이션이 RabbitMQ 프로토콜과 호환되어야 함을 전제).**
- C. 단일 브로커 인스턴스를 사용하고 정기적으로 스냅샷 백업(단일 브로커는 장애 시 자동 장애 조치 자체가 없으며 스냅샷 복원은 다운타임과 메시지 유실 위험이 있음).
- D. 브로커 앞에 ALB를 두어 여러 독립적인 브로커 인스턴스로 라우팅(메시지 브로커는 일반적인 무상태 웹 서버와 달리 상태(큐, 메시지)를 가지므로, ALB로 여러 독립 브로커에 단순히 트래픽을 분산하는 것은 메시지 정합성과 순서를 보장하지 못함).

**정답: B**

**해설**
Amazon MQ는 ActiveMQ와 RabbitMQ 두 엔진을 지원하며, 이 중 **Amazon MQ for RabbitMQ의 클러스터 배포**는 여러 브로커 노드가 **동시에 활성 상태**로 동작하는 클러스터를 구성할 수 있어, 하나의 브로커에만 장애가 발생해도 나머지 노드들이 계속 트래픽을 처리하는 더 높은 수준의 가용성을 제공합니다(ActiveMQ 엔진은 액티브/스탠바이 방식 중심). 다만 이는 애플리케이션이 RabbitMQ 프로토콜(AMQP 등)과 호환되어야 한다는 조건이 있습니다.

**왜 다른 보기는 오답인가**
- A: 액티브/스탠바이는 한 번에 하나만 활성 상태라 이 문제가 원하는 다중 활성 노드 구성과 다릅니다.
- C: 단일 브로커는 자동 장애 조치가 없고 스냅샷 복원은 다운타임/유실 위험이 있습니다.
- D: 메시지 브로커는 상태를 가지므로 단순 ALB 분산으로는 메시지 정합성/순서를 보장할 수 없습니다.

> 💡 **시험 꿀팁**: 메시지 브로커에서 **여러 노드가 동시에 활성 상태인 고가용성 클러스터**가 필요하면 **Amazon MQ for RabbitMQ의 클러스터 배포**가 표준 정답입니다(RabbitMQ 프로토콜 호환 전제).

## QUESTION 464

**문제**: 회사가 EKS 클러스터에서 특정 네임스페이스의 파드가 다른 네임스페이스의 파드와 통신하지 못하도록 네트워크 정책을 시행하고 싶다. 기본 Amazon VPC CNI 플러그인은 파드에 VPC IP를 직접 할당하지만, 표준 Kubernetes NetworkPolicy 시행을 위한 별도 구성이 필요하다는 것을 알게 되었다. 솔루션은?

**보기**
- A. 각 네임스페이스를 별도 서브넷으로 분리하고 서브넷 간 NACL로 통제(Kubernetes 파드는 서브넷 경계와 무관하게 스케줄링되며, 네임스페이스 단위로 서브넷을 물리적으로 분리하는 것은 Kubernetes의 네트워크 정책 모델과 맞지 않고 실용적이지도 않음).
- B. **Amazon VPC CNI 플러그인에서 네트워크 정책 기능을 활성화(NetworkPolicy controller 구성)해, 표준 Kubernetes NetworkPolicy 리소스를 정의함으로써 네임스페이스/파드 간 트래픽을 세밀하게 제어.**
- C. 서드파티 CNI 플러그인(Calico 등)으로 전체 교체(가능한 방법이지만, 최근 Amazon VPC CNI 자체가 네트워크 정책 기능을 네이티브로 지원하므로, 이미 VPC CNI를 사용 중이라면 전체 교체보다 네이티브 기능 활성화가 더 간단하고 표준적임).
- D. 각 파드에 개별 보안 그룹을 수동으로 할당해 관리(파드별 보안 그룹 할당(Security Groups for Pods)은 가능한 기능이지만, 네임스페이스 간 포괄적인 Kubernetes 네이티브 정책 시행이라는 목적에는 NetworkPolicy가 더 적합하고 관리도 간단함).

**정답: B**

**해설**
Amazon VPC CNI 플러그인은 네트워크 정책 기능을 **네이티브로 지원**하며, 이를 활성화하면 표준 **Kubernetes NetworkPolicy** 리소스(예: 특정 네임스페이스 라벨을 가진 파드로부터의 인그레스만 허용)를 정의해 네임스페이스/파드 간 트래픽을 세밀하게 제어할 수 있습니다. 이는 서드파티 CNI로 전체 교체하지 않고도 EKS에서 표준 Kubernetes 방식의 네트워크 격리를 구현하는 가장 간단하고 표준적인 방법입니다.

**왜 다른 보기는 오답인가**
- A: 파드는 서브넷 경계와 무관하게 스케줄링되어 네임스페이스별 서브넷 분리는 실용적이지 않습니다.
- C: 서드파티 CNI 전체 교체는 가능하지만, VPC CNI가 이미 네이티브로 정책 기능을 지원하므로 불필요한 전환입니다.
- D: 파드별 보안 그룹은 가능한 대안이지만, 네임스페이스 간 정책 시행에는 표준 NetworkPolicy가 더 직접적입니다.

> 💡 **시험 꿀팁**: EKS에서 **표준 Kubernetes NetworkPolicy로 네임스페이스/파드 간 트래픽을 제어**하려면 **Amazon VPC CNI의 네트워크 정책 기능 활성화**가 표준 정답입니다.

## QUESTION 465

**문제**: 회사가 온프레미스에서 실행 중인 레거시 애플리케이션이 특정 하드웨어 보안 모듈(HSM)의 PKCS#11 인터페이스에 의존해 암호화 연산을 수행하는데, 이를 AWS로 마이그레이션하면서 애플리케이션 코드(PKCS#11 호출 방식)를 변경하지 않고 그대로 유지하고 싶다. 솔루션은?

**보기**
- A. AWS KMS로 전환하고 애플리케이션 코드를 KMS API 호출 방식으로 재작성(KMS는 강력한 관리형 키 서비스이지만 PKCS#11 인터페이스를 네이티브로 지원하지 않아 애플리케이션 코드의 대대적인 재작성이 필요 — "코드 변경 없이"라는 요구에 반함).
- B. **AWS CloudHSM을 사용해, CloudHSM이 제공하는 PKCS#11 라이브러리를 통해 기존 애플리케이션이 코드 변경 없이 그대로 표준 PKCS#11 인터페이스로 CloudHSM의 하드웨어 보안 모듈과 통신하도록 구성.**
- C. Secrets Manager에 암호화 키를 저장하고 애플리케이션이 API로 조회하도록 재작성(Secrets Manager는 시크릿 저장/조회 서비스이며 PKCS#11 표준 인터페이스를 제공하지 않아 코드 재작성이 필요).
- D. 온프레미스 HSM을 그대로 유지하고 VPN으로 애플리케이션 서버만 AWS로 이전(온프레미스 HSM 유지는 완전한 AWS 마이그레이션이라는 목표에 부합하지 않으며 하이브리드 복잡성을 증가시킴).

**정답: B**

**해설**
**AWS CloudHSM**은 업계 표준 **PKCS#11**, Java Cryptography Extension(JCE), Microsoft CryptoNG(CNG) 같은 표준 암호화 인터페이스를 지원하는 라이브러리를 제공합니다. PKCS#11에 의존하는 기존 온프레미스 애플리케이션은 CloudHSM이 제공하는 PKCS#11 라이브러리로 연결 설정만 변경하면, 애플리케이션의 암호화 호출 코드 자체는 변경 없이 그대로 CloudHSM의 전용 하드웨어 보안 모듈을 사용할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: KMS는 PKCS#11 표준 인터페이스를 네이티브로 지원하지 않아 코드 재작성이 필요합니다.
- C: Secrets Manager는 PKCS#11 인터페이스가 아닌 자체 API를 사용해 코드 변경이 필요합니다.
- D: 온프레미스 HSM 유지는 완전한 마이그레이션 목표에 부합하지 않습니다.

> 💡 **시험 꿀팁**: **PKCS#11 인터페이스에 의존하는 레거시 애플리케이션**을 코드 변경 없이 AWS로 마이그레이션하려면 **AWS CloudHSM**(PKCS#11 라이브러리 제공)이 표준 정답입니다.

## QUESTION 466

**문제**: 회사가 여러 계정에서 실행되는 Lambda 함수들의 코드 의존성 중 알려진 취약점이 있는 서드파티 라이브러리(예: 특정 CVE가 있는 npm/pip 패키지)를 사용하는지 배포 파이프라인에서 자동으로 검사하고, 취약점이 발견되면 **배포 자체를 차단**하고 싶다. 솔루션은?

**보기**

- B. **CI/CD 파이프라인(CodePipeline/CodeBuild 등)에 소프트웨어 구성 분석(SCA) 도구를 통합하는 빌드 단계를 추가해, 배포 전 코드 의존성의 알려진 취약점(CVE)을 스캔하고 취약점 발견 시 파이프라인 자체를 실패시켜 배포를 차단.**

**왜 다른 보기는 오답인가**
- A: Inspector의 사후 스캔은 유용한 지속적 모니터링이지만, "배포 자체를 차단"하는 사전 예방 요구와는 다릅니다.
- C: IAM 권한 최소화는 다른 보안 원칙이며 코드 의존성 취약점 검사와는 무관합니다.
- D: 로그 모니터링은 사후 대응 수단입니다.

> 💡 **시험 꿀팁**: 배포 파이프라인에서 **코드 의존성의 알려진 취약점을 사전에 검사해 배포 자체를 차단**하려면 **CI/CD 파이프라인의 빌드 단계에 SCA(취약점 스캔) 통합**이 표준 정답입니다.

## QUESTION 467

**문제**: 회사가 API Gateway REST API에서, 특정 헤더 값이나 쿼리 파라미터 조합에 따라 **서로 다른 백엔드 Lambda 함수 버전**(예: 카나리 배포 중인 v2 또는 안정적인 v1)으로 요청을 라우팅하고 싶다. 클라이언트가 헤더를 통해 어느 버전을 사용할지 명시적으로 선택할 수 있게 하려는 것이며, 단순 무작위 트래픽 분할이 아니다. 솔루션은?

**보기**
- A. Lambda 함수의 별칭(alias) 가중치 기반 트래픽 이동만 사용(별칭 가중치는 무작위 비율 기반 트래픽 분할에는 적합하지만, 특정 헤더 값에 따라 결정론적으로 특정 버전을 선택하는 요구에는 맞지 않음).
- B. **API Gateway의 요청 매핑 템플릿 또는 Lambda 프록시 통합과 함께, API Gateway 단계 변수(stage variables)를 사용하거나, 커스텀 Lambda 함수(또는 API Gateway의 헤더 기반 라우팅 설정 가능한 경로)로 특정 헤더 값에 따라 호출할 Lambda 별칭/버전을 명시적으로 결정하도록 구성.**

- D: CloudFront 캐시 정책은 캐싱을 위한 것이지 백엔드 라우팅 결정 메커니즘이 아닙니다.

> 💡 **시험 꿀팁**: API Gateway에서 **특정 헤더 값에 따라 결정론적으로 다른 Lambda 버전/별칭을 호출**하려면 단계 변수나 커스텀 라우팅 로직을 활용하는 것이 표준 정답이며, 무작위 비율 분할(별칭 가중치)과는 구분해야 합니다.

## QUESTION 468

**문제**: 회사가 S3 버킷에 저장된 로그 파일들을 정기적으로 분석하는데, 로그 파일의 압축 형식(gzip)이 Athena 쿼리 성능에 영향을 주는지 확인하고자 한다. 압축을 사용하되 **Athena가 병렬로 파일을 분할해 읽을 수 있는(splittable)** 방식으로 압축하고 싶다. 표준 gzip은 분할이 불가능하다는 것을 알게 되었다. 대안은?

**보기**
- A. 압축을 전혀 사용하지 않고 원시 텍스트로 저장(압축을 포기하면 스토리지 비용과 스캔 데이터량이 증가해 쿼리 비용도 커짐 — 분할 가능한 압축이라는 목표를 우회하는 것이지 해결책이 아님).
- B. **BZip2나 LZO(인덱싱 포함) 같은 분할 가능한(splittable) 압축 포맷을 사용하거나, Parquet/ORC 같은 컬럼형 포맷을 사용(이들 포맷은 내부적으로 블록 단위 압축을 지원해 병렬 읽기가 가능).**

- D. gzip 압축 파일의 확장자만 .txt로 변경(파일 확장자 변경은 실제 압축 포맷 자체(및 분할 가능 여부)를 바꾸지 못하며, Athena가 파일을 잘못 해석할 위험만 추가함).

**정답: B**

**해설**
표준 **gzip**은 스트림 압축 방식이라 병렬로 분할해서 읽을 수 없어(non-splittable), 대용량 gzip 파일 하나를 여러 작업자가 병렬로 처리하지 못하고 단일 작업자가 처음부터 끝까지 순차적으로 읽어야 합니다. 이를 해결하려면 **BZip2**(자체적으로 분할 가능) 같은 압축 포맷을 사용하거나, 더 표준적으로는 **Parquet/ORC** 같은 컬럼형 포맷(내부적으로 블록 단위로 압축되어 병렬 읽기와 컬럼 프루닝이 모두 가능)으로 전환하는 것이 Athena 쿼리 성능을 최적화하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 압축을 포기하면 비용과 스캔량이 늘어나 근본적인 해결책이 아닙니다.
- C: 하나의 큰 gzip 파일로 병합해도 여전히 분할 불가능해 오히려 병렬성이 줄어들 수 있습니다.
- D: 확장자 변경은 실제 파일 포맷을 바꾸지 못합니다.

> 💡 **시험 꿀팁**: Athena에서 **압축된 로그 파일을 병렬로 분할해 읽으려면(splittable)** BZip2 같은 분할 가능 압축 포맷이나 **Parquet/ORC 같은 컬럼형 포맷**을 사용하는 것이 표준 정답입니다. 표준 gzip은 분할 불가능하다는 점을 기억하세요.

> 💡 **시험 꿀팁**: 기존 온프레미스 **AD와 연동해 그룹 멤버십 기반으로 여러 AWS 계정에 SSO 접근**을 제공하려면 **IAM Identity Center + AD 연동(AD Connector/신뢰 관계)**이 표준 정답입니다.

- B. **SageMaker 노트북 인스턴스를 프라이빗 서브넷에 VPC 연결로 생성하고, 해당 VPC에 S3용 VPC 엔드포인트(게이트웨이 또는 인터페이스)를 구성해 노트북이 인터넷을 거치지 않고 프라이빗하게 S3의 훈련 데이터에 접근하도록 구성.**
- C. 노트북 인스턴스에서 NAT Gateway를 통해 S3에 접근(NAT Gateway를 거치는 것은 결국 인터넷 경로를 사용하는 것으로 "인터넷을 전혀 거치지 않고"라는 엄격한 요구에 반함).

**정답: B**

**해설**
SageMaker 노트북 인스턴스를 **프라이빗 서브넷**에서 VPC에 연결해 생성하면 퍼블릭 인터넷으로부터 격리됩니다. 여기에 해당 VPC에 **S3용 VPC 엔드포인트**(게이트웨이 엔드포인트가 일반적)를 구성하면, 노트북 인스턴스가 인터넷 게이트웨이나 NAT Gateway를 거치지 않고 AWS 프라이빗 네트워크를 통해 S3의 훈련 데이터에 직접 접근할 수 있습니다. 이는 규제가 요구하는 완전한 네트워크 격리와 인터넷 우회 없는 S3 접근을 동시에 만족하는 표준 구성입니다.

**왜 다른 보기는 오답인가**
- A: 퍼블릭 서브넷 배치는 격리 요구에 반합니다.
- C: NAT Gateway 경유는 결국 인터넷 경로이므로 "인터넷을 전혀 거치지 않고"라는 요구를 위반합니다.
- D: 로컬 복사는 확장성이 없고 지속적으로 갱신되는 데이터에 대한 근본적 해결책이 아닙니다.

> 💡 **시험 꿀팁**: SageMaker 노트북이 **프라이빗 서브넷에서 인터넷 없이 S3에 접근**해야 하면 **프라이빗 서브넷 배치 + S3 VPC 엔드포인트**가 표준 정답입니다.

## QUESTION 471

**문제**: 회사가 여러 개발팀이 공유하는 EKS 클러스터에서, 팀마다 서로 다른 노드 그룹(예: GPU 노드, 스팟 노드, 온디맨드 노드)에만 자신의 워크로드가 스케줄링되도록 강제하고 싶다. 팀 A의 파드가 실수로 팀 B 전용의 값비싼 GPU 노드에 스케줄링되는 것을 방지하려면?

- A. 각 팀에게 별도의 EKS 클러스터를 제공(공유 클러스터를 사용하고 싶다는 전제와 다르며 클러스터 수가 늘어나 관리 부담이 커짐).
- B. **노드에 테인트(taint)를 설정하고 해당 노드를 사용해야 하는 파드에는 일치하는 톨러레이션(toleration)을 지정하며, 추가로 노드 어피니티(node affinity)를 함께 사용해 특정 팀의 워크로드가 지정된 노드 그룹에만 스케줄링되고 다른 워크로드는 배제되도록 구성.**

- D. 각 노드 그룹을 별도의 서브넷에 배치하고 서브넷 라우팅으로 격리(Kubernetes 스케줄러는 서브넷이 아닌 노드 라벨/테인트 기반으로 파드를 배치하므로, 서브넷 분리만으로는 스케줄링 자체를 제어하지 못함).

**왜 다른 보기는 오답인가**
- A: 별도 클러스터 제공은 공유 클러스터 전제와 다르고 관리 부담을 늘립니다.
- C: 리소스 요청/제한은 자원 할당량 제어이며 노드 그룹 배치 제어와는 다른 메커니즘입니다.
- D: Kubernetes 스케줄러는 서브넷이 아닌 노드 라벨/테인트 기반으로 동작해 서브넷 분리만으로는 스케줄링을 제어하지 못합니다.

> 💡 **시험 꿀팁**: EKS/Kubernetes에서 **특정 워크로드를 지정된 노드 그룹에만 스케줄링하고 다른 워크로드를 배제**하려면 **테인트/톨러레이션 + 노드 어피니티**가 표준 정답입니다.

## QUESTION 472

**문제**: 회사가 CloudFormation으로 인프라를 관리하는데, 특정 스택 업데이트가 실수로 프로덕션 데이터베이스 리소스(RDS 인스턴스)를 **삭제하거나 대체(replace)**하는 변경을 포함할 위험이 있다. 이런 파괴적인 변경이 실수로 적용되는 것을 스택 업데이트 시점에 방지하고 싶다. 솔루션은?

**보기**
- A. CloudFormation 스택 업데이트 후 수동으로 RDS 콘솔에서 인스턴스가 그대로 있는지 확인(사후 확인은 이미 삭제/대체가 발생한 뒤에는 되돌릴 수 없어 사전 방지가 아님).
- B. **CloudFormation 변경 세트(change set)를 생성해 실제 적용 전 예정된 변경 사항(삭제, 대체 여부 포함)을 미리 검토하고, 파괴적인 변경이 포함된 경우 실행을 보류하거나 취소. 추가로 해당 리소스에 스택 정책(stack policy)이나 DeletionPolicy: Retain을 설정해 실수로라도 삭제/대체가 발생하지 않도록 보호.**

**해설**
**CloudFormation 변경 세트(change set)**는 스택을 실제로 업데이트하기 전에 어떤 리소스가 추가/수정/**삭제/대체**되는지 미리 시뮬레이션해서 보여주므로, 파괴적인 변경을 사전에 검토하고 실행 여부를 결정할 수 있습니다. 여기에 더해 중요한 리소스(RDS 등)에 **스택 정책**으로 특정 업데이트 액션을 금지하거나, `DeletionPolicy: Retain`(혹은 `Snapshot`)을 설정해두면, 실수로 스택에서 해당 리소스 정의가 제거되거나 대체되더라도 실제 리소스 삭제를 방지하는 추가 안전장치를 확보할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 사후 확인은 이미 발생한 삭제/대체를 되돌릴 수 없어 예방이 아닙니다.
- C: 수동 개별 업데이트는 IaC의 이점을 포기하고 오히려 실수 위험과 비일관성을 늘립니다.
- D: 종료 방지는 스택 전체 삭제를 막을 뿐, 업데이트 중 개별 리소스의 대체/삭제를 막는 세밀한 보호는 아닙니다.

> 💡 **시험 꿀팁**: CloudFormation 스택 업데이트에서 **파괴적인 변경(삭제/대체)을 사전에 검토하고 방지**하려면 **변경 세트(change set) 검토 + 스택 정책/DeletionPolicy**가 표준 정답입니다.

## QUESTION 474

**문제**: 회사가 대규모 이커머스 플랫폼의 주문 처리 마이크로서비스를 운영하는데, 특정 다운스트림 서비스(재고 확인 API)가 간헐적으로 느려지거나 응답하지 않을 때, 이 문제가 전체 주문 처리 시스템으로 **연쇄적으로 전파(cascading failure)**되는 것을 방지하고 싶다. 애플리케이션 코드 레벨에서 구현 가능한 복원력 패턴은?

**보기**
- A. 다운스트림 서비스 호출에 대한 타임아웃 설정만 구성(타임아웃만으로는 반복적으로 실패하는 다운스트림 서비스에 계속 요청을 보내 자원을 낭비하는 것을 막지 못하며, 연쇄 장애를 근본적으로 방지하는 패턴은 아님).
- B. **서킷 브레이커(circuit breaker) 패턴을 구현해, 다운스트림 서비스의 실패율이 임계값을 초과하면 일정 시간 동안 해당 서비스로의 요청 자체를 즉시 차단(open 상태)하고 폴백(fallback) 응답을 반환하며, 이후 점진적으로 half-open 상태에서 소수의 요청으로 복구 여부를 확인.**
- C. 다운스트림 서비스에 대한 재시도 횟수를 무제한으로 늘림(무제한 재시도는 오히려 이미 부하가 걸린 다운스트림 서비스에 더 많은 요청을 보내 상황을 악화시키고, 호출 측의 자원도 고갈시켜 연쇄 장애 위험을 키움).
- D. 모든 마이크로서비스를 하나의 모놀리식 애플리케이션으로 재통합(마이크로서비스 아키텍처 자체를 포기하는 것으로 과도한 재설계이며 이 문제가 요구하는 해결책이 아님).

**정답: B**

**해설**
**서킷 브레이커 패턴**은 다운스트림 서비스의 실패율을 모니터링하다가 임계값을 초과하면 회로를 "열어(open)" 해당 서비스로의 요청을 일정 시간 즉시 차단하고 대신 **폴백 응답**(예: 캐시된 데이터, 기본값, 우아한 오류 메시지)을 반환합니다. 이를 통해 실패하는 다운스트림 서비스에 계속 요청을 보내 자원을 낭비하거나 대기 시간이 누적되어 상위 서비스까지 장애가 전파되는 것을 방지합니다. 일정 시간 후 "반열림(half-open)" 상태로 전환해 소수의 테스트 요청으로 서비스 복구 여부를 확인한 뒤 정상화되면 회로를 다시 닫습니다.

**왜 다른 보기는 오답인가**
- A: 타임아웃만으로는 반복적인 실패 요청 자체를 막지 못해 연쇄 장애를 근본적으로 방지하지 못합니다.
- C: 무제한 재시도는 오히려 상황을 악화시키고 연쇄 장애 위험을 키웁니다.
- D: 모놀리식으로의 재통합은 이 문제의 범위를 벗어나는 과도한 조치입니다.

> 💡 **시험 꿀팁**: 마이크로서비스에서 **다운스트림 장애가 연쇄적으로 전파되는 것을 방지**하려면 애플리케이션 레벨의 **서킷 브레이커(circuit breaker) 패턴**이 표준 정답입니다.

## QUESTION 476

**문제**: 회사가 여러 계정에서 실행되는 Lambda 함수의 실행 역할(execution role)에 대해, 특정 조건(예: 특정 VPC 내에서만, 또는 특정 시간대에만)에서만 유효한 임시 권한 상승이 필요한 경우를 지원하고 싶다. 평상시에는 최소 권한만 갖고, 특정 조건이 충족될 때만 추가 권한이 자동으로 활성화되도록 하려면?

- A. Lambda 실행 역할에 처음부터 모든 필요한 최대 권한을 부여(평상시에도 불필요하게 넓은 권한을 유지하게 되어 최소 권한 원칙에 위배되며, "특정 조건에서만" 이라는 요구를 반영하지 못함).
- B. **IAM 정책의 조건(Condition) 키(예: aws:CurrentTime, aws:SourceVpc 등)를 사용해 역할에 연결된 정책 자체에 조건부 권한을 정의함으로써, 지정된 조건이 충족될 때만 해당 정책 구문이 유효하게 적용되도록 구성.**

**해설**
IAM 정책의 **조건(Condition) 요소**를 사용하면, 정책 구문 자체에 `aws:CurrentTime`(시간대), `aws:SourceVpc`(VPC 조건), `aws:SourceIp` 등 다양한 조건 키를 지정해, **해당 조건이 충족될 때만** 그 정책의 허용/거부가 유효하게 적용되도록 구성할 수 있습니다. 이를 통해 역할 자체는 하나이지만, 특정 조건(시간, 네트워크 위치 등)에서만 추가 권한이 실질적으로 활성화되는 동적이고 세밀한 권한 부여를 구현할 수 있습니다.

**왜 다른 보기는 오답인가**

- C: 수동 사용자 생성/권한 부여는 자동화되지 않고 운영 부담이 큽니다.
- D: SCP를 수동으로 매번 변경하는 것은 비현실적이고 위험한 접근입니다.

> 💡 **시험 꿀팁**: 마이크로서비스 간 **분산 추적으로 요청 경로와 지연시간을 시각적으로 분석**하려면 **AWS X-Ray**가 표준 정답입니다.

## QUESTION 479

**문제**: 회사가 AWS Direct Connect를 통해 다수의 VPC와 온프레미스를 연결하는데, 특정 애플리케이션 트래픽에 대해서만 **QoS(서비스 품질) 우선순위**를 적용해, 네트워크 혼잡 시에도 우선순위가 높은 트래픽(예: VoIP)이 우선 전달되도록 하고 싶다. AWS Direct Connect에서 QoS를 구성하는 방법은?

**보기**
- A. AWS Direct Connect 콘솔에서 트래픽 유형별 QoS 우선순위 정책을 직접 설정(AWS Direct Connect 자체는 이런 종류의 세분화된 애플리케이션 트래픽 QoS 마킹/우선순위 설정 기능을 콘솔에서 제공하지 않음 — 개념 오류).
- B. **온프레미스 라우터와 Direct Connect 회선 양단에서 802.1p 또는 DSCP 기반 트래픽 분류/마킹을 구성해 우선순위 큐잉을 적용하되, Direct Connect 자체가 대역폭 보장이나 세분화된 QoS 메커니즘을 기본 제공하지 않는다는 한계를 인지하고, 필요시 별도의 전용 회선(우선순위 높은 트래픽 전용)을 구성하는 것을 고려.**
- C. VPC 보안 그룹 규칙 우선순위로 트래픽 QoS 구현(보안 그룹은 허용/거부만 결정하는 방화벽 기능이며 트래픽 우선순위나 대역폭 QoS를 제어하는 기능이 아님).
- D. CloudFront를 사용해 QoS 문제를 해결(CloudFront는 콘텐츠 배포 서비스이며 Direct Connect 같은 전용 네트워크 연결의 QoS와는 무관함).

**정답: B**

**해설**
AWS Direct Connect는 기본적으로 세분화된 애플리케이션 수준 QoS 마킹/우선순위 설정 기능을 자체 콘솔에서 제공하지 않습니다. 이 경우 표준 네트워킹 접근으로, 온프레미스와 Direct Connect 라우터 양단에서 **802.1p(L2) 또는 DSCP(L3) 마킹**을 통해 트래픽을 분류하고 우선순위 큐잉을 구성할 수 있으며, 정말 엄격한 대역폭 보장이 필요하다면 우선순위가 높은 트래픽을 위한 **별도의 전용 Direct Connect 회선**을 고려해야 합니다. 이는 Direct Connect가 세분화된 QoS 메커니즘을 기본 제공하지 않는다는 한계를 이해하고 접근하는 것이 핵심입니다.

**왜 다른 보기는 오답인가**
- A: Direct Connect 콘솔은 이런 애플리케이션별 QoS 설정 기능을 제공하지 않습니다.
- C: 보안 그룹은 방화벽 기능이며 QoS와 무관합니다.
- D: CloudFront는 콘텐츠 배포용이며 전용 네트워크 연결의 QoS와 무관합니다.

> 💡 **시험 꿀팁**: **AWS Direct Connect 자체는 세분화된 애플리케이션 QoS 마킹 기능을 기본 제공하지 않는다**는 점을 이해하고, 표준 네트워크 QoS 마킹(802.1p/DSCP)이나 전용 회선 분리로 접근하는 것이 표준 정답입니다.

## QUESTION 480

**문제**: 회사가 조직 내 여러 팀이 각자 독립적으로 Terraform으로 인프라를 관리하고 있는데, **Terraform 상태 파일(state file)을 안전하게 중앙에서 저장하고, 동시에 여러 사람이 같은 상태를 수정하려는 것을 방지(잠금)**하고 싶다. AWS에서 이를 위한 표준적인 백엔드 구성은?

**보기**
- A. 각 팀원의 로컬 컴퓨터에 상태 파일을 저장(로컬 저장은 팀원 간 공유가 안 되고 컴퓨터 손실 시 상태 파일 자체를 잃게 되며, 동시 수정 방지 기능도 없음).
- B. **S3 버킷을 Terraform 상태 파일의 원격 백엔드로 사용하고(버전 관리 활성화로 이력 보존), DynamoDB 테이블을 상태 잠금(state locking) 메커니즘으로 함께 구성해 동시에 여러 사용자가 동일한 상태를 수정하지 못하도록 방지.**
- C. RDS 데이터베이스에 상태 파일 내용을 직접 저장(Terraform의 표준 S3 백엔드 생태계는 RDS를 상태 저장소로 사용하는 것을 지원하지 않으며, S3+DynamoDB가 공식적으로 문서화된 표준 조합).
- D. 상태 파일을 CodeCommit 리포지토리에 커밋해 버전 관리(Git 기반 버전 관리는 상태 파일의 동시 잠금 메커니즘을 제공하지 않아 여러 사람이 동시에 apply를 실행할 경우 충돌/손상 위험이 있음).

**정답: B**

**해설**
Terraform에서 팀 협업 시 표준적인 원격 백엔드 구성은 **S3 버킷**(상태 파일 저장, 버전 관리로 이력 보존 및 실수 복구 가능)과 **DynamoDB 테이블**(상태 잠금 메커니즘)의 조합입니다. 누군가 `terraform apply`를 실행하는 동안 DynamoDB의 잠금 항목이 생성되어, 다른 사용자가 동시에 같은 상태를 수정하려는 시도를 방지합니다(state locking). 이는 AWS 환경에서 Terraform 상태를 안전하게 중앙 관리하는 공식적으로 권장되는 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- A: 로컬 저장은 공유/백업/잠금 어느 것도 제공하지 못합니다.
- C: RDS는 Terraform의 표준 S3 백엔드 생태계에서 상태 저장소로 사용되지 않습니다.
- D: Git 기반 버전 관리는 동시 잠금 메커니즘이 없어 충돌 위험이 있습니다.

> 💡 **시험 꿀팁**: 팀에서 **Terraform 상태 파일을 안전하게 중앙 저장하고 동시 수정을 방지(잠금)**하려면 **S3(상태 저장, 버전 관리) + DynamoDB(상태 잠금)** 조합이 표준 정답입니다.
