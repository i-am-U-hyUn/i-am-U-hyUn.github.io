## QUESTION 61

**Question**: A financial company receives financial data records via SFTP nightly from third parties, moving them into an S3 data lake. It currently runs its own SFTP server on EC2 in a public subnet, using a cron job to move files. How should reliability and scalability be improved?

**Choices**
- A. Move EC2 to an Auto Scaling group and place it behind an ALB.
- B. **Migrate the SFTP server to AWS Transfer Family (AWS Transfer for SFTP).**
- C. Migrate the SFTP server to an AWS Storage Gateway File Gateway.
- D. Place EC2 instances behind an NLB.

**Correct Answer: B**

**Explanation**
**AWS Transfer Family** is a fully-managed SFTP service natively integrated with S3, eliminating the need to manage a self-hosted SFTP server while providing built-in reliability and scalability.

**Why the other choices are wrong**
- A: **ALB is Layer-7 (HTTP/HTTPS) only** and cannot handle the SFTP protocol.
- C: A File Gateway serves NFS/SMB protocols, not SFTP.
- D: Passing SFTP TCP traffic through an NLB is technically possible, but it still requires patching and managing your own SFTP server fleet, failing to achieve the goal of moving to a managed service.

> 💡 **Exam tip**: When you need a fully managed SFTP service natively integrated with S3, think **AWS Transfer Family**. Continuing to run and patch your own EC2-based SFTP server is usually the wrong answer.

## QUESTION 62

**Question**: Migrating an application from on-premises VMware to EC2, needing to **preserve software and configuration settings** as-is.

**Choices**
- A. Configure AWS DataSync to replicate the VMware datastore to Amazon FSx for Windows File Server, then use VM Import/Export.
- B. **Export the application as an OVF image via the vSphere client → store in S3 → create an IAM role for VM Import → run the EC2 import command via the AWS CLI.**
- C. Configure a Storage Gateway File Gateway to export a CIFS share, and create an AMI from a backup copy.
- D. Use Systems Manager hybrid activation and an AWS Backup snapshot to create an AMI.

**Correct Answer: B**

**Explanation**
**VM Import/Export** is the AWS-native service designed to bring an existing VM image (including OS, installed software, and configuration) directly into an AMI/EC2 instance. Exporting via OVF, uploading to S3, and running the import command via the CLI is the standard procedure.

**Why the other choices are wrong**
- A: DataSync+FSx is for replicating **file data**, not the standard process for moving a full VM image including OS and settings.
- C: Creating an AMI from a "backup copy" isn't how AMI creation actually works.
- D: Systems Manager hybrid activation is for **managing** on-premises servers (patching, etc.), not for importing a VM disk image.

> 💡 **Exam tip**: To bring an on-premises VM (with OS, software, and settings intact) into AWS, think **VM Import/Export** (export to OVF → upload to S3 → run the import command).

## QUESTION 63

**Question**: A video-processing Lambda app (S3 download → process → S3 save → DynamoDB metadata update) now **frequently times out** since image sizes grew (the timeout is already set to the maximum). Without wanting to manage infrastructure, how do you prevent invocation failures? (Choose two.)

**Choices**
- A. **Build a Docker image containing the application code and publish it to ECR.**
- B. **Create a new ECS task definition with Fargate compatibility, configured to use the new image; orchestrate the Lambda function to invoke the ECS task when a new file arrives in S3.**
- C. Invoke the Lambda function via a Step Functions Parallel state, and increase its provisioned concurrency.
- D. Create a new ECS task definition with EC2 compatibility.
- E. Store images on EFS and move metadata storage to RDS.

**Correct Answer: A, B**

**Explanation**
Since the root cause is exceeding **Lambda's 15-minute maximum execution duration**, move the actual processing work to **ECS Fargate** (no execution time limit, no servers to manage), and redesign Lambda to be a thin trigger that just invokes the ECS task in response to an S3 event.

**Why the other choices are wrong**
- C: Wrapping it in Step Functions doesn't change Lambda's own 15-minute limit, and provisioned concurrency addresses cold starts, not execution duration.
- D: **EC2 compatibility** requires directly managing instances/a cluster, contradicting the "don't want to manage infrastructure" requirement.
- E: Changing storage architecture is unrelated to the root cause (Lambda timeouts).

> 💡 **Exam tip**: When a task consistently exceeds **Lambda's 15-minute execution limit**, and you don't want to manage infrastructure, redesign to move the actual work to **ECS Fargate**, keeping Lambda only as a trigger.

## QUESTION 64

**Question**: An organization using Control Tower to deploy a landing zone needs a policy to **detect idle, unencrypted RDS instances** in the Production OU.

**Choices**
- A. Turn on a Control Tower **Mandatory guardrail** and apply it to the Production OU.
- B. **Enable the appropriate guardrail from Control Tower's "Strongly Recommended" guardrail list** and apply it to the Production OU.
- C. Create a new AWS Config rule directly and apply it.
- D. Create a custom SCP and apply it.

**Correct Answer: B**

**Explanation**
Control Tower guardrails are categorized into **Mandatory (always-on, non-optional)** and **Strongly Recommended (must be explicitly enabled)**. A specific detective check like "detect idle, unencrypted RDS" belongs to the Strongly Recommended list, which must be found and enabled.

**Why the other choices are wrong**
- A: Mandatory guardrails are a fixed baseline set — this specific check isn't something you "turn on" from that category.
- C: Building a raw Config rule directly bypasses the guardrail catalog Control Tower already provides — non-standard.
- D: An SCP blocks permissions (actions), but has no capability to **detect a resource's state** like "idle and unencrypted."

> 💡 **Exam tip**: Control Tower guardrails split into **Mandatory (fixed)** and **Strongly Recommended (must be explicitly enabled)**. For a specific detective requirement, look in the **Strongly Recommended** catalog first.

## QUESTION 65

**Question**: A startup's engineers rely heavily on SSH access to an EC2 fleet in private subnets for troubleshooting, with security groups currently allowing direct SSH from on-premises. The company needs to **strengthen SSH access security** and get an **audit trail of the commands engineers run.**

**Choices**
- A. Install EC2 Instance Connect and remove all inbound port 22 rules.
- B. Restrict port 22 to engineer device IPs, and send OS audit logs to CloudWatch via a CloudWatch agent.
- C. Restrict port 22 to engineer device IPs, and use AWS Config/Firewall Manager to auto-remediate security group changes.
- D. **Attach an IAM role with the `AmazonSSMManagedInstanceCore` policy to all EC2 instances, remove all inbound port 22 rules entirely, and have engineers use AWS Systems Manager Session Manager to remotely access instances.**

**Correct Answer: D**

**Explanation**
**Systems Manager Session Manager** allows access without opening port 22 at all (IAM-permission-based), completely eliminating the SSH attack surface, while natively logging session activity to CloudWatch Logs/S3 — satisfying both requirements at once.

**Why the other choices are wrong**
- A: EC2 Instance Connect pushes a temporary SSH key but **still requires port 22 to be open**, and lacks Session Manager's built-in command auditing.
- B, C: Restricting port 22 by IP still leaves a **port open**, a weaker posture than D, and C only monitors SG changes — it doesn't audit the engineer's **actual commands.**

> 💡 **Exam tip**: To completely close port 22 while also getting command-level audit logging, **AWS Systems Manager Session Manager** (with the `AmazonSSMManagedInstanceCore` role) is the answer. EC2 Instance Connect and IP-restricted security groups both leave the port open.

## QUESTION 66

**Question**: A company using Organizations to let developers experiment with AWS wants to prevent them from launching costly services and give each developer a **fixed monthly budget.** (Choose three.)

**Choices**
- A. Create an SCP that sets a fixed monthly usage limit.
- B. **Use AWS Budgets to create a fixed monthly budget for each developer account, as part of account creation.**
- C. **Create an SCP that denies access to expensive services**, applied to developer accounts.
- D. Create an IAM policy denying expensive services, applied to developer accounts.
- E. Create a Budgets notification action that "terminates all services" when the budget is reached.
- F. **Create a Budgets notification action that sends an SNS notification and invokes a Lambda function to terminate services when the budget is reached.**

**Correct Answer: B, C, F**

**Explanation**
**SCPs cannot directly cap spend/usage** (they only allow/deny permissions). So set the budget itself via **AWS Budgets** (B), block access to expensive services via an **SCP** (C), and implement custom termination logic on budget overage via **SNS + Lambda** (F).

**Why the other choices are wrong**
- A: There's no such thing as an SCP that enforces a "monthly usage limit" — category error.
- D: An organization-wide, centrally-enforced **SCP** is more appropriate for consistently restricting all developer accounts than a per-identity IAM policy.
- E: A Budgets action that automatically "terminates all services" isn't how AWS Budgets Actions actually work (custom termination requires SNS+Lambda, as in F).

> 💡 **Exam tip**: **SCPs can't limit cost — only permissions.** Set the cap with **AWS Budgets**, block expensive services with an **SCP**, and implement automated overage response with **SNS + Lambda.**

## QUESTION 67

**Question**: Migrating an app (Lambda + Aurora inventory data with automated backups configured) from the Source account to a new Target account in the same Organization, needing to **minimize downtime** for this critical data.

**Choices**
- A. Download and recreate the Lambda deployment package, and **share an Aurora automated backup snapshot.**
- B. Download and recreate the Lambda deployment package, and **use AWS RAM to share the Aurora DB cluster, granting the Target account permission to clone it.**
- C. Use RAM to share both the Lambda function and the Aurora cluster.
- D. Use RAM to share the Lambda function, plus share an Aurora automated backup snapshot.

**Correct Answer: B**

**Explanation**
**Sharing an Aurora DB cluster via AWS RAM** lets the target account create a near-instant **clone**, with far less downtime than a snapshot restore. **Lambda functions cannot be shared via RAM**, so the deployment package must be downloaded and used to recreate the function in the new account.

**Why the other choices are wrong**
- A: Sharing/restoring from an automated backup snapshot takes longer than cloning, meaning more downtime.
- C, D: **Lambda functions are not a resource type that can be shared via AWS RAM.** This premise is simply wrong.

> 💡 **Exam tip**: **AWS RAM supports sharing an Aurora DB cluster** (enabling cloning), but **not Lambda functions** — those must be recreated from the deployment package in the target account.

## QUESTION 68

**Question**: A Python script on EC2 processes S3 files every 10 minutes (averaging 5 minutes per file). CloudWatch shows EC2 is idle about 40% of the time. Improve availability/scalability and reduce long-term management overhead, most cost-effectively.

**Choices**
- A. **Migrate the processing script to a Lambda function, invoked directly via S3 event notifications** on object upload.
- B. Create an SQS queue and an EC2 Auto Scaling group (minimum size 1) polling the queue.
- C. Migrate to a container image running on EC2, polling S3 for new objects.
- D. Migrate to a container image on ECS Fargate, with a separate Lambda function calling the Fargate RunTask API, triggered by S3 events.

**Correct Answer: A**

**Explanation**
Since per-file processing time (avg. 5 minutes) comfortably fits **within Lambda's 15-minute limit**, invoking Lambda directly on each S3 event is the simplest, cheapest, and most scalable redesign — no idle-cost infrastructure at all.

**Why the other choices are wrong**
- B: A minimum-size-1 EC2 ASG still runs an instance continuously, incurring idle cost and management overhead.
- C: Switching to a container still runs on/polls from EC2, leaving the same management burden.
- D: Adding ECS Fargate plus an orchestrating Lambda is unnecessary complexity for a task well within Lambda's own duration limit.

> 💡 **Exam tip**: When a task fits comfortably **within Lambda's 15-minute limit**, a simple event-driven **S3 event notification → direct Lambda invocation** is the cheapest, lowest-management answer. Reserve ECS Fargate for tasks exceeding 15 minutes (see Question 63).

## QUESTION 69

**Question**: A North American financial company is launching a new web app on EC2 in us-east-1, needing high availability and dynamic scaling, plus **active-passive DR** in us-west-1.

**Choices**
- A. Configure VPC peering, with a **single ALB spanning multiple AZs across both VPCs.**
- B. Independent regional stacks are correctly configured, but only a simple health check record is created (no explicit failover routing policy).
- C. **Independent VPC/ALB/ASG per Region (no VPC peering needed), a Route 53 hosted zone with a record per ALB, health checks enabled, and a Failover routing policy configured.**
- D. VPC peering, plus a single ALB spanning both VPCs, with a simple non-failover record.

**Correct Answer: C**

**Explanation**
Building a **fully independent stack** in each Region (its own VPC, ALB, ASG spanning that Region's own AZs), connected via a **Route 53 Failover routing policy plus health checks**, is the standard active-passive DR pattern — no VPC peering is needed since it's a DNS-level failover mechanism.

**Why the other choices are wrong**
- A, D: **An ALB is a regional resource and cannot span VPCs across two different Regions.** These configurations are architecturally invalid.
- B: The two regional stacks are set up correctly, but without an explicit **Failover routing policy**, simple health checks alone don't guarantee active-passive behavior.

> 💡 **Exam tip**: **An ALB is regional and cannot span multiple Regions.** For cross-Region active-passive DR, build independent stacks per Region connected via a **Route 53 Failover routing policy** — no VPC peering required.

## QUESTION 70

**Question**: In a single-account environment, IT support staff currently log into the console as named IAM users mapped to job roles. They want to stop maintaining both AD and IAM accounts, and use existing AD credentials for console access instead, via IAM Identity Center. Most cost-effective solution?

**Choices**
- A. AWS Managed Microsoft AD (two-way trust) + only the IAM Identity Center feature turned on.
- B. AD Connector + only the IAM Identity Center feature turned on (not all Organizations features).
- C. AWS Managed Microsoft AD (two-way trust) + **all features** of the organization enabled.
- D. **AD Connector + all features of the organization enabled**, with the AD Connector set as IAM Identity Center's identity source, and permission sets mapped to existing AD groups.

**Correct Answer: D**

**Explanation**
Since the goal is just to use the EXISTING on-prem AD (not stand up a new directory), the lightweight **AD Connector** (a proxy to existing AD) is far cheaper than an AWS Managed Microsoft AD (a whole separate directory). **IAM Identity Center also requires Organizations' "all features" to be enabled.**

**Why the other choices are wrong**
- A, C: AWS Managed Microsoft AD stands up a **completely separate directory** in AWS, more costly/complex than needed when a simple authentication proxy suffices.
- B: Same approach as D, but only turns on the "IAM Identity Center feature" without enabling **all features** of the organization — a prerequisite IAM Identity Center requires.

> 💡 **Exam tip**: A lightweight authentication proxy to an existing on-prem AD needs only an **AD Connector** (cheap); AWS Managed Microsoft AD (a full separate directory) is only needed when you require an actual in-AWS directory. Remember **IAM Identity Center requires "all features" enabled in Organizations.**

## QUESTION 71

**Question**: A video streaming app uploads 1GB-10GB files to an S3 bucket in us-east-1. Users in Australia experience long upload times, with occasional incomplete uploads. Improve performance. (Choose two.)

**Choices**
- A. **Enable S3 Transfer Acceleration and configure the app to use the acceleration endpoint.**
- B. Configure buckets in each Region and use Cross-Region Replication to distribute files.
- C. Set up Route 53 latency-based routing to the nearest bucket Region.
- D. **Configure the app to split video files into chunks and use multipart upload.**
- E. Modify the app to add a random prefix to files before uploading.

**Correct Answer: A, D**

**Explanation**
**S3 Transfer Acceleration** routes uploads through CloudFront's global edge network onto AWS's optimized backbone, dramatically improving upload speed for geographically distant users. **Multipart upload** splits large files into independently retryable parts, addressing both performance and the "sometimes doesn't fully upload" reliability issue.

**Why the other choices are wrong**
- B: This addresses data distribution **after** upload completes, not the actual slow/failing upload problem itself.
- C: With a single bucket in us-east-1, "nearest bucket Region" doesn't apply, and multi-Region buckets would require significant re-architecture.
- E: Random key prefixing is an outdated tip for a since-resolved S3 partitioning performance issue, unrelated to this long-distance network latency problem.

> 💡 **Exam tip**: For slow or unreliable large-file uploads from distant users, the classic combo is **S3 Transfer Acceleration + Multipart Upload** — not post-upload replication or the outdated random-prefix tip.

## QUESTION 72

**Question**: An app using RDS for MySQL Multi-AZ in us-east-1 lost its database connection after a failover test and **couldn't reestablish it** (only an app restart fixed it). How can the app reestablish connections without restarting?

**Choices**
- A. Migrate to Aurora Serverless v1 and point the app at the reader endpoint.
- B. **Create an RDS Proxy, configure the existing RDS endpoint as its target, and update the app's connection settings to point at the RDS Proxy endpoint.**
- C. Migrate to an Aurora cluster, and also add an RDS Proxy.
- D. Export the database to S3 via DMS and query it with Athena.

**Correct Answer: B**

**Explanation**
**RDS Proxy** maintains a connection pool between the app and database, and **transparently handles reconnection during a failover** — the app itself keeps its apparent connection without needing a restart.

**Why the other choices are wrong**
- A: Pointing at a reader endpoint doesn't fit general read/write connections and doesn't itself solve the reconnection issue.
- C: RDS Proxy is correct, but migrating the database engine to Aurora too is unnecessary — RDS Proxy alone on the existing RDS MySQL instance suffices.
- D: Turning the database into an analytical S3/Athena data store is completely unsuited to a live transactional application.

> 💡 **Exam tip**: If an app can't reconnect on its own after a Multi-AZ failover, don't change the app or database engine — put **RDS Proxy** in front to handle connection pooling and failover reconnection.

## QUESTION 73

**Question**: An IoT solution needs devices to send/receive real-time data via MQTT, with each device authenticating via a unique X.509 certificate. Minimal operational overhead?

**Choices**
- A. Set up IoT Core, but create individual **Amazon MQ queues** per device.
- B. Run a self-hosted MQTT broker on EC2 (behind an NLB with a Lambda authorizer).
- C. **Set up AWS IoT Core, create an AWS IoT "thing" and provision a certificate for each device, and connect each device to AWS IoT Core.**
- D. Use API Gateway HTTP API + NLB + mutual TLS authorizer + a self-hosted MQTT broker on EC2.

**Correct Answer: C**

**Explanation**
**AWS IoT Core** natively supports the MQTT protocol and per-device X.509 certificate authentication as a fully-managed service — exactly matching this requirement.

**Why the other choices are wrong**
- A: Amazon MQ is a general message broker (JMS/AMQP-oriented) — it doesn't provide the IoT-specific MQTT+per-device-cert capabilities.
- B, D: Both require self-hosting and managing your own MQTT broker infrastructure, violating "minimal operational overhead."

> 💡 **Exam tip**: Whenever you see **MQTT + per-device X.509 certificates**, go straight to **AWS IoT Core.** Don't confuse it with Amazon MQ or self-hosted broker architectures.

## QUESTION 74

**Question**: In a single account with multiple workloads, a new policy requires engineers to provision only **approved resources**, and only **via CloudFormation.** How should the engineers' existing IAM role be restricted?

**Choices**
- A. Upload an approved-resources template to S3, and update the engineer role to allow only S3+CloudFormation access.
- B. Grant the engineer role both approved-resource permissions and CloudFormation permissions.
- C. **Restrict the engineer role to CloudFormation actions only. Create a new IAM policy with permission to provision approved resources, assign it to a new IAM service role, and assign that service role to CloudFormation during stack creation.**
- D. Provision resources via a CloudFormation stack, and restrict the engineer role to access only their own stack.

**Correct Answer: C**

**Explanation**
Give the engineer's IAM role **only CloudFormation action permissions** (no direct resource-creation rights), and grant the actual resource-creation permissions to a **separate CloudFormation service role**, assigned during stack creation — so CloudFormation performs the work on the engineer's behalf, and the engineer can never create a resource except through CloudFormation.

**Why the other choices are wrong**
- A: "Only S3 and CloudFormation access" is vague and doesn't clearly close off other direct resource-creation paths.
- B: Granting the engineer role direct approved-resource permissions means they could bypass CloudFormation entirely via console/CLI.
- D: Restricting access to "their own stack" controls stack-level scope, not which resource types are approved.

> 💡 **Exam tip**: To enforce "only via CloudFormation, only approved resources," separate: **engineer role = CloudFormation actions only**, **actual resource-creation permissions = a separate CloudFormation service role.**

## QUESTION 75

**Question**: Millions of small records (under 4KB each) are ingested per minute from global devices, needing low-latency, durable retrieval. Data is retained only 120 days, then deletable, at ~10-15TB/year. Most cost-effective strategy?

**Choices**
- A. Store each record as an individual .csv file in S3, with a lifecycle policy deleting data after 120 days.
- B. **Store each record in a DynamoDB table provisioned at scale, using DynamoDB TTL to automatically delete records after 120 days.**
- C. Store each record in a single RDS MySQL table, with a nightly cron job deleting old records.
- D. Batch records before writing to S3, using object metadata for search.

**Correct Answer: B**

**Explanation**
**DynamoDB** natively supports massive write throughput, millisecond-latency retrieval, and **native TTL** for automatic expiration — exactly matching this requirement with zero custom cleanup logic.

**Why the other choices are wrong**
- A: "Indexed search" across millions of individual S3 files is unnatural and inefficient.
- C: A relational database doesn't scale as naturally to this write volume, and a manual cron job is more overhead than native TTL.
- D: A batching + custom metadata search approach is unnecessarily complex and doesn't provide DynamoDB's simple low-latency retrieval.

> 💡 **Exam tip**: For **massive small-record ingestion + low-latency retrieval + time-based auto-deletion**, default to **DynamoDB + native TTL.**

## QUESTION 76

**Question**: A multi-Region e-commerce site must always be available, storing data in RDS for MySQL. Which solution provides the **highest availability** for the database?

**Choices**
- A. Configure RDS automated backups; promote a backup to a standalone instance on outage.
- B. Configure RDS "Global Tables" (a nonexistent RDS feature) and read replicas, manually copying replicas cross-Region via Lambda on outage.
- C. Configure RDS "Global Tables" and automated backups, with the same manual Lambda copy process.
- D. **Configure a cross-Region RDS read replica; on outage, promote it to a standalone instance and redirect traffic; create a new replica from the promoted instance.**

**Correct Answer: D**

**Explanation**
The standard **cross-Region read replica promotion** pattern: keep a continuously-replicating standby replica, promote it to primary on regional outage, redirect traffic, and create a new replica for future resilience.

**Why the other choices are wrong**
- A: Using **automated backups** (not continuous replication) for recovery has a worse RPO/recovery speed than an already-current standby replica.
- B, C: **"Global Tables" is a DynamoDB feature and does not exist for RDS/MySQL.** This premise is simply wrong, and manually copying replicas via Lambda is inefficient.

> 💡 **Exam tip**: **"Global Tables" is DynamoDB-only** and doesn't exist for RDS. The standard RDS/Aurora cross-Region DR pattern is: **continuous read replica → promote on failure → re-replicate.**

## QUESTION 77

**Question**: Example Corp's on-premises network connects to VPC A via Site-to-Site VPN. Acquired AnyCompany's VPC B is peered with VPC A (no overlapping IPs). Example Corp wants on-premises to also reach **VPC B.** NACLs/SGs are already correctly configured. Minimal operational effort?

**Choices**
- A. **Create a Transit Gateway, attach the Site-to-Site VPN, VPC A, and VPC B to it, and update every network's TGW route tables with routes to each other.**
- B. Create a **new, separate** Site-to-Site VPN connection between on-premises and VPC B, attached to a Transit Gateway.
- C. Update VPN and VPC route tables plus configure BGP propagation across all three networks (no Transit Gateway).
- D. Modify the virtual private gateway definition to include both VPCs.

**Correct Answer: A**

**Explanation**
**VPC peering is not transitive.** Even though VPC A and B are peered and on-premises reaches A via VPN, on-premises cannot reach B "through" A. Attaching the on-premises VPN and both VPCs to a single **Transit Gateway** and configuring routing solves this.

**Why the other choices are wrong**
- B: Building an entirely new, separate VPN connection is far more operational effort than reusing the existing connection via a Transit Gateway.
- C: **The non-transitive nature of VPC peering cannot be overcome by route tables or BGP alone** — a hub like a Transit Gateway is required.
- D: A single virtual private gateway attached across two VPCs isn't a real configuration (VPN gateways attach to one VPC only).

> 💡 **Exam tip**: **VPC peering is non-transitive** (A-B and B-C peered doesn't let A reach C directly). For transitive routing across an on-premises VPN and multiple VPCs, use a **Transit Gateway.**

## QUESTION 78

**Question**: A critical app depends on a legacy SMTP service (no TLS support, TCP port 25). The app can **only use SMTP**. The company decides to switch to Amazon SES, having already verified its domain and requested a sending limit increase. How should the app be modified to send via SES?

**Choices**
- A. Connect via a **"TLS wrapper"** + attach an **IAM role** with `ses:SendEmail` permissions to the EC2 instance.
- B. **Connect using STARTTLS, obtain SES SMTP credentials, and authenticate with them.**
- C. Send via the **SES API**, using an IAM role as a service role.
- D. Send via the **AWS SDK**, authenticating with an IAM user's access key.

**Correct Answer: B**

**Explanation**
Since the app can only use SMTP, it must use SES's **SMTP interface**, which uses **STARTTLS** (not implicit TLS wrapping). Authentication requires dedicated **SES SMTP credentials** (a username/password), not an IAM role.

**Why the other choices are wrong**
- A: SES SMTP uses **STARTTLS**, not a "TLS wrapper." SMTP auth also requires dedicated credentials, not an API-calling IAM role.
- C, D: Both directly contradict the constraint that the app can only speak SMTP, not make API/SDK calls.

> 💡 **Exam tip**: A legacy, **SMTP-only** app can use Amazon SES via its **SMTP interface (STARTTLS) with dedicated SES SMTP credentials** — IAM roles and API/SDK authentication only apply to code capable of making AWS API calls.

## QUESTION 79

**Question**: A company consolidated accounts from several acquisitions (each with different billing/reporting methods) into one Organizations org, but struggles to generate meaningful grouped cost reports. Finance needs a solution to report costs via **their own self-managed application.**

**Choices**
- A. **Generate an organization-wide Cost and Usage Report (CUR), define tags and cost categories, create an Athena table, build a QuickSight dataset from it, and share the dataset with finance.**
- B. Generate a CUR, and create a "special template" in Cost Explorer for the finance department.
- C. Create a QuickSight dataset fed by the AWS Price List Query API.
- D. Use the Price List Query API to collect spend data, plus a special Cost Explorer template.

**Correct Answer: A**

**Explanation**
Since finance needs flexibility via "their own application," the **CUR (raw data) → Athena (SQL layer) → QuickSight/custom app** pipeline provides the queryable foundation for flexible, custom groupings across the consolidated organization.

**Why the other choices are wrong**
- B: Cost Explorer's built-in templates aren't as flexible as CUR+Athena+QuickSight for custom groupings needed by a self-managed app.
- C, D: **The AWS Price List Query API returns published service pricing, not actual usage/billing data** — completely the wrong data source for reporting actual incurred costs.

> 💡 **Exam tip**: **The Price List Query API is pricing/rate-card data, not actual usage data.** For flexible custom cost reporting across consolidated accounts, use **CUR (tags/cost categories) → Athena → QuickSight or a custom application.**

## QUESTION 80

**Question**: An IoT platform: sensors send data to a Node.js API server on EC2 behind an ALB, storing it in RDS MySQL on a 4TB General Purpose SSD volume. Sensor count keeps growing significantly; API servers are constantly overloaded and RDS shows high write latency. Solve permanently and cost-effectively while allowing future growth. (Choose two.)

**Choices**
- A. Resize the MySQL General Purpose SSD storage to 6TB to improve IOPS.
- B. Redesign the database tier to use Amazon Aurora with read replicas instead of RDS MySQL.
- C. **Leverage Amazon Kinesis Data Streams and AWS Lambda to ingest and process the raw data.**
- D. Use AWS X-Ray to analyze/debug application issues and add more API servers.
- E. **Redesign the database tier to use Amazon DynamoDB instead of RDS MySQL.**

**Correct Answer: C, E**

**Explanation**
Since ever-growing IoT data is overwhelming both the API tier and the database's write capacity, the fundamental redesign combines ① **Kinesis Data Streams** to decouple ingestion from processing (relieving the API tier) and ② **DynamoDB**, purpose-built for massive-scale writes, replacing the relational database.

**Why the other choices are wrong**
- A: Resizing storage is a temporary band-aid that doesn't address the fundamental scaling ceiling as sensor count grows.
- B: Aurora with read replicas helps **read** scalability, but the stated problem is specifically **write** latency — not addressed by this.
- D: X-Ray is for tracing/debugging, and adding more API servers is a band-aid on the existing flawed synchronous architecture, leaving the downstream database bottleneck unresolved.

> 💡 **Exam tip**: For ever-growing IoT/telemetry ingestion overwhelming both an API tier and a relational database's write capacity, the standard permanent fix combines **① Kinesis Data Streams + Lambda (decoupled async processing) and ② migrating to DynamoDB** (write-optimized) — not just adding read replicas or more servers.
