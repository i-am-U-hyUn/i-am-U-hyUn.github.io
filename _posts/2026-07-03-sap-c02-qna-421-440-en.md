## QUESTION 421

**Question**: A company wants to adopt an Apache Kafka-based event streaming platform, but traffic patterns are unpredictable (a new service, hard to gauge usage), and they don't want to plan/manage cluster capacity themselves — broker count, partitions, storage capacity. They want to keep using standard Kafka APIs and tools. What's the solution?

**Choices**
- A. Build a cluster with Amazon MSK (provisioned mode) and decide broker count upfront based on expected traffic (provisioned mode requires you to directly plan capacity like broker count/type upfront, contradicting the "don't want to plan capacity myself" requirement).
- B. **Use Amazon MSK Serverless to build a fully managed Kafka cluster that automatically scales up/down with traffic, with no broker provisioning or capacity planning, while still using the standard Kafka API.**
- C. Install and operate Kafka directly on your own EC2 (takes on all the operational burden — capacity planning, broker management, patching, etc. — directly contradicting the requirement).
- D. Fully switch to Kinesis Data Streams (Kinesis is a strong streaming service, but uses its own API rather than the Kafka API, failing to meet the requirement to keep using standard Kafka APIs and tools).

**Correct Answer: B**

**Explanation**
**Amazon MSK Serverless** provides a fully managed Kafka cluster that **automatically scales up/down** with traffic, with no need for the user to provision or plan cluster capacity like broker count, partitions, or storage. It supports the standard Apache Kafka API and existing Kafka clients/tools as-is, making it well suited to adopting Kafka for a new service with unpredictable traffic, with no capacity-planning burden.

**Why the other choices are wrong**
- A: Provisioned mode requires directly planning capacity like broker count upfront, contradicting the requirement.
- C: Self-operating on EC2 takes on all capacity-planning and operational burden yourself.
- D: Kinesis doesn't use the Kafka API, failing the requirement to keep using existing Kafka tools/API.

> 💡 **Exam tip**: For a streaming platform that keeps using the **standard Kafka API with no capacity planning** and auto-scales with traffic, **Amazon MSK Serverless** is the standard answer.

## QUESTION 422

**Question**: A production RDS PostgreSQL database currently uses a standard read replica for read-load distribution, but they want to further shorten failover time, and also want the standby instance to serve read traffic under normal conditions. How do you go beyond the limitations of standard Multi-AZ (a single, non-readable standby instance)?

**Choices**
- A. Keep standard Multi-AZ deployment and just add more read replicas (the standard Multi-AZ standby instance itself still can't serve reads, and adding separate read replicas is unrelated to shortening failover time).
- B. **Switch to an RDS Multi-AZ DB cluster deployment, configuring one primary with two readable standby instances. Distribute read traffic across the two standbys under normal conditions, and get automatic failover faster than standard Multi-AZ during a failure.**
- C. Switch to Aurora Global Database (Global Database is a cross-Region disaster-recovery feature, a different purpose than this question's requirement of faster failover and readable standbys within a single Region).
- D. Create multiple read replicas at the same spec as the primary and distribute traffic with a load balancer (viable, but standard read replicas have asynchronous replication lag, and their standard automatic-failover mechanism isn't as fast as a Multi-AZ DB cluster's).

**Correct Answer: B**

**Explanation**
An **RDS Multi-AZ DB cluster** deployment configures **two readable standby instances** in separate AZs alongside one primary instance. Under normal conditions, these two standby instances can serve distributed read traffic (the key difference from standard Multi-AZ, which can't serve reads), and during a primary failure, automatic failover happens **faster (typically under 35 seconds)** than standard Multi-AZ, based on semi-synchronous replication and a fast storage layer.

**Why the other choices are wrong**
- A: Standard Multi-AZ's standby instance can't be used for reads — overcoming this exact limitation is the question's goal.
- C: Aurora Global Database is a cross-Region DR feature — different from this question's single-Region requirement.
- D: Standard read replicas use asynchronous replication, which can lag, and their automatic-failover speed isn't as fast as a Multi-AZ DB cluster's.

> 💡 **Exam tip**: For an RDS workload needing both **readable standby instances and faster automatic failover**, a **Multi-AZ DB cluster deployment** is the standard answer.

## QUESTION 423

**Question**: The security team wants to eliminate **SSH key management, opening port 22, and running a bastion host** entirely for administrative access to EC2 instances. Every session must be centrally logged for audit purposes, and access should be finely controlled via IAM permissions. What's the solution?

**Choices**
- A. Harden the bastion host and store SSH keys in Secrets Manager (running a bastion host and the SSH access method [opening port 22] both remain in place, failing to meet the "eliminate all of these" requirement).
- B. **Use AWS Systems Manager Session Manager to start a browser- or CLI-based shell session on an instance based on IAM permissions, with no SSH key, bastion host, or inbound port opened, and centrally log all session activity via CloudTrail and S3/CloudWatch Logs.**
- C. Access a private subnet via VPN and then use SSH (even using a VPN still requires SSH key management and opening port 22, not fully meeting the requirement).
- D. Remove public IPs from all instances and place them behind a NAT Gateway (removing public IPs alone doesn't eliminate SSH key management itself, and doesn't fundamentally change the instance access/management method).

**Correct Answer: B**

**Explanation**
**AWS Systems Manager Session Manager** lets you start a browser-based or CLI-based shell session on an EC2 instance (or on-premises server) based on **IAM permissions**, with no SSH key, bastion host, or inbound port (22, etc.) opened. Every session start/end and executed command is centrally logged via **CloudTrail** and **S3/CloudWatch Logs**, providing a complete audit trail, and IAM policy lets you finely control who can access which instances.

**Why the other choices are wrong**
- A: A bastion host and the SSH access method itself both remain, failing the "eliminate all of these" goal.
- C: VPN access still requires an SSH key and open port.
- D: Removing public IPs reduces network exposure but doesn't eliminate SSH key management itself.

> 💡 **Exam tip**: To **access instances via IAM-based permissions with no SSH key/bastion host/inbound port opened, and audit-log every session**, **AWS Systems Manager Session Manager** is the standard answer.

## QUESTION 424

**Question**: A mobile app needs to access S3 and DynamoDB directly, without going through a backend server, but they don't want to create an IAM user per end user, and app users authenticate via social login (Google, Facebook, etc.). How do you issue temporary AWS credentials with scoped access to authenticated (or guest) users?

**Choices**
- A. Hardcode one shared access key/secret key for all mobile users into the app (hardcoding an access key into a client app is a serious security risk, and can't isolate individual users).
- B. **Use Amazon Cognito Identity Pools to issue temporary AWS credentials via STS to users authenticated by a social login provider (or a Cognito user pool) (and unauthenticated guests), with IAM roles specifying fine-grained access scope to S3/DynamoDB.**
- C. Dynamically create an individual IAM user per mobile user in the backend (creating an IAM user per user runs into IAM user limits and scalability problems, directly contradicting the "don't want to create IAM users" requirement).
- D. Proxy all S3/DynamoDB requests through API Gateway + Lambda and handle authentication in the backend (the question explicitly wants direct access "without going through a backend server," so this doesn't fit the requirement).

**Correct Answer: B**

**Explanation**
**Amazon Cognito Identity Pools** issues **temporary credentials via AWS STS** to users authenticated by a social login provider (Google, Facebook, etc.), a Cognito user pool, SAML, or similar (or unauthenticated guest users). These temporary credentials are tied to an IAM role with fine-grained permissions to S3, DynamoDB, etc., letting the mobile app securely access AWS resources directly, with no backend server and no individual IAM users created.

**Why the other choices are wrong**
- A: Hardcoding a shared access key into a client is a serious security vulnerability.
- C: Creating an IAM user per user doesn't scale and directly contradicts the requirement.
- D: A backend proxy approach differs from the requirement to access directly with no backend server.

> 💡 **Exam tip**: For a mobile app to **issue temporary AWS credentials to social-login-authenticated users for direct AWS resource access**, **Amazon Cognito Identity Pools** is the standard answer.

## QUESTION 425

**Question**: When deploying a new version of a web application on Elastic Beanstalk, a company wants to fully validate the new version in a separate environment with no impact on the existing version, then **switch traffic immediately if there are no issues, or immediately revert to the original version if there are**. What's the zero-downtime deployment approach?

**Choices**
- A. Use Elastic Beanstalk's rolling deployment policy (rolling deployment sequentially replaces instances within the existing environment — different from fully validating a new version separately and then switching all at once, and rollback also requires sequential re-replacement — not immediate).
- B. **Use Elastic Beanstalk's environment swap (blue/green-like) deployment method: deploy the new version to a separate environment (green), validate it thoroughly, then use environment URL swap to immediately switch traffic. If a problem occurs, swap again to immediately roll back to the original environment (blue).**
- C. Use the "all at once" deployment policy (replaces all instances with the new version at once, with no pre-validation in a separate environment or an immediate rollback mechanism — a problem during deployment directly impacts the service).
- D. Fully terminate the existing environment and create a new one from scratch (terminating the existing environment causes downtime and also contradicts the requirement to validate "with no impact on the existing version").

**Correct Answer: B**

**Explanation**
Elastic Beanstalk's **environment swap (swap URL, blue/green-like) deployment method** deploys the new version to a new environment (green) that's entirely separate from the existing production environment (blue), letting you test thoroughly with zero impact on production. Once validation is complete, **swapping the two environments' CNAMEs (URLs)** immediately switches traffic to the new environment, and if a problem occurs, swapping again lets you **immediately roll back** to the original environment — meeting all of this question's requirements (pre-validation, immediate switch, immediate rollback).

**Why the other choices are wrong**
- A: Rolling deployment is a sequential replacement within the existing environment and doesn't provide fully separate pre-validation or immediate full rollback.
- C: All-at-once replaces everything immediately with no validation stage — a problem directly impacts the service.
- D: Terminating and recreating the environment causes downtime.

> 💡 **Exam tip**: To **switch immediately to a fully validated new version and roll back immediately on problems** in Elastic Beanstalk, **environment swap (blue/green) deployment** is the standard answer.

## QUESTION 426

**Question**: A manufacturing facility collects and stores millions of sensor measurements per second (timestamped temperature, pressure, etc.), and wants recent data queried quickly while old data automatically moves to cheaper storage, along with efficient time-based aggregation queries (e.g., "average over the last hour"). What service specializes in this purpose better than a relational DB or general-purpose NoSQL?

**Choices**
- A. Store in DynamoDB using the timestamp as a sort key (viable, but doesn't natively provide time-series-specific automatic data tiering [separating recent/old data] or built-in time-based aggregation functions — requires self-implementation).
- B. **Use Amazon Timestream, optimized storage and a query engine for time-series data, ingesting millions of measurements per second, with automatic data tiering (memory store → magnetic store) and built-in time-based aggregation functions for efficient analysis.**
- C. Store all data in RDS PostgreSQL and manage with partitioning (a relational DB isn't optimized for ingesting/aggregating time-series data at this scale, and automatic tiering would need self-implementation).
- D. Store raw data in S3 and run aggregation queries via Athena every time (an S3+Athena batch-query approach doesn't fit near-real-time ingestion at millions of events per second, nor fast recent-data lookups).

**Correct Answer: B**

**Explanation**
**Amazon Timestream** is a database specifically designed for time-series data, capable of ingesting millions of events per second, and **automatically tiering** recent data into a memory store and older data into a cheaper magnetic store. It has built-in time-series-specific functions like time-based aggregation, interpolation, and smoothing, making it the standard service for handling large-scale time-series workloads like IoT sensor data more efficiently and cost-effectively than a relational DB or general-purpose NoSQL.

**Why the other choices are wrong**
- A: DynamoDB is viable but requires self-implementing time-series-specific tiering or time-based aggregation functions.
- C: A relational DB isn't optimized for time-series ingestion/aggregation at this scale.
- D: An S3+Athena batch-query approach doesn't fit near-real-time, high-volume ingestion or fast recent-data lookups.

> 💡 **Exam tip**: For **large-scale time-series (IoT sensor, etc.) data ingestion, automatic tiering, and time-based aggregation**, **Amazon Timestream** is the standard answer.

## QUESTION 427

**Question**: A development team wants to deliver messages from a specific SQS queue to a Step Functions workflow, but only messages with a specific attribute value should be delivered, and message format should be simply transformed before delivery. They don't want to write and maintain a separate Lambda function each time (simple connecting/transforming "glue code"). What's the solution?

**Choices**
- A. Write a connector-only Lambda function between SQS and Step Functions implementing the filtering and transformation logic (exactly the approach the question explicitly wants to avoid — writing/maintaining separate glue-code Lambda each time).
- B. **Use Amazon EventBridge Pipes, specifying SQS as the source and Step Functions as the target, with a filtering step passing through only messages matching a specific attribute condition, and an enrichment/transformation step converting the message format before delivering to the target — with no custom Lambda glue code.**
- C. Add an SNS topic in the middle and filter messages with a filter policy (SNS filter policies can filter, but require an additional architectural layer re-routing SQS through SNS, and transformation would still need to be separately implemented).
- D. Implement the filtering logic as a Choice state inside the Step Functions state machine (every message would still trigger a workflow execution just to be filtered, incurring unnecessary execution cost, and this differs from source-to-target filtering).

**Correct Answer: B**

**Explanation**
**Amazon EventBridge Pipes** is a service for configuring **point-to-point integration** between an event source (SQS, Kinesis, DynamoDB Streams, etc.) and a target (Step Functions, Lambda, etc.) with no custom glue code. You can declaratively configure a **filtering** step (passing through only events matching certain conditions) and an **enrichment/transformation** step (converting data format before sending to the target, calling an external API, etc.) in the pipe, eliminating the need to write and maintain a simple connector Lambda function each time.

**Why the other choices are wrong**
- A: Writing a connector-only Lambda is exactly the approach this question wants to avoid.
- C: An SNS filter policy can filter, but requires an additional architectural layer and separate transformation implementation.
- D: Filtering inside Step Functions incurs unnecessary workflow execution cost and differs from source-to-target filtering.

> 💡 **Exam tip**: To configure **point-to-point integration between an event source and target, including filtering/enrichment/transformation, with no custom glue-code Lambda**, **Amazon EventBridge Pipes** is the standard answer.

## QUESTION 428

**Question**: A company loads clickstream data into an S3 data lake via Kinesis Data Firehose, and wants to **automatically partition it by record content** — customer ID or event type — to optimize Athena query performance and cost. They want to avoid writing and managing a separate Lambda transform function each time to extract the partition key. What's the solution?

**Choices**
- A. Have Firehose partition simply by time (year/month/day/hour) only (time-based partitioning is Firehose's default option, but doesn't meet this question's requirement for partitioning based on record content [customer ID, event type, etc.]).
- B. **Use Kinesis Data Firehose's dynamic partitioning feature, configured with a JQ expression to extract a partition key (customer ID, event type, etc.) from record content, automatically loading data into S3 in a content-based partition structure with no separate Lambda transform function.**
- C. Load all data into a single location with no partitioning, and fully scan on every Athena query (with no partitioning, every query must scan all the data, worsening both performance and cost — the opposite of what this question wants to solve).
- D. Have a Lambda function parse records directly and generate an S3 key path, calling individual PutObject calls instead of Firehose (calling individual PutObject per record is very inefficient for high-volume streaming data and gives up the batching/buffering benefits Firehose provides).

**Correct Answer: B**

**Explanation**
**Kinesis Data Firehose's dynamic partitioning** uses a **JQ parsing expression** to extract a partition key from the actual content (JSON fields, etc.) of incoming records, and automatically builds a folder structure in S3 based on it to load the data. This implements fine-grained, content-based partitioning with just Firehose console/API configuration, with no separate Lambda transform function needed, letting a query engine like Athena efficiently scan only relevant partitions — improving both performance and cost.

**Why the other choices are wrong**
- A: Time-based partitioning alone doesn't meet the requirement for fine-grained, record-content-based partitioning.
- C: Full-scanning with no partitioning is the opposite of what this question wants to solve.
- D: Individual PutObject calls are very inefficient at high-volume streaming and give up Firehose's batching benefit.

> 💡 **Exam tip**: To **automatically partition S3 data by record content, with no separate Lambda transform**, in Kinesis Data Firehose, **dynamic partitioning** is the standard answer.

## QUESTION 429

**Question**: A SaaS company embeds QuickSight dashboards into multiple customers' web portals, but **each customer's users must see only their own company's data**, and they don't want to duplicate the same dataset and dashboard separately for each customer. What's the solution?

**Choices**
- A. Create a completely separate dataset and dashboard individually for each customer (requires duplicating/maintaining datasets/dashboards per customer, directly contradicting the "don't want to duplicate" requirement, and carries very heavy management burden).
- B. **Use QuickSight's Row-Level Security (RLS), defining data access rules per user/group on a single shared dataset and dashboard, so that even though all users view the same dashboard, each user sees only the rows corresponding to their own company's data.**
- C. Completely remove the customer column from the dataset itself (removing the column eliminates the very basis for filtering by specific customer — not a solution, and violates the requirement).
- D. Segment access to each customer via IAM policies only (row-level access control over QuickSight's own data is hard to implement with IAM policies alone — RLS is a QuickSight-dedicated feature specialized for this purpose).

**Correct Answer: B**

**Explanation**
**QuickSight's Row-Level Security (RLS)** lets a single dataset and dashboard be shared across multiple users/groups, while defining a rule table (mapping users/groups to allowed data values) to control so that **each user sees only the rows they're allowed to see**. This lets a multi-tenant SaaS dashboard safely isolate each customer to their own data without duplicating the dataset and dashboard itself per customer.

**Why the other choices are wrong**
- A: Creating individual datasets/dashboards per customer contradicts the "don't want to duplicate" requirement and carries heavy management burden.
- C: Removing the column eliminates the basis for filtering — doesn't solve the problem.
- D: Row-level data access control is hard to implement with IAM policies alone — RLS is QuickSight's dedicated feature for this.

> 💡 **Exam tip**: For a multi-tenant QuickSight dashboard needing to **share one dataset/dashboard while each customer sees only their own data**, **Row-Level Security (RLS)** is the standard answer.

## QUESTION 430

**Question**: A data engineering team needs to intermittently (once or twice a day) run large-scale Spark batch jobs, and wants compute resources to automatically scale up/down to match workload, with no operational burden of sizing the EMR cluster, choosing node types, or managing cluster shutdown. What's the solution?

**Choices**
- A. Run an EMR on EC2 cluster continuously (running a cluster continuously for an intermittent job incurs unnecessary cost during idle time, and the operational burden of sizing, etc. still remains).
- B. **Use Amazon EMR Serverless: submit a Spark/Hive job with no cluster provisioning or node type/count decisions, and EMR automatically scales compute resources up/down based on workload, automatically scaling down when there's no job.**
- C. Manually provision a new EMR cluster each time and manually terminate it after the job (requires a repetitive manual provisioning/termination process — still heavy operational burden, and forgetting to terminate leads to ongoing cost).
- D. Fully switch to AWS Glue ETL jobs (Glue is also serverless ETL, but if you want to keep using existing Spark code/jobs as-is, EMR Serverless is the more direct choice for Spark/Hive ecosystem compatibility).

**Explanation**
**Amazon EMR Serverless** requires no cluster provisioning or deciding instance type/count — simply submit a Spark or Hive job, and EMR **automatically scales compute resources up/down** based on workload. Resources automatically scale down to near zero when there's no job, incurring no idle cost — a serverless big-data processing approach precisely suited to intermittent, large-scale batch jobs.

**Why the other choices are wrong**
- A: Running continuously is inefficient for an intermittent job pattern and still leaves operational burden.
- C: Manual provisioning/termination carries repetitive operational burden and risk of wasted cost from forgetting to terminate.
- D: Glue is also serverless, but EMR Serverless is more direct if you want to keep existing Spark/Hive code as-is.

> 💡 **Exam tip**: For intermittent **Spark/Hive batch jobs** to auto-scale up/down with no cluster operational burden, **Amazon EMR Serverless** is the standard answer.

## QUESTION 431

**Question**: A scientific research institute needs to run **tightly coupled** parallel computation (MPI-based fluid simulation, requiring constant inter-node communication) across multiple EC2 instances. Rather than each node independently processing its own task, multiple nodes must exchange data in real time and cooperate on a single job. What AWS Batch feature supports this kind of workload?

**Choices**
- A. AWS Batch array jobs (array jobs are optimized for running the same job many times independently in parallel — unsuitable for an MPI workload needing tight, real-time inter-node communication).
- B. **Use AWS Batch multi-node parallel jobs, grouping several EC2 instances into a single job unit, combined with a cluster placement group for low-latency inter-node communication, and coordinated via a framework like MPI.**
- C. Submit each node as an independent Batch job and implement inter-node communication via S3 as an intermediary (communication mediated by S3 has very high latency, unsuitable for MPI-based real-time, tightly coupled communication needs).
- D. Run each computation unit in parallel as a Lambda function (Lambda is optimized for independent, short executions and unsuitable for a tightly coupled HPC workload needing continuous, low-latency inter-node communication).

**Correct Answer: B**

**Explanation**
**AWS Batch multi-node parallel jobs** group several EC2 instances into **a single logical job**, supporting tightly coupled HPC workloads that use a framework like MPI (Message Passing Interface). Combining with a cluster placement group minimizes inter-node network latency, suiting computational tasks like fluid simulation where multiple nodes must continuously exchange data and cooperate.

**Why the other choices are wrong**
- A: Array jobs are optimized for independent repeated execution of the same job and don't support tight inter-node communication.
- C: Communication mediated by S3 has too much latency for MPI's real-time communication needs.
- D: Lambda is optimized for independent, short executions and doesn't support continuous, low-latency inter-node communication.

> 💡 **Exam tip**: For an HPC workload where multiple nodes **tightly communicate and cooperate via MPI, etc.**, on AWS Batch, **multi-node parallel jobs** is the standard answer.

## QUESTION 432

**Question**: A startup's data-analytics workload shows almost no usage initially, but runs intensively only during specific events (month-end closing, etc.) — a highly variable pattern. They don't want to provision a Redshift cluster continuously, and want to pay only for what they use. What's the solution?

**Choices**
- A. Run a minimally sized Redshift provisioned cluster continuously (still incurs cluster cost even during near-zero-usage periods, contradicting the "pay only for what you use" requirement).
- B. **Use Amazon Redshift Serverless, with no cluster provisioning; compute resources automatically scale when a query runs, and you pay only for the compute capacity used.**
- C. Fully migrate to RDS PostgreSQL (RDS is optimized for OLTP and is less suitable than Redshift-family services for large-scale analytical query performance in this workload).
- D. Manually create a Redshift cluster each time and delete it after use (requires a repetitive manual create/delete process — heavy operational burden, and slow to respond to unpredictable events).

**Correct Answer: B**

**Explanation**
**Amazon Redshift Serverless** requires no cluster provisioning in advance — it automatically scales compute resources (RPUs, Redshift Processing Units) when a query request comes in, and automatically scales down when finished. Since billing is based **only on the compute capacity actually used**, it's a cost-effective serverless data-warehouse solution precisely suited to an analytical workload with highly variable, unpredictable usage as in this question.

**Why the other choices are wrong**
- A: A continuously running cluster incurs cost even during idle periods, contradicting the requirement.
- C: RDS is optimized for OLTP; Redshift-family services are more suited to large-scale analytical workloads.
- D: Manual create/delete carries repetitive operational burden and response delay.

> 💡 **Exam tip**: For a **highly variable, unpredictable analytical workload**, to pay only for what's used with no cluster provisioning, **Amazon Redshift Serverless** is the standard answer.

## QUESTION 433

**Question**: A company wants to **immediately apply a transformation like adding a watermark or resizing** to original images stored in S3 at the moment a client requests them, but doesn't want to separately store/manage each transformed version in S3 (avoiding storage cost and sync burden). They want to keep the existing application's S3 GetObject request approach unchanged. What's the solution?

**Choices**
- A. Pre-transform images into several sizes/versions at upload time and store each as a separate object in S3 (requires separately storing/managing transformed versions, contradicting the "don't want to store separately" requirement, and incurs storage cost and sync burden when the original changes).
- B. **Use S3 Object Lambda, configured so that a Lambda function attached to a GetObject request fetches the original object and performs on-the-fly transformation (watermarking, resizing, etc.) before returning it. The application keeps using the same GetObject request approach as before.**
- C. Implement all transformation logic in CloudFront Functions (CloudFront Functions is a very lightweight JavaScript execution environment with tight execution-time/memory constraints, unsuitable for heavy processing like image watermarking/resizing — Lambda@Edge or S3 Object Lambda is more suitable for this purpose).
- D. Create a separate API Gateway + Lambda endpoint for every request to handle it (requires using a separate API endpoint different from the existing S3 GetObject request approach, contradicting the "keep the existing approach" requirement).

**Correct Answer: B**

**Explanation**
**S3 Object Lambda** attaches a Lambda function to the standard S3 **GetObject** API call, letting it fetch the original object at the moment the client requests it and **transform it on the fly** (watermarking, resizing, data masking, format conversion, etc.) before returning it. There's no need to separately store the transformed result in S3, avoiding storage cost and original-vs-transformed sync burden, while the application keeps using the same standard S3 GetObject request approach as before.

**Why the other choices are wrong**
- A: Pre-transforming and storing separately incurs exactly the storage/sync burden this question wants to avoid.
- C: CloudFront Functions is optimized for very lightweight processing, unsuitable for heavy work like image transformation.
- D: A separate API endpoint approach contradicts the requirement to keep the existing GetObject request approach.

> 💡 **Exam tip**: To **transform data on the fly at the moment of an S3 GetObject request**, with no separately stored transformed copy and the existing request approach unchanged, **S3 Object Lambda** is the standard answer.

## QUESTION 434

**Question**: A remote field worker needs to collect a small amount of data (a few TB or less) in an extremely space-constrained environment (inside a vehicle, a small work tent, etc.) and move it to AWS, or perform edge processing with very limited compute resources. Even a standard Snowball Edge is burdensome in size/weight for this ultra-compact, lightweight environment. What's the solution?

**Choices**

- C. Compress data and send it directly over the internet (the core issue is device-based processing in a physically space-constrained environment; if there's no nuance about avoiding internet transfer, this could also be considered, but if edge processing and physical transfer options are explicitly wanted, Snowcone is more specialized for this form-factor requirement).

**AWS Snowcone** is the smallest, lightest device in the AWS Snow family (about 2.1 kg), used for small-volume data transfer (up to 8TB on the SSD model) or lightweight edge computing in extremely space-constrained or mobility-critical environments. ## QUESTION 435

**Question**: A company wants to connect to many VPCs across multiple Regions via a Direct Connect gateway, but these VPCs are each connected to an individual Transit Gateway (rather than connecting to each VPC directly, going through a Transit Gateway). What type of virtual interface is needed for the Direct Connect gateway to integrate with a Transit Gateway?

**Choices**
- A. Use only a private virtual interface (private VIF) (a private VIF is used to connect a Direct Connect gateway to an individual VPC's virtual private gateway [VGW] — connecting to a Transit Gateway requires a different VIF type).

**Why the other choices are wrong**

> 💡 **Exam tip**: To connect a Direct Connect gateway **to a Transit Gateway**, a **transit virtual interface (transit VIF)** is the standard answer. Remember the distinction from a private VIF, used for connecting to an individual VPC (VGW).
