## QUESTION 221

**Question**: Accounts managed via Organizations. Need a list of all EC2 instances with underutilized CPU or memory, plus rightsizing recommendations. Minimal-effort solution?

**Choices**
- A. Install an AWS Marketplace CPU/memory monitoring tool on all EC2 instances + store results in S3 + implement a Python script to identify underutilized instances (a lot of direct implementation effort).
- B. **Use Systems Manager to install the CloudWatch agent on all EC2 instances. Retrieve resource optimization recommendations from AWS Cost Explorer in the organization's master account. Use the recommendations to rightsize underutilized instances across all organization accounts.**
- C. Install the CloudWatch agent + check Cost Explorer individually in each account (checking the whole organization at once from the master account is more efficient than per-account checks).
- D. Install the CloudWatch agent + a Lambda function extracting metrics + store in S3 + analyze with Athena (a lot of direct implementation effort).

**Correct Answer: B**

**Explanation**
**AWS Cost Explorer's Rightsizing Recommendations** automatically provide concrete instance-downsizing recommendations based on CPU/memory utilization, including memory metrics collected by the CloudWatch agent. Viewing this from the **organization's master account** gives a consolidated view across all organization accounts at once, meeting the requirement with minimal effort.

**Why the other choices are wrong**
- A, D: Directly implementing analysis logic via custom scripts/Lambda/Athena reinvents Cost Explorer's built-in feature — unnecessarily much effort.
- C: Checking each account individually is far less efficient than viewing the whole organization at once from the master account.

> 💡 **Exam tip**: For organization-wide **identification of underutilized EC2 instances and rightsizing recommendations**, **CloudWatch agent (memory metrics) + AWS Cost Explorer Rightsizing Recommendations from the master account** is the minimal-effort standard answer.

## QUESTION 222

**Question**: A custom network analysis software runs on an Auto Scaling group (3 EC2 instances) deployed via CloudFormation, with network routing configured to inspect traffic. When the analysis software stops working, the ASG replaces the instance, but **network routes aren't updated** when this happens. Which combination fixes this? (Choose three.)

**Choices**
- A. Create an alarm based on the EC2 status check metric so the ASG replaces failed instances (the ASG is already replacing them — the problem is routing isn't updated after replacement).
- B. **Update the CloudFormation template to install the CloudWatch agent on the EC2 instances. Configure the CloudWatch agent to send process metrics for the application.**
- C. Install the AWS Systems Manager Agent and configure it to send process metrics (the CloudWatch agent is the standard tool for metric collection; SSM Agent isn't for this purpose).
- D. **Create an alarm on a custom metric in CloudWatch for the failure scenario. Configure the alarm to publish a message to an SNS topic.**
- E. **Create a Lambda function that responds to the SNS message to remove the instance from service and update the network route to point to the replacement instance.**
- F. Write a condition in the CloudFormation template to update the network route when a replacement instance launches (CloudFormation itself isn't well-suited to dynamically updating stack resources in response to runtime events — a Lambda+EventBridge/SNS approach is standard).

**Correct Answer: B, D, E**

**Explanation**
Collecting application process metrics via the **CloudWatch agent** (B), creating a **custom metric alarm** based on this and publishing to **SNS** (D), and having **Lambda** respond to this SNS message to remove the failed instance from service and update the network route to the new instance (E) — this flow fully automates "application process failure → automatic detection → automatic routing update," the standard pattern.

**Why the other choices are wrong**
- A: The problem isn't that the ASG fails to replace instances — it already does. The issue is that **the network route isn't updated** after replacement, which this option doesn't address.
- C: The CloudWatch agent is the standard tool for collecting process metrics; the Systems Manager Agent isn't suited to this purpose.
- F: Static conditions in the CloudFormation template itself can't dynamically respond to runtime instance-replacement events to update routing — an event-driven Lambda is needed.

> 💡 **Exam tip**: To **automatically update network routes to match instances replaced by Auto Scaling**, the standard answer is the event-driven automation chain: **CloudWatch custom metric (application process health) → alarm → SNS → Lambda (routing update).**

## QUESTION 223

**Question**: A microservices-based VOD app: 5 million users at launch, growing to 30 million in 6 months. ECS (Fargate), using HTTPS. Updates must use **blue/green deployment**, with a load balancer distributing traffic to each ECS service, and the application must **auto-scale task count** in response to CloudWatch alarms.

**Choices**
- A. Blue/green + NLB + request a service quota increase (NLB isn't suited for HTTPS/L7 routing, and a quota increase isn't auto-scaling).
- B. Blue/green + NLB + Cluster Autoscaler (Cluster Autoscaler is a Kubernetes/EKS concept, different from ECS — a conceptual error, and NLB is also unsuitable).
- C. Blue/green + ALB + Cluster Autoscaler (Cluster Autoscaler isn't a native ECS feature — a conceptual error).
- D. **Configure the ECS service to use blue/green deployment type and an Application Load Balancer. Implement Service Auto Scaling for each ECS service.**

**Correct Answer: D**

**Explanation**
**ALB** (supporting L7 routing) is appropriate for HTTPS-based traffic distribution, and ECS blue/green deployment standardly uses ALB together with CodeDeploy. Automatically scaling task count in response to CloudWatch alarms is the native ECS feature **Service Auto Scaling** (Application Auto Scaling).

**Why the other choices are wrong**
- A, B: NLB is an L4 (TCP) load balancer; ALB is better suited for fine-grained HTTPS traffic routing, and ALB is also the standard combination for blue/green ECS deployment.
- B, C: **Cluster Autoscaler is a Kubernetes (EKS) concept** — no such feature name exists in ECS, which uses Service Auto Scaling instead.

> 💡 **Exam tip**: For **ECS blue/green deployment**, **ALB** (not NLB) is standard, and for auto-scaling task count, use **ECS Service Auto Scaling** — don't confuse "Cluster Autoscaler" (EKS/Kubernetes terminology) with ECS.

## QUESTION 224

**Question**: An ECS (EC2, ASG)+ECR containerized application. Every new image tag must be scanned for common vulnerabilities. Image tags with **high or critical severity findings must be automatically deleted**, and the deletion must notify the development team.

**Choices**
- A. **Configure scan on push in the repository. When a scan completes with high or critical severity findings, invoke an AWS Step Functions state machine via Amazon EventBridge. Use the state machine to delete the image tag and notify the development team via SNS.**
- B. Configure scan on push + push results to an SQS queue + invoke Lambda on new message + Lambda deletes the image tag + notify via SES (workable, but SES is a plain email-sending API, not an event trigger — A's EventBridge+Step Functions+SNS combination is more standard event-driven architecture).
- C. Schedule hourly manual image scans via Lambda + on completion, invoke a second Lambda via EventBridge + delete image tags + SNS notification (a periodic schedule introduces delay relative to the "as soon as a new image version is uploaded" requirement — scan on push is more appropriate).
- D. Configure periodic image scanning + SQS + Step Functions + SES notification (periodic scanning lacks immediacy, and SES isn't an event trigger service).

**Correct Answer: A**

**Explanation**
ECR's **"scan on push"** feature scans immediately every time a new image is uploaded, and detecting the scan-completion event (with critical/high findings) via **EventBridge** to invoke **Step Functions**, orchestrating image tag deletion and **SNS notification** — exactly satisfies this requirement (immediacy + automatic deletion + notification) as a fully event-driven serverless flow.

**Why the other choices are wrong**
- B, D: **Amazon SES is an email-sending API**, not a service for subscribing to/routing events, so it's unsuitable for directly wiring into a "notify on completion" flow (SNS is standard).
- C, D: Hourly/periodic scanning reacts later than the "as soon as a new image version is uploaded" immediacy requirement — scan on push is more accurate.

> 💡 **Exam tip**: ECR's **scan on push + EventBridge (scan-completion event) + Step Functions (deletion orchestration) + SNS (notification)** is the standard answer for automatic vulnerable-image deletion/notification. Remember SES is a plain sending API, not an event trigger.

## QUESTION 225

**Question**: Multiple accounts managed via Organizations, with EC2/Fargate/Lambda workloads. Some workloads have unpredictable demand (monthly usage fluctuates). Optimize compute costs over the next 3 years, based on a 6-month average usage across each account organization-wide. Which solution provides the greatest cost savings for all compute usage in the organization?

**Choices**
- A. Purchase Reserved Instances matching the most common EC2 instance sizes/counts across member accounts (RIs are tied to specific instance types/families, lacking flexibility for unpredictable, varied workloads across EC2+Fargate+Lambda).
- B. **Purchase an organization-wide Compute Savings Plan from the master account, using master-account-level recommendations.**
- C. Purchase individual RIs per high-EC2-usage member account based on the last 6 months' data (per-account individual purchases are less efficient than organization-wide optimization, and RIs are tied to instance types).
- D. Purchase individual EC2 Instance Savings Plans per member account from the master account based on the last 6 months' EC2 usage data (EC2 Instance SPs are tied to an instance family, less flexible than Compute SPs).

**Correct Answer: B**

**Explanation**
**Compute Savings Plans** apply a discount across EC2, Fargate, and Lambda **collectively** (based on hourly $ commitment), independent of instance type/family/Region, offering the greatest flexibility and savings for unpredictable, diverse workloads. Purchasing from the **organization's master account** based on organization-wide recommendations consolidates all accounts' usage under one commitment, maximizing utilization.

**Why the other choices are wrong**
- A, C: Reserved Instances commit to a specific instance type/family, unable to flexibly handle mixed workloads including Fargate/Lambda or unpredictable demand shifts.
- D: EC2 Instance Savings Plans are more tied to a specific instance family than Compute Savings Plans, and purchasing per-account is also less efficient than organization-wide consolidated optimization.

> 💡 **Exam tip**: For maximum cost savings in an organization mixing **EC2+Fargate+Lambda** with **unpredictable demand**, purchase **Compute Savings Plans** (most flexible) **organization-wide from the master account** — the standard answer.

## QUESTION 226

**Question**: Hundreds of AWS accounts, Organizations (all features on). The finance team needs an email notification when the organization's AWS costs exceed **80%** of the allocated budget. Cost-tracking/notification solution?

**Choices**
- A. **Create a budget with a daily period using AWS Budgets in the organization's master account. Add an alert threshold set to 80%. Notify the finance team via SNS.**
- B. Set up Trusted Advisor's organizational view in the master account + generate a cost optimization organizational report + set an 80% alert threshold (Trusted Advisor doesn't provide this kind of real-time threshold alerting for budget overruns — a conceptual error).
- C. Register the organization with Control Tower + enable optional cost control guardrails + set the guardrail parameter to 80% (Control Tower guardrails are primarily for policy compliance, not a dedicated budget-overrun alert feature).
- D. Configure member accounts to store daily AWS Cost and Usage Reports in an organization S3 bucket in the master account + schedule a daily Athena query via EventBridge to calculate organization cost + configure a CloudWatch alarm when total cost exceeds 80% of the budget + notify via SNS (far more direct implementation required than AWS Budgets).

**Correct Answer: A**

**Explanation**
**AWS Budgets** natively supports setting a budget targeting the entire organization's (all linked accounts') costs from the master account, and automatically sending a notification via **SNS** upon reaching an **alert threshold (e.g., 80%)** — exactly the service purpose-built for this requirement.

**Why the other choices are wrong**
- B: Trusted Advisor is a cost-optimization recommendation tool, not one offering percentage-threshold alerts against a specific budget.
- C: Control Tower's guardrails serve policy/compliance purposes; AWS Budgets is the tool purpose-built for this kind of fine-grained budget threshold alert.
- D: A custom implementation (S3+Athena+CloudWatch) reinvents a feature AWS Budgets already provides out of the box — unnecessarily much effort.

> 💡 **Exam tip**: For **notification when organization-wide cost exceeds a certain % of the budget**, **AWS Budgets (master account) + alert threshold + SNS** is the simplest, standard answer.

## QUESTION 227

**Question**: An art auction service with North American and European users. A us-east-1 EC2 application, uploading large images to a central S3 bucket (us-east-1). European users report slow upload speeds. How to improve?

**Choices**
- A. Redeploy the application to use S3 multipart upload (splits a single large file into parallel parts, improving reliability, but doesn't reduce the fundamental latency from geographic distance).
- B. Create a CloudFront distribution + designate the application as a custom origin (CloudFront is primarily for accelerating downloads/distribution; S3 Transfer Acceleration is more direct for upload acceleration itself).
- C. **Configure the bucket to use S3 Transfer Acceleration.**
- D. Create an EC2 Auto Scaling group (scaling the application server is unrelated to European users' geographic latency issue).

**Correct Answer: C**

**Explanation**
**S3 Transfer Acceleration** leverages CloudFront's global edge locations to first receive uploads at an edge near the user, then deliver quickly to the destination bucket over AWS's optimized backbone network — specifically designed to improve upload speeds for geographically distant users (Europe).

**Why the other choices are wrong**
- A: Multipart upload splits a large file into parallel chunks for reliability/retry efficiency, but doesn't reduce the fundamental round-trip latency caused by geographic distance.
- B: CloudFront is primarily optimized for content delivery (download) acceleration; Transfer Acceleration is the more direct feature for upload acceleration.
- D: EC2 scaling addresses server processing capacity, unrelated to Europe-US geographic network latency.

> 💡 **Exam tip**: To improve **S3 upload speed for geographically distant users**, **S3 Transfer Acceleration** (leveraging CloudFront edges) is the standard answer. Remember: multipart upload improves reliability, while Transfer Acceleration improves latency.

## QUESTION 228

**Question**: A multi-tier web application (web+app+DB tiers) is containerized and moved from on-premises to AWS. Needs fault tolerance/scalability. Some frequently-accessed data must **always be available** on application servers. The frontend web server needs **session persistence** and must scale with increasing traffic. Minimal operational overhead?

**Choices**
- A. Fargate ECS + EFS for shared data between web-app tiers + store session data in SQS (SQS is a message queue, unsuitable as a session-state store — a conceptual error).
- B. EC2 ECS + ElastiCache for Redis (session) + EBS Multi-Attach on EC2 across multiple AZs (EBS Multi-Attach only works within the same AZ, conflicting with the "multiple AZs" requirement).
- C. EKS (managed node group) + ReplicaSet + mount EFS to all pods to store session data (technically usable, but DynamoDB is more suited and lower-latency for short key-value lookups like sessions).
- D. **Deploy the application on EKS. Configure EKS to use managed node groups. Run the web server/application as a Kubernetes deployment on the EKS cluster. Store frontend web server session data in a DynamoDB table. Create an EFS volume mounted by all applications on deployment.**

**Correct Answer: D**

**Explanation**
An **EKS managed node group** reduces the operational burden of container orchestration; **frequently-accessed data** (that must always be available to app servers) is stored in **EFS** (shared access across multiple containers/AZs); and **session data** is stored in **DynamoDB**, optimized for low-latency key-value lookups, keeping sessions consistent regardless of which instance a web request is routed to — satisfying all requirements.

**Why the other choices are wrong**
- A: SQS is a message queue service, not meant for storing queryable session state.
- B: EBS Multi-Attach is supported **only within the same Availability Zone**, unsuitable for sharing across instances spread over multiple AZs.
- C: EFS can technically be used for session storage too, but DynamoDB is better suited and lower-latency for short key-value data like sessions, while EFS is more appropriate for frequently-accessed file-type data (separating roles as in D is optimal).

> 💡 **Exam tip**: For containerized workloads, the standard pattern is separating roles: **EFS** for **shared file data**, **DynamoDB** (or ElastiCache) for **session state**. Remember EBS Multi-Attach has a same-AZ constraint.

## QUESTION 229

**Question**: Migrate a legacy Microsoft SQL Server database to a modern data architecture on AWS, with **almost no downtime.**

**Choices**
- A. Application Migration Service + SCT + in-place upgrade then cutover + export to Aurora Serverless (many steps, complex, not optimized for minimizing downtime).
- B. DMS (rehost) + S3 target + CDC replication + once fully synced, load from S3 into RDS for SQL Server (an added intermediate S3 step, more complex).
- C. **Use the database's native high-availability tools. Connect the source system to Amazon RDS for SQL Server. Configure replication accordingly. Once data replication completes, cut over the workload to Amazon RDS for SQL Server.**
- D. Application Migration Service + rehost on EC2 + once data replication completes, detach and move the database to RDS + reconnect (a two-stage move — first to EC2, then to RDS — is inefficient).

**Correct Answer: C**

**Explanation**
Using SQL Server's **native (built-in) high-availability/replication tools** (e.g., Always On Availability Groups, transactional replication) to configure replication between the source and RDS for SQL Server, then cutting over once data is fully synchronized, is the standard method leveraging tools familiar to the SQL Server ecosystem to minimize downtime.

**Why the other choices are wrong**
- A: The multi-stage process of in-place upgrade then re-exporting to Aurora Serverless is complex and not optimized for minimizing downtime.
- B, D: Going through DMS+S3 or first moving to EC2 then to RDS adds unnecessary intermediate steps, increasing complexity and downtime risk.

> 💡 **Exam tip**: For migrating SQL Server to AWS with **near-zero downtime**, leveraging SQL Server's **own native high-availability/replication tools** to sync with RDS before cutting over is often the standard answer — the key is avoiding unnecessary intermediate storage (S3) or double-migration stages.

## QUESTION 230

**Question**: Single Region, multiple AZs, managing two organizations under Organizations post-acquisition. One organization has PrivateLink-based VPC endpoint service applications (service providers); the other has service consumer apps. **Data transfer charges are far higher than expected.** Guidelines to minimize cost? (Choose two.)

**Choices**
- A. Share the service provider subnets with other accounts via RAM (subnet sharing itself doesn't directly address the cross-AZ/cross-organization data transfer cost problem).
- B. **Place service provider applications and service consumer applications in AWS accounts within the same organization.**
- C. Turn off cross-zone load balancing for the NLB in all service provider deployments (turning off cross-zone could cause availability/distribution issues and isn't the key fix for minimizing data transfer cost).
- D. **Use the endpoint's local (per-Availability-Zone) DNS name to ensure service consumers use the endpoint service in the same Availability Zone (avoiding cross-AZ data transfer).**
- E. Create a Savings Plan covering the organization's planned cross-AZ data transfer usage (Savings Plans discount compute usage, not the cross-AZ data transfer charge itself).

**Correct Answer: B, D**

**Explanation**
Communication **across different organizations (separate account groups)** via PrivateLink often incurs data transfer charges regardless of organizational boundaries, so placing tightly-communicating services **within the same organization (account)** reduces cost (B). Also, since PrivateLink endpoints provide **per-Availability-Zone local DNS names**, having consumers use the endpoint in the **same AZ** avoids **cross-AZ data transfer charges** (D).

**Why the other choices are wrong**
- A: Subnet sharing itself doesn't directly address this scenario's key cost driver (cross-AZ/cross-organization data transfer).
- C: Turning off cross-zone load balancing risks reduced availability and isn't the key fix for cost reduction.
- E: Savings Plans discount compute usage — they don't reduce the data transfer charge itself.

> 💡 **Exam tip**: In a PrivateLink-based architecture, to **reduce data transfer costs**: ① place tightly-communicating services within the **same account/organization**, and ② have consumers use the endpoint's **per-AZ local DNS** to communicate **within the same AZ.**

## QUESTION 231

**Question**: An on-premises SQL Server generates a 200GB export to a local drive every night. Move backups to S3 for stronger cloud storage. A 10Gbps Direct Connect connection exists. Most cost-effective solution?

**Choices**
- A. **Create a new S3 bucket. Deploy an AWS Storage Gateway file gateway inside the VPC connected to Direct Connect. Create a new SMB file share. Write the nightly database export to this SMB file share.**
- B. Single-AZ FSx for Windows File Server + SMB share + enable nightly backups (FSx is itself file server storage separate from the goal of "moving to S3" — would require an additional S3 backup step, more complex than A).
- C. Multi-AZ FSx for Windows File Server (costs more than single-AZ, and doesn't align with the goal of storing directly to S3).
- D. New S3 bucket + Storage Gateway **volume** gateway + SMB share + automate copying this data to S3 (volume gateway is for block storage — for a file-based SMB share scenario, file gateway is more direct and simpler).

**Correct Answer: A**

**Explanation**
**AWS Storage Gateway file gateway** lets an on-premises application (SQL Server) write to what looks like a local file via SMB/NFS, while automatically storing it as an object directly in **S3** in the background — exactly matching this scenario (moving file-based backups to S3). No separate copy-automation step is needed; the file gateway itself handles S3 storage.

**Why the other choices are wrong**
- B, C: FSx is its own complete file server storage; if the goal is moving data to S3, file gateway is more direct. Multi-AZ FSx (C) is unnecessarily more costly.
- D: Volume gateway is for block (iSCSI)-based storage; file gateway better fits a backup scenario via SMB file shares, and unlike D, doesn't require a separate "copy automation" configuration.

> 💡 **Exam tip**: To store an on-premises application's **file-based backups directly to S3**, **Storage Gateway file gateway** (SMB/NFS share → automatic S3 storage) is the most direct, cost-effective standard answer.

## QUESTION 232

**Question**: Establishing an on-premises-to-AWS connection. Requires **transitive routing** between VPCs to connect all VPCs across multiple Regions. Also needs to reduce outbound traffic costs, increase bandwidth throughput, and provide a consistent network experience for end users.

**Choices**
- A. Site-to-Site VPN (central VPC) + VPC peering from the central VPC to every other VPC (VPN has limited bandwidth throughput, and VPC peering is non-transitive, inefficient for connecting many VPCs).
- B. **Create a Direct Connect connection + provision a transit VIF connected to a Direct Connect gateway + in each Region, use a Transit Gateway to connect the DXGW to every other VPC.**
- C. Site-to-Site VPN (central VPC) + connect every other VPC via a Transit Gateway with dynamic routing (VPN has lower bandwidth/consistency than Direct Connect).
- D. Direct Connect + Site-to-Site VPN connections between every VPC in each Region + VPC peering from the central VPC (adding VPN plus non-transitive peering is both inefficient).

**Correct Answer: B**

**Explanation**
Combining **Direct Connect** (higher bandwidth, more consistent network performance, lower outbound cost than VPN) with a **transit VIF + Direct Connect Gateway**, and connecting the DXGW to multiple VPCs via **Transit Gateway** in each Region, achieves transitive routing (one DX connection reaching every VPC across all Regions) while meeting all three requirements (cost, bandwidth, consistency).

**Why the other choices are wrong**
- A, C, D: Site-to-Site VPN travels over the internet, having more limited bandwidth and a less consistent network experience than Direct Connect, and VPC peering is non-transitive, inefficient for connecting many VPCs.

> 💡 **Exam tip**: When you need **transitive routing across multi-Region VPCs + high bandwidth + consistent network experience + low cost**, **Direct Connect + transit VIF + Direct Connect Gateway + (per-Region) Transit Gateway** is the standard answer.

## QUESTION 233

**Question**: Migrating development/production workloads to a new Organizations organization, with consolidated billing in the master account. In the master account, create an IAM user able to **stop or terminate resources in both member accounts.**

**Choices**
- A. Create an IAM user + cross-account role in the master account, configure a least-privilege cross-account role in the member accounts (describing the role as being in the master account doesn't match the actual cross-account access pattern — the role must live in the target account).
- B. Create IAM users in each member account + a least-privilege cross-account role in the master account + grant the users access to the role via a trust policy (having the user needing permissions reside in the member account rather than the master account mismatches the goal of "control from the master account").
- C. Create an IAM user in the master account + a least-privilege IAM group in the member accounts + add the user to each group (IAM groups cannot directly add users from another account across account boundaries — a conceptual error; cross-account access must go through roles).
- D. **Create an IAM user in the master account. Create a least-privilege cross-account role in the member accounts. Use a trust policy to grant the master account's IAM user access to this role.**

**Correct Answer: D**

**Explanation**
The standard **cross-account access pattern** is creating a **least-privilege IAM role** in the target (member) account, with the role's **trust policy** naming the requesting principal (the master account's IAM user). When the master account's IAM user assumes this role, it can control the member account's resources (e.g., stopping/terminating EC2).

**Why the other choices are wrong**
- A, B: The relationship between where the role should live (the target account holding the resources) and who should be trusted (the user in the account requesting access) is reversed, mismatching the actual cross-account access pattern.
- C: **IAM groups cannot add users from another account across account boundaries as members** — cross-account access must always go through a role.

> 💡 **Exam tip**: The standard cross-account access pattern is **creating a least-privilege role in the target account holding the resources, with its trust policy naming the requesting principal (an IAM user/role in another account).** Remember IAM groups cannot cross account boundaries.

## QUESTION 234

**Question**: Hundreds of on-premises Windows servers (mounting a common share) need disaster recovery. RTO 15 minutes, RPO 5 minutes. Must support **failover and failback.** Most cost-effective solution?

**Choices**
- A. Storage Gateway file gateway + daily backups + S3 storage + on disaster, restore on-premises servers from backup + run on EC2 during failback (daily backups don't meet a 5-minute RPO).
- B. CloudFormation templates (infrastructure creation) + DataSync replicating data to EFS + on disaster, deploy/restore templates via CodePipeline + DataSync for failback (restoring hundreds of servers from scratch via CloudFormation is hard to complete within a 15-minute RTO).
- C. A CDK pipeline maintaining a multi-site active-active environment + replicate data via s3 sync (always running active-active is too costly, mismatching "most cost-effective").
- D. **Replicate on-premises servers using AWS Elastic Disaster Recovery. Use AWS DataSync to replicate data to an Amazon FSx for Windows File Server file system. Mount the file system to AWS servers. On disaster, fail the on-premises servers over to AWS. Use Elastic Disaster Recovery to fail back to new or existing servers.**

**Correct Answer: D**

**Explanation**
**AWS Elastic Disaster Recovery (DRS)** provides continuous (second-level) block-level replication meeting short RPO/RTO, and **natively supports both failover and failback.** The shared file (common share) is replicated via DataSync to **FSx for Windows File Server**, which supports native Windows protocols, so servers can access the same file share once in AWS.

**Why the other choices are wrong**
- A: A daily backup cycle cannot meet a 5-minute RPO.
- B: Provisioning/restoring infrastructure for hundreds of servers from scratch via CloudFormation takes too long to meet a 15-minute RTO.
- C: An always-on multi-site active-active setup runs two sites simultaneously — too expensive to be "most cost-effective."

> 💡 **Exam tip**: For DR of hundreds of servers needing **short RPO/RTO with failover/failback support**, **AWS Elastic Disaster Recovery (DRS)** is the standard answer, naturally paired with **FSx for Windows File Server** (native Windows protocol support) for shared file storage replication.

## QUESTION 235

**Question**: A tightly-coupled HPC cluster generating many shared files on EFS. Worked well with 100 EC2 instances, but **performance dropped far below expected when scaled to 1,000.** Which design achieves maximum performance? (Choose three.)

**Choices**
- A. **Ensure the HPC cluster launches within a single Availability Zone (avoiding cross-AZ latency).**
- B. Launch EC2 instances attaching elastic network interfaces in multiples of 4 (not a standard element of HPC performance improvement — an arbitrary configuration lacking justification).
- C. **Choose EC2 instance types with Elastic Fabric Adapter (EFA) enabled (key for low-latency inter-node communication in tightly-coupled HPC).**
- D. Ensure the cluster launches across multiple Availability Zones (tightly-coupled HPC is highly sensitive to inter-node latency, so spreading across multiple AZs would actually degrade performance — conflicts with A).
- E. Replace Amazon EFS with multiple Amazon EBS volumes in a RAID array (EBS isn't as optimized as EFS/FSx for large-scale parallel shared access across many instances).
- F. **Replace Amazon EFS with Amazon FSx for Lustre (a high-performance parallel file system optimized for HPC workloads).**

**Correct Answer: A, C, F**

**Explanation**
Tightly-coupled HPC workloads are extremely sensitive to inter-node communication latency, so running within a **single Availability Zone** (A, avoiding cross-AZ latency), using **EFA** (C, an HPC-specialized network interface for low-latency, high-throughput inter-node communication), and switching from general-purpose EFS to **FSx for Lustre** (F, a parallel file system optimized for HPC) is the standard combination to maximize performance at a 1,000-node scale.

**Why the other choices are wrong**
- B: Attaching ENIs "in multiples of 4" isn't a standard element of HPC performance optimization.
- D: Spreading a tightly-coupled workload across multiple AZs adds cross-AZ network latency, actually degrading performance (conflicts with choice A).
- E: RAID-ing EBS volumes can achieve some performance, but FSx for Lustre is far more specialized for large-scale parallel shared access across hundreds-to-thousands of instances.

> 💡 **Exam tip**: To maximize performance of a **tightly-coupled HPC cluster**, the standard combination is: ① **single AZ** (avoiding latency), ② **EFA** (low-latency networking), ③ **FSx for Lustre** (high-performance parallel file system). ## QUESTION 240

**Question**: A web+app+NoSQL 3-tier application reference architecture. Requirements: ① high availability within the Region, ② failover to another Region for disaster recovery **within 1 minute**, ③ the most efficient solution while minimizing impact on user experience. (Choose three.)

**Choices**
- A. A 100/0 Route 53 weighted routing policy across two chosen Regions + TTL of 1 hour (weighted routing isn't a failover mechanism, and a 1-hour TTL could take up to an hour to switch — clearly violating "within 1 minute").
- B. **A Route 53 failover routing policy from the primary Region to the DR Region. TTL of 30 seconds.**
- C. **Use DynamoDB global tables so data is accessible in both chosen Regions.**
- D. Back up DynamoDB data every 60 minutes, write it to S3 + use S3 CRR to copy to the DR Region + in a DR scenario, a script imports data back into DynamoDB (a 60-minute backup cycle and manual import script utterly fail the 1-minute RTO/data-freshness requirement).
- E. **Implement a warm standby model with Auto Scaling groups across multiple AZs for the web/app tiers. Use Regional Reserved Instances for the minimum server count and On-Demand instances for additional resources.**
- F. Auto Scaling groups across multiple AZs for web/app tiers + use Spot Instances for needed resources (Spot's interruption risk conflicts with the "immediately available" warm-standby requirement for the DR target Region).

**Correct Answer: B, C, E**

**Explanation**
**Route 53 failover routing + a short TTL (30 seconds)** (B) achieves fast DNS switching within 1 minute, **DynamoDB global tables** (C) ensure both Regions always have access to the latest data, and a **warm standby** (Auto Scaling across multiple AZs, minimum capacity via Reserved Instances + additional via On-Demand) (E) reduces normal-time costs while keeping the environment ready to scale immediately on failure — the most efficient combination meeting all three requirements.

**Why the other choices are wrong**
- A: Weighted routing is for traffic distribution, not a failover mechanism, and a 1-hour TTL falls far short of "within 1 minute."
- D: A 60-minute backup cycle with manual script-based restoration can't meet a 1-minute RTO or data-freshness requirement at all.
- F: Spot Instances can be reclaimed at any time, unsuitable for the "must be immediately usable" warm-standby role in the DR target Region during a disaster.

> 💡 **Exam tip**: For **cross-Region failover within 1 minute**, use **Route 53 failover routing + a short TTL**; for the data layer, use **DynamoDB global tables**; for the compute layer, combine **warm standby (mixed Reserved + On-Demand)** — the standard answer. Remember Spot Instances conflict with the DR target Region's immediate-availability requirement.
