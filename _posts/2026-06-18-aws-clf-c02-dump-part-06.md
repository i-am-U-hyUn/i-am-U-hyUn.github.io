## Q1. AWS 계정 액세스 보호 보안 조치 (두 개 선택)

다음 중 AWS 계정에 대한 액세스를 보호하는 보안 조치는 무엇입니까? (두 개를 선택합니다.)

- A. AWS CloudTrail을 사용합니다.
- B. IAM 사용자에게 최소한의 권한 액세스 부여
- C. 하나의 IAM 사용자를 생성하고 많은 개발자 및 사용자와 공유합니다.
- D. Amazon CloudFront 사용
- E. 권한 있는 사용자에 대한 MFA(다중 인증) 활성화

**정답: B, E**

✅ **B. IAM 사용자에게 최소한의 권한 액세스 부여**: 최소 권한 원칙(Principle of Least Privilege)은 AWS 보안의 핵심 원칙으로, 각 사용자에게 업무 수행에 필요한 최소한의 권한만 부여하여 잠재적인 보안 위협을 최소화합니다. 권한이 과도하게 부여될 경우 계정 탈취 시 피해 범위가 커질 수 있습니다.

✅ **E. 권한 있는 사용자에 대한 MFA(다중 인증) 활성화**: MFA는 비밀번호 외에 추가적인 인증 수단(OTP 앱, 하드웨어 키 등)을 요구하여, 비밀번호가 유출되더라도 계정을 보호할 수 있는 강력한 보안 계층을 제공합니다.

❌ **A. AWS CloudTrail을 사용합니다.**: CloudTrail은 API 호출 기록을 감사(Audit)하는 서비스로, 보안 모니터링에 유용하지만 계정 액세스 자체를 "보호"하는 수단은 아닙니다. 로그 기록이지 접근 차단이나 인증 강화 메커니즘이 아닙니다.

❌ **C. 하나의 IAM 사용자를 생성하고 많은 개발자 및 사용자와 공유합니다.**: IAM 사용자를 공유하는 것은 보안 모범 사례에 완전히 반하는 행위입니다. 각 사용자에게 개별 계정을 부여해야 책임 추적과 최소 권한 적용이 가능합니다.

❌ **D. Amazon CloudFront 사용**: CloudFront는 콘텐츠 전송 네트워크(CDN) 서비스로, 웹 콘텐츠 배포 속도 향상에 사용됩니다. AWS 계정 액세스 보호와는 직접적인 관련이 없습니다.

💡 **시험 꿀팁**: AWS 계정 보안 = **최소 권한 원칙(Least Privilege)** + **MFA 활성화** + **루트 계정 사용 최소화**. CloudTrail은 감사(audit) 도구이지 보호(protection) 도구가 아님을 구분하세요.

## Q2. 하이브리드 스토리지 서비스

사내 애플리케이션이 클라우드 스토리지를 원활하게 사용할 수 있도록 지원하는 하이브리드 스토리지 서비스는 무엇입니까?

- A. 아마존 빙하 (Amazon Glacier)
- B. AWS 스노우볼 (AWS Snowball)
- C. AWS 스토리지 게이트웨이 (AWS Storage Gateway)
- D. Amazon Elastic Block 스토리지(Amazon EBS)

**정답: C**

✅ **C. AWS 스토리지 게이트웨이 (AWS Storage Gateway)**: Storage Gateway는 온프레미스 환경과 AWS 클라우드 스토리지를 연결하는 하이브리드 스토리지 서비스입니다. 기존 사내 애플리케이션이 변경 없이 클라우드 스토리지(S3, EBS, Glacier 등)를 로컬 스토리지처럼 사용할 수 있도록 표준 스토리지 프로토콜(NFS, SMB, iSCSI)을 제공합니다.

❌ **A. 아마존 빙하 (Amazon Glacier)**: Amazon S3 Glacier는 저비용 장기 아카이브 스토리지 서비스입니다. 하이브리드 연결 기능을 제공하지 않으며, 데이터 검색에 시간이 걸리는 콜드 스토리지입니다.

❌ **B. AWS 스노우볼 (AWS Snowball)**: Snowball은 대용량 데이터를 물리적 디바이스를 통해 AWS로 이전하는 데이터 마이그레이션 서비스입니다. 지속적인 하이브리드 스토리지 연결이 아닌 일회성 데이터 전송에 사용됩니다.

❌ **D. Amazon Elastic Block 스토리지(Amazon EBS)**: EBS는 EC2 인스턴스에 연결하여 사용하는 블록 스토리지로, 온프레미스 환경과의 하이브리드 연결을 지원하지 않습니다.

💡 **시험 꿀팁**: **하이브리드 스토리지 = AWS Storage Gateway**. "온프레미스 + 클라우드", "사내 애플리케이션 + AWS 스토리지" 키워드가 나오면 Storage Gateway를 선택하세요. Snowball은 "대량 데이터 물리적 이전"에 사용됩니다.

## Q3. 고객이 직접 관리해야 하는 책임 (공유 책임 모델)

다음 중 운영 체제 구성, 보안 패치 및 네트워킹을 유지하는 고객의 책임은 무엇입니까?

- A. Amazon RDS
- B. 아마존 EC2
- C. Amazon ElastiCache
- D. AWS Fargate

**정답: B**

✅ **B. 아마존 EC2**: EC2는 IaaS(Infrastructure as a Service) 형태의 서비스로, AWS는 하이퍼바이저 아래의 물리적 인프라만 관리합니다. 고객은 운영 체제 설치 및 패치, 보안 그룹 설정, 네트워크 구성, 미들웨어 관리 등 OS 수준 이상의 모든 작업을 직접 책임져야 합니다.

❌ **A. Amazon RDS**: RDS는 관리형 데이터베이스 서비스로, AWS가 OS 패치, 데이터베이스 엔진 업데이트, 백업 등을 관리합니다. 고객은 데이터와 DB 설정만 관리하면 됩니다.

❌ **C. Amazon ElastiCache**: ElastiCache는 완전 관리형 인메모리 캐싱 서비스로, AWS가 OS 및 캐시 엔진(Redis, Memcached)의 유지보수를 담당합니다. 고객은 캐시 설정과 데이터만 관리합니다.

❌ **D. AWS Fargate**: Fargate는 서버리스 컨테이너 실행 서비스로, 서버(OS, 패치, 인프라)를 AWS가 완전히 관리합니다. 고객은 컨테이너 이미지와 애플리케이션 코드에만 집중하면 됩니다.

💡 **시험 꿀팁**: 공유 책임 모델에서 **EC2 = 고객이 OS 관리** (IaaS), **RDS/ElastiCache/Fargate = AWS가 OS 관리** (PaaS/관리형). "운영 체제 패치를 고객이 직접" → EC2가 정답입니다.

## Q4. 클라우드 아키텍처 설계 원칙

다음 중 클라우드 애플리케이션을 설계할 때 중요한 아키텍처 설계 원칙은 무엇입니까?

- A. 여러 가용성 영역을 사용합니다.
- B. 단단히 결합된 구성 요소를 사용합니다.
- C. 오픈 소스 소프트웨어를 사용합니다.
- D. 추가 용량 프로비저닝

**정답: A**

✅ **A. 여러 가용성 영역을 사용합니다.**: 여러 가용성 영역(Multi-AZ)에 리소스를 분산하면 단일 데이터 센터 장애가 발생해도 서비스가 지속됩니다. 이는 AWS Well-Architected Framework의 핵심 원칙 중 하나인 고가용성(High Availability)과 내결함성(Fault Tolerance)을 달성하는 방법입니다.

❌ **B. 단단히 결합된 구성 요소를 사용합니다.**: 느슨한 결합(Loose Coupling)이 클라우드 아키텍처 원칙입니다. 구성 요소 간 의존성을 최소화하면 하나의 컴포넌트 장애가 전체 시스템에 영향을 주지 않아 복원력이 높아집니다.

❌ **C. 오픈 소스 소프트웨어를 사용합니다.**: 오픈 소스 사용은 비용 절감에 도움이 될 수 있지만, AWS 아키텍처 설계의 핵심 원칙이 아닙니다. Well-Architected Framework에 명시된 원칙이 아닙니다.

❌ **D. 추가 용량 프로비저닝**: 클라우드의 핵심 장점은 필요한 만큼만 사용하는 탄력성(Elasticity)입니다. 미리 과도한 용량을 프로비저닝하는 것은 온프레미스 방식으로, 클라우드 원칙에 반합니다.

💡 **시험 꿀팁**: AWS Well-Architected Framework 핵심 원칙 = **Multi-AZ(고가용성)** + **느슨한 결합(Loose Coupling)** + **탄력성(Elasticity)** + **자동화**. "단단히 결합"은 무조건 오답입니다.

## Q5. Amazon RDS의 이점

Amazon RDS(Amazon Relational Database Service)는 다음 중 기존 데이터베이스 관리에 비해 어떤 이점을 제공합니까?

- A. AWS는 Amazon RDS 테이블에 저장된 데이터를 관리합니다.
- B. AWS는 운영체제의 유지보수를 관리합니다.
- C. AWS는 요청 시 인스턴스 유형을 자동으로 확장합니다.
- D. AWS는 데이터베이스 유형을 관리합니다.

**정답: B**

✅ **B. AWS는 운영체제의 유지보수를 관리합니다.**: Amazon RDS는 관리형 데이터베이스 서비스로, 운영 체제 패치, 데이터베이스 엔진 업데이트, 백업, 복제 등 인프라 수준의 유지보수를 AWS가 담당합니다. 이를 통해 고객은 DB 관리 작업 대신 애플리케이션 개발에 집중할 수 있습니다.

❌ **A. AWS는 Amazon RDS 테이블에 저장된 데이터를 관리합니다.**: 저장된 데이터와 데이터 구조(스키마, 테이블)는 여전히 고객의 책임입니다. AWS는 데이터의 내용을 관리하지 않으며, 이는 공유 책임 모델에 따른 고객 영역입니다.

❌ **C. AWS는 요청 시 인스턴스 유형을 자동으로 확장합니다.**: RDS의 인스턴스 유형 변경(스케일 업/다운)은 자동으로 이루어지지 않으며, 고객이 직접 변경을 요청해야 합니다. 자동 스토리지 확장(Auto Scaling)은 지원하지만 인스턴스 유형 자동 변경은 아닙니다.

❌ **D. AWS는 데이터베이스 유형을 관리합니다.**: 어떤 데이터베이스 엔진(MySQL, PostgreSQL, Oracle 등)을 사용할지는 고객이 결정합니다. AWS는 선택된 엔진을 운영할 뿐, 데이터베이스 유형 선택을 관리하지 않습니다.

💡 **시험 꿀팁**: RDS의 핵심 장점 = **AWS가 OS 패치/백업/복제 관리** (언더더후드). 고객은 **데이터, 스키마, 접근 권한**만 관리. "데이터는 항상 고객 책임"임을 기억하세요.

## Q6. 데이터베이스 쿼리 결과 캐싱 서비스

데이터베이스 액세스 부하를 줄이는 데 도움이 되는 공통 데이터베이스 쿼리 결과를 저장하는 데 가장 적합한 서비스는 무엇입니까?

- A. Amazon 기계 학습 (Amazon Machine Learning)
- B. Amazon SQS
- C. Amazon ElastiCache
- D. Amazon EC2 인스턴스 저장소

**정답: C**

✅ **C. Amazon ElastiCache**: ElastiCache는 완전 관리형 인메모리 캐싱 서비스(Redis 또는 Memcached 기반)로, 자주 조회되는 데이터베이스 쿼리 결과를 메모리에 저장합니다. 이를 통해 반복적인 DB 요청을 캐시에서 처리하여 응답 속도를 대폭 향상시키고 데이터베이스 부하를 줄입니다.

❌ **A. Amazon 기계 학습 (Amazon Machine Learning)**: Amazon ML은 머신러닝 모델을 구축하고 예측하는 서비스로, 데이터베이스 쿼리 결과 캐싱과는 전혀 관계가 없습니다.

❌ **B. Amazon SQS**: SQS(Simple Queue Service)는 메시지 큐 서비스로, 애플리케이션 간 메시지를 비동기적으로 전달하는 데 사용됩니다. 캐싱 기능을 제공하지 않습니다.

❌ **D. Amazon EC2 인스턴스 저장소**: EC2 인스턴스 저장소(Instance Store)는 인스턴스에 직접 연결된 임시 블록 스토리지로, 인스턴스 종료 시 데이터가 삭제됩니다. 분산 캐싱이나 쿼리 결과 저장에 적합하지 않습니다.

💡 **시험 꿀팁**: **캐싱 = ElastiCache** (Redis/Memcached). "DB 부하 감소", "쿼리 결과 저장", "인메모리 캐시" 키워드 → ElastiCache. SQS는 "메시지 큐", SNS는 "알림/푸시"로 구분하세요.

## Q7. AWS가 전적으로 관리하는 공유 책임 모델 구성요소

다음 중 AWS에서 전적으로 관리하는 공유 책임 모델의 구성요소는 무엇입니까?

- A. 운영 체제 소프트웨어 패치 적용
- B. 데이터 암호화
- C. 멀티 팩터 인증 적용
- D. 물리적 데이터 센터 자산 감사

**정답: D**

✅ **D. 물리적 데이터 센터 자산 감사**: AWS는 물리적 데이터 센터의 보안, 인프라 관리, 자산 감사를 전적으로 책임집니다. 고객은 데이터 센터에 물리적으로 접근할 수 없으며, 이는 "클라우드의 보안(Security OF the Cloud)"에 해당하는 AWS 책임 영역입니다.

❌ **A. 운영 체제 소프트웨어 패치 적용**: EC2와 같은 IaaS 서비스에서 OS 패치는 고객의 책임입니다. 물론 RDS처럼 관리형 서비스에서는 AWS가 담당하지만, 일반적으로 OS 패치는 고객 책임 영역에 포함됩니다.

❌ **B. 데이터 암호화**: 데이터 암호화는 고객이 선택적으로 활성화하는 기능으로, "클라우드에서의 보안(Security IN the Cloud)" 영역입니다. AWS는 암호화 도구를 제공하지만 암호화 적용 여부는 고객이 결정합니다.

❌ **C. 멀티 팩터 인증 적용**: MFA 설정은 고객이 IAM을 통해 직접 구성하는 보안 설정입니다. AWS는 MFA 기능을 제공하지만 활성화 여부는 고객의 책임입니다.

💡 **시험 꿀팁**: 공유 책임 모델 = **AWS 책임(Security OF the Cloud)**: 물리적 보안, 하드웨어, 네트워크 인프라, 하이퍼바이저 / **고객 책임(Security IN the Cloud)**: OS 패치, 데이터 암호화, MFA, 방화벽 설정. "물리적 데이터 센터" = 항상 AWS 책임입니다.

## Q8. 강사 주도 클라우드 보안 교육 옵션 (두 개 선택)

강사 주도 설정에서 클라우드 보안에 대해 알아보려는 고객에게 AWS는 어떤 옵션을 제공합니까? (두 개를 선택합니다.)

- A. AWS Trusted Advisor
- B. AWS Online Tech Talks
- C. AWS 블로그
- D. AWS 포럼
- E. AWS 강의실 교육

**정답: B, E**

✅ **B. AWS Online Tech Talks**: AWS Online Tech Talks는 AWS 전문가가 진행하는 온라인 웨비나 형식의 강사 주도 교육입니다. 특정 AWS 서비스와 보안 주제에 대해 실시간으로 학습하고 질문할 수 있는 구조화된 교육 환경을 제공합니다.

✅ **E. AWS 강의실 교육**: AWS 공인 강사(ACI, AWS Certified Instructor)가 진행하는 공식 강의실 교육으로, 체계적인 커리큘럼과 실습을 통해 클라우드 보안을 학습할 수 있는 대표적인 강사 주도 교육 방식입니다.

❌ **A. AWS Trusted Advisor**: Trusted Advisor는 AWS 환경의 보안, 비용, 성능, 내결함성을 자동으로 검사하고 권고 사항을 제공하는 도구입니다. 강사 주도 교육이 아닌 자동화된 조언 서비스입니다.

❌ **C. AWS 블로그**: AWS 블로그는 자기 주도 학습(Self-paced) 콘텐츠로, 강사가 직접 진행하는 교육 형식이 아닙니다.

❌ **D. AWS 포럼**: AWS 포럼(re:Post)은 커뮤니티 Q&A 플랫폼으로, 강사 주도 교육이 아닌 커뮤니티 기반 자기 학습 방식입니다.

💡 **시험 꿀팁**: **강사 주도(Instructor-led) 교육** = AWS 강의실 교육 + AWS Online Tech Talks (웨비나). **자기 주도(Self-paced)** = AWS 블로그, AWS 포럼, AWS 문서, AWS Skill Builder. "강사 주도" 키워드를 놓치지 마세요.

## Q9. Amazon VPC 대시보드에서 구성 가능한 기능 (두 개 선택)

다음 중 Amazon Virtual Private Cloud(Amazon VPC) 대시보드를 통해 구성할 수 있는 기능은 무엇입니까? (두 개를 선택합니다.)

- A. Amazon CloudFront 분포
- B. 아마존 루트 53 (Amazon Route 53)
- C. Security Group (보안 그룹)
- D. 서브넷
- E. 탄성 부하 분산 (Elastic Load Balancing)

**정답: C, D**

✅ **C. Security Group (보안 그룹)**: 보안 그룹은 VPC 내 인스턴스의 인바운드/아웃바운드 트래픽을 제어하는 가상 방화벽으로, VPC 대시보드에서 직접 생성하고 관리합니다. VPC의 핵심 네트워크 보안 구성 요소입니다.

✅ **D. 서브넷**: 서브넷은 VPC의 IP 주소 범위를 세분화한 것으로, 퍼블릭 서브넷과 프라이빗 서브넷으로 나뉩니다. VPC 대시보드에서 서브넷을 생성하고 라우팅 테이블을 구성합니다.

❌ **A. Amazon CloudFront 분포**: CloudFront는 CDN 서비스로, VPC와는 별개의 독립적인 글로벌 서비스입니다. CloudFront 콘솔에서 별도로 구성하며 VPC 대시보드를 통해 설정하지 않습니다.

❌ **B. 아마존 루트 53 (Amazon Route 53)**: Route 53은 DNS 서비스로, 별도의 Route 53 콘솔에서 구성합니다. VPC 대시보드의 구성 항목이 아닙니다.

❌ **E. 탄성 부하 분산 (Elastic Load Balancing)**: ELB는 별도의 EC2 또는 로드 밸런서 콘솔에서 구성하는 서비스입니다. VPC 내에서 동작하지만 VPC 대시보드에서 직접 생성하지 않습니다.

💡 **시험 꿀팁**: **VPC 대시보드 구성 요소** = 서브넷, 보안 그룹, 라우팅 테이블, 인터넷 게이트웨이, NAT 게이트웨이, NACL(네트워크 ACL), VPN, VPC 피어링. CloudFront, Route 53, ELB는 별도 서비스로 VPC 콘솔에 없습니다.

## Q10. 통합 과금 활성화 방법

회사 내의 각 부서에서 자체 AWS 계정을 가지고 있다면 통합 과금을 활성화하는 한 가지 방법은 무엇입니까?

- A. 각 계정의 AWS 예산을 예산에만 사용합니다.
- B. 월 청구서는 AWS 지원팀에 문의하십시오.
- C. 결제자 계정으로 AWS 조직을 만들고 다른 계정을 가입시킵니다.
- D. 모든 송장을 하나의 Amazon Simple Storage Service(Amazon S3) 버킷에 넣고 데이터를 Amazon Redshift에 로드한 다음 청구 보고서를 실행합니다.

**정답: C**

✅ **C. 결제자 계정으로 AWS 조직을 만들고 다른 계정을 가입시킵니다.**: AWS Organizations를 통해 마스터(결제자) 계정을 생성하고 멤버 계정들을 조직에 초대하면, 모든 계정의 비용이 단일 청구서로 통합됩니다. 이를 통합 과금(Consolidated Billing)이라 하며, 사용량 합산으로 볼륨 할인 혜택도 받을 수 있습니다.

❌ **A. 각 계정의 AWS 예산을 예산에만 사용합니다.**: AWS Budgets는 비용 알림 및 예산 설정 도구로, 통합 과금과는 다른 기능입니다. 각 계정의 예산을 따로 설정해도 청구서는 통합되지 않습니다.

❌ **B. 월 청구서는 AWS 지원팀에 문의하십시오.**: 지원팀에 문의해서 통합 과금을 설정할 수 없습니다. AWS Organizations를 통해 고객이 직접 설정해야 합니다.

❌ **D. 모든 송장을 하나의 Amazon S3 버킷에 넣고 데이터를 Amazon Redshift에 로드한 다음 청구 보고서를 실행합니다.**: 이 방법은 사후 분석을 위한 복잡한 워크플로우로, 실제 통합 과금 메커니즘이 아닙니다. 청구 통합 자체가 아닌 청구 데이터 분석 방법에 해당합니다.

💡 **시험 꿀팁**: **통합 과금(Consolidated Billing) = AWS Organizations** 사용. 혜택은 3가지: ① 단일 청구서, ② 사용량 합산으로 볼륨 할인, ③ 미사용 예약 인스턴스 공유. "여러 계정을 하나로 묶어 관리" = AWS Organizations입니다.

## Q11. 규모의 경제로 인한 고객 혜택

아마존의 거대한 규모의 경제로 인해 고객은 어떤 혜택을 받을 수 있을까요?

- A. Amazon의 운영 효율성에 따른 주기적인 가격 인하
- B. 최신 하드웨어를 제공하는 새로운 Amazon EC2 인스턴스 유형
- C. 필요할 때 스케일업 및 스케일다운 기능
- D. Amazon EC2 인스턴스의 기본 하드웨어의 안정성 향상

**정답: A**

✅ **A. Amazon의 운영 효율성에 따른 주기적인 가격 인하**: AWS는 수백만 명의 고객으로부터 확보한 규모의 경제를 통해 운영 비용을 절감하고, 이 절감분을 고객에게 가격 인하로 돌려줍니다. 실제로 AWS는 출범 이후 수십 차례 가격을 인하해왔으며, 이는 클라우드 채택의 6대 이점 중 하나인 "규모의 경제로 인한 이익"에 해당합니다.

❌ **B. 최신 하드웨어를 제공하는 새로운 Amazon EC2 인스턴스 유형**: 새로운 인스턴스 유형 출시는 기술 혁신의 결과이지, 규모의 경제로 인한 직접적인 혜택이 아닙니다. 이는 "최신 기술 활용" 이점에 해당합니다.

❌ **C. 필요할 때 스케일업 및 스케일다운 기능**: 탄력성(Elasticity)은 클라우드의 주요 장점이지만, 규모의 경제가 아닌 클라우드 아키텍처 자체의 특성에서 비롯됩니다.

❌ **D. Amazon EC2 인스턴스의 기본 하드웨어의 안정성 향상**: 하드웨어 안정성은 AWS의 지속적인 인프라 투자의 결과이지, 규모의 경제가 고객에게 주는 직접적인 혜택이 아닙니다.

💡 **시험 꿀팁**: AWS 클라우드 채택의 6대 이점 = ① **규모의 경제 → 가격 인하**, ② 자본 지출 → 가변 비용 전환, ③ 데이터 센터 운영 부담 감소, ④ 용량 추측 불필요, ⑤ 속도 및 민첩성 향상, ⑥ 글로벌 확장. "규모의 경제" = 가격 인하입니다.

## Q12. AWS 계정 활동 정보 수집 서비스 (두 개 선택)

AWS 계정 활동에 대한 정보를 수집하는 데 사용할 수 있는 AWS 서비스는 무엇입니까? (두 개를 선택합니다.)

- A. Amazon 클라우드 전면 (Amazon CloudFront)
- B. AWS Cloud9
- C. AWS CloudTrail
- D. AWS 클라우드HSM (AWS CloudHSM)
- E. Amazon CloudWatch

**정답: C, E**

✅ **C. AWS CloudTrail**: CloudTrail은 AWS 계정 내 모든 API 호출과 사용자 활동을 기록하는 감사(Audit) 서비스입니다. 누가, 언제, 어떤 AWS 리소스에 어떤 작업을 했는지 추적할 수 있어 계정 활동 모니터링과 보안 분석에 필수입니다.

✅ **E. Amazon CloudWatch**: CloudWatch는 AWS 리소스와 애플리케이션의 모니터링 서비스로, 지표(메트릭), 로그, 이벤트를 수집하고 분석합니다. EC2 CPU 사용률, API 호출 빈도 등 계정 활동과 관련된 다양한 정보를 실시간으로 수집합니다.

❌ **A. Amazon 클라우드 전면 (Amazon CloudFront)**: CloudFront는 콘텐츠 전송 네트워크(CDN) 서비스로, 계정 활동 정보 수집이 아닌 웹 콘텐츠 배포 속도 향상에 사용됩니다.

❌ **B. AWS Cloud9**: Cloud9은 클라우드 기반 통합 개발 환경(IDE)으로, 코드 작성 및 디버깅에 사용됩니다. 계정 활동 수집 기능이 없습니다.

❌ **D. AWS 클라우드HSM (AWS CloudHSM)**: CloudHSM은 전용 하드웨어 보안 모듈(HSM)을 제공하는 서비스로, 암호화 키 관리에 사용됩니다. 계정 활동 정보를 수집하는 서비스가 아닙니다.

💡 **시험 꿀팁**: **CloudTrail = API 호출 감사 로그** (누가 무엇을 했는가), **CloudWatch = 리소스 성능/상태 모니터링** (얼마나 사용하는가). 둘 다 "계정 활동 정보 수집"이지만 역할이 다릅니다. Cloud9은 IDE, CloudHSM은 암호화 키 관리로 구분하세요.

## Q13. AWS에서 처리 가능한 일반적 IT 작업 (두 개 선택)

AWS에서 회사 IT 리소스를 확보하기 위해 다룰 수 있는 일반적인 IT 작업은 무엇입니까? (두 개를 선택합니다.)

- A. 패치 적용 데이터베이스 소프트웨어
- B. 애플리케이션 릴리스 테스트
- C. 데이터베이스 백업
- D. 데이터베이스 스키마 작성
- E. 관통 테스트 실행 (Penetration Testing)

**정답: A, C**

✅ **A. 패치 적용 데이터베이스 소프트웨어**: RDS와 같은 AWS 관리형 데이터베이스 서비스를 사용하면 AWS가 데이터베이스 소프트웨어 패치를 자동으로 처리합니다. 고객이 온프레미스에서 직접 수행해야 했던 이 작업을 AWS가 대신 처리해주므로 운영 부담이 크게 줄어듭니다.

✅ **C. 데이터베이스 백업**: AWS 관리형 서비스(RDS, DynamoDB 등)를 사용하면 자동 백업 기능이 제공됩니다. RDS는 자동 백업과 스냅샷을 통해 데이터 복구를 지원하며, 고객이 수동으로 백업 스크립트를 관리할 필요가 없습니다.

❌ **B. 애플리케이션 릴리스 테스트**: 애플리케이션 테스트는 고객이 자신의 코드와 로직을 검증하는 작업으로, AWS가 대신 수행할 수 없습니다. 이는 항상 고객의 책임 영역입니다.

❌ **D. 데이터베이스 스키마 작성**: 데이터베이스 스키마(테이블 구조, 관계 정의)는 비즈니스 로직에 따라 고객이 설계하는 영역입니다. AWS는 스키마 설계를 대신 해주지 않습니다.

❌ **E. 관통 테스트 실행 (Penetration Testing)**: 침투 테스트는 고객의 애플리케이션 보안을 검증하기 위해 고객이 직접 수행하는 작업입니다. AWS는 특정 서비스에 대한 침투 테스트를 허용하지만, 직접 수행하지는 않습니다.

💡 **시험 꿀팁**: AWS가 대신 처리해주는 작업 = **인프라 유지보수, OS/DB 패치, 자동 백업, 하드웨어 교체**. 고객이 직접 해야 하는 작업 = **애플리케이션 코드, 스키마 설계, 테스트, 비즈니스 로직**. "관리형 서비스 = AWS가 더 많이 관리"를 기억하세요.

## Q14. Amazon EC2 스폿 인스턴스 사용 시나리오

어떤 시나리오에서 Amazon EC2 스폿 인스턴스를 사용해야 합니까?

- A. 회사는 사내 웹 서버에서 AWS로 메인 웹 사이트를 이동하려고 합니다.
- B. SLA(Service Level Agreement)에 99.999%의 가동 시간이 필요한 수많은 애플리케이션 서비스를 보유하고 있는 기업
- C. 회사에서 많이 사용하는 레거시 데이터베이스가 현재 사내에서 실행되고 있습니다.
- D. 기업에는 현재 온디맨드 인스턴스를 사용하고 있는 간헐적이고 중단 없는 여러 작업이 있습니다.

**정답: D**

✅ **D. 기업에는 현재 온디맨드 인스턴스를 사용하고 있는 간헐적이고 중단 없는 여러 작업이 있습니다.**: 스폿 인스턴스는 온디맨드 대비 최대 90% 저렴하지만, AWS가 용량을 회수할 경우 인스턴스가 중단될 수 있습니다. 따라서 중단을 견딜 수 있는(Interruption-tolerant) 간헐적 작업(배치 처리, 빅데이터 분석, CI/CD 등)에 가장 적합합니다. 현재 온디맨드를 사용 중이라면 스폿으로 전환해 비용을 대폭 절감할 수 있습니다.

❌ **A. 회사는 사내 웹 서버에서 AWS로 메인 웹 사이트를 이동하려고 합니다.**: 메인 웹 사이트는 지속적인 가용성이 요구되므로, 언제든 중단될 수 있는 스폿 인스턴스는 적합하지 않습니다. 온디맨드 또는 예약 인스턴스를 사용해야 합니다.

❌ **B. SLA에 99.999%의 가동 시간이 필요한 경우**: 매우 높은 가용성을 요구하는 서비스에는 중단 가능성이 있는 스폿 인스턴스를 절대 사용하면 안 됩니다. 예약 인스턴스나 온디맨드 인스턴스를 Multi-AZ로 구성해야 합니다.

❌ **C. 레거시 데이터베이스가 현재 사내에서 실행되고 있는 경우**: 데이터베이스는 지속적인 운영이 필요하며, 스폿 인스턴스가 중단되면 데이터 손실이나 서비스 중단이 발생할 수 있습니다. 데이터베이스에는 스폿 인스턴스를 권장하지 않습니다.

💡 **시험 꿀팁**: **스폿 인스턴스 = 저렴(최대 90% 할인) + 중단 가능**. 적합한 워크로드: 배치 처리, 빅데이터 분석, 머신러닝 학습, 렌더링, CI/CD. 부적합: 웹 서버, 데이터베이스, 고가용성 필요 서비스. "중단 허용(fault-tolerant)" 키워드 = 스폿 인스턴스.

## Q15. 애플리케이션 고가용성 달성을 위한 AWS 기능

애플리케이션의 고가용성을 달성하기 위해 고객이 활용해야 하는 AWS 기능은 무엇입니까?

- A. AWS Direct Connect
- B. 가용성 영역 (Availability Zones)
- C. 데이터 센터
- D. Amazon Virtual Private Cloud(Amazon VPC)

**정답: B**

✅ **B. 가용성 영역 (Availability Zones)**: 가용성 영역(AZ)은 동일 리전 내에 물리적으로 분리된 데이터 센터 클러스터입니다. 여러 AZ에 애플리케이션을 배포하면(Multi-AZ 아키텍처) 하나의 AZ에 장애가 발생해도 다른 AZ의 인스턴스가 계속 서비스를 제공하므로 고가용성을 달성할 수 있습니다.

❌ **A. AWS Direct Connect**: Direct Connect는 온프레미스 데이터 센터와 AWS 간의 전용 네트워크 연결 서비스입니다. 네트워크 안정성을 높이지만, 애플리케이션 자체의 고가용성을 직접 달성하는 기능이 아닙니다.

❌ **C. 데이터 센터**: AWS의 물리적 데이터 센터 자체는 고객이 직접 선택하거나 활용하는 단위가 아닙니다. 고객은 가용성 영역과 리전을 통해 인프라를 선택합니다.

❌ **D. Amazon Virtual Private Cloud(Amazon VPC)**: VPC는 논리적으로 격리된 가상 네트워크 환경을 제공하지만, 고가용성 자체를 달성하는 기능이 아닙니다. VPC 내에서 Multi-AZ를 구성해야 고가용성이 달성됩니다.

💡 **시험 꿀팁**: **고가용성(High Availability) = 가용성 영역(AZ) 분산 배포**. AWS 인프라 계층: 리전(Region) > 가용성 영역(AZ) > 데이터 센터. 하나의 리전에 보통 3개 이상의 AZ가 있으며, Multi-AZ = 고가용성의 핵심입니다.

## Q16. 인프라 이벤트 관리 포함 최소 지원 계획

추가 비용 없이 인프라 이벤트 관리를 포함하는 최소 AWS 지원 계획은 무엇입니까?

- A. 기업 (Enterprise)
- B. 비즈니스 (Business)
- C. 개발자 (Developer)
- D. 기본 (Basic)

**정답: A**

✅ **A. 기업 (Enterprise)**: 인프라 이벤트 관리(Infrastructure Event Management, IEM)는 대규모 이벤트(제품 출시, 마케팅 캠페인 등) 전에 AWS가 사전 지원을 제공하는 서비스입니다. 이 기능은 Enterprise 지원 계획에 기본 포함되어 있습니다. Business 계획에서도 제공되지만 추가 비용이 발생합니다.

❌ **B. 비즈니스 (Business)**: Business 지원 계획에서도 인프라 이벤트 관리를 이용할 수 있지만, 추가 비용이 발생합니다. 문제에서 "추가 비용 없이"를 명시했으므로 Enterprise가 정답입니다.

❌ **C. 개발자 (Developer)**: Developer 지원 계획은 비용 효율적인 기본 기술 지원을 제공하지만, 인프라 이벤트 관리 기능이 포함되어 있지 않습니다.

❌ **D. 기본 (Basic)**: Basic 지원은 무료이지만 기술 지원이 제공되지 않으며, 인프라 이벤트 관리는 포함되지 않습니다.

💡 **시험 꿀팁**: AWS 지원 계획 4단계: **Basic(무료) < Developer < Business < Enterprise**. 인프라 이벤트 관리(IEM): Business=유료 추가, **Enterprise=기본 포함**. TAM(기술 계정 관리자)도 Enterprise에만 포함됩니다.

## Q17. 정적 웹 사이트 서비스 가능한 AWS 서비스

정적 웹 사이트를 서비스할 수 있는 AWS 서비스는 무엇입니까?

- A. 아마존 S3
- B. 아마존 루트 53 (Amazon Route 53)
- C. Amazon QuickSight
- D. AWS X-Ray

**정답: A**

✅ **A. 아마존 S3**: Amazon S3는 객체 스토리지 서비스이지만, 정적 웹 사이트 호스팅 기능을 기본으로 제공합니다. HTML, CSS, JavaScript, 이미지 등 정적 파일을 버킷에 업로드하고 정적 웹 사이트 호스팅을 활성화하면 서버 없이도 웹 사이트를 운영할 수 있습니다. 서버리스로 비용 효율적이며, CloudFront와 결합하면 성능도 향상됩니다.

❌ **B. 아마존 루트 53 (Amazon Route 53)**: Route 53은 DNS(도메인 이름 서비스) 서비스로, 도메인 이름을 IP 주소로 변환합니다. 웹 사이트 콘텐츠를 직접 호스팅하는 기능이 없으며, S3와 함께 사용하여 사용자 지정 도메인을 연결하는 데 활용됩니다.

❌ **C. Amazon QuickSight**: QuickSight는 비즈니스 인텔리전스(BI) 및 데이터 시각화 서비스로, 대시보드와 보고서를 만드는 데 사용됩니다. 웹 사이트 호스팅 기능이 없습니다.

❌ **D. AWS X-Ray**: X-Ray는 분산 애플리케이션의 성능을 분석하고 디버깅하는 추적 서비스입니다. 웹 사이트 호스팅과 관련이 없습니다.

💡 **시험 꿀팁**: **정적 웹 사이트 호스팅 = Amazon S3**. S3 정적 호스팅 특징: 서버 불필요, HTML/CSS/JS/이미지만 가능, 서버 사이드 코드(PHP, Node.js) 불가. 동적 웹 사이트는 EC2나 Elastic Beanstalk를 사용하세요.

## Q18. AWS의 IT 리소스 프로비저닝 시간 단축 방법

AWS는 IT 리소스 프로비저닝 시간을 어떻게 단축합니까?

- A. 리소스 요청을 위한 온라인 IT 티켓팅 플랫폼을 제공합니다.
- B. 자동 코드 유효성 검사 서비스를 지원합니다.
- C. 기존 리소스를 프로그래밍 방식으로 프로비저닝할 수 있는 기능을 제공합니다.
- D. 회사의 IT 공급업체 목록에서 리소스 요청 프로세스를 자동화합니다.

**정답: C**

✅ **C. 기존 리소스를 프로그래밍 방식으로 프로비저닝할 수 있는 기능을 제공합니다.**: AWS는 AWS Management Console, AWS CLI, SDK, CloudFormation 등을 통해 리소스를 프로그래밍 방식(코드)으로 즉시 프로비저닝할 수 있습니다. 기존 온프레미스 환경에서는 서버 구매부터 설치까지 수주~수개월이 걸렸지만, AWS에서는 몇 분 내에 완료됩니다. 이것이 클라우드의 핵심 장점인 "속도와 민첩성"입니다.

❌ **A. 리소스 요청을 위한 온라인 IT 티켓팅 플랫폼을 제공합니다.**: AWS는 티켓 시스템을 통해 리소스를 요청하는 방식이 아닙니다. AWS 콘솔이나 API를 통해 즉시 직접 프로비저닝합니다.

❌ **B. 자동 코드 유효성 검사 서비스를 지원합니다.**: 코드 검증 서비스는 리소스 프로비저닝 시간 단축과 직접적인 관련이 없습니다. AWS CodeCommit, CodeBuild 등이 있지만 이는 CI/CD 도구입니다.

❌ **D. 회사의 IT 공급업체 목록에서 리소스 요청 프로세스를 자동화합니다.**: AWS는 외부 IT 공급업체 관리 시스템과 연동하여 프로비저닝 시간을 줄이는 서비스가 아닙니다.

💡 **시험 꿀팁**: AWS의 프로비저닝 속도 향상 도구 = **AWS CloudFormation**(IaC, 인프라를 코드로), **AWS CLI**, **AWS SDK**, **AWS Management Console**. "프로그래밍 방식(Programmatic)" + "API 호출" = 몇 분 내 프로비저닝. 온프레미스의 긴 조달 기간 vs. 클라우드의 즉각적인 프로비저닝을 비교하세요.

## Q19. AWS 엣지 로케이션 사용 용도 (두 개 선택)

AWS 에지 위치는 어디에 사용할 수 있습니까? (2개 선택)

- A. 애플리케이션 호스팅
- B. 사용자에게 더 가까운 콘텐츠 제공
- C. NoSQL 데이터베이스 캐싱 서비스 실행
- D. 응답을 캐싱하여 서버 트래픽 감소
- E. 최종 사용자에게 통지 메시지 보내기

**정답: B, D**

✅ **B. 사용자에게 더 가까운 콘텐츠 제공**: 엣지 로케이션은 CloudFront CDN의 핵심 인프라로, 전 세계 수백 개 위치에 분산되어 있습니다. 사용자와 가장 가까운 엣지 로케이션에서 콘텐츠를 제공함으로써 지연 시간(Latency)을 최소화하고 사용자 경험을 향상시킵니다.

✅ **D. 응답을 캐싱하여 서버 트래픽 감소**: 엣지 로케이션은 원본 서버(오리진)의 콘텐츠를 캐싱합니다. 동일한 요청이 들어오면 원본 서버까지 가지 않고 엣지에서 직접 응답하므로, 원본 서버의 부하를 크게 줄일 수 있습니다.

❌ **A. 애플리케이션 호스팅**: 엣지 로케이션은 콘텐츠 캐싱과 배포를 위한 인프라이지, EC2 같은 애플리케이션 호스팅 서비스를 실행하는 공간이 아닙니다. 애플리케이션은 리전의 AZ에 호스팅됩니다.

❌ **C. NoSQL 데이터베이스 캐싱 서비스 실행**: DynamoDB Accelerator(DAX)나 ElastiCache 같은 DB 캐싱 서비스는 리전 내 AZ에서 실행되며, 엣지 로케이션에서 실행되지 않습니다.

❌ **E. 최종 사용자에게 통지 메시지 보내기**: 알림/푸시 메시지는 Amazon SNS(Simple Notification Service)를 통해 제공됩니다. 이는 엣지 로케이션의 기능이 아닙니다.

💡 **시험 꿀팁**: **엣지 로케이션 = CloudFront CDN 캐시 서버**. 주요 용도: ① 콘텐츠 캐싱으로 지연 시간 감소, ② 오리진 서버 트래픽 감소. 엣지 로케이션에서 실행되는 서비스: CloudFront, Route 53, AWS Shield, Lambda@Edge, Amazon Route 53.

## Q20. Amazon S3 버킷 액세스 제한 방법

다음 중 특정 사용자에 대한 Amazon S3(Simple Storage Service) 버킷 액세스를 제한할 수 있는 항목은 무엇입니까?

- A. 공개 및 개인 키 쌍
- B. Amazon 검사관 (Amazon Inspector)
- C. AWS IAM(Identity and Access Management) 정책
- D. 보안 그룹 (Security Group)

**정답: C**

✅ **C. AWS IAM(Identity and Access Management) 정책**: IAM 정책을 사용하면 특정 IAM 사용자, 그룹, 역할에 대해 S3 버킷 및 객체에 대한 세밀한 접근 제어가 가능합니다. S3 버킷 정책(Bucket Policy)과 IAM 정책을 조합하여 특정 사용자만 허용하거나 차단하는 세밀한 권한 설정을 구현할 수 있습니다.

❌ **A. 공개 및 개인 키 쌍**: EC2 인스턴스에 SSH로 접속할 때 사용하는 키 페어입니다. S3 버킷 접근 제어와는 관련이 없으며, S3는 AWS 서명(SigV4)과 IAM으로 인증을 처리합니다.

❌ **B. Amazon 검사관 (Amazon Inspector)**: Amazon Inspector는 EC2 인스턴스와 컨테이너의 보안 취약점을 자동으로 검사하는 서비스입니다. S3 버킷 액세스 제한 기능을 제공하지 않습니다.

❌ **D. 보안 그룹 (Security Group)**: 보안 그룹은 EC2 인스턴스의 네트워크 트래픽(인바운드/아웃바운드)을 제어하는 가상 방화벽입니다. S3는 인터넷을 통해 HTTP/HTTPS로 접근하는 서비스이므로 보안 그룹으로 접근을 제어하지 않습니다. S3 VPC 엔드포인트를 사용할 때는 VPC 엔드포인트 정책을 사용합니다.

💡 **시험 꿀팁**: **S3 접근 제어 = IAM 정책 + S3 버킷 정책 + ACL**. 보안 그룹은 EC2/RDS/VPC 리소스에 사용, S3에는 적용 안 됨. Amazon Inspector = 취약점 스캔 도구(EC2/컨테이너). "특정 사용자에게 S3 접근 제한" = IAM 정책이 정답입니다.
