## QUESTION 321

**Question**: In an EKS-based microservices environment, when deploying a new version, they want to shift traffic gradually — **only a portion (e.g., 5%) to the new version** — while observing the error rate, rather than cutting over all traffic at once. They also want detailed observability (latency, error rate) into service-to-service communication. What's the solution that minimizes application code changes?

**Choices**
- A. Use only ALB's weighted target groups (ALB weighted routing can achieve gradual traffic shifting, but doesn't provide detailed service-to-service observability like latency, retries, or circuit breaking).
- B. **Adopt AWS App Mesh to manage microservice-to-microservice communication via a service mesh, use a virtual router's weighted routing to gradually shift only a portion of traffic to the new version, and collect detailed observability metrics via the sidecar.**
- C. Switch service endpoints using Route 53 weighted routing (Route 53 weighted routing operates at the DNS level, with precision issues from client-side DNS caching for fine-grained traffic ratio control, and provides no detailed microservice observability).
- D. Hardcode custom canary logic into the application code (randomly routing 5% of requests to a different endpoint) (requires implementing/maintaining this logic directly in every service's code, contradicting "minimize code changes").

**Correct Answer: B**

**Explanation**
**AWS App Mesh** controls microservice-to-microservice communication at a layer separate from application code, via a service mesh. Configuring weighted routing rules on a **virtual router** implements canary deployment — gradually shifting only a certain percentage (e.g., 5%) of traffic to the new version — with no code changes, while the Envoy sidecar injected into each service automatically collects detailed observability metrics like latency and error rate.

**Why the other choices are wrong**
- A: ALB weighted routing can achieve gradual shifting itself, but doesn't provide detailed service-to-service observability (retries, circuit breaking, etc.) out of the box.
- C: DNS-based weighted routing can be imprecise in actual ratio control due to client/resolver caching, and provides no observability feature.
- D: A custom implementation requires repeating and maintaining the same logic across every service, contradicting "minimize code changes."

> 💡 **Exam tip**: To implement **gradual canary traffic shifting plus detailed observability** between microservices with no code changes, **AWS App Mesh** (virtual router weighted routing + sidecar observability) is the standard answer.

## QUESTION 322

**Question**: A company operates hundreds of S3 buckets across multiple accounts, and some may inadvertently contain personally identifiable information (PII, e.g., national ID numbers, credit card numbers). They want to **automatically detect** buckets/objects containing such sensitive data organization-wide and alert the security team. What's the solution?

**Choices**
- A. Implement a Lambda function that periodically downloads objects from each bucket and scans for PII patterns directly with regex (a custom implementation downloading/scanning large volumes of objects each time carries heavy cost and operational burden, and requires maintaining accurate detection logic for various PII types yourself).
- B. **Integrate and enable Amazon Macie at the organization level, and configure sensitive-data discovery jobs against S3 buckets across all accounts in the organization to automatically report results when PII is found.**
- C. Use GuardDuty to detect PII in S3 buckets (GuardDuty specializes mainly in detecting threats like abnormal API call patterns or malicious activity — scanning object content for sensitive data [PII] itself is Macie's role).
- D. Generate S3 Inventory reports and check only object metadata (Inventory just lists object metadata [size, last-modified date, etc.] and has no capability to analyze object content to determine PII presence).

**Correct Answer: B**

**Explanation**
**Amazon Macie** is a managed service that uses machine learning and pattern matching to **automatically detect** sensitive data — PII, credentials, financial information — stored in S3. Integrating with Organizations and centrally configuring discovery jobs against S3 buckets across all organization accounts from a delegated administrator account lets you identify and get reports on buckets/objects containing sensitive data at scale, without implementing scanning logic yourself.

**Why the other choices are wrong**
- A: A custom scanning implementation carries very heavy cost for large-volume data processing and a heavy burden maintaining detection accuracy.
- C: GuardDuty specializes in threat/anomaly detection and doesn't provide a feature to scan object content for sensitive data itself.
- D: S3 Inventory is just a metadata listing feature with no content-analysis capability.

> 💡 **Exam tip**: To **automatically detect PII and other sensitive data** stored in S3, **Amazon Macie** (organization integration + discovery jobs) is the standard answer.

## QUESTION 323

**Question**: Data on a local file server at a branch office needs to continuously sync to S3 in the headquarters' AWS account, but the branch's internet bandwidth is limited, so they want to **throttle bandwidth usage during business hours** and sync at maximum speed overnight. File metadata (permissions, timestamps) must also be preserved. What's the solution?

**Choices**
- A. Schedule rsync via cron to run only at night (rsync alone lacks integrated AWS monitoring, retry, and verification features, and time-based fine-grained bandwidth throttling would need to be implemented yourself).
- B. **Deploy an AWS DataSync agent at the branch office, configure bandwidth throttling on the task for low bandwidth during business hours, and use scheduling for unlimited or high bandwidth overnight. Enable the metadata-preservation option.**
- C. Use only S3 Transfer Acceleration to speed up transfer (Transfer Acceleration only optimizes the transfer path and doesn't offer time-based bandwidth throttling or file metadata preservation controls).
- D. Switch to Storage Gateway File Gateway (File Gateway is a caching gateway optimized for low-latency access; DataSync is more suitable for a bulk sync task with time-based bandwidth throttling as in this scenario).

**Correct Answer: B**

**Explanation**
**AWS DataSync** is a managed service for data transfer between on-premises (or another cloud) and AWS storage, offering **bandwidth throttling** to control network usage during specific times, and **scheduling** to configure different behavior for business hours versus overnight. It also provides a built-in option to **preserve file metadata** — ownership, permissions, timestamps — meeting every requirement in this scenario (bandwidth control, scheduling, metadata preservation) in a managed way.

**Why the other choices are wrong**
- A: rsync can do basic syncing, but you'd need to implement integrated AWS monitoring/verification and fine-grained time-based bandwidth management yourself.
- C: Transfer Acceleration only optimizes transfer speed and doesn't offer bandwidth throttling or metadata preservation.
- D: File Gateway is a caching solution for low-latency file access; DataSync is more standard for this scenario's bulk/scheduled sync needs.

> 💡 **Exam tip**: For on-premises-to-S3 data sync needing **bandwidth throttling + scheduling + metadata preservation**, **AWS DataSync** is the standard answer.

## QUESTION 324

**Question**: During traffic spikes, a Lambda function spins up thousands of concurrent execution instances, each connecting directly to an RDS PostgreSQL database, causing frequent "too many connections" errors from **exceeding the database's connection limit**. How do you fix this while minimizing application code changes?

**Choices**
- A. Increase the RDS instance class to the maximum to raise the maximum connection limit itself (even a larger instance eventually hits a ceiling, and this fundamentally doesn't fit Lambda's bursty concurrency pattern — poor cost-effectiveness and only a stopgap).
- B. **Place Amazon RDS Proxy in front of the database to pool and manage Lambda's mass connection requests, so only a small number of connections are maintained against the actual database.**
- C. Limit Lambda's concurrent executions low via reserved concurrency (limiting concurrency eases the connection problem but artificially lowers request-handling capacity during traffic spikes, negatively affecting application performance/availability).
- D. Switch RDS to Aurora Serverless v2 with no other action (Serverless v2 auto-scales compute capacity, but that doesn't fundamentally solve the connection-limit problem caused by Lambda's mass concurrent connections — a pooling layer like RDS Proxy is still needed for connection management).

**Correct Answer: B**

**Explanation**
**Amazon RDS Proxy** is a fully managed proxy that performs **connection pooling** between the application (Lambda) and the database. Even if the Lambda function attempts a connection from thousands of concurrent execution instances, RDS Proxy pools them so only a much smaller number of connections are maintained against the actual database — solving the "too many connections" problem with almost no application code change (just point the connection string's endpoint at the RDS Proxy endpoint).

**Why the other choices are wrong**
- A: Increasing the instance class only somewhat raises the maximum connection count — it doesn't solve the fundamental connection-surge problem, and is costly.
- C: Limiting concurrency can ease the connection problem but is a stopgap that trades off reduced throughput.
- D: Aurora Serverless v2 is an auto-scaling compute-capacity feature; managing the mass-connection problem caused by Lambda still requires a separate pooling mechanism like RDS Proxy.

> 💡 **Exam tip**: For a relational-DB connection-limit problem caused by **Lambda's bursty concurrency**, **Amazon RDS Proxy** (connection pooling) is the standard answer that minimizes code changes.

## QUESTION 325

**Question**: The finance team wants to analyze EC2 usage history across multiple accounts to get data-driven recommendations on **what and how much Savings Plans/Reserved Instances to purchase**. How do you do this using only AWS-provided features, without implementing your own usage-analysis logic?

**Choices**
- A. Collect CloudWatch metrics and calculate optimal purchase amounts in a custom spreadsheet (implementing your own logic to analyze usage history and calculate optimal commitment recommendations is inefficient and likely less accurate than AWS's recommendation engine).
- B. **Use AWS Cost Explorer's Savings Plans recommendations and Reserved Instance recommendations features to see the optimal commitment type/amount/term AWS suggests based on historical usage.**
- C. Check only Trusted Advisor's cost-optimization check results (Trusted Advisor offers some cost-related checks, but Cost Explorer's dedicated feature for sophisticated, usage-history-based Savings Plans/RI purchase recommendations is more detailed and standard).
- D. Manually review the bill every month to estimate next month's purchase amount (manual estimation lacks data-driven precision and requires repetitive manual work).

**Correct Answer: B**

**Explanation**
**AWS Cost Explorer** analyzes an account's (or organization's) historical usage to automatically generate **Savings Plans recommendations** and **Reserved Instance recommendations**. These recommendations present, based on data, what type of commitment, at what hourly amount (or quantity), for what term, maximizes expected savings — enabling optimal purchasing decisions with no custom analysis logic needed.

**Why the other choices are wrong**
- A: Implementing your own analysis logic is unnecessary development burden and is hard to guarantee matches AWS's sophisticated recommendation algorithm's accuracy.
- C: Trusted Advisor has some cost-related checks, but generating detailed commitment purchase recommendations is a feature Cost Explorer provides dedicatedly.
- D: Manual bill review can't substitute for precise, data-driven recommendations.

> 💡 **Exam tip**: To get **optimal Savings Plans/Reserved Instance purchase recommendations** based on historical usage, **AWS Cost Explorer's recommendation features** is the standard answer.

## QUESTION 326

**Question**: A company connects to AWS via Direct Connect, and wants to access not just VPC-internal resources but also **AWS public services like S3 and DynamoDB** privately through Direct Connect, without going over the internet. What's the solution?

**Choices**
- A. Access S3 using only Direct Connect's private virtual interface (private VIF) (a private VIF is for connecting to VPC-internal resources [private IP ranges] and can't reach public service endpoints [public IP ranges] like S3 — a conceptual error).
- B. **Additionally configure a public virtual interface (public VIF) on Direct Connect, so traffic to all AWS public service (S3, DynamoDB, etc.) public IP ranges routes over the Direct Connect circuit rather than the internet.**
- C. Access S3 from the VPC via a NAT Gateway (going through a NAT Gateway ultimately uses an internet path, contradicting the "without going over the internet" requirement).
- D. Only create a VPC gateway endpoint for S3 (a gateway endpoint is valid for VPC-internal resources accessing S3 privately, but for a separate on-premises network accessing AWS public services via Direct Connect as in this question, a public VIF is needed).

**Correct Answer: B**

**Explanation**
Configuring a **public virtual interface (public VIF)** on Direct Connect lets an on-premises network route traffic to all of a Region's AWS **public service endpoints** (S3, DynamoDB, etc. public IP ranges) over the dedicated Direct Connect circuit instead of the internet. This is the standard way to keep on-premises-to-AWS-public-service traffic private while also gaining bandwidth and latency benefits.

**Why the other choices are wrong**
- A: A private VIF is used for connecting to a VPC (private IP range) and can't reach public service endpoints like S3.
- C: Access via a NAT Gateway ultimately uses an internet path, contradicting the requirement.
- D: A gateway endpoint handles access from within a VPC; access from on-premises via Direct Connect needs a public VIF.

> 💡 **Exam tip**: To access **AWS public services like S3/DynamoDB** from on-premises via Direct Connect without the internet, a **public virtual interface (public VIF)** is the standard answer. Remember the distinction from a private VIF, used for VPC-internal resource access.

## QUESTION 327

**Question**: A startup wants to run several workloads on EKS but doesn't want to handle worker node (EC2) provisioning, patching, or capacity management at all, and wants to pay per pod. Only some workloads need this serverless approach; the rest can keep using an existing managed node group. What's the solution?

**Choices**
- A. Convert all nodes to a managed node group made of On-Demand EC2 (still requires node provisioning/patching management, contradicting "no management at all").
- B. **Configure an EKS Fargate profile for a specific namespace (or label selector), so pods matching that condition run serverlessly on Fargate with no node management, while the rest of the workload keeps running on the existing managed node group.**
- C. Configure the entire cluster as EKS Fargate only (a viable option, but the question states some workloads can keep using the existing managed node group, so a full conversion isn't required, and some workload types [like DaemonSets] aren't supported on Fargate).
- D. Switch to a Spot-Instance-based managed node group just for cost savings (switching to Spot still requires provisioning/managing nodes [EC2], failing to meet the "no node management at all" serverless requirement).

**Correct Answer: B**

**Explanation**
Configuring an **EKS Fargate profile** matched to a specific namespace or label condition means pods matching that condition run **serverlessly on Fargate** — with no worker node provisioning/patching/capacity management — billed per vCPU/memory the pod uses. This lets you **selectively** convert only some workloads within the cluster to serverless, while the rest continues to run on the existing EC2-based managed node group — a hybrid setup.

**Why the other choices are wrong**
- A: Even a managed node group still has underlying EC2 nodes, so the concept of provisioning/patching management still exists (a managed node group automates some management, but doesn't eliminate the node concept the way Fargate does).
- C: The question explicitly states some workloads can keep the existing node group, so a full conversion is unnecessary, and there are workload types Fargate doesn't support (e.g., DaemonSets, certain storage requirements).
- D: A Spot node group still requires managing EC2 nodes, failing to meet the serverless requirement.

> 💡 **Exam tip**: To run **only specific workloads serverlessly, billed per pod, with no node management** in EKS, an **EKS Fargate profile** (namespace/label-based) is the standard answer, mixable with an existing managed node group for the rest.

## QUESTION 328

**Question**: A company's internal-employees-only application uses API Gateway, and this API must be **accessible only from within the company VPC**, never exposed to the public internet. They want to keep using existing API Gateway features (request validation, usage plans, etc.). What's the solution?

**Choices**
- A. Create an API Gateway regional endpoint and allow only specific IPs via a resource policy (a regional endpoint is, by default, reachable from the public internet; even with IP restriction via resource policy, the endpoint itself is still exposed to the internet via a public DNS name — insufficient for the "must never be exposed" requirement).
- B. **Create the API Gateway as a private endpoint type, create an interface VPC endpoint for API Gateway (execute-api) in the VPC, and configure the resource policy so the API is only accessible through this endpoint.**
- C. Use only an internal ALB to call Lambda directly instead of API Gateway (gives up API Gateway's request validation, usage plans, API key management, etc., contradicting the "keep using existing API Gateway features" requirement).
- D. Use the API Gateway Edge-optimized endpoint type (an edge-optimized endpoint is a public endpoint exposed worldwide via CloudFront — the opposite of a private-access requirement).

**Correct Answer: B**

**Explanation**
API Gateway's **private endpoint type** is not reachable from the public internet at all, and can only be accessed through an **interface VPC endpoint (service name: execute-api)** created in the VPC. Configuring the API's resource policy to allow access only from a specific VPC endpoint makes the API completely private while preserving existing API Gateway features — request validation, usage plans, API keys.

**Why the other choices are wrong**
- A: A regional endpoint's DNS name is still exposed publicly even with IP restrictions — a private endpoint is more appropriate for the strict "must never be exposed" requirement.
- C: An internal ALB + direct Lambda call is possible, but gives up API Gateway's rich feature set (request validation, usage plans, etc.).
- D: An edge-optimized endpoint is meant to be exposed worldwide — the opposite direction of a private-access requirement.

> 💡 **Exam tip**: To make API Gateway **accessible only from within a VPC (never exposed publicly)**, **the private endpoint type + an interface VPC endpoint (execute-api) + a resource policy** is the standard answer.

## QUESTION 329

**Question**: A data-platform team (Account A) manages a Lake Formation-based data lake, and wants to share specific databases/tables so an analytics team (Account B) can query them directly with Athena from their own account. How do you share this without physically copying the data, while maintaining fine-grained (table-level) access control?

**Choices**
- A. Grant read permission directly to Account B's role via Account A's S3 bucket policy (bucket/object-level permissions alone can't maintain Lake Formation's fine-grained database/table-level permissions and governance, and access to Glue Data Catalog metadata is also separately needed).
- B. **Use AWS Lake Formation's cross-account grants (or resource links) feature to grant permissions on specific databases/tables from Account A to Account B, and in Account B, query those tables via a resource link as if they were in your own catalog.**
- C. Implement a batch job that copies the data to Account B's S3 bucket every day (physical copying causes data duplication, sync delay, and storage cost, contradicting the "without copying" requirement).
- D. Create an IAM role in Account A for Account B's users to access via AssumeRole (role delegation alone doesn't leverage Lake Formation's table/column-level fine-grained permission management — Lake Formation's native cross-account sharing feature is more appropriate).

**Correct Answer: B**

**Explanation**
**AWS Lake Formation** provides native **cross-account data sharing**, letting the data-owning account (A) directly grant permissions on specific databases or tables to another account (B). The granted account creates a **resource link** to the shared resource in its own Data Catalog, letting it query it via Athena, etc. as if it were in its own catalog. The data is never physically copied — it stays in the original S3 location — and Lake Formation's table/column-level fine-grained permission system is preserved across the account boundary.

**Why the other choices are wrong**
- A: An S3 bucket policy alone can't manage both Lake Formation catalog metadata access and fine-grained table/column permissions together.
- C: Physical data copying causes duplication, sync delay, and additional cost, contradicting the "without copying" requirement.
- D: Simple role delegation bypasses Lake Formation's fine-grained data-governance features and isn't optimal for this scenario.

> 💡 **Exam tip**: To **share a data lake with another account with fine-grained permissions without physically copying data**, **Lake Formation's cross-account grants (resource links)** is the standard answer.

## QUESTION 330

**Question**: An SRE team wants to regularly run **"Game Days"** in production, injecting real failure conditions — like a specific AZ's network outage or an EC2 instance termination — in a **controlled** manner to verify the system's actual resilience. They also need safeguards (stop conditions, scope limits) to prevent uncontrolled failure spread. What's the solution?

**Choices**
- A. Write a custom script that randomly terminates real production resources and run it without warning (uncontrolled random termination with no safeguards or scope limits carries a very high risk of unintended, widespread outages).
- B. **Use AWS Fault Injection Simulator (FIS) to define a specific fault type (AZ outage simulation, instance termination, etc.) and a target scope (only resources with specific tags) in an experiment template, and set a CloudWatch-alarm-based stop condition that automatically halts the experiment if a predefined threshold is exceeded.**
- C. Only run failure tests in a staging environment and never apply them to production (staging tests are useful too, but the question explicitly requires verifying actual resilience in the production environment, so this doesn't meet the requirement).
- D. Monitor the AWS Health Dashboard and wait for an actual AWS outage to observe response capability (a real outage's timing and type can't be controlled, which doesn't fit a planned Game Day operating model).

**Correct Answer: B**

**Explanation**
**AWS Fault Injection Simulator (FIS)** is a managed service for chaos engineering, letting an experiment template explicitly define the **fault type to inject** (AZ outage, instance/API errors, etc.) and the **target resource scope** (tag-based, etc.). In particular, attaching a CloudWatch alarm as a **stop condition** means the experiment **automatically and immediately halts** if a predefined threshold (e.g., a spike in error rate) is exceeded during the experiment — allowing safe production resilience verification within a controlled scope.

**Why the other choices are wrong**
- A: A random script with no safeguards can't control the blast radius of the failure — very risky.
- C: Staging-only testing doesn't achieve the Game Day's purpose of verifying resilience under production's actual traffic/configuration.
- D: Passively waiting for a real outage isn't a planned, repeatable resilience-verification method.

> 💡 **Exam tip**: To **inject failures in a controlled way to verify resilience** in production, **AWS Fault Injection Simulator (FIS)** (experiment template scoping + CloudWatch-alarm-based stop conditions) is the standard answer.

## QUESTION 331

**Question**: A large enterprise manages 50 AWS accounts via Organizations, and employees also access SaaS applications like Salesforce and Microsoft 365. They want employees to **log in to all AWS accounts and SaaS applications via SSO with a single identity**, with access permissions managed centrally. What's the solution?

**Choices**
- A. Create individual IAM users in each AWS account, and use separate credentials for SaaS applications (managing separate credentials per account entirely fails the SSO requirement, and user provisioning/deprovisioning management becomes very cumbersome).
- B. **Use AWS IAM Identity Center (formerly AWS SSO): assign permission sets for multiple AWS accounts from a single identity source (built-in directory, or integration with existing AD/an external IdP), and also integrate SAML 2.0-supporting SaaS applications for unified SSO.**

- D. Grant every employee an administrator IAM role on a single account and have them switch between accounts via AssumeRole (granting every employee broad administrator permissions violates least privilege, and this doesn't address SaaS application SSO integration either).

- A: Separate credentials per account directly contradicts the definition of SSO and carries very heavy management burden.

> 💡 **Exam tip**: For centralized SSO across multiple **AWS accounts + SAML-based SaaS applications**, **AWS IAM Identity Center** is the standard answer.

## QUESTION 332

**Question**: A company's primary connectivity is Direct Connect, but they need an **automatic backup path** so connectivity between on-premises and the VPC doesn't drop if the Direct Connect circuit fails. Switching to the backup path must happen with no manual intervention. What's the solution?

**Choices**
- A. Use only Direct Connect, configured with two redundant physical circuits (this is redundancy within the same Direct Connect service itself; the question asks for an automatic backup path via an entirely different connection method [e.g., VPN]).
- B. **Configure both a Direct Connect private VIF and a Site-to-Site VPN, using BGP dynamic routing on both connections. Give the Direct Connect path a lower BGP path preference [e.g., AS path prepending] so Direct Connect is preferred normally, and let BGP automatically switch to the VPN path on failure.**
- C. Detect Direct Connect failure via CloudWatch and have Lambda manually create a new VPN connection (creating a new connection only after the failure occurs takes a long time to switch over, is more reactive after-the-fact response than "automatic" backup, and is far slower than BGP's instantaneous dynamic switchover).
- D. Configure separate circuits through two different Direct Connect partners (redundancy within the same connection type [Direct Connect] is still vulnerable to a broad outage affecting that connection type, and differs from the requirement for a backup via an entirely different connection method — though circuit redundancy itself does help resilience).

**Correct Answer: B**

**Explanation**
Configuring **Direct Connect (private VIF) + Site-to-Site VPN** together, using **BGP dynamic routing** on both, means traffic normally flows over the Direct Connect path (with priority adjusted via AS path prepending, etc.), and if the Direct Connect circuit fails, BGP automatically withdraws that route and **switches immediately to the VPN path with no manual intervention**. This is the standard resilience pattern of using an entirely different connection method as a backup.

**Why the other choices are wrong**
- A: Redundancy within Direct Connect alone is still vulnerable to a broad outage affecting the Direct Connect connection method itself.
- C: Creating a new resource only after a failure occurs is slow to switch over and reactive — inferior to BGP's instantaneous automatic switchover.
- D: Redundancy across different partners helps too, but differs from this question's requirement of a backup via an entirely different connection technology (VPN), and can still be vulnerable to structural issues with Direct Connect itself.

> 💡 **Exam tip**: To automatically switch to a backup path **with no manual intervention** if Direct Connect fails, the standard answer is configuring **Direct Connect + Site-to-Site VPN together with BGP dynamic routing** and adjusting priority.

## QUESTION 333

**Question**: A globally used application needs to perform **simultaneous (active-active) writes to S3 across multiple Regions**, with each user writing data to their nearest Region while other Regions can also read that data. They want the application to use a single endpoint with no Region-awareness. What's the solution?

**Choices**
- A. Use a single-Region S3 bucket with CloudFront distributed worldwide (CloudFront is effective for read caching, but doesn't support simultaneous [active-active] writes across multiple Regions or automatic inter-Region data sync).
- B. **Create S3 buckets in multiple Regions, set up bidirectional cross-Region replication (CRR), and create an S3 Multi-Region Access Point so the application uses a single global endpoint that automatically routes to the nearest Region's bucket.**
- C. Keep the S3 bucket in only one Region and only improve access speed to that Region's endpoint with Global Accelerator (data exists in only one Region, so write latency for users in other Regions remains high, and the "simultaneous writes across multiple Regions" requirement isn't met at all).
- D. Create independent S3 buckets per Region and hardcode the application to select a Region-specific endpoint based on user location (contradicts the requirement for the application to use a single, Region-unaware endpoint, and inter-Region data sync must also be separately implemented).

**Correct Answer: B**

**Explanation**
Placing S3 buckets in multiple Regions and syncing data via **bidirectional cross-Region replication (CRR)**, then creating an **S3 Multi-Region Access Point**, means the application only needs to use one **global endpoint**, while actual requests are automatically routed by the AWS global network to the **nearest (or healthiest) Region's bucket**. This implements both active-active writes across multiple Regions and Region-unaware single-endpoint access simultaneously.

**Why the other choices are wrong**
- A: CloudFront is optimized for read caching and doesn't provide simultaneous multi-Region writes or inter-Region data sync.
- C: Keeping data in only one Region doesn't solve write-latency problems for distant users or the "simultaneous multi-Region writes" requirement at all.
- D: Having the application select a Region-specific endpoint itself contradicts the "single endpoint" requirement, and inter-Region sync would also need to be self-implemented.

> 💡 **Exam tip**: For **active-active S3 writes across multiple Regions plus a single global endpoint**, **bidirectional CRR + an S3 Multi-Region Access Point** is the standard answer.

## QUESTION 334

**Question**: Instances used in an Auto Scaling group take **8-10 minutes** after boot for heavy application initialization (cache warming, loading a large runtime, etc.), causing a long delay before they can actually handle requests during a traffic spike. Without shortening the initialization time (i.e., no redesign of the init logic), how do you improve response speed to spikes?

**Choices**
- A. Significantly raise the minimum capacity so extra instances are always kept running (a viable approach, but keeps unnecessarily many instances running at all times even under normal conditions — poor cost efficiency).
- B. **Configure a warm pool on the Auto Scaling group, maintaining a pool of instances that have already completed initialization (Init) and are stopped or running, so that when scale-out is needed, they immediately transition from the warm pool into service.**
- C. Change the instance purchase option from Spot to On-Demand (a purchase-option change is unrelated to initialization time itself and doesn't solve this problem).
- D. Set the Auto Scaling policy's cooldown period to 0 (cooldown only adjusts the wait time between successive scaling actions — it doesn't shorten an individual instance's boot/initialization time itself).

**Correct Answer: B**

**Explanation**
A **warm pool** is a feature that pre-prepares Auto Scaling group instances at a stage before they receive actual service traffic (pre-initialization completed). These instances wait in a stopped state (saving cost) or a running state, and when scale-out is needed, they **transition immediately into service** without going through boot/initialization from scratch — greatly improving spike-response speed without changing the initialization logic itself.

**Why the other choices are wrong**
- A: Raising minimum capacity also improves response speed, but has worse cost efficiency than a warm pool due to keeping unnecessary instances running under normal conditions (a warm pool can leverage stopped instances to save compute cost).
- C: Changing the purchase option (Spot/On-Demand) is unrelated to initialization time.
- D: The cooldown setting adjusts wait time between scaling actions and doesn't shorten an individual instance's initialization time.

## QUESTION 340

**Question**: The security team wants all new EBS volumes in the organization to be **encrypted by default**, and wants to identify existing unencrypted volumes to remediate them. They also want to grant fine-grained permission for a specific application (e.g., Lambda) to access snapshots of volumes encrypted with a customer-managed KMS key. What's the standard combination for configuring this?

**Choices**
- A. Instruct users to manually check an encryption option every time they launch an EC2 instance (a manual process is at high risk of being missed and doesn't meet the "encrypted by default" enforcement requirement).
- B. **Enable "EBS encryption by default" at the account/Region level to enforce automatic encryption of new volumes/snapshots, use an AWS Config rule to detect existing unencrypted volumes, and for specific services (e.g., Lambda), grant only the necessary scope of usage permission via a KMS key policy or KMS grants.**
- C. Force the entire organization to use only the same AWS managed key (aws/ebs) for all EBS volumes (using only the managed key forfeits the flexible access control a customer-managed key offers, like fine-grained key policy customization or scoped grants for specific services).
- D. Implement only application-level encryption instead of EBS volume encryption (this bypasses EBS's own at-rest data protection and is a different approach than the question's core requirement of "enforcing EBS volume encryption," and other paths like volume snapshots could still expose data).

**Correct Answer: B**

**Explanation**
Enabling the **account/Region-level EBS encryption by default** setting means every new EBS volume and snapshot created going forward is automatically encrypted, with no need for users to manually toggle the option each time. Existing unencrypted volumes can be detected separately via an **AWS Config rule** (e.g., `encrypted-volumes`) for remediation (e.g., recreation). Additionally, using a **customer-managed KMS key** lets you grant fine-grained permission — via a **key policy** or **KMS grants** — to a specific service/role like Lambda, only as much as needed (e.g., `Decrypt` only under a specific encryption context condition), meeting every requirement in this question (default-encryption enforcement, existing-resource detection, fine-grained per-service permission).

**Why the other choices are wrong**
- A: A manual process is prone to being missed, failing to reliably meet the "encrypted by default" enforcement requirement.
- C: Using only the AWS managed key makes fine-grained key policy customization or grant-based scoped permissions difficult, failing to meet the fine-grained per-service access-control requirement.
- D: Application-level encryption doesn't substitute for encrypting the EBS volume/snapshot itself and is a different approach than the question's core requirement.

> 💡 **Exam tip**: To enforce **EBS volume encryption by default** organization-wide and also need **fine-grained per-service key usage permissions**, the standard combination is **EBS encryption by default + a Config rule (detecting existing resources) + a customer-managed KMS key (key policy/grants)**.
