## QUESTION 161

**문제**: 한 회사가 JSON 문서를 처리하고 그 결과를 온프레미스 SQL 데이터베이스에 저장하는 작은 Python 애플리케이션을 운영하고 있습니다. 이 애플리케이션은 매일 수천 번 실행됩니다. 회사는 이 애플리케이션을 AWS 클라우드로 이전하려고 하며, 확장성을 극대화하면서 운영 오버헤드는 최소화하는 고가용성 솔루션이 필요합니다. 이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. JSON 문서를 Amazon S3 버킷에 저장한다. 여러 Amazon EC2 인스턴스에서 Python 코드를 실행해 문서를 처리한다. 결과는 Amazon Aurora DB 클러스터에 저장한다. (EC2 인스턴스의 수동 프로비저닝과 확장 관리가 필요해 운영 오버헤드가 큼)
- B. **JSON 문서를 Amazon S3 버킷에 저장한다. 문서가 S3 버킷에 도착하면 이를 처리하는 AWS Lambda 함수를 트리거한다. 결과는 Amazon Aurora DB 클러스터에 저장한다.**
- C. JSON 문서를 Amazon EBS 볼륨에 저장한다. EBS 다중 연결 기능으로 여러 EC2 인스턴스에 볼륨을 연결해 문서를 처리한다. 결과는 Amazon RDS DB 인스턴스에 저장한다. (다중 연결은 지원 인스턴스 유형이 제한적이고 여전히 EC2 관리 부담이 존재)
- D. JSON 문서를 Amazon SQS 대기열 메시지로 전송한다. EC2 시작 유형의 Amazon ECS 클러스터에 Python 코드를 컨테이너로 배포해 처리한다. 결과는 Amazon RDS DB 인스턴스에 저장한다. (EC2 시작 유형은 클러스터 용량을 직접 관리해야 해 오버헤드가 추가됨)

**정답: B**

**해설**
이 문제의 핵심은 "이벤트 기반 처리"와 "서버 관리 최소화"입니다. **Amazon S3**는 JSON 문서를 위한 내구성 있고 확장 가능한 저장소 역할을 하며, 문서가 업로드되는 즉시 **AWS Lambda**를 트리거해 서버 프로비저닝 없이 자동으로 처리량에 맞춰 확장할 수 있습니다. 처리된 결과는 완전관리형 관계형 데이터베이스인 **Amazon Aurora**에 저장해 고가용성과 확장성을 동시에 확보합니다. S3+Lambda+Aurora 조합은 서버리스 아키텍처의 전형적인 패턴으로, 인프라 관리 부담 없이 수천 번의 실행을 자동으로 처리할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: EC2 인스턴스를 직접 프로비저닝하고 스케일링 정책을 관리해야 하므로 운영 오버헤드가 커진다.
- C: EBS 다중 연결은 특정 Nitro 기반 인스턴스와 클러스터형 파일시스템에서만 지원되며 EC2 관리 부담이 그대로 남는다.
- D: ECS를 EC2 시작 유형으로 운영하면 클러스터의 EC2 용량을 사용자가 직접 관리해야 해 서버리스만큼 운영 효율이 좋지 않다.

> 💡 **시험 꿀팁**: "S3에 파일 도착 → 이벤트 기반 처리 → 운영 오버헤드 최소화"라는 조건이 나오면 S3 + Lambda 조합이 표준 정답입니다.

## QUESTION 162

**문제**: 한 회사가 재무 위험 모델링을 위해 AWS에서 고성능 컴퓨팅(HPC) 인프라를 구축하려고 합니다. HPC 워크로드는 Linux에서 실행되며, 각 워크플로는 수백 개의 Amazon EC2 스팟 인스턴스에서 실행되고 수명이 짧지만, 분석 및 향후 장기 사용을 위해 영구 저장소에 보관해야 하는 수천 개의 출력 파일을 생성합니다. 온프레미스 데이터를 장기 영구 스토리지로 옮겨 모든 EC2 인스턴스가 처리할 수 있게 하면서, 데이터 세트와 출력 파일을 읽고 쓰는 데 사용할 고성능 파일 시스템이 영구 스토리지와 통합되어 있어야 합니다. 이러한 요구 사항을 충족하는 AWS 서비스 조합은 무엇입니까?

**보기**
- A. **Amazon S3와 통합된 Amazon FSx for Lustre**
- B. Amazon S3와 통합된 Amazon FSx for Windows File Server (SMB 기반 Windows 워크로드용으로 Linux HPC 컴퓨팅에는 적합하지 않음)
- C. Amazon EBS와 통합된 Amazon S3 Glacier (Glacier는 아카이브용 콜드 스토리지로 EBS와 통합되어 고성능 파일 시스템을 제공하지 않음)
- D. gp2 EBS 볼륨과 VPC 엔드포인트가 있는 Amazon S3 버킷 (gp2 EBS는 단일 AZ의 단일 인스턴스에 연결되는 블록 스토리지로 수백 개 인스턴스의 동시 병렬 접근을 지원하지 않음)

**정답: A**

**해설**
**Amazon FSx for Lustre**는 머신러닝, HPC, 비디오 렌더링, 금융 시뮬레이션과 같이 대규모 컴퓨팅 인스턴스가 동일한 데이터 세트에 초고속으로 동시 접근해야 하는 워크로드를 위해 설계된 완전관리형 병렬 파일 시스템입니다. **Amazon S3**와 네이티브로 통합되어 S3에 있는 데이터를 파일 시스템으로 링크(lazy-load)하고, 처리 결과를 다시 S3로 내보내 영구 저장할 수 있습니다. 이 조합은 수백 개의 스팟 인스턴스가 짧은 시간에 대량의 I/O를 처리하면서도 데이터를 S3에 장기 보관하려는 이 시나리오에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- B: FSx for Windows File Server는 SMB 프로토콜 기반 Windows 파일 공유용으로 Linux HPC 워크로드의 요구와 맞지 않는다.
- C: S3 Glacier는 아카이브 및 백업용 스토리지 클래스이며 컴퓨팅 인스턴스가 직접 읽고 쓰는 고성능 파일 시스템 역할을 하지 못한다.
- D: gp2 EBS 볼륨은 기본적으로 단일 인스턴스에만 연결되므로 수백 개 인스턴스가 동시에 공유 접근해야 하는 HPC 요구를 충족할 수 없다.

> 💡 **시험 꿀팁**: "Linux 기반 HPC + S3와 통합된 고성능 공유 파일 시스템"이라는 조건이 나오면 FSx for Lustre가 표준 정답입니다.

## QUESTION 163

**문제**: 한 회사가 온프레미스에서 컨테이너화된 애플리케이션을 구축했고, 이를 AWS로 이전하려고 합니다. 이 애플리케이션은 배포 직후 수천 명의 사용자를 확보할 것으로 예상되지만, 회사는 규모에 맞춰 컨테이너 배포를 관리하는 방법에 확신이 없습니다. 운영 오버헤드를 최소화하면서 고가용성 아키텍처에 컨테이너화된 애플리케이션을 배포해야 합니다. 이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. **컨테이너 이미지를 Amazon ECR 리포지토리에 저장한다. AWS Fargate 시작 유형의 Amazon ECS 클러스터에서 컨테이너를 실행하고, 대상 추적으로 수요에 따라 자동 확장한다.**
- B. 컨테이너 이미지를 Amazon ECR에 저장한다. EC2 시작 유형의 ECS 클러스터에서 컨테이너를 실행하고 대상 추적으로 자동 확장한다. (EC2 시작 유형은 사용자가 직접 EC2 용량을 프로비저닝·관리해야 해 운영 부담이 남음)
- C. EC2 인스턴스에서 실행되는 자체 리포지토리에 이미지를 저장하고 여러 AZ의 EC2 인스턴스에서 컨테이너를 실행하며, CloudWatch로 CPU를 모니터링해 필요시 인스턴스를 수동으로 시작한다. (완전 수동 확장 방식으로 오케스트레이션 기능이 없어 오버헤드가 매우 큼)
- D. 컨테이너 이미지를 포함한 EC2 AMI를 생성하고, 여러 AZ의 Auto Scaling 그룹에서 인스턴스를 실행하며 CPU 임계값 기반으로 확장한다. (AMI 기반 방식은 이미지 관리가 번거롭고 컨테이너 오케스트레이션의 배치·헬스체크 기능이 없음)

**정답: A**

**해설**
**AWS Fargate**는 서버를 프로비저닝하거나 관리할 필요가 없는 서버리스 컴퓨팅 엔진으로, **Amazon ECS**와 결합하면 사용자는 컨테이너 정의만 신경 쓰고 나머지 인프라 관리는 AWS가 담당합니다. 대상 추적(target tracking) 자동 확장 정책을 사용하면 실제 트래픽 지표(예: CPU 사용률, 요청 수)에 따라 자동으로 태스크 수를 늘리거나 줄여 배포 직후 급증하는 사용자 트래픽에도 신속히 대응할 수 있습니다. ECR에 이미지를 저장해 배포 파이프라인을 단순화하는 것도 이 아키텍처의 자연스러운 구성 요소입니다.

**왜 다른 보기는 오답인가**
- B: EC2 시작 유형은 컨테이너가 실행될 EC2 인스턴스의 용량 계획과 패치, 스케일링을 사용자가 직접 관리해야 하므로 Fargate보다 운영 오버헤드가 크다.
- C: 자체 구축한 레지스트리와 수동 CPU 모니터링 후 인스턴스 시작 방식은 오케스트레이션 자동화가 전혀 없어 규모 확장에 취약하다.
- D: 컨테이너 이미지를 AMI에 굽는 방식은 배포 주기마다 AMI를 재생성해야 해 비효율적이며, ECS/EKS 같은 오케스트레이터의 이점(자동 배치, 헬스체크, 롤링 업데이트)을 누리지 못한다.

> 💡 **시험 꿀팁**: "컨테이너화된 애플리케이션 + 운영 오버헤드 최소화 + 고가용성"이라는 조건이 나오면 ECS + Fargate 조합이 표준 정답입니다.

## QUESTION 164

**문제**: 한 회사에 처리할 페이로드를 담은 메시지를 보내는 발신자 애플리케이션과, 그 메시지를 수신해 처리하는 처리 애플리케이션 두 가지가 있습니다. 발신자 애플리케이션은 시간당 약 1,000개의 메시지를 보낼 수 있고, 메시지 처리에는 최대 2일이 걸릴 수 있습니다. 처리에 실패한 메시지는 나머지 메시지 처리에 영향을 주지 않도록 별도로 보관해야 합니다. 이러한 요구 사항을 가장 운영 효율적으로 충족하는 솔루션은 무엇입니까?

**보기**
- A. Redis 데이터베이스를 실행하는 EC2 인스턴스를 구성해 두 애플리케이션이 메시지를 저장·처리·삭제하도록 한다. (EC2 기반 Redis 자체 구축과 운영 관리에 상당한 오버헤드가 발생)
- B. Amazon Kinesis Data Streams로 메시지를 수신하고 처리 애플리케이션을 Kinesis Client Library(KCL)와 통합한다. (실시간 스트리밍에 최적화된 서비스로, 장시간 처리와 실패 메시지 격리 요구에는 추가 복잡성이 발생)
- C. **발신자 및 처리 애플리케이션을 Amazon SQS 대기열과 통합하고, 처리에 실패한 메시지를 위한 데드 레터 큐(DLQ)를 구성한다.**
- D. 처리 애플리케이션이 Amazon SNS 주제를 구독해 알림을 받고, 발신자 애플리케이션이 해당 주제에 메시지를 발행하도록 통합한다. (SNS는 Pub/Sub 브로드캐스트용으로 재시도·순서·장시간 보관 같은 큐잉 특성이 부족함)

**정답: C**

**해설**
**Amazon SQS**는 발신자와 처리자 사이에 완전관리형 메시지 큐를 두어 두 애플리케이션을 느슨하게 결합(decoupling)하고, 최대 2일까지 걸리는 장시간 처리도 가시성 제한 시간(visibility timeout) 조정만으로 안전하게 지원합니다. 여기에 **데드 레터 큐(DLQ)**를 구성하면 반복적으로 처리에 실패하는 메시지를 별도로 격리해 나머지 정상 메시지 처리 흐름에 영향을 주지 않으면서도 실패 원인을 나중에 분석할 수 있습니다. 이는 관리형 서비스 조합만으로 요구 사항을 충족하는 가장 운영 효율적인 방법입니다.

**왜 다른 보기는 오답인가**
- A: EC2에서 Redis를 직접 운영하면 고가용성 구성, 패치, 백업 등 추가적인 운영 부담이 발생한다.
- B: Kinesis Data Streams와 KCL은 실시간 스트림 처리에 강점이 있지만, 이 시나리오처럼 단순한 1:1 작업 큐잉과 실패 격리에는 불필요하게 복잡하다.
- D: SNS는 여러 구독자에게 메시지를 동시에 전달하는 발행-구독 모델로, 순서 보장이나 실패 메시지 재시도·격리 같은 큐 특유의 기능이 없어 이 요구에 적합하지 않다.

> 💡 **시험 꿀팁**: "처리 실패 메시지를 격리해서 나머지 처리에 영향을 주지 않아야 한다"는 조건이 나오면 SQS + DLQ가 표준 정답입니다.

## QUESTION 165

**문제**: 솔루션 설계자가 정적 웹 사이트를 저장하기 위해 Amazon S3 오리진과 Amazon CloudFront를 사용하는 솔루션을 설계해야 합니다. 회사의 보안 정책에 따라 모든 웹 사이트 트래픽은 AWS WAF에서 검사되어야 합니다. 솔루션 설계자는 이 요구 사항을 어떻게 충족해야 합니까?

**보기**
- A. AWS WAF의 ARN에서만 오는 요청을 수락하도록 S3 버킷 정책을 구성한다. (버킷 정책의 principal로 WAF ARN을 지정하는 방식 자체가 존재하지 않음)
- B. S3 오리진에서 콘텐츠를 요청하기 전에 모든 수신 요청을 AWS WAF로 "전달"하도록 CloudFront를 구성한다. (WAF는 CloudFront에 연결되어 요청을 검사하는 방식으로 동작하며, 이런 전달 개념은 존재하지 않음)
- C. CloudFront IP 주소만 S3에 접근하도록 허용하는 보안 그룹을 구성하고 WAF를 CloudFront에 연결한다. (S3에는 보안 그룹 개념이 적용되지 않으며 IP 기반 제한은 OAI/OAC만큼 안전하지 않음)
- D. **원본 액세스 ID(OAI)를 사용해 S3 버킷에 대한 접근을 CloudFront로만 제한하고, 배포에서 AWS WAF를 활성화한다.**

**정답: D**

**해설**
**OAI(Origin Access Identity, 최신 권장 방식은 OAC)**를 사용하면 S3 버킷을 퍼블릭으로 열지 않고 오직 지정된 CloudFront 배포를 통해서만 콘텐츠에 접근하도록 강제할 수 있습니다. 이 상태에서 CloudFront 배포에 **AWS WAF**를 연결하면 사용자로부터 오는 모든 HTTP/HTTPS 요청이 S3에 도달하기 전에 WAF 규칙(SQL 인젝션, XSS 등)으로 검사됩니다. 즉 "우회 경로 차단(OAI)"과 "요청 검사(WAF)"를 함께 적용해야 모든 웹 사이트 트래픽이 예외 없이 WAF를 거치도록 보장할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: S3 버킷 정책의 principal에 WAF ARN을 지정하는 기능은 존재하지 않는다.
- B: CloudFront가 요청을 별도의 WAF 서비스로 "전달"하는 구조가 아니라, WAF가 CloudFront 배포에 직접 연결되어 요청을 가로채 검사한다.
- C: S3는 보안 그룹의 적용 대상이 아니며, IP 기반 접근 제어는 CloudFront 배포가 바뀌거나 IP 범위가 변경될 때 취약점이 생길 수 있어 OAI보다 안전성이 떨어진다.

> 💡 **시험 꿀팁**: "S3 정적 사이트 + CloudFront + 모든 트래픽을 WAF로 검사"라는 조건이 나오면 OAI(또는 OAC)로 직접 접근을 차단하고 CloudFront에 WAF를 연결하는 것이 표준 정답입니다.

- B: 교차 리전 복제는 데이터 내구성·재해복구 목적이며, 엣지 캐싱을 통한 지연시간 단축이나 오리진 부하 절감 효과는 없다.

> 💡 **시험 꿀팁**: "S3에 저장된 정적 콘텐츠 + 전 세계 대량 조회"라는 조건이 나오면 S3 + CloudFront 조합이 표준 정답입니다.

- D: Amazon GuardDuty는 CloudTrail·VPC Flow Logs 등을 분석해 이상 행위를 탐지하는 위협 탐지 서비스일 뿐, 공격 트래픽 자체를 차단·완화하는 기능은 없다.

> 💡 **시험 꿀팁**: "DDoS 공격 위험 감소"라는 조건이 나오면 AWS Shield(특히 정교한 대규모 공격은 Advanced)가 표준 정답입니다.

**AWS WAF**는 지리적 일치(geo match) 규칙 문을 지원해 요청의 출발 국가를 기준으로 트래픽을 허용하거나 차단할 수 있습니다. ALB에 WAF 웹 ACL을 연결하고 허용할 국가에 대한 지리적 일치 규칙을 추가(또는 차단할 국가에 대한 규칙 추가)하면, 정책에서 요구하는 특정 국가 전용 접근 제한을 애플리케이션 코드 변경 없이 구현할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 보안 그룹은 인스턴스 수준의 IP/포트 화이트리스트일 뿐 국가 정보를 인식하지 못한다.
- B: ALB의 보안 그룹 역시 IP 대역 기반 제어만 가능하며 지리적 위치 판단 기능이 없다.
- D: 네트워크 ACL도 서브넷 단위의 IP 기반 허용/거부 규칙으로 국가 단위 필터링을 지원하지 않는다.

> 💡 **시험 꿀팁**: "특정 국가에서만 접근을 허용/차단"이라는 조건이 나오면 AWS WAF의 지리적 일치(Geo Match) 규칙이 표준 정답입니다.

## QUESTION 172

**문제**: 솔루션 설계자가 애플리케이션을 위한 새 Amazon CloudFront 배포를 생성하고 있습니다. 사용자가 제출하는 정보 중 일부는 민감한 정보입니다. 애플리케이션은 HTTPS를 사용하지만 추가 보안 계층이 필요하며, 민감한 정보는 전체 애플리케이션 스택에서 보호되어야 하고 정보에 대한 접근은 특정 애플리케이션으로 제한되어야 합니다. 솔루션 설계자는 어떤 조치를 취해야 합니까?

**보기**
- A. CloudFront 서명된 URL을 구성한다. (콘텐츠 접근 권한·기간을 제한하는 기능일 뿐 저장된 민감 데이터 자체를 암호화하지 않음)
- B. CloudFront 서명된 쿠키를 구성한다. (마찬가지로 접근 제어 수단일 뿐 데이터 필드 자체를 보호하지 않음)
- C. **CloudFront 필드 수준 암호화 프로필을 구성한다.**
- D. 뷰어 프로토콜 정책과 오리진 프로토콜 정책을 모두 HTTPS 전용으로 설정한다. (전송 구간 암호화만 강화할 뿐, 애플리케이션 스택 전체에서 특정 필드를 계속 암호화 상태로 유지하지는 못함)

**정답: C**

**해설**
**CloudFront 필드 수준 암호화**는 HTTPS로 이미 보호되는 전송 구간을 넘어, 사용자가 입력한 특정 필드(예: 신용카드 번호, 주민등록번호 등 민감 데이터)를 공개 키로 추가 암호화해 오리진 서버와 그 이후의 애플리케이션 스택 전체에서도 암호화된 상태를 유지합니다. 오직 해당 개인 키를 보유한 특정 애플리케이션(백엔드 컴포넌트)만 복호화해 값을 볼 수 있으므로, "전체 스택에서 보호 + 특정 애플리케이션으로 접근 제한"이라는 두 요구를 동시에 충족합니다.

**왜 다른 보기는 오답인가**
- A: 서명된 URL은 특정 사용자에게 제한된 시간 동안 콘텐츠 접근 권한을 부여하는 기능으로, 필드 단위 데이터 암호화와는 무관하다.
- B: 서명된 쿠키도 URL과 동일하게 접근 제어 목적이며 데이터 자체를 암호화하지 않는다.
- D: HTTPS 전용 설정은 뷰어-CloudFront-오리진 구간의 전송 암호화만 보장할 뿐, 오리진 이후 애플리케이션 스택 내부에서 데이터가 평문으로 노출되는 것을 막지 못한다.

> 💡 **시험 꿀팁**: "HTTPS만으로는 부족하고, 특정 필드를 전체 스택에서 암호화 유지 + 특정 애플리케이션만 열람 가능"이라는 조건이 나오면 CloudFront 필드 수준 암호화가 표준 정답입니다.

## QUESTION 173

**문제**: 한 게임 회사가 AWS에서 브라우저 기반 애플리케이션을 호스팅합니다. 사용자들은 Amazon S3에 저장된 다량의 비디오와 이미지를 소비하며, 이 콘텐츠는 모든 사용자에게 동일합니다. 애플리케이션이 인기를 얻으며 전 세계 수백만 명이 이 미디어 파일에 접근하고 있습니다. 회사는 오리진 부하를 줄이면서 사용자에게 파일을 제공하려고 합니다. 이러한 요구 사항을 가장 비용 효율적으로 충족하는 솔루션은 무엇입니까?

**보기**
- A. 웹 서버 앞에 AWS Global Accelerator를 배포한다. (Global Accelerator는 TCP/UDP 기반 비-HTTP 워크로드나 고정 IP가 필요한 경우에 강점이 있으며, 정적 미디어 캐싱에는 CloudFront보다 비용 효율이 낮음)
- B. **S3 버킷 앞에 Amazon CloudFront 웹 배포를 둔다.**
- C. 웹 서버 앞에 Redis용 Amazon ElastiCache를 배포한다. (ElastiCache는 데이터베이스 조회 지연을 줄이는 인메모리 캐시로 정적 파일 배포용 CDN 역할을 하지 않음)
- D. 웹 서버 앞에 Memcached용 Amazon ElastiCache를 배포한다. (C와 동일한 이유로 정적 미디어 파일 배포에는 부적합)

동일한 비디오·이미지 콘텐츠를 전 세계 수백만 사용자가 반복적으로 요청하는 상황은 **Amazon CloudFront**의 전형적인 사용 사례입니다. CloudFront를 S3 버킷 앞에 배치하면 자주 요청되는 콘텐츠가 엣지 로케이션에 캐싱되어 사용자에게 더 빠르게 전달되는 동시에, S3 오리진으로 가는 반복 요청이 크게 줄어들어 오리진 부하와 데이터 전송 비용이 동시에 감소합니다. 이는 정적 파일을 대규모로 배포하면서 비용까지 최적화하는 가장 표준적인 조합입니다.

**왜 다른 보기는 오답인가**

- C, D: ElastiCache(Redis/Memcached)는 데이터베이스 앞단에서 쿼리 결과를 캐싱해 지연을 줄이는 용도로, S3에 저장된 대용량 미디어 파일 자체를 캐싱·배포하는 CDN 기능을 대체하지 못한다.

> 💡 **시험 꿀팁**: "S3의 동일한 정적 콘텐츠를 전 세계 다수 사용자가 반복 요청 + 오리진 부하 감소"라는 조건이 나오면 CloudFront가 표준 정답입니다.

## QUESTION 174

**문제**: 한 회사가 ALB 뒤의 단일 가용 영역에 있는 Amazon EC2 Auto Scaling 그룹에서 6개의 프런트엔드 웹 서버를 실행하는 다중 계층 애플리케이션을 운영하고 있습니다. 솔루션 설계자는 애플리케이션을 수정하지 않고 인프라를 고가용성으로 만들어야 합니다. 어떤 아키텍처를 선택해야 합니까?

**보기**
- A. 두 리전 각각에서 3개의 인스턴스를 사용하는 Auto Scaling 그룹을 생성한다. (Auto Scaling 그룹은 리전을 넘어 인스턴스를 배치할 수 없어 애초에 구현 불가능한 접근)
- B. **2개의 가용 영역 각각에서 3개의 인스턴스를 사용하도록 기존 Auto Scaling 그룹을 수정한다.**
- C. 다른 리전에서 더 많은 인스턴스를 빠르게 생성할 수 있는 Auto Scaling 템플릿을 만든다. (재해복구 관점의 준비 작업일 뿐 즉각적인 다중 AZ 이중화를 제공하지 못함)
- D. ALB를 라운드 로빈 구성으로 변경해 웹 계층 트래픽 균형을 맞춘다. (ALB의 라운드로빈은 이미 기본 동작이며, 단일 AZ 장애 시 전체 다운이라는 근본 문제를 해결하지 못함)

**정답: B**

**해설**
Auto Scaling 그룹은 리전 내 여러 가용 영역(AZ)에 걸쳐 인스턴스를 분산 배치할 수 있으며, 여기에 로드 밸런서가 각 AZ로 들어오는 트래픽을 분배합니다. 기존 ASG의 설정을 수정해 인스턴스가 2개 AZ에 총 6대(각 3대)로 분산되도록 하면, 애플리케이션 코드는 전혀 변경하지 않으면서도 한 AZ에 장애가 발생해도 다른 AZ가 트래픽을 계속 처리할 수 있는 고가용성 아키텍처가 완성됩니다. 이는 가장 간단하고 비용 대비 효과적인 고가용성 확보 방법입니다.

**왜 다른 보기는 오답인가**
- A: Auto Scaling 그룹은 단일 리전 내에서만 동작하며 여러 리전에 걸친 단일 ASG를 만들 수 없다.
- C: 다른 리전에 빠르게 인스턴스를 생성하는 준비는 재해 복구(DR) 대비책이지, AZ 장애에 즉시 대응하는 고가용성 아키텍처가 아니다.
- D: ALB는 기본적으로 등록된 대상에 트래픽을 분산하는 로드 밸런싱을 이미 수행하고 있으며, 이 문제의 근본 원인인 "단일 AZ에만 인스턴스가 존재"하는 구조는 해결하지 못한다.

> 💡 **시험 꿀팁**: "애플리케이션 수정 없이 인프라만 고가용성으로 개선"이라는 조건이 나오면 기존 Auto Scaling 그룹을 여러 가용 영역에 걸치도록 수정하는 것이 표준 정답입니다.

Lambda처럼 짧은 수명의 함수가 대량으로 동시 실행되면 데이터베이스에 대한 연결이 빠르게 열리고 닫히기를 반복해 연결 수가 폭증하고 메모리·CPU 자원을 고갈시킬 수 있습니다. **Amazon RDS 프록시**는 데이터베이스 앞단에서 커넥션 풀을 관리하며 연결을 재사용하기 때문에, 매번 새 연결을 맺는 데 드는 오버헤드를 없애고 급격한 트래픽 스파이크에도 데이터베이스가 과다 구독되지 않도록 보호합니다. Lambda 함수는 연결 대상 엔드포인트만 RDS 프록시로 바꾸면 되므로 애플리케이션 코드 변경도 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: 프로비저닝된 동시성은 Lambda의 콜드 스타트 지연을 줄이는 기능일 뿐 데이터베이스 연결 폭주 문제와는 무관하며, 글로벌 데이터베이스는 다중 리전 재해복구/저지연 읽기용으로 이 시나리오의 원인과 관계가 없다.
- C: 읽기 전용 복제본과 쿼리 파라미터 기반 라우팅은 애플리케이션 로직을 상당 부분 변경해야 하고, 애초에 문제였던 "많은 열린 연결" 자체를 줄이지 못한다.
- D: DynamoDB로의 마이그레이션은 데이터 모델과 애플리케이션 코드를 전면적으로 재설계해야 하는 큰 작업으로 "최소한의 변경"이라는 조건에 정면으로 위배된다.

> 💡 **시험 꿀팁**: "Lambda + RDS 조합에서 연결 수 급증으로 인한 CPU/메모리 문제"라는 조건이 나오면 Amazon RDS 프록시가 표준 정답입니다.

- D: D 역시 존재하지 않는 개념(DB 인스턴스와 EC2 간 신뢰 관계)을 전제로 하며 Systems Manager를 보안 주체로 지정하는 것도 이 요구 사항 달성과 무관하다.

> 💡 **시험 꿀팁**: "EC2 애플리케이션이 Parameter Store의 암호화된 자격 증명에 안전하게 접근"이라는 조건이 나오면 읽기 권한 + KMS Decrypt 권한을 가진 IAM 역할을 EC2에 할당하는 것이 표준 정답입니다.

- C. **AWS WAF로 Amazon API Gateway를 보호한다.**
- D. AWS Shield Standard와 Amazon GuardDuty를 함께 사용한다. (GuardDuty는 위협 탐지 서비스로 DDoS 완화나 SQL 인젝션 차단 기능이 없음)
- E. Amazon API Gateway와 함께 AWS Shield Standard를 사용한다. (Shield Standard는 기본 제공되는 네트워크/전송 계층 방어만 제공하며, "대규모의 정교한" 공격에 대한 고급 완화 기능은 Advanced에만 있음)

**정답: B, C**

**해설**
이 시나리오는 두 종류의 위협, 즉 "웹 익스플로잇(SQL 인젝션)"과 "대규모·정교한 DDoS 공격"을 모두 방어해야 합니다. **AWS WAF**는 API Gateway와 같은 애플리케이션 계층 리소스에 연결되어 SQL 인젝션, XSS 등 일반적인 웹 공격 패턴을 규칙 기반으로 차단합니다. 한편 **AWS Shield Advanced**는 EC2, ELB(NLB 포함), CloudFront, Route 53, Global Accelerator 리소스에 대해 정교하고 대규모인 DDoS 공격까지 탐지·완화하며 AWS Shield 대응 팀(SRT)의 지원과 AWS WAF와의 통합도 제공합니다. 따라서 NLB에는 Shield Advanced를, API Gateway에는 WAF를 각각 적용하는 조합이 두 요구 사항을 모두 충족하는 가장 강력한 보호책입니다.

**왜 다른 보기는 오답인가**
- A: AWS WAF는 HTTP/HTTPS 요청을 검사하는 애플리케이션 계층(L7) 방화벽으로, 전송 계층(L4)에서 동작하는 NLB에는 직접 연결할 수 없다.
- D: Amazon GuardDuty는 로그 기반 이상 탐지 서비스로 DDoS 공격을 완화하거나 SQL 인젝션을 차단하는 기능이 없어 이 요구 사항에 부합하지 않는다.
- E: AWS Shield Standard는 모든 AWS 계정에 기본 제공되는 네트워크/전송 계층 DDoS 방어이지만, "대규모의 정교한" 공격에 대한 고급 완화·가시성·SRT 지원 등은 Shield Advanced에서만 제공된다.

> 💡 **시험 꿀팁**: "SQL 인젝션 등 웹 공격 방어 + 대규모 정교한 DDoS 완화"라는 조건이 함께 나오면 애플리케이션 계층 리소스(API Gateway, ALB 등)에는 AWS WAF를, 네트워크 계층 리소스(NLB, EC2, CloudFront 등)에는 AWS Shield Advanced를 적용하는 조합이 표준 정답입니다.
