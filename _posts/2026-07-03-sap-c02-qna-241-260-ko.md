## QUESTION 241

**문제**: 스마트 자동차 회사, MQTT로 차량 데이터를 애플리케이션에 전송, 5분마다 처리 후 온프레미스 스토리지에 복사, 이상 감지. 차량 수 증가 + 데이터량 증가로 온프레미스 스토리지가 확장 못해 데이터 손실. AWS로 현대화, 최소 운영 오버헤드는?

**보기**
- A. IoT Greengrass로 MSK에 전송 + Kafka 앱으로 S3 저장 + SageMaker 사전훈련 모델로 이상 감지(MSK 클러스터 운영 자체가 상대적으로 관리 오버헤드가 크고, Greengrass는 엣지용으로 이 클라우드 수집 시나리오와 다소 안 맞음).
- B. **IoT Core로 차량 데이터 수신. 데이터를 S3에 저장하는 Kinesis Data Firehose 전송 스트림으로 라우팅하는 규칙 구성. 전송 스트림에서 읽어 이상을 감지하는 Kinesis Data Analytics 애플리케이션 생성.**
- C. IoT FleetWise + Kinesis Data Streams + Firehose로 S3 저장 + Glue 내장 ML 변환으로 이상 감지(IoT FleetWise는 주로 차량 데이터 표준화/전송 최적화용이며, Glue의 ML 변환은 이상 탐지에 특화된 기능이 아님).
- D. Amazon MQ(RabbitMQ) + Firehose로 S3 저장 + Lookout for Metrics로 이상 감지(MQTT 네이티브 지원이 IoT Core만큼 직접적이지 않고, RabbitMQ 브로커 관리가 추가 오버헤드).

**정답: B**

**해설**
**AWS IoT Core**는 MQTT를 네이티브로 지원하는 완전관리형 서비스로 수백만 대의 차량 연결을 손쉽게 처리합니다. **IoT 규칙**으로 데이터를 **Kinesis Data Firehose**로 라우팅해 S3에 자동 저장하고, **Kinesis Data Analytics**로 스트림을 실시간 분석해 이상을 감지하는 조합은 완전 관리형 서비스만으로 구성되어 운영 오버헤드가 최소입니다.

**왜 다른 보기는 오답인가**
- A: 자체 MSK 클러스터 운영은 완전 서버리스인 B보다 관리 오버헤드가 크고, Greengrass는 엣지 게이트웨이용으로 이 시나리오의 핵심(클라우드로 대량 수집)과 다소 어긋납니다.
- C: Glue의 내장 ML 변환은 ETL 과정의 데이터 정제/매칭에 특화되어 있으며, 실시간 이상 탐지에는 Kinesis Data Analytics가 더 적합합니다.
- D: RabbitMQ 브로커(Amazon MQ)를 관리하는 것은 IoT Core의 완전 관리형 MQTT 수신보다 오버헤드가 큽니다.

> 💡 **시험 꿀팁**: MQTT 기반 대량 IoT 데이터 수집에는 **IoT Core**, 저장에는 **Kinesis Data Firehose(S3)**, 실시간 이상 탐지에는 **Kinesis Data Analytics**의 완전관리형 조합이 최소 운영 오버헤드 표준 정답입니다.

## QUESTION 242

**문제**: 개발 팀이 IAM 사용자 액세스 키를 코드에 넣고 CodeCommit에 커밋. 보안 팀은 이 취약점을 **자동으로** 찾아 수정하려 함. 자격 증명이 자동으로 적절히 보호되도록 하는 솔루션은?

**보기**
- A. Systems Manager Run Command로 야간에 개발 인스턴스에서 자격 증명 검색 + Secrets Manager로 교체(코드 저장소 자체가 아닌 인스턴스를 스캔하는 것이라 목표와 어긋남).
- B. 예약된 Lambda로 CodeCommit 코드 다운로드/스캔 + 발견 시 새 자격 증명 생성 후 KMS에 저장(KMS는 암호화 키 서비스이지 자격 증명 저장/교체 서비스가 아님 — 개념 오류. 예약 스캔도 실시간 커밋 시점 대응보다 느림).
- C. Macie로 CodeCommit에서 자격 증명 검색 + 발견 시 Lambda로 비활성화+알림(Macie는 주로 S3의 민감 데이터 탐지에 특화되어 있으며 CodeCommit 리포지토리 스캔이 주 용도가 아님).
- D. **CodeCommit 트리거를 구성해 새 코드 제출 시 Lambda 함수를 호출해 자격 증명 스캔. 발견되면 IAM에서 비활성화하고 사용자에게 알림.**

**정답: D**

**해설**
**CodeCommit 트리거**를 사용해 코드가 커밋되는 **바로 그 시점**에 Lambda 함수를 호출해 자격 증명 패턴을 스캔하고, 발견 즉시 **IAM에서 해당 액세스 키를 비활성화**하는 것이 가장 빠르고 자동화된 대응입니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스를 스캔하는 것은 코드 저장소(CodeCommit)에 커밋된 자격 증명을 직접 찾는 목표와 어긋납니다.
- B: KMS는 암호화 키 관리 서비스로, 유출된 IAM 액세스 키를 저장하거나 교체하는 용도가 아닙니다. 야간 예약 스캔도 실시간성이 떨어집니다.
- C: Amazon Macie는 주로 S3에 저장된 민감 데이터를 탐지하는 서비스이며, CodeCommit 리포지토리 코드 스캔에는 최적화되어 있지 않습니다.

> 💡 **시험 꿀팁**: **코드 커밋 시점에 즉시 자격 증명 유출을 탐지하고 자동 대응**하려면 **CodeCommit 트리거 + Lambda(스캔) + IAM(키 비활성화)** 조합이 표준 정답입니다.

## QUESTION 243

**문제**: S3 데이터 레이크, 여러 AWS 계정의 수백 개 애플리케이션이 접근. 공용 인터넷 접근 금지 + 최소 권한. 각 애플리케이션의 특정 VPC로 제한된 **S3 액세스 포인트** 사용 계획. 구현 단계는? (2개 선택)

**보기**
- A. **S3 버킷을 소유한 계정에 각 애플리케이션별 S3 액세스 포인트 생성. 각 액세스 포인트를 해당 애플리케이션의 VPC로만 제한. 액세스 포인트를 통한 접근만 요구하도록 버킷 정책 업데이트.**
- B. 각 애플리케이션 VPC에 S3 인터페이스 엔드포인트 생성 + 엔드포인트 정책으로 액세스 포인트 허용 + S3 엔드포인트에 VPC 게이트웨이 연결(S3는 인터페이스 엔드포인트가 아닌 게이트웨이 엔드포인트를 사용 — "인터페이스 엔드포인트"와 "게이트웨이 연결"이 혼재된 개념 오류).
- C. **각 애플리케이션 VPC에 S3 게이트웨이 엔드포인트 생성. 엔드포인트 정책으로 S3 액세스 포인트로의 접근만 허용. 액세스 포인트 접근에 사용되는 라우팅 테이블 지정.**
- D. 각 AWS 계정에서 애플리케이션별 액세스 포인트 생성 후 버킷에 연결(액세스 포인트는 버킷을 소유한 계정에서 만드는 것이 표준이며, VPC 제한이 있는 액세스 포인트를 다른 계정에서 만드는 방식은 일반적이지 않음).
- E. 데이터 레이크 VPC에 게이트웨이 엔드포인트 생성 + 버킷 접근 허용 엔드포인트 정책(액세스 포인트가 아닌 버킷에 직접 접근을 허용하는 방식으로, "특정 VPC로 제한된 액세스 포인트"라는 요구와 다름).

**정답: A, C**

**해설**
**S3 액세스 포인트는 버킷을 소유한 계정에서 생성**하며, 각 애플리케이션 전용으로 만들어 특정 VPC로 제한할 수 있습니다(A). 각 애플리케이션의 VPC에는 **S3 게이트웨이 엔드포인트**(S3는 인터페이스가 아닌 게이트웨이 엔드포인트 사용)를 만들고, 엔드포인트 정책으로 해당 액세스 포인트로의 접근만 허용하면(C), 공용 인터넷을 거치지 않고 VPC별로 제한된 최소 권한 접근이 구현됩니다.

**왜 다른 보기는 오답인가**
- B: S3는 게이트웨이 엔드포인트를 사용하는 것이 표준이며, "인터페이스 엔드포인트"와 "VPC 게이트웨이 연결"을 혼용한 설명은 개념적으로 부정확합니다.
- D: 액세스 포인트는 버킷을 소유한 계정에서 생성하는 것이 표준이며, 각 애플리케이션 계정에서 개별적으로 만들어 버킷에 "연결"하는 방식은 일반적인 패턴이 아닙니다.
- E: 데이터 레이크 VPC에 게이트웨이 엔드포인트를 만들어 버킷에 직접 접근을 허용하는 것은 "각 애플리케이션의 특정 VPC로 제한된 액세스 포인트"라는 세밀한 제어 요구와 다릅니다.

> 💡 **시험 꿀팁**: S3 액세스 포인트는 **버킷 소유 계정에서 생성**하며 특정 VPC로 제한할 수 있고, 각 소비자 VPC에는 **S3 게이트웨이 엔드포인트**(인터페이스 아님)를 두어 엔드포인트 정책으로 특정 액세스 포인트만 허용하는 것이 표준 조합입니다.

## QUESTION 244

**문제**: 하이브리드 환경(VPC+EC2, 앱 로그를 CloudWatch로 전송, EC2가 온프레미스 관계형 DB 읽음). DB 연결 EC2를 **거의 실시간**으로 모니터링해야 함. 온프레미스에 이미 Splunk 모니터링 솔루션 있음. 네트워킹 트래픽을 Splunk로 보내는 방법은?

**보기**
- A. VPC 흐름 로그→CloudWatch + Lambda로 주기적 S3 내보내기 + 액세스 키로 Splunk가 S3에서 가져오기(주기적 배치 방식이라 "거의 실시간" 요구에 부합하지 않고, 액세스 키 사용은 보안상 덜 바람직).
- B. **VPC 흐름 로그 활성화해 CloudWatch로 전송. 로그 이벤트를 Kinesis Data Firehose 전송 스트림으로 보내는 CloudWatch Logs 구독 생성(Firehose 대상: Splunk).**
- C. 모든 DB 요청을 EC2 IP와 함께 로깅 요청 + CloudWatch→S3 내보내기 + Athena 쿼리 + 결과를 다른 S3로 + Lambda로 Splunk 전송(다단계 배치 처리라 실시간성이 크게 떨어짐).
- D. Kinesis Data Analytics(SQL)로 CloudWatch 로그를 Kinesis 스트림으로 전송 + 1분 슬라이딩 윈도우 + 이상 탐지 SQL 쿼리 + Firehose로 Splunk 전송(네트워킹 트래픽 자체의 실시간 전달보다는 이상 탐지 분석에 초점이 맞춰진 과도하게 복잡한 접근).

**정답: B**

**해설**
**CloudWatch Logs 구독 필터(subscription filter)**를 사용해 로그 이벤트를 **Kinesis Data Firehose**로 실시간 스트리밍하고, Firehose가 **Splunk를 대상**으로 데이터를 직접 전달하도록 구성하는 것이 CloudWatch에서 온프레미스 Splunk로 거의 실시간 데이터를 전달하는 표준 네이티브 통합 패턴입니다(Firehose가 Splunk 대상을 직접 지원합니다).

**왜 다른 보기는 오답인가**
- A: 주기적(batch) S3 내보내기 방식은 "거의 실시간"이라는 요구에 지연이 발생하며, 장기 액세스 키 사용도 보안 모범 사례에 어긋납니다.
- C: 여러 단계의 배치 처리(S3 내보내기→Athena→S3→Lambda)를 거치는 것은 실시간성과 거리가 멉니다.
- D: 이상 탐지 분석에 초점을 맞춘 접근으로, 단순히 "네트워킹 트래픽을 Splunk로 실시간 전달"하는 이 문제의 핵심 요구보다 불필요하게 복잡합니다.

> 💡 **시험 꿀팁**: CloudWatch Logs를 온프레미스 **Splunk**로 거의 실시간 전달하려면 **CloudWatch Logs 구독 필터 → Kinesis Data Firehose(Splunk 대상 네이티브 지원)** 조합이 표준 정답입니다.

## QUESTION 245

**문제**: 5개 개발 팀, 각자 5개 AWS 계정. 매월 수동으로 콘솔 로그인해 비용 확인 후 재무 팀에 보고. 엄격한 규정 준수 요구사항: 리소스는 **미국 리전에서만** 생성되어야 하나 일부 다른 리전에서 생성됨. 재무 팀이 모든 계정 지출을 추적/통합 + 미국 리전 제한 강제. 운영 효율적인 조합은? (3개 선택)

**보기**
- A. 새 마스터 계정 생성 + 재무 팀용 S3 버킷 + Cost and Usage Report로 월별 보고서 저장(가능한 방법 중 하나지만, B/E와 결합할 필요 없이 B의 조직 구성이 먼저 필요하며 A 자체는 필수 단계로 선택되지 않음).
- B. **새 마스터 계정 생성. 모든 기능 활성화 상태로 Organizations에 조직 배포. 모든 기존 계정을 조직에 초대해 수락 확인.**
- C. 모든 개발 팀 포함 OU 생성 + 미국 리전만 허용하는 SCP(Allow 방식, 조건이 있는 Allow SCP는 구성이 더 복잡하고 일반적으로 Deny 방식이 더 명확).
- D. **모든 개발 팀 포함 OU 생성. 미국 이외 리전에서 리소스 생성을 거부하는 SCP 생성. SCP를 OU에 적용.**
- E. **마스터 계정에서 Billing and Cost Management 콘솔 조회 권한이 있는 IAM 역할 생성. 재무 팀 사용자가 이 역할을 맡도록 허용. Cost Explorer와 Billing 콘솔로 비용 분석.**
- F. 각 AWS 계정에서 개별적으로 Billing 콘솔 조회 역할 생성(계정마다 개별 구성해야 해서 "운영상 가장 효율적"이라는 요구에 맞지 않음 — Organizations 통합 결제를 활용하는 것이 더 효율적).

**정답: B, D, E**

**해설**

- B: 인터페이스 엔드포인트는 클라이언트 측 VPC에 있으므로, 로깅 서비스 서브넷과 "엔드포인트 서브넷" 간 통신이라는 설명 자체가 실제 아키텍처와 맞지 않습니다.
- D: NLB를 거쳐 트래픽이 전달되므로, EC2의 보안 그룹은 원본 클라이언트가 아니라 NLB(또는 NLB가 위치한 서브넷)로부터의 트래픽을 허용해야 합니다.
- E: **Network Load Balancer 자체는 보안 그룹 개념을 갖지 않습니다**(대상 인스턴스의 보안 그룹으로 제어) — 이 보기 자체가 개념적으로 성립하지 않습니다.

> 💡 **시험 꿀팁**: NLB를 경유한 PrivateLink 트래픽이 백엔드에 도달하지 못하면, **NLB 서브넷 ↔ 백엔드(EC2) 서브넷 간 NACL 양방향 허용**과 **백엔드 EC2의 보안 그룹이 NLB 소스로부터의 인바운드를 허용**하는지 확인하세요. **NLB 자체에는 보안 그룹이 없다**는 점을 기억하세요.

## QUESTION 256

**문제**: S3에 수백만 개 객체(S3 Standard, 자주 액세스, SSE-KMS 암호화). 접근하는 사용자/앱 수 급증. 월별 청구서에서 **S3 요청 급증으로 KMS 비용 증가** 확인. 애플리케이션 변경 최소화하며 비용 최적화, 최소 운영 오버헤드는?

**보기**

- B. **SSE-S3(Amazon S3 관리형 키)로 새 버킷 생성. S3 배치 작업으로 기존 객체를 새 버킷에 복사, SSE-S3 지정.**

**정답: B**

**해설**

**왜 다른 보기는 오답인가**
- A: SSE-C는 애플리케이션이 매 요청마다 암호화 키 자체를 제공해야 해서 코드 변경이 훨씬 크고 키 관리 부담도 애플리케이션 측으로 이전됩니다.
- C: CloudHSM은 전용 하드웨어 보안 모듈로 SSE-KMS보다 비용이 더 크면 컸지 절감 방향이 아닙니다.
- D: 객체들이 "자주 액세스"된다고 명시되어 있으므로, 스토리지 계층화/아카이브는 이 시나리오(빈번한 접근)와 무관하며 KMS 비용 문제를 해결하지 못합니다.

> 💡 **시험 꿀팁**: **SSE-KMS의 요청량 기반 API 호출 비용이 급증**할 때, 애플리케이션 변경을 최소화하며 해결하려면 **SSE-S3(Amazon S3 관리형 키)로 전환**하는 것이 표준 정답입니다 — KMS API 호출 자체가 사라지기 때문입니다. 대량 객체 재암호화에는 **S3 배치 작업**을 활용하세요.

**문제**: 미디어 스토리지 앱, S3 업로드→Lambda 처리, 상태는 DynamoDB. 수천 명 동시 업로드 시 일부 사진이 제대로 처리되지 않음. 원인: **Lambda 동시성 제한 + DynamoDB 성능**. 성능/안정성 향상 조치는? (2개 선택)

**보기**
- A. RCU 평가/조정(읽기 용량이 아닌 쓰기 관련 문제로 보이므로 우선순위가 낮음).

> 💡 **시험 꿀팁**: **동시 트래픽 폭증으로 Lambda 동시성 제한과 다운스트림 DB 쓰기 병목**이 겹치는 문제에는 **SQS 버퍼(S3-Lambda 사이)로 부하 완충 + DynamoDB WCU 조정**의 조합이 표준 정답입니다.

## QUESTION 260

**문제**: 인증 없는 정적 웹사이트(S3+CloudFront+WAF), 등록 양식 제출 시 API Gateway→Lambda 호출, 외부 API로 전달. 테스트 중 **CORS 오류** 발생. CloudFront 배포 오리진에는 `Access-Control-Allow-Origin: www.example.com` 헤더가 있음을 확인. 해결 방법은?

**보기**
- A. S3 버킷의 CORS 구성 변경(오류의 원인은 S3가 아니라 API Gateway 호출 시점에서 발생하는 CORS이므로 S3 CORS 설정과는 무관).
- B. WAF에서 CORS 설정 활성화(WAF에는 CORS 헤더를 직접 설정하는 기능이 없음 — 개념 오류).
- C. **API Gateway API 엔드포인트에서 CORS 설정 활성화. 모든 응답에 `Access-Control-Allow-Origin: www.example.com` 헤더가 포함되도록 API 엔드포인트 구성 확인.**
- D. Lambda 함수에서 CORS 설정 활성화(브라우저의 CORS 정책 검사는 API Gateway가 반환하는 응답 헤더를 기준으로 하며, Lambda 응답에 헤더를 넣어도 API Gateway의 통합 응답 매핑 설정이 없으면 최종적으로 클라이언트에 전달되지 않을 수 있음 — API Gateway 레벨에서의 CORS 구성이 표준 해법).

**정답: C**

**해설**
CORS 오류는 브라우저가 실제로 호출하는 대상, 즉 **API Gateway 엔드포인트**의 응답에 올바른 `Access-Control-Allow-Origin` 헤더가 없기 때문에 발생합니다. **API Gateway에서 CORS를 활성화**(OPTIONS 메서드에 대한 모의 통합 및 실제 메서드 응답에 헤더 매핑 포함)하여 모든 응답에 이 헤더가 포함되도록 구성해야 합니다.

**왜 다른 보기는 오답인가**
- A: S3는 정적 웹사이트 콘텐츠를 제공할 뿐이며, 문제가 되는 요청(등록 양식 제출)은 API Gateway를 호출하는 것이므로 S3 CORS 설정과는 무관합니다.
- B: AWS WAF에는 CORS 헤더를 설정/관리하는 기능이 존재하지 않습니다.
- D: Lambda 함수 코드에서 헤더를 반환하더라도, API Gateway의 통합 응답에서 이를 실제 헤더로 매핑하도록 구성되어 있지 않으면 브라우저에 전달되지 않을 수 있습니다 — API Gateway 자체의 CORS 구성이 근본적인 해법입니다.

> 💡 **시험 꿀팁**: 브라우저에서 발생하는 **CORS 오류**는 항상 **실제로 호출되는 엔드포인트(이 경우 API Gateway)**가 올바른 `Access-Control-Allow-Origin` 헤더를 응답에 포함하는지를 먼저 확인하세요. S3나 WAF, Lambda 코드 수정이 아니라 **API Gateway의 CORS 설정**이 표준 해법입니다.
