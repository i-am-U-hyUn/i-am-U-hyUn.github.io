## QUESTION 1

**문제**: 회사가 하이브리드 DNS 솔루션을 설계해야 합니다. VPC 내 리소스에 대해 `cloud.example.com` 도메인의 Amazon Route 53 프라이빗 호스팅 영역을 사용합니다. 요구 사항은 다음과 같습니다.
- 온프레미스 시스템이 `cloud.example.com`을 확인(resolve)하고 연결할 수 있어야 함
- 모든 VPC가 `cloud.example.com`을 확인할 수 있어야 함
- 온프레미스 네트워크와 AWS Transit Gateway 사이에는 이미 AWS Direct Connect 연결이 있음

최고의 성능으로 이 요구 사항을 충족하는 아키텍처는?

**보기**
- A. 프라이빗 호스팅 영역을 모든 VPC에 연결한다. 공유 서비스 VPC에서 Route 53 **인바운드** 리졸버를 생성한다. 모든 VPC를 전송 게이트웨이에 연결하고, 온프레미스 DNS 서버에서 인바운드 리졸버를 가리키는 `cloud.example.com`에 대한 전달 규칙을 생성한다.
- B. 프라이빗 호스팅 영역을 모든 VPC에 연결한다. 공유 서비스 VPC에 Amazon EC2 조건부 전달자를 배포한다. 온프레미스 DNS 서버에서 이 전달자를 가리키는 전달 규칙을 생성한다.
- C. 프라이빗 호스팅 영역을 공유 서비스 VPC에만 연결한다. 공유 서비스 VPC에서 Route 53 **아웃바운드** 리졸버를 생성한다. 온프레미스 DNS 서버에서 아웃바운드 리졸버를 가리키는 전달 규칙을 생성한다.
- D. 프라이빗 호스팅 영역을 공유 서비스 VPC에만 연결한다. 공유 서비스 VPC에서 Route 53 인바운드 리졸버를 생성한다. 공유 서비스 VPC만 전송 게이트웨이에 연결하고 전달 규칙을 생성한다.

**정답: A**

**해설**
온프레미스가 VPC 프라이빗 호스팅 영역의 레코드를 확인하려면, 온프레미스 → AWS 방향으로 들어오는 쿼리를 받아줄 **Route 53 Resolver 인바운드 엔드포인트**가 필요합니다. 온프레미스 DNS 서버는 `cloud.example.com`에 대한 조건부 전달 규칙을 이 인바운드 엔드포인트로 설정합니다. 동시에 "모든 VPC가 확인 가능해야 한다"는 요구 사항을 최고 성능으로 만족시키려면, 매 쿼리마다 공유 서비스 VPC를 거치는 홉을 추가하는 대신 프라이빗 호스팅 영역 자체를 모든 VPC에 직접 연결(association)해야 합니다.

**왜 다른 보기는 오답인가**
- B: EC2 조건부 전달자는 직접 관리해야 하는 자체 구축 방식으로, 관리형 서비스인 Route 53 Resolver보다 운영 부담이 크고 가용성도 떨어집니다.
- C: 아웃바운드 리졸버는 VPC 내부 리소스가 온프레미스 DNS를 확인할 때 사용하는 구성요소입니다. 이 문제는 반대 방향(온프레미스 → VPC)이 필요하므로 방향이 틀렸습니다.
- D: 호스팅 영역과 전송 게이트웨이 연결을 공유 서비스 VPC로만 한정하면, 다른 VPC들은 매번 공유 서비스 VPC를 경유해야 해서 홉이 늘어나 "최고 성능" 조건을 만족하지 못합니다.

> 💡 **시험 꿀팁**: Route 53 Resolver는 **인바운드 = 온프레미스에서 AWS로 들어오는 쿼리 수신**, **아웃바운드 = AWS에서 온프레미스로 나가는 쿼리 전달**로 방향을 외우면 헷갈리지 않습니다.

## QUESTION 2

**문제**: REST API를 Amazon API Gateway + AWS Lambda로 운영 중이며, Route 53에 `weather.example.com` 레코드가 있고 데이터는 Amazon DynamoDB에 저장합니다. API가 다른 AWS 리전으로 장애 조치(failover)할 수 있어야 합니다. 어떤 솔루션이 적합할까요?

**보기**
- A. 새 리전에 Lambda 함수를 배포하고, 두 리전을 대상으로 하는 엣지 최적화 API 엔드포인트를 사용하도록 API Gateway를 업데이트한다. DynamoDB를 글로벌 테이블로 전환한다.
- B. 다른 리전에 API Gateway와 Lambda를 배포한다. Route 53 레코드를 **다중값 응답(Multivalue Answer)**으로 변경하고 두 API Gateway를 모두 등록, 상태 확인을 활성화한다. DynamoDB를 글로벌 테이블로 전환한다.
- C. 다른 리전에 API Gateway와 Lambda를 배포한다. Route 53 레코드를 **장애 조치(Failover)** 레코드로 변경하고 상태 확인을 활성화한다. DynamoDB를 글로벌 테이블로 전환한다.
- D. 새 리전에 API Gateway를 배포하고 Lambda 함수를 "전역 함수"로 변경한다. Route 53 레코드를 다중값 응답으로 변경한다. DynamoDB를 글로벌 테이블로 전환한다.

**정답: C**

**해설**
"다른 리전으로 장애 조치"라는 요구 사항은 정상적으로는 기본(주) 리전만 트래픽을 받다가, 장애 시에만 보조 리전으로 전환하는 **액티브-패시브** 패턴입니다. Route 53의 **Failover 라우팅 정책**은 정확히 이 시나리오(주 레코드 + 보조 레코드 + 상태 확인)를 위해 설계되었습니다. DynamoDB 글로벌 테이블로 두 리전의 데이터를 동기화하는 것도 필수입니다.

**왜 다른 보기는 오답인가**
- A: 단일 엣지 최적화 API 엔드포인트가 두 리전을 동시에 대상으로 하는 구성은 실질적인 장애 조치 메커니즘이 아니며, 트래픽 전환 로직이 명확하지 않습니다.
- B: 다중값 응답은 상태가 정상인 리소스 중 임의로 응답을 섞어주는 방식으로, 정상 시에도 두 리전에 트래픽이 분산될 수 있어 "장애 시에만 전환"이라는 액티브-패시브 요구 사항과는 맞지 않습니다.
- D: "전역 Lambda 함수"라는 개념 자체가 존재하지 않으며, 다중값 응답 조합도 B와 같은 이유로 부적합합니다.

> 💡 **시험 꿀팁**: **Failover 라우팅 정책** = 액티브-패시브(주/보조), **Multivalue Answer** = 여러 정상 리소스 중 무작위 응답(부하 분산에 가까움). "장애 시에만 전환"이라는 표현이 나오면 무조건 Failover 정책을 떠올리세요.

## QUESTION 3

**문제**: AWS Organizations에서 `Production`이라는 단일 OU로 여러 계정을 관리 중이며, 조직 루트에 특정 서비스를 제한하는 **거부 목록(Deny list) SCP**가 걸려 있습니다. 최근 인수한 새 사업부의 계정을 조직에 초대했는데, 이 계정의 관리자가 회사 정책을 맞추기 위해 AWS Config 규칙을 업데이트하려 해도 SCP에 막혀 실패합니다. 관리자가 추가 장기 유지보수 없이 정책을 변경하고 계속 시행할 수 있는 방법은?

**보기**
- A. 루트 SCP를 제거하고, AWS Config 규칙을 AWS Service Catalog 제품으로 만들어 조직 전체에 배포한다.
- B. `Onboarding`이라는 임시 OU를 만들고 AWS Config 작업을 허용하는 SCP를 적용한다. 조정이 끝나면 새 계정을 Production OU로 이동한다. (조직 루트 SCP는 그대로 둠)
- C. 루트 SCP를 거부 목록에서 허용 목록 방식으로 바꾸고, 새 계정에 대해서만 AWS Config를 허용하는 SCP를 루트에 일시적으로 적용한다.
- D. `Onboarding`이라는 임시 OU를 만들고 AWS Config 작업을 허용하는 SCP를 적용한다. **기존 루트 SCP를 Production OU로 이동**시킨다. 조정이 끝나면 새 계정을 Production OU로 이동한다.

**정답: D**

**해설**
이 문제의 핵심은 **SCP의 평가 방식**입니다. SCP는 계정에 적용되는 모든 SCP(루트 → OU → 계정)의 **교집합**으로 유효 권한이 결정되며, 상위 계층의 명시적 **Deny는 하위 계층의 어떤 Allow로도 무효화할 수 없습니다.** 따라서 거부 SCP가 조직 루트에 남아있는 한, 새로 만든 Onboarding OU에 아무리 Allow SCP를 붙여도 여전히 Config가 막힙니다. 해결책은 거부 SCP를 **루트에서 Production OU로 이동**시켜, Onboarding OU에는 애초에 이 SCP가 적용되지 않도록 만드는 것입니다. 조정이 끝난 뒤 계정을 Production OU로 옮기면 다시 원래 제약이 적용됩니다.

**왜 다른 보기는 오답인가**
- A: 루트 SCP를 완전히 제거하면 조직 전체의 제한 정책이 사라져 보안 목표(제한된 서비스 통제)를 해치므로 부적절합니다.
- B: D와 거의 동일한 절차이지만 루트 SCP를 그대로 두기 때문에, SCP 교집합 규칙상 Onboarding OU의 Allow SCP가 루트의 Deny를 이길 수 없어 문제가 해결되지 않습니다. (D와의 결정적 차이!)
- C: 루트 SCP 자체의 방식(거부→허용 목록)을 바꾸는 것은 조직 전체 정책에 미치는 영향이 크고, "장기 유지보수 없이"라는 조건에 맞지 않는 큰 구조 변경입니다.

> 💡 **시험 꿀팁**: **SCP는 Deny 우선, 교집합으로 평가**됩니다. 특정 OU/계정만 예외를 주려면 하위에 Allow를 추가하는 게 아니라, 제한하려는 대상에만 Deny SCP가 적용되도록 SCP의 **부착 위치(attach point)를 옮기는 것**이 정답 패턴입니다.

## QUESTION 4

**문제**: 온프레미스 2계층 애플리케이션(상태 저장, PostgreSQL 백엔드)을 Amazon Aurora PostgreSQL, EC2 Auto Scaling, Elastic Load Balancing으로 AWS 마이그레이션합니다. 두 계층 모두 확장 가능하면서 일관된 사용자 경험을 제공하는 솔루션은?

**보기**
- A. Aurora **복제본**에 Aurora Auto Scaling 활성화, **최소 미결 요청 라우팅** + 고정 세션 활성화된 **Network Load Balancer** 사용
- B. Aurora **작성자(Writer)**에 Aurora Auto Scaling 활성화, 라운드 로빈 + 고정 세션 활성화된 Application Load Balancer 사용
- C. Aurora **복제본**에 Aurora Auto Scaling 활성화, **라운드 로빈 라우팅** + 고정 세션 활성화된 **Application Load Balancer** 사용
- D. Aurora 작성자에 Aurora Auto Scaling 활성화, 최소 미결 요청 라우팅 + 고정 세션 활성화된 Network Load Balancer 사용

**정답: C**

**해설**
Aurora Auto Scaling은 오직 **읽기 복제본(Replica) 개수**만 자동 조정할 수 있으며, 쓰기를 담당하는 **작성자(Writer) 인스턴스는 확장 대상이 아닙니다.** 따라서 "작성자에 Auto Scaling"이라고 말하는 B, D는 그 자체로 틀렸습니다. 또한 애플리케이션이 "상태 저장(stateful)"이므로 세션 고정(sticky session)이 필요한데, 이는 **애플리케이션 계층(L7) 쿠키 기반 고정 세션을 지원하는 ALB**에서 가능하며, NLB는 L4 기반이라 이런 방식의 세션 고정을 지원하지 않습니다.

**왜 다른 보기는 오답인가**
- A: 방향은 복제본 Auto Scaling으로 맞지만, NLB + "최소 미결 요청" 알고리즘은 ALB 전용 라우팅 알고리즘이라 NLB에는 존재하지 않는 조합입니다.
- B: 작성자에 Auto Scaling을 적용한다는 전제 자체가 틀렸습니다(Aurora 아키텍처상 불가능).
- D: B와 같은 이유로 작성자 Auto Scaling이 틀렸고, NLB의 라우팅 알고리즘 설명도 부정확합니다.

> 💡 **시험 꿀팁**: "Aurora Auto Scaling" = 복제본(Reader)만 대상. 상태 저장 애플리케이션 + 세션 고정 요구사항이 보이면 **ALB**(쿠키 기반)를 먼저 떠올리고, NLB(L4)와 헷갈리지 마세요.

## QUESTION 5

**문제**: 온프레미스에서 메타데이터 수집 서비스를 운영 중이며, TV·인터넷 라디오 같은 구형 기기는 특정 HTTP 헤더를 지원하지 않아 응답에 해당 헤더가 있으면 오류가 납니다. 현재는 온프레미스 로드밸런서가 User-Agent 헤더를 보고 구형 기기 응답에서 문제 헤더를 제거합니다. 서비스를 이미 Lambda 함수 세트로 마이그레이션했고, 구형 기기 지원을 유지하면서 서버리스로 전환하려 합니다.

**보기**
- A. 메타데이터 서비스용 CloudFront 배포 생성 → ALB 생성 → CloudFront가 ALB로 요청 전달 → ALB가 요청 유형별로 올바른 Lambda 호출 → **CloudFront Function**을 만들어 User-Agent 값 기반으로 문제 헤더 제거
- B. Amazon API Gateway REST API 생성 → 요청 유형별 Lambda 통합 → User-Agent 기반으로 **기본 게이트웨이 응답(Gateway Response)**을 수정해 헤더 제거
- C. Amazon API Gateway **HTTP API** 생성 → 요청 유형별 Lambda 통합 → User-Agent 기반 **응답 매핑 템플릿**을 만들어 헤더 제거
- D. CloudFront 배포 + ALB 구성은 A와 동일 → **Lambda@Edge** 함수를 만들어 최종 사용자 응답에서 문제 헤더 제거

**정답: A**

**해설**
단순히 응답 헤더를 제거하는 가벼운 로직에는 **CloudFront Functions**가 AWS의 권장 선택지입니다. CloudFront Functions는 엣지에서 실행되는 초경량 함수로 지연 시간이 매우 짧고(서브 밀리초 단위) Lambda@Edge보다 저렴하며, 뷰어 요청/응답 단계에서의 헤더 조작·URL 재작성 같은 단순 작업에 최적화되어 있습니다.

**왜 다른 보기는 오답인가**
- B: "기본 게이트웨이 응답"은 인증 실패 등 API Gateway 자체의 오류 응답을 커스터마이징하는 기능으로, 정상적인 Lambda 통합 응답의 헤더를 User-Agent별로 동적으로 제거하는 용도가 아닙니다.
- C: **API Gateway HTTP API는 REST API와 달리 응답 매핑 템플릿(VTL)을 지원하지 않습니다.** 이 보기 자체가 존재하지 않는 기능을 전제로 하므로 오답입니다.
- D: Lambda@Edge도 기능적으로는 가능하지만, 이런 단순 헤더 제거 작업에는 CloudFront Functions보다 무겁고 비용도 더 듭니다. AWS는 "복잡한 로직·외부 네트워크 호출·오리진 요청 처리가 필요할 때만 Lambda@Edge를, 단순 뷰어 요청/응답 처리는 CloudFront Functions를 사용하라"고 권장합니다.

> 💡 **시험 꿀팁**: **CloudFront Functions vs Lambda@Edge** 구분은 자주 출제됩니다. 단순·경량(헤더/URL 조작, 뷰어 단계) → CloudFront Functions. 복잡한 로직·오리진 처리·외부 호출 → Lambda@Edge. 그리고 **HTTP API는 매핑 템플릿을 지원하지 않는다**는 것도 자주 나오는 함정입니다.

## QUESTION 10

## QUESTION 14

**문제**: ALB + Auto Scaling 그룹의 EC2 인스턴스에서 로그 파일이 15분마다 S3로 복사됩니다. 그런데 일부 인스턴스가 종료될 때 다음 복사 주기 전에 종료되어 로그가 유실됩니다. 종료 시점에 로그가 반드시 S3로 복사되도록 하려면?

**보기**
- A. 로그 복사 스크립트를 SSM 문서 없이 저장해두고, ASG 수명 주기 후크 + EventBridge 규칙으로 `TERMINATING` 전환 감지 → Lambda가 **ABANDON**을 보내 종료를 막고 → 직접 스크립트 실행 후 AWS SDK로 수동 종료
- B. 로그 복사 스크립트로 **SSM 문서(Run Command)**를 만들고, ASG 수명 주기 후크 + EventBridge 규칙으로 `TERMINATING` 전환 감지 → Lambda가 SSM `SendCommand`로 문서 실행 → 완료 후 **CONTINUE**를 보내 정상 종료 진행
- C. 로그 전송 주기를 5분으로 단축 + EventBridge로 EC2 종료 자체를 감지해 스크립트 실행
- D. SSM 문서를 만들고, 수명 주기 후크가 SNS에 메시지 게시 → SNS 알림에서 SendCommand 호출 → 완료 후 **ABANDON** 전송

**정답: B**

**해설**
AWS가 권장하는 표준 패턴은 **Auto Scaling 수명 주기 후크(`EC2_INSTANCE_TERMINATING`)**로 종료를 일시 정지시키고, EventBridge 규칙이 이를 감지해 Lambda를 호출하며, Lambda가 **SSM SendCommand**로 로그 복사 문서를 실행한 뒤, 작업이 끝나면 **`CompleteLifecycleAction`을 CONTINUE로 호출**해 정상적인 종료 절차를 이어가게 하는 것입니다.

**왜 다른 보기는 오답인가**
- A: ABANDON 후 수동으로 AWS SDK로 종료시키는 방식은 표준 수명 주기 후크 완료 흐름보다 복잡하고 관리 포인트가 늘어납니다.
- C: EventBridge가 "EC2 인스턴스 종료(이미 종료된 후)" 이벤트를 감지하면, 그 시점엔 이미 인스턴스가 사라진 뒤라 로그를 복사할 수 없습니다. 수명 주기 후크의 `TERMINATING`(종료 직전 일시 정지) 단계를 활용해야 합니다.
- D: 작업을 정상적으로 마쳤다면 `CONTINUE`를 보내 표준 종료 절차를 이어가는 것이 맞으며, `ABANDON`은 일반적으로 실패·건너뛰기 상황에 쓰는 신호로 이 흐름에는 적합하지 않습니다.

> 💡 **시험 꿀팁**: "인스턴스 종료 직전에 정리 작업을 실행"하는 패턴은 **Lifecycle Hook(TERMINATING) → EventBridge → Lambda → SSM SendCommand → CompleteLifecycleAction(CONTINUE)** 흐름으로 외워두세요. ABANDON은 정상 완료가 아니라 실패/스킵 신호입니다.

- B. 인스턴스 스토어 볼륨을 사용하도록 사이트를 변경하고, 시작 시 콘텐츠를 복사, 종료 시 S3로 백업한다.
- C. **CloudFront 배포를 만들어 오리진을 S3로 지정하고, 동영상을 EFS에서 Amazon S3로 마이그레이션**한다.
- D. 전체 사이트 콘텐츠에 대해 CloudFront 배포를 만들고 오리진을 ALB로 지정한다.

**정답: C**

**해설**
문제의 근본 원인은 대용량 동영상 파일을 EC2/EFS 조합으로 계속 서빙하는 구조 자체입니다. 동영상처럼 크고 자주 반복 요청되는 정적 콘텐츠는 **Amazon S3 + CloudFront** 조합으로 옮기는 것이 가장 비용 효율적이고 확장성이 뛰어난 표준 해법입니다.

**왜 다른 보기는 오답인가**
- A: Max I/O는 EFS의 처리량 모드를 높여주지만, 여전히 모든 요청이 EC2/EFS를 거쳐야 하므로 근본적인 병목을 해소하지 못합니다.
- B: 인스턴스 스토어는 휘발성이라 인스턴스 중지·종료 시 데이터가 손실될 위험이 크고, 수동 동기화 로직도 복잡해 신뢰성이 떨어집니다.
- D: CloudFront가 ALB(EC2)를 오리진으로 하면 캐시 미스마다 여전히 EC2가 동영상을 서빙해야 해, 동영상을 S3로 완전히 옮기는 C만큼 근본적인 해결책이 아닙니다.

> 💡 **시험 꿀팁**: EC2/EFS로 서빙하던 **대용량 정적 콘텐츠(동영상 등)가 트래픽 병목**이라면, "EFS 튜닝"이 아니라 **S3 + CloudFront로 콘텐츠 자체를 이전**하는 것이 정답 패턴입니다.

## QUESTION 17

**문제**: 글로벌 기업이 단일 리전에 1Gbps Direct Connect 연결 1개(프라이빗 VIF 1개, 단일 VPC 연결)를 보유합니다. 같은 리전에 중복(redundant) DX 연결을 추가하면서, 향후 다른 리전으로 확장할 때도 같은 연결 쌍으로 연결을 제공하려 합니다. 어떤 솔루션이 적합할까요?

**보기**
- A. **Direct Connect Gateway**를 프로비저닝하고, 기존 프라이빗 VIF를 삭제한 뒤 두 번째 DX 연결을 만들어 각각 새 프라이빗 VIF를 생성, 두 VIF를 모두 Direct Connect Gateway에 연결한다.
- B. Direct Connect Gateway를 단일 VPC에 직접 연결하고, 기존 VIF는 유지, 두 번째 연결의 새 VIF만 그 VPC에 연결한다.
- C. 두 번째 연결에 **퍼블릭 VIF**를 만들어 단일 VPC에 연결한다.
- D. **Transit Gateway**를 프로비저닝하고 두 프라이빗 VIF를 전송 게이트웨이에 연결한다.

**정답: A**

**해설**
**Direct Connect Gateway(DXGW)**는 하나(또는 이중화된) DX 연결 쌍이 **여러 리전의 VPC**에 연결될 수 있게 해주는 AWS의 표준 구성 요소입니다. 이 회사처럼 "향후 여러 리전으로 확장"이 요구 사항에 명시되면 DXGW가 정답 패턴입니다.

**왜 다른 보기는 오답인가**
- B: DXGW를 "VPC에 직접" 연결한다는 설명이 부정확하고(실제로는 가상 프라이빗 게이트웨이/Transit Gateway를 통해 연결), 새 VIF만 DXGW를 거치고 기존 VIF는 그대로 두어 "동일한 연결 쌍으로 여러 리전 확장"이라는 목표에 부합하지 않습니다.
- C: 퍼블릭 VIF는 S3, DynamoDB 같은 AWS 퍼블릭 서비스에 접근할 때 쓰는 것이며, 프라이빗 VPC 리소스 연결에는 프라이빗 VIF가 필요합니다.
- D: Transit Gateway는 리전 범위 서비스라, "여러 리전으로의 확장"이라는 목표에는 리전 간 연결을 기본 지원하는 DXGW가 더 적합합니다.

> 💡 **시험 꿀팁**: "하나의 DX 연결(쌍)로 여러 리전의 VPC에 연결하고 싶다"는 요구 사항이 나오면 **Direct Connect Gateway**를 떠올리세요. 퍼블릭 VIF와 프라이빗 VIF의 용도 차이(퍼블릭 서비스 vs VPC 리소스)도 함께 기억해두면 좋습니다.

## QUESTION 18

**문제**: 사용자가 동영상을 업로드하는 웹 앱이 있고, 동영상은 EBS에 저장되며 서드파티 인식 소프트웨어(EC2 + SQS 워커)로 분류됩니다. 가능한 한 AWS 관리형 서비스를 사용해 운영 부담을 줄이고 서드파티 소프트웨어 종속성을 없애려 합니다.

**보기**
- A. 웹 앱은 ECS 컨테이너, SQS 처리는 스팟 인스턴스 ASG 사용, 인식 소프트웨어는 **Amazon Rekognition**으로 교체
- B. 업로드 동영상을 **EFS**에 저장, 웹 앱은 계속 EC2에서 실행, SQS를 처리하는 Lambda가 Rekognition 호출
- C. 웹 앱을 **Amazon S3**에서 호스팅, 동영상을 **S3**에 저장, S3 이벤트 알림 → SQS → **Lambda**가 Rekognition API 호출로 분류
- D. Elastic Beanstalk의 Auto Scaling 웹 티어 + 워커 환경으로 SQS 처리, 인식 소프트웨어는 Rekognition으로 교체

**정답: C**

**해설**
"가능한 한 관리형 서비스를 활용해 운영 부담을 최소화"라는 목표에 가장 부합하는 것은, 웹 호스팅부터 저장, 이벤트 처리, 분류까지 **EC2/컨테이너 관리가 전혀 필요 없는** 완전 서버리스 조합입니다: **S3(정적 호스팅+저장) + S3 이벤트 알림 → SQS → Lambda → Amazon Rekognition**.

**왜 다른 보기는 오답인가**
- A: ECS 컨테이너와 스팟 ASG를 여전히 운영·관리해야 해서 EC2/클러스터 관리 부담이 남아있습니다.
- B: 동영상 저장을 EFS로 하고 웹 앱도 여전히 EC2에서 실행되므로, C의 완전 서버리스 구성보다 관리 요소가 많습니다.
- D: Elastic Beanstalk도 내부적으로 EC2 인스턴스를 관리해야 하므로 "서버 관리 최소화" 목표에 덜 부합합니다.

> 💡 **시험 꿀팁**: "관리형 서비스로 운영 부담 최소화"라는 표현이 나오는 미디어 처리 파이프라인 문제는 **S3 → S3 이벤트 알림 → SQS → Lambda → Rekognition**(완전 서버리스) 조합을 우선적으로 검토하세요. EC2/ECS/EKS/Elastic Beanstalk가 남아있는 보기는 대부분 차선책입니다.

## QUESTION 19

**문제**: CloudFront + API Gateway + Lambda로 구성된 서버리스 앱이 있습니다. 현재는 AWS CLI 스크립트로 새 Lambda 버전을 배포하고, 오류 시 다른 스크립트로 이전 버전을 재배포해 되돌립니다. 배포 시간과 오류 감지·롤백 시간을 모두 줄이려면?

**보기**
- A. 상위(CloudFront+API Gateway) / 하위(Lambda) 중첩 CloudFormation 스택 구성, Lambda 변경 시 **CloudFormation 변경 세트**를 수동 생성·배포, 오류 시 변경 세트를 수동으로 되돌림
- B. **AWS SAM + 내장 AWS CodeDeploy**로 새 Lambda 버전을 점진적으로 배포(카나리/선형), 트래픽 전·후 테스트 훅으로 코드 검증, **CloudWatch 경보 발생 시 자동 롤백**
- C. 여러 AWS CLI 스크립트를 하나로 리팩터링, 배포 후 별도 테스트 스크립트 실행, 오류 감지 시 이전 버전으로 수동 롤백
- D. 새 Lambda 버전을 참조하는 새 API Gateway 엔드포인트로 CloudFormation 스택 생성·배포, CloudFront 오리진을 수동으로 전환하며 오류 모니터링, 문제 시 수동으로 되돌림

**정답: B**

**해설**
**AWS SAM에 내장된 AWS CodeDeploy 통합**은 Lambda 배포 시 트래픽을 점진적으로(카나리/선형) 새 버전으로 옮기면서, 배포 전·후 테스트 훅으로 코드를 검증하고, CloudWatch 경보가 발동하면 **자동으로 롤백**하는 기능을 기본 제공합니다. 이는 배포 시간과 오류 대응 시간을 모두 자동화로 줄이는 AWS 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- A, D: CloudFormation 변경 세트나 API Gateway 엔드포인트 전환을 수동으로 생성·모니터링·롤백하는 방식은 여전히 사람이 개입해야 해서 "시간 단축"이라는 목표를 충분히 달성하지 못합니다.
- C: 여러 스크립트를 하나로 합쳐도 근본적으로 수동 스크립트 기반 프로세스라는 점은 변하지 않아, 자동화 수준에서 B에 크게 못 미칩니다.

> 💡 **시험 꿀팁**: Lambda 배포 자동화 + 자동 롤백 요구 사항이 나오면 **AWS SAM + CodeDeploy(카나리/선형 배포, Pre/Post-traffic 훅, CloudWatch 경보 기반 자동 롤백)**를 정답으로 우선 고려하세요.

## QUESTION 20

**문제**: 대량의 보관 문서를 저장하고 직원이 사내 인트라넷(VPC에 연결된 클라이언트 VPN)을 통해 사용할 수 있어야 합니다. 데이터는 공개되면 안 되고, 요청 수는 적으며 가용성·검색 속도는 중요하지 않습니다. 최저 비용으로 요구 사항을 충족하는 솔루션은?

**보기**
- A. S3 버킷 생성, **S3 One Zone-IA**를 기본 스토리지 클래스로 구성, 웹 사이트 호스팅 구성, **S3 인터페이스 엔드포인트**를 만들어 해당 엔드포인트로만 접근 허용
- B. 웹 서버 EC2 인스턴스 + EFS(One Zone-IA) 연결, 프라이빗 네트워크에서만 접근하도록 보안 그룹 구성
- C. 웹 서버 EC2 인스턴스 + EBS(Cold HDD, sc1) 볼륨, 프라이빗 네트워크에서만 접근 허용
- D. S3 버킷 생성, **S3 Glacier Deep Archive**를 기본 스토리지 클래스로 구성, 웹 사이트 호스팅 + S3 인터페이스 엔드포인트로 접근 제한

**정답: A**

**해설**
요구 사항에 "직원이 문서를 **사용**할 수 있어야 한다"는 조건이 있으므로, 조회 시 즉시(밀리초 단위) 응답 가능한 스토리지 클래스가 필요합니다. **S3 One Zone-IA**는 단일 AZ에만 저장해 비용은 낮추면서도 S3 Standard와 동일하게 즉시 조회가 가능해 이 조건에 맞습니다. 여기에 **S3 인터페이스 VPC 엔드포인트**로 접근을 해당 VPC로만 제한하면 "공개 불가" 조건도 만족합니다.

**왜 다른 보기는 오답인가**
- B, C: EC2 인스턴스를 상시 운영해야 하므로 컴퓨팅 비용이 계속 발생해, 순수 S3 기반 정적 호스팅(A)보다 비용이 높습니다.
- D: **S3 Glacier Deep Archive는 검색(조회) 요청 시 최소 수 시간(최대 48시간)이 걸리는 비동기 복원 방식**이라, "문서를 사용할 수 있어야 한다"는 즉시 접근 요구 사항과 맞지 않습니다. 요청 수가 적다는 것과 "즉시 조회 가능해야 한다"는 것은 별개의 조건이라는 점에 유의해야 합니다.

> 💡 **시험 꿀팁**: **S3 Glacier 계열은 저장 비용은 가장 싸지만 조회에 시간이 걸립니다.** 문제에 "가끔 접근하지만 그래도 바로 사용(조회)할 수 있어야 한다"는 뉘앙스가 있다면 Glacier가 아니라 **S3 Standard-IA / One Zone-IA**가 정답입니다. Glacier는 "장기 보관용이며 즉시 조회가 필요 없다"는 조건이 명시될 때만 정답이 됩니다.
