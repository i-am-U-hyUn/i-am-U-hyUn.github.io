## QUESTION 341

**문제**: 금융 데이터 회사가 실시간 시세 데이터를 **동시에 수백 개의 VPC**(고객사별로 분리된)에 낮은 지연시간으로 배포해야 한다. 각 VPC마다 개별 연결을 구성하는 것은 운영 오버헤드가 너무 크다. 하나의 소스에서 여러 VPC로 동일한 데이터 스트림을 효율적으로 브로드캐스트하는 솔루션은?

**보기**
- A. 각 VPC마다 개별 NLB를 두고 유니캐스트로 동일 데이터를 반복 전송(VPC 수만큼 동일 데이터를 반복 전송해야 해서 대역폭과 운영 부담이 VPC 수에 비례해 증가).
- B. **Transit Gateway 멀티캐스트를 구성해, 하나의 멀티캐스트 그룹에 여러 VPC를 멤버로 등록하고 소스가 한 번만 데이터를 전송하면 Transit Gateway가 등록된 모든 VPC로 효율적으로 복제해 전달.**
- C. 각 VPC에 동일한 데이터를 저장하는 S3 버킷을 두고 폴링 방식으로 지속적으로 조회(폴링 기반 S3 조회는 실시간 저지연 브로드캐스트에 적합하지 않고 각 VPC가 반복 조회해야 해서 비효율적).
- D. 각 VPC 간 개별 VPC 피어링을 모두 연결해 메시지 브로드캐스트(수백 개 VPC 간 전체 메시(mesh) 피어링은 관리해야 할 연결 수가 기하급수적으로 증가해 비현실적).

**정답: B**

**해설**
**Transit Gateway 멀티캐스트**는 하나의 멀티캐스트 그룹에 여러 VPC(의 서브넷)를 멤버로 등록해두면, 소스가 멀티캐스트 그룹으로 데이터를 **한 번만 전송**해도 Transit Gateway가 이를 등록된 **모든 멤버 VPC로 효율적으로 복제**해 전달합니다. 개별 유니캐스트 연결이나 전체 메시 피어링 없이도 다수의 VPC에 동일한 실시간 데이터를 저지연으로 브로드캐스트할 수 있어, 대규모 VPC 대상 데이터 배포에 최적화된 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 유니캐스트 반복 전송은 VPC 수에 비례해 대역폭과 운영 부담이 커집니다.
- C: 폴링 기반 S3 조회는 실시간성이 떨어지고 반복 조회로 인한 비효율이 발생합니다.
- D: 수백 개 VPC 간 전체 피어링(메시 토폴로지)은 연결 수가 기하급수적으로 늘어나 비현실적입니다.

> 💡 **시험 꿀팁**: 하나의 소스에서 **다수의 VPC로 동일한 데이터를 저지연으로 브로드캐스트**하려면 **Transit Gateway 멀티캐스트**가 표준 정답입니다.

## QUESTION 342

**문제**: 헬스케어 회사가 환자의 민감한 개인 건강 정보(PHI)를 처리하는 애플리케이션을 개발 중이다. 이 처리 로직은 **AWS 운영자를 포함한 어느 누구도(관리자 접근, SSH 접근 등을 통해서도) 처리 중인 데이터에 접근할 수 없는 격리된 컴퓨팅 환경**에서 실행되어야 하며, 외부 네트워크/영구 스토리지 접근도 없어야 한다. 솔루션은?

**보기**
- A. 표준 EC2 인스턴스에서 실행하고 IAM 정책으로 모든 사용자의 접근을 거부(IAM 정책으로 다른 IAM 사용자의 접근은 제한할 수 있지만, 이는 인스턴스 자체에 대한 하드웨어 수준의 격리가 아니며, 인스턴스 관리 권한이 있는 사람은 여전히 다양한 경로로 접근 가능).
- B. **AWS Nitro Enclaves를 사용해 EC2 인스턴스로부터 분리된 격리된 컴퓨팅 환경(엔클레이브)에서 민감 데이터 처리 로직을 실행. 엔클레이브는 영구 스토리지, 대화형 접근, 외부 네트워크 접근이 없으며, 부모 인스턴스와는 안전한 로컬 채널로만 통신.**
- C. AWS Outposts에 전용 하드웨어를 배치해 물리적으로 격리된 환경 구성(Outposts는 온프레미스 하드웨어 확장이지만, "AWS 운영자를 포함한 누구도 접근할 수 없는" 하드웨어 수준의 암호학적 격리 증명을 제공하는 것은 아니며, 애초에 클라우드 네이티브 격리 컴퓨팅 요구에는 Nitro Enclaves가 특화되어 있음).
- D. Lambda 함수 내에서 데이터를 처리하고 VPC 연결을 제거(Lambda는 실행 환경에 대한 세밀한 격리 증명[attestation]이나 부모-엔클레이브 간 통신 모델을 제공하지 않으며, 이 정도로 엄격한 격리 보장이 필요한 시나리오에는 Nitro Enclaves가 표준).

**정답: B**

**해설**
**AWS Nitro Enclaves**는 EC2 인스턴스로부터 CPU와 메모리를 분리한 완전히 격리된 컴퓨팅 환경을 제공합니다. 엔클레이브에는 **영구 스토리지, 대화형 접근(SSH 등), 외부 네트워크 연결이 전혀 없으며**, 부모 EC2 인스턴스와는 오직 보안 로컬 채널(vsock)로만 통신합니다. 또한 **암호학적 증명(attestation)** 기능으로 엔클레이브에서 실행 중인 코드가 변조되지 않았음을 검증할 수 있어, AWS 운영자를 포함한 누구도 접근할 수 없는 극도로 민감한 데이터 처리(PHI, PII, 암호화 키 처리 등)에 이상적입니다.

**왜 다른 보기는 오답인가**
- A: IAM 정책은 다른 IAM 주체의 접근을 제한할 뿐, 인스턴스 관리 권한을 가진 사람의 접근 자체를 하드웨어 수준에서 원천 차단하지는 못합니다.
- C: Outposts는 온프레미스로 AWS 인프라를 확장하는 서비스로, 이 문제가 요구하는 격리된 컴퓨팅 환경(대화형/네트워크/스토리지 접근 완전 차단) 자체를 제공하는 기능은 아닙니다.
- D: Lambda는 이 정도의 엄격한 격리 증명이나 통신 모델을 제공하지 않습니다.

> 💡 **시험 꿀팁**: **AWS 운영자를 포함해 누구도 접근할 수 없는 격리된 환경에서 극도로 민감한 데이터를 처리**해야 한다면 **AWS Nitro Enclaves**가 표준 정답입니다.

## QUESTION 343

**문제**: 회사가 AWS Application Migration Service(MGN)로 수십 대의 서버를 마이그레이션 준비 중인데, 실제 프로덕션 전환(cutover) 전에 **소스 서버에 영향을 주지 않으면서** 복제된 타겟 인스턴스가 정상적으로 부팅되고 애플리케이션이 작동하는지 미리 검증하고 싶다. 솔루션은?

**보기**
- A. 바로 실제 cutover를 진행해 문제가 있으면 그때 롤백(실제 전환 전 사전 검증 없이 바로 전환하는 것은 프로덕션 영향 리스크가 크며, 문제가 요구하는 "소스에 영향 없는 사전 검증"과 정반대).
- B. **MGN의 테스트 실행(test launch) 기능을 사용해, 지속적인 복제는 그대로 유지한 채 격리된 네트워크 환경에서 타겟 인스턴스를 임시로 기동해 검증한 뒤, 검증이 끝나면 테스트 인스턴스를 종료(소스 서버나 실제 복제 프로세스에는 영향 없음).**
- C. 소스 서버를 일시적으로 종료하고 복제본이 잘 동작하는지 확인(소스 서버를 종료하는 것은 "소스 서버에 영향을 주지 않으면서"라는 요구에 정면으로 반함).
- D. 복제된 스냅샷을 별도의 AWS 계정으로 수동으로 내보내 별도로 테스트 환경 구축(MGN이 기본 제공하는 테스트 실행 기능을 두고 수동으로 별도 환경을 구축하는 것은 불필요하게 복잡하고 비효율적).

**정답: B**

**해설**
**AWS MGN의 테스트 실행(test launch)** 기능은 실제 cutover 없이도, 지속적인 데이터 복제를 유지한 상태에서 격리된(비프로덕션) 네트워크에 타겟 인스턴스를 임시로 기동해 애플리케이션이 정상 동작하는지 검증할 수 있게 해줍니다. 이 과정은 소스 서버나 복제 파이프라인에 전혀 영향을 주지 않으며, 테스트가 끝나면 테스트 인스턴스를 정리(clean up)하고 실제 cutover는 나중에 별도로 수행할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 사전 검증 없이 바로 전환하는 것은 이 문제가 요구하는 "사전 검증"이라는 목적 자체를 달성하지 못합니다.
- C: 소스 서버를 종료하는 것은 "소스에 영향 없이"라는 핵심 요구를 위반합니다.
- D: MGN이 기본 제공하는 테스트 실행 기능이 있음에도 수동으로 별도 환경을 구축하는 것은 불필요한 중복 작업입니다.

> 💡 **시험 꿀팁**: MGN 마이그레이션에서 **실제 전환 전 소스에 영향 없이 타겟 인스턴스를 미리 검증**하려면 **테스트 실행(test launch)** 기능이 표준 정답입니다.

## QUESTION 344

**문제**: 회사가 Aurora MySQL 데이터베이스에 대해, 다른 리전에 **읽기 전용 복제본**을 두어 그 리전의 사용자에게 낮은 지연시간의 읽기를 제공하고 싶을 뿐, 해당 리전으로의 **쓰기 승격이나 재해 복구 기능은 필요하지 않다**(별도의 백업 기반 DR 전략을 이미 갖추고 있음). 비용을 최소화하면서 이 요구를 충족하는 방법은?

**보기**
- A. **Aurora MySQL의 일반 크로스 리전 읽기 복제본(cross-Region read replica)을 생성해 다른 리전에서 읽기 트래픽을 처리.**
- B. Aurora Global Database를 구성해 보조 리전에 읽기 복제본을 둠(Global Database는 빠른 재해 복구(1분 이내 승격) 등 추가 기능을 위한 전용 복제 인프라를 사용해 일반 크로스 리전 읽기 복제본보다 비용이 높으며, 이 문제처럼 DR 기능이 필요 없는 단순 읽기 지연시간 개선 목적에는 과도함).
- C. DMS를 사용해 지속적으로 다른 리전의 별도 Aurora 클러스터에 데이터 복제(DMS 기반 지속 복제는 관리 오버헤드가 크고, Aurora의 네이티브 크로스 리전 복제 기능보다 지연시간이 크며 이 단순한 요구에는 과도하게 복잡함).
- D. 다른 리전에 완전히 독립적인 두 번째 Aurora 클러스터를 만들고 애플리케이션에서 이중 쓰기 구현(단순 읽기 지연시간 개선 목적에 비해 이중 쓰기 구현은 데이터 정합성 관리 복잡도가 지나치게 큼).

**정답: A**

**해설**
**Aurora의 일반 크로스 리전 읽기 복제본**은 다른 리전에서 낮은 지연시간의 읽기를 제공하는 목적에 정확히 맞으며, Aurora Global Database처럼 빠른 재해 복구를 위한 전용 복제 인프라(추가 비용 발생)를 사용하지 않아 **더 저렴**합니다. 이 문제처럼 별도의 DR 전략이 이미 있고 단순히 읽기 지연시간만 개선하고 싶다면, 더 많은 기능(빠른 페일오버 등)을 제공하지만 비용도 높은 Global Database보다 일반 크로스 리전 읽기 복제본이 비용 효율적인 선택입니다.

**왜 다른 보기는 오답인가**
- B: Global Database는 이 문제가 필요로 하지 않는 빠른 재해 복구 기능까지 포함되어 있어 비용 대비 과도한 선택입니다.
- C: DMS를 통한 별도 복제는 관리 부담이 크고 Aurora 네이티브 복제보다 비효율적입니다.
- D: 애플리케이션 레벨 이중 쓰기는 이 단순한 요구에 비해 지나치게 복잡하고 리스크가 큽니다.

> 💡 **시험 꿀팁**: 리전 간 **재해 복구 기능 없이 단순히 읽기 지연시간만 개선**하고 싶다면 **Aurora 일반 크로스 리전 읽기 복제본**이 비용 효율적인 표준 정답이며, 빠른 페일오버가 필요할 때만 Aurora Global Database를 고려하세요.

## QUESTION 345

**문제**: 회사가 특정 인스턴스 패밀리에 대해 3년 전체 선결제 표준 예약 인스턴스(Standard RI)를 구매했으나, 사업 방향 전환으로 이제 해당 인스턴스 패밀리가 더 이상 필요 없어졌다. 잔여 약정 기간에 대한 금전적 손실을 최소화하고 싶다. 조치는?

**보기**
- A. 예약 인스턴스를 그냥 사용하지 않고 방치(구매 비용은 이미 선결제되어 있으므로 사용하지 않아도 환불되지 않으며, 그대로 손실로 남음 — 손실 최소화에 도움이 되지 않음).
- B. **AWS Reserved Instance Marketplace에서 남은 약정 기간의 예약 인스턴스를 제3자에게 판매.**
- C. AWS 지원팀에 환불을 요청(Standard RI는 일반적으로 AWS의 표준 정책상 임의 환불이 지원되지 않으며, RI Marketplace를 통한 판매가 표준적인 처리 방법).
- D. 컨버터블 예약 인스턴스로 변환 요청(이미 구매한 Standard RI를 사후에 Convertible RI로 전환하는 기능은 없으며, 애초에 컨버터블로 전환해도 여전히 EC2 약정에 묶여 있어 "필요 없어진 패밀리"라는 근본 문제는 해결되지 않음).

**정답: B**

**해설**
**AWS Reserved Instance Marketplace**는 더 이상 필요하지 않은 표준 예약 인스턴스(Standard RI)의 **남은 약정 기간을 제3자에게 판매**할 수 있는 공식 채널입니다. 이를 통해 선결제한 비용의 일부를 회수함으로써, 사용하지 않고 방치하는 것보다 금전적 손실을 최소화할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 사용하지 않고 방치하면 이미 지불한 비용을 전혀 회수하지 못해 손실이 그대로 남습니다.
- C: Standard RI는 일반적으로 임의 환불이 지원되지 않으며, Marketplace 판매가 표준적인 손실 최소화 방법입니다.
- D: 이미 구매를 완료한 Standard RI를 사후에 Convertible RI로 전환하는 기능은 없으며, 변환 자체가 "더 이상 필요 없는 패밀리"라는 근본 문제를 해결하지도 않습니다.

> 💡 **시험 꿀팁**: 더 이상 필요 없어진 **Standard RI의 잔여 약정에 대한 손실을 최소화**하려면 **AWS Reserved Instance Marketplace**에서 판매하는 것이 표준 정답입니다.

## QUESTION 347

**문제**: 보안 팀이 특정 EC2 인스턴스들을 오가는 네트워크 트래픽을 **원본 트래픽에 영향을 주지 않으면서** 서드파티 침입 탐지 시스템(IDS) 어플라이언스로 복사해 심층 패킷 분석을 수행하고 싶다. 애플리케이션 코드 변경 없이 트래픽의 사본만 얻으려면?

> 💡 **시험 꿀팁**: 원본 트래픽에 영향 없이 **네트워크 트래픽 사본을 서드파티 IDS/보안 어플라이언스로 전달**해 심층 패킷 검사를 하려면 **VPC 트래픽 미러링**이 표준 정답입니다.

- D: 자체 스크립트 구현은 "직접 구현하고 싶지 않다"는 요구에 명백히 반합니다.

> 💡 **시험 꿀팁**: EFS 파일 시스템의 **짧은 RPO 크로스 리전 재해 복구**가 필요하면 자체 구현 없이 **EFS 복제(EFS Replication)** 기능이 표준 정답입니다.

**문제**: 대규모 유전체 시뮬레이션 작업이 메모리에 수 시간에 걸쳐 계산 상태를 쌓아가며 실행되는데, 작업이 유휴 상태일 때(야간 등)는 비용을 아끼기 위해 인스턴스를 내리고 싶지만, 다시 시작할 때 **메모리 상의 계산 상태를 처음부터 다시 만드는 것은 매우 비용이 크다**(수 시간 소요). 인스턴스를 중지했다가 재개해도 메모리 상태를 그대로 유지하려면?

**보기**
- A. 인스턴스를 중지(stop)했다가 시작(start)(일반적인 EC2 중지/시작은 메모리(RAM) 내용을 보존하지 않으며, 재시작 시 메모리는 초기화되어 애플리케이션이 처음부터 계산 상태를 다시 만들어야 함).

- C. 인스턴스를 절대 중지하지 않고 계속 실행(비용 절감이라는 목표를 포기하는 것으로, 유휴 시간에도 비용이 계속 발생).
- D. 애플리케이션을 재작성해 매번 체크포인트를 디스크에 저장하고 재시작 시 이를 읽어 복원(가능한 대안이지만, 애플리케이션을 재설계/재작성해야 하는 큰 개발 부담이 있으며, 하이버네이션을 사용하면 이런 재설계 없이 동일한 효과를 얻을 수 있음).

**정답: B**

**해설**
**EC2 하이버네이션**은 지원되는 인스턴스 유형에서 인스턴스를 중지할 때 **RAM의 내용을 암호화된 형태로 EBS 루트 볼륨에 저장**하고, 이후 인스턴스를 시작하면 **저장된 메모리 상태를 복원**해 운영체제 부팅과 애플리케이션 재초기화 과정 없이 중단되었던 지점부터 즉시 이어서 실행할 수 있게 해줍니다. 이를 통해 유휴 시간에는 인스턴스 요금 없이(EBS 스토리지 비용만 발생) 비용을 절감하면서도, 메모리에 쌓인 오래 걸리는 계산 상태를 그대로 보존할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 일반적인 중지/시작은 메모리 내용을 보존하지 않아 애플리케이션이 상태를 처음부터 재구성해야 합니다.
- C: 계속 실행하는 것은 비용 절감이라는 목표 자체를 포기하는 것입니다.
- D: 자체 체크포인트 구현도 유효하지만 애플리케이션 재설계가 필요해, 하이버네이션이라는 인프라 수준의 기능보다 개발 부담이 큽니다.

> 💡 **시험 꿀팁**: 인스턴스를 중지해도 **메모리(RAM) 상태를 그대로 보존**했다가 재개하려면 **EC2 하이버네이션(Hibernate)**이 표준 정답입니다.

**문제**: 전자상거래 사이트가 정상적인 사용자처럼 보이지만 실제로는 상품 가격을 지속적으로 긁어가는 **스크래퍼 봇**과, 재고를 매점매석하기 위해 장바구니에 자동으로 담는 봇으로 인해 골머리를 앓고 있다. 단순한 IP 기반 차단이나 속도 기반 규칙만으로는 정교한 봇을 걸러내기 어렵다. AWS WAF에서 이런 정교한 봇 트래픽에 특화된 대응 방법은?

**보기**
- A. WAF의 IP 평판 목록(Amazon IP reputation list) 규칙만 사용(알려진 악성 IP 목록 기반 차단은 유효하지만, 새로운 IP를 사용하거나 정상 트래픽처럼 위장하는 정교한 스크래퍼/매점매석 봇까지 포괄적으로 탐지하지는 못함).
- B. **AWS WAF Bot Control을 활성화해, 알려진 좋은/나쁜 봇을 분류하고 브라우저 지문·행동 패턴 분석 등을 통해 스크래이퍼, 매점매석 봇 같은 정교한 자동화 트래픽까지 탐지 및 차단(관리형 규칙 그룹 및 CAPTCHA/Challenge 액션 활용).**
- C. 속도 기반 규칙(rate-based rule)만 세밀하게 조정(속도 기반 규칙은 짧은 시간 내 대량 요청을 탐지하는 데는 유효하지만, 정상적인 속도로 활동하며 정교하게 사람처럼 행동하는 봇까지는 걸러내지 못함).
- D. 모든 사용자에게 로그인을 의무화해 익명 접근을 차단(전자상거래 사이트에서 모든 탐색/구매에 로그인을 강제하는 것은 사용자 경험을 크게 해치며, 봇도 계정을 만들어 로그인할 수 있어 근본적인 해결책이 아님).

**정답: B**

**해설**
**AWS WAF Bot Control**은 알려진 좋은 봇(검색엔진 크롤러 등)과 나쁜 봇을 구분하고, 스크래이퍼나 매점매석(scalping) 봇처럼 사람처럼 행동하도록 정교하게 위장된 자동화 트래픽까지 브라우저 지문, 행동 패턴 등을 분석해 탐지하는 관리형 규칙 그룹입니다. 탐지된 봇 트래픽에 대해 차단, CAPTCHA, Challenge(JavaScript 기반 검증) 같은 다양한 대응 액션을 적용할 수 있어, 단순 IP/속도 기반 규칙으로는 걸러내기 어려운 정교한 봇 위협에 특화된 표준 솔루션입니다.

**왜 다른 보기는 오답인가**
- A: IP 평판 목록은 알려진 악성 IP 차단에는 유용하지만 정교하게 위장된 신규 봇까지 포괄하지 못합니다.
- C: 속도 기반 규칙은 대량 급증 트래픽 탐지에 특화되어 있으며, 낮은 속도로 사람처럼 행동하는 봇은 걸러내지 못합니다.
- D: 전면 로그인 강제는 사용자 경험을 해치고, 봇도 계정 생성이 가능해 근본적 해결책이 아닙니다.

> 💡 **시험 꿀팁**: **스크래이퍼, 매점매석 봇 같은 정교한 자동화 트래픽**을 탐지/차단하려면 **AWS WAF Bot Control**이 표준 정답입니다.

## QUESTION 351

**문제**: 여러 팀이 Kafka(MSK)와 Kinesis를 통해 스트리밍 데이터를 주고받는데, 프로듀서가 이벤트 스키마를 변경할 때마다 하위 호환성이 깨져 컨슈머 애플리케이션에서 파싱 오류가 자주 발생한다. 스키마 버전을 중앙에서 관리하고 **호환성 규칙(하위/상위 호환성)을 강제**하고 싶다. 솔루션은?

**보기**
- A. 각 팀이 스키마를 문서로 작성해 위키에 공유하고 수동으로 검토(수동 프로세스는 강제력이 없어 실수로 호환성이 깨지는 배포를 막지 못함).
- B. **AWS Glue Schema Registry를 사용해 Kafka/Kinesis 스트림의 이벤트 스키마를 중앙에서 버전 관리하고, 호환성 모드(하위 호환, 상위 호환, 완전 호환 등)를 설정해 호환성을 위반하는 스키마 등록 자체를 차단.**

**정답: B**

**왜 다른 보기는 오답인가**
- A: 수동 문서화/검토는 강제력이 없어 실수를 원천 차단하지 못합니다.
- C: 스키마 자체를 포기하는 것은 문제의 근본 원인(호환성 강제 부재)을 해결하지 못하고 오히려 파싱 오류 위험을 컨슈머에게 전가합니다.
- D: 토픽/스트림을 매번 새로 만드는 것은 마이그레이션 부담만 늘릴 뿐 스키마 호환성 강제 기능이 아닙니다.

> 💡 **시험 꿀팁**: 스트리밍 데이터의 **이벤트 스키마를 중앙에서 버전 관리하고 호환성 규칙을 강제**하려면 **AWS Glue Schema Registry**가 표준 정답입니다.

## QUESTION 352

**문제**: 회사가 원격 근무 직원 수천 명에게 VPC 내부 리소스에 대한 안전한 접근을 제공해야 한다. 기존 하드웨어 VPN 어플라이언스는 확장성이 부족하다. 사용자 인증서 기반의 **상호 인증(mutual authentication)**을 사용하고, 접속 시 자동으로 VPN 클라이언트 소프트웨어와 통합되는 관리형 솔루션을 원한다. 솔루션은?

**보기**
- A. 여러 개의 On-Demand EC2 인스턴스에 OpenVPN을 직접 설치해 자체 VPN 서버 팜 구성(자체 구축/운영은 패치, 확장, 고가용성 관리를 직접 해야 해서 운영 부담이 크며 관리형 서비스가 아님).
- B. **AWS Client VPN을 사용해 관리형 클라이언트 기반 VPN 엔드포인트를 구성하고, ACM Private CA로 발급한 클라이언트 인증서를 통한 상호 인증(mutual TLS authentication)을 설정.**

**정답: B**

**AWS Client VPN**은 완전관리형 클라이언트 기반 VPN 서비스로, OpenVPN 기반 클라이언트 소프트웨어를 통해 사용자가 VPC(및 온프레미스 네트워크까지)에 안전하게 접속할 수 있게 해줍니다. **ACM Private CA**로 발급한 클라이언트 인증서를 사용한 **상호 TLS 인증**을 구성하면, 사용자마다 고유한 인증서로 강력하게 인증하면서도 인증서 발급/배포/해지를 중앙에서 관리할 수 있습니다. 자동 확장도 관리형으로 처리되어 수천 명 규모의 원격 근무자를 지원하는 데 적합합니다.

**왜 다른 보기는 오답인가**
- A: 자체 OpenVPN 서버 구축은 패치, 확장성, 고가용성을 직접 관리해야 하는 운영 부담이 큽니다.
- C, D: Site-to-Site VPN과 Direct Connect는 네트워크 대 네트워크(고정 위치) 연결에 최적화된 서비스로, 수천 명의 개별 원격 사용자를 대상으로 하는 이 시나리오에는 부적합합니다.

> 💡 **시험 꿀팁**: 다수의 **원격 근무 직원에게 인증서 기반 상호 인증으로 VPC 접근**을 제공하려면 **AWS Client VPN(ACM Private CA 기반 mTLS)**이 표준 정답입니다.

## QUESTION 353

**문제**: 대규모 이기종 데이터베이스 마이그레이션(Oracle → Aurora PostgreSQL)을 DMS로 진행한 후, 전환(cutover) 전에 **소스와 타겟의 데이터가 실제로 정확히 일치하는지**(행 수, 값 자체까지) 자동으로 검증하고 싶다. 별도의 검증 스크립트를 직접 작성하고 싶지 않다. 솔루션은?

**보기**
- A. 소스와 타겟에서 각각 SELECT COUNT(*)만 실행해 행 수만 비교(행 수 일치만으로는 값 자체의 불일치(예: 문자 인코딩 손상, 타입 변환 오류)를 발견할 수 없어 불완전한 검증).
- B. **DMS의 데이터 검증(data validation) 기능을 활성화해, DMS가 자동으로 소스와 타겟의 데이터를 행 단위/컬럼 단위로 비교하고 불일치가 발견되면 이를 보고.**
- C. 전체 데이터를 애플리케이션으로 각각 읽어와 메모리에서 직접 비교하는 커스텀 스크립트 작성(대용량 데이터 전체를 애플리케이션 메모리로 읽어와 비교하는 것은 비효율적이고 별도 스크립트 구현 부담도 그대로 남음).
- D. 타겟 데이터베이스에서 무작위 샘플 100개 행만 육안으로 검토(샘플링 기반 수동 검토는 전체 데이터의 정확한 일치를 보장하지 못하고 대규모 마이그레이션의 신뢰할 수 있는 검증 방법이 아님).

**정답: B**

**해설**
**AWS DMS의 데이터 검증(data validation)** 기능을 마이그레이션 태스크에서 활성화하면, DMS가 복제 과정 중 또는 이후에 소스와 타겟의 데이터를 **행 단위 및 컬럼 단위로 자동 비교**해 값의 불일치를 탐지하고 보고합니다. 별도의 검증 스크립트를 직접 작성/유지할 필요 없이, DMS 자체 기능만으로 대규모 이기종 마이그레이션의 데이터 정확성을 신뢰성 있게 검증할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 행 수만 비교하는 것은 개별 값의 손상이나 변환 오류를 발견하지 못하는 불완전한 검증입니다.
- C: 자체 비교 스크립트 구현은 대용량 데이터에서 비효율적이며 "직접 작성하고 싶지 않다"는 요구에도 반합니다.
- D: 샘플링 기반 육안 검토는 전체 데이터의 정확한 일치를 보장하는 신뢰할 수 있는 방법이 아닙니다.

> 💡 **시험 꿀팁**: DMS 마이그레이션에서 **소스-타겟 데이터의 정확한 일치를 자동으로 검증**하려면 자체 스크립트 없이 **DMS의 데이터 검증(data validation)** 기능이 표준 정답입니다.

**정답: B**

**해설**
**Route 53 다중값 응답 라우팅**은 하나의 레코드에 여러 IP 주소(및 각각에 대한 상태 확인)를 등록하면, DNS 쿼리에 대해 **상태가 양호한(healthy) 레코드들 중 최대 8개를 무작위로** 응답합니다. 가중치나 지연시간 같은 정교한 라우팅 정책을 설정할 필요 없이, 여러 엔드포인트에 대해 클라이언트 측 간단한 로드 분산과 상태 기반 자동 제외(비정상 엔드포인트는 응답에서 제외)를 동시에 얻을 수 있는 가장 단순한 방법입니다.

**왜 다른 보기는 오답인가**
- A: 가중치 라우팅도 가능하지만 가중치 값을 지정/관리해야 해서 다중값 응답보다 설정이 조금 더 필요합니다.
- C: 페일오버 라우팅은 프라이머리/세컨더리의 능동-대기 구조에 특화되어 있으며, 여러 엔드포인트를 동시에 번갈아 사용하는 이 요구와는 다릅니다.
- D: 지연시간 기반 라우팅은 지연시간 최적화가 목적이며, 이 문제의 "가장 간단한 다중 엔드포인트 상태 기반 응답"이라는 목적과는 다릅니다.

> 💡 **시험 꿀팁**: 복잡한 정책 없이 **여러 정상 엔드포인트를 간단히 번갈아 응답하면서 비정상 엔드포인트는 자동 제외**하고 싶다면 **Route 53 다중값 응답 라우팅(multivalue answer routing)**이 표준 정답입니다.

**문제**: 대기업이 Control Tower로 다중 계정 랜딩존을 운영 중인데, 신규 계정 프로비저닝을 콘솔 클릭이 아닌 **코드로 관리되는 파이프라인(GitOps 방식)**으로 처리하고, 계정 생성 후 커스터마이징(추가 IAM 역할, 네트워킹 등)도 Terraform으로 자동 적용하고 싶다. 솔루션은?

**보기**
- A. Control Tower 계정 팩토리를 콘솔에서 계속 수동으로 사용하고, 생성 후 별도로 Terraform을 수동 실행(계정 생성과 커스터마이징 과정에 여전히 수동 개입이 남아 있어 "코드로 관리되는 파이프라인" 요구에 완전히 부합하지 않음).

**해설**
**Account Factory for Terraform(AFT)**은 AWS Control Tower와 통합되어, 신규 계정 프로비저닝 요청을 **Terraform 코드로 정의하고 Git 리포지토리를 통해 관리(GitOps)**할 수 있게 해주는 솔루션입니다. 계정이 생성된 후에도 계정별 커스터마이징(IAM 역할, 네트워킹, SCP 등)을 **자동화된 Terraform 파이프라인**으로 적용할 수 있어, 콘솔 클릭 없이 완전히 코드 기반으로 다중 계정 랜딩존의 계정 생명주기를 관리하는 표준 방법입니다.

- C: Service Catalog는 프로비저닝에는 유용하지만, 이 문제가 명시한 Terraform 기반 코드화 및 자동 커스터마이징 파이프라인 요구에는 AFT가 더 특화되어 있습니다.
- D: 콘솔에서의 수동 개별 스택 생성은 GitOps/코드 기반 관리 요구와 정반대입니다.

> 💡 **시험 꿀팁**: Control Tower 환경에서 **Terraform/GitOps 기반으로 계정 프로비저닝과 사후 커스터마이징을 자동화**하려면 **Account Factory for Terraform(AFT)**이 표준 정답입니다.

## QUESTION 356

**문제**: 비용 최적화 담당자가 조직 전체의 EBS 볼륨(과다 프로비저닝된 IOPS/처리량)과 Lambda 함수(적절하지 않은 메모리 설정으로 인한 비효율)에 대해, 실제 사용 지표를 기반으로 한 구체적인 최적화 권장 사항을 얻고 싶다. 직접 CloudWatch 지표를 분석하는 로직을 구현하지 않고 이를 자동화하려면?

**보기**
- A. CloudWatch 지표를 Athena로 내보내 자체 분석 쿼리 작성(자체 분석 로직 구현은 불필요한 개발 부담이며 AWS가 이미 제공하는 권장 엔진을 재구현하는 것).
- B. **AWS Compute Optimizer를 활성화해, EC2뿐 아니라 EBS 볼륨과 Lambda 함수에 대해서도 실제 사용률 지표(CloudWatch)를 머신러닝으로 분석한 구체적인 사이징/구성 최적화 권장 사항을 자동으로 받음.**

**정답: B**

**해설**
**AWS Compute Optimizer**는 EC2 인스턴스뿐 아니라 **EBS 볼륨**(IOPS, 처리량, 볼륨 유형 최적화)과 **Lambda 함수**(메모리 크기 최적화)에 대해서도 CloudWatch의 실제 사용률 지표를 머신러닝으로 분석해 구체적인 최적화 권장 사항(예: "이 gp3 볼륨의 프로비저닝된 IOPS를 X로 낮추세요", "이 Lambda 함수의 메모리를 Y MB로 조정하세요")을 자동으로 제공합니다. 자체 분석 로직 구현 없이 조직 전체의 리소스를 정밀하게 최적화할 수 있는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 자체 분석 로직 구현은 Compute Optimizer가 이미 제공하는 머신러닝 기반 권장 기능을 불필요하게 재구현하는 것입니다.
- C: Trusted Advisor도 일부 도움이 되지만, EBS/Lambda에 특화된 정교한 사이징 권장 사항은 Compute Optimizer의 전용 기능입니다.
- D: 수동 판단은 대규모 리소스에 비효율적이고 일관성이 떨어집니다.

> 💡 **시험 꿀팁**: EC2뿐 아니라 **EBS 볼륨과 Lambda 함수의 사이징까지 자동으로 최적화 권장**받으려면 **AWS Compute Optimizer**가 표준 정답입니다.

## QUESTION 357

**문제**: 회사가 VPC 내부 리소스에서 S3에 접근할 때, **VPC 게이트웨이 엔드포인트를 통한 접근이라도 회사가 승인한 특정 버킷들에만** 접근할 수 있도록 제한하고 싶다(직원의 실수나 침해된 자격 증명으로 회사 소유가 아닌 임의의 퍼블릭 S3 버킷에 데이터가 유출되는 것을 방지). 버킷 정책과는 별개로 VPC 수준에서 추가적인 방어 계층을 두려면?

**보기**
- A. 각 IAM 사용자/역할의 정책에서 허용된 버킷 ARN만 명시(IAM 정책만으로는 관리자 권한이 있는 자격 증명이나 정책 실수가 있을 경우 여전히 다른 버킷에 접근 가능해, VPC 수준의 추가 방어 계층이라는 요구를 충족하지 못함).
- B. **S3용 VPC 게이트웨이 엔드포인트에 엔드포인트 정책(endpoint policy)을 연결해, 이 엔드포인트를 통한 S3 접근을 회사가 승인한 특정 버킷 ARN 목록으로만 제한.**
- C. NACL 규칙으로 S3 관련 트래픽을 제어(NACL은 IP/포트 기반 필터링만 가능하며 특정 S3 버킷 단위로 접근을 제어하는 기능이 없음 — S3 게이트웨이 엔드포인트는 AWS 소유 IP 대역을 사용해 NACL로 특정 버킷을 구분하는 것이 사실상 불가능).
- D. 모든 S3 접근을 차단하고 필요할 때마다 예외적으로 허용(비현실적으로 관리 부담이 크며, 정상적인 업무에 필요한 접근까지 매번 예외 처리해야 함).

**정답: B**

**해설**
S3용 **VPC 게이트웨이 엔드포인트**에 **엔드포인트 정책**을 연결하면, 해당 엔드포인트를 통해 이루어지는 모든 S3 요청에 대해 접근 가능한 버킷을 명시적으로 제한할 수 있습니다. 이는 IAM 정책(자격 증명 기반)과는 별개의 **네트워크 경로 수준의 방어 계층**으로, 설사 IAM 정책에 실수가 있거나 자격 증명이 침해되더라도 VPC를 통한 S3 접근 자체가 승인된 버킷 목록으로 강제되어, 회사 소유가 아닌 임의의 버킷으로의 데이터 유출을 심층 방어(defense-in-depth) 차원에서 막을 수 있습니다.

**왜 다른 보기는 오답인가**
- A: IAM 정책만으로는 다른 정책(예: 관리자 정책)이나 실수로 인해 여전히 우회될 수 있어, 별도의 VPC 수준 계층이라는 요구를 충족하지 못합니다.
- C: NACL은 IP/포트 기반이며 S3 같은 AWS 관리형 서비스의 특정 버킷 단위 제어에는 사용할 수 없습니다.
- D: 전면 차단 후 예외 허용 방식은 관리 부담이 지나치게 커 비현실적입니다.

> 💡 **시험 꿀팁**: VPC에서 S3로의 접근을 **승인된 특정 버킷으로만 제한**하는 추가 방어 계층이 필요하면 **S3 VPC 게이트웨이 엔드포인트의 엔드포인트 정책**이 표준 정답입니다.

**보기**
- A. 온프레미스 인증 서비스의 IP로 직접 라우팅되도록 VPC 라우팅 테이블만 구성(직접 라우팅도 가능한 방법이지만, "AWS 네이티브 서비스에 접근하는 것처럼 간단한 인터페이스 엔드포인트로 접근"하고 싶다는 요구, 그리고 여러 VPC/계정에 걸친 접근 제어 세분화 측면에서 PrivateLink 방식이 더 적합).
- B. **온프레미스 인증 서비스를 가리키는 대상 그룹(IP 기반)을 가진 NLB를 VPC에 생성하고, 이 NLB를 대상으로 VPC 엔드포인트 서비스(PrivateLink)를 게시. 접근이 필요한 각 VPC(또는 계정)에서 인터페이스 엔드포인트를 생성해 연결.**
- C. 온프레미스 인증 서비스 앞에 API Gateway를 두고 퍼블릭 엔드포인트로 노출(퍼블릭 엔드포인트로 노출하는 것은 "인터넷을 거치지 않아야 한다"는 요구에 정면으로 반함).
- D. 온프레미스 인증 서비스를 S3에 정적 파일로 미러링해 VPC에서 조회(인증 서비스는 상태를 가진 동적 서비스이며 정적 파일로 대체할 수 있는 대상이 아님 — 개념 오류).

**정답: B**

**해설**
NLB의 **대상 그룹에 온프레미스 인증 서비스의 IP 주소를 (Direct Connect로 연결된) IP 기반 대상으로 등록**하면, 온프레미스 서비스를 향한 트래픽을 NLB가 받아 전달할 수 있습니다. 이 NLB를 대상으로 **VPC 엔드포인트 서비스(AWS PrivateLink)**를 게시하면, 접근이 필요한 각 VPC(같은 계정이든 다른 계정이든)에서 **인터페이스 엔드포인트**만 생성해 온프레미스 서비스에 마치 AWS 네이티브 서비스처럼 프라이빗하게, 인터넷을 거치지 않고 접근할 수 있습니다. 이는 "PrivateLink를 온프레미스 서비스 노출에 활용"하는 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- A: 직접 라우팅도 유효하지만, 여러 VPC/계정에 걸쳐 세분화된 접근 제어와 "네이티브 서비스처럼 간단한 엔드포인트" 경험을 원한다면 PrivateLink(NLB+VPC 엔드포인트 서비스) 방식이 더 표준적입니다.
- C: 퍼블릭 노출은 "인터넷을 거치지 않아야 한다"는 요구를 정면으로 위반합니다.
- D: 인증 서비스는 동적 상호작용이 필요한 서비스이며 정적 파일 미러링 대상이 아닙니다.

> 💡 **시험 꿀팁**: **온프레미스 서비스를 VPC(또는 여러 계정)에 AWS 네이티브 서비스처럼 프라이빗하게 노출**하려면 **NLB(온프레미스 IP 대상) + VPC 엔드포인트 서비스(PrivateLink)** 조합이 표준 정답입니다.

## QUESTION 359

**문제**: 회사가 x86 기반 EC2 인스턴스로 실행 중인 웹 애플리케이션(Java 기반, 표준 오픈소스 라이브러리만 사용, 커스텀 네이티브 바이너리 없음)의 비용을 절감하고 싶다. 애플리케이션 아키텍처나 코드 변경 없이 최대한의 비용 대비 성능 개선을 얻으려면?

**보기**
- A. 동일한 x86 인스턴스 패밀리 내에서 세대만 최신으로 업그레이드(어느 정도 효과는 있지만, x86 세대 업그레이드만으로 얻는 비용 대비 성능 개선 폭은 아키텍처 자체를 바꾸는 것보다 작음).
- B. **AWS Graviton(ARM 기반) 프로세서를 사용하는 인스턴스 유형으로 전환. Java 애플리케이션은 JVM이 ARM을 지원하므로 대부분 재컴파일 없이(또는 최소한의 검증만으로) 이전 가능하며, 동급 x86 인스턴스 대비 최대 40%까지 더 나은 가격 대비 성능을 기대.**
- C. 스팟 인스턴스로 전면 전환해 비용만 절감(스팟은 중단 가능성이 있어 상시 운영되는 웹 애플리케이션의 가용성 요구와 상충할 수 있으며, 이 문제는 "아키텍처/코드 변경 없이 성능 개선"을 원하는 것이지 가용성을 희생한 비용 절감이 목적이 아님).
- D. 인스턴스 크기를 무조건 한 단계 낮춰 비용만 줄임(성능 요구사항을 고려하지 않고 무작정 축소하는 것은 실제 트래픽을 감당하지 못해 서비스 저하로 이어질 위험이 있음).

**정답: B**

**해설**
**AWS Graviton** 프로세서 기반 인스턴스는 표준 오픈소스 소프트웨어 스택(Java/JVM, Python, 대부분의 Linux 배포판과 오픈소스 라이브러리)을 사용하는 워크로드에서 동급 x86 인스턴스 대비 **최대 약 40% 더 나은 가격 대비 성능**을 제공합니다. Java 애플리케이션은 JVM이 ARM 아키텍처를 완전히 지원하므로, 커스텀 네이티브 바이너리(x86 전용으로 컴파일된 것)가 없다면 애플리케이션 코드 변경 없이 인스턴스 유형만 전환해 테스트/검증 후 이전할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 동일 아키텍처(x86) 내 세대 업그레이드도 도움이 되지만, Graviton으로의 아키텍처 전환만큼의 가격 대비 성능 개선 폭에는 미치지 못합니다.
- C: 스팟 전환은 중단 가능성으로 인해 상시 가용성이 필요한 웹 서비스에는 리스크가 있으며, 이 문제의 목적(코드 변경 없는 성능/비용 개선)과는 다른 트레이드오프입니다.
- D: 성능 요구사항을 고려하지 않은 무조건적인 축소는 서비스 저하 위험이 있습니다.

> 💡 **시험 꿀팁**: 표준 오픈소스 스택(Java 등)을 사용하는 워크로드의 **가격 대비 성능을 코드 변경 없이 개선**하려면 **AWS Graviton(ARM) 인스턴스로의 전환**이 표준 정답입니다.

## QUESTION 360

**문제**: 규제 산업의 회사가 AWS Backup으로 백업을 관리하고 있으며, 백업 자체가 **규제가 요구하는 보존 기간 동안 어떤 방식으로도(관리자 포함) 삭제되거나 보존 기간이 단축될 수 없도록** 강제하고 싶다. S3 Object Lock의 준수 모드와 유사한 불변성을 AWS Backup 볼트 수준에서 구현하려면?

**보기**
- A. 백업 볼트에 대한 IAM 정책으로 삭제 API를 거부(IAM 정책은 충분한 권한을 가진 사용자에 의해 언제든 변경/삭제될 수 있어 진정한 의미의 불변성을 보장하지 못함).
- B. **AWS Backup Vault Lock을 사용해 백업 볼트에 규정 준수 모드(compliance mode)의 잠금 정책을 적용, 최소/최대 보존 기간을 설정해 이 볼트에 저장된 백업이 보존 기간 동안 삭제되거나 보존 기간이 단축되는 것을 root 계정을 포함한 누구도 할 수 없도록 강제.**
- C. 백업을 정기적으로 다른 계정의 S3 버킷으로 수동 내보내기(수동 내보내기 프로세스 자체는 불변성을 강제하는 기술적 장치가 아니며, 내보낸 후에도 삭제/수정이 여전히 가능함).
- D. 볼트 삭제 방지를 위해 MFA Delete만 활성화(MFA Delete는 추가 인증 단계를 요구할 뿐이며, MFA를 통과한 충분한 권한의 사용자는 여전히 삭제할 수 있어 완전한 불변성을 보장하지 못함).

**정답: B**

**해설**
**AWS Backup Vault Lock**은 백업 볼트에 잠금 정책을 적용해 WORM(Write Once Read Many) 모델을 강제하는 기능입니다. 특히 **규정 준수 모드(compliance mode)**로 잠그면, 설정된 최소/최대 보존 기간이 끝나기 전까지는 **AWS 계정 루트 사용자를 포함한 어느 누구도** 해당 볼트에 저장된 복구 지점(백업)을 삭제하거나 보존 기간을 단축할 수 없습니다(볼트 잠금 자체도 규정 준수 모드에서는 해제 불가). 이는 S3 Object Lock의 준수 모드와 유사한 수준의 강력한 불변성을 백업 계층에서 제공하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: IAM 정책은 권한이 있는 사용자에 의해 변경될 수 있어 진정한 불변성을 보장하지 못합니다.
- C: 수동 내보내기는 그 자체로 삭제/수정을 막는 기술적 장치가 아닙니다.
- D: MFA Delete는 추가 인증 절차일 뿐이며, 인증을 통과하면 여전히 삭제가 가능해 완전한 불변성과는 다릅니다.

> 💡 **시험 꿀팁**: 백업이 **규제 준수 목적으로 보존 기간 동안 누구도(관리자 포함) 삭제할 수 없도록** 강제하려면 **AWS Backup Vault Lock의 규정 준수 모드(compliance mode)**가 표준 정답입니다.
