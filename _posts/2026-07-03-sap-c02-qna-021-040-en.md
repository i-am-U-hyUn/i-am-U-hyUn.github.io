## QUESTION 21

**Question**: A company authenticates users against an on-premises Active Directory and wants to use the same authentication for logging into multiple AWS accounts under AWS Organizations. A Site-to-Site VPN already connects on-premises to every AWS account. Conditional access based on user groups/roles is required, and user identities must be managed from a single location.

**Choices**
- A. Configure **AWS IAM Identity Center (AWS SSO)** to connect to Active Directory using **SAML 2.0**. Enable automatic provisioning with **SCIM v2.0**. Grant AWS account access using **ABAC (attribute-based access control)**.
- B. Configure IAM Identity Center to use itself as the identity source, provision with SCIM, and grant account access via permission sets.
- C. Configure IAM in one account to use a SAML 2.0 identity provider, provision IAM users mapped to federated users, and grant access via cross-account IAM users.
- D. Configure IAM in one account to use an OIDC identity provider, provision IAM roles for federated users, and grant access via cross-account IAM roles.

**Correct Answer: A**

**Explanation**
The key requirement is that user identities be managed from **a single location (the on-premises AD).** The correct answer connects **IAM Identity Center to the existing Active Directory via SAML 2.0**, automatically syncs users/groups via **SCIM**, and uses **ABAC** to control conditional account access based on user attributes (group/role).

**Why the other choices are wrong**
- B: Using IAM Identity Center itself as the "identity source" creates a second user store separate from AD, violating the "single location" requirement.
- C: Provisioning individual IAM users per account and granting access via cross-account IAM users becomes an enormous operational burden as the number of accounts grows.
- D: OIDC isn't the standard protocol for on-premises AD federation (SAML 2.0 is), and manually provisioning roles per account also doesn't scale.

> 💡 **Exam tip**: Whenever you see "SSO across many AWS accounts + existing AD integration + centralized identity management," think **IAM Identity Center (SAML federation) + SCIM + permission sets/ABAC** first.

## QUESTION 22

**Question**: In an API Gateway + Lambda + DynamoDB app, PUT request errors are increasing, caused by a small number of clients (identified by API key) making excessive requests. The API isn't critical and clients can tolerate retries, but the errors are visible to customers and damaging the API's reputation. How can customer experience be improved?

**Choices**
- A. Implement retry logic with exponential backoff and jitter on the client side.
- B. Implement API throttling via an **API Gateway Usage Plan**, and ensure clients handle HTTP 429 responses gracefully.
- C. Turn on API caching to improve responsiveness in the production stage.
- D. Configure reserved concurrency at the Lambda function level.

**Correct Answer: B**

**Explanation**
Since specific clients can be identified via API keys, the fundamental fix is to use an **API Gateway Usage Plan** to rate-limit/quota those specific clients. This politely rejects excessive requests with an expected, retryable **429 (Too Many Requests)** response that clients can treat as a signal to back off.

**Why the other choices are wrong**
- A: Client-side retry logic alone doesn't stop the root cause (one client's excessive requests), and requiring every client to implement it isn't something you can control.
- C: API caching helps idempotent reads like GET, but doesn't apply to data-mutating PUT requests.
- D: Reserved concurrency helps guard resources but isn't a mechanism for rate-limiting a specific client, and could even affect other well-behaved clients sharing the function.

> 💡 **Exam tip**: When excessive calls from a specific API key are the problem, reach for **API Gateway Usage Plans** for throttling first. Also remember 429 is an "expected, normal" response in this pattern.

## QUESTION 23

**Question**: A cluster of hundreds of EC2 instances reads and modifies data from a 200 TB shared file system (hosted on separate, always-running EC2 instances) to generate reports. The job runs monthly, reads only a subset of files, and takes about 72 hours. Compute scales via Auto Scaling, but the shared file system instances keep running continuously. The company needs to reduce cost while maintaining high-performance access during the 72-hour window.

**Choices**
- A. Migrate data to **S3 Intelligent-Tiering**. Before each monthly job, create a new **Amazon FSx for Lustre** file system linked to S3 using **lazy loading**, use it as shared storage during the job, and delete it once the job completes.
- B. Migrate data to a large **Multi-Attach Amazon EBS** volume and attach it to each instance.
- C. Migrate data to **S3 Standard**. Before each monthly job, create an FSx for Lustre file system using **batch loading**.
- D. Migrate data to S3, and before each monthly job, create an AWS Storage Gateway File Gateway to use as shared storage.

**Correct Answer: A**

**Explanation**
Since the data sits idle most of the time and is only accessed once a month, minimize storage cost with **S3 Intelligent-Tiering**, and only spin up **FSx for Lustre** (linked to S3) temporarily during the job window for high-performance parallel filesystem access, deleting it afterward. Since the job only reads a **subset** of files, **lazy loading** (pulling files from S3 only on first access) is more efficient than batch loading everything upfront.

**Why the other choices are wrong**
- B: A large Multi-Attach EBS volume requires additional cluster-aware filesystem software, adding complexity, and doesn't achieve the same cost savings as the S3-based approach.
- C: S3 Standard costs more than Intelligent-Tiering for data that's idle most of the time, and batch loading wastes time and cost loading files that may never be needed.
- D: Storage Gateway File Gateway suits ongoing hybrid storage access patterns, but isn't as optimized as FSx for Lustre for a burst of high-performance parallel HPC-style compute over 72 hours.

> 💡 **Exam tip**: For a workload that's "normally idle, but periodically needs high-performance parallel file access for a short window," reach for the **S3 (Intelligent-Tiering) + FSx for Lustre (lazy loading, created just before the job and deleted after)** combo.

## QUESTION 24

**Question**: A new service is being developed that's accessed via TCP on a fixed port. It needs high availability with redundancy across Availability Zones, and must be reachable via a public DNS name (`my.service.com`). Other companies need to add its address to an allow-list, requiring a **static IP address**. Resources are deployed across multiple AZs in a single Region.

**Choices**
- A. Assign an Elastic IP directly to each EC2 instance, register the instances with an NLB, and point the DNS record at the instances' Elastic IPs.
- B. Assign a public IP to an ECS cluster and expose it via an NLB, with an A record pointing at the ECS cluster's public IP.
- C. Create EC2 instances for the service. Create **one Elastic IP per Availability Zone**, and **assign each to the NLB per AZ**. Register the EC2 instances with a target group, and use a DNS **Alias A record** pointing at the NLB's DNS name.
- D. Put an ALB in front of an ECS cluster exposing a static TCP port, and use a CNAME record pointing at a public IP.

**Correct Answer: C**

**Explanation**
When a **static IP address** is needed for allow-listing purposes, use a **Network Load Balancer (NLB)** — the only ELB type that supports assigning a static Elastic IP per Availability Zone. Register the EC2 instances with the NLB's target group, and point DNS at the NLB via an alias record.

**Why the other choices are wrong**
- A: Attaching Elastic IPs directly to individual instances instead of a load balancer loses the benefits of load balancing and automatic failover.
- B: Public IPs assigned to ECS tasks are **dynamic** — they can change on task restart — failing the "static IP" requirement.
- D: **ALB operates at Layer 7 (HTTP/HTTPS)**, unsuitable for passing through arbitrary TCP traffic, and ALB doesn't offer static IPs either.

> 💡 **Exam tip**: Whenever "a static/fixed IP for allow-listing" appears, think **NLB with an Elastic IP assigned per Availability Zone**. ALB and ECS's dynamic public IPs cannot satisfy this requirement.

## QUESTION 25

**Question**: An on-premises analytics platform runs fully redundant across 12 servers. Scheduled jobs (20 min-2 hr, strict SLA) account for 65% of usage; user jobs (under 5 min, no SLA) account for 35%. During a system failure, scheduled jobs must still meet their SLA, but user jobs may be delayed. Migrating to EC2, adopting a consumption-based model to cut cost without long-term commitments, while keeping high availability and SLA intact.

**Choices**
- A. Split 12 instances across 2 AZs: 2 On-Demand instances with Capacity Reservations plus 4 Spot instances per AZ.
- B. Split across 3 AZs, but put all 4 On-Demand Capacity-Reservation instances in a **single AZ**, with the rest as Spot.
- C. Split across 3 AZs: 2 On-Demand instances using a **Savings Plan** plus 2 Spot instances per AZ.
- D. Split across 3 AZs: **3 On-Demand instances with Capacity Reservations plus 1 Spot instance per AZ.**

**Correct Answer: D**

**Explanation**
An **On-Demand Capacity Reservation** guarantees capacity in a specific AZ at On-Demand pricing, with **no long-term commitment required**. Option D spreads guaranteed capacity evenly across all 3 AZs (9 instances, 75%), so even if all 3 Spot instances are reclaimed simultaneously, there's still more than enough guaranteed capacity to cover the SLA-bound scheduled jobs (65%), and no single AZ failure wipes out all guaranteed capacity at once.

**Why the other choices are wrong**
- A: Only 2 AZs means less redundancy, and only 4 guaranteed instances (33%) — insufficient to cover the 65% SLA requirement if Spot instances are reclaimed.
- B: Concentrating all 4 guaranteed instances in **one AZ** creates a single point of failure — if that AZ fails, all guaranteed capacity disappears at once.
- C: **Savings Plans require a 1- or 3-year commitment**, directly violating the "no long-term commitment" requirement.

> 💡 **Exam tip**: **On-Demand Capacity Reservations** guarantee capacity in a specific AZ **without requiring a long-term commitment**, unlike Reserved Instances or Savings Plans. When mixing guaranteed capacity with Spot, spread the guaranteed portion **evenly across all AZs** so a single AZ failure doesn't take down all your SLA-critical capacity.

## QUESTION 26

**Question**: A database password must be a randomly generated, strong password stored in a secure AWS-managed service, resources must be deployed via CloudFormation, and credentials must rotate every 90 days. Which CloudFormation resource configuration meets these requirements with the least operational overhead?

**Choices**
- A. Use **AWS Secrets Manager** to create the database password as a Secret resource. Create a Lambda function resource to rotate it. Specify a Secrets Manager **`RotationSchedule` resource that rotates it every 90 days**.
- B. Use Systems Manager Parameter Store with a SecureString parameter type for the password, a Lambda function to rotate it, and a "Parameter Store RotationSchedule" resource for the 90-day rotation.
- C. Use Secrets Manager and a rotation Lambda, but trigger the Lambda directly via an **EventBridge scheduled rule** every 90 days.
- D. Use Parameter Store's SecureString type for the password, and specify an "AWS AppSync DataSource" resource to auto-rotate it every 90 days.

**Correct Answer: A**

**Explanation**
**AWS Secrets Manager natively supports automated rotation via a `RotationSchedule` resource** — an AWS-native feature that ties the secret, a rotation Lambda function, and the rotation schedule together, without needing to build your own scheduling infrastructure. This gives the lowest operational overhead.

**Why the other choices are wrong**
- B: **Parameter Store has no native automatic-rotation schedule feature like Secrets Manager does.** The "Parameter Store RotationSchedule" resource described here doesn't exist.
- C: Uses Secrets Manager correctly, but reimplements the same result manually via EventBridge instead of using the built-in `RotationSchedule` — more operational overhead than A.
- D: AWS AppSync is a GraphQL API service with no relation to credential rotation whatsoever.

> 💡 **Exam tip**: For automated database credential rotation, default to **Secrets Manager + RotationSchedule + a rotation Lambda function**. Parameter Store can store secrets but has no built-in rotation capability.

## QUESTION 27

**Question**: A company stores data across several DynamoDB tables and needs to expose it as a simple public API over HTTPS using a serverless architecture that scales automatically with demand. (Choose two.)

**Choices**
- A. Create an **API Gateway REST API**, configured with the **AWS integration type for direct integration to DynamoDB**.
- B. Create an API Gateway **HTTP API**, configured with the AWS integration type for direct integration to DynamoDB.
- C. Create an API Gateway **HTTP API**, integrated with **a Lambda function that returns data from the DynamoDB table**.
- D. Create an accelerator in AWS Global Accelerator, integrated with a Lambda@Edge function returning data from DynamoDB.
- E. Create a Network Load Balancer, with listener rules forwarding to the appropriate Lambda function.

**Correct Answer: A, C**

**Explanation**
**API Gateway REST API supports direct AWS service integration** with DynamoDB, requiring no Lambda function (A). **HTTP API does not support this direct AWS service integration** — it only supports Lambda proxy integration — so to use HTTP API, you must go through a Lambda function (C).

**Why the other choices are wrong**
- B: HTTP API, unlike REST API, does not support direct integration with AWS services like DynamoDB. This choice assumes a feature that doesn't exist.
- D: Global Accelerator improves global network performance and has nothing to do with this kind of simple backend API architecture.
- E: NLB operates at Layer 4 and lacks the path/method-based routing rules needed to route requests to specific Lambda functions the way API Gateway does.

> 💡 **Exam tip**: **API Gateway REST API can integrate directly with AWS services like DynamoDB without Lambda**, but **HTTP API cannot.** Whenever a choice involving HTTP API mentions "direct AWS service integration," it's likely wrong.

## QUESTION 28

**Question**: A company registered 10 new domains for online marketing and needs to redirect visitors to specific target URLs per domain, defined in a JSON document. DNS is managed by Route 53. The service must accept both HTTP and HTTPS requests with minimal operational effort. (Choose three.)

**Choices**
- A. Create a dynamic web page running on an EC2 instance.
- B. Create an ALB with HTTP and HTTPS listeners.
- C. Create a **Lambda function that looks up the redirect URL using the JSON document** and responds accordingly.
- D. Publish a Lambda function via an API Gateway API with a custom domain.
- E. Create a **CloudFront distribution**. Deploy a **Lambda@Edge** function.
- F. Use **AWS Certificate Manager (ACM)** to create an SSL certificate that includes the domains as Subject Alternative Names.

**Correct Answer: C, E, F**

**Explanation**
This exactly matches AWS's own reference architecture for a "**redirect service using CloudFront + Lambda@Edge**." A **CloudFront distribution** accepts both HTTP and HTTPS, a **Lambda@Edge** function at the viewer-request stage looks up the JSON mapping and returns the redirect, and to handle all 10 domains on one distribution, the **ACM certificate must include all the domains as SANs**.

**Why the other choices are wrong**
- A: Building a dynamic page on EC2 requires server management, contradicting "minimal operational effort."
- B: An ALB alone can't handle the redirect-lookup logic itself — you'd still need compute behind it.
- D: An API Gateway custom domain per Lambda could work, but requires separate configuration for each of the 10 domains, carrying more operational overhead than the CloudFront + Lambda@Edge combo.

> 💡 **Exam tip**: For a low-operational-overhead service that "redirects visitors from many custom domains to different target URLs," the AWS reference architecture is **CloudFront + Lambda@Edge (viewer request) + ACM (SAN certificate)**.

## QUESTION 29

**Question**: A company wants to accurately charge back the cost of a security tool (running on EC2 across multiple AWS accounts) to the compliance team's account. Related resources are tagged `costCenter=compliance`.

**Choices**
- A. Activate the `costCenter` tag **in the organization's management (master) account**, and configure a monthly Cost and Usage Report (CUR) in that account, using the report's tag breakdown to calculate cost.
- B. Activate the `costCenter` tag in the member accounts, configure a CUR in the master account, and use a Lambda function to compute monthly cost.
- C. Activate the `costCenter` tag in the member accounts, and schedule a CUR in the master account.
- D. Create a custom report in AWS Trusted Advisor's organization view.

**Correct Answer: A**

**Explanation**
Cost allocation tags must be **activated in the organization's management (payer) account** for tag-based breakdowns to work in the organization-wide Cost and Usage Report. Activating the tag in member accounts (B, C) doesn't work for organization-level cost allocation purposes.

**Why the other choices are wrong**
- B, C: Activating the tag at the member-account level is itself the mistake. Cost allocation tag activation is a payer (management) account-level setting.
- D: AWS Trusted Advisor provides best-practice recommendations — it isn't a billing tool for producing detailed tag-based cost breakdowns.

> 💡 **Exam tip**: **Cost allocation tags must be activated in the Organizations management (payer) account** to be usable in the organization-wide CUR. Watch out for the trap of activating them in a member account instead.

## QUESTION 30

**Question**: 50 AWS accounts (under Organizations) each have multiple VPCs, and a Transit Gateway is used to connect VPCs between member accounts. The company wants to automate creating a new VPC and Transit Gateway attachment whenever a new member account is created. (Choose two.)

**Choices**
- A. **In the master account, use AWS RAM to share the Transit Gateway** with member accounts.
- B. In the master account, use an SCP to share the Transit Gateway.
- C. **In the master account, launch a CloudFormation StackSet** that automatically creates a new VPC and VPC-to-Transit-Gateway attachment in member accounts, connecting to the master account's Transit Gateway ID.
- D. Use a StackSet to automatically create a new VPC and a "peering Transit Gateway attachment" in member accounts, sharing via a service-linked role.
- E. Use AWS Service Catalog to share the Transit Gateway.

**Correct Answer: A, C**

**Explanation**
The standard service for cross-account resource sharing is **AWS Resource Access Manager (RAM)**. Share the Transit Gateway from the owning (master) account via RAM (A), and use a **CloudFormation StackSet** to automate creating a VPC and attachment in every new member account (C).

**Why the other choices are wrong**
- B: **SCPs are permission guardrails**, not a resource-sharing mechanism — the concept itself is wrong.
- D: The description of a "peering Transit Gateway attachment" (implying separate TGWs peered together) is inaccurate for this scenario, and "sharing via a service-linked role" isn't the correct RAM-based sharing method.
- E: AWS Service Catalog is a standardized self-service provisioning catalog, not a mechanism for directly sharing resources like a Transit Gateway across accounts.

> 💡 **Exam tip**: To share resources like a Transit Gateway or subnets across accounts, use **AWS RAM**. To automatically provision matching resources when new accounts join, combine it with **CloudFormation StackSets**.

## QUESTION 31

**Question**: An enterprise wants to restrict developers to buying only approved third-party software via AWS Marketplace's **Private Marketplace** feature. Only a role named `procurement-manager-role` should be able to administer Private Marketplace; everyone else (users, groups, roles, account admins) must be denied. The organization uses all features of AWS Organizations, with a shared services account per OU.

**Choices**
- A. Create `procurement-manager-role` in every account, grant PowerUserAccess, and apply individual inline deny policies to every IAM user/role across every account.
- B. Create `procurement-manager-role` in every account, grant AdministratorAccess, and use a permission boundary to restrict developer roles.
- C. Create `procurement-manager-role` **in every shared services account** with the `AWSPrivateMarketplaceAdminFullAccess` policy attached. Create an **organization-root SCP** denying Private Marketplace admin access to everyone except this role. Create **another organization-root SCP** denying everyone from being able to create a role with this same name.
- D. Create `procurement-manager-role` only in accounts developers use, and apply the SCP only to shared services accounts.

**Correct Answer: C**

**Explanation**
The standard pattern for restricting a sensitive permission to exactly one named role across an entire organization is a **pair of root-level SCPs**: ① deny everyone except the named role (`procurement-manager-role`) from Private Marketplace admin actions, and ② **deny everyone from being able to create a role with that exact same name** — preventing anyone from spoofing the trusted role to bypass restriction #1.

**Why the other choices are wrong**
- A: Granting an overly broad policy (PowerUserAccess) and attaching individual inline deny policies to every IAM user/role across every account is unmaintainable as the number of accounts/users grows.
- B: AdministratorAccess violates least privilege, and using a "permission boundary" attached to developer roles doesn't cleanly implement "allow only this role, deny everyone else."
- D: The role's location doesn't match the org structure (shared services accounts), and the restricting SCP is scoped only to shared services accounts, failing to cover the whole organization (including developer accounts).

> 💡 **Exam tip**: To restrict a sensitive permission to exactly one role across an entire organization, remember the pattern: **① an SCP denying everyone except that role, plus ② an SCP denying anyone from creating a role with that same name.** Without ②, someone could create a fake role with the same name to bypass restriction ①.

## QUESTION 32

**Question**: An SCP was deployed to a developer-only OU intended to allow only EC2, S3, and DynamoDB, but developer IAM users can still use other AWS services outside that list. What should be done to remove developers' ability to use out-of-scope services?

**Choices**
- A. Create explicit deny statements individually for every service that should be restricted.
- B. **Remove the default `FullAWSAccess` SCP** from the developer accounts' OU.
- C. Modify the FullAWSAccess SCP itself to explicitly deny all services.
- D. Add a wildcard explicit deny statement at the end of the SCP.

**Correct Answer: B**

**Explanation**
AWS Organizations automatically attaches a default **`FullAWSAccess` (allow everything) SCP** to every OU and account. When multiple SCPs are attached at the same level, their **Allow statements combine via union (OR)**, so no matter how narrow a custom "allow only EC2/S3/DynamoDB" SCP is, combining it with the default FullAWSAccess (allow everything) still results in "everything allowed." You must **remove FullAWSAccess** for the narrow Allow SCP to actually function as a restrictive allow-list.

**Why the other choices are wrong**
- A: AWS constantly adds new services, so maintaining an ever-growing per-service deny list isn't sustainable.
- C: Modifying the AWS-managed FullAWSAccess policy itself isn't the standard approach and could have unintended organization-wide effects.
- D: SCPs aren't evaluated like ordered firewall rules — they're evaluated as combined Allow/Deny statements — so simply appending a wildcard deny at the end of the document doesn't achieve the intended effect the way you might expect.

> 💡 **Exam tip**: **Every OU/account has the default `FullAWSAccess` SCP attached.** Multiple SCPs at the same level combine their Allow statements via union, so to build an "allow-list" style SCP, you must **first remove FullAWSAccess**. (Note: Deny always takes priority *across* levels — see Question 21's tip for that different axis.)

## QUESTION 33

**Question**: A monolithic REST API runs on 5 EC2 instances in a public subnet, exposed via Route 53 Multivalue Answer routing to each instance's IP. A recent sudden traffic surge overwhelmed the application. How can the application handle new, variable load with minimal operational overhead?

**Choices**
- A. **Break the API apart into individual Lambda functions.** Configure an **API Gateway REST API with Lambda integration** for the backend, and update the Route 53 record to point at API Gateway.
- B. Containerize the app and run an EKS cluster on EC2, connecting via a Kubernetes Ingress.
- C. Attach an Auto Scaling group to the existing EC2 fleet, scale based on CPU utilization, and use a Lambda function to update the Route 53 record on scaling events.
- D. Put an ALB in front, move the EC2 instances to a private subnet, and point DNS at the ALB.

**Correct Answer: A**

**Explanation**
To flexibly handle sudden traffic spikes while minimizing operational overhead, fully re-architecting the monolith into **individual Lambda functions behind API Gateway** is the most fundamental fix — scaling is then entirely offloaded to managed services.

**Why the other choices are wrong**
- B: EKS requires managing a Kubernetes control plane, contradicting "minimal operational overhead."
- C: Still keeps the monolithic EC2 architecture, and adds a custom Lambda function to manage DNS record updates — more complexity, not less.
- D: Adding an ALB helps somewhat, but the monolithic EC2-based backend still needs to be operated and managed, so operational overhead remains higher than the fully serverless rewrite in A.

> 💡 **Exam tip**: For a monolithic API overwhelmed by unpredictable traffic that needs "minimal operational overhead" going forward, consider a full serverless rewrite (**API Gateway + Lambda**) before just adding a load balancer or Auto Scaling group on top of the existing architecture.

## QUESTION 34

**Question**: A company creates an OU per engineering team, and each OU owns multiple accounts, totaling hundreds of AWS accounts. How can each OU see the cost breakdown for all of its accounts?

**Choices**
- A. Use AWS RAM to generate a Cost and Usage Report (CUR) for each OU.
- B. **Generate a Cost and Usage Report (CUR) in the Organizations management (master) account**, and let each team visualize it via an Amazon QuickSight dashboard.
- C. Generate a separate CUR in each member account.
- D. Use AWS Systems Manager to generate the CUR and visualize it via an OpsCenter dashboard.

**Correct Answer: B**

**Explanation**
Generating the CUR at the **payer (management) account level** aggregates usage data across every account in the organization into a single report. Each team can then filter and visualize just their OU/accounts' costs from that single CUR using **QuickSight**.

**Why the other choices are wrong**
- A: AWS RAM is a resource-sharing service, not a tool for generating CURs.
- C: Generating and reconciling separate CURs across hundreds of accounts is extremely inefficient compared to a single consolidated CUR at the master account.
- D: Systems Manager and OpsCenter are operational issue-management tools, unrelated to cost/billing reports.

> 💡 **Exam tip**: **Generate the CUR just once, at the Organizations management (payer) account**, which already covers all account data. Handle per-team views through a visualization layer like QuickSight with filtering.

## QUESTION 35

**Question**: A company stores data on an on-premises Windows File Server, generating 5 GB of new data daily. Some Windows workloads have already been migrated to AWS, and the data must be usable from a filesystem in the cloud. A Direct Connect connection already exists. Which migration strategy should be used?

**Choices**
- A. Replace the existing Windows File Server entirely with an AWS Storage Gateway File Gateway.
- B. **Use AWS DataSync to schedule a daily job replicating data between the on-premises Windows File Server and Amazon FSx for Windows File Server.**
- C. Use AWS Data Pipeline to schedule a daily job replicating data between the on-premises file server and Amazon EFS.
- D. Use AWS DataSync to schedule a daily job replicating data between the on-premises file server and Amazon EFS.

**Correct Answer: B**

**Explanation**
Since the source is a **Windows** File Server, the natural AWS counterpart is **Amazon FSx for Windows File Server**, which natively supports the SMB protocol and Windows ACLs. Pairing it with **AWS DataSync**, the purpose-built service for efficient scheduled on-premises-to-AWS synchronization, is the correct answer.

**Why the other choices are wrong**
- A: A File Gateway is closer to a hybrid storage pattern that fully replaces the existing server with a cache-fronted gateway — for the goal of "using the data from a filesystem in AWS," the FSx + DataSync combination is a better fit.
- C: AWS Data Pipeline is a general ETL/workflow orchestration tool, not as efficient as DataSync for file-level replication, and its target (EFS) is Linux-oriented, mismatched with a Windows source.
- D: DataSync is correct, but **EFS is a Linux/NFS-oriented filesystem** that doesn't fully support native Windows semantics like ACLs.

> 💡 **Exam tip**: When the on-premises source is a **Windows File Server**, the AWS destination should be **Amazon FSx for Windows File Server** (not EFS), and **AWS DataSync** is the tool for scheduled on-premises-to-AWS synchronization.

## QUESTION 36

**Question**: A web app references static assets in an S3 bucket in us-east-1, and needs resilience across multiple Regions. A second bucket has already been created in another Region. Which solution meets these requirements with minimal operational overhead?

**Choices**
- A. Configure the app to write to both buckets, and connect them via a Route 53 record with weighted routing.
- B. Create a Lambda function triggered on every S3 write that manually copies objects to the second Region's bucket.
- C. Configure **Cross-Region Replication (CRR)** from the us-east-1 bucket to the second Region's bucket, and set up a **CloudFront distribution with an Origin Group** containing both buckets as origins.
- D. Configure CRR, but manually update the application code to use the second bucket whenever failover is needed.

**Correct Answer: C**

**Explanation**
**S3 Cross-Region Replication** automatically keeps both buckets in sync, and a **CloudFront Origin Group** automatically fails over to the secondary origin (the second Region's bucket) if the primary origin fails — achieving fully managed multi-Region resilience with no custom code or manual intervention.

**Why the other choices are wrong**
- A: Requires application code changes to write to both buckets, and DNS-based weighted routing isn't as seamless as CloudFront Origin Group's automatic failover.
- B: Reimplementing what S3 CRR already provides natively via a custom Lambda is unnecessary operational overhead.
- D: CRR is correct, but requiring a **manual application code change** at failover time makes this far less automated than C.

> 💡 **Exam tip**: For multi-Region resilience of static content, combine **S3 CRR (data sync)** with a **CloudFront Origin Group (automatic failover)** to avoid any code changes.

## QUESTION 37

**Question**: An on-premises three-tier .NET web app (dependent on MySQL) has suffered downtime from traffic surges, prompting a mandate to migrate to AWS. It needs a scalable, highly available solution supporting 20,000 daily users.

**Choices**
- A. Elastic Beanstalk with EC2 Auto Scaling across 3 AZs behind a **Network Load Balancer**, and RDS MySQL Multi-AZ.
- B. Use CloudFormation to launch a stack with an **Application Load Balancer** in front of an **EC2 Auto Scaling group across 3 AZs**, and a **Multi-AZ Aurora MySQL DB cluster with a Retain deletion policy**. Route traffic from the company domain via a Route 53 alias record to the ALB.
- C. Elastic Beanstalk environments spanning **two separate Regions**, connected via geo-proximity routing.
- D. An ECS cluster of **Spot Instances**, paired with an RDS MySQL instance with a Snapshot deletion policy (no mention of Multi-AZ).

**Correct Answer: B**

**Explanation**
The standard answer pattern for "migrate an on-premises multi-tier web app to a single Region with high availability and scalability" is **ALB + EC2 Auto Scaling across 3 AZs + Multi-AZ Aurora (or RDS)**. For typical HTTP web traffic, ALB (Layer 7 routing) is the appropriate choice.

**Why the other choices are wrong**
- A: For a typical HTTP web application, **ALB is the standard choice over a Layer-4 NLB**.
- C: The requirement is single-Region high availability/scalability, not multi-Region operation — two Regions with geo-proximity routing is over-engineered.
- D: Using **Spot Instances** for production compute risks interruption, hurting reliability, and the database's lack of an explicit Multi-AZ configuration fails the high-availability requirement.

> 💡 **Exam tip**: For a typical "migrate an on-premises web app to a single Region with high availability and scalability" scenario, default to **ALB + EC2 Auto Scaling across 3 AZs + Multi-AZ Aurora/RDS**. Watch for red flags like NLB for ordinary web traffic, Spot Instances in production, or an unnecessary multi-Region design.

## QUESTION 38

**Question**: A company manages multiple accounts via AWS Organizations and needs an SNS topic created in every member account (for third-party notification integration), automated via a CloudFormation StackSet, with trusted access already enabled for the organization. What's needed to deploy the StackSet to all accounts?

**Choices**
- A. Create the stack set in a member account, use service-managed permissions, and enable drift detection.
- B. Create a stack in a member account, use self-service permissions, and enable automatic deployment.
- C. **Create the stack set in the organization's management (master) account**, use **service-managed permissions**, set the deployment target to the whole organization, and **enable automatic deployment**.
- D. Create a stack in the master account, use service-managed permissions, and enable drift detection.

**Correct Answer: C**

**Explanation**
To deploy a StackSet with service-managed permissions across the whole organization, it must be created from the **management (master) account**, and **automatic deployment** must be enabled so newly added accounts automatically receive the stack as well.

**Why the other choices are wrong**
- A, B: The premise that a stack set can be created org-wide from a member account is itself wrong — this must be done from the master account.
- D: Confuses a "stack" (single account) with a "stack set" (org-wide deployment), and "drift detection" detects out-of-band manual changes to already-deployed stacks — it's not the mechanism for automatically deploying to newly created accounts.

> 💡 **Exam tip**: To auto-deploy CloudFormation across an entire organization, you need: **create the StackSet from the management account, use service-managed permissions, and enable automatic deployment.** Don't confuse drift detection with automatic deployment.

## QUESTION 39

**Question**: A company is migrating on-premises workloads (Linux and Windows) to AWS. It needs to capture system configuration, performance, running processes, and network connection details, group applications for migration, and get cost-effective EC2 instance type recommendations. (Choose three.)

**Choices**
- A. **Install the AWS Application Discovery Agent** on physical machines and VMs to assess existing applications.
- B. Install the AWS Systems Manager Agent to assess existing applications.
- C. Use AWS Systems Manager Application Manager to group servers into applications.
- D. **Use AWS Migration Hub to group servers into applications** for migration.
- E. **Use AWS Migration Hub to generate recommended instance types and associated costs.**
- F. Import server sizing data into AWS Trusted Advisor and follow its cost optimization recommendations.

**Correct Answer: A, D, E**

**Explanation**
**AWS Application Discovery Agent** is a purpose-built tool for collecting detailed on-premises system configuration, performance, process, and network connection data (A). This data feeds into **AWS Migration Hub**, which lets you group discovered servers into applications for migration (D), and generate EC2 instance type and cost recommendations based on actual observed usage data (E).

- C: Systems Manager Application Manager is for operating applications already running in AWS, not for grouping on-premises servers for migration planning — that's Migration Hub's job (already handled by D).
- F: Trusted Advisor gives best-practice recommendations for resources already running in AWS — recommending EC2 instance types based on on-premises data is Migration Hub's role (already handled by E).

## QUESTION 40

**Question**: An image processing service runs in a VPC across 2 AZs (each with a public and private subnet). The service runs on EC2 in the private subnets, with an ALB in front and internet access via two NAT gateways. Images are stored in S3, and EC2 retrieves about 1 TB per day from the bucket. The company markets itself as very secure. Reduce cloud spend as much as possible without compromising the security posture or increasing ongoing operational time.

**Choices**
- A. Replace the NAT gateways with NAT instances.
- B. Move the EC2 instances to the public subnet and remove the NAT gateways.
- C. **Set up an S3 Gateway VPC endpoint in the VPC**, with an endpoint policy allowing the necessary S3 actions.
- D. Attach an Amazon EFS volume to the EC2 instances and host images there.

**Correct Answer: C**

**Explanation**
Currently, EC2-to-S3 traffic (about 1 TB/day) passes through the NAT gateways, incurring **NAT data processing charges**. An **S3 Gateway VPC Endpoint is free** and routes S3-bound traffic privately without going through the NAT gateway, eliminating that processing cost. Since traffic never touches the public internet, the security posture is unchanged, and the operational burden added is minimal.

**Why the other choices are wrong**
- A: Switching to NAT instances can cut cost but requires ongoing patching and management — **increasing operational overhead**, violating the "no increase in ongoing operational time" constraint.
- B: Moving EC2 to the public subnet exposes it directly to the internet, directly contradicting the "very secure" security goal.
- D: Introducing EFS is an unrelated architectural change that doesn't address the NAT/S3 traffic cost issue, adds a migration effort (operational overhead), and doesn't meaningfully reduce cost for this specific problem.

> 💡 **Exam tip**: When EC2 instances in a private subnet reach **Amazon S3** through a NAT gateway, adding a **free S3 Gateway VPC Endpoint** removes that NAT data processing cost — a classic "cut cost without compromising security" answer pattern on this exam.
