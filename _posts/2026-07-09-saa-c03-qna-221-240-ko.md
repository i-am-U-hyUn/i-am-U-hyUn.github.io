## QUESTION 221

**문제**: 한 회사가 Amazon Linux EC2 인스턴스 그룹에서 애플리케이션을 실행합니다. 규정 준수를 위해 모든 애플리케이션 로그 파일을 7년 동안 보관해야 하며, 로그 파일은 모든 파일에 동시에 접근해야 하는 보고 도구로 분석됩니다. 이러한 요구 사항을 가장 비용 효율적으로 충족하는 스토리지 솔루션은 무엇입니까?

**보기**
- A. Amazon Elastic Block Store(Amazon EBS) (특정 인스턴스에 종속된 블록 스토리지로, 여러 도구의 동시 접근을 지원하지 않고 장기 보관 비용도 상대적으로 높음)
- B. Amazon Elastic File System(Amazon EFS) (동시 접근은 가능하지만 S3 대비 스토리지 단가가 높아 7년 장기 보관에는 비용 효율이 떨어짐)
- **D. Amazon S3**
- C. Amazon EC2 인스턴스 스토어 (인스턴스 종료 시 데이터가 소멸되는 임시 스토리지로 내구성과 장기 보관 요건을 전혀 충족하지 못함)

**정답: D**

**해설**
**Amazon S3**는 사실상 무제한의 동시 접근을 지원하고, 11 9's의 내구성을 제공하며, 스토리지 클래스(S3 Standard-IA, Glacier 등)를 조합하면 장기 보관 비용을 크게 낮출 수 있습니다. 여러 클라이언트(보고 도구)가 동일한 객체를 동시에 읽을 수 있다는 점과, 수명 주기 정책으로 오래된 로그를 자동으로 저렴한 클래스로 전환할 수 있다는 점이 7년 보관 + 동시 분석이라는 요구 사항에 정확히 맞아떨어집니다.

**왜 다른 보기는 오답인가**
- A: EBS 볼륨은 기본적으로 하나의 EC2 인스턴스에만 연결되므로 여러 보고 도구의 동시 접근에 적합하지 않고, 장기 보관용으로는 S3보다 비쌉니다.
- B: EFS는 여러 인스턴스에서 동시 마운트가 가능하지만, GB당 요금이 S3보다 훨씬 높아 "가장 비용 효율적"이라는 조건을 만족하지 못합니다.
- C: 인스턴스 스토어는 휘발성 스토리지이므로 인스턴스가 종료/중지되면 데이터가 사라져 규정 준수 요건(7년 보관)을 근본적으로 충족할 수 없습니다.

> 💡 **시험 꿀팁**: "장기 보관 + 다수의 동시 읽기 접근 + 최저 비용"이라는 키워드가 나오면 S3가 표준 정답입니다.

## QUESTION 222

**문제**: 한 회사가 자사 AWS 계정에서 작업을 수행할 외부 공급업체를 고용했습니다. 공급업체는 자신들이 소유한 AWS 계정에서 호스팅되는 자동화 도구를 사용하며, 회사의 AWS 계정에 대한 IAM 접근 권한은 없습니다. 솔루션 설계자는 공급업체에 어떻게 접근 권한을 부여해야 합니까?

**보기**
- **A. 공급업체의 IAM 역할에 위임 권한을 부여하는 IAM 역할을 회사 계정에 생성하고, 공급업체가 요청한 권한에 맞는 IAM 정책을 이 역할에 연결한다**
- B. 암호 복잡성 요구 사항을 충족하는 암호로 회사 계정에 IAM 사용자를 생성하고 정책을 연결한다 (자격 증명을 외부와 공유해야 하므로 보안상 권장되지 않음)
- C. 회사 계정에 IAM 그룹을 만들고 공급업체 계정의 IAM 사용자를 그룹에 추가한다 (다른 계정의 IAM 사용자를 자사 IAM 그룹에 직접 추가하는 것은 불가능함)
- D. IAM 콘솔에서 자격 증명 공급자를 새로 만들어 공급업체 계정 ID와 사용자 이름을 등록한다 (자격 증명 공급자는 SAML/OIDC 기반 페더레이션용이며 계정 간 위임에는 적합하지 않음)

**정답: A**

**해설**
AWS 계정 간에 접근 권한을 위임하는 표준 방법은 **크로스 계정 IAM 역할(Cross-Account IAM Role)**입니다. 회사 계정에 신뢰 정책(trust policy)으로 공급업체 계정 또는 특정 역할을 신뢰 주체(principal)로 지정한 IAM 역할을 생성하고, 여기에 필요한 권한만 담은 정책을 연결하면 공급업체의 자동화 도구가 `sts:AssumeRole`을 통해 임시 자격 증명을 발급받아 작업을 수행할 수 있습니다. 이 방식은 장기 자격 증명(암호, 액세스 키)을 공유하지 않고도 최소 권한 원칙을 지킬 수 있다는 장점이 있습니다.

**왜 다른 보기는 오답인가**
- B: IAM 사용자와 암호를 만들어 공유하면 장기 자격 증명 유출 위험이 커지고, MFA·순환 관리 등 추가 부담이 발생합니다.
- C: 타 AWS 계정의 IAM 사용자를 자사 IAM 그룹의 멤버로 직접 추가하는 기능 자체가 존재하지 않습니다.
- D: IAM의 자격 증명 공급자(Identity Provider)는 SAML 2.0이나 OIDC를 사용하는 외부 ID 시스템과의 페더레이션을 위한 기능으로, 계정 간 역할 위임 시나리오와는 목적이 다릅니다.

> 💡 **시험 꿀팁**: "외부 계정에 우리 계정 접근 권한을 안전하게 위임"이라는 조건이 나오면 크로스 계정 IAM 역할(AssumeRole)이 표준 정답입니다.

## QUESTION 223

**문제**: 한 회사가 Java Spring Boot 애플리케이션을 프라이빗 서브넷의 Amazon EKS 파드로 배포했습니다. 이 애플리케이션은 Amazon DynamoDB 테이블에 데이터를 기록해야 하는데, 솔루션 설계자는 인터넷에 트래픽을 노출하지 않고 DynamoDB와 통신할 수 있도록 해야 합니다. 이 목표를 달성하려면 어떤 단계 조합을 수행해야 합니까? (2개 선택)

**보기**
- **A. 충분한 권한을 가진 IAM 역할을 EKS 파드에 연결한다**
- B. 충분한 권한을 가진 IAM 사용자를 EKS 파드에 연결한다 (IAM 사용자는 사람/애플리케이션이 콘솔·CLI로 인증하기 위한 것으로, 파드에 직접 연결하는 개념이 아님)
- C. 프라이빗 서브넷의 네트워크 ACL에서 DynamoDB로 향하는 아웃바운드를 허용한다 (네트워크 ACL 허용만으로는 트래픽이 여전히 퍼블릭 인터넷 경로를 거치므로 "인터넷 미노출" 요건을 만족 못함)
- **D. DynamoDB용 VPC 엔드포인트(게이트웨이 엔드포인트)를 생성한다**
- E. Java Spring Boot 코드에 액세스 키를 하드코딩한다 (자격 증명을 코드에 삽입하는 것은 보안 모범 사례에 정면으로 위배됨)

**정답: A, D**

**해설**
EKS 파드가 DynamoDB에 안전하게 접근하려면 두 가지가 필요합니다. 첫째, **IRSA(IAM Roles for Service Accounts)**를 통해 EKS 파드에 IAM 역할을 연결하면 장기 자격 증명 없이 임시 보안 자격 증명으로 DynamoDB API를 호출할 수 있습니다. 둘째, DynamoDB용 **VPC 게이트웨이 엔드포인트**를 생성하면 VPC 라우팅 테이블에 DynamoDB로 향하는 프라이빗 경로가 추가되어, 트래픽이 인터넷 게이트웨이나 NAT를 거치지 않고 AWS 백본 네트워크 내부에서만 이동합니다. 두 조치를 함께 적용해야 "인증"과 "네트워크 경로 차단"이라는 두 요구 사항이 동시에 충족됩니다.

**왜 다른 보기는 오답인가**
- B: IAM 사용자는 파드 단위 워크로드 자격 증명 방식이 아니며, 액세스 키 관리 부담과 유출 위험만 커집니다.
- C: 네트워크 ACL로 아웃바운드를 허용해도 기본적으로 트래픽은 퍼블릭 인터넷 경로(NAT Gateway 등)를 통해 나가므로 요구 사항(인터넷 미노출)을 해결하지 못합니다.
- E: 코드에 액세스 키를 삽입하는 것은 자격 증명 유출의 대표적 안티패턴입니다.

> 💡 **시험 꿀팁**: "쿠버네티스 파드가 인터넷 경유 없이 AWS 서비스를 호출해야 한다"는 조건이 나오면 IRSA(IAM 역할)와 VPC 엔드포인트 조합이 표준 정답입니다.

## QUESTION 224

**문제**: 한 회사가 최근 단일 AWS 리전의 EC2 인스턴스에서 웹 애플리케이션을 리호스팅하여 마이그레이션했습니다. 이제 아키텍처를 고가용성·내결함성을 갖추도록 재설계하려 하며, 트래픽은 실행 중인 모든 EC2 인스턴스에 무작위로 도달해야 합니다. 이러한 요구 사항을 충족하려면 어떤 조합의 단계를 수행해야 합니까? (2개 선택)

**보기**
- A. Amazon Route 53 장애 조치 라우팅 정책을 생성한다 (기본 리소스가 다운됐을 때만 보조 리소스로 전환하는 방식으로, 무작위 분산 목적과 다름)
- B. Amazon Route 53 가중 라우팅 정책을 생성한다 (가중치대로 분산되지만 트래픽이 균등·무작위하게 분산됨을 보장하지 않음)
- **C. Amazon Route 53 다중값 응답 라우팅 정책을 생성한다**
- D. 하나의 AZ에 2개, 다른 AZ에 1개, 총 3개의 EC2 인스턴스를 시작한다 (다중 AZ 배치는 맞지만 인스턴스 수가 홀수라 트래픽이 균등하게 분산되지 않음)
- **E. 각 AZ에 2개씩, 총 4개의 EC2 인스턴스를 시작한다**

**정답: C, E**

**해설**
**Route 53 다중값 응답(Multivalue Answer) 라우팅 정책**을 사용하면 DNS 쿼리에 대해 최대 8개의 정상 IP 주소를 무작위 순서로 반환하여, 클라이언트가 여러 리소스 중 하나에 무작위로 연결되도록 유도할 수 있습니다. 여기에 서로 다른 두 가용 영역에 각각 2개씩 총 4대의 EC2 인스턴스를 배치하면, 한 AZ에 장애가 발생해도 나머지 AZ의 인스턴스들이 트래픽을 감당할 수 있어 고가용성과 내결함성이 확보됩니다.

**왜 다른 보기는 오답인가**
- A: 장애 조치 라우팅은 페일오버(주/보조 전환)를 위한 것으로, 정상 상태에서 트래픽을 여러 인스턴스에 무작위 분산하는 요구 사항과 맞지 않습니다.
- B: 가중 라우팅은 지정한 비율대로 트래픽을 나누지만 "무작위" 분산을 보장하는 메커니즘이 아닙니다.
- D: AZ 간 배치 자체는 올바른 방향이지만, 인스턴스 3대(2:1)로는 부하가 균등하게 분산되지 않아 리소스 활용이 비효율적입니다.

> 💡 **시험 꿀팁**: "여러 리소스에 무작위로 균등 분산"이라는 조건이 나오면 Route 53 다중값 응답 라우팅 정책이 표준 정답입니다.

## QUESTION 225

**문제**: 한 미디어 회사가 온프레미스에서 수집·분석하던 사용자 활동 데이터를 AWS로 마이그레이션하려 합니다. 데이터 저장소는 계속 성장해 페타바이트 규모가 될 것이며, 회사는 SQL을 사용해 기존 데이터와 신규 데이터를 온디맨드로 분석할 수 있는 고가용성 수집 솔루션이 필요합니다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. 활동 데이터를 Amazon Kinesis Data Streams로 보내고, 스트림을 S3 버킷으로 전달하도록 구성한다 (S3에 적재된 후 SQL 온디맨드 분석을 위한 별도 처리가 추가로 필요함)
- **B. 활동 데이터를 Amazon Kinesis Data Firehose 전송 스트림으로 보내고, 데이터를 Amazon Redshift 클러스터로 전달하도록 구성한다**
- C. 활동 데이터를 S3 버킷에 적재하고, 도착 시 AWS Lambda 함수를 실행하도록 S3를 구성한다 (관리형 완전 자동 파이프라인인 Firehose+Redshift 조합보다 수동 구성·운영 부담이 큼)
- D. 여러 AZ에 분산된 EC2 인스턴스로 수집 서비스를 구축하고 RDS 다중 AZ DB로 전달한다 (EC2 인프라를 직접 프로비저닝·확장·관리해야 하므로 운영 오버헤드가 가장 큼)

**정답: B**

**해설**
**Amazon Kinesis Data Firehose**는 서버 관리 없이 스트리밍 데이터를 자동으로 확장하며 수집하는 완전관리형 서비스이고, **Amazon Redshift**는 페타바이트급으로 확장 가능한 완전관리형 데이터 웨어하우스로 표준 SQL 및 기존 BI 도구를 그대로 사용할 수 있습니다. Firehose가 데이터를 버퍼링하여 Redshift에 직접 적재하도록 구성하면, 별도의 ETL 파이프라인 구축 없이도 지속적으로 증가하는 데이터를 최소한의 운영 부담으로 수집하고 SQL로 온디맨드 분석할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Kinesis Data Streams만으로는 스트리밍 데이터를 처리해 S3에 저장할 뿐, SQL 기반 온디맨드 분석을 위한 별도 처리(예: Athena, Redshift 적재)가 추가로 필요합니다.
- C: S3+Lambda 조합은 구현 가능하지만 트리거·처리 로직을 직접 구성하고 유지보수해야 하므로 완전관리형 옵션보다 운영 부담이 큽니다.
- D: EC2와 RDS 인프라를 직접 관리해야 하므로 확장성 확보와 운영 효율성 모두에서 불리합니다.

> 💡 **시험 꿀팁**: "페타바이트급 성장 + SQL 온디맨드 분석 + 최소 운영 오버헤드"라는 조건이 나오면 Kinesis Data Firehose → Redshift 조합이 표준 정답입니다.

## QUESTION 226

**문제**: 한 회사가 EC2 인스턴스에서 실행되는 RESTful 웹 서비스로 수천 개의 원격 장치에서 데이터를 수집합니다. EC2 인스턴스는 원시 데이터를 수신·변환하여 S3 버킷에 저장하는데, 조만간 장치 수가 수백만 개로 늘어날 예정입니다. 운영 오버헤드를 최소화하면서 확장성이 뛰어난 솔루션을 만들려면 어떤 조합의 단계를 수행해야 합니까? (2개 선택)

**보기**
- **A. AWS Glue를 사용해 S3의 원시 데이터를 처리(ETL)한다**
- B. Amazon Route 53으로 트래픽을 다른 EC2 인스턴스로 라우팅한다 (DNS 라우팅만으로는 수백만 장치 규모의 수집·처리 확장 문제를 근본적으로 해결하지 못함)
- C. 들어오는 데이터양에 맞춰 EC2 인스턴스를 더 추가한다 (인스턴스를 직접 늘리고 관리해야 하므로 운영 오버헤드가 오히려 증가함)
- D. 원시 데이터를 Amazon SQS로 보내고 EC2 인스턴스로 처리한다 (SQS를 도입해도 여전히 EC2 기반 처리 로직과 인프라를 직접 관리해야 하므로 운영 부담이 남음)
- **E. Amazon API Gateway로 원시 데이터를 Kinesis Data Streams로 보내고, 이 스트림을 소스로 Kinesis Data Firehose를 구성해 S3로 전달한다**

**정답: A, E**

**해설**
"RESTful 웹 서비스"로 수백만 장치의 요청을 받아야 한다는 점에서 **Amazon API Gateway**가 완전관리형·자동 확장되는 HTTPS 엔드포인트를 제공하는 최적의 진입점이 됩니다. 수신한 원시 데이터를 **Kinesis Data Streams**로 전달하고, 이를 소스로 하는 **Kinesis Data Firehose**가 자동으로 S3에 적재하도록 구성하면 서버 프로비저닝 없이 처리량이 자동으로 확장됩니다. 이후 S3에 쌓인 원시 데이터를 정제·변환(추출-변환-적재)하는 과정은 **AWS Glue**의 서버리스 ETL 기능으로 처리해, 스키마 자동 검색과 코드 생성까지 관리형으로 해결할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: Route 53은 DNS 트래픽 분산에 특화된 서비스로, 데이터 수집·처리 파이프라인의 확장성 문제와는 직접적인 관련이 없습니다.
- C: 인스턴스를 계속 추가하는 방식은 확장할수록 관리해야 할 EC2 자원이 늘어나 운영 오버헤드가 증가합니다.
- D: SQS+EC2 조합도 동작은 하지만, EC2 처리 계층을 여전히 직접 운영·확장해야 하므로 완전관리형 스트리밍 파이프라인보다 복잡합니다.

> 💡 **시험 꿀팁**: "수백만 개 장치의 RESTful 데이터 수집 + 최소 운영 오버헤드"라는 조건이 나오면 API Gateway + Kinesis Data Streams/Firehose + Glue 조합이 표준 정답입니다.

## QUESTION 227

**문제**: 한 회사가 AWS CloudTrail 로그를 3년간 보관해야 하며, AWS Organizations의 상위 계정을 통해 여러 계정에 CloudTrail을 적용하고 있습니다. 대상 S3 버킷은 버전 관리가 활성화되어 있고, 3년 후 현재 버전 객체를 삭제하는 수명 주기 정책이 설정되어 있습니다. 그런데 4년 차 이후 버킷의 객체 수가 계속 증가하는 반면 신규 CloudTrail 로그 수는 일정하게 유지되고 있습니다. 가장 비용 효율적으로 3년이 지난 객체를 삭제하는 솔루션은 무엇입니까?

**보기**
- A. 조직의 중앙 집중식 CloudTrail 추적에서 3년 후 만료되도록 구성한다 (CloudTrail 추적 자체의 이벤트 보존 설정이 아니라 S3에 이미 쌓인 객체 삭제 문제이므로 근본 해결이 안 됨)
- **B. 현재 버전뿐 아니라 이전(비현재) 버전도 삭제하도록 S3 수명 주기 정책을 구성한다**
- C. 3년이 지난 객체를 열거하고 삭제하는 AWS Lambda 함수를 생성한다 (동작은 하지만 직접 코드를 작성·유지보수해야 하므로 관리형 수명 주기 정책보다 운영 복잡도와 비용이 높음)
- D. 상위 계정을 버킷으로 전달되는 모든 객체의 소유자로 구성한다 (객체 소유권 변경은 삭제 동작 자체에 영향을 주지 않음)

**정답: B**

**해설**
버전 관리가 활성화된 버킷에서는 객체를 "삭제"해도 실제로는 삭제 마커가 추가될 뿐, 기존 버전은 **비현재 버전(noncurrent version)**으로 남아 계속 스토리지를 차지합니다. 기존 수명 주기 정책이 현재 버전만 만료시키도록 되어 있었기 때문에, 매번 새로 생성되는 비현재 버전들이 계속 누적되어 객체 수가 늘어난 것입니다. 따라서 `NoncurrentVersionExpiration` 규칙을 추가해 비현재 버전도 일정 기간(3년) 후 자동 삭제되도록 수명 주기 정책을 수정하는 것이 추가 인프라 없이 문제를 근본적으로, 가장 저렴하게 해결하는 방법입니다.

**왜 다른 보기는 오답인가**
- A: CloudTrail 추적의 만료 설정은 이벤트 로깅 자체를 제어할 뿐, 이미 S3에 저장된 객체(특히 비현재 버전)의 삭제와는 무관합니다.
- C: Lambda로 직접 열거·삭제 로직을 구현하면 목적은 달성하지만, 정기 실행 스케줄링과 코드 유지보수 등 추가적인 운영 오버헤드와 비용이 발생합니다.
- D: 객체 소유자를 변경하는 것은 접근 제어/과금 귀속과 관련된 설정으로, 만료·삭제 동작에는 아무 영향을 주지 않습니다.

> 💡 **시험 꿀팁**: "버전 관리 버킷에서 객체 수가 계속 늘어난다"는 증상이 나오면 비현재 버전(Noncurrent Version) 만료 규칙 누락을 의심하고 수명 주기 정책에 추가하는 것이 표준 정답입니다.

## QUESTION 228

**문제**: 한 회사가 여러 모니터링 장치에서 실시간 데이터를 수신하는 API를 운영하며, 이 데이터를 Amazon RDS DB 인스턴스에 저장합니다. 장치가 보내는 데이터량은 변동이 크고, 트래픽이 몰리는 시간대에는 API가 자주 시간 초과 오류를 반환합니다. 로그를 분석한 결과 데이터베이스가 API의 쓰기 트래픽을 감당하지 못하는 것으로 확인되었습니다. 데이터베이스에 대한 연결 수를 최소화하면서 트래픽 폭주 시에도 데이터 손실이 없어야 한다면 어떤 솔루션이 적합합니까?

**보기**
- A. 메모리가 더 많은 인스턴스 유형으로 DB 인스턴스 크기를 늘린다 (메모리를 늘려도 다수의 동시 연결과 쓰기 폭주 문제 자체는 해결되지 않음)
- B. DB 인스턴스를 다중 AZ로 수정하고 모든 활성 인스턴스에 쓰도록 구성한다 (가용성은 높아지지만 쓰기 연결 수를 줄이거나 폭주를 흡수하는 방식이 아님)
- **C. 수신 데이터를 Amazon SQS 대기열에 쓰도록 API를 수정하고, SQS가 호출하는 Lambda 함수로 대기열의 데이터를 데이터베이스에 기록한다**
- D. 수신 데이터를 Amazon SNS 주제로 보내고, SNS가 호출하는 Lambda로 데이터베이스에 기록한다 (SNS는 즉시 전달을 시도하는 푸시 기반 구조라 대기열처럼 버퍼링해 폭주를 흡수하는 데는 SQS만큼 적합하지 않음)

**정답: C**

**해설**
**Amazon SQS**를 API와 데이터베이스 사이에 두면 API는 데이터를 큐에 적재하기만 하면 되므로 DB에 대한 직접 연결이 사라지고, 큐가 트래픽 폭주를 흡수하는 **버퍼** 역할을 합니다. 이후 **AWS Lambda**가 큐에서 메시지를 가져와 완만한 속도로 데이터베이스에 기록하도록 하면, 순간적인 쓰기 폭증이 있어도 메시지가 큐에 안전하게 남아 있다가 순차 처리되므로 데이터 손실 없이 DB 연결 수를 최소화할 수 있습니다. 이는 전형적인 "디커플링(decoupling)을 통한 완충" 패턴입니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스 크기를 키우면 처리 능력은 다소 개선되지만, 근본적으로 동시 쓰기 연결 수를 줄이거나 폭주를 완충하는 구조적 해법이 아닙니다.
- B: 다중 AZ는 장애 복구(자동 페일오버)를 위한 것이며, 모든 활성 인스턴스에 동시에 쓰면 오히려 연결 수와 복잡도가 늘어납니다.
- D: SNS는 구독자에게 즉시 푸시하는 메시징 서비스로 메시지를 계속 보관하는 큐가 아니므로, 처리 실패 시 재시도·순서 보장 등 버퍼링 특성이 SQS보다 약합니다.

> 💡 **시험 꿀팁**: "쓰기 폭주로 DB 연결이 과부하되고 데이터 손실 우려가 있다"는 조건이 나오면 SQS + Lambda로 디커플링하는 것이 표준 정답입니다.

**정답: C**

**해설**
**NAT 게이트웨이**는 AWS가 완전관리형으로 제공하는 아웃바운드 NAT 서비스로, 대역폭에 따라 자동으로 확장되며 별도의 용량 관리가 필요 없습니다. 각 가용 영역마다 독립된 NAT 게이트웨이를 배치하고, 해당 AZ의 서브넷이 자신의 AZ에 있는 NAT 게이트웨이를 사용하도록 라우팅 테이블을 구성하면, 한 AZ에 장애가 발생해도 다른 AZ의 리소스는 영향을 받지 않는 AZ 독립적 아키텍처가 완성됩니다. 이는 NAT 인스턴스를 직접 운영·확장하는 것보다 훨씬 적은 운영 부담으로 고가용성과 자동 확장을 동시에 달성하는 방법입니다.

**왜 다른 보기는 오답인가**
- A: 두 NAT 게이트웨이를 같은 AZ에 두면 해당 AZ 장애 시 아웃바운드 경로 전체가 끊겨 내결함성 요건을 충족하지 못합니다.
- B: NAT 인스턴스는 사용자가 직접 크기·이중화를 관리해야 하는 EC2 기반 솔루션으로, 관리형 NAT 게이트웨이 대비 확장성과 가용성 확보가 번거롭고 권장되지 않습니다.
- D: 스팟 인스턴스는 용량 부족 시 언제든 회수될 수 있어, 지속적인 가용성이 요구되는 NAT와 같은 핵심 네트워크 구성 요소에는 적합하지 않습니다.

> 💡 **시험 꿀팁**: "NAT의 고가용성/자동 확장"이 요구되면 NAT 인스턴스가 아니라 여러 AZ에 하나씩 배치한 NAT 게이트웨이가 표준 정답입니다.

**문제**: 한 회사가 EC2 인스턴스에서 고객용 데모 환경을 운영하며 각 환경은 자체 VPC로 격리되어 있습니다. 환경에 대한 RDP 또는 SSH 접근이 발생하면 즉시 운영팀에 알려야 합니다. 이 요구 사항을 충족하는 솔루션은 무엇입니까?

- A. RDP/SSH 접근이 감지되면 AWS Systems Manager OpsItems를 생성하도록 Amazon CloudWatch Application Insights를 구성한다 (Application Insights는 애플리케이션 성능 이상을 감지하는 용도로, RDP/SSH 접근 자체를 탐지하도록 설계되지 않음)
- B. AmazonSSMManagedInstanceCore 정책이 연결된 IAM 인스턴스 프로필로 EC2를 구성한다 (Systems Manager 사용을 가능하게 할 뿐, RDP/SSH 접근 발생 시 알림을 보내는 기능이 아님)
- **C. VPC 흐름 로그를 CloudWatch Logs에 게시하고, 필요한 지표 필터를 생성한 뒤, 경보가 ALARM 상태가 되면 알림을 보내는 CloudWatch 지표 경보를 생성한다**
- D. EC2 인스턴스 상태 변경 알림 이벤트를 수신하는 EventBridge 규칙을 만들고 SNS 주제를 대상으로 구성해 운영팀을 구독시킨다 (인스턴스 시작/중지 등 상태 변경만 감지할 뿐 RDP/SSH 포트로의 접근 자체는 탐지하지 못함)

**왜 다른 보기는 오답인가**

- B: SSM Agent용 인스턴스 프로필 구성은 Systems Manager 기능(세션 관리 등) 사용을 위한 전제 조건일 뿐, RDP/SSH 접근 탐지·알림과는 무관합니다.
- D: EC2 상태 변경 알림은 인스턴스의 시작·중지·종료 같은 라이프사이클 이벤트를 다룰 뿐, 로그인 시도나 포트 접근 여부는 알려주지 않습니다.

> 💡 **시험 꿀팁**: "특정 포트/트래픽 패턴이 감지되면 알림"이라는 요구 사항이 나오면 VPC 흐름 로그 → CloudWatch Logs 지표 필터 → 지표 경보 조합이 표준 정답입니다.

## QUESTION 233

**문제**: 솔루션 설계자가 새 AWS 계정을 생성했고 AWS 계정 루트 사용자의 접근을 보호해야 합니다. 어떤 작업 조합이 이를 달성합니까? (2개 선택)

**보기**
- **A. 루트 사용자가 강력한 암호를 사용하도록 한다**
- **B. 루트 사용자에 대해 다단계 인증(MFA)을 활성화한다**
- C. 암호화된 S3 버킷에 루트 사용자 액세스 키를 저장한다 (루트 사용자 액세스 키는 애초에 발급·사용을 피하는 것이 권장 사례임)
- D. 관리 권한이 포함된 그룹에 루트 사용자를 추가한다 (루트 사용자는 이미 모든 권한을 가지고 있어 불필요하며 오히려 오남용 위험만 커짐)
- E. 인라인 정책 문서로 루트 사용자에게 필요한 권한을 적용한다 (루트 사용자에게는 권한을 제한할 수 없고, 애초에 일상 업무는 IAM 사용자로 수행해야 함)

**왜 다른 보기는 오답인가**
- C: 루트 사용자 액세스 키는 발급 자체를 피하는 것이 권장되며, S3에 암호화해 저장한다고 해서 근본적인 위험(장기 자격 증명 존재)이 사라지지 않습니다.
- D: 루트 사용자는 이미 모든 권한을 보유하고 있어 추가 그룹 권한 부여는 의미가 없고, 관리 관행상 지양해야 할 접근입니다.
- E: 루트 사용자에게는 권한을 제한하는 정책을 적용할 수 없으며, 애초에 권한이 필요한 작업은 IAM 사용자/역할로 위임하는 것이 표준입니다.

> 💡 **시험 꿀팁**: "루트 사용자 보호"라는 키워드가 나오면 강력한 암호 + MFA 활성화, 그리고 일상 업무는 IAM 사용자/역할로 전환하는 것이 표준 정답 패턴입니다.

## QUESTION 234

**문제**: 한 회사가 새로운 웹 기반 CRM 애플리케이션을 구축 중입니다. 이 애플리케이션은 Application Load Balancer(ALB) 뒤에서 EBS 볼륨을 사용하는 여러 EC2 인스턴스와 Amazon Aurora 데이터베이스를 사용합니다. 애플리케이션의 모든 데이터는 저장 시(at rest)와 전송 중(in transit) 모두 암호화되어야 합니다. 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. ALB에서 AWS KMS 인증서로 전송 중 데이터를 암호화하고, ACM으로 EBS·Aurora 저장 데이터를 암호화한다 (KMS는 인증서가 아닌 키를 제공하며, ACM은 암호화 기능이 아닌 인증서 발급 기능만 제공하므로 역할이 뒤바뀜)
- B. 루트 계정으로 로그인해 회사의 암호화 인증서를 업로드하고, 계정 전체의 저장/전송 데이터 암호화를 한 번에 켜는 옵션을 선택한다 (그런 전역 스위치는 존재하지 않으며 루트 계정 상시 사용도 보안상 권장되지 않음)
- **C. AWS KMS로 EBS 볼륨과 Aurora 스토리지의 저장 데이터를 암호화하고, ALB에 ACM 인증서를 연결해 전송 중 데이터를 암호화한다**
- D. BitLocker로 저장 데이터를 암호화하고 회사의 TLS 인증서 키를 KMS로 가져와 ALB에 연결한다 (BitLocker는 Windows 전용 기능으로 Linux 기반 Aurora 스토리지 암호화에 적용할 수 없음)

**정답: C**

**해설**
저장 데이터 암호화는 **AWS KMS**가 관리하는 키로 EBS 볼륨과 Aurora 스토리지를 암호화하는 것이 표준 방법이며, 활성화 시 AWS가 투명하게 암복호화를 처리합니다. 전송 중 데이터 암호화는 **AWS Certificate Manager(ACM)**에서 발급받은 TLS/SSL 인증서를 **ALB**에 연결해 클라이언트-ALB 구간에 HTTPS를 적용하는 방식으로 해결합니다. 즉 "저장 데이터=KMS, 전송 중 데이터=ACM+ALB"라는 역할 분담이 정확히 이 시나리오의 요구 사항(저장/전송 모두 암호화)을 충족시킵니다.

**왜 다른 보기는 오답인가**
- A: KMS는 암호화 키만 제공하고 TLS 인증서를 발급하지 않으며, ACM은 반대로 인증서만 제공할 뿐 EBS/Aurora 저장 데이터를 암호화하는 기능이 없어 역할이 서로 바뀌어 있습니다.
- B: "계정 전체 암호화 켜기"라는 단일 전역 옵션은 AWS에 존재하지 않으며, 암호화는 서비스·리소스별로 개별 설정해야 합니다. 또한 루트 계정 상시 사용은 보안 모범 사례에 어긋납니다.
- D: BitLocker는 Windows 볼륨 암호화 기능으로, Aurora는 AWS가 관리하는 리눅스 기반 인프라 위에서 동작하므로 적용할 수 없고, ALB에는 인증서가 필요하지 KMS 키 자체를 직접 연결할 수 없습니다.

> 💡 **시험 꿀팁**: "저장 데이터 암호화는 KMS, 전송 중 데이터 암호화(HTTPS)는 ACM 인증서를 ALB/CloudFront에 연결"이라는 조합이 표준 정답 패턴입니다.

- A. 초기 마이그레이션에 AWS DataSync를 사용하고, DMS로 CDC 복제 작업 및 모든 테이블에 대한 테이블 매핑만 생성한다 (DataSync는 파일/객체 데이터 전송용 서비스로 이기종 DB 스키마 변환 및 초기 전체 로드에 적합하지 않음)
- B. 초기 마이그레이션에 AWS DataSync를 사용하고, DMS로 전체 로드 + CDC 복제 작업과 모든 테이블 매핑을 생성한다 (DataSync 자체가 관계형 DB 마이그레이션에 적합한 도구가 아님)
- **C. AWS SCT와 메모리 최적화 복제 인스턴스를 사용하는 AWS DMS로 전체 로드 + CDC 복제 작업과 모든 테이블에 대한 테이블 매핑을 생성한다**
- D. AWS SCT와 컴퓨팅 최적화 복제 인스턴스를 사용하는 AWS DMS로 전체 로드 + CDC 복제 작업을 생성하되 가장 큰 테이블만 매핑한다 (컴퓨팅 최적화 인스턴스는 대량 읽기·쓰기 처리에 불리하고, 일부 테이블만 매핑하면 같은 테이블에 쓰는 다른 애플리케이션의 데이터가 누락됨)

**정답: C**

**해설**
Oracle에서 Aurora PostgreSQL로의 이기종 마이그레이션에서는 먼저 **AWS Schema Conversion Tool(SCT)**로 스키마와 코드 객체를 PostgreSQL 호환 형태로 변환해야 합니다. 이후 **AWS DMS**의 **전체 로드(Full Load) + CDC(변경 데이터 캡처)** 복제 작업을 구성하면 초기 데이터 이전과 함께 이후 발생하는 변경 사항이 지속적으로 Aurora PostgreSQL에 반영되어, 여러 애플리케이션이 순차적으로 이전되는 동안에도 두 데이터베이스가 계속 동기화됩니다. 읽기·쓰기 트래픽이 많은 상황이므로 처리량과 메모리 사용량이 큰 CDC 작업의 성능을 고려해 **메모리 최적화(Memory Optimized) 복제 인스턴스**를 사용하는 것이 권장되며, 같은 테이블에 여러 앱이 쓰는 만큼 "모든 테이블"을 매핑에 포함해야 데이터 정합성이 보장됩니다.

**왜 다른 보기는 오답인가**
- A, B: AWS DataSync는 주로 파일·객체 스토리지 간 데이터 전송에 특화된 서비스로, 관계형 데이터베이스의 스키마 변환과 초기 적재·지속 복제에는 적합하지 않습니다. 이 시나리오에는 SCT+DMS 조합이 필요합니다.
- D: 컴퓨팅 최적화 인스턴스는 CPU 집약적 작업에 유리하지만 대량의 읽기·쓰기가 발생하는 CDC 복제에는 메모리 최적화 인스턴스가 더 적합하며, 가장 큰 테이블만 매핑하면 같은 테이블에 쓰는 다른 애플리케이션의 데이터가 동기화에서 빠지게 됩니다.

> 💡 **시험 꿀팁**: "이기종 DB 마이그레이션(Oracle→PostgreSQL 등) + 지속적 동기화"라는 조건이 나오면 SCT(스키마 변환)+DMS 전체 로드/CDC 조합이 표준 정답이며, 읽기·쓰기 부하가 크면 메모리 최적화 복제 인스턴스를 선택합니다.

## QUESTION 236

**문제**: 한 회사가 이미지 공유를 위한 3계층 애플리케이션을 운영합니다. 프런트엔드 계층, 애플리케이션 계층, MySQL 데이터베이스 계층이 각각 별도의 EC2 인스턴스로 구성되어 있습니다. 솔루션 설계자는 애플리케이션에 최소한의 변경만으로 확장 가능하고 고가용성을 갖춘 솔루션을 설계해야 합니다. 어떤 솔루션이 이 요구 사항을 충족합니까?

**보기**
- A. S3로 프런트엔드를 호스팅하고, 애플리케이션 계층에 Lambda를 사용하며, DB를 DynamoDB로 이전한다 (Lambda·DynamoDB로의 전환은 애플리케이션 로직과 DB 접근 코드를 대폭 재작성해야 하므로 "최소 변경" 요건에 어긋남)
- B. 프런트엔드와 애플리케이션 계층에 로드 밸런싱된 다중 AZ Elastic Beanstalk 환경을 사용하고, DB는 읽기 전용 복제본이 있는 RDS 인스턴스로 이전해 사용자 이미지를 서비스한다 (이미지 서빙을 RDS로 처리하는 것은 S3보다 비효율적이며 이미지 저장에 적합하지 않음)
- C. S3로 프런트엔드를 호스팅하고, 애플리케이션 계층에 Auto Scaling 그룹의 EC2 플릿을 사용하며, DB를 메모리 최적화 인스턴스로 이전해 이미지를 저장·서비스한다 (프런트엔드를 S3로 옮기는 것 자체가 아키텍처 변경을 요구하고, DB에 이미지를 저장하는 것은 비효율적임)
- **D. 프런트엔드와 애플리케이션 계층에 로드 밸런싱된 다중 AZ Elastic Beanstalk 환경을 사용하고, DB는 RDS 다중 AZ 인스턴스로 이전하며, 사용자 이미지는 S3에 저장·서비스한다**

**정답: D**

**해설**
**AWS Elastic Beanstalk**의 로드 밸런싱·다중 AZ 환경을 사용하면 기존 EC2 기반 프런트엔드/애플리케이션 코드를 거의 그대로 배포하면서 오토스케일링과 고가용성을 자동으로 얻을 수 있습니다. 데이터베이스는 **RDS 다중 AZ**로 전환해 자동 장애 조치와 고가용성을 확보하되, 엔진(MySQL 호환)은 유지되므로 애플리케이션의 DB 접근 코드를 바꿀 필요가 없습니다. 여기에 이미지 파일 자체는 데이터베이스가 아닌 **Amazon S3**에 저장·서비스하도록 하면, 대용량 정적 콘텐츠를 확장성 있고 저렴하게 처리할 수 있어 전체적으로 "최소 변경 + 확장성 + 고가용성" 요구를 모두 만족합니다.

**왜 다른 보기는 오답인가**
- A: 서버리스(Lambda)와 NoSQL(DynamoDB)로의 전환은 애플리케이션 로직과 데이터 접근 계층을 크게 재작성해야 하므로 "최소한의 변경" 조건에 위배됩니다.
- B: 이미지 같은 대용량 바이너리 데이터를 RDS(관계형 DB)에서 서비스하는 것은 S3에 저장·서비스하는 것보다 비용·성능 면에서 비효율적입니다.
- C: 프런트엔드를 S3 정적 호스팅으로 옮기려면 애플리케이션 아키텍처를 상당 부분 수정해야 하고, 이미지를 메모리 최적화 DB 인스턴스에 저장하는 것도 적절한 스토리지 전략이 아닙니다.

> 💡 **시험 꿀팁**: "기존 EC2 3계층 애플리케이션을 최소 변경으로 확장 가능·고가용성 있게"라는 조건이 나오면 Elastic Beanstalk(다중 AZ, 로드밸런싱) + RDS 다중 AZ + S3(정적 콘텐츠) 조합이 표준 정답입니다.

## QUESTION 237

**문제**: VPC-A의 EC2 인스턴스에서 실행되는 애플리케이션이 VPC-B의 다른 EC2 인스턴스에 있는 파일에 접근해야 합니다. 두 VPC는 서로 다른 AWS 계정에 있습니다. 네트워크 관리자는 단일 장애 지점이나 대역폭 문제가 없는 안전한 접근 솔루션을 설계해야 합니다. 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- **A. VPC-A와 VPC-B 사이에 VPC 피어링 연결을 설정한다**
- B. VPC-B에서 실행되는 EC2 인스턴스에 대한 VPC 게이트웨이 엔드포인트를 설정한다 (게이트웨이 엔드포인트는 S3·DynamoDB 같은 AWS 서비스 접근용으로, EC2 인스턴스 간 통신용 기능이 아님)
- C. 가상 프라이빗 게이트웨이를 VPC-B에 연결하고 VPC-A에서 라우팅을 설정한다 (가상 프라이빗 게이트웨이는 온프레미스와의 VPN 연결용으로, VPC 간 연결에는 적합하지 않고 복잡성만 늘어남)
- D. VPC-B의 EC2 인스턴스에 대한 프라이빗 가상 인터페이스(VIF)를 생성하고 VPC-A에서 경로를 추가한다 (프라이빗 VIF는 Direct Connect로 온프레미스와 VPC를 연결할 때 쓰는 개념으로, 두 VPC 간 직접 통신 시나리오에는 해당하지 않음)

**정답: A**

**해설**
**VPC 피어링 연결**은 같은 계정이든 다른 계정이든, 같은 리전이든 다른 리전이든 두 VPC 간에 AWS의 기존 네트워크 인프라를 활용해 직접 연결을 생성합니다. 게이트웨이나 VPN 장비, 별도의 물리적 하드웨어를 거치지 않으므로 단일 장애 지점이 존재하지 않고, 대역폭도 인스턴스 자체의 네트워크 성능에 따라 결정되어 병목이 발생하지 않습니다. 따라서 계정이 다른 VPC-A와 VPC-B 사이의 EC2 인스턴스 간 통신에는 VPC 피어링이 가장 적합합니다.

**왜 다른 보기는 오답인가**
- B: VPC 게이트웨이 엔드포인트는 S3, DynamoDB처럼 특정 AWS 서비스에 인터넷 경유 없이 접근하기 위한 기능으로, EC2 인스턴스 간의 통신 경로를 만들어주지 않습니다.
- C: 가상 프라이빗 게이트웨이는 Site-to-Site VPN으로 온프레미스 네트워크와 VPC를 연결할 때 사용하는 구성 요소로, 이를 VPC 간 연결에 억지로 적용하면 복잡성과 잠재적 장애 지점만 늘어납니다.
- D: 프라이빗 가상 인터페이스(VIF)는 AWS Direct Connect를 통해 온프레미스와 VPC를 연결할 때 사용하는 개념으로, 별도 계정의 두 VPC 간 통신 시나리오와는 무관합니다.

> 💡 **시험 꿀팁**: "서로 다른(혹은 같은) 계정의 VPC 간에 단일 장애 지점 없이 직접 통신"이라는 조건이 나오면 VPC 피어링 연결이 표준 정답입니다.

> 💡 **시험 꿀팁**: "계정/서비스별 사용량이 임계값을 초과하면 알림을 받고 싶다"는 조건이 나오면 AWS Budgets + SNS 조합이 가장 비용 효율적인 표준 정답입니다.

- B. 함수에 Lambda 함수 URL을 생성하고 인증 유형으로 AWS_IAM을 지정한다 (IAM 인증은 가능하지만 요청 유효성 검사, 스로틀링 등 API Gateway가 제공하는 관리 기능이 빠져 있음)
- C. CloudFront 배포를 생성하고 함수를 Lambda@Edge에 배포한 뒤 IAM 인증 로직을 직접 통합한다 (엣지에서 커스텀 인증 로직을 직접 구현해야 하므로 관리형 IAM 인증보다 복잡도가 큼)
- D. CloudFront 배포를 생성하고 CloudFront Functions에 함수를 배포한 뒤 인증 유형으로 AWS_IAM을 지정한다 (CloudFront Functions는 경량 엣지 로직용으로 Go 런타임 자체를 지원하지 않고 IAM 인증 유형 지정 기능도 없음)

**정답: A**

**해설**
**Amazon API Gateway REST API**는 HTTPS 엔드포인트 정의, 요청 라우팅, 그리고 **IAM 인증(Authorization: AWS_IAM)** 활성화를 기본 기능으로 제공합니다. 메서드를 Lambda 함수와 프록시 통합하고 IAM 인증을 켜면, 클라이언트는 SigV4로 서명된 요청만 보낼 수 있고 API Gateway가 자동으로 서명을 검증합니다. 요청 유효성 검사, 스로틀링, 사용량 계획(Usage Plan) 등 API Gateway의 관리형 기능을 추가 구성 없이 그대로 활용할 수 있어 운영 효율성이 가장 높습니다.

**왜 다른 보기는 오답인가**
- B: Lambda 함수 URL도 AWS_IAM 인증 유형을 지원하지만, API Gateway의 요청 검증·속도 제한·API 키 관리 같은 부가 기능이 없어 상대적으로 기능이 제한적입니다.
- C: Lambda@Edge에서 인증 로직을 직접 구현하려면 개발자가 코드 수준에서 SigV4 검증을 처리해야 하므로 관리형 IAM 인증보다 복잡하고 유지보수 부담이 큽니다.
- D: CloudFront Functions는 매우 가벼운 JavaScript 기반 엣지 로직만 지원하며 Go 런타임이나 AWS_IAM 인증 유형 지정 자체를 지원하지 않습니다.

> 💡 **시험 꿀팁**: "HTTPS 엔드포인트 + IAM 인증 + Lambda 백엔드"라는 조건이 나오면 API Gateway REST API + IAM 인가(Authorization: AWS_IAM) 조합이 표준 정답입니다.

## QUESTION 240

**문제**: 한 회사가 이전에 데이터 웨어하우스 솔루션을 AWS로 마이그레이션했고, AWS Direct Connect 연결도 보유하고 있습니다. 본사 사용자는 시각화 도구로 데이터 웨어하우스를 쿼리하며, 쿼리 결과의 평균 크기는 50MB, 시각화 도구가 보내는 각 웹 페이지는 약 500KB입니다. 쿼리 결과는 캐시되지 않습니다. 가장 낮은 데이터 전송(송신) 비용을 제공하는 솔루션은 무엇입니까?

**보기**
- A. 시각화 도구를 온프레미스에서 호스팅하고 인터넷을 통해 직접 데이터 웨어하우스를 쿼리한다 (모든 쿼리 결과가 인터넷 송신 데이터 전송 요금에 노출되어 비용이 가장 큼)
- B. 데이터 웨어하우스와 동일한 리전에서 시각화 도구를 호스팅하되 인터넷으로 접근한다 (같은 리전이어도 인터넷 경유 접근이므로 각 쿼리 결과에 여전히 인터넷 송신 요금이 부과됨)
- C. 시각화 도구를 온프레미스에서 호스팅하고 동일 리전의 Direct Connect 위치를 통해 데이터 웨어하우스를 직접 쿼리한다 (Direct Connect 경유로 인터넷 요금은 줄지만, 온프레미스로 나가는 모든 쿼리 결과(50MB 단위)에 대해 여전히 DX 데이터 전송 요금이 발생함)
- **D. 데이터 웨어하우스와 동일한 리전에서 시각화 도구를 호스팅하고, 동일 리전의 Direct Connect 위치를 통해 접근한다**

**정답: D**

**해설**
데이터 전송 비용은 트래픽이 AWS 리전 경계를 벗어날 때 발생합니다. 시각화 도구를 데이터 웨어하우스와 **같은 리전 내부**에서 호스팅하면 쿼리 결과(평균 50MB, 캐시되지 않아 매번 재전송)가 리전을 벗어나지 않고 오가므로 리전 간·인터넷 송신 요금이 아예 발생하지 않습니다. 여기에 사용자가 보는 웹 페이지(약 500KB, 상대적으로 훨씬 작은 트래픽)만 **Direct Connect**를 통해 본사로 전달하면 되므로, 전체적으로 가장 저렴하면서도 지연 시간이 짧고 대역폭이 안정적인 구성이 됩니다.

**왜 다른 보기는 오답인가**
- A: 온프레미스에서 인터넷으로 데이터 웨어하우스를 직접 쿼리하면 50MB에 달하는 모든 쿼리 결과가 인터넷 송신 요금 대상이 되어 비용이 가장 큽니다.
- B: 같은 리전에 있어도 인터넷을 통해 접근하면 쿼리 결과가 리전 경계를 넘나드는 인터넷 트래픽으로 처리되어 여전히 송신 요금이 발생합니다.
- C: Direct Connect를 사용해 인터넷 요금은 피할 수 있지만, 크기가 큰 쿼리 결과(50MB)가 매번 온프레미스로 전송되므로 상대적으로 작은 웹 페이지(500KB)만 오가는 D안보다 데이터 전송량과 비용이 훨씬 큽니다.

> 💡 **시험 꿀팁**: "무거운 데이터(쿼리 결과)와 가벼운 데이터(화면 표시용)를 구분해 전송 비용을 최소화"하려면 무거운 처리는 데이터가 있는 리전 내부에서 끝내고, 가벼운 결과만 Direct Connect로 외부에 전달하는 구조가 표준 정답입니다.
