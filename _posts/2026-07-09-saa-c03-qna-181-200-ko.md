## QUESTION 181

**문제**: 회사에 Amazon EC2 인스턴스에서 실행되는 레거시 데이터 처리 애플리케이션이 있다. 데이터는 순차적으로 처리되지만 결과의 순서는 중요하지 않다. 애플리케이션은 모놀리식 아키텍처를 사용하며, 회사가 수요 증가에 맞춰 확장할 수 있는 유일한 방법은 인스턴스 크기를 늘리는 것뿐이다. 개발자는 Amazon ECS에서 마이크로서비스 아키텍처로 애플리케이션을 다시 작성하기로 했다. 솔루션 설계자는 마이크로서비스 간 통신을 위해 무엇을 권장해야 하는가?

**보기**
- A. **Amazon SQS 대기열을 생성한다. 데이터 생산자에 코드를 추가해 대기열로 데이터를 보내고, 데이터 소비자에 코드를 추가해 대기열의 데이터를 처리한다.**
- B. Amazon SNS 주제를 생성한다. 데이터 생산자가 주제에 알림을 게시하고, 데이터 소비자가 주제를 구독한다(구독자가 없거나 처리에 실패하면 메시지가 유실될 수 있어 버퍼링·재처리 목적에는 부적합).
- C. 메시지를 전달할 AWS Lambda 함수를 생성한다. 데이터 생산자가 데이터 객체로 Lambda 함수를 동기 호출하고, 데이터 소비자가 그 결과를 수신한다(동기 호출은 생산자와 소비자를 강하게 결합시켜 소비자 장애나 지연에 그대로 영향을 받음).
- D. Amazon DynamoDB 테이블을 생성하고 DynamoDB 스트림을 활성화한다. 데이터 생산자가 테이블에 항목을 삽입하고, 데이터 소비자가 스트림 API로 새 항목을 감지·조회한다(단순 큐잉 용도로 쓰기엔 설계와 운영이 과도하게 복잡함).

**정답: A**

**해설**
**Amazon SQS**는 완전관리형 메시지 큐 서비스로, 생산자와 소비자를 시간적으로 분리(decoupling)해 한쪽의 장애나 처리 지연이 다른 쪽에 즉시 전파되지 않게 합니다. 메시지 순서가 중요하지 않은 이번 요구 사항에는 표준 큐로 충분하며, 소비자가 처리 가능한 속도로 폴링해 가져가므로 마이크로서비스 아키텍처로 전환할 때 서비스 간 결합도를 낮추는 표준적인 방법입니다.

**왜 다른 보기는 오답인가**
- B: SNS는 발행-구독(pub/sub) 알림 서비스로, 순서 보장이나 소비자 처리 완료 전까지 메시지를 보관하는 큐잉 개념이 없어 처리 실패 시 데이터 유실 위험이 있습니다.
- C: Lambda 직접 호출은 생산자가 소비자의 가용성과 응답 속도에 직접 의존하게 만들어 마이크로서비스 분리라는 목적에 어긋납니다.
- D: DynamoDB 스트림은 테이블 변경 이력을 캡처하는 메커니즘이지 범용 작업 큐가 아니며, 이 용도로는 불필요하게 복잡합니다.

> 💡 **시험 꿀팁**: "생산자-소비자를 분리하고 순서는 중요하지 않다"는 조건이 나오면 **Amazon SQS**가 표준 정답입니다.

## QUESTION 182

**문제**: 회사에서 MySQL 데이터베이스를 온프레미스에서 AWS로 마이그레이션하려 한다. 최근 비즈니스에 큰 영향을 미친 데이터베이스 중단을 겪었기 때문에, 데이터 손실을 최소화하고 모든 트랜잭션을 최소 두 개의 노드에 저장하는 안정적인 AWS 데이터베이스 솔루션을 원한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. 3개의 가용 영역에 있는 3개의 노드에 대한 동기식 복제로 Amazon RDS DB 인스턴스를 생성한다(RDS Multi-AZ는 기본적으로 프라이머리와 하나의 대기 인스턴스, 즉 2개 노드 구성이며 3개 AZ 동기 복제는 RDS의 표준 동작 방식이 아님).
- B. **다중 AZ 기능이 활성화된 Amazon RDS MySQL DB 인스턴스를 생성해 데이터를 동기식으로 복제한다.**
- C. Amazon RDS MySQL DB 인스턴스를 생성한 뒤 별도 리전에서 데이터를 동기식으로 복제하는 읽기 전용 복제본을 생성한다(RDS 읽기 전용 복제본은 비동기 복제 방식이라 요구 사항인 "동기식 복제"를 충족하지 못함).
- D. Amazon RDS MySQL DB 인스턴스에 동기식으로 복제하기 위해 AWS Lambda 함수를 트리거하는, MySQL 엔진이 설치된 Amazon EC2 인스턴스를 생성한다(직접 구축한 복제 파이프라인은 운영 부담이 크고 동기 복제와 자동 장애 조치를 보장하지 않음).

**정답: B**

**해설**
**Amazon RDS Multi-AZ**는 프라이머리 DB 인스턴스의 데이터를 다른 가용 영역의 대기(standby) 인스턴스에 동기식으로 복제하여, 트랜잭션이 커밋되는 즉시 두 개의 노드에 저장되도록 보장합니다. 장애가 감지되면 RDS가 수동 개입 없이 자동으로 대기 인스턴스로 장애 조치하므로, 데이터 손실 최소화와 안정성이라는 두 요구 사항을 동시에 충족합니다.

**왜 다른 보기는 오답인가**
- A: RDS Multi-AZ는 프라이머리와 대기 인스턴스 한 쌍(2개 노드) 구조이며, 3개 AZ에 걸친 3노드 동기 복제라는 옵션 자체가 RDS MySQL의 표준 아키텍처가 아닙니다.
- C: 읽기 전용 복제본으로의 복제는 비동기식이라 프라이머리 장애 시 최신 트랜잭션 일부가 유실될 수 있습니다.
- D: EC2에 직접 구축한 복제 파이프라인은 자동 장애 조치, 동기 복제 보장, 패치·백업 관리를 모두 회사가 직접 책임져야 해 운영 부담이 큽니다.

> 💡 **시험 꿀팁**: "트랜잭션을 최소 두 노드에 동기식으로 저장 + 자동 장애 조치"라는 조건에는 **RDS Multi-AZ**가 표준 정답입니다.

## QUESTION 183

**문제**: 회사가 새로운 동적 주문 웹사이트를 구축하고 있다. 서버 유지 관리와 패치를 최소화하고 싶고, 웹사이트는 가용성이 높아야 하며 사용자 수요 변화에 맞춰 읽기 및 쓰기 용량을 가능한 한 빨리 확장해야 한다. 이 요구 사항을 충족하는 솔루션은?

**보기**
- A. **Amazon S3에서 정적 콘텐츠를 호스팅한다. Amazon API Gateway와 AWS Lambda로 동적 콘텐츠를 처리한다. 데이터베이스에는 온디맨드 용량의 Amazon DynamoDB를 사용한다. Amazon CloudFront로 웹사이트 콘텐츠를 제공한다.**
- B. Amazon S3에서 정적 콘텐츠를 호스팅한다. API Gateway와 Lambda로 동적 콘텐츠를 처리한다. 데이터베이스에는 Aurora Auto Scaling과 함께 Amazon Aurora를 사용한다. CloudFront로 콘텐츠를 제공한다(Aurora Auto Scaling은 읽기 전용 복제본 수를 자동 조정하는 기능으로, 쓰기 용량 자체를 즉시 확장하지는 못함).
- C. Amazon EC2 인스턴스에서 모든 콘텐츠를 호스팅하고 Auto Scaling 그룹과 ALB로 트래픽을 분산한다. 데이터베이스에는 프로비저닝된 쓰기 용량의 DynamoDB를 사용한다(EC2 서버 운영·패치가 그대로 남아 "서버 유지 관리 최소화" 요구에 어긋나고, 프로비저닝 용량은 즉각적인 확장에 온디맨드보다 불리함).
- D. Amazon EC2 인스턴스에서 모든 콘텐츠를 호스팅하고 Auto Scaling 그룹과 ALB로 트래픽을 분산한다. 데이터베이스에는 Aurora Auto Scaling과 함께 Amazon Aurora를 사용한다(EC2 기반이라 서버 관리 부담이 남고, Aurora Auto Scaling은 읽기 확장 위주라 쓰기 용량의 신속한 확장에는 한계가 있음).

**정답: A**

**해설**
서버리스 조합인 **S3 + API Gateway + Lambda**는 별도의 서버 프로비저닝이나 패치 작업 없이 정적/동적 콘텐츠를 모두 처리할 수 있어 운영 오버헤드를 최소화합니다. **DynamoDB 온디맨드 모드**는 트래픽 변화에 따라 읽기·쓰기 용량을 즉시 자동으로 확장하므로, 용량 계획 없이도 가용성 높은 주문 데이터 처리가 가능합니다. CloudFront는 전 세계 사용자에게 낮은 지연으로 콘텐츠를 전달합니다.

**왜 다른 보기는 오답인가**
- B: Aurora Auto Scaling은 읽기 전용 복제본의 수를 늘리거나 줄이는 기능으로, 쓰기 용량을 즉각적으로 확장하는 문제의 핵심 요구를 충족하지 못합니다.
- C: EC2 기반 아키텍처는 인스턴스 패치·유지 관리가 필요해 "서버 유지 관리 최소화" 조건에 부합하지 않으며, 프로비저닝된 용량은 예측 못한 수요 급증에 즉시 대응하기 어렵습니다.
- D: C와 마찬가지로 EC2 운영 부담이 남고, Aurora Auto Scaling 역시 쓰기 확장에는 한계가 있습니다.

> 💡 **시험 꿀팁**: "서버 관리 최소화 + 읽기·쓰기 용량을 즉시 확장"이라는 조합에는 **DynamoDB 온디맨드 모드**가 표준 정답입니다.

## QUESTION 184

**문제**: 회사에 소프트웨어 엔지니어링용 AWS 계정이 있고, 한 쌍의 AWS Direct Connect 연결로 온프레미스 데이터 센터에 접근한다. 모든 비-VPC 트래픽은 가상 프라이빗 게이트웨이로 라우팅된다. 개발팀이 콘솔에서 생성한 AWS Lambda 함수가 회사 데이터 센터의 프라이빗 서브넷에서 실행되는 데이터베이스에 접근할 수 있어야 한다. 이 요구 사항을 충족하는 솔루션은?

**보기**
- A. **적절한 보안 그룹을 사용해 VPC에서 실행되도록 Lambda 함수를 구성한다.**
- B. AWS에서 데이터 센터로 VPN 연결을 설정하고, VPN을 통해 Lambda 함수의 트래픽을 라우팅한다(이미 Direct Connect 연결이 존재하는 상황에서 VPN을 추가로 구성하는 것은 불필요하며, 근본적으로 Lambda가 VPC에 연결되지 않으면 이 트래픽 자체가 발생하지 않음).
- C. Lambda 함수가 Direct Connect를 통해 온프레미스 데이터 센터에 접근하도록 VPC 라우팅 테이블을 업데이트한다(Lambda 함수가 먼저 해당 VPC에 연결되어 있어야 라우팅 테이블 설정이 의미를 가지며, 기본적으로 Lambda는 AWS가 관리하는 별도 VPC에서 실행됨).
- D. 탄력적 IP 주소를 생성하고, 탄력적 네트워크 인터페이스 없이 이를 통해 트래픽을 보내도록 Lambda 함수를 구성한다(탄력적 IP는 퍼블릭 IP이며 온프레미스 데이터베이스가 위치한 프라이빗 서브넷과는 애초에 통신 방식이 맞지 않음).

**정답: A**

**해설**
Lambda 함수는 기본적으로 AWS가 관리하는 별도의 VPC에서 실행되지만, 함수를 사용자 **VPC의 프라이빗 서브넷에 연결(VPC 구성)** 하도록 설정하면 해당 서브넷의 라우팅 테이블과 보안 그룹 설정을 그대로 따르게 됩니다. VPC에 연결된 후에는 이미 구성된 Direct Connect와 가상 프라이빗 게이트웨이 경로를 통해 온프레미스 데이터베이스와 통신할 수 있으므로, 적절한 보안 그룹으로 Lambda를 VPC에 연결하는 것이 핵심 단계입니다.

**왜 다른 보기는 오답인가**
- B: 이미 Direct Connect가 있어 별도 VPN을 구축할 필요가 없고, Lambda가 VPC에 연결되지 않은 상태에서는 VPN 경로 자체를 이용할 수 없습니다.
- C: 라우팅 테이블 조정은 Lambda가 VPC에 연결되어 있다는 전제가 충족된 이후에나 의미가 있는 부수적 조치입니다.
- D: 탄력적 IP는 퍼블릭 통신에 쓰이는 자원으로, 온프레미스 프라이빗 서브넷의 데이터베이스에 접근하는 경로 문제를 해결하지 못합니다.

> 💡 **시험 꿀팁**: "Lambda가 온프레미스나 VPC 내부 사설 리소스에 접근"해야 한다면, 우선 **Lambda를 해당 VPC/서브넷에 보안 그룹과 함께 연결**하는 것이 표준 정답입니다.

## QUESTION 185

**문제**: 회사가 Amazon ECS로 애플리케이션을 실행한다. 애플리케이션은 원본 이미지의 크기를 조정한 뒤 Amazon S3 API를 호출해 결과 이미지를 S3에 저장한다. 솔루션 설계자는 애플리케이션이 S3에 접근할 권한을 갖도록 어떻게 보장해야 하는가?

**보기**
- A. Amazon ECS에서 읽기/쓰기 액세스를 허용하도록 IAM에서 S3 역할을 업데이트한 다음 컨테이너를 다시 시작한다("S3 역할"이라는 개념 자체가 모호하며, ECS 서비스가 아니라 태스크가 실제로 S3를 호출할 권한을 가져야 함).
- B. **S3 권한이 있는 IAM 역할을 생성한 다음, 작업 정의에서 해당 역할을 taskRoleArn으로 지정한다.**
- C. Amazon ECS에서 Amazon S3로의 접근을 허용하는 보안 그룹을 생성하고 ECS 클러스터가 사용하는 시작 구성을 업데이트한다(보안 그룹은 네트워크 트래픽 필터링 도구일 뿐 IAM 기반의 API 호출 권한과는 무관하며, 아웃바운드는 기본적으로 모두 허용됨).
- D. S3 권한이 있는 IAM 사용자를 만들고, 그 계정으로 로그인한 상태에서 ECS 클러스터의 EC2 인스턴스를 다시 시작한다(사람 사용자 자격 증명을 컨테이너 워크로드에 결합하는 방식은 비효율적이며 표준 방법이 아님).

**정답: B**

**해설**

- A: 질문은 S3 접근 권한을 물었는데, "ECS 역할"을 수정하는 것은 대상이 잘못되었고 개념적으로도 명확하지 않습니다.
- C: 보안 그룹은 네트워크 수준의 트래픽 허용/차단을 담당할 뿐 API 호출에 필요한 IAM 권한 부여와는 관련이 없으며, 아웃바운드는 기본값이 전체 허용입니다.
- D: 사람용 IAM 사용자 자격 증명을 인스턴스에 결합시키는 방식은 권한 관리 모범 사례에 어긋나고 불필요하게 번거롭습니다.

> 💡 **시험 꿀팁**: ECS 컨테이너(태스크)가 다른 AWS 서비스를 호출해야 한다면 **작업 정의의 taskRoleArn에 IAM 역할을 지정**하는 것이 표준 정답입니다.

- E: 고객이 직접 가져온 키(SSE-C 성격의 KMS 가져온 키)는 자동 순환을 지원하지 않아 매년 수동으로 키를 재가져와야 하므로 운영 오버헤드가 커집니다.

**보기**
- A. S3 버킷을 만들어 정적 웹 호스팅을 활성화하고 정적 콘텐츠를 업로드한다. AWS Lambda로 모든 동적 콘텐츠를 처리한다(기존 Java/PHP 애플리케이션 구조를 서버리스 아키텍처로 다시 작성해야 해 "이전"이라는 전제와 개발 변경 최소화 취지에 맞지 않음).
- B. **웹 애플리케이션을 AWS Elastic Beanstalk 환경에 배포한다. 기능 테스트를 위해 URL 스와핑으로 여러 Elastic Beanstalk 환경을 전환한다.**

**해설**
**AWS Elastic Beanstalk**는 Java, PHP 등 다양한 런타임을 지원하며, 인프라 프로비저닝·로드 밸런싱·오토스케일링·상태 모니터링을 자동으로 관리해주는 완전관리형 플랫폼입니다. 서로 다른 Elastic Beanstalk 환경(예: 프로덕션/스테이징)을 만들어 두고 **URL 스와핑**으로 트래픽 대상을 전환하면, 복잡한 라우팅 규칙이나 인프라 변경 없이 새 기능을 빠르게 테스트하고 즉시 되돌릴 수 있습니다.

- D: 컨테이너화 및 로드밸런서 컨트롤러 구성은 추가 개발과 클러스터 운영 지식을 요구해 최소 오버헤드 조건에 맞지 않습니다.

> 💡 **시험 꿀팁**: "기존 언어 스택을 그대로 유지하며 빠르게 배포·테스트"해야 한다면 **Elastic Beanstalk + URL 스와핑**이 표준 정답입니다.

## QUESTION 191

**문제**: 회사에 Amazon RDS for MySQL에 고객 정보를 저장하는 주문 애플리케이션이 있다. 정규 업무 시간 동안 직원들이 보고 목적의 일회성 쿼리를 실행하는데, 쿼리 실행 시간이 길어 주문 처리 중 시간 초과가 발생한다. 회사는 직원의 쿼리 수행을 막지 않으면서 시간 초과를 제거해야 한다. 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. **읽기 전용 복제본을 생성하고, 보고 쿼리를 읽기 전용 복제본으로 이동한다.**
- B. 읽기 전용 복제본을 생성하고, 주문 애플리케이션을 기본 DB 인스턴스와 읽기 전용 복제본 모두에 배포한다(주문 처리 자체는 여전히 프라이머리에 부하를 주는 장기 실행 보고 쿼리와 같은 인스턴스에서 경쟁하게 되어 문제를 해결하지 못함).
- C. 주문형 용량의 Amazon DynamoDB로 주문 애플리케이션을 마이그레이션한다(관계형 스키마와 조인 기반 보고 쿼리 구조를 전면 재설계해야 해 요구 사항 대비 과도한 변경임).
- D. 사용량이 적은 시간대에 보고 쿼리를 예약한다(직원이 원하는 시간에 즉시 쿼리를 수행하지 못하게 되어 "쿼리 수행을 막지 않는다"는 조건을 위반함).

**정답: A**

**해설**
**RDS 읽기 전용 복제본**은 프라이머리 인스턴스의 데이터를 비동기로 복제한 별도의 인스턴스로, 장기 실행 조회 쿼리를 이곳으로 오프로드하면 프라이머리는 주문 처리(쓰기 위주 트랜잭션)에만 집중할 수 있습니다. 그 결과 보고 쿼리로 인한 자원 경합이 사라져 주문 처리 시간 초과가 해소되면서도, 직원은 여전히 원하는 시점에 자유롭게 쿼리를 실행할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 주문 애플리케이션을 복제본에도 배포하는 것은 보고 쿼리를 분리하지 않으므로 문제의 근본 원인을 해결하지 못합니다.
- C: DynamoDB로의 마이그레이션은 데이터 모델과 쿼리 방식을 전면 재설계해야 하는 큰 변화로, 이번 요구에는 과도합니다.
- D: 쿼리를 특정 시간대로 강제하면 직원이 원하는 시점에 쿼리를 실행하지 못하게 되어 조건을 위반합니다.

> 💡 **시험 꿀팁**: "쓰기(트랜잭션) 처리와 무거운 조회(보고) 쿼리를 분리"해야 한다면 **RDS 읽기 전용 복제본**이 표준 정답입니다.

## QUESTION 193

**문제**: 회사가 Amazon EC2 인스턴스에서 배치 애플리케이션을 실행하며, 여러 Amazon RDS 데이터베이스로 구성된 백엔드를 사용한다. 애플리케이션으로 인해 데이터베이스에서 많은 읽기가 발생하고 있다. 솔루션 설계자는 고가용성을 유지하면서 데이터베이스 읽기 수를 줄여야 한다. 무엇을 해야 하는가?

- A. **Amazon RDS 읽기 전용 복제본을 추가한다.**
- B. Redis용 Amazon ElastiCache를 사용한다(캐시 계층 도입은 애플리케이션 로직 변경이 필요하고, RDS와의 데이터 정합성·무효화 전략을 별도로 설계해야 해 단순 읽기 부하 분산보다 복잡함).
- C. Amazon Route 53 DNS 캐싱을 사용한다(DNS 캐싱은 이름 조회 성능에 관여할 뿐 데이터베이스로 전달되는 쿼리 자체의 수를 줄이지 못함).
- D. Memcached용 Amazon ElastiCache를 사용한다(B와 마찬가지로 캐시 계층 추가 설계가 필요하며 RDS 자체의 읽기 부하 분산 기능은 아님).

- C: Route 53 DNS 캐싱은 도메인 이름 조회 과정에만 관여하며 데이터베이스로 전달되는 쿼리 수와는 무관합니다.

> 💡 **시험 꿀팁**: "RDS 읽기 부하를 줄이면서 고가용성 유지"라는 조건에는 **RDS 읽기 전용 복제본 추가**가 표준 정답입니다.

## QUESTION 194

**문제**: 회사가 AWS에서 중요한 애플리케이션을 실행해야 하며, 데이터베이스에는 Amazon EC2를 사용해야 한다. 데이터베이스는 가용성이 높아야 하고 중단이 발생하면 자동으로 장애 조치되어야 한다. 이 요구 사항을 충족하는 솔루션은?

**보기**
- A. **동일 리전의 서로 다른 가용 영역에서 EC2 인스턴스 2개를 시작한다. 두 인스턴스 모두에 데이터베이스를 설치하고 클러스터로 구성한 뒤 데이터베이스 복제를 설정한다.**
- B. 한 가용 영역에서 EC2 인스턴스를 시작하고 데이터베이스를 설치한 뒤 AMI로 데이터를 백업한다. 중단 발생 시 AWS CloudFormation으로 EC2 인스턴스 프로비저닝을 자동화한다(장애 발생 후에야 새 인스턴스를 재생성하는 방식이라 자동 장애 조치라 보기 어렵고, 복구까지의 다운타임이 발생함).
- C. 서로 다른 리전에서 EC2 인스턴스 2개를 시작하고 데이터베이스를 설치한 뒤 복제를 설정하고, 필요 시 두 번째 리전으로 수동 장애 조치한다(리전 간 장애 조치는 재해 복구 목적에 가깝고, 문제에서 요구하는 자동 장애 조치가 아니라 수동 절차로 설명됨).
- D. 한 가용 영역에서 EC2 인스턴스를 시작하고 데이터베이스를 설치한 뒤 AMI로 백업하고, 중단 시 EC2 자동 복구를 사용한다(자동 복구는 동일 하드웨어/AZ 내 장애를 대상으로 한 인스턴스 복구 기능이며, 다중 인스턴스·다중 AZ 수준의 데이터베이스 고가용성을 제공하지 않음).

**정답: A**

**해설**
서로 다른 **가용 영역에 두 개의 EC2 인스턴스**를 배치하고 데이터베이스 소프트웨어 수준에서 **클러스터링과 복제**를 구성하면, 한 인스턴스나 AZ에 장애가 발생해도 다른 인스턴스가 즉시 서비스를 이어받는 자동 장애 조치 구조를 만들 수 있습니다. 관리형 RDS를 쓸 수 없는 EC2 기반 데이터베이스 환경에서 고가용성을 확보하는 표준적인 접근입니다.

**왜 다른 보기는 오답인가**
- B: 단일 인스턴스 구성이라 장애 발생 시 새 인스턴스를 프로비저닝하는 동안 서비스가 중단되며, 사전에 대기 중인 인스턴스가 없어 자동 장애 조치라 볼 수 없습니다.
- C: 리전 간 구성과 수동 장애 조치는 재해 복구(DR)에는 유용하지만 문제에서 요구하는 "자동" 장애 조치 조건을 충족하지 못합니다.

> 💡 **시험 꿀팁**: "EC2에 직접 설치한 데이터베이스의 자동 장애 조치"가 필요하면 **다른 AZ의 두 인스턴스를 클러스터+복제로 구성**하는 것이 표준 정답입니다.

## QUESTION 195

**문제**: 회사의 주문 시스템은 클라이언트 요청을 EC2 인스턴스로 보내고, EC2 인스턴스는 주문을 처리한 뒤 Amazon RDS에 저장한다. 사용자들은 시스템 장애 시 주문을 다시 처리해야 한다고 보고한다. 회사는 시스템 중단이 발생해도 주문을 자동으로 처리할 수 있는 탄력적인 솔루션을 원한다. 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. EC2 인스턴스를 Auto Scaling 그룹으로 옮기고, ECS 작업을 대상으로 하는 Amazon EventBridge 규칙을 생성한다(이벤트 규칙만으로는 실패한 주문 메시지를 안전하게 보관했다가 재처리하는 메커니즘을 제공하지 못함).

- B: ALB는 요청을 실시간으로 라우팅하는 로드밸런서로, 백엔드 장애 시 요청을 버퍼링해 두는 기능이 없어 주문이 유실될 수 있습니다.
- D: SNS는 즉시 전달을 전제로 한 알림 서비스이고, Run Command로 EC2에 명령을 보내는 방식은 안정적인 순차 재처리를 보장하는 표준적인 방법이 아닙니다.

> 💡 **시험 꿀팁**: "처리 중 장애가 나도 요청(주문)이 유실되지 않고 나중에 자동으로 재처리"되어야 한다면 **Amazon SQS를 통한 디커플링**이 표준 정답입니다.

- A. AWS CloudFormation 템플릿으로 전체 솔루션을 배포하고, 30일마다 스택을 재배포한 뒤 원래 스택을 삭제한다(주기적인 스택 재배포·삭제 절차를 관리해야 해 개발·운영 노력이 오히려 늘어남).

> 💡 **시험 꿀팁**: "일정 기간이 지난 DynamoDB 항목을 자동으로, 추가 비용 없이 삭제"해야 한다면 **DynamoDB TTL**이 표준 정답입니다.

**문제**: 회사가 온프레미스 데이터 센터의 Kubernetes 클러스터에서 컨테이너화된 애플리케이션을 실행하며 MongoDB를 데이터 저장소로 사용한다. 일부 환경을 AWS로 마이그레이션하려 하지만 현재는 코드나 배포 방법을 변경할 수 없다. 운영 오버헤드를 최소화하는 솔루션이 필요하다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**왜 다른 보기는 오답인가**

- B: ECS로의 전환 자체가 배포 방법 변경이며, DynamoDB는 MongoDB와 호환되지 않아 애플리케이션 코드 수정이 불가피합니다.
- C: EKS로 배포 방식은 유지되지만, DynamoDB로 데이터 저장소를 바꾸면 MongoDB 전용 코드를 다시 작성해야 합니다.

> 💡 **시험 꿀팁**: "Kubernetes 배포 방식과 MongoDB 코드를 그대로 유지"해야 한다면 **Amazon EKS(+Fargate) + Amazon DocumentDB**가 표준 정답입니다.

- C. 여러 화자 인식에 Amazon Translate를 사용한다. 기록 파일을 Amazon Redshift에 저장하고 SQL 쿼리로 분석한다(Translate는 언어 간 기계 번역 서비스로 화자 인식이나 음성-텍스트 변환 기능이 없음).
- D. 여러 화자 인식에 Amazon Rekognition을 사용한다. 성적표 파일을 S3에 저장하고 분석에 Amazon Textract를 사용한다(Rekognition은 화자 인식에 부적합하며, Textract는 이미지 속 문서 텍스트를 추출하는 OCR 서비스라 통화 녹음 분석과 무관함).

**정답: B**

**해설**
**Amazon Transcribe**는 통화 녹음과 같은 음성 데이터를 텍스트로 변환하면서 화자 분리(speaker diarization) 기능을 지원해, 누가 무엇을 말했는지 구분된 트랜스크립트를 생성할 수 있습니다. 생성된 트랜스크립트 파일을 S3에 저장하고 **Amazon Athena**로 표준 SQL 쿼리를 실행하면, 별도 인프라 없이도 비즈니스 패턴 분석과 7년간의 감사용 장기 보관 요구를 함께 충족할 수 있습니다.

**왜 다른 보기는 오답인가**
- A, D: Amazon Rekognition은 이미지·영상 분석 서비스로 음성 통화를 다루는 콜센터 시나리오와 화자 인식에 적합하지 않습니다.
- C: Amazon Translate는 언어 간 번역 서비스일 뿐 화자 인식이나 음성-텍스트 변환 기능을 제공하지 않습니다.

> 💡 **시험 꿀팁**: "통화 음성에서 화자를 구분한 트랜스크립트 생성"에는 **Amazon Transcribe**, "S3에 저장된 텍스트 데이터의 SQL 분석"에는 **Amazon Athena**가 표준 정답 조합입니다.

## QUESTION 200

**문제**: 회사가 AWS에서 애플리케이션을 호스팅하며 Amazon Cognito로 사용자를 관리한다. 사용자가 로그인하면 애플리케이션은 API Gateway에서 호스팅되는 REST API를 통해 DynamoDB의 데이터를 가져온다. 회사는 개발 노력을 줄이기 위해 REST API 접근을 제어하는 AWS 관리형 솔루션을 원한다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은?

**보기**
- A. 요청한 사용자를 확인하기 위해 API Gateway의 권한 부여자(authorizer)로 동작하는 Lambda 함수를 구성한다(커스텀 권한 부여 로직을 직접 개발·유지해야 해 이미 있는 Cognito 통합형 관리 솔루션보다 개발·운영 부담이 큼).
- B. 각 사용자에게 API 키를 발급해 요청마다 함께 보내도록 하고, Lambda 함수로 키를 검증한다(API 키 발급·검증 로직과 키 관리 체계를 직접 구축해야 해 개발 노력이 늘어나며, 사용자 인증 정보와 API 키를 별도로 관리해야 하는 번거로움이 있음).
- C. 모든 요청 헤더에 사용자 이메일 주소를 담아 보내고, Lambda 함수로 해당 사용자의 접근 권한을 검증한다(이메일 기반 검증 로직을 직접 구현해야 하고, 헤더 값을 신뢰할 수 있는 자격 증명으로 검증하는 보안 설계도 별도로 필요함).
- D. **API Gateway에서 Amazon Cognito 사용자 풀 권한 부여자를 구성해 Amazon Cognito가 각 요청을 검증하도록 한다.**

**정답: D**

**해설**
API Gateway는 **Amazon Cognito 사용자 풀 권한 부여자**를 기본 기능으로 지원하여, 요청에 포함된 Cognito가 발급한 JWT 토큰의 유효성을 API Gateway가 자동으로 검증하도록 설정할 수 있습니다. 이미 Cognito로 사용자를 관리하고 있으므로 별도의 커스텀 인증 코드를 개발할 필요 없이 콘솔 설정만으로 인증된 사용자만 API에 접근하도록 제어할 수 있어, 개발 노력과 운영 오버헤드를 모두 최소화하는 완전관리형 솔루션입니다.

**왜 다른 보기는 오답인가**
- A: Lambda 권한 부여자는 커스텀 인증 로직을 직접 작성·유지해야 해, 이미 존재하는 Cognito 사용자 풀 통합보다 개발 노력이 더 필요합니다.
- B: API 키 발급과 검증 체계를 별도로 구축·관리해야 하며, 이는 사용자 자격 증명 관리를 이원화시켜 운영 복잡성을 높입니다.
- C: 헤더의 이메일 값을 신뢰할 근거가 없어 보안상 취약하며, 검증 로직도 직접 개발해야 합니다.

> 💡 **시험 꿀팁**: "이미 Cognito로 사용자를 관리 중이고 API Gateway 접근을 제어"해야 한다면 **Amazon Cognito 사용자 풀 권한 부여자**가 표준 정답입니다.
