## QUESTION 421

**문제**: 회사가 Apache Kafka 기반 이벤트 스트리밍 플랫폼을 도입하려 하는데, 트래픽 패턴이 예측 불가능하고(신규 서비스라 사용량을 가늠하기 어려움) 브로커 수, 파티션, 스토리지 용량 같은 클러스터 용량 계획을 직접 세우고 관리하고 싶지 않다. 표준 Kafka API와 도구는 그대로 사용하고 싶다. 솔루션은?

**보기**
- A. Amazon MSK(프로비저닝 모드)로 클러스터를 구성하고 예상 트래픽에 맞춰 브로커 수를 사전에 결정(프로비저닝 모드는 브로커 수/유형 등 용량을 사전에 직접 계획해야 해서 "용량 계획을 직접 세우고 싶지 않다"는 요구에 반함).
- B. **Amazon MSK Serverless를 사용해, 브로커 프로비저닝이나 용량 계획 없이 트래픽에 따라 자동으로 확장/축소되는 완전관리형 Kafka 클러스터를 구성하면서 표준 Kafka API를 그대로 사용.**
- C. 자체 EC2에 Kafka를 직접 설치해 운영(용량 계획, 브로커 관리, 패치 등 모든 운영 부담을 직접 떠안게 되어 요구사항에 정면으로 반함).
- D. Kinesis Data Streams로 전면 전환(Kinesis는 강력한 스트리밍 서비스이지만 Kafka API가 아닌 자체 API를 사용해, "표준 Kafka API와 도구를 그대로 사용"하려는 요구를 충족하지 못함).

**정답: B**

**해설**
**Amazon MSK Serverless**는 브로커 수, 파티션, 스토리지 용량 같은 클러스터 용량을 사용자가 직접 프로비저닝하거나 계획할 필요 없이, 트래픽에 따라 **자동으로 확장/축소**되는 완전관리형 Kafka 클러스터를 제공합니다. 표준 Apache Kafka API와 기존 Kafka 클라이언트/도구를 그대로 사용할 수 있어, 예측 불가능한 트래픽을 가진 신규 서비스에서 용량 계획 부담 없이 Kafka를 도입하는 데 적합합니다.

**왜 다른 보기는 오답인가**
- A: 프로비저닝 모드는 브로커 수 등 용량을 사전에 직접 계획해야 해서 요구사항에 반합니다.
- C: 자체 EC2 운영은 모든 용량 계획과 운영 부담을 직접 떠안는 것입니다.
- D: Kinesis는 Kafka API가 아니므로 기존 Kafka 도구/API를 그대로 사용하려는 요구를 충족하지 못합니다.

> 💡 **시험 꿀팁**: **용량 계획 없이 표준 Kafka API를 그대로 사용**하면서 트래픽에 따라 자동 확장되는 스트리밍 플랫폼이 필요하면 **Amazon MSK Serverless**가 표준 정답입니다.

## QUESTION 422

**문제**: 프로덕션 RDS PostgreSQL 데이터베이스에서 읽기 부하 분산을 위해 기존 읽기 전용 복제본을 사용 중인데, 장애 조치 시간을 더욱 단축하고 싶고 대기(standby) 인스턴스도 평상시에 읽기 트래픽 처리에 활용하고 싶다. 기존 표준 Multi-AZ(단일 대기 인스턴스, 읽기 불가) 방식의 한계를 넘어서려면?

**보기**
- A. 표준 Multi-AZ 배포를 유지하고 읽기 전용 복제본 수만 늘림(표준 Multi-AZ의 대기 인스턴스 자체는 여전히 읽기에 활용할 수 없으며, 별도의 읽기 복제본을 늘리는 것은 장애 조치 시간 단축과는 무관).
- B. **RDS Multi-AZ DB 클러스터 배포로 전환해, 하나의 프라이머리와 함께 읽기 가능한 두 개의 대기(standby) 인스턴스를 구성. 평상시 두 대기 인스턴스로 읽기 트래픽을 분산하고, 장애 시 표준 Multi-AZ보다 짧은 시간에 자동 장애 조치.**
- C. Aurora Global Database로 전환(Global Database는 리전 간 재해 복구를 위한 기능이며, 이 문제가 요구하는 단일 리전 내에서의 더 빠른 장애 조치와 대기 인스턴스의 읽기 활용이라는 목적과는 다름).
- D. 읽기 전용 복제본을 프라이머리와 동일한 사양으로 여러 개 생성해 로드 밸런서로 트래픽 분산(가능한 방법이지만, 일반 읽기 복제본은 비동기 복제로 인해 대기 시간이 있고 자동 장애 조치의 표준 메커니즘도 Multi-AZ DB 클러스터만큼 빠르지 않음).

**정답: B**

**해설**
**RDS Multi-AZ DB 클러스터** 배포는 하나의 프라이머리 인스턴스와 함께 **두 개의 읽기 가능한 대기(standby) 인스턴스**를 별도의 AZ에 구성합니다. 평상시에는 이 두 대기 인스턴스로 읽기 트래픽을 분산해 활용할 수 있고(읽기가 불가능한 표준 Multi-AZ와의 핵심 차이), 프라이머리 장애 시에는 준동기(semi-synchronous) 복제와 빠른 스토리지 계층을 기반으로 표준 Multi-AZ보다 **더 짧은 시간(일반적으로 35초 이내)**에 자동 장애 조치가 이루어집니다.

**왜 다른 보기는 오답인가**
- A: 표준 Multi-AZ의 대기 인스턴스는 읽기에 사용할 수 없으며, 이 한계 자체를 극복하는 것이 문제의 목적입니다.
- C: Aurora Global Database는 리전 간 DR용 기능으로 이 문제의 단일 리전 요구와 다릅니다.
- D: 일반 읽기 복제본은 비동기 복제라 최신성이 떨어질 수 있고, 자동 장애 조치 속도도 Multi-AZ DB 클러스터만큼 빠르지 않습니다.

> 💡 **시험 꿀팁**: **읽기 가능한 대기 인스턴스 + 더 빠른 자동 장애 조치**가 모두 필요한 RDS 워크로드에는 **Multi-AZ DB 클러스터 배포**가 표준 정답입니다.

## QUESTION 423

**문제**: 보안 팀이 EC2 인스턴스에 대한 관리 접근에서 **SSH 키 관리, 22번 포트 개방, 배스천 호스트 운영**을 모두 없애고 싶다. 모든 접속 세션은 중앙에서 기록되어 감사 가능해야 하며, IAM 권한으로 접근을 세밀하게 통제하고 싶다. 솔루션은?

**보기**
- A. 배스천 호스트를 강화(hardening)하고 SSH 키를 Secrets Manager에 저장(배스천 호스트 운영 자체와 SSH 접속 방식(22번 포트 개방)은 여전히 남아 있어 "모두 없애고 싶다"는 요구를 충족하지 못함).
- B. **AWS Systems Manager Session Manager를 사용해, SSH 키나 배스천 호스트, 인바운드 포트 개방 없이 IAM 권한 기반으로 인스턴스에 브라우저 또는 CLI를 통한 셸 세션을 시작하고, 모든 세션 활동을 CloudTrail 및 S3/CloudWatch Logs로 중앙 기록.**
- C. VPN을 통해 프라이빗 서브넷에 접근한 뒤 SSH 사용(VPN을 사용해도 여전히 SSH 키 관리와 22번 포트 개방이 필요해 요구사항을 완전히 충족하지 못함).
- D. 모든 인스턴스에 퍼블릭 IP를 제거하고 NAT Gateway 뒤에 배치(퍼블릭 IP 제거만으로는 SSH 키 관리 자체가 없어지지 않으며, 인스턴스 접근/관리 방법에 대한 근본적인 변화가 없음).

**정답: B**

**해설**
**AWS Systems Manager Session Manager**는 SSH 키, 배스천 호스트, 인바운드 포트(22번 등) 개방 없이, **IAM 권한**을 기반으로 EC2 인스턴스(및 온프레미스 서버)에 대한 브라우저 기반 또는 CLI 기반 셸 세션을 시작할 수 있게 해줍니다. 모든 세션 시작/종료 및 실행된 명령은 **CloudTrail**과 **S3/CloudWatch Logs**로 중앙 기록되어 완전한 감사 추적이 가능하며, IAM 정책으로 누가 어떤 인스턴스에 접근할 수 있는지 세밀하게 통제할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 배스천 호스트와 SSH 접속 방식 자체가 여전히 남아있어 "모두 없애고 싶다"는 목표를 달성하지 못합니다.
- C: VPN 경유도 여전히 SSH 키와 포트 개방이 필요합니다.
- D: 퍼블릭 IP 제거는 네트워크 노출을 줄이지만 SSH 키 관리 자체를 없애지는 못합니다.

> 💡 **시험 꿀팁**: **SSH 키/배스천 호스트/인바운드 포트 개방 없이 IAM 기반으로 인스턴스에 접근하고 모든 세션을 감사 기록**하려면 **AWS Systems Manager Session Manager**가 표준 정답입니다.

## QUESTION 424

**문제**: 모바일 앱이 백엔드 서버를 거치지 않고 앱에서 직접 S3와 DynamoDB에 접근해야 하는데, 각 최종 사용자에게 IAM 사용자를 만들고 싶지 않으며, 앱 사용자는 Google, Facebook 같은 소셜 로그인으로 인증한다. 인증된(또는 게스트) 사용자에게 임시 AWS 자격 증명을 발급해 스코프가 지정된 접근을 허용하려면?

**보기**
- A. 모든 모바일 사용자에게 공유되는 하나의 액세스 키/비밀 키를 앱에 하드코딩(액세스 키를 클라이언트 앱에 하드코딩하는 것은 심각한 보안 위험이며, 개별 사용자 격리도 불가능).
- B. **Amazon Cognito 자격 증명 풀(Identity Pools)을 사용해, 소셜 로그인 제공업체(또는 Cognito 사용자 풀)로 인증된 사용자(및 인증되지 않은 게스트)에게 STS를 통한 임시 AWS 자격 증명을 발급하고, IAM 역할로 S3/DynamoDB에 대한 세분화된 접근 범위를 지정.**
- C. 각 모바일 사용자마다 개별 IAM 사용자를 백엔드에서 동적으로 생성(사용자 수만큼 IAM 사용자를 생성하는 것은 IAM 사용자 한도 문제와 확장성 문제를 야기하며 "IAM 사용자를 만들고 싶지 않다"는 요구에 정면으로 반함).
- D. API Gateway + Lambda로 모든 S3/DynamoDB 요청을 프록시하고 백엔드에서 인증 처리(문제에서 명시적으로 "백엔드 서버를 거치지 않고" 직접 접근하고 싶다고 했으므로 요구사항과 다름).

**정답: B**

**해설**
**Amazon Cognito 자격 증명 풀(Identity Pools)**은 소셜 로그인 공급자(Google, Facebook 등)나 Cognito 사용자 풀, SAML 등으로 인증된 사용자(또는 인증되지 않은 게스트 사용자)에게 **AWS STS를 통한 임시 자격 증명**을 발급합니다. 이 임시 자격 증명은 IAM 역할에 연결되어 S3, DynamoDB 등에 대한 세분화된 접근 권한을 가지므로, 모바일 앱이 백엔드 서버 없이도 개별 IAM 사용자를 만들지 않고 안전하게 AWS 리소스에 직접 접근할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 공유 액세스 키를 클라이언트에 하드코딩하는 것은 심각한 보안 취약점입니다.
- C: 사용자마다 IAM 사용자를 생성하는 것은 확장성이 없고 요구사항에 정면으로 반합니다.
- D: 백엔드 프록시 방식은 "백엔드 서버를 거치지 않고" 접근하려는 요구와 다릅니다.

> 💡 **시험 꿀팁**: 모바일 앱이 **소셜 로그인 인증 사용자에게 임시 AWS 자격 증명을 발급해 AWS 리소스에 직접 접근**하도록 하려면 **Amazon Cognito 자격 증명 풀(Identity Pools)**이 표준 정답입니다.

## QUESTION 425

**문제**: 회사가 Elastic Beanstalk으로 배포하는 웹 애플리케이션의 신규 버전을 배포할 때, 기존 버전에 영향을 주지 않고 새 버전을 별도 환경에서 완전히 검증한 뒤, **문제가 없으면 즉시 트래픽을 전환하고 문제가 있으면 즉시 원래 버전으로 되돌릴 수 있는** 무중단 배포 방식을 원한다. 솔루션은?

**보기**
- A. Elastic Beanstalk의 롤링(rolling) 배포 정책 사용(롤링 배포는 기존 환경 내에서 인스턴스를 순차적으로 교체하는 방식이라, 새 버전을 완전히 별도로 검증한 뒤 한 번에 전환하는 것과는 다르며, 롤백도 순차적 재교체가 필요해 즉각적이지 않음).
- B. **Elastic Beanstalk의 환경 교체(blue/green) 배포 방식을 사용해, 새 버전을 별도의 환경(그린)에 배포하고 충분히 검증한 뒤, 환경 URL 교체(swap)로 즉시 트래픽을 전환. 문제 발생 시 다시 교체해 즉시 원래 환경(블루)으로 롤백.**
- C. All at once 배포 정책 사용(전체 인스턴스를 한 번에 새 버전으로 교체하는 방식으로, 별도 환경에서의 사전 검증이나 즉각적인 롤백 메커니즘을 제공하지 않아 배포 중 문제 발생 시 서비스에 직접 영향).
- D. 기존 환경을 완전히 종료한 뒤 새 환경을 처음부터 생성(기존 환경 종료 시 다운타임이 발생하며 "기존 버전에 영향 없이" 검증한다는 요구에도 반함).

**정답: B**

**해설**
Elastic Beanstalk의 **환경 교체(swap URL, 블루/그린 유사) 배포 방식**은 새 버전을 기존 프로덕션 환경(블루)과 완전히 분리된 새로운 환경(그린)에 배포해, 프로덕션에 전혀 영향을 주지 않고 충분히 테스트할 수 있게 해줍니다. 검증이 끝나면 두 환경의 **CNAME(URL)을 교체**해 즉시 트래픽을 새 환경으로 전환하며, 문제가 발생하면 다시 교체해 **즉시 원래 환경으로 롤백**할 수 있어 이 문제의 요구(사전 검증, 즉각 전환, 즉각 롤백)를 모두 충족합니다.

**왜 다른 보기는 오답인가**
- A: 롤링 배포는 기존 환경 내 순차 교체 방식이라 완전히 분리된 사전 검증과 즉각적인 전면 롤백을 제공하지 않습니다.
- C: All at once는 검증 단계 없이 즉시 전체를 교체해 문제 발생 시 서비스에 바로 영향을 줍니다.
- D: 기존 환경 종료 후 재생성은 다운타임을 유발합니다.

> 💡 **시험 꿀팁**: Elastic Beanstalk에서 **완전히 검증된 새 버전으로 즉시 전환하고 문제 시 즉각 롤백**하려면 **환경 교체(블루/그린) 배포**가 표준 정답입니다.

**문제**: 개발팀이 특정 SQS 큐의 메시지를 Step Functions 워크플로우로 전달하되, 메시지 중 특정 속성 값을 가진 것만 필터링해 전달하고, 전달 전 메시지 형식을 간단히 변환하고 싶다. 이를 위해 매번 별도의 Lambda 함수(단순 연결/변환 목적의 "글루 코드")를 작성하고 유지하고 싶지 않다. 솔루션은?

- A: 상시 가동은 간헐적 작업 패턴에 비효율적이며 운영 부담도 남습니다.
- C: 수동 프로비저닝/종료는 반복적인 운영 부담과 실수로 인한 비용 낭비 위험이 있습니다.
- D: Glue도 서버리스이지만, 기존 Spark/Hive 코드를 그대로 유지하고 싶다면 EMR Serverless가 더 직접적인 선택입니다.

> 💡 **시험 꿀팁**: 간헐적인 **Spark/Hive 배치 작업**을 클러스터 운영 부담 없이 자동으로 확장/축소되도록 처리하려면 **Amazon EMR Serverless**가 표준 정답입니다.

## QUESTION 431

**문제**: 과학 연구소가 여러 EC2 인스턴스에 걸쳐 **긴밀하게 결합된(tightly coupled)** 병렬 계산(MPI 기반 유체 시뮬레이션, 노드 간 지속적인 통신 필요)을 수행해야 한다. 각 노드가 독립적으로 작업을 처리하는 것이 아니라 여러 노드가 하나의 작업을 위해 실시간으로 데이터를 주고받으며 협력해야 한다. AWS Batch에서 이런 워크로드를 지원하는 기능은?

**보기**
- A. AWS Batch의 배열 작업(array job)(배열 작업은 동일한 작업을 여러 번 독립적으로 병렬 실행하는 데 최적화되어 있으며, 노드 간 긴밀한 실시간 통신이 필요한 MPI 워크로드에는 적합하지 않음).
- B. **AWS Batch의 다중 노드 병렬 작업(multi-node parallel job)을 사용해, 여러 EC2 인스턴스를 하나의 작업 단위로 묶고 클러스터 배치 그룹과 결합해 노드 간 낮은 지연시간의 통신을 지원하며 MPI 같은 프레임워크로 노드 간 조율.**

- D. Lambda 함수로 각 계산 단위를 병렬 실행(Lambda는 독립적인 짧은 실행에 최적화되어 있으며, 노드 간 지속적인 저지연 통신이 필요한 긴밀 결합 HPC 워크로드에는 부적합).

**정답: B**

**해설**
**AWS Batch의 다중 노드 병렬 작업(multi-node parallel job)**은 여러 EC2 인스턴스를 **하나의 논리적 작업**으로 묶어, MPI(Message Passing Interface) 같은 프레임워크를 사용하는 긴밀하게 결합된 HPC 워크로드를 지원합니다. 클러스터 배치 그룹과 결합하면 노드 간 네트워크 지연시간을 최소화할 수 있어, 유체 시뮬레이션처럼 여러 노드가 지속적으로 데이터를 주고받으며 협력해야 하는 계산 작업에 적합합니다.

**왜 다른 보기는 오답인가**
- A: 배열 작업은 동일 작업의 독립적 반복 실행에 최적화되어 있으며 노드 간 긴밀한 통신을 지원하지 않습니다.
- C: S3를 매개로 한 통신은 지연시간이 너무 커서 MPI의 실시간 통신 요구에 부적합합니다.
- D: Lambda는 독립적인 짧은 실행에 최적화되어 있으며 지속적인 노드 간 저지연 통신을 지원하지 않습니다.

> 💡 **시험 꿀팁**: 여러 노드가 **MPI 등으로 긴밀하게 통신하며 협력하는 HPC 워크로드**를 AWS Batch에서 실행하려면 **다중 노드 병렬 작업(multi-node parallel job)**이 표준 정답입니다.

**문제**: 회사가 Direct Connect 게이트웨이를 통해 여러 리전에 있는 다수의 VPC에 연결하려 하는데, 이 VPC들이 각각 개별 Transit Gateway에 연결되어 있다(각 VPC에 직접 연결하는 것이 아니라 Transit Gateway를 경유). Direct Connect 게이트웨이가 Transit Gateway와 통합되려면 어떤 유형의 가상 인터페이스가 필요한가?

- A. 프라이빗 가상 인터페이스(private VIF)만 사용(프라이빗 VIF는 Direct Connect 게이트웨이를 개별 VPC의 가상 프라이빗 게이트웨이(VGW)와 연결하는 데 사용되며, Transit Gateway와의 연결에는 다른 유형의 VIF가 필요).
- B. **전송 가상 인터페이스(transit virtual interface, transit VIF)를 사용해, Direct Connect 게이트웨이를 Transit Gateway와 연결. 이를 통해 온프레미스가 Transit Gateway에 연결된 다수의 VPC에 도달.**
- C. 퍼블릭 가상 인터페이스(public VIF)만 사용(퍼블릭 VIF는 AWS 퍼블릭 서비스 엔드포인트(S3 등)에 접근하기 위한 것이며, VPC나 Transit Gateway 같은 프라이빗 리소스 연결과는 무관).
- D. 가상 인터페이스 없이 Direct Connect 게이트웨이만으로 자동 연결(Direct Connect 게이트웨이는 가상 인터페이스를 통해서만 연결이 성립하며, 인터페이스 없이 자동으로 연결되지 않음 — 개념 오류).

**정답: B**

**해설**
Direct Connect 게이트웨이가 **Transit Gateway**와 연결되려면 **전송 가상 인터페이스(transit VIF)**가 필요합니다. 이는 Direct Connect 게이트웨이를 개별 VPC의 가상 프라이빗 게이트웨이에 연결하는 **프라이빗 VIF**와는 다른 유형으로, Transit Gateway를 경유해 그 안에 연결된 다수의 VPC에 온프레미스에서 도달할 수 있게 해줍니다. 대규모 다중 VPC 환경에서 Direct Connect와 Transit Gateway를 통합하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 프라이빗 VIF는 개별 VPC의 VGW와의 직접 연결용이며 Transit Gateway 연결에는 transit VIF가 필요합니다.
- C: 퍼블릭 VIF는 AWS 퍼블릭 서비스 엔드포인트 접근용으로 이 시나리오와 무관합니다.
- D: 가상 인터페이스 없이는 Direct Connect 게이트웨이 연결 자체가 성립하지 않습니다.

> 💡 **시험 꿀팁**: Direct Connect 게이트웨이를 **Transit Gateway와 연결**하려면 **전송 가상 인터페이스(transit VIF)**가 표준 정답입니다. 개별 VPC(VGW) 연결용인 프라이빗 VIF와의 차이를 기억하세요.

**보기**
- A. 모든 사용자에게 항상 MFA를 의무화(가능한 방법이지만, "위험도가 높은 경우에만" 추가 인증을 요구하고 유출 자격 증명 여부를 자동으로 확인하고 싶다는 세밀한 요구와는 다르며 사용자 경험에도 영향).

- C. WAF의 속도 기반 규칙만 사용해 짧은 시간 내 다수의 로그인 시도를 차단(속도 기반 규칙은 무차별 대입 공격의 빈도 자체를 제어하는 데는 도움이 되지만, 특정 자격 증명이 알려진 유출 목록과 일치하는지 확인하는 기능은 아님).
- D. 모든 로그인 시도를 CloudTrail로 로깅한 뒤 사후에 수동으로 유출 여부 분석(사후 로그 분석은 실시간 차단이나 적응형 인증을 제공하지 못하며, 공격이 이미 성공한 뒤에야 발견하게 됨).

**해설**
**Amazon Cognito 사용자 풀의 고급 보안 기능**은 **유출된 자격 증명 감지**를 통해 사용자가 입력한 사용자명/비밀번호가 알려진 유출 데이터베이스와 일치하는지 자동으로 확인하고, **적응형 인증**을 통해 비정상적인 위치, 디바이스, 로그인 패턴 등을 분석해 위험도를 평가합니다. 위험도가 높다고 판단되면 자동으로 MFA 같은 추가 인증 단계를 요구하거나 로그인을 차단할 수 있어, 크리덴셜 스터핑 같은 공격에 실시간으로 대응하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 모든 사용자에게 항상 MFA를 강제하는 것은 위험 기반의 세밀한 대응이 아니며 사용자 경험을 저해합니다.
- C: WAF 속도 기반 규칙은 요청 빈도를 제어할 뿐 유출 자격 증명 일치 여부를 확인하지 못합니다.
- D: 사후 로그 분석은 실시간 방어가 아니라 공격 이후의 뒤늦은 발견에 그칩니다.

> 💡 **시험 꿀팁**: Cognito 인증에서 **유출된 자격 증명 감지 + 위험 기반 적응형 인증(추가 MFA 요구)**이 필요하면 **Cognito 사용자 풀의 고급 보안 기능(advanced security features)**이 표준 정답입니다.

## QUESTION 437

**문제**: 금융 회사가 사기 탐지 시스템을 구축하려 하는데, 핵심 로직은 "이 계좌가 알려진 사기 계좌와 몇 단계(hop) 이내로 연결되어 있는가", "특정 거래 패턴이 사기 네트워크의 일부처럼 보이는가" 같은 **복잡하게 연결된 관계를 탐색**하는 쿼리다. 관계형 DB의 다중 JOIN으로는 이런 다단계 관계 탐색 쿼리의 성능이 매우 나쁘다. 솔루션은?

**보기**
- A. 관계형 DB(RDS)에서 인덱스를 최대한 추가해 JOIN 성능 개선(다단계(multi-hop) 관계 탐색은 관계형 모델의 근본적인 한계이며, 인덱스 추가만으로는 그래프 순회 쿼리의 성능 문제를 근본적으로 해결하지 못함).
- B. **Amazon Neptune을 사용해, 계좌와 거래를 정점(vertex)과 간선(edge)으로 모델링하는 그래프 데이터베이스로 전환하고, Gremlin이나 openCypher 같은 그래프 쿼리 언어로 다단계 관계 탐색(예: 몇 단계 이내 연결 여부)을 효율적으로 수행.**
- C. DynamoDB로 전환해 계좌 ID를 파티션 키로 사용(DynamoDB는 키-값/문서 조회에 최적화되어 있으며, 임의 깊이의 관계 그래프 순회 쿼리에는 그래프 데이터베이스가 훨씬 적합).
- D. Redshift로 전환해 사기 탐지를 위한 대규모 집계 쿼리 실행(Redshift는 대규모 정형 데이터 집계/분석에 강하지만, 다단계 관계 순회 같은 그래프 탐색 쿼리 패턴에는 최적화되어 있지 않음).

**정답: B**

**해설**
**Amazon Neptune**은 관계(그래프) 자체를 1급 개념으로 다루는 그래프 데이터베이스로, 계좌·거래 등을 **정점**과 **간선**으로 모델링하면 "몇 단계 이내로 연결된 계좌 찾기" 같은 **다단계(multi-hop) 관계 탐색 쿼리**를 관계형 DB의 다중 JOIN보다 훨씬 효율적으로 수행할 수 있습니다. Gremlin, openCypher 같은 그래프 전용 쿼리 언어를 지원해, 사기 탐지처럼 복잡하게 연결된 네트워크 패턴을 분석하는 워크로드에 특화된 표준 서비스입니다.

**왜 다른 보기는 오답인가**
- A: 다단계 관계 탐색은 관계형 모델의 근본적 한계이며 인덱스만으로 해결되지 않습니다.
- C: DynamoDB는 키-값 조회에 최적화되어 있으며 임의 깊이의 그래프 순회에는 부적합합니다.
- D: Redshift는 대규모 집계 분석에 강하지만 그래프 탐색 쿼리 패턴에는 최적화되어 있지 않습니다.

> 💡 **시험 꿀팁**: **복잡하게 연결된 관계(다단계 관계 탐색)를 분석**해야 하는 사기 탐지, 추천, 소셜 네트워크 같은 워크로드에는 **Amazon Neptune**(그래프 데이터베이스)이 표준 정답입니다.

## QUESTION 439

**문제**: 보안 팀이 Control Tower로 관리되는 계정에서, 원래 배포된 가드레일 관련 리소스(예: 특정 IAM 역할이나 SCP가 적용된 OU 구성)가 누군가에 의해 수동으로 변경되어 랜딩존의 기준 상태와 달라진("드리프트") 경우, 이를 자동으로 탐지하고 싶다. 솔루션은?

**AWS Control Tower**는 자체적으로 **드리프트 감지** 기능을 제공해, 랜딩존이 계정/OU에 배포한 가드레일 관련 리소스(특정 IAM 역할, SCP 연결 등)가 사용자의 수동 변경 등으로 인해 원래의 기준 구성과 달라졌는지 자동으로 식별합니다. 드리프트가 감지된 계정은 콘솔에서 표시되며, 필요시 해당 계정을 **재등록(re-register)**해 원래의 랜딩존 기준 상태로 복원할 수 있습니다. 이는 Control Tower 환경에 특화된 거버넌스 무결성 검증 기능입니다.

**왜 다른 보기는 오답인가**
- A: 일반 Config 규칙은 리소스 구성 준수 평가에는 유용하지만 Control Tower의 랜딩존 드리프트라는 특정 개념을 전용으로 다루지 않습니다.
- C: 수동 로그 검토는 비효율적이고 Control Tower가 이미 제공하는 기능을 재구현하는 것입니다.
- D: 전체 재배포는 불필요하게 파괴적이고 비효율적입니다.

> 💡 **시험 꿀팁**: Control Tower 랜딩존의 **가드레일 관련 리소스가 기준 상태에서 벗어났는지(드리프트) 자동으로 탐지하고 복원**하려면 **Control Tower의 드리프트 감지(drift detection) 및 계정 재등록** 기능이 표준 정답입니다.

## QUESTION 440

**문제**: 회사가 여러 EKS 클러스터에 걸쳐 실행되는 컨테이너 워크로드의 지표(CPU, 메모리, 커스텀 애플리케이션 지표)와 대시보드를 **중앙에서 통합 수집/시각화**하고 싶다. 각 클러스터마다 자체 Prometheus 서버를 구축/운영/스케일링하는 부담을 지고 싶지 않다. 솔루션은?

**보기**
- A. 각 EKS 클러스터에 자체 Prometheus 서버를 개별 설치하고 수동으로 통합 대시보드 구축(Prometheus 서버를 클러스터마다 직접 운영/스케일링/장기 보관 관리해야 해서 "부담을 지고 싶지 않다"는 요구에 반함).
- B. **Amazon Managed Service for Prometheus(지표 수집/장기 저장, 완전관리형)와 Amazon Managed Grafana(시각화)를 결합해, 여러 EKS 클러스터의 지표를 중앙에서 수집하고 통합된 대시보드로 시각화하며 Prometheus 서버 운영 부담을 AWS에 위임.**
- C. CloudWatch Container Insights만 사용(Container Insights도 유용한 컨테이너 모니터링 기능이지만, 기존에 Prometheus 형식의 커스텀 애플리케이션 지표를 광범위하게 사용 중이라면 Prometheus 호환 관리형 서비스가 기존 지표 형식과 쿼리(PromQL)를 그대로 활용하는 데 더 적합).
- D. 모든 클러스터의 로그를 S3로 내보내 Athena로 지표를 계산(로그 기반 사후 배치 분석 방식은 실시간에 가까운 모니터링 대시보드 요구에 부합하지 않고 매우 비효율적).

**정답: B**

**해설**
**Amazon Managed Service for Prometheus**는 Prometheus와 호환되는 지표 수집·저장·쿼리(PromQL) 기능을 완전관리형으로 제공해, 여러 EKS 클러스터의 지표를 중앙 워크스페이스로 수집하면서도 Prometheus 서버 자체의 프로비저닝, 스케일링, 장기 저장 관리 부담을 AWS에 위임할 수 있습니다. 여기에 **Amazon Managed Grafana**를 결합하면 수집된 지표를 통합된 대시보드로 시각화할 수 있어, 다중 클러스터 컨테이너 관찰성을 관리형으로 구현하는 표준 조합입니다.

**왜 다른 보기는 오답인가**
- A: 클러스터마다 자체 Prometheus를 운영하는 것은 이 문제가 피하고자 하는 운영 부담 그 자체입니다.
- C: Container Insights도 유용하지만, 기존 Prometheus 지표 형식/PromQL을 그대로 활용하려면 Managed Service for Prometheus가 더 직접적입니다.
- D: 로그 기반 사후 배치 분석은 실시간 모니터링 요구에 맞지 않고 비효율적입니다.

> 💡 **시험 꿀팁**: 여러 **EKS 클러스터의 Prometheus 형식 지표를 관리형으로 중앙 수집하고 통합 시각화**하려면 **Amazon Managed Service for Prometheus + Amazon Managed Grafana**가 표준 정답입니다.
