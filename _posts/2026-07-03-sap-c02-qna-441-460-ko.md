## QUESTION 441

**문제**: 온라인 게임 회사가 전 세계 게임 서버 인스턴스에 플레이어를 연결해야 하는데, 표준 로드 밸런싱(가장 가까운 정상 엔드포인트로 균등 분산)이 아니라, **각 플레이어를 이미 참여 중인 특정 게임 세션이 실행 중인 정확한 인스턴스/포트로 라우팅**해야 한다(세션 고정, 커스텀 라우팅 로직). 여전히 정적 Anycast IP와 전 세계 최적 경로의 이점은 누리고 싶다. 솔루션은?

**보기**
- A. 표준 AWS Global Accelerator 사용(표준 Global Accelerator는 상태 확인 기반으로 정상 엔드포인트에 트래픽을 자동 분산하는 방식이며, 애플리케이션이 특정 클라이언트를 특정 인스턴스/포트로 임의 매핑하는 커스텀 라우팅 로직을 직접 제어하지는 못함).
- B. **AWS Global Accelerator의 커스텀 라우팅 액셀러레이터(custom routing accelerator)를 사용해, 애플리케이션이 특정 클라이언트 IP/포트 조합을 특정 대상 EC2 인스턴스의 특정 IP/포트로 매핑하는 라우팅 테이블을 직접 제어하면서, 여전히 정적 Anycast IP와 AWS 글로벌 네트워크를 통한 최적 경로를 활용.**
- C. Route 53로 각 세션마다 새로운 DNS 레코드 생성(DNS 기반 라우팅은 세션 단위의 세밀한 포트/인스턴스 매핑에 적합하지 않고 DNS 캐싱으로 인한 지연도 발생하며 매번 레코드를 생성/관리하는 것은 비현실적).
- D. ALB의 대상 그룹 스티키니스(고정 세션) 사용(ALB 스티키니스는 HTTP 쿠키 기반의 동일 대상 재사용 메커니즘이며, 게임 서버처럼 UDP 기반 커스텀 프로토콜이나 임의의 클라이언트-인스턴스 매핑을 지원하지 않음).

**정답: B**

**해설**
**AWS Global Accelerator의 커스텀 라우팅 액셀러레이터**는 표준 액셀러레이터와 달리, 애플리케이션이 **특정 클라이언트(수신 IP/포트)를 특정 대상 EC2 인스턴스의 특정 목적지 IP/포트로 매핑**하는 라우팅 테이블을 직접 제어할 수 있게 해줍니다. 이를 통해 게임 세션처럼 특정 클라이언트가 정확히 어느 인스턴스/포트로 연결되어야 하는지에 대한 세밀한 제어권을 애플리케이션이 가지면서도, 여전히 Global Accelerator의 정적 Anycast IP와 AWS 글로벌 네트워크를 통한 전 세계 최적 경로 라우팅의 이점을 그대로 누릴 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 표준 액셀러레이터는 정상 엔드포인트로의 자동 분산에 최적화되어 있으며, 애플리케이션이 임의로 클라이언트-인스턴스 매핑을 제어하는 커스텀 라우팅 로직은 지원하지 않습니다.
- C: DNS 기반 접근은 세션 단위 세밀한 라우팅에 적합하지 않고 캐싱 지연과 관리 부담이 큽니다.
- D: ALB 스티키니스는 HTTP 쿠키 기반이며 게임 서버의 UDP/커스텀 프로토콜 세션 라우팅에는 적용되지 않습니다.

> 💡 **시험 꿀팁**: 애플리케이션이 **특정 클라이언트를 특정 인스턴스/포트로 직접 매핑하는 커스텀 라우팅**을 제어하면서도 정적 IP와 글로벌 최적 경로를 유지하려면 **Global Accelerator의 커스텀 라우팅 액셀러레이터**가 표준 정답입니다.

## QUESTION 442

**문제**: 회사가 Aurora MySQL의 트랜잭션 데이터를 거의 실시간으로 Redshift에서 분석하고 싶은데, 기존에는 이를 위해 별도의 ETL 파이프라인(DMS나 커스텀 Lambda로 지속적 복제)을 구축/유지해야 했다. ETL 파이프라인 구축 없이 Aurora의 데이터 변경 사항이 Redshift에 자동으로, 거의 실시간으로 반영되도록 하고 싶다. 솔루션은?

**보기**
- A. DMS로 지속적 복제 작업을 구성(DMS도 유효한 방법이지만, 별도의 복제 태스크 구성/모니터링/관리라는 ETL 파이프라인 운영 부담이 여전히 발생하며, 문제는 이를 없애고 싶어함).
- B. **Aurora zero-ETL 통합(zero-ETL integration with Amazon Redshift)을 사용해, 별도의 ETL 파이프라인 구축 없이 Aurora의 데이터 변경 사항이 자동으로, 몇 초 이내에 Redshift에 복제되도록 네이티브 통합을 구성.**
- C. 매일 밤 Aurora 데이터를 S3로 내보낸 뒤 Redshift COPY 명령으로 적재(일일 배치 방식은 "거의 실시간" 요구에 크게 못 미치며, 여전히 파이프라인을 구축/관리해야 함).
- D. Redshift Spectrum으로 Aurora 스냅샷 데이터를 직접 쿼리(Redshift Spectrum은 S3 데이터 레이크의 외부 테이블을 쿼리하는 기능이며, Aurora 같은 운영 데이터베이스를 직접 쿼리하는 용도가 아님 — 개념 오류).

**정답: B**

**해설**
**Aurora zero-ETL 통합**은 Aurora(MySQL 호환)와 Amazon Redshift 간의 네이티브 통합 기능으로, 별도의 ETL 파이프라인을 구축/관리할 필요 없이 Aurora의 트랜잭션 데이터 변경 사항이 **자동으로 몇 초 이내에 Redshift에 복제**되어 거의 실시간 분석이 가능합니다. 이는 운영 데이터베이스와 데이터 웨어하우스 사이의 데이터 이동을 위한 커스텀 파이프라인 구축/유지 부담을 완전히 제거하는 최신 표준 솔루션입니다.

**왜 다른 보기는 오답인가**
- A: DMS도 가능하지만 여전히 별도의 복제 태스크를 구성/운영해야 하는 파이프라인 관리 부담이 남습니다.
- C: 일일 배치 방식은 실시간성 요구에 크게 부족합니다.
- D: Redshift Spectrum은 S3 데이터를 대상으로 하며 Aurora를 직접 쿼리하는 기능이 아닙니다.

> 💡 **시험 꿀팁**: **Aurora의 데이터를 별도 ETL 파이프라인 없이 거의 실시간으로 Redshift에서 분석**하려면 **Aurora zero-ETL 통합**이 표준 정답입니다.

## QUESTION 443

**문제**: 소매 체인점이 각 매장에 재고 관리·POS 처리를 위한 AWS 네이티브 컴퓨팅 자원을 두고 싶어하는데, 매장 공간이 매우 제한적이라 표준 Outposts 랙(전체 랙 크기)을 설치할 여유가 없다. 소규모 매장 환경에 맞는 더 작은 폼팩터의 AWS Outposts 옵션은?

**보기**
- A. 표준 Outposts 랙을 그대로 축소 설치(Outposts 랙은 고정된 랙 크기의 폼팩터이며 임의로 축소할 수 없음 — 개념 오류).
- B. **AWS Outposts 서버(1U 또는 2U 폼팩터)를 사용해, 랙 전체가 필요 없는 소규모 공간에도 설치 가능한 컴팩트한 형태로 AWS 네이티브 컴퓨팅/스토리지를 매장에 배치.**
- C. AWS Snowball Edge를 상시 설치형 인프라로 사용(Snowball Edge는 주로 데이터 전송/임시 엣지 처리용이며, 지속적인 프로덕션 워크로드를 위한 상시 설치형 컴퓨팅 인프라로 설계된 것은 Outposts 서버가 더 적합).
- D. 각 매장에 일반 온프레미스 서버를 구축하고 VPN으로 AWS와 연결(AWS 네이티브 API/도구를 그대로 사용하려는 Outposts의 핵심 이점을 포기하는 것이며, 일반 서버 구축/관리 부담을 스스로 떠안게 됨).

**정답: B**

**해설**
**AWS Outposts 서버**는 전체 랙이 필요 없는 소규모 공간(소매점, 지사 등)을 위해 설계된 **1U 또는 2U 폼팩터**의 소형 Outposts 옵션입니다. 표준 Outposts 랙보다 훨씬 작은 물리적 공간에 설치할 수 있으면서도, 동일한 AWS 네이티브 API, 서비스, 관리 도구를 사용해 매장 현장에서 저지연 로컬 처리(재고 관리, POS 등)를 수행할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Outposts 랙은 고정된 대형 폼팩터이며 임의로 축소할 수 있는 옵션이 아닙니다.
- C: Snowball Edge는 데이터 전송/임시 처리에 더 적합하며, 지속적인 프로덕션 워크로드의 상시 설치형 인프라로는 Outposts 서버가 표준입니다.
- D: 일반 온프레미스 서버 구축은 AWS 네이티브 통합이라는 Outposts의 핵심 이점을 포기하는 것입니다.

> 💡 **시험 꿀팁**: 공간이 제한적인 **소규모 현장(매장 등)에 AWS 네이티브 컴퓨팅**을 두려면 컴팩트한 **AWS Outposts 서버(1U/2U)**가 표준 정답입니다.

## QUESTION 444

**문제**: 보안 팀이 조직의 S3 버킷, IAM 역할, KMS 키 등에 대해, **의도하지 않게 외부 계정(조직 외부)이나 퍼블릭에 접근을 허용하는 리소스 기반 정책**이 있는지 자동으로 찾아내고 싶다. 각 리소스 정책을 수동으로 검토하는 것은 규모가 커서 비현실적이다. 솔루션은?

**보기**
- A. 각 팀에게 자신의 리소스 정책을 검토하도록 요청(수동 검토는 규모가 큰 조직에서 비현실적이고 일관성이 없으며 실수를 놓치기 쉬움).
- B. **IAM Access Analyzer를 사용해, S3, IAM 역할, KMS 키, Lambda 등 지원되는 리소스의 정책을 분석해 조직 외부 엔티티나 퍼블릭에 의도치 않게 접근을 허용하는 발견 사항(finding)을 자동으로 식별하고 지속적으로 모니터링.**
- C. Macie로 모든 리소스 정책을 스캔(Macie는 S3에 저장된 데이터 자체의 민감 정보(PII 등) 탐지에 특화되어 있으며, 리소스 정책의 외부 접근 허용 여부를 분석하는 기능은 IAM Access Analyzer의 역할).
- D. Config 규칙만으로 모든 외부 접근 패턴을 탐지(Config 규칙으로 일부 특정 조건은 만들 수 있지만, 다양한 리소스 유형에 걸쳐 정책 논리 자체를 분석해 의도치 않은 외부/퍼블릭 접근을 포괄적으로 자동 식별하는 것은 Access Analyzer가 전용으로 제공하는 기능).

**정답: B**

**해설**
**IAM Access Analyzer**는 논리적 추론(자동 추론) 기술을 사용해 S3 버킷, IAM 역할, KMS 키, SQS 큐, Lambda 함수 등의 **리소스 기반 정책을 분석**하고, 이 정책이 신뢰 영역(조직/계정) 외부의 엔티티나 퍼블릭에게 의도치 않게 접근을 허용하는지 **발견 사항(finding)**으로 자동 식별합니다. 새로운 정책이 생성/변경될 때마다 지속적으로 분석해, 수동 검토 없이도 조직 전체의 의도치 않은 외부 노출을 지속적으로 모니터링할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 수동 검토는 대규모 조직에서 비현실적이고 일관성이 없습니다.
- C: Macie는 데이터 콘텐츠의 민감 정보 탐지에 특화되어 있으며, 정책 자체의 외부 접근 허용 여부 분석은 Access Analyzer의 역할입니다.
- D: Config 규칙으로 일부는 가능하지만, 다양한 리소스 유형의 정책 논리를 포괄적으로 자동 분석하는 전용 기능은 Access Analyzer입니다.

> 💡 **시험 꿀팁**: 리소스 정책이 **의도치 않게 조직 외부/퍼블릭에 접근을 허용하는지 자동으로 찾아내려면** **IAM Access Analyzer**가 표준 정답입니다.

## QUESTION 445

**문제**: 규제 요구사항에 따라, S3 버킷의 객체가 업로드된 후 **정해진 시간(SLA) 이내에 반드시** 다른 리전으로 복제가 완료되었음을 보장하고 모니터링해야 한다. 표준 CRR은 "대부분 몇 분 이내"라는 목표는 있지만 보장된 SLA나 복제 지연 모니터링 지표를 제공하지 않는다. 솔루션은?

**보기**
- A. 표준 교차 리전 복제(CRR)만 사용하고 별도 조치 없음(표준 CRR은 복제 시간에 대한 보장된 SLA를 제공하지 않아 규제가 요구하는 "정해진 시간 이내 보장"이라는 요구를 충족하지 못함).
- B. **S3 복제 규칙에 복제 시간 제어(Replication Time Control, RTC)를 활성화해, 99.99%의 객체가 15분 이내에 복제되도록 보장하는 SLA를 적용하고, 복제 지연을 추적하는 CloudWatch 지표(S3 Replication metrics)로 모니터링.**
- C. 애플리케이션에서 객체 업로드 후 즉시 동기적으로 두 번째 리전에도 직접 업로드(애플리케이션 레벨 이중 업로드는 두 리전에 대한 별도 오류 처리, 재시도, 정합성 관리를 직접 구현해야 해서 복잡도가 크게 증가).
- D. 매시간 배치 작업으로 복제 상태를 수동 확인(수동 배치 확인은 실시간에 가깝지 않고 SLA 위반을 사전에 방지하지 못하며 사후 발견에 그침).

**정답: B**

**해설**

- C: 애플리케이션 레벨 이중 업로드는 복잡도와 운영 부담이 크게 증가합니다.

## QUESTION 458

**문제**: 개발 팀이 여러 오픈소스 컨테이너 이미지(Docker Hub 같은 퍼블릭 레지스트리)를 자주 사용하는데, 매번 퍼블릭 레지스트리에서 직접 풀(pull)하다 보니 속도가 느리고 레이트 리밋(rate limit)에 걸리는 경우가 있다. 자체적으로 모든 퍼블릭 이미지를 미리 다운로드해 자체 ECR 리포지토리에 수동으로 동기화하고 유지하고 싶지는 않다. 솔루션은?

**보기**
- A. 각 개발자가 개인적으로 이미지를 다운로드한 뒤 사내 파일 공유 서버에 업로드해 공유(수동 개별 관리 방식으로 확장성이 없고 이미지 최신화도 보장되지 않음).
- B. **Amazon ECR 풀스루 캐시(pull-through cache)를 구성해, 업스트림 퍼블릭 레지스트리(Docker Hub 등)에 대한 캐시 규칙을 설정. 개발자가 ECR을 통해 이미지를 요청하면 최초 요청 시 자동으로 업스트림에서 가져와 캐싱하고, 이후 요청은 캐시된 이미지를 빠르게 제공.**

- D. 모든 이미지를 수동으로 다운로드해 ECR에 개별적으로 푸시하고 정기적으로 최신화(수동 동기화 프로세스가 필요해 "수동으로 동기화하고 유지하고 싶지 않다"는 요구에 정면으로 반함).

**정답: B**

**해설**
**Amazon ECR 풀스루 캐시(pull-through cache)**는 Docker Hub, Quay 같은 업스트림 퍼블릭 레지스트리에 대한 캐시 규칙을 ECR에 설정해, 개발자가 ECR 엔드포인트를 통해 이미지를 요청하면 **최초 요청 시에만 업스트림에서 자동으로 가져와 ECR에 캐싱**하고, 이후의 동일 이미지 요청은 ECR에 캐싱된 사본을 빠르게 제공합니다. 수동으로 이미지를 미리 동기화/유지할 필요 없이, 자동으로 캐싱되면서 업스트림 레이트 리밋 문제와 속도 문제를 모두 개선하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 개인 수동 관리는 확장성이 없고 최신화가 보장되지 않습니다.
- C: Docker Hub는 AWS 서비스가 아니므로 VPC 인터페이스 엔드포인트 대상이 될 수 없습니다.
- D: 수동 동기화 프로세스는 이 문제가 명시적으로 피하고 싶다고 한 방식입니다.

> 💡 **시험 꿀팁**: 퍼블릭 레지스트리의 이미지를 **수동 동기화 없이 자동으로 캐싱**해 속도와 레이트 리밋 문제를 해결하려면 **Amazon ECR 풀스루 캐시(pull-through cache)**가 표준 정답입니다.

## QUESTION 459

**문제**: 회사가 Systems Manager Parameter Store에 애플리케이션 설정값과 함께 일부 민감한 설정(작지만 임계적인 시크릿)을 저장하는데, 표준(Standard) 계층의 크기 제한(4KB)을 초과하는 값이 일부 있고, 특정 파라미터에 대해서는 **일정 기간 후 자동 만료 알림**을 받고 싶다(예: 발급된 임시 인증서 갱신 알림). 솔루션은?

- A. 모든 파라미터를 Secrets Manager로 이전(가능한 방법이지만, 문제는 명시적으로 Parameter Store를 계속 사용하는 맥락에서 크기 제한과 만료 알림이라는 두 요구를 해결하는 방법을 묻고 있으며, Parameter Store 자체의 고급 기능으로 해결 가능).

- D. CloudWatch 알람으로 파라미터 값의 마지막 수정 시각을 모니터링(Parameter Store 값 자체의 변경 시각을 추적하는 표준적인 CloudWatch 지표가 없으며, 이는 파라미터 정책의 만료 알림 기능이 제공하는 것과는 다른 접근).

**왜 다른 보기는 오답인가**
- A: Secrets Manager로의 전면 이전도 가능하지만, 문제는 Parameter Store의 고급 계층 기능으로 두 요구를 해결하는 방법을 묻고 있습니다.
- C: 수동 분할은 애플리케이션 복잡성을 유발하고 만료 알림 문제를 해결하지 못합니다.
- D: 표준 CloudWatch 지표로는 파라미터 값 변경을 추적하는 기능이 파라미터 정책만큼 직접적이지 않습니다.

> 💡 **시험 꿀팁**: Parameter Store에서 **4KB를 초과하는 값 저장과 만료 알림**이 모두 필요하면 **고급(Advanced) 파라미터 계층 + 파라미터 정책(만료/알림)**이 표준 정답입니다.

## QUESTION 460

**문제**: 미디어 편집 회사가 Linux 기반 워크스테이션 플릿에서 사용할 공유 파일 스토리지가 필요한데, ZFS의 **스냅샷, 클론, 압축** 기능에 이미 익숙하며 이를 그대로 활용하고 싶고, 높은 IOPS와 낮은 지연시간도 필요하다. 관리형 서비스로 이를 구현하려면?

**보기**
- A. Amazon EFS 사용(EFS도 Linux용 관리형 파일 시스템이지만, ZFS 특유의 스냅샷/클론 시맨틱이나 이 정도의 매우 높은 IOPS/낮은 지연시간 프로파일에는 최적화되어 있지 않음).
- B. **Amazon FSx for OpenZFS를 사용해, ZFS의 스냅샷·클론·압축 기능을 그대로 제공하면서 높은 IOPS와 낮은 지연시간을 갖춘 관리형 공유 파일 시스템을 Linux 워크스테이션 플릿에 제공.**
- C. Amazon FSx for NetApp ONTAP 사용(ONTAP도 스냅샷/클론을 제공하지만 이는 NetApp의 자체 기술이며, 문제에서 명시적으로 요구하는 "ZFS" 고유의 기능/경험과는 다름).
- D. 각 워크스테이션에 로컬 스토리지만 사용하고 파일은 수동으로 동기화(로컬 스토리지는 공유 파일 스토리지 요구 자체를 충족하지 못하며 수동 동기화는 비현실적).

**정답: B**

**해설**
**Amazon FSx for OpenZFS**는 오픈소스 ZFS 파일 시스템을 기반으로 한 완전관리형 파일 스토리지 서비스로, ZFS의 핵심 기능인 **스냅샷, 클론(복제본이 원본과 스토리지를 공유해 즉각적이고 공간 효율적), 압축**을 그대로 제공합니다. 또한 매우 높은 IOPS와 낮은 지연시간을 지원해 미디어 편집처럼 성능이 중요한 Linux 기반 워크로드의 공유 파일 스토리지 요구에 적합한 표준 서비스입니다.

**왜 다른 보기는 오답인가**
- A: EFS는 Linux용 관리형 파일 시스템이지만 ZFS 고유의 기능과 이 정도의 성능 프로파일에는 최적화되어 있지 않습니다.
- C: FSx for NetApp ONTAP은 NetApp의 자체 스냅샷/클론 기술을 사용하며, 문제가 명시한 "ZFS" 경험과는 다릅니다.
- D: 로컬 스토리지는 공유 파일 시스템 요구 자체를 충족하지 못합니다.

> 💡 **시험 꿀팁**: Linux 워크로드에서 **ZFS의 스냅샷/클론/압축 기능과 고성능(높은 IOPS, 낮은 지연시간)을 갖춘 관리형 공유 파일 스토리지**가 필요하면 **Amazon FSx for OpenZFS**가 표준 정답입니다.
