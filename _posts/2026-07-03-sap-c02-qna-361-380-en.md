## QUESTION 361

**Question**: A company needs to give remote employees access to internal web applications (HR system, internal wiki, etc.), but their existing VPN approach tunnels all traffic, causing performance degradation and management complexity. They want a zero-trust model where users access applications individually **directly in the browser, with no VPN client installed**, evaluating user identity and device posture on every request. What's the solution?

**Choices**
- A. Only increase the bandwidth of the existing Site-to-Site VPN (the VPN's underlying architecture [tunneling the entire network] remains unchanged, failing to meet the "no VPN client, per-application zero-trust access" requirement).
- B. **Use AWS Verified Access to define per-application access policies integrated with IAM Identity Center and device-trust data providers, letting users access directly via browser with no VPN client, while identity/device posture is evaluated on every request.**
- C. Put API Gateway in front of each application and control access only with API keys (API keys alone can't implement fine-grained identity/device-posture-based zero-trust policy, nor easily support per-request dynamic evaluation).
- D. Expose all internal applications to the public internet and authenticate only with Cognito (exposing internal applications publicly greatly increases the attack surface, and lacks a core zero-trust element like device-posture evaluation).

**Correct Answer: B**

**Explanation**
**AWS Verified Access** is a service that controls access to internal applications according to zero-trust principles, with no VPN. Integrating with **IAM Identity Center** (identity) and third-party device-trust data providers (device posture) lets you define fine-grained per-application access policies (e.g., "only company-managed devices + MFA-authenticated users"), while users access applications directly via browser but are **continuously evaluated on identity and device posture on every request**. This is a more fine-grained and secure access model than a traditional VPN tunneling the entire network.

**Why the other choices are wrong**
- A: Increasing VPN bandwidth doesn't change the underlying architecture (full network tunneling), failing to meet the zero-trust requirement.
- C: API keys alone can't implement dynamic zero-trust evaluation of identity/device posture.
- D: Publicly exposing internal applications increases the attack surface and lacks a core zero-trust element like device-posture evaluation.

> 💡 **Exam tip**: For **per-application zero-trust access** (identity + device-posture-based) with no VPN client, **AWS Verified Access** is the standard answer.

## QUESTION 362

**Question**: A production RDS MySQL database needs a major version upgrade (e.g., 5.7 → 8.0), and they must be able to **revert immediately** to the original version if application compatibility issues are found, while minimizing downtime and risk from the upgrade. What's the solution?

**Choices**
- A. Perform an in-place major version upgrade directly on the production instance (an in-place upgrade is very hard or impossible to revert, requiring a complex, time-consuming rollback procedure like a snapshot restore if problems occur).
- B. **Use RDS Blue/Green Deployments to create a separate, synchronized green environment with the upgraded new version alongside production (blue), test it thoroughly, then quickly switch over if there are no issues — or discard the green environment and keep the blue environment as-is if problems are found.**
- C. Upgrade a read replica to the new version and then promote it to primary (a read replica maintaining a different engine version than the primary is technically restrictive, and this isn't a dedicated mechanism for safe pre-isolation testing and fast rollback).
- D. Briefly stop the application, manually dump/restore, and import into the new version (manual dump/restore causes very long downtime on a large database, and rollback is also complex if problems occur).

**Correct Answer: B**

**Explanation**
**RDS Blue/Green Deployments** creates an isolated **green environment** with the upgraded new version, synchronized (via logical replication) with production (blue), letting you test thoroughly with no impact on production. If testing is satisfactory, a **fast switchover** makes the green environment the new production; if a problem is found, simply discard the green environment and keep the existing blue environment — minimizing both risk and downtime for a major version upgrade, the standard method.

**Why the other choices are wrong**
- A: An in-place upgrade is hard to revert and very complex to handle if a problem occurs.
- C: Running a read replica on a different major version has many restrictions and isn't a dedicated pre-test/fast-rollback mechanism.
- D: Manual dump/restore causes very long downtime on a large dataset.

> 💡 **Exam tip**: To safely perform a **major version upgrade** (with pre-testing + fast rollback capability) on RDS/Aurora, **Blue/Green Deployments** is the standard answer.

## QUESTION 363

**Question**: A company needs to bulk-tag or copy objects matching a specific condition (e.g., created before 2023, a specific prefix) out of billions of objects stored in S3, to another bucket. The object count is too large for individual API calls to be practical. What's the solution?

**Choices**
- A. List each object and repeatedly invoke a Lambda function to tag/copy individually (managing billions of individual API calls yourself [retries, progress tracking, rate limiting, etc.] is very inefficient and hard to recover from errors).
- B. **Use S3 Batch Operations, specifying the target object list via an S3 Inventory report or CSV manifest as input, and run a large-scale tagging (PUT object tagging) or copy operation, with progress and failed items automatically tracked.**
- C. Download all objects to an application, process locally, and re-upload (downloading/re-uploading billions of objects incurs enormous time and cost — very inefficient).
- D. Use an S3 lifecycle policy to automatically tag objects (lifecycle policies are for storage-class transitions or expiration and don't offer a feature for bulk-tagging with arbitrary conditions or copying to another bucket).

**Correct Answer: B**

**Explanation**
**S3 Batch Operations** is a managed feature for running operations — tagging, copying, ACL changes, Object Lock retention settings, invoking a Lambda function, etc. — **at scale** across a set of objects numbering in the billions. Specifying the target object list via an S3 Inventory report or a CSV manifest, it tracks job progress and automatically generates a report of failed items, letting you reliably perform large-scale object operations with no need to manage individual API calls yourself.

**Why the other choices are wrong**
- A: Managing billions of API calls yourself requires implementing your own retry/tracking/rate-limiting logic — very inefficient.
- C: Downloading/re-uploading the entire object set is impractical in time and cost.
- D: Lifecycle policies are for storage-class transitions/expiration and don't offer arbitrary bulk-tagging or copy features.

> 💡 **Exam tip**: To reliably perform **bulk tagging/copying/other operations on a large-scale object set (billions of objects)** in S3, **S3 Batch Operations** is the standard answer.

## QUESTION 364

**Question**: A Lambda function written in Python experiences cold-start delay from importing a large machine-learning library. This function's runtime doesn't support SnapStart (SnapStart is currently limited to Java, Python, and some .NET runtimes — this scenario assumes a specific unsupported runtime/configuration). Given a predictable traffic pattern (concentrated during business hours), what's an alternative to eliminate cold starts?

**Choices**
- A. Fully rewrite the function code to remove the library dependency (may require giving up core machine-learning functionality itself — high risk of conflicting with functional requirements).
- B. **Integrate with Application Auto Scaling to pre-adjust the amount of Provisioned Concurrency on a schedule, matched to the predictable traffic pattern (e.g., before business hours start).**
- C. Convert the function to a container-image base (a container-image-based Lambda can actually have longer cold starts if the image is large, and this itself isn't a feature that eliminates cold starts).
- D. Increase the function's timeout to the maximum (timeout only extends the maximum executable duration and is unrelated to cold-start delay itself).

**Correct Answer: B**

**Explanation**
**Provisioned Concurrency** maintains pre-initialized execution environments, categorically eliminating cold starts. If traffic follows a **predictable pattern** — e.g., concentrated during business hours — integrating with Application Auto Scaling's **scheduled scaling** lets you increase the amount of Provisioned Concurrency right before traffic surges and reduce it during low-traffic nights/weekends, minimizing unnecessary standing cost while achieving cold-start-free responsiveness.

**Why the other choices are wrong**
- A: Removing the library dependency is a fundamental redesign risking loss of core functionality.
- C: Switching to a container image isn't itself a cold-start-eliminating feature, and can actually worsen it depending on image size.
- D: Adjusting timeout is a separate setting unrelated to cold-start delay.

> 💡 **Exam tip**: For a runtime that can't use SnapStart, to eliminate cold starts matched to a **predictable traffic pattern**, **scheduled Provisioned Concurrency (Provisioned Concurrency + Application Auto Scaling scheduled scaling)** is the standard answer.

## QUESTION 365

**Question**: A multi-tenant SaaS company wants to **accurately allocate** shared AWS infrastructure costs (multiple customers sharing the same EC2/RDS/Lambda) **per individual customer tenant**. The resources themselves aren't clearly separated by account or tag, but application logs record a tenant identifier. What's the solution?

**Choices**
- A. Tag all resources with a tenant ID and check cost by tag in Cost Explorer (since the resources themselves are shared across multiple tenants, resource-level tagging alone can't provide fine-grained, usage-based allocation per individual tenant — it can't reflect the actual usage ratio of each tenant within a shared resource).
- B. **Use AWS Application Cost Profiler to accurately allocate shared infrastructure cost to individual tenants based on usage data the application itself reports (per-tenant resource consumption).**
- C. Provision a completely separate AWS account and infrastructure for each customer (abandons the efficiency of shared infrastructure entirely and requires a large-scale redesign of the existing architecture).
- D. Simply divide total cost evenly by the number of customers (doesn't reflect usage differences at all, failing the "accurate allocation" requirement, and unfairly benefits high-usage customers).

**Correct Answer: B**

**Explanation**
**AWS Application Cost Profiler** collects **per-tenant resource usage data** (CPU time, memory, API call counts, etc.) that a multi-tenant application reports itself, and generates a report that accurately allocates shared AWS infrastructure cost to individual tenants based on actual usage ratios. It's specialized for implementing accurate cost allocation in a SaaS architecture where resources aren't physically separated per tenant.

**Why the other choices are wrong**
- A: Since resources are shared across multiple tenants, resource-level tagging alone can't distinguish actual per-tenant consumption.
- C: Completely separating accounts abandons shared infrastructure efficiency — a large-scale redesign.
- D: Simple even division doesn't reflect actual usage differences and is inaccurate.

> 💡 **Exam tip**: For a multi-tenant SaaS to **accurately allocate shared infrastructure cost per tenant based on application usage data**, **AWS Application Cost Profiler** is the standard answer.

## QUESTION 366

Instead of manually cross-analyzing multiple log sources (VPC Flow Logs, CloudTrail, DNS logs, GuardDuty findings), what service accelerates security investigation?

**Choices**
- A. Repeatedly check only the finding details in the GuardDuty console (GuardDuty provides information about individual findings, but isn't a dedicated investigation feature that automatically integrates and analyzes multiple log sources to visualize a full activity timeline for an actor/resource).
- B. **Use Amazon Detective, which automatically collects/normalizes data from multiple sources like GuardDuty, VPC Flow Logs, and CloudTrail, and lets you explore activity related to a specific resource, IP, or user chronologically via graph-based visualization, quickly identifying the root cause.**

- D. Only check the AWS Config resource timeline (Config shows resource configuration change history, but doesn't provide integrated analysis of the broader activity data — network traffic, API call patterns — needed for a security investigation).

## QUESTION 367

**Question**: A global enterprise operates a complex global network spanning VPCs in multiple Regions, on-premises data centers, and SD-WAN branch offices, and wants to **declaratively manage the connectivity and policy (routing, segmentation) of all these network segments from a single central dashboard**. Previously, manually peering each Region's Transit Gateway individually caused very high complexity. What's the solution?

**Choices**
- A. Keep peering each Region's Transit Gateway individually but just add automation scripts (the underlying architecture of individual TGW peering remains unchanged, so the complexity problem itself isn't solved, and per-Region individual management is still needed).
- B. **Use AWS Cloud WAN to define the global network from a central dashboard (a core network policy document), declaratively managing segments across multiple Regions, on-premises, and SD-WAN, with AWS automatically configuring inter-Region connectivity.**
- C. Concentrate all traffic through a single Region's Transit Gateway and manage policy only there (concentrating on a single Region causes unnecessary detour routes and latency for other Regions' traffic — inefficient for a globally distributed architecture).
- D. Configure individual Direct Connect per branch and manage policy individually at each branch's on-premises router (the opposite of a centralized management requirement, and harder to keep policy consistent as branches grow).

**Correct Answer: B**

**Explanation**
**AWS Cloud WAN** is a managed service that lets you declaratively define and manage a complex global network — spanning multiple Regions, on-premises, and SD-WAN — from a **single central dashboard** via a **core network policy document**. - C: Concentrating on a single Region causes unnecessary detours and latency for other Regions — inefficient.

> 💡 **Exam tip**: To **declaratively manage a complex global network** spanning multiple Regions/on-premises/SD-WAN from a central location, **AWS Cloud WAN** is the standard answer.

## QUESTION 368

**Question**: A company wants to build an SFTP-based file exchange service on AWS, where user authentication must go through the company's **existing custom user database** (a self-built LDAP-like system), and they don't want to create individual IAM users. How do you implement this in AWS Transfer Family?

**Choices**
- A. Write a script to automatically create an IAM user for every SFTP user (creating/managing individual IAM users for thousands of users carries heavy operational burden, may run into IAM user limits, and contradicts the requirement to keep using the existing custom user database).
- B. **Use AWS Transfer Family's custom identity provider integration feature to delegate authentication to the existing custom user database via API Gateway and Lambda.**
- C. Build a custom SFTP server on EC2 instead of Transfer Family, implementing a custom authentication module directly (gives up the benefits of a managed service and takes on server-operation burden yourself, when Transfer Family already provides an integration feature for this exact requirement).

**Correct Answer: B**

## QUESTION 369

**Question**: The security team wants to enforce that EC2 instance metadata service **must use only IMDSv2** (disabling IMDSv1) across every account in the organization. They need this centrally enforced at the account-level default-setting level, per Region/service, so it can't be reverted by an individual account administrator's mistake or intentional change. When an SCP alone has limited ability to declaratively enforce a "setting value itself" this way, what relatively recent Organizations feature can be used?

**Choices**
- A. Use an AWS Config rule in each account to detect instances not using IMDSv2 and just get notified (detection/notification is only after-the-fact discovery — not a preventive enforcement blocking the setting from being changed in the first place).
- B. **Use Organizations declarative policies to centrally declare EC2's default metadata options as requiring IMDSv2 across all accounts in the organization (and future new accounts), preventing individual accounts from deviating from this default.**
- C. Write an SCP with a conditional policy explicitly denying IMDSv1 use (an SCP is powerful for controlling an IAM principal's API-call permissions, but declarative policies are more specialized and simpler to implement for declaratively unifying a service's default setting value itself at instance-launch time and categorically preventing per-account changes).
- D. Distribute an internal guideline document instructing teams to use IMDSv2 (a document-based guideline has no enforcement power and can't prevent mistakes or intentional violations).

**Correct Answer: B**

**Explanation**
**Organizations declarative policies**, unlike an SCP (which controls IAM permissions), let you organization-wide declaratively define a specific AWS service's **default behavior/setting itself** (e.g., requiring IMDSv2 for EC2 instance metadata options), categorically preventing individual accounts from arbitrarily changing this setting. It also automatically applies to newly created accounts — a relatively recent feature that precisely fits the requirement of "centrally, declaratively enforcing a setting value itself."

**Why the other choices are wrong**
- A: Config-rule-based detection is only after-the-fact discovery — it doesn't prevent the setting change itself in advance.
- C: An SCP can also be configured to conditionally deny the relevant API call, but a declarative policy is more direct and simpler for the goal of declaratively unifying a service's default setting itself.
- D: A document-based guideline has no enforcement power at all.

> 💡 **Exam tip**: To **declaratively unify a specific service's default setting value organization-wide and categorically block individual account changes**, **Organizations declarative policies** is the standard answer.

## QUESTION 370

**Question**: A company stores important log/search data in an Amazon OpenSearch Service domain, and needs to quickly resume service in another Region during a Regional disaster. Snapshot-based backup/restore is judged to have too long an RPO. What's the solution?

**Choices**
- A. Create a manual snapshot every hour and copy it to another Region's S3 (a manual snapshot-based approach has an RPO of at least an hour, similar to the approach already judged "too long" — not much improvement).
- B. **Use OpenSearch Service's cross-cluster replication feature to configure a follower domain in another Region, continuously replicating data, and promote the follower index during a failure.**
- C. Have the application send every indexing request to both Regions' OpenSearch domains simultaneously (application-level dual writes require the application itself to handle indexing failures/inconsistencies between two clusters — high complexity and risk, less stable than a native replication feature).
- D. Periodically export OpenSearch data to S3 and re-index from scratch in another Region (re-indexing takes a long time for large data volumes and doesn't provide a near-real-time RPO).

**Correct Answer: B**

**Explanation**
**Amazon OpenSearch Service's cross-cluster replication** continuously (near-real-time) replicates a leader domain's index changes to a **follower domain** in another Region. During a Regional disaster, promoting the follower index to a writable state lets service resume with a short RPO — a much shorter RPO than manual snapshot-based backup/restore, the standard DR method.

**Why the other choices are wrong**
- A: A manual snapshot approach is essentially similar to the approach already judged to have too long an RPO.
- C: Application-level dual writes carry very high consistency-management complexity and risk.
- D: Periodic re-indexing takes a long time for large data volumes and doesn't provide a short RPO.

> 💡 **Exam tip**: For **short-RPO cross-Region disaster recovery** on OpenSearch Service, **cross-cluster replication** is the standard answer.

## QUESTION 371

**Question**: A Lambda function is invoked asynchronously by S3 events, and they want the result **automatically routed to one SQS queue on success and a different SQS queue (acting as a DLQ) on failure**, without implementing success/failure handling and retry logic directly in the function code. What's the solution?

**Choices**
- A. Use try-catch at the end of the function code to determine success/failure and publish to a different SQS directly for each (requires implementing this logic directly in the function code, contradicting the "don't want to implement this in code" requirement, and can't capture situations like the function's own timeout or crash).
- B. **In the Lambda function's destinations configuration, specify a different SQS queue each for the asynchronous invocation's success (OnSuccess) and failure (OnFailure) destination, so the Lambda service automatically routes based on the execution result.**
- C. Create an EventBridge rule to detect Lambda execution-completion events and branch accordingly (not a standard way to detect asynchronous invocation completion, and creates an unnecessarily complex workaround when Lambda's built-in destinations feature already exists).
- D. Wrap the Lambda call in Step Functions and branch based on success/failure state (a viable approach, but introducing an entire Step Functions workflow is overly complex for a case needing only simple success/failure routing).

**Correct Answer: B**

**Explanation**
The **Lambda destinations** feature **automatically routes** to a specified destination (SQS, SNS, EventBridge, another Lambda function) based on the **success (OnSuccess) or failure (OnFailure)** result of an asynchronous invocation, with no code changes. This lets you declaratively configure follow-up processing (splitting into success/failure queues) based on the execution result — including failures from the function's own timeout or crash — without implementing separate logic in the function code.

**Why the other choices are wrong**
- A: Requires implementing this directly in the function code, contradicting the requirement, and can't catch the function's own crash/timeout via an internal try-catch.
- C: Routing through EventBridge is unnecessarily complex when Lambda's built-in destinations feature already exists.
- D: Introducing a full Step Functions workflow is overkill for a case needing only simple success/failure branching.

> 💡 **Exam tip**: To **automatically route a Lambda asynchronous invocation's result to a different destination (SQS, etc.) based on success/failure**, with no function code changes, the **Lambda destinations** feature is the standard answer.

## QUESTION 373

**Question**: A financial company has a Direct Connect redundant setup (two separate connections), and wants to **regularly test that failover to the backup path actually works correctly**, before a real failure occurs, with no impact on production traffic. Instead of a risky manual test that physically severs a circuit, what feature can be used?

**Choices**
- A. Have someone physically remove the Direct Connect circuit cable to test (a dangerous, hard-to-control manual physical intervention with a risk of unexpected impact or delayed recovery).
- B. **Use the Direct Connect console's connection test (Direct Connect failover test) feature to software-down a specific virtual interface's BGP session for a set duration, safely verifying that traffic actually switches to the alternate path.**
- C. Create a new test virtual interface each time to verify separately from the actual connection (a separate test virtual interface doesn't verify failover of the actual production traffic path itself — it tests a different configuration, missing the point).

- A: Physically removing a cable is dangerous, hard to control, and risks unexpected side effects.
- C: A separate test virtual interface doesn't verify failover of the actual production path.

## QUESTION 374

**Question**: They need to deploy a new AMI with a security patch to EC2 instances running in an Auto Scaling group. They want to **gradually replace all running instances with the new-AMI-based instance with no service disruption**, and want the rollout to automatically halt if a problem is found. What's the solution?

**Choices**
- A. Only update the launch template's AMI ID and leave existing instances as-is (updating the launch template only applies to future newly launched instances — it doesn't automatically replace existing running instances).
- B. **Use the Auto Scaling group's Instance Refresh feature, specifying a new launch template version (new AMI), configuring a minimum healthy percentage and warm-up time to gradually replace instances, along with a CloudWatch-alarm-based rollback condition.**
- C. Terminate all existing instances at once and let Auto Scaling relaunch with the new AMI (terminating all instances simultaneously causes a service disruption, directly contradicting the "no service disruption" requirement).
- D. Create a completely separate second Auto Scaling group with the new AMI and manually scale down the existing group (viable, but requires managing two groups in parallel and manually adjusting load balancer attachment — more operational complexity than Instance Refresh's integrated, automated gradual replacement).

**Correct Answer: B**

**Explanation**
The Auto Scaling group's **Instance Refresh** feature gradually replaces instances (in batches), targeting a new launch template version (including the patched new AMI), configured with a **minimum healthy percentage** (minimum service capacity to maintain during replacement) and a **warm-up time**. Attaching a CloudWatch alarm as a rollback trigger means the refresh **automatically halts** if a metric goes out of bounds during replacement — a standard feature meeting every requirement in this question (gradual replacement, no service disruption, automatic rollback).

**Why the other choices are wrong**
- A: Updating only the launch template leaves existing running instances unreplaced.
- C: Terminating everything at once causes a service disruption, contradicting the requirement.
- D: Running a parallel separate group is viable but carries more manual management burden than Instance Refresh.

> 💡 **Exam tip**: To replace an Auto Scaling group's instances with a new AMI **gradually, with no service disruption, and automatic rollback on problems**, **Instance Refresh** (minimum healthy percentage + alarm-based rollback) is the standard answer.

## QUESTION 375

**Question**: A global e-commerce company runs a shopping-cart service on DynamoDB global tables allowing **simultaneous (active-active) writes** across multiple Regions. They want to understand what happens, on the rare occasion the same item is modified almost simultaneously in two different Regions, to which value ultimately gets applied. What's DynamoDB global tables' conflict-resolution approach?

**Choices**
- A. Whichever write arrives at a Region first always takes priority (this is based on the last write's timestamp, not arrival order — describing it as arrival-order-based is itself inaccurate).
- B. **DynamoDB global tables use a "last writer wins" approach: each Region's write is assigned an internal timestamp, and among writes occurring simultaneously across multiple Regions, the write with the most recent timestamp is ultimately applied across all Regions.**
- C. On conflict, both values are merged and stored (DynamoDB global tables don't offer a feature to merge values themselves — only one value is ultimately adopted via last-writer-wins).
- D. On conflict, an error is returned to the application requiring manual resolution (global tables don't return a conflict error to the application — conflicts are automatically resolved internally [last writer wins] and ultimately converge to the same value across all Regions).

**Correct Answer: B**

**Explanation**
**DynamoDB global tables** automatically resolve write conflicts across multiple Regions using a **"last writer wins"** approach. Each Region's write is internally assigned a timestamp, and when the same item is written almost simultaneously in multiple Regions, **the write with the most recent timestamp wins**, ultimately converging to that value across all Regions via eventual consistency. This is a built-in conflict-resolution mechanism that happens automatically with no application intervention.

**Why the other choices are wrong**
- A: The accurate description is "last write" based on timestamp, not arrival order.
- C: No feature is provided to merge values — only one value is ultimately adopted.
- D: No error is returned to the application — resolution happens automatically internally.

> 💡 **Exam tip**: Remember that DynamoDB global tables' **multi-Region simultaneous-write conflicts** are automatically resolved via **last writer wins (based on timestamp)**, with no application intervention.
