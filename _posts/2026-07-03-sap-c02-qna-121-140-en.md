## QUESTION 121

**Question**: A financial company is migrating a web app from on-premises to AWS EC2 (dedicated VPC, ASG). It has used a third-party security tool (15 years, no cloud version) to inspect all inbound/outbound traffic **in real time, without impacting performance.** High availability within the Region is also required. (Choose two.)

**Choices**
- A. **Deploy the security tool on EC2 instances in a new Auto Scaling group in the existing VPC.**
- B. Deploy the web application behind a Network Load Balancer.
- C. Deploy an Application Load Balancer in front of the security tool instances.
- D. **Provision a Gateway Load Balancer in each Availability Zone to redirect traffic to the security tool.**
- E. Provision a Transit Gateway to facilitate communication between VPCs.

**Correct Answer: A, D**

**Explanation**
**Gateway Load Balancer (GWLB)** is purpose-built for exactly this scenario: transparently inserting a legacy (non-cloud-native) third-party appliance into the traffic path. Placing a GWLB in each AZ to redirect traffic to the security tool instances (A) provides scalability and HA without needing the tool itself to be cloud-adapted.

**Why the other choices are wrong**
- B: Placing the web app behind an NLB is unrelated to the core need of inserting the security tool into the traffic path.
- C: Putting an ALB in front of the security tool isn't the standard GWLB-based inspection architecture.
- E: A Transit Gateway is for VPC-to-VPC communication, unrelated to inserting an inspection appliance within a single VPC's traffic.

> 💡 **Exam tip**: To transparently insert a legacy third-party security/inspection appliance into the traffic path with HA and no performance impact, think **Gateway Load Balancer (one per AZ)** — the standard AWS answer pattern.

## QUESTION 122

**Question**: A company buys appliances from various vendors, each with IoT sensors sending status info in proprietary formats to a legacy app that parses it to JSON (each vendor's format differs). The app parses all JSON records once daily and stores them in a relational database. Design a faster, more cost-optimized data analytics solution.

**Choices**
- A. **Connect the IoT sensors to AWS IoT Core. Set up a rule invoking a Lambda function to parse the info and store .csv files in S3. Use AWS Glue to catalog the files. Use Amazon Athena and Amazon QuickSight for analysis.**
- B. Migrate the application server to AWS Fargate and store parsed info in Amazon Redshift.
- C. Create AWS Transfer for SFTP, and update the IoT sensor code to transfer via SFTP.
- D. Use AWS Snowball Edge to collect data directly from the sensors and periodically ingest into Redshift.

**Correct Answer: A**

**Explanation**
Using **AWS IoT Core** for ingestion, **Lambda** for per-vendor parsing, and **Glue + Athena + QuickSight** for fully serverless storage/analysis is a much faster, more cost-optimized redesign than the existing daily-batch relational pipeline.

**Why the other choices are wrong**
- B: Moving the app server to Fargate keeps the same receive-parse-store architecture and adds a continuously-running Redshift cluster cost, failing "faster and cost-optimized."
- C: Reprogramming diverse proprietary vendor IoT sensor code to use SFTP is impractical, and doesn't leverage IoT Core's native ingestion.
- D: Snowball Edge is for bulk, one-time transfers — not a continuous, real-time sensor data pipeline.

> 💡 **Exam tip**: For continuous IoT sensor data ingestion with per-vendor format variability, the standard combo is **IoT Core (ingestion) + Lambda (parsing) + S3+Glue+Athena/QuickSight (serverless storage and analysis).**

## QUESTION 123

**Question**: A company migrating apps wants to finalize networking/security quickly. A central network account has Direct Connect, and it expects **hundreds** of accounts/VPCs soon. The company network needs seamless access to all VPCs, and wants to **route cloud resources' internet traffic through the on-premises data center.** (Choose three.)

**Choices**
- A. Create Direct Connect Gateway connection proposals using account IDs and virtual private gateways.
- B. **Create a Direct Connect Gateway and Transit Gateway in the central network account. Attach the Transit Gateway to the DXGW via a transit VIF.**
- C. Provision an internet gateway, attach it to a subnet, and allow internet traffic through it.
- D. **Share the Transit Gateway with other accounts. Attach VPCs to the Transit Gateway.**
- E. Provision VPC peering as needed.
- F. **Provision only private subnets. Open the necessary routes on the Transit Gateway and customer gateway so AWS's outbound internet traffic flows through a NAT service running in the data center.**

**Correct Answer: B, D, F**

**Explanation**
**DXGW+TGW (transit VIF)** provides scalable on-premises-to-many-VPCs connectivity (B), **sharing the TGW via RAM** connects hundreds of VPCs (D), and using **only private subnets** with routes directing outbound internet traffic through on-premises NAT satisfies the "route through the data center" requirement (F).

**Why the other choices are wrong**
- A: The older account-ID/VGW-based DX sharing method doesn't scale to hundreds of accounts/VPCs.
- C: Direct internet gateway access directly contradicts "route through on-premises" requirement.
- E: VPC peering "as needed" doesn't scale to hundreds of VPCs (non-transitive, doesn't scale well).

> 💡 **Exam tip**: At hundreds-of-accounts/VPCs scale, use **DXGW+TGW (transit VIF) + RAM sharing.** To route internet traffic through on-premises, use **private-subnet-only VPCs** with routes pointing back through the TGW/customer gateway to on-premises NAT.

## QUESTION 124

**Question**: A company with hundreds of accounts wants to switch Reserved Instance purchasing/modification to a centralized process (via a dedicated team), replacing autonomous per-business-unit purchasing. Enforce the new process as securely as possible. (Choose two.)

**Choices**
- A. **Ensure all AWS accounts belong to an AWS Organizations organization with "all features" enabled.**
- B. Use AWS Config to report on whether a denying IAM policy is attached.
- C. Create an individual IAM policy denying RI actions in each account.
- D. **Create an SCP denying `ec2:PurchaseReservedInstancesOffering` and `ec2:ModifyReservedInstances`, applied to each OU.**
- E. Ensure all accounts belong to an organization using only "consolidated billing."

**Correct Answer: A, D**

**Explanation**
SCPs require Organizations' **"all features"** to be enabled (A, an often-overlooked prerequisite). With that in place, an **SCP denying RI purchase/modification** applied org-wide (D) is the most centralized and secure enforcement.

**Why the other choices are wrong**
- B: Config-based "reporting" is detective, not a true preventive block.
- C: Replicating the same IAM policy across hundreds of accounts individually is far more maintenance-heavy and less consistent than one org-wide SCP.
- E: SCPs require "**all features**" — "consolidated billing" alone isn't sufficient.

> 💡 **Exam tip**: **SCPs require "All Features" enabled in Organizations** (not just consolidated billing). For restrictions across many accounts, a single **org-wide SCP** is more secure and maintainable than per-account IAM policies or Config-based reporting.

## QUESTION 125

**Question**: A critical app uses RDS for MySQL Multi-AZ; a recent failover test caused **40 seconds** of downtime. Reduce it to **under 20 seconds.** (Choose three.)

**Choices**
- A. ElastiCache for Memcached in front of the database.
- B. ElastiCache for Redis in front of the database.
- C. **Use RDS Proxy in front of the database.**
- D. **Migrate the database to Amazon Aurora MySQL.**
- E. **Create an Aurora Replica.**
- F. Create an RDS for MySQL read-only replica.

**Correct Answer: C, D, E**

**Explanation**
**Aurora's native failover is much faster than standard RDS Multi-AZ**, and having an **Aurora Replica** ready for promotion speeds it up further. **RDS Proxy** in front masks reconnection downtime from the application during failover.

**Why the other choices are wrong**
- A, B: ElastiCache reduces read load but has nothing to do with the **failover duration itself** (write availability gap).
- F: An RDS for MySQL read replica (unlike Aurora Replicas) is **not part of the automatic failover mechanism** — it requires manual promotion.

> 💡 **Exam tip**: To reduce Multi-AZ database failover time, combine **migrating to Aurora + Aurora Replicas + RDS Proxy.** Caching doesn't help failover duration, and plain RDS read replicas aren't automatic failover targets.

## QUESTION 126

**Question**: An AWS partner (org1) needs API/CLI access to a customer account's resources in a separate organization (org2), with minimum-privilege security. Most secure approach?

**Choices**
- A. The customer gives the partner AWS account login access keys.
- B. The customer creates an IAM user and shares its credentials with the partner.
- C. The customer creates an IAM role; the partner uses only the role's ARN.
- D. **The customer creates an IAM role; the partner uses the role's ARN plus an External ID in the trust policy.**

**Correct Answer: D**

**Explanation**
This is the standard **cross-account role assumption with an External ID** pattern, specifically recommended by AWS for **third-party partners accessing many unrelated customer accounts.** The External ID prevents the "confused deputy" problem.

**Why the other choices are wrong**
- A, B: Sharing account keys or IAM user credentials directly is a severe security anti-pattern — unscoped, hard to revoke.
- C: Without an External ID, the partner is vulnerable to the "confused deputy" problem when handling multiple customer accounts.

> 💡 **Exam tip**: For a **third-party partner accessing many customer accounts** (a classic SaaS integration pattern), use a **role ARN + a unique External ID** in the trust policy — the AWS-recommended defense against the "confused deputy" problem.

## QUESTION 127

**Question**: A shipping company migrates a third-party route-planning app (public registry Docker image); delivery areas are divided into sections, each with its own configured set of containers. Allocate resources cost-effectively based on the number of running containers, with minimal operational overhead.

**Choices**
- A. An EKS cluster on EC2 + EKS CLI `--tags` on pods.
- B. An EKS cluster on Fargate + `tag-resource` API for pod tags.
- C. An ECS cluster on EC2 + `--tags` on tasks.
- D. **An ECS cluster on AWS Fargate, launching via `run-task` with `enableECSManagedTags=true`, assigning custom tags to tasks via `--tags`.**

**Correct Answer: D**

**Explanation**
**Fargate** (no server/cluster management, cost tied precisely to running tasks) combined with **native ECS task tagging** (`run-task --tags`, `enableECSManagedTags`) is the standard way to organize section-specific containers by tag with minimal overhead.

**Why the other choices are wrong**
- A, B: Kubernetes (EKS) doesn't use this AWS `--tags`/`tag-resource` mechanism for pods (it uses labels/annotations) — mismatched tagging approach.
- C: ECS on EC2 still requires managing the underlying instances, more overhead than Fargate, and cost ties to provisioned EC2 capacity, not precisely to running container count.

> 💡 **Exam tip**: For cost tied directly to running container count with minimal overhead, use **ECS on Fargate** with **native ECS task tagging** — not EKS/Kubernetes, which doesn't use this tagging mechanism.

## QUESTION 128

**Question**: Peering an Application VPC (us-east-1, CIDR 10.10.0.0/16) with a Shared Services VPC in another account (us-east-2, CIDR 10.10.10.0/24) fails. What could cause this? (Choose two.)

**Choices**
- A. **The two VPCs' IPv4 CIDR ranges overlap.**
- B. The VPCs aren't in the same Region.
- C. One or both accounts lack internet gateway access.
- D. One VPC wasn't shared via AWS RAM.
- E. **The peer accepter account's IAM role lacks the correct permissions.**

**Correct Answer: A, E**

**Explanation**
`10.10.10.0/24` is entirely contained within `10.10.0.0/16` — these CIDRs **actually overlap**, a hard blocker for VPC peering (A). Additionally, cross-account peering acceptance requires correct **IAM permissions on the peer accepter side** (E), or the request fails.

**Why the other choices are wrong**
- B: VPC peering **explicitly supports different Regions.**
- C: Internet gateway access is unrelated to VPC peering.
- D: AWS RAM is unrelated to the VPC peering process itself.

> 💡 **Exam tip**: The most common VPC peering failure causes are **① actually overlapping CIDR ranges** (calculate the real overlap, don't just eyeball "they look different") and **② insufficient IAM permissions on the peer accepter.**

## QUESTION 129

**Question**: An external audit finds overly-permissive IAM policies on Lambda execution roles (broad S3/DynamoDB access across hundreds of functions). Determine each function's minimum required permissions with minimal effort.

**Choices**
- A. Set up Amazon CodeGuru to profile Lambda functions and detect API calls.
- B. **Turn on CloudTrail logging, and use AWS IAM Access Analyzer to generate IAM policies based on CloudTrail activity**, then review.
- C. Write a custom script parsing CloudTrail logs to generate summary reports.
- D. Export CloudTrail logs to S3 and process them with Amazon EMR.

**Correct Answer: B**

**Explanation**
**IAM Access Analyzer's policy generation feature** automatically creates a least-privilege policy for a role based on its actual CloudTrail activity — a native, minimal-effort AWS feature exactly solving this problem.

**Why the other choices are wrong**
- A: CodeGuru is a code quality/performance profiler — it doesn't generate IAM policies from API call patterns.
- C: A custom log-parsing script reimplements what Access Analyzer already provides natively.
- D: Using EMR for this is an unnecessarily heavyweight big-data pipeline.

> 💡 **Exam tip**: To right-size overly-permissive IAM roles based on actual usage, use **IAM Access Analyzer's policy generation feature** first — far less effort than custom log analysis or EMR.

## QUESTION 130

**Question**: Several large, high-capacity EC2 instances host an active/passive database cluster; utilization varies unpredictably with no identified pattern. Analyze the environment and act on results, most cost-effectively.

**Choices**
- A. Build a dashboard with Systems Manager OpsCenter + CloudWatch metrics, review periodically.
- B. Enable CloudWatch detailed monitoring, build and review dashboards.
- C. **Install the CloudWatch agent on each instance, turn on AWS Compute Optimizer and let it run at least 12 hours, then resize based on its recommendations.**
- D. Purchase an Enterprise Support plan, turn on Trusted Advisor, and resize based on its recommendations.

**Explanation**
**AWS Compute Optimizer** (free, with the CloudWatch agent enabling memory-aware recommendations) analyzes actual utilization and provides specific rightsizing recommendations with minimal manual effort.

**Why the other choices are wrong**

- D: Trusted Advisor's cost checks are more general/less granular than Compute Optimizer, and requires a paid support plan.

> 💡 **Exam tip**: For EC2/EBS rightsizing recommendations, use **AWS Compute Optimizer** (free, granular) before building custom dashboards or paying for Trusted Advisor via Enterprise Support.

## QUESTION 131

**Question**: An Organizations (Control Tower) + Transit Gateway environment. A web app (Lambda+RDS) runs in the Application account; a DBA in a separate DBA account accesses the RDS database via an EC2 instance. The app team stores DB credentials in Secrets Manager (default AWS-managed key) in the Application account, and **manually** shares them with the DBA. Eliminate manual sharing.

**Choices**
- A. Share the secret with the DBA account via AWS RAM.
- B. **Create a "DBA-Secret" role in the Application account (secret access permission). Create a "DBA-Admin" role in the DBA account. Grant DBA-Admin permission to assume DBA-Secret. Attach DBA-Admin to the EC2 instance.**
- C. Create a role in the DBA account + attach a resource-based policy to the **default managed key** in the Application account.
- D. Create a role in the DBA account + attach an SCP allowing secret access.

**Correct Answer: B**

**Explanation**
The standard **cross-account role assumption** pattern: create a role in the Application account (owning the secret), and have the DBA account's role assume it — eliminating manual sharing entirely.

**Why the other choices are wrong**
- A: **Secrets Manager secrets are not a RAM-shareable resource type.**
- C: The stem states a **default AWS-managed key** is used — **default managed keys can't have custom resource policies attached** (only customer-managed keys can).
- D: **SCPs cannot grant cross-account resource access** — they only set a ceiling.

> 💡 **Exam tip**: Cross-account Secrets Manager access uses the **role-assumption pattern.** Remember: secrets aren't RAM-shareable, **default AWS-managed KMS keys can't have custom policies** (only customer-managed keys can), and SCPs never grant access.

## QUESTION 132

**Question**: Organizations has Research and DataOps OUs. Compliance requires **all** deployed resources to be in ap-northeast-1, and **EC2 instances deployed to the DataOps OU specifically** must use a predefined instance type list. Maximize operational efficiency, minimize ongoing maintenance. (Choose two.)

**Choices**
- A. An IAM role inline policy in one DataOps account restricting `ec2:InstanceType`.
- B. IAM users in every account under the root OU, restricting `aws:RequestedRegion` via inline policies.
- C. **An SCP using `aws:RequestedRegion` to restrict to only ap-northeast-1, applied to the root OU.**
- D. An SCP using `ec2:Region`, applied individually to the root, DataOps, and Research OUs.
- E. **An SCP using `ec2:InstanceType` to restrict specific instance types, applied only to the DataOps OU.**

**Correct Answer: C, E**

**Explanation**
Since the Region restriction applies org-wide, one **SCP at the root OU** (C) is most efficient. Since the instance type restriction applies only to DataOps, scope that SCP narrowly to just that **OU** (E).

**Why the other choices are wrong**
- A: Scoped to one account/role, doesn't cover the whole DataOps OU.
- B: Managing IAM users individually across every account is far more maintenance than one SCP.
- D: The correct condition key is **`aws:RequestedRegion`**, not `ec2:Region`, and applying it individually to three OUs is less efficient than once at root.

> 💡 **Exam tip**: For org-wide restrictions, apply a single SCP at the **root OU** using **`aws:RequestedRegion`** (not `ec2:Region`). For OU-specific restrictions, scope the SCP to just that OU — don't replicate via per-account IAM.

## QUESTION 133

**Question**: A single-Region serverless app: publishes URLs to an SNS topic → SQS queue (Lambda event source) → Lambda extracts metadata → S3. Process each URL from a **different Region** for localization comparison, while URLs must still be **published in the existing Region** and results written to the **existing S3 bucket.** (Choose two.)

**Choices**
- A. **Deploy the SQS queue (with the Lambda function) in the other Region(s).**
- B. Subscribe each Region's SNS topic to the SQS queue.
- C. **Subscribe each Region's SQS queue to the (existing, single) SNS topic.**
- D. Configure the SQS queues to publish URLs to SNS topics in each Region.
- E. Deploy the SNS topic and Lambda function in the other Region.

**Correct Answer: A, C**

**Explanation**
**SNS supports cross-Region subscriptions.** Deploy SQS+Lambda pairs in other Regions (A) and subscribe each to the **existing single-Region SNS topic** (C) — URLs are still published once, but processed across multiple Regions.

**Why the other choices are wrong**
- B, D: Both describe the subscription/publish relationship backward.
- E: Duplicating the SNS topic itself contradicts "URLs must be published in the existing Region only."

> 💡 **Exam tip**: **SNS supports cross-Region subscriptions** (a queue in another Region can subscribe to a topic in a different Region). To fan out from a single publish point, replicate only the SQS+Lambda pair, keeping one SNS topic.

## QUESTION 134

**Question**: A proprietary stateless ETL app (Linux binary, no source code changes possible, single-threaded, 2GB RAM, CPU-intensive) runs every 4 hours for up to 20 minutes. Redesign the architecture.

**Choices**
- A. Use Lambda, invoked every 4 hours via CloudWatch Logs.
- B. Use AWS Batch, invoked via a Step Functions state machine every 4 hours.
- C. **Use AWS Fargate, invoked every 4 hours via Amazon EventBridge (scheduled rule).**
- D. Use EC2 Spot Instances, deployed and run every 4 hours via AWS CodeDeploy.

**Correct Answer: C**

**Explanation**
Since it's an unmodifiable Linux binary, **Fargate** lets you containerize it as-is with no code changes, and no infrastructure is needed between runs — a scheduled **EventBridge** rule every 4 hours is the simplest trigger.

**Why the other choices are wrong**
- A: Lambda requires adapting code to its execution/handler model (impossible given "no code changes"), and "invoked via CloudWatch Logs" isn't a real scheduling mechanism.
- B: AWS Batch suits larger, more complex job-queuing needs — overkill for this simple scheduled single-container task.
- D: Spot + CodeDeploy requires managing actual EC2 instances, more overhead than serverless Fargate.

> 💡 **Exam tip**: For an unmodifiable legacy binary run on a schedule for a bounded duration, use **Fargate + a scheduled EventBridge rule** — simpler than AWS Batch, Lambda (runtime mismatch), or EC2/CodeDeploy.

## QUESTION 135

**Question**: A sequel to a popular online game expects massive global traffic in its first week. Current single-Region architecture: S3 (game assets) + DynamoDB (player scores). Design a multi-Region solution reducing latency and improving reliability, with minimal implementation effort.

**Choices**
- A. S3 **Same-Region** Replication (error) + custom DMS CDC-based DynamoDB replication.
- B. S3 Same-Region Replication (error) + a new DynamoDB table as a "Global Table replication target" (conceptual error).
- C. **Add another S3 bucket in the new Region + S3 Cross-Region Replication. Configure a CloudFront distribution with Origin Failover across both buckets. Enable DynamoDB Streams and configure DynamoDB Global Tables with a replica in the new Region.**
- D. S3 Same-Region Replication (error) + CloudFront origin failover + DynamoDB Global Tables.

**Correct Answer: C**

**Explanation**
Static assets: **S3 Cross-Region Replication + CloudFront Origin Failover** (improving both latency and reliability). Player data: **DynamoDB Global Tables** (a minimal-effort, managed, multi-Region feature).

**Why the other choices are wrong**
- A, B, D: **"Same-Region" replication doesn't satisfy the multi-Region requirement** (must be Cross-Region), and building custom DMS-based replication reimplements what DynamoDB Global Tables already provides.

> 💡 **Exam tip**: For multi-Region game asset delivery, use **S3 Cross-Region Replication (not Same-Region) + CloudFront Origin Failover.** For multi-Region player data, use **DynamoDB Global Tables** — not custom DMS replication.

## QUESTION 136

**Question**: An on-premises website (Java backend + NoSQL MongoDB) must be migrated to AWS with a **similar architecture**, **without changing the application**, deployed for high availability.

**Choices**
- A. **Amazon Aurora** (relational — incompatible) as the database + multi-AZ EC2 ASG.
- B. Self-managed **MongoDB on EC2** + **single-AZ** ASG.
- C. **Amazon DocumentDB (MongoDB-compatible) sized appropriately across multiple AZs** + a multi-AZ EC2 Auto Scaling group for the Java backend.
- D. DocumentDB with a nonexistent **"on-demand capacity mode"** + multi-AZ EC2 ASG.

**Correct Answer: C**

**Explanation**
Since the app cannot be changed and uses MongoDB, **Amazon DocumentDB** (MongoDB-compatible, fully managed) is the natural code-unchanged replacement, deployed across multiple AZs for HA.

**Why the other choices are wrong**
- A: **Aurora is relational (SQL)** — fundamentally incompatible with a MongoDB-based, unmodifiable application.
- B: Self-managed MongoDB adds operational overhead vs. managed DocumentDB, and **single-AZ** fails the HA requirement.
- D: DocumentDB has no such "on-demand capacity mode" — it uses instance-based provisioning.

> 💡 **Exam tip**: For an unmodifiable **MongoDB**-based app migrating to AWS, use **Amazon DocumentDB (MongoDB-compatible)** — not Aurora (incompatible) or self-managed MongoDB (more overhead).

## QUESTION 137

**Question**: The Creative team's account has a KMS-encrypted S3 bucket to share (read-only) with the Strategy team's account. A `strategy_reviewer` IAM role was created in the Strategy account, but assuming it and accessing the bucket returns **Access Denied.** Fix with minimum necessary permissions. (Choose three.)

**Choices**
- A. **Create a bucket policy including read permission, with the Principal set to the Strategy account/role.**
- B. Update the `strategy_reviewer` role to grant **full** bucket permissions and KMS decrypt access.
- C. **In the Creative account, update the custom KMS key policy to grant decrypt permission to the `strategy_reviewer` role.**
- D. Set the bucket policy's Principal to **anonymous users** + update the KMS key policy.
- F. **Update the `strategy_reviewer` role to grant S3 read permission and KMS decrypt permission.**

**Correct Answer: A, C, F**

**Explanation**
Cross-account access to a bucket encrypted with a **customer-managed KMS key** requires permission aligned in three places: ① the **bucket policy** grants read access (A), ② the **KMS key policy** (customer-managed keys support custom policies) grants decrypt access (C), and ③ the requester's own **IAM role policy** grants both S3 and KMS permissions (F).

**Why the other choices are wrong**
- B: "Full" permissions violate least privilege (only read access is needed).
- D: Setting the Principal to **anonymous users** makes the bucket **publicly** accessible — a severe security risk.

> 💡 **Exam tip**: Cross-account access to an **S3 bucket encrypted with a customer-managed KMS key** requires permission in **all three places**: bucket policy, KMS key policy (only possible with customer-managed keys), and the requester's own IAM policy. Missing any one causes Access Denied.

## QUESTION 138

**Question**: A life sciences company processes genomic data via Docker containers on-premises, using open-source workflow tools; sequencing data lands on a local SAN before processing. R&D faces capacity constraints; redesign on AWS to scale with demand and shorten processing from weeks to days. A high-speed Direct Connect exists. Each genome generates ~200GB; jobs can take hours. Results go to S3. ~10-15 job requests daily.

**Choices**
- A. Regularly scheduled **Snowball Edge** transfers + S3 event triggering Lambda.
- B. AWS Data Pipeline for transfer + S3 event triggering a **custom AMI EC2 Auto Scaling group.**
- C. **AWS DataSync to transfer to S3, S3 event triggers a Lambda function that starts a Step Functions workflow, Docker images stored in ECR, AWS Batch runs containers to process data.**
- D. Storage Gateway File Gateway for transfer + AWS Batch jobs running on EC2 instances with Docker.

**Correct Answer: C**

**Explanation**
**AWS DataSync** suits ongoing transfer over an existing Direct Connect link (Snowball is for bulk one-time transfers). **AWS Batch** is purpose-built for variable-volume, containerized, compute-intensive batch jobs (10-15/day, hours each), orchestrated via Step Functions with images in ECR.

**Why the other choices are wrong**
- A: Snowball Edge suits bulk/one-time transfers, not ongoing daily flow when Direct Connect already exists.
- B: Data Pipeline + custom AMI ASG manually reimplements what AWS Batch provides natively — more overhead.
- D: File Gateway suits ongoing hybrid file access patterns, less directly efficient than DataSync for this ingestion pipeline.

> 💡 **Exam tip**: For ongoing data transfer over an **existing Direct Connect**, use **AWS DataSync** (not Snowball). For variable-volume, containerized, compute-intensive batch jobs, use **AWS Batch** (with ECR + Step Functions) — the purpose-built, auto-scaling service.

## QUESTION 139

**Question**: A content management app runs on a single Windows EC2 instance (2TB EBS root device) in dev. Deploy to production across multiple AZs with at least 3 instances for HA/fault tolerance. All instances must join an **Active Directory domain**, implementing **Windows ACLs.** All instances must always maintain **exactly the same content.** Minimal management overhead?

**Choices**
- A. Amazon EFS (no Windows ACL support).
- B. FSx for Lustre (no Windows/SMB support).
- C. **Create an Amazon FSx for Windows File Server file system. Create an Auto Scaling group spanning 3 AZs with a minimum of 3 instances. Use a user data script to install the app and mount the FSx file system. Perform seamless domain join.**
- D. EFS + seamless domain join (still no Windows ACL support).

**Correct Answer: C**

**Explanation**
**Amazon FSx for Windows File Server** natively supports **SMB and Windows ACLs** (a hard requirement), and its shared file system guarantees identical content across all instances. Its **seamless domain join** feature natively handles AD integration.

**Why the other choices are wrong**
- A, D: **Amazon EFS doesn't support Windows ACLs** (Linux/NFS-oriented) — fails the explicit requirement.
- B: **FSx for Lustre is for HPC workloads** and doesn't support Windows/SMB.

> 💡 **Exam tip**: For shared storage needing **Windows ACLs and AD domain integration**, use **Amazon FSx for Windows File Server** — not EFS (no Windows ACLs) or FSx for Lustre (HPC-focused, no Windows support). Its **seamless domain join** feature covers AD integration.

## QUESTION 140

**Question**: A SaaS company's case management solution sends email via a standalone SMTP server; the app also stores email templates for confirmation emails filled with customer data. Migrate this messaging to AWS, minimizing operational overhead, most cost-effectively.

**Choices**
- A. An SMTP server on EC2 (Marketplace AMI) + templates in S3 + custom Lambda merge + SDK to send.
- B. Amazon SES for sending + templates stored in **S3** + Lambda retrieves/merges + SDK to send.
- C. An SMTP server on EC2 + templates stored in SES (with parameters) + Lambda substitutes parameters, sent via the **Marketplace SMTP server.**
- D. **Set up Amazon SES to send email. Store the email template directly in SES with parameters for customer data. Create a Lambda function calling the `SendTemplatedEmail` API, passing customer data to replace parameters and the destination.**

**Correct Answer: D**

**Explanation**
**Amazon SES's native templated email feature** (`SendTemplatedEmail` + templates stored directly in SES with parameters) is purpose-built for exactly this pattern — no separate template storage or manual merge logic needed, and no EC2/SMTP server to manage.

**Why the other choices are wrong**
- A, C: **Rebuilding a self-managed SMTP server on EC2** reintroduces the exact server management overhead the migration should eliminate.
- B: Uses SES for sending, but storing templates separately in S3 with custom Lambda merge logic reimplements what SES's native templating already provides.

> 💡 **Exam tip**: **Amazon SES can store parameterized email templates directly and send them via `SendTemplatedEmail`** — eliminating separate template storage and custom merge logic, and (naturally) any self-managed SMTP server. Rebuilding a self-managed SMTP server is almost always the wrong answer in a migration scenario.
