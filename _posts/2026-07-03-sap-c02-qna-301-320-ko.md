## QUESTION 301

**문제**: 대기업이 수천 대의 온프레미스 서버를 AWS로 마이그레이션하려 하지만, 어떤 서버가 어떤 서버와 통신하는지, 각 서버의 CPU/메모리 사용률이 어느 정도인지 등의 **기초 데이터가 전혀 없다**. 에이전트를 설치하기 어려운 서버도 일부 있다. 마이그레이션 계획을 세우기 위한 첫 단계는?

**보기**
- A. 모든 서버에 즉시 Application Migration Service(MGN) 에이전트를 설치해 바로 마이그레이션 시작(현황 파악 없이 바로 마이그레이션을 시작하는 것은 위험하며, 일부 서버는 에이전트 설치가 어렵다는 제약도 무시함).
- B. **AWS Application Discovery Service를 사용해, 에이전트 설치가 가능한 서버는 에이전트 기반으로, 어려운 서버는 에이전트리스(agentless, VMware 환경용)로 서버 사용률과 네트워크 종속성 데이터를 수집.**
- C. 수동으로 각 팀에 설문조사를 보내 서버 용도와 사양을 파악(수천 대 규모에서 수동 설문은 부정확하고 시간이 오래 걸리며, 실제 네트워크 종속성 같은 정량적 데이터는 얻기 어려움).
- D. Trusted Advisor로 온프레미스 서버 사용률 확인(Trusted Advisor는 AWS 계정 내 리소스에 대한 점검 도구이며 온프레미스 서버는 점검 대상이 아님 — 개념 오류).

**정답: B**

**해설**
**AWS Application Discovery Service**는 대규모 마이그레이션 계획 수립 전 단계에서 서버 사용률(CPU/메모리/디스크)과 프로세스 간 **네트워크 종속성**을 수집하는 도구입니다. 에이전트를 설치할 수 있는 서버는 **에이전트 기반 검색**으로, VMware 환경이라 에이전트 설치가 어려운 서버는 **에이전트리스 검색**으로 데이터를 수집할 수 있어, 서버 특성에 따라 유연하게 대응하며 마이그레이션 웨이브(wave) 계획을 데이터 기반으로 세울 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 사전 현황 파악 없이 바로 마이그레이션을 시작하는 것은 종속성 누락, 다운타임 등 큰 리스크를 초래합니다.
- C: 수동 설문은 대규모 환경에서 정확하고 정량적인 사용률/종속성 데이터를 제공하지 못합니다.
- D: Trusted Advisor는 AWS 계정 내 리소스 점검용이며 온프레미스 인프라와는 무관합니다.

> 💡 **시험 꿀팁**: 대규모 마이그레이션 전 **서버 사용률과 네트워크 종속성 데이터를 수집**하려면 **AWS Application Discovery Service**(에이전트 기반 + 에이전트리스 병행)가 표준 정답입니다.

## QUESTION 302

**문제**: 여러 리전에 배포된 미션 크리티컬 애플리케이션의 DR 계획이 있지만, 실제 장애 시 페일오버 절차가 제대로 작동할지 **사전에 지속적으로 검증**하고, 장애 발생 시 각 리전의 상태를 판단해 안전하게 트래픽을 전환하는 신뢰할 수 있는 방법이 필요하다. 솔루션은?

**보기**
- A. CloudWatch 알람만으로 리전 장애를 감지하고 운영자가 수동으로 Route 53 레코드를 변경(수동 개입은 속도가 느리고 사람의 실수 위험이 있으며, 페일오버 준비 상태를 사전에 지속 검증하는 기능도 없음).
- B. **Route 53 Application Recovery Controller(ARC)를 사용해 리전별 상태를 판단하는 라우팅 컨트롤을 구성하고, 읽기 준비 상태 확인(readiness check)으로 각 리전이 페일오버를 받을 준비가 되어 있는지 지속적으로 검증하며, 안전 규칙(safety rule)으로 동시에 모든 리전을 비활성화하는 실수를 방지.**
- C. 각 리전에 독립적인 Route 53 상태 확인만 설정하고 그 외 추가 조치 없음(단순 상태 확인만으로는 리소스 용량 등 다차원적인 "페일오버 준비 상태"를 검증하지 못하고, 동시 다운 같은 위험한 라우팅 변경을 막는 안전장치도 없음).
- D. AWS Fault Injection Simulator(FIS)로 실제 프로덕션 트래픽을 무작위로 차단해 상시 테스트(실제 프로덕션에 무작위로 지속적인 장애를 주입하는 것은 통제되지 않은 리스크가 크며, ARC처럼 안전하게 페일오버 준비 상태를 검증하는 목적에 맞지 않음).

**정답: B**

**해설**
**Route 53 Application Recovery Controller(ARC)**는 라우팅 컨트롤로 트래픽 전환을 세밀하게 제어하고, **읽기 준비 상태 확인(readiness check)**으로 각 리전/자원이 실제로 트래픽을 받을 준비(용량, 구성 일치 등)가 되어 있는지 상시 모니터링합니다. 또한 **안전 규칙(safety rule)**을 통해 모든 리전을 동시에 비활성화하는 것과 같은 위험한 운영 실수를 원천 차단합니다. 이는 DR 페일오버의 신뢰성을 사전/사후 모두 강화하는 표준 서비스입니다.

**왜 다른 보기는 오답인가**
- A: 수동 개입은 속도와 정확성 모두에서 불리하며, 사전 준비 상태 검증 기능이 없습니다.
- C: 단순 상태 확인은 ARC의 readiness check처럼 용량/구성까지 포괄적으로 검증하지 못하며 안전 규칙도 없습니다.
- D: 실제 프로덕션에 통제되지 않은 무작위 장애를 지속 주입하는 것은 안전한 검증 방법이 아닙니다(카오스 엔지니어링은 통제된 실험이어야 함).

> 💡 **시험 꿀팁**: 다중 리전 DR의 **페일오버 준비 상태를 지속적으로 검증**하고 **위험한 라우팅 실수를 방지**하려면 **Route 53 Application Recovery Controller(ARC)**(라우팅 컨트롤 + readiness check + safety rule)가 표준 정답입니다.

## QUESTION 303

**문제**: 회사가 온프레미스 NetApp 스토리지에서 운영 중인 NFS/SMB 파일 워크로드를 AWS로 리프트&시프트하려 한다. 기존에 사용하던 **중복 제거(deduplication), 압축, 스냅샷, 클론** 같은 NetApp ONTAP 고유 기능을 클라우드에서도 그대로 활용하고 싶다. 솔루션은?

**보기**
- A. Amazon EFS로 마이그레이션(EFS는 NFS는 지원하지만 SMB는 지원하지 않고, ONTAP 고유의 중복 제거/클론 같은 기능 세트를 동일하게 제공하지 않음).
- B. **Amazon FSx for NetApp ONTAP로 마이그레이션해 NFS와 SMB를 모두 지원하면서 기존 ONTAP 관리 도구와 기능(중복 제거, 압축, 스냅샷, 클론 등)을 그대로 활용.**
- C. Amazon FSx for Windows File Server로 마이그레이션(SMB는 지원하지만 NFS는 기본 지원하지 않으며, ONTAP 고유 기능 세트도 제공하지 않음).
- D. S3에 파일을 객체로 저장하고 애플리케이션을 S3 API를 사용하도록 재작성(파일 시스템 프로토콜[NFS/SMB]을 사용하는 기존 애플리케이션을 객체 스토리지 API로 재작성해야 해서 "리프트&시프트"라는 목표와 크게 어긋남).

**정답: B**

**해설**
**Amazon FSx for NetApp ONTAP**는 관리형 서비스로 **NFS와 SMB 프로토콜을 모두 지원**하며, 온프레미스에서 사용하던 것과 동일한 ONTAP 기능(스토리지 효율화를 위한 **중복 제거, 압축**, 데이터 보호를 위한 **스냅샷, 클론** 등)을 클라우드에서도 그대로 제공합니다. 기존 ONTAP 기반 워크로드를 애플리케이션 변경 없이 리프트&시프트하기에 가장 적합합니다.

**왜 다른 보기는 오답인가**
- A: EFS는 NFS 전용이며 SMB를 지원하지 않고, ONTAP 특유의 기능 세트도 다릅니다.
- C: FSx for Windows File Server는 SMB 중심이며 NFS 지원이 제한적이고 ONTAP 기능과도 다릅니다.
- D: 객체 스토리지로의 전환은 애플리케이션 재작성을 요구해 리프트&시프트 목표에 반합니다.

> 💡 **시험 꿀팁**: 온프레미스 **NetApp ONTAP 기반 NFS/SMB 워크로드**를 애플리케이션 변경 없이 그대로 클라우드로 옮기려면 **Amazon FSx for NetApp ONTAP**가 표준 정답입니다.

## QUESTION 304

**문제**: 마이크로서비스 간 통신에 **상호 TLS(mTLS)**를 적용해 서비스가 서로의 신원을 인증서로 검증하도록 하고 싶다. 인증서는 내부 서비스 전용이며 공인 CA에 등록할 필요는 없다. 인증서 발급과 순환(rotation)을 자동화하려면?

**보기**
- A. 각 서비스 팀이 OpenSSL로 자체 서명 인증서를 직접 생성하고 수동으로 배포/갱신(수백 개 서비스에서 수동으로 인증서를 생성/배포/갱신하는 것은 운영 오류와 만료로 인한 장애 위험이 매우 큼).
- B. **AWS Certificate Manager Private Certificate Authority(ACM Private CA)로 내부 전용 CA 계층을 구성하고, ACM과 통합해 서비스에 필요한 사설 인증서를 발급하며 자동 갱신을 활용.**
- C. 공인 CA(예: 상용 SSL 인증서 발급기관)에서 모든 내부 서비스용 인증서를 개별 구매(내부 전용 통신에 공인 인증서를 구매하는 것은 불필요한 비용이 발생하며, 내부 서비스 이름에 대한 공인 인증서 발급 자체가 제한적일 수 있음).
- D. AWS Secrets Manager에 자체 생성한 인증서 파일을 저장만 하고 발급/순환은 직접 스크립트로 구현(Secrets Manager는 저장/배포에는 유용하지만 인증서 발급 자체와 자동 순환 파이프라인 구축은 ACM Private CA가 더 표준적이고 통합된 방법).

**정답: B**

**해설**
**ACM Private CA**는 조직 내부용 사설 인증 기관(CA) 계층 구조를 관리형으로 운영할 수 있게 해주며, **AWS Certificate Manager(ACM)**와 통합되어 서비스에 필요한 사설 TLS 인증서를 발급하고 **자동으로 갱신**할 수 있습니다. 이를 통해 마이크로서비스 간 mTLS를 구현하는 데 필요한 인증서 발급/배포/순환을 안전하고 자동화된 방식으로 관리할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 수동 자체 서명 인증서 관리는 대규모 마이크로서비스 환경에서 만료/오류로 인한 장애 위험이 매우 큽니다.
- C: 내부 전용 통신에 공인 CA 인증서를 사용하는 것은 불필요한 비용이며, 내부 도메인 이름에 대한 공인 인증서 발급도 실용적이지 않습니다.
- D: Secrets Manager는 저장소로 유용하지만, 인증서 "발급" 자체와 CA 계층 관리 기능은 ACM Private CA의 역할입니다.

> 💡 **시험 꿀팁**: 마이크로서비스 간 **mTLS를 위한 내부 전용 인증서 발급/자동 순환**이 필요하면 **ACM Private CA + ACM 통합**이 표준 정답입니다.

## QUESTION 305

**문제**: DynamoDB 테이블에서 특정 파티션 키 값(예: 인기 상품 ID)에 트래픽이 몰려 **핫 파티션(hot partition)** 현상이 발생해 스로틀링이 자주 일어난다. 테이블 전체의 프로비저닝된 용량은 충분함에도 특정 파티션만 병목이 생기는 상황을 해결하려면?

**보기**
- A. 테이블 전체의 프로비저닝된 처리량(RCU/WCU)을 대폭 증가(전체 용량을 늘려도 특정 파티션 키에 대한 접근 자체가 물리적으로 하나(또는 소수)의 파티션에 집중되는 근본 문제는 해결되지 않고 비용만 증가).
- B. **파티션 키 설계를 개선해 자주 접근되는 키 값 뒤에 임의의 접미사(랜덤 슈플렉스, write sharding)를 붙이거나, 접근 패턴을 고르게 분산시킬 수 있는 복합 파티션 키(예: 상품ID#샤드번호)로 재설계.**
- C. DynamoDB Accelerator(DAX)만 추가해 읽기 캐싱(DAX는 읽기 성능 향상에는 도움이 되지만, 쓰기 트래픽으로 인한 핫 파티션이나 근본적인 파티션 키 설계 문제는 해결하지 못함).
- D. 테이블을 온디맨드 모드로 전환(온디맨드 모드도 내부적으로는 파티션 단위로 처리량이 분배되므로, 특정 파티션 키에 트래픽이 극단적으로 집중되면 여전히 해당 파티션 수준에서 스로틀링이 발생할 수 있음 — 근본 해법은 키 설계 개선).

**정답: B**

**해설**
DynamoDB의 처리량은 물리적으로 파티션 단위로 분배되므로, 특정 파티션 키 값에 트래픽이 쏠리면 테이블 전체 용량이 충분해도 **그 파티션만** 병목이 생깁니다. 이를 근본적으로 해결하려면 **파티션 키 설계 자체를 개선**해야 하며, 대표적으로 인기 키 값에 **랜덤/순환 접미사를 붙여 여러 물리적 파티션에 쓰기를 분산**시키는 쓰기 샤딩(write sharding) 기법을 사용합니다.

**왜 다른 보기는 오답인가**
- A: 테이블 전체 용량을 늘려도 특정 파티션 키에 대한 접근이 물리적으로 집중되는 근본 원인은 해결되지 않습니다.
- C: DAX는 읽기 캐싱에는 효과적이지만, 쓰기 위주의 핫 파티션 문제나 키 설계 자체의 근본 원인은 해결하지 못합니다.
- D: 온디맨드 모드도 내부적으로 파티션 단위 처리량 분배 원칙을 따르므로, 극단적인 키 쏠림 자체를 해결해주지는 않습니다.

> 💡 **시험 꿀팁**: DynamoDB의 **핫 파티션(특정 키에 트래픽 집중)** 문제는 용량 증설이 아니라 **파티션 키 설계 개선(랜덤/순환 접미사를 이용한 쓰기 샤딩)**으로 근본적으로 해결하는 것이 표준 정답입니다.

> 💡 **시험 꿀팁**: VPC 인터페이스 엔드포인트의 **고가용성**을 확보하려면 엔드포인트 생성 시 **애플리케이션이 배포된 모든 AZ의 서브넷을 선택**해 AZ별 ENI가 생성되도록 구성하는 것이 표준 정답입니다.

- D. 각 리소스에 대해 수동으로 콘솔에서 태그가 있는지 확인 후 승인하는 프로세스 도입(수천 개 리소스 생성 요청마다 수동 검토는 확장성이 없고 비효율적).

**정답: B**

**해설**
**Organizations 태그 정책(Tag Policy)**은 허용되는 태그 키와 값의 형식(대소문자, 허용값 목록 등)을 조직 차원에서 표준화합니다. 여기에 **필수 태그가 없는 리소스의 생성 API 호출 자체를 거부하는 SCP**를 함께 적용하면, 태그 표준화와 "차단"이라는 사전 예방적 강제를 동시에 달성해, 이후 생성되는 모든 리소스가 정확한 비용 배분에 필요한 태그를 갖추도록 보장할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 자율에 맡기는 방식은 강제력이 없어 일관된 준수를 보장하지 못합니다.
- C: Config 규칙 기반 사후 탐지는 이미 생성된 리소스의 누락을 발견하는 데는 유용하지만, 애초에 생성을 막는 사전 차단 기능은 아닙니다.
- D: 수동 승인 프로세스는 리소스 생성 규모가 커질수록 병목이 되어 확장성이 없습니다.

> 💡 **시험 꿀팁**: 조직 전체에서 **태그 형식을 표준화하고 필수 태그 없는 리소스 생성 자체를 사전에 차단**하려면 **Organizations 태그 정책(Tag Policy) + SCP** 조합이 표준 정답입니다.

## QUESTION 311

**문제**: 전자상거래 주문 처리 시스템에서 **같은 고객의 주문은 반드시 접수된 순서대로** 처리되어야 하고, 네트워크 재시도로 인한 **중복 주문 처리도 방지**해야 한다. 서버리스 아키텍처에서 이를 구현하는 메시징 솔루션은?

**보기**
- A. 표준(Standard) SQS 큐 사용(표준 큐는 처리량은 높지만 순서 보장이 안 되고 최소 한 번 이상 전달로 인한 중복 발생 가능성이 있어 두 요구사항 모두 충족하지 못함).
- B. **SQS FIFO 큐를 사용하고, 메시지 그룹 ID(MessageGroupId)에 고객 ID를 지정해 고객별 순서를 보장하며, 콘텐츠 기반 중복 제거(또는 명시적 중복 제거 ID)로 중복 메시지를 방지.**
- C. SNS 표준 주제로 주문 이벤트를 발행하고 여러 Lambda 구독자가 병렬 처리(SNS 표준 주제는 순서를 보장하지 않으며 병렬 처리는 오히려 순서를 더 깨뜨릴 수 있음).
- D. Kinesis Data Streams를 사용하고 파티션 키 없이 라운드로빈으로 샤드에 분배(파티션 키 없이 라운드로빈으로 분배하면 같은 고객의 이벤트가 서로 다른 샤드에 흩어져 순서 보장이 되지 않음).

**정답: B**

**해설**
**SQS FIFO 큐**는 동일한 **메시지 그룹 ID** 내에서 메시지가 전송된 순서대로 처리되도록 보장합니다. 여기에 **고객 ID를 메시지 그룹 ID로 사용**하면 같은 고객의 주문끼리는 순서가 보장되면서도, 서로 다른 고객의 주문은 병렬로 처리되어 처리량도 확보할 수 있습니다. 또한 FIFO 큐의 **중복 제거(deduplication)** 기능(5분 중복 제거 구간 내 콘텐츠 기반 해시 또는 명시적 중복 제거 ID)을 사용하면 네트워크 재시도로 인한 중복 메시지도 자동으로 걸러집니다.

**왜 다른 보기는 오답인가**
- A: 표준 SQS 큐는 순서 보장과 정확히 한 번 처리(중복 방지)를 모두 제공하지 않습니다.
- C: SNS 표준 주제는 순서를 보장하지 않으며, 여러 구독자의 병렬 처리는 순서 문제를 오히려 악화시킬 수 있습니다.
- D: Kinesis에서 순서를 보장하려면 동일 개체(예: 고객)에 대해 동일한 파티션 키를 사용해 같은 샤드로 라우팅해야 하는데, 파티션 키 없이 라운드로빈으로 분배하면 순서가 깨집니다.

> 💡 **시험 꿀팁**: **그룹(고객) 단위 순서 보장 + 중복 처리 방지**가 필요한 서버리스 메시징에는 **SQS FIFO 큐(그룹 ID + 중복 제거)**가 표준 정답입니다.

- C: Config 규칙의 주기적 평가는 실시간성이 떨어지고 자동 교정 액션도 기본적으로 포함하지 않습니다.

> 💡 **시험 꿀팁**: 애플리케이션과 데이터베이스를 함께 마이그레이션할 때는 **MGN(앱)과 DMS(DB)를 병렬로 지속 복제**시키다가 **동일한 짧은 전환 창에 함께 cutover**하는 것이 다운타임을 최소화하는 표준 정답입니다.

## QUESTION 314

**문제**: 3개 AZ에 걸쳐 배포된 EC2 대상 그룹이 있는데, 한 AZ에는 대상(target)이 8개, 다른 두 AZ에는 각 1개씩만 있어 트래픽 분산이 매우 불균등하다. 이를 균등하게 분산시키고 싶다. NLB와 ALB 각각에서 이를 처리하는 방법의 차이는?

**보기**
- A. ALB와 NLB 모두 기본적으로 AZ 수준에서만 균등 분산하며 대상 개수 차이는 고려하지 않음(ALB는 기본적으로 대상 개수와 무관하게 개별 대상 단위로 균등 분산하는 것이 기본 동작이라는 점에서 부정확함).
- B. **ALB는 기본적으로 개별 대상(target) 단위로 균등하게 트래픽을 분산(교차 영역 로드 밸런싱이 기본 활성화, 무료)하지만, NLB는 기본적으로 AZ 단위로 균등 분산(교차 영역 로드 밸런싱이 기본 비활성화)하므로 명시적으로 교차 영역 로드 밸런싱을 활성화해야 하며, 이때 활성화하면 대상 간 데이터 전송 요금이 발생할 수 있음.**
- C. NLB는 대상 개수와 무관하게 항상 완벽하게 균등 분산하며 추가 설정이 필요 없음(NLB는 기본적으로 AZ 단위 라우팅이라 이 설명은 부정확 — 대상 개수가 AZ마다 다르면 명시적으로 교차 영역 로드 밸런싱을 켜야 함).
- D. ALB는 교차 영역 로드 밸런싱을 활성화해야만 균등 분산이 가능하며 기본은 비활성화 상태(ALB는 교차 영역 로드 밸런싱이 기본적으로 활성화되어 있어 이 설명은 반대로 되어 있음).

**정답: B**

**해설**
**ALB**는 **교차 영역 로드 밸런싱이 기본적으로 활성화**되어 있어, AZ별 대상 개수와 무관하게 등록된 개별 대상들에 트래픽을 고르게 분산하며 추가 데이터 전송 요금도 없습니다. 반면 **NLB**는 **교차 영역 로드 밸런싱이 기본적으로 비활성화**되어 있어 기본 동작은 각 AZ로 균등하게(AZ 내 대상 수와 무관하게) 트래픽을 분산합니다. 이 문제처럼 AZ별 대상 수가 크게 다른 경우 불균형이 발생하므로, NLB에서 대상 단위로 고르게 분산하려면 **교차 영역 로드 밸런싱을 명시적으로 활성화**해야 하며, 활성화 시 AZ 간 데이터 전송에 대한 별도 요금이 부과될 수 있다는 점도 고려해야 합니다.

**왜 다른 보기는 오답인가**
- A, C: NLB의 기본 동작(AZ 단위 분산)과 명시적 활성화 필요성을 정확히 반영하지 못한 설명입니다.
- D: ALB는 교차 영역 로드 밸런싱이 기본적으로 켜져 있으므로 이 보기는 사실 관계가 반대입니다.

**문제**: 보안 팀이 수십 개 VPC의 VPC 흐름 로그(Flow Logs)를 장기간 보관하며 필요할 때 Athena로 특정 IP나 포트에 대한 트래픽을 조회하고 싶다. 데이터 양이 매우 커서 **쿼리 비용과 스캔 시간을 최소화**하고 싶다. 권장되는 저장/쿼리 구성은?

- A. 흐름 로그를 CloudWatch Logs로만 전송하고 CloudWatch Logs Insights로 모든 조회를 수행(CloudWatch Logs는 장기 대용량 로그 보관 비용이 S3보다 높은 편이며, Logs Insights는 Athena만큼 비용 효율적인 파티셔닝 기반 대규모 스캔 최적화를 제공하지 않음).
- B. **흐름 로그를 S3로 전송하고 Parquet 같은 컬럼형 포맷으로 변환(Firehose의 포맷 변환 기능 등 활용)한 뒤, 연/월/일/시간 등으로 파티셔닝하고 Glue Data Catalog에 등록해 Athena로 쿼리.**

**해설**
Athena 쿼리 비용은 **스캔한 데이터양**에 비례하므로, 흐름 로그를 S3에 저장할 때 **Parquet 같은 압축된 컬럼형 포맷**으로 변환하고 **시간 기준(연/월/일/시)으로 파티셔닝**하면, 특정 기간을 조회하는 쿼리가 해당 파티션만 스캔하게 되어 스캔량과 비용이 크게 줄어듭니다. Glue Data Catalog에 파티션 정보를 등록해두면 Athena가 이를 인식해 파티션 프루닝(pruning)을 효율적으로 수행합니다.

**왜 다른 보기는 오답인가**
- A: CloudWatch Logs는 대용량 장기 보관 비용이 S3보다 높고, Logs Insights는 Athena의 파티셔닝 기반 스캔 최적화만큼 비용 효율적이지 않습니다.
- C: 파티셔닝이 없는 텍스트 형식은 매번 전체 데이터를 스캔해야 해서 비용과 조회 시간이 매우 커집니다.
- D: DynamoDB는 대용량 로그의 유연한 분석 쿼리(임의 조건 필터링)에 적합하지 않고 비용도 매우 큽니다.

> 💡 **시험 꿀팁**: 대용량 로그를 Athena로 **저비용/고속 조회**하려면 **S3 저장 + 컬럼형 포맷(Parquet) 변환 + 시간 기준 파티셔닝 + Glue Data Catalog 등록**이 표준 정답입니다.

- A. 계약업체마다 개별 IAM 역할과 세밀한 리소스 기반 정책을 미리 하나하나 생성(리소스와 계약업체 조합이 많아질수록 사전에 정의해야 할 정책 수가 기하급수적으로 늘어나 비현실적).
- B. **속성 기반 접근 제어(ABAC)를 사용해, 계약업체의 세션 태그(예: project=alpha)와 리소스의 태그가 일치하는 경우에만 접근을 허용하는 소수의 범용 IAM 정책을 정의. STS AssumeRole 시 세션 태그를 전달.**
- C. 모든 계약업체에게 동일한 광범위 권한의 역할을 부여한 뒤 계약업체 스스로 필요한 리소스만 사용하도록 안내(최소 권한 원칙에 정면으로 위배되며 실수/악의적 접근에 대한 기술적 방어가 없음).
- D. 계약업체마다 완전히 별도의 AWS 계정을 생성해 리소스를 계정 단위로 분리(리소스별로 세밀하게 다른 계약업체에 접근을 부여해야 하는 상황에서 계정을 통째로 나누는 것은 기존 리소스 배치를 재구성해야 해서 비현실적이고 과도함).

**정답: B**

**해설**
**ABAC(속성 기반 접근 제어)**는 사용자/역할의 **속성(태그)**과 리소스의 **속성(태그)**을 비교해 접근을 허용하는 방식으로, 리소스나 역할이 아무리 많아도 **소수의 범용 정책**(예: "요청자의 `project` 태그와 리소스의 `project` 태그가 같으면 허용")만으로 확장 가능하게 접근을 제어할 수 있습니다. 계약업체가 AssumeRole로 역할을 위임받을 때 **세션 태그**로 해당 계약업체의 프로젝트/범위를 전달하면, 신규 리소스가 추가되거나 계약업체가 늘어나도 정책을 다시 작성할 필요가 없습니다.

**왜 다른 보기는 오답인가**
- A: 역할-리소스 조합마다 개별 정책을 사전 정의하는 RBAC(역할 기반) 방식은 조합이 많아질수록 관리가 불가능해집니다.
- C: 모든 계약업체에게 광범위한 권한을 주는 것은 최소 권한 원칙을 위반하며 리스크가 큽니다.
- D: 계정을 통째로 분리하는 것은 세밀한 리소스별 접근 제어가 필요한 상황에 비해 지나치게 큰 구조 변경입니다.

> 💡 **시험 꿀팁**: 리소스/역할 조합이 매우 많아 사전에 정책을 일일이 정의하기 어려운 상황에서 확장 가능한 접근 제어가 필요하면 **ABAC(속성 기반 접근 제어) + 세션 태그**가 표준 정답입니다.

## QUESTION 320

**문제**: 아키텍트가 Well-Architected 프레임워크의 신뢰성 기둥에 따라 멀티 AZ 아키텍처를 설계하면서, 리전 전체의 **제어 플레인(control plane) 장애**(예: Auto Scaling API, ELB API 자체가 일시적으로 응답하지 않는 상황) 중에도 이미 배포된 인프라가 계속 정상 동작해야 한다는 원칙("정적 안정성", static stability)을 반영하고 싶다. 이 원칙에 부합하는 설계는?

**보기**
- A. 장애가 발생한 AZ의 용량을 감지해 그 즉시 Auto Scaling API를 호출해 다른 AZ에 신규 인스턴스를 추가로 기동하는 방식에만 의존(제어 플레인 자체가 저하된 상황에서는 이 API 호출 역시 실패할 수 있어, 제어 플레인 장애 중에도 살아남는 정적 안정성을 제공하지 못함).
- B. **평상시에도 각 AZ에 장애 발생 시 트래픽을 감당할 수 있는 충분한 용량을 미리 배포(예: 3개 AZ 각각 50% 용량 배치로 한 AZ 장애 시 나머지 두 AZ가 100% 트래픽 처리)해, 제어 플레인 API 호출 없이도 이미 존재하는 자원만으로 장애를 흡수.**
- C. 단일 AZ에 필요한 용량을 모두 배치하고 장애 시에만 다른 AZ로 전체를 재배포(단일 AZ 집중 배치는 AZ 장애 시 서비스 전체가 중단되며, 재배포 자체도 제어 플레인 API에 의존해야 해서 정적 안정성과 정반대).
- D. 모든 용량을 On-Demand API 호출을 통해 실시간으로만 프로비저닝하고 미리 배포하지 않음(사전에 자원을 확보해두지 않고 장애 시점에 API로 새로 프로비저닝하는 방식은 제어 플레인 저하 시 실패할 수 있어 정적 안정성 원칙에 반함).

**정답: B**

**해설**
**정적 안정성(static stability)**은 장애 발생 시점에 새로운 API 호출(Auto Scaling, 새 리소스 프로비저닝 등)에 의존하지 않고, **이미 배포되어 있는 자원만으로** 장애를 흡수할 수 있도록 사전에 충분한 용량을 확보해두는 설계 원칙입니다. 예를 들어 3개 AZ에 각각 정상 부하의 50%씩(N+1 이상) 용량을 미리 배치해두면, 한 AZ가 완전히 장애를 겪어도 나머지 AZ들이 제어 플레인의 개입 없이 즉시 전체 트래픽을 흡수할 수 있습니다. 이는 제어 플레인 자체가 저하되는 광범위한 장애 상황에서도 데이터 플레인(이미 실행 중인 리소스)이 계속 정상 동작하도록 보장하는 신뢰성 모범 사례입니다.

**왜 다른 보기는 오답인가**
- A, D: 장애 시점에 API를 호출해 새로 용량을 확보하려는 방식은, 정작 그 API(제어 플레인)가 저하된 상황에서는 실패할 수 있어 정적 안정성을 제공하지 못합니다.
- C: 단일 AZ 집중 배치는 애초에 여러 AZ에 걸친 장애 격리라는 신뢰성 기본 원칙부터 위배합니다.

> 💡 **시험 꿀팁**: **제어 플레인 장애 중에도 살아남는 신뢰성**을 원한다면, 장애 시점에 새로 자원을 프로비저닝하는 것에 의존하지 말고 **평상시에 여러 AZ에 충분한 여유 용량을 미리 배치**해두는 **정적 안정성(static stability)** 설계가 표준 정답입니다.
