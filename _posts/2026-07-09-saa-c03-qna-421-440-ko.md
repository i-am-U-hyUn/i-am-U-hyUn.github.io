## QUESTION 421

**문제**: 한 스타트업 그룹이 모회사 산하에 5개의 자회사를 운영하고 있으며, 각 자회사는 별도의 AWS 계정을 사용합니다. 재무팀은 매달 각 계정의 청구서를 개별적으로 처리하는 대신, 전체 사용량을 합산하여 AWS의 볼륨 할인(volume discount) 혜택을 받고 하나의 통합된 청구서로 관리하고 싶어합니다. 계정 간 리소스 접근 권한은 그대로 분리 유지되어야 합니다. 솔루션 아키텍트는 어떤 방법을 사용해야 합니까?

**보기**
- A. **AWS Organizations를 사용하여 모든 계정을 하나의 조직으로 통합하고 통합 결제(Consolidated Billing) 기능을 활성화한다.**
- B. 모든 자회사가 하나의 AWS 계정만 공유하도록 마이그레이션한다 (계정 분리를 통한 보안 격리가 사라지고 마이그레이션 비용과 위험이 크다).
- C. AWS Budgets에서 예산 알림을 설정하여 각 계정의 사용량을 수동으로 합산한다 (예산 알림은 비용 통합 결제나 할인 혜택을 제공하지 않는다).
- D. 각 계정에서 Cost Explorer 보고서를 내보낸 뒤 재무팀이 스프레드시트로 수작업 합산한다 (자동화되지 않고 볼륨 할인 자체를 받을 수 없다).

**정답: A**

**해설**: **AWS Organizations**의 **통합 결제(Consolidated Billing)** 기능을 사용하면 여러 AWS 계정을 하나의 관리 계정 아래 조직으로 묶어 사용량을 합산 청구할 수 있습니다. 이를 통해 계정별로 분산되어 있던 사용량이 합쳐지면서 볼륨 기반 할인 구간에 더 쉽게 도달할 수 있고, 각 계정은 여전히 독립적으로 리소스와 IAM 권한을 관리하므로 보안 격리도 유지됩니다.

**왜 다른 보기는 오답인가**
- B: 계정을 하나로 합치면 계정 단위의 격리와 권한 분리가 사라져 보안 및 거버넌스 측면에서 바람직하지 않고, 마이그레이션 자체가 큰 비용과 리스크를 동반합니다.
- C: AWS Budgets는 비용 모니터링과 알림을 위한 도구일 뿐, 계정 간 사용량을 실제로 합산하여 할인 구간을 적용해 주는 기능이 아닙니다.
- D: 수작업 합산은 자동화되지 않으며, 스프레드시트로 정리한다고 해서 AWS 청구서 자체에 볼륨 할인이 적용되지는 않습니다.

> 💡 **시험 꿀팁**: 여러 계정의 비용을 합산해 할인 혜택을 받고 싶다는 시나리오가 나오면 거의 항상 정답은 AWS Organizations의 통합 결제입니다.

## QUESTION 422

**문제**: 한 미디어 회사는 사용자 업로드 콘텐츠를 S3에 저장하고 있는데, 파일별 접근 빈도가 매우 불규칙합니다. 어떤 파일은 업로드 직후 폭발적으로 조회되다가 이후 몇 주간 전혀 조회되지 않기도 하고, 반대로 오래된 파일이 갑자기 다시 인기를 얻기도 합니다. 회사는 접근 패턴을 예측하거나 수동으로 라이프사이클 규칙을 세밀하게 관리하지 않고도 스토리지 비용을 자동으로 최적화하고 싶습니다. 어떤 스토리지 클래스를 사용해야 합니까?

**보기**
- A. S3 Standard-IA로 모든 객체를 즉시 이전한다 (자주 접근되는 객체에는 조회 요금이 추가로 부과되어 오히려 비용이 늘어날 수 있다).
- B. **S3 Intelligent-Tiering을 사용하여 접근 패턴에 따라 객체가 자동으로 계층 간 이동하도록 한다.**
- C. S3 Glacier Deep Archive에 모든 객체를 저장한다 (검색에 최대 12시간이 걸려 즉시 조회가 필요한 콘텐츠에는 부적합하다).
- D. EC2 인스턴스의 EBS 볼륨으로 데이터를 옮겨 직접 접근 빈도를 모니터링한다 (관리 부담이 크고 S3의 내구성과 확장성을 포기하게 된다).

**정답: B**

**해설**: **S3 Intelligent-Tiering**은 접근 패턴을 알 수 없거나 예측할 수 없는 객체에 최적화된 스토리지 클래스로, 일정 기간 접근이 없으면 자동으로 더 저렴한 계층(Infrequent Access, Archive Instant Access 등)으로 객체를 이동시키고, 다시 접근이 발생하면 자동으로 빈번 접근 계층으로 되돌립니다. 조회 요금 없이 자동 계층 이동이 이루어지므로 수동 관리 없이 비용을 최적화할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Standard-IA는 접근 빈도가 낮은 데이터에 적합하지만 조회 시 별도 요금이 부과되므로, 자주 조회되는 객체가 섞여 있으면 비용이 오히려 증가할 수 있습니다.
- C: Glacier Deep Archive는 가장 저렴하지만 검색(retrieval) 시간이 길어 즉각적인 접근이 필요한 콘텐츠에는 맞지 않습니다.
- D: EBS로 옮기는 것은 S3의 관리형 확장성과 내구성을 포기하는 것이며, 접근 빈도 모니터링과 계층 이동을 직접 구현해야 하는 큰 운영 부담을 초래합니다.

> 💡 **시험 꿀팁**: "접근 패턴을 알 수 없다/예측할 수 없다"는 표현이 나오면 정답은 거의 항상 S3 Intelligent-Tiering입니다.

## QUESTION 423

**문제**: 한 전자상거래 회사가 Amazon RDS for MySQL을 사용 중인데, 배포 스크립트 오류로 인해 특정 시각에 주문 테이블의 데이터가 잘못 갱신되었습니다. 데이터베이스 팀은 문제가 발생하기 정확히 몇 분 전 시점의 상태로 데이터베이스를 복구하고 싶어하며, 별도의 백업 인프라를 구축하지 않고 RDS 자체 기능만으로 이를 해결하려 합니다. 어떤 방법을 사용해야 합니까?

**보기**
- A. 수동 스냅샷을 매일 자정에 생성해 두었다가 가장 최근 스냅샷으로 복원한다 (자정 스냅샷 시점으로만 복원 가능해 원하는 정확한 시각으로는 복구할 수 없다).
- B. RDS 읽기 복제본(Read Replica)을 승격시켜 복구용 인스턴스로 사용한다 (읽기 복제본은 원본과 거의 동일한 시점을 유지하므로 문제 발생 이전 시점으로 되돌릴 수 없다).
- C. **자동 백업과 트랜잭션 로그를 이용한 특정 시점 복구(Point-in-Time Recovery)를 사용하여 문제 발생 직전 시각으로 새 DB 인스턴스를 복원한다.**
- D. Amazon S3에 매일 데이터를 수동으로 내보내기(export)한 후 필요할 때 다시 가져오기(import)한다 (초 단위 정밀도의 특정 시점 복구가 불가능하고 운영 부담이 크다).
- E. (옵션 없음)

**정답: C**

**해설**: RDS의 **자동 백업(Automated Backups)**은 트랜잭션 로그를 지속적으로 캡처해 두기 때문에, 백업 보존 기간 내의 임의의 시각(초 단위)으로 **특정 시점 복구(Point-in-Time Recovery, PITR)**를 수행할 수 있습니다. 이 기능은 원본 인스턴스와 별도로 새로운 DB 인스턴스를 생성하여 지정한 시각 직전 상태로 복원하므로, 잘못된 배포가 발생하기 직전 시점으로 정확히 되돌릴 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 수동 스냅샷은 생성된 시점으로만 복원할 수 있어 스냅샷과 스냅샷 사이의 임의 시각으로는 복구가 불가능합니다.
- B: 읽기 복제본은 원본 데이터베이스의 최신 상태를 비동기로 복제하므로, 문제가 발생하기 이전의 과거 시점으로 되돌리는 용도로 사용할 수 없습니다.
- D: 수동 내보내기/가져오기 방식은 정밀한 시점 지정이 어렵고 자동화되어 있지 않아 운영 효율이 매우 떨어집니다.

> 💡 **시험 꿀팁**: "특정 시각/분 단위로 복구하고 싶다"는 문구가 나오면 정답은 RDS의 자동 백업 기반 Point-in-Time Recovery입니다.

## QUESTION 424

**문제**: 한 SaaS 기업은 Auto Scaling 그룹으로 웹 서버 플릿을 운영하고 있습니다. 스케일 인(scale-in)이 발생하여 인스턴스가 종료되기 전에, 해당 인스턴스에 남아 있는 처리 중인 작업 로그를 S3에 업로드하고 로드 밸런서의 커넥션 드레이닝이 끝날 때까지 종료를 지연시키고 싶습니다. 어떤 Auto Scaling 기능을 사용해야 합니까?

**보기**
- A. 종료 정책(Termination Policy)을 커스터마이징하여 특정 인스턴스가 먼저 종료되도록 지정한다 (어떤 인스턴스가 종료될지 순서만 정할 뿐, 종료 전 커스텀 작업을 실행하는 기능은 아니다).
- B. 상태 확인 유예 기간(Health Check Grace Period)을 늘려 인스턴스 종료를 지연시킨다 (이는 신규 인스턴스가 시작될 때 상태 확인을 유예하는 설정으로 종료 프로세스와는 무관하다).
- C. 웜 풀(Warm Pool)을 구성하여 종료 대신 미리 준비된 상태로 전환한다 (웜 풀은 시작 지연을 줄이기 위한 기능으로 종료 전 커스텀 정리 작업을 실행하지 않는다).
- D. **Auto Scaling 수명 주기 후크(Lifecycle Hook)의 EC2_INSTANCE_TERMINATING 상태를 사용하여 종료 전 커스텀 정리 작업을 수행한다.**

**정답: D**

**해설**: **Auto Scaling 수명 주기 후크(Lifecycle Hook)**를 사용하면 인스턴스가 실제로 종료되기 전에 `EC2_INSTANCE_TERMINATING` 상태에서 대기 상태(Pending:Wait)로 전환시켜, 로그 업로드나 커넥션 드레이닝 완료 대기와 같은 커스텀 작업을 수행할 시간을 확보할 수 있습니다. 작업이 끝나면 `CompleteLifecycleAction` API를 호출하여 종료를 계속 진행시킵니다.

**왜 다른 보기는 오답인가**
- A: 종료 정책은 여러 인스턴스 중 어떤 것을 먼저 종료할지 순서를 결정하는 규칙일 뿐, 종료 과정 자체에 커스텀 로직을 끼워 넣지는 못합니다.
- B: 상태 확인 유예 기간은 새로 시작된 인스턴스가 헬스 체크를 통과하기 전 잠시 실패로 간주되지 않도록 유예하는 설정으로, 종료 시나리오와는 관련이 없습니다.
- C: 웜 풀은 스케일 아웃 시 인스턴스 준비 시간을 단축하기 위한 기능이며, 스케일 인 종료 전 정리 작업을 수행하는 목적이 아닙니다.

> 💡 **시험 꿀팁**: "인스턴스 종료 전에 커스텀 작업을 실행하고 싶다"는 요구사항은 Auto Scaling Lifecycle Hook을 가리키는 전형적인 신호입니다.

## QUESTION 425

**문제**: 한 회사가 두 개의 VPC(VPC-A, VPC-B)를 피어링 연결로 연결했습니다. VPC-A의 EC2 인스턴스는 VPC-B에 있는 인스턴스의 프라이빗 DNS 호스트 이름을 사용해 접속하려고 하는데, 현재는 퍼블릭 IP로 해석되거나 아예 해석되지 않는 문제가 있습니다. VPC 간 트래픽은 반드시 프라이빗 IP로만 라우팅되어야 합니다. 이 문제를 해결하려면 무엇을 해야 합니까?

**보기**
- A. **VPC 피어링 연결의 "요청자 VPC용 DNS 확인 옵션(피어링 연결의 DNS 확인 활성화)"을 활성화하여 프라이빗 DNS 호스트 이름이 프라이빗 IP로 해석되도록 한다.**
- B. 각 인스턴스의 /etc/hosts 파일에 상대방 프라이빗 IP를 수동으로 등록한다 (인스턴스가 늘어날수록 확장이 불가능하고 유지보수 부담이 크다).
- C. 두 VPC를 하나의 VPC로 병합한다 (VPC 병합은 지원되지 않는 대규모 마이그레이션 작업이며 근본적인 해결책이 아니다).
- D. VPC-B에 퍼블릭 서브넷을 만들어 인스턴스를 옮기고 퍼블릭 IP로 통신하게 한다 (요구사항인 프라이빗 IP 전용 통신을 위반한다).

**정답: A**

**해설**: VPC 피어링 연결에서는 기본적으로 프라이빗 DNS 호스트 이름이 퍼블릭 IP로 해석됩니다. 피어링 연결의 **DNS 확인 옵션(DNS resolution support)**을 활성화하면, 피어링된 VPC에서 조회하는 프라이빗 DNS 호스트 이름이 퍼블릭 IP 대신 프라이빗 IP 주소로 해석되어, 트래픽이 인터넷을 거치지 않고 VPC 피어링 연결을 통해 프라이빗하게 라우팅됩니다.

**왜 다른 보기는 오답인가**
- B: hosts 파일 수동 등록은 인스턴스 수가 늘어나면 관리가 불가능해지는 임시방편에 불과합니다.
- C: VPC는 서로 병합할 수 없으며, 이는 애초에 존재하지 않는 방법입니다.
- D: 퍼블릭 IP로 전환하는 것은 프라이빗 통신이라는 핵심 요구사항 자체를 위반합니다.

> 💡 **시험 꿀팁**: VPC 피어링 환경에서 프라이빗 DNS 호스트 이름이 프라이빗 IP로 해석되길 원한다면 "피어링 연결의 DNS 확인 옵션 활성화"를 떠올리세요.

## QUESTION 426

## QUESTION 427

**문제**: 한 핀테크 스타트업이 Lambda 함수로 결제 검증 로직을 처리하고, 이 함수는 처리량이 제한적인 온프레미스 레거시 데이터베이스에 연결합니다. 트래픽이 급증할 때 Lambda가 동시에 너무 많이 실행되어 데이터베이스 커넥션이 초과되고 연결 오류가 발생하는 문제가 있습니다. 다른 중요한 Lambda 함수들의 동시 실행 용량에 영향을 주지 않으면서, 이 특정 함수의 동시 실행 수를 제한하려고 합니다. 어떻게 해야 합니까?

**보기**
- A. 함수의 제한 시간(Timeout)을 늘린다 (동시 실행 개수를 제한하지 못하며 오히려 오래 실행되는 요청이 쌓여 문제를 악화시킬 수 있다).
- B. Amazon SQS 대기열을 두지 않고 API Gateway의 초당 요청 수 제한만 높인다 (동시 실행 수 자체를 제어하지 못하고 오히려 더 많은 트래픽을 허용하게 된다).
- C. **해당 Lambda 함수에 예약된 동시 실행(Reserved Concurrency)을 설정하여 최대 동시 실행 수를 제한한다.**
- D. 계정 전체의 동시 실행 할당량을 낮춰 달라고 AWS 지원에 요청한다 (계정의 모든 Lambda 함수에 영향을 주어 다른 중요한 함수의 실행까지 제한하게 된다).

**정답: C**

**해설**: **Lambda 예약된 동시성(Reserved Concurrency)**을 특정 함수에 설정하면, 해당 함수가 사용할 수 있는 최대 동시 실행 인스턴스 수를 계정 전체의 동시성 풀과 분리하여 고정할 수 있습니다. 이를 통해 다운스트림 리소스(온프레미스 DB)가 감당할 수 있는 수준으로 동시 실행을 제한하면서도, 다른 함수들이 사용할 수 있는 동시성 풀에는 영향을 주지 않습니다.

**왜 다른 보기는 오답인가**
- A: 제한 시간 조정은 함수 하나의 실행 시간에만 영향을 줄 뿐 동시에 몇 개까지 실행될 수 있는지를 제어하지 못합니다.
- B: API Gateway의 요청 제한을 높이는 것은 오히려 더 많은 트래픽을 통과시켜 문제를 악화시킬 수 있으며 동시 실행 수를 낮추는 조치가 아닙니다.
- D: 계정 전체의 동시성 할당량을 낮추면 그 계정에 있는 다른 모든 Lambda 함수의 실행 가능 용량도 함께 줄어들어 부작용이 큽니다.

> 💡 **시험 꿀팁**: 특정 Lambda 함수만 동시 실행을 제한하면서 다운스트림 자원을 보호하고 싶다면 Reserved Concurrency를 떠올리세요.

## QUESTION 428

**문제**: 한 대기업은 여러 사업부가 각자의 AWS 계정에서 애플리케이션 로그를 S3 버킷에 저장하고 있습니다. 보안팀은 규정 준수 감사를 위해 모든 로그를 하나의 중앙 로깅 계정에 있는 단일 S3 버킷으로 자동으로 복제하여 통합 모니터링하고 싶어합니다. 모든 버킷은 같은 리전에 있으며, 원본 계정의 로그도 그대로 유지되어야 합니다. 어떤 방법을 사용해야 합니까?

**보기**
- A. AWS DataSync를 사용해 매주 수동으로 각 버킷의 데이터를 복사한다 (실시간성이 없고 자동화된 지속적 복제가 아니라 운영 부담이 크다).
- B. 각 사업부 버킷에 대해 EventBridge 규칙과 Lambda 함수를 작성해 객체가 생성될 때마다 직접 복사 로직을 구현한다 (기능은 가능하지만 관리형 서비스가 이미 제공하는 기능을 재구현하는 비효율적인 방법이다).
- C. S3 Transfer Acceleration을 활성화하여 업로드 속도를 높인다 (전송 속도를 높이는 기능일 뿐 버킷 간 자동 복제 기능이 아니다).
- D. **각 사업부 버킷에서 중앙 로깅 계정의 버킷으로 향하는 S3 동일 리전 복제(Same-Region Replication, SRR)를 설정하여 크로스 계정 복제를 활성화한다.**

**정답: D**

**해설**: **S3 동일 리전 복제(Same-Region Replication, SRR)**는 동일 리전 내 서로 다른 계정에 있는 버킷 간에도 객체를 자동으로 비동기 복제할 수 있도록 지원합니다(크로스 계정 복제를 위한 대상 버킷 정책 및 IAM 역할 설정 포함). 원본 버킷의 객체는 그대로 유지되면서, 새로 생성되거나 변경된 객체가 자동으로 중앙 로깅 계정의 버킷으로 복제되어 규정 준수 감사에 필요한 통합 모니터링이 가능해집니다.

**왜 다른 보기는 오답인가**
- A: DataSync를 이용한 수동 주간 복사는 실시간이 아니며 자동화 수준이 낮아 지속적인 로그 통합에 적합하지 않습니다.
- B: 직접 EventBridge와 Lambda로 복제 로직을 구현하는 것은 가능은 하지만, 이미 관리형으로 제공되는 SRR 기능을 두고 불필요하게 개발/운영 부담을 늘리는 방법입니다.
- C: Transfer Acceleration은 클라이언트에서 S3로의 업로드 속도를 개선하는 기능으로 버킷 간 복제와는 무관합니다.

> 💡 **시험 꿀팁**: 같은 리전 내 여러 계정의 버킷을 하나로 자동 통합하고 싶다면 S3 Same-Region Replication(크로스 계정 지원)을 떠올리세요.

## QUESTION 429

**문제**: 한 회사는 12개의 AWS 계정을 운영 중이며, 수백 명의 직원이 각자 여러 계정에 접근해야 합니다. 현재는 계정마다 별도의 IAM 사용자와 비밀번호를 관리하고 있어 사용자 온보딩/오프보딩이 번거롭고 보안 위험도 큽니다. 회사는 기존 사내 Active Directory 자격 증명을 사용해 한 번 로그인하면 권한이 부여된 모든 AWS 계정과 역할에 접근할 수 있는 중앙화된 방식을 원합니다. 어떤 서비스를 사용해야 합니까?

## QUESTION 430

**문제**: 한 소셜 미디어 스타트업이 DynamoDB 테이블을 프로비저닝된 용량 모드로 운영하고 있습니다. 트래픽이 저녁 시간대에 급증했다가 새벽에는 크게 줄어드는 패턴을 보이는데, 매번 수동으로 읽기/쓰기 용량을 조정하는 것은 비효율적입니다. 회사는 트래픽 변화에 따라 프로비저닝된 용량이 자동으로 늘어나거나 줄어들도록 하여 성능과 비용의 균형을 맞추고 싶습니다. 어떤 기능을 사용해야 합니까?

**보기**
- A. DynamoDB 테이블을 온디맨드(On-Demand) 모드로 전환하고 이를 "자동 조정"이라 부른다 (온디맨드는 용량 관리를 아예 없애는 다른 접근이며, 문제에서 요구하는 프로비저닝된 용량의 동적 조정 기능이 아니다).
- B. **Application Auto Scaling을 사용하여 DynamoDB 테이블의 프로비저닝된 읽기/쓰기 용량을 목표 사용률에 따라 자동으로 조정한다.**
- C. Amazon CloudWatch 알람만 설정하고 용량 조정은 담당자가 알람을 받을 때마다 수동으로 진행한다 (자동화가 아니라 사람이 개입해야 하므로 즉각적인 대응이 어렵다).
- D. AWS Auto Scaling 대신 Lambda 함수를 두어 매시간 정각에 고정된 값으로 용량을 변경한다 (실제 트래픽 변화에 반응하지 못하고 고정 스케줄에만 의존하는 방식이라 정교하지 않다).

**정답: B**

**해설**: **Application Auto Scaling**은 DynamoDB의 프로비저닝된 읽기/쓰기 용량(RCU/WCU)에 대해 목표 활용률(target utilization) 기반의 조정 정책을 설정할 수 있게 해주며, CloudWatch 지표를 기반으로 실제 트래픽 패턴에 따라 용량을 자동으로 늘리거나 줄여줍니다. 이를 통해 저녁 피크 시간대에는 용량을 늘리고 새벽 한산한 시간에는 용량을 줄여 성능과 비용의 균형을 자동으로 맞출 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 온디맨드 모드는 용량 프로비저닝 자체를 없애고 요청당 과금하는 완전히 다른 용량 모드이며, "프로비저닝된 용량을 자동 조정"하는 요구사항과는 접근 방식이 다릅니다.
- C: CloudWatch 알람만으로는 실제 조정이 자동으로 일어나지 않고 사람이 개입해야 하므로 트래픽 급증에 즉각 대응하기 어렵습니다.
- D: 고정 스케줄 기반 조정은 실제 실시간 트래픽 변화를 반영하지 못해 예측과 다른 트래픽 패턴에서는 성능 저하나 과잉 프로비저닝이 발생할 수 있습니다.

> 💡 **시험 꿀팁**: DynamoDB의 프로비저닝된 용량을 트래픽에 따라 자동으로 조정하고 싶다는 요구사항은 Application Auto Scaling을 가리킵니다.

**문제**: 한 온라인 뱅킹 회사는 프로덕션 환경에서 다중 가용 영역(AZ) 장애나 네트워크 지연과 같은 실제 장애 상황에서 시스템이 설계한 대로 복원력 있게 동작하는지 사전에 검증하고 싶습니다. 무작위로 인프라를 망가뜨리는 자체 스크립트를 만드는 대신, AWS 관리형 서비스를 이용해 통제되고 안전하게 중단 가능한(revert 가능한) 실험을 실행하려고 합니다. 어떤 서비스를 사용해야 합니까?

- B: CloudWatch Synthetics는 엔드포인트나 워크플로가 정상적으로 동작하는지 지속적으로 모니터링하는 카나리 도구로, 장애를 의도적으로 발생시키는 기능은 없습니다.
- D: AWS Config는 리소스 구성이 정책이나 모범 사례를 준수하는지 지속적으로 평가하고 기록하는 서비스로, 실제 장애 조건을 만들어내는 기능은 제공하지 않습니다.

> 💡 **시험 꿀팁**: "통제된 카오스 엔지니어링 실험"이라는 표현이 나오면 AWS Fault Injection Simulator(FIS)를 떠올리세요.

**문제**: 한 회사가 수백 개의 EBS 볼륨을 운영 중이며, 각 볼륨에 대해 매일 스냅샷을 생성하고 30일이 지난 스냅샷은 자동으로 삭제되도록 정책을 표준화하고 싶습니다. 현재는 각 팀이 cron 작업과 AWS CLI 스크립트를 직접 작성해 스냅샷을 관리하고 있어 정책이 일관되지 않고 관리 부담이 큽니다. 이를 완전관리형 서비스로 표준화하려면 어떤 방법을 사용해야 합니까?

## QUESTION 434

**문제**: 한 금융 거래 플랫폼은 초저지연 TCP 기반 주문 체결 API를 운영하고 있습니다. 이 API는 방화벽 화이트리스트 정책 때문에 고정된 IP 주소로 노출되어야 하며, 초당 수백만 건의 연결을 최소한의 지연 시간으로 처리해야 합니다. HTTP 계층의 라우팅 기능은 필요하지 않습니다. 어떤 로드 밸런서를 사용해야 합니까?

**보기**
- A. Application Load Balancer(ALB) (HTTP/HTTPS 계층 라우팅에 특화되어 있고, 고정 IP를 직접 제공하지 않으며 초저지연 TCP 처리보다는 L7 기능에 최적화되어 있다).
- B. **Network Load Balancer(NLB)를 사용하여 각 가용 영역에 고정 IP(탄력적 IP)를 할당하고 TCP 계층에서 초고성능·저지연 트래픽을 처리한다.**
- C. Classic Load Balancer(CLB) (레거시 로드 밸런서로 고정 IP를 기본 제공하지 않고 NLB만큼의 처리 성능과 확장성을 제공하지 못한다).
- D. Amazon CloudFront (콘텐츠 전송 및 캐싱에 최적화된 CDN 서비스로, TCP 커넥션 기반의 초저지연 주문 체결 워크로드에는 적합하지 않다).

**정답: B**

**해설**: **Network Load Balancer(NLB)**는 OSI 4계층에서 동작하며 초당 수백만 건의 요청을 매우 낮은 지연 시간으로 처리할 수 있도록 설계되었습니다. 각 가용 영역마다 고정된 정적 IP(또는 탄력적 IP)를 할당할 수 있어 방화벽 화이트리스트 요구사항을 만족시키며, TCP/UDP 기반의 극한 성능이 필요한 초저지연 워크로드에 가장 적합한 로드 밸런서입니다.

**왜 다른 보기는 오답인가**
- A: ALB는 HTTP/HTTPS 요청 기반 라우팅, 경로/호스트 기반 규칙 등 L7 기능에 특화되어 있으며 고정 IP를 기본으로 제공하지 않아 이 시나리오의 요구사항에 맞지 않습니다.
- C: Classic Load Balancer는 레거시 서비스로 고정 IP 지원이 제한적이고, NLB에 비해 성능과 기능 면에서 뒤떨어져 신규 아키텍처에는 권장되지 않습니다.
- D: CloudFront는 콘텐츠 캐싱과 전송 가속에 초점을 맞춘 CDN이며, TCP 커넥션 기반의 초저지연 주문 체결 시스템에는 적합하지 않습니다.

> 💡 **시험 꿀팁**: "고정 IP + 초저지연 TCP/UDP 처리"라는 조합이 나오면 Network Load Balancer가 정답입니다.

## QUESTION 435

**문제**: 한 회사가 수십 개의 마이크로서비스로 구성된 주문 처리 시스템을 운영 중입니다. 최근 특정 요청이 비정상적으로 느려지는 문제가 발생했는데, 어느 마이크로서비스에서 병목이 생기는지 파악하기가 어렵습니다. 개발팀은 하나의 요청이 여러 서비스를 거치는 전체 경로를 시각화하고, 각 서비스 구간에서 소요된 시간을 세분화하여 분석하고 싶어합니다. 어떤 서비스를 사용해야 합니까?

**보기**
- A. Amazon CloudWatch 지표(metric)만 사용하여 각 서비스의 평균 응답 시간을 개별적으로 모니터링한다 (서비스별 지표는 확인할 수 있지만 하나의 요청이 여러 서비스를 거치는 종단 간 경로를 추적하지는 못한다).
- B. VPC Flow Logs를 활성화하여 네트워크 트래픽을 분석한다 (IP/포트 수준의 네트워크 흐름 정보만 제공할 뿐 애플리케이션 계층의 요청 추적에는 사용할 수 없다).
- C. **AWS X-Ray를 사용하여 서비스 맵을 생성하고 요청의 종단 간(end-to-end) 추적 정보를 수집·분석한다.**
- D. AWS CloudTrail 로그를 분석하여 API 호출 이력을 확인한다 (CloudTrail은 AWS API 호출에 대한 감사 로그를 제공할 뿐, 애플리케이션 내부의 요청 흐름이나 지연 시간 분석에는 사용되지 않는다).

**정답: C**

**해설**: **AWS X-Ray**는 분산 애플리케이션에서 하나의 요청이 여러 마이크로서비스를 거치는 전체 경로를 추적하여 서비스 맵으로 시각화하고, 각 서비스 구간에서 소요된 지연 시간과 오류 발생 지점을 세분화하여 보여줍니다. 이를 통해 어느 마이크로서비스가 병목의 원인인지 신속하게 파악할 수 있어 분산 추적/관찰 가능성(observability) 요구사항에 가장 적합합니다.

**왜 다른 보기는 오답인가**
- A: CloudWatch 지표는 각 서비스의 개별 성능을 모니터링하는 데는 유용하지만, 하나의 요청이 여러 서비스를 넘나드는 전체 흐름을 연결해서 보여주지는 못합니다.
- B: VPC Flow Logs는 네트워크 인터페이스 수준의 트래픽 로그(IP, 포트, 바이트 수 등)를 제공할 뿐 애플리케이션 요청 단위의 추적 정보는 담고 있지 않습니다.
- D: CloudTrail은 AWS 리소스에 대한 API 호출 기록(누가, 언제, 무엇을 호출했는지)을 감사하는 서비스로, 애플리케이션 내부 로직의 요청 경로나 지연 분석과는 목적이 다릅니다.

> 💡 **시험 꿀팁**: 마이크로서비스 간 요청 흐름을 추적하고 병목 구간을 시각화하고 싶다면 AWS X-Ray를 떠올리세요.

**문제**: 한 회사가 몇 년 전에 암호화를 활성화하지 않은 채로 생성한 Amazon RDS for PostgreSQL 인스턴스를 운영 중입니다. 최근 보안 감사에서 저장 데이터 암호화(encryption at rest)가 필수 요건으로 지정되었습니다. RDS는 기존 인스턴스에 대해 암호화를 직접 켜는 기능을 제공하지 않습니다. 다운타임을 최소화하면서 이 데이터베이스를 암호화된 상태로 전환하려면 어떤 절차를 따라야 합니까?

**보기**
- A. RDS 콘솔에서 인스턴스를 선택하고 "암호화 활성화" 옵션을 토글로 켠다 (RDS는 이미 존재하는 인스턴스의 암호화를 즉시 켜고 끄는 토글 기능을 제공하지 않는다).
- B. 인스턴스를 삭제한 후 동일한 이름으로 암호화 옵션을 켠 채 새로 생성한다 (기존 데이터가 모두 사라지므로 데이터 손실 위험이 매우 크고 권장되지 않는다).
- C. AWS DMS(Database Migration Service)를 이용해 실시간으로 다른 암호화된 데이터베이스 엔진으로 이전한다 (엔진을 변경하지 않고 동일 엔진 그대로 암호화를 적용하려는 시나리오에는 불필요하게 복잡하고 무거운 방법이다).
- D. **암호화되지 않은 인스턴스의 스냅샷을 생성한 뒤, 스냅샷을 복사하면서 암호화를 활성화하고, 암호화된 스냅샷으로부터 새 DB 인스턴스를 복원한다.**

**정답: D**

**왜 다른 보기는 오답인가**
- A: RDS 콘솔이나 API에는 기존 인스턴스의 암호화 여부를 즉시 전환하는 토글 기능이 존재하지 않습니다.
- B: 인스턴스를 삭제하고 새로 생성하면 기존 데이터가 모두 사라지므로, 스냅샷을 통한 데이터 보존 없이 진행하는 것은 데이터 손실 위험이 매우 큽니다.
- C: DMS를 이용한 이전은 이기종 엔진 마이그레이션이나 무중단 마이그레이션이 필요한 복잡한 시나리오에 적합하며, 단순히 동일 엔진에서 암호화만 적용하려는 목적에는 과도하게 복잡한 방법입니다.

> 💡 **시험 꿀팁**: 기존 미암호화 RDS 인스턴스를 암호화하고 싶다면 "스냅샷 생성 → 암호화하며 스냅샷 복사 → 암호화된 스냅샷에서 복원"의 3단계 절차를 기억하세요.

**문제**: 한 회사가 레거시 웹 애플리케이션을 Application Load Balancer 뒤의 여러 EC2 인스턴스로 운영 중입니다. 이 애플리케이션은 사용자의 세션 상태를 외부 저장소가 아닌 각 인스턴스의 메모리에 저장하도록 설계되어 있어, 동일 사용자의 후속 요청이 처음 연결되었던 인스턴스와 다른 인스턴스로 라우팅되면 세션이 끊기고 로그인 정보가 사라집니다. 애플리케이션 코드를 즉시 재작성할 수 없는 상황에서, 로드 밸런서 설정만으로 이 문제를 완화하려면 어떻게 해야 합니까?

**보기**
- A. 모든 요청을 라운드 로빈 방식으로 균등하게 분배하는 기본 알고리즘을 유지한다 (기본 라운드 로빈은 동일 사용자의 요청도 매번 다른 인스턴스로 분산시킬 수 있어 세션 유지 문제를 해결하지 못한다).

- C: 인스턴스를 1개로 고정하면 세션 문제는 우회할 수 있지만 다중 AZ 고가용성과 트래픽 증가에 대한 확장성을 완전히 포기하게 되어 바람직한 해결책이 아닙니다.
- D: Route 53 가중치 기반 라우팅은 DNS 수준에서 여러 리소스로 트래픽 비율을 나누는 기능이며, 개별 사용자 세션을 특정 인스턴스에 고정시키는 기능이 아닙니다.

> 💡 **시험 꿀팁**: 인스턴스 메모리에 세션을 저장하는 레거시 앱에서 동일 사용자를 같은 인스턴스로 계속 보내고 싶다면 ALB의 스티키 세션(고정 세션) 활성화를 떠올리세요. (장기적으로는 ElastiCache 등 외부 세션 저장소로 전환하는 것이 더 바람직합니다.)

## QUESTION 439

**문제**: 한 법률 회사가 계약서 원본 문서를 S3 버킷에 저장하고 있습니다. 최근 내부 직원의 실수로 중요한 계약서 객체가 삭제되는 사고가 발생했습니다. 회사는 향후 이러한 객체가 삭제되더라도 이전 버전을 복구할 수 있어야 하고, 나아가 객체를 영구적으로 삭제하려면 반드시 루트 계정 수준의 추가 인증(MFA)이 필요하도록 강화하고 싶습니다. 어떤 조합을 사용해야 합니까?

**보기**
- A. S3 버킷 정책으로 모든 삭제(DeleteObject) API 호출을 거부한다 (정당한 사유로 객체를 삭제해야 하는 경우까지 원천 차단하여 운영 유연성이 없고, 버전 복구라는 요구사항 자체를 해결하지 못한다).
- B. S3 버킷에 라이프사이클 규칙을 설정하여 90일 후 객체를 Glacier로 전환한다 (아카이브 비용 절감에는 도움이 되지만 삭제 방지나 버전 복구, MFA 강제와는 무관하다).
- C. **S3 버킷 버전 관리(Versioning)를 활성화하고 MFA 삭제(MFA Delete)를 함께 구성하여 이전 버전 복구 및 영구 삭제 시 추가 인증을 요구한다.**
- D. AWS Backup을 사용해 S3 버킷을 매일 다른 버킷으로 백업한다 (별도 백업 사본을 만드는 방식으로 어느 정도 복구는 가능하지만, 버전별 즉시 복구나 MFA 삭제 강제와 같은 세밀한 보호 기능을 제공하지는 않는다).

**정답: C**

**해설**: **S3 버전 관리(Versioning)**를 활성화하면 객체가 덮어써지거나 삭제되더라도 이전 버전이 버킷 내에 보존되어 언제든 복구할 수 있습니다. 여기에 **MFA 삭제(MFA Delete)**를 함께 구성하면, 버전 관리를 비활성화하거나 특정 버전을 영구적으로 삭제하려고 할 때 루트 계정의 MFA 토큰 기반 추가 인증이 반드시 필요해져 실수나 악의적인 삭제로부터 객체를 이중으로 보호할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 모든 삭제 API를 원천 차단하면 정당한 운영상의 삭제 작업까지 막혀버리고, 실수로 삭제된 이전 버전을 복구하는 요구사항도 해결하지 못합니다.
- B: Glacier로의 라이프사이클 전환은 스토리지 비용 최적화를 위한 것으로, 삭제 방지나 버전 복구, MFA 인증 강제와는 목적이 다릅니다.
- D: 별도 버킷으로의 백업은 추가적인 복구 수단이 될 수는 있지만, 원본 버킷에서의 즉각적인 버전별 복구나 MFA 삭제 강제와 같은 세밀한 통제를 제공하지 않습니다.

> 💡 **시험 꿀팁**: "삭제된 객체를 복구하고 싶다 + 영구 삭제 시 추가 인증을 강제하고 싶다"는 요구사항 조합은 S3 Versioning과 MFA Delete를 함께 떠올리게 하는 신호입니다.

## QUESTION 440

- D. **리소스에 사업부를 나타내는 비용 할당 태그(Cost Allocation Tag)를 지정하고 이를 활성화하여 Cost Explorer와 청구서에서 태그별 비용 내역을 확인한다.**

**정답: D**

**해설**: **비용 할당 태그(Cost Allocation Tag)**를 리소스(EC2 인스턴스, S3 버킷, RDS 인스턴스 등)에 부여하고 결제 콘솔에서 해당 태그를 활성화하면, Cost Explorer와 상세 청구서(Cost and Usage Report)에서 태그 값별로 비용을 그룹화하여 확인할 수 있습니다. 이를 통해 계정을 분리하지 않고도 사업부 단위로 비용을 세분화하여 차지백/쇼우백 보고에 활용할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 계정을 새로 나누는 것은 비용 세분화의 한 방법이 될 수 있지만, 대규모 마이그레이션이 필요하고 "계정을 나누지 않고" 해결하려는 요구사항에 부합하지 않습니다.
- B: AWS Budgets는 예산 초과 시 알림을 주는 기능일 뿐, 리소스별로 비용을 사업부 단위로 세분화하여 추적하는 근본적인 방법이 아닙니다.
- C: 리전을 사업부별로 강제 분리하는 것은 비용 추적과 무관한 결정이며, 지연 시간이나 데이터 주권 등 다른 이유로 사용되는 개념을 오용한 것입니다.

> 💡 **시험 꿀팁**: 공유 계정 내에서 사업부/프로젝트별로 비용을 나누어 차지백/쇼우백을 하고 싶다면 비용 할당 태그(Cost Allocation Tag)를 떠올리세요.
