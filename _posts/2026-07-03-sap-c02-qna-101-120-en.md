## QUESTION 101

**Question**: In a multi-account setup, the Sales account's S3 bucket (petabyte-scale, KMS-encrypted) must be accessed by the Marketing account's QuickSight (which already has a dedicated IAM service role). Provide secure cross-account access with minimal operational overhead.

> ⚠️ The boundaries between choices A/B/C in the original PDF were garbled during scanning and couldn't be reliably reconstructed. The summary below covers what could be recovered; the key lesson is in the logic behind correct answer D.

**Choices (summarized)**
- A. Create a new S3 bucket in the Marketing account, replicate objects from Sales via S3 replication, and update QuickSight permissions.
- B. Create an SCP that "grants" the Marketing account access to the S3 bucket.
- C. Share the Sales account's KMS key via AWS RAM, update the bucket policy, create a KMS grant for decrypt access, and update QuickSight permissions.
- D. **Create an IAM role in the Sales account granting S3 bucket access. Have the Marketing account assume that role to access the bucket. Update the QuickSight role's trust relationship with the new IAM role in the Sales account.**

**Correct Answer: D**

**Explanation**
This is the standard **cross-account role assumption** pattern. Create an IAM role with the needed permissions in the Sales account (which owns the resource), and have Marketing's QuickSight role **assume** it via a trust relationship. This provides secure access without duplicating the data — the most standard, lowest-overhead approach.

**Why the other choices are wrong**
- A: Replicating (copying) data into a new Marketing-account bucket introduces sync lag and duplicate storage cost at petabyte scale, and doesn't match "grant access" so much as duplicate the data itself.
- B: **SCPs don't grant permissions — they only set a ceiling (restriction).** The concept of "granting access via an SCP" is simply invalid.
- C: Sharing the KMS key via RAM plus separately managing a bucket policy and KMS grant could technically work, but managing multiple separate resources (key sharing, bucket policy, KMS grant) is more operationally complex than the single role-assumption approach in D.

> 💡 **Exam tip**: For secure access to another account's encrypted S3 data, don't duplicate the data or try to "grant" access via an SCP — the standard pattern is to **create a role in the resource-owning account and have the other account assume it.** Remember SCPs can never grant permissions (see Questions 32 and 57).

## QUESTION 102

**Question**: An on-premises Microsoft SQL Server Always On cluster needs a **heterogeneous** migration to an AWS managed database service (a different engine, e.g., MySQL).

**Choices**
- A. Migrate using backup and restore utilities to Amazon RDS for MySQL.
- B. Transfer data to S3 via Snowball Edge, then load into RDS MySQL using SQL Server's "BULK INSERT" S3 integration feature.
- C. **Use AWS Schema Conversion Tool (SCT) to convert the schema to Amazon RDS for MySQL, then use AWS DMS to migrate the data.**
- D. Transfer data to S3 via DataSync, then load into RDS MySQL using SQL Server's S3 integration feature.

**Correct Answer: C**

**Explanation**
For a **heterogeneous** migration between different database engines, always use **AWS Schema Conversion Tool (schema conversion) + AWS DMS (data migration).**

**Why the other choices are wrong**
- A: Backup/restore utilities only work for **homogeneous** migrations (SQL Server to SQL Server) — the backup file format itself isn't compatible with a different engine (MySQL).
- B, D: "BULK INSERT with S3 integration" is a **SQL Server-only** feature; RDS for MySQL has no such capability. Both assume a nonexistent feature combination.

> 💡 **Exam tip**: For migrations between **different database engines (heterogeneous)**, always think **SCT (schema conversion) + DMS (data migration)**. Backup/restore utilities and engine-specific bulk-load features only work for same-engine migrations.

## QUESTION 103

**Question**: A publisher's design team (in the dev account) needs to upload static assets to the production account's S3 bucket after testing, without exposing other parts of the web app to risk. (Choose three.)

**Choices**
- A. **Create a new IAM policy in the production account allowing read/write access to the S3 bucket.**
- B. Create an IAM policy in the dev account granting access to the S3 bucket.
- C. **Create a role in the production account, attach the new policy, and define the dev account as a trusted entity.**
- D. Create a role in the dev account, defining the production account as a trusted entity.
- E. **Create a group in the dev account containing all design team IAM users, and attach a policy allowing `sts:AssumeRole` on the role in the production account.**
- F. Create a group in the dev account, allowing `sts:AssumeRole` on a role within the dev account itself.

**Correct Answer: A, C, E**

**Explanation**
Create a narrowly-scoped policy (A) and a trusting role (C) in the **production** account (which owns the resource), and grant the dev account's design team group only the ability to assume that role (E). This scopes design team access to exactly that S3 bucket, without exposing other production resources.

**Why the other choices are wrong**
- B: Creating a policy in the dev account for production resources isn't the correct flow.
- D: The trust direction is backward — the role must live in the **production** account (owning the resource), trusting the dev account.
- F: Assuming a role **within the dev account itself** doesn't cross the account boundary needed to reach production.

> 💡 **Exam tip**: The standard cross-account access pattern: **① a narrowly-scoped policy + role in the resource-owning account (trusting the other account), ② `sts:AssumeRole` permission granted only in the requesting account.** Getting the trust direction backward breaks it.

## QUESTION 104

**Question**: An Elastic Beanstalk pilot app is running as a **single-instance environment** (to save cost during development), with CPU utilization frequently exceeding 85%, causing bottlenecks. Mitigate this before launching to production, with minimal operational overhead.

**Choices**
- A. Create a new Elastic Beanstalk application, choosing the load-balanced environment type.
- B. Create a second environment with a traffic-splitting deployment policy.
- C. **Modify the existing environment's capacity configuration to the load-balanced type**, select all AZs, and add a scaling rule for CPU exceeding 85%.
- D. Choose an "environment rebuild" action with a load-balancing option.

**Correct Answer: C**

**Explanation**
Elastic Beanstalk lets you **modify an existing environment's capacity configuration** in place, switching from single-instance to load-balanced (Auto Scaling). No need to create a new application or environment — the lowest-overhead path.

**Why the other choices are wrong**
- A: Creating an entirely new application is unnecessary duplication of what simply modifying the existing environment achieves.
- B: Traffic-splitting deployment is a feature for **testing new application versions**, not for solving a capacity/scaling problem.
- D: "Environment rebuild" tears down and recreates the environment — more disruptive than a simple configuration change.

> 💡 **Exam tip**: To convert an Elastic Beanstalk environment from single-instance to load-balanced, **modify the existing environment's capacity configuration directly** — no need for a new application/environment or a full rebuild.

## QUESTION 105

**Question**: A financial company runs a business-critical app on EC2 (ELB+ASG) with a self-managed MySQL database experiencing heavy I/O. It handles normal traffic fine but slows down during the **last 3 days of each month** (month-end reporting). Minimize database performance impact while handling the month-end load.

**Choices**
- A. Use larger instances and change all EBS volumes to GP2.
- B. **Perform a one-time migration of the database cluster to Amazon RDS, and create additional read-only replicas to handle the month-end load.**
- C. Use CloudWatch + Lambda to dynamically change EBS volume type/size/IOPS.
- D. Snapshot before month-end, swap to max-size/max-IOPS PIOPS volumes, then revert afterward.

**Correct Answer: B**

**Explanation**
The root cause is one self-managed MySQL instance handling both writes and heavy reporting reads simultaneously. **Migrating to RDS and adding read replicas** lets month-end reporting queries be offloaded to replicas, without impacting the primary's write performance.

**Why the other choices are wrong**
- A: Bigger instances/volumes are a band-aid that doesn't fix the underlying "single DB handling both roles" architecture problem.
- C: Dynamic EBS scaling automation is complex and still doesn't address the root architectural issue.
- D: Manually swapping snapshots/volumes every month is a cumbersome, risky operational process.

> 💡 **Exam tip**: When a self-managed database struggles under **predictable periodic reporting load** (like month-end), migrate to a **managed service and add read replicas** to offload reporting queries — the standard fix, rather than manual storage resizing or custom automation.

## QUESTION 106

**Question**: A stable Java application with complex dependencies runs on an on-premises VM. The company wants to modernize its tech stack, migrate to AWS, and minimize **both server management overhead and code changes.**

**Choices**
- A. **Use AWS App2Container to migrate to Amazon ECS on AWS Fargate**, store the image in ECR, grant the ECS task execution role ECR access, and interact via an ALB.
- B. Migrate the code into a container running on Lambda, plus API Gateway.
- C. Use App2Container to migrate to **EKS with a managed node group.**
- D. Migrate the code into a Lambda container, using an ALB.

**Correct Answer: A**

**Explanation**
**AWS App2Container** automatically containerizes an existing complex Java (or .NET) VM-based application with **minimal code changes.** Combined with **Fargate** (no server/cluster management), this satisfies both requirements simultaneously.

**Why the other choices are wrong**
- B, D: Adapting the application code to Lambda's execution model (cold starts, stateless invocation) requires much more significant change than App2Container's approach.
- C: App2Container is correct, but **EKS managed node groups still require managing the underlying EC2 instances (nodes)** — more server management overhead than Fargate (A).

> 💡 **Exam tip**: To containerize an existing complex VM-based app with **minimal code change**, think **AWS App2Container** first, and pair it with **Fargate** (not EKS managed node groups, which still need EC2 management) to also minimize server management overhead.

## QUESTION 107

**Question**: An asynchronous HTTP app runs on Lambda + a public API Gateway endpoint in us-east-1. Redesign it to support failover to another AWS Region.

**Choices**
- A. Create only a new API Gateway endpoint in us-west-2, still routing traffic to the Lambda function in us-east-1, plus Route 53 failover.
- B. Add SQS between API Gateway and Lambda.
- C. Deploy Lambda in us-west-2 too, create an API Gateway endpoint there, and manage traffic between the two endpoints with Global Accelerator + an ALB.
- D. **Deploy both the Lambda function and API Gateway endpoint in us-west-2 too, and use a Route 53 Failover routing policy to route traffic between the two API Gateway endpoints.**

**Correct Answer: D**

**Explanation**
Since **both Lambda and API Gateway are regional resources**, true failover requires fully duplicating **both** in a second Region. A **Route 53 Failover routing policy** connecting the two API Gateway endpoints is the standard, simplest pattern.

**Why the other choices are wrong**
- A: Duplicating only API Gateway while Lambda stays solely in us-east-1 means a full us-east-1 outage would still break the "failover" endpoint, since it depends on the same Lambda function.
- B: Adding SQS fundamentally changes the architecture from synchronous to asynchronous — unrelated to the regional failover goal.
- C: Global Accelerator + an ALB in front of API Gateway is an unusual, unnecessarily complex combination (Global Accelerator typically targets ALB/NLB/EIP endpoints).

> 💡 **Exam tip**: For cross-Region failover of a serverless (Lambda + API Gateway) app, **fully duplicate both Lambda and API Gateway** in the second Region and connect them via **Route 53 Failover routing** — duplicating only one component isn't real failover.

## QUESTION 108

**Question**: A retail company set up consolidated billing under Organizations, mapping departments to OUs (Finance, Sales, HR, Marketing, Operations). HR purchased several Reserved Instances (RIs) in its production account ahead of a new system launch. HR wants to **prevent other departments from sharing** this discount.

**Choices**
- A. Turn off sharing in the HR production account's **own** Billing console.
- B. Remove the HR production account from the organization and add it only to a separate consolidated billing configuration.
- C. **In the organization's master account's Billing and Cost Management console, turn off discount sharing for the HR production account.**
- D. Create an SCP restricting access to accounts, applied to other departments' OUs.

**Correct Answer: C**

**Explanation**
**RI/Savings Plan discounts are automatically shared across all accounts in a consolidated billing family by default.** To exclude a specific account, this setting must be toggled off **from the master (payer) account's Billing and Cost Management console** for that account.

**Why the other choices are wrong**
- A: This setting must be controlled from the **master account**, not the member account's own console.
- B: Removing the account from the organization entirely is an extreme measure that also forfeits all other Organizations benefits (SCPs, centralized management, etc.).
- D: **SCPs govern IAM permissions only, and have nothing to do with billing/RI sharing settings.**

> 💡 **Exam tip**: **RI/Savings Plan discount sharing is automatic by default** — to exclude a specific account, toggle sharing off for it from the **master (payer) account's Billing console.** Neither the member account itself nor an SCP can control this.

## QUESTION 109

**Question**: A popular web app runs on EC2 (private subnets, ASG) behind an ALB, with Session Manager configured. After a new release, some instances are marked unhealthy and get **terminated**, reducing capacity. CloudWatch logs are inconclusive. How to access the instances before they're terminated, for investigation?

**Choices**
- A. Suspend the Auto Scaling group's **HealthCheck** process.
- B. Enable EC2 **termination protection.**
- C. Set the termination policy to **OldestInstance.**
- D. **Suspend the Auto Scaling group's "Terminate" process**, and log into the unhealthy instances via Session Manager.

**Correct Answer: D**

**Explanation**
Auto Scaling groups have individually **suspendable processes** (Launch, Terminate, HealthCheck, etc.). Suspending only the **"Terminate" process** keeps instances marked unhealthy (still detected) but prevents actual termination — giving time to investigate via Session Manager.

**Why the other choices are wrong**
- A: Suspending HealthCheck itself stops instances from even being **marked** unhealthy — losing the very signal used to find affected instances.
- B: EC2 termination protection is a separate feature (blocks direct termination via the EC2 API/console) and doesn't stop ASG's own unhealthy-instance replacement.
- C: A termination policy (like OldestInstance) only governs **which instance to remove during scale-in** — a different mechanism than unhealthy-instance termination.

> 💡 **Exam tip**: To preserve an instance ASG has marked unhealthy for investigation, **suspend the ASG's "Terminate" process** specifically — not HealthCheck (stops detection), EC2 termination protection, or the termination policy.

## QUESTION 110

**Question**: A company wants to centrally manage AWS WAF rules across multiple accounts (different OUs), with the ability to add/remove target accounts/OUs as needed, and **automatically detect and remediate non-compliant WAF rules** everywhere. Minimal operational overhead?

**Choices**
- A. **Use AWS Firewall Manager** to manage WAF rules across the organization, store target accounts/OUs in **Parameter Store**, and use **EventBridge to detect parameter changes and invoke Lambda** to update the security policy in the Firewall Manager admin account.
- B. Deploy an org-wide AWS Config rule + Lambda auto-remediation + WAF rule deployment via StackSets.
- C. Create WAF rules in the master account, track target accounts via Lambda environment variables, and use STS to assume cross-account roles.
- D. Use Control Tower with target accounts stored in KMS, plus IAM users/access keys in member accounts.

**Correct Answer: A**

**Explanation**
**AWS Firewall Manager** is the purpose-built service for centrally managing (and auto-remediating) WAF policies across a multi-account, multi-OU Organizations environment. Parameter Store + EventBridge + Lambda provides a light, low-ops way to dynamically manage the target account/OU list.

**Why the other choices are wrong**
- B: Reimplements what Firewall Manager already provides natively via Config rules + custom remediation + StackSets.
- C: A fully custom cross-account automation solution — far more operational overhead than the purpose-built service.
- D: **Control Tower doesn't manage WAF rules, and KMS isn't a configuration store** — a technically mismatched combination.

> 💡 **Exam tip**: For centralized WAF rule management with automatic compliance remediation across an organization, **AWS Firewall Manager** is the answer — don't reinvent it with Config+Lambda+StackSets or Control Tower.

## QUESTION 111

**Question**: A Lambda function (same VPC as Aurora) receives DB credentials via environment variables, aggregates data, and stores it in an SSE-KMS-encrypted S3 bucket. Data must not traverse the internet. **Minimize the impact if the DB credentials are compromised.**

**Choices**
- A. **Enable IAM database authentication on the Aurora cluster**, update the Lambda IAM role accordingly, and **deploy a Gateway VPC endpoint for S3.**
- B. IAM database authentication + enforce **HTTPS only** for S3.
- C. Store credentials in Parameter Store (with rotation) + S3 Gateway endpoint.
- D. Store credentials in Secrets Manager (with rotation) + enforce **HTTPS only** for S3.

**Correct Answer: A**

**Explanation**
**IAM database authentication** eliminates static credentials entirely, replacing them with short-lived IAM-based tokens — fundamentally minimizing the impact of any "compromise" since there's no long-lived credential to steal. A **Gateway VPC endpoint for S3** ensures traffic stays within the AWS network, never touching the internet.

**Why the other choices are wrong**
- B: IAM DB auth is correct, but **HTTPS alone** doesn't prevent traffic from traversing the internet — encryption ≠ staying off the public internet (a VPC endpoint is needed).
- C, D: Rotation in Parameter Store/Secrets Manager is an improvement, but a **static, stealable credential still exists** — less fundamental than eliminating credentials via IAM auth. D also only enforces HTTPS, failing the "no internet" requirement.

> 💡 **Exam tip**: **IAM database authentication** eliminates static DB credentials entirely — a stronger mitigation against credential compromise than even Secrets Manager/Parameter Store rotation. And "must not travel over the internet" requires a **VPC endpoint**, not just HTTPS.

## QUESTION 112

**Question**: A mobile gaming company migrated all infrastructure to AWS. Cost Explorer shows frequent creation/termination of large instance types driving high costs — caused by developers launching inappropriately expensive instance types for testing. **Restrict which instance types developers can launch.**

**Choices**
- A. An AWS Config managed rule (allowed instance types).
- B. An EC2 launch template specifying allowed instance types.
- C. **Create a new IAM policy specifying allowed instance types, attached to the developers' IAM group.**
- D. Use EC2 Image Builder to create a golden image pipeline.

**Correct Answer: C**

**Explanation**
An **IAM policy with an `ec2:InstanceType` condition, attached directly to the developer group**, is the simplest, most direct **preventive** control — blocking `ec2:RunInstances` for any type outside the allowed list.

**Why the other choices are wrong**
- A: An AWS Config rule is a **detective** control (flags violations after launch) — it doesn't prevent the launch itself.
- B: A launch template is a convenience default — it doesn't enforce/prevent a user from launching a different type if they have general permission.
- D: EC2 Image Builder manages AMI content (standardized images) — unrelated to instance type selection.

> 💡 **Exam tip**: To restrict which **EC2 instance types** a specific group can launch, use an **IAM policy with an `ec2:InstanceType` condition** attached to that group — Config (detective), launch templates (unenforced defaults), and Image Builder (AMI content) don't fit this need.

## QUESTION 113

**Question**: Multiple projects across multiple accounts under one Organization need cost allocated per project. Many EC2 instances are found missing the project cost-allocation tag. Fix the existing problem and prevent recurrence. (Choose three.)

**Choices**
- A. **Create an AWS Config rule in each account** to find resources missing the tag.
- B. **Create an SCP that denies `ec2:RunInstances` when the project tag is missing**, applied organization-wide.
- C. Use Amazon Inspector to find resources missing the tag.
- D. Create an IAM policy in each account denying `ec2:RunInstances` when the tag is missing.
- E. **Create an AWS Config aggregator** to collect an org-wide list of EC2 instances missing the project tag.
- F. Use AWS Security Hub to aggregate the list of EC2 instances missing the project tag.

**Correct Answer: A, B, E**

**Explanation**
Find existing violations with **Config rules per account (A)**, aggregate the findings org-wide with a **Config aggregator (E)**, and prevent recurrence with a **preventive SCP** denying instance creation without the tag (B).

**Why the other choices are wrong**
- C: **Amazon Inspector is a vulnerability-scanning service** — it has no capability to find resources missing a tag.
- D: Per-account IAM policies are more maintenance-heavy than a single org-wide SCP.
- F: **Security Hub aggregates security findings** — an AWS Config aggregator is the more direct, specific tool for this tag-compliance aggregation task.

> 💡 **Exam tip**: To find and prevent recurrence of tag-missing resources across an organization: **① Config rules (per account) + ② a Config aggregator (org-wide view) + ③ a preventive SCP** — not Inspector (security scanning) or per-account IAM policies.

## QUESTION 114

**Question**: An on-premises monitoring solution uses PostgreSQL for event persistence, but can't scale due to excessive ingestion, running out of storage. Design a hybrid solution (VPN already exists) with: (1) managed services minimizing operational complexity, (2) a buffer that auto-scales with ingestion and needs no ongoing management, (3) a near-real-time visualization dashboard tool, (4) support for semi-structured JSON with dynamic schema. (Choose two.)

**Choices**
- A. **Use Amazon Kinesis Data Firehose to buffer events**, plus a Lambda function to process/transform them.
- B. Use Kinesis **Data Streams** (requires shard management) to buffer events, plus Lambda.
- C. Configure an Aurora PostgreSQL DB cluster to receive events, and use QuickSight to visualize.
- D. **Configure Amazon Elasticsearch Service (ES) to receive events**, using the **deployed Kibana endpoint for near-real-time visualization and dashboards.**
- E. Configure an Amazon Neptune (graph database) instance to receive events, and use QuickSight to visualize.

**Correct Answer: A, D**

**Explanation**
**Kinesis Data Firehose** is fully managed and auto-scales with ingestion volume without shard management (the key difference from Data Streams). **Elasticsearch Service + Kibana** natively supports semi-structured JSON/dynamic schema and provides built-in near-real-time dashboards.

**Why the other choices are wrong**
- B: Kinesis **Data Streams** requires manual shard management, failing "needs no ongoing management."
- C: Aurora PostgreSQL is a **fixed-schema relational database** — less natural for dynamic semi-structured JSON, and reintroduces the same "can't scale" problem as their original PostgreSQL solution.
- E: **Neptune is a graph database** — a completely mismatched data model for semi-structured JSON events and dashboards.

> 💡 **Exam tip**: For a "fully managed, auto-scaling, no-ongoing-management buffer," use **Kinesis Data Firehose** (not Data Streams). For **semi-structured JSON with dynamic schema plus near-real-time dashboards**, use **Elasticsearch (OpenSearch) + Kibana.**

## QUESTION 115

**Question**: A multi-AZ VPC (public/private subnets, a NAT gateway per public subnet) runs apps mostly reading/writing to Kinesis Data Streams, mostly from private subnets. Cost Explorer's "EC2-Other" category stays high, driven by **NAT Gateway byte-processing charges.** Reduce cost while maintaining functionality.

**Choices**
- A. Enable VPC Flow Logs, analyze "removable traffic" with Athena, and check if security groups are blocking high-cost traffic.
- B. Add an interface VPC endpoint for Kinesis Data Streams, and check only **IAM permissions.**
- C. Enable VPC Flow Logs and Amazon Detective, review findings unrelated to Kinesis, and block that traffic.
- D. **Add an interface VPC endpoint for Kinesis Data Streams to the VPC, and verify the VPC endpoint policy allows the application's traffic.**

**Correct Answer: D**

**Explanation**
Private-subnet apps sending Kinesis traffic through the NAT Gateway incur processing charges. A **Kinesis Data Streams interface VPC endpoint** routes this traffic privately, eliminating the cost — but you must also verify the **VPC endpoint policy** (not just IAM permissions) actually permits the traffic.

**Why the other choices are wrong**
- A: A vague investigative approach without a concrete fix for the already-identified root cause.
- B: Adding the endpoint is correct, but checking only IAM permissions is incomplete — the **VPC endpoint policy** must also allow the traffic.
- C: Amazon Detective is a **security investigation tool**, not a cost-optimization tool, and doesn't directly address the identified NAT cost driver.

> 💡 **Exam tip**: When private-subnet resources reach an **AWS service with an available interface VPC endpoint** (like Kinesis) through a NAT Gateway, add that **interface VPC endpoint** — and remember to verify the **VPC endpoint policy**, not just IAM permissions.

## QUESTION 116

**Question**: A retail company has an on-premises European data center plus two AWS Regions (eu-west-1, us-east-1). It needs on-premises traffic to route to a VPC in **either** Region, plus **direct VPC-to-VPC routing between the two Regions**, with **no single point of failure.** Two existing 1Gbps Direct Connect connections (to separate DX locations, DX-A and DX-B) exist. Each Region has a single Transit Gateway routing all its own VPCs.

**Choices**
- A. Create **private VIFs** from DX-A/DX-B to one Direct Connect Gateway, attach both regional TGWs to the DXGW, and peer the TGWs together.
- B. Create a transit VIF from DX-A to DXGW1 (attached to the eu-west-1 TGW), a separate transit VIF from DX-B to DXGW2 (attached to us-east-1 TGW), and **peer the two DXGWs together.**
- C. Create transit VIFs from both DX-A/DX-B to one DXGW, attach both TGWs, and **configure the DXGW to route traffic between the TGWs.**
- D. **Create transit VIFs from both DX-A and DX-B to one Direct Connect Gateway (redundant), attach both the eu-west-1 and us-east-1 TGWs to it, and peer the TGWs together for cross-Region routing.**

**Correct Answer: D**

**Explanation**
Connecting a Direct Connect Gateway to a **Transit Gateway** requires a **transit VIF** (not private VIF). Connecting **both** DX-A and DX-B to the same DXGW via transit VIFs provides redundancy, and attaching both regional TGWs lets on-premises reach either Region. However, **direct cross-Region VPC routing** requires **peering the TGWs** separately — DXGW attachment alone doesn't provide this.

**Why the other choices are wrong**
- A: **Private VIFs are for VGWs/single VPCs** — connecting to a Transit Gateway requires a transit VIF. Wrong VIF type.
- B: Splitting into two separate DXGWs is unnecessarily complex compared to D's clean shared-DXGW-with-redundant-connections design.
- C: Correctly attaches both TGWs to one DXGW, but **"configuring the DXGW to route between TGWs" doesn't actually work** — DXGW only handles on-premises-to-Region connectivity; cross-Region TGW-to-TGW routing specifically requires **TGW peering.**

> 💡 **Exam tip**: Connecting a Direct Connect Gateway to a **Transit Gateway** requires a **transit VIF**, not a private VIF. One DXGW can attach to multiple Regions' TGWs (on-premises → multiple Regions), but **direct cross-Region VPC routing** additionally requires **peering the TGWs** themselves.

## QUESTION 117

**Question**: The security team must approve all new IAM user creation. When a new IAM user is created, **all access must be automatically removed**, then the security team must be notified for approval. The account has a multi-Region CloudTrail trail. (Choose three.)

**Choices**
- A. **Create an EventBridge rule** with a pattern for detail-type = "AWS API Call via CloudTrail" and eventName = "CreateUser".
- C. Invoke a container running on ECS (Fargate) to remove access.
- D. **Invoke an AWS Step Functions state machine to remove access.**
- E. **Use Amazon SNS to notify the security team.**

**Correct Answer: A, D, E**

**Explanation**
The workflow: CloudTrail logs the `CreateUser` call → an **EventBridge rule** (A) detects the pattern → a **Step Functions state machine** (D) handles the multi-step access-removal process → **SNS** (E) notifies the security team for approval.

**Why the other choices are wrong**
- C: Invoking an ECS/Fargate container for a simple event-driven remediation task is far heavier infrastructure than needed compared to Step Functions.

> 💡 **Exam tip**: For a "detect CloudTrail event → remediate → notify" automation workflow, the standard combo is **EventBridge (event pattern matching) → Step Functions (multi-step remediation) → SNS (notification)** — don't reach for a full container for lightweight remediation.

## QUESTION 118

**Question**: A migration plan calls for a multi-account structure with centralized access management, keeping traffic on private networks, requiring MFA at login, and role-based group assignments. Separate accounts for development, staging, production, and shared network are needed. **Production and shared-network accounts must connect to all accounts**, while **development and staging accounts should only connect to each other.** (Choose three.)

**Choices**
- A. **Use AWS Control Tower to deploy a landing zone**, registering and inviting existing accounts into the resulting Organizations org.
- B. Enable Security Hub in every account, and collect CloudTrail findings to enforce MFA login.
- C. **Create a Transit Gateway and Transit Gateway VPC attachments in each account, with appropriate routing tables.**
- D. **Set up and enable AWS IAM Identity Center (SSO)**, creating appropriate permission sets requiring MFA.
- E. Enable Control Tower in every account to manage cross-account routing, and collect CloudTrail findings to enforce MFA login.
- F. Create IAM users/groups, configure MFA for all users, and use Amazon Cognito user/identity pools to manage cross-account access.

**Correct Answer: A, C, D**

**Explanation**
**Control Tower** deploys the multi-account landing zone (A), a **Transit Gateway with per-account route table segmentation** implements the selective connectivity pattern (production/shared-network connect to everyone; dev/staging connect only to each other) (C), and **IAM Identity Center** provides centralized, MFA-enforced, role-based access management (D).

**Why the other choices are wrong**
- B, E: **Security Hub aggregates security findings** — it doesn't manage cross-account access, and "using CloudTrail findings to enforce MFA" isn't how MFA enforcement actually works. Control Tower also doesn't manage cross-account **routing** (that's Transit Gateway's job).
- F: **Amazon Cognito is for end-user/customer-facing app authentication** — not suited for managing internal employee cross-account console access (IAM Identity Center is the right tool).

> 💡 **Exam tip**: Multi-account landing zone governance → **Control Tower.** Selective cross-account network connectivity (some fully connected, some isolated) → **Transit Gateway with per-account route table segmentation.** Centralized, MFA-based access management → **IAM Identity Center.** Cognito is for customers; Security Hub is a security dashboard.

## QUESTION 119

**Question**: A company runs apps in eu-west-1 with one account per environment (dev/test/prod). All environments run 24/7 using stateful EC2 and RDS for MySQL (500-800GB). Dev/test teams work business hours only; production runs 24/7. Resources are tagged by environment. Reduce cost with minimal operational effort.

**Choices**
- A. One EventBridge rule running once daily, invoking one Lambda function that decides start/stop based on tag, day of week, and time.
- B. **A daily evening EventBridge rule invoking a Lambda function that stops instances by tag, plus a second morning EventBridge rule invoking another Lambda function that starts instances by tag.**
- C. An evening rule stopping instances based on "delay," and a morning rule restoring instances from the last backup.
- D. An hourly rule that terminates or restores instances from backup based on tag, day, and time.

**Correct Answer: B**

**Explanation**
For dev/test resources only needed during business hours, the standard pattern is **evening-stop / morning-start**, implemented via **two separate EventBridge rules**, each invoking a simple tag-based Lambda function (production, tagged separately, is excluded from this schedule).

**Why the other choices are wrong**
- A: Combining start/stop decision logic (day/time conditions) into a single function is more complex than B's two simple, role-specific rules.
- C, D: "Restoring from backup" is a much slower, heavier operation than simply **starting** an already-stopped instance, and hourly scheduling is unnecessary for a twice-daily need.

> 💡 **Exam tip**: For cost savings on business-hours-only dev/test resources, use **separate evening-stop / morning-start EventBridge rules with simple tag-based Lambda functions** — avoid combining complex conditional logic into one function or using a heavy "restore from backup" approach.

## QUESTION 120

**Question**: A SaaS company deployed API Gateway REST API + Lambda integration across multiple Regions, all in the same production account. A tiered pricing model lets Premium customers make up to 3,000 API calls/second, identified by a unique API key. Multiple Premium customers across various Regions report **429 Too Many Requests** errors on several API methods during peak hours. Logs show **the Lambda function was not invoked.** What's the cause?

**Choices**
- A. The Lambda function reached its concurrency limit.
- B. Lambda's regional concurrency-limiting feature.
- C. **The API Gateway account-level calls-per-second limit was reached.**
- D. The API Gateway default per-method calls-per-second limit was reached.

**Correct Answer: C**

**Explanation**
The key clue is that Lambda **was never invoked** — a Lambda concurrency issue would still show invocation attempts in the logs. API Gateway has an account-level (per-Region) aggregate limit, **separate from any individual customer's usage plan limit.** Multiple Premium customers being affected simultaneously — each individually within their own 3,000/sec allocation — points to the account's aggregate traffic exceeding this broader ceiling.

**Why the other choices are wrong**
- A, B: A Lambda concurrency issue would still show invocation **attempts** in the logs — contradicting "Lambda was not invoked."
- D: A "default per-method limit" is a narrower tier; the symptom (multiple customers/methods/Regions affected simultaneously) better matches the broader **account-level** limit being exhausted.

> 💡 **Exam tip**: API Gateway throttling has **three layers: ① account-level (Region-wide aggregate) → ② stage-level → ③ usage-plan (per-API-key) level.** When multiple different customers get 429s simultaneously and **Lambda was never invoked**, suspect the **account-level limit**, not an individual customer's usage plan or Lambda's own concurrency.
