## QUESTION 341

**문제**: 한 회사가 AWS Lake Formation이 관리하는 Amazon S3 데이터 레이크를 보유하고 있다. 이 회사는 데이터 레이크의 데이터를 Amazon Aurora MySQL 데이터베이스에 저장된 운영 데이터와 결합해 Amazon QuickSight에서 시각화를 만들려고 한다. 회사는 마케팅 팀이 데이터베이스의 열 하위 집합에만 접근할 수 있도록 열 수준 권한을 적용하고자 한다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. Amazon EMR을 사용하여 데이터베이스에서 QuickSight SPICE 엔진으로 필요한 열만 직접 수집한다(열 제한 로직을 매번 별도 구현·유지해야 해 운영 부담이 크고, Lake Formation의 중앙 권한 관리 이점을 활용하지 못함).
- B. AWS Glue Studio로 데이터베이스에서 S3 데이터 레이크로 데이터를 수집하고, IAM 정책을 QuickSight 사용자에게 연결해 열 수준 접근 제어를 적용하며, QuickSight에서 S3를 데이터 원본으로 사용한다(IAM 정책은 S3 리소스 단위 접근 제어이며 파일 내부의 특정 열만 골라 제어하는 세밀한 권한 부여 기능은 제공하지 않음).
- C. AWS Glue Elastic Views로 S3에 데이터베이스의 구체화된 뷰를 생성하고, S3 버킷 정책으로 QuickSight 사용자의 열 수준 접근을 제어하며, QuickSight에서 S3를 데이터 원본으로 사용한다(S3 버킷 정책 역시 버킷/객체 단위 제어이며 열 단위 권한 부여 기능이 없음).
- D. **Lake Formation 블루프린트를 사용하여 데이터베이스에서 S3 데이터 레이크로 데이터를 수집하고, Lake Formation으로 QuickSight 사용자에 대한 열 수준 접근 제어를 적용하며, QuickSight에서 Amazon Athena를 데이터 원본으로 사용한다.**

**정답: D**

**해설**
**AWS Lake Formation**은 데이터 레이크에 대해 테이블/열 단위의 세밀한 접근 제어(데이터 필터, LF-Tags 등)를 중앙에서 정의하고 적용할 수 있는 관리형 서비스입니다. Lake Formation 블루프린트로 Aurora MySQL의 운영 데이터를 S3 데이터 레이크로 손쉽게 수집한 뒤, Lake Formation의 열 수준 권한을 QuickSight 사용자·그룹에 매핑하고 **Amazon Athena**를 QuickSight의 데이터 원본으로 사용하면, 마케팅 팀에게는 허용된 열만 노출하면서 별도의 커스텀 필터링 파이프라인 없이 운영 오버헤드를 최소화할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: EMR로 SPICE에 직접 수집하는 방식은 열 제한을 매번 파이프라인 코드로 구현해야 해 운영 부담이 크고, Lake Formation의 중앙 권한 관리를 활용하지 못합니다.
- B: IAM 정책은 S3 객체/버킷 단위 접근 제어 수단이며, 파일 내부의 특정 열만 골라 권한을 부여하는 세밀한 제어 기능이 없습니다.
- C: S3 버킷 정책도 버킷/객체 수준 제어이며 열 단위 권한 부여를 제공하지 않아 요구 사항을 충족하지 못합니다.

> 💡 **시험 꿀팁**: **데이터 레이크에서 열 수준(column-level) 접근 제어**가 필요하면 **Lake Formation + Athena(QuickSight 데이터 원본)** 조합이 표준 정답입니다.

## QUESTION 342

**문제**: 트랜잭션 처리 회사가 Auto Scaling 그룹에 속한 Amazon EC2 인스턴스에서 매주 스크립팅된 배치 작업을 실행한다. 트랜잭션 수는 실행마다 다르지만, 각 실행에서 기록되는 기준 CPU 사용률은 항상 60% 이상이다. 회사는 작업이 실행되기 30분 전에 용량을 미리 프로비저닝해야 한다. 현재는 엔지니어가 Auto Scaling 그룹 파라미터를 수동으로 수정해 이 작업을 처리하며, 회사에는 그룹에 필요한 용량 추세를 분석할 인력이 없다. 회사는 Auto Scaling 그룹의 원하는 용량을 자동으로 조정하는 방법이 필요하다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. Auto Scaling 그룹에 대한 동적 조정 정책을 생성하고, CPU 사용률 지표를 기준으로 확장하도록 구성하며 목표값을 60%로 설정한다(실제 부하가 상승한 이후에만 반응하는 방식이라 작업 실행 30분 전에 미리 용량을 준비하는 요구를 충족하지 못함).
- B. Auto Scaling 그룹에 대한 예약 조정 정책을 생성하고, 원하는/최소/최대 용량을 설정한 뒤 매주 반복되도록 하고 작업 실행 30분 전을 시작 시간으로 설정한다(고정된 용량 수치를 사람이 직접 산정해야 하므로, 용량 추세를 분석할 인력이 없는 회사의 상황에서는 지속적인 수동 튜닝 부담이 남음).
- C. **Auto Scaling 그룹에 대한 예측 조정 정책을 생성하고, 예측을 기반으로 확장하도록 구성하며 스케일링 지표를 CPU 사용률로, 목표값을 60%로 설정하고, 작업 실행 30분 전에 인스턴스를 사전 실행하도록 설정한다.**
- D. Auto Scaling 그룹의 CPU 사용률이 60%에 도달하면 Lambda 함수를 호출하는 EventBridge 이벤트를 생성하고, Lambda가 원하는 용량과 최대 용량을 20% 늘리도록 구성한다(CPU가 이미 60%에 도달한 뒤에야 반응하는 사후 대응 방식이라 사전 프로비저닝 요구를 충족하지 못함).

**정답: C**

**해설**
**Auto Scaling 예측 조정(predictive scaling)**은 CloudWatch에 쌓인 과거 사용률 데이터를 머신러닝으로 학습해 향후 트래픽을 예측하고, 실제 부하가 발생하기 전에 미리 용량을 조정하는 정책입니다. 스케일링 지표를 CPU 사용률로, 목표값을 60%로 설정하면 매주 관측되는 기준 사용률과 일치시킬 수 있고, 작업 실행 30분 전에 인스턴스를 사전 실행하도록 설정하면 회사가 직접 용량 추세를 분석하지 않아도 자동으로 배치 작업 시작 전에 충분한 용량이 준비됩니다.

**왜 다른 보기는 오답인가**
- A: 동적 조정은 실제 CPU 사용률 변화에 반응하는 방식이라 트래픽이 오르기 전에 미리 용량을 준비하는 방법을 제공하지 않습니다.
- B: 예약 조정은 사람이 정한 고정 스케줄과 용량 수치로만 동작해, 회사에 용량 추세를 분석할 리소스가 없는 상황에서는 값을 정확히 산정하고 유지보수하는 부담이 그대로 남습니다.
- D: EventBridge + Lambda 조합은 CPU가 60%에 이미 도달한 이후에 반응하는 사후 대응 구조라 사전 프로비저닝 요구에 맞지 않습니다.

> 💡 **시험 꿀팁**: **"미리 예측해서 사전에 용량을 프로비저닝"**해야 하고 **직접 추세 분석할 인력도 없다**는 조건이 나오면 **Auto Scaling 예측 조정(Predictive Scaling)**이 표준 정답입니다.

## QUESTION 343

**문제**: 한 솔루션 설계자가 회사의 재해 복구(DR) 아키텍처를 설계하고 있다. 회사는 예약된 백업이 설정된 프라이빗 서브넷의 EC2 인스턴스에서 MySQL 데이터베이스를 운영 중이며, DR 설계는 여러 AWS 리전을 포함해야 한다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. MySQL 데이터베이스를 여러 EC2 인스턴스로 마이그레이션하고, DR 리전에 대기 EC2 인스턴스를 구성한 뒤 복제를 켠다(복제 설정, 장애 감지, 수동 페일오버까지 직접 구축·운영해야 해 오버헤드가 큼).
- B. MySQL 데이터베이스를 Amazon RDS로 마이그레이션하고 다중 AZ 배포를 사용하며, 다른 가용 영역에서 기본 DB 인스턴스에 대한 읽기 복제본을 켠다(다중 AZ와 읽기 복제본은 모두 동일 리전 내 가용성 확보 수단이며, 리전 단위 DR 요구를 충족하지 못함).
- C. **MySQL 데이터베이스를 Amazon Aurora 글로벌 데이터베이스로 마이그레이션하고, 기본 리전에서 기본 DB 클러스터를, DR 리전에서 보조 DB 클러스터를 호스팅한다.**
- D. S3 교차 리전 복제(CRR)로 구성된 S3 버킷에 MySQL 데이터베이스의 예약된 백업을 저장하고, 데이터 백업을 사용해 DR 리전에서 데이터베이스를 복원한다(백업 기반 복원은 RPO/RTO가 크고, 장애 시마다 수동 복원 절차가 필요해 운영 오버헤드가 큼).

**정답: C**

**해설**
**Amazon Aurora 글로벌 데이터베이스**로 마이그레이션하면 관리형 서비스가 리전 간 복제와 자동 장애 조치를 대신 처리하므로 대기 인스턴스를 수동으로 구성할 필요가 없습니다. 기본 DB 클러스터는 기본 리전에서, 보조 DB 클러스터는 DR 리전에서 호스팅되며, 1초 미만의 복제 지연으로 데이터를 여러 리전에서 항상 최신 상태로 유지할 수 있어 대규모 수동 개입 없이 DR 요구 사항을 충족합니다.

**왜 다른 보기는 오답인가**
- A: 자체 관리형 EC2 복제 구성은 복제 설정, 모니터링, 페일오버까지 모두 직접 운영해야 해 오버헤드가 매우 큽니다.
- B: 다중 AZ와 동일 리전 읽기 복제본은 가용 영역 장애에는 대응하지만, 리전 전체 장애에 대비하는 DR 요구는 충족하지 못합니다.
- D: 예약 백업의 교차 리전 복제와 수동 복원 방식은 복구까지 시간이 오래 걸리고 절차가 반복적으로 필요해 운영 오버헤드가 큽니다.

> 💡 **시험 꿀팁**: **여러 리전에 걸친 관계형 DB 재해 복구**에는 **Aurora 글로벌 데이터베이스**가 표준 정답입니다(다중 AZ는 리전 내 가용성일 뿐, 리전 간 DR과는 다릅니다).

## QUESTION 344

**문제**: 한 회사가 Amazon SQS를 사용해 메시지를 구문 분석하는 Java 애플리케이션을 운영 중이다. 이 애플리케이션은 크기가 256KB보다 큰 메시지를 처리할 수 없는데, 회사는 애플리케이션이 최대 50MB 크기의 메시지까지 처리할 수 있는 기능을 제공하려고 한다. 코드를 가장 적게 변경하면서 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. **Java용 Amazon SQS 확장 클라이언트 라이브러리를 사용하여 256KB보다 큰 메시지를 Amazon S3에서 호스팅한다.**
- B. Amazon SQS 대신 Amazon EventBridge를 사용해 애플리케이션에서 큰 메시지를 게시한다(메시지 처리 로직 자체를 EventBridge 기반으로 전면 재작성해야 해 코드 변경 최소화 요구에 위배).
- C. 256KB보다 큰 메시지를 처리하도록 Amazon SQS의 제한을 변경한다(SQS의 최대 메시지 크기 256KB는 서비스의 하드 리밋으로 사용자가 임의로 변경할 수 없음).
- D. Amazon EFS에 256KB보다 큰 메시지를 저장하고, 메시지에서 이 위치를 참조하도록 SQS를 구성한다(SQS에 EFS 참조를 자동으로 연동하는 표준 기능이 없어 참조 생성·조회 로직을 직접 구현해야 함).

**정답: A**

**해설**
**Amazon SQS 확장 클라이언트 라이브러리(Extended Client Library)**는 256KB를 초과하는 페이로드를 자동으로 Amazon S3에 저장하고, SQS 메시지에는 해당 객체에 대한 포인터만 담아 전송하는 SDK 확장 기능입니다. 애플리케이션 코드에서는 라이브러리를 통해 평소처럼 메시지를 보내고 받으면 되므로, 최대 2GB(문제의 요구인 50MB 포함)까지 처리 가능한 대용량 메시지 기능을 최소한의 코드 변경으로 제공할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: EventBridge로 전환하려면 메시지 발행/구독 로직을 새 서비스에 맞게 다시 작성해야 해 코드 변경이 커집니다.
- C: SQS의 최대 메시지 크기 256KB는 서비스 자체의 제한이며 설정으로 늘릴 수 있는 값이 아닙니다.
- D: EFS 기반 참조 방식은 표준 통합이 없어 저장·조회·삭제 로직을 모두 직접 구현해야 하므로 확장 클라이언트 라이브러리보다 코드 변경이 큽니다.

> 💡 **시험 꿀팁**: **SQS 256KB 제한을 넘는 대용량 메시지**를 다뤄야 한다면 **SQS 확장 클라이언트 라이브러리(S3 오프로드)**가 표준 정답입니다.

## QUESTION 345

## QUESTION 346

**문제**: 한 회사의 데이터 센터에 노후화된 NAS(Network-Attached Storage) 어레이가 있으며, 이 어레이는 클라이언트 워크스테이션에 SMB 공유와 NFS 공유를 제공한다. 회사는 새 NAS 어레이 구매도, 기존 어레이의 지원 계약 갱신 비용도 원하지 않는다. 일부 데이터는 자주 액세스되지만 대부분은 비활성 상태다. 솔루션 설계자는 데이터를 Amazon S3로 마이그레이션하고 S3 수명 주기 정책을 사용하면서 클라이언트 워크스테이션에는 동일한 사용 경험을 유지하는 솔루션을 구현해야 하며, AWS Storage Gateway를 그 일부로 식별했다. 이러한 요구 사항을 충족하려면 어떤 유형의 스토리지 게이트웨이를 프로비저닝해야 하는가?

**보기**
- A. 볼륨 게이트웨이(iSCSI 기반 블록 스토리지를 제공하는 게이트웨이로, SMB/NFS 파일 공유 대체 용도가 아님).

- D. **Amazon S3 파일 게이트웨이**

**정답: D**

**해설**
**Amazon S3 파일 게이트웨이**는 온프레미스 클라이언트에게 기존과 동일한 SMB 및 NFS 인터페이스를 제공하면서, 실제 데이터는 S3 버킷에 객체로 저장하는 하이브리드 스토리지입니다. 자주 액세스하는 파일은 로컬 캐시로 빠르게 제공하고, S3 수명 주기 정책을 적용해 비활성 데이터를 자동으로 더 저렴한 스토리지 클래스로 전환할 수 있어, 새 NAS 구매나 지원 계약 갱신 없이 클라이언트의 사용 경험을 그대로 유지할 수 있습니다.

**왜 다른 보기는 오답인가**

- B: 테이프 게이트웨이는 백업 아카이빙을 위한 가상 테이프 라이브러리로 파일 공유 요구와 무관합니다.
- C: FSx 파일 게이트웨이는 FSx for Windows File Server에 대한 온프레미스 캐시 접근을 제공하는 것으로, S3 수명 주기 정책 기반 계층화라는 이 문제의 핵심 요구와는 맞지 않습니다.

> 💡 **시험 꿀팁**: **기존 SMB/NFS 파일 공유를 유지하며 S3 수명 주기 정책으로 비용을 절감**하려면 **S3 파일 게이트웨이**가 표준 정답입니다.

> 💡 **시험 꿀팁**: **RDS 고가용성 + 보고/분석 쿼리 분리**가 함께 요구되면 **다중 AZ 배포 + 읽기 전용 복제본** 조합이 표준 정답입니다.

**문제**: 한 회사가 단일 가용 영역의 EC2 인스턴스에서 3계층 웹 애플리케이션을 호스팅한다. 웹 애플리케이션은 EC2에서 실행되는 자체 관리형 MySQL 데이터베이스를 사용해 1TB 프로비저닝된 IOPS SSD(io2) EBS 볼륨에 데이터를 저장하며, 피크 트래픽에서 읽기·쓰기 합산 1,000 IOPS의 트래픽이 발생할 것으로 예상한다. 회사는 현재의 두 배 IOPS 용량을 유지하면서 중단을 최소화하고 성능을 안정화하며 비용을 절감하고자 하고, 데이터베이스 계층을 고가용성·내결함성을 갖춘 완전관리형 솔루션으로 옮기려 한다. 이러한 요구 사항을 가장 비용 효율적으로 충족하는 솔루션은 무엇인가?

**보기**
- A. io2 Block Express EBS 볼륨을 사용하는 MySQL DB 인스턴스용 Amazon RDS의 다중 AZ 배포를 사용한다(io2 Block Express는 최대 256,000 IOPS까지 지원하는 고성능 옵션이지만, 이 워크로드가 필요로 하는 2,000 IOPS 수준에는 과도한 사양이라 비용 절감 요구에 부합하지 않음).
- B. **범용 SSD(gp2) EBS 볼륨을 사용하는 MySQL DB 인스턴스용 Amazon RDS의 다중 AZ 배포를 사용한다.**
- C. Amazon S3 Intelligent-Tiering 액세스 계층을 사용한다(S3는 객체 스토리지 서비스로, MySQL 트랜잭션 데이터베이스가 필요로 하는 블록 스토리지·SQL 엔진 요구를 충족하지 못함).
- D. 두 개의 대형 EC2 인스턴스를 사용해 활성-수동 모드로 데이터베이스를 호스팅한다(자체 관리형 방식이라 페일오버·백업·패치 등을 직접 운영해야 해 완전관리형 요구에 부합하지 않음).

**정답: B**

**해설**
**gp2 볼륨**은 볼륨 크기에 비례해 기준 IOPS가 결정되며, 1TB 규모라면 약 3,000 IOPS의 기준 성능을 제공해 요구되는 2배 용량(2,000 IOPS)을 충분히 만족합니다. io2보다 GB당 비용이 낮아 성능 요구를 충족하면서도 비용을 절감할 수 있고, **Amazon RDS 다중 AZ 배포**로 전환하면 동기 복제 대기 인스턴스와 자동 페일오버를 통해 완전관리형으로 고가용성·내결함성을 확보할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: io2 Block Express는 훨씬 높은 IOPS를 제공하지만 이 워크로드에는 과도한 사양으로, gp2 대비 비용이 높아 비용 절감 요구에 맞지 않습니다.
- C: S3는 객체 스토리지로 MySQL 같은 관계형 데이터베이스 엔진을 구동할 수 없습니다.
- D: EC2 기반 활성-수동 구성은 페일오버·패치·백업을 모두 직접 관리해야 하는 자체 관리형 방식으로 완전관리형 요구를 충족하지 못합니다.

> 💡 **시험 꿀팁**: **필요 IOPS가 크지 않은 예측 가능한 워크로드**라면 고가의 io1/io2 대신 **gp2/gp3 + RDS 다중 AZ**로 비용을 절감하는 것이 표준 정답 패턴입니다.

**문제**: 한 회사가 AWS에서 Amazon API Gateway, AWS Lambda, Amazon RDS for PostgreSQL을 사용하는 서버리스 애플리케이션을 호스팅한다. 회사는 트래픽이 급증하거나 예측할 수 없는 시간대에 데이터베이스 연결 시간 초과로 인한 애플리케이션 오류 증가를 확인했다. 회사는 최소한의 코드 변경으로 애플리케이션 오류를 줄이는 솔루션이 필요하다. 솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. Lambda 동시성 비율을 줄인다(동시 실행 수를 줄이면 처리량 자체가 감소해 오히려 요청 처리 지연·오류가 늘어날 수 있으며 연결 초과 문제의 근본 원인을 해결하지 못함).

- C. 더 많은 연결을 허용하도록 RDS DB 인스턴스 클래스 크기를 조정한다(비용이 상승하고 최대 연결 수를 어느 정도 늘릴 수는 있지만, 순간적인 연결 폭증 자체를 관리하는 근본적인 해결책은 아님).

**정답: B**

**해설**
**Amazon RDS 프록시**는 애플리케이션과 데이터베이스 사이에서 커넥션 풀을 관리하는 완전관리형 중개 계층으로, Lambda 함수가 급증하는 트래픽 속에서 각각 새 연결을 열지 않고 풀에 있는 기존 연결을 재사용하도록 해줍니다. 이를 통해 데이터베이스가 감당할 수 없는 수의 연결이 한꺼번에 몰리는 것을 방지하고, 애플리케이션 코드에서는 연결 엔드포인트만 RDS 프록시 엔드포인트로 바꾸면 되므로 최소한의 코드 변경으로 연결 시간 초과 오류를 줄일 수 있습니다.

- C: 인스턴스 클래스를 키우면 비용이 늘어나고 연결 상한이 다소 올라갈 뿐, 순간적인 연결 폭증을 근본적으로 제어하지 못합니다.
- D: DynamoDB로의 마이그레이션은 데이터 모델과 쿼리 로직을 전면 재작성해야 해 코드 변경을 최소화해야 한다는 요구에 맞지 않습니다.

> 💡 **시험 꿀팁**: **서버리스(Lambda) + RDS 조합에서 연결 폭증으로 인한 오류**가 발생하면 **RDS 프록시(커넥션 풀링)**가 표준 정답입니다.

## QUESTION 357

**문제**: 한 소셜 미디어 회사가 Application Load Balancer 뒤의 EC2 인스턴스에서 애플리케이션을 실행하며, ALB는 Amazon CloudFront 배포의 오리진이다. 이 애플리케이션은 S3 버킷에 저장된 10억 개 이상의 이미지를 초당 수천 건씩 처리한다. 회사는 이미지 크기를 동적으로 조정하고 고객에게 적절한 형식을 제공하려고 한다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. EC2 인스턴스에 외부 이미지 관리 라이브러리를 설치하고 이를 사용해 이미지를 처리한다(오리진 서버에서 직접 처리해 오리진 부하와 지연이 늘어나고, 트래픽 증가에 따른 확장 관리를 별도로 해야 함).
- B. CloudFront 오리진 요청 정책을 생성하고, 이를 사용해 자동으로 이미지 크기를 조정하고 User-Agent HTTP 헤더에 따라 적절한 형식을 제공한다(오리진 요청 정책은 오리진으로 전달할 헤더/쿼리스트링 등을 제어하는 정책일 뿐, 이미지를 실제로 변환하는 컴퓨팅 기능은 없음).
- C. **외부 이미지 관리 라이브러리와 함께 Lambda@Edge 함수를 사용하고, 이 함수를 이미지를 제공하는 CloudFront 동작(behavior)에 연결한다.**
- D. CloudFront 응답 헤더 정책을 생성하고, 이를 사용해 자동으로 이미지 크기를 조정하고 User-Agent HTTP 헤더에 따라 적절한 형식을 제공한다(응답 헤더 정책은 응답에 HTTP 헤더를 추가·제거하는 기능일 뿐 이미지 변환 로직을 실행하지 못함).

**정답: C**

**해설**
**Lambda@Edge**는 CloudFront 엣지 로케이션에서 Lambda 함수를 실행해 요청·응답을 가로채 수정할 수 있는 서비스입니다. 이미지를 제공하는 CloudFront 동작에 외부 이미지 처리 라이브러리를 포함한 Lambda@Edge 함수를 연결하면, 요청의 User-Agent 헤더를 기준으로 사용자에게 맞는 크기·형식의 이미지를 엣지에서 즉시 생성해 응답할 수 있습니다. 이를 통해 오리진(EC2/S3)의 부하와 지연을 줄이면서 서버 인프라를 직접 확장·운영할 필요 없이 이미지 처리를 자동화할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: EC2에서 직접 처리하면 오리진 부하가 커지고, 트래픽 증가에 맞춰 컴퓨팅 자원을 계속 관리해야 해 운영 오버헤드가 큽니다.
- B: 오리진 요청 정책은 오리진으로 보낼 요청 값을 제어하는 정책일 뿐이며 이미지 변환을 수행하는 컴퓨팅 기능이 없습니다.
- D: 응답 헤더 정책도 헤더 추가/제거 기능일 뿐, 이미지 리사이징 같은 실질적인 처리 로직을 실행할 수 없습니다.

> 💡 **시험 꿀팁**: **CloudFront를 거치는 요청/응답에서 동적으로 콘텐츠(이미지 등)를 가공**해야 한다면 **Lambda@Edge**가 표준 정답입니다.

## QUESTION 358

**문제**: 한 병원이 환자 기록을 Amazon S3 버킷에 저장해야 한다. 병원의 컴플라이언스 팀은 모든 보호 건강 정보(PHI)가 전송 중 및 저장 시 모두 암호화되도록 해야 하며, 규정 준수 팀이 미사용 데이터에 대한 암호화 키를 직접 관리해야 한다. 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. AWS Certificate Manager(ACM)에서 퍼블릭 SSL/TLS 인증서를 생성해 S3와 연결하고, AWS KMS 키(SSE-KMS)로 각 S3 버킷의 기본 암호화를 구성한 뒤 규정 준수 팀에 KMS 키 관리를 맡긴다(S3는 ACM 인증서를 버킷에 직접 연결하는 기능을 제공하지 않으며, 전송 중 암호화를 보장하는 표준 방법이 아님).
- B. S3 버킷 정책에서 `aws:SecureTransport` 조건으로 HTTPS(TLS) 연결만 허용하고, S3 관리형 키(SSE-S3)로 각 버킷의 기본 암호화를 구성한 뒤 규정 준수 팀에 SSE-S3 키 관리를 맡긴다(SSE-S3는 AWS가 키를 전적으로 관리해 고객이 키에 대한 제어 권한을 가질 수 없어, 규정 준수 팀이 직접 키를 관리해야 한다는 요구를 충족하지 못함).
- C. **S3 버킷 정책에서 `aws:SecureTransport` 조건으로 HTTPS(TLS) 연결만 허용하고, AWS KMS 키(SSE-KMS)로 각 버킷의 기본 암호화를 구성한 뒤 규정 준수 팀에 KMS 키 관리를 맡긴다.**
- D. S3 버킷 정책에서 `aws:SecureTransport` 조건으로 HTTPS(TLS) 연결만 허용하고, Amazon Macie로 S3에 저장된 민감한 데이터를 보호하며 규정 준수 팀에 Macie 관리를 맡긴다(Macie는 민감 데이터 탐지·분류 서비스로 암호화 키 관리 기능이 없어 요구 사항과 무관).

**정답: C**

**해설**
S3 버킷 정책에 **`aws:SecureTransport`** 조건을 추가하면 HTTPS(TLS)를 사용하지 않는 연결 요청이 모두 거부되어 전송 중 암호화가 강제됩니다. 저장 시 암호화는 **SSE-KMS**로 구성하면 고객 관리형 KMS 키를 사용하게 되어, 규정 준수 팀이 키 정책·교체·감사 등 암호화 키에 대한 실질적인 제어 권한을 가질 수 있습니다. 이 조합으로 전송·저장 양쪽의 암호화와 키에 대한 조직 내부 통제라는 두 요구를 동시에 충족합니다.

**왜 다른 보기는 오답인가**
- A: ACM 인증서를 S3 버킷에 직접 연결하는 기능은 존재하지 않으며, 전송 중 암호화를 강제하는 표준 방법도 아닙니다.
- B: SSE-S3는 AWS가 암호화 키를 전적으로 소유·관리해 고객(규정 준수 팀)이 키에 대한 제어권을 가질 수 없습니다.
- D: Macie는 민감 데이터 탐지·분류에 특화된 서비스로 암호화 키 관리 기능을 제공하지 않습니다.

> 💡 **시험 꿀팁**: **전송 중 암호화 강제 + 저장 시 암호화 키를 고객(회사)이 직접 관리**해야 한다면 **`aws:SecureTransport` 버킷 정책 조건 + SSE-KMS(고객 관리형 키)** 조합이 표준 정답입니다.

## QUESTION 359

**문제**: 한 회사가 동일한 VPC 내에서 두 개의 REST API로 구성된 프라이빗 Amazon API Gateway를 운영한다. BuyStock RESTful 웹 서비스는 주식을 구매하기 전에 CheckFunds RESTful 웹 서비스를 호출해 충분한 자금이 있는지 확인한다. 회사는 VPC 흐름 로그를 통해 BuyStock 서비스가 VPC 내부가 아니라 인터넷을 경유해 CheckFunds 서비스를 호출하고 있음을 확인했다. 솔루션 설계자는 API들이 VPC를 통해 통신하도록 만들어야 한다. 코드를 가장 적게 변경하여 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. 인증을 위해 HTTP 헤더에 X-API-Key 헤더를 추가한다(API 키는 인증·사용량 제한을 위한 것으로, 트래픽이 인터넷을 거치는 네트워크 경로 자체를 바꾸지 못함).
- B. **인터페이스 엔드포인트를 사용한다.**
- C. 게이트웨이 엔드포인트를 사용한다(게이트웨이 엔드포인트는 Amazon S3와 DynamoDB 전용이며 API Gateway에 대한 프라이빗 연결을 제공하지 않음).
- D. 두 REST API 사이에 Amazon SQS 대기열을 추가한다(동기식 API 호출 구조를 비동기 메시징 아키텍처로 전면 재설계해야 해 코드를 가장 적게 변경해야 한다는 요구에 위배).

**정답: B**

**해설**
**인터페이스 엔드포인트(PrivateLink 기반 VPC 엔드포인트)**는 고객의 VPC 안에 탄력적 네트워크 인터페이스(ENI)를 생성해 API Gateway 프라이빗 API에 대한 진입점을 제공합니다. BuyStock 서비스가 CheckFunds 서비스의 인터페이스 엔드포인트 DNS 이름을 통해 호출하도록 구성하면, 트래픽이 인터넷을 거치지 않고 VPC 내부 경로로만 흐르게 되며 API 코드 자체는 거의 바뀌지 않습니다.

**왜 다른 보기는 오답인가**
- A: X-API-Key는 인증 및 사용량 관리를 위한 헤더로, 요청이 인터넷을 경유하는지 여부와는 무관합니다.
- C: 게이트웨이 엔드포인트는 S3와 DynamoDB 전용 기능이며 API Gateway에는 적용할 수 없습니다.
- D: SQS를 추가해 비동기 아키텍처로 바꾸는 것은 호출 방식 자체를 재설계하는 큰 변경이라 "최소 코드 변경" 요구에 부합하지 않습니다.

> 💡 **시험 꿀팁**: **프라이빗 API Gateway 간 통신을 인터넷이 아닌 VPC 내부로 유지**하고 싶다면 **인터페이스 VPC 엔드포인트(PrivateLink)**가 표준 정답입니다.

## QUESTION 360

**문제**: 한 회사가 AWS에서 멀티플레이어 게임 애플리케이션을 운영한다. 이 회사는 데이터를 밀리초 미만의 지연 시간으로 읽으면서도, 과거 데이터에 대한 일회성 쿼리를 실행할 수 있기를 원한다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. 자주 액세스되는 데이터에는 Amazon RDS를 사용하고, 주기적인 커스텀 스크립트를 실행해 데이터를 Amazon S3 버킷으로 내보낸다(RDS는 디스크 기반 관계형 DB로 밀리초 미만 지연을 보장하지 않고, 커스텀 내보내기 스크립트를 직접 개발·유지해야 해 운영 부담이 큼).
- B. 데이터를 Amazon S3 버킷에 직접 저장하고, S3 수명 주기 정책으로 오래된 데이터를 S3 Glacier Deep Archive로 이동하며, Amazon Athena로 S3 데이터에 대한 일회성 쿼리를 실행한다(S3는 객체 스토리지 특성상 밀리초 미만의 응답을 보장하는 저장소가 아니라 실시간 읽기 요구에 부적합).
- C. **자주 액세스되는 데이터에는 DynamoDB Accelerator(DAX)를 갖춘 Amazon DynamoDB를 사용하고, DynamoDB 테이블 내보내기 기능으로 데이터를 S3 버킷으로 내보낸 뒤 Amazon Athena로 S3 데이터에 대한 일회성 쿼리를 실행한다.**
- D. 자주 액세스되는 데이터에는 Amazon DynamoDB를 사용하고, Amazon Kinesis Data Streams로의 스트리밍을 켠 뒤 Kinesis Data Firehose로 스트림 데이터를 읽어 S3 버킷에 저장한다(스트리밍 파이프라인을 직접 구성·운영해야 해, 완전관리형 일괄 내보내기 기능을 활용하는 C보다 운영 오버헤드가 큼).

**정답: C**

**해설**
**Amazon DynamoDB**는 기본적으로 한 자릿수 밀리초의 응답 시간을 제공하며, 여기에 인메모리 캐시인 **DAX**를 추가하면 자주 조회되는 데이터에 대해 밀리초 미만 수준까지 지연을 더 낮출 수 있습니다. 과거 데이터에 대한 일회성 분석은 **DynamoDB 테이블 내보내기(완전관리형, 운영 부하 없이 S3로 내보내기)** 기능으로 데이터를 S3에 저장한 뒤 **Amazon Athena**로 서버 프로비저닝 없이 SQL 쿼리를 실행하면 되므로, 실시간 저지연 접근과 과거 데이터 분석이라는 두 요구를 최소한의 운영 오버헤드로 동시에 충족합니다.

**왜 다른 보기는 오답인가**
- A: RDS는 밀리초 미만 지연을 보장하는 저장소가 아니며, 커스텀 내보내기 스크립트를 직접 만들고 유지해야 해 운영 부담이 큽니다.
- B: S3에 데이터를 직접 저장하는 방식은 객체 스토리지 특성상 밀리초 미만의 실시간 읽기 요구를 충족하지 못합니다.
- D: Kinesis Data Streams와 Firehose로 별도 스트리밍 파이프라인을 구성하는 것은, DynamoDB의 완전관리형 테이블 내보내기 기능을 사용하는 것보다 구성 요소가 많아 운영 오버헤드가 더 큽니다.

> 💡 **시험 꿀팁**: **밀리초 미만 지연의 실시간 조회 + 과거 데이터의 일회성 분석**을 함께 요구하면 **DynamoDB(+ DAX) + 테이블 내보내기 + Athena** 조합이 표준 정답입니다.
