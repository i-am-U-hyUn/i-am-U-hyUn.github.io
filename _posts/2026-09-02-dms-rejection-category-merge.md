## 들어가며

앞서 만든 DMS 반려사유 분류 대시보드를 처음으로 리뷰하는 자리를 가졌다. 결과를 공유하고 피드백을 받는 자리였는데, 그중 1차 대분류 카테고리 체계를 하나 정리하기로 한 부분과 그걸 실제 노트북 두 개에 반영한 과정을 기록해둔다.

> 이 글에는 실제 계약 내용, 회사명, 금액, 참석자 정보 등 사내 정보는 담지 않았다. 카탈로그·스키마 식별자도 제외했다.

## 리뷰 결과

분석 대상은 Review와 QA 두 버킷으로 나눠서 봤다. 주요 반려 사유는 프로세스 미준수(DMS 단계 오류, 합의 결재자 승인 누락)와 자료 누락이 가장 큰 비중을 차지했다.

---

## 카테고리 병합 결정

기존에 정의해둔 1차 대분류 7개 중 아래 두 항목이 대상이었다.

| 1차 대분류 | 설명 |
|---|---|
| DMS 정보 오기재 | 금액, 기간, 수량 등 잘못 입력 |
| 계약서/견적서와 DMS 정보 불일치 | 계약서/견적서/인보이스 상 정보와 DMS 입력값이 다름 |

리뷰 중에 이 두 카테고리를 하나로 합치기로 했다. 오기재는 원인이고 불일치는 결과라서, 사실상 같은 사건을 시점만 다르게 표현하고 있었기 때문이다. DMS에 정보를 잘못 입력(오기재)했기 때문에 결과적으로 계약서·견적서와 내용이 달라지는(불일치) 것이니, 하나의 반려 사유를 원인 관점과 결과 관점으로 나눠 두 카테고리에 걸쳐 놓은 셈이었다. 이 병합으로 1차 대분류는 7개에서 6개로 줄었다.

---

## 반영: 노트북이 두 개라 고칠 방식도 달랐다

분류 파이프라인은 노트북 두 개, 테이블 두 개로 나뉘어 있다.

| 테이블 | 역할 |
|---|---|
| `rejection_classified` | 1차 일괄 분류 결과의 원본 스냅샷 |
| `rejection_classified_live` | 매일 갱신되는 스케줄링 대상 테이블 |

그런데 이 두 테이블을 만드는 노트북 두 개가 카테고리 이름을 처리하는 방식이 서로 달라서, 같은 병합이라도 고칠 위치가 달랐다.

### 대시보드용 노트북 (`rejection_classified.ipynb`)

이 노트북은 이름을 2단계로 처리한다.

1. 프롬프트 셀에서 Gemini에게 짧은 이름("정보 오기재", "정보 불일치")으로 분류시키고
2. 저장 직전 셀에서 짧은 이름을 대시보드에 노출할 긴 이름("DMS 정보 오기재", "계약서/견적서와 DMS 정보 불일치")으로 매핑

그래서 고칠 곳이 세 군데였다.

**① 프롬프트의 대분류 목록 (7개 → 6개)**, 그리고 소분류 예시에서 `### 정보 오기재`와 `### 정보 불일치` 두 블록을 `### 정보 오기재/불일치` 하나로 병합.

**② 같은 셀의 `VALID_PRIMARY` 검증 목록**

```python
# 변경 전
VALID_PRIMARY = ["자료 누락", "정보 미기재", "정보 오기재", "정보 불일치", "프로세스 미준수", "계약 조건 협의", "기타"]

# 변경 후
VALID_PRIMARY = ["자료 누락", "정보 미기재", "정보 오기재/불일치", "프로세스 미준수", "계약 조건 협의", "기타"]
```

**③ 짧은 이름 → 긴 이름으로 바꾸는 `rename_primary` 함수** — 여기가 가장 중요했다. 이 함수가 "오기재"와 "불일치"를 각각 다른 긴 이름으로 매핑하고 있었기 때문에, 이 부분을 하나로 합치지 않으면 프롬프트와 `VALID_PRIMARY`를 고쳐도 저장 단계에서 다시 둘로 갈라진다.

```python
# 변경 전
elif val == "정보 오기재":
    return "DMS 정보 오기재"
elif val == "정보 불일치":
    return "계약서/견적서와 DMS 정보 불일치"

# 변경 후
elif val == "정보 오기재/불일치":
    return "DMS 정보 오기재/불일치"
```

### 스케줄링 노트북 (`rejection_classified_live (1).ipynb`)

이 노트북은 애초에 짧은 이름/긴 이름 구분 없이, 프롬프트가 처음부터 긴 이름을 그대로 쓰도록 짜여 있었다. 그래서 별도의 rename 단계 없이, 고칠 곳은 프롬프트의 대분류 목록과 `VALID_PRIMARY` 두 군데뿐이었다.

```python
# 변경 전
VALID_PRIMARY = ["자료 누락", "DMS 정보 미기재(공란)", "DMS 정보 오기재", "계약서/견적서와 DMS 정보 불일치", "프로세스 미준수", "계약 조건 협의", "기타"]

# 변경 후
VALID_PRIMARY = ["자료 누락", "DMS 정보 미기재(공란)", "DMS 정보 오기재/불일치", "프로세스 미준수", "계약 조건 협의", "기타"]
```

같은 카테고리 체계를 다루는 노트북인데도 이름 처리 방식이 서로 달랐던 셈이라, 코드를 고칠 때 "여기도 고쳐야 하나?"를 노트북별로 따로 확인해야 했다.

## 이미 쌓인 과거 데이터는 어떻게 했나

두 노트북 모두 코드 수정 자체는 끝냈다. 문제는 이 수정이 앞으로 새로 분류될 건에만 적용된다는 점이었다 — 이미 두 테이블에 쌓여 있는 과거 분류 결과는 코드를 고쳐도 그대로 남는다. 그렇다고 노트북을 처음부터 다시 돌리면 이미 분류가 끝난 건들까지 전부 Gemini 호출을 다시 하게 되어 비용과 시간이 크게 든다. 그래서 노트북 재실행 대신, 저장된 값 자체를 SQL로 바로 고치는 쪽을 택했다.

```sql
UPDATE rejection_classified
SET `1차_대분류` = 'DMS 정보 오기재/불일치'
WHERE `1차_대분류` IN ('DMS 정보 오기재', '계약서/견적서와 DMS 정보 불일치');
```

같은 패턴의 UPDATE문을 `rejection_classified_live` 테이블에도 동일하게 적용해서, 두 테이블 모두 과거 데이터까지 새 카테고리명으로 맞췄다.
