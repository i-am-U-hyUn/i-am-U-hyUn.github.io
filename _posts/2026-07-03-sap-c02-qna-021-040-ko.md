## QUESTION 21

**문제**: 회사가 온프레미스 Active Directory로 사용자 인증을 하고 있고, 동일한 인증을 AWS Organizations의 여러 AWS 계정 로그인에도 사용하려 합니다. 온프레미스와 모든 AWS 계정 사이에는 이미 Site-to-Site VPN이 있습니다. 사용자 그룹/역할에 따른 조건부 액세스가 필요하고, 사용자 ID는 단일 위치에서 관리되어야 합니다.

**보기**
- A. **SAML 2.0**으로 Active Directory에 연결하도록 **AWS IAM Identity Center(AWS SSO)**를 구성한다. **SCIM v2.0**으로 자동 프로비저닝을 활성화한다. **ABAC(속성 기반 액세스 제어)**로 AWS 계정 접근 권한을 부여한다.
- B. IAM Identity Center 자체를 자격 증명 소스로 사용하도록 구성하고 SCIM으로 프로비저닝, 권한 집합으로 계정 접근을 부여한다.
- C. 한 계정에서 SAML 2.0 IdP를 사용하도록 IAM을 구성하고, 연동 사용자에 매핑된 IAM 사용자를 프로비저닝하며 교차 계정 IAM 사용자로 접근을 부여한다.
- D. 한 계정에서 OIDC IdP를 사용하도록 IAM을 구성하고, IAM 역할을 프로비저닝해 교차 계정 IAM 역할로 접근을 부여한다.

**정답: A**

**해설**
"사용자 ID는 단일 위치(온프레미스 AD)에서 관리"라는 조건이 핵심입니다. **IAM Identity Center를 SAML 2.0으로 기존 Active Directory에 연결**하고, **SCIM**으로 사용자·그룹 정보를 자동 동기화하며, **ABAC**로 사용자 속성(그룹/역할)에 따라 조건부 계정 접근을 제어하는 것이 정답입니다.

**왜 다른 보기는 오답인가**
- B: IAM Identity Center 자체를 "자격 증명 소스"로 쓰면 AD와는 별개의 두 번째 사용자 저장소가 생기는 셈이라, "단일 위치 관리" 요구사항에 위배됩니다.
- C: 계정마다 IAM 사용자를 개별 프로비저닝하고 교차 계정 IAM 사용자로 접근을 주는 방식은 계정 수가 늘어날수록 운영 부담이 매우 커집니다.
- D: OIDC는 온프레미스 AD 연동에 일반적으로 쓰이는 프로토콜이 아니며(SAML 2.0이 표준), 계정별 수동 역할 프로비저닝 방식도 확장성이 떨어집니다.

> 💡 **시험 꿀팁**: "많은 AWS 계정에 걸친 SSO + 기존 AD 연동 + 중앙 사용자 관리"라는 조합이 나오면 **IAM Identity Center(SAML 연동) + SCIM + 권한 집합/ABAC**을 먼저 떠올리세요.

## QUESTION 22

**문제**: API Gateway + Lambda + DynamoDB 앱에서 PUT 요청 오류가 늘고 있습니다. 원인은 API 키로 인증된 소수 클라이언트의 과도한 요청 때문입니다. API는 중요하지 않고 재시도가 가능하지만, 오류가 고객에게 노출되어 평판이 손상됩니다. 고객 경험을 개선하려면?

**보기**
- A. 클라이언트 측에 지수 백오프 + 지터가 있는 재시도 로직을 구현한다.
- B. **API Gateway 사용량 계획(Usage Plan)으로 API 조절(Throttling)을 구현**하고, 클라이언트가 429 응답을 정상적으로 처리하도록 한다.
- C. API 캐싱을 켜서 프로덕션 단계의 응답성을 높인다.
- D. Lambda에 예약된 동시성을 구성한다.

**정답: B**

**해설**
API 키로 특정 클라이언트를 식별할 수 있으므로, **API Gateway의 사용량 계획**으로 해당 클라이언트에 대한 요청 속도/할당량을 제한하는 것이 근본적인 해법입니다. 이렇게 하면 과도한 요청은 예상되고 처리 가능한 **429(Too Many Requests)** 응답으로 정중하게 거절되며, 클라이언트는 이를 재시도 신호로 받아들일 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 클라이언트 측 재시도 로직만으로는 근본 원인(한 클라이언트의 과도한 요청)을 막지 못하고, 모든 클라이언트가 로직을 구현해야 하는 것도 통제 불가능한 전제입니다.
- C: API 캐싱은 GET 같은 멱등 조회에 유효하며, 데이터를 변경하는 PUT 요청에는 적용되지 않습니다.
- D: Lambda 예약 동시성은 리소스 확보에는 도움이 되지만, 특정 클라이언트만 골라 속도를 제한하는 용도가 아니며 다른 정상 클라이언트에 영향을 줄 수도 있습니다.

> 💡 **시험 꿀팁**: 특정 API 키의 과도한 호출이 문제라면 **API Gateway 사용량 계획(Usage Plan)**을 통한 조절을 먼저 떠올리세요. 429는 "정상적으로 예상되는" 응답이라는 점도 기억하세요.

## QUESTION 23

**문제**: 수백 대 EC2로 구성된 클러스터가 200TB 공유 파일 시스템(별도 EC2에서 상시 운영)의 데이터를 읽고 수정해 보고서를 생성합니다. 작업은 월 1회, 파일의 일부만 읽으며 완료까지 약 72시간이 걸립니다. 컴퓨트는 Auto Scaling으로 늘었다 줄지만, 공유 파일 시스템 인스턴스는 계속 실행됩니다. 비용을 줄이면서 72시간 동안은 고성능 액세스를 유지해야 합니다.

**보기**
- A. 데이터를 **S3 Intelligent-Tiering**으로 마이그레이션한다. 매월 작업 전 **Amazon FSx for Lustre**를 **지연 로딩(lazy loading)**으로 S3와 연결해 새로 만들고, 작업 동안 공유 스토리지로 사용한 뒤 작업 완료 후 삭제한다.
- B. 데이터를 다중 연결(Multi-Attach) EBS 볼륨으로 마이그레이션하고 각 인스턴스에 연결한다.
- C. 데이터를 **S3 Standard**로 마이그레이션한다. 매월 작업 전 FSx for Lustre를 **일괄 로드(batch load)**로 생성해 사용한다.
- D. 데이터를 S3로 옮기고 매월 작업 전 AWS Storage Gateway 파일 게이트웨이를 생성해 사용한다.

**정답: A**

**해설**
평소엔 접근이 없다가 월 1회만 쓰이는 데이터이므로 저장 비용은 **S3 Intelligent-Tiering**으로 최소화하고, 작업이 시작될 때만 **FSx for Lustre**를 S3와 연동해 임시로 만들어 고성능 병렬 파일시스템으로 활용한 뒤 삭제하는 것이 가장 비용 효율적입니다. 특히 작업이 파일의 "일부만" 읽으므로, 전체를 미리 로드하는 일괄 로드보다 실제 접근 시 필요한 파일만 가져오는 **지연 로딩**이 더 효율적입니다.

**왜 다른 보기는 오답인가**
- B: 대용량 EBS 볼륨 다중 연결은 별도의 클러스터 인식 파일 시스템 소프트웨어가 필요해 복잡하고, S3 기반 방식만큼 비용을 절감하기 어렵습니다.
- C: S3 Standard는 대부분의 시간 동안 미사용 상태인 데이터에는 Intelligent-Tiering보다 비용이 높고, 일괄 로드는 필요 없는 파일까지 전부 로드해 시간·비용이 낭비됩니다.
- D: Storage Gateway 파일 게이트웨이는 지속적인 하이브리드 스토리지 접근에 적합하며, 72시간의 폭발적인 고성능 병렬 컴퓨팅 워크로드에는 FSx for Lustre만큼 최적화되어 있지 않습니다.

> 💡 **시험 꿀팁**: "평소엔 유휴 상태지만 주기적으로 짧은 기간 고성능 병렬 파일 접근이 필요한" 워크로드에는 **S3(Intelligent-Tiering) + FSx for Lustre(지연 로딩, 작업 시에만 생성 후 삭제)** 조합이 정답 패턴입니다.

## QUESTION 24

**문제**: 고정 포트의 TCP로 접속하는 새 서비스를 개발 중입니다. 가용 영역 전체에 중복성이 있고 공개 DNS 이름(`my.service.com`)으로 접근 가능해야 하며, 다른 회사가 허용 목록에 추가할 수 있도록 **고정 IP 주소**가 필요합니다. 단일 리전, 다중 가용 영역 배포를 전제로 합니다.

**보기**
- A. 각 EC2 인스턴스에 탄력적 IP를 직접 할당하고, NLB에 인스턴스를 등록, DNS 레코드는 인스턴스의 탄력적 IP를 가리키게 한다.
- B. ECS 클러스터에 퍼블릭 IP를 할당하고 NLB로 노출, DNS A 레코드가 ECS의 퍼블릭 IP를 가리키게 한다.
- C. EC2 인스턴스를 생성하고, **각 가용 영역마다 탄력적 IP를 하나씩 생성**해 **NLB에 가용 영역별로 할당**한다. 대상 그룹에 EC2를 등록하고, DNS **별칭(Alias) A 레코드**가 NLB의 DNS 이름을 가리키게 한다.
- D. ECS 클러스터 앞에 ALB를 두고 정적 TCP 포트를 노출, CNAME 레코드로 퍼블릭 IP를 연결한다.

**정답: C**

**해설**
다른 회사의 허용 목록에 등록할 수 있는 **고정(정적) IP**가 필요할 때는, ELB 유형 중 유일하게 **가용 영역별로 탄력적 IP를 직접 할당할 수 있는 Network Load Balancer(NLB)**를 사용해야 합니다. EC2 인스턴스는 NLB 뒤의 대상 그룹에 등록하고, DNS는 NLB를 가리키는 별칭 레코드로 설정합니다.

**왜 다른 보기는 오답인가**
- A: 탄력적 IP를 로드밸런서가 아닌 개별 인스턴스에 직접 붙이면 로드밸런싱·자동 장애 조치의 이점을 잃게 됩니다.
- B: ECS 태스크에 할당되는 퍼블릭 IP는 태스크가 재시작될 때마다 바뀔 수 있는 **동적** IP라, "고정 IP" 요구 사항을 만족하지 못합니다.
- D: **ALB는 L7(HTTP/HTTPS)** 기반이라 임의 TCP 포트 트래픽을 그대로 전달하는 용도에 맞지 않고, ALB 자체도 고정 IP를 제공하지 않습니다.

> 💡 **시험 꿀팁**: "허용 목록에 등록할 고정/정적 IP"라는 요구 사항이 보이면 **가용 영역마다 탄력적 IP를 할당할 수 있는 NLB**를 떠올리세요. ALB와 ECS의 동적 퍼블릭 IP는 이 조건을 만족하지 못합니다.

## QUESTION 25

**문제**: 온프레미스에서 완전 이중화된 12대 서버로 운영되는 분석 플랫폼이 있습니다. 예약 작업(20분~2시간, 엄격한 SLA)이 사용량의 65%, 사용자 작업(5분 이내, SLA 없음)이 35%를 차지합니다. 시스템 오류 시에도 예약 작업은 SLA를 지켜야 하지만 사용자 작업은 지연될 수 있습니다. EC2로 이전하면서 장기 약정 없는 소비 기반 모델로 비용을 절감하고, 고가용성과 SLA를 유지해야 합니다.

**보기**
- A. 2개 가용 영역에 12대 분할, 각 AZ에 용량 예약이 있는 온디맨드 2대 + 스팟 4대
- B. 3개 가용 영역에 분할하되, **한 AZ에만** 용량 예약 온디맨드 4대를 몰아넣고 나머지는 스팟
- C. 3개 가용 영역에 분할, 각 AZ에 **Savings Plan** 온디맨드 2대 + 스팟 2대
- D. 3개 가용 영역에 분할, **각 AZ에 용량 예약이 있는 온디맨드 3대 + 스팟 1대**

**정답: D**

**해설**
**On-Demand 용량 예약(Capacity Reservation)**은 특정 AZ에서 용량을 보장받으면서도 **장기 약정이 필요 없는** 온디맨드 요금제입니다. D는 3개 AZ 전체에 걸쳐 보장 용량(9대, 75%)을 고르게 분산해, 스팟 인스턴스(3대)가 모두 회수되더라도 SLA가 있는 예약 작업(65%)을 충분히 커버할 수 있고, 특정 AZ 하나가 장애 나더라도 보장 용량 전체가 한 번에 사라지지 않습니다.

**왜 다른 보기는 오답인가**
- A: 가용 영역이 2개뿐이라 이중화 수준이 낮고, 보장 용량도 4대(33%)에 불과해 스팟이 회수되면 65% SLA를 충족하지 못할 위험이 있습니다.
- B: 보장 용량 4대를 **한 AZ에 몰아넣어** 그 AZ에 장애가 생기면 보장 용량이 한꺼번에 사라지는 단일 장애점이 됩니다.
- C: **Savings Plan은 1년/3년 약정이 필요**해 "장기 약정 없이"라는 요구 사항에 정면으로 위배됩니다.

> 💡 **시험 꿀팁**: **On-Demand 용량 예약**은 특정 AZ의 용량을 보장하면서도 **장기 약정이 필요 없다**는 점에서 Reserved Instance/Savings Plan과 다릅니다. 보장 용량과 스팟을 섞어 쓸 땐, 보장 용량을 **모든 AZ에 고르게 분산**해야 단일 AZ 장애에도 안전합니다.

## QUESTION 26

**문제**: DB 비밀번호는 안전한 AWS 관리형 서비스에 저장된 무작위 강력 비밀번호를 사용해야 하고, 리소스는 CloudFormation으로 배포되며, 자격 증명은 90일마다 교체되어야 합니다. 최소 운영 오버헤드로 이를 만족하는 CloudFormation 리소스 구성은?

**보기**
- A. **AWS Secrets Manager**로 DB 암호를 Secret으로 생성한다. 암호를 교체할 Lambda 함수를 만든다. **90일마다 교체하는 Secrets Manager RotationSchedule 리소스**를 지정한다.
- B. Systems Manager Parameter Store의 SecureString으로 암호를 생성하고, Lambda로 교체하며, "Parameter Store RotationSchedule" 리소스로 90일 교체를 지정한다.
- C. Secrets Manager로 암호를 생성하고 Lambda로 교체하되, **EventBridge 예약 규칙**으로 90일마다 Lambda를 직접 트리거한다.
- D. Parameter Store SecureString으로 암호를 생성하고, "AWS AppSync DataSource" 리소스로 90일마다 자동 교체를 지정한다.

**정답: A**

**해설**

## QUESTION 32

**문제**: 개발자 전용 OU에 EC2·S3·DynamoDB만 허용하는 SCP를 배포했지만, 개발자 IAM 사용자가 여전히 그 외의 다른 AWS 서비스도 사용할 수 있습니다. 이 SCP 범위를 벗어난 서비스 사용을 막으려면?

- A. 제한할 각 서비스마다 명시적 거부 문을 개별적으로 만든다.
- B. **개발자 계정 OU에서 기본 `FullAWSAccess` SCP를 제거**한다.

**해설**

**왜 다른 보기는 오답인가**
- A: AWS가 계속 새 서비스를 추가하므로, 서비스별로 일일이 거부 문을 유지보수하는 것은 지속 불가능합니다.

- B: Systems Manager Agent는 일반적인 관리(패치, 명령 실행 등)를 위한 것으로, Discovery Agent가 제공하는 상세 마이그레이션 평가 데이터를 수집하지 않습니다.
- C: Systems Manager Application Manager는 이미 AWS로 이전된 애플리케이션을 운영·관리하는 도구이지, 온프레미스 서버를 마이그레이션 그룹으로 묶는 도구가 아닙니다.
- F: Trusted Advisor는 이미 AWS에서 실행 중인 리소스에 대한 모범 사례 권장 서비스로, 온프레미스 데이터를 기반으로 한 EC2 인스턴스 유형 추천 기능은 Migration Hub의 역할입니다.

> 💡 **시험 꿀팁**: 마이그레이션 평가는 **Application Discovery Agent(데이터 수집) → Migration Hub(애플리케이션 그룹화 + 인스턴스/비용 추천)**의 흐름으로 기억하세요. Systems Manager나 Trusted Advisor는 이 역할을 대체하지 못합니다.

## QUESTION 40

**문제**: 2개 AZ(각 AZ에 퍼블릭·프라이빗 서브넷)로 구성된 VPC에서 이미지 처리 서비스를 운영합니다. 서비스는 프라이빗 서브넷 EC2에서 실행되고 앞단에 ALB, 인터넷 통신은 2개의 NAT 게이트웨이를 경유합니다. 이미지는 S3에 저장되며, EC2는 매일 약 1TB를 S3에서 가져옵니다. 회사는 "매우 안전한" 서비스를 표방합니다. 보안 수준을 낮추거나 운영 시간을 늘리지 않으면서 비용을 최대한 절감하려면?

**보기**
- A. NAT 게이트웨이를 NAT 인스턴스로 교체한다.
- B. EC2를 퍼블릭 서브넷으로 옮기고 NAT 게이트웨이를 제거한다.
- C. **VPC에 S3 게이트웨이 VPC 엔드포인트를 설정**하고, 필요한 작업만 허용하는 엔드포인트 정책을 연결한다.
- D. EC2에 EFS 볼륨을 연결해 이미지를 EFS에서 호스팅한다.

**정답: C**

**해설**
현재 EC2 → S3 트래픽(하루 약 1TB)이 **NAT 게이트웨이를 거치면서 데이터 처리 요금**이 발생하고 있습니다. **S3 게이트웨이 VPC 엔드포인트는 무료**이며, S3로 향하는 트래픽을 NAT 게이트웨이를 거치지 않고 프라이빗하게 직접 라우팅해 그만큼의 NAT 처리 비용을 제거합니다. 트래픽이 인터넷을 거치지 않으므로 보안 수준도 그대로 유지되며, 추가 운영 부담도 거의 없습니다.

**왜 다른 보기는 오답인가**
- A: NAT 인스턴스로 바꾸면 비용은 줄일 수 있지만, 패치·관리 등 **운영 부담이 늘어나** "운영 시간을 늘리지 않는다"는 조건에 위배됩니다.
- B: EC2를 퍼블릭 서브넷으로 옮기면 인터넷에 직접 노출되어, "매우 안전한 서비스"라는 보안 목표에 정면으로 위배됩니다.
- D: EFS 도입은 NAT/S3 트래픽 비용 문제와 무관한 별개의 아키텍처 변경이며, 비용 절감 효과도 목적에 맞지 않고 마이그레이션 작업(운영 부담)만 추가됩니다.

> 💡 **시험 꿀팁**: 프라이빗 서브넷의 EC2가 **NAT 게이트웨이를 거쳐 S3에 접근**하고 있다면, **무료인 S3 게이트웨이 VPC 엔드포인트**를 추가해 NAT 데이터 처리 비용을 제거하는 것이 "보안 저하 없이 비용만 줄이는" 전형적인 정답 패턴입니다.
