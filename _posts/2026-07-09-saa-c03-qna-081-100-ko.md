## QUESTION 81

**문제**: 솔루션 설계자가 AWS에 배포할 새 애플리케이션의 아키텍처를 설계하고 있다. 처리할 작업 수에 따라 애플리케이션 노드를 필요한 만큼 추가/제거하면서 여러 프로세스가 병렬로 실행되어야 하며, 프로세서 애플리케이션은 상태 비저장(stateless)이다. 애플리케이션은 느슨하게 결합되어 있어야 하고, 작업 항목은 영구적으로 저장되어야 한다. 어떤 설계를 사용해야 하는가?

**보기**
- A. 처리할 작업을 보낼 Amazon SNS 주제를 생성하고, 프로세서 애플리케이션 AMI로 시작 구성(launch configuration)을 만들어 Auto Scaling 그룹을 구성한다. CPU 사용률에 따라 노드를 추가/제거한다(SNS는 메시지를 영구 보관하는 큐가 아니라 발행-구독 알림 서비스이며, CPU 사용률은 대기 중인 작업량과 직접적인 상관관계가 없음).
- B. 처리할 작업을 보관할 Amazon SQS 대기열을 생성하고, AMI로 시작 구성을 만들어 Auto Scaling 그룹을 구성한다. 네트워크 사용량에 따라 노드를 추가/제거한다(네트워크 사용량은 대기 중인 작업 수(백로그)를 반영하는 지표가 아님).
- C. **처리할 작업을 보관할 Amazon SQS 대기열을 생성하고, AMI로 시작 템플릿을 만들어 Auto Scaling 그룹을 구성한다. SQS 대기열의 항목 수를 기준으로 노드를 추가/제거하도록 조정 정책을 설정한다.**
- D. 처리할 작업을 보낼 Amazon SNS 주제를 생성하고, AMI로 시작 템플릿을 만들어 Auto Scaling 그룹을 구성한다. SNS 주제에 게시된 메시지 수를 기준으로 노드를 추가/제거한다(SNS는 메시지를 유지하지 않으므로 "게시된 메시지 수"를 대기 작업량 지표로 사용할 수 없고, 작업 항목의 영구 저장 요구도 충족하지 못함).

**정답: C**

**해설**
**Amazon SQS**는 메시지(작업 항목)를 대기열에 내구성 있게 보관해 프로듀서와 컨슈머를 느슨하게 결합시키는 완전관리형 큐 서비스입니다. SQS 대기열의 `ApproximateNumberOfMessagesVisible` 지표(인스턴스당 백로그)를 기준으로 **Auto Scaling** 조정 정책을 구성하면, 대기 중인 작업량에 정확히 비례해 상태 비저장 처리 노드를 늘리거나 줄일 수 있어 문제에서 요구하는 "느슨한 결합 + 영구 저장 + 수요 기반 병렬 처리"를 모두 만족합니다. 최신 모범 사례상 시작 템플릿(launch template)이 시작 구성보다 권장되는 방식이라는 점도 C를 선택하는 근거가 됩니다.

**왜 다른 보기는 오답인가**
- A: SNS는 메시지를 저장하지 않는 알림/팬아웃 서비스라 작업 항목의 영구 저장 요구를 충족하지 못하며, CPU 사용률 기반 조정은 백로그 크기와 무관합니다.
- B: 대기열을 사용한 것은 맞지만, 네트워크 사용량은 처리 대기 중인 작업 수와 직접적인 인과관계가 없어 적절한 조정 기준이 아닙니다.
- D: SNS는 큐가 아니므로 메시지가 영구 보관되지 않고, 소비자가 메시지를 가져가 처리하는 폴링 모델도 지원하지 않습니다.

> 💡 **시험 꿀팁**: **상태 비저장 워커를 작업량에 따라 동적으로 스케일**해야 한다는 조건이 나오면 **SQS 대기열 + 대기열 깊이 기반 Auto Scaling**이 표준 정답입니다.

## QUESTION 82

**문제**: 회사는 AWS 클라우드에서 웹 애플리케이션을 호스팅하며, AWS Certificate Manager(ACM)로 가져온(import) 인증서를 사용하도록 Elastic Load Balancer를 구성했다. 각 인증서가 만료되기 30일 전에 보안팀에 알려야 한다. 솔루션 설계자는 무엇을 권장해야 하는가?

**보기**
- A. ACM에 규칙을 추가해 인증서 만료 30일 전부터 매일 Amazon SNS 주제에 사용자 지정 메시지를 게시한다(ACM은 이런 반복 알림 규칙을 자체적으로 제공하지 않으며, 요구 사항은 "30일 전 1회 통보"이지 매일 반복 통보가 아님).
- B. **30일 이내에 만료되는 인증서를 확인하는 AWS Config 규칙(`acm-certificate-expiration-check`)을 생성한다. AWS Config가 비준수 리소스를 보고할 때 Amazon EventBridge를 통해 Amazon SNS로 알림을 보내도록 구성한다.**
- C. AWS Trusted Advisor로 30일 이내 만료 인증서를 확인하고, 상태 변경을 감지하는 CloudWatch 경보를 만들어 SNS로 알림을 보낸다(Trusted Advisor는 비용/성능/보안/내결함성 개선 권고에 초점을 맞춘 서비스로, ACM으로 가져온 인증서의 만료 감시를 목적으로 설계되지 않음).
- D. 30일 이내에 만료되는 모든 인증서를 감지하는 EventBridge 규칙을 만들어 Lambda 함수를 호출하고, Lambda가 SNS로 알림을 보내게 한다(ACM으로 가져온 인증서는 만료가 임박해도 자체적으로 "다가오는 만료" 이벤트를 발생시키지 않으므로, EventBridge가 감지할 트리거 이벤트 자체가 존재하지 않음).

**정답: B**

**해설**
ACM은 자체 발급/자동 갱신 인증서에 대해서는 만료 관련 이벤트를 제공하지만, 이 문제처럼 **가져온(imported) 인증서**는 ACM이 자동으로 갱신하거나 만료를 사전에 이벤트로 알려주지 않습니다. 따라서 **AWS Config**의 관리형 규칙인 `acm-certificate-expiration-check`로 지정한 일수(예: 30일) 이내에 만료되는 인증서를 주기적으로 평가하고, 규칙이 비준수(NON_COMPLIANT)로 전환될 때 발생하는 Config 이벤트를 **Amazon EventBridge**가 감지해 **Amazon SNS**로 보안팀에 알리는 조합이 정확히 요구 사항에 부합합니다.

**왜 다른 보기는 오답인가**
- A: ACM에는 이런 사용자 지정 반복 알림 규칙 기능이 없고, 설령 있다 해도 "매일 알림"은 "30일 전에 알림"이라는 요구와 다릅니다.
- C: Trusted Advisor의 점검 범위는 비용 절감, 성능, 보안, 내결함성, 서비스 한도이며 이 시나리오(가져온 ACM 인증서 만료 감시)를 다루지 않습니다.
- D: EventBridge는 이벤트가 실제로 발생한 뒤 이를 감지해 반응하는 서비스입니다. 가져온 인증서는 만료 임박을 알리는 이벤트 자체를 생성하지 않으므로 EventBridge만으로는 트리거할 대상이 없습니다.

> 💡 **시험 꿀팁**: **ACM으로 가져온 인증서의 만료를 감시**해야 한다면 **AWS Config 규칙 + EventBridge + SNS** 조합이 표준 정답입니다(ACM 자체 발급 인증서의 자동 갱신 이벤트와 헷갈리지 마세요).

## QUESTION 83

**문제**: 회사의 동적 웹 사이트는 미국의 온프레미스 서버로 호스팅되고 있다. 유럽에서 제품을 출시하며 신규 유럽 사용자를 위한 사이트 로딩 시간을 최적화하려 하지만, 백엔드는 반드시 미국에 있어야 한다. 제품이 며칠 내 출시되므로 즉각적인 솔루션이 필요하다. 솔루션 설계자는 무엇을 권장해야 하는가?

**보기**
- A. us-east-1에서 Amazon EC2 인스턴스를 시작하고 사이트를 마이그레이션한다(us-east-1도 여전히 미국 리전이라 유럽 사용자와의 물리적 거리는 줄어들지 않고, 며칠 내 마이그레이션까지 완료하기도 현실적이지 않음).
- B. 웹사이트를 Amazon S3로 옮기고 교차 리전 복제를 사용한다(문제의 사이트는 동적 웹사이트이므로 정적 콘텐츠 호스팅 용도인 S3로는 백엔드 로직을 그대로 옮길 수 없음).
- C. **온프레미스 서버를 가리키는 사용자 지정 오리진(custom origin)과 함께 Amazon CloudFront를 사용한다.**
- D. 온프레미스 서버를 가리키는 Amazon Route 53 지리 근접 라우팅 정책을 사용한다(DNS 라우팅만 바꿀 뿐 실제 요청이 처리되는 서버 위치는 그대로 미국이라 지연 시간 개선 효과가 없음).

**정답: C**

**해설**
**Amazon CloudFront**는 S3뿐 아니라 온프레미스 HTTP 서버와 같은 **사용자 지정 오리진**도 지정할 수 있습니다. 백엔드는 미국에 그대로 둔 채, 유럽을 포함한 전 세계 엣지 로케이션에 CloudFront 배포만 추가하면 정적/동적 콘텐츠 전송을 가속화하고 TCP 연결 재사용, 엣지 캐싱 등을 통해 유럽 사용자의 체감 로딩 시간을 즉시 개선할 수 있습니다. 기존 인프라 변경이 거의 없어 "며칠 내 즉각적인 솔루션"이라는 조건에도 가장 잘 맞습니다.

**왜 다른 보기는 오답인가**
- A: us-east-1으로 옮겨도 여전히 미국이라 유럽과의 거리 문제가 해결되지 않고, 마이그레이션 자체에 시간이 필요합니다.
- B: 동적 웹사이트는 서버 사이드 처리가 필요한데 S3는 정적 파일 호스팅만 지원합니다.
- D: 지리 근접 라우팅은 DNS 응답을 조정할 뿐이며, 실제 백엔드가 미국에 고정되어 있으면 유럽 사용자의 요청은 여전히 대서양을 건너야 해서 지연 개선 효과가 없습니다.

> 💡 **시험 꿀팁**: **백엔드는 그대로 두고 전 세계 사용자의 체감 속도만 빠르게 개선**해야 한다면 **CloudFront + 사용자 지정 오리진**이 표준 정답입니다.

## QUESTION 84

**문제**: 회사는 기존 3계층 웹 아키텍처의 비용을 절감하려 한다. 웹/애플리케이션/DB 서버는 개발, 테스트, 프로덕션용 Amazon EC2 인스턴스에서 실행된다. 프로덕션 인스턴스는 하루 24시간 실행되고, 개발/테스트 인스턴스는 매일 최소 8시간 실행되며, 사용하지 않을 때 자동으로 중지하는 자동화를 구현할 계획이다. 가장 비용 효율적인 EC2 구매 옵션 조합은 무엇인가?

**보기**
- A. 프로덕션에 스팟 인스턴스, 개발/테스트에 예약 인스턴스를 사용한다(스팟 인스턴스는 중단될 수 있어 24시간 상시 가동이 필요한 프로덕션에는 부적합).
- B. **프로덕션에 예약 인스턴스, 개발/테스트에 온디맨드 인스턴스를 사용한다.**
- C. 프로덕션에 스팟 블록, 개발/테스트에 예약 인스턴스를 사용한다(스팟 블록은 2021년 7월부로 신규 고객에게 제공되지 않으며, 스팟 계열 자체가 24시간 가동 워크로드에 부적합).
- D. 프로덕션에 온디맨드 인스턴스, 개발/테스트에 스팟 블록을 사용한다(24시간 가동되는 프로덕션은 온디맨드보다 예약 인스턴스가 더 저렴하고, 스팟 블록은 단종된 상품).

**정답: B**

**해설**
**예약 인스턴스(Reserved Instance)**는 1년/3년 약정으로 상시 가동되는 워크로드에서 온디맨드 대비 큰 폭의 비용 절감을 제공하므로, 하루 24시간 실행되는 프로덕션 인스턴스에 적합합니다. 반면 개발/테스트 인스턴스는 매일 최소 8시간 이상 가변적으로 실행되고 사용하지 않을 때 자동 중지되는 특성상, 약정이 필요한 예약 인스턴스보다 사용한 만큼만 과금되는 **온디맨드 인스턴스**가 더 유연하고 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- A: 스팟 인스턴스는 AWS가 언제든 회수할 수 있어 상시 가동이 필수인 프로덕션 DB/앱 서버에는 가용성 리스크가 큽니다.
- C: 스팟 블록(정의된 기간의 스팟 인스턴스)은 이미 단종된 서비스이며, 스팟 계열이라는 점에서 A와 같은 문제를 가집니다.
- D: 24시간 실행되는 프로덕션에 온디맨드를 쓰면 예약 인스턴스 대비 불필요하게 비용이 높아지고, 스팟 블록은 단종되어 사용할 수 없습니다.

> 💡 **시험 꿀팁**: **상시 가동(24시간) 워크로드에는 예약 인스턴스, 가변적/단기 가동 워크로드에는 온디맨드**가 비용 최적화의 표준 조합입니다.

## QUESTION 85

**문제**: 회사에는 사용자가 웹 인터페이스 또는 모바일 앱으로 문서를 업로드하는 프로덕션 웹 애플리케이션이 있다. 새로운 규제 요구 사항에 따라 저장된 문서는 이후 수정하거나 삭제할 수 없어야 한다. 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. **업로드된 문서를 S3 버전 관리 및 S3 객체 잠금(Object Lock)이 활성화된 Amazon S3 버킷에 저장한다.**
- B. 문서를 Amazon S3 버킷에 저장하고 주기적으로 보관(archive)하는 수명 주기 정책을 구성한다(수명 주기 정책은 스토리지 클래스 전환/만료를 관리할 뿐 삭제나 수정 자체를 원천 차단하지 않음).
- C. S3 버전 관리를 활성화한 버킷에 문서를 저장하고, 모든 액세스를 읽기 전용으로 제한하는 ACL을 구성한다(ACL 설정은 버킷 정책이나 IAM 권한 변경으로 다시 되돌릴 수 있어 규제 수준의 강제적 불변성을 보장하지 못함).
- D. 문서를 Amazon EFS 볼륨에 저장하고 읽기 전용 모드로 마운트해 접근한다(마운트 옵션은 클라이언트 측 설정일 뿐이며 다른 클라이언트가 쓰기 모드로 다시 마운트하면 삭제/수정이 가능해 강제성이 없음).

**정답: A**

**해설**
"저장 후 수정·삭제 불가"라는 요구는 **WORM(Write Once Read Many)** 모델을 뜻하며, AWS에서 이를 구현하는 표준 기능이 **S3 객체 잠금(Object Lock)**입니다. 객체 잠금은 S3 **버전 관리**가 활성화된 버킷에서만 사용할 수 있으며, 거버넌스 모드나 컴플라이언스 모드로 지정 기간 또는 무기한 동안 객체의 삭제·덮어쓰기를 관리자조차 우회할 수 없도록 강제할 수 있어 규제 요구 사항을 정확히 충족합니다.

**왜 다른 보기는 오답인가**
- B: 수명 주기 정책은 스토리지 클래스 전환이나 만료 삭제를 자동화하는 기능이지, 삭제 자체를 금지하는 잠금 기능이 아닙니다.
- C: ACL이나 권한 설정은 IAM 정책 변경 등을 통해 언제든 다시 조정될 수 있어 규제 수준의 불변성 보장 수단이 되지 못합니다.
- D: 읽기 전용 마운트는 해당 클라이언트에서만 유효한 설정이며, 파일 시스템 자체에 삭제/수정을 원천 차단하는 잠금 기능이 없습니다.

> 💡 **시험 꿀팁**: **저장된 데이터를 수정·삭제할 수 없어야 한다(WORM)**는 요구가 나오면 **S3 버전 관리 + S3 Object Lock**이 표준 정답입니다.

**문제**: 회사에는 공통 Amazon RDS MySQL 다중 AZ DB 인스턴스에 자주 접속해야 하는 여러 웹 서버가 있다. 사용자 자격 증명을 자주 교체해야 하는 보안 요구 사항을 충족하면서, 웹 서버가 데이터베이스에 안전하게 연결할 수 있는 방법은?

**보기**

**AWS Secrets Manager**는 데이터베이스 자격 증명, API 키 등의 비밀 정보를 안전하게 저장하고, 지정한 일정에 따라 **Lambda 함수 기반의 자동 교체(rotation)**를 수행할 수 있는 완전관리형 서비스입니다. 코드나 서버에 자격 증명을 하드코딩하지 않고 API 호출로 런타임에 조회하도록 하면, 자격 증명이 교체되어도 애플리케이션 코드 변경 없이 최신 값을 항상 안전하게 가져올 수 있어 "자주 교체 + 안전한 접근"이라는 요구를 동시에 만족합니다.

- B: OpsCenter는 운영 이슈 대응을 위한 도구로 비밀 정보의 저장·교체와는 무관합니다.

- D: 서버마다 파일을 배포·갱신해야 하므로 교체 작업이 수동적이고 서버 수가 늘어날수록 운영 오버헤드와 불일치 위험이 커집니다.

> 💡 **시험 꿀팁**: **자격 증명을 자주 자동으로 교체**해야 한다는 조건이 나오면 **AWS Secrets Manager**가 표준 정답입니다.

## QUESTION 87

**문제**: 회사는 Amazon API Gateway가 호출하는 AWS Lambda 함수에서 애플리케이션을 호스팅하며, Lambda 함수는 고객 데이터를 Amazon Aurora MySQL 데이터베이스에 저장한다. 데이터베이스 업그레이드 중에는 Lambda 함수가 연결을 맺지 못해 일부 고객 데이터가 유실된다. 업그레이드 중 생성되는 고객 데이터를 보존하는 솔루션은?

**보기**
- A. Lambda 함수와 데이터베이스 사이에 Amazon RDS 프록시를 배치하고 Lambda가 RDS 프록시에 연결하도록 구성한다(RDS 프록시는 연결 풀링과 장애 조치 시 연결 유지에는 효과적이지만, 업그레이드로 DB 자체가 응답하지 못하는 시간이 Lambda의 최대 실행 시간(15분)을 넘기면 여전히 함수가 타임아웃되어 데이터가 유실될 수 있음).
- B. Lambda 함수의 실행 시간을 최대로 늘리고 데이터베이스 저장 코드에 재시도 메커니즘을 추가한다(Lambda 최대 실행 시간은 15분으로 고정되어 있어 업그레이드가 그보다 길어지면 결국 타임아웃되며, 재시도만으로는 근본적인 유실 방지가 안 됨).
- C. 고객 데이터를 Lambda 로컬 스토리지(/tmp)에 보관하고, 이를 스캔해 DB에 저장하는 새 Lambda 함수를 둔다(/tmp는 함수 인스턴스에 종속된 임시 스토리지로 인스턴스가 재활용/종료되면 데이터가 사라질 수 있어 내구성 있는 저장소가 아님).
- D. **Amazon SQS FIFO 대기열에 고객 데이터를 저장하고, 대기열을 폴링해 DB에 저장하는 새 Lambda 함수를 만든다.**

**정답: D**

**해설**
근본 해법은 API 요청 처리와 DB 저장을 **비동기로 분리(decoupling)**하는 것입니다. **Amazon SQS**는 메시지를 내구성 있게 보관하므로, 원본 Lambda 함수는 고객 데이터를 즉시 SQS FIFO 대기열에 적재해 빠르게 응답을 반환하고, DB가 업그레이드로 일시적으로 응답하지 않는 동안에도 메시지는 대기열에 안전하게 남아 있다가 별도의 소비자 Lambda 함수가 DB 복구 후 폴링해 저장을 완료할 수 있습니다. 이 방식은 업그레이드 소요 시간이 Lambda의 15분 실행 제한을 넘어서도 데이터 유실 위험이 없다는 점에서 RDS 프록시보다 근본적입니다.

**왜 다른 보기는 오답인가**
- A: RDS 프록시는 커넥션 관리와 짧은 장애 조치 상황의 가용성 향상에는 유용하지만, DB 업그레이드처럼 장시간 미가용 상태에서는 대기 중인 Lambda 실행 자체가 타임아웃될 수 있습니다.
- B: Lambda 최대 실행 시간은 15분으로 상한이 있어, 그보다 긴 업그레이드 작업에는 근본적 해결책이 되지 못합니다.
- C: /tmp는 함수 인스턴스와 생명주기를 같이하는 임시 저장 공간이라 내구성을 보장할 수 없습니다.

> 💡 **시험 꿀팁**: **백엔드가 일시적으로 응답하지 않는 동안 들어오는 데이터를 잃지 않아야 한다**면 **SQS 큐로 비동기 버퍼링** 하는 것이 표준 정답입니다.

## QUESTION 88

**문제**: 설문 조사 회사가 미국 지역에서 수년간 수집한 데이터를 3TB 규모(계속 증가)의 Amazon S3 버킷에 저장하고 있다. 이 데이터를 S3 버킷을 가진 유럽 마케팅 회사와 공유하기 시작했으며, 데이터 전송 비용을 최대한 낮게 유지하고자 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. **회사의 S3 버킷에서 요청자 지불(Requester Pays) 기능을 구성한다.**
- B. 회사의 S3 버킷에서 마케팅 회사의 S3 버킷으로 교차 리전 복제를 구성한다(복제는 저장 비용을 두 배로 만들 뿐 아니라 복제 시 발생하는 전송 비용은 여전히 버킷 소유자인 회사가 부담).
- C. 마케팅 회사에 대한 교차 계정 액세스를 구성해 회사의 S3 버킷에 접근하도록 한다(접근 권한 문제는 해결되지만 데이터를 다운로드할 때 발생하는 전송 비용은 기본적으로 여전히 버킷 소유자가 지불).
- D. S3 Intelligent-Tiering을 구성하고 마케팅 회사의 S3 버킷과 동기화한다(Intelligent-Tiering은 저장 비용 최적화 기능이며, 별도 버킷으로 동기화하면 오히려 중복 저장과 추가 전송 비용이 발생).

**정답: A**

**해설**
**요청자 지불(Requester Pays) 버킷**을 구성하면 버킷 소유자는 계속 스토리지 비용만 부담하고, 데이터를 실제로 다운로드하는 요청자(이 경우 유럽 마케팅 회사)가 데이터 전송 및 요청 비용을 부담하게 됩니다. 대용량 데이터셋을 여러 조직과 공유하면서도 소유자의 전송 비용 부담을 최소화하려는 이 시나리오에 정확히 부합하는 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- B: 교차 리전 복제는 스토리지를 이중화하는 것으로, 복제 자체의 전송 비용은 물론 저장 비용까지 추가로 발생시킵니다.
- C: 단순 교차 계정 접근 허용만으로는 기본적으로 회사(버킷 소유자)가 다운로드 전송 비용을 계속 부담하게 됩니다.
- D: Intelligent-Tiering은 접근 패턴에 따라 스토리지 클래스를 자동 전환해 저장 비용을 절감하는 기능으로, 전송 비용 부담 주체 문제와는 무관합니다.

> 💡 **시험 꿀팁**: **데이터를 공유하되 다운로드 비용은 상대방이 부담**하게 하려면 **S3 요청자 지불(Requester Pays) 버킷**이 표준 정답입니다.

## QUESTION 89

**문제**: 회사가 Amazon S3에 기밀 감사 문서를 저장하며, 최소 권한 원칙에 따라 버킷 정책으로 감사 팀 IAM 사용자만 접근하도록 제한하고 있다. 회사 관리자는 실수로 인한 문서 삭제를 우려해 더 안전한 솔루션을 원한다. 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. **S3 버킷에서 버전 관리(Versioning) 및 MFA 삭제(MFA Delete) 기능을 활성화한다.**
- B. 각 감사 팀 IAM 사용자 계정에 다단계 인증(MFA)을 활성화한다(로그인/API 호출 보안은 강화되지만, 정상 인증된 사용자의 실수(오조작)로 인한 객체 삭제 자체를 막거나 되돌리는 기능은 아님).
- C. 감사 기간 동안 s3:DeleteObject 작업을 거부하는 S3 수명 주기 정책을 IAM 사용자 계정에 추가한다(수명 주기 정책은 버킷/객체에 적용되는 스토리지 관리 기능이며 IAM 사용자 계정에 붙일 수 있는 권한 정책이 아니어서 구성 자체가 성립하지 않음).
- D. AWS KMS로 S3 버킷을 암호화하고 감사 팀이 KMS 키에 접근하지 못하도록 제한한다(키 접근을 막으면 감사 팀이 정상적인 업무에 필요한 객체 자체를 읽지 못하게 되어 실수 방지가 아니라 정상 사용까지 차단하는 결과를 낳음).

**정답: A**

**해설**
**S3 버전 관리**는 객체가 삭제되거나 덮어써져도 이전 버전을 보존해 복구할 수 있게 하며, 여기에 **MFA 삭제**를 함께 활성화하면 버전 관리 설정 변경이나 객체 버전의 영구 삭제 시 추가 MFA 인증을 요구해 실수로 인한(또는 악의적인) 영구 삭제 자체를 어렵게 만듭니다. 이 두 기능의 조합이 "실수로 인한 삭제로부터 더 안전하게 보호"라는 요구에 가장 직접적으로 부합합니다.

**왜 다른 보기는 오답인가**
- B: 로그인 단계의 MFA는 계정 탈취를 막는 데 유용하지만, 정당하게 로그인한 사용자의 실수(오조작) 자체를 막지는 못합니다.
- C: 수명 주기 정책은 객체의 스토리지 클래스 전환·만료를 관리하는 기능이며, IAM 사용자 계정에 권한 거부를 부여하는 메커니즘이 아니라 이 옵션 자체가 기술적으로 성립하지 않습니다.
- D: KMS 키 접근 차단은 암호화된 데이터를 아예 읽지 못하게 만들어 정상 업무까지 방해하며, 삭제 자체를 막는 기능이 아닙니다.

> 💡 **시험 꿀팁**: **S3에서 실수로 인한 삭제를 방지**해야 한다면 **버전 관리 + MFA 삭제**가 표준 정답입니다.

## QUESTION 90

**문제**: 회사가 SQL 데이터베이스로 공개적으로 접근 가능한 영화 데이터를 저장하며, Amazon RDS 단일 AZ DB 인스턴스에서 실행한다. 매일 임의의 간격으로 실행되는 스크립트가 신규 영화 수를 집계해 업무 시간 동안의 최종 합계를 보고한다. 스크립트 실행 중 데이터베이스 성능이 저하되어 개발 작업에 지장을 준다. 최소한의 운영 오버헤드로 이 문제를 해결하는 솔루션은?

**보기**
- A. DB 인스턴스를 다중 AZ 배포로 수정한다(RDS MySQL 등의 다중 AZ 대기(standby) 인스턴스는 장애 조치 전용으로 읽기 트래픽을 서비스하지 않으므로 쿼리 부하 분리에는 도움이 되지 않음).
- B. **데이터베이스의 읽기 전용 복제본을 생성하고, 스크립트가 읽기 전용 복제본만 쿼리하도록 구성한다.**
- C. 개발 팀에게 매일 업무 종료 시 데이터베이스 항목을 수동으로 내보내도록 지시한다(수동 프로세스는 운영 오버헤드가 크고, "매일 임의의 간격"으로 실행되는 요구 사항과도 맞지 않음).
- D. Amazon ElastiCache로 스크립트가 실행하는 일반적인 쿼리를 캐싱한다(스크립트는 계속 변화하는 최신 집계치를 조회해야 하므로 캐시 무효화 관리가 추가로 필요해지고, 근본 원인인 프라이머리 DB의 쿼리 부하 자체를 줄이지 못함).

**정답: B**

**해설**
집계 스크립트가 프라이머리 DB에 직접 쿼리를 실행하면서 부하를 유발하고 있으므로, **읽기 전용 복제본(Read Replica)**을 만들어 스크립트의 읽기 쿼리를 복제본으로 라우팅하면 프라이머리 DB의 부하를 분리해 개발 작업에 미치는 영향을 없앨 수 있습니다. RDS는 관리 콘솔에서 몇 번의 클릭만으로 복제본을 생성·구성할 수 있어 운영 오버헤드도 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: 다중 AZ의 대기 인스턴스는 장애 조치(failover) 용도로만 사용되며 별도의 읽기 엔드포인트를 제공하지 않아, 이 구성만으로는 쿼리 부하가 여전히 프라이머리에 집중됩니다.
- C: 수동 내보내기는 사람이 개입해야 하는 반복 작업이라 운영 오버헤드가 크고 자동화 요구에 맞지 않습니다.
- D: 캐싱은 반복적으로 동일한 결과를 조회할 때 유리하지만, 계속 갱신되는 집계 카운트를 다루는 이 시나리오에는 캐시 무효화 로직이 추가로 필요해 근본적 해법이 아닙니다.

> 💡 **시험 꿀팁**: **읽기 쿼리 부하가 프라이머리 DB의 성능에 영향을 줄 때**는 **읽기 전용 복제본으로 읽기 트래픽 분리**가 표준 정답입니다.

## QUESTION 91

**문제**: VPC의 Amazon EC2 인스턴스에서 실행되는 애플리케이션이 Amazon S3 API를 호출해 객체를 저장·읽어야 한다. 보안 규정상 애플리케이션 트래픽은 인터넷을 통과할 수 없다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. **S3 게이트웨이 엔드포인트를 구성한다.**
- B. 프라이빗 서브넷에 S3 버킷을 생성한다(S3 버킷은 서브넷에 속하는 리소스가 아니며, 이렇게 해도 EC2와 S3 API 간 트래픽 경로 자체는 바뀌지 않음).
- C. EC2 인스턴스와 동일한 AWS 리전에 S3 버킷을 생성한다(같은 리전에 두어도 기본적으로 S3 API 호출은 퍼블릭 엔드포인트를 경유하는 인터넷 경로를 사용).
- D. EC2 인스턴스와 동일한 서브넷에 NAT 게이트웨이를 구성한다(NAT 게이트웨이는 프라이빗 서브넷의 아웃바운드 인터넷 접근을 가능하게 할 뿐이며, S3로 향하는 트래픽도 여전히 인터넷 경로를 거치게 되어 "인터넷 통과 금지" 요구를 위반함).

**정답: A**

**해설**
**Amazon S3용 게이트웨이 VPC 엔드포인트**를 구성하면 VPC 라우팅 테이블에 S3 프리픽스 목록을 대상으로 하는 경로가 추가되어, 인터넷 게이트웨이나 NAT 없이도 AWS 백본 네트워크 내부에서 EC2와 S3 사이의 트래픽이 오갈 수 있습니다. 이는 추가 비용 없이 트래픽이 인터넷을 전혀 통과하지 않도록 보장하는 가장 표준적인 방법입니다.

**왜 다른 보기는 오답인가**
- B: S3 버킷은 서브넷 개념과 무관한 리전 단위 리소스이므로, 프라이빗 서브넷에 "생성"한다는 개념 자체가 성립하지 않고 트래픽 경로도 바뀌지 않습니다.
- C: 같은 리전이라는 것은 지리적 근접성일 뿐, 게이트웨이 엔드포인트 없이는 여전히 S3의 퍼블릭 엔드포인트를 인터넷 경로로 호출하게 됩니다.
- D: NAT 게이트웨이는 프라이빗 서브넷 리소스가 인터넷으로 나가는 것을 도와주는 장치이므로, S3로 향하는 트래픽도 결국 인터넷을 경유하게 되어 요구 사항에 정면으로 위배됩니다.

> 💡 **시험 꿀팁**: **VPC 내 EC2가 인터넷을 거치지 않고 S3에 접근**해야 한다면 **S3 게이트웨이 VPC 엔드포인트**가 표준 정답입니다.

## QUESTION 92

**문제**: 회사가 Amazon S3 버킷에 민감한 사용자 정보를 저장하며, VPC 내부 Amazon EC2 인스턴스에서 실행되는 애플리케이션 계층에서만 이 버킷에 안전하게 접근하도록 하려 한다. 솔루션 설계자는 어떤 단계 조합을 취해야 하는가? (2개를 선택하세요.)

**보기**
- A. **VPC 내에서 Amazon S3용 VPC 게이트웨이 엔드포인트를 구성한다.**
- B. S3 버킷의 객체를 퍼블릭으로 만드는 버킷 정책을 생성한다(민감한 데이터를 퍼블릭으로 공개하는 것은 보안 요구 사항과 정반대).
- C. **VPC에서 실행되는 애플리케이션 계층으로만 접근을 제한하는 버킷 정책을 생성한다.**
- D. S3 액세스 정책을 가진 IAM 사용자를 생성하고 IAM 자격 증명을 EC2 인스턴스에 복사한다(장기 자격 증명을 인스턴스에 직접 복사·배포하는 방식은 유출 위험이 크고 모범 사례에 어긋나며, EC2에는 IAM 역할을 사용하는 것이 표준).
- E. NAT 인스턴스를 생성하고 EC2가 NAT 인스턴스를 통해 S3 버킷에 접근하도록 한다(NAT를 거치면 트래픽이 인터넷 경로를 경유하게 되어 게이트웨이 엔드포인트보다 보안성과 효율성이 떨어짐).

**정답: A, C**

**해설**
민감한 데이터가 담긴 S3 버킷에 대한 접근을 특정 VPC 내 애플리케이션으로만 제한하려면, 먼저 **S3 게이트웨이 VPC 엔드포인트**를 구성해 인터넷을 거치지 않는 사설 경로를 확보하고, 여기에 `aws:sourceVpc` 또는 `aws:sourceVpce` 조건을 사용한 **버킷 정책**으로 해당 VPC(엔드포인트)를 통한 요청만 허용하도록 제한합니다. 이 두 단계를 결합하면 네트워크 경로와 접근 권한 두 측면 모두에서 버킷을 안전하게 보호할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 객체를 퍼블릭으로 만들면 누구나 접근할 수 있게 되어 "민감한 사용자 정보 보호"라는 목적과 정면으로 배치됩니다.
- D: IAM 사용자의 장기 자격 증명을 EC2에 복사해 배포하는 방식은 자격 증명 유출·관리 부담 측면에서 IAM 역할 기반 접근보다 열등한 안티패턴입니다.
- E: NAT 인스턴스를 경유하면 트래픽이 다시 인터넷 게이트웨이를 통과하게 되어, 게이트웨이 엔드포인트가 제공하는 사설 경로의 이점을 얻지 못합니다.

> 💡 **시험 꿀팁**: **특정 VPC의 애플리케이션에게만 S3 접근을 제한**하는 문제에는 **게이트웨이 VPC 엔드포인트 + VPC 조건이 걸린 버킷 정책** 조합이 표준 정답입니다.

## QUESTION 93

**문제**: 회사가 MySQL 데이터베이스로 구동되는 온프레미스 애플리케이션을 AWS로 마이그레이션해 탄력성과 가용성을 높이려 한다. 현재 정상 운영 시간 동안 데이터베이스에서 읽기 활동이 많고, 개발 팀은 4시간마다 프로덕션 DB의 전체 내보내기를 가져와 스테이징 DB를 채우는데, 이 동안 사용자가 허용하기 어려운 지연을 겪고 개발 팀도 그동안 스테이징을 사용하지 못한다. 애플리케이션 지연을 완화하면서 개발 팀이 지연 없이 스테이징 환경을 계속 쓸 수 있게 하는 솔루션은?

**보기**
- A. 프로덕션용 다중 AZ Aurora 복제본과 함께 Amazon Aurora MySQL을 사용하고, mysqldump 유틸리티 기반 백업/복원으로 스테이징 DB를 채운다(mysqldump는 데이터 규모가 커질수록 내보내기/가져오기에 상당한 시간이 걸려, 그 동안 스테이징이 여전히 사용 불가능해지는 근본 문제를 해결하지 못함).
- B. **프로덕션용 다중 AZ Aurora 복제본과 함께 Amazon Aurora MySQL을 사용하고, 데이터베이스 복제(클로닝) 기능으로 요청 시 스테이징 DB를 생성한다.**
- C. 다중 AZ 배포 및 읽기 전용 복제본을 둔 Amazon RDS for MySQL을 프로덕션에 사용하고, 스테이징 DB에는 대기(standby) 인스턴스를 사용한다(다중 AZ의 대기 인스턴스는 장애 조치 전용 리소스로 별도의 독립된 스테이징 환경으로 전용할 수 없음).
- D. 다중 AZ 배포 및 읽기 전용 복제본을 둔 Amazon RDS for MySQL을 프로덕션에 사용하고, mysqldump 기반 백업/복원으로 스테이징 DB를 채운다(A와 동일하게 mysqldump 방식 자체가 대규모 데이터에서 느려 지연 문제를 해결하지 못함).

**정답: B**

**해설**
**Amazon Aurora**는 항상 3개의 가용 영역에 걸쳐 6개의 데이터 사본을 유지해 RDS 표준 엔진보다 가용성과 탄력성이 뛰어나므로 프로덕션 요구에 부합합니다. 스테이징 환경 요구의 핵심은 mysqldump처럼 시간이 걸리는 내보내기/가져오기 없이 즉시 사용 가능한 사본을 만드는 것인데, Aurora의 **빠른 데이터베이스 클로닝(fast database cloning)** 기능은 카피-온-라이트(copy-on-write) 방식으로 몇 분 내에 필요할 때마다 프로덕션과 독립된 스테이징 DB를 생성할 수 있어, 원본 성능에 영향을 주지 않으면서 지연 없는 스테이징 사용을 가능하게 합니다.

**왜 다른 보기는 오답인가**
- A: mysqldump는 전체 데이터를 덤프하고 다시 가져오는 방식이라 데이터가 커질수록 소요 시간이 길어져, 기존 4시간마다의 지연 문제를 사실상 반복하게 됩니다.
- C: RDS MySQL 다중 AZ의 대기 인스턴스는 오직 장애 조치를 위한 것으로, 애플리케이션이 별도로 접속해 사용할 수 있는 스테이징 환경이 아닙니다.
- D: mysqldump 기반 방식이라는 점에서 A와 동일한 한계를 가집니다.

> 💡 **시험 꿀팁**: **운영에 영향 없이 즉시 사용 가능한 사본 DB**가 필요하다면 **Amazon Aurora의 빠른 클로닝** 기능이 표준 정답입니다.

**정답: C**

**해설**
**S3 이벤트 알림 → SQS 대기열 → Lambda → DynamoDB**로 이어지는 완전 서버리스 파이프라인은 파일이 업로드될 때만 이벤트가 발생하고 그때만 비용이 청구되므로, 업로드량이 들쭉날쭉한 워크로드에 이상적입니다. SQS는 버스트 트래픽을 흡수하는 버퍼 역할을 하고, Lambda는 대기열 메시지를 이벤트 소스 매핑으로 자동 폴링해 업로드 직후 신속하게 일회성 처리를 수행하며, DynamoDB는 JSON 문서를 기본적으로 지원해 결과 저장에 적합합니다. 인프라 프로비저닝이나 상시 가동 리소스가 없어 운영 오버헤드도 최소입니다.

**왜 다른 보기는 오답인가**
- A: EMR은 대규모 배치/빅데이터 분석에 적합한 클러스터 기반 서비스라 업로드가 뜸한 날에도 비용이 발생하는 과잉 설계입니다.
- B: EC2로 큐를 폴링하려면 인스턴스가 상시 실행되어야 해 수요가 없는 날에도 비용이 들고, "일회성 단순 처리"라는 요구에는 서버리스인 Lambda가 더 적합합니다.
- D: Kinesis Data Streams는 지속적인 대용량 스트림 처리에 맞는 서비스라 샤드 관리 등 부가적 운영 부담이 있고, 파일 업로드가 없는 날에도 스트림 유지 비용이 발생합니다.

> 💡 **시험 꿀팁**: **트래픽이 들쭉날쭉한 워크로드를 최소 운영 오버헤드로 처리**해야 한다면 **S3 이벤트 → SQS → Lambda**의 서버리스 조합이 표준 정답입니다.

**문제**: 회사 본사 사용자가 Amazon RDS MySQL DB 인스턴스에 저장된 제품 데이터에 접근한다. 운영 팀은 애플리케이션 성능 저하를 격리하고 쓰기 트래픽에서 읽기 트래픽을 분리하려 한다. 솔루션 설계자는 애플리케이션 성능을 신속히 최적화해야 한다. 무엇을 권장해야 하는가?

> 💡 **시험 꿀팁**: **읽기/쓰기 트래픽 분리 및 성능 저하 격리**가 필요하면 **원본과 동일한 사양의 읽기 전용 복제본**이 표준 정답입니다(다중 AZ 대기 인스턴스와 혼동하지 마세요).

## QUESTION 96

**문제**: Amazon EC2 관리자가 여러 사용자가 속한 IAM 그룹에 다음 정책을 연결했다: 소스 IP가 `10.100.100.0/24`인 경우 모든 리소스에 대해 `ec2:TerminateInstances`를 허용(Allow)하는 문과, 리전이 `us-east-1`이 아닌 경우 모든 EC2 작업을 거부(Deny)하는 문으로 구성된다. 이 정책의 효과는 무엇인가?

**보기**
- A. 사용자는 us-east-1을 제외한 모든 리전에서 EC2 인스턴스를 종료할 수 있다(정책의 Deny 문을 정반대로 해석한 오류로, 실제로는 us-east-1 이외 리전에서의 EC2 작업이 전부 차단됨).
- B. 사용자는 us-east-1 리전에서 IP 주소가 10.100.100.1인 EC2 인스턴스를 종료할 수 있다(정책의 조건은 대상 인스턴스의 IP가 아니라 요청을 보내는 사용자의 소스 IP에 걸려 있으므로 조건 대상 자체를 잘못 해석한 설명).
- C. **사용자의 소스 IP가 10.100.100.254일 때 us-east-1 리전에서 EC2 인스턴스를 종료할 수 있다.**
- D. 사용자의 소스 IP가 10.100.100.254인 경우 사용자는 us-east-1 리전에서 EC2 인스턴스를 종료할 수 없다(C와 정반대의 결론으로, 실제로는 해당 IP가 허용 대역에 포함되어 종료가 가능함).

**정답: C**

**해설**
IAM 정책 평가에서는 **명시적 Deny가 Allow보다 항상 우선**합니다. 이 정책은 (1) 소스 IP가 `10.100.100.0/24` 대역이면 `ec2:TerminateInstances`를 허용하고, (2) 리전이 `us-east-1`이 아니면 모든 EC2 작업을 거부합니다. 두 문을 종합하면 결국 "**소스 IP가 10.100.100.0/24 대역이면서 리전이 us-east-1인 경우에만** 인스턴스 종료가 허용"됩니다. `10.100.100.254`는 `10.100.100.0/24`(10.100.100.0~10.100.100.255) 범위에 포함되므로, 해당 IP를 가진 사용자는 us-east-1 리전에서 인스턴스를 종료할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Deny 문은 us-east-1이 아닌 리전에서의 작업을 막는 것이지, us-east-1을 제외한 리전에서 종료를 허용한다는 의미가 아니어서 해석이 정반대입니다.
- B: 조건은 요청자의 출발지 IP(`aws:SourceIp`)에 대한 것이지 종료 대상 EC2 인스턴스의 IP 주소에 대한 조건이 아닙니다.
- D: `10.100.100.254`는 허용 대역인 `/24` 범위 안에 있으므로 종료가 불가능하다는 설명은 사실과 반대입니다.

> 💡 **시험 꿀팁**: **Allow + Deny가 함께 있는 IAM 정책 해석 문제**는 항상 **명시적 Deny 우선 원칙**과 **조건이 걸리는 대상(요청자 속성 vs. 리소스 속성)**을 먼저 정확히 구분하세요.

## QUESTION 98

**문제**: 이미지 처리 회사의 웹 애플리케이션이 사용자가 업로드한 이미지를 Amazon S3에 저장하고, 객체 생성 이벤트를 Amazon SQS 표준 대기열에 게시하도록 구성했다. SQS 대기열은 이미지를 처리해 결과를 이메일로 발송하는 AWS Lambda 함수의 이벤트 소스다. 사용자들이 업로드 1건당 여러 통의 이메일을 받고 있으며, 원인은 SQS 메시지가 Lambda 함수를 두 번 이상 호출하는 것으로 확인됐다. 최소한의 운영 오버헤드로 이를 해결하려면?

**보기**
- A. SQS 긴 폴링(long polling)의 ReceiveMessage 대기 시간을 30초로 늘린다(긴 폴링 대기 시간의 최댓값은 20초이며, 애초에 긴 폴링은 빈 응답/지연 최소화를 위한 것으로 중복 호출 문제의 원인과 무관함).
- B. SQS 표준 대기열을 FIFO 대기열로 바꾸고 메시지 중복 제거 ID로 중복 메시지를 제거한다(FIFO의 중복 제거는 프로듀서 쪽에서 동일한 메시지가 여러 번 유입되는 것을 막는 기능이며, 이 사례처럼 가시성 제한 시간 만료로 동일 메시지가 재수신되어 발생하는 중복 호출의 원인과는 다름).
- C. **SQS 대기열의 가시성 제한 시간(visibility timeout)을 Lambda 함수의 제한 시간과 일괄 처리 창(batch window) 제한 시간의 합보다 크게 늘린다.**
- D. Lambda 함수가 처리 전에 메시지를 읽자마자 SQS 대기열에서 바로 삭제하도록 수정한다(처리 완료 전에 메시지를 삭제하면 처리 도중 함수가 실패했을 때 메시지가 영구히 유실될 위험이 있어 안전하지 않은 방식이며, 근본 원인 해결도 아님).

**정답: C**

**해설**
Lambda가 SQS 메시지를 처리하는 동안 **가시성 제한 시간(visibility timeout)**이 처리 완료 전에 만료되면, 다른 폴러(또는 동일 이벤트 소스 매핑)가 같은 메시지를 다시 볼 수 있게 되어 동일 메시지가 Lambda를 중복 호출하게 됩니다. 이를 막으려면 가시성 제한 시간을 **Lambda 함수 제한 시간(timeout) + 배치 처리 창(batch window) 제한 시간의 합보다 크게** 설정해, 정상 처리가 끝나 메시지가 삭제될 때까지 다른 컨슈머에게 메시지가 노출되지 않도록 해야 합니다. 설정값 변경만으로 해결되어 운영 오버헤드도 최소입니다.

**왜 다른 보기는 오답인가**
- A: 긴 폴링의 최대 대기 시간은 20초로 제한되어 있어 30초 설정 자체가 불가능하고, 애초에 중복 호출의 원인과도 무관합니다.
- B: FIFO 중복 제거 ID는 프로듀서가 동일 메시지를 중복 전송하는 상황을 막는 기능이며, 이 사례의 원인인 가시성 제한 시간 만료로 인한 재수신 문제와는 다른 메커니즘입니다.
- D: 처리 완료 전 메시지를 즉시 삭제하면 처리 중 실패 시 재시도 기회 자체가 사라져 메시지 유실 위험이 커지고, 표준 사례에서 벗어난 안티패턴입니다.

> 💡 **시험 꿀팁**: **SQS-Lambda 조합에서 동일 메시지가 중복 처리**된다면 우선 **가시성 제한 시간이 함수 처리 시간보다 충분히 긴지**부터 점검하는 것이 표준 접근입니다.

**문제**: 회사가 온프레미스 데이터 센터에서 호스팅되는 게임 애플리케이션을 위한 공유 스토리지 솔루션을 구현하려 한다. Lustre 클라이언트로 데이터에 접근할 수 있어야 하며, 솔루션은 완전관리형이어야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. AWS Storage Gateway 파일 게이트웨이를 생성하고 필요한 클라이언트 프로토콜의 파일 공유를 만든다(파일 게이트웨이는 NFS/SMB 프로토콜을 지원할 뿐 Lustre 클라이언트 접근을 지원하지 않음).
- B. Amazon EC2 Windows 인스턴스를 생성해 Windows 파일 공유 역할을 설치·구성한다(Windows 파일 공유는 SMB 기반으로 Lustre 클라이언트 접근을 제공하지 않으며, 인스턴스를 직접 관리해야 해 완전관리형 요구에도 어긋남).
- C. Amazon EFS 파일 시스템을 생성하고 Lustre를 지원하도록 구성한다(EFS는 NFS 기반 범용 파일 스토리지 서비스로 애초에 Lustre 프로토콜 지원 기능 자체가 없음).
- D. **Lustre 파일 시스템용 Amazon FSx를 생성한다.**

**정답: D**

**해설**
**Amazon FSx for Lustre**는 고성능 컴퓨팅(HPC)과 대규모 병렬 워크로드에 최적화된 완전관리형 Lustre 파일 시스템으로, Lustre 클라이언트를 통한 네이티브 접근을 지원하면서도 프로비저닝, 패치, 백업 등의 인프라 관리 부담을 AWS가 대신 처리합니다. Lustre 클라이언트 접근과 완전관리형이라는 두 요구 사항을 동시에 충족하는 유일한 선택지입니다.

**왜 다른 보기는 오답인가**
- A: Storage Gateway 파일 게이트웨이는 NFS/SMB 파일 공유만 제공하며 Lustre 프로토콜을 지원하지 않습니다.
- B: Windows 파일 공유는 SMB 기반 서비스로 Lustre와 무관하며, EC2를 직접 운영·관리해야 하므로 완전관리형 요구에도 맞지 않습니다.
- C: EFS는 NFS 기반 범용 파일 스토리지로 설계되어 있어 Lustre 클라이언트 프로토콜을 지원하지 않습니다.

> 💡 **시험 꿀팁**: **Lustre 클라이언트 접근이 필요한 완전관리형 고성능 파일 스토리지**를 물으면 **Amazon FSx for Lustre**가 표준 정답입니다.

## QUESTION 100

**문제**: 회사의 컨테이너화된 애플리케이션이 Amazon EC2 인스턴스에서 실행되며, 다른 비즈니스 애플리케이션과 통신하기 전에 보안 인증서를 다운로드해야 한다. 회사는 인증서를 거의 실시간으로 암호화/복호화할 수 있는 매우 안전한 솔루션을 원하며, 암호화된 데이터는 고가용성 스토리지에 저장되어야 한다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은?

**보기**
- A. 암호화된 인증서를 위한 AWS Secrets Manager 암호(secret)를 생성하고 필요에 따라 인증서를 수동으로 업데이트한다. 세분화된 IAM 액세스로 데이터 접근을 제어한다(수동 업데이트 방식은 "거의 실시간 암호화/복호화"라는 요구와 맞지 않고 운영 개입이 반복적으로 필요함).
- B. Python 암호화 라이브러리로 암호화 작업을 수행하는 AWS Lambda 함수를 만들고 함수를 Amazon S3 버킷에 저장한다(자체 구현한 암호화 로직은 키 관리·감사·보안 검증 측면에서 AWS KMS 같은 관리형 서비스보다 신뢰성이 떨어지고 유지보수 부담이 크며, "함수를 S3에 저장"한다는 표현 자체도 암호화 데이터 저장소 요구와 어긋남).
- C. **AWS KMS 고객 관리형 키를 생성하고 EC2 역할이 암호화 작업에 이 키를 사용하도록 허용한다. 암호화된 데이터를 Amazon S3에 저장한다.**
- D. AWS KMS 고객 관리형 키를 생성하고 EC2 역할이 암호화 작업에 이 키를 사용하도록 허용한다. 암호화된 데이터를 Amazon EBS 볼륨에 저장한다(EBS는 단일 AZ에 종속된 블록 스토리지로, S3처럼 기본적으로 다중 AZ에 걸친 고가용성/내구성을 제공하지 않음).

**정답: C**

**해설**
**AWS KMS 고객 관리형 키**를 사용하면 EC2 인스턴스에 부여된 IAM 역할 권한만으로 API 호출을 통해 인증서를 거의 실시간으로 암호화·복호화할 수 있고, 키 사용 내역은 CloudTrail로 감사되어 매우 안전합니다. 암호화된 결과 데이터를 **Amazon S3**에 저장하면 여러 가용 영역에 걸친 높은 내구성과 가용성을 기본으로 확보할 수 있어, "거의 실시간 암복호화 + 매우 안전 + 고가용성 저장소"라는 세 가지 요구를 모두 최소 운영 오버헤드로 충족합니다.

**왜 다른 보기는 오답인가**
- A: 수동으로 인증서를 갱신하는 절차가 필요해 실시간성이 떨어지고 사람이 반복 개입해야 하는 운영 부담이 있습니다.
- B: 자체 구현한 암호화 로직은 KMS처럼 검증된 키 관리·감사 체계를 갖추지 못해 보안성과 유지보수성이 떨어집니다.
- D: EBS 볼륨은 특정 AZ에 종속된 블록 스토리지라서 S3와 같은 다중 AZ 기반 고가용성을 기본으로 제공하지 않습니다.

> 💡 **시험 꿀팁**: **거의 실시간으로 안전하게 암호화/복호화 + 고가용성 저장**이 필요하면 **KMS 고객 관리형 키 + S3** 조합이 표준 정답입니다.
