## QUESTION 261

**문제**: 온프레미스 VMware 환경에 수백 대의 대형 VM(일부는 상태 저장 레거시 앱) 운영 중. AWS로 마이그레이션하되 **다운타임 최소화**, 애플리케이션 코드 변경 없이 리호스팅. 최소 운영 오버헤드로 대량 서버를 옮기는 방법은?

**보기**
- A. AWS Database Migration Service(DMS)로 서버 전체를 마이그레이션(DMS는 데이터베이스 마이그레이션 전용이며, OS/애플리케이션이 포함된 서버 전체를 옮기는 용도가 아님 — 개념 오류).
- B. **AWS Application Migration Service(MGN)로 지속적 블록 수준 복제를 설정해 소스 서버를 AWS로 복제. 전환(cutover) 시점에 최신 상태의 EC2 인스턴스를 짧은 다운타임으로 기동.**
- C. 각 VM을 수동으로 AMI로 내보낸 후 EC2에 개별 업로드(수백 대를 수동으로 처리하는 것은 운영 오버헤드가 매우 크고, 지속적 복제가 없어 전환 시점까지의 데이터 변경분을 반영하지 못해 다운타임이 길어짐).
- D. AWS Server Migration Service(SMS)로 정기 스냅샷 기반 복제(SMS는 이미 MGN으로 대체된 레거시 서비스이며, 스냅샷 주기가 길수록 전환 시 다운타임과 데이터 유실 위험이 커짐).

**정답: B**

**해설**
**AWS Application Migration Service(MGN)**는 소스 서버에 에이전트를 설치해 **지속적인 블록 수준 복제**로 AWS에 최신 상태를 유지하다가, 실제 전환(cutover) 시점에만 짧게 인스턴스를 중지하고 EC2를 기동하므로 다운타임을 최소화합니다. 상태 저장 레거시 앱이라도 OS/애플리케이션 변경 없이 그대로 리호스팅할 수 있어 대량 서버 마이그레이션의 표준 도구입니다.

**왜 다른 보기는 오답인가**
- A: DMS는 데이터베이스(스키마/데이터)를 마이그레이션하는 서비스이며, 서버 전체(OS 포함) 리호스팅과는 목적이 다릅니다.
- C: 수동 AMI 내보내기/업로드는 수백 대 규모에서 운영 오버헤드가 극심하고, 지속적 복제가 없어 전환 시점의 다운타임도 길어집니다.
- D: SMS는 AWS가 MGN으로 대체를 권고하는 레거시 서비스이며, 지속적 복제가 아닌 주기적 스냅샷 방식이라 다운타임 최소화에 불리합니다.

> 💡 **시험 꿀팁**: 대규모 서버를 **다운타임 최소화 + 코드 변경 없이** 리호스팅할 때는 **AWS Application Migration Service(MGN)**의 지속적 블록 수준 복제 + 짧은 cutover 조합이 표준 정답입니다.

## QUESTION 262

**문제**: 조직 내 50개 AWS 계정에서 GuardDuty를 각각 개별적으로 활성화/관리 중이라 보안 팀이 위협을 한눈에 파악하기 어려움. 보안 계정 하나에서 **모든 계정의 GuardDuty 탐지 결과를 중앙에서 확인**하고, 신규 계정도 자동으로 포함되도록 하고 싶다. 운영 오버헤드를 최소화하는 방법은?

**보기**
- A. 각 계정에서 GuardDuty 탐지 결과를 EventBridge로 보안 계정의 SQS로 전달하도록 개별 설정(계정마다 개별적으로 EventBridge 규칙을 구성/유지해야 해서 운영 부담이 크고, 신규 계정 자동 포함도 안 됨).
- B. **보안 계정을 GuardDuty의 위임된 관리자(delegated administrator)로 지정. Organizations와 통합해 모든 기존/신규 멤버 계정의 GuardDuty를 자동 활성화 및 중앙에서 결과 확인.**
- C. 각 계정에서 GuardDuty 결과를 S3로 내보내는 Lambda를 개별 배포 + 보안 계정에서 Athena로 통합 조회(계정마다 Lambda를 개별 배포/유지해야 하고, 신규 계정 자동 포함 기능도 없어 운영 오버헤드가 큼).
- D. 마스터 계정에서 각 멤버 계정에 GuardDuty 초대를 수동으로 발송(멤버 계정 수가 많아질수록 수동 초대/수락 프로세스가 비효율적이며, Organizations 위임 관리자 방식이 신규 계정 자동 포함 측면에서 더 우수).

**정답: B**

**해설**
GuardDuty를 Organizations와 통합해 **위임된 관리자(delegated administrator)** 계정을 지정하면, 기존 멤버 계정은 물론 **향후 조직에 추가되는 신규 계정에도 자동으로 GuardDuty가 활성화**되며, 위임된 관리자 계정에서 모든 계정의 탐지 결과를 중앙 콘솔에서 한 번에 확인할 수 있습니다. 이는 계정별 개별 설정이 전혀 필요 없는 가장 운영 효율적인 방식입니다.

**왜 다른 보기는 오답인가**
- A, C: 계정마다 EventBridge 규칙이나 Lambda를 개별적으로 구성/유지하는 것은 계정 수가 늘어날수록 운영 부담이 커지고, 신규 계정에 자동 적용되지 않습니다.
- D: 수동 초대 방식은 Organizations 통합 위임 관리자 방식보다 신규 계정 자동 포함 및 운영 효율성 면에서 열등합니다.

> 💡 **시험 꿀팁**: 다수 계정의 보안 탐지를 **중앙에서, 신규 계정까지 자동으로** 관리하려면 **GuardDuty(또는 Security Hub, Macie 등) + Organizations 위임된 관리자(delegated administrator)** 조합이 표준 정답입니다.

## QUESTION 263

**문제**: 제조 공장에 온프레미스 애플리케이션이 있고 로컬 파일 서버를 **저지연으로 자주 읽고 씀**. 동시에 이 파일들을 클라우드에도 백업해 재해 복구에 활용하고 싶음. 온프레미스 인프라 투자를 최소화하는 솔루션은?

**보기**
- A. 온프레미스 NAS를 계속 사용하고 매일 밤 AWS DataSync로 S3에 백업(NAS 자체의 하드웨어 확장/유지보수 부담이 그대로 남아 "온프레미스 인프라 투자 최소화" 요구에 부합하지 않음).
- B. **Storage Gateway의 파일 게이트웨이(File Gateway)를 배포해 로컬 캐시로 저지연 접근을 제공하면서 파일을 S3에 객체로 저장.**
- C. FSx for Windows File Server를 온프레미스에 직접 설치(FSx는 AWS에서 실행되는 완전관리형 서비스이며 온프레미스에 설치하는 형태가 아님 — 개념 오류).
- D. 온프레미스 파일 서버 데이터를 Snowball Edge로 정기적으로 물리 이송(정기적 물리 이송은 실시간에 가까운 저지연 접근 요구와 무관하며 운영 복잡도만 높임).

**정답: B**

**해설**
**Storage Gateway 파일 게이트웨이**는 온프레미스에 가상 어플라이언스로 배포되어 **로컬 캐시**를 통해 자주 접근하는 파일에 저지연 접근을 제공하면서, 실제 데이터는 **S3에 객체로 저장**되어 자동으로 클라우드에 백업됩니다. 추가 온프레미스 하드웨어(NAS 확장 등) 투자 없이 기존 파일 워크플로를 그대로 유지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 온프레미스 NAS를 계속 운영/확장해야 하므로 온프레미스 투자 최소화 요구와 어긋납니다.
- C: FSx for Windows File Server는 AWS 리전에서 실행되는 관리형 서비스이며, 온프레미스에 직접 설치할 수 없습니다.
- D: Snowball Edge를 이용한 정기적 물리 이송은 배치성 백업에 가까워 "저지연으로 자주 읽고 쓰는" 요구를 충족하지 못합니다.

> 💡 **시험 꿀팁**: 온프레미스에서 **저지연 파일 접근을 유지하면서 클라우드로 자동 백업**하려는 요구에는 **Storage Gateway 파일 게이트웨이(로컬 캐시 + S3 저장)**가 표준 정답입니다.

## QUESTION 264

**문제**: 전 세계 사용자를 대상으로 하는 애플리케이션의 Aurora MySQL 데이터베이스. 쓰기는 한 리전에 집중되지만 **여러 리전에서 읽기 지연시간을 낮추고**, 리전 장애 시 **1분 이내 RTO**로 다른 리전에서 쓰기를 재개해야 함. 솔루션은?

**보기**
- A. 여러 리전에 독립적인 Aurora 클러스터를 두고 애플리케이션에서 이중 쓰기(dual write) 구현(애플리케이션 레벨 이중 쓰기는 데이터 정합성 보장이 매우 어렵고 구현/운영 복잡도가 큼).
- B. 기본 리전에 Aurora + 다른 리전에는 읽기 전용 복제본을 두는 표준 Aurora 읽기 복제본(리전 간 Aurora 읽기 복제본은 일반적인 비동기 복제로, 승격 시간이 수 분 이상 걸려 1분 RTO를 충족하기 어려움).
- C. **Aurora Global Database를 구성해 보조 리전에 읽기 전용 복제본을 두고, 장애 시 빠른 승격(fast recoverability)으로 보조 리전을 쓰기 가능한 리전으로 전환.**
- D. DynamoDB 글로벌 테이블로 데이터베이스 전체를 마이그레이션(관계형 스키마/쿼리 요구사항을 명시하지 않았더라도 기존 Aurora MySQL 데이터베이스를 그대로 유지해야 하는 상황에서 DynamoDB로의 전면 마이그레이션은 애플리케이션 재작성 부담이 매우 큼).

**정답: C**

**해설**
**Aurora Global Database**는 전용 복제 인프라를 통해 보조 리전에 **1초 미만의 지연시간**으로 읽기 전용 복제본을 유지해 전 세계 읽기 지연시간을 낮추고, 리전 장애 시 보조 리전을 **일반적으로 1분 이내**에 쓰기 가능한 리전으로 승격(promote)할 수 있어 엄격한 RTO 요구를 충족합니다.

**왜 다른 보기는 오답인가**
- A: 애플리케이션 레벨의 이중 쓰기는 충돌 해결, 정합성 보장이 매우 까다로워 운영 리스크가 큽니다.
- B: 일반 Aurora 읽기 복제본(리전 간)의 승격은 Global Database의 빠른 복구 기능보다 훨씬 느립니다.
- D: 기존 관계형 워크로드를 유지해야 하는 상황에서 DynamoDB로 전면 전환하는 것은 요구사항에 없는 과도한 재설계입니다.

> 💡 **시험 꿀팁**: **전 세계 읽기 지연시간 감소 + 짧은 RTO의 리전 장애 복구**가 동시에 필요한 Aurora 워크로드에는 **Aurora Global Database**가 표준 정답입니다.

## QUESTION 265

**문제**: 하나의 EKS 클러스터에서 여러 팀의 워크로드를 운영하며 팀 간 **네트워크/리소스 격리**와 **각 팟(Pod)이 최소 권한의 AWS 자격 증명**을 사용하도록 해야 함. 클러스터를 팀별로 나누지 않고 운영 오버헤드를 최소화하려면?

**보기**
- A. 모든 팀의 워크로드를 하나의 네임스페이스에 배포하고 EC2 인스턴스 프로파일로 AWS 권한 부여(네임스페이스 분리가 없어 격리가 되지 않고, 인스턴스 프로파일은 노드의 모든 팟이 동일 권한을 공유하게 되어 최소 권한 원칙 위반).
- B. **팀별로 별도의 네임스페이스와 네트워크 정책(NetworkPolicy)을 구성하고, IAM Roles for Service Accounts(IRSA)로 각 팀의 서비스 어카운트에 최소 권한 IAM 역할 매핑.**
- C. 팀마다 별도의 EKS 클러스터를 신규 생성(클러스터를 나누지 않고 하나로 운영하고 싶다는 요구사항에 위배되며 운영 오버헤드도 증가).
- D. 모든 팟에 동일한 광범위 권한의 IAM 역할을 노드에 연결해 사용(모든 팟이 동일하게 넓은 권한을 갖게 되어 최소 권한 원칙에 정면으로 위배).

**정답: B**

**해설**
Kubernetes **네임스페이스**로 팀별 논리적 경계를 만들고 **NetworkPolicy**로 네임스페이스 간 트래픽을 제어해 네트워크 격리를 구현하며, **IRSA(IAM Roles for Service Accounts)**를 사용하면 노드 단위가 아닌 **팟(서비스 어카운트) 단위**로 최소 권한 IAM 역할을 세밀하게 부여할 수 있습니다. 이는 클러스터를 나누지 않고도 강력한 격리와 최소 권한을 동시에 달성하는 표준 방식입니다.

**왜 다른 보기는 오답인가**
- A, D: 인스턴스(노드) 수준의 IAM 역할은 해당 노드에서 실행되는 모든 팟이 동일한 권한을 공유하게 되어, 팟별 최소 권한을 요구하는 시나리오에 맞지 않습니다.
- C: 문제에서 클러스터를 나누지 않고 운영 오버헤드를 최소화하고 싶다고 명시했으므로, 클러스터 분리는 요구사항에 반합니다.

> 💡 **시험 꿀팁**: EKS에서 **팟 단위 최소 권한 AWS 자격 증명**이 필요하면 **IRSA(IAM Roles for Service Accounts)**, 팀/워크로드 간 **네트워크 격리**에는 **네임스페이스 + NetworkPolicy**를 결합하는 것이 표준 정답입니다.

## QUESTION 266

**문제**: 여러 AWS 계정에 분산된 수십 개의 마이크로서비스가 서로 통신해야 하며, 서비스마다 다른 VPC에 위치. 서비스 디스커버리와 접근 제어를 **VPC 피어링이나 Transit Gateway 같은 네트워크 연결 관리 없이** 애플리케이션 계층에서 간소화하고 싶다. 솔루션은?

**보기**
- A. 모든 VPC를 Transit Gateway로 연결 + 각 서비스에 보안 그룹 규칙 개별 적용(문제에서 명시적으로 네트워크 연결 관리 부담을 줄이고 싶다고 했으므로, TGW로 모든 VPC를 연결하는 전통적 네트워킹 접근은 요구에 반함).
- B. **Amazon VPC Lattice를 사용해 서비스 네트워크를 구성하고, 서비스들을 계정/VPC 경계와 무관하게 서비스 네트워크에 연결해 애플리케이션 계층 라우팅과 접근 제어(인증/인가) 정책을 적용.**
- C. 모든 서비스를 API Gateway 프라이빗 엔드포인트로 노출하고 각 소비자 VPC에 인터페이스 엔드포인트 개별 생성(서비스마다 엔드포인트를 개별 생성/관리해야 해서 수십 개 규모에서 운영 부담이 크고, 통합 서비스 네트워크 개념이 없음).
- D. 모든 마이크로서비스를 하나의 VPC로 통합 이전(계정/VPC 경계를 유지한 채 통신을 간소화하고 싶은 요구와 달리 아키텍처 전체를 재구성해야 해서 부담이 훨씬 큼).

**정답: B**

**해설**
**Amazon VPC Lattice**는 VPC/계정 경계를 넘나드는 서비스 간 통신을 **애플리케이션 계층(L7)**에서 관리하는 서비스로, 복잡한 VPC 피어링·Transit Gateway 구성 없이도 서비스를 하나의 논리적 **서비스 네트워크**에 연결하고, 인증/인가 기반의 접근 제어 정책을 중앙에서 정의할 수 있습니다. 이는 다수 계정/VPC에 흩어진 마이크로서비스 간 통신을 가장 간소화하는 최신 표준 접근입니다.

**왜 다른 보기는 오답인가**
- A: 전통적인 네트워크 계층(TGW, 보안 그룹)으로 모든 것을 관리하는 것은 이 문제가 피하고자 하는 방식 그 자체입니다.
- C: API Gateway 프라이빗 엔드포인트를 서비스마다 개별적으로 만들고 엔드포인트를 관리하는 것은 수십 개 규모에서 운영 부담이 여전히 큽니다.
- D: 계정/VPC 경계를 유지해야 하는 조직 구조를 무시하고 전부 하나의 VPC로 합치는 것은 비현실적인 대규모 재설계입니다.

> 💡 **시험 꿀팁**: 여러 계정/VPC에 흩어진 마이크로서비스 간 통신을 **네트워크 계층 관리 부담 없이** 애플리케이션 계층에서 간소화하려면 **Amazon VPC Lattice**가 표준 정답입니다.

> 💡 **시험 꿀팁**: **파일럿 라이트 DR**은 최소 사양의 핵심 구성 요소(예: RDS 읽기 복제본)를 상시 유지하다가 장애 시 **승격 + 확장**으로 빠르게 복구하고, **Route 53 페일오버**로 트래픽을 전환하는 것이 표준 패턴입니다.

## QUESTION 269

**문제**: 유전체 분석 회사가 페타바이트급 유전체 데이터를 배치(batch)로 처리해야 함. 각 작업은 서로 다른 CPU/메모리 요구사항을 가지며, 수천 개의 병렬 작업을 실행하되 **작업 스케줄링과 인프라 관리에 드는 운영 부담을 최소화**하고 싶다. 적절한 서비스는?

- D. 각 작업을 개별 Lambda 함수로 구현(Lambda의 최대 실행 시간과 리소스 제한으로 인해 페타바이트급 장시간 배치 작업에는 부적합).

**해설**

- A: 자체 큐/스케줄러 구현은 AWS Batch가 이미 제공하는 기능을 직접 재구현하는 것으로 운영 부담이 매우 큽니다.
- C: EMR은 Hadoop/Spark 같은 분산 데이터 처리 프레임워크에 특화되어 있고, 상시 가동 클러스터는 가변적인 배치 워크로드에 비용 비효율적입니다.
- D: Lambda는 최대 실행 시간(15분) 제한이 있어 장시간 실행되는 대규모 배치 작업에 적합하지 않습니다.

> 💡 **시험 꿀팁**: 자원 요구사항이 제각각인 **대규모 병렬 배치 작업**을 운영 부담 없이 처리하려면 **AWS Batch**(컴퓨팅 환경 자동 프로비저닝 + 완전관리형 작업 큐/스케줄링)가 표준 정답입니다.

## QUESTION 270

**문제**: 여러 AWS 계정에 분산된 RDS 데이터베이스들이 자격 증명을 사용하는데, 보안 팀은 **비밀번호를 중앙에서 자동으로 순환(rotation)**시키고 각 애플리케이션 계정이 필요한 비밀만 최소 권한으로 조회하도록 하고 싶다. 계정마다 개별 Secrets Manager 인스턴스를 운영하지 않고 중앙화하려면?

**보기**
- A. 각 계정에서 개별적으로 Secrets Manager 비밀을 생성/순환하고 수동으로 동기화(계정마다 개별 관리해야 해서 중앙화 요구에 반하고, 수동 동기화는 오류 발생 가능성이 큼).
- B. **보안 계정(중앙 계정)에 비밀을 저장하고 Secrets Manager 리소스 정책으로 각 애플리케이션 계정의 IAM 역할에 크로스 계정 접근을 허용. Lambda 순환 함수는 중앙 계정에서 관리.**
- C. 모든 데이터베이스 비밀번호를 하나의 KMS 키로 암호화해 S3에 저장하고 각 애플리케이션이 S3에서 직접 읽음(S3에 원문/암호화된 비밀을 저장하는 방식은 Secrets Manager의 자동 순환·감사·세분화된 접근 제어 기능을 활용하지 못하는 반패턴).
- D. Systems Manager Parameter Store의 SecureString으로 전환하고 각 계정에서 개별적으로 순환 로직 구현(Parameter Store는 자체 자동 순환 기능이 Secrets Manager만큼 통합되어 있지 않아 순환 로직을 직접 구현해야 하는 부담이 있고, 계정별 개별 구현은 중앙화 요구에도 반함).

**정답: B**

**해설**
**중앙 보안 계정의 Secrets Manager**에 비밀을 저장하고, **리소스 기반 정책**으로 각 애플리케이션 계정의 특정 IAM 역할에만 크로스 계정 조회 권한을 부여하면, 비밀은 한 곳에서 중앙 관리되면서도 각 계정은 필요한 비밀만 최소 권한으로 조회할 수 있습니다. 순환용 Lambda 함수도 중앙 계정에서 한 번만 관리하면 되어 운영 오버헤드가 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: 계정마다 개별 관리 후 수동 동기화하는 것은 중앙화 요구에 정면으로 반하며 운영 리스크도 큽니다.
- C: S3에 직접 비밀을 저장하는 것은 Secrets Manager의 자동 순환, 세분화된 접근 제어, 감사 로그 등 핵심 이점을 포기하는 방식입니다.
- D: Parameter Store SecureString은 가능한 대안이지만, RDS 자격 증명에 대한 통합 자동 순환 기능은 Secrets Manager가 더 강력하며, 계정별 개별 구현은 중앙화 취지에 어긋납니다.

> 💡 **시험 꿀팁**: 다중 계정에서 **비밀을 중앙 관리하면서 최소 권한으로 공유**하려면 **중앙 계정의 Secrets Manager + 리소스 정책 기반 크로스 계정 접근**이 표준 정답입니다.

## QUESTION 271

**문제**: 금융 회사가 온프레미스 데이터센터와 AWS 간에 **최대 복원력(maximum resiliency)**을 갖춘 Direct Connect 연결을 구성하려 한다. 단일 장애 지점(회선, 디바이스, 위치)이 없어야 한다. AWS가 권장하는 구성은?

**보기**
- A. 하나의 Direct Connect 위치에서 하나의 회선만 구성(단일 위치, 단일 회선이라 위치 장애/회선 장애 모두에 취약 — 복원력 없음).
- B. 하나의 Direct Connect 위치에서 서로 다른 두 개의 디바이스를 경유하는 두 개의 회선 구성(단일 위치 장애 시 두 회선 모두 영향을 받아 위치 수준 복원력이 없음).
- C. **서로 다른 두 개의 Direct Connect 위치 각각에서, 해당 위치의 서로 다른 두 디바이스를 경유하는 두 개씩의 회선을 구성(총 4개 회선, 2개 위치, 각 위치 내 디바이스 이중화).**
- D. 하나의 Direct Connect 위치에서 두 개의 회선을 구성하고, 나머지 백업은 인터넷 기반 VPN으로만 대체(단일 위치에 의존하며, VPN은 대역폭/지연시간이 Direct Connect보다 낮아 완전한 대체가 아님 — 최대 복원력 모델에는 미달).

**정답: C**

**해설**
AWS Direct Connect Resiliency Toolkit이 정의하는 **최대 복원력(maximum resiliency)** 모델은 **서로 다른 두 개 이상의 Direct Connect 위치** 각각에서 **서로 다른 디바이스를 경유하는 복수의 회선**을 구성하는 것입니다. 이렇게 하면 특정 위치 전체의 장애, 특정 디바이스의 장애, 특정 회선의 장애 중 어느 하나가 발생해도 나머지 경로로 연결이 유지됩니다.

**왜 다른 보기는 오답인가**
- A, B: 단일 위치에만 의존하는 구성은 그 위치 자체에 장애가 발생하면(정전, 재해 등) 완전히 연결이 끊기므로 최대 복원력 기준에 미달합니다.
- D: 인터넷 기반 VPN은 유효한 백업 경로가 될 수 있지만, Direct Connect 수준의 대역폭/지연시간 요구가 있는 금융 워크로드에서 단일 Direct Connect 위치의 완전한 대체 수단으로는 부족하며, 여전히 단일 위치에 의존합니다.

> 💡 **시험 꿀팁**: Direct Connect의 **최대 복원력(maximum resiliency)** 모델은 **서로 다른 2개 이상의 위치 × 각 위치의 서로 다른 디바이스를 경유하는 다중 회선**을 구성하는 것이 표준입니다. 단일 위치 기반 구성은 위치 자체가 SPOF(단일 장애 지점)가 됩니다.

## QUESTION 273

**문제**: 여러 부서가 각자 다른 스키마의 데이터를 S3 데이터 레이크에 적재하고 있으며, 시간이 지나며 스키마가 자주 변경됨(컬럼 추가/타입 변경). 분석 팀은 Athena로 쿼리하되, **각 데이터셋에 대한 세분화된 컬럼/행 수준 접근 제어**도 필요하다. 운영 부담을 최소화하는 데이터 카탈로그/거버넌스 솔루션은?

**보기**
- A. 각 부서가 자체적으로 Hive 메타스토어를 EC2에 구축해 스키마를 관리(자체 구축/운영해야 해서 오버헤드가 크고, 세분화된 접근 제어 기능도 직접 구현해야 함).
- B. **AWS Glue 크롤러로 스키마 변경을 자동으로 감지해 Glue Data Catalog에 반영하고, AWS Lake Formation의 세분화된 권한(컬럼/행 수준)으로 데이터셋 접근을 제어.**
- C. 모든 원본 데이터를 RDS로 옮겨 관계형 스키마로 강제 통일(스키마가 자주 바뀌는 반정형/다양한 데이터에 관계형 강제 통일은 부적합하며 마이그레이션 부담도 큼).

**정답: B**

**해설**
**AWS Glue 크롤러**는 S3 데이터의 스키마 변경을 주기적으로 자동 감지해 **Glue Data Catalog**를 최신 상태로 유지하므로 별도 수작업 스키마 관리가 필요 없습니다. **AWS Lake Formation**은 이 카탈로그 위에서 **컬럼 수준, 행 수준**의 세밀한 접근 제어 정책을 중앙에서 정의할 수 있어, Athena로 쿼리하는 분석 팀에게 데이터셋별로 필요한 부분만 노출할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 자체 Hive 메타스토어 운영은 Glue Data Catalog가 완전관리형으로 제공하는 기능을 직접 구축/유지하는 것으로 운영 부담이 큽니다.
- C: 스키마가 자주 바뀌는 다양한 데이터를 관계형 DB로 강제 통일하는 것은 유연성을 해치고 마이그레이션 비용이 큽니다.
- D: S3 버킷 정책은 객체/버킷 단위 제어만 가능하며, 문제에서 요구하는 컬럼/행 수준의 세분화된 접근 제어를 지원하지 않습니다.

> 💡 **시험 꿀팁**: 데이터 레이크에서 **자동 스키마 관리 + 컬럼/행 수준 세분화된 접근 제어**가 필요하면 **Glue Data Catalog(크롤러로 자동 업데이트) + Lake Formation(세분화된 권한)** 조합이 표준 정답입니다.

## QUESTION 275

**문제**: 회사가 사용하는 상용 소프트웨어 라이선스가 **특정 물리 서버의 소켓/코어 수**를 기준으로 과금되며, 라이선스 계약상 **가상화 환경의 물리적 특성(소켓, 코어, 호스트 ID)을 확인**할 수 있어야 한다. EC2에서 이 요구를 만족하며 라이선스 비용을 최적화하려면?

**보기**
- A. 표준 On-Demand EC2 인스턴스를 사용하고 별도 조치 없음(공유 하드웨어를 사용하는 표준 인스턴스는 물리 서버 단위의 소켓/코어 정보를 명확히 통제/확인하기 어려워 라이선스 계약 요구를 충족하지 못할 수 있음).
- B. **Amazon EC2 Dedicated Hosts를 사용해 물리 서버 전체를 단독으로 할당받고, 호스트의 소켓/코어 정보를 확인해 기존 라이선스를 그대로 적용(BYOL, Bring Your Own License).**
- C. Dedicated Instances(전용 인스턴스)를 사용(전용 인스턴스는 다른 계정과 하드웨어를 공유하지 않는 것은 보장하지만, 특정 호스트의 소켓/코어 ID 같은 물리적 정보에 대한 가시성/제어는 Dedicated Host보다 제한적).
- D. Savings Plans를 구매해 라이선스 비용까지 포함해 할인받음(Savings Plans는 컴퓨팅 사용량 할인 프로그램이며 소켓/코어 기반 소프트웨어 라이선스 요구사항 자체를 해결하지 못함).

**정답: B**

**왜 다른 보기는 오답인가**
- A: 공유 하드웨어 기반의 표준 인스턴스는 물리적 소켓/코어 단위의 통제가 불가능해 이런 라이선스 요구사항에 부적합합니다.
- C: Dedicated Instances는 하드웨어 미공유는 보장하지만, 특정 물리 호스트에 대한 세부 가시성(소켓/코어/호스트 ID 확인)은 Dedicated Host만큼 제공하지 않습니다.

## QUESTION 278

**문제**: 규정 준수 요구사항에 따라 여러 리전에 저장되는 백업 데이터를 **동일한 키 자료(key material)**로 암호화해야 하며(리전마다 별도 키로 재암호화하지 않고), 각 리전에서 로컬로 빠르게 암호화/복호화가 가능해야 한다. 솔루션은?

**보기**
- A. 각 리전에 독립적인 KMS 키를 생성하고, 백업 시 소스 리전에서 복호화 후 대상 리전 키로 재암호화(리전마다 다른 키 자료를 사용하게 되어 "동일한 키 자료" 요구에 반하며, 매번 복호화/재암호화하는 추가 처리 비용과 지연이 발생).
- B. **KMS 다중 리전 키(multi-Region key)를 기본 키로 생성하고, 필요한 각 리전에 복제 키(replica key)를 생성. 동일한 키 ID/키 자료를 공유하므로 리전 간 재암호화 없이 각 리전에서 로컬로 암호화/복호화.**
- C. 하나의 리전에만 KMS 키를 생성하고, 다른 리전의 리소스는 항상 해당 키가 있는 리전을 넘어 API를 호출해 암복호화(리전 간 API 호출은 지연시간이 크고, 해당 키 리전에 장애가 발생하면 다른 리전의 암복호화도 영향을 받아 "각 리전에서 로컬로" 요구에 반함).
- D. CloudHSM 클러스터를 각 리전에 독립적으로 구축하고 클러스터 간 수동으로 키를 내보내기/가져오기(수동 키 이동은 운영 부담과 보안 리스크가 크며, KMS 다중 리전 키가 제공하는 네이티브 복제 기능보다 훨씬 번거로움).

**정답: B**

**해설**
**KMS 다중 리전 키(multi-Region key)**는 기본 키를 생성한 뒤 다른 리전에 **동일한 키 자료를 공유하는 복제 키**를 만들 수 있어, 각 리전이 **독립적인 키 ID를 가지면서도 동일한 암호화 자료**를 사용합니다. 따라서 한 리전에서 암호화한 데이터를 다른 리전의 복제 키로 재암호화 없이 바로 복호화할 수 있고, 각 리전에서 로컬로 API를 호출하므로 지연시간도 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: 리전마다 독립된(다른 키 자료를 가진) 키를 사용하고 재암호화하는 방식은 "동일한 키 자료" 요구를 충족하지 못하고 추가 처리 오버헤드가 발생합니다.
- C: 단일 리전 키에 의존해 매번 리전 간 API를 호출하는 것은 지연시간이 크고 해당 리전 장애 시 다른 리전 전체가 영향을 받는 단일 장애 지점이 됩니다.
- D: CloudHSM 간 수동 키 이동은 KMS 다중 리전 키의 네이티브 복제보다 훨씬 복잡하고 운영 리스크가 큽니다.

> 💡 **시험 꿀팁**: 여러 리전에서 **동일한 키 자료로 재암호화 없이 로컬 암복호화**가 필요하면 **KMS 다중 리전 키(multi-Region key) + 복제 키(replica key)**가 표준 정답입니다.

**문제**: 하이브리드 환경에서 온프레미스 서버가 VPC 내 프라이빗 호스팅 영역의 도메인을 조회해야 하고, 반대로 VPC의 EC2도 온프레미스 DNS 서버가 관리하는 도메인을 조회해야 한다(양방향 하이브리드 DNS 해석). VPN/Direct Connect로 연결되어 있다는 전제하에 솔루션은?

**보기**
- A. 온프레미스 서버들의 DNS 설정을 모두 Route 53 퍼블릭 호스팅 영역의 네임서버로 직접 변경(프라이빗 호스팅 영역은 퍼블릭 네임서버로 조회할 수 없으며, 온프레미스 자체 도메인 조회 요구도 해결하지 못함 — 개념 오류).

**왜 다른 보기는 오답인가**
- A: 프라이빗 호스팅 영역은 퍼블릭 네임서버로 조회되지 않으며, 온프레미스 자체 도메인에 대한 VPC 측 조회 요구도 다루지 않습니다.
- C: hosts 파일을 대규모로 지속 동기화하는 것은 현실적으로 운영 불가능한 방식입니다.
- D: 프라이빗 데이터를 퍼블릭으로 노출하는 것은 보안 요구사항 위반이며, 애초에 문제의 요구사항(프라이빗 영역 유지)과 배치됩니다.

> 💡 **시험 꿀팁**: 온프레미스와 VPC 간 **양방향 DNS 조회**가 필요한 하이브리드 환경에서는 **Route 53 Resolver의 아웃바운드 엔드포인트(조건부 전달) + 인바운드 엔드포인트** 조합이 표준 정답입니다.

- B. **AWS Global Accelerator로 NLB를 엔드포인트로 등록해 Anycast IP로 전 세계 최적 경로 트래픽 유입을 구성하고, AWS Shield Advanced를 가입해 Global Accelerator/NLB를 보호(DDoS 비용 보호 및 DRT 지원 포함).**
- C. Route 53 지리 근접 라우팅으로 리전별 NLB에 트래픽 분산 + 기본 제공되는 AWS Shield Standard만 사용(Shield Standard는 기본 무료 보호이며 금전적 보호(cost protection)나 전담 대응팀(DRT) 지원이 포함되지 않아 요구사항에 미달).
- D. API Gateway를 NLB 앞에 두어 요청 속도 제한 적용(API Gateway는 REST/HTTP API 및 WebSocket 용도이며 UDP 기반 실시간 게임 트래픽을 처리할 수 없음 — 개념 오류).

**정답: B**

**해설**
**AWS Global Accelerator**는 고정 Anycast IP를 통해 AWS 글로벌 네트워크의 가장 가까운 엣지로 사용자를 유입시켜 TCP/UDP 트래픽 모두에 대해 최적의 경로와 낮은 지연시간을 제공하며, NLB를 엔드포인트로 등록할 수 있습니다. 여기에 **AWS Shield Advanced**를 적용하면 Global Accelerator/NLB에 대한 대규모 DDoS 공격 방어는 물론, DDoS로 인한 **확장 비용에 대한 금전적 보호**와 **DDoS 대응팀(DRT, DDoS Response Team)**의 24/7 지원을 받을 수 있어 경영진의 요구사항을 모두 충족합니다.

**왜 다른 보기는 오답인가**
- A: CloudFront는 HTTP(S) 콘텐츠 전송에 특화되어 있어 UDP 게임 트래픽을 처리할 수 없습니다.
- C: Shield Standard는 모든 AWS 고객에게 기본 제공되는 일반적인 네트워크/전송 계층 DDoS 보호이지만, 비용 보호나 DRT 전담 지원 같은 고급 기능은 Shield Advanced에서만 제공됩니다.
- D: API Gateway는 UDP 기반 실시간 트래픽을 처리하는 서비스가 아닙니다.

> 💡 **시험 꿀팁**: **UDP 등 비-HTTP 트래픽**을 전 세계 최적 경로로 유입시키며 **DDoS 비용 보호 + DRT 지원**까지 필요하면 **Global Accelerator(Anycast IP, TCP/UDP 지원) + Shield Advanced**의 조합이 표준 정답입니다. CloudFront는 HTTP(S) 전용이라는 점을 기억하세요.
