## QUESTION 281

**문제**: 온프레미스 Oracle 데이터베이스를 Aurora PostgreSQL로 마이그레이션(엔진 이기종 전환, heterogeneous migration)해야 함. 스토어드 프로시저 등 Oracle 전용 코드를 최대한 자동 변환하고, 실제 데이터 이관 중에는 **애플리케이션 중단 시간을 최소화**하고 싶다. 표준 접근은?

**보기**
- A. AWS DMS만 사용해 스키마와 데이터를 한 번에 마이그레이션(DMS는 스키마 객체[특히 스토어드 프로시저 같은 코드]의 자동 변환 기능이 제한적이며, 이기종 마이그레이션에서는 SCT와 함께 쓰는 것이 표준).
- B. **AWS Schema Conversion Tool(SCT)로 Oracle 스키마와 코드를 PostgreSQL 호환 형태로 변환한 뒤, AWS DMS로 전체 로드(full load) + 지속적 복제(CDC)를 수행해 전환 시점까지 최신 데이터를 유지하고 짧은 전환 창(cutover window)에 트래픽 이전.**
- C. mysqldump와 유사한 방식으로 Oracle 데이터를 텍스트로 내보낸 뒤 PostgreSQL에 수동으로 임포트(수동 방식은 대용량 데이터에서 오류 발생 가능성이 크고, 전환 중 발생하는 변경분을 지속적으로 반영할 방법이 없어 다운타임이 커짐).
- D. Aurora PostgreSQL 대신 RDS for Oracle로 우선 리호스팅한 뒤 나중에 재검토(문제에서 명시적으로 Aurora PostgreSQL로의 엔진 전환을 요구하고 있으므로 목표에 부합하지 않음).

**정답: B**

**해설**
**AWS SCT**는 Oracle의 스키마와 스토어드 프로시저/함수 같은 애플리케이션 코드를 최대한 자동으로 PostgreSQL 호환 코드로 변환합니다(자동 변환이 안 되는 부분은 변환 보고서로 식별). 이후 **AWS DMS**로 전체 데이터를 최초 적재(full load)하고, 그 이후 발생하는 변경분은 **CDC(변경 데이터 캡처)**로 지속 복제하여 소스와 타겟을 동기화 상태로 유지하다가, 짧은 전환 창에만 애플리케이션을 타겟으로 전환하면 다운타임을 최소화할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: DMS는 데이터 이관에 강하지만 스토어드 프로시저 같은 코드 객체의 자동 변환 기능은 SCT보다 제한적입니다. 이기종 마이그레이션은 SCT(스키마/코드 변환)+DMS(데이터 이관) 조합이 표준입니다.
- C: 수동 내보내기/임포트는 대용량 데이터에서 비효율적이고 오류 위험이 크며, 지속적 복제가 없어 전환 시점까지의 다운타임이 길어집니다.
- D: 문제의 목표 자체가 Aurora PostgreSQL로의 전환이므로, RDS for Oracle 리호스팅은 요구사항에 맞지 않습니다.

> 💡 **시험 꿀팁**: 서로 다른 데이터베이스 엔진 간 **이기종 마이그레이션**에는 **SCT(스키마/코드 변환) + DMS(전체 로드 + CDC 지속 복제)** 조합이 표준 정답이며, 이는 다운타임을 최소화하는 표준 패턴이기도 합니다.

## QUESTION 282

**문제**: SaaS 회사가 자사 API를 NLB 뒤의 EC2 플릿으로 서비스하며, 수백 개의 고객 AWS 계정이 **공용 인터넷을 거치지 않고** 이 API에 접근할 수 있게 하고 싶다. 고객이 늘어나도 운영 오버헤드가 커지지 않는 구조는?

**보기**
- A. 각 고객 VPC와 SaaS VPC 간 VPC 피어링 연결(피어링은 비전이적이며 CIDR 중복 문제가 발생할 수 있고, 수백 개 고객 규모에서 개별 피어링 관리는 운영 부담이 매우 큼).
- B. **NLB를 기반으로 VPC 엔드포인트 서비스(PrivateLink 서비스)를 생성해 게시하고, 고객들이 각자의 VPC에 인터페이스 엔드포인트를 생성해 연결하도록 허용.**
- C. SaaS API를 퍼블릭 인터넷에 노출하고 고객사 IP만 허용하는 보안 그룹 규칙 추가(공용 인터넷을 거치지 않아야 한다는 요구사항에 정면으로 반함).
- D. Direct Connect 게이트웨이를 통해 모든 고객사와 개별 프라이빗 가상 인터페이스 연결(고객마다 물리적/전용 회선 기반의 Direct Connect를 구성하는 것은 SaaS 다중 고객 연결 시나리오에 비해 훨씬 비용이 크고 시간이 오래 걸림).

**정답: B**

**해설**
NLB를 대상으로 **VPC 엔드포인트 서비스(AWS PrivateLink)**를 생성해 게시하면, 고객들은 각자의 VPC에 **인터페이스 엔드포인트**만 생성해 공용 인터넷을 거치지 않고 SaaS API에 연결할 수 있습니다. CIDR 중복 문제도 없고, 신규 고객이 추가될 때마다 SaaS 제공자 측에서 별도 네트워크 구성을 할 필요가 없어 고객 수가 늘어나도 운영 오버헤드가 거의 증가하지 않습니다.

**왜 다른 보기는 오답인가**
- A: VPC 피어링은 CIDR 중복 시 연결이 불가능하고, 수백 개 고객과의 개별 피어링 관리는 확장성이 없습니다.
- C: 퍼블릭 노출 방식은 "공용 인터넷을 거치지 않아야 한다"는 핵심 요구사항을 위반합니다.
- D: Direct Connect는 전용 회선 기반이라 비용/구축 기간 면에서 다수 SaaS 고객을 연결하는 시나리오에 부적합합니다.

> 💡 **시험 꿀팁**: SaaS 제공자가 **다수의 고객 VPC에 공용 인터넷 없이 확장 가능하게 서비스를 노출**하려면 **NLB 기반 VPC 엔드포인트 서비스(AWS PrivateLink)**가 표준 정답입니다.

## QUESTION 283

**문제**: 금융 규제 기관이 특정 거래 기록을 **일정 기간 동안 어떤 방식으로도 삭제·수정 불가능**(WORM, Write Once Read Many)하게 보관하도록 요구한다(SEC 17a-4 유사 규정 준수). 관리자 계정을 포함해 누구도 보존 기간 내에는 삭제할 수 없어야 한다. S3에서 이를 구현하는 방법은?

**보기**
- A. S3 버킷 정책으로 삭제(DeleteObject) API를 모든 사용자에게 거부(버킷 정책은 관리자 권한이 있는 사용자가 정책 자체를 수정하거나 삭제할 수 있어 진정한 의미의 변경 불가능성을 보장하지 못함).
- B. **S3 버전 관리를 활성화한 뒤 S3 Object Lock을 준수 모드(Compliance mode)로 설정하고, 필요한 보존 기간(retention period)을 지정.**
- C. S3 Object Lock을 거버넌스 모드(Governance mode)로 설정(거버넌스 모드는 특별 권한(s3:BypassGovernanceRetention)을 가진 사용자가 보존 설정을 우회해 삭제할 수 있어 "관리자도 삭제 불가능"이라는 요구를 완전히 충족하지 못함).
- D. 라이프사이클 정책으로 일정 기간 이후 Glacier Deep Archive로 전환(스토리지 계층 전환일 뿐이며 삭제/수정 자체를 원천적으로 방지하는 기능이 아님).

**정답: B**

**해설**
**S3 Object Lock**은 버전 관리가 활성화된 버킷에서 객체를 WORM 모델로 보호합니다. 이 중 **준수 모드(Compliance mode)**로 설정하면 **root 계정을 포함한 어떤 사용자도** 보존 기간이 끝나기 전까지 객체를 삭제하거나 보존 설정 자체를 약화시킬 수 없어, SEC 17a-4와 같은 엄격한 규제 준수 요구사항을 충족합니다.

**왜 다른 보기는 오답인가**
- A: 버킷 정책은 그 자체로 IAM 권한이 있는 사용자에 의해 변경/삭제될 수 있어, 규제가 요구하는 근본적인 불변성을 보장하지 못합니다.
- C: 거버넌스 모드는 특별 권한을 가진 사용자가 보존 설정을 우회할 수 있는 예외가 있어, "누구도 삭제 불가능"이라는 엄격한 요구에는 준수 모드가 더 적합합니다.
- D: 스토리지 클래스 전환은 비용 최적화 기능이며 삭제/수정 방지와는 무관합니다.

> 💡 **시험 꿀팁**: **관리자를 포함해 누구도 삭제/수정할 수 없는 WORM 규제 준수**가 필요하면 **S3 버전 관리 + S3 Object Lock 준수 모드(Compliance mode)**가 표준 정답입니다. 거버넌스 모드는 우회 가능하다는 차이를 기억하세요.

## QUESTION 284

**문제**: 여러 사업부가 각자의 AWS 계정에서 발생시키는 이벤트(주문 생성, 재고 변경 등)를 **중앙의 이벤트 버스**로 모아, 여러 소비 애플리케이션(다른 계정에 위치)이 관심 있는 이벤트만 구독해 처리하도록 하고 싶다. 계정 간 강한 결합 없이 이벤트 기반 아키텍처를 구성하려면?

**보기**
- A. 각 사업부 계정에서 소비 계정으로 직접 SNS 메시지를 발행하고, 소비 계정마다 별도의 SNS 주제 구독 관리(사업부-소비자 쌍마다 개별 연결을 관리해야 해서 계정이 늘어날수록 N:M 관계가 복잡해짐).
- B. **중앙 계정에 커스텀 EventBridge 이벤트 버스를 생성하고, 각 사업부 계정에서 이 중앙 버스로 이벤트를 전송하도록 리소스 정책 설정. 소비 애플리케이션은 규칙(rule)을 통해 관심 있는 이벤트 패턴만 필터링해 구독.**
- C. 모든 이벤트를 하나의 계정에 있는 RDS 테이블에 기록하고 소비 애플리케이션이 주기적으로 폴링(폴링 방식은 실시간성이 떨어지고, 관심사 기반 필터링을 위한 이벤트 라우팅 기능이 기본 제공되지 않음).
- D. 각 사업부가 자체 SQS 큐를 만들고 소비 애플리케이션이 필요한 모든 큐를 개별 구독(사업부-소비자 조합마다 큐를 개별 관리해야 해서 확장성이 떨어지고 이벤트 패턴 기반 필터링 기능도 없음).

**정답: B**

**해설**
**Amazon EventBridge**의 커스텀 이벤트 버스를 중앙 계정에 두고, 각 사업부 계정이 **리소스 기반 정책**을 통해 이 버스로 이벤트를 발행하도록 허용하면, 이벤트 발행자와 소비자가 서로를 알 필요 없이 느슨하게 결합됩니다. 소비 애플리케이션은 **이벤트 패턴 기반 규칙**으로 관심 있는 이벤트만 선택적으로 구독할 수 있어, N:M 관계를 이벤트 버스 하나로 단순화하는 표준 이벤트 기반 아키텍처입니다.

**왜 다른 보기는 오답인가**
- A, D: 발행자-소비자 쌍마다 개별 연결(SNS 구독, SQS 큐)을 관리해야 하는 방식은 계정 수가 늘어날수록 관리 복잡도가 기하급수적으로 증가합니다.
- C: 폴링 기반 방식은 이벤트 기반 아키텍처가 지향하는 실시간성과 느슨한 결합을 제공하지 못하며, 이벤트 패턴 필터링도 직접 구현해야 합니다.

> 💡 **시험 꿀팁**: 여러 계정에서 발생하는 이벤트를 **중앙에서 수집하고 관심사 기반으로 선택적으로 배포**하려면 **중앙 계정의 EventBridge 커스텀 이벤트 버스(리소스 정책으로 크로스 계정 발행 허용) + 규칙 기반 구독**이 표준 정답입니다.

## QUESTION 285

**문제**: 회사가 보관 중인 데이터 중 일부는 **분기별 감사 시 즉시(밀리초 단위) 조회**가 필요하고, 일부는 **연 1회, 조회까지 최대 12시간 정도는 허용**되는 규제 보관용 데이터다. 두 데이터셋 모두 접근 빈도는 매우 낮다. 비용을 최소화하는 스토리지 전략은?

**보기**
- A. 두 데이터셋 모두 S3 Glacier Deep Archive에 저장(Deep Archive의 복원 시간은 최대 12시간 이상 걸릴 수 있어, 즉시 조회가 필요한 감사용 데이터셋 요구사항을 충족하지 못함).
- B. **즉시 조회가 필요한 데이터는 S3 Glacier Instant Retrieval에, 12시간까지 허용되는 규제 보관 데이터는 S3 Glacier Deep Archive에 저장.**
- C. 두 데이터셋 모두 S3 Standard-IA(Standard-Infrequent Access)에 저장(접근 빈도가 매우 낮고 장기 보관 목적이므로, 더 저렴한 Glacier 계열 스토리지 클래스를 사용하지 않는 것은 비용 최적화 기회를 놓치는 것).
- D. 두 데이터셋 모두 S3 Glacier Flexible Retrieval(구 Glacier)에 저장하고 긴급 조회 시 Expedited 검색 사용(Expedited도 최소 몇 분의 지연이 있고 비용이 더 높으며, 밀리초 단위 즉시 조회에는 Glacier Instant Retrieval이 더 적합하고 저렴함).

**정답: B**

**해설**

**왜 다른 보기는 오답인가**
- A: Deep Archive는 복원에 최대 12시간 이상 걸릴 수 있어 즉시 조회가 필요한 데이터셋에는 부적합합니다.
- C: Standard-IA는 Glacier 계열보다 저장 비용이 높아, 이렇게 접근 빈도가 극히 낮은 데이터에는 비용 최적화 기회를 놓치는 선택입니다.
- D: Glacier Flexible Retrieval의 Expedited 검색도 지연시간과 비용 면에서 즉시 조회 요구에는 Glacier Instant Retrieval보다 불리합니다.

> 💡 **시험 꿀팁**: 접근 빈도는 낮지만 **조회 시간 요구가 서로 다른 데이터**는 하나의 스토리지 클래스로 뭉뚱그리지 말고, **즉시 조회 → Glacier Instant Retrieval**, **긴 지연 허용 → Glacier Deep Archive**처럼 요구사항별로 분리해 비용을 최적화하는 것이 표준 정답입니다.

## QUESTION 287

**문제**: 대규모 조직이 수십 개 VPC의 아웃바운드/동서(east-west) 트래픽을 **중앙 한 곳에서 검사**(침입 탐지/방지, 도메인 필터링 등)하고 싶다. 기존에 사용하던 서드파티 방화벽 어플라이언스도 계속 활용하고 싶어한다. 확장 가능한 중앙 집중식 트래픽 검사 아키텍처는?

**보기**
- A. 각 VPC에 서드파티 방화벽 인스턴스를 개별 배포하고 라우팅 테이블로 트래픽을 강제로 통과시킴(VPC마다 개별 배포/관리해야 해서 "중앙 집중식"이라는 요구에 반하고 운영 부담이 큼).
- B. **중앙 검사(inspection) VPC를 만들어 Gateway Load Balancer(GWLB) 뒤에 서드파티 방화벽 어플라이언스를 배치하고, GWLB 엔드포인트를 각 스포크 VPC에 배치해 Transit Gateway와 라우팅 구성으로 모든 트래픽이 중앙 검사 VPC를 경유하도록 구성.**
- C. AWS Network Firewall만 각 VPC에 개별 배포(기존 서드파티 방화벽 어플라이언스를 계속 활용하고 싶다는 요구를 충족하지 못하며, VPC별 개별 배포는 중앙 집중식이 아님).

**해설**
**Gateway Load Balancer(GWLB)**는 서드파티 방화벽 같은 가상 어플라이언스를 확장 가능하게 배치하고 트래픽을 투명하게 전달하는 서비스입니다. 중앙 **검사 VPC**에 GWLB와 서드파티 어플라이언스를 두고, 각 스포크 VPC에는 **GWLB 엔드포인트**를 배치한 뒤 Transit Gateway와 라우팅 테이블을 구성해 모든 아웃바운드/동서 트래픽이 중앙 검사 VPC를 거치도록 하면, 기존 서드파티 방화벽 투자를 유지하면서도 확장 가능한 중앙 집중식 트래픽 검사 아키텍처를 구현할 수 있습니다.

**왜 다른 보기는 오답인가**

- C: 기존 서드파티 방화벽 어플라이언스를 계속 사용하고 싶다는 요구를 무시하고 AWS Network Firewall로 완전히 대체하는 것은 요구사항에 맞지 않습니다(다만 서드파티 대신 AWS Network Firewall을 사용하는 경우라면 GWLB 없이도 중앙 검사 VPC 구성이 가능합니다).
- D: NACL은 상태 비저장 IP/포트 필터링만 가능해 침입 탐지/방지 같은 심층 검사 기능을 대체할 수 없습니다.

> 💡 **시험 꿀팁**: 기존 **서드파티 방화벽 어플라이언스**를 활용해 다수 VPC의 트래픽을 **중앙에서 확장 가능하게 검사**하려면 **Gateway Load Balancer + 중앙 검사 VPC + GWLB 엔드포인트 + Transit Gateway 라우팅** 조합이 표준 정답입니다.

- B. **AWS Config의 조직 conformance pack을 관리 계정(또는 위임된 관리자 계정)에서 배포해 조직 내 모든 기존/신규 계정에 동일한 규칙 세트를 자동 적용하고, 준수 현황을 중앙에서 집계.**
- C. Trusted Advisor의 기본 무료 검사 항목만 사용(무료 등급의 Trusted Advisor는 보안 검사 항목이 제한적이며, 커스텀 규칙 정의나 조직 전체 자동 배포 기능을 제공하지 않음).
- D. 각 계정에 Lambda 함수를 배포해 정기적으로 리소스를 스캔하고 위반 시 SNS로 알림(직접 구현/유지해야 하는 부담이 크고, 계정마다 개별 배포해야 해서 신규 계정 자동 적용도 안 됨).

**정답: B**

**해설**
**AWS Config의 조직 conformance pack**은 관리 계정(또는 위임된 관리자)에서 한 번 배포하면, 조직 내 **모든 기존 계정과 향후 추가되는 신규 계정에도 자동으로** 동일한 규칙 세트(관리형 규칙 모음)가 적용되며, 준수 현황을 중앙에서 대시보드로 집계해 확인할 수 있습니다. 이는 다중 계정 환경에서 일관된 컴플라이언스 감사를 자동화하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 계정별 수동 설정과 수작업 취합은 운영 부담이 크고 신규 계정에 자동 적용되지 않습니다.
- C: Trusted Advisor 무료 등급은 검사 항목이 제한적이고, 조직 전체에 커스텀 규칙을 자동 배포하는 기능이 없습니다.
- D: 자체 Lambda 스캐너를 구현/배포하는 것은 AWS Config가 이미 제공하는 기능을 재구현하는 것으로 불필요한 운영 부담을 만듭니다.

> 💡 **시험 꿀팁**: 다중 계정에서 **동일한 컴플라이언스 규칙을 신규 계정까지 자동으로 적용하고 중앙에서 감사**하려면 **AWS Config의 조직 conformance pack**이 표준 정답입니다.

## QUESTION 291

**문제**: 수십 개 VPC에서 각각 개별 NAT Gateway를 운영하며 아웃바운드 인터넷 비용(NAT Gateway 시간당 요금 + 데이터 처리 요금)이 예상보다 훨씬 크게 청구되고 있다. 각 VPC의 아웃바운드 트래픽 요구사항은 유지하면서 NAT 관련 비용을 절감하려면?

**보기**
- A. 각 VPC의 NAT Gateway를 그대로 두고 인스턴스 유형만 축소(NAT Gateway는 관리형 서비스로 인스턴스 유형 개념이 없으며, 비용은 가동 시간과 처리 데이터량 기준이라 이 방법 자체가 성립하지 않음).
- B. **중앙 이그레스(egress) VPC에 하나의 NAT Gateway(또는 소수의 이중화된 NAT Gateway)를 두고, Transit Gateway를 통해 각 스포크 VPC의 아웃바운드 트래픽을 이 중앙 NAT Gateway로 라우팅.**

**정답: B**

**해설**
NAT Gateway별 시간당 요금이 VPC 수만큼 중복해서 발생하는 것이 비용 증가의 핵심 원인입니다. **중앙 이그레스 VPC**에 소수의 NAT Gateway만 배치하고, **Transit Gateway**를 통해 여러 스포크 VPC의 아웃바운드 트래픽을 이 중앙 NAT Gateway로 집중시키면, NAT Gateway 자체의 시간당 요금을 크게 줄이면서도 각 VPC의 아웃바운드 인터넷 접근 요구사항은 그대로 충족할 수 있습니다(데이터 처리 요금은 Transit Gateway 처리 요금과 트레이드오프를 고려해야 함).

**왜 다른 보기는 오답인가**

- C: 프라이빗 리소스에 퍼블릭 IP를 직접 노출하는 것은 보안 모범 사례를 정면으로 위반합니다.
- D: 자체 NAT 인스턴스 운영은 패치, 이중화, 확장성 관리를 직접 수행해야 해서 관리형 NAT Gateway보다 운영 부담이 크고, 처리량 한계도 낮습니다.

> 💡 **시험 꿀팁**: 다수 VPC의 **NAT Gateway 비용을 절감**하려면 **중앙 이그레스 VPC의 NAT Gateway + Transit Gateway 라우팅**으로 집중화하는 것이 표준 정답입니다. 다만 Transit Gateway 자체의 데이터 처리 비용과의 트레이드오프도 함께 고려해야 합니다.

## QUESTION 292

**문제**: 여러 독립된 소비 애플리케이션이 동일한 Kinesis Data Stream을 각자 실시간으로(초 단위 지연 이내) 읽어야 하는데, 소비자 수가 늘어나면서 **각 소비자가 공유 처리량(2MB/s/샤드) 경쟁으로 인한 지연**을 겪고 있다. 소비자별로 전용 처리량을 보장하려면?

**보기**
- A. 샤드 수를 대폭 늘려 전체 스트림 처리량을 증가(샤드를 늘리면 전체 처리량은 늘지만, 여전히 모든 소비자가 샤드당 2MB/s를 공유(polling 방식)해야 해서 소비자가 늘어나면 동일한 경쟁 문제가 재발함).
- B. **Kinesis Data Streams의 향상된 팬아웃(Enhanced Fan-Out)을 사용해 각 소비자를 등록하고, 소비자별로 샤드당 전용 2MB/s 처리량을 HTTP/2 푸시 방식으로 제공.**
- C. 소비자마다 별도의 Kinesis Data Stream을 만들고 프로듀서가 동일 데이터를 각 스트림에 중복 발행(프로듀서 측에서 데이터 중복 발행 로직을 구현/유지해야 해서 복잡도와 비용이 증가하고, 신규 소비자 추가 시마다 프로듀서 수정이 필요).
- D. SQS로 전환해 각 소비자가 개별 큐를 구독(SQS는 표준 발행-구독 팬아웃에 적합하지 않으며, Kinesis 같은 순서 보장 스트리밍 재처리[replay] 기능도 없어 요구사항에 맞지 않음).

**정답: B**

**해설**
**향상된 팬아웃(Enhanced Fan-Out)**을 사용하면 등록된 각 소비자가 폴링 방식이 아닌 **HTTP/2를 통한 푸시** 방식으로 데이터를 받으며, 샤드당 **소비자 각각에게 전용 2MB/s** 처리량이 보장됩니다. 따라서 소비자 수가 늘어나도 소비자 간 처리량 경쟁이 발생하지 않고, 각 소비자가 약 70ms 이내의 낮은 지연시간으로 데이터를 수신할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 표준(폴링) 방식의 소비자는 여전히 샤드당 처리량을 공유하므로, 샤드를 늘려도 소비자 수가 함께 늘면 동일한 경쟁 문제가 반복됩니다.
- C: 스트림을 소비자 수만큼 복제하고 프로듀서가 중복 발행하는 것은 운영/비용 부담이 크고 확장성이 떨어집니다.
- D: SQS는 이 시나리오가 요구하는 다중 소비자의 순서 보장 스트림 재처리에 적합하지 않습니다.

> 💡 **시험 꿀팁**: Kinesis Data Streams에서 **다수의 소비자가 경쟁 없이 각자 전용 처리량으로 저지연 실시간 처리**를 해야 하면 **향상된 팬아웃(Enhanced Fan-Out)**이 표준 정답입니다.

## QUESTION 294

**문제**: 규제 요구사항에 따라 프로덕션 데이터의 백업을 원본 계정/리전과 **분리된 별도의 계정과 리전**에도 보관해야 한다(랜섬웨어나 계정 침해 시에도 백업이 안전해야 함). 여러 AWS 서비스(EBS, RDS, DynamoDB 등)에 걸쳐 이를 중앙에서 관리하고 싶다. 솔루션은?

**보기**
- A. 각 서비스(EBS, RDS, DynamoDB)마다 자체 스냅샷/백업 기능을 사용해 개별적으로 다른 리전에 복사하는 스크립트 작성(서비스마다 개별 스크립트를 구현/유지해야 해서 운영 부담이 크고 중앙 관리가 어려움).
- B. **AWS Backup으로 여러 서비스에 걸친 백업 계획(backup plan)을 중앙에서 정의하고, 크로스 계정·크로스 리전 백업 복사(copy) 규칙을 설정해 별도의 백업 계정/리전으로 자동 복사.**

- D. 프로덕션 계정의 IAM 정책만 강화해 백업 삭제를 막음(동일 계정 내에서의 권한 강화이며, 계정 자체가 침해되면 이 방어도 우회될 수 있어 "별도 계정 보관"이라는 핵심 요구를 충족하지 못함).

**정답: B**

**해설**
**AWS Backup**은 EBS, RDS, DynamoDB 등 여러 AWS 서비스에 걸친 백업을 하나의 **백업 계획(backup plan)**으로 중앙에서 정의할 수 있으며, **크로스 계정/크로스 리전 복사 규칙**을 설정하면 백업이 자동으로 별도의 격리된 백업 계정과 리전으로 복사됩니다. 이를 통해 원본 계정이 랜섬웨어나 침해를 당하더라도 별도 계정의 백업은 안전하게 보호되며, 여러 서비스의 백업을 하나의 콘솔에서 중앙 관리할 수 있습니다.

**왜 다른 보기는 오답인가**
- A, C: 서비스별로 개별 스크립트/수동 프로세스를 구현하는 것은 AWS Backup이 이미 제공하는 중앙화된 정책 관리, 자동화, 모니터링 기능을 재구현하는 것으로 비효율적입니다.
- D: 동일 계정 내 IAM 정책 강화만으로는 계정 자체가 침해될 경우의 리스크를 제거하지 못해 "별도 계정에 보관"해야 한다는 핵심 요구사항을 충족하지 못합니다.

> 💡 **시험 꿀팁**: 여러 AWS 서비스의 백업을 **중앙에서 관리하며 별도 계정/리전으로 자동 격리 복사**하려면 **AWS Backup의 백업 계획 + 크로스 계정/크로스 리전 복사 규칙**이 표준 정답입니다.

**문제**: Java로 작성된 Lambda 함수가 JVM 초기화와 클래스 로딩으로 인해 **콜드 스타트 지연시간**이 커서, 트래픽이 간헐적인 API의 응답 시간이 불안정하다. 프로비저닝된 동시성을 사용하지 않고(추가 상시 비용 없이) 콜드 스타트를 줄이고 싶다. 솔루션은?

- A. 함수 메모리 크기를 최대치로 늘려 CPU 성능 향상(메모리 증가로 실행 성능은 개선될 수 있지만, JVM 초기화 자체의 콜드 스타트 지연 문제를 근본적으로 해결하지는 못함).
- B. **Lambda SnapStart를 활성화해, 함수 배포 시 미리 초기화된 실행 환경의 암호화된 스냅샷을 캐싱해두고, 호출 시 이 스냅샷에서 실행 환경을 빠르게 복원.**
- C. 프로비저닝된 동시성(Provisioned Concurrency)을 상시 최대치로 설정(문제에서 추가 상시 비용 없이 해결하라고 명시했으므로, 상시 비용이 발생하는 프로비저닝된 동시성은 요구사항에 반함).
- D. 함수를 Node.js로 재작성(재작성은 가능한 해결책일 수 있으나, 기존 Java 코드베이스를 그대로 유지하면서 콜드 스타트만 개선하고 싶은 요구에는 SnapStart가 더 직접적인 해법).

**정답: B**

**해설**
**Lambda SnapStart**(Java 기반 런타임 지원)는 함수를 배포할 때 초기화가 완료된 실행 환경의 **암호화된 스냅샷**을 미리 생성해 캐싱해두고, 실제 호출이 발생하면 이 스냅샷에서 실행 환경을 빠르게 복원해 JVM 초기화 등 콜드 스타트 지연을 크게 줄입니다. 프로비저닝된 동시성처럼 대기 상태의 실행 환경을 상시 유지하지 않으므로 추가 상시 비용이 발생하지 않습니다.

**왜 다른 보기는 오답인가**
- A: 메모리를 늘리면 실행 성능은 개선될 수 있지만, 콜드 스타트의 근본 원인인 초기화 과정 자체를 단축하지는 못합니다.
- C: 프로비저닝된 동시성은 효과적이지만 상시 유지 비용이 발생해 "추가 상시 비용 없이"라는 요구를 위반합니다.
- D: 런타임을 통째로 바꾸는 것은 가능한 해결책이지만, 기존 코드베이스 유지를 전제로 한 상황에서는 SnapStart가 더 직접적이고 낮은 리스크의 해법입니다.

> 💡 **시험 꿀팁**: **Java(등) Lambda 함수의 콜드 스타트**를 **추가 상시 비용 없이** 줄이려면 **Lambda SnapStart**가 표준 정답입니다. 상시 비용이 드는 프로비저닝된 동시성과의 차이를 기억하세요.

## QUESTION 296

**문제**: 금융 거래 회사가 TCP 기반의 커스텀 바이너리 프로토콜(비-HTTP)을 사용하는 클라이언트 애플리케이션을 서비스한다. 클라이언트 측 방화벽 화이트리스트 등록을 위해 **고정된 정적 IP 주소**가 필요하며, 전 세계 클라이언트에게 최적의 네트워크 경로를 제공하고 싶다. 솔루션은?

**보기**
- A. Amazon CloudFront를 사용해 정적 IP 제공(CloudFront는 HTTP/HTTPS 콘텐츠 전송에 특화되어 있고 임의의 TCP 바이너리 프로토콜을 지원하지 않으며, 엣지 IP도 광범위해 고정 IP 화이트리스트 요구에 맞지 않음).
- B. **AWS Global Accelerator를 사용해 애플리케이션 앞단에 고정된 Anycast 정적 IP 주소를 할당하고, 클라이언트가 이 IP로 접속하면 AWS 글로벌 네트워크를 통해 가장 가까운 최적 엔드포인트로 라우팅.**
- C. Route 53 지리 근접 라우팅과 각 리전 ALB의 동적 IP를 사용(ALB의 IP는 시간에 따라 변경될 수 있어 고정 IP 화이트리스트 요구를 충족하지 못하고, ALB는 HTTP/HTTPS/TCP 리스너를 지원하지만 임의의 커스텀 TCP 애플리케이션에는 NLB가 더 적합).
- D. 각 리전에 Elastic IP를 가진 EC2 인스턴스를 두고 클라이언트가 가장 가까운 리전을 직접 선택(클라이언트가 수동으로 리전을 선택해야 해서 최적 경로 자동 라우팅이라는 요구를 충족하지 못하고, 리전별로 서로 다른 IP를 화이트리스트에 등록해야 하는 번거로움도 있음).

**정답: B**

**해설**
**AWS Global Accelerator**는 TCP/UDP 트래픽에 대해 **고정된 Anycast 정적 IP 주소**를 제공하며, 클라이언트는 이 하나의 IP로 접속하기만 하면 AWS의 글로벌 백본 네트워크를 통해 자동으로 **가장 가까운 최적의 엔드포인트**(NLB, ALB, EC2 등)로 라우팅됩니다. HTTP가 아닌 임의의 TCP 프로토콜도 지원하므로, 고정 IP 화이트리스트가 필요한 비-HTTP 금융 프로토콜 시나리오에 정확히 맞습니다.

**왜 다른 보기는 오답인가**
- A: CloudFront는 HTTP(S) 콘텐츠 전송 전용이며, 커스텀 TCP 바이너리 프로토콜을 지원하지 않고 고정 IP도 제공하지 않습니다.
- C: ALB의 IP는 가변적이라 화이트리스트 요구에 맞지 않으며, 커스텀 TCP 프로토콜에는 NLB가 더 적합한 리스너를 제공합니다.
- D: 클라이언트가 리전을 직접 선택하고 리전별로 다른 IP를 관리해야 하는 방식은 자동 최적 라우팅과 단일 고정 IP라는 요구를 모두 충족하지 못합니다.

> 💡 **시험 꿀팁**: **비-HTTP TCP/UDP 프로토콜에 고정 정적 IP + 전 세계 최적 경로 라우팅**이 필요하면 **AWS Global Accelerator**가 표준 정답입니다.

## QUESTION 297

**문제**: ECS 클러스터에서 실행되는 애플리케이션의 가용성을 높이기 위해 태스크를 **여러 가용 영역에 고르게 분산**시키고, 평상시에는 비용 절감을 위해 Fargate Spot을 최대한 활용하되 **최소 보장 용량**은 반드시 Fargate On-Demand로 유지하고 싶다. 솔루션은?

**보기**
- A. 태스크 배치 제약 조건(placement constraints) 없이 기본 스케줄링만 사용(기본 스케줄링은 AZ 간 균등 분산을 보장하지 않을 수 있고, Fargate Spot/On-Demand 비율을 세밀하게 제어하는 기능도 없음).
- B. **ECS 서비스에 Fargate와 Fargate Spot 두 가지 용량 공급자(capacity provider)를 연결하고, 용량 공급자 전략(capacity provider strategy)에서 base(최소 보장량)는 Fargate로, weight(나머지 비율)는 Fargate Spot으로 설정. 서비스는 기본적으로 AZ 간 태스크를 분산 배치.**
- C. 모든 태스크를 Fargate Spot으로만 실행(최소 보장 용량 없이 전부 Spot으로 실행하면 대규모 동시 중단(Spot 회수) 시 가용성이 크게 저하될 위험이 있어 "최소 보장 용량"이라는 요구를 충족하지 못함).
- D. EC2 시작 유형으로 전환해 Auto Scaling 그룹의 다중 AZ 배포와 Spot/On-Demand 혼합 인스턴스 정책 사용(EC2 시작 유형으로 전환하면 인스턴스 자체를 직접 관리해야 해서 Fargate의 서버리스 이점을 포기하게 되며, 문제에서 특별히 EC2로 전환할 필요성을 요구하지 않음).

**정답: B**

**해설**
ECS 서비스에서 **용량 공급자 전략(capacity provider strategy)**의 `base` 값으로 Fargate(On-Demand)에 최소 보장 태스크 수를 지정하고, `weight` 값으로 나머지 확장분을 Fargate Spot에 분배하도록 설정하면, 평상시 비용은 Spot 활용으로 절감하면서도 항상 일정 수의 태스크는 안정적인 On-Demand Fargate에서 실행되도록 보장할 수 있습니다. ECS 서비스 스케줄러는 기본적으로 태스크를 여러 AZ에 고르게 분산 배치합니다.

**왜 다른 보기는 오답인가**
- A: 배치 제약 조건이나 용량 공급자 전략 없이는 Spot/On-Demand 비율이나 AZ 분산을 세밀하게 제어할 수 없습니다.
- C: 모든 태스크를 Spot으로만 실행하면 대량 중단 시 최소 가용성을 보장할 수 없어 요구사항을 위반합니다.
- D: EC2 시작 유형으로의 전환은 Fargate의 서버리스 운영 이점을 포기하는 것으로, 이 문제가 요구하지 않는 불필요한 변경입니다.

> 💡 **시험 꿀팁**: ECS에서 **최소 보장 용량은 On-Demand로, 나머지는 저비용 Spot으로** 혼합하려면 **Fargate + Fargate Spot 용량 공급자(base/weight 설정)** 조합이 표준 정답입니다.

## QUESTION 298

**문제**: 회사가 안정적이고 예측 가능한 EC2 사용량(항상 켜져 있는 기준 부하)을 보이지만, 향후 1~2년 내에 **인스턴스 패밀리나 운영체제, 심지어 Fargate/Lambda 같은 다른 컴퓨팅 옵션으로 전환할 가능성**도 열어두고 싶다. 이런 유연성을 유지하면서 최대한의 할인을 받으려면 어떤 약정을 선택해야 하는가?

**보기**
- A. EC2 Instance Savings Plans를 특정 인스턴스 패밀리와 리전에 맞춰 구매(특정 인스턴스 패밀리에 약정이 고정되어, 다른 패밀리나 컴퓨팅 서비스로 전환 시 할인 혜택을 잃게 되어 "유연성 유지"라는 요구에 부합하지 않음).

**왜 다른 보기는 오답인가**
- A: EC2 Instance Savings Plans는 특정 인스턴스 패밀리에 한정되어, 패밀리 변경이나 다른 컴퓨팅 서비스로의 전환 시 할인을 잃을 수 있습니다.
- C, D: 예약 인스턴스(표준/컨버터블) 계열은 EC2(또는 관련 서비스)에 한정되며, 특히 표준 RI는 유연성이 가장 낮고, 컨버터블 RI도 Fargate/Lambda로의 전환 시 할인이 유지되지 않습니다.

> 💡 **시험 꿀팁**: 향후 **인스턴스 패밀리 변경뿐 아니라 Fargate/Lambda 같은 다른 컴퓨팅 옵션으로의 전환 가능성**까지 열어두면서 할인을 받으려면 **Compute Savings Plans**가 표준 정답입니다. 특정 패밀리에 고정되는 EC2 Instance Savings Plans와의 차이를 기억하세요.

## QUESTION 299

**문제**: 중앙 플랫폼 팀이 개발자들에게 셀프서비스로 IAM 역할을 생성할 수 있는 권한을 위임하려 하지만, 개발자가 **자신에게 관리자 권한을 부여하는 등 권한을 상승(privilege escalation)**시키는 것은 막아야 한다. 개발자의 유연성은 유지하면서 권한 상승을 원천 차단하는 방법은?

**보기**
- A. 개발자에게 IAM 역할 생성 권한(iam:CreateRole, iam:AttachRolePolicy 등)만 부여하고 별도 통제 없이 신뢰(권한 상승을 막을 기술적 장치가 없어, 개발자가 의도적/실수로 관리자 정책을 붙인 역할을 만들 위험을 방치함).
- B. **개발자의 IAM 역할 생성 권한에 권한 경계(permissions boundary)를 함께 적용해, 개발자가 생성하는 어떤 역할이라도 이 경계에 정의된 최대 권한을 절대 초과할 수 없도록 강제.**
- C. 개발자의 IAM 콘솔 접근 자체를 차단하고 플랫폼 팀이 모든 역할을 대신 생성(개발자의 셀프서비스 유연성을 완전히 없애는 것으로, "유연성은 유지"라는 요구에 반함).
- D. SCP로 모든 계정에서 iam:CreateRole 자체를 차단(역할 생성 자체를 막아버리면 개발자의 셀프서비스 역할 생성이라는 목적을 달성할 수 없음).

**정답: B**

**해설**
**IAM 권한 경계(permissions boundary)**는 개발자가 생성할 수 있는 IAM 역할/사용자의 **최대 허용 권한 상한선**을 정의하는 고급 기능입니다. 개발자에게 역할 생성 권한을 주되, 반드시 특정 권한 경계를 첨부하도록 정책 조건을 강제하면, 개발자가 아무리 광범위한 권한(심지어 관리자 정책)을 역할에 붙이려 해도 실제 유효 권한은 권한 경계를 절대 벗어날 수 없습니다. 이는 셀프서비스의 유연성과 권한 상승 방지를 동시에 달성하는 표준 패턴입니다.

**왜 다른 보기는 오답인가**
- A: 기술적 통제 없이 신뢰에만 의존하는 것은 권한 상승 위험을 그대로 방치하는 것입니다.
- C: 개발자의 셀프서비스 권한을 완전히 제거하는 것은 유연성 유지 요구와 정면으로 배치됩니다.
- D: 역할 생성 자체를 SCP로 전면 차단하면 개발자가 아예 역할을 만들 수 없게 되어 셀프서비스라는 목적을 달성하지 못합니다.

> 💡 **시험 꿀팁**: 사용자에게 **IAM 역할/정책 생성을 위임하면서도 권한 상승을 방지**하려면 **권한 경계(permissions boundary)**를 함께 강제하는 것이 표준 정답입니다.

## QUESTION 300

**문제**: 회사가 서드파티 SaaS 벤더가 PrivateLink로 제공하는 API를 VPC 내부 리소스에서 사용하려 한다. 애플리케이션 코드는 이미 SaaS의 공개 도메인 이름(예: api.saas-vendor.com)으로 하드코딩되어 있으며, 코드 변경 없이 이 도메인으로의 요청이 자동으로 PrivateLink를 경유하도록 하고 싶다. 솔루션은?

**보기**
- A. VPC 인터페이스 엔드포인트만 생성하고 애플리케이션 코드를 엔드포인트 고유 DNS 이름을 사용하도록 전부 수정(코드 변경이 필요해 "코드 변경 없이"라는 요구에 반함).
- B. **VPC 인터페이스 엔드포인트를 생성하면서 프라이빗 DNS(private DNS) 옵션을 활성화해, SaaS의 원래 공개 도메인 이름이 VPC 내부에서 자동으로 엔드포인트의 프라이빗 IP로 해석되도록 구성.**
- C. Route 53 퍼블릭 호스팅 영역에 SaaS 도메인과 동일한 이름의 레코드를 만들어 엔드포인트 IP로 재정의(SaaS 벤더가 소유한 퍼블릭 도메인을 자체적으로 재정의할 수 없으며, 이는 DNS 스푸핑에 해당해 기술적으로도 불가능/부적절함).
- D. 온프레미스 DNS 서버에만 이 도메인에 대한 재정의 레코드를 추가(문제의 시나리오는 VPC 내부 리소스가 사용하는 것이므로 온프레미스 DNS 변경은 VPC 내부 트래픽 경로에 영향을 주지 못함).

**정답: B**

**해설**
VPC 인터페이스 엔드포인트 생성 시 **프라이빗 DNS(private DNS)** 옵션을 활성화하면, AWS가 해당 서비스의 **원래 공개 도메인 이름**을 VPC 내부에서 자동으로 인터페이스 엔드포인트의 프라이빗 IP 주소로 해석(resolve)되도록 Route 53 프라이빗 호스팅 영역을 자동 구성합니다. 따라서 애플리케이션은 기존에 하드코딩된 공개 도메인 이름을 그대로 사용하면서도, 실제 트래픽은 코드 변경 없이 자동으로 PrivateLink를 경유하게 됩니다.

**왜 다른 보기는 오답인가**
- A: 엔드포인트 전용 DNS 이름으로 코드를 수정하는 것은 "코드 변경 없이"라는 핵심 요구를 위반합니다.
- C: 다른 조직(SaaS 벤더)이 소유한 퍼블릭 도메인을 자체적으로 재정의하는 것은 불가능하며 시도해서도 안 됩니다.
- D: 온프레미스 DNS 설정 변경은 VPC 내부 리소스의 이름 해석에 영향을 주지 않습니다.

> 💡 **시험 꿀팁**: PrivateLink 인터페이스 엔드포인트를 사용하면서 **애플리케이션 코드 변경 없이 기존 공개 도메인 이름이 자동으로 프라이빗 IP로 해석**되게 하려면, 엔드포인트 생성 시 **프라이빗 DNS(private DNS)** 옵션을 활성화하는 것이 표준 정답입니다.
