## QUESTION 341

**Question**: A financial data company must distribute real-time quote data to **hundreds of VPCs simultaneously** (separated per customer) with low latency. Configuring an individual connection per VPC carries too much operational overhead. What's the solution for efficiently broadcasting the same data stream from one source to many VPCs?

**Choices**
- A. Place an individual NLB per VPC and repeatedly unicast the same data (bandwidth and operational burden grow proportionally with the number of VPCs, since the same data must be sent repeatedly per VPC).
- B. **Configure Transit Gateway multicast, registering multiple VPCs as members of a single multicast group; the source sends data only once, and Transit Gateway efficiently replicates and delivers it to all registered VPCs.**
- C. Place an S3 bucket storing the same data in each VPC and continuously poll it (polling-based S3 lookups aren't suited to real-time, low-latency broadcast, and each VPC repeatedly polling is inefficient).
- D. Connect every VPC to every other VPC individually via peering to broadcast messages (full-mesh peering across hundreds of VPCs grows the number of connections to manage exponentially — impractical).

**Correct Answer: B**

**Explanation**
**Transit Gateway multicast** lets you register multiple VPCs (their subnets) as members of a single multicast group; when the source sends data to the multicast group **only once**, Transit Gateway **efficiently replicates and delivers it to every registered member VPC**. This lets you broadcast the same real-time data to many VPCs with low latency, with no individual unicast connections or full-mesh peering needed — the standard approach optimized for distributing data to a large number of VPCs.

**Why the other choices are wrong**
- A: Repeated unicast transmission grows bandwidth and operational burden proportionally with the number of VPCs.
- C: Polling-based S3 lookups lack real-time-ness and incur inefficiency from repeated polling.
- D: Full peering (mesh topology) across hundreds of VPCs grows the number of connections exponentially — impractical.

> 💡 **Exam tip**: To **broadcast the same data from one source to many VPCs with low latency**, **Transit Gateway multicast** is the standard answer.

## QUESTION 342

**Question**: A healthcare company is developing an application that processes patients' sensitive personal health information (PHI). This processing logic must run in an **isolated compute environment that no one — including AWS operators — can access (not even via administrative or SSH access) while data is being processed**, with no external network or persistent storage access. What's the solution?

**Choices**
- A. Run it on a standard EC2 instance and deny access to all users via an IAM policy (an IAM policy can restrict other IAM users' access, but this isn't hardware-level isolation of the instance itself, and someone with instance-management permissions can still access it through various paths).
- B. **Use AWS Nitro Enclaves to run the sensitive-data processing logic in an isolated compute environment (an enclave) separated from the EC2 instance. The enclave has no persistent storage, no interactive access, and no external network access, communicating with the parent instance only via a secure local channel.**
- C. Deploy dedicated hardware on AWS Outposts for a physically isolated environment (Outposts extends on-premises hardware, but doesn't provide the hardware-level, cryptographically attested isolation guaranteeing "no one, including AWS operators, can access" — Nitro Enclaves is specifically built for this cloud-native isolated-compute requirement).
- D. Process the data within a Lambda function and remove VPC connectivity (Lambda doesn't provide fine-grained execution-environment attestation or a parent-enclave communication model; Nitro Enclaves is the standard for a scenario requiring this level of strict isolation guarantee).

**Correct Answer: B**

**Explanation**
**AWS Nitro Enclaves** provides a fully isolated compute environment with CPU and memory separated from the EC2 instance. The enclave has **absolutely no persistent storage, interactive access (SSH, etc.), or external network connectivity**, and communicates with the parent EC2 instance only through a secure local channel (vsock). It also offers **cryptographic attestation** to verify that the code running in the enclave hasn't been tampered with — ideal for processing extremely sensitive data (PHI, PII, cryptographic key handling, etc.) that no one, including AWS operators, should be able to access.

**Why the other choices are wrong**
- A: An IAM policy only restricts other IAM principals' access — it doesn't categorically block access at the hardware level by someone with instance-management permissions.
- C: Outposts extends AWS infrastructure on-premises, but doesn't itself provide the isolated compute environment (fully blocked interactive/network/storage access) this question requires.
- D: Lambda doesn't provide this level of strict isolation attestation or communication model.

> 💡 **Exam tip**: To process extremely sensitive data in an **isolated environment no one — including AWS operators — can access**, **AWS Nitro Enclaves** is the standard answer.

## QUESTION 343

**Question**: A company is preparing to migrate dozens of servers via AWS Application Migration Service (MGN), and before the actual production cutover, wants to verify **without impacting the source servers** that the replicated target instance boots correctly and the application works. What's the solution?

**Choices**
- A. Proceed directly with the actual cutover and roll back if there's a problem (proceeding straight to cutover without prior verification carries high production-impact risk — the opposite of the "verify without impacting the source" requirement).
- B. **Use MGN's test launch feature to temporarily launch a target instance in an isolated network environment while keeping continuous replication running, verify it, then terminate the test instance when done (no impact on the source server or the actual replication process).**
- C. Temporarily shut down the source server and check that the replica works (shutting down the source server directly contradicts the "without impacting the source server" requirement).
- D. Manually export the replicated snapshot to a separate AWS account and build a separate test environment (unnecessarily complex and inefficient given MGN's built-in test launch feature already exists).

**Correct Answer: B**

**Explanation**
**AWS MGN's test launch** feature lets you temporarily launch a target instance in an isolated (non-production) network — while continuous data replication keeps running — to verify the application works correctly, all without an actual cutover. This process has zero impact on the source server or the replication pipeline; once testing is done, the test instance is cleaned up and the actual cutover can be performed separately later.

**Why the other choices are wrong**
- A: Proceeding straight to cutover without prior verification fails to achieve the "prior verification" goal this question requires.
- C: Shutting down the source server violates the core "without impacting the source" requirement.
- D: Manually building a separate environment is unnecessary duplication given MGN's built-in test launch feature.

> 💡 **Exam tip**: To **verify a target instance before the actual cutover without impacting the source** in an MGN migration, the **test launch** feature is the standard answer.

## QUESTION 344

**Question**: A company wants an Aurora MySQL database to have a **read-only replica** in another Region purely to serve low-latency reads to users there — they don't need **write promotion or disaster-recovery capability** in that Region (they already have a separate backup-based DR strategy). What's the cost-minimizing way to meet this?

**Choices**
- A. **Create a standard Aurora MySQL cross-Region read replica to handle read traffic from the other Region.**
- B. Set up Aurora Global Database with a read replica in the secondary Region (Global Database uses dedicated replication infrastructure for extra features like fast disaster recovery [sub-minute promotion], costing more than a standard cross-Region read replica — overkill for this simple read-latency-improvement goal with no DR need).
- C. Use DMS to continuously replicate data into a separate Aurora cluster in another Region (DMS-based continuous replication carries heavier management overhead and higher latency than Aurora's native cross-Region replication — overly complex for this simple requirement).
- D. Create a fully independent second Aurora cluster in another Region and implement dual writes at the application level (dual-write implementation is far too complex in data-consistency management terms for a simple read-latency-improvement goal).

**Correct Answer: A**

**Explanation**
A **standard Aurora cross-Region read replica** precisely fits the goal of serving low-latency reads from another Region, and is **cheaper** since it doesn't use the dedicated replication infrastructure (extra cost) Aurora Global Database uses for fast disaster recovery. As in this question, if a separate DR strategy already exists and you simply want to improve read latency, a standard cross-Region read replica is the more cost-effective choice than Global Database, which offers more features (fast failover, etc.) at higher cost.

**Why the other choices are wrong**
- B: Global Database includes fast-disaster-recovery capability this question doesn't need, making it overkill for the cost.
- C: Separate replication via DMS carries heavier management burden and is less efficient than Aurora's native replication.
- D: Application-level dual writes are excessively complex and risky for this simple requirement.

> 💡 **Exam tip**: To simply **improve cross-Region read latency with no disaster-recovery need**, a **standard Aurora cross-Region read replica** is the cost-effective standard answer — reserve Aurora Global Database for when fast failover is actually needed.

## QUESTION 345

**Question**: A company purchased a 3-year, full-upfront Standard Reserved Instance for a specific instance family, but a business pivot means that instance family is no longer needed. They want to minimize the financial loss on the remaining commitment term. What action should they take?

**Choices**
- A. Just leave the Reserved Instance unused (the purchase cost is already prepaid, so not using it doesn't get refunded — it just remains a sunk loss, not helping minimize loss).
- B. **Sell the Reserved Instance's remaining term to a third party on the AWS Reserved Instance Marketplace.**
- C. Request a refund from AWS support (Standard RIs generally aren't eligible for arbitrary refunds under AWS's standard policy — selling via the RI Marketplace is the standard remedy).
- D. Request conversion to a Convertible Reserved Instance (there's no feature to convert an already-purchased Standard RI into a Convertible RI after the fact, and even if converted, it would still be tied to an EC2 commitment, not solving the root problem of "no longer needing this family").

**Correct Answer: B**

**Explanation**
The **AWS Reserved Instance Marketplace** is the official channel for **selling the remaining term** of a Standard Reserved Instance that's no longer needed, to a third party. This recovers part of the prepaid cost, minimizing financial loss compared to letting it sit unused.

**Why the other choices are wrong**
- A: Leaving it unused recovers none of the already-paid cost — the loss remains as-is.
- C: Standard RIs generally aren't eligible for arbitrary refunds — Marketplace sale is the standard loss-minimization method.
- D: There's no feature to convert an already-completed Standard RI purchase into a Convertible RI after the fact, and conversion itself wouldn't solve the root problem of "no longer needing this family."

> 💡 **Exam tip**: To minimize loss on the remaining term of a **Standard RI that's no longer needed**, selling it on the **AWS Reserved Instance Marketplace** is the standard answer.

## QUESTION 346

**Question**: A mobile game's in-app purchase verification workflow is invoked tens of thousands of times per second, with each execution being a short task finishing within seconds. There's no strong need to retain detailed state-transition history, and **very high throughput and low cost** are the key priorities. What workflow type in AWS Step Functions fits this workload?

**Choices**
- A. Use a Standard Workflow (Standard Workflows are optimized for durable execution-history tracking that can run up to a year, but for very high throughput [tens of thousands per second], per-state-transition billing is relatively costly and startup is slower than Express).
- B. **Use an Express Workflow, optimized for short, high-throughput event processing, with billing based on execution duration/memory to save cost.**
- C. Reimplement using individual SQS queues and Lambda instead of Step Functions (gives up Step Functions' workflow visualization, error handling, and retry features, requiring self-implementation — unnecessarily complex).
- D. Implement all logic sequentially in one large Lambda function with no workflow (viable, but Step Functions Express is better suited to managing clear multi-step state transitions and retry/error handling, and the question itself presupposes using Step Functions).

**Correct Answer: B**

**Explanation**
**Express Workflows** are optimized for **high event throughput** — tens of thousands per second or more — and **short duration** (up to 5 minutes), and unlike Standard Workflows, are billed based on **execution duration and memory usage**, making them far more cost-effective for this kind of high-frequency, short-duration workload. It precisely fits this scenario, where detailed execution-history retention isn't mandatory (logging is optional).

**Why the other choices are wrong**
- A: Standard Workflows are optimized for long-running execution and complete execution-history tracking (auto-retained up to 90 days) — its per-state-transition billing model gets expensive for a very high-throughput, short workload.
- C, D: Giving up Step Functions' visual workflow management and retry/error-handling features to self-implement adds unnecessary complexity.

> 💡 **Exam tip**: For a workflow needing **very high throughput + short duration**, **Step Functions Express Workflows** is the standard answer; use Standard Workflows when long-running execution and complete execution history matter.

## QUESTION 347

**Question**: The security team wants to copy network traffic to/from specific EC2 instances to a third-party intrusion detection system (IDS) appliance for deep packet inspection **without affecting the original traffic**. How do you get a copy of the traffic with no application code changes?

**Choices**
- A. Log every request/response in the application code and send it to the IDS (requires application code changes, contradicting the requirement, and doesn't cover all network-layer traffic including non-HTTP).
- B. **Configure VPC Traffic Mirroring to copy traffic from a source ENI, with no impact on the original, and deliver it to a target (an ENI, an NLB, etc.) where the IDS appliance sits.**
- C. Enable VPC Flow Logs and analyze with the IDS (Flow Logs only provide traffic metadata [source/destination IP, port, etc.] and don't include the actual packet payload — unsuitable for deep packet inspection).
- D. Reconfigure route tables so all traffic must inline traverse the IDS appliance (an inline approach can affect actual traffic flow if the IDS fails — a mirroring approach that copies traffic is more suitable for the "without affecting the original traffic" requirement).

**Correct Answer: B**

**Explanation**
**VPC Traffic Mirroring** copies network traffic to/from a specified source (ENI) **with zero impact on the original flow**, delivering it to another ENI or a security appliance (IDS/IPS, etc.) behind an NLB. This gets a copy of traffic at the network layer with no application code changes, and is the standard approach for security-monitoring scenarios requiring deep packet inspection.

**Why the other choices are wrong**
- A: Requires application code changes and doesn't cover all network-layer traffic.
- C: VPC Flow Logs only provide metadata, not the packet payload itself, so they can't be used for deep packet inspection (DPI).
- D: An inline approach forces the actual traffic flow to pass through the IDS, which can affect the real service if the IDS fails — mismatched with the "no impact on the original" requirement.

> 💡 **Exam tip**: To deliver a copy of network traffic to a third-party IDS/security appliance for deep packet inspection **with no impact on the original traffic**, **VPC Traffic Mirroring** is the standard answer.

## QUESTION 348

**Question**: A company needs shared application data stored on an EFS file system to be **quickly recoverable in another Region** in the event of a Regional disaster. The RPO must be within a few minutes, and they don't want to implement the migration process themselves in scripts. What's the solution?

**Choices**
- A. Back up EFS to an S3 bucket in another Region every night (a daily backup has an RPO of up to 24 hours, far short of the "within a few minutes" requirement).
- B. **Use the EFS Replication feature to automatically maintain a read-only replica file system in another Region, and fail over the replica to a writable state during a disaster.**
- C. Schedule a DataSync task to run every few hours, syncing to EFS in another Region (scheduled DataSync sync is also viable, but EFS's native replication feature provides a much shorter RPO [typically within minutes] automatically, with no need to manage scripts/jobs yourself — simpler).
- D. Implement a cron job on each EC2 instance to directly rsync files to EFS in another Region (requires implementing/managing a custom script, contradicting the "don't want to implement this myself" requirement).

**Correct Answer: B**

**Explanation**
**EFS Replication** is a fully managed feature that continuously replicates changes from a source EFS file system to a target file system in another Region (or another AZ in the same Region), **automatically, typically with an RPO within minutes**. During a disaster, the target file system can be failed over to a writable state in just a few steps, achieving short-RPO cross-Region DR with no need to manage separate backup scripts or DataSync jobs.

**Why the other choices are wrong**
- A: Daily backups have an RPO of up to 24 hours, far short of the requirement.
- C: Scheduled DataSync sync is viable, but EFS's native replication automatically provides a shorter RPO with less management burden — the more standard choice.
- D: A custom script implementation clearly contradicts the "don't want to implement this myself" requirement.

> 💡 **Exam tip**: For **short-RPO cross-Region disaster recovery** of an EFS file system with no self-implementation, the **EFS Replication** feature is the standard answer.

## QUESTION 349

**Question**: A large-scale genomics simulation job runs for hours, building up computation state in memory. To save cost, they want to shut down the instance when the job is idle (e.g., overnight), but **rebuilding the in-memory computation state from scratch is very costly** (taking hours) when restarting. How do you keep the memory state intact across a stop/resume cycle?

**Choices**
- A. Stop and then start the instance (standard EC2 stop/start doesn't preserve RAM content — memory is reset on restart, requiring the application to rebuild its computation state from scratch).
- B. **Configure an instance type that supports EC2 Hibernate and enable the hibernation option, so on stop the RAM content is saved to the EBS root volume, and on start the saved memory state is restored, letting the application resume immediately from where it left off.**
- C. Never stop the instance and keep it running continuously (abandons the cost-saving goal — cost continues to accrue during idle time).
- D. Rewrite the application to save a checkpoint to disk periodically and restore from it on restart (a viable alternative, but requires a significant redesign/rewrite burden; hibernation achieves the same effect without this redesign).

**Correct Answer: B**

**Explanation**
**EC2 Hibernate**, on a supported instance type, **saves the RAM content in encrypted form to the EBS root volume** when the instance is stopped, and **restores the saved memory state** when the instance is started — letting execution resume immediately from where it left off, with no OS boot or application re-initialization needed. This saves cost during idle time (no instance charge, only EBS storage cost) while preserving the long-to-rebuild computation state held in memory.

**Why the other choices are wrong**
- A: Standard stop/start doesn't preserve memory content, requiring the application to rebuild state from scratch.
- C: Keeping it running continuously abandons the cost-saving goal entirely.
- D: A custom checkpoint implementation is valid but requires an application redesign — a heavier development burden than the infrastructure-level hibernation feature.

> 💡 **Exam tip**: To **preserve an instance's memory (RAM) state** across a stop and resume, **EC2 Hibernate** is the standard answer.

## QUESTION 350

**Question**: An e-commerce site is troubled by **scraper bots** that look like normal users but continuously scrape product prices, and bots that auto-add items to carts to hoard inventory (scalping). Simple IP-based blocking or rate-based rules alone struggle to filter out these sophisticated bots. What AWS WAF capability specializes in handling this kind of sophisticated bot traffic?

**Choices**
- A. Use only the WAF Amazon IP reputation list rule (blocking based on known-malicious IP lists is useful, but doesn't comprehensively detect sophisticated scraper/scalping bots that use new IPs or disguise themselves as normal traffic).
- B. **Enable AWS WAF Bot Control, which classifies known good/bad bots and detects sophisticated automated traffic like scrapers and scalping bots via browser fingerprinting and behavioral pattern analysis (using a managed rule group and CAPTCHA/Challenge actions).**
- C. Only finely tune rate-based rules (rate-based rules are effective at detecting a burst of requests in a short time, but don't filter out bots that operate at a normal rate while sophisticatedly mimicking human behavior).
- D. Require login for all users, blocking anonymous access (forcing login for all browsing/purchasing on an e-commerce site significantly hurts user experience, and bots can also create accounts and log in — not a fundamental solution).

**Correct Answer: B**

**Explanation**
**AWS WAF Bot Control** is a managed rule group that distinguishes known good bots (search-engine crawlers, etc.) from bad bots, and detects sophisticated automated traffic disguised to act like a human — like scraper or scalping bots — through browser fingerprinting and behavioral pattern analysis. Detected bot traffic can be handled with various response actions — block, CAPTCHA, or Challenge (JavaScript-based verification) — making it the standard solution specialized for sophisticated bot threats that simple IP/rate-based rules struggle to catch.

**Why the other choices are wrong**
- A: IP reputation lists are useful for known malicious IPs but don't cover sophisticated, newly disguised bots.
- C: Rate-based rules specialize in detecting burst traffic and don't filter out low-rate, human-mimicking bots.
- D: Forcing login for everything hurts user experience, and bots can create accounts too — not a fundamental fix.

> 💡 **Exam tip**: To detect/block **sophisticated automated traffic like scraper and scalping bots**, **AWS WAF Bot Control** is the standard answer.

## QUESTION 351

**Question**: Several teams exchange streaming data via Kafka (MSK) and Kinesis, but whenever a producer changes an event schema, backward compatibility breaks, causing frequent parsing errors in consumer applications. They want to manage schema versions centrally and **enforce compatibility rules (backward/forward compatibility)**. What's the solution?

**Choices**
- A. Have each team document schemas on a wiki and review manually (a manual process has no enforcement power and can't prevent a deployment that accidentally breaks compatibility).
- B. **Use AWS Glue Schema Registry to centrally version-manage event schemas for Kafka/Kinesis streams, and configure a compatibility mode (backward, forward, full, etc.) so registering a schema that violates compatibility is itself blocked.**
- C. Send all events as schemaless JSON and have consumers parse them as best they can (abandons schema enforcement entirely, failing to address the root cause — the lack of enforced compatibility rules).
- D. Create a new Kafka topic/Kinesis stream every time the schema changes, separate from the old version (creating new topics burdens both producers and consumers with ongoing migration, and isn't itself a schema versioning or compatibility-enforcement mechanism).

**Correct Answer: B**

**Explanation**
**AWS Glue Schema Registry** is a service for centrally registering and version-managing event schemas for streaming data like Kafka (MSK) and Kinesis Data Streams. Setting a **compatibility mode** (BACKWARD, FORWARD, FULL, etc.) means that **registration itself is rejected** if a new schema violates that compatibility rule — preventing a producer from accidentally deploying a schema change that breaks consumers.

**Why the other choices are wrong**
- A: Manual documentation/review has no enforcement power and can't categorically prevent mistakes.
- C: Abandoning schema enforcement doesn't address the root cause and shifts parsing-error risk onto consumers.
- D: Creating a new topic/stream every time only adds migration burden and isn't itself a schema-compatibility-enforcement feature.

> 💡 **Exam tip**: To **centrally version-manage streaming event schemas and enforce compatibility rules**, **AWS Glue Schema Registry** is the standard answer.

## QUESTION 352

**Question**: A company needs to provide thousands of remote employees secure access to VPC-internal resources. Their existing hardware VPN appliance lacks scalability. They want **certificate-based mutual authentication** and a managed solution that automatically integrates with VPN client software on connection. What's the solution?

**Choices**
- A. Install OpenVPN directly on several On-Demand EC2 instances to build a custom VPN server farm (building/operating this yourself requires handling patching, scaling, and high availability directly — heavy operational burden, and not a managed service).
- B. **Use AWS Client VPN to set up a managed client-based VPN endpoint, and configure mutual TLS authentication using client certificates issued by ACM Private CA.**
- C. Configure Site-to-Site VPN individually for each employee's home (Site-to-Site VPN is designed for network-to-network connections — configuring it individually for thousands of individual remote users is impractical).
- D. Configure AWS Direct Connect as an individual circuit to each employee's home (Direct Connect is a dedicated-circuit, fixed-location connection — entirely unsuitable in cost and setup time for connecting thousands of individual remote workers).

**Correct Answer: B**

**Explanation**
**AWS Client VPN** is a fully managed client-based VPN service that lets users securely connect to a VPC (and on-premises networks) via OpenVPN-based client software. Configuring **mutual TLS authentication** using client certificates issued by **ACM Private CA** lets each user authenticate strongly with a unique certificate, while certificate issuance/distribution/revocation is managed centrally. Auto-scaling is also handled in a managed way, suitable for supporting thousands of remote workers.

**Why the other choices are wrong**
- A: Building your own OpenVPN server carries heavy operational burden — patching, scalability, and high availability must be managed yourself.
- C, D: Site-to-Site VPN and Direct Connect are optimized for network-to-network (fixed-location) connections, unsuitable for this scenario targeting thousands of individual remote users.

> 💡 **Exam tip**: To provide many **remote employees VPC access with certificate-based mutual authentication**, **AWS Client VPN (with ACM Private CA-based mTLS)** is the standard answer.

## QUESTION 353

**Question**: After running a large-scale heterogeneous database migration (Oracle → Aurora PostgreSQL) via DMS, they want to automatically verify **that the source and target data actually match exactly** (row counts, and the values themselves) before cutover, without writing a separate verification script themselves. What's the solution?

**Choices**
- A. Just run SELECT COUNT(*) on both source and target and compare row counts (matching row counts alone can't catch value-level mismatches like corrupted character encoding or type-conversion errors — incomplete verification).
- B. **Enable DMS's data validation feature, so DMS automatically compares source and target data row-by-row and column-by-column, reporting any mismatches found.**
- C. Write a custom script that reads all the data into an application and compares it directly in memory (reading all large-volume data into application memory for comparison is inefficient, and the burden of building a separate script remains).
- D. Manually eyeball a random sample of 100 rows in the target database (sampling-based manual review can't guarantee exact matching of the full dataset — not a reliable verification method for a large-scale migration).

**Correct Answer: B**

**Explanation**
Enabling **AWS DMS's data validation** feature on a migration task has DMS **automatically compare source and target data row-by-row and column-by-column**, during or after replication, detecting and reporting any value mismatches. This lets you reliably verify data accuracy for a large-scale heterogeneous migration using DMS's own built-in feature, with no separate verification script to write or maintain.

**Why the other choices are wrong**
- A: Comparing only row counts is incomplete verification that can't catch individual value corruption or conversion errors.
- C: A custom comparison script is inefficient for large data volumes and also contradicts the "don't want to write this myself" requirement.
- D: Sampling-based manual review isn't a reliable method for guaranteeing exact matching of the full dataset.

> 💡 **Exam tip**: To **automatically verify exact source-target data matching** in a DMS migration with no custom script, DMS's **data validation** feature is the standard answer.

## QUESTION 354

**Question**: A small startup wants to **simply** have multiple Region endpoints for its web application returned to clients on a rotating basis — **without sophisticated automatic failover logic** — while automatically excluding any endpoint that fails a health check. What's the simplest way to do this without configuring a complex weighted/latency-based routing policy?

**Choices**
- A. Set a weighted routing policy to 50/50 and attach a health check to each record (weighted routing is viable, but requires managing a weight value per record — slightly more setup than the "simplest" approach this question wants).
- B. **Use Route 53 multivalue answer routing, registering multiple IP addresses on the record with a health check attached to each. Route 53 randomly includes up to 8 healthy records in each response.**
- C. Use a failover routing policy with explicit primary/secondary designation (failover routing suits an active-passive structure — different from this question's simpler, round-robin-like requirement of rotating among multiple endpoints simultaneously).
- D. Use latency-based routing to route users to the nearest Region (latency-based routing is valid but serves a different purpose [latency optimization] than this question's "simplest health-based multi-endpoint response with no sophisticated logic" goal).

**Correct Answer: B**

**Explanation**
**Route 53 multivalue answer routing** lets you register multiple IP addresses (each with its own health check) on a single record; for each DNS query, Route 53 responds with **up to 8 randomly chosen healthy records**. With no need to configure sophisticated policies like weights or latency, this is the simplest way to get both simple client-side load distribution across multiple endpoints and automatic health-based exclusion of unhealthy endpoints.

**Why the other choices are wrong**
- A: Weighted routing is also viable but requires specifying/managing weight values — slightly more setup than multivalue answer.
- C: Failover routing specializes in an active-passive primary/secondary structure, different from this requirement of rotating among multiple endpoints simultaneously.
- D: Latency-based routing's purpose is latency optimization, different from this question's "simplest multi-endpoint, health-based response" goal.

> 💡 **Exam tip**: To simply **rotate among multiple healthy endpoints while automatically excluding unhealthy ones**, with no complex policy, **Route 53 multivalue answer routing** is the standard answer.

## QUESTION 355

**Question**: A large enterprise operates a multi-account landing zone via Control Tower, and wants to provision new accounts not through console clicks but via a **code-managed pipeline (GitOps style)**, with post-creation customization (additional IAM roles, networking, etc.) also automatically applied via Terraform. What's the solution?

**Choices**
- A. Keep using Control Tower's Account Factory manually in the console, and manually run Terraform separately after creation (manual intervention still remains in both account creation and customization, not fully meeting the "code-managed pipeline" requirement).
- B. **Deploy Control Tower's Account Factory for Terraform (AFT), managing new account requests as Terraform code (in a Git repository), and configure a pipeline so post-creation customization (a per-account customization pipeline) is also automatically applied via Terraform.**
- C. Use only Service Catalog to create accounts with no post-creation customization (Service Catalog can provision accounts, but AFT is the more specialized standard solution for the Terraform-based, codified account creation and automated post-creation customization this question requires).
- D. Manually create a CloudFormation stack one by one in the console for each new account (manual individual execution directly contradicts the "code-managed pipeline" GitOps requirement).

**Correct Answer: B**

**Explanation**
**Account Factory for Terraform (AFT)** integrates with AWS Control Tower to let you define and manage new-account provisioning requests **as Terraform code via a Git repository (GitOps)**. After an account is created, per-account customization (IAM roles, networking, SCPs, etc.) can also be applied via an **automated Terraform pipeline** — the standard way to manage a multi-account landing zone's account lifecycle entirely code-based, with no console clicks.

**Why the other choices are wrong**
- A: Manual steps still remain in both account creation and customization, failing to meet a fully code-based pipeline requirement.
- C: Service Catalog is useful for provisioning, but AFT is more specialized for the Terraform-based codification and automated customization pipeline this question specifies.
- D: Manual individual stack creation in the console is the opposite of a GitOps/code-based management requirement.

> 💡 **Exam tip**: To **automate account provisioning and post-creation customization via Terraform/GitOps** in a Control Tower environment, **Account Factory for Terraform (AFT)** is the standard answer.

## QUESTION 357

**Question**: A company wants to restrict access from VPC-internal resources to S3, via a VPC gateway endpoint, to only **specific company-approved buckets** (to prevent an employee mistake or compromised credential from leaking data to an arbitrary public S3 bucket not owned by the company). Separate from bucket policies, how do you add an extra defensive layer at the VPC level?

**Choices**
- A. Specify only allowed bucket ARNs in each IAM user/role's policy (an IAM policy alone still allows access to other buckets if there's an over-privileged credential or a policy mistake — doesn't meet the requirement for an additional VPC-level defensive layer).
- B. **Attach an endpoint policy to the S3 VPC gateway endpoint, restricting S3 access through this endpoint to only a company-approved list of specific bucket ARNs.**
- C. Control S3-related traffic with NACL rules (NACLs only support IP/port-based filtering and have no feature to control access at the level of a specific S3 bucket — since the S3 gateway endpoint uses AWS-owned IP ranges, distinguishing specific buckets via NACL is effectively impossible).
- D. Block all S3 access and allow exceptions case by case as needed (impractically heavy management burden, requiring an exception process even for normal, necessary business access).

**Correct Answer: B**

**Explanation**
Attaching an **endpoint policy** to the S3 **VPC gateway endpoint** lets you explicitly restrict which buckets are accessible for every S3 request made through that endpoint. This is a **network-path-level defensive layer** separate from IAM policies (identity-based), so even if there's a mistake in an IAM policy or a credential is compromised, S3 access via the VPC is still forced to the approved bucket list — blocking data leakage to an arbitrary bucket not owned by the company, as a defense-in-depth measure.

**Why the other choices are wrong**
- A: An IAM policy alone can still be bypassed by another policy (e.g., an administrator policy) or a mistake, failing to meet the requirement for a separate VPC-level layer.
- C: NACLs are IP/port-based and can't be used to control access at the level of a specific bucket for an AWS-managed service like S3.
- D: A block-everything-then-allow-exceptions approach carries impractically heavy management burden.

> 💡 **Exam tip**: To add an extra defensive layer restricting VPC-to-S3 access to only **approved specific buckets**, an **endpoint policy on the S3 VPC gateway endpoint** is the standard answer.

## QUESTION 358

**Question**: A company wants to expose a legacy authentication service running in an on-premises data center — without migrating it to AWS — so that **multiple applications inside a VPC can access it privately**. It must avoid the internet, and on the VPC side, they want access to feel as simple as a native AWS service via an interface endpoint. They're already connected to on-premises via Direct Connect. What's the solution?

**Choices**
- A. Just configure the VPC route table to route directly to the on-premises authentication service's IP (direct routing is viable, but for the "access like a native AWS service via a simple interface endpoint" requirement, and for fine-grained access control across multiple VPCs/accounts, a PrivateLink approach is more suitable).
- B. **Create an NLB in the VPC with an IP-based target group pointing at the on-premises authentication service, and publish a VPC endpoint service (PrivateLink) targeting this NLB. Each VPC (or account) needing access creates an interface endpoint to connect.**
- C. Put API Gateway in front of the on-premises authentication service and expose it via a public endpoint (exposing a public endpoint directly contradicts the "must avoid the internet" requirement).
- D. Mirror the on-premises authentication service as static files in S3 and query them from the VPC (an authentication service is a stateful, dynamic service and isn't something that can be replaced by static files — a conceptual error).

**Correct Answer: B**

**Explanation**
Registering the on-premises authentication service's IP address (reachable via Direct Connect) as an **IP-based target in an NLB's target group** lets the NLB receive and forward traffic toward the on-premises service. Publishing a **VPC endpoint service (AWS PrivateLink)** targeting this NLB lets any VPC needing access (whether the same account or a different one) simply create an **interface endpoint** to access the on-premises service privately and without the internet, just like a native AWS service. This is the standard pattern of "using PrivateLink to expose an on-premises service."

**Why the other choices are wrong**
- A: Direct routing is valid, but for fine-grained access control across multiple VPCs/accounts and the "simple endpoint like a native service" experience, the PrivateLink (NLB + VPC endpoint service) approach is more standard.
- C: Public exposure directly violates the "must avoid the internet" requirement.
- D: An authentication service needs dynamic interaction and isn't a candidate for static file mirroring.

> 💡 **Exam tip**: To **expose an on-premises service to a VPC (or multiple accounts) privately, like a native AWS service**, **an NLB (with on-premises IP targets) + a VPC endpoint service (PrivateLink)** is the standard answer.

## QUESTION 359

**Question**: A company wants to reduce the cost of a web application (Java-based, using only standard open-source libraries, no custom native binaries) currently running on x86-based EC2 instances. How do they get the maximum price-performance improvement with no application architecture or code changes?

**Choices**
- A. Only upgrade to the latest generation within the same x86 instance family (has some effect, but the price-performance improvement from just an x86 generation upgrade is smaller than switching the architecture itself).
- B. **Switch to instance types using AWS Graviton (ARM-based) processors. Since the JVM supports ARM, the Java application can migrate mostly with no recompilation (or with only minimal validation), expecting up to about 40% better price-performance than equivalent x86 instances.**
- C. Fully switch to Spot Instances just for cost savings (Spot's interruption risk can conflict with an always-on web application's availability requirement; the question wants performance improvement with no architecture/code changes, not cost savings at the expense of availability).
- D. Just downsize the instance size by one step unconditionally (downsizing without regard to performance requirements risks the service degrading under actual traffic).

**Correct Answer: B**

**Explanation**
**AWS Graviton**-based instances deliver **up to about 40% better price-performance** than equivalent x86 instances for workloads using standard open-source software stacks (Java/JVM, Python, most Linux distributions and open-source libraries). ## QUESTION 360

**Question**: A company in a regulated industry manages backups via AWS Backup, and wants to enforce that backups themselves **cannot be deleted or have their retention period shortened by any means (including by administrators)** for the regulator-required retention period. How do you implement immutability similar to S3 Object Lock's compliance mode, at the AWS Backup vault level?

**Choices**
- A. Deny the delete API on the backup vault via an IAM policy (an IAM policy can always be changed/deleted by a sufficiently privileged user, so it doesn't guarantee true immutability).
- B. **Use AWS Backup Vault Lock, applying a compliance-mode lock policy to the backup vault and setting a minimum/maximum retention period, so that no one — including the root account — can delete backups stored in this vault or shorten the retention period during that time.**
- C. Periodically manually export backups to an S3 bucket in another account (a manual export process itself isn't a technical mechanism enforcing immutability, and deletion/modification is still possible after export).
- D. Only enable MFA Delete to prevent vault deletion (MFA Delete only requires an additional authentication step — a sufficiently privileged user who passes MFA can still delete, so it doesn't guarantee complete immutability).

**Correct Answer: B**

**Explanation**
**AWS Backup Vault Lock** applies a lock policy to a backup vault to enforce a WORM (Write Once Read Many) model. In particular, locking with **compliance mode** means that until the configured minimum/maximum retention period ends, **no one — not even the AWS account root user** — can delete a recovery point (backup) stored in that vault or shorten its retention period (the vault lock itself also can't be removed in compliance mode). This is the standard way to provide backup-layer immutability as strong as S3 Object Lock's compliance mode.

**Why the other choices are wrong**
- A: An IAM policy can be changed by a privileged user, so it doesn't guarantee true immutability.
- C: A manual export process itself isn't a technical mechanism that prevents deletion/modification.
- D: MFA Delete is just an additional authentication step — deletion is still possible after passing MFA, unlike true immutability.

> 💡 **Exam tip**: To enforce that backups **cannot be deleted by anyone — including administrators — during the retention period** for compliance purposes, **AWS Backup Vault Lock's compliance mode** is the standard answer.
