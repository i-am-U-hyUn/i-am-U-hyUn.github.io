## QUESTION 161

**문제**: Direct Connect로 온프레미스와 연결된 통신 회사. 내부 ALB(TLS 종료, 경로 기반 라우팅) 뒤 여러 AZ의 EC2. 온프레미스 방화벽에서 **IP 기반 허용 목록**을 적용하려 함. 클라이언트 접근을 유지하며 트래픽을 허용하는 솔루션은?

**보기**
- A. 기존 ALB에 고정 IP 구성 + 방화벽에 ALB IP 추가 (ALB는 고정 IP 미지원).
- B. **NLB 생성(여러 AZ에 정적 IP 연결) + NLB의 대상 그룹으로 기존 ALB 추가(ALB 타입 대상 그룹) + 방화벽에 NLB IP 추가 + 클라이언트가 NLB로 연결하도록 업데이트.**
- C. NLB 생성 + 기존 대상 그룹을 NLB에 직접 추가 + ALB 삭제 (ALB의 경로 기반 라우팅 기능을 잃음).
- D. GWLB 생성 + ALB를 대상 그룹으로 추가(GWLB는 트래픽 인스펙션용, 이 용도에 부적합).

**정답: B**

**해설**
**ALB는 정적/고정 IP를 지원하지 않습니다.** IP 기반 허용 목록에 등록할 고정 IP가 필요할 때는 **NLB(고정 IP 지원)를 ALB 앞에 두고, NLB의 대상 그룹으로 기존 ALB를 연결(ALB 타입 대상 그룹)**하는 것이 표준 해법입니다. 이렇게 하면 ALB의 경로 기반 라우팅 기능도 그대로 유지됩니다.

**왜 다른 보기는 오답인가**
- A: ALB는 정적 IP를 할당할 수 없습니다.
- C: 기존 ALB를 삭제하면 경로 기반 라우팅(여러 대상 그룹) 기능을 잃게 됩니다.
- D: Gateway Load Balancer는 트래픽 인스펙션 어플라이언스 삽입용으로, 이 시나리오(고정 IP 확보)와 목적이 다릅니다.

> 💡 **시험 꿀팁**: **ALB는 고정 IP를 가질 수 없습니다.** 고정 IP가 필요하면 **NLB를 앞에 두고 ALB를 대상 그룹으로 연결**하는 패턴을 기억하세요.

## QUESTION 162

**문제**: 프라이빗 서브넷 EC2 → 인터넷 연결 ALB → CloudFront(AWS 관리형 규칙 WAF 웹 ACL 연결) 아키텍처. 인터넷 트래픽이 ALB에 **직접** 접근하지 못하게 해야 함. 최소 운영 오버헤드 솔루션은?

**보기**
- A. 동일 규칙의 새 웹 ACL 생성 + ALB에 연결.
- B. 기존 웹 ACL을 ALB에 연결(중복 검사만 될 뿐 직접 접근 자체는 차단 못함).
- C. **ALB 보안 그룹에 CloudFront용 AWS 관리형 접두사 목록(prefix list)의 트래픽만 허용하는 규칙 추가.**
- D. CloudFront IP 주소 범위를 수동으로 나열하여 보안 그룹에 허용 규칙 추가.

**정답: C**

**해설**
**AWS가 관리하는 CloudFront 오리진용 접두사 목록(Managed Prefix List)**을 보안 그룹 규칙에 사용하면, CloudFront에서 오는 트래픽만 허용하고 그 외 인터넷의 직접 접근을 차단할 수 있습니다. AWS가 이 목록을 자동으로 최신 상태로 관리해주므로 운영 오버헤드가 최소화됩니다.

**왜 다른 보기는 오답인가**
- A, B: 웹 ACL은 요청 내용을 검사하는 것이지, ALB로의 직접 네트워크 접근 자체를 차단하지 못합니다.
- D: CloudFront IP 범위를 수동으로 관리하면 범위가 바뀔 때마다 직접 업데이트해야 해서 운영 오버헤드가 큽니다.

> 💡 **시험 꿀팁**: **CloudFront만 오리진(ALB/EC2)에 접근하도록 제한**하려면 **AWS 관리형 접두사 목록(com.amazonaws.global.cloudfront.origin-facing)**을 보안 그룹에 사용하는 것이 최소 오버헤드의 표준 정답입니다.

## QUESTION 163

**문제**: ElastiCache for Redis(저장 시 암호화는 구성됨)를 캐싱 계층으로 사용. **전송 중 암호화 미구성**, 사용자 인증 없이 접근 가능. 인증 요구 + 엔드투엔드 암호화로 변경하는 솔루션은?

**보기**
- A. AUTH 토큰 생성 + Parameter Store(암호화된 매개변수)에 저장 + **새 클러스터** 생성.
- B. **AUTH 토큰 생성 + Secrets Manager에 저장 + 기존 클러스터를 AUTH 토큰 사용 및 전송 중 암호화로 구성. 필요 시 Secrets Manager에서 조회하여 애플리케이션에 사용.**
- C. SSL 인증서 생성 + Secrets Manager에 저장 + 새 클러스터 생성(Redis 인증은 SSL 인증서가 아닌 AUTH 토큰 방식).
- D. SSL 인증서 + Parameter Store + 기존 클러스터 업데이트(마찬가지로 인증서 개념이 잘못됨).

**정답: B**

**해설**
ElastiCache for Redis의 인증은 **AUTH 토큰** 방식이며(SSL 인증서 방식이 아님), 이를 **AWS Secrets Manager**(민감한 자격 증명 관리에 특화된 서비스)에 저장하고, **기존 클러스터를 업데이트**하여 AUTH와 전송 중 암호화(in-transit encryption)를 구성하는 것이 정답입니다.

**왜 다른 보기는 오답인가**
- A: Parameter Store도 암호화된 매개변수를 저장할 수 있지만, 자격 증명(비밀) 관리에는 Secrets Manager가 더 적합하며, 굳이 새 클러스터를 만들 필요 없이 기존 클러스터를 업데이트하면 됩니다.
- C, D: Redis의 인증 메커니즘은 SSL 인증서가 아니라 **AUTH 토큰**입니다 — 개념 오류입니다.

> 💡 **시험 꿀팁**: **ElastiCache for Redis의 사용자 인증은 AUTH 토큰**을 사용하며(SSL 인증서 아님), 토큰은 **Secrets Manager**에 저장하는 것이 모범 사례입니다. 기존 클러스터도 AUTH+전송 중 암호화로 업데이트할 수 있습니다.

## QUESTION 164

**문제**: Auto Scaling 그룹의 스팟 인스턴스(시작 템플릿, 2개 배치 그룹, 단일 인스턴스 유형)로 컴퓨팅 워크로드 실행. 인스턴스 시작 실패로 대기 시간이 길어짐. 안정성 개선 솔루션은?

**보기**
- A. 시작 템플릿을 시작 구성(launch configuration)으로 교체(구식 기능으로 다운그레이드, 속성 기반 선택도 지원 안 함).
- B. **속성 기반 인스턴스 유형 선택을 사용하는 새 시작 템플릿 버전 생성. 이 버전을 사용하도록 Auto Scaling 그룹 구성.**
- C. 배치 그룹 수를 늘림(단일 인스턴스 유형의 스팟 가용성 문제와 무관).
- D. 더 큰 인스턴스 유형으로 변경(단일 유형 의존 문제를 그대로 유지).

**정답: B**

**해설**
단일 인스턴스 유형에만 의존하면 해당 유형의 스팟 용량이 부족할 때 시작 실패가 발생합니다. **속성 기반 인스턴스 유형 선택(Attribute-Based Instance Type Selection, ABIS)**을 사용하면 Auto Scaling이 필요한 속성(vCPU, 메모리 등)을 만족하는 여러 인스턴스 유형 풀에서 자동으로 선택해, 특정 유형의 용량 부족에 훨씬 강건해집니다.

**왜 다른 보기는 오답인가**
- A: 시작 구성은 더 오래된 기능이며 ABIS 같은 최신 기능을 지원하지 않습니다.
- C: 배치 그룹 수 증가는 스팟 용량/시작 실패 문제와 직접적인 관련이 없습니다.
- D: 더 큰 단일 인스턴스 유형으로 바꿔도 여전히 "단일 유형 의존"이라는 근본 문제가 남습니다.

> 💡 **시험 꿀팁**: 스팟 인스턴스의 **단일 유형 의존으로 인한 시작 실패**는 **속성 기반 인스턴스 유형 선택(ABIS)**으로 여러 유형의 풀을 활용하게 하는 것이 표준 해법입니다.

## QUESTION 165

**문제**: Linux 문서 저리 서버(초당 5개 문서 생성, S3 API 지원 불가능한 레거시)가 만드는 파일에 **빠른 로컬 액세스** 필요, 처리 완료 후 30분 이내 대중이 S3에서 다운로드 가능해야 함. 최소 노력 솔루션은?

**보기**
- A. 애플리케이션을 Lambda로 마이그레이션(레거시 서버 자체를 즉시 재작성 불가라는 제약 위반).
- B. **Amazon S3 파일 게이트웨이 설정 + NFS로 EC2에 파일 공유 마운트 + 변경 시 RefreshCache API로 업데이트.**
- C. FSx for Lustre(가져오기/내보내기 정책, S3 연결) + NFS 마운트(Lustre는 NFS가 아닌 Lustre 프로토콜을 사용 — 개념 오류).
- D. AWS DataSync로 EC2에 연결 + S3와 동기화(실시간에 가까운 로컬 접근과 자동 반영이라는 요구에는 파일 게이트웨이가 더 적합).

**정답: B**

**해설**
**Amazon S3 파일 게이트웨이**는 레거시 서버가 NFS/SMB로 로컬 파일처럼 빠르게 접근하면서, 백그라운드에서 자동으로 S3에 데이터를 저장/동기화해주는 정확히 이 시나리오를 위한 서비스입니다. 서버 코드를 바꿀 필요가 전혀 없습니다.

**왜 다른 보기는 오답인가**
- A: 서버를 Lambda로 즉시 마이그레이션하는 것은 "S3 API 지원을 위해 즉시 업데이트 불가"라는 제약을 위반합니다.
- C: FSx for Lustre는 NFS가 아닌 자체 Lustre 클라이언트/프로토콜을 사용하므로 "NFS를 사용하여 마운트"라는 설명과 맞지 않습니다.
- D: DataSync는 배치성 동기화 작업에 가깝고, 이 시나리오처럼 로컬 파일 시스템처럼 즉각적인 접근이 필요한 경우 파일 게이트웨이가 더 자연스럽습니다.

> 💡 **시험 꿀팁**: **레거시 서버가 S3 API를 지원하지 못하지만 로컬 파일처럼 빠른 접근이 필요**할 때는 **Storage Gateway (S3 파일 게이트웨이)**가 표준 정답입니다 — 서버는 NFS/SMB로 로컬 마운트처럼 사용하고, 백그라운드에서 S3와 동기화됩니다.

## QUESTION 166

**문제**: 서버리스 배송 솔루션(여러 마이크로서비스), 중앙 사용자 서비스가 DynamoDB에 중요 데이터 저장, 다른 마이크로서비스는 민감 데이터 사본을 각자 저장소에 저장. 사용자 삭제 시 **모든** 마이크로서비스가 즉시 사본을 삭제해야 함.

**보기**
- A. DynamoDB 스트림 → SQS 게시 Lambda → 각 마이크로서비스가 큐를 폴링(단일 큐를 여러 서비스가 폴링하면 메시지가 한 소비자에게만 전달됨 — 팬아웃 부적합).
- B. DynamoDB 이벤트 알림 → SNS 주제 → 각 마이크로서비스 구독(DynamoDB 테이블 자체에 이런 "이벤트 알림" 기능은 없음 — 스트림을 통해야 함).
- C. **중앙 사용자 서비스가 사용자 삭제 시 사용자 지정 EventBridge 이벤트 버스에 이벤트 게시. 각 마이크로서비스별 EventBridge 규칙(삭제 이벤트 패턴)을 생성해 각자 로직 호출.**
- D. SQS 대기열에 메시지 게시 + SQS의 "이벤트 필터"로 각 마이크로서비스가 삭제(SQS는 단일 소비자 모델이라 다중 마이크로서비스에 팬아웃 부적합).

**정답: C**

**해설**
하나의 이벤트를 **여러 독립적인 마이크로서비스에 팬아웃**해야 하는 시나리오에는 **Amazon EventBridge**(발행-구독 모델, 각 서비스가 자체 규칙으로 이벤트를 구독)가 정확히 맞습니다. SQS는 기본적으로 단일 소비자(경쟁 소비자) 모델이라 여러 서비스에 동일 이벤트를 팬아웃하기에 부적합합니다.

**왜 다른 보기는 오답인가**
- A, D: SQS 대기열은 한 메시지가 하나의 소비자에게만 전달되는 것이 기본이므로, 여러 마이크로서비스가 동시에 같은 삭제 이벤트를 받아야 하는 요구를 만족하지 못합니다(SNS 팬아웃 패턴이 필요합니다).
- B: DynamoDB 테이블 자체가 "이벤트 알림"을 직접 발행하는 기능은 없으며, DynamoDB Streams를 통해야 합니다.

> 💡 **시험 꿀팁**: 하나의 이벤트를 **여러 독립 마이크로서비스에 팬아웃**해야 할 때는 **EventBridge(또는 SNS)**를 사용하세요 — SQS 단일 큐는 팬아웃에 부적합합니다(SNS+SQS 조합이면 가능).

## QUESTION 167

**문제**: VPC 웹 애플리케이션(ALB+WAF). 외부 고객에게 **IP 주소**를 제공해야 함(고객 방화벽 허용 목록용으로 추정). 최소 운영 오버헤드 솔루션은?

**보기**
- A. ALB를 NLB로 교체 + 탄력적 IP 할당(ALB의 WAF/L7 기능을 잃음).
- B. 탄력적 IP를 ALB에 직접 할당(ALB는 EIP를 직접 할당받을 수 없음).
- C. **AWS Global Accelerator 표준 가속기 생성. ALB를 엔드포인트로 지정. 액셀러레이터의 고정 IP 주소를 고객에게 제공.**
- D. CloudFront 배포 구성 + DNS 이름을 ping해 IP 확인(CloudFront의 IP는 고정되지 않고 여러 개이며 변경될 수 있음).

**정답: C**

**해설**

- C. **Migration Evaluator로 서버 목록 생성 + 비즈니스 사례 보고서 작성. Migration Hub로 포트폴리오 확인. AWS Application Discovery Service로 애플리케이션 종속성 파악.**

문서화가 부실해 **무엇이 존재하는지조차 모르는** 상황에서는, **AWS Application Discovery Service**(에이전트/에이전트리스 방식으로 서버·네트워크·프로세스 종속성을 자동 발견)로 실제 인프라를 파악하고, **AWS Migration Evaluator**로 이 데이터를 기반으로 비즈니스 사례(TCO)를 작성하며, **AWS Migration Hub**에서 전체 포트폴리오 진행 상황을 한눈에 확인하는 조합이 정확히 맞습니다.

- A. ALB + SQS(대상 그룹으로 SQS 직접 연결은 지원되지 않음 — ALB 대상 그룹은 EC2/IP/Lambda만 가능) + Fargate ECS로 큐 메시지 처리.
- B. **API Gateway HTTP API + SQS 대기열 + API Gateway-SQS 서비스 통합(직접 통합) + Lambda로 큐 메시지 처리.**
- C. API Gateway REST API + Auto Scaling EC2 + API Gateway-Auto Scaling 그룹 프록시 통합(이런 직접 프록시 통합 방식은 일반적이지 않으며 확장성 완충 장치가 없음).
- D. CloudFront + Kinesis Data Streams(배포 오리진으로 데이터 스트림을 직접 설정하는 것은 일반적인 아키텍처가 아님) + Lambda 소비.

**정답: B**

**해설**
API Gateway는 **SQS와의 직접 서비스 통합**을 지원하여, 백엔드 컴퓨팅 리소스 없이도 수신 요청을 즉시 큐에 안전하게 적재할 수 있습니다. SQS는 트래픽 폭증을 완충하는 버퍼 역할을 하여 **데이터 손실 없이** 처리 속도를 조절할 수 있고, Lambda가 큐를 폴링해 처리량에 맞춰 자동으로 확장됩니다.

**왜 다른 보기는 오답인가**
- A: ALB의 대상 그룹은 SQS를 직접 대상으로 지정할 수 없습니다(EC2/IP/Lambda만 가능).
- C: API Gateway와 Auto Scaling 그룹 간의 직접 프록시 통합은 일반적인 패턴이 아니며, 트래픽 폭증을 완충할 버퍼가 없어 데이터 손실 위험이 있습니다.
- D: CloudFront를 Kinesis Data Streams 앞에 직접 두는 것은 이 RESTful API 수집 시나리오에 맞지 않는 아키텍처입니다.

> 💡 **시험 꿀팁**: **예측 불가능한 트래픽 폭증 속에서도 데이터 손실 없이** API 요청을 수집해야 할 때는 **API Gateway의 SQS 직접 서비스 통합**으로 요청을 즉시 큐에 적재하고, Lambda로 비동기 처리하는 패턴이 표준 정답입니다.
