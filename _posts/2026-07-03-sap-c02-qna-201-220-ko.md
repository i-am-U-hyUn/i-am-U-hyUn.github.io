## QUESTION 201

**문제**: Aurora MySQL 애플리케이션(대부분 INSERT 작업)에서 연결 과부하 발생. 자격 증명은 현재 텍스트 파일에 저장. 연결 부하 처리 + 자격 증명 안전 보관 + 정기 자동 교체를 만족하는 솔루션은?

**보기**
- A. **DB 인스턴스 앞에 RDS Proxy 배포. 연결 자격 증명을 Secrets Manager에 비밀로 저장.**
- B. RDS Proxy 배포 + Parameter Store에 저장(Parameter Store는 자동 교체 기능이 Secrets Manager만큼 통합되어 있지 않음).
- C. Aurora 복제본 생성 + Secrets Manager(복제본은 읽기 확장용으로 INSERT가 대부분인 이 워크로드의 연결 과부하 문제 해결과 무관).
- D. Aurora 복제본 + Parameter Store(마찬가지로 쓰기 연결 문제 해결과 무관, 자동 교체도 부족).

**정답: A**

**해설**
**RDS Proxy**는 연결 풀링을 통해 데이터베이스에 대한 연결 수를 크게 줄여 연결 과부하 문제를 해결하며, **AWS Secrets Manager**는 데이터베이스 자격 증명을 안전하게 저장하고 **자동 교체(rotation)** 기능을 네이티브로 지원합니다. 이 둘의 조합이 두 요구사항을 모두 만족하는 표준 해법입니다.

**왜 다른 보기는 오답인가**
- B: Parameter Store도 보안 저장은 가능하지만 Secrets Manager만큼 통합된 자동 교체 기능을 제공하지 않습니다.
- C, D: Aurora 복제본은 읽기 워크로드 분산용이며, 이 시나리오처럼 대부분 **쓰기(INSERT)**인 워크로드의 연결 과부하 문제를 해결하지 못합니다.

> 💡 **시험 꿀팁**: **데이터베이스 연결 과부하**에는 **RDS Proxy**(연결 풀링), **자격 증명 안전 보관+자동 교체**에는 **Secrets Manager**가 표준 조합입니다. Aurora 복제본은 읽기 확장용이지 연결 수 문제 해결책이 아닙니다.

## QUESTION 202

**문제**: 전자상거래(t3.large EC2, 여러 AZ Auto Scaling, RDS MySQL) DR 솔루션. **RPO 30초, RTO 10분**으로 보조 환경 장애 조치. 가장 비용 효율적인 솔루션은?

**보기**
- A. IaC로 DR 리전 인프라 프로비저닝 + RDS 리전 간 읽기 전용 복제본 + AWS Backup(교차 리전) + 30초마다 백업 cron + EC2를 최신 백업에서 복구 + Route 53 지리적 위치 라우팅(백업 기반 복구는 RTO 10분을 만족하기엔 EC2 복구/부팅에 시간이 걸림).
- B. **IaC로 DR 리전 인프라 프로비저닝 + RDS 리전 간 읽기 전용 복제본 + EC2를 AWS Elastic Disaster Recovery로 지속 복제 + DR 리전에서 최소 용량으로 EC2 실행 + Route 53 장애 조치 라우팅 + Auto Scaling 그룹의 원하는 용량 증가.**
- C. AWS Backup(교차 리전) + 30초마다 cron 백업 + IaC 프로비저닝 + 수동 복원 + Route 53 단순 라우팅(수동 개입이 필요해 RTO 10분 충족 어려움).
- D. IaC + Aurora 글로벌 데이터베이스 + EC2를 DRS로 지속 복제 + DR 리전에서 **전체 용량**으로 상시 실행 + Route 53 장애 조치(항상 전체 용량 가동은 비용이 과도함).

**정답: B**

**해설**
**AWS Elastic Disaster Recovery(DRS)**로 EC2를 지속적으로(초 단위) 복제하고, DR 리전에서는 **최소 용량**(파일럿 라이트/웜 스탠바이 방식)만 유지하다가 장애 시 Auto Scaling 그룹의 용량을 늘리는 방식이 RPO 30초/RTO 10분을 만족하면서도 상시 전체 용량 가동보다 훨씬 저렴합니다. RDS는 **읽기 전용 복제본**으로 승격시켜 빠른 DB 장애 조치를 지원합니다.

**왜 다른 보기는 오답인가**
- A, C: 30초 간격 백업/cron 기반 방식은 데이터는 챙길 수 있어도, EC2를 백업에서 처음부터 복구/부팅하는 과정이 10분 RTO를 넘기기 쉽습니다.
- D: DR 리전에서 항상 전체 용량으로 EC2를 가동하는 것은 "가장 비용 효율적으로"라는 요구에 맞지 않는 과도한 상시 비용입니다.

> 💡 **시험 꿀팁**: 짧은 RPO/RTO의 EC2 DR에는 **AWS Elastic Disaster Recovery(DRS)**의 지속 복제가 정답이며, 비용 최적화를 위해 DR 리전은 **최소 용량(파일럿 라이트)**으로 유지하다가 장애 시에만 확장하는 것이 핵심입니다.

## QUESTION 203

**문제**: 온프레미스 MySQL(60TB)을 us-east-1의 Aurora MySQL로 일회성 마이그레이션. 인터넷 대역폭 제한으로 전송에 한 달 소요 예상. 가장 짧은 시간 내 마이그레이션 솔루션은?

**보기**
- A. 1Gbps Direct Connect 요청 + DMS로 마이그레이션(신규 DX 연결 구축 자체가 시간이 오래 걸림).
- B. 기존 인터넷 연결 + DataSync + Application Migration Service(여전히 제한된 대역폭에 의존, 60TB에는 부적합).
- C. **Snowball Edge 디바이스 주문. S3 인터페이스로 데이터를 S3 버킷에 로드. DMS로 S3에서 Aurora MySQL로 마이그레이션.**
- D. Snowball 디바이스 + S3 어댑터로 로드 + Application Migration Service(Application Migration Service는 서버 마이그레이션용이지 DB 마이그레이션 도구가 아님 — 개념 오류).

**정답: C**

**해설**
제한된 대역폭으로 60TB를 전송하는 데 한 달이 걸린다면, **AWS Snowball Edge**로 물리적으로 데이터를 옮기는 것이 훨씬 빠릅니다. 데이터를 Snowball을 통해 S3에 적재한 후, **AWS DMS**로 S3에서 Aurora MySQL로 마이그레이션을 완료합니다.

**왜 다른 보기는 오답인가**
- A: 새로운 Direct Connect 연결을 구축하는 것 자체가 수 주가 걸릴 수 있어 "가장 짧은 시간"이라는 목표에 부합하지 않습니다.
- B: DataSync를 쓰더라도 여전히 제한된 인터넷 연결에 의존하므로 근본적 병목이 해소되지 않습니다.
- D: AWS Application Migration Service는 서버(컴퓨팅) 마이그레이션 도구이지 데이터베이스 마이그레이션 도구가 아닙니다 — DMS가 정답입니다.

> 💡 **시험 꿀팁**: **대용량 데이터(수십 TB)를 제한된 대역폭**으로 옮겨야 할 때는 **Snowball Edge(물리적 전송) → S3 → DMS(DB로 마이그레이션)** 조합이 표준 정답입니다.

## QUESTION 204

**문제**: 20개 EC2 인스턴스(영구적, 여러 EBS 볼륨) 애플리케이션. 별도 리전에 백업 유지 필요. **하루치 데이터 손실 없이, 영업일 1일 이내** 복구. 직원 제한적, 운영 효율/비용 최적화. 보조 리전 네트워크 구성용 CloudFormation 템플릿은 이미 있음.

**보기**
- A. 두 번째 CloudFormation 템플릿(EC2 재생성) + Systems Manager Automation Runbook으로 매일 다중 볼륨 스냅샷 + 보조 리전 복사 + 장애 시 템플릿 실행+EBS 복원(가능한 방법이지만 AWS Backup 대비 관리 요소가 많음).
- B. DLM으로 일일 다중 볼륨 스냅샷 + 장애 시 템플릿+DLM으로 복원(DLM은 스냅샷 생성/보관 자동화 도구이며, 크로스 리전 복사와 인스턴스/구성 복원까지 통합 관리하는 데는 AWS Backup이 더 적합).
- C. **AWS Backup으로 EC2 예약 일일 백업 계획 생성. 보조 리전 볼트로 백업 복사 구성. 장애 시 CloudFormation 템플릿 실행 + 백업 볼트에서 인스턴스 볼륨/구성 복원 + 트래픽을 보조 리전으로 전환.**
- D. 보조 리전에 동일 구성 EC2 상시 배포 + 매일 DataSync로 데이터 복사(상시 이중 인프라 유지로 비용이 훨씬 큼 — "직원 제한적, 비용 최적화" 요건에 안 맞음).

**정답: C**

**해설**
**AWS Backup**은 EC2 인스턴스(연결된 여러 EBS 볼륨 포함)에 대한 예약 백업과 **크로스 리전 복사**를 하나의 관리형 서비스로 통합 제공하여, 제한된 인력으로도 최소 운영 부담으로 하루 단위 RPO를 만족시킬 수 있습니다. 장애 시에는 준비된 CloudFormation 템플릿으로 네트워크를 구성하고 백업 볼트에서 복원하면 영업일 1일 이내 RTO도 만족합니다.

**왜 다른 보기는 오답인가**
- A, B: DLM이나 Systems Manager Runbook으로 스냅샷을 직접 관리하는 것은 AWS Backup의 통합 백업 계획/크로스 리전 복사 기능보다 구성 요소가 많아 운영 부담이 더 큽니다.
- D: 보조 리전에 상시 동일 인프라를 유지하는 것은 "직원 제한적이며 비용을 최적화해야 한다"는 조건에 맞지 않게 비용이 큽니다.

> 💡 **시험 꿀팁**: 제한된 인력으로 **EC2+EBS의 크로스 리전 백업/복구**를 관리형으로 단순화하려면 **AWS Backup**(예약 백업 계획 + 크로스 리전 복사)이 표준 정답입니다.

## QUESTION 205

**문제**: 정적 콘텐츠 웹사이트(대용량 파일 업/다운로드), S3+CloudFront 사용. **전송 중 및 저장 시 모두 암호화** 필요. (3개 선택)

**보기**
- A. **웹 애플리케이션이 사용하는 S3 버킷에 S3 서버 측 암호화 켜기(저장 시 암호화).**
- B. S3 ACL의 읽기/쓰기 작업에 "aws:SecureTransport":"true" 속성 추가(ACL이 아닌 버킷 정책에 조건을 넣는 것이 표준 — 개념 다소 부정확).
- C. **웹 애플리케이션이 사용하는 S3 버킷에서 암호화되지 않은 작업(HTTP)을 거부하는 버킷 정책 생성(전송 중 암호화 강제).**
- D. CloudFront에서 SSE-KMS로 유휴 암호화 구성(CloudFront 자체는 저장소가 아니므로 "CloudFront에서 유휴 암호화"라는 개념이 성립하지 않음 — 저장 시 암호화는 오리진인 S3에서 처리).
- E. **CloudFront에서 HTTP 요청을 HTTPS로 리디렉션하도록 구성(전송 중 암호화, 사용자-CloudFront 구간).**
- F. 미리 서명된 URL 생성 시 RequireSSL 옵션 사용(S3 사전 서명 URL API에는 이런 옵션이 존재하지 않음 — 버킷 정책의 SecureTransport 조건이 표준 방법).

**정답: A, C, E**

**해설**
저장 시 암호화는 **S3 서버 측 암호화**(A)로, 전송 중 암호화는 두 구간에서 각각 강제해야 합니다: **CloudFront-사용자 구간**은 HTTP→HTTPS 리디렉션(E)으로, **애플리케이션-S3 구간**은 버킷 정책으로 HTTPS가 아닌 요청을 거부(C)하여 강제합니다.

**왜 다른 보기는 오답인가**
- B: SecureTransport 조건은 ACL이 아니라 **버킷 정책**에 추가하는 것이 표준 방식입니다(C가 이를 올바르게 표현).
- D: CloudFront는 콘텐츠를 저장하는 스토리지가 아니므로 "CloudFront에서 저장 시 암호화"라는 개념 자체가 맞지 않습니다.
- F: S3 사전 서명 URL 생성 API에는 "RequireSSL"이라는 옵션이 존재하지 않습니다.

> 💡 **시험 꿀팁**: S3+CloudFront 아키텍처에서 **전 구간 암호화**를 강제하려면 ① S3 서버 측 암호화(저장 시), ② CloudFront의 HTTP→HTTPS 리디렉션(사용자-CF 구간, 전송 중), ③ 버킷 정책의 `aws:SecureTransport` 조건(앱-S3 구간, 전송 중) 세 가지가 필요합니다.

## QUESTION 206

**문제**: Lambda가 RDS SQL Server에 접근하는 서버리스 아키텍처. 개발/프로덕션 환경 분리. 개발 DB 자격 증명은 개발자가 접근 가능. **프로덕션 DB 자격 증명은 IT 보안 팀의 IAM 사용자 그룹만 접근 가능한 키로 암호화**해야 하며, 이 키는 **정기적으로 순환**되어야 함. 프로덕션 환경에서 해야 할 일은?

**보기**
- A. Parameter Store SecureString(KMS 고객 관리형 키) + Lambda 역할 연결 + IT 보안 팀만 매개변수/키 접근 제한(Parameter Store 자체에는 자격 증명 값의 자동 교체 기능이 내장되어 있지 않음).
- B. KMS 기본(AWS 관리형) Lambda 키로 암호화 + 환경 변수에 자격 증명 저장(기본 키는 접근을 특정 IAM 그룹으로만 제한하는 사용자 지정 정책을 적용하기 어려움).
- C. 환경 변수에 자격 증명 저장 + KMS 고객 관리형 키로 암호화(환경 변수 자체는 자동 교체 매커니즘을 갖지 않음).
- D. **데이터베이스 자격 증명을 Secrets Manager에 KMS 고객 관리형 키와 연결된 비밀로 저장. 각 Lambda 함수에 비밀 접근 권한이 있는 역할 연결. IT 보안 팀만 키에 접근 가능하도록 고객 관리형 키 접근 제한.**

**정답: D**

**해설**
**AWS Secrets Manager**는 자격 증명 저장과 **자동 순환(rotation)**을 네이티브로 지원하며, 저장 시 사용하는 **KMS 고객 관리형 키**의 키 정책을 IT 보안 팀 IAM 그룹으로만 제한하면 "이 키에는 보안 팀만 접근 가능"이라는 요구를 정확히 만족합니다.

**왜 다른 보기는 오답인가**
- A, C: Parameter Store나 환경 변수는 값 자체를 안전하게 암호화 저장할 수 있지만, Secrets Manager처럼 통합된 **자동 교체 기능**을 제공하지 않습니다.

**보기**
- A. VPC-API Gateway 간 Site-to-Site VPN + API 키 요구(API Gateway는 VPN 연결 대상이 아니며, API 키는 인증 수단이지 네트워크 경로를 프라이빗하게 만들지 못함 — 개념 오류).
- B. **API Gateway에 인터페이스 VPC 엔드포인트 생성 + 특정 API만 허용하는 엔드포인트 정책 설정. VPC 엔드포인트에서의 접근만 허용하는 리소스 정책을 API Gateway에 추가. API Gateway 엔드포인트 유형을 프라이빗으로 변경.**
- C. IAM 인증 사용 + EC2 인스턴스 역할 정책 업데이트 + API Gateway를 새 VPC로 이동 + Transit Gateway 배포(API Gateway 자체를 VPC "안으로 이동"시키는 개념은 API Gateway의 실제 작동 방식과 다름 — 프라이빗 엔드포인트 방식이 표준).
- D. Global Accelerator + 라우팅 테이블 업데이트 + API 키(Global Accelerator는 트래픽을 여전히 공용 네트워크 경유로 가속화하는 것으로, "공용 인터넷 미경유"라는 핵심 요건과 상충).

**정답: B**

**해설**
**API Gateway 프라이빗 엔드포인트**로 전환하고, VPC에 **인터페이스 VPC 엔드포인트**를 생성한 뒤, API Gateway의 **리소스 정책**으로 이 VPC 엔드포인트에서의 접근만 허용하도록 제한하면, 트래픽이 공용 인터넷을 전혀 거치지 않고 AWS 프라이빗 네트워크 내에서만 API를 호출할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: API Gateway는 VPN 연결의 대상이 아니며, API 키는 단순 인증/스로틀링 수단으로 네트워크 경로를 프라이빗하게 만들지 못합니다.
- C: API Gateway를 VPC "안으로 이동"시킨다는 개념은 실제 서비스 작동 방식과 맞지 않습니다(프라이빗 엔드포인트가 표준 방법).
- D: Global Accelerator는 여전히 AWS의 공용 엣지 네트워크를 통해 트래픽을 가속화하는 것으로, "공용 인터넷을 절대 거치지 않아야 한다"는 요구와 맞지 않습니다.

> 💡 **시험 꿀팁**: API Gateway를 **공용 인터넷 경유 없이 VPC 내부에서만** 호출 가능하게 하려면 **프라이빗 API 엔드포인트 + 인터페이스 VPC 엔드포인트 + 리소스 정책**(VPC 엔드포인트로만 접근 제한)의 조합이 표준 정답입니다.

## QUESTION 219

**문제**: EC2(전자상거래)+S3 인프라, 엔지니어 3명이 단일 계정에서 관리. 엔지니어가 다른 엔지니어의 EC2 보안 그룹 설정을 변경해 비준수 문제 발생. 변경 사항 추적 + 보안 그룹이 **비준수로 변경되면 알림**을 보내는 시스템을 **가장 빠르게** 구축하는 방법은?

**보기**
- A. Organizations 설정 + SCP로 비준수 보안 그룹 변경 관리/추적(SCP는 권한의 상한선을 정하는 예방적 도구이지, 변경을 "추적"하거나 "알림"을 보내는 기능이 없음 — 개념 오류).
- B. CloudTrail 활성화(보안 그룹 변경 캡처) + CloudWatch 규칙으로 비준수 감지 시 알림(가능한 방법이지만, "비준수" 여부 자체를 판단하는 규칙 엔진 구축을 직접 해야 해서 AWS Config보다 구현이 더 필요함).
- C. SCP로 비준수 보안 그룹 변경 시 알림 활성화(SCP는 애초에 알림 기능이 없음 — 개념 오류).
- D. **EC2 보안 그룹에 대해 AWS Config 활성화해 비준수 변경 추적. SNS 주제를 통해 변경 사항을 알림으로 전송.**

**정답: D**

**해설**
**AWS Config**는 리소스 구성 변경 이력을 자동으로 추적하고, 미리 정의된(또는 사용자 지정) 규칙과 비교해 **비준수(NON_COMPLIANT)** 여부를 즉시 평가하는 서비스입니다. Config 규칙 위반 시 **SNS**로 알림을 보내도록 구성하면, 별도의 판단 로직을 직접 짤 필요 없이 가장 빠르게(관리형 규칙 활용) 요구사항을 구현할 수 있습니다.

**왜 다른 보기는 오답인가**
- A, C: **SCP는 권한을 사전에 제한하는 예방적 도구**로, 변경 이력을 추적하거나 알림을 보내는 기능 자체가 없습니다 — 개념적으로 맞지 않습니다.
- B: CloudTrail+CloudWatch로도 구현 가능하지만, "비준수 여부"를 판별하는 규칙 로직을 직접 만들어야 해 AWS Config의 관리형 규칙보다 구현 노력이 더 필요합니다.

> 💡 **시험 꿀팁**: 리소스 구성이 **규정을 준수하는지 지속적으로 추적하고 위반 시 알림**을 보내려면 **AWS Config(관리형 규칙) + SNS**가 가장 빠르고 표준적인 정답입니다. SCP는 예방적 상한선 도구일 뿐 추적/알림 기능이 없다는 점을 기억하세요.

## QUESTION 220

**문제**: 대도시 교통 패턴 IoT 센서 데이터가 Kinesis Data Streams로 스트리밍, 여러 애플리케이션이 스트림에서 읽음. 소비자들이 조절(throttling) 및 주기적 `ReadProvisionedThroughputExceeded` 오류 경험. 해결 조치는? (3개 선택)

**보기**
- A. **스트림을 리샤딩해 샤드 수 증가.**
- B. 폴링 빈도 조정(구체적으로 "늘리는" 방향이면 오히려 상황 악화 — 문항의 의미상 이 단독 항목은 정답 세트에 포함되지 않음).
- C. **향상된 팬아웃(Enhanced Fan-Out) 기능이 있는 소비자 사용.**
- D. 스트림을 리샤딩해 샤드 수 감소(샤드 수를 줄이면 오히려 처리량이 줄어 문제 악화).
- E. **소비자 로직에서 오류 재시도 및 지수 백오프 메커니즘 사용.**
- F. 동적 파티셔닝을 사용하도록 스트림 구성(동적 파티셔닝은 Kinesis Data Firehose의 기능으로, Kinesis Data Streams 자체의 스로틀링 해결과는 무관).

**정답: A, C, E**

**해설**
**샤드 수 증가(리샤딩)**로 전체 읽기 처리량 한도 자체를 늘리고(A), 여러 소비자가 각자 샤드당 전체 처리량(2MB/s)을 공유하지 않고 개별적으로 소비할 수 있는 **향상된 팬아웃(Enhanced Fan-Out)**을 사용하며(C), 애플리케이션 레벨에서는 **지수 백오프를 포함한 재시도 로직**(E)을 구현해 일시적 조절 상황에서도 안정적으로 복구되도록 하는 것이 표준 해법입니다.

**왜 다른 보기는 오답인가**
- D: 샤드 수를 줄이면 처리량 한도가 더 낮아져 조절 문제가 악화됩니다.
- F: 동적 파티셔닝은 Kinesis Data Firehose(전송 스트림)의 기능이며, Kinesis Data Streams의 소비자 스로틀링 문제와는 무관합니다.

> 💡 **시험 꿀팁**: 여러 소비자가 Kinesis Data Streams에서 **`ReadProvisionedThroughputExceeded`** 오류를 겪을 때는 ① **샤드 수 증가(리샤딩)**, ② **향상된 팬아웃(Enhanced Fan-Out)**(소비자별 전용 처리량), ③ **재시도+지수 백오프** 세 가지를 조합하는 것이 표준 정답입니다.
