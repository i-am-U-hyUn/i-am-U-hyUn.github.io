## QUESTION 21

**문제**: 한 전자상거래 회사가 AWS에서 하루에 한 번 여는 웹 사이트를 준비하고 있습니다. 이 사이트는 매일 24시간 동안 정확히 하나의 제품만 판매합니다. 회사는 피크 시간대에 밀리초 단위의 지연 시간으로 시간당 수백만 건의 요청을 처리할 수 있기를 원합니다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. Amazon S3를 사용하여 전체 웹 사이트를 다른 S3 버킷에 호스팅합니다. Amazon CloudFront 배포를 추가하고 S3 버킷을 오리진으로 설정합니다. 주문 데이터는 Amazon S3에 저장합니다. (전체 애플리케이션에는 동적 처리 로직이 필요한데, S3+CloudFront만으로는 정적 콘텐츠만 제공할 수 있어 부적합합니다)
- B. 여러 가용 영역의 Auto Scaling 그룹에서 실행되는 Amazon EC2 인스턴스에 전체 웹 사이트를 배포하고, ALB(Application Load Balancer)로 웹 트래픽을, 별도의 ALB로 백엔드 API 트래픽을 분산합니다. 데이터는 MySQL용 Amazon RDS에 저장합니다. (RDS는 컴퓨팅 계층의 자동 확장을 기본 지원하지 않아 트래픽 폭증 대응이 어렵고 운영 부담도 큽니다)
- C. 전체 애플리케이션을 컨테이너로 마이그레이션하여 Amazon EKS에서 호스팅하고, Kubernetes 클러스터 오토스케일링으로 포드 수를 조절합니다. 데이터는 MySQL용 Amazon RDS에 저장합니다. (컨테이너 클러스터 운영 오버헤드가 크고, RDS 확장성 한계도 B와 동일하게 존재합니다)
- D. **Amazon S3 버킷으로 웹 사이트의 정적 콘텐츠를 호스팅하고 Amazon CloudFront 배포를 구성하여 S3 버킷을 오리진으로 설정합니다. 백엔드 API는 Amazon API Gateway와 AWS Lambda 함수로 구현하고, 데이터는 Amazon DynamoDB에 저장합니다.**

**정답: D**

**해설**
이 문제의 핵심은 예측 가능한 짧은 피크 구간에 폭증하는 트래픽을 서버 프로비저닝 없이 처리하는 것입니다. **S3 + CloudFront**는 정적 콘텐츠를 전 세계 엣지 로케이션에 캐싱해 밀리초 단위로 응답하며, **API Gateway + Lambda**는 요청량에 정비례하여 자동으로 확장되는 완전 서버리스 백엔드를 제공합니다. **DynamoDB**는 단일 자릿수 밀리초 지연으로 응답하고 트래픽에 맞춰 용량을 자동 조정하므로, 서버나 클러스터를 직접 관리할 필요가 없어 운영 오버헤드가 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: 전체 웹 사이트에는 주문 처리 같은 동적 로직이 포함되는데, S3+CloudFront 조합은 정적 콘텐츠 제공에만 적합합니다.
- B: RDS는 스토리지 오토스케일링은 지원하지만 컴퓨팅 계층 자체의 자동 확장은 기본 제공하지 않아, 시간당 수백만 요청의 급격한 변화에 대응하기 어렵고 이중 ALB 구성으로 운영 부담도 큽니다.
- C: EKS와 RDS 조합 역시 B와 같은 이유로 RDS 확장성 한계가 있고, 컨테이너 클러스터 운영 자체가 상당한 관리 오버헤드를 수반합니다.

> 💡 **시험 꿀팁**: 밀리초 지연 시간 + 트래픽 폭증 + 최소 운영 오버헤드라는 조건이 나오면 S3+CloudFront(정적) + API Gateway+Lambda+DynamoDB(완전 서버리스) 조합이 표준 정답입니다.

## QUESTION 22

**문제**: 한 솔루션 설계자가 Amazon S3를 사용하여 새로운 디지털 미디어 애플리케이션의 스토리지 아키텍처를 설계하고 있습니다. 미디어 파일은 가용 영역(AZ) 손실에도 견딜 수 있는 복원력을 가져야 합니다. 일부 파일은 자주 액세스되는 반면 다른 파일은 예측할 수 없는 패턴으로 거의 액세스되지 않습니다. 솔루션 설계자는 미디어 파일을 저장하고 검색하는 비용을 최소화해야 합니다. 이러한 요구 사항을 충족하는 스토리지 옵션은 무엇입니까?

**보기**
- A. S3 Standard (S3 표준) (자주 액세스되는 데이터 기준의 요금이 항상 적용되어, 거의 액세스되지 않는 파일에 대해서는 비용이 불필요하게 높습니다)
- B. **S3 Intelligent-Tiering (S3 지능형 계층화)**
- C. S3 Standard-Infrequent Access(S3 Standard-IA) (수명 주기 전체를 저빈도 요금으로 고정하므로, 자주 액세스되는 파일에는 검색 비용이 추가로 발생해 오히려 비쌉니다)
- D. S3 One Zone-Infrequent Access(S3 One Zone-IA) (단일 가용 영역에만 데이터를 저장하므로 AZ 손실에 대한 복원력 요구 사항을 충족하지 못합니다)

**정답: B**

**해설**
핵심 조건은 "액세스 패턴을 예측할 수 없음"과 "AZ 손실에 대한 복원력"입니다. **S3 Intelligent-Tiering**은 객체별 액세스 패턴을 자동으로 모니터링하여 일정 기간 액세스가 없으면 저빈도 계층으로, 다시 액세스되면 빈번 계층으로 자동 이동시켜 별도의 수명 주기 규칙 설계 없이도 비용을 최적화합니다. 또한 표준 계층과 마찬가지로 여러 AZ에 데이터를 복제하므로 복원력 요구 사항도 함께 충족합니다.

**왜 다른 보기는 오답인가**
- A: 모든 객체에 자주 액세스 요금이 적용되어, 거의 액세스되지 않는 파일까지 불필요하게 높은 비용을 지불하게 됩니다.
- C: 액세스 빈도가 낮은 데이터 전용 요금 체계이므로, 자주 액세스되는 파일에 검색(retrieval) 비용이 추가되어 비효율적입니다.
- D: 단일 가용 영역에만 저장되므로 AZ 손실 시 데이터를 잃을 수 있어 복원력 요구 사항 자체를 충족하지 못합니다.

> 💡 **시험 꿀팁**: "액세스 패턴을 예측할 수 없다"는 조건이 나오면 S3 Intelligent-Tiering이 표준 정답입니다.

## QUESTION 23

**문제**: 한 회사가 Amazon S3 Standard 스토리지를 사용하여 백업 파일을 저장하고 있습니다. 파일은 처음 1개월 동안 자주 액세스되지만, 1개월이 지난 후에는 전혀 액세스되지 않습니다. 회사는 이 파일들을 무기한 보관해야 합니다. 이러한 요구 사항을 가장 비용 효율적으로 충족하는 스토리지 솔루션은 무엇입니까?

**보기**
- A. 객체를 자동으로 마이그레이션하도록 S3 Intelligent-Tiering을 구성합니다. (모니터링 요금이 추가로 부과되는데, 이 시나리오는 액세스 패턴(1개월 후 완전 미접근)이 이미 명확히 알려져 있어 수명 주기 정책만으로 충분합니다)
- B. **S3 수명 주기 구성을 생성하여 1개월 후에 S3 Standard에서 S3 Glacier Deep Archive로 객체를 전환합니다.**
- C. S3 수명 주기 구성을 생성하여 1개월 후에 객체를 S3 Standard-Infrequent Access(S3 Standard-IA)로 전환합니다. (1개월 이후 완전히 미접근 상태이며 무기한 보관이 목적인데, Standard-IA는 Glacier Deep Archive보다 저장 비용이 훨씬 높아 최적이 아닙니다)
- D. S3 수명 주기 구성을 생성하여 1개월 후에 객체를 S3 One Zone-Infrequent Access(S3 One Zone-IA)로 전환합니다. (Standard-IA보다는 저렴하지만 여전히 Glacier Deep Archive보다 비싸고, 단일 AZ 저장이라 무기한 보관용으로는 내구성 측면에서도 부적합합니다)

**정답: B**

**해설**
"1개월 후 완전 미접근" + "무기한 보관"이라는 두 조건이 만나면 **Amazon S3 Glacier Deep Archive**가 정답입니다. Deep Archive는 S3의 스토리지 클래스 중 가장 저렴하며, 몇 시간의 검색 지연이 허용되는 장기 보존용 데이터에 최적화되어 있습니다. S3 수명 주기 구성을 이용하면 애플리케이션 코드 변경 없이 1개월 경과 시점에 객체를 자동으로 Deep Archive로 전환할 수 있어 저장 비용을 최소화하면서도 무기한 보관 요구를 만족시킵니다.

**왜 다른 보기는 오답인가**
- A: 액세스 패턴이 이미 확정적으로 알려져 있으므로 Intelligent-Tiering의 자동 모니터링 기능은 불필요한 추가 비용만 발생시킵니다.
- C: Standard-IA는 저빈도 액세스용이지만 Deep Archive보다 저장 단가가 훨씬 높아 무기한 보관 목적에는 비효율적입니다.
- D: One Zone-IA도 Deep Archive보다 비싸고, 단일 AZ에만 저장되어 장기 보관 데이터의 내구성 요구에 적합하지 않습니다.

> 💡 **시험 꿀팁**: 특정 시점 이후 완전히 액세스하지 않고 장기간(무기한) 보관만 하면 되는 조건이 나오면 S3 Glacier Deep Archive로의 수명 주기 전환이 표준 정답입니다.

## QUESTION 24

**문제**: 한 회사가 최근 청구서에서 Amazon EC2 비용 증가를 확인했습니다. 청구 팀은 일부 EC2 인스턴스에서 의도하지 않은 인스턴스 유형의 수직적 확장(스케일 업)이 있었음을 발견했습니다. 솔루션 설계자는 지난 2개월간의 EC2 비용을 비교하는 그래프를 생성하고 심층 분석을 수행하여 수직적 확장의 근본 원인을 파악해야 합니다. 솔루션 설계자는 운영 오버헤드를 최소화하면서 이 정보를 어떻게 생성해야 합니까?

**보기**
- A. AWS Budgets를 사용하여 예산 보고서를 생성하고 인스턴스 유형에 따라 EC2 비용을 비교합니다. (Budgets는 예산 설정 및 초과 알림에 특화된 서비스로, 인스턴스 유형별 세분화된 심층 분석에는 적합하지 않습니다)
- B. **Cost Explorer의 세분화된 필터링 기능을 사용하여 인스턴스 유형을 기준으로 EC2 비용에 대한 심층 분석을 수행합니다.**
- C. AWS Billing and Cost Management 대시보드의 그래프를 사용하여 지난 2개월 동안의 인스턴스 유형 기준 EC2 비용을 비교합니다. (기본 대시보드는 개괄적인 비용 요약만 제공할 뿐, 인스턴스 유형 단위의 세분화된 필터링·근본 원인 분석 기능은 제한적입니다)
- D. AWS 비용 및 사용 보고서(Cost and Usage Report)를 생성해 Amazon S3 버킷으로 보내고, Amazon QuickSight로 대화형 그래프를 생성합니다. (기능적으로는 가능하지만 보고서 생성, S3 연동, QuickSight 구축까지 필요해 운영 오버헤드가 훨씬 큽니다)

**정답: B**

**해설**
**AWS Cost Explorer**는 별도의 인프라 구축 없이 콘솔에서 바로 비용과 사용량을 시각화하고 분석할 수 있는 관리형 도구입니다. 특히 세분화된 필터링(인스턴스 유형, 리전, 태그 등) 기능을 사용하면 최근 몇 개월간의 추세를 비교하고, 어떤 인스턴스 유형에서 비용이 급증했는지 빠르게 파고들 수 있어 "운영 오버헤드 최소화"라는 요구 사항에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: Budgets는 임계값 초과 알림에 초점이 맞춰져 있어 세분화된 근본 원인 분석 도구로는 적합하지 않습니다.
- C: 기본 Billing 대시보드는 요약 수준의 그래프만 제공하며 Cost Explorer만큼 정교한 필터링을 지원하지 않습니다.
- D: 원하는 결과를 얻을 수는 있으나 보고서 파이프라인과 QuickSight 대시보드를 직접 구축·유지해야 하므로 운영 부담이 훨씬 큽니다.

> 💡 **시험 꿀팁**: 특정 항목(인스턴스 유형 등) 기준으로 비용을 세분화해 심층 분석해야 한다는 조건이 나오면 Cost Explorer의 필터링 기능이 표준 정답입니다.

## QUESTION 25

**문제**: 한 회사가 애플리케이션을 설계하고 있습니다. 이 애플리케이션은 Amazon API Gateway를 통해 AWS Lambda 함수로 정보를 수신하고, 이를 Amazon Aurora PostgreSQL 데이터베이스에 저장합니다. 개념 증명(PoC) 단계에서 회사는 데이터베이스에 적재해야 하는 대용량 데이터를 처리하기 위해 Lambda 동시 실행 할당량을 크게 늘려야 했습니다. 솔루션 설계자는 확장성을 개선하고 구성 부담을 최소화하는 새로운 설계를 권장해야 합니다. 어떤 솔루션이 이 요구 사항을 충족합니까?

**보기**
- A. Lambda 함수 코드를 Amazon EC2 인스턴스에서 실행되는 Apache Tomcat 코드로 리팩터링하고, 네이티브 JDBC 드라이버로 데이터베이스에 연결합니다. (서버리스 구조를 포기하고 EC2를 직접 프로비저닝·관리해야 하므로 구성 부담과 운영 오버헤드가 오히려 증가합니다)
- B. 플랫폼을 Aurora에서 Amazon DynamoDB와 DynamoDB Accelerator(DAX) 클러스터로 변경하고, DAX 클라이언트 SDK로 기존 DynamoDB API 호출을 DAX로 전환합니다. (관계형 데이터베이스를 완전히 다른 NoSQL 플랫폼으로 교체하는 대규모 마이그레이션이 필요해 요구 사항에 맞지 않습니다)
- C. 두 개의 Lambda 함수를 구성하여 하나는 정보 수신, 다른 하나는 데이터베이스 적재를 담당하게 하고 Amazon SNS로 두 함수를 통합합니다. (SNS는 발행-구독 알림 서비스로 메시지를 버퍼링하지 않아, 대량 유입 시 그대로 다운스트림 Lambda와 데이터베이스에 부하가 전달됩니다)
- D. **두 개의 Lambda 함수를 구성하여 하나는 정보 수신, 다른 하나는 데이터베이스 적재를 담당하게 하고 Amazon SQS 대기열로 두 함수를 통합합니다.**

**정답: D**

**해설**
대량의 데이터가 한꺼번에 유입될 때 문제의 본질은 수신 속도와 처리(DB 적재) 속도의 불일치입니다. **Amazon SQS**를 두 Lambda 함수 사이에 두면 큐가 버퍼 역할을 하여 트래픽 스파이크를 흡수하고, 적재용 Lambda는 자신의 처리 속도에 맞춰 큐에서 메시지를 꺼내 가므로 Lambda 동시 실행 수를 인위적으로 늘리지 않고도 확장성을 확보할 수 있습니다. 이는 구성 변경도 단순해 운영 부담이 적습니다.

- B: 요구 사항은 기존 Aurora PostgreSQL 기반 설계의 확장성 개선이지, 데이터베이스 플랫폼 자체의 교체가 아닙니다.
- C: SNS는 메시지 버퍼링이나 순서 보장이 없는 알림 서비스라서, 대량 유입 시 병목이나 유실 위험을 그대로 남겨둡니다.

> 💡 **시험 꿀팁**: 대량 데이터 처리와 확장성 개선이 동시에 필요할 때 Lambda 두 개 사이에 SQS 큐를 두어 완충하는 구조가 표준 정답입니다.

## QUESTION 28

**문제**: 한 회사가 애플리케이션을 AWS로 마이그레이션하고 있으며, 애플리케이션은 여러 계정에 분산 배포됩니다. 회사는 AWS Organizations로 계정을 중앙에서 관리합니다. 보안 팀은 회사의 모든 계정에 SSO(Single Sign-On) 솔루션이 필요하다고 요구하지만, 사용자와 그룹은 계속해서 사내 자체 관리형 Microsoft Active Directory에서 관리해야 합니다. 어떤 솔루션이 이 요구 사항을 충족합니까?

## QUESTION 29

**문제**: 한 회사가 UDP 연결을 사용하는 VoIP(Voice over Internet Protocol) 서비스를 제공합니다. 이 서비스는 Auto Scaling 그룹에서 실행되는 Amazon EC2 인스턴스로 구성되며, 회사는 여러 AWS 리전에 배포하고 있습니다. 회사는 사용자를 지연 시간이 가장 짧은 리전으로 라우팅해야 하며, 리전 간 자동 장애 조치도 필요합니다. 어떤 솔루션이 이 요구 사항을 충족합니까?

**보기**
- A. **NLB(Network Load Balancer)와 연결된 대상 그룹을 배포하고 Auto Scaling 그룹과 연결합니다. 각 리전의 NLB를 AWS Global Accelerator의 엔드포인트로 사용합니다.**
- B. ALB(Application Load Balancer)와 연결된 대상 그룹을 배포하고 Auto Scaling 그룹과 연결합니다. 각 리전의 ALB를 AWS Global Accelerator의 엔드포인트로 사용합니다. (ALB는 HTTP/HTTPS 계층에서만 동작하여 UDP 트래픽을 처리할 수 없습니다)
- C. NLB와 연결된 대상 그룹을 배포하고, 각 NLB의 별칭을 가리키는 Amazon Route 53 지연 시간 레코드를 생성한 뒤 이를 오리진으로 하는 CloudFront 배포를 생성합니다. (CloudFront는 HTTP/HTTPS 기반 CDN으로 UDP 트래픽을 전달할 수 없고, Route 53 지연 시간 라우팅은 DNS TTL에 의존해 Global Accelerator의 애니캐스트 방식보다 장애 조치가 느립니다)
- D. ALB와 연결된 대상 그룹을 배포하고, 각 ALB의 별칭을 가리키는 Route 53 가중치 레코드를 생성한 뒤 이를 오리진으로 하는 CloudFront 배포를 배포합니다. (ALB는 UDP를 지원하지 않고, 가중치 라우팅은 지연 시간 기반 라우팅이 아니며 CloudFront 역시 UDP를 지원하지 않습니다)

**정답: A**

**해설**
UDP를 처리할 수 있는 로드 밸런서는 **NLB**뿐이며, 리전 간 지연 시간 기반 라우팅과 즉각적인 자동 장애 조치가 필요하다면 **AWS Global Accelerator**가 정답입니다. Global Accelerator는 고정된 애니캐스트 IP 주소를 통해 AWS 글로벌 네트워크로 트래픽을 유입시킨 뒤 사용자와 가장 가까운(지연 시간이 가장 짧은) 정상 엔드포인트로 라우팅하며, 상태 확인을 통해 장애 발생 시 즉시 다른 리전으로 트래픽을 전환합니다.

**왜 다른 보기는 오답인가**
- B: ALB는 애플리케이션(HTTP/HTTPS) 계층 로드 밸런서로 UDP 프로토콜을 지원하지 않습니다.
- C: CloudFront는 HTTP/HTTPS 기반 CDN이라 UDP 트래픽 전달이 불가능하며, Route 53 지연 시간 레코드는 DNS 캐시/TTL의 영향을 받아 장애 조치 속도가 Global Accelerator보다 느립니다.
- D: ALB의 UDP 미지원 문제가 동일하게 적용되고, 가중치 라우팅은 지연 시간을 기준으로 하지 않습니다.

> 💡 **시험 꿀팁**: UDP 트래픽 + 리전 간 최저 지연 라우팅 + 자동 장애 조치라는 조건이 함께 나오면 NLB + AWS Global Accelerator 조합이 표준 정답입니다.

- B: Kinesis Data Firehose는 지정된 고정 대상(S3, Redshift, OpenSearch 등)으로 데이터를 전달하는 서비스로, 여러 커스텀 애플리케이션이 동시에 원본 스트림을 자유롭게 소비하는 구조에는 Kinesis Data Streams가 더 적합합니다.
- D: 파일 단위 배치 처리는 파일이 쌓이고 처리되는 동안 지연이 발생해 "거의 실시간"이라는 요구 사항에 부합하지 않습니다.

> 💡 **시험 꿀팁**: 여러 애플리케이션이 동일한 데이터를 실시간으로 각자 소비해야 한다는 조건이 나오면 Kinesis Data Streams가 표준 정답입니다(Firehose는 고정된 대상으로의 단방향 전달용).

- D. AWS CloudTrail로 구성 변경을 추적하고 Amazon CloudWatch로 API 호출을 기록합니다. (구성 변경 추적과 API 호출 기록 모두 각 서비스의 본래 목적과 맞지 않는 매핑입니다)

**정답: B**

**해설**

**왜 다른 보기는 오답인가**
- A: Config와 CloudTrail의 역할이 반대로 서술되어 있습니다.
- C: CloudWatch는 API 호출 이력을 CloudTrail 수준으로 상세히 기록하는 감사 서비스가 아닙니다.
- D: CloudTrail은 구성 변경 이력 자체를 추적하는 서비스가 아니며, CloudWatch도 API 호출 감사에는 적합하지 않습니다.

> 💡 **시험 꿀팁**: 구성 변경 이력은 AWS Config, API 호출 이력은 AWS CloudTrail — 이 매핑을 헷갈리지 않는 것이 핵심입니다.

## QUESTION 35

**문제**: 한 회사가 AWS 클라우드에서 공개 웹 애플리케이션을 출시할 준비를 하고 있습니다. 아키텍처는 Elastic Load Balancer(ELB) 뒤의 VPC 내 Amazon EC2 인스턴스로 구성되며, DNS에는 타사 서비스를 사용합니다. 솔루션 설계자는 대규모 DDoS 공격을 탐지하고 방어할 수 있는 솔루션을 권장해야 합니다. 어떤 솔루션이 이 요구 사항을 충족합니까?

**보기**
- A. 계정에서 Amazon GuardDuty를 활성화합니다. (GuardDuty는 계정과 워크로드 내 악의적 활동을 탐지하는 위협 탐지 서비스로, 대규모 네트워크/전송 계층 DDoS 공격에 특화된 방어 기능은 제공하지 않습니다)
- B. EC2 인스턴스에서 Amazon Inspector를 활성화합니다. (Inspector는 소프트웨어 취약점 및 네트워크 노출을 스캔하는 서비스로 DDoS 방어와는 무관합니다)
- C. AWS Shield를 활성화하고 Amazon Route 53에 할당합니다. (이 회사는 DNS로 타사 서비스를 사용하므로 Route 53에 Shield를 연결해도 실제 서비스 진입점을 보호하지 못하며, 기본 Shield Standard는 대규모·정교한 공격에 대한 고급 방어·가시성 기능이 부족합니다)
- D. **AWS Shield Advanced를 활성화하고 ELB에 할당합니다.**

**정답: D**

**해설**
**AWS Shield Advanced**는 Shield Standard가 기본 제공하는 일반적인 네트워크/전송 계층 DDoS 방어를 넘어, 대규모·정교한 공격에 대한 추가 완화 기능, 실시간에 가까운 공격 가시성, AWS WAF와의 통합, DDoS 공격 관련 요금 보호(Cost Protection)를 제공합니다. 이 애플리케이션의 실제 트래픽 진입점은 ELB이므로 Shield Advanced를 ELB에 연결하는 것이 대규모 DDoS 탐지·방어 요구 사항에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: GuardDuty는 계정 활동 기반의 위협 탐지 서비스이며 DDoS 공격 자체를 방어하지 않습니다.
- B: Inspector는 취약점 스캐닝 서비스로 DDoS와는 목적이 다릅니다.
- C: DNS가 타사 서비스이므로 Route 53에 Shield를 붙이는 것은 실제 방어 지점이 아니며, Shield Standard만으로는 대규모 공격에 대한 고급 방어가 부족합니다.

> 💡 **시험 꿀팁**: 대규모·정교한 DDoS 공격에 대한 탐지와 방어라는 조건이 나오면 AWS Shield Advanced를 실제 트래픽 진입점(ELB, CloudFront 등)에 연결하는 것이 표준 정답입니다.

## QUESTION 36

**문제**: 한 회사가 AWS 클라우드에서 애플리케이션을 구축하고 있습니다. 이 애플리케이션은 두 개의 AWS 리전에 있는 Amazon S3 버킷에 데이터를 저장합니다. 회사는 AWS KMS 고객 관리형 키를 사용해 두 S3 버킷에 저장된 모든 데이터를 암호화해야 하며, 두 버킷의 데이터는 동일한 KMS 키로 암호화·복호화되어야 합니다. 데이터와 키는 각 리전에도 저장되어야 합니다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. 각 리전에 S3 버킷을 생성하고 Amazon S3 관리형 키(SSE-S3)로 서버 측 암호화를 구성한 뒤 버킷 간 복제를 설정합니다. (SSE-S3는 AWS가 완전히 관리하는 키를 사용하므로 고객 관리형 키를 사용해야 한다는 요구 사항 자체를 충족하지 못합니다)
- B. **고객 관리형 다중 리전 KMS 키를 생성하고, 각 리전에 S3 버킷을 생성해 버킷 간 복제를 설정합니다. 애플리케이션이 클라이언트 측 암호화와 함께 이 KMS 키를 사용하도록 구성합니다.**
- C. 각 리전에 고객 관리형 KMS 키와 S3 버킷을 생성하고 SSE-S3로 서버 측 암호화를 구성한 뒤 버킷 간 복제를 설정합니다. (A와 마찬가지로 SSE-S3는 고객 관리형 키를 사용하지 않으므로, 리전마다 고객 관리형 키를 만들어도 실제로는 사용되지 않습니다)
- D. 각 리전에 고객 관리형 KMS 키와 S3 버킷을 생성하고 SSE-KMS로 서버 측 암호화를 구성한 뒤 버킷 간 복제를 설정합니다. (KMS 키로 암호화된 객체를 업로드하려면 키와 버킷이 동일한 리전에 있어야 하고, 일반 KMS 키는 리전마다 독립적으로 생성되므로 두 리전에서 "동일한" 키를 공유할 수 없습니다)

**정답: B**

**해설**
일반적인 AWS KMS 키는 특정 리전에 종속되지만, **다중 리전 키(Multi-Region Key)**를 사용하면 여러 리전에 동일한 키 자재를 가진 복제 키를 만들어 사실상 "동일한 키"로 취급할 수 있습니다. 다만 SSE-KMS는 객체를 암호화할 때 사용하는 키와 버킷이 같은 리전에 있어야 하는 제약이 있으므로, 두 리전에 걸쳐 진짜 동일한 키로 암복호화하려면 **클라이언트 측 암호화**로 애플리케이션이 직접 다중 리전 KMS 키를 사용해 암호화한 뒤 S3에 업로드하는 방식이 필요합니다. 이렇게 하면 리전 제약 없이 동일한 고객 관리형 키로 양쪽 데이터를 암복호화할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: SSE-S3는 AWS 관리형 키를 사용하므로 "고객 관리형 키 사용"이라는 핵심 요구 사항을 아예 충족하지 못합니다.
- C: 고객 관리형 키를 리전마다 만들어도 실제 암호화 방식이 SSE-S3이므로 그 키가 사용되지 않습니다.
- D: SSE-KMS는 키와 버킷이 동일 리전에 있어야 하고, 일반 KMS 키는 리전별로 독립적이라 두 리전이 진짜 동일한 키를 공유할 수 없습니다.

> 💡 **시험 꿀팁**: 여러 리전에서 동일한 고객 관리형 KMS 키로 암·복호화해야 한다는 조건이 나오면 다중 리전 KMS 키 + 클라이언트 측 암호화가 표준 정답입니다(SSE-KMS는 키와 버킷이 같은 리전에 있어야 함을 기억하세요).

## QUESTION 37

**문제**: 한 회사가 최근 AWS 계정의 Amazon EC2 인스턴스에서 다양한 새 워크로드를 출시했습니다. 회사는 이 인스턴스들에 원격으로 안전하게 접속하고 관리하는 전략을 수립해야 하며, 기본 AWS 서비스와 함께 동작하고 AWS Well-Architected 프레임워크를 따르는 반복 가능한 프로세스가 필요합니다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇입니까?

- D: VPN 인프라까지 구축해야 하고 여전히 SSH 키 관리가 필요해 운영 오버헤드가 가장 큽니다.

## QUESTION 38

**문제**: 한 회사가 Amazon S3에서 정적 웹 사이트를 호스팅하며 DNS에는 Amazon Route 53을 사용하고 있습니다. 웹 사이트에 대한 전 세계적 수요가 증가하고 있어, 회사는 웹 사이트에 접속하는 사용자의 지연 시간을 줄여야 합니다. 어떤 솔루션이 이 요구 사항을 가장 비용 효율적으로 충족합니까?

**보기**
- A. 웹 사이트가 담긴 S3 버킷을 모든 AWS 리전에 복제하고 Route 53 지리적 위치 라우팅 레코드를 추가합니다. (콘텐츠가 갱신될 때마다 모든 리전의 버킷에 복제해야 해 관리 부담과 스토리지 비용이 크게 증가합니다)
- B. AWS Global Accelerator에서 액셀러레이터를 프로비저닝하고 제공된 IP 주소를 S3 버킷에 연결한 뒤, 해당 IP를 가리키도록 Route 53 레코드를 편집합니다. (Global Accelerator는 TCP/UDP 기반 네트워크 계층 서비스로 S3를 직접 엔드포인트로 연결할 수 없어 이 구성 자체가 성립하지 않습니다)
- C. **S3 버킷 앞에 Amazon CloudFront 배포를 추가하고, 이 CloudFront 배포를 가리키도록 Route 53 레코드를 편집합니다.**
- D. 버킷에서 S3 Transfer Acceleration을 활성화하고 새 엔드포인트를 가리키도록 Route 53 레코드를 편집합니다. (Transfer Acceleration은 전 세계에서 하나의 버킷으로 업로드하는 속도를 높이는 기능으로, 사용자가 콘텐츠를 다운로드할 때의 지연 시간 감소와는 목적이 다릅니다)

**정답: C**

**해설**
**Amazon CloudFront**는 전 세계 엣지 로케이션에 정적 콘텐츠를 캐싱하는 CDN으로, S3 버킷 앞단에 배치하면 사용자가 자신과 가장 가까운 엣지에서 콘텐츠를 받아 지연 시간이 크게 줄어듭니다. 데이터 전송 비용도 S3에서 직접 전송하는 것보다 효율적으로 설계되어 있으며, Route 53에서 CloudFront 배포를 가리키는 별칭(alias) 레코드만 추가하면 되어 구성도 간단합니다.

**왜 다른 보기는 오답인가**
- A: 전 리전 복제는 콘텐츠 변경 시마다 동기화 비용과 관리 부담이 커 비효율적입니다.
- B: Global Accelerator는 네트워크 계층에서 동작하며 S3를 직접적인 엔드포인트로 지원하지 않아 아키텍처가 성립하지 않습니다.
- D: Transfer Acceleration은 업로드 가속 기능으로, 전 세계 사용자의 다운로드 지연 시간 감소라는 목표에는 맞지 않습니다.

> 💡 **시험 꿀팁**: S3 정적 웹 사이트의 전 세계 사용자 지연 시간을 가장 비용 효율적으로 줄여야 한다는 조건이 나오면 CloudFront를 앞단에 두는 것이 표준 정답입니다.

## QUESTION 39

**문제**: 한 회사가 웹 사이트에서 검색 가능한 항목 저장소를 유지 관리합니다. 데이터는 천만 개 이상의 행이 있는 Amazon RDS for MySQL 테이블에 저장되며, 데이터베이스는 2TB의 범용 SSD 스토리지를 사용합니다. 웹 사이트를 통해 매일 수백만 건의 업데이트가 발생하는데, 일부 삽입(insert) 작업이 10초 이상 걸리는 문제가 확인되었습니다. 회사는 데이터베이스 스토리지 성능이 원인이라고 판단했습니다. 이 성능 문제를 해결하는 솔루션은 무엇입니까?

**보기**
- A. **스토리지 유형을 프로비저닝된 IOPS SSD(io1/io2)로 변경합니다.**
- B. DB 인스턴스를 메모리 최적화 인스턴스 클래스로 변경합니다. (문제의 원인은 이미 스토리지 I/O 성능으로 특정되었으므로, 컴퓨팅/메모리 계층을 바꾸는 것은 근본 원인을 해결하지 못합니다)
- C. DB 인스턴스를 버스트 가능한 성능 인스턴스 클래스로 변경합니다. (버스트 가능 인스턴스는 누적된 CPU 크레딧을 소진하면 기준 성능 이하로 저하되며, 애초에 CPU가 아닌 스토리지 I/O 병목을 근본적으로 개선하지 못합니다)
- D. MySQL 기본 비동기 복제를 사용하는 다중 AZ RDS 읽기 전용 복제본을 활성화합니다. (읽기 복제본은 읽기 트래픽 분산에 유용할 뿐, 쓰기(삽입) 경로의 기본 스토리지 I/O 병목 자체는 해결하지 못합니다)

**정답: A**

**해설**
범용 SSD(gp2/gp3) 스토리지는 기준 IOPS와 버스트 크레딧 모델로 동작하기 때문에, 지속적으로 대량의 쓰기가 발생하면 크레딧이 소진되어 삽입 지연이 급격히 늘어날 수 있습니다. **프로비저닝된 IOPS SSD(Provisioned IOPS, io1/io2)**는 요청한 IOPS를 일관되게 보장하도록 설계된 스토리지 유형으로, I/O 집약적인 데이터베이스 워크로드의 지연 시간을 안정적으로 낮출 수 있어 근본적인 스토리지 성능 문제를 해결합니다.

**왜 다른 보기는 오답인가**
- B: 메모리 최적화는 연산·캐싱 성능을 높일 뿐, 디스크 I/O 처리량 자체를 늘리지 못합니다.
- C: 버스트 가능 인스턴스는 CPU 크레딧 모델을 사용하며, 크레딧이 소진되면 오히려 성능이 기준선 이하로 떨어져 지속적인 쓰기 부하에는 적합하지 않습니다.
- D: 읽기 전용 복제본은 읽기 부하 분산 수단이며, 문제가 되는 삽입(쓰기) 작업의 스토리지 병목과는 직접적인 관련이 없습니다.

> 💡 **시험 꿀팁**: 삽입/쓰기 지연이 스토리지 I/O 성능 문제로 확인되면 프로비저닝된 IOPS SSD로 전환하는 것이 표준 정답입니다.

## QUESTION 40

**문제**: 한 회사에 수천 개의 에지 장치가 있으며, 이 장치들은 매일 총 1TB의 상태 알림을 생성합니다. 각 알림의 크기는 약 2KB입니다. 솔루션 설계자는 향후 분석을 위해 이 알림을 수집·저장하는 솔루션을 구현해야 합니다. 회사는 고가용성을 원하지만 비용은 최소화해야 하며 추가 인프라 관리는 원하지 않습니다. 또한 즉각적인 분석을 위해 14일간의 데이터를 유지하고, 14일이 지난 데이터는 보관(archive)하기를 원합니다. 이 요구 사항을 가장 운영 효율적으로 충족하는 솔루션은 무엇입니까?

**보기**
- A. **Amazon Kinesis Data Firehose 전송 스트림을 생성해 알림을 수집하고, Amazon S3 버킷으로 전달하도록 구성합니다. 14일 후 데이터를 Amazon S3 Glacier로 전환하는 S3 수명 주기 구성을 설정합니다.**
- B. 두 가용 영역에서 Amazon EC2 인스턴스를 기동해 Elastic Load Balancer 뒤에 배치하고 알림을 수집합니다. EC2 인스턴스가 S3 버킷에 알림을 저장하도록 스크립트를 작성하고, 14일 후 S3 Glacier로 전환하는 수명 주기 구성을 설정합니다. (EC2 인스턴스와 로드 밸런서를 직접 프로비저닝·운영해야 해 "추가 인프라 관리를 원하지 않는다"는 요구 사항에 정면으로 위배됩니다)
- C. Kinesis Data Firehose로 알림을 수집해 Amazon OpenSearch Service 클러스터로 전달하고, 매일 수동 스냅샷을 생성한 뒤 클러스터에서 14일이 지난 데이터를 삭제합니다. (14일이 지난 데이터를 보관해야 하는데 삭제해 버리므로 요구 사항을 충족하지 못하며, OpenSearch 클러스터의 수동 스냅샷·용량 관리도 추가적인 운영 부담입니다)
- D. Amazon SQS 표준 대기열을 생성해 알림을 수집하고 메시지 보존 기간을 14일로 설정합니다. 소비자가 대기열을 폴링하며 메시지 수명을 확인하고, 14일이 지난 메시지는 S3에 복사한 뒤 대기열에서 삭제하도록 구성합니다. (메시지 수명 관리, S3로의 이관, 삭제 로직까지 모두 커스텀 소비자 애플리케이션으로 직접 구현·운영해야 해 운영 효율성이 크게 떨어집니다)

**정답: A**

**해설**
**Kinesis Data Firehose**는 완전관리형 서비스로 수천 개의 소스에서 유입되는 데이터를 별도 인프라 관리 없이 자동으로 지정된 대상(S3 등)에 전달하며, 기본적으로 여러 AZ에 걸쳐 고가용성을 제공합니다. 전달된 데이터를 **S3**에 저장해 두면 14일간은 즉시 조회·분석이 가능하고, **S3 수명 주기 정책**을 통해 14일이 지난 객체를 자동으로 **Glacier**로 전환해 저비용으로 장기 보관할 수 있습니다. 이 조합은 서버나 클러스터를 직접 운영하지 않고도 모든 요구 사항(고가용성, 저비용, 14일 유지 후 보관)을 만족시킵니다.

**왜 다른 보기는 오답인가**
- B: EC2와 ELB를 직접 구축·운영해야 해 "추가 인프라 관리를 원하지 않는다"는 핵심 조건에 위배됩니다.
- C: 14일이 지난 데이터를 보관이 아니라 삭제하므로 요구 사항을 충족하지 못하고, 클러스터의 수동 스냅샷 관리도 부담이 큽니다.
- D: SQS는 데이터 저장소가 아니라 메시징 큐이므로, 메시지 수명 확인과 S3로의 이관 로직을 모두 직접 구현해야 해 운영 효율성이 떨어집니다.

> 💡 **시험 꿀팁**: 완전관리형으로 대량의 스트리밍 데이터를 수집하고, 일정 기간 후 저비용으로 보관해야 한다는 조건이 나오면 Kinesis Data Firehose → S3 → 수명 주기 정책으로 Glacier 전환하는 조합이 표준 정답입니다.
