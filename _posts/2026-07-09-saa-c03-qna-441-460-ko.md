## QUESTION 441

**문제**: 한 온라인 멀티플레이어 게임 회사는 전 세계 사용자를 대상으로 실시간 UDP 기반 게임 서버를 운영하고 있습니다. 이 회사는 사용자가 가장 가까운 정상 상태의 엔드포인트로 낮은 지연 시간에 라우팅되기를 원하며, 콘텐츠를 캐싱할 필요는 없습니다. 최소한의 설정 변경으로 전 세계 트래픽 라우팅 성능을 개선할 수 있는 솔루션 아키텍트의 권장 사항은 무엇입니까?

**보기**
- A. **AWS Global Accelerator를 사용하여 UDP/TCP 트래픽을 Anycast IP를 통해 가장 가까운 AWS 엣지 로케이션으로 라우팅하고, 상태 확인 결과에 따라 최적의 엔드포인트로 전달한다.**
- B. Amazon CloudFront를 사용하여 게임 서버 트래픽을 캐싱하고 엣지 로케이션에서 배포한다 (CloudFront는 HTTP/HTTPS 콘텐츠 캐싱에 최적화된 서비스로, 캐싱이 불가능한 실시간 UDP 트래픽에는 적합하지 않다).
- C. Amazon Route 53 지연 시간 기반 라우팅 정책만 사용하여 리전별로 트래픽을 분산한다 (DNS 조회 결과를 클라이언트가 캐싱하므로 장애 조치나 최적 경로 변경이 즉시 반영되지 않는다).
- D. 각 리전에 별도의 Application Load Balancer를 배치하고 사용자가 수동으로 접속할 엔드포인트를 선택하게 한다 (ALB는 UDP를 지원하지 않으며, 수동 선택 방식은 운영 부담이 크고 확장성이 없다).

**정답: A**

**해설**: **AWS Global Accelerator**는 Anycast IP 주소를 사용해 TCP 및 UDP 트래픽을 AWS 글로벌 네트워크를 통해 사용자와 가장 가까운 엣지 로케이션으로 라우팅한 후, 상태 확인 결과에 따라 가장 성능이 좋은 정상 엔드포인트로 트래픽을 전달합니다. 이는 캐싱이 필요 없는 실시간 게임 트래픽처럼 비 HTTP 기반 워크로드의 전역 라우팅 성능을 개선하는 데 적합합니다.

**왜 다른 보기는 오답인가**
- B: CloudFront는 콘텐츠 캐싱을 위한 CDN 서비스로, 캐싱이 불가능한 UDP 기반 실시간 트래픽 라우팅에는 적합하지 않습니다.
- C: Route 53 지연 시간 라우팅만으로는 DNS TTL 캐싱으로 인해 빠른 장애 조치가 어렵습니다.
- D: ALB는 UDP를 지원하지 않으며 수동 엔드포인트 선택은 확장성이 없습니다.

> 💡 **시험 꿀팁**: 캐싱 가능한 HTTP 콘텐츠는 CloudFront, 캐싱 불가능한 TCP/UDP 실시간 트래픽의 전역 라우팅 개선은 Global Accelerator로 구분해서 기억하세요.

## QUESTION 442

**문제**: 한 물류 회사는 프라이빗 서브넷의 EC2 인스턴스가 소프트웨어 업데이트를 위해 아웃바운드 인터넷 연결이 필요합니다. 현재는 EC2 NAT 인스턴스를 직접 구성하고 가용 영역 간 장애 조치를 위한 커스텀 스크립트를 운영하고 있지만, 인스턴스 장애 시 다운타임이 발생하고 있습니다. 운영 부담을 줄이면서 아웃바운드 연결의 복원력을 높이려면 어떻게 해야 합니까?

**보기**
- A. 기존 NAT 인스턴스를 Auto Scaling 그룹으로 감싸고 상태 확인 및 커스텀 장애 조치 스크립트를 계속 유지한다 (여전히 인스턴스 패치, 대역폭 확장, 장애 조치 로직을 직접 관리해야 하며 완전한 관리형 서비스가 아니다).
- B. **각 가용 영역에 관리형 NAT 게이트웨이를 배포하여 AWS가 가용성, 확장성, 소프트웨어 패치를 자동으로 관리하도록 한다.**
- C. 프라이빗 서브넷의 라우팅 테이블을 인터넷 게이트웨이로 직접 연결한다 (프라이빗 서브넷을 사실상 퍼블릭으로 노출시켜 보안 요구사항에 위배된다).
- D. NAT 인스턴스 앞에 Network Load Balancer를 배치해 여러 NAT 인스턴스로 트래픽을 분산한다 (여전히 인스턴스 관리, 패치, 확장을 직접 수행해야 하며 관리형 서비스보다 운영 부담이 크다).

**정답: B**

**해설**: **NAT 게이트웨이**는 AWS가 완전히 관리하는 서비스로, 가용 영역 내에서 고가용성을 제공하며 최대 100Gbps까지 자동으로 확장되고 별도의 패치나 장애 조치 스크립트가 필요 없습니다. 각 가용 영역에 하나씩 NAT 게이트웨이를 배포하면 특정 가용 영역 장애가 다른 가용 영역의 아웃바운드 연결에 영향을 주지 않아 복원력이 향상됩니다.

**왜 다른 보기는 오답인가**
- A: NAT 인스턴스 기반 접근은 Auto Scaling을 추가해도 여전히 OS 패치와 장애 조치 로직을 직접 관리해야 합니다.
- C: 프라이빗 서브넷을 인터넷 게이트웨이에 직접 연결하면 보안이 크게 저하됩니다.
- D: NLB를 앞에 두어도 NAT 인스턴스 자체의 관리 부담은 사라지지 않습니다.

> 💡 **시험 꿀팁**: "직접 관리하는 NAT 인스턴스" vs "완전 관리형 NAT 게이트웨이"가 보기로 함께 나오면, 운영 부담과 고가용성을 이유로 항상 NAT 게이트웨이가 정답입니다.

## QUESTION 443

**문제**: 한 SaaS 기업은 프로덕션 Amazon RDS 데이터베이스에 대해 위험도가 높은 스키마 변경과 메이저 버전 업그레이드를 계획하고 있습니다. 서비스 다운타임을 최소화하면서 문제가 발생할 경우 신속하게 이전 상태로 되돌릴 수 있는 방법이 필요합니다. 어떤 솔루션을 사용해야 합니까?

**보기**
- A. RDS 읽기 전용 복제본을 생성해 프로덕션에서 직접 스키마를 변경하며 테스트한다 (읽기 전용 복제본은 원본의 변경 사항을 그대로 복제하는 용도로, 별도의 독립적인 스키마 변경 테스트 환경을 제공하지 않는다).
- B. 데이터베이스를 스냅숏으로 백업한 뒤 프로덕션에서 직접 스키마를 변경하고 문제가 생기면 스냅숏에서 복원한다 (스냅숏 복원은 시간이 오래 걸려 그동안 서비스 중단이 발생하며, 복원 시점 이후의 데이터가 유실될 위험이 있다).
- C. **Amazon RDS Blue/Green Deployments를 사용해 프로덕션과 동일한 그린 환경을 생성하고, 그린 환경에서 스키마 변경을 충분히 검증한 뒤 안전하게 전환하며 필요 시 신속히 롤백한다.**
- D. Multi-AZ 대기 인스턴스를 강제로 페일오버시켜 그동안 스키마를 변경한다 (Multi-AZ 페일오버는 동일한 데이터베이스의 동기화된 복제본으로 전환하는 것일 뿐, 별도의 격리된 테스트 환경을 제공하지 않는다).

**정답: C**

**해설**: **Amazon RDS Blue/Green Deployments**는 프로덕션(블루) 환경과 동기화된 별도의 스테이징(그린) 환경을 자동으로 생성해줍니다. 그린 환경에서 스키마 변경이나 엔진 업그레이드를 충분히 검증한 후, 애플리케이션 다운타임을 최소화하며 트래픽을 전환할 수 있고, 문제가 발생하면 빠르게 원래 환경으로 되돌릴 수 있어 위험도가 높은 변경 작업에 적합합니다.

**왜 다른 보기는 오답인가**
- A: 읽기 전용 복제본은 원본과 동일한 스키마를 유지해야 하므로 독립적인 스키마 변경 테스트에 적합하지 않습니다.
- B: 스냅숏 복원 방식은 복원 시간 동안 다운타임이 발생하고 데이터 유실 위험이 있습니다.
- D: Multi-AZ 페일오버는 별도의 테스트 환경을 제공하지 않으며 스키마 검증 목적에 맞지 않습니다.

> 💡 **시험 꿀팁**: "위험한 스키마 변경/메이저 버전 업그레이드 + 다운타임 최소화 + 쉬운 롤백"이라는 키워드 조합은 RDS Blue/Green Deployments를 가리킵니다.

## QUESTION 444

**문제**: 한 핀테크 회사는 금융 거래 메시지를 처리하는 큐를 설계하고 있습니다. 요구사항은 메시지가 반드시 발생한 순서대로 처리되어야 하고, 동일한 거래가 중복으로 처리되지 않아야 한다는 것입니다. 이 요구사항을 충족하는 메시징 솔루션은 무엇입니까?

**보기**
- A. Amazon SQS 표준 큐를 사용하고 애플리케이션에서 자체적으로 중복 제거 로직을 구현한다 (표준 큐는 최소 한 번 이상 전달 방식이며 순서를 best-effort로만 보장하므로 엄격한 순서와 중복 방지를 완전히 충족하지 못한다).
- B. Amazon SNS 표준 주제를 사용해 트랜잭션 메시지를 여러 구독자에게 팬아웃한다 (SNS 표준 주제는 메시지 순서 보장이나 중복 제거 기능을 제공하지 않는다).
- C. Amazon Kinesis Data Streams를 사용하고 컨슈머 애플리케이션이 직접 중복 제거 로직을 구현하도록 한다 (샤드 내 순서는 보장되지만 중복 제거는 애플리케이션이 별도로 구현해야 하는 추가 부담이 있다).
- D. **Amazon SQS FIFO 큐와 메시지 그룹 ID, 콘텐츠 기반 중복 제거 기능을 사용해 메시지 처리 순서와 exactly-once에 가까운 처리를 보장한다.**

**정답: D**

**해설**: **Amazon SQS FIFO 큐**는 메시지 그룹 내에서 메시지가 전송된 순서대로 처리되는 것을 보장하며, 콘텐츠 기반 중복 제거 또는 명시적 중복 제거 ID를 사용하면 5분의 중복 제거 구간 내에서 동일한 메시지가 큐에 두 번 추가되지 않도록 방지합니다. 이는 금융 거래처럼 순서와 정확성이 중요한 워크로드에 적합합니다.

**왜 다른 보기는 오답인가**
- A: 표준 큐는 순서를 엄격히 보장하지 않고 중복 전달 가능성이 있어 자체 구현만으로는 완전한 해결이 어렵습니다.
- B: SNS 표준 주제는 순서 보장이나 중복 제거 기능 자체가 없습니다.
- C: Kinesis는 순서는 보장하지만 중복 제거는 기본 제공 기능이 아니라 별도 구현이 필요합니다.

> 💡 **시험 꿀팁**: "엄격한 순서 + 중복 방지"라는 키워드가 함께 나오면 SQS FIFO 큐(메시지 그룹 ID + 중복 제거)를 떠올리세요.

## QUESTION 445

**문제**: 빠르게 성장하는 한 기업이 여러 사업부를 위한 다계정 AWS 환경을 새로 구축하려고 합니다. 이 기업은 모범 사례에 기반한 계정 구조와 가드레일을 자동으로 설정하고, 조직 전체에 걸쳐 거버넌스를 일관되게 적용하고 싶어 합니다. 어떤 서비스를 사용해야 합니까?

**보기**
- A. **AWS Control Tower를 사용해 모범 사례 기반의 랜딩존을 자동으로 설정하고, 조직 단위(OU)와 사전 정의된 가드레일을 통해 다계정 환경을 거버넌스한다.**
- B. 모든 팀을 위한 단일 AWS 계정을 생성하고 IAM 정책만으로 리소스를 논리적으로 격리한다 (단일 계정 구조는 장애나 보안 사고 발생 시 영향 범위가 커지고 청구 및 권한 분리가 어려워 확장성이 떨어진다).
- C. AWS Organizations만 수동으로 구성하고 각 계정에 개별적으로 SCP와 로깅을 설정한다 (수동 구성은 반복 가능한 표준화된 가드레일 적용이 어렵고 계정이 늘어날수록 관리 부담이 급격히 커진다).
- D. AWS Config를 각 계정에 개별 배포해 규정 준수 여부만 모니터링한다 (Config는 규정 준수 모니터링 도구일 뿐 계정 프로비저닝이나 랜딩존 구성 자체를 자동화하지 않는다).

**정답: A**

**해설**: **AWS Control Tower**는 AWS Organizations, IAM Identity Center, AWS Config 등을 조합하여 모범 사례가 반영된 다계정 랜딩존을 자동으로 구축해줍니다. 조직 단위(OU)별로 사전 정의된 가드레일(예방적/탐지적 통제)을 일괄 적용할 수 있어, 계정이 늘어나도 일관된 거버넌스를 유지할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 단일 계정 구조는 폭발 반경이 커지고 부서별 격리가 어렵습니다.
- C: 수동 구성은 반복 가능성이 낮고 계정이 증가할수록 관리 부담이 커집니다.
- D: Config만으로는 새 계정 프로비저닝이나 표준 랜딩존 구성을 자동화할 수 없습니다.

> 💡 **시험 꿀팁**: "다계정 환경을 처음부터 모범 사례에 따라 자동으로 구축"이라는 표현이 나오면 AWS Control Tower를 떠올리세요.

## QUESTION 446

- B. 각 팀을 위해 동일한 데이터를 별도의 버킷으로 복제하여 개별적으로 관리한다 (데이터 복제는 스토리지 비용과 동기화 복잡성을 증가시키며 근본적인 관리 단순화 방법이 아니다).

- D. IAM 사용자를 팀별로 생성하고 각 사용자에게 버킷 전체에 대한 권한을 부여한다 (버킷 전체에 대한 권한 부여는 최소 권한 원칙에 위배되며 세분화된 접근 관리가 어렵다).

**정답: A**

**해설**: **Amazon S3 Access Points**는 하나의 버킷에 대해 애플리케이션이나 팀별로 고유한 호스트 이름과 전용 접근 정책을 가진 여러 개의 접근 지점을 생성할 수 있게 해줍니다. 각 Access Point는 독립적인 정책을 가지므로 단일 버킷 정책의 복잡도를 낮추고, 팀이나 애플리케이션이 늘어나도 접근 관리를 손쉽게 확장할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 데이터 복제는 비용과 동기화 복잡성만 늘릴 뿐 접근 관리 자체를 단순화하지 못합니다.
- C: 단일 버킷 정책에 조건을 계속 추가하면 관리가 어려워지고 정책 크기 제한에 부딪힐 수 있습니다.
- D: 버킷 전체 권한 부여는 최소 권한 원칙에 위배됩니다.

> 💡 **시험 꿀팁**: "하나의 버킷을 여러 팀/애플리케이션이 공유하며 접근 관리를 단순화·확장"하려는 요구사항은 S3 Access Points의 대표적인 사용 사례입니다.

## QUESTION 458

**문제**: 한 기업은 자체 보유한 라이선스(BYOL)로 상용 소프트웨어를 여러 EC2 인스턴스에 설치해 사용하고 있습니다. 라이선스 사용 한도를 초과하지 않도록 사용 현황을 추적하고, 한도를 초과할 경우 새로운 인스턴스 시작을 제한하고 싶어 합니다. 어떤 서비스를 사용해야 합니까?

**보기**
- A. 각 팀이 스프레드시트로 라이선스 사용 현황을 수동 추적한다 (수동 추적은 오류 발생 가능성이 높고 실시간으로 사용 한도 초과를 방지할 수 없다).
- B. **AWS License Manager를 사용해 라이선스 규칙을 정의하고 EC2 전반의 BYOL 소프트웨어 사용을 추적하며, 한도 초과 시 새 인스턴스 시작을 제한한다.**
- C. AWS Systems Manager Inventory만으로 설치된 소프트웨어 목록을 수집한다 (설치된 소프트웨어 목록은 파악할 수 있지만 라이선스 규칙 적용이나 사용량 강제 제한 기능은 제공하지 않는다).
- D. AWS Config 규칙을 만들어 라이선스가 없는 소프트웨어가 설치된 인스턴스를 사후에 알림받는다 (사후 알림 방식으로는 라이선스 한도 초과를 사전에 방지할 수 없다).

**정답: B**

**해설**: **AWS License Manager**는 소프트웨어 벤더의 라이선스 규칙(예: vCPU당, 코어당, 인스턴스당 라이선스 수)을 정의하고, EC2 및 온프레미스 환경 전반에서 BYOL 소프트웨어 사용 현황을 자동으로 추적합니다. 정의된 한도를 초과하려는 시도가 있을 경우 새로운 인스턴스 시작을 제한하는 강제(enforcement) 기능도 제공하여 라이선스 규정 준수를 사전에 보장합니다.

**왜 다른 보기는 오답인가**
- A: 수동 스프레드시트 추적은 오류에 취약하고 실시간 강제가 불가능합니다.
- C: Systems Manager Inventory는 설치된 소프트웨어 목록 수집에 그치며 라이선스 규칙 강제 기능이 없습니다.
- D: Config 규칙은 사후 탐지 방식으로 사전 예방적 한도 제한이 불가능합니다.

> 💡 **시험 꿀팁**: "BYOL 라이선스 추적 + 사용 한도 강제"라는 키워드는 AWS License Manager를 가리킵니다.

## QUESTION 459

**문제**: 한 기업은 Windows 기반 애플리케이션을 위해 SMB 프로토콜 파일 공유가 필요하며, 기존 온프레미스 Microsoft Active Directory와 네이티브로 통합되어야 합니다. 완전 관리형 서비스로 이를 구현하려면 무엇을 사용해야 합니까?

**보기**
- A. Amazon EFS를 사용해 파일 공유를 구성한다 (EFS는 NFS 프로토콜 기반으로 주로 Linux 워크로드에 적합하며 SMB 및 Active Directory 네이티브 통합을 지원하지 않는다).
- B. Amazon S3에 파일을 저장하고 자체적으로 SMB 게이트웨이를 구축한다 (자체 구축한 게이트웨이는 관리 부담이 크고 완전 관리형 Active Directory 통합을 기본 제공하지 않는다).
- C. **Amazon FSx for Windows File Server를 사용해 완전 관리형 SMB 파일 공유를 제공하고 Microsoft Active Directory와 네이티브로 통합한다.**
- D. 각 EC2 인스턴스에 개별 EBS 볼륨을 연결해 로컬 파일 공유를 구성한다 (EBS 볼륨은 단일 인스턴스에 연결되는 블록 스토리지로 여러 인스턴스 간 공유 파일 시스템을 제공하지 않는다).

**정답: C**

**해설**: **Amazon FSx for Windows File Server**는 완전 관리형 Windows 파일 서버로, SMB 프로토콜을 네이티브로 지원하고 AWS Managed Microsoft AD 또는 온프레미스 Active Directory와 직접 통합되어 기존 Windows 기반 애플리케이션과 사용자 권한 체계를 그대로 활용할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: EFS는 NFS 기반으로 SMB 및 AD 네이티브 통합을 지원하지 않습니다.
- B: 자체 구축 SMB 게이트웨이는 관리 부담이 크고 완전 관리형 AD 통합을 제공하지 않습니다.
- D: EBS는 단일 인스턴스 전용 블록 스토리지로 다중 인스턴스 파일 공유에 적합하지 않습니다.

> 💡 **시험 꿀팁**: "Windows SMB 파일 공유 + Active Directory 통합"이라는 요구사항은 Amazon FSx for Windows File Server를 가리킵니다.

## QUESTION 460

**문제**: 한 기업의 아키텍처 팀은 기존 애플리케이션의 장애 대응 능력을 체계적으로 검토하고 개선하고자 합니다. 장애 복구, 확장 수요 처리, 변경 관리 등 여러 측면에서 아키텍처의 복원력을 종합적으로 평가하는 표준화된 방법론이 필요합니다. 무엇을 활용해야 합니까?

**보기**
- A. AWS Trusted Advisor의 비용 최적화 점검 항목만 검토한다 (비용 최적화 점검 항목은 신뢰성 향상과 직접적인 관련이 없다).
- B. AWS Config의 규정 준수 대시보드만 확인한다 (Config는 리소스 구성의 규정 준수 여부를 추적할 뿐 아키텍처의 복원력을 종합적으로 평가하지 않는다).
- C. Amazon CloudWatch 지표만 검토해 장애 발생 시점을 사후에 파악한다 (사후 지표 검토만으로는 장애를 예방하기 위한 체계적인 아키텍처 개선 방향을 도출하기 어렵다).
- D. **AWS Well-Architected Framework의 신뢰성 축(Reliability Pillar)을 적용해 장애 복구, 확장 수요 처리, 변경 관리 등의 관점에서 아키텍처를 체계적으로 검토하고 개선한다.**

**정답: D**

**해설**: **AWS Well-Architected Framework**의 신뢰성 축(Reliability Pillar)은 장애로부터의 복구, 인프라 및 서비스 중단 대응, 동적인 수요 변화에 대한 확장 처리, 운영 중 발생하는 변경 관리라는 관점에서 워크로드를 체계적으로 평가하는 모범 사례 모음을 제공합니다. AWS Well-Architected Tool을 통해 실제 워크로드에 이 프레임워크를 적용하여 개선 항목을 도출할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 비용 최적화 점검은 신뢰성 향상과 목적이 다릅니다.
- B: Config 규정 준수 확인은 구성 추적에 그치며 종합적인 복원력 평가가 아닙니다.
- C: CloudWatch 지표의 사후 검토만으로는 예방적 아키텍처 개선 방향을 체계적으로 도출하기 어렵습니다.

> 💡 **시험 꿀팁**: "장애 복구, 확장 수요 처리, 변경 관리 등 복원력을 종합적으로 검토"라는 표현은 Well-Architected Framework의 신뢰성 축을 가리킵니다.
