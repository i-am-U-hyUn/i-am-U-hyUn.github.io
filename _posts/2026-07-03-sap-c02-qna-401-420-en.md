## QUESTION 401

**Question**: A company runs a third-party SD-WAN appliance at a branch office, and wants to connect many branch networks through this appliance **directly to AWS Transit Gateway, using GRE tunnels with dynamic routing (BGP)**. They want a method that natively integrates with the SD-WAN vendor's virtual appliance, not a VPN connection. What's the solution?

**Choices**
- A. Configure a standard Site-to-Site VPN connection from each branch to Transit Gateway (a standard VPN is possible, but doesn't meet the requirement for native GRE integration with the SD-WAN appliance, and doesn't provide optimized integration with the SD-WAN vendor ecosystem).
- B. **Use Transit Gateway Connect to connect the SD-WAN appliance to Transit Gateway via a GRE tunnel, and configure BGP dynamic routing through a Transit Gateway Connect peer.**
- C. Build individual Direct Connect connections at each branch (not about integrating with the SD-WAN vendor appliance, but building an entirely new dedicated circuit — cost and setup time balloon, and this differs from the question's requirement).
- D. Treat each branch network as a VPC and connect directly via VPC peering with no Transit Gateway (peering doesn't support GRE-based dynamic routing integration with an SD-WAN appliance, and doesn't scale to many branches).

**Correct Answer: B**

**Explanation**
**Transit Gateway Connect** lets you connect a third-party SD-WAN appliance directly to Transit Gateway via a **GRE tunnel** rather than a standard VPN connection. Configuring **BGP dynamic routing** through a Transit Gateway Connect peer natively integrates with the SD-WAN vendor's virtual appliance and supports higher throughput than a standard VPN. This is the standard way to connect many branches to Transit Gateway via an SD-WAN appliance.

**Why the other choices are wrong**
- A: A standard VPN is a possible connection method, but doesn't meet the specific requirement for native GRE integration with the SD-WAN appliance.
- C: Direct Connect is for building a dedicated circuit — unrelated to this question's core requirement of SD-WAN appliance integration.
- D: VPC peering doesn't support GRE-based dynamic routing integration or scale to many branches.

> 💡 **Exam tip**: To **natively integrate a third-party SD-WAN appliance with Transit Gateway via a GRE tunnel**, **Transit Gateway Connect** is the standard answer.

## QUESTION 402

**Question**: A company wants to migrate a legacy commercial database application to RDS, but this application needs **operating-system-level access** to the database (installing a custom agent, changing registry settings, third-party backup tools, etc.), which standard RDS's managed constraint (no OS access) can't accommodate. They still want to maximize RDS-level managed benefits like automated backups, patching, and high availability. What's the solution?

**Choices**
- A. Use a standard RDS instance and give up the application requirement (fails to meet the requirement for OS-level access, making the migration impossible).
- B. **Use RDS Custom, gaining SSH/RDP access to the underlying operating system and database instance to apply custom configuration, while still leveraging RDS's managed features like automated backup/monitoring/high availability.**
- C. Install the database self-managed on EC2, going fully self-managed (gains OS access, but requires giving up and self-implementing/managing all of RDS's automated backup/patching/high-availability features).
- D. Switch to Aurora, using standard Aurora rather than RDS Custom for Aurora (standard Aurora also doesn't allow OS-level access, failing to meet the application's custom requirements).

**Correct Answer: B**

**Explanation**
**RDS Custom** is a service occupying the middle ground between standard RDS and a fully self-managed EC2 database, allowing **SSH/RDP access** to the underlying operating system and database instance for OS-level customization like installing a custom agent or changing registry settings, while still retaining much of RDS's managed features — **automated backups, patching, monitoring, high availability**. It's the standard service for simultaneously obtaining a legacy commercial application's special OS-level requirements and RDS's managed benefits.

**Why the other choices are wrong**
- A: Standard RDS doesn't allow OS access at all, failing to meet the application's requirement.
- C: Self-managed EC2 gains OS access but requires giving up all of RDS's managed benefits.
- D: Standard Aurora, like RDS, doesn't provide OS-level access.

> 💡 **Exam tip**: To migrate a **legacy database application needing OS-level customization** while keeping RDS's managed benefits (backup/patching/high availability), **RDS Custom** is the standard answer.

## QUESTION 403

**Question**: The security team wants to centrally apply the **same AWS WAF rule set** to ALBs and CloudFront distributions scattered across the organization's 200 accounts, and enforce that this rule automatically applies to newly created resources too. How do you prevent individual account administrators from changing WAF settings individually or bypassing rule enforcement?

**Choices**
- A. Instruct each account administrator to deploy and apply the standard WAF rule set (instruction alone has no enforcement power, carrying high risk that rules are missing or applied inconsistently per account).
- B. **Use AWS Firewall Manager to define an organization-wide WAF policy, automatically applying it to target resources (ALB, CloudFront, etc.) in every account (including new ones) in the organization, and centrally, continuously enforcing and remediating rule changes/bypasses in individual accounts.**
- C. Create WAF web ACLs individually per account, then deploy via CloudFormation StackSets (StackSets is good for initial deployment, but the ongoing detection of rule changes/deletions in individual accounts and automatic re-remediation is a feature Firewall Manager provides dedicatedly).
- D. Use an SCP to block all WAF-related API calls entirely (blocking WAF API calls entirely also blocks legitimate rule-management work, and this simply prevents all use rather than applying a central policy — doesn't fit the goal).

**Correct Answer: B**

**Explanation**
**AWS Firewall Manager** integrates with Organizations to centrally define **organization-wide security policies** (WAF rules, Shield Advanced protection, security groups, etc.) and **automatically apply** them to every account and resource (existing and new) in the organization. If a policy is changed in an individual account or a resource falls out of policy scope, Firewall Manager continuously detects this and **automatically remediates** it — effectively preventing account administrators from arbitrarily bypassing rules, centrally.

**Why the other choices are wrong**
- A: Instruction alone has no enforcement power and can't guarantee consistent application.
- C: StackSets is useful for initial deployment, but ongoing detection/remediation is Firewall Manager's dedicated strength.
- D: Blocking WAF APIs entirely also blocks legitimate management work — impractical, and different from the goal of deploying a central policy.

> 💡 **Exam tip**: To **centrally apply WAF/security policy across multiple accounts and automatically enforce/remediate it on new accounts/resources**, **AWS Firewall Manager** is the standard answer.

## QUESTION 404

**Question**: A company recently set up a new cross-region replication (CRR) rule on an S3 bucket, and discovered this rule **only applies to objects uploaded after the rule was configured**. They want to retroactively replicate millions of existing objects that were already in the bucket before the rule was set, to another Region. What's the solution?

**Choices**
- A. Delete the replication rule and recreate it (recreating the rule still only applies to new objects from the recreation point forward — not a feature for retroactively replicating existing objects).
- B. **Use S3 Batch Replication to run a one-time replication job targeting the existing objects that predate the replication rule's creation, retroactively replicating them to the destination Region.**
- C. Download all existing objects and directly re-upload them to a bucket in another Region (manually downloading/re-uploading millions of objects is enormously time-consuming, costly, and inefficient).
- D. Use a lifecycle policy to transition existing objects to a different storage class (storage-class transition is a separate feature unrelated to cross-region replication).

**Correct Answer: B**

**Explanation**
A standard S3 replication rule only applies to objects **uploaded/changed after the rule was activated**. To replicate existing objects that predate the rule's creation, you need **S3 Batch Replication**, which is built on S3 Batch Operations to run a large-scale, one-time replication job against a list of existing objects, efficiently retroactively replicating even millions of existing objects to the destination Region.

**Why the other choices are wrong**
- A: Recreating the rule doesn't apply retroactively — it still only applies to future new objects.
- C: Manually downloading/re-uploading is very inefficient at large object counts.
- D: A lifecycle policy is for storage-class transitions, not a cross-region replication feature.

> 💡 **Exam tip**: To **retroactively replicate existing objects that predate an S3 replication rule's creation**, **S3 Batch Replication** is the standard answer.

## QUESTION 405

**Question**: They want an Auto Scaling group instance being terminated during scale-in to first **fully drain its remaining application logs to a central log store** before actually terminating. If the instance terminates suddenly before log transfer finishes, logs are lost. What's the solution?

**Choices**
- A. Only enable termination protection on the instance (termination protection prevents accidental manual termination — it doesn't control or delay termination from Auto Scaling's normal scale-in process).
- B. **Configure an Auto Scaling lifecycle hook on the Terminating state, so before the instance actually terminates, it enters a wait state giving time to run a log-draining script, and calls CompleteLifecycleAction when done to proceed with termination.**
- C. Only write a UserData script that runs automatically on instance termination (UserData standardly runs at instance launch, not a standard mechanism guaranteeing execution at termination, and has no wait/completion signaling integrated with Auto Scaling's termination process).
- D. Detect instances scheduled for termination via a CloudWatch event and have a separate Lambda collect logs afterward (once an instance has already terminated, its logs are no longer accessible — after-the-fact collection is impossible).

**Correct Answer: B**

**Explanation**
Configuring an **Auto Scaling lifecycle hook** on the **Terminating** state keeps the instance in a **defined wait state** before it actually terminates. During this wait period, running a log-draining script (e.g., via SSM Run Command or an in-instance agent) fully transfers remaining logs, and only after calling the **CompleteLifecycleAction** API does termination proceed. This is the standard pattern for ensuring clean-up work completes with no data loss during scale-in.

**Why the other choices are wrong**
- A: Termination protection prevents accidental manual termination and is unrelated to Auto Scaling's automatic scale-in process.
- C: UserData standardly runs at launch and doesn't provide a wait/completion signaling mechanism at termination time.
- D: Once an instance has already terminated, its log data is no longer accessible — after-the-fact collection is impossible.

> 💡 **Exam tip**: To **complete clean-up work (like log draining) before an instance terminates** during Auto Scaling scale-in, an **Auto Scaling lifecycle hook (Terminating state)** is the standard answer.

## QUESTION 406

**Question**: A large enterprise wants to purchase multiple third-party software products (several commercial products offered on AWS Marketplace) in bulk, at **individually negotiated pricing and terms** (bulk discounts, custom license duration, etc.) with the vendor. What's the standard way to purchase at negotiated terms rather than standard public Marketplace pricing?

**Choices**
- A. Request a separate contract directly from the vendor and pay outside of AWS (contracting/paying separately outside AWS Marketplace loses all the benefits of consolidated billing, AWS credit usage, and Marketplace purchase management).
- B. **Use AWS Marketplace's private offer feature, receiving the vendor's negotiated custom price/terms as a private offer, accepting and purchasing it through AWS Marketplace, and having it reflected directly in the consolidated AWS bill.**
- C. Purchase multiple units at standard public pricing, then request a refund from the vendor afterward (an after-the-fact refund request isn't a standard or reliable approach, and isn't itself a way to purchase at the negotiated price in the first place).
- D. Search for a similar product on the Reserved Instance Marketplace (the Reserved Instance Marketplace is for reselling EC2 Reserved Instances — entirely unrelated to negotiating with a third-party software vendor — a conceptual error).

**Correct Answer: B**

**Explanation**
An **AWS Marketplace private offer** is an offer a software vendor presents individually, containing a **custom price, terms, and license duration** negotiated for a specific customer. The customer accepts and purchases this private offer through AWS Marketplace, applying the negotiated terms as-is while still retaining all of Marketplace's benefits — AWS consolidated billing, linkage with existing commitments (EDP, etc.), and purchase management.

**Why the other choices are wrong**
- A: Contracting separately outside AWS loses core Marketplace benefits like consolidated billing.
- C: Requesting a refund after a standard-price purchase isn't reliable and isn't a standard negotiated-purchase method.
- D: The Reserved Instance Marketplace is an entirely different service for reselling EC2 Reserved Instances.

> 💡 **Exam tip**: To purchase an AWS Marketplace product at **vendor-negotiated custom price/terms** while keeping AWS consolidated billing benefits, a **private offer** is the standard answer.

## QUESTION 407

**Question**: The security team wants to **automatically block at the DNS layer** any EC2 instance or container's attempt to resolve a known malicious domain or a recently registered suspicious domain. They want to enforce this across the entire VPC, without configuring it individually per application or instance. What's the solution?

**Choices**
- A. Manually register known malicious domains in each instance's local hosts file to block them (manual management requiring the malicious-domain list to be constantly updated — doesn't scale, and requires per-instance individual configuration, contradicting the requirement).
- B. **Use Route 53 Resolver DNS Firewall to configure domain-list-based rules (including AWS-managed threat lists) at the VPC level, automatically blocking or alerting on DNS queries to malicious/suspicious domains.**
- C. Block specific IP ranges via a security group's outbound rules (a malicious domain's IP can change frequently, making IP-based blocking alone inefficient, and this is network-layer control, not DNS-layer).
- D. Individually install third-party DNS filtering software on each instance (requires individual installation/management per instance, contradicting the requirement for central VPC-wide enforcement).

**Correct Answer: B**

**Explanation**
**Route 53 Resolver DNS Firewall** is a feature for defining DNS query filtering rules at the VPC level. Attaching AWS-managed **threat-intelligence-based domain lists** (malware, botnets, etc.) to a rule, or building a custom domain list, lets you **block (BLOCK), allow (ALLOW), or alert (ALERT)** on DNS lookups for specific domains. Attaching this to the VPC's resolver rule group applies it uniformly across the entire VPC with no per-instance configuration — the standard way to categorically block malicious domain communication at the DNS layer.

**Why the other choices are wrong**
- A: Manual hosts-file management doesn't scale and requires per-instance work.
- C: Security groups are IP-based controls; given how frequently a malicious domain's IP changes, this is inefficient and isn't DNS-layer control.
- D: Individually installing third-party software per instance contradicts the requirement for central VPC-wide enforcement.

> 💡 **Exam tip**: To **centrally, automatically block DNS queries to malicious/suspicious domains** across an entire VPC, **Route 53 Resolver DNS Firewall** is the standard answer.

## QUESTION 408

**Question**: A mobile app development team needs the app to work offline (storing changes locally while offline, then automatically syncing when back online), and also needs real-time notification (real-time subscription) of connected clients whenever specific data changes. They prefer a flexible, GraphQL-based API. What service meets all these requirements in a managed way?

**Choices**
- A. API Gateway REST API + DynamoDB (a REST API itself doesn't offer GraphQL's flexible query capability, and both offline sync and real-time subscription would have to be entirely self-implemented — heavy burden).
- B. **Use AWS AppSync, querying multiple data sources (DynamoDB, etc.) in a unified way via a GraphQL API, and leveraging its built-in offline data sync (local caching and conflict resolution) and real-time subscription features in a managed way.**
- C. Implement only real-time messaging with Amazon MQ, self-implementing offline sync in the mobile SDK (MQ is a message broker and doesn't provide a GraphQL API or offline sync features — very heavy self-implementation burden).
- D. Cache only static API responses with CloudFront + S3 (static caching doesn't address dynamic data queries, real-time subscriptions, or offline write sync at all).

**Correct Answer: B**

**Explanation**
**AWS AppSync** is a managed **GraphQL** service that lets you flexibly query multiple data sources — DynamoDB, Lambda, RDS, etc. — through a single unified GraphQL API. Through its mobile/web SDKs, it natively supports **local data caching while offline and automatic sync (including conflict resolution) when reconnecting**, and its GraphQL **subscription** feature can push specific data changes to all connected clients in real time. This is the standard managed service meeting both the offline-first and real-time requirements of a mobile app.

**Why the other choices are wrong**
- A: A REST API doesn't provide GraphQL's flexibility, and offline sync/real-time subscription would need to be self-implemented.
- C: Amazon MQ is a message broker with no GraphQL API or built-in offline sync feature.
- D: Static caching doesn't address dynamic queries, real-time, or offline write sync at all.

> 💡 **Exam tip**: For a mobile app needing **a GraphQL API + offline data sync + real-time subscriptions**, **AWS AppSync** is the standard answer.

## QUESTION 410

**Question**: A company operates dozens of VPCs scattered across multiple Regions, and wants to connect them all to on-premises through a single Direct Connect connection (located in a specific Region). Building a separate Direct Connect connection per Region is too costly. What's the solution?

**Choices**
- A. Build an individual Direct Connect connection and dedicated circuit per Region (explicitly stated to be too costly — the approach this question wants to avoid).
- B. **Use a Direct Connect Gateway to connect one Direct Connect connection (and its private virtual interface) to many VPCs (via each VPC's virtual private gateway or a Transit Gateway) located across multiple Regions.**
- C. Migrate all Regions' VPCs into a single Region (a multi-Region deployment might itself be a requirement, unnecessarily constraining the architecture, and not a fundamental solution to the cost problem).
- D. Connect each Region's VPC individually via an internet-based VPN (an internet-based connection gives up Direct Connect's dedicated-circuit performance/security benefits; the question asks how to leverage the existing Direct Connect connection across multiple Regions).

**Correct Answer: B**

**Explanation**
A **Direct Connect Gateway** is a global resource that lets a single Direct Connect connection (a private virtual interface located in a specific Region) connect to **many VPCs located in Regions around the world** (via each VPC's virtual private gateway or a Transit Gateway). This lets you efficiently connect an on-premises network to many VPCs distributed globally with a single connection, with no need to build a separate, costly Direct Connect connection per Region.

**Why the other choices are wrong**
- A: Building an individual connection per Region is the approach the question already states is too costly.
- C: Consolidating all VPCs into a single Region unnecessarily constrains a multi-Region architecture requirement.
- D: An internet-based VPN gives up Direct Connect's benefits and differs from the question's intent of leveraging the existing Direct Connect connection.

> 💡 **Exam tip**: To connect a single Direct Connect connection to **many VPCs located across multiple Regions**, a **Direct Connect Gateway** is the standard answer.

## QUESTION 411

**Question**: An e-commerce company wants to detect, in real time, whenever a new order is added or its status changes in a DynamoDB orders table, and trigger event-driven follow-up processing like inventory-system updates or sending email notifications. How do you use the table's own changes as an event source, without a separate polling mechanism?

**Choices**
- A. Have the application periodically Scan the table and compare to previous state (polling-based scanning is costly, incurs delay, lacks real-time-ness, and is very inefficient on a large table).
- B. **Enable DynamoDB Streams to capture the table's item-level changes (inserts/updates/deletes), and connect the stream as a Lambda function's event source, so Lambda is triggered in real time to perform follow-up processing whenever a change occurs.**
- C. Migrate to RDS and use its trigger feature (migrating to a relational database is an unnecessary redesign beyond this question's scope, and DynamoDB itself already supports change data capture).
- D. Log DynamoDB API calls via CloudTrail and analyze them (CloudTrail specializes in auditing management events/API calls; capturing data events [individual item changes] by default requires separate configuration and isn't as optimized for real-time item-level change processing as DynamoDB Streams).

**Correct Answer: B**

**Explanation**
**DynamoDB Streams** captures a chronological record of a table's item changes whenever items are inserted, updated, or deleted. Connecting this stream as a **Lambda function's event source** lets Lambda be automatically triggered the instant a table change occurs, with no polling, to perform real-time event-driven follow-up processing like inventory updates or notifications. This is the standard way to implement a DynamoDB-based change data capture (CDC) pattern.

**Why the other choices are wrong**
- A: Periodic scanning lacks real-time-ness and carries a very heavy cost/performance burden on a large table.
- C: Migrating to a relational database is an unnecessary redesign, and DynamoDB itself already provides a streams feature.
- D: CloudTrail specializes in API-call auditing; DynamoDB Streams is more suited to real-time, item-level change processing.

> 💡 **Exam tip**: To **detect item-level changes in a DynamoDB table as real-time events and trigger follow-up processing**, **DynamoDB Streams + Lambda** is the standard answer.

## QUESTION 414

**Question**: A batch-processing workload extensively uses Spot Instances, but relying on a single instance type repeatedly causes the entire job to stall whenever that type's Spot capacity runs short. How do you diversify Spot capacity across multiple instance types while preferring capacity pools with the lowest interruption likelihood?

**Choices**
- A. Keep using only a single instance type in the Auto Scaling group but duplicate the group across multiple Regions (multi-Region duplication increases management complexity and doesn't directly address this question's core need — diversifying Spot across multiple instance types).
- B. **Configure a mixed instances policy on the Auto Scaling group, specifying several compatible instance types, and set the Spot allocation strategy to capacity-optimized, so instances launch preferentially from the capacity pool with the lowest interruption likelihood.**
- C. Only set the Spot allocation strategy to lowest-price (a lowest-price strategy can minimize cost, but can actually increase interruption likelihood by concentrating requests on one cheap type — capacity-optimized is more suitable if minimizing interruptions is the goal).
- D. Switch all instances to On-Demand (fully gives up Spot's cost benefit; the question asks how to diversify while keeping Spot usage).

**Correct Answer: B**

**Explanation**
Configuring a **mixed instances policy** on an Auto Scaling group, specifying several compatible instance types (various families of similar size, etc.), diversifies Spot capacity across multiple types/pools, so even if one type runs short, capacity can still be secured from other types. Setting the Spot allocation strategy to **capacity-optimized** launches instances preferentially not just from the cheapest pool, but from **the pool currently least likely to be interrupted**, minimizing interruption frequency while retaining Spot's cost benefit.

**Why the other choices are wrong**
- A: Multi-Region duplication only adds management complexity and doesn't solve the root problem of single-type reliance.
- C: A lowest-price strategy can increase interruption risk by concentrating demand on a specific cheap type.
- D: Switching to On-Demand gives up Spot's cost benefit — a different direction than the question's intent.

> 💡 **Exam tip**: To **minimize Spot Instance interruption likelihood while diversifying across multiple instance types**, a **mixed instances policy + capacity-optimized allocation strategy** is the standard answer.

## QUESTION 415

**Question**: A fluid-dynamics simulation (HPC) workload runs in parallel across thousands of cores, needing a **very high-throughput, low-latency shared scratch file system** between compute nodes (POSIX-compatible, hundreds of GB/s of throughput). Only the final computed results need to be permanently stored in S3. What's the solution?

**Choices**
- A. Use Amazon EFS (EFS is also a POSIX-compatible shared file system, but FSx for Lustre specializes in the hundreds-of-GB/s throughput and low latency characteristics needed for this level of ultra-high-performance HPC scratch workload).
- B. **Use Amazon FSx for Lustre, mounting a high-performance parallel file system integrated with S3 on the compute nodes; process simulation intermediate data on the fast scratch, then export only the final results to S3.**
- C. Use only local instance store on each compute node, implementing inter-node data sharing directly in the application (local store isn't shared between nodes, failing to meet the parallel HPC workload's shared-file-system requirement at all).
- D. Mount S3 directly as if it were a file system (S3 is object storage and doesn't natively provide POSIX file-system semantics or this level of low latency — unsuitable for an HPC scratch workload).

**Correct Answer: B**

**Explanation**
**Amazon FSx for Lustre** is a high-performance parallel file system designed for compute-intensive workloads like HPC and machine learning, providing hundreds of GB/s of throughput and low latency, and is **POSIX-compatible**.
