## QUESTION 121

**문제**: 한 회사가 AWS에서 OLTP(온라인 트랜잭션 처리) 워크로드를 실행하고 있다. 이 워크로드는 다중 AZ 배포에서 암호화되지 않은 Amazon RDS DB 인스턴스를 사용하며, 이 인스턴스로부터 일일 데이터베이스 스냅샷을 생성한다. 앞으로 데이터베이스와 스냅샷이 항상 암호화되도록 하려면 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. **최신 DB 스냅샷의 사본을 암호화한다. 암호화된 스냅샷을 복원하여 기존 DB 인스턴스를 교체한다.**
- B. 새 암호화된 Amazon EBS 볼륨을 생성하고 여기에 스냅샷을 복사한 뒤 DB 인스턴스에서 암호화를 활성화한다(RDS는 생성 후 인스턴스 자체에서 암호화를 "켜는" 기능을 제공하지 않으며, EBS 볼륨 복사는 RDS 관리형 스토리지 구조와 맞지 않음).
- C. AWS KMS를 사용하여 스냅샷을 복사하고 암호화를 활성화한 뒤, 암호화된 스냅샷을 기존 DB 인스턴스로 복원한다(암호화된 스냅샷은 새 DB 인스턴스로만 복원 가능하며 기존 인스턴스에 덮어씌울 수 없음).
- D. AWS KMS 관리형 키(SSE-KMS)로 서버 측 암호화를 사용하는 Amazon S3 버킷에 스냅샷을 복사한다(스냅샷을 S3로 내보내는 것은 RDS DB 인스턴스 자체를 암호화된 상태로 교체하는 요구 사항을 충족하지 못함).

**정답: A**

**해설**
**Amazon RDS**는 DB 인스턴스 생성 시점에만 암호화 여부를 설정할 수 있고, 생성 후에는 기존 인스턴스를 직접 암호화할 방법이 없습니다. 대신 암호화되지 않은 스냅샷을 복사하면서 암호화를 적용한 사본을 만들고, 이 암호화된 스냅샷으로 새 DB 인스턴스를 복원한 뒤 기존 인스턴스를 교체하는 방식으로 우회할 수 있습니다. 이 과정에서 KMS 키가 사용되지만, 핵심은 "스냅샷 복사(암호화) → 복원(신규 인스턴스) → 교체" 흐름입니다.

**왜 다른 보기는 오답인가**
- B: EBS 볼륨을 별도로 암호화하는 방식은 RDS의 관리형 스토리지 구조에 맞지 않으며, DB 인스턴스에는 사후 암호화 활성화 옵션이 없습니다.
- C: 암호화된 스냅샷은 기존 인스턴스에 복원할 수 없고 항상 새 인스턴스로 복원됩니다.
- D: 스냅샷을 S3로 내보내는 것은 백업 저장 방식이며, 실행 중인 DB 인스턴스 자체를 암호화된 상태로 만드는 요구 사항과는 무관합니다.

> 💡 **시험 꿀팁**: "기존 RDS 인스턴스를 나중에 암호화"하고 싶다는 조건이 나오면 **스냅샷 복사(암호화) 후 새 인스턴스로 복원**이 표준 정답입니다.

## QUESTION 122

**문제**: 한 회사가 애플리케이션 데이터를 암호화해야 하는 개발자들을 지원하기 위해 확장 가능한 키 관리 인프라를 구축하려고 한다. 솔루션 설계자는 운영 부담을 줄이기 위해 무엇을 해야 하는가?

**보기**
- A. MFA(다단계 인증)를 사용하여 암호화 키를 보호한다(MFA는 사용자 인증 강화 수단일 뿐 키 생성·저장·수명 주기 관리와는 무관).
- B. **AWS Key Management Service(AWS KMS)를 사용하여 암호화 키를 보호한다.**
- C. AWS Certificate Manager(ACM)를 사용하여 암호화 키를 생성, 저장 및 할당한다(ACM은 SSL/TLS 인증서 관리 서비스로 범용 암호화 키 관리 용도가 아님).
- D. IAM 정책을 사용하여 암호화 키에 접근할 수 있는 사용자 범위를 제한한다(IAM은 권한 제어 수단일 뿐, 키 자체를 생성·저장·교체하는 관리형 키 서비스가 아님).

**정답: B**

**해설**
**AWS KMS**는 암호화 키를 생성, 저장, 교체(rotation), 감사하는 기능을 완전 관리형으로 제공하는 서비스입니다. 개발자가 직접 키 관리 인프라를 구축·운영할 필요 없이 API 호출만으로 키를 생성하고 데이터 암호화에 사용할 수 있어, 확장 가능하면서도 운영 부담이 가장 낮은 선택지입니다.

**왜 다른 보기는 오답인가**
- A: MFA는 로그인 인증을 강화하는 기능이며 키 관리와는 별개입니다.
- C: ACM은 공인/사설 SSL/TLS 인증서의 프로비저닝과 갱신을 담당하는 서비스로, 데이터 암호화용 키 관리와는 목적이 다릅니다.
- D: IAM 정책은 누가 KMS 키에 접근할 수 있는지를 제어할 뿐이며, 그 자체로 키를 생성하거나 관리하지는 않습니다.

> 💡 **시험 꿀팁**: "암호화 키를 직접 운영하지 않고 확장 가능하게 관리"하고 싶다는 요구에는 **AWS KMS**가 표준 정답입니다.

## QUESTION 123

**문제**: 한 회사가 두 개의 Amazon EC2 인스턴스에서 호스팅되는 동적 웹 애플리케이션을 운영하며, SSL 종료를 위해 각 인스턴스에 자체 SSL 인증서를 두고 있다. 최근 트래픽 증가로 SSL 암호화·복호화 연산 때문에 웹 서버의 컴퓨팅 용량이 한계에 도달했다. 솔루션 설계자는 애플리케이션 성능을 향상시키기 위해 무엇을 해야 하는가?

**보기**
- A. AWS Certificate Manager(ACM)로 새 SSL 인증서를 생성하고 각 인스턴스에 설치한다(인증서를 새로 발급해도 SSL 처리 부하는 여전히 각 EC2 인스턴스에 남아 근본 문제를 해결하지 못함).
- B. Amazon S3 버킷을 생성해 SSL 인증서를 마이그레이션하고 SSL 종료를 위해 이를 참조하도록 EC2 인스턴스를 구성한다(S3는 정적 객체 저장소일 뿐 SSL 종료를 수행하는 컴퓨팅 계층이 아님).
- C. 다른 EC2 인스턴스를 프록시 서버로 생성해 인증서를 마이그레이션한다(관리형 서비스 대신 직접 관리해야 하는 프록시 인스턴스를 추가하는 것은 운영 부담을 늘릴 뿐 근본적인 해결책이 아님).
- D. **SSL 인증서를 AWS Certificate Manager(ACM)로 가져온다. ACM의 SSL 인증서를 사용하는 HTTPS 리스너로 Application Load Balancer를 생성한다.**

**정답: D**

**해설**
**Application Load Balancer(ALB)**의 HTTPS 리스너에 ACM 인증서를 연결하면 **SSL 종료(SSL offloading)**가 로드밸런서 계층에서 이루어지므로, 백엔드 EC2 인스턴스는 더 이상 암호화·복호화 연산을 부담하지 않고 애플리케이션 처리에만 컴퓨팅 자원을 집중할 수 있습니다. 기존에 사용 중이던 인증서를 ACM으로 가져오기만 하면 되므로 새 인증서를 발급할 필요도 없습니다.

**왜 다른 보기는 오답인가**
- A: 인증서만 새로 만들 뿐 SSL 처리 위치가 EC2 인스턴스 그대로이므로 CPU 부하 문제가 해결되지 않습니다.
- B: S3는 SSL 종료 기능을 제공하는 서비스가 아닙니다.
- C: 별도 프록시 EC2 인스턴스를 직접 운영해야 하므로 관리형 로드밸런서를 쓰는 것보다 운영 오버헤드가 크고 확장성도 떨어집니다.

> 💡 **시험 꿀팁**: "SSL 처리로 인해 EC2 컴퓨팅 자원이 소진된다"는 조건이 나오면 **ALB + ACM 인증서로 SSL 오프로드**가 표준 정답입니다.

## QUESTION 124

**문제**: 한 회사가 많은 Amazon EC2 인스턴스를 사용해 완료하는 매우 동적인 배치 처리 작업을 운영한다. 이 작업은 상태 비저장(stateless)이며, 부정적인 영향 없이 언제든 시작·중지할 수 있고, 일반적으로 완료까지 60분 이상 걸린다. 솔루션 설계자는 확장 가능하고 비용 효율적인 솔루션으로 무엇을 권장해야 하는가?

**보기**
- A. **EC2 스팟 인스턴스를 구현한다.**
- B. EC2 예약 인스턴스를 구매한다(예약 인스턴스는 안정적이고 예측 가능한 장기 워크로드에 적합하며, 동적이고 중단 가능한 배치 작업에는 비용 효율이 떨어짐).
- C. EC2 온디맨드 인스턴스를 구현한다(중단 허용이 가능한 워크로드임에도 정가를 지불하는 것은 비용 효율적이지 않음).
- D. AWS Lambda에서 처리를 구현한다(Lambda는 최대 실행 시간 제한이 있어 60분 이상 걸리는 배치 작업에는 적합하지 않음).

**정답: A**

**해설**
**EC2 스팟 인스턴스**는 여유 컴퓨팅 용량을 최대 90%까지 할인된 가격으로 사용할 수 있는 대신 AWS가 필요 시 회수(중단)할 수 있는 인스턴스입니다. 이 배치 작업은 상태 비저장이고 언제든 시작·중지가 가능하다는 특성이 스팟 인스턴스의 중단 가능성과 정확히 맞아떨어지므로, 비용을 크게 절감하면서도 요구 사항을 충족할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 예약 인스턴스는 1~3년 약정을 통해 꾸준히 실행되는 워크로드에 유리하며, "매우 동적인" 배치 작업의 특성과는 맞지 않습니다.
- C: 온디맨드는 중단 가능성을 활용하지 못해 스팟 대비 비용이 훨씬 높습니다.
- D: Lambda는 함수 실행 시간에 제한(최대 15분)이 있어 60분 이상 걸리는 작업을 직접 처리할 수 없습니다.

> 💡 **시험 꿀팁**: "상태 비저장 + 언제든 중단 가능 + 비용 최적화" 조합이 나오면 **EC2 스팟 인스턴스**가 표준 정답입니다.

## QUESTION 125

**문제**: 한 회사가 AWS에서 2계층 전자상거래 웹사이트를 운영한다. 웹 계층은 트래픽을 Amazon EC2 인스턴스로 전달하는 로드밸런서로 구성되며, 데이터베이스 계층은 Amazon RDS DB 인스턴스를 사용한다. EC2 인스턴스와 RDS DB 인스턴스는 공용 인터넷에 노출되어서는 안 되지만, EC2 인스턴스는 타사 결제 서비스 연동을 위해 인터넷 액세스가 필요하다. 애플리케이션은 고가용성을 갖춰야 한다. 이 요구 사항을 충족하는 구성 옵션의 조합은 무엇인가? (2개를 선택하세요.)

**보기**
- A. **Auto Scaling 그룹을 사용하여 프라이빗 서브넷에서 EC2 인스턴스를 시작한다. 프라이빗 서브넷에 RDS 다중 AZ DB 인스턴스를 배포한다.**
- B. 2개의 가용 영역에 걸쳐 2개의 프라이빗 서브넷과 2개의 NAT 게이트웨이가 있는 VPC를 구성한다. 프라이빗 서브넷에 Application Load Balancer를 배포한다(ALB는 인터넷과 통신해야 하므로 반드시 퍼블릭 서브넷에 위치해야 함).
- C. Auto Scaling 그룹을 사용하여 2개의 가용 영역에 걸쳐 퍼블릭 서브넷에서 EC2 인스턴스를 시작한다. 프라이빗 서브넷에 RDS 다중 AZ DB 인스턴스를 배포한다(EC2 인스턴스가 퍼블릭 서브넷에 있어 공용 인터넷에 노출되지 않아야 한다는 조건을 위반함).
- D. 2개의 가용 영역에 걸쳐 1개의 퍼블릭 서브넷, 1개의 프라이빗 서브넷 및 2개의 NAT 게이트웨이로 VPC를 구성한다. 퍼블릭 서브넷에 Application Load Balancer를 배포한다(하나의 서브넷은 하나의 가용 영역에만 속할 수 있으므로, 서브넷 1개로 2개의 가용 영역에 걸칠 수 없음).
- E. **2개의 가용 영역에 걸쳐 2개의 퍼블릭 서브넷, 2개의 프라이빗 서브넷 및 2개의 NAT 게이트웨이로 VPC를 구성한다. 퍼블릭 서브넷에 Application Load Balancer를 배포한다.**

**정답: A, E**

**해설**
EC2와 RDS는 공용 인터넷에 노출되면 안 되므로 **프라이빗 서브넷**에 위치해야 하고, 고가용성을 위해 **Auto Scaling 그룹**과 **RDS 다중 AZ**가 필요합니다(A). 동시에 EC2가 아웃바운드 인터넷 접근을 하려면 **NAT 게이트웨이**가 필요한데, NAT 게이트웨이는 퍼블릭 서브넷에 위치해야 하며 각 가용 영역마다 하나씩 두어야 고가용성이 보장됩니다. 또한 **Application Load Balancer**는 인터넷 트래픽을 받아야 하므로 퍼블릭 서브넷에 배치해야 합니다(E). 결과적으로 2개 AZ에 각각 퍼블릭·프라이빗 서브넷과 NAT 게이트웨이를 구성하는 조합이 필요합니다.

**왜 다른 보기는 오답인가**
- B: ALB는 클라이언트로부터 인터넷 트래픽을 직접 수신해야 하므로 프라이빗 서브넷에 배치할 수 없습니다.
- C: EC2 인스턴스를 퍼블릭 서브넷에 두면 공용 인터넷에 노출되지 않아야 한다는 요구 사항에 위배됩니다.

- A: 단순 확장 정책은 알람이 발동될 때마다 고정된 수의 인스턴스를 추가/제거할 뿐, 목표 지표값을 지속적으로 유지하도록 조정하지는 않습니다.
- C: Lambda로 직접 구현하면 지표 모니터링과 조정 로직을 모두 직접 관리해야 해 운영 오버헤드가 커집니다.
- D: 예약된 조정은 특정 시간에 맞춰 용량을 변경하는 방식으로, 실시간 CPU 사용률에 반응하지 않습니다.

> 💡 **시험 꿀팁**: "특정 지표(CPU 등)를 목표값으로 유지"하라는 조건이 나오면 **대상 추적(Target Tracking) 조정 정책**이 표준 정답입니다.

## QUESTION 133

**문제**: 한 회사가 온프레미스에서 Oracle 데이터베이스를 실행하고 있으며, AWS로 마이그레이션하면서 데이터베이스를 사용 가능한 최신 버전으로 업그레이드하려고 한다. 회사는 데이터베이스에 대한 재해 복구(DR)도 설정하려 하며, 정상 운영 및 DR 구성의 운영 오버헤드를 최소화해야 한다. 또한 회사는 데이터베이스의 기본 운영 체제에 대한 접근을 유지해야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. Oracle 데이터베이스를 Amazon EC2 인스턴스로 마이그레이션한다. 다른 AWS 리전으로 데이터베이스 복제를 설정한다(OS 접근은 가능하지만 DB 엔진 패치, 백업, 복제 등을 모두 직접 관리해야 해 운영 오버헤드 최소화 요구에 부합하지 않음).

**왜 다른 보기는 오답인가**
- A: EC2에 직접 설치하면 OS 접근은 가능하지만 DB 엔진의 패치·백업·복제를 모두 수동으로 관리해야 해 운영 부담이 가장 큽니다.
- B: 표준 RDS는 운영 부담은 적지만 기본 OS에 대한 접근을 전혀 제공하지 않습니다.
- D: 표준 RDS는 OS 접근이 불가능하며, 동일 리전 내 다른 AZ의 대기 DB는 리전 전체 장애에 대비하는 DR 요구를 충족하지 못합니다.

> 💡 **시험 꿀팁**: "관리형이면서도 기본 OS/DB 환경에 접근"해야 한다는 조건이 나오면 **Amazon RDS Custom**이 표준 정답입니다.

## QUESTION 134

**문제**: 한 회사가 애플리케이션을 서버리스 솔루션으로 이전하려고 한다. 이 솔루션은 SQL을 사용해 기존 및 신규 데이터를 분석해야 하며, 데이터는 Amazon S3 버킷에 저장된다. 데이터는 암호화가 필요하고 다른 AWS 리전으로 복제되어야 한다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. 새 S3 버킷을 생성하고 데이터를 로드한다. S3 CRR로 암호화된 객체를 다른 리전 버킷에 복제하고, AWS KMS 다중 리전 키(SSE-KMS)로 서버 측 암호화를 사용하며, Amazon Athena로 데이터를 쿼리한다(이미 기존 S3 버킷에 데이터가 있는 상황에서 새 버킷 생성은 불필요한 단계이며, SSE-KMS는 키 관리 작업이 추가되어 SSE-S3보다 운영 오버헤드가 큼).
- B. 새 S3 버킷을 생성하고 데이터를 로드한다. S3 CRR과 SSE-KMS를 사용하며, Amazon RDS로 데이터를 쿼리한다(S3에 있는 데이터를 쿼리하는 데는 RDS보다 서버리스 쿼리 서비스인 Athena가 적합하며, RDS 도입은 서버리스 요구에도 어긋남).
- C. **기존 S3 버킷에 데이터를 로드한다. S3 교차 리전 복제(CRR)를 사용하여 암호화된 객체를 다른 리전의 S3 버킷에 복제한다. Amazon S3 관리형 암호화 키(SSE-S3)로 서버 측 암호화를 사용한다. Amazon Athena를 사용하여 데이터를 쿼리한다.**
- D. 기존 S3 버킷에 데이터를 로드한다. S3 CRR과 SSE-S3를 사용하며, Amazon RDS로 데이터를 쿼리한다(RDS는 서버 프로비저닝과 관리가 필요해 서버리스 및 최소 운영 오버헤드 요구에 맞지 않음).

**정답: C**

**해설**
이미 데이터가 S3에 저장되어 있으므로 기존 버킷을 그대로 활용하는 것이 가장 단순합니다. **S3 CRR**을 사용하면 별도 애플리케이션 로직 없이 객체가 자동으로 다른 리전에 복제되고, **SSE-S3**는 AWS가 키 생성·교체를 전부 관리해 KMS 키 정책을 별도로 운영할 필요가 없어 운영 오버헤드가 가장 낮습니다. **Amazon Athena**는 서버리스 쿼리 서비스로 S3에 있는 기존 및 신규 데이터를 인프라 프로비저닝 없이 표준 SQL로 분석할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 새 버킷을 만들 필요가 없고, SSE-KMS는 키 관리 정책·권한 설정이 추가로 필요해 SSE-S3보다 운영 부담이 큽니다.
- B, D: RDS는 서버 인스턴스를 프로비저닝하고 관리해야 하므로 서버리스 요구 사항과 배치되며, S3 데이터 분석에는 Athena가 표준적인 선택입니다.

> 💡 **시험 꿀팁**: "S3의 기존/신규 데이터를 서버리스+SQL로 분석하면서 운영 오버헤드 최소화"라는 조건이 나오면 **기존 버킷 유지 + SSE-S3 + Athena** 조합이 표준 정답입니다.

> 💡 **시험 꿀팁**: "루트 계정 알림을 소수 관리자에게, 놓치지 않게" 하라는 조건이 나오면 **루트 이메일을 배포 목록으로 구성 + 계정 대체 연락처 설정**이 표준 정답입니다.

- C, D: 대기열을 자체 관리형 EC2 Auto Scaling 그룹으로 이중화하는 방식은 Amazon MQ의 완전관리형 활성/대기 구성보다 설정과 유지 관리 부담이 큽니다.

> 💡 **시험 꿀팁**: "최소 운영 오버헤드로 최고 가용성"이라는 조건에서 자체 관리형 미들웨어/DB가 선택지에 있다면, 동급 관리형 서비스(Amazon MQ, RDS 다중 AZ)를 사용하는 조합이 표준 정답입니다.

**정답: D**

**해설**
**S3 복제(Replication)**를 구성하면 초기 버킷에 파일이 들어오는 즉시 자동으로 분석 버킷에 복사되어, 파일 복사를 위한 Lambda 함수를 별도로 작성·유지할 필요가 없습니다. 분석 버킷에서 객체가 생성될 때 **Amazon EventBridge**로 이벤트를 보내도록 구성하면, 하나의 `ObjectCreated` 규칙에 **Lambda 함수**(패턴 매칭)와 **SageMaker Pipelines**를 여러 대상으로 동시에 연결할 수 있어 안정적이고 운영 부담이 적은 이벤트 기반 아키텍처가 완성됩니다.

**왜 다른 보기는 오답인가**
- A, B: S3 복제로 자동화할 수 있는 파일 이동 작업을 굳이 Lambda 함수로 별도 구현하면 불필요한 코드와 운영 부담이 추가됩니다.
- C: S3 이벤트 알림에 여러 대상을 직접 연결하면 이벤트가 많을 때 제한(throttling)이나 전달 실패가 발생할 수 있어, 다중 대상 라우팅에 특화된 EventBridge를 경유하는 것이 더 안정적입니다.

> 💡 **시험 꿀팁**: "버킷 간 자동 복사 + 여러 대상(Lambda, SageMaker 등)으로 이벤트 라우팅"이 필요하면 **S3 복제 + EventBridge 규칙(다중 대상)**이 표준 정답입니다.

## QUESTION 140

**문제**: 솔루션 설계자는 한 회사가 AWS에서 애플리케이션을 실행하는 비용을 최적화하도록 도와야 한다. 이 애플리케이션은 컴퓨팅을 위해 Amazon EC2 인스턴스, AWS Fargate, AWS Lambda를 함께 사용한다. EC2 인스턴스는 데이터 수집 계층을 실행하며 사용량이 산발적이고 예측 불가능하고, 언제든 중단되어도 무방하다. 애플리케이션 프런트엔드는 Fargate에서, API 계층은 Lambda에서 실행되며 이 두 계층의 향후 1년 사용률은 예측 가능하다. 이 애플리케이션을 가장 비용 효율적으로 호스팅하는 구매 옵션 조합은 무엇인가? (2개 선택)

**보기**
- A. **데이터 수집 계층에 스팟 인스턴스를 사용한다.**
- B. 데이터 수집 계층에 온디맨드 인스턴스를 사용한다(언제든 중단 가능한 워크로드에 정가를 지불하는 온디맨드를 쓰는 것은 비용 최적화 기회를 놓침).
- C. **프런트엔드 및 API 계층에 대해 1년 Compute Savings Plans를 구매한다.**
- D. 데이터 수집 계층에 1년 전체 선결제 예약 인스턴스를 구매한다(예약 인스턴스는 안정적이고 예측 가능한 사용량에 적합하며, 산발적이고 예측 불가능한 데이터 수집 계층의 사용 패턴과는 맞지 않음).
- E. 프런트엔드 및 API 계층을 위한 1년 EC2 인스턴스 Savings Plans를 구매한다(EC2 인스턴스 Savings Plans는 EC2에만 적용되며 Fargate와 Lambda 사용량에는 할인이 적용되지 않음).

**정답: A, C**

**해설**
데이터 수집 계층은 "언제든 중단 가능"하다는 특성이 있으므로 **스팟 인스턴스**를 사용하면 큰 폭의 비용 절감이 가능합니다. 반면 프런트엔드(Fargate)와 API 계층(Lambda)은 향후 1년 사용률을 예측할 수 있으므로 **Compute Savings Plans**로 약정 사용량에 대해 할인을 받을 수 있습니다. Compute Savings Plans는 인스턴스 패밀리, 크기, AZ, 리전, OS, 테넌시에 관계없이 EC2는 물론 **Fargate와 Lambda 사용량에도 적용**되는 가장 유연한 요금제이므로, 서로 다른 컴퓨팅 서비스를 함께 사용하는 이 시나리오에 정확히 들어맞습니다.

**왜 다른 보기는 오답인가**
- B: 중단을 허용할 수 있는 워크로드에 온디맨드 정가를 지불하는 것은 비효율적입니다.
- D: 예약 인스턴스는 예측 가능하고 안정적인 사용량에 적합하며, "산발적이고 예측 불가능한" 데이터 수집 계층에는 맞지 않습니다.
- E: EC2 인스턴스 Savings Plans는 할인율(최대 72%)은 더 높지만 EC2에만 적용되어 Fargate와 Lambda로 구성된 프런트엔드·API 계층에는 적용할 수 없습니다.

> 💡 **시험 꿀팁**: "EC2 + Fargate + Lambda를 함께 예측 가능하게 사용"한다면 **Compute Savings Plans**(EC2 전용이면 EC2 Instance Savings Plans)가 표준 정답이며, "중단 허용 + 예측 불가"라면 **스팟 인스턴스**가 표준 정답입니다.
