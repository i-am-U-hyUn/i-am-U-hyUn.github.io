## QUESTION 401

**문제**: 한 금융 서비스 회사는 Amazon RDS, Amazon EBS, Amazon EFS, Amazon DynamoDB 등 여러 AWS 서비스에 데이터를 분산 저장하고 있습니다. 규정 준수 담당 부서는 이 모든 리소스에 대해 단일 콘솔에서 백업 정책을 정의하고, 백업 일정과 보존 기간을 중앙에서 관리하며, 감사에 필요한 백업 이력을 추적할 수 있는 방법을 요구합니다. 솔루션 아키텍트는 어떤 서비스를 사용해야 합니까?

**보기**
- A. **AWS Backup을 사용하여 백업 계획을 생성하고 여러 서비스의 리소스를 태그 기반으로 백업 계획에 할당한다.**
- B. Amazon EventBridge 규칙을 만들어 매일 정해진 시간에 각 서비스의 스냅샷 API를 개별적으로 호출한다 (서비스마다 별도 자동화를 구축해야 하며 중앙 관리 콘솔이 없음).
- C. 각 서비스마다 자체 콘솔에서 자동 백업을 개별적으로 활성화하고 CloudWatch로 상태만 모니터링한다 (정책이 서비스별로 분산되어 중앙 관리가 불가능함).
- D. AWS Config 규칙을 사용하여 백업 미설정 리소스를 탐지하고 수동으로 알림을 받는다 (규정 위반 탐지 도구일 뿐 실제 백업을 수행하지 않음).

**정답: A**

**해설**: **AWS Backup**은 RDS, EBS, EFS, DynamoDB, Amazon FSx 등 다양한 AWS 서비스에 걸쳐 백업 정책을 하나의 콘솔에서 중앙 집중적으로 정의하고 적용할 수 있는 완전관리형 백업 서비스입니다. 백업 계획(backup plan)에 일정, 보존 기간, 수명 주기(라이프사이클) 규칙을 설정한 뒤 태그 기반으로 대상 리소스를 자동 할당할 수 있고, 백업 볼트와 백업 작업 이력을 통해 감사 요구 사항도 충족할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: EventBridge와 개별 스냅샷 API 호출 조합은 구현 가능하지만 서비스마다 별도의 자동화 코드를 작성해야 하고, 중앙 집중식 정책 관리와 통합 감사 로그를 제공하지 않습니다.
- C: 서비스별 자동 백업(RDS 자동 백업 등)은 각각 독립적으로 설정되어야 하며 통합된 정책 관리 화면이 없습니다.
- D: AWS Config는 리소스 구성 준수 여부를 평가하는 서비스로, 백업 미설정을 탐지할 수는 있어도 실제 백업 작업을 수행하지는 않습니다.

> 💡 **시험 꿀팁**: 여러 서비스에 걸친 "중앙 집중식 백업 정책"이라는 키워드가 나오면 AWS Backup을 먼저 떠올리세요.

## QUESTION 402

**문제**: 한 스타트업이 VPC 내에 웹 티어 서브넷과 데이터베이스 티어 서브넷을 분리해 운영하고 있습니다. 최근 애플리케이션 배포 이후 웹 서버가 데이터베이스 서브넷의 인스턴스와 통신하지 못한다는 보고가 들어왔습니다. 보안 그룹과 라우팅 테이블 설정은 정상으로 보이며, 팀은 실제로 트래픽이 어느 지점에서 차단되고 있는지 상세히 확인하고 싶습니다. 가장 적절한 진단 방법은 무엇입니까?

**보기**
- A. Amazon CloudWatch 대시보드에서 EC2 CPU 사용률 지표를 확인한다 (네트워크 수준의 허용/거부 정보는 제공하지 않음).
- B. **VPC Flow Logs를 활성화하여 두 서브넷 간 트래픽의 ACCEPT/REJECT 기록을 캡처하고 분석한다.**
- C. AWS X-Ray를 사용하여 애플리케이션 코드의 요청 추적 정보를 수집한다 (애플리케이션 계층 추적 도구로 네트워크 계층 차단 여부는 확인할 수 없음).
- D. Amazon Inspector로 EC2 인스턴스의 취약점을 스캔한다 (보안 취약점 점검 도구이며 트래픽 흐름 진단과는 무관함).

**정답: B**

**해설**: **VPC Flow Logs**는 VPC 내 네트워크 인터페이스를 오가는 IP 트래픽에 대한 정보를 캡처하여 CloudWatch Logs나 S3로 전송합니다. 각 흐름 레코드에는 소스/대상 IP, 포트, 프로토콜과 함께 ACCEPT 또는 REJECT 여부가 기록되므로, 보안 그룹이나 네트워크 ACL 중 어느 지점에서 트래픽이 거부되고 있는지 정확히 파악할 수 있어 이번 시나리오의 근본 원인 분석에 가장 적합합니다.

**왜 다른 보기는 오답인가**
- A: CloudWatch의 CPU 지표는 인스턴스 성능 지표일 뿐 네트워크 트래픽의 허용/차단 여부를 알려주지 않습니다.
- C: X-Ray는 분산 애플리케이션의 요청 흐름을 추적하는 도구로, 네트워크 계층에서 패킷이 차단되었는지는 확인할 수 없습니다.
- D: Inspector는 소프트웨어 취약점과 네트워크 도달 가능성을 평가하는 보안 평가 서비스로, 실시간 트래픽 허용/거부 기록을 제공하지는 않습니다.

> 💡 **시험 꿀팁**: "어느 지점에서 트래픽이 차단되는지 확인"이라는 문구가 나오면 VPC Flow Logs를 정답 후보 1순위로 두세요.

## QUESTION 403

**문제**: 한 미디어 회사는 S3 버킷에 저작권이 있는 동영상 파일을 비공개로 저장하고 있습니다. 프리미엄 구독자에게는 로그인 후 15분 동안만 특정 동영상 파일을 다운로드할 수 있는 링크를 제공하고 싶지만, 버킷 자체를 퍼블릭으로 전환하고 싶지는 않습니다. 이 요구 사항을 가장 간단하게 충족하는 방법은 무엇입니까?

**보기**
- A. S3 버킷 정책을 수정하여 모든 사용자에게 GetObject 권한을 부여한다 (버킷 전체가 퍼블릭이 되어 시간 제한 접근이 불가능함).
- B. CloudFront 배포를 생성하고 오리진 액세스를 퍼블릭으로 설정한다 (오리진을 퍼블릭으로 열면 접근 시간을 제한할 방법이 없음).
- C. **애플리케이션 서버에서 S3 프리사인드 URL(presigned URL)을 생성하여 만료 시간을 15분으로 설정한 링크를 제공한다.**
- D. IAM 사용자를 구독자 수만큼 생성하고 각각에게 해당 객체에 대한 GetObject 권한을 부여한다 (사용자 수만큼 IAM 자격 증명을 관리해야 하며 확장성이 떨어지고 시간 제한도 자동으로 걸리지 않음).

**정답: C**

**해설**: **S3 프리사인드 URL**은 객체 소유자의 자격 증명으로 서명된 임시 URL로, 만료 시간을 지정할 수 있어 버킷이나 객체를 퍼블릭으로 전환하지 않고도 특정 사용자에게 제한된 시간 동안만 접근을 허용할 수 있습니다. 애플리케이션 서버가 인증된 구독자 요청에 대해서만 URL을 생성해 주면 되므로 구현도 간단합니다.

**왜 다른 보기는 오답인가**
- A: 버킷 정책으로 모든 사용자에게 권한을 주면 객체가 완전히 퍼블릭이 되어 시간 제한이나 사용자별 접근 통제가 불가능합니다.
- B: CloudFront 오리진을 퍼블릭으로 노출하면 누구나 URL을 알면 접근할 수 있게 되어 "15분 제한"이라는 요구 사항을 만족시키지 못합니다.
- D: 구독자마다 IAM 사용자를 만드는 방식은 관리 오버헤드가 매우 크고, 자동으로 15분 후 만료되는 접근 제어를 기본 제공하지 않습니다.

> 💡 **시험 꿀팁**: "비공개 객체에 대한 시간 제한 임시 접근"은 거의 항상 S3 프리사인드 URL을 가리킵니다.

## QUESTION 404

**문제**: 한 전자상거래 회사는 트래픽 급증 시간대에 AWS Lambda 함수 수천 개가 동시에 Amazon RDS for MySQL에 연결을 시도하면서 "too many connections" 오류가 자주 발생한다고 호소합니다. 데이터베이스 인스턴스 크기를 늘리지 않고 연결 관리를 개선하고 싶습니다. 가장 적절한 해결책은 무엇입니까?

**보기**
- A. RDS 인스턴스 클래스를 더 큰 사이즈로 업그레이드하여 최대 연결 수를 늘린다 (비용은 증가하지만 근본적으로 연결 폭주 문제를 해결하지 못하고 임시방편에 불과함).
- B. Lambda 함수의 동시 실행 수를 예약 동시성으로 제한하여 트래픽을 인위적으로 줄인다 (처리량을 떨어뜨려 사용자 경험을 저하시키는 우회책일 뿐임).
- C. 애플리케이션 코드에 재시도 로직과 지수 백오프를 추가하여 연결 실패를 흡수한다 (근본 원인인 연결 수 폭증 자체는 해결하지 못하고 지연 시간만 늘어남).
- D. **Amazon RDS Proxy를 데이터베이스 앞단에 배치하여 Lambda의 연결을 풀링하고 관리한다.**

**정답: D**

**해설**: **Amazon RDS Proxy**는 애플리케이션과 데이터베이스 사이에서 커넥션 풀링을 관리하는 완전관리형 프록시로, Lambda처럼 짧은 수명의 연결을 많이 생성하는 서버리스 워크로드에서 발생하는 연결 폭주 문제를 효과적으로 해결합니다. 다수의 함수 실행이 소수의 실제 데이터베이스 연결을 공유하도록 하여 "too many connections" 오류를 방지하고 장애 조치 시간도 단축시킵니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스 크기를 키우면 최대 연결 수 한도는 늘어나지만 비용이 크게 증가하고, Lambda의 특성상 연결 수가 계속 증가하면 다시 한계에 부딪힙니다.
- B: 동시성을 제한하면 문제 자체를 우회할 뿐 처리량이 줄어 비즈니스 요구 사항(트래픽 급증 처리)을 만족시키지 못합니다.
- C: 재시도 로직은 오류를 감추는 임시 대응일 뿐 연결 수 폭증이라는 근본 원인은 그대로 남습니다.

> 💡 **시험 꿀팁**: "Lambda + 관계형 데이터베이스 + 연결 폭주"라는 조합은 RDS Proxy를 가리키는 전형적인 신호입니다.

## QUESTION 405

**문제**: 한 다국적 기업은 AWS Organizations로 수십 개의 계정을 관리하고 있습니다. 보안팀은 모든 멤버 계정에서 발생하는 API 호출 이력을 하나의 중앙 S3 버킷에 통합하여, 누가 언제 어떤 API를 호출했는지 조직 전체 단위로 감사하고 싶어 합니다. 어떤 서비스를 사용해야 합니까?

**보기**
- A. **조직 전체에 적용되는 AWS CloudTrail 조직 추적(organization trail)을 생성하여 모든 멤버 계정의 이벤트를 관리 계정의 S3 버킷으로 통합한다.**
- B. 각 멤버 계정에서 개별적으로 CloudTrail을 활성화하고 관리자가 매일 수동으로 로그를 취합한다 (계정 수만큼 반복 작업이 필요하며 중앙화된 자동 통합이 아님).
- C. Amazon CloudWatch Logs Insights를 각 계정에 배포하여 API 로그를 쿼리한다 (CloudWatch Logs Insights는 로그 분석 도구일 뿐 API 호출 자체를 기록하는 서비스가 아님).
- D. AWS Config Aggregator를 사용하여 계정 간 리소스 구성 변경 이력을 수집한다 (리소스 구성 변경 이력을 다루는 서비스로 API 호출 감사 목적과는 다름).

**정답: A**

**해설**: **AWS CloudTrail**의 조직 추적 기능을 사용하면 AWS Organizations의 관리 계정에서 추적을 하나 생성하는 것만으로 모든 멤버 계정의 관리 이벤트와 데이터 이벤트를 자동으로 지정된 S3 버킷에 통합 기록할 수 있습니다. 이를 통해 계정별로 개별 설정할 필요 없이 조직 전체에 대한 API 호출 감사를 중앙에서 수행할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 계정마다 개별적으로 CloudTrail을 켜고 수동으로 로그를 모으는 방식은 운영 부담이 크고 실수 가능성이 높으며 "중앙 집중식" 요구를 만족하지 못합니다.
- C: CloudWatch Logs Insights는 이미 수집된 로그를 검색·분석하는 도구로, API 호출 자체를 기록하는 것은 CloudTrail의 역할입니다.
- D: AWS Config는 리소스 구성 변경 이력을 추적하는 서비스이며 "누가 어떤 API를 호출했는가"라는 감사 요구에는 CloudTrail이 맞습니다.

> 💡 **시험 꿀팁**: "조직 전체 API 호출 감사"라는 표현이 나오면 CloudTrail 조직 추적(organization trail)을 떠올리세요.

## QUESTION 406

**문제**: 한 SaaS 기업은 프로덕션에 배포되는 EC2 인스턴스와 Amazon ECR에 저장된 컨테이너 이미지에 알려진 소프트웨어 취약점(CVE)이 있는지 지속적으로, 자동으로 스캔하고 싶어 합니다. 별도의 에이전트 배포 부담을 최소화하면서 취약점 발견 시 우선순위가 매겨진 결과를 받고자 합니다. 어떤 서비스가 적합합니까?

**보기**

- C. **Direct Connect 게이트웨이를 생성하여 기존 Direct Connect 연결에 여러 리전의 VPC(가상 프라이빗 게이트웨이)를 연결한다.**
- D. 각 리전마다 인터넷 게이트웨이를 통해 퍼블릭 인터넷으로 트래픽을 라우팅하고 IPsec으로 암호화한다 (퍼블릭 인터넷을 경유하므로 Direct Connect의 프라이빗 연결 이점을 상실함).

**정답: C**

**해설**: **AWS Direct Connect 게이트웨이(Direct Connect Gateway)**를 사용하면 하나의 Direct Connect 연결을 여러 AWS 리전에 있는 다수의 VPC와 연결할 수 있습니다. Direct Connect 게이트웨이에 각 리전 VPC의 가상 프라이빗 게이트웨이(또는 Transit Gateway)를 연결하기만 하면 되므로 리전마다 물리적인 Direct Connect 연결을 추가로 구축할 필요가 없습니다.

**왜 다른 보기는 오답인가**
- A: VPC 피어링과 리전별 VPN을 조합하는 방식은 기존 Direct Connect 연결 하나를 재사용하지 못하고 리전마다 별도 구성이 필요해 요구 사항에 부합하지 않습니다.
- B: Route 53 Resolver는 온프레미스와 VPC 간 DNS 쿼리 전달을 처리하는 서비스로 네트워크 연결 자체와는 관련이 없습니다.
- D: 퍼블릭 인터넷을 통한 IPsec VPN은 동작은 하지만 Direct Connect의 전용 회선을 통한 낮은 지연 시간과 안정적인 대역폭이라는 이점을 활용하지 못합니다.

> 💡 **시험 꿀팁**: "하나의 Direct Connect 연결로 여러 리전 VPC 연결"이라는 문구는 Direct Connect 게이트웨이를 가리키는 결정적 단서입니다.

**문제**: 한 온라인 게임 회사는 최근 대규모 분산 서비스 거부(DDoS) 공격을 받아 서비스가 몇 시간 동안 중단된 경험이 있습니다. 향후 대규모 계층 3/4 및 계층 7 DDoS 공격으로부터 애플리케이션을 보호하는 동시에, 공격으로 인해 급증한 리소스 사용량에 대한 비용 보호와 24시간 전담 대응팀(DRT) 지원까지 받고 싶어 합니다. 가장 적합한 솔루션은 무엇입니까?

- A: Shield Standard는 모든 AWS 고객에게 무료로 기본 제공되지만 계층 7 공격 방어, DRT 지원, 비용 보호와 같은 고급 기능은 포함되어 있지 않습니다.

> 💡 **시험 꿀팁**: "DDoS 비용 보호 + 전담 대응팀(DRT)"이라는 키워드 조합은 Shield Standard가 아니라 Shield Advanced를 가리킵니다.

**문제**: 한 지질 조사 기업은 현장에서 수집한 페타바이트 규모의 원시 센서 데이터를 AWS로 한 번만 이전하려고 합니다. 현재 인터넷 회선 대역폭으로 계산했을 때 전체 데이터를 전송하는 데 수개월이 소요될 것으로 예상되며, 향후 반복적인 전송 요구는 없습니다. 가장 비용 효율적이고 빠른 이전 방법은 무엇입니까?

**보기**
- A. AWS Direct Connect 전용 회선을 새로 구축하여 데이터를 전송한다 (구축에 수 주에서 수개월이 걸리고 일회성 이전에는 비용 대비 효율이 낮음).
- B. S3 Transfer Acceleration을 활성화하여 인터넷을 통한 업로드 속도를 높인다 (네트워크 경로를 최적화해 속도를 개선할 수는 있으나 페타바이트 규모에서는 여전히 수개월이 소요될 수 있음).
- C. AWS DataSync 에이전트를 설치하여 온프레미스 NAS에서 S3로 지속적으로 동기화한다 (네트워크 대역폭에 의존하는 방식이라 페타바이트 규모의 일회성 전송에는 여전히 오랜 시간이 걸림).
- D. **AWS Snowball Edge 디바이스를 주문하여 오프라인으로 데이터를 적재한 뒤 AWS로 배송하여 S3에 임포트한다.**

**정답: D**

**해설**: **AWS Snowball Edge**는 물리적인 데이터 전송 디바이스로, 페타바이트 규모의 데이터를 네트워크를 거치지 않고 디바이스에 직접 적재한 뒤 AWS로 배송하여 가져오는 방식입니다. 네트워크 대역폭의 제약을 받지 않으므로 수개월이 걸릴 인터넷 기반 전송보다 훨씬 빠르고 비용 효율적으로 대규모 일회성 마이그레이션을 완료할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Direct Connect는 지속적이고 반복적인 하이브리드 연결에 적합한 전용 회선 서비스로, 구축 기간이 길고 일회성 대량 이전에는 적합하지 않습니다.
- B: Transfer Acceleration은 CloudFront 엣지 로케이션을 활용해 업로드 속도를 개선하지만 근본적으로 인터넷 대역폭에 의존하므로 페타바이트급 데이터에는 한계가 있습니다.
- C: DataSync 역시 네트워크를 통해 데이터를 전송하는 서비스이므로 대역폭이 제한된 환경에서 페타바이트 규모를 옮기기에는 시간이 오래 걸립니다.

> 💡 **시험 꿀팁**: "네트워크로는 수개월이 걸리는 페타바이트급 일회성 이전"이라는 조건은 Snowball(Edge)을 가리키는 전형적인 신호입니다.

## QUESTION 417

**문제**: 한 회사는 3개의 가용 영역에 걸쳐 백엔드 EC2 인스턴스를 배포했지만, 각 가용 영역에 등록된 인스턴스 수가 서로 다릅니다(AZ-1에 6대, AZ-2에 2대, AZ-3에 2대). 로드 밸런서가 가용 영역 단위로만 트래픽을 균등 분배하다 보니 AZ-2와 AZ-3의 인스턴스가 AZ-1보다 훨씬 많은 부하를 받고 있습니다. 모든 가용 영역의 전체 타깃에 걸쳐 트래픽이 고르게 분배되도록 하려면 어떻게 해야 합니까?

**보기**
- A. **로드 밸런서에서 교차 영역 로드 밸런싱(cross-zone load balancing)을 활성화하여 모든 가용 영역의 모든 대상에 트래픽을 균등하게 분배한다.**
- B. 모든 가용 영역에 정확히 동일한 수의 인스턴스를 배치하도록 Auto Scaling 그룹을 재구성한다 (근본적인 로드 밸런서 분배 방식을 바꾸지 않고 인스턴스 수만 강제로 맞추는 우회적 방법이며 유연성이 떨어짐).
- C. 각 가용 영역마다 별도의 로드 밸런서를 생성하고 Route 53 가중치 라우팅으로 트래픽을 분산한다 (구성이 복잡해지고 여전히 각 로드 밸런서 내부에서는 AZ 단위 분배 문제가 그대로 남을 수 있음).
- D. 대상 그룹의 상태 검사 임계값을 조정하여 비정상 인스턴스를 더 빨리 제외시킨다 (상태 검사는 장애 인스턴스를 제외하는 기능일 뿐 정상 인스턴스 간의 트래픽 분배 방식과는 무관함).

**정답: A**

**해설**: **교차 영역 로드 밸런싱(cross-zone load balancing)**을 활성화하면 로드 밸런서 노드가 자신이 위치한 가용 영역뿐 아니라 다른 모든 가용 영역에 등록된 대상까지 포함하여 트래픽을 균등하게 분배합니다. 이렇게 하면 가용 영역별 인스턴스 수가 서로 다르더라도 전체 타깃 풀에 걸쳐 고르게 부하가 분산됩니다. Application Load Balancer는 기본적으로 활성화되어 있고, Network Load Balancer는 명시적으로 활성화해야 합니다.

**왜 다른 보기는 오답인가**
- B: 가용 영역마다 인스턴스 수를 강제로 동일하게 맞추는 것은 Auto Scaling의 유연한 확장/축소를 제한하고 근본적인 로드 밸런서 분배 로직 문제를 해결하지 못합니다.
- C: 로드 밸런서를 여러 개로 나누고 Route 53으로 분산하는 방식은 아키텍처를 불필요하게 복잡하게 만들 뿐 각 로드 밸런서 내부의 AZ 단위 분배 문제를 직접 해결하지 않습니다.
- D: 상태 검사 설정은 비정상 대상을 트래픽 분배에서 제외하는 기능으로, 정상 대상 간의 트래픽 분배 비율 자체를 조정하지는 않습니다.

> 💡 **시험 꿀팁**: "AZ별 인스턴스 수가 달라 부하가 불균등"하다는 문제에는 교차 영역 로드 밸런싱 활성화가 정답입니다.

## QUESTION 418

**문제**: 한 글로벌 전자상거래 회사는 Amazon CloudFront를 통해 정적 콘텐츠를 제공하고 있습니다. 이 회사는 사용자의 위치나 요청 헤더에 따라 엣지 로케이션에서 실시간으로 요청 URL을 재작성하거나 응답 헤더에 개인화된 콘텐츠를 삽입하고 싶어 하며, 오리진 서버까지 요청을 보내지 않고 최대한 사용자와 가까운 곳에서 로직을 처리하고자 합니다. 어떤 방법이 적합합니까?

**보기**
- A. 오리진 서버에 애플리케이션 로직을 추가하여 모든 요청을 처리한다 (요청이 오리진까지 왕복해야 하므로 지연 시간이 늘어나고 엣지에서 처리한다는 요구 사항에 맞지 않음).
- B. **Lambda@Edge를 사용하여 CloudFront 엣지 로케이션에서 요청/응답을 가로채 실시간으로 수정한다.**
- C. Amazon API Gateway를 CloudFront 앞단에 두고 매핑 템플릿으로 요청을 변환한다 (API Gateway는 리전 기반 서비스로 엣지 로케이션에서 실행되지 않아 지연 시간 이점을 제공하지 못함).

**해설**: **Lambda@Edge**는 CloudFront의 엣지 로케이션에서 실행되는 서버리스 함수로, 뷰어 요청/응답, 오리진 요청/응답의 네 가지 시점에 개입하여 콘텐츠를 실시간으로 수정할 수 있습니다. 이를 통해 오리진까지 왕복하지 않고도 사용자와 가장 가까운 위치에서 URL 재작성, 헤더 삽입, 개인화 로직 등을 처리할 수 있어 지연 시간을 최소화합니다.

**왜 다른 보기는 오답인가**
- A: 오리진에서 처리하면 매 요청이 오리진까지 왕복해야 하므로 CloudFront의 엣지 이점을 활용하지 못하고 지연 시간이 늘어납니다.
- C: API Gateway는 특정 AWS 리전에서 실행되는 리전 서비스로, CloudFront의 전 세계 엣지 로케이션에서 직접 실행되지 않습니다.
- D: Global Accelerator는 애니캐스트 IP를 통해 최적의 네트워크 경로로 트래픽을 라우팅하는 서비스로, 요청/응답 콘텐츠 자체를 수정하는 컴퓨팅 기능은 제공하지 않습니다.

> 💡 **시험 꿀팁**: "CloudFront 엣지에서 요청/응답을 실시간으로 수정"이라는 요구 사항은 Lambda@Edge를 가리키는 결정적 단서입니다.

## QUESTION 419

**문제**: 한 실시간 입찰 광고 플랫폼은 Amazon DynamoDB 테이블에서 초당 수십만 건의 읽기 요청을 처리해야 하며, 응답 지연 시간을 마이크로초 단위로 유지해야 합니다. 팀은 범용 캐싱 계층으로 Amazon ElastiCache를 도입하는 방안도 검토했지만, DynamoDB API와의 완벽한 호환성과 캐시 무효화를 자동으로 처리해 주는 관리 편의성을 더 중요하게 여기고 있습니다. 어떤 서비스를 선택해야 합니까?

**보기**
- A. Amazon ElastiCache for Redis를 도입하고 애플리케이션 코드에서 캐시 조회 및 DynamoDB 폴백 로직, 캐시 무효화 로직을 직접 구현한다 (범용 캐시로 강력하지만 DynamoDB 전용 캐시 무효화나 API 호환을 자동으로 제공하지 않아 개발 부담이 큼).
- B. Amazon ElastiCache for Memcached를 도입하고 TTL 기반으로 캐시를 관리한다 (범용 인메모리 캐시로 DynamoDB API와 네이티브로 통합되지 않아 별도의 통합 계층을 직접 구축해야 함).
- C. **Amazon DynamoDB Accelerator(DAX)를 도입하여 DynamoDB API와 호환되는 인메모리 캐시로 마이크로초 단위의 읽기 지연 시간을 달성한다.**
- D. Amazon RDS 읽기 전용 복제본을 추가하여 읽기 부하를 분산한다 (DynamoDB가 아닌 관계형 데이터베이스에 적용되는 방식으로 이번 아키텍처와 호환되지 않음).

**정답: C**

**해설**: **Amazon DynamoDB Accelerator(DAX)**는 DynamoDB 전용으로 설계된 완전관리형 인메모리 캐시로, 기존 DynamoDB API 호출과 호환되는 방식으로 동작하여 애플리케이션 코드 변경을 최소화하면서 응답 지연 시간을 마이크로초 단위로 낮춰줍니다. 또한 쓰기 시 캐시를 자동으로 갱신하는 write-through 방식을 사용해 별도의 캐시 무효화 로직을 직접 구현할 필요가 없습니다.

**왜 다른 보기는 오답인가**
- A: ElastiCache for Redis는 강력한 범용 캐시이지만 DynamoDB 전용 API 호환이나 자동 캐시 무효화를 기본 제공하지 않아 개발자가 캐시-스루/라이트-스루 로직을 직접 구현해야 합니다.
- B: ElastiCache for Memcached 역시 범용 캐시로 DynamoDB와 네이티브로 통합되지 않으며 TTL 기반 관리만으로는 일관성 문제를 해결하기 어렵습니다.
- D: RDS 읽기 전용 복제본은 관계형 데이터베이스에 적용되는 확장 기법으로 DynamoDB 기반 아키텍처와는 무관합니다.

> 💡 **시험 꿀팁**: "DynamoDB API 호환 + 마이크로초 지연 시간 캐시"라는 조건이 나오면 ElastiCache가 아니라 DAX를 선택하세요.

## QUESTION 420

- B. AWS Cost Explorer에서 서비스별 비용 추이를 시각화하여 수동으로 분석한다 (비용 데이터 시각화 도구일 뿐 구체적인 개선 권장 사항이나 보안 체크 항목을 자동으로 제시하지 않음).

**왜 다른 보기는 오답인가**
- A: Cost Anomaly Detection은 비정상적인 비용 급증을 탐지하는 데 특화된 기능으로 보안이나 유휴 리소스 등 폭넓은 모범 사례 점검은 다루지 않습니다.
- B: Cost Explorer는 비용 데이터를 시각화하고 분석하는 도구로, 사전 정의된 개선 권장 사항이나 보안 체크 항목을 자동으로 제시하지는 않습니다.
- C: QuickSight는 범용 비즈니스 인텔리전스 시각화 서비스로, Trusted Advisor처럼 AWS 모범 사례에 기반한 사전 정의된 체크 항목을 기본 제공하지 않으며 대시보드를 직접 구축해야 합니다.

> 💡 **시험 꿀팁**: "비용 절감과 보안 모범 사례를 아우르는 자동화된 계정 점검 및 권장 사항"이라는 표현은 AWS Trusted Advisor를 가리킵니다.
