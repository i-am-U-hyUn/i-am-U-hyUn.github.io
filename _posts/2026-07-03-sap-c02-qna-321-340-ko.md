## QUESTION 321

**문제**: EKS 기반 마이크로서비스 환경에서 신규 버전을 배포할 때, 전체 트래픽을 한 번에 전환하지 않고 **트래픽의 일부(예: 5%)만 새 버전으로 점진적으로 이전**하면서 오류율을 관찰하고 싶다. 또한 서비스 간 통신에 대한 상세한 관찰성(지연시간, 오류율)도 함께 얻고 싶다. 애플리케이션 코드 수정을 최소화하는 솔루션은?

**보기**
- A. ALB의 가중치 기반 대상 그룹(weighted target group)만 사용(ALB 가중치 라우팅으로 점진적 트래픽 전환은 가능하지만, 서비스 간 상세한 관찰성[지연시간, 재시도, 서킷 브레이커 등]까지 함께 제공하지는 않음).
- B. **AWS App Mesh를 도입해 서비스 메시로 마이크로서비스 간 통신을 관리하고, 가상 라우터(virtual router)의 가중치 기반 라우팅으로 새 버전에 트래픽의 일부만 점진적으로 전달하며, 사이드카를 통해 상세한 관찰성 지표를 수집.**
- C. Route 53 가중치 기반 라우팅으로 서비스 엔드포인트 전환(Route 53 가중치 라우팅은 DNS 수준에서 동작해 세밀한 트래픽 비율 제어와 클라이언트 측 DNS 캐싱으로 인한 정밀도 문제가 있고, 마이크로서비스 간 상세 관찰성도 제공하지 않음).
- D. 애플리케이션 코드에 자체 카나리 로직(요청의 5%를 무작위로 다른 엔드포인트로 라우팅)을 하드코딩(모든 서비스 코드에 이 로직을 직접 구현/유지해야 해서 "코드 수정 최소화" 요구에 반함).

**정답: B**

**해설**
**AWS App Mesh**는 서비스 메시를 통해 마이크로서비스 간 통신을 애플리케이션 코드와 분리된 계층에서 제어합니다. **가상 라우터**에서 가중치 기반 라우팅 규칙을 설정하면 트래픽의 일정 비율(예: 5%)만 새 버전으로 점진적으로 전환하는 카나리 배포를 코드 변경 없이 구현할 수 있으며, 각 서비스에 주입된 Envoy 사이드카가 지연시간·오류율 같은 상세한 관찰성 지표를 자동으로 수집합니다.

**왜 다른 보기는 오답인가**
- A: ALB 가중치 라우팅은 점진적 전환 자체는 가능하지만, 서비스 간 통신에 대한 세밀한 관찰성(재시도, 회로 차단 등)까지 기본 제공하지는 않습니다.
- C: DNS 기반 가중치 라우팅은 클라이언트/리졸버 캐싱으로 인해 실제 비율 제어가 부정확할 수 있고, 관찰성 기능도 없습니다.
- D: 자체 구현은 모든 서비스에 동일한 로직을 반복 구현/유지해야 해서 "코드 수정 최소화"에 반합니다.

> 💡 **시험 꿀팁**: 마이크로서비스 간 **점진적 카나리 트래픽 전환 + 상세 관찰성**을 코드 변경 없이 구현하려면 **AWS App Mesh**(가상 라우터 가중치 라우팅 + 사이드카 관찰성)가 표준 정답입니다.

## QUESTION 322

**문제**: 회사가 여러 계정에 걸쳐 수백 개의 S3 버킷을 운영하며, 그중 일부에 개인 식별 정보(PII, 예: 주민등록번호, 신용카드 번호)가 실수로 저장되어 있을 가능성이 있다. 조직 전체에서 이런 민감 데이터가 저장된 버킷/객체를 **자동으로 탐지**하고 보안 팀에 알리고 싶다. 솔루션은?

**보기**
- A. 각 버킷의 객체를 정기적으로 다운로드해 정규식으로 PII 패턴을 직접 스캔하는 Lambda 함수 구현(대량의 객체를 매번 다운로드/스캔하는 자체 구현은 비용과 운영 부담이 크고, 다양한 PII 유형에 대한 정확도 높은 탐지 로직을 직접 유지보수해야 함).
- B. **Amazon Macie를 조직 계정으로 통합해 활성화하고, 조직 내 모든 계정의 S3 버킷에 대해 민감 데이터 검색 작업(discovery job)을 구성해 PII 탐지 시 자동으로 결과를 보고받도록 설정.**
- C. GuardDuty로 S3 버킷의 PII를 탐지(GuardDuty는 주로 비정상적인 API 호출 패턴이나 악성 활동 같은 위협 탐지에 특화되어 있으며, 객체 내용의 민감 데이터[PII] 자체를 스캔하는 기능은 Macie의 역할).
- D. S3 Inventory 리포트를 생성해 객체 메타데이터만 확인(Inventory는 객체의 메타데이터[크기, 마지막 수정일 등]를 나열할 뿐이며, 객체 내용을 분석해 PII 여부를 판단하는 기능이 없음).

**정답: B**

**해설**
**Amazon Macie**는 머신러닝과 패턴 매칭을 사용해 S3에 저장된 데이터에서 개인 식별 정보(PII), 자격 증명, 금융 정보 같은 민감 데이터를 **자동으로 탐지**하는 관리형 서비스입니다. Organizations와 통합해 위임된 관리자 계정에서 조직 내 모든 계정의 S3 버킷에 대한 검색 작업을 중앙에서 구성하면, 대규모 환경에서도 직접 스캔 로직을 구현할 필요 없이 민감 데이터가 발견된 버킷/객체를 자동으로 식별하고 보고받을 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 자체 스캔 로직 구현은 대량 데이터 처리 비용과 탐지 정확도 유지보수 부담이 매우 큽니다.
- C: GuardDuty는 위협/이상 행위 탐지에 특화되어 있으며, 객체 콘텐츠의 민감 데이터 자체를 스캔하는 기능은 제공하지 않습니다.
- D: S3 Inventory는 메타데이터 목록화 기능일 뿐 콘텐츠 분석 기능이 없습니다.

> 💡 **시험 꿀팁**: S3에 저장된 데이터에서 **PII 등 민감 데이터를 자동으로 탐지**하려면 **Amazon Macie**(조직 통합 + 검색 작업)가 표준 정답입니다.

## QUESTION 323

**문제**: 지사 사무실의 로컬 파일 서버 데이터를 본사 AWS 계정의 S3로 지속적으로 동기화해야 하는데, 지사의 인터넷 회선 대역폭이 제한적이라 **업무 시간대에는 대역폭 사용을 제한**하고, 야간에는 최대 속도로 동기화하고 싶다. 파일 메타데이터(권한, 타임스탬프)도 보존해야 한다. 솔루션은?

**보기**
- A. rsync를 크론으로 스케줄링해 매일 밤에만 실행(rsync 자체로는 AWS와의 통합 모니터링, 재시도, 검증 기능이 부족하고, 대역폭 제한을 시간대별로 세밀하게 관리하는 기능도 직접 구현해야 함).
- B. **AWS DataSync 에이전트를 지사에 배포하고, 태스크에 대역폭 제한(bandwidth throttling)을 설정해 업무 시간대에는 낮은 대역폭으로, 야간에는 스케줄을 통해 무제한 또는 높은 대역폭으로 동기화. 파일 메타데이터 보존 옵션 활성화.**
- C. S3 Transfer Acceleration만 사용해 전송 속도를 높임(Transfer Acceleration은 전송 경로를 최적화할 뿐 시간대별 대역폭 제한이나 파일 메타데이터 보존 같은 세밀한 제어 기능을 제공하지 않음).
- D. Storage Gateway 파일 게이트웨이로 전환(파일 게이트웨이는 저지연 접근에 최적화된 캐싱 게이트웨이이며, 이 시나리오처럼 시간대별 대역폭 제한이 있는 대량 동기화 작업에는 DataSync가 더 적합).

**정답: B**

**해설**
**AWS DataSync**는 온프레미스(또는 다른 클라우드)와 AWS 스토리지 간 데이터 전송을 위한 관리형 서비스로, **대역폭 제한(bandwidth throttling)** 설정을 통해 특정 시간대의 네트워크 사용량을 제어할 수 있고, **스케줄링**으로 업무 시간대와 야간의 동작을 다르게 구성할 수 있습니다. 또한 파일의 **소유권, 권한, 타임스탬프 등 메타데이터를 보존**하는 옵션을 기본 제공해, 이 시나리오의 모든 요구사항(대역폭 제어, 스케줄링, 메타데이터 보존)을 관리형으로 충족합니다.

**왜 다른 보기는 오답인가**
- A: rsync는 기본적인 동기화는 가능하지만, AWS 서비스와의 통합 모니터링/검증, 세밀한 시간대별 대역폭 관리를 직접 구현해야 하는 부담이 있습니다.
- C: Transfer Acceleration은 전송 속도 최적화 기능일 뿐, 대역폭 제한이나 메타데이터 보존 기능을 제공하지 않습니다.
- D: 파일 게이트웨이는 저지연 파일 접근용 캐싱 솔루션으로, 이 시나리오의 대량/예약 동기화 요구에는 DataSync가 더 표준적입니다.

> 💡 **시험 꿀팁**: 온프레미스-S3 간 **대역폭 제한 + 스케줄링 + 메타데이터 보존**이 필요한 데이터 동기화에는 **AWS DataSync**가 표준 정답입니다.

## QUESTION 324

**문제**: Lambda 함수가 트래픽 급증 시 수천 개의 동시 실행 인스턴스를 생성하며 각각 RDS PostgreSQL에 직접 연결하는데, 이로 인해 **데이터베이스 연결 수 한계를 초과**해 "too many connections" 오류가 자주 발생한다. 애플리케이션 코드 변경을 최소화하며 이를 해결하려면?

**보기**
- A. RDS 인스턴스 클래스를 최대로 늘려 최대 연결 수 한도 자체를 늘림(인스턴스를 늘려도 결국 상한이 존재하며, Lambda의 폭발적 동시성 패턴 자체와는 근본적으로 맞지 않아 비용 대비 효과가 낮고 임시방편에 불과함).
- B. **Amazon RDS Proxy를 데이터베이스 앞단에 배치해 Lambda의 대량 연결 요청을 풀링(pooling)하고 관리해, 실제 데이터베이스에는 적은 수의 연결만 유지하도록 구성.**
- C. Lambda 동시 실행 수를 예약된 동시성(reserved concurrency)으로 낮게 제한(동시성을 제한하면 연결 문제는 완화되지만 트래픽 급증 시 요청 처리량 자체가 인위적으로 낮아져 애플리케이션 성능/가용성에 부정적 영향).
- D. RDS를 Aurora Serverless v2로 전환하고 별도 조치 없음(Serverless v2가 컴퓨팅 용량은 자동 조정하지만, Lambda의 대량 동시 연결로 인한 연결 수 한계 문제 자체를 근본적으로 해결하는 기능은 아니며, 연결 관리에는 여전히 RDS Proxy 같은 풀링 계층이 필요).

**정답: B**

**해설**
**Amazon RDS Proxy**는 애플리케이션(Lambda)과 데이터베이스 사이에서 **연결 풀링**을 수행하는 완전관리형 프록시입니다. Lambda 함수가 수천 개의 동시 실행 인스턴스에서 각각 연결을 시도해도, RDS Proxy가 이를 풀링해 실제 데이터베이스에는 훨씬 적은 수의 연결만 유지하므로, 애플리케이션 코드(연결 문자열의 엔드포인트만 RDS Proxy 엔드포인트로 변경)를 거의 수정하지 않고도 "too many connections" 문제를 해결할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스 클래스를 키우는 것은 최대 연결 수를 다소 늘릴 뿐 근본적인 연결 폭증 문제를 해결하지 못하며 비용도 큽니다.
- C: 동시성 제한은 연결 문제를 완화할 수 있지만 처리량 저하라는 부작용을 감수해야 하는 임시방편입니다.
- D: Aurora Serverless v2는 컴퓨팅 용량의 자동 확장/축소 기능이며, Lambda발 대량 연결 관리 문제는 별도로 RDS Proxy 같은 풀링 메커니즘이 필요합니다.

> 💡 **시험 꿀팁**: **Lambda의 폭발적 동시성으로 인한 관계형 DB 연결 수 초과** 문제에는 **Amazon RDS Proxy**(연결 풀링)가 코드 변경을 최소화하는 표준 정답입니다.

## QUESTION 325

**문제**: 재무 팀이 여러 계정에 걸친 EC2 사용 이력을 분석해 **어떤 Savings Plans/예약 인스턴스를 얼마나 구매해야 할지**에 대한 데이터 기반 권장 사항을 얻고 싶다. 자체적으로 사용률 분석 로직을 구현하지 않고 AWS가 제공하는 기능만으로 이를 수행하려면?

**보기**
- A. CloudWatch 지표를 수집해 자체 스프레드시트로 최적 구매량 계산(사용량 이력을 직접 분석해 최적 약정 구매 권장치를 계산하는 로직을 자체 구현해야 해서 비효율적이고 정확도도 AWS 권장 엔진보다 낮을 가능성).
- B. **AWS Cost Explorer의 Savings Plans 권장 사항(Savings Plans recommendations) 및 예약 인스턴스 권장 사항 기능을 사용해, 과거 사용 이력 기반으로 AWS가 제안하는 최적의 약정 유형/금액/기간을 확인.**
- C. Trusted Advisor의 비용 최적화 검사 결과만 확인(Trusted Advisor도 일부 비용 관련 점검을 제공하지만, 사용 이력 기반의 정교한 Savings Plans/RI 구매 권장 사항은 Cost Explorer의 전용 기능이 더 상세하고 표준적임).

**해설**
**AWS Cost Explorer**는 계정(또는 조직)의 과거 사용 이력을 분석해 **Savings Plans 권장 사항**과 **예약 인스턴스 권장 사항**을 자동으로 생성합니다. 이 권장 사항은 어떤 유형의 약정을 얼마의 시간당 금액(또는 수량)으로, 얼마의 기간 동안 구매하면 예상 절감액이 최대화되는지를 데이터 기반으로 제시해, 자체 분석 로직 구현 없이 최적의 구매 결정을 내릴 수 있게 해줍니다.

**왜 다른 보기는 오답인가**
- A: 자체 분석 로직 구현은 불필요한 개발 부담이며, AWS의 정교한 권장 알고리즘만큼의 정확도를 보장하기 어렵습니다.
- C: Trusted Advisor도 비용 관련 점검 항목이 있지만, 상세한 약정 구매 권장 사항 생성은 Cost Explorer가 전용으로 제공하는 기능입니다.
- D: 수동 청구서 검토는 정밀한 데이터 기반 권장 사항을 대체할 수 없습니다.

> 💡 **시험 꿀팁**: 과거 사용 이력을 기반으로 **최적의 Savings Plans/예약 인스턴스 구매 권장 사항**을 얻으려면 **AWS Cost Explorer의 권장 사항 기능**이 표준 정답입니다.

## QUESTION 326

**문제**: 회사가 Direct Connect로 AWS와 연결되어 있으며, VPC 내부 리소스뿐 아니라 **S3, DynamoDB 같은 AWS 퍼블릭 서비스**에도 인터넷을 거치지 않고 Direct Connect를 통해 비공개로 접근하고 싶다. 솔루션은?

- A. Direct Connect의 프라이빗 가상 인터페이스(private VIF)만으로 S3에 접근(프라이빗 VIF는 VPC 내부 리소스(사설 IP 대역)와의 연결용이며, S3 같은 퍼블릭 서비스 엔드포인트[퍼블릭 IP 대역]에는 접근할 수 없음 — 개념 오류).
- B. **Direct Connect에 퍼블릭 가상 인터페이스(public VIF)를 추가로 구성해, AWS의 모든 퍼블릭 서비스(S3, DynamoDB 등) 퍼블릭 IP 대역에 대한 트래픽을 인터넷을 거치지 않고 Direct Connect 회선으로 라우팅.**

**해설**
Direct Connect의 **퍼블릭 가상 인터페이스(public VIF)**를 구성하면, 온프레미스 네트워크에서 AWS의 모든 리전 **퍼블릭 서비스 엔드포인트**(S3, DynamoDB 등의 퍼블릭 IP 대역)에 대한 트래픽을 인터넷이 아닌 Direct Connect 전용 회선을 통해 라우팅할 수 있습니다. 이는 온프레미스에서 AWS 퍼블릭 서비스로의 트래픽을 비공개로 유지하면서 대역폭과 지연시간 이점도 얻을 수 있는 표준 방법입니다.

**왜 다른 보기는 오답인가**

- C: NAT Gateway를 통한 접근은 결국 인터넷 경로를 사용하므로 요구사항에 반합니다.
- D: 게이트웨이 엔드포인트는 VPC 내부에서의 접근을 다루며, 온프레미스에서 Direct Connect를 통한 접근에는 퍼블릭 VIF가 필요합니다.

> 💡 **시험 꿀팁**: 온프레미스에서 Direct Connect를 통해 **S3/DynamoDB 같은 AWS 퍼블릭 서비스**에 인터넷 없이 접근하려면 **퍼블릭 가상 인터페이스(public VIF)**가 표준 정답입니다. VPC 내부 리소스 접근용인 프라이빗 VIF와의 차이를 기억하세요.

## QUESTION 327

**문제**: 스타트업이 EKS에서 여러 워크로드를 실행하려 하지만, 워커 노드(EC2)의 프로비저닝·패치·용량 관리를 전혀 하고 싶지 않으며, 파드 단위로만 과금되기를 원한다. 일부 워크로드만 이런 서버리스 방식이 필요하고 나머지는 기존 관리형 노드 그룹을 계속 사용해도 된다. 솔루션은?

> 💡 **시험 꿀팁**: EKS에서 **특정 워크로드만 노드 관리 없이 파드 단위로 과금되는 서버리스 방식**으로 실행하려면 **EKS Fargate 프로파일**(네임스페이스/라벨 기반)이 표준 정답이며, 나머지는 기존 관리형 노드 그룹과 혼용 가능합니다.

## QUESTION 328

**문제**: 회사 내부 직원 전용 애플리케이션이 API Gateway를 사용하는데, 이 API가 **회사 VPC 내부에서만 접근 가능**해야 하며 절대 퍼블릭 인터넷에 노출되어서는 안 된다. 기존 API Gateway 기능(요청 검증, 사용량 계획 등)은 그대로 활용하고 싶다. 솔루션은?

**보기**
- A. API Gateway 리전 엔드포인트를 만들고 리소스 정책으로 특정 IP만 허용(리전 엔드포인트는 기본적으로 퍼블릭 인터넷에서 도달 가능한 엔드포인트이며, 리소스 정책으로 IP를 제한해도 엔드포인트 자체는 여전히 퍼블릭 DNS로 인터넷에 노출되어 "절대 노출되어서는 안 된다"는 요구에는 미흡).
- B. **API Gateway를 프라이빗 엔드포인트 유형으로 생성하고, VPC에 API Gateway용 인터페이스 VPC 엔드포인트(execute-api)를 만들어 이 엔드포인트를 통해서만 API에 접근하도록 리소스 정책을 구성.**
- C. API Gateway 대신 내부 ALB만 사용해 Lambda를 직접 호출(API Gateway가 제공하는 요청 검증, 사용량 계획, API 키 관리 같은 기능을 포기해야 해서 "기존 API Gateway 기능을 그대로 활용"하려는 요구에 반함).
- D. API Gateway 엣지 최적화(Edge-optimized) 엔드포인트 유형 사용(엣지 최적화 엔드포인트는 CloudFront를 통해 전 세계에 노출되는 퍼블릭 엔드포인트로, 프라이빗 접근 요구와 정반대).

**정답: B**

**해설**
API Gateway의 **프라이빗 엔드포인트 유형**은 퍼블릭 인터넷에서 전혀 도달할 수 없으며, VPC에 생성한 **인터페이스 VPC 엔드포인트(서비스 이름: execute-api)**를 통해서만 접근할 수 있습니다. API의 리소스 정책에서 특정 VPC 엔드포인트로부터의 접근만 허용하도록 구성하면, 요청 검증·사용량 계획·API 키 같은 기존 API Gateway 기능은 그대로 유지하면서 API를 완전히 비공개로 만들 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 리전 엔드포인트는 IP 제한을 걸어도 DNS 이름 자체는 퍼블릭에 노출되어 있어, "절대 노출 금지"라는 엄격한 요구에는 프라이빗 엔드포인트가 더 적합합니다.
- C: 내부 ALB+Lambda 직접 호출은 가능하지만 API Gateway의 풍부한 기능(요청 검증, 사용량 계획 등)을 포기하게 됩니다.
- D: 엣지 최적화 엔드포인트는 전 세계에 공개되는 것을 목적으로 하며, 프라이빗 접근과는 반대 방향입니다.

> 💡 **시험 꿀팁**: API Gateway를 **VPC 내부에서만 접근 가능하게(퍼블릭 노출 없이)** 구성하려면 **프라이빗 엔드포인트 유형 + 인터페이스 VPC 엔드포인트(execute-api) + 리소스 정책**이 표준 정답입니다.

- D: 서로 다른 파트너사를 통한 이중화도 도움은 되지만, 완전히 다른 연결 기술(VPN)을 통한 백업이라는 이 문제의 요구와는 다르며, Direct Connect 자체의 구조적 문제에는 여전히 취약할 수 있습니다.

> 💡 **시험 꿀팁**: Direct Connect 장애 시 **수동 개입 없이 자동으로** 백업 경로로 전환하려면 **Direct Connect + Site-to-Site VPN을 BGP 동적 라우팅으로 함께 구성**하고 우선순위를 조정하는 것이 표준 정답입니다.

- B. **Auto Scaling 그룹에 웜 풀(warm pool)을 구성해, 초기화(Init) 상태까지 미리 완료된 정지(stopped) 또는 실행(running) 상태의 인스턴스 풀을 유지하다가, 스케일 아웃 필요 시 이 웜 풀에서 즉시 서비스 상태로 전환.**
- C. 인스턴스 시작 유형을 Spot에서 On-Demand로 변경(구매 옵션 변경은 초기화 시간 자체와는 무관하며 이 문제를 해결하지 못함).
- D. Auto Scaling 정책의 쿨다운(cooldown) 시간을 0으로 설정(쿨다운은 연속적인 스케일링 액션 사이의 대기 시간을 조정할 뿐이며, 개별 인스턴스의 부팅/초기화 시간 자체를 줄이지는 못함).

**정답: B**

**해설**
**웜 풀(warm pool)**은 Auto Scaling 그룹이 실제 서비스 트래픽을 받기 전 단계(사전 초기화 완료)의 인스턴스를 미리 준비해두는 기능입니다. 이 인스턴스들은 정지 상태(비용 절감)나 실행 상태로 대기하다가, 스케일 아웃이 필요할 때 처음부터 부팅/초기화를 거치지 않고 **즉시 서비스 상태로 전환**되므로, 초기화 로직 자체를 바꾸지 않고도 급증 대응 속도를 크게 개선할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 최소 용량을 늘리는 것도 대응 속도는 개선되지만, 평상시 불필요한 인스턴스 유지로 비용 효율이 웜 풀보다 낮습니다(웜 풀은 정지 상태 인스턴스를 활용해 컴퓨팅 비용을 절감할 수 있음).
- C: 구매 옵션(Spot/On-Demand) 변경은 초기화 시간과 무관합니다.
- D: 쿨다운 설정은 스케일링 액션 간 대기 시간 조정 기능이며 개별 인스턴스의 초기화 시간을 줄이지 못합니다.

> 💡 **시험 꿀팁**: 인스턴스 **초기화 시간이 긴 워크로드**에서 스케일 아웃 대응 속도를 개선하려면 **Auto Scaling 웜 풀(warm pool)**이 표준 정답입니다.

## QUESTION 339

**문제**: 스타트업이 Organizations의 통합 결제를 사용 중이며, 특정 개발 계정에서 실수로 비용이 폭증하는 사고를 막기 위해 **월 예산의 90%를 초과하면 자동으로 해당 계정의 비운영 EC2/RDS 인스턴스를 중지**시키는 자동 대응을 원한다. 사람의 개입 없이 이를 구현하는 방법은?

**보기**
- A. Cost Explorer에서 예산 초과를 매일 수동으로 확인하고 발견 시 담당자가 콘솔에서 인스턴스를 직접 중지(수동 확인/조치는 "사람의 개입 없이"라는 요구에 반하고 대응이 늦음).
- B. **AWS Budgets에서 예산을 생성하고, 임계값(90%) 초과 시 실행할 예산 작업(budget action)으로 특정 태그가 붙은 EC2/RDS 인스턴스를 자동으로 중지하는 IAM 정책 기반 작업을 구성.**
- C. CloudWatch 청구 알람만 설정해 임계값 초과 시 이메일로 관리자에게 통보(알람+이메일은 결국 사람이 수동으로 조치해야 해서 완전 자동 대응이 아님).
- D. Cost Anomaly Detection으로 비정상적인 비용 패턴을 탐지해 보고서만 생성(이상 탐지 자체는 유용하지만 기본적으로 자동 교정 액션[인스턴스 중지 등]을 수행하지는 않으며 탐지/알림에 초점을 둠).

**정답: B**

**해설**
**AWS Budgets**의 **예산 작업(budget action)** 기능은 예산이 특정 임계값(예: 90%)을 초과할 때 **사람의 개입 없이 자동으로** 사전 정의된 IAM 기반 작업(예: 특정 태그가 붙은 EC2/RDS 인스턴스를 중지하는 서비스 제어 정책 적용, 또는 IAM 정책을 특정 역할에 연결해 추가 리소스 생성 차단)을 실행할 수 있습니다. 이를 통해 예산 초과를 사후에 확인하는 것이 아니라, 초과 시점에 즉시 자동으로 비용 발생을 억제하는 조치를 취할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 수동 확인/조치는 "사람의 개입 없이"라는 핵심 요구를 위반하고 대응 속도도 느립니다.
- C: 청구 알람은 알림까지만 제공하며, 실제 리소스를 중지하는 교정 액션은 직접 구현해야 합니다.
- D: Cost Anomaly Detection은 비정상 패턴 탐지/보고에 초점이 있으며 기본적으로 자동 교정 액션을 수행하지 않습니다.

> 💡 **시험 꿀팁**: 예산 초과 시 **사람 개입 없이 자동으로 리소스를 중지하는 등의 교정 조치**를 취하려면 **AWS Budgets의 예산 작업(budget actions)**이 표준 정답입니다.

## QUESTION 340

**문제**: 보안 팀이 조직의 모든 신규 EBS 볼륨이 **기본적으로 암호화**되도록 강제하고 싶으며, 이미 존재하는 미암호화 볼륨도 식별해 조치하고 싶다. 또한 특정 애플리케이션(예: Lambda)이 고객 관리형 KMS 키로 암호화된 볼륨의 스냅샷에 접근할 수 있도록 세밀하게 권한을 부여하고 싶다. 이를 구성하는 표준 조합은?

**보기**
- A. 각 EC2 인스턴스 시작 시 사용자가 매번 수동으로 암호화 옵션을 체크하도록 안내(수동 프로세스는 실수로 누락될 위험이 크며 "기본적으로 암호화"라는 강제 요구를 충족하지 못함).
- B. **계정/리전 수준에서 "EBS 암호화 기본값(EBS encryption by default)"을 활성화해 신규 볼륨/스냅샷이 자동으로 암호화되도록 강제하고, AWS Config 규칙으로 기존 미암호화 볼륨을 탐지하며, 특정 서비스(Lambda 등)에 대해서는 KMS 키 정책 또는 KMS grant를 사용해 필요한 범위의 사용 권한만 부여.**
- C. 모든 EBS 볼륨에 대해 조직 전체에서 동일한 AWS 관리형 키(aws/ebs)만 사용하도록 강제(관리형 키만 사용하면 세밀한 키 정책 커스터마이징이나 특정 서비스에 대한 범위가 지정된 grant 발급 등 고객 관리형 키가 제공하는 유연한 접근 제어를 활용할 수 없음).
- D. EBS 볼륨 암호화 대신 애플리케이션 레벨 암호화만 구현(EBS 자체의 저장 데이터 보호[미사용 데이터 암호화]를 우회하는 것으로, 문제의 핵심 요구인 "EBS 볼륨 암호화 강제"와는 다른 접근이며 볼륨 스냅샷 등 다른 경로의 데이터는 여전히 노출될 수 있음).

**정답: B**

**해설**
**계정/리전 수준의 EBS 암호화 기본값** 설정을 활성화하면 이후 생성되는 모든 새 EBS 볼륨과 스냅샷이 자동으로 암호화되어, 사용자가 매번 수동으로 옵션을 켤 필요가 없습니다. 이미 존재하는 미암호화 볼륨은 **AWS Config 규칙**(예: `encrypted-volumes`)으로 탐지해 별도로 조치(재생성 등)할 수 있습니다. 또한 **고객 관리형 KMS 키**를 사용하면 **키 정책**이나 **KMS grant**를 통해 Lambda 같은 특정 서비스/역할에 필요한 만큼만(예: 특정 암호화 컨텍스트 조건 하에 `Decrypt`만) 세밀하게 권한을 부여할 수 있어, 이 문제의 모든 요구(기본 암호화 강제, 기존 리소스 탐지, 세밀한 서비스별 권한 부여)를 충족합니다.

**왜 다른 보기는 오답인가**
- A: 수동 프로세스는 실수로 누락되기 쉬워 "기본적으로 암호화"라는 강제 요구를 안정적으로 충족하지 못합니다.
- C: AWS 관리형 키만 사용하면 세밀한 키 정책 커스터마이징이나 grant 기반의 범위 지정 권한 부여가 어려워, 특정 서비스에 대한 세밀한 접근 제어 요구를 충족하기 어렵습니다.
- D: 애플리케이션 레벨 암호화는 EBS 볼륨/스냅샷 자체의 암호화를 대체하지 못하며, 문제의 핵심 요구와 다른 접근입니다.

> 💡 **시험 꿀팁**: 조직 전체에 **EBS 볼륨 암호화를 기본으로 강제**하고 **세밀한 서비스별 키 사용 권한**까지 필요하다면 **EBS 암호화 기본값 설정 + Config 규칙(기존 리소스 탐지) + 고객 관리형 KMS 키(키 정책/grant)** 조합이 표준 정답입니다.
