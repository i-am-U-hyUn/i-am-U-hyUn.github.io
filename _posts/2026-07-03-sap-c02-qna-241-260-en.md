## QUESTION 241

**Question**: A smart-car company streams vehicle telemetry over MQTT to an application, processes it every 5 minutes, and copies it to on-premises storage for anomaly detection. As the fleet and data volume grow, on-premises storage can't scale and data is being lost. Modernize onto AWS with minimal operational overhead — what's the solution?

**Choices**
- A. IoT Greengrass to MSK + a Kafka app to store in S3 + a pre-trained SageMaker model for anomaly detection (running your own MSK cluster carries relatively heavy management overhead, and Greengrass is meant for edge use cases, which doesn't quite fit this cloud-ingestion scenario).
- B. **Ingest vehicle data with IoT Core. Configure a rule that routes the data to a Kinesis Data Firehose delivery stream that stores it in S3. Create a Kinesis Data Analytics application that reads from the delivery stream to detect anomalies.**
- C. IoT FleetWise + Kinesis Data Streams + Firehose to S3 + Glue's built-in ML transform for anomaly detection (IoT FleetWise is mainly for standardizing/optimizing vehicle data transfer, and Glue's ML transform isn't purpose-built for anomaly detection).
- D. Amazon MQ (RabbitMQ) + Firehose to S3 + Lookout for Metrics for anomaly detection (native MQTT support isn't as direct as IoT Core's, and managing a RabbitMQ broker adds overhead).

**Correct Answer: B**

**Explanation**
**AWS IoT Core** is a fully managed service with native MQTT support that easily handles connections from millions of vehicles. Routing data via an **IoT rule** to **Kinesis Data Firehose** for automatic storage in S3, then using **Kinesis Data Analytics** to analyze the stream in real time for anomalies, is built entirely from fully managed services — minimizing operational overhead.

**Why the other choices are wrong**
- A: Running your own MSK cluster carries more management overhead than the fully serverless option B, and Greengrass is meant for edge gateways, which doesn't fit this scenario's core need (bulk ingestion into the cloud).
- C: Glue's built-in ML transform is specialized for data cleansing/matching during ETL — Kinesis Data Analytics is better suited to real-time anomaly detection.
- D: Managing a RabbitMQ broker (Amazon MQ) carries more overhead than IoT Core's fully managed MQTT ingestion.

> 💡 **Exam tip**: For large-scale MQTT-based IoT data ingestion, the fully managed combination of **IoT Core** for ingestion, **Kinesis Data Firehose (to S3)** for storage, and **Kinesis Data Analytics** for real-time anomaly detection is the standard minimal-overhead answer.

## QUESTION 242

**Question**: A dev team hardcoded IAM user access keys and committed them to CodeCommit. The security team wants to **automatically** find and remediate this vulnerability. Which solution automatically protects the credentials appropriately?

**Choices**
- A. Nightly Systems Manager Run Command to scan dev instances for credentials + rotate via Secrets Manager (this scans instances, not the code repository itself — misaligned with the goal).
- B. A scheduled Lambda that downloads/scans CodeCommit code + generates new credentials and stores them in KMS on discovery (KMS is a key-management service, not a credential storage/rotation service — a conceptual error. A scheduled scan is also slower than reacting at commit time).
- C. Use Macie to scan CodeCommit for credentials + Lambda to disable and notify on discovery (Macie is mainly specialized for detecting sensitive data in S3, not scanning CodeCommit repositories).
- D. **Configure a CodeCommit trigger to invoke a Lambda function on new code submissions to scan for credentials. If found, disable them in IAM and notify the user.**

**Correct Answer: D**

**Explanation**
Using a **CodeCommit trigger** to invoke a Lambda function **at the moment code is committed** to scan for credential patterns, and immediately **disabling the access key in IAM** upon detection, is the fastest, most automated response.

**Why the other choices are wrong**
- A: Scanning instances doesn't directly address finding credentials committed to the code repository (CodeCommit).
- B: KMS is a key-management service, not a place to store or rotate leaked IAM access keys. A nightly scheduled scan also lacks real-time responsiveness.
- C: Amazon Macie is mainly a service for detecting sensitive data stored in S3, and isn't optimized for scanning CodeCommit repository code.

> 💡 **Exam tip**: To **detect and automatically respond to leaked credentials the moment code is committed**, the standard answer is the combination of a **CodeCommit trigger + Lambda (scan) + IAM (disable the key)**.

## QUESTION 243

**Question**: An S3 data lake is accessed by hundreds of applications across multiple AWS accounts. No public internet access is allowed, and least privilege is required. The plan is to use **S3 access points** restricted to each application's specific VPC. What are the implementation steps? (Choose two.)

**Choices**
- A. **In the account that owns the S3 bucket, create an S3 access point for each application. Restrict each access point to that application's VPC only. Update the bucket policy to require access only through an access point.**
- B. Create an S3 interface endpoint in each application VPC + allow the access point via an endpoint policy + attach a VPC gateway to the S3 endpoint (S3 uses gateway endpoints, not interface endpoints — this mixes up "interface endpoint" and "gateway attachment," a conceptual error).
- C. **Create an S3 gateway endpoint in each application's VPC. Use an endpoint policy to allow access only to the S3 access point. Specify the route table used to reach the access point.**
- D. Create per-application access points in each AWS account, then attach them to the bucket (access points are standardly created in the account that owns the bucket — creating VPC-restricted access points in other accounts isn't the typical pattern).
- E. Create a gateway endpoint in the data lake's VPC + an endpoint policy allowing bucket access (this allows direct access to the bucket rather than an access point, which doesn't match the requirement for "access points restricted to specific VPCs").

**Correct Answer: A, C**

**Explanation**
**S3 access points are created in the account that owns the bucket**, one per application, restricted to a specific VPC (A). In each application's VPC, create an **S3 gateway endpoint** (S3 uses gateway, not interface, endpoints), and use an endpoint policy to allow access only to that access point (C) — this achieves least-privilege, per-VPC-restricted access without traversing the public internet.

**Why the other choices are wrong**
- B: S3 standardly uses gateway endpoints, and mixing "interface endpoint" with "VPC gateway attachment" is conceptually inaccurate.
- D: Access points are standardly created in the bucket-owning account — creating them individually in each application account and "attaching" them to the bucket isn't a typical pattern.
- E: Creating a gateway endpoint in the data lake VPC to allow direct bucket access doesn't match the fine-grained control required by "access points restricted to each application's specific VPC."

> 💡 **Exam tip**: S3 access points are **created in the bucket-owning account** and can be restricted to a specific VPC; in each consumer VPC, place an **S3 gateway endpoint** (not interface) and use an endpoint policy to allow only the specific access point — that's the standard combination.

## QUESTION 244

**Question**: A hybrid environment (VPC+EC2, app logs sent to CloudWatch, EC2 reads an on-premises relational database). DB-connected EC2 instances need to be monitored **near real time**. A Splunk monitoring solution already exists on-premises. How do you send the networking traffic to Splunk?

**Choices**
- A. VPC Flow Logs → CloudWatch + a Lambda that periodically exports to S3 + Splunk pulls from S3 using access keys (a periodic batch approach doesn't meet the "near real time" requirement, and using access keys is also less secure).
- B. **Enable VPC Flow Logs to CloudWatch. Create a CloudWatch Logs subscription that sends log events to a Kinesis Data Firehose delivery stream (Firehose destination: Splunk).**
- C. Log every DB request with the EC2 IP + export CloudWatch to S3 + query with Athena + write results to another S3 bucket + Lambda sends to Splunk (a multi-stage batch pipeline that falls far short of real-time).
- D. Kinesis Data Analytics (SQL) to move CloudWatch logs into a Kinesis stream + a 1-minute sliding window + an anomaly-detection SQL query + Firehose to Splunk (an overly complex approach focused on anomaly-detection analysis rather than simply delivering the networking traffic in real time).

**Correct Answer: B**

**Explanation**
Using a **CloudWatch Logs subscription filter** to stream log events in real time to **Kinesis Data Firehose**, and configuring Firehose to deliver directly to a **Splunk destination**, is the standard native integration pattern for delivering near-real-time data from CloudWatch to an on-premises Splunk instance (Firehose natively supports a Splunk destination).

**Why the other choices are wrong**
- A: A periodic (batch) S3 export introduces delay that violates the "near real time" requirement, and using long-lived access keys also goes against security best practices.
- C: Routing through multiple batch stages (S3 export → Athena → S3 → Lambda) is far from real time.
- D: This approach is focused on anomaly-detection analysis, which is unnecessarily complex compared to the core requirement of simply delivering networking traffic to Splunk in real time.

> 💡 **Exam tip**: To deliver CloudWatch Logs to on-premises **Splunk** in near real time, the standard answer is **CloudWatch Logs subscription filter → Kinesis Data Firehose (native Splunk destination support)**.

## QUESTION 245

**Question**: 5 dev teams, each with 5 AWS accounts. Each month someone manually logs into the console to check costs and reports to finance. There's a strict compliance requirement that resources be created **only in US Regions**, but some are being created in other Regions. Finance needs to track/consolidate spend across all accounts and enforce the US-Region restriction. What's the operationally efficient combination? (Choose three.)

**Choices**
- A. Create a new master account + an S3 bucket for finance + store Cost and Usage Reports monthly (a viable approach on its own, but it doesn't need to combine with B/E, and B's organizational setup needs to happen first — A itself isn't a required step).
- B. **Create a new master account. Deploy an organization in Organizations with all features enabled. Invite and confirm acceptance of all existing accounts into the organization.**
- C. Create an OU containing all dev teams + an SCP allowing only US Regions (an Allow-style SCP with conditions is more complex to configure, and a Deny-style approach is generally clearer).
- D. **Create an OU containing all dev teams. Create an SCP that denies resource creation outside US Regions. Apply the SCP to the OU.**
- E. **Create an IAM role in the master account with read access to the Billing and Cost Management console. Allow finance team users to assume this role. Analyze costs via Cost Explorer and the Billing console.**
- F. Individually create a billing-console read role in each AWS account (requiring separate configuration per account doesn't meet the "most operationally efficient" requirement — leveraging Organizations' consolidated billing is more efficient).

**Correct Answer: B, D, E**

**Explanation**
First, **set up an Organizations organization** (all features enabled, invite existing accounts) (B) to establish the foundation for consolidated billing and central management. Apply an **SCP denying resource creation outside US Regions** to the OU (D) to enforce compliance. Then create a **cross-account role for finance** in the master account so they can view organization-wide costs at once via Cost Explorer/the Billing console (E) — the most operationally efficient approach.

**Why the other choices are wrong**
- A: A Cost and Usage Report approach can also be valid, but the organizational setup (B) and role-based access (E) need to be established first, and it isn't required as part of this combination.
- C: A Deny-style SCP (D) is a more common and clearer SCP design pattern than an Allow-style one.
- F: Creating a role individually in every account is less operationally efficient than a consolidated, organization-wide approach (E).

> 💡 **Exam tip**: For **consolidated cost tracking + enforced Region restriction** across multiple accounts, the standard three-step answer is ① **set up an Organizations organization** (all features + invite accounts), ② **a Region-restriction SCP** (deny outside allowed Regions, applied to the OU), and ③ **a cross-account role in the master account for consolidated Cost Explorer/Billing console access**.

## QUESTION 246

**Question**: Multiple AWS accounts across departments are created/managed centrally. The security team needs **read-only access to all other accounts** from their **own AWS account**. Organizations is in use, and the security team's account already exists. What's the approach?

**Choices**
- A. Create a new **IAM policy** in each member account and establish a trust relationship with the security account (an IAM policy itself can't have a trust relationship — only roles have trust policies; a conceptual error).
- B. **In each member account, create a new IAM role with read-only permissions. Establish a trust relationship between each member account's IAM role and the security account. Have the security team access using this IAM role.**
- C. Have the security team use STS AssumeRole from the security account to call the **master account's** OrganizationAccountAccessRole (OrganizationAccountAccessRole is the role the master account uses to manage member accounts — describing this role as living in the master account misrepresents the actual structure; it exists in each member account).
- D. Have the security team use STS AssumeRole from the security account to call the **member account's** OrganizationAccountAccessRole (this role is configured by default to trust only the master account, so it would need to be reconfigured to trust the security account — and it may also violate least privilege [read-only]; creating a dedicated read-only role as in B is more appropriate).

**Correct Answer: B**

**Explanation**
Creating a **dedicated, read-only-only IAM role** in each member account and configuring its trust policy to **trust the security account** is the standard cross-account access pattern that aligns with least privilege.

**Why the other choices are wrong**
- A: An IAM policy cannot itself have a "trust relationship" — a trust policy is a property of a role.
- C, D: `OrganizationAccountAccessRole` is an administrator-level role that Organizations automatically creates for new accounts, **configured by default to trust only the master account**. Repurposing it for the security account requires reconfiguring the trust policy and grants excessive (full admin) permissions — creating a dedicated read-only role better aligns with least privilege.

> 💡 **Exam tip**: To grant one account (e.g., the security team) **read-only (or restricted) access to many other accounts**, create a **dedicated, least-privilege role in each target account** and configure its trust policy to trust the requesting account. Repurposing `OrganizationAccountAccessRole` as-is is inappropriate because it grants excessive permissions.

## QUESTION 247

**Question**: Hundreds of AWS accounts, each with VPCs (public+private subnets across multiple AZs), currently being redesigned as a hub-and-spoke topology. All private subnets in spoke VPCs must route internet traffic through an **egress VPC**. A NAT gateway is already deployed in the central account's egress VPC. What additional steps are needed?

**Choices**
- A. A peering connection between the egress VPC and each spoke VPC (VPC peering is non-transitive, unsuitable at a scale of hundreds of VPCs — Transit Gateway is the standard for hub-and-spoke).
- B. **Create a Transit Gateway and share it with the existing AWS accounts (RAM). Attach the existing VPCs to the Transit Gateway. Configure routing for internet access.**
- C. Individually create a transit gateway in every account + attach the NAT gateway to the transit gateway (creating a transit gateway per account contradicts the "centralized" hub-and-spoke design, and the notion of "attaching" a NAT gateway to a TGW is also inaccurate — VPCs are what get attached to a TGW).
- D. AWS PrivateLink between the egress VPC and spoke VPCs (PrivateLink is for exposing specific services, not for centralizing outbound internet traffic).

**Correct Answer: B**

**Explanation**
Creating a **Transit Gateway** in the central account and **sharing it with the other accounts via AWS RAM**, then attaching each spoke VPC to this Transit Gateway and configuring the private subnets' default route to go through the Transit Gateway to the NAT gateway in the egress VPC, completes a hub-and-spoke outbound internet architecture that scales to hundreds of VPCs.

**Why the other choices are wrong**
- A: VPC peering is non-transitive, so it doesn't scale to a large hub-and-spoke design connecting hundreds of VPCs to a single central egress VPC.
- C: Creating a transit gateway "in every account" individually contradicts the intent of a centralized design, and describing a NAT gateway as being "attached" to a TGW misrepresents the actual structure (VPCs attach to a TGW).
- D: PrivateLink is for exposing a specific service to other VPCs/accounts — it isn't meant for centralizing outbound internet traffic.

> 💡 **Exam tip**: For **centralized (hub-and-spoke) outbound internet routing** across hundreds of VPCs, the standard answer is a **Transit Gateway (shared via RAM) + TGW attachments for each VPC + a default route in each private subnet pointing to the TGW**.

## QUESTION 248

**Question**: An ECS (Fargate) web application behind an ALB with Auto Scaling. Weekly spikes in failed login attempts against the auth service, originating from around 500 IPs that change every week. Prevent failed logins from overloading the auth service, with operational efficiency as the top priority.

**Choices**
- A. Firewall Manager with a security group policy to block the IPs (managing 500 weekly-changing IPs individually via security groups is highly inefficient).
- B. **Create an AWS WAF web ACL with a rate-based rule, set the rule action to block, and associate the web ACL with the ALB.**
- C. Firewall Manager with a security group policy allowing only specific CIDRs (the web application needs to be publicly accessible, so allowing only specific CIDRs is inappropriate).
- D. A WAF web ACL with an IP set match rule (manually and continually updating the IP set for weekly-changing IPs is operationally inefficient — a rate-based rule responds automatically without any IP-list management).

**Correct Answer: B**

**Explanation**
An **AWS WAF rate-based rule** automatically identifies and blocks IPs whose request count exceeds a threshold within a time window, and it automatically responds to new attacking IPs **with no need to manually manage an IP list**, even as the IPs change weekly. This is the most operationally efficient approach.

**Why the other choices are wrong**
- A, C: Individually managing 500 (weekly-changing) IPs via security groups is a very heavy operational burden.
- D: An IP set match rule also requires manually updating the weekly-changing IP list, making it less operationally efficient than a rate-based rule's automatic threshold-based detection.

> 💡 **Exam tip**: For **brute-force/failed-login attacks from a large, constantly changing set of IPs**, an **AWS WAF rate-based rule** is the standard, most operationally efficient answer, since it responds automatically without any IP-list management.

## QUESTION 249

**Question**: An on-premises SaaS ingests files daily, offering customers several public SFTP endpoints, and customers have allow-listed these IPs in their firewalls (**the IPs cannot change**). Migrating to AWS while reducing operational overhead. What's the solution?

**Choices**
- A. **Register the customer-owned IP address block to the company's AWS account (BYOIP). Allocate Elastic IPs from the address pool and assign them to AWS Transfer Family SFTP endpoints. Use AWS Transfer to store files in S3.**
- B. BYOIP subnet + assign Elastic IPs to an ALB + EBS volumes + host FTP on EC2 (ALB doesn't support the FTP protocol, and running your own EC2 FTP server carries heavy overhead).
- C. Register BYOIP in Route 53 + an alias pointing to an NLB + host FTP on EC2 (a self-managed FTP server carries more operational overhead than AWS Transfer).
- D. BYOIP + assign Elastic IPs to an S3 VPC endpoint + enable SFTP support on the S3 bucket (there's no feature to enable SFTP directly on an S3 VPC endpoint — a conceptual error; AWS Transfer is the service that plays this role).

**Correct Answer: A**

**Explanation**
Since the core constraint is that **customers cannot change their IP addresses**, using **BYOIP (Bring Your Own IP)** to bring the customer's existing IP block into AWS and assigning it directly to an **AWS Transfer Family (SFTP)** endpoint lets you move to a fully managed SFTP service without requiring any firewall changes on the customer side. AWS Transfer stores files directly in S3, removing the burden of running your own server.

**Why the other choices are wrong**
- B, C: ALB doesn't support the FTP protocol, and running your own FTP/SFTP server on EC2 carries far more operational overhead than the managed AWS Transfer Family.
- D: There's no concept of "enabling" SFTP directly on an S3 VPC endpoint — SFTP is a capability provided by AWS Transfer Family.

> 💡 **Exam tip**: When migrating an existing SFTP service to AWS where customers **cannot change their IPs**, **BYOIP + AWS Transfer Family (SFTP, S3 backend)** is the standard answer for minimizing operational overhead.

## QUESTION 250

**Question**: An application runs on 5 EC2 instances in a single Region. All instances need **high-throughput, low-latency** networking between them. There's no fault-tolerance requirement. What's the solution?

**Choices**
- A. **Launch the 5 EC2 instances in a cluster placement group. Verify the instance types support enhanced networking.**
- B. An Auto Scaling group in the same AZ + attach an additional ENI to each instance (simply placing instances in the same AZ doesn't guarantee the same level of low-latency, high-throughput network proximity as a cluster placement group).
- C. A partition placement group (partition placement groups are for fault isolation in large-scale distributed workloads, a different purpose than this requirement's focus on low latency/high throughput).
- D. A spread placement group + an additional ENI (a spread placement group's purpose is to maximize fault isolation by placing each instance on separate hardware — the opposite direction from a low-latency networking requirement).

**Correct Answer: A**

**Explanation**
A **cluster placement group** places instances on physically close hardware within the same AZ, delivering the **highest possible network throughput and lowest latency**, and combining it with instance types that support **enhanced networking** maximizes this performance. This also fits well with the no-fault-tolerance-needed condition (a cluster placement group can be more vulnerable to a single point of failure).

**Why the other choices are wrong**
- B: Merely being in the same AZ doesn't guarantee the physical proximity and network performance level of a cluster placement group.
- C: Partition placement groups exist to prevent failure propagation across partitions in large distributed systems (Hadoop, Cassandra, etc.) — low latency isn't their core goal.
- D: A spread placement group does the opposite — spreading instances apart to maximize fault isolation — which conflicts with the "high throughput and low latency" requirement.

> 💡 **Exam tip**: When you need the **highest possible network throughput/lowest latency** among all instances and fault tolerance is secondary, **a cluster placement group + enhanced-networking-capable instance types** is the standard answer. Remember partition/spread placement groups exist for fault isolation instead.

## QUESTION 251

**Question**: A REST API (API Gateway regional endpoint) shares information with 6 US-based partners, who access it once a day each. After deployment, 1,000 requests per second are observed from 500 IPs worldwide (suspected botnet). How do you protect the API while minimizing cost?

**Choices**
- A. CloudFront + WAF (block clients exceeding 5 requests/day) + OAI restricting access to API Gateway (adding CloudFront/OAI introduces an unnecessary extra layer in front of an API Gateway regional endpoint, and adds cost).
- B. CloudFront + WAF (block over 5 requests/day) + a CloudFront custom header carrying an API key + require the API key on POST (again, an unnecessary extra CloudFront layer with added cost/complexity).
- C. A WAF web ACL allowing only the 6 partner IPs + a **resource policy** with a request limit + require an API key on POST (setting a request limit directly on a resource policy isn't a typical feature — a Usage Plan is the standard mechanism).
- D. **Create a WAF web ACL allowing only the IPs used by the 6 partners, and associate it with the API. Create a Usage Plan with a request limit and associate it with the API. Create an API key and add it to the Usage Plan.**

**Correct Answer: D**

**Explanation**
A **WAF web ACL** allowing only the 6 known partner IPs filters out the vast majority of the botnet traffic, and enforcing per-partner request limits via API Gateway's **Usage Plan + API key** is the most efficient combination — natively integrated with the API Gateway regional endpoint and adding no extra cost (no separate layer like CloudFront needed).

**Why the other choices are wrong**
- A, B: Adding CloudFront in front of an existing API Gateway regional endpoint adds unnecessary cost and complexity for this scenario (a small number of known partners, accessed once a day).
- C: There's no feature to set a request limit (throttling) directly on a resource policy — API Gateway's standard throttling mechanism is the **Usage Plan**.

> 💡 **Exam tip**: To protect an API used only by a small number of known partners from a botnet **cost-effectively**, the standard answer is applying **WAF (IP allow list) + an API Gateway Usage Plan + API key** directly to the regional endpoint, without an extra layer like CloudFront.

## QUESTION 252

**Question**: A single-Region Aurora PostgreSQL database. The database team needs to monitor **all data activity across all databases**. What's the solution?

**Choices**
- A. A DMS CDC task (Aurora source, Firehose target) + upload to OpenSearch (DMS CDC's main purpose is replicating data changes, not comprehensively capturing database "activity" such as queries or logins).
- B. Capture Aurora **Database Activity Streams** via EventBridge + a Lambda target + Lambda decrypts EventBridge messages and publishes to S3 (activity streams target Kinesis Data Streams by default — this EventBridge workaround isn't the standard approach).
- C. **Start Aurora Database Activity Streams, pushing to a Kinesis data stream. Configure Kinesis Data Firehose to deliver the data to S3.**
- D. A DMS CDC task (Aurora source, Firehose target) + upload to Redshift + query activity via Redshift (DMS CDC captures only data changes, not activity streams that include all SQL activity).

**Correct Answer: C**

**Explanation**
Aurora's **Database Activity Streams** is a native feature that captures all database activity (DML, DDL, login attempts, etc.) in real time, and by default pushes data to an **Amazon Kinesis data stream**. Connecting this to **Kinesis Data Firehose** to store it in S3 gives a complete, further-analyzable record of all database activity.

**Why the other choices are wrong**
- A, D: DMS's CDC (change data capture) replicates **changes to data values** — it isn't an auditing feature covering "all data activity" such as login attempts or read queries.
- B: Database Activity Streams targets a Kinesis data stream by default — routing through EventBridge isn't the standard integration method.

> 💡 **Exam tip**: To fully capture **all database activity (for auditing purposes)** on Aurora, the standard answer is **Database Activity Streams → Kinesis data stream → Kinesis Data Firehose → S3**. DMS CDC serves a different purpose — replicating data changes.

## QUESTION 253

**Question**: For a game launch, 12 r6g.16xlarge (memory-optimized) instances were statically deployed behind an NLB. The CloudWatch agent monitors memory utilization. Analysis shows CPU/memory consumption is only about 1/4 of expected (demand is lower and more varied). Decision made to use an Auto Scaling group for dynamic scaling. What's the most cost-effective configuration?

**Choices**
- A. c6g.4xlarge (compute-optimized) + min 3/desired 3/max 12 (switching to compute-optimized ignores the memory-optimized characteristics of the original workload, which may not fit the actual requirements).
- B. m6g.4xlarge (general purpose) + min 3/desired 3/max 12 (similarly may not fit a workload that originally needed memory optimization).
- C. **r6g.4xlarge (memory-optimized, 1/4 the size of the original instance) + min 3/desired 3/max 12.**
- D. r6g.8xlarge (1/2 size) + min 2/desired 2/max 6 (too large relative to the observed 1/4 usage, and also less flexible).

**Correct Answer: C**

**Explanation**
Since actual usage was about **1/4** of expected, scaling down to **r6g.4xlarge** — 1/4 the size of the original r6g.16xlarge, keeping the same memory-optimized family that matches the workload — and configuring the Auto Scaling group with min 3/desired 3 (1/4 of the original 12) and max 12 (to handle peaks) precisely matches the observed usage pattern while optimizing cost.

**Why the other choices are wrong**
- A, B: Ignoring the fact that the workload originally required a memory-optimized instance family (r6g) by switching to compute-optimized or general-purpose risks mismatching the actual workload characteristics.
- D: Choosing a half-size instance is still excessive relative to the observed 1/4 usage, and scaling in finer (4xlarge) increments offers better flexibility.

> 💡 **Exam tip**: When downsizing instances based on observed utilization data (e.g., 1/4 of expected), the standard answer is to **keep the same instance family** (preserving workload characteristics) while **shrinking the size to match the observed ratio**, combined with an Auto Scaling group for flexible scaling.

## QUESTION 254

**Question**: DynamoDB (on-demand capacity) stores millions of historical stock trades, bulk-loaded every midnight, with bursty reads throughout the day that repeatedly query a **limited set of keys**. What's the cost-saving strategy?

**Choices**
- A. Deploy ElastiCache in front of DynamoDB (building/managing your own caching layer carries more operational burden than DAX, and requires custom integration with the DynamoDB protocol).
- B. Deploy DAX + configure DynamoDB Auto Scaling + purchase Savings Plans (Auto Scaling is a different concept from on-demand mode, and for a predictable pattern like daily bulk loads + repeated queries, provisioned capacity is generally more cost-effective).
- C. Use provisioned capacity mode + purchase Savings Plans (doesn't take advantage of the "limited key set repeatedly queried" characteristic — adding DAX caching could further reduce read costs).
- D. **Deploy DAX. Use provisioned capacity mode. Configure DynamoDB Auto Scaling.**

**Correct Answer: D**

**Explanation**
The characteristic of a **"limited set of keys being repeatedly queried"** is ideal for **DAX (DynamoDB Accelerator)** caching, which absorbs a large share of repeated reads and significantly reduces read costs against DynamoDB itself. Additionally, for a predictable pattern like **daily midnight bulk loads + bursty reads throughout the day**, **provisioned capacity mode** (combined with DynamoDB Auto Scaling) is generally cheaper than on-demand.

**Why the other choices are wrong**
- A: Integrating ElastiCache yourself carries more implementation/operational burden than DAX, a cache purpose-built to be compatible with the DynamoDB protocol.
- B: Auto Scaling alone doesn't reduce on-demand mode's fundamental cost structure (per-request billing) as much as provisioned capacity, and without DAX, the benefit of repeated queries isn't captured.
- C: Without DAX, the key benefit of "a limited key set being repeatedly queried" isn't leveraged for cost savings.

> 💡 **Exam tip**: When DynamoDB has a **limited key set that's repeatedly queried** and a **predictable traffic pattern**, **DAX (caching for repeated reads) + provisioned capacity mode (+ Auto Scaling)** is the standard answer, saving significantly more than on-demand with no cache.

## QUESTION 255

**Question**: A centralized logging service running on EC2 (receiving logs from hundreds of accounts) connected via PrivateLink (a per-client interface endpoint). The logging service consists of an NLB + EC2 across multiple subnets. **Clients can't submit logs to the VPC endpoint.** What are the troubleshooting steps? (Choose two.)

**Choices**
- A. **Verify the NACL attached to the logging service's subnet allows communication with the NLB's subnet. Verify the NACL attached to the NLB's subnet allows communication with the logging service (EC2)'s subnet.**
- B. Verify the NACL on the logging service's subnet allows communication with the **interface endpoint subnet** (the logging service lives in its own account, not the client's — the interface endpoint is in the client's VPC, so the key issue is communication between the NLB and EC2 subnets within the logging service's own account, not direct communication with the endpoint subnet).
- C. **Verify the logging service (EC2)'s security group allows inbound traffic from the NLB's subnet.**
- D. Verify the logging service's security group allows inbound traffic from the client (since traffic arrives via the NLB, the security group needs to allow traffic from the NLB [or its subnet], not directly from the client).
- E. Verify the NLB's security group allows inbound from the interface endpoint subnet (an NLB generally doesn't support security groups directly — a Network Load Balancer itself has no security group concept; control happens via the target's security group).

**Correct Answer: A, C**

**Explanation**
The issue is most likely in the network path **within the logging service's own account** — between the subnet containing the NLB and the subnet containing the EC2 logging service. Checking that the **NACLs allow bidirectional communication between both subnets** (A), and that the **EC2 security group allows inbound traffic from the subnet containing the NLB** (C), addresses the root cause of traffic routed through the NLB failing to reach the actual EC2 logging service.

- B: The interface endpoint lives in the client-side VPC, so describing this as "communication between the logging service's subnet and the endpoint subnet" doesn't match the actual architecture.
- D: Since traffic passes through the NLB, the EC2 security group needs to allow traffic from the NLB (or its subnet), not directly from the original client.
- E: **A Network Load Balancer itself has no security group concept** (control is via the target instance's security group) — this option is conceptually invalid on its face.

> 💡 **Exam tip**: When PrivateLink traffic routed through an NLB doesn't reach the backend, check **bidirectional NACL allow rules between the NLB subnet and the backend (EC2) subnet**, and that the **backend EC2's security group allows inbound from the NLB's source**. Remember **an NLB itself has no security group**.

## QUESTION 256

**Question**: S3 holds millions of objects (S3 Standard, frequently accessed, SSE-KMS encrypted). The number of accessing users/apps has surged. The monthly bill shows **KMS costs rising due to a surge in S3 requests**. Optimize cost with minimal application changes and minimal operational overhead — what's the solution?

**Choices**
- A. Create a new bucket with SSE-C (customer-provided keys) + copy existing objects (SSE-C requires the application to supply the key directly on every request — a much bigger application change, violating the "minimal change" requirement).
- B. **Create a new bucket using SSE-S3 (Amazon S3-managed keys). Use an S3 Batch Operations job to copy existing objects to the new bucket, specifying SSE-S3.**
- C. Store an encryption key in CloudHSM + a new bucket + copy via S3 Batch Operations + encrypt with the CloudHSM key (CloudHSM is a heavier, more expensive dedicated HSM service than SSE-KMS — the opposite direction of the cost-reduction goal).
- D. S3 Intelligent-Tiering + move objects unaccessed for 90 days to Glacier Deep Archive (these objects are explicitly stated to be "frequently accessed," so tiering/archiving is unrelated to the KMS cost issue).

**Correct Answer: B**

**Explanation**
**SSE-KMS triggers a KMS API call on every request**, so KMS costs spike when request volume is high. Switching to **SSE-S3 (Amazon S3-managed keys)** eliminates KMS API calls entirely, removing this cost altogether, while still being "server-side encryption" from the application's point of view — requiring only **minimal changes**. **S3 Batch Operations** can efficiently re-encrypt millions of existing objects while copying them to the new bucket.

**Why the other choices are wrong**
- A: SSE-C requires the application to supply the encryption key itself on every request, a much bigger code change that also shifts key-management burden onto the application.
- C: CloudHSM is a dedicated hardware security module that costs more, not less, than SSE-KMS — the wrong direction for cost reduction.
- D: Since the objects are explicitly "frequently accessed," storage tiering/archiving is irrelevant to this scenario and doesn't address the KMS cost issue.

> 💡 **Exam tip**: When **SSE-KMS's per-request API call costs spike**, the standard answer for minimizing application changes is to **switch to SSE-S3 (Amazon S3-managed keys)** — this eliminates KMS API calls entirely. Use **S3 Batch Operations** to re-encrypt large numbers of objects.

- A. Evaluate/adjust RCUs (this looks like a write-related issue, not a read-capacity one, so this is a lower priority).

## QUESTION 260

**Question**: An unauthenticated static website (S3+CloudFront+WAF) calls API Gateway → Lambda when a registration form is submitted, which forwards to an external API. During testing, a **CORS error** occurs. It's confirmed the CloudFront distribution's origin includes an `Access-Control-Allow-Origin: www.example.com` header. What's the fix?

**Choices**
- A. Change the S3 bucket's CORS configuration (the error originates at the point of calling API Gateway, not S3, so S3's CORS settings are unrelated).
- B. Enable CORS settings in WAF (WAF has no feature to directly set CORS headers — a conceptual error).
- C. **Enable CORS on the API Gateway API endpoint. Verify the API endpoint is configured so every response includes an `Access-Control-Allow-Origin: www.example.com` header.**
- D. Enable CORS settings in the Lambda function (the browser's CORS check is based on the response headers returned by API Gateway — even if Lambda's response includes the header, it may not ultimately reach the client without integration response mapping configured in API Gateway; configuring CORS at the API Gateway level is the standard fix).

**Correct Answer: C**

**Explanation**
The CORS error occurs because the response from the actual endpoint the browser calls — the **API Gateway endpoint** — lacks the correct `Access-Control-Allow-Origin` header. You need to **enable CORS in API Gateway** (a mock integration for the OPTIONS method, and header mapping included in the actual method's response) so that this header is included in every response.

**Why the other choices are wrong**

- B: AWS WAF has no feature to configure/manage CORS headers.
- D: Even if the Lambda function code returns the header, it may not reach the browser unless API Gateway's integration response is configured to map it to an actual header — configuring CORS at the API Gateway level itself is the fundamental fix.

> 💡 **Exam tip**: For a **CORS error** occurring in the browser, always first check whether the **endpoint actually being called (here, API Gateway)** includes the correct `Access-Control-Allow-Origin` header in its response. The standard fix is **API Gateway's CORS configuration**, not changes to S3, WAF, or Lambda code.
