## Q1. 표준 SQL로 S3 데이터 쿼리하기

Amazon S3에 직접 저장된 데이터 세트를 표준 SQL로 쿼리하는 데 사용할 수 있는 AWS 서비스는 무엇입니까?

- A. AWS Glue
- B. AWS Data Pipeline
- C. Amazon CloudSearch
- D. Amazon Athena

**정답: D**

✅ **D. Amazon Athena**: Amazon Athena는 표준 SQL을 사용하여 Amazon S3에 직접 저장된 데이터를 분석할 수 있는 서버리스 대화형 쿼리 서비스입니다. 관리할 인프라가 없으며, S3의 데이터를 지정하고 스키마를 정의한 후 쿼리를 시작하면 됩니다.

❌ **A. AWS Glue**: AWS Glue는 데이터를 준비하고 변환하는 ETL(추출, 변환, 적재) 서비스이며, S3에서 직접 애드혹 SQL 쿼리를 실행하는 서비스가 아닙니다.

❌ **B. AWS Data Pipeline**: AWS Data Pipeline은 AWS 서비스 간 데이터 이동 및 변환을 위한 워크플로 오케스트레이션 서비스이며, S3 데이터에 대한 SQL 쿼리 기능을 제공하지 않습니다.

❌ **C. Amazon CloudSearch**: Amazon CloudSearch는 애플리케이션에 검색 기능을 구축하기 위한 관리형 검색 서비스이며, S3 데이터에 대한 SQL 쿼리를 지원하지 않습니다.

💡 **시험 꿀팁**: Amazon Athena = S3에서 직접 서버리스 SQL 쿼리. 관리할 서버 없음. 스캔된 TB당 쿼리 비용 지불. 주로 AWS Glue 데이터 카탈로그와 함께 사용됩니다.

## Q2. AWS CloudFormation의 목적

AWS CloudFormation은 다음 중 어느 것을 지원하도록 설계되었습니까?

- A. 리소스 모델링 및 프로비저닝
- B. 애플리케이션 코드 업데이트
- C. 데이터 레이크 설정
- D. 청구 보고서 생성

**정답: A**

✅ **A. 리소스 모델링 및 프로비저닝**: AWS CloudFormation은 전체 AWS 인프라를 템플릿 파일로 모델링하고 자동화된 반복 가능한 방식으로 해당 리소스를 프로비저닝할 수 있는 인프라를 코드로(IaC) 서비스입니다.

❌ **B. 애플리케이션 코드 업데이트**: CloudFormation은 인프라 리소스를 관리하며, 애플리케이션 수준의 코드 배포를 처리하지 않습니다. AWS CodeDeploy 같은 서비스가 애플리케이션 코드 업데이트를 담당합니다.

❌ **C. 데이터 레이크 설정**: 데이터 레이크 설정은 일반적으로 AWS Lake Formation이나 Glue와 결합된 Amazon S3를 사용하며, CloudFormation을 직접 사용하지 않습니다(CloudFormation이 해당 서비스를 프로비저닝할 수는 있지만).

❌ **D. 청구 보고서 생성**: 청구 보고서는 AWS Cost Explorer 또는 AWS Budgets를 통해 생성되며, CloudFormation이 아닙니다.

💡 **시험 꿀팁**: CloudFormation = 인프라를 코드로(IaC). 템플릿(JSON/YAML)이 AWS 리소스를 정의합니다. 반복 가능하고 자동화된 프로비저닝을 가능하게 합니다. "AWS 환경의 청사진"으로 생각하세요.

## Q3. 제한 없는 보안 그룹 접근 식별

Cloud Practitioner가 AWS 계정의 보안 그룹 중 특정 포트에 대한 제한 없는 접근을 허용하는 것이 있는지 확인해야 합니다. 가장 쉬운 방법은 무엇입니까?

- A. Amazon EC2 관리 콘솔에서 각 보안 그룹의 인바운드 규칙을 검토하고 0.0.0.0/0 포트를 확인합니다.
- B. AWS Trusted Advisor를 실행하고 결과를 검토합니다.
- C. AWS IAM 콘솔을 열고 인바운드 규칙 필터가 개방으로 설정되어 있는지 확인합니다.
- D. AWS Config에서 Lambda 함수를 호출하는 사용자 지정 규칙을 만들어 인바운드 액세스 규칙을 검토합니다.

**정답: B**

✅ **B. AWS Trusted Advisor를 실행하고 결과 검토**: AWS Trusted Advisor는 제한 없는 액세스(0.0.0.0/0)를 허용하는 보안 그룹에 대한 특정 보안 검사를 포함하여 AWS 환경을 모범 사례에 맞게 자동으로 검사합니다. 이것이 가장 단순하고 자동화된 방법입니다.

❌ **A. EC2 콘솔에서 인바운드 규칙 검토**: 기술적으로 가능하지만, 특히 대규모 계정에서 모든 보안 그룹을 수동으로 검토하는 것은 시간이 많이 걸리고 오류가 발생하기 쉬워 "가장 단순한" 방법이 아닙니다.

❌ **C. AWS IAM 콘솔 열기**: IAM은 사용자 및 역할에 대한 ID와 액세스 정책을 관리하며, 네트워크 수준의 보안 그룹 규칙이 아닙니다. 이 작업에 잘못된 콘솔입니다.

❌ **D. Lambda를 포함한 AWS Config 사용자 지정 규칙**: 이 접근 방식은 작동하겠지만 상당한 설정 작업이 필요합니다. Trusted Advisor가 이미 이 검사를 기본으로 제공할 때 가장 간단한 해결책이 아닙니다.

💡 **시험 꿀팁**: AWS Trusted Advisor = 5개 카테고리에 걸친 자동 모범 사례 검사: 비용 최적화, 성능, 보안, 내결함성, 서비스 한도. 보안 그룹 검사에는 Trusted Advisor가 가장 쉬운 자동화 접근 방식입니다.

## Q4. 온프레미스 대비 AWS 개발 이점 (2개 선택)

온프레미스가 아닌 AWS 클라우드에서 새 애플리케이션을 개발하고 실행하면 어떤 이점이 있습니까? (2개 선택)

- A. AWS는 높은 내구성을 위해 데이터를 전 세계적으로 자동 배포합니다.
- B. AWS는 애플리케이션 운영을 담당합니다.
- C. AWS는 고가용성 설계를 쉽게 합니다.
- D. AWS는 애플리케이션 수요 변화에 쉽게 대응할 수 있게 합니다.
- E. AWS는 애플리케이션 보안 패치를 관리합니다.

**정답: C, D**

✅ **C. AWS는 고가용성 설계를 쉽게 합니다**: AWS는 다중 AZ 배포, 로드 밸런서, Auto Scaling, 글로벌 인프라를 제공하여 고가용성 애플리케이션을 쉽게 구축할 수 있게 합니다. 온프레미스에서 동일한 것을 구현하는 데는 막대한 비용이 드는 기능들입니다.

✅ **D. AWS는 애플리케이션 수요 변화에 쉽게 대응할 수 있게 합니다**: AWS의 탄력적 스케일링 기능(Auto Scaling, 온디맨드 리소스)을 통해 애플리케이션이 실제 수요에 따라 확장하거나 축소할 수 있습니다. 이는 고정된 온프레미스 하드웨어로 달성하기 어렵고 비용이 많이 드는 기능입니다.

❌ **A. AWS는 데이터를 전 세계적으로 자동 배포합니다**: AWS는 모든 데이터를 자동으로 전 세계에 배포하지 않습니다. 교차 리전 복제는 명시적으로 구성해야 합니다.

❌ **B. AWS는 애플리케이션 운영을 담당합니다**: 공유 책임 모델에 따라 AWS는 기본 인프라를 관리하지만, 고객은 애플리케이션의 운영 및 관리를 담당합니다.

❌ **E. AWS는 애플리케이션 보안 패치를 관리합니다**: AWS는 기본 인프라와 관리형 서비스 플랫폼을 패치하지만, 고객은 EC2 인스턴스에서 자신의 애플리케이션 코드와 운영 체제를 패치해야 합니다.

💡 **시험 꿀팁**: 클라우드의 주요 이점 = 탄력성(수요에 따른 확장/축소), 고가용성(다중 AZ), 민첩성(빠른 프로비저닝). 공유 책임 모델을 기억하세요 — AWS는 인프라를 관리하고, 고객은 애플리케이션을 관리합니다.

## Q5. EC2에 대한 자동화된 보안 평가 서비스

사용자가 Amazon EC2 인스턴스에 대한 의도하지 않은 네트워크 접근과 인스턴스의 취약점을 식별하는 자동화된 보안 평가 보고서가 필요합니다. 이 평가 보고서를 제공하는 AWS 서비스는 무엇입니까?

- A. EC2 Security Groups
- B. AWS Config
- C. Amazon Macie
- D. Amazon Inspector

**정답: D**

✅ **D. Amazon Inspector**: Amazon Inspector는 EC2 인스턴스의 소프트웨어 취약점과 의도하지 않은 네트워크 노출을 스캔하는 자동화된 보안 평가 서비스입니다. 심각도 등급 및 수정 지침과 함께 상세한 조사 결과 보고서를 생성합니다.

❌ **A. EC2 Security Groups**: 보안 그룹은 네트워크 트래픽을 제어하는 방화벽 규칙이며, 보안 평가를 수행하거나 취약성 보고서를 생성하지 않습니다.

❌ **B. AWS Config**: AWS Config는 규정 준수 규칙에 대한 구성 변경을 추적하고 리소스를 평가하지만, EC2 인스턴스에 대한 취약점 스캔이나 네트워크 노출 평가를 수행하지 않습니다.

❌ **C. Amazon Macie**: Amazon Macie는 머신 러닝을 사용하여 Amazon S3에서 민감한 데이터(PII 등)를 발견하고 보호합니다. EC2 취약점 평가나 네트워크 접근 분석을 위해 설계되지 않았습니다.

💡 **시험 꿀팁**: Amazon Inspector = EC2 및 컨테이너 이미지에 대한 자동화된 취약점 스캔. CVE(공통 취약점 및 노출) 및 네트워크 도달 가능성 확인. Macie(S3 민감한 데이터)나 GuardDuty(위협 탐지)와 혼동하지 마세요.

## Q6. 프로덕션 및 비프로덕션 비용 격리

AWS에서 프로덕션 및 비프로덕션 워크로드의 비용을 어떻게 격리할 수 있습니까?

- A. 운영 및 비운영 워크로드에 대한 IAM 역할 생성
- B. 프로덕션 및 비프로덕션 비용에 서로 다른 계정 사용
- C. 비프로덕션 워크로드에는 Amazon EC2를, 프로덕션 워크로드에는 다른 서비스 사용
- D. Amazon CloudWatch를 사용하여 서비스 사용량 모니터링

**정답: B**

✅ **B. 프로덕션 및 비프로덕션 비용에 서로 다른 계정 사용**: 워크로드를 별도의 AWS 계정으로 분리하는 것은 비용 격리를 위한 AWS 권장 모범 사례입니다. 각 계정에는 자체 청구가 있어 프로덕션과 비프로덕션 환경의 비용을 쉽게 추적, 할당, 보고할 수 있습니다.

❌ **A. 운영 및 비운영 워크로드에 대한 IAM 역할 생성**: IAM 역할은 액세스 권한을 제어하며, 워크로드 간 청구를 분리하거나 비용을 격리하지 않습니다.

❌ **C. 환경에 따라 다른 서비스 사용**: 환경에 따라 다른 서비스를 선택해도 비용이 격리되지 않으며 불필요한 아키텍처 복잡성이 생깁니다.

❌ **D. Amazon CloudWatch로 서비스 사용량 모니터링**: CloudWatch는 성능 지표 및 로그를 모니터링하며, 사용량에 대한 가시성을 제공할 수 있지만 워크로드 간 비용을 격리하거나 분리하지 않습니다.

💡 **시험 꿀팁**: 비용 격리 모범 사례 = 환경별 별도 AWS 계정(프로덕션/비프로덕션). 중앙에서 여러 계정을 관리하려면 통합 청구 및 서비스 제어 정책(SCP)과 함께 AWS Organizations를 사용하세요.

## Q7. AWS 인증 타사 보안 솔루션 카탈로그 위치

사용자가 AWS 인증 타사 보안 솔루션 공급업체의 카탈로그를 어디에서 찾을 수 있습니까?

- A. AWS Service Catalog
- B. AWS Marketplace
- C. AWS Quick Start
- D. AWS CodeDeploy

**정답: B**

✅ **B. AWS Marketplace**: AWS Marketplace는 AWS가 검증하고 인증한 보안 솔루션을 포함하여 독립 소프트웨어 공급업체(ISV)의 수천 개의 소프트웨어 목록이 있는 디지털 카탈로그입니다. 고객은 Marketplace에서 직접 타사 소프트웨어를 찾아 구매하고 배포할 수 있습니다.

❌ **A. AWS Service Catalog**: AWS Service Catalog는 조직이 자체적으로 승인된 IT 서비스 포트폴리오를 관리하고 배포하는 서비스이며, 타사 공급업체 솔루션의 공개 카탈로그가 아닙니다.

❌ **C. AWS Quick Start**: AWS Quick Starts는 AWS 및 파트너가 주로 구축한 인기 있는 워크로드에 대한 자동화된 참조 배포입니다. 공급업체 카탈로그가 아닌 배포 가이드입니다.

❌ **D. AWS CodeDeploy**: AWS CodeDeploy는 EC2, Lambda 또는 온프레미스 서버에 애플리케이션 배포를 자동화하는 배포 서비스이며, 공급업체 카탈로그와는 무관합니다.

💡 **시험 꿀팁**: AWS Marketplace = 타사 소프트웨어 카탈로그. AMI, SaaS 구독, 보안 도구 등을 찾을 수 있습니다. 요금은 AWS 청구서에 나타납니다. AWS Service Catalog(내부, 큐레이션된 IT 포트폴리오)와 구분하세요.

## Q8. 7년간 규정 준수를 위한 장기 저비용 데이터 스토리지

Cloud Practitioner가 규정 요구 사항을 충족하기 위해 가능한 최저 비용으로 7년 동안 데이터를 저장해야 합니다. 이 요구 사항에 가장 적합한 AWS 서비스는 무엇입니까?

- A. Amazon S3
- B. AWS Snowball
- C. Amazon Redshift
- D. Amazon S3 Glacier

**정답: D**

✅ **D. Amazon S3 Glacier**: Amazon S3 Glacier(특히 S3 Glacier Deep Archive)는 AWS 포트폴리오에서 가장 낮은 스토리지 비용으로 장기 아카이브 스토리지를 위해 설계되었습니다. 데이터에 거의 액세스하지 않는 규정 준수 및 규제 데이터 보존 시나리오에 이상적입니다.

❌ **A. Amazon S3**: Amazon S3는 내구성 높은 객체 스토리지를 제공하지만, 표준 S3 스토리지 계층은 장기 아카이브 사용 사례에 비해 S3 Glacier보다 훨씬 비쌉니다.

❌ **B. AWS Snowball**: AWS Snowball은 대용량 데이터를 AWS로 이동하는 데 사용되는 물리적 데이터 전송 디바이스입니다. 장기 보존을 위한 스토리지 서비스가 아닙니다.

❌ **C. Amazon Redshift**: Amazon Redshift는 대규모 데이터 세트에 대한 분석 쿼리에 최적화된 완전 관리형 데이터 웨어하우스 서비스입니다. 저비용 장기 아카이브 스토리지를 위한 서비스가 아닙니다.

💡 **시험 꿀팁**: S3 Glacier Deep Archive = AWS에서 가장 저렴한 스토리지. 검색 시간: 12~48시간. 7년 규정 보존에 완벽합니다. S3 스토리지 클래스 비용 순서(높은 것부터): S3 Standard > S3-IA > S3 One Zone-IA > S3 Glacier Instant > S3 Glacier Flexible > S3 Glacier Deep Archive.

## Q9. AWS 클라우드 사용의 즉각적인 이점 (2개 선택)

AWS 클라우드 사용의 즉각적인 이점은 무엇입니까? (2개 선택)

- A. IT 직원 증가
- B. 자본 지출이 변동 비용으로 대체됩니다.
- C. 인프라에 대한 사용자 제어 증가
- D. 민첩성 증가
- E. AWS가 클라우드 보안을 담당합니다.

**정답: B, D**

✅ **B. 자본 지출이 변동 비용으로 대체됩니다**: AWS는 하드웨어에 대한 대규모 선불 자본 지출(CapEx)의 필요성을 없앱니다. 대신 사용한 만큼만 지불(OpEx — 운영 지출)하므로 현금 흐름이 개선되고 재무 위험이 감소합니다.

✅ **D. 민첩성 증가**: AWS는 기업이 빠르게 실험하고 배포하며 새로운 아이디어를 반복할 수 있게 합니다. 리소스를 수 주가 아닌 수 분 안에 프로비저닝할 수 있어 혁신 사이클이 크게 가속화됩니다.

❌ **A. IT 직원 증가**: AWS로 마이그레이션하면 인프라 관리 직원의 필요성이 줄어드는 경향이 있습니다(유지 관리할 서버가 적어짐). 증가하는 것이 아닙니다.

❌ **C. 인프라에 대한 사용자 제어 증가**: AWS에서는 기본 인프라의 물리적 제어를 포기합니다. 이것은 AWS가 관리합니다. 절충점은 운영 부담 감소이지, 제어 증가가 아닙니다.

❌ **E. AWS가 클라우드 보안을 담당합니다**: AWS 공유 책임 모델에 따라 AWS는 인프라를 보호하지만(클라우드의 보안), 고객은 데이터와 구성을 보호해야 합니다(클라우드에서의 보안).

💡 **시험 꿀팁**: 클라우드 컴퓨팅의 6가지 이점: CapEx를 OpEx로 전환, 대규모 경제 이점, 용량 추정 불필요, 속도 및 민첩성 향상, 데이터 센터 운영 비용 절감, 몇 분 만에 글로벌 확장. CapEx → OpEx와 민첩성이 가장 자주 출제됩니다.

## Q10. 민감한 데이터를 자동으로 인식하고 분류하는 서비스

AWS에서 중요한 데이터나 지적 재산을 자동으로 인식하고 분류하는 AWS 보안 서비스는 무엇입니까?

- A. Amazon GuardDuty
- B. Amazon Macie
- C. Amazon Inspector
- D. AWS Shield

**정답: B**

✅ **B. Amazon Macie**: Amazon Macie는 머신 러닝을 사용하여 Amazon S3에 저장된 민감한 데이터(PII, 금융 데이터, 지적 재산 등)를 자동으로 발견, 분류, 보호하는 완전 관리형 데이터 보안 및 개인 정보 보호 서비스입니다.

❌ **A. Amazon GuardDuty**: Amazon GuardDuty는 AWS 계정 전반의 악의적인 활동 및 무단 동작을 모니터링하는 위협 탐지 서비스입니다. 데이터를 분류하지 않습니다.

❌ **C. Amazon Inspector**: Amazon Inspector는 EC2 인스턴스 및 컨테이너 이미지에 대한 자동화된 취약점 평가를 수행합니다. 민감한 데이터를 발견하거나 분류하도록 설계되지 않았습니다.

❌ **D. AWS Shield**: AWS Shield는 DDoS 보호 서비스입니다. 데이터 콘텐츠를 인식하거나 분류하는 기능이 없습니다.

💡 **시험 꿀팁**: Amazon Macie = S3의 머신 러닝 기반 민감한 데이터 발견. 신용카드 번호, 주민번호, 여권 등의 PII 탐지. Macie = S3 데이터 분류; GuardDuty = 위협 탐지; Inspector = 취약점 스캔을 기억하세요.

## Q11. AWS Storage Gateway의 목적

AWS Storage Gateway의 목적은 무엇입니까?

- A. 온프레미스 데이터 스토리지에 99.9999999% 내구성 보장
- B. AWS에서 페타바이트 규모의 데이터 전송
- C. 여러 Amazon EC2 인스턴스에 연결
- D. 온프레미스 데이터 스토리지를 AWS 클라우드에 연결

**정답: D**

✅ **D. 온프레미스 데이터 스토리지를 AWS 클라우드에 연결**: AWS Storage Gateway는 온프레미스 환경과 AWS 클라우드 스토리지 간의 원활한 통합을 제공하는 하이브리드 클라우드 스토리지 서비스입니다. 표준 스토리지 프로토콜을 통해 온프레미스 애플리케이션이 AWS 스토리지 서비스(S3, Glacier, EBS)를 사용할 수 있게 합니다.

❌ **A. 온프레미스 데이터 스토리지에 99.9999999% 내구성 보장**: AWS Storage Gateway는 온프레미스에 저장된 데이터의 내구성을 보장하지 않습니다. 내구성은 게이트웨이가 연결하는 기본 AWS 서비스(S3 등)에 적용됩니다.

❌ **B. AWS에서 페타바이트 규모의 데이터 전송**: 페타바이트 규모의 데이터 전송은 AWS Snowball 또는 AWS DataSync의 사용 사례이며, Storage Gateway가 아닙니다. Storage Gateway는 일회성 대규모 마이그레이션이 아닌 지속적인 하이브리드 연결을 위해 설계되었습니다.

❌ **C. 여러 Amazon EC2 인스턴스에 연결**: AWS Storage Gateway는 EC2 연결 솔루션이 아닙니다. EBS(Elastic Block Store)나 EFS(Elastic File System)가 EC2 인스턴스에 스토리지를 연결하는 데 사용됩니다.

💡 **시험 꿀팁**: AWS Storage Gateway = 온프레미스와 AWS 간 하이브리드 스토리지 브리지. 세 가지 주요 유형: 파일 게이트웨이(NFS/SMB를 통한 S3), 볼륨 게이트웨이(iSCSI 블록 스토리지), 테이프 게이트웨이(가상 테이프 라이브러리). 주요 사용 사례: 온프레미스 스토리지를 클라우드로 확장.

## Q12. 지리적으로 분리된 위치에 애플리케이션 배포

지리적으로 분리된 위치에 애플리케이션을 어떻게 배포해야 합니까?

- A. 여러 인터넷 게이트웨이를 사용하여 애플리케이션을 설치합니다.
- B. Amazon VPC에 애플리케이션을 배포합니다.
- C. 여러 AWS 리전에 애플리케이션을 배포합니다.
- D. 여러 NAT 게이트웨이를 사용하여 애플리케이션을 구성합니다.

**정답: C**

✅ **C. 여러 AWS 리전에 애플리케이션 배포**: AWS 리전은 전 세계의 지리적으로 분리된 위치입니다. 여러 리전에 애플리케이션을 배포하면 지리적 분리가 보장되고 전 세계 사용자의 지연 시간이 줄어들며 재해 복구 기능이 제공됩니다.

❌ **A. 여러 인터넷 게이트웨이 사용**: 인터넷 게이트웨이는 단일 VPC 내의 리소스에 인터넷 접근을 제공하며, 지리적 분리를 제공하지 않습니다. VPC당 하나의 인터넷 게이트웨이만 연결할 수 있습니다.

❌ **B. Amazon VPC에 애플리케이션 배포**: Amazon VPC는 단일 리전 내에 존재합니다. VPC는 네트워크 격리를 제공하지만 전 세계적인 지리적 분리를 달성하지 못합니다.

❌ **D. 여러 NAT 게이트웨이 구성**: NAT 게이트웨이는 단일 VPC/리전 내에서 프라이빗 서브넷의 리소스가 인터넷에 접근할 수 있게 합니다. 지리적 분산을 제공하지 않습니다.

💡 **시험 꿀팁**: AWS 글로벌 인프라 계층: 리전(지리적 영역) > 가용 영역(리전 내 격리된 데이터 센터) > 엣지 로케이션(CloudFront CDN 엔드포인트). 지리적 분리 = 여러 리전. 리전 내 내결함성 = 여러 AZ.

## Q13. 컴포넌트 장애를 견디도록 설계된 시스템

AWS 클라우드의 시스템이 하나 이상의 컴포넌트 장애를 견딜 수 있도록 설계되었습니다. 이것은 어떤 설계 원칙을 나타냅니까?

- A. 탄력성(Elasticity)
- B. 고가용성(High Availability)
- C. 확장성(Scalability)
- D. 민첩성(Agility)

**정답: B**

✅ **B. 고가용성**: 고가용성(HA)은 개별 컴포넌트가 장애를 겪어도 계속 작동하는 시스템을 설계하는 것을 의미합니다. AWS는 여러 가용 영역에 걸친 중복성, 자동 페일오버, 로드 밸런싱을 통해 이를 달성하여 최소한의 다운타임 또는 제로 다운타임을 보장합니다.

❌ **A. 탄력성**: 탄력성은 수요에 따라 리소스를 자동으로 확장하거나 축소하는 능력을 말합니다. 용량 관리를 다루며, 장애 내성이 아닙니다.

❌ **C. 확장성**: 확장성은 리소스를 추가하여 증가하는 워크로드를 처리하는 시스템의 능력을 말합니다. 성장 용량에 초점을 맞추며, 장애에 대한 복원력이 아닙니다.

❌ **D. 민첩성**: 민첩성은 새 리소스를 배포하고 변경할 수 있는 속도를 말합니다. 개발 속도에 관한 것이지, 장애 내성이 아닙니다.

💡 **시험 꿀팁**: 고가용성(HA) = 최소 다운타임으로 컴포넌트 장애를 견디도록 설계. 주요 AWS HA 도구: 다중 AZ 배포, Elastic Load Balancing, Auto Scaling, Route 53 상태 확인. 내결함성은 더 엄격한 형태로, 장애 중에도 제로 다운타임입니다.

## Q14. AWS와 온프레미스 시스템 간의 일관되고 전용 연결

Cloud Practitioner가 AWS 리소스와 온프레미스 시스템 간에 일관되고 전용적인 연결이 필요합니다. 이 요구 사항을 충족하는 AWS 서비스는 무엇입니까?

- A. AWS Direct Connect
- B. AWS VPN
- C. Amazon Connect
- D. AWS Data Pipeline

**정답: A**

✅ **A. AWS Direct Connect**: AWS Direct Connect는 온프레미스 데이터 센터와 AWS 간에 전용 프라이빗 네트워크 연결을 설정합니다. 인터넷 기반 연결과 달리 Direct Connect는 일관된 네트워크 성능, 감소된 지연 시간, 더 높은 대역폭을 제공합니다. 안정적이고 예측 가능한 연결이 필요한 애플리케이션에 이상적입니다.

❌ **B. AWS VPN**: AWS VPN은 공용 인터넷을 통해 암호화된 연결을 설정합니다. 안전한 연결을 제공하지만 인터넷 성능이 변동될 수 있어 Direct Connect의 일관성과 전용 대역폭을 제공하지 않습니다.

❌ **C. Amazon Connect**: Amazon Connect는 고객 서비스 운영을 위한 클라우드 기반 콜센터 서비스입니다. 온프레미스와 AWS 간의 네트워크 연결과는 전혀 무관합니다.

❌ **D. AWS Data Pipeline**: AWS Data Pipeline은 AWS 서비스 간 데이터 이동 및 변환을 자동화하는 워크플로 서비스입니다. 네트워크 연결 솔루션이 아닙니다.

💡 **시험 꿀팁**: AWS Direct Connect = 전용, 프라이빗, 일관된 네트워크 링크(물리적 광섬유 연결). VPN = 공용 인터넷을 통한 암호화(가변 성능). Direct Connect = 전용 회선; VPN = 인터넷을 통한 암호화 터널. Direct Connect는 더 비싸지만 더 안정적입니다.

## Q15. 보안 및 규정 준수에 대한 공유 책임

AWS 공유 책임 모델에 따르면 보안 및 규정 준수의 책임은 누가 집니까?

- A. 고객이 책임집니다.
- B. AWS가 책임집니다.
- C. AWS와 고객이 책임을 공유합니다.
- D. AWS는 관련 규제 기관과 책임을 공유합니다.

**정답: C**

✅ **C. AWS와 고객이 책임을 공유합니다**: AWS 공유 책임 모델은 AWS와 고객 간에 보안 책임을 분담합니다. AWS는 "클라우드의 보안"(물리적 인프라, 하드웨어, 소프트웨어, 네트워킹)을 담당하고, 고객은 "클라우드에서의 보안"(데이터, 자격 증명 관리, 애플리케이션 구성, 자체 환경 내 네트워크 트래픽 보호)을 담당합니다.

❌ **A. 고객이 책임집니다**: 고객은 부분적으로만 책임이 있습니다. AWS도 기본 인프라에 대한 상당한 보안 책임을 집니다.

❌ **B. AWS가 책임집니다**: AWS는 부분적으로만 책임이 있습니다. 고객은 자신의 데이터, 접근 제어, 애플리케이션 계층 구성의 보안을 관리해야 합니다.

❌ **D. AWS는 규제 기관과 책임을 공유합니다**: AWS는 정부나 규제 기관과 보안 책임을 공유하지 않습니다. AWS는 규정 준수 인증을 획득하지만(PCI DSS, HIPAA, SOC), 책임은 고객과 공유하며 규제 기관과 공유하지 않습니다.

💡 **시험 꿀팁**: 공유 책임 모델 — AWS = 클라우드의 보안(하드웨어, 시설, 글로벌 인프라, 관리형 서비스). 고객 = 클라우드에서의 보안(데이터 암호화, IAM, EC2의 OS 패치, 방화벽 구성). 관리형 서비스(RDS, Lambda)는 더 많은 책임을 AWS로 이전합니다.

## Q16. AWS CLI 사용을 위해 생성해야 하는 것

AWS CLI를 사용하려면 사용자가 무엇을 생성해야 합니까?

- A. 비밀번호 정책
- B. 액세스 키 / 시크릿 키
- C. 관리형 정책
- D. API 키

**정답: B**

✅ **B. 액세스 키 / 시크릿 키**: AWS CLI 인증에는 액세스 키 ID와 시크릿 액세스 키가 필요합니다. 이것들은 AWS IAM에서 생성되고 `aws configure` 명령을 사용하여 구성됩니다. CLI는 이 자격 증명을 사용하여 API 요청을 프로그래밍 방식으로 인증합니다.

❌ **A. 비밀번호 정책**: 비밀번호 정책은 IAM 사용자 콘솔 로그인(AWS 관리 콘솔의 사용자 이름 + 비밀번호)에 적용됩니다. AWS CLI에서는 사용하지 않습니다.

❌ **C. 관리형 정책**: 관리형 정책은 권한(허용되는 작업)을 정의하지만, 단독으로 CLI에 사용자를 인증하지 않습니다. 인증을 위해서는 여전히 액세스 키가 필요합니다.

❌ **D. API 키**: "API 키"는 특정 AWS IAM 객체 유형이 아닙니다. AWS는 프로그래밍 방식 액세스에 액세스 키 ID와 시크릿 액세스 키를 사용합니다. 이 조합이 때로 API 자격 증명으로 불리지만, 올바른 AWS 용어는 액세스 키입니다.

💡 **시험 꿀팁**: AWS CLI 인증 = 액세스 키 ID + 시크릿 액세스 키(`aws configure`로 구성). 코드에 액세스 키를 절대 공유하거나 포함하지 마세요. 모범 사례: EC2 인스턴스 및 다른 AWS 서비스에는 장기 액세스 키 대신 IAM 역할을 사용하세요.

## Q17. Amazon EBS 암호화를 제공하는 AWS 서비스

Amazon EBS 암호화를 제공하는 데 사용되는 AWS 서비스는 무엇입니까?

- A. AWS Certificate Manager
- B. AWS Systems Manager
- C. AWS KMS
- D. AWS Config

**정답: C**

✅ **C. AWS KMS**: AWS 키 관리 서비스(KMS)는 Amazon EBS 볼륨 암호화에 사용되는 암호화 키를 관리합니다. EBS 암호화를 활성화하면 AWS KMS는 고객 마스터 키(CMK)를 사용하여 데이터 암호화 키(DEK)를 생성하고 관리하여 저장 중 데이터를 보호합니다.

❌ **A. AWS Certificate Manager**: AWS Certificate Manager(ACM)는 HTTPS 통신을 위한 SSL/TLS 인증서를 프로비저닝하고 관리합니다. 전송 중 데이터 암호화에 사용되며, EBS의 저장 중 데이터 암호화에 사용되지 않습니다.

❌ **B. AWS Systems Manager**: AWS Systems Manager는 EC2 인스턴스에서 운영 작업(패치 적용, 구성, 파라미터 스토어)을 관리하고 자동화하는 데 도움이 됩니다. EBS 볼륨 암호화를 제공하지 않습니다.

❌ **D. AWS Config**: AWS Config는 규정 준수를 위해 AWS 리소스 구성을 기록하고 평가합니다. EBS 볼륨이 암호화되어 있는지 확인할 수 있지만, 직접 암호화를 수행하지는 않습니다.

💡 **시험 꿀팁**: AWS KMS = AWS 서비스 전반의 암호화를 위한 중앙화된 키 관리. EBS, S3, RDS, Lambda 등과 함께 사용됩니다. CMK(고객 마스터 키) = 데이터 키를 암호화하는 키. KMS는 EBS, S3, RDS를 포함하는 "저장 중 암호화" 질문의 정답입니다.

## Q18. AWS Lambda의 프리 티어 이후 요금 방식 (2개 선택)

프리 티어를 초과하면 AWS Lambda 사용 요금은 어떻게 부과됩니까? (2개 선택)

- A. Lambda 함수 실행에 걸리는 시간 기반
- B. 특정 Lambda 함수의 버전 수 기반
- C. 주어진 Lambda 함수의 요청 수 기반
- D. Lambda 함수에서 사용하는 프로그래밍 언어 기반
- E. AWS 계정의 총 Lambda 함수 수 기반

**정답: A, C**

✅ **A. Lambda 함수 실행에 걸리는 시간 기반**: AWS Lambda는 컴퓨팅 기간(함수가 실행되는 시간, 밀리초 단위로 측정)에 따라 요금을 부과합니다. 코드 실행이 시작될 때부터 완료될 때까지의 시간에 대해 가장 가까운 1ms 단위로 청구됩니다.

✅ **C. 주어진 Lambda 함수의 요청 수 기반**: AWS Lambda는 호출(요청) 수에 따라 요금을 부과합니다. 함수가 트리거될 때마다 하나의 요청으로 계산됩니다. 프리 티어에는 월 100만 요청과 400,000 GB-초가 포함됩니다.

❌ **B. Lambda 함수 버전 수 기반**: Lambda는 만든 함수의 버전 수에 따라 요금을 부과하지 않습니다. 버전 관리 및 별칭은 무료 기능입니다.

❌ **D. 사용하는 프로그래밍 언어 기반**: Lambda는 여러 런타임(Python, Node.js, Java 등)을 지원하며 어떤 언어를 사용하든 요금이 동일합니다.

❌ **E. 계정의 총 Lambda 함수 수 기반**: 계정에서 만들거나 저장하는 Lambda 함수의 수에 대한 요금이 없습니다. 실제 호출 및 컴퓨팅 기간에 대해서만 비용을 지불합니다.

💡 **시험 꿀팁**: AWS Lambda 요금 = 요청 수 + 기간(GB-초). 공식: 기간 = (실행 시간 ms) x (할당된 메모리 GB). 프리 티어: 월 100만 요청 및 400,000 GB-초. Lambda는 이벤트 기반 서버리스 서비스로 유휴 요금이 없습니다.

## Q19. AWS 리전, 가용 영역, 엣지 로케이션 간의 관계 (2개 선택)

다음 중 AWS 리전, 가용 영역, 엣지 로케이션 간의 관계를 설명하는 것은 무엇입니까? (2개 선택)

- A. AWS 리전이 가용 영역보다 더 많습니다.
- B. 엣지 로케이션이 AWS 리전보다 더 많습니다.
- C. 엣지 로케이션이 가용 영역입니다.
- D. AWS 리전이 엣지 로케이션보다 더 많습니다.
- E. 가용 영역이 AWS 리전보다 더 많습니다.

**정답: B, E**

✅ **B. 엣지 로케이션이 AWS 리전보다 더 많습니다**: AWS는 전 세계에 수백 개의 엣지 로케이션(CloudFront CDN 접속 지점)이 있으며, 이는 리전(약 30개 이상)보다 훨씬 많습니다. 엣지 로케이션은 전체 리전보다 훨씬 더 많은 도시와 국가에 존재합니다.

✅ **E. 가용 영역이 AWS 리전보다 더 많습니다**: 각 AWS 리전에는 최소 2개(일반적으로 3개 이상)의 가용 영역이 있습니다. 따라서 전 세계적으로 총 가용 영역 수가 리전 수보다 많습니다.

❌ **A. AWS 리전이 가용 영역보다 더 많습니다**: 거짓입니다. 각 리전에는 여러 AZ가 있으므로 총 AZ 수가 리전 수를 초과합니다.

❌ **C. 엣지 로케이션이 가용 영역입니다**: 엣지 로케이션과 가용 영역은 완전히 다른 인프라 구성 요소입니다. 엣지 로케이션은 CloudFront CDN 엔드포인트이고, AZ는 리전 내 격리된 데이터 센터입니다.

❌ **D. AWS 리전이 엣지 로케이션보다 더 많습니다**: 거짓입니다. 전 세계에 수백 개의 엣지 로케이션이 있어 리전 수를 훨씬 초과합니다.

💡 **시험 꿀팁**: AWS 인프라 수량 순서(적은 것부터 많은 것 순): 리전 < 가용 영역 < 엣지 로케이션. 엣지 로케이션(400개 이상) > AZ(100개 이상) > 리전(30개 이상). 엣지 로케이션은 CloudFront(CDN)와 Route 53을 지원합니다.

## Q20. AWS Shield Standard가 제공하는 것

AWS Shield Standard는 무엇을 제공합니까?

- A. WAF 규칙
- B. DDoS 보호
- C. ID 및 액세스 관리(IAM) 권한 및 리소스 접근
- D. 데이터 암호화

**정답: B**

✅ **B. DDoS 보호**: AWS Shield Standard는 추가 비용 없이 모든 AWS 고객에게 자동적이고 항상 켜져 있는 DDoS(분산 서비스 거부) 보호를 제공합니다. AWS 리소스를 대상으로 하는 일반적인 네트워크 및 전송 계층(레이어 3 및 4) DDoS 공격으로부터 방어합니다.

❌ **A. WAF 규칙**: WAF(웹 애플리케이션 방화벽) 규칙은 애플리케이션 계층(레이어 7)에서 악의적인 웹 트래픽을 필터링하는 별도의 서비스인 AWS WAF에서 관리합니다. AWS Shield Standard는 WAF 규칙을 포함하지 않습니다(Shield Advanced는 WAF와 통합됩니다).

❌ **C. IAM 권한 및 리소스 접근**: ID 및 액세스 관리는 완전히 별도의 서비스인 AWS IAM이 처리합니다. Shield는 ID 관리가 아닌 네트워크 수준 위협 보호에 중점을 둡니다.

❌ **D. 데이터 암호화**: 데이터 암호화는 AWS KMS, ACM, 개별 서비스에 내장된 암호화 기능(S3, EBS, RDS)이 제공합니다. AWS Shield는 암호화를 처리하지 않습니다.

💡 **시험 꿀팁**: AWS Shield = DDoS 보호. 두 가지 계층: Shield Standard(무료, 자동, 모든 AWS 고객 보호, L3/L4 공격 방어) vs. Shield Advanced(유료, L7 보호 포함, 비용 보호, 24/7 DDoS 대응 팀 포함). Shield와 WAF(애플리케이션 계층 필터링) 또는 GuardDuty(위협 인텔리전스)를 혼동하지 마세요.
