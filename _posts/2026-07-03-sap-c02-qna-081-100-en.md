## QUESTION 81

**Question**: A fully serverless e-document management system (in eu-central-1) is built with CloudFront (S3 origin) + an API Gateway **regional endpoint** + Lambda + Aurora Serverless (metadata) + S3 (documents). The company has completed a PoC with its largest customer and needs to improve **latency outside Europe.** (Choose two.)

**Choices**
- A. **Enable S3 Transfer Acceleration on the bucket** and ensure the web app uses acceleration signed URLs.
- B. Create an AWS Global Accelerator accelerator and attach it to the CloudFront distribution.
- C. **Change the API Gateway regional endpoint to an edge-optimized endpoint.**
- D. Provision the full stack in two more locations worldwide, using an Aurora Serverless global database.
- E. Add an Amazon RDS Proxy between the Lambda function and the Aurora Serverless database.

**Correct Answer: A, C**

**Explanation**
For document uploads (typically direct-to-S3 via presigned URLs), use **S3 Transfer Acceleration** to speed up uploads from distant users. For API calls, **switch to an edge-optimized endpoint** to leverage CloudFront's edge network for the API too.

**Why the other choices are wrong**
- B: **Global Accelerator isn't meant to attach to a CloudFront distribution** (it's for ALB/NLB/EIP-type endpoints; CloudFront already has its own edge network).
- D: Replicating the full stack elsewhere plus an Aurora global database is a much larger re-architecture than warranted at this early growth stage.
- E: RDS Proxy addresses connection management, unrelated to geographic latency.

> 💡 **Exam tip**: For improving performance for geographically distant users, separate the fixes: **S3 Transfer Acceleration for uploads**, and an **edge-optimized endpoint for API Gateway calls.**

## QUESTION 82

**Question**: Photos/videos uploaded at any time by an app are stored in S3 Standard and served via CloudFront. Most become rarely accessed after 30 days, but **some remain frequently accessed even after 30 days.** Optimize storage cost at the lowest possible price while keeping millisecond retrieval.

**Choices**
- A. **Configure S3 Intelligent-Tiering on the bucket.**
- B. Configure a lifecycle policy transitioning objects to S3 Glacier Deep Archive after 30 days.
- C. Replace S3 with Amazon EFS mounted on EC2 instances.
- D. Add a Cache-Control: max-age header set to 30 days.

**Correct Answer: A**

**Explanation**
For an unpredictable/mixed access pattern where some objects remain hot, **S3 Intelligent-Tiering** automatically moves objects between tiers based on actual access, while always maintaining millisecond-scale retrieval.

**Why the other choices are wrong**
- B: Glacier Deep Archive requires hours to retrieve, failing the millisecond requirement, and ignores objects that stay frequently accessed.
- C: EC2+EFS adds unnecessary compute cost, mismatched with the serverless S3+CloudFront setup.
- D: Cache-Control headers control browser/CDN caching duration, unrelated to S3 storage class/cost.

> 💡 **Exam tip**: When access patterns become **unpredictable (some stay hot)** after a certain age, use **S3 Intelligent-Tiering** rather than a blanket lifecycle transition to Glacier — it optimizes cost automatically while keeping millisecond retrieval.

## QUESTION 83

**Question**: A company stores files/images across various S3 storage classes; S3 costs grew significantly last year. Review 12 months of trends and identify the appropriate storage class per object.

**Choices**
- A. Download 12 months of CUR data and review AWS Trusted Advisor recommendations.
- B. Use S3 Storage Class Analysis and import trend data into a QuickSight dashboard.
- C. **Use Amazon S3 Storage Lens** and **upgrade the default dashboard to include advanced metrics.**
- D. Use Access Analyzer for S3 and import its reports into QuickSight.

**Correct Answer: C**

**Explanation**
**Amazon S3 Storage Lens** is the AWS-native analytics service purpose-built for organization-wide S3 usage/cost trend analysis, storage class recommendations, and advanced metrics — exactly matching this requirement.

**Why the other choices are wrong**
- A: CUR+Trusted Advisor provides cost data and general best-practice advice, but not the same S3-specific granular storage-class trend analysis as Storage Lens.
- B: S3 Storage Class Analysis is a narrower, single-bucket feature (mainly for Standard-IA transition candidates); manually piping it into QuickSight is more effort than Storage Lens's built-in advanced dashboard.
- D: **Access Analyzer for S3 checks for unintended external exposure of a bucket (security)** — a completely different purpose from cost/storage-class analysis.

> 💡 **Exam tip**: For organization-wide S3 usage trend and storage-class optimization analysis, **Amazon S3 Storage Lens** (advanced metrics tier) is the answer. Don't confuse it with S3 Storage Class Analysis (single-bucket, IA-focused) or IAM Access Analyzer for S3 (a security exposure tool).

## QUESTION 84

**Question**: Infrastructure must be defined as code; currently deployed in a single Region, but expansion plans call for deploying across **multiple Regions and multiple AWS accounts.**

**Choices**
- A. Use CloudFormation templates with added IAM policies to control various accounts.
- B. Use AWS Organizations, deploy the template from the master account, and manage deployments across accounts with Control Tower.
- C. **Use AWS Organizations and AWS CloudFormation StackSets**, deploying the template from an account with the necessary IAM permissions.
- D. Use nested stacks with a CloudFormation template, changing Region via the nested stacks.

**Correct Answer: C**

**Explanation**
**CloudFormation StackSets** is designed to deploy the same template across **multiple accounts and Regions simultaneously**, integrated with AWS Organizations for account/OU targeting — exactly matching this requirement.

**Why the other choices are wrong**
- A: Plain CloudFormation templates with IAM policies don't actually enable cross-account deployment (stacks are single-account/single-Region by default).
- B: Control Tower governs landing zone/account provisioning and governance, not the actual template-based multi-Region deployment mechanism (that's StackSets' job).
- D: Nested stacks only modularize resources within a **single** stack/account/Region — not a cross-account/Region deployment mechanism.

> 💡 **Exam tip**: To deploy the same infrastructure across **multiple accounts and Regions**, the standard combo is **AWS Organizations + CloudFormation StackSets.**

## QUESTION 86

**Question**: A company is refactoring a monolith to a modern design; the CI/CD pipeline must support (1) **releasing multiple times per hour**, and (2) **rolling back as fast as possible.**

**Choices**
- A. Bake the app and its configuration into an AMI, and deploy by replacing EC2 instances.
- B. **Designate AWS Elastic Beanstalk (staging in a secondary environment) as the deployment target. Deploy by swapping the staging and production environment URLs.**
- C. Re-provision infrastructure via Systems Manager on each deployment, updating EC2 user data to pull the latest code, using Route 53 weighted routing.
- D. Roll out updates via pre-built AMIs during Auto Scaling events, adding new-version instances and phasing out old-version ones.

**Correct Answer: B**

**Explanation**
Elastic Beanstalk's **swap-environment-URLs (blue/green) deployment** lets you deploy to a staging environment, validate it, then swap URLs instantly to go live — and swap back just as instantly to roll back, satisfying both requirements.

**Why the other choices are wrong**
- A: Baking a fresh AMI each time is too slow for "multiple releases per hour."
- C: Re-provisioning infrastructure on every deployment is far slower and more operationally heavy.
- D: A rolling deployment is gradual, so rollback is equally gradual — not as instant as the URL-swap approach.

> 💡 **Exam tip**: For **extremely frequent releases with instant rollback**, think **Elastic Beanstalk's environment URL swap (blue/green)** pattern — faster than rebuilding AMIs or gradual rolling deployments.

## QUESTION 87

**Question**: An app on EC2 (all instances share one security group) needs **least-privilege** access to an Aurora DB cluster (its own security group). Which two rule combinations are needed? (Choose two.)

**Choices**
- A. Add an **inbound** rule to the EC2 security group, with the DB cluster's security group as source.
- B. **Add an outbound rule to the EC2 security group, targeting the DB cluster's security group (default Aurora port).**
- C. **Add an inbound rule to the DB cluster's security group, with the EC2 security group as source (default Aurora port).**
- D. Add an outbound rule to the DB cluster's security group, targeting the EC2 security group.
- E. Add an outbound rule to the DB cluster's security group, targeting the EC2 security group on an ephemeral port.

**Correct Answer: B, C**

**Explanation**
This is the "security-group-referencing-security-group" least-privilege pattern. Since EC2 initiates the connection to the DB, EC2's side needs an **outbound** rule (targeting the DB's security group, B), and the DB's side needs an **inbound** rule (from the EC2 security group, C).

**Why the other choices are wrong**
- A: An inbound rule on EC2's own security group sourced from the DB is backward — EC2 initiates the request, not the DB.
- D, E: Outbound rules on the DB's security group targeting EC2 are also backward. Return traffic is automatically permitted because security groups are **stateful** — no separate outbound rule is needed for that leg.

> 💡 **Exam tip**: For least-privilege EC2→DB security groups, remember: **① EC2's outbound rule (targeting the DB's security group) + ② the DB's inbound rule (sourced from EC2's security group).** Security groups are stateful, so return traffic needs no separate rule.

## QUESTION 88

**Question**: Multiple business-unit accounts under Organizations want a **centralized** monthly cost report and threshold-alerting solution using existing tags (application, environment, owner). Most cost-effective approach?

**Choices**
- A. Configure AWS Budgets individually in each account, and generate reports per business unit using Cost Explorer in each account.
- B. **Configure AWS Budgets in the organization's master account** (grouped by tags, notifying each business unit via SNS), and **generate monthly reports using Cost Explorer in the master account.**
- C. Configure AWS Budgets individually in each account, and generate reports using the Billing and Cost Management dashboard in each account.
- D. Enable a Cost and Usage Report in the master account, and build a custom Lambda function to process it, send budget alerts, and email monthly reports.

**Correct Answer: B**

**Explanation**
Running **AWS Budgets and Cost Explorer from the organization's master account** lets you see and group all member accounts' data in one place — far more centralized and efficient than configuring the same setup separately in each account.

**Why the other choices are wrong**
- A, C: Repeating identical configuration in every individual account directly contradicts "centralized" and adds maintenance burden.
- D: Enabling the CUR is fine, but reimplementing what Budgets/Cost Explorer already provide natively via a custom Lambda function is unnecessary development effort.

> 💡 **Exam tip**: **Running AWS Budgets and Cost Explorer from the Organizations management account lets you see all member accounts' data at once.** Don't repeat configuration per account or reimplement native features with custom Lambda code.

## QUESTION 89

**Question**: A company deploying infrastructure via CloudFormation is concerned that deleting a production stack might also delete critical data in RDS or EBS. How can accidental data deletion be prevented?

**Choices**
- A. **Modify the CloudFormation template to add a `DeletionPolicy` attribute to the RDS and EBS resources.**
- B. Configure a stack policy that doesn't allow deletion of RDS and EBS resources.
- C. Modify an IAM policy to deny deletion of RDS/EBS resources tagged with the `aws:cloudformation:stack-name` tag.
- D. Use an AWS Config rule to prevent deletion of RDS and EBS resources.

**Correct Answer: A**

**Explanation**
CloudFormation's **`DeletionPolicy`** attribute (`Retain` or `Snapshot`) on a resource ensures that resource is preserved (or snapshotted) rather than deleted along with the rest of the stack — the exact, template-native mechanism for this scenario.

**Why the other choices are wrong**
- B: **Stack policies govern resource changes/deletions during a stack "update,"** not resource preservation during a full stack deletion.
- C: Such an IAM policy would risk blocking CloudFormation's own execution role, too, potentially preventing legitimate resource management as well — too blunt a tool.
- D: AWS Config is a detective/evaluation tool — it has no capability to actually block a resource deletion during a stack deletion.

> 💡 **Exam tip**: To protect a specific resource (RDS, EBS, etc.) when its parent stack is deleted, add a **`DeletionPolicy` attribute** (Retain/Snapshot) directly to that resource. Don't confuse it with stack policies (which protect against update-time changes).

## QUESTION 90

**Question**: VPC Flow Logs on a NAT Gateway show `Action=ACCEPT` for inbound traffic from public IP 198.51.100.2 to a private EC2 instance. Determine whether this represents an unwanted inbound connection from the internet. The VPC CIDR block's first two octets are 203.0.

**Choices**
- A. Open CloudTrail, filter with destination=203.0/source=198.51.100.2.
- B. **Open CloudWatch, select the relevant log group, filter with destination address "like 203.0" and source address "like 198.51.100.2", and run a stats command to sum bytes.**
- C. Open CloudTrail, filter with destination=198.51.100.2/source=203.0 (reversed direction).
- D. Open CloudWatch, filter with destination=198.51.100.2/source=203.0 (reversed direction).

**Correct Answer: B**

**Explanation**
**VPC Flow Logs are typically delivered to CloudWatch Logs** (not CloudTrail, which audits API activity, not network flow data). To investigate "inbound from the internet," filter with **source = the external IP, destination = your VPC's internal range** — the correct direction.

**Why the other choices are wrong**
- A: Wrong console (CloudTrail isn't for flow log data), though the filter direction happens to be correct.
- C: Wrong console AND reversed filter direction (would investigate outbound traffic instead).
- D: Correct console (CloudWatch), but reversed filter direction investigates outbound traffic, not inbound-from-internet.

> 💡 **Exam tip**: **Query VPC Flow Logs via CloudWatch Logs Insights (or Athena over S3), not CloudTrail.** When investigating "inbound from an external source," filter with **source = the external IP, destination = your VPC's CIDR** — get the direction right, or you'll answer a different question (outbound).

## QUESTION 91

**Question**: Two business units (separate accounts under Organizations) regularly share critical documents via slow S3-to-S3 replication (millions of objects). A security audit found neither bucket has encryption at rest enabled. Policy requires all documents encrypted at rest, using **SSE-S3.** Most operationally efficient solution?

**Choices**
- A. **Turn on SSE-S3 on both buckets, and use S3 Batch Operations to copy objects in place to encrypt them.**
- B. Create a KMS key in each account, turn on SSE-KMS, and re-upload existing objects via CLI.
- C. Turn on SSE-S3, and re-upload existing objects using **the S3 copy command in the CLI.**
- D. Create a KMS key in each account, turn on SSE-KMS, and use S3 Batch Operations to copy objects.

**Correct Answer: A**

**Explanation**
Since the requirement explicitly states **SSE-S3**, the KMS-based options (B, D) are wrong from the start. Since default encryption only affects new objects, re-encrypting **millions of existing objects** requires the purpose-built **S3 Batch Operations** for bulk processing (far more efficient than a manual CLI copy loop).

**Why the other choices are wrong**
- B, D: The company explicitly wants **SSE-S3**, but these introduce **SSE-KMS** (customer-managed keys) — a different encryption scheme than requested.
- C: SSE-S3 is correct, but re-encrypting millions of objects one-by-one via CLI copy commands is far less operationally efficient than S3 Batch Operations.

> 💡 **Exam tip**: To re-encrypt **millions of existing S3 objects**, use **S3 Batch Operations** instead of a manual CLI script. When a requirement explicitly says SSE-S3, don't introduce KMS keys.

## QUESTION 92

**Question**: An app continuously ingests large volumes of unstructured data into S3 Standard, needing to be queried/analyzed. Data older than 1 year is never accessed but must be retained indefinitely for compliance. Most cost-effective solution?

**Choices**
- A. Query with S3 Select, and transition data older than 1 year to Glacier Deep Archive.
- B. Query with Redshift Spectrum (requiring a cluster), and transition data older than 1 year to Glacier Deep Archive.
- C. **Query with AWS Glue Data Catalog + Amazon Athena**, and **use a lifecycle policy to transition data older than 1 year to S3 Glacier Deep Archive.**
- D. Query with Redshift Spectrum, and transition data older than 1 year to S3 Intelligent-Tiering.

**Correct Answer: C**

**Explanation**
To query unstructured data without running a cluster, the standard combo is **AWS Glue Data Catalog (schema catalog) + Amazon Athena (serverless SQL)**, paying only per query. Data confirmed **never accessed** after a year but still requiring indefinite retention should transition to the cheapest class, **S3 Glacier Deep Archive** (slow retrieval doesn't matter since it's never queried anyway).

**Why the other choices are wrong**
- A: S3 Select queries individual objects — too limited for a large, growing, catalog-based dataset.
- B, D: Redshift Spectrum requires a **continuously running cluster**, incurring more ongoing compute cost. D also uses Intelligent-Tiering (which has its own monitoring overhead) for data confirmed completely cold, when Glacier Deep Archive is cheaper.

> 💡 **Exam tip**: Query **unstructured** S3 data without a cluster using **Glue Data Catalog + Athena** (fully serverless, pay-per-query) — cheaper than Redshift Spectrum. For data **never accessed** but requiring **indefinite retention**, transition it to **Glacier Deep Archive.**

## QUESTION 93

**Question**: A video company wants to build an ML model using 600TB of compressed data (thousands of files) on an on-premises NAS. No on-prem ML compute exists, so they'll use AWS. The transfer (one-time) must complete within **3 weeks**, with **encryption in transit.** Measured upload speed is 100Mbps, shared across departments. Most cost-effective solution?

**Choices**
- A. **Order multiple AWS Snowball Edge Storage Optimized devices via the console. Configure them with the target S3 bucket, copy data to the devices, and ship them back.**
- B. Set up a 10Gbps Direct Connect connection to the nearest Region.
- C. Set up a VPN connection to the nearest Region.
- D. Deploy an AWS Storage Gateway File Gateway on-premises.

**Correct Answer: A**

**Explanation**
Transferring 600TB over a shared 100Mbps link would take well over a year — network-based options (B, C, D) are all bound by this bandwidth and cannot meet the 3-week deadline. **AWS Snowball Edge** (a physical device filled locally and shipped) is the only realistic option to meet the deadline, and the devices are encrypted, satisfying the security requirement.

**Why the other choices are wrong**
- B: Provisioning a new 10Gbps Direct Connect connection often takes longer than 3 weeks to set up, and is excessive cost for a one-time transfer.
- C: A VPN is still bound by the same underlying 100Mbps shared connection's bandwidth — equally too slow.
- D: A File Gateway also transfers over the network, hitting the same bandwidth bottleneck.

> 💡 **Exam tip**: Always **calculate the transfer time** (data size ÷ bandwidth) before choosing a solution. When the math shows it's infeasible within the deadline, think **AWS Snowball/Snowball Edge** — a classic "do the bandwidth math" pattern on this exam.

## QUESTION 94

**Question**: A migrated form-processing app: users upload scanned forms → SNS notifies the team → team members log in and manually validate/extract data before entering it into another system's API. Automate the manual processing with accurate extraction, while minimizing **both time-to-launch and long-term operational overhead.**

**Choices**
- A. Develop a custom OCR library and deploy it on an EKS cluster.
- B. Extend via Step Functions/Lambda, using a **custom AI/ML model trained and hosted on EC2** for OCR.
- C. Host a new application layer on EC2, calling a **custom model trained and hosted on SageMaker**, storing output in ElastiCache.
- D. **Extend via Step Functions + Lambda, using Amazon Textract and Amazon Comprehend to perform OCR and extract data**, storing output in S3.

**Correct Answer: D**

**Explanation**
**Amazon Textract** (purpose-built form/table-aware OCR) and **Amazon Comprehend** (NLP entity extraction) are fully-managed AWS AI services requiring no custom model training or hosting — minimizing time-to-launch (no training) and long-term overhead (no infrastructure to manage).

**Why the other choices are wrong**
- A: Developing a custom OCR library plus managing an EKS cluster increases both time and operational burden significantly.
- B, C: **Training and hosting a custom AI/ML model** (on EC2 or SageMaker) takes considerable time and leaves ongoing infrastructure management overhead.

> 💡 **Exam tip**: For document/form data extraction automation needing minimal launch time and operational overhead, reach for fully-managed **Amazon Textract (+ Comprehend if needed)** before building a custom OCR/ML model.

## QUESTION 95

**Question**: An on-premises order-processing platform (web frontend on multiple VMs, RabbitMQ connecting frontend to backend, a Kubernetes cluster running the containerized backend) is being refactored to AWS. The company **doesn't want to significantly change the application.** Minimal operational overhead?

**Choices**
- A. **Create an AMI of the web server VM, use an EC2 Auto Scaling group with an ALB, replace the on-prem message queue with Amazon MQ, and host the backend on Amazon EKS.**
- B. Use a custom Lambda runtime and API Gateway to replace the frontend entirely.
- C. AMI+ASG+ALB + Amazon MQ, but **manually install Kubernetes on a fleet of EC2 instances.**
- D. AMI+ASG+ALB + **Amazon SQS** to replace the queue, plus EKS.

**Correct Answer: A**

**Explanation**
To avoid significant application changes, replace messaging with **Amazon MQ** (protocol-compatible with RabbitMQ, no code changes needed) and move the backend to **Amazon EKS** (a managed control plane running standard Kubernetes, unchanged application containers). The web tier stays as VMs via AMI+ASG+ALB.

**Why the other choices are wrong**
- B: Rewriting the web server as Lambda+API Gateway is a major redesign, directly violating "don't significantly change the application."
- C: Manually installing Kubernetes on EC2 (instead of EKS) leaves the same control-plane management burden the company had on-premises.
- D: **Amazon SQS is not protocol-compatible with RabbitMQ/AMQP** — a different proprietary API, requiring application code changes.

> 💡 **Exam tip**: To migrate **RabbitMQ** with minimal code changes, use **Amazon MQ** (not SQS, which requires a rewrite). To migrate self-managed **Kubernetes** with minimal changes, use **Amazon EKS** (not manually installed Kubernetes on raw EC2).

## QUESTION 96

**Question**: Client-side encryption for objects in a new S3 bucket uses a KMS CMK. An IAM policy allows `s3:GetObject/GetObjectVersion/PutObject/PutObjectAcl` and `kms:Decrypt`. Testing shows existing object **downloads succeed**, but new object **uploads fail with "operation is forbidden."** What KMS action needs to be added?

**Choices**
- A. **`kms:GenerateDataKey`**
- B. `kms:GetKeyPolicy`
- C. `kms:GetPublicKey`
- D. `kms:Sign`

**Correct Answer: A**

**Explanation**
For client-side encryption, **encryption (upload) requires `kms:GenerateDataKey`** (to generate a new data key), while **decryption (download) only requires `kms:Decrypt`.** Since the policy only has `kms:Decrypt`, downloads work but uploads (which need a key generated first) fail.

**Why the other choices are wrong**
- B: `kms:GetKeyPolicy` retrieves the key's resource policy — an administrative action, unrelated to encrypt/decrypt operations.
- C: `kms:GetPublicKey` is for **asymmetric** KMS keys — irrelevant to a standard symmetric CMK workflow.
- D: `kms:Sign` is for digitally signing data with an asymmetric key — unrelated to object encryption.

> 💡 **Exam tip**: For client-side encryption with a KMS CMK, remember: **`kms:GenerateDataKey` for encryption (upload)**, **`kms:Decrypt` for decryption (download).** If downloads work but uploads fail with a KMS error, it's almost always a missing `kms:GenerateDataKey`.

## QUESTION 97

**Question**: A web app on EC2 behind an ALB wants to improve its security posture with AWS WAF, **without negatively impacting legitimate traffic.** How should the Web ACL be configured?

**Choices**
- A. **Set the Web ACL rules' action to Count. Enable WAF logging. Analyze requests for false positives. Modify rules accordingly. Over time, change the action from Count to Block.**
- B. Use only rate-based rules with the throttle limit set as high as possible.
- C. Set rules to Block immediately, using only AWS Managed Rule Groups.
- D. Use only custom rule groups with the action set to Allow, gradually shifting to Block.

**Correct Answer: A**

**Explanation**
The AWS-recommended progressive rollout is: **Count mode first → analyze logs for false positives → tune rules → switch to Block** once confident — ensuring legitimate traffic isn't impacted.

**Why the other choices are wrong**
- B: Rate-based rules alone provide narrow protection (missing SQLi/XSS-style attacks).
- C: Jumping straight to Block without testing risks blocking legitimate traffic if managed rules produce false positives.
- D: Excludes AWS Managed Rule Groups, and "Allow" isn't the standard observability/testing action (Count is).

> 💡 **Exam tip**: When rolling out new WAF rules safely, always follow **Count → analyze logs for false positives → tune → Block.**

## QUESTION 98

**Question**: An organization with many accounts needs a common set of IP CIDR ranges (for on-prem allow-listing) reflected in every account's security groups. Currently, developers manually add ranges per account, and the security team (its own account) notifies others of changes. Design a solution to distribute a common CIDR set to all accounts with minimal operational overhead.

**Choices**
- A. Set up an SNS topic in the security team's account, deploy a Lambda function to every account that updates security groups on notification.
- B. Create a separate customer-managed prefix list in each account, notifying owners of updates.
- C. **Create a customer-managed prefix list in the security team's account, populate it with internal CIDR ranges, share it via AWS RAM with the organization, and notify each account owner to allow the new prefix list ID in their security groups.**
- D. Create an IAM role in every account (with security-group-update permission), and have a Lambda function in the security team's account assume each role to update security groups directly.

**Correct Answer: C**

**Explanation**
(Same pattern as Question 53.) Creating a **managed prefix list** once (in the security team's account) and sharing it via **AWS RAM** org-wide means each account only references the list ID once — future updates to the list propagate automatically everywhere.

**Why the other choices are wrong**
- A: A custom Lambda-based sync deployed everywhere reimplements what a managed prefix list already does natively.
- B: Separate prefix lists **per account** still require manually updating every account on future changes — the same problem repeated.
- D: Cross-account IAM roles plus a central Lambda directly modifying security groups is far more complex than a natively-shareable prefix list.

> 💡 **Exam tip**: (Same as Question 53) For a CIDR list shared across many accounts, use a **managed prefix list shared via AWS RAM** — far less overhead than custom Lambda sync or per-account duplicate lists.

## QUESTION 99

**Question**: A new WFH policy requires employees to connect via VPN. Internal apps are hosted across multiple AWS accounts' VPCs, and the primary account's VPC is **already peered** with the others. Design a scalable, most cost-effective AWS Client VPN solution.

**Choices**
- A. Create a separate Client VPN endpoint in each AWS account.
- B. **Create a single Client VPN endpoint in the primary AWS account, and configure the necessary routing to reach internal applications.**
- C. Create a Client VPN endpoint in the primary account, plus provision a Transit Gateway connected to every account.
- D. Create a Client VPN endpoint in the primary account and connect it to the existing Site-to-Site VPN.

**Correct Answer: B**

**Explanation**
Since the primary VPC is **already directly peered** with the other accounts' VPCs, a single Client VPN endpoint in the primary account, with appropriate routing, can reach every peered VPC through the existing connections. Since endpoints incur hourly cost, having just one is the cheapest.

**Why the other choices are wrong**
- A: Separate endpoints per account are unnecessary extra cost when existing peering already provides connectivity.
- C: Adding a Transit Gateway is unnecessary when direct peering already connects everything (needed only for actual transitive multi-hop routing).
- D: Chaining the Client VPN endpoint through the Site-to-Site VPN is an unnecessary detour — Site-to-Site VPN serves the physical office connection, a different purpose.

> 💡 **Exam tip**: When accounts' VPCs are **already directly peered**, a single Client VPN endpoint in a hub VPC with proper routing reaches all peered VPCs. Add a Transit Gateway only when genuine transitive routing is required.

## QUESTION 100

**Question**: An app's response times are inconsistent and error rates have significantly increased, caused by calls to a third-party service. The app currently invokes Lambda functions **directly and synchronously** to call the third-party service. Decouple the calls and ensure they **all eventually complete.**

**Choices**
- A. **Use an Amazon SQS queue to store events and invoke the Lambda function.**
- B. Use an AWS Step Functions state machine to deliver events to the Lambda function.
- C. Use an Amazon EventBridge rule to deliver events to the Lambda function.
- D. Use an Amazon SNS topic to store events and invoke the Lambda function.

**Correct Answer: A**

**Explanation**
Inserting **SQS** between the trigger and the Lambda function calling the third party durably stores events and lets Lambda process them using SQS's built-in retry/redrive mechanisms — guaranteeing eventual completion even during transient third-party issues, without the caller waiting synchronously.

**Why the other choices are wrong**
- B: Step Functions is primarily for multi-step workflow orchestration — SQS more directly fits the simple "durable decoupling" need here.
- C: EventBridge is useful for pattern-based routing, but doesn't provide the same durable, retry-until-success queue semantics as SQS.
- D: **SNS is a pub/sub notification service** — it doesn't retain and retry failed deliveries the way SQS's durable queue does.

> 💡 **Exam tip**: To decouple a synchronous call to an unreliable/slow third party and guarantee **eventual completion**, insert an **Amazon SQS queue** between the trigger and the calling Lambda function — different purpose from SNS (fan-out, no retry-until-success) or EventBridge (routing).
