## Q1. 확장성(Scalability) 관련 클라우드 아키텍처 원칙

성능 저하 없이 사용자, 트래픽 또는 데이터 크기의 증가를 지원할 수 있는 솔루션은 어떤 클라우드 아키텍처 원칙에 부합합니까?

- A. 평행하게 생각하라
- B. 탄력성 구현
- C. 구성 요소 분리
- D. 고장 설계

**정답: B**

✅ **B. 탄력성 구현**: 탄력성(Elasticity)은 수요 변화에 따라 리소스를 동적으로 확장하거나 축소할 수 있는 능력을 의미합니다. 사용자, 트래픽, 데이터 증가에 맞춰 성능 저하 없이 대응하는 것이 바로 탄력성의 핵심 개념입니다.

❌ **A. 평행하게 생각하라**: 병렬 처리(Think in parallel)는 여러 작업을 동시에 처리하여 효율을 높이는 원칙으로, 확장성과 관련이 있으나 이 질문의 핵심인 수요 증가 대응 능력을 직접적으로 설명하지 않습니다.

❌ **C. 구성 요소 분리**: 느슨한 결합(Loose Coupling)을 통해 개별 컴포넌트의 독립적 확장이 가능하게 하지만, 성능 저하 없이 증가를 지원하는 핵심 원칙은 탄력성입니다.

❌ **D. 고장 설계**: 장애를 예상하고 설계하는 원칙(Design for Failure)으로, 고가용성과 관련된 개념이며 확장성을 직접적으로 다루지 않습니다.

💡 **시험 꿀팁**: 탄력성(Elasticity) = 수요에 따른 자동 확장/축소 / 확장성(Scalability) = 증가하는 부하를 처리하는 능력. 두 개념 모두 중요하며 AWS Auto Scaling이 대표적인 탄력성 구현 서비스입니다.

## Q2. 온프레미스에서 AWS로 이전 시 재정적 변화

기업이 사내 데이터 센터에서 AWS 클라우드로 이전합니다. 이사 후 한 가지 재정적 차이는 무엇입니까?

- A. 가변 운영 비용(opex)에서 초기 자본 비용(capex)으로 전환
- B. 초기 자본 비용(자본 비용)에서 가변 자본 비용(자본 비용)으로 전환
- C. 초기 자본 비용(자본 비용)에서 가변 운영 비용(opex)으로 전환
- D. 초기 자본 비용(자본 비용) 제거 및 가변 운영 비용(opex) 제거

**정답: C**

✅ **C. 초기 자본 비용(CapEx)에서 가변 운영 비용(OpEx)으로 전환**: 온프레미스 환경에서는 서버, 네트워크 장비 등을 구매하는 초기 자본 비용(CapEx)이 발생하지만, AWS 클라우드로 이전하면 사용한 만큼만 지불하는 가변 운영 비용(OpEx) 모델로 전환됩니다. 이것이 AWS 클라우드 도입의 핵심 재정적 이점입니다.

❌ **A. 가변 운영 비용에서 초기 자본 비용으로 전환**: 방향이 반대입니다. AWS 클라우드로 이전하면 OpEx에서 CapEx로 가는 것이 아니라 CapEx에서 OpEx로 전환됩니다.

❌ **B. 초기 자본 비용에서 가변 자본 비용으로 전환**: 클라우드 비용은 CapEx가 아닌 OpEx(운영 비용) 범주에 속합니다. 자본 비용에서 자본 비용으로의 전환은 올바른 설명이 아닙니다.

❌ **D. 초기 자본 비용 제거 및 가변 운영 비용 제거**: 클라우드 이전 후에도 사용량에 따른 운영 비용(OpEx)은 계속 발생합니다. 두 비용이 모두 제거되는 것은 아닙니다.

💡 **시험 꿀팁**: CapEx(자본 지출) = 서버/장비 구매 등 초기 대규모 투자 (온프레미스) / OpEx(운영 지출) = 사용한 만큼 지불, 월별 청구 (클라우드). AWS 클라우드의 6대 이점 중 하나가 바로 "CapEx → OpEx 전환"입니다.

## Q3. 새로운 웹 애플리케이션의 향후 비용 예측

고객은 새로운 웹 애플리케이션을 실행할 때 향후 비용을 어떻게 예측해야 합니까?

- A. Amazon Aurora 백트랙
- B. Amazon CloudWatch 청구 경보
- C. AWS 가격 계산기
- D. AWS 비용 및 사용량 보고서

**정답: C**

✅ **C. AWS 가격 계산기**: AWS Pricing Calculator는 특정 아키텍처와 서비스 사용량을 기반으로 향후 AWS 비용을 사전에 추정하고 예측할 수 있는 무료 웹 도구입니다. 새로운 애플리케이션의 예상 비용을 계획 단계에서 파악하는 데 최적화된 도구입니다.

❌ **A. Amazon Aurora 백트랙**: Aurora Backtrack은 데이터베이스를 특정 시점으로 되돌리는 기능으로, 비용 예측과는 전혀 관계가 없습니다.

❌ **B. Amazon CloudWatch 청구 경보**: CloudWatch 청구 경보는 실제 비용이 특정 임계값을 초과할 때 알림을 보내는 기능으로, 사전 비용 예측이 아닌 사후 모니터링 도구입니다.

❌ **D. AWS 비용 및 사용량 보고서**: Cost and Usage Report는 현재 및 과거의 실제 사용량과 비용을 분석하는 도구이며, 아직 배포되지 않은 새 애플리케이션의 향후 비용을 예측하는 데는 적합하지 않습니다.

💡 **시험 꿀팁**: 비용 관련 AWS 도구 구분 — 사전 예측: AWS Pricing Calculator / 현재 모니터링: AWS Cost Explorer, CloudWatch 청구 경보 / 상세 기록: AWS Cost and Usage Report (CUR) / 예산 설정: AWS Budgets

## Q4. 전화 기술 지원을 제공하는 최소 AWS 지원 플랜

전화를 통해 기술 지원을 제공하는 MINIMUM AWS 지원 계획은 무엇입니까?

- A. 기업(Enterprise)
- B. 비즈니스(Business)
- C. 개발자(Developer)
- D. 기본(Basic)

**정답: B**

✅ **B. 비즈니스(Business)**: Business 지원 플랜부터 전화(24/7 전화), 채팅, 이메일을 통한 기술 지원이 포함됩니다. 비즈니스 플랜은 전화 지원을 제공하는 가장 낮은(최소) 등급의 지원 플랜입니다.

❌ **A. 기업(Enterprise)**: Enterprise 플랜도 전화 지원을 제공하지만, 전화 지원을 제공하는 최소 플랜이 아니라 Business 플랜이 더 낮은 등급입니다.

❌ **C. 개발자(Developer)**: Developer 플랜은 이메일을 통한 기술 지원만 제공하며, 전화 지원은 포함되지 않습니다.

❌ **D. 기본(Basic)**: Basic 플랜은 AWS 문서, 백서, 포럼에 대한 접근만 제공하며 기술 지원 담당자와의 직접 연락은 불가합니다.

💡 **시험 꿀팁**: AWS 지원 플랜 등급별 채널 — Basic: 문서/포럼만 / Developer: 이메일만 / Business: 전화+채팅+이메일 24/7 / Enterprise: Business 모든 기능 + TAM(기술 계정 관리자) 전담 배정

## Q5. AWS 공유 책임 모델 - AWS의 책임

다음 중 AWS의 책임은 무엇입니까?

- A. 클라이언트측 데이터 암호화
- B. AWS IAM(Identity and Access Management) 역할 구성
- C. Amazon EC2 하이퍼바이저 보안
- D. 사용자 비밀번호 정책 설정

**정답: C**

✅ **C. Amazon EC2 하이퍼바이저 보안**: 하이퍼바이저는 클라우드 인프라의 핵심 구성 요소로, AWS가 관리하는 물리적 인프라 계층에 속합니다. AWS는 호스트 운영체제, 가상화 계층(하이퍼바이저), 물리적 인프라 보안에 대한 완전한 책임을 집니다.

❌ **A. 클라이언트측 데이터 암호화**: 고객이 생성하고 관리하는 데이터의 암호화는 고객의 책임입니다. AWS는 서버측 암호화 옵션을 제공하지만 적용 여부는 고객이 결정합니다.

❌ **B. AWS IAM 역할 구성**: IAM 역할, 정책, 사용자 권한 설정은 고객이 관리하는 영역입니다. AWS는 IAM 서비스를 제공하지만, 그 내용을 구성하는 것은 고객의 책임입니다.

❌ **D. 사용자 비밀번호 정책 설정**: 사용자 계정의 비밀번호 정책 설정도 고객이 IAM을 통해 관리하는 영역으로, 고객의 책임에 해당합니다.

💡 **시험 꿀팁**: 공유 책임 모델 핵심 구분 — AWS 책임("클라우드의 보안"): 물리적 인프라, 하이퍼바이저, 네트워크 하드웨어, 데이터센터 / 고객 책임("클라우드에서의 보안"): 데이터, OS 패치, IAM 설정, 암호화, 방화벽 규칙

## Q6. 온디맨드 Amazon EC2 가격의 이점

주문형 Amazon EC2(Amazon Elastic Compute Cloud) 가격의 한 가지 이점은 다음과 같습니다.

- A. 시간당 비용 절감에 입찰할 수 있는 능력
- B. 사용 시간에 관계없이 일별 요금을 지불한다.
- C. 사용한 시간에 대해서만 지불.
- D. 인스턴스에 대한 선지급 및 낮은 시간당 요금 지급

**정답: C**

✅ **C. 사용한 시간에 대해서만 지불**: 온디맨드 인스턴스의 가장 큰 특징은 선약정 없이 사용한 시간(초 단위 또는 시간 단위)에 대해서만 비용을 지불하는 것입니다. 장기 계약 없이 필요할 때 바로 사용하고 중단할 수 있어 유연성이 높습니다.

❌ **A. 시간당 비용 절감에 입찰할 수 있는 능력**: 이것은 온디맨드가 아닌 스팟 인스턴스(Spot Instance)의 특징입니다. 스팟 인스턴스는 AWS의 미사용 EC2 용량을 경매 방식으로 저렴하게 이용합니다.

❌ **B. 사용 시간에 관계없이 일별 요금을 지불**: 온디맨드는 실제 사용 시간에 비례하여 청구됩니다. 사용하지 않아도 일별 요금이 발생하는 방식이 아닙니다.

❌ **D. 인스턴스에 대한 선지급 및 낮은 시간당 요금 지급**: 이것은 예약 인스턴스(Reserved Instance)의 특징입니다. 예약 인스턴스는 선납 또는 부분 선납을 하고 낮은 시간당 요금을 적용받습니다.

💡 **시험 꿀팁**: EC2 구매 옵션 비교 — 온디맨드: 사용한 만큼만 지불, 약정 없음 / 예약 인스턴스(RI): 1~3년 약정, 최대 75% 할인 / 스팟 인스턴스: 경매 방식, 최대 90% 할인, 중단 가능 / 전용 호스트(Dedicated Host): 물리적 서버 단독 사용

## Q7. IT 솔루션 신속 배포를 위한 AWS 서비스

관리자는 널리 사용되는 IT 솔루션을 신속하게 배포하고 바로 사용해야 합니다. 여기에서 지원을 받을 수 있습니까?

- A. AWS 잘 설계된 프레임워크 설명서
- B. Amazon 클라우드 전면(CloudFront)
- C. AWS CodeCommit
- D. AWS Quick Start 참조 배포

**정답: D**

✅ **D. AWS Quick Start 참조 배포**: AWS Quick Start는 AWS 전문가가 만든 자동화된 참조 배포 모음으로, 검증된 아키텍처를 CloudFormation 템플릿을 통해 수분 내에 AWS에 배포할 수 있게 해줍니다. SAP, WordPress, Microsoft Active Directory 등 다양한 솔루션을 빠르게 배포 가능합니다.

❌ **A. AWS 잘 설계된 프레임워크 설명서**: Well-Architected Framework는 아키텍처 설계 모범 사례를 제공하는 문서이지, 실제 솔루션을 자동으로 배포해주는 도구가 아닙니다.

❌ **B. Amazon 클라우드 전면(CloudFront)**: CloudFront는 콘텐츠 전송 네트워크(CDN) 서비스로, IT 솔루션의 빠른 배포와는 관련이 없습니다.

❌ **C. AWS CodeCommit**: CodeCommit은 소스 코드를 저장하는 완전 관리형 Git 리포지토리 서비스입니다. 솔루션 배포 도구가 아닌 코드 저장소입니다.

💡 **시험 꿀팁**: AWS Quick Start = 널리 사용되는 소프트웨어를 AWS에 빠르게 배포하기 위한 자동화된 CloudFormation 템플릿 모음. "신속하게 배포", "바로 사용", "검증된 아키텍처" 등의 키워드가 나오면 Quick Start를 떠올리세요.

## Q8. AWS 서버리스 플랫폼에 포함되는 서비스

다음 중 AWS 서버리스 플랫폼의 범주에 포함되는 서비스는 무엇입니까?

- A. Amazon EMR
- B. 탄성 부하 분산(Elastic Load Balancing)
- C. AWS 람다(Lambda)
- D. AWS Mobile Hub

**정답: C**

✅ **C. AWS 람다(Lambda)**: AWS Lambda는 대표적인 서버리스 컴퓨팅 서비스로, 서버를 직접 관리하지 않고 코드를 실행할 수 있습니다. 이벤트 기반으로 자동 실행되며, 사용한 컴퓨팅 시간에 대해서만 비용이 청구됩니다.

❌ **A. Amazon EMR**: EMR(Elastic MapReduce)은 빅데이터 처리를 위한 관리형 클러스터 서비스입니다. EC2 인스턴스 기반으로 동작하므로 서버리스가 아닙니다.

❌ **B. 탄성 부하 분산(ELB)**: Elastic Load Balancing은 트래픽을 여러 EC2 인스턴스에 분산하는 서비스입니다. 완전 관리형이지만 서버리스 플랫폼 범주에는 포함되지 않습니다.

❌ **D. AWS Mobile Hub**: Mobile Hub는 모바일 앱 개발을 위한 구성 및 관리 콘솔이며, 서버리스 컴퓨팅 서비스가 아닙니다.

💡 **시험 꿀팁**: 주요 AWS 서버리스 서비스 목록 — 컴퓨팅: AWS Lambda / 데이터베이스: Amazon DynamoDB / 저장소: Amazon S3 / API: Amazon API Gateway / 큐/메시지: Amazon SQS, Amazon SNS / 분석: Amazon Athena / 워크플로: AWS Step Functions

## Q9. AWS 서버리스 플랫폼 서비스 조합

AWS 서버 없는 플랫폼의 일부인 서비스는 무엇입니까?

- A. Amazon EC2, Amazon S3, Amazon Athena
- B. Amazon Kinesis, Amazon SQS, Amazon EMR
- C. AWS 스텝 기능, Amazon DynamoDB, Amazon SNS
- D. Amazon Athena, Amazon Cognito, Amazon EC2

**정답: C**

✅ **C. AWS 스텝 기능(Step Functions), Amazon DynamoDB, Amazon SNS**: 세 서비스 모두 완전 서버리스입니다. Step Functions는 서버리스 워크플로 오케스트레이션, DynamoDB는 서버리스 NoSQL 데이터베이스, SNS는 서버리스 알림 서비스로 모두 서버 관리 없이 사용 가능합니다.

❌ **A. Amazon EC2, Amazon S3, Amazon Athena**: EC2는 가상 서버 서비스로 서버리스가 아닙니다. S3는 객체 스토리지로 서버리스에 가깝지만 EC2가 포함되므로 조합 전체가 서버리스라고 할 수 없습니다.

❌ **B. Amazon Kinesis, Amazon SQS, Amazon EMR**: EMR은 EC2 클러스터 기반의 빅데이터 서비스로 서버리스가 아닙니다.

❌ **D. Amazon Athena, Amazon Cognito, Amazon EC2**: Amazon EC2가 포함되어 있어 서버리스 조합이 아닙니다. Athena와 Cognito는 서버리스이지만 EC2가 포함된 그룹은 서버리스가 아닙니다.

💡 **시험 꿀팁**: EC2, EMR, RDS, Redshift(프로비저닝 모드)는 서버리스가 아닙니다. "서버리스" 키워드가 보이면 Lambda, DynamoDB, S3, API Gateway, SQS, SNS, Step Functions, Athena, Fargate를 우선 떠올리세요.

## Q10. AWS 공유 책임 모델 - AWS의 유일한 책임

AWS 공유 책임 모델에 따르면 AWS의 유일한 책임은 무엇입니까?

- A. 애플리케이션 보안
- B. 가장자리 위치(Edge Location) 관리
- C. 패치 관리
- D. 고객측 데이터

**정답: B**

✅ **B. 가장자리 위치(Edge Location) 관리**: Edge Location은 AWS가 소유하고 운영하는 물리적 인프라의 일부입니다. 데이터센터, 가용 영역, 리전, 엣지 로케이션 등 물리적 인프라의 관리는 전적으로 AWS의 책임입니다.

❌ **A. 애플리케이션 보안**: 고객이 AWS에서 실행하는 애플리케이션의 보안(코드 취약점, 애플리케이션 로직 등)은 고객의 책임입니다.

❌ **C. 패치 관리**: 패치 관리는 공유 책임 영역입니다. AWS는 인프라(호스트 OS, 하이퍼바이저) 패치를 담당하고, 고객은 자신이 관리하는 EC2 게스트 OS와 애플리케이션 패치를 담당합니다.

❌ **D. 고객측 데이터**: 고객이 AWS에 저장하는 데이터는 전적으로 고객의 소유이며, 데이터 분류, 암호화, 접근 제어 등은 고객의 책임입니다.

💡 **시험 꿀팁**: AWS 단독 책임 영역 = 물리적 인프라 전체 (데이터센터, 서버 하드웨어, 네트워크 장비, 가용 영역, 리전, 엣지 로케이션). "물리적"이라는 단어가 보이면 AWS의 책임입니다.

## Q11. 권한 집합을 여러 사용자와 연결하는 IAM 기능

사용 권한 집합을 여러 사용자와 연결하는 데 사용되는 AWS IAM 기능은 무엇입니까?

- A. 멀티 팩터 인증(MFA)
- B. 그룹(Group)
- C. 암호 정책
- D. 액세스 키

**정답: B**

✅ **B. 그룹(Group)**: IAM 그룹은 여러 IAM 사용자의 집합으로, 그룹에 정책(권한)을 연결하면 그룹 내 모든 사용자에게 동일한 권한이 자동으로 적용됩니다. 다수의 사용자에게 동일한 권한을 효율적으로 관리하는 핵심 기능입니다.

❌ **A. 멀티 팩터 인증(MFA)**: MFA는 사용자 계정 보안을 강화하는 인증 방법으로, 권한 집합을 연결하는 기능이 아닙니다.

❌ **C. 암호 정책**: 암호 정책은 계정의 비밀번호 복잡도, 길이, 만료 기간 등을 설정하는 기능으로, 권한 부여와는 관련이 없습니다.

❌ **D. 액세스 키**: 액세스 키는 AWS CLI 또는 SDK를 사용할 때 프로그래밍 방식으로 인증하기 위한 자격 증명(Access Key ID + Secret Access Key)이며, 권한 집합을 여러 사용자에게 연결하는 기능이 아닙니다.

💡 **시험 꿀팁**: IAM 주요 개념 — 사용자(User): 개인 계정 / 그룹(Group): 사용자 집합, 그룹에 정책 연결 / 역할(Role): 임시 권한 부여, EC2/Lambda 등에 할당 / 정책(Policy): 권한 정의 문서(JSON). "여러 사용자에게 동일한 권한" = IAM 그룹

## Q12. AWS 클라우드의 이점 (두 가지 선택)

다음 중 AWS 클라우드의 이점은 무엇입니까? (두 가지를 선택하십시오.)

- A. 무제한 가동 시간
- B. 탄력성
- C. 민첩성
- D. 코로케이션
- E. 자본 비용

**정답: B, C**

✅ **B. 탄력성**: 수요에 따라 리소스를 자동으로 확장하거나 축소하는 능력은 AWS 클라우드의 핵심 이점 중 하나입니다. 과도한 용량 프로비저닝 없이 비용을 최적화할 수 있습니다.

✅ **C. 민첩성**: AWS 클라우드는 새로운 리소스를 빠르게 프로비저닝하고 실험을 저렴하게 수행할 수 있어 비즈니스 혁신 속도를 높이는 민첩성을 제공합니다.

❌ **A. 무제한 가동 시간**: AWS는 높은 가용성을 제공하지만 "무제한(unlimited)" 가동 시간을 보장하지는 않습니다. SLA에 따른 특정 수준의 가용성을 보장합니다.

❌ **D. 코로케이션**: 코로케이션(Colocation)은 기업이 자체 서버를 데이터센터 시설에 임대 설치하는 방식으로, 온프레미스 개념에 가깝습니다. AWS 클라우드의 이점이 아닙니다.

❌ **E. 자본 비용**: AWS로 이전하면 자본 비용(CapEx)이 줄어드는 것이 이점이지, 자본 비용 자체가 이점은 아닙니다. 오히려 AWS는 OpEx 모델로의 전환을 이점으로 제공합니다.

💡 **시험 꿀팁**: AWS 클라우드의 6대 이점(Six Advantages) — 1) CapEx → OpEx 전환 2) 규모의 경제로 인한 비용 절감 3) 용량 추정 불필요 4) 속도와 민첩성 향상 5) 데이터센터 운영 비용 절감 6) 글로벌 확장 용이성

## Q13. AWS 콘솔에 대한 SSO(Single Sign-On) 활성화

다음 중 고객이 AWS 콘솔에 대한 SSO(Single Sign-On)를 활성화하기 위해 사용할 수 있는 것은 무엇입니까?

- A. Amazon Connect
- B. AWS 디렉터리 서비스(Directory Service)
- C. Amazon 핀포인트(Pinpoint)
- D. 아마존 인식(Amazon Rekognition)

**정답: B**

✅ **B. AWS 디렉터리 서비스(Directory Service)**: AWS Directory Service는 Microsoft Active Directory와 호환되는 디렉터리 서비스를 제공하며, 기존 온프레미스 Active Directory와 연동하여 AWS 콘솔 및 AWS 서비스에 대한 SSO를 구현할 수 있습니다. AWS IAM Identity Center(구 AWS SSO)와 함께 사용됩니다.

❌ **A. Amazon Connect**: Amazon Connect는 클라우드 기반 콜센터(고객 상담) 서비스로, 인증이나 SSO와는 관련이 없습니다.

❌ **C. Amazon 핀포인트(Pinpoint)**: Amazon Pinpoint는 마케팅 커뮤니케이션 및 분석 서비스로, 이메일, SMS, 푸시 알림 등을 전송하는 데 사용됩니다. SSO와는 무관합니다.

❌ **D. 아마존 인식(Amazon Rekognition)**: Amazon Rekognition은 이미지 및 동영상 분석 AI 서비스로, 얼굴 인식, 객체 감지 등의 기능을 제공합니다. SSO 기능과는 관련이 없습니다.

💡 **시험 꿀팁**: AWS의 인증/디렉터리 관련 서비스 — AWS Directory Service: Active Directory 관리 및 SSO 연동 / AWS IAM Identity Center(구 AWS SSO): 중앙 집중식 SSO 관리 / Amazon Cognito: 웹/모바일 앱의 사용자 인증 및 관리

## Q14. AWS 리전 내 격리된 위치 (가용 영역)

AWS 영역 내에서 대기 시간이 짧은 네트워크로 연결된 여러 개의 격리된 위치는 무엇입니까?

- A. AWS Direct Connects
- B. Amazon VPC
- C. 가장자리 위치(Edge Location)
- D. 가용성 영역(Availability Zone)

**정답: D**

✅ **D. 가용성 영역(Availability Zone)**: 가용 영역은 AWS 리전 내에 있는 물리적으로 분리된 데이터센터 그룹입니다. 각 리전에는 여러 개의 가용 영역이 있으며, 이들은 저지연 전용 네트워크로 연결되어 있어 고가용성 아키텍처를 구성하는 데 활용됩니다.

❌ **A. AWS Direct Connects**: Direct Connect는 온프레미스 데이터센터와 AWS 사이를 전용 회선으로 연결하는 서비스로, AWS 인프라의 위치 단위가 아닙니다.

❌ **B. Amazon VPC**: VPC(Virtual Private Cloud)는 AWS 내에서 논리적으로 격리된 가상 네트워크 공간이며, 물리적 위치 개념이 아닙니다.

❌ **C. 가장자리 위치(Edge Location)**: 엣지 로케이션은 CloudFront CDN 콘텐츠 전송을 위한 글로벌 캐시 서버 위치이며, 리전 내 격리된 위치가 아닙니다.

💡 **시험 꿀팁**: AWS 인프라 계층 구조 — 글로벌 (Global) > 리전 (Region, 예: ap-northeast-2) > 가용 영역 (AZ, 예: ap-northeast-2a/2b/2c) > 데이터센터. 엣지 로케이션(Edge Location)은 이 계층과 별도로 콘텐츠 캐싱용으로 전 세계에 분산 배치됩니다.

## Q15. AWS Compliance 프로그램이 고객에게 제공하는 이점 (두 가지 선택)

다음 중 AWS Compliance 프로그램이 AWS 고객에게 제공하는 이점은 무엇입니까? (두 가지 선택)

- A. 호스팅된 워크로드가 지원되는 컴플라이언스 프레임워크의 제어를 자동으로 준수하는지 확인합니다.
- B. AWS는 공통 컴플라이언스 프레임워크 문서의 유지관리를 담당합니다.
- C. AWS가 물리적 보안 및 데이터 보호를 유지하고 있음을 고객에게 보장합니다.
- D. 다른 클라우드 공급자가 사용하고 있는 컴플라이언스 프레임워크의 사용을 보장합니다.
- E. 고객 워크로드와 관련이 있는 새로운 규정 준수 프레임워크를 채택합니다.

**정답: B, C**

✅ **B. AWS는 공통 컴플라이언스 프레임워크 문서의 유지관리를 담당합니다**: AWS는 ISO 27001, PCI DSS, HIPAA 등 다양한 컴플라이언스 프레임워크에 대한 인증서, 감사 보고서, 문서를 직접 유지 관리하고 AWS Artifact를 통해 고객에게 제공합니다.

✅ **C. AWS가 물리적 보안 및 데이터 보호를 유지하고 있음을 고객에게 보장합니다**: AWS Compliance 프로그램은 AWS가 물리적 데이터센터 보안, 인프라 보안 등을 규정에 맞게 관리하고 있음을 제3자 감사를 통해 보장하여 고객이 이를 상속받을 수 있도록 합니다.

❌ **A. 워크로드의 자동 준수 확인**: AWS Compliance 프로그램이 고객 워크로드의 컴플라이언스 준수를 자동으로 확인해 주지는 않습니다. 이는 AWS Config, AWS Security Hub 등의 도구를 활용하여 고객이 직접 확인해야 합니다.

❌ **D. 다른 클라우드 공급자의 프레임워크 보장**: AWS Compliance 프로그램은 AWS 자체의 컴플라이언스를 다루며, 타 클라우드 공급자의 프레임워크 사용을 보장하지 않습니다.

❌ **E. 새로운 규정 준수 프레임워크 채택**: AWS가 새로운 프레임워크를 지속적으로 추가하기는 하지만, 고객 워크로드와 관련된 모든 새 프레임워크를 채택하는 것을 보장하지는 않습니다.

💡 **시험 꿀팁**: AWS Compliance 프로그램의 핵심 = 제3자 독립 감사를 통해 AWS 인프라의 보안/컴플라이언스를 검증하고, 그 결과를 고객이 AWS Artifact를 통해 다운로드하여 자신의 컴플라이언스 활동에 활용 가능. 공유 책임 모델에서 AWS 영역의 컴플라이언스는 고객이 상속(Inherit)받습니다.

다음 중 AWS 컴플라이언스 보고서에 대한 온디맨드 액세스를 제공하는 서비스는 무엇입니까?

💡 **시험 꿀팁**: AWS Artifact = AWS 공식 컴플라이언스 문서 저장소. "감사 보고서", "ISO 인증", "PCI DSS", "SOC 보고서", "컴플라이언스 문서 다운로드" 키워드 = AWS Artifact. GuardDuty = 보안 위협 탐지 (전혀 다른 서비스!)

## Q17. 공유 책임 모델 - 고객이 AWS에서 완전히 상속하는 운영 제어

AWS 공유 책임 모델의 일부로, 다음 중 사용자가 AWS에서 완전히 상속하는 운영 제어는 무엇입니까?

- A. 데이터 센터의 보안 관리
- B. 패치 관리
- C. 구성 관리
- D. 사용자 및 액세스 관리

**정답: A**

✅ **A. 데이터 센터의 보안 관리**: 물리적 데이터센터의 보안(출입 통제, 감시, 환경 제어 등)은 전적으로 AWS가 책임지는 영역이며, 고객은 이 책임을 완전히 AWS에 위임(상속)합니다. 고객은 데이터센터에 접근할 필요도 없고 관리할 수도 없습니다.

❌ **B. 패치 관리**: 패치 관리는 공유 책임 영역입니다. AWS는 인프라 패치를 담당하고, 고객은 게스트 OS 및 애플리케이션 패치를 담당합니다. 완전히 상속되는 영역이 아닙니다.

❌ **C. 구성 관리**: 구성 관리도 공유 책임 영역입니다. AWS는 인프라 구성을 관리하고, 고객은 자신의 애플리케이션과 서비스 구성을 책임집니다.

❌ **D. 사용자 및 액세스 관리**: IAM을 통한 사용자 생성, 권한 부여, 역할 관리 등은 고객이 직접 수행해야 하는 고객의 책임 영역입니다.

💡 **시험 꿀팁**: "완전히 상속" = AWS 단독 책임 = 물리적 인프라 관련 모든 것 (데이터센터 보안, 하드웨어, 전력, 냉각 등). 반대로 데이터, IAM, OS, 네트워크 설정, 암호화 등은 고객 책임. 패치/구성 관리는 공유 영역임을 주의!

## Q18. AWS 클라우드와 온프레미스 TCO 비교 시 고려 비용 (두 가지 선택)

AWS 클라우드를 사내 총 소유 비용과 비교할 때 고려해야 하는 비용은 무엇입니까? (두 개를 선택합니다.)

- A. 소프트웨어 개발
- B. 프로젝트 관리
- C. 스토리지 하드웨어
- D. 물리적 서버
- E. 안티바이러스 소프트웨어 라이센스

**정답: C, D**

✅ **C. 스토리지 하드웨어**: 온프레미스 환경에서는 SAN, NAS 등의 스토리지 장비를 직접 구매하고 유지보수해야 하지만, AWS 클라우드에서는 S3, EBS 등을 통해 스토리지를 종량제로 사용할 수 있습니다. TCO 비교에서 핵심적인 하드웨어 비용입니다.

✅ **D. 물리적 서버**: 온프레미스에서는 서버를 직접 구매, 설치, 유지보수, 교체해야 하는 비용이 발생하지만, AWS에서는 EC2를 통해 가상 서버를 온디맨드로 사용할 수 있습니다. TCO 비교의 가장 중요한 항목입니다.

❌ **A. 소프트웨어 개발**: 소프트웨어 개발 비용은 온프레미스와 클라우드 환경 모두에서 발생하며, 인프라 이전과 직접적인 관련이 없는 비용입니다.

❌ **B. 프로젝트 관리**: 프로젝트 관리 비용도 양쪽 환경 모두에 적용되는 비용이므로, TCO 비교에서 차별화되는 항목이 아닙니다.

❌ **E. 안티바이러스 소프트웨어 라이센스**: 안티바이러스 소프트웨어는 클라우드와 온프레미스 모두에서 필요할 수 있으며, 인프라 자체의 TCO 비교 항목으로는 적합하지 않습니다.

💡 **시험 꿀팁**: 온프레미스 vs AWS TCO 비교 시 핵심 항목 = 하드웨어(서버, 스토리지, 네트워크 장비), 데이터센터 임대료/전력/냉각, 하드웨어 유지보수 인력, 구매·조달 비용. AWS TCO 계산기(AWS Pricing Calculator)를 활용해 비교할 수 있습니다.

## Q19. 공유 책임 모델 - 고객의 책임 (두 가지 선택)

공유책임모형에서 다음 중 고객의 책임은 무엇입니까? (두 개를 선택합니다.)

- A. 기본 Amazon EC2 하드웨어 유지 관리
- B. VPC 네트워크 액세스 제어 목록(NACL) 관리
- C. 전송 중 및 유휴 상태의 데이터 암호화
- D. 장애가 발생한 하드 디스크 드라이브 교체
- E. 서로 다른 가용성 영역에 하드웨어 구축

**정답: B, C**

✅ **B. VPC 네트워크 액세스 제어 목록(NACL) 관리**: VPC 설정, 서브넷 구성, 보안 그룹, 네트워크 ACL 등 가상 네트워크 내의 트래픽 제어는 고객이 직접 구성하고 관리해야 하는 고객의 책임입니다.

✅ **C. 전송 중 및 유휴 상태의 데이터 암호화**: 데이터를 어떻게 암호화할지(TLS, KMS, 클라이언트 측 암호화 등)는 고객이 결정하고 구현해야 합니다. AWS는 암호화 도구를 제공하지만, 사용 여부는 고객의 책임입니다.

❌ **A. 기본 Amazon EC2 하드웨어 유지 관리**: EC2를 실행하는 물리적 서버 하드웨어 유지보수는 AWS의 책임입니다. 고객은 물리적 하드웨어에 접근할 수 없습니다.

❌ **D. 장애가 발생한 하드 디스크 드라이브 교체**: 물리적 스토리지 장치의 교체는 AWS 데이터센터 운영 팀의 책임입니다.

❌ **E. 서로 다른 가용성 영역에 하드웨어 구축**: 가용 영역의 물리적 인프라 구축 및 관리는 AWS의 책임입니다. 고객은 어느 AZ에 리소스를 배포할지 선택할 수 있지만, 하드웨어를 직접 구축하지는 않습니다.

💡 **시험 꿀팁**: 고객 책임 핵심 키워드 — 데이터 암호화, IAM/권한 관리, OS 패치(EC2), 보안 그룹/NACL 설정, 애플리케이션 보안, VPC 구성. "물리적(physical)", "하드웨어(hardware)", "교체", "구축"이 들어간 선택지는 보통 AWS의 책임입니다.

## Q20. AWS 탄력성 개념을 나타내는 시나리오 (두 가지 선택)

AWS의 탄력성 개념을 나타내는 시나리오는 무엇입니까? (두 가지 선택)

- A. 트래픽에 따라 Amazon EC2 인스턴스 수 확장
- B. 비즈니스 요구 변화에 따라 Amazon RDS 인스턴스 크기 조정
- C. 사용량이 적은 Amazon EC2 인스턴스로 트래픽을 자동으로 전달합니다.
- D. AWS 컴플라이언스 문서를 사용하여 컴플라이언스 프로세스 가속화
- E. 코드를 사용하여 환경을 만들고 관리할 수 있는 능력 보유

**정답: A, B**

✅ **A. 트래픽에 따라 Amazon EC2 인스턴스 수 확장**: 트래픽 증가 시 EC2 인스턴스를 추가하고 감소 시 줄이는 수평적 확장(Scale-Out/Scale-In)은 탄력성의 대표적인 예입니다. Auto Scaling 그룹을 통해 자동화할 수 있습니다.

✅ **B. 비즈니스 요구 변화에 따라 Amazon RDS 인스턴스 크기 조정**: 수요 변화에 맞춰 RDS 인스턴스의 크기(vCPU, 메모리)를 변경하는 수직적 확장(Scale-Up/Scale-Down)도 탄력성의 개념에 해당합니다.

❌ **C. 사용량이 적은 EC2 인스턴스로 트래픽을 자동으로 전달**: 이는 Elastic Load Balancing의 로드 밸런싱 기능을 설명하는 것으로, 탄력성이 아닌 부하 분산 개념입니다.

❌ **D. AWS 컴플라이언스 문서 활용**: 컴플라이언스 프로세스 가속화는 탄력성과 전혀 관련이 없으며, AWS Compliance 프로그램의 이점을 설명하는 것입니다.

❌ **E. 코드를 사용하여 환경을 만들고 관리**: 이는 Infrastructure as Code(IaC) 개념으로, 민첩성(Agility)과 자동화에 관한 것이며 탄력성과는 다른 개념입니다.

💡 **시험 꿀팁**: 탄력성(Elasticity) = 수요에 맞게 리소스를 동적으로 늘리거나 줄이는 능력. Scale-Out(인스턴스 수 증가) + Scale-In(인스턴스 수 감소) = 탄력성. Scale-Up(인스턴스 크기 업그레이드) + Scale-Down(인스턴스 크기 다운그레이드)도 탄력성에 포함. AWS Auto Scaling이 핵심 서비스입니다.
