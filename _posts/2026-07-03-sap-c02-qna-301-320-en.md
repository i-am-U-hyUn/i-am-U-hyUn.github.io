## QUESTION 301

**Question**: A large enterprise wants to migrate thousands of on-premises servers to AWS, but has **no baseline data at all** on which servers communicate with which, or each server's CPU/memory utilization. Some servers are also difficult to install agents on. What's the first step in building a migration plan?

**Choices**
- A. Immediately install AWS Application Migration Service (MGN) agents on all servers and start migrating right away (starting migration without first understanding the current state is risky, and ignores the constraint that some servers are hard to install agents on).
- B. **Use AWS Application Discovery Service to collect server utilization and network dependency data — agent-based for servers where an agent can be installed, and agentless (for VMware environments) where it can't.**
- C. Send a manual survey to each team to gather server purpose and specs (manual surveys at a scale of thousands are inaccurate and slow, and hard quantitative data like actual network dependencies is difficult to obtain this way).
- D. Use Trusted Advisor to check on-premises server utilization (Trusted Advisor is a checkup tool for resources within an AWS account and doesn't cover on-premises servers — a conceptual error).

**Correct Answer: B**

**Explanation**
**AWS Application Discovery Service** is a tool for the pre-planning stage of a large-scale migration, collecting server utilization (CPU/memory/disk) and inter-process **network dependencies**. Servers that can have an agent installed use **agent-based discovery**, while VMware-environment servers where an agent is hard to install can use **agentless discovery** — flexibly adapting to server characteristics and enabling a data-driven migration wave plan.

**Why the other choices are wrong**
- A: Starting migration without understanding the current state risks missed dependencies, downtime, and other major risks.
- C: Manual surveys can't provide accurate, quantitative utilization/dependency data at a large-scale environment.
- D: Trusted Advisor checks resources within an AWS account and is unrelated to on-premises infrastructure.

> 💡 **Exam tip**: To **collect server utilization and network dependency data** before a large-scale migration, **AWS Application Discovery Service** (combining agent-based and agentless) is the standard answer.

## QUESTION 302

**Question**: A mission-critical application deployed across multiple Regions has a DR plan, but they need a reliable way to **continuously verify in advance** that the failover procedure will actually work during a real outage, and to safely switch traffic by assessing each Region's status during an actual failure. What's the solution?

**Choices**
- A. Detect Regional failure using only CloudWatch alarms, with an operator manually changing Route 53 records (manual intervention is slow and risks human error, and provides no way to continuously verify failover readiness in advance).
- B. **Use Route 53 Application Recovery Controller (ARC) to configure routing controls that determine each Region's status, continuously verify each Region's readiness to accept failover traffic via readiness checks, and use safety rules to prevent the mistake of disabling all Regions at once.**
- C. Set up only independent Route 53 health checks per Region with no other measures (simple health checks alone can't verify multi-dimensional "failover readiness" like resource capacity, and there's no safeguard against dangerous routing changes like simultaneous outages).
- D. Use AWS Fault Injection Simulator (FIS) to randomly disrupt actual production traffic on an ongoing basis (continuously injecting uncontrolled random failures into actual production carries high uncontrolled risk and doesn't fit ARC's purpose of safely verifying failover readiness).

**Correct Answer: B**

**Explanation**
**Route 53 Application Recovery Controller (ARC)** provides fine-grained traffic-switching control via routing controls, and continuously monitors whether each Region/resource is actually ready to receive traffic (capacity, configuration match, etc.) via **readiness checks**. It also uses **safety rules** to categorically prevent dangerous operational mistakes like disabling all Regions simultaneously. This is the standard service for reinforcing DR failover reliability both before and during an event.

**Why the other choices are wrong**
- A: Manual intervention is inferior in both speed and accuracy, and provides no advance readiness verification.
- C: Simple health checks don't comprehensively verify capacity/configuration the way ARC's readiness check does, and offer no safety rules.
- D: Continuously injecting uncontrolled random failures into actual production isn't a safe verification method (chaos engineering should be a controlled experiment).

> 💡 **Exam tip**: To **continuously verify multi-Region DR failover readiness** and **prevent dangerous routing mistakes**, **Route 53 Application Recovery Controller (ARC)** (routing controls + readiness checks + safety rules) is the standard answer.

## QUESTION 303

**Question**: A company wants to lift-and-shift an NFS/SMB file workload currently running on on-premises NetApp storage to AWS. They want to keep using NetApp ONTAP-specific features they already rely on — **deduplication, compression, snapshots, and clones** — in the cloud too. What's the solution?

**Choices**
- A. Migrate to Amazon EFS (EFS supports NFS but not SMB, and doesn't offer the same ONTAP-specific feature set like deduplication/cloning).
- B. **Migrate to Amazon FSx for NetApp ONTAP, supporting both NFS and SMB while keeping the existing ONTAP management tools and features (deduplication, compression, snapshots, clones, etc.) intact.**
- C. Migrate to Amazon FSx for Windows File Server (supports SMB but doesn't natively support NFS, and doesn't provide the ONTAP-specific feature set either).
- D. Store files as objects in S3 and rewrite the application to use the S3 API (rewriting an existing application that uses file-system protocols [NFS/SMB] to use an object-storage API contradicts the "lift-and-shift" goal significantly).

**Correct Answer: B**

**Explanation**
**Amazon FSx for NetApp ONTAP** is a managed service that supports **both NFS and SMB protocols**, and provides the same ONTAP features used on-premises — **deduplication and compression** for storage efficiency, and **snapshots and clones** for data protection — in the cloud as well. It's best suited to lift-and-shift an existing ONTAP-based workload with no application changes.

**Why the other choices are wrong**
- A: EFS is NFS-only, doesn't support SMB, and its feature set differs from ONTAP's.
- C: FSx for Windows File Server is SMB-centric with limited NFS support, and differs from ONTAP's feature set.
- D: Switching to object storage requires an application rewrite, contradicting the lift-and-shift goal.

> 💡 **Exam tip**: To move an on-premises **NetApp ONTAP-based NFS/SMB workload** to the cloud as-is with no application changes, **Amazon FSx for NetApp ONTAP** is the standard answer.

## QUESTION 304

**Question**: They want to apply **mutual TLS (mTLS)** between microservices so services verify each other's identity via certificates. The certificates are for internal service use only and don't need to be registered with a public CA. How do you automate certificate issuance and rotation?

**Choices**
- A. Each service team generates its own self-signed certificates via OpenSSL and manually deploys/renews them (manually generating/deploying/renewing certificates across hundreds of services carries very high risk of outages from operational errors and expirations).
- B. **Build an internal-only CA hierarchy with AWS Certificate Manager Private Certificate Authority (ACM Private CA), integrated with ACM to issue private certificates services need, leveraging automatic renewal.**
- C. Individually purchase certificates for every internal service from a public CA (e.g., a commercial SSL certificate issuer) (buying public certificates for purely internal communication is unnecessary cost, and issuing public certificates for internal service names may itself be restricted).
- D. Only store self-generated certificate files in AWS Secrets Manager and implement issuance/rotation yourself via scripts (Secrets Manager is useful for storage/distribution, but certificate issuance itself and building an automated rotation pipeline is more standard and integrated via ACM Private CA).

**Correct Answer: B**

**Explanation**
**ACM Private CA** lets you run an organization's internal-only certificate authority (CA) hierarchy in a managed way, and integrates with **AWS Certificate Manager (ACM)** to issue private TLS certificates services need with **automatic renewal**. This lets you manage the issuance/distribution/rotation needed for mTLS between microservices securely and in an automated fashion.

**Why the other choices are wrong**
- A: Manually managing self-signed certificates carries very high risk of outages from expiration/errors at a large microservices scale.
- C: Using public CA certificates for purely internal communication is unnecessary cost, and issuing public certificates for internal domain names isn't practical either.
- D: Secrets Manager is useful as a store, but certificate "issuance" itself and CA hierarchy management is ACM Private CA's role.

> 💡 **Exam tip**: For **internal-only certificate issuance/automatic rotation for mTLS** between microservices, **ACM Private CA + ACM integration** is the standard answer.

## QUESTION 305

**Question**: A DynamoDB table experiences a **hot partition** because traffic concentrates on a specific partition key value (e.g., a popular product ID), causing frequent throttling. Even though the table's overall provisioned capacity is sufficient, only that specific partition becomes a bottleneck. How do you fix this?

**Choices**
- A. Significantly increase the table's overall provisioned throughput (RCU/WCU) (increasing overall capacity doesn't solve the root problem that access to a specific partition key is physically concentrated on one [or a few] partitions — it only increases cost).
- B. **Improve the partition key design — append a random suffix (random sharding/write sharding) to frequently accessed key values, or redesign to a composite partition key (e.g., productID#shardNumber) that evenly distributes the access pattern.**
- C. Only add DynamoDB Accelerator (DAX) for read caching (DAX helps read performance, but doesn't solve hot partitions caused by write traffic or the underlying partition key design problem).
- D. Switch the table to on-demand mode (on-demand mode also internally distributes throughput per partition, so extreme traffic concentration on a specific partition key can still cause throttling at that partition — the root fix is improving key design).

**Correct Answer: B**

**Explanation**
Because DynamoDB throughput is physically distributed per partition, traffic concentrated on a specific partition key value creates a bottleneck **at just that partition** even when overall table capacity is sufficient. Fundamentally fixing this requires **improving the partition key design itself** — the classic technique is write sharding, appending a **random/cyclic suffix to popular key values to spread writes across multiple physical partitions**.

**Why the other choices are wrong**
- A: Increasing overall table capacity doesn't solve the root cause — physical concentration of access on a specific partition key.
- C: DAX is effective for read caching but doesn't solve a write-heavy hot-partition problem or the underlying key design issue.
- D: On-demand mode also follows the internal principle of per-partition throughput distribution, so it doesn't itself resolve extreme key skew.

> 💡 **Exam tip**: DynamoDB **hot partitions (traffic concentrated on a specific key)** are fundamentally solved not by increasing capacity but by **improving partition key design (write sharding via random/cyclic suffixes)** — the standard answer.

## QUESTION 306

**Question**: Hundreds of S3 buckets are scattered across multiple accounts organization-wide, and they want organization-wide visibility into **storage usage patterns and cost-optimization opportunities** — which buckets drive the most cost, how much old-version or incomplete multipart-upload data has accumulated, etc. What's the solution?

**Choices**
- A. Individually check bucket metrics in the S3 console per account and manually compile results (manual compilation becomes more inefficient and harder to keep current as the number of accounts/buckets grows).
- B. **Configure S3 Storage Lens at the organization level to view storage usage and activity metrics across all accounts/buckets in the organization on a single dashboard, along with cost-optimization recommendations (e.g., incomplete multipart uploads, old noncurrent versions).**
- C. Use only Cost Explorer to check cost by service (Cost Explorer shows cost trends by service/account, but doesn't provide bucket-level detailed usage patterns or storage-level metrics like incomplete multipart uploads).
- D. Individually set up S3 Inventory reports per bucket and analyze manually with Athena (a viable approach, but requires configuring each bucket individually and writing/maintaining your own analysis queries — more operational burden than Storage Lens's built-in organization-wide dashboard).

**Correct Answer: B**

**Explanation**
**S3 Storage Lens** automatically aggregates storage usage and activity metrics across all of an organization's accounts and buckets into a **single dashboard**, along with **recommendations** for cost-saving opportunities (old versions, incomplete multipart uploads, inefficient storage class usage, etc.). This is the standard way to get organization-wide S3 visibility and cost-optimization insight with no custom build required.

**Why the other choices are wrong**
- A: Manual compilation becomes more inefficient and error-prone as scale grows.
- C: Cost Explorer is useful for cost trends but doesn't provide bucket-level detailed storage usage pattern metrics.
- D: Individual Inventory reports + Athena analysis are viable but reinvent the organization-wide aggregation/recommendation functionality Storage Lens provides out of the box — more operational burden.

> 💡 **Exam tip**: To get organization-wide **S3 storage usage patterns and cost-optimization opportunities on a single dashboard**, **S3 Storage Lens** (configured at the organization level) is the standard answer.

## QUESTION 307

**Question**: A containerized machine-learning inference workload requires **GPU acceleration**. The company prefers a fully managed container runtime with no server management burden wherever possible, but this workload requires a GPU. What's the correct choice for running this workload on ECS?

**Choices**
- A. Configure a GPU-supporting task definition with ECS + the Fargate launch type (the Fargate launch type doesn't support GPUs — a conceptual error. A GPU-required workload must use the EC2 launch type).
- B. **Use ECS + the EC2 launch type, building a cluster with GPU-capable instance types (e.g., the P/G families), and requesting GPU resources in the task definition.**
- C. Run the GPU workload on Fargate Spot to save cost (Fargate [including Spot] doesn't support GPUs at all, so this option isn't valid in the first place).
- D. Rebuild the inference workload as a container-image-based Lambda function (Lambda doesn't support GPU acceleration, unsuitable for a GPU-required workload).

**Correct Answer: B**

**Explanation**
Since AWS Fargate doesn't support GPU acceleration, a **GPU-required containerized workload must use ECS's EC2 launch type**. Building a cluster with GPU-capable instance types (P family, G family, etc.) and specifying the number of GPUs needed in the task definition lets the container access that GPU resource. It gives up some of the fully managed benefit, but it's the only standard way to meet the hard GPU requirement.

**Why the other choices are wrong**
- A, C: Fargate (Spot included) is a serverless container runtime that currently doesn't support GPU acceleration, so it's simply not a valid choice for a GPU-required workload.
- D: Lambda also doesn't support GPU acceleration, unsuitable for a GPU-required workload.

> 💡 **Exam tip**: When a containerized workload **requires GPU acceleration**, **ECS (or EKS) with the EC2 launch type + GPU-capable instances** is the standard answer. Remember **Fargate doesn't support GPUs**.

## QUESTION 308

**Question**: For its mission-critical on-premises physical servers, a company wants strict disaster recovery with an **RPO measured in seconds and an RTO of a few minutes** in the event of a Regional disaster. Server types vary (Windows/Linux physical servers, mixed with VMs), and the application can't be rewritten. What's the solution?

**Choices**
- A. Back up data to S3 every night and reconstruct EC2 during a failure to restore (daily backups have an RPO of up to 24 hours, entirely failing to meet the "RPO in seconds" requirement).
- B. **Use AWS Elastic Disaster Recovery (AWS DRS): install a lightweight agent on source servers for continuous block-level replication, keeping an up-to-date replica in AWS, and launch recovery instances within minutes during an actual disaster.**
- C. Use AWS Application Migration Service (MGN) as-is for disaster recovery purposes (MGN is originally optimized for one-time migration [ending after cutover], while DRS is more specialized for ongoing DR standby operation and repeated failback/drill capabilities — in fact DRS is built on the same replication engine as MGN but adds DR-specific features like recurring drills and automated failback).
- D. Back up all servers weekly as AMIs and copy them to another Region (weekly AMI backups have an RPO of up to 7 days, far off from the requirement).

**Correct Answer: B**

**Explanation**
**AWS Elastic Disaster Recovery (AWS DRS)** installs a lightweight agent on source servers (physical, virtual, other clouds — platform-agnostic) to maintain a near-real-time replica in AWS via **continuous block-level replication**. During an actual disaster, it can launch a **fully specified recovery instance within minutes** from low-cost staging resources, achieving a near-seconds RPO alongside a short RTO — AWS's standard DR service. No application code changes are needed either.

**Why the other choices are wrong**
- A, D: Periodic (daily/weekly) backup approaches incur data loss (RPO) equal to the backup interval, failing to meet a seconds-level RPO requirement.
- C: MGN is optimized for one-time migration (ending the source-server relationship after cutover); DRS provides the dedicated features (recurring recovery drills, automated failback, etc.) needed for ongoing DR operation.

> 💡 **Exam tip**: For disaster recovery of on-premises (or other-cloud) servers needing a **near-seconds RPO + short RTO**, **AWS Elastic Disaster Recovery (AWS DRS)** is the standard answer.

## QUESTION 309

**Question**: An application deployed across multiple AZs accesses a specific AWS service through a VPC interface endpoint. How should you configure the **interface endpoint's own availability** so that if a specific AZ fails, the application in that AZ can still reach the service?

**Choices**
- A. Create the interface endpoint only in a subnet in a single AZ (with the endpoint's ENI in only one AZ, a failure of that AZ leaves applications in other AZs without an access path, or forces them onto cross-AZ traffic).
- B. **When creating the interface endpoint, select subnets in multiple (ideally all AZs where the application is deployed), so an endpoint ENI is created in each AZ.**
- C. Create a separate interface endpoint (with a different service name) individually per AZ (there's no need to create separate endpoints per AZ for the same service — specifying multiple subnets on a single endpoint is the standard, and individual creation adds unnecessary management complexity and cost).
- D. Access the service's public endpoint via a NAT Gateway instead of an interface endpoint (this abandons the private-connectivity benefit of an interface endpoint and routes around it publicly — contradicting the very reason for wanting private connectivity via an interface endpoint in the first place).

**Correct Answer: B**

**Explanation**
When creating a VPC interface endpoint, **selecting subnets in multiple Availability Zones** causes AWS to create one **Elastic Network Interface (ENI)** for the endpoint in each AZ. This lets applications in each AZ access the service locally through the endpoint ENI in the same AZ, so a failure in one AZ doesn't affect access from other AZs — a highly available configuration.

**Why the other choices are wrong**
- A: An endpoint in only one AZ affects availability if that AZ fails, or forces other AZs to rely on cross-AZ traffic.
- C: There's no need to create separate endpoints per AZ for the same service — specifying multiple subnets (AZs) on a single endpoint resource is the standard and simpler approach.
- D: Routing around via NAT Gateway to a public endpoint contradicts the fundamental reason (private connectivity) for using an interface endpoint.

> 💡 **Exam tip**: To achieve **high availability for a VPC interface endpoint**, the standard answer is to **select subnets in every AZ where the application is deployed** when creating the endpoint, so a per-AZ ENI is created.

## QUESTION 310

**Question**: The finance team wants to accurately allocate the cost of every resource by department/project, but many resources are missing required tags (e.g., `CostCenter`, `Project`). Going forward, they want to **block resource creation entirely without the required tags**, and also standardize the tag key/value format. How do you enforce this organization-wide?

**Choices**
- A. Send an email asking each team to tag their resources, leaving compliance up to them (no enforcement means compliance varies wildly by team, and this doesn't meet the "block" requirement at all).
- B. **Create a Tag Policy in Organizations to standardize allowed tag key/value formats, and apply an SCP together that blocks the creation of resources missing required tags.**
- C. Use an AWS Config rule to detect tag-missing resources after the fact and just report a list (after-the-fact detection/reporting only finds resources already created — it doesn't meet the preventive "block creation itself" requirement).
- D. Introduce a process where each resource is manually checked in the console for tags and approved before creation (manual review for thousands of resource-creation requests doesn't scale and is inefficient).

**Correct Answer: B**

**Explanation**
An **Organizations Tag Policy** standardizes the allowed format for tag keys and values (case, allowed value lists, etc.) organization-wide. Applying an **SCP that denies the resource-creation API call itself** for resources missing required tags achieves both tag standardization and preventive "blocking" enforcement, ensuring every resource created going forward carries the tags needed for accurate cost allocation.

**Why the other choices are wrong**
- A: Leaving it up to voluntary compliance has no enforcement power and can't guarantee consistent compliance.
- C: Config-rule-based after-the-fact detection is useful for finding already-created resources missing tags, but isn't a preventive block on creation itself.
- D: A manual approval process becomes a bottleneck and doesn't scale as resource-creation volume grows.

> 💡 **Exam tip**: To **standardize tag format organization-wide and preventively block the creation of resources missing required tags**, the combination of **Organizations Tag Policy + SCP** is the standard answer.

## QUESTION 311

**Question**: In an e-commerce order-processing system, orders from **the same customer must be processed strictly in the order received**, and **duplicate order processing from network retries must also be prevented**. What messaging solution implements this in a serverless architecture?

**Choices**
- A. Use a standard SQS queue (standard queues offer high throughput but no ordering guarantee, and at-least-once delivery can cause duplicates — failing to meet either requirement).
- B. **Use an SQS FIFO queue, setting the customer ID as the message group ID to guarantee per-customer order, and using content-based deduplication (or an explicit deduplication ID) to prevent duplicate messages.**
- C. Publish order events to a standard SNS topic with multiple Lambda subscribers processing in parallel (a standard SNS topic doesn't guarantee order, and parallel processing could actually make ordering worse).
- D. Use Kinesis Data Streams, distributing to shards round-robin with no partition key (distributing round-robin with no partition key scatters the same customer's events across different shards, breaking order guarantees).

**Correct Answer: B**

**Explanation**
An **SQS FIFO queue** guarantees messages are processed in the order sent, within the same **message group ID**. **Using the customer ID as the message group ID** guarantees order within the same customer's orders, while orders from different customers process in parallel — preserving throughput too. The FIFO queue's **deduplication** feature (content-based hashing within a 5-minute deduplication window, or an explicit deduplication ID) also automatically filters out duplicate messages caused by network retries.

**Why the other choices are wrong**
- A: A standard SQS queue provides neither ordering guarantees nor exactly-once processing (deduplication).
- C: A standard SNS topic doesn't guarantee order, and parallel processing by multiple subscribers can actually worsen ordering issues.
- D: To guarantee order in Kinesis, the same entity (e.g., customer) must use the same partition key to route to the same shard — round-robin distribution with no partition key breaks ordering.

> 💡 **Exam tip**: For serverless messaging needing **per-group (customer) ordering plus duplicate-processing prevention**, an **SQS FIFO queue (group ID + deduplication)** is the standard answer.

## QUESTION 312

**Question**: When Security Hub raises a Critical-severity finding like "publicly exposed access key," the security team wants the corresponding IAM access key **immediately and automatically** disabled with no human intervention, and a notification sent to the security team. What's the standard way to build this auto-remediation pipeline?

**Choices**
- A. Have someone continuously monitor the Security Hub console and manually disable the key in IAM when found (requires constant human monitoring, failing the "immediately automatic" requirement, and is also slow to respond).
- B. **Detect Security Hub findings via an EventBridge rule (an event pattern based on severity and type), triggering a Lambda function that automatically disables the IAM access key, then notifies the security team via SNS.**
- C. Only check periodically via a Config rule and generate a report at the next evaluation cycle on violation (periodic evaluation isn't near-real-time immediate response, and it only reports with no automated corrective action).
- D. Store GuardDuty findings in S3 and analyze/respond via a daily batch job (a batch approach has too much delay to meet the "immediate" response requirement).

**Correct Answer: B**

**Explanation**
Configuring **Amazon EventBridge** to detect **Security Hub findings** in real time (e.g., matching a pattern for a certain severity plus a certain finding type), triggering a **Lambda function** that immediately disables the IAM access key programmatically (`UpdateAccessKey`), and sending a notification to the security team via **SNS**, completes the standard SOAR (security orchestration, automation, and response) pattern — automated response within seconds, with no human intervention.

**Why the other choices are wrong**
- A: Constant human monitoring doesn't meet the "immediately automatic" requirement and doesn't scale.
- C: Config rule periodic evaluation lacks real-time-ness and doesn't include automated corrective action by default.
- D: A batch-analysis approach has too much delay between detection and response to meet the immediate-response requirement.

> 💡 **Exam tip**: For **immediate, human-intervention-free automated response (auto-remediation)** to a security finding, the standard answer is the pipeline **Security Hub (or GuardDuty) → EventBridge (real-time event-pattern matching) → Lambda (auto-remediation) → SNS (notification)**.

## QUESTION 313

**Question**: In a large-scale migration, application servers (hundreds of them) need to migrate via AWS Application Migration Service (MGN), and the backend database via AWS DMS, **both in parallel simultaneously**, with the entire application stack's downtime confined to a single short cutover window. What's the approach?

**Choices**
- A. Fully migrate and cut over the database via DMS first, then sequentially migrate the application servers via MGN afterward (cutting over the database and applications at different times risks inconsistency during the gap — the application may not know whether to point at the old or new database).
- B. **Run MGN (application servers, continuous block replication) and DMS (database, full load + CDC) in parallel simultaneously, keeping both replications current, and plan to cut over both migrations together during the same pre-defined short cutover window.**
- C. Migrate all servers (application + DB) using only MGN (MGN replicates entire servers at the block level; a DMS-based CDC approach is more suitable for migrations where the relational database's logical consistency matters — DMS is the standard for migrations that account for the database engine itself).
- D. Accept downtime for both application and database and manually copy the entire system offline over a weekend (unnecessarily long downtime that fails to leverage the continuous-replication benefits MGN/DMS provide).

**Correct Answer: B**

**Explanation**
Migrating application servers via **MGN** and the database via **DMS**, each maintaining **continuous replication** (block-level for MGN, full load + CDC for DMS) to keep source and target continuously synchronized, and then cutting over both the application and database together during a pre-coordinated **same short cutover window**, maintains data consistency between the two components while minimizing the entire stack's downtime. This is the standard large-scale migration pattern for coordinating multiple migration tools in waves.

**Why the other choices are wrong**
- A: Misaligned cutover timing between the application and database risks data inconsistency or connection errors during the gap.
- C: Relational database migration is better served by DMS (and SCT if needed), which handles schema/data consistency, rather than MGN.
- D: Manual offline copying doesn't leverage the short-downtime benefit continuous-replication tools provide at all.

> 💡 **Exam tip**: When migrating an application and its database together, the standard downtime-minimizing answer is to **run MGN (app) and DMS (DB) in parallel with continuous replication**, then **cut over both together during the same short window**.

## QUESTION 314

**Question**: An EC2 target group spans 3 AZs, but one AZ has 8 targets while the other two have just 1 each — traffic distribution is very uneven. They want it balanced evenly. What's the difference in how ALB and NLB each handle this?

**Choices**
- A. Both ALB and NLB by default only balance evenly at the AZ level, without considering the difference in target counts (this is inaccurate for ALB, whose default behavior is to balance evenly at the individual-target level regardless of target count).
- B. **ALB by default distributes traffic evenly at the individual target level (cross-zone load balancing is enabled by default, at no extra charge), while NLB by default distributes evenly at the AZ level (cross-zone load balancing is disabled by default) — so you must explicitly enable cross-zone load balancing, which can then incur inter-AZ data transfer charges.**
- C. NLB always balances perfectly evenly regardless of target count, with no additional configuration needed (inaccurate — NLB routes at the AZ level by default, so if target counts differ per AZ, cross-zone load balancing must be explicitly enabled).
- D. ALB requires enabling cross-zone load balancing to balance evenly, and it's disabled by default (this is backwards — ALB has cross-zone load balancing enabled by default).

**Correct Answer: B**

**Explanation**
**ALB** has **cross-zone load balancing enabled by default**, distributing traffic evenly among registered individual targets regardless of per-AZ target counts, with no extra data-transfer charge. **NLB**, in contrast, has **cross-zone load balancing disabled by default**, so its default behavior distributes traffic evenly **per AZ** (regardless of how many targets are in that AZ). As in this question, when per-AZ target counts differ significantly, this causes imbalance — so to distribute evenly per target on an NLB, you must **explicitly enable cross-zone load balancing**, which can then incur a separate charge for inter-AZ data transfer.

**Why the other choices are wrong**
- A, C: Neither accurately reflects NLB's default behavior (AZ-level distribution) and the need to explicitly enable cross-zone balancing.
- D: This states the ALB default backwards — cross-zone load balancing is on by default for ALB.

> 💡 **Exam tip**: Remember **ALB has cross-zone load balancing on by default (free)**, while **NLB has it off by default**. To balance evenly per target on an NLB when per-AZ target counts are uneven, you must enable cross-zone load balancing — which can incur inter-AZ data transfer charges.

## QUESTION 315

**Question**: The data team wants to **join in a single SQL query** a petabyte-scale S3 data lake (Parquet format) with structured data stored in a Redshift cluster, for analysis. Loading all the S3 data into Redshift is unrealistic given storage cost and time. What's the solution?

**Choices**
- A. Batch-COPY all S3 data into Redshift every day (replicating petabyte-scale data entirely into Redshift storage is enormously costly, and a full daily reload is unrealistic).
- B. **Use Redshift Spectrum to directly query external tables over the S3 data lake from the Redshift cluster, and join them with native Redshift tables.**
- C. Query the S3 data separately via Athena and the Redshift data separately, then combine results at the application level (manually joining results from two separate systems at the application level contradicts the "single SQL query" requirement and is complex to implement).
- D. Delete the Redshift cluster, move all data to S3, and use only Athena (an excessive redesign that gives up the existing native Redshift data and its optimized query performance — not called for by the question).

**Correct Answer: B**

**Explanation**
**Redshift Spectrum** uses the Redshift cluster's compute resources to **directly query S3 data as external tables with no separate load step**, and these external tables can be **joined in a single SQL query** with native tables inside the Redshift cluster. This is the standard way to run unified analysis across a data lake and a data warehouse, saving both storage cost and load time by avoiding replicating petabyte-scale data into Redshift storage.

**Why the other choices are wrong**
- A: Replicating all the data into Redshift carries an enormous storage cost and time/cost burden from daily reloads.
- C: Manually combining results from two systems at the application level fails the "join in a single SQL query" requirement and is complex.
- D: Eliminating Redshift entirely is an unnecessary redesign beyond the question's scope.

> 💡 **Exam tip**: To **join an S3 data lake and native Redshift data in a single query** without a full load, directly querying external tables via **Redshift Spectrum** is the standard answer.

## QUESTION 316

**Question**: A retail company's traffic shows a **clear daily pattern**, spiking repeatedly at noon and 7pm. Their existing dynamic (reactive) Auto Scaling policy only starts scaling out **after** a spike begins, causing a few minutes of degraded response time at the start. How do you provision capacity **ahead of** the traffic spike?

**Choices**
- A. Set the target-tracking scaling policy's target value lower (a lower target value does react earlier, but this is still a reactive approach that responds "after" an actual metric change is detected — fundamentally not prediction-based).
- B. **Configure Predictive Scaling on the Auto Scaling group, using machine learning trained on historical traffic patterns (at least 24 hours, ideally days to weeks of data) to forecast upcoming traffic spikes and scale out ahead of time before the spike occurs.**
- C. Keep instances permanently fixed at maximum capacity (keeping maximum capacity even during low-traffic periods is over-provisioning without prediction — not cost-effective).
- D. Manually adjust instance counts in the console every day at noon and 7pm (manual intervention isn't automated, carries heavy operational burden, and lags behind even small pattern changes).

**Correct Answer: B**

**Explanation**
**Predictive Scaling** uses a machine learning model trained on at least 24 hours of historical metric data to forecast upcoming traffic and scale out capacity **ahead of** the predicted spike actually occurring. For workloads with recurring daily/weekly patterns, this precisely prevents the "initial lag" performance degradation that dynamic scaling alone misses, and can be combined with dynamic scaling policies to cover cases where the prediction is off.

**Why the other choices are wrong**
- A: Adjusting the target value still falls into the reactive (after-the-fact) category, different from a predictive approach that scales out before the spike occurs.
- C: Running permanently at maximum capacity is cost-inefficient over-provisioning.
- D: Manual adjustment isn't automated, is fragile to pattern changes, and carries heavy operational burden.

> 💡 **Exam tip**: For a **recurring, predictable traffic pattern**, to provision capacity **ahead of** the spike, **Auto Scaling's Predictive Scaling** is the standard answer.

## QUESTION 317

**Question**: The security team wants to retain VPC Flow Logs from dozens of VPCs long-term and query traffic for a specific IP or port via Athena when needed. Given the huge data volume, they want to **minimize query cost and scan time**. What's the recommended storage/query configuration?

**Choices**
- A. Send flow logs only to CloudWatch Logs and perform all queries via CloudWatch Logs Insights (CloudWatch Logs tends to have higher cost than S3 for long-term, large-volume log retention, and Logs Insights doesn't offer partitioning-based large-scale scan optimization as cost-effective as Athena).
- B. **Send flow logs to S3, convert them to a columnar format like Parquet (e.g., via Firehose's format-conversion feature), partition by year/month/day/hour, register in the Glue Data Catalog, and query with Athena.**
- C. Store flow logs as-is in text (gzip) format in S3 with no partitioning, and full-scan via Athena (with no partitioning, every query must scan the entire dataset, greatly increasing cost and time, and text format scans less efficiently than a columnar format).
- D. Store flow logs as individual records in DynamoDB and implement query logic in the application (storing large-volume log data in DynamoDB is very costly, and it's unsuitable for flexible analytical queries over arbitrary IP/port combinations).

**Correct Answer: B**

**Explanation**
Since Athena query cost is proportional to **the amount of data scanned**, converting flow logs stored in S3 to a **compressed columnar format like Parquet** and **partitioning by time (year/month/day/hour)** means a query targeting a specific time range only scans that partition, greatly reducing scan volume and cost. Registering partition information in the Glue Data Catalog lets Athena efficiently perform partition pruning.

**Why the other choices are wrong**
- A: CloudWatch Logs has higher cost for large-volume, long-term retention than S3, and Logs Insights isn't as cost-efficient as Athena's partitioning-based scan optimization.
- C: Text format with no partitioning requires scanning all data every time, greatly increasing cost and query time.
- D: DynamoDB isn't suited to flexible analytical queries (arbitrary conditional filtering) over large-volume logs and is very costly.

> 💡 **Exam tip**: For **low-cost, fast** querying of large-volume logs via Athena, the standard answer is **store in S3 + convert to a columnar format (Parquet) + partition by time + register in the Glue Data Catalog**.

## QUESTION 318

**Question**: A factory automation company wants to build its manufacturing-equipment control application using cloud-native services, but some workloads (e.g., robotic arm control) require **millisecond-level ultra-low latency** and **local processing of factory-local data** (round-trip latency to a Regional data center is unacceptable). The rest of the workload is fine running in a normal AWS Region. What's the solution that keeps using cloud-native APIs/tools while meeting this requirement?

**Choices**
- A. Use the nearest AWS Region and optimize latency with Global Accelerator (even the nearest Region has physical round-trip latency, and a Region-based service can't meet a millisecond-level local-processing requirement).
- B. **Install AWS Outposts on the factory floor: run the latency-sensitive workload on-premises on Outposts using the same AWS APIs/tools, processed locally, while the rest runs in a normal AWS Region.**
- C. Build a separate data center and a separate open-source container-orchestration stack at the factory from scratch (contradicts the desire to keep using native AWS APIs/tools, and building/operating infrastructure from scratch is a very heavy burden).
- D. Use AWS Wavelength, deployed at a telecom's 5G network edge (Wavelength is optimized for ultra-low latency to mobile end users over a telecom network, whereas Outposts better fits local processing within a specific on-premises facility like factory equipment control).

**Correct Answer: B**

**Explanation**
**AWS Outposts** is a fully managed hybrid solution that extends AWS's infrastructure, services, APIs, and tools directly to a customer's on-premises facility (here, the factory). Latency-sensitive workloads are **processed locally on-site**, eliminating round-trip latency to a Region, while developers can keep using the same AWS APIs/console/tools. The rest of the workload can run in a normal AWS Region as usual — a hybrid architecture that precisely matches the requirement.

**Why the other choices are wrong**

> 💡 **Exam tip**: When you need **ultra-low-latency local processing at a specific on-premises facility while keeping native AWS APIs/tools**, **AWS Outposts** is the standard answer. Distinguish it from **Wavelength**, which fits a telecom-network-edge, mobile-end-user scenario.

## QUESTION 319

**Question**: A large enterprise needs to grant contractors temporary access to various resource groups, where each contractor's accessible resource scope differs, and access must be revoked immediately when a contract ends. With a very large number of resources, **pre-defining an individual policy per role** is impractical. What's a scalable access-control approach?

**Choices**
- A. Pre-create an individual IAM role and fine-grained resource-based policy for every contractor one by one (as the number of resource/contractor combinations grows, the number of policies to pre-define grows explosively — impractical).
- B. **Use attribute-based access control (ABAC): define a small number of general-purpose IAM policies that allow access only when a contractor's session tag (e.g., project=alpha) matches a resource's tag. Pass session tags when the contractor calls STS AssumeRole.**
- C. Grant every contractor the same broad-permission role and instruct them to use only the resources they need (directly violates least privilege, with no technical defense against mistakes or malicious access).
- D. Create a completely separate AWS account per contractor, separating resources by account (splitting into entirely separate accounts when fine-grained, resource-level access needs to be granted differently per contractor requires restructuring existing resource placement — impractical and excessive).

**Correct Answer: B**

**Explanation**
**ABAC (attribute-based access control)** grants access by comparing **attributes (tags)** of the user/role against **attributes (tags)** of the resource, so no matter how many resources or roles exist, a **small number of general-purpose policies** (e.g., "allow if the requester's `project` tag matches the resource's `project` tag") can scalably control access. When a contractor assumes a role via AssumeRole, passing that contractor's project/scope as a **session tag** means no policy rewrite is needed as new resources are added or more contractors come on board.

**Why the other choices are wrong**
- A: The RBAC (role-based) approach of pre-defining an individual policy per role-resource combination becomes unmanageable as combinations grow.
- C: Granting broad permissions to every contractor violates least privilege and carries high risk.
- D: Splitting into entirely separate accounts is a far larger structural change than needed for a situation requiring fine-grained, per-resource access control.

> 💡 **Exam tip**: When there are too many resource/role combinations to pre-define policies for individually and you need scalable access control, **ABAC (attribute-based access control) + session tags** is the standard answer.

## QUESTION 320

**Question**: An architect designing a multi-AZ architecture per the Well-Architected Framework's reliability pillar wants to reflect the principle that already-deployed infrastructure should keep working correctly even during a Region-wide **control-plane outage** (e.g., the Auto Scaling API or ELB API itself is temporarily unresponsive) — the "static stability" principle. Which design reflects this principle?

**Choices**
- A. Rely solely on detecting capacity loss in a failed AZ and immediately calling the Auto Scaling API to launch new instances in another AZ (if the control plane itself is degraded, this API call could fail too, so it doesn't provide static stability that survives a control-plane outage).
- B. **Pre-deploy enough capacity in each AZ at all times to absorb a failure (e.g., 3 AZs each at 50% capacity, so that if one AZ fails, the remaining two handle 100% of traffic) — absorbing the failure using only already-existing resources, with no control-plane API calls needed.**
- C. Place all needed capacity in a single AZ and redeploy the entire stack to another AZ only during a failure (concentrating in a single AZ means the entire service goes down if that AZ fails, and redeployment itself depends on control-plane APIs — the opposite of static stability).
- D. Provision all capacity only in real time via On-Demand API calls, with nothing pre-deployed (provisioning new resources via API only at the moment of failure, with nothing reserved in advance, can fail during control-plane degradation — contradicting the static stability principle).

**Correct Answer: B**

**Explanation**
**Static stability** is a design principle where, rather than relying on new API calls (Auto Scaling, new resource provisioning, etc.) at the moment of failure, you **pre-reserve sufficient capacity** so that **already-deployed resources alone** can absorb the failure. For example, pre-placing 50% of normal load's capacity (N+1 or more) in each of 3 AZs means that even if one AZ completely fails, the remaining AZs can immediately absorb all traffic with no control-plane involvement. This is a reliability best practice that ensures the data plane (already-running resources) keeps working correctly even during a broad outage where the control plane itself is degraded.

**Why the other choices are wrong**
- A, D: Relying on calling an API to secure new capacity at the moment of failure can fail precisely when that API (the control plane) is degraded — it doesn't provide static stability.
- C: Concentrating in a single AZ violates the basic reliability principle of failure isolation across multiple AZs from the outset.

> 💡 **Exam tip**: For reliability that **survives a control-plane outage**, don't rely on provisioning new resources at the moment of failure — the standard answer is **static stability** design: **pre-deploying sufficient spare capacity across multiple AZs at all times**.
