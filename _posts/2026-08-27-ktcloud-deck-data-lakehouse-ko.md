## 개요

kt cloud를 운영하며 쌓이는 로그·지표·이벤트·사용량 데이터가 시스템마다 흩어져 있어, 정작 의사결정에는 바로 쓰지 못하던 문제를 다룬 구축 사례입니다. 이를 해결하기 위해 만든 운영 데이터 통합 플랫폼이 **Deck**입니다.

| 축 | 내용 |
|---|---|
| **문제의식** | 데이터는 충분히 쌓이지만, 시스템마다 형태가 달라 의사결정에 바로 연결되지 않음 |
| **아키텍처** | Object Storage를 단일 기준 저장소(SSOT)로 삼는 데이터 레이크하우스 |
| **설계 원칙** | 순수 오픈소스 기반 구축 + 원본은 한 번만 저장하고 재사용(복제 지양) |
| **적용 사례** | 사용량 기반 과금(Usage-based Billing) 파이프라인 전 과정 |

관통하는 메시지는 "정보 하나를 확인하려 여러 도구를 순차적으로 열어야 하고, 팀마다 같은 데이터를 중복 수집·가공하는" 비효율을, 하나의 공통 기준 위에서 없애자는 것입니다.

---

## 1. 왜 데이터 레이크하우스인가

Deck의 첫 번째 선택은 아키텍처 형태였습니다. Data Warehouse, Data Lake, Data Lakehouse 세 가지를 비교합니다.

| 구분 | Data Warehouse | Data Lake | **Data Lakehouse** |
|---|---|---|---|
| 데이터 유형 | 정형 | 정형/반정형/비정형 | 정형/반정형/비정형 |
| 장점 | 신뢰성 | 유연성 | 유연성 + 신뢰성 |
| 한계 | 확장성, 비용 | 품질 관리 | 구현 복잡도 |

클라우드 운영 데이터는 정형 사용량부터 비정형 로그까지 스펙트럼이 넓지만, 과금처럼 신뢰성이 필수인 영역도 함께 다뤄야 합니다. 레이크하우스는 "레이크의 유연성 위에 ACID와 스키마 관리를 얹어 신뢰성까지 확보"할 수 있다는 점에서 선택됐습니다.

---

## 2. 두 가지 설계 원칙

1. **순수 오픈소스 기반 구축** — 벤더 종속성 제거로 기술 자율성을 확보하고, 라이선스 비용을 최소화해 장기 비용 효율을 노림
2. **Object Storage를 단일 기준 저장소(SSOT)로 설정** — 원본은 한 번만 저장하고, 이후 단계에서는 복제하지 않고 같은 원본을 참조하거나 파생 형태로 재사용해 데이터 중복과 관리 복잡도를 줄임

---

## 3. Deck의 계층별 아키텍처

Object Storage를 중심축으로 두고, 각 레이어가 독립적으로 확장 가능하도록 계층화했습니다.

| 레이어 | 핵심 기술 | 선택 이유 |
|---|---|---|
| 🚄 수집 | Kafka, Vector | Kafka는 검증된 안정성과 표준화된 연동성, Vector는 경량·고성능의 유연한 전처리 |
| 📁 저장 | Object Storage | 확장성·내구성·비용 효율, 모든 레이어가 엔진 중립적으로 접근 가능 |
| 🔥 쿼리 | Trino | 적재 없이 Object Storage를 바로 SQL로 조회하는 대화형 분석 |
| ⚙️ 처리 | Airflow, Spark | Airflow는 배치 파이프라인의 스케줄·의존성·재처리 관리, Spark는 대용량 정제·집계 |
| 🚀 서빙 | StarRocks | 실시간 Upsert·고속 조인, 스토리지·컴퓨트 분리로 저지연 OLAP 서빙 |
| 🖥️ 표현 | Superset | 완전 오픈소스 BI로 라이선스 비용 제거, 벤더 비종속성 확보 |

설계 철학은 명확합니다. "하나의 엔진이 수집부터 서빙까지 떠받치면 어딘가 반드시 병목이 된다"는 것. 그래서 목적별로 최적화된 도구를 배치하고, Object Storage라는 공통 기준 위에서 레이어마다 독립적으로 확장할 수 있게 했습니다.

Trino, Spark, StarRocks의 역할이 겹쳐 보일 수 있지만, 최적화 지점이 다릅니다.

- **Trino**: 적재 없는 대화형 탐색
- **Spark + Airflow**: 대용량 배치 처리
- **StarRocks**: 다중 사용자 대상 저지연 OLAP 서빙

---

## 4. 적용 사례: 빌링 파이프라인

kt cloud는 수십 종의 상품을 사용량 기반으로 과금(Usage-based Billing)합니다. 미터링부터 과금, 청구까지 일관된 기준으로 처리하는 것이 핵심 과제였는데, Deck은 이 전 과정을 하나의 흐름으로 연결합니다.

1. **수집** (Kafka, Vector): 각 서비스의 사용량 데이터 수집
2. **저장** (Object Storage): 단일 기준 원본으로 적재
3. **처리** (Airflow, Spark): 서비스·기간·지표 단위로 정제·집계
4. **서빙** (StarRocks): 저지연 조회 제공

이 구조로 얻는 효과는 세 가지입니다.

- **단일 기준 원본 위의 표준 정산**: 서비스별 사용량을 표준 구조로 처리
- **정책 기반 자동화**: 신규 상품 추가 시 별도 개발 없이 과금 자동화
- **투명한 근거 제시**: 과금 근거를 추적·검증하고 비용을 분석 가능

핵심 성과는 "미터링부터 청구까지가 하나의 데이터 기준 위에서 일관되게 처리된다"는 점입니다.

## 5. 향후 방향

1. 클라우드 운영 데이터의 단계적 확대 적재
2. 저장 환경에서 분석 플랫폼으로의 진화
3. 확장성 개선 (자원 유연성)
4. 서비스 자동화 (신규 테넌트 추가 시 수작업 최소화)
5. 통합 보안 체계 (Multi-tenancy, RBAC, 인증·인가 포함)

## 정리

이 글이 눈에 들어온 이유가 있습니다. 요즘 클라우드 업계 데이터를 분석하다 보면 정보량 자체는 넘쳐나는데, 그게 서로 다른 도구·형식·기준에 흩어져 있어서 "결국 뭘 믿고 판단해야 하나"라는 답답함을 느낄 때가 많았고, 그 와중에 데이터 레이크하우스라는 개념의 필요성을 스스로도 체감하고 있었습니다. Deck 사례는 그 체감을 실제 프로덕션 아키텍처 수준에서 어떻게 풀어냈는지 잘 보여줍니다.

특히 "원본은 한 번만 저장하고 복제하지 않는다"는 SSOT 원칙과, 수집·저장·쿼리·처리·서빙을 목적별로 다른 엔진에 맡기되 Object Storage라는 공통 기준으로 묶는 설계는 왜 레이크하우스가 단순한 유행어가 아니라 실무적 해법인지를 잘 설명해줍니다. 마침 AWS Data Engineer Associate 자격증을 준비하면서 Lake Formation, Glue, Redshift Spectrum처럼 레이크와 웨어하우스의 경계를 넘나드는 서비스들을 공부하고 있던 참이라, Deck이 오픈소스 스택(Kafka·Trino·Spark·StarRocks)으로 같은 문제를 어떻게 풀었는지 비교하면서 읽으니 개념이 훨씬 입체적으로 와닿았습니다.
