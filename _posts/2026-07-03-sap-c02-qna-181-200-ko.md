## QUESTION 181

**문제**: Organizations 다중 계정, 3개 OU(각 100개 이상 계정), 각 계정 단일 VPC(동일 리전, CIDR 겹치지 않음). **같은 OU 내 VPC끼리만** 통신 가능해야 함(다른 OU와는 불가). 최소 운영 오버헤드는?

**보기**
- A. 각 OU 계정 간 VPC 피어링을 설정하는 CloudFormation StackSets(계정 수가 많아 N:N 피어링 관리가 매우 복잡).
- B. 각 OU에 전용 네트워킹 계정 + RAM으로 VPC 공유 + 네트워킹 계정과 각 계정 간 피어링(허브 하나에 100개 이상 피어링 연결 관리 필요, 대안보다 복잡).
- C. **각 OU 계정에서 전송 게이트웨이 프로비저닝. RAM으로 조직 전체에 전송 게이트웨이 공유. 각 VPC에 대해 전송 게이트웨이 VPC 연결 생성.**
- D. 전용 네트워킹 계정 + VPN 연결 + 타사 라우팅 소프트웨어(관리 부담 매우 큼).

**정답: C**

**해설**
**Transit Gateway + AWS RAM**은 대규모(OU당 100개 이상 계정) 환경에서 다대다 VPC 연결을 관리형으로 단순화하는 표준 방법입니다. OU별로 전송 게이트웨이를 만들고 라우팅 테이블을 통해 "같은 OU 내에서만 통신 가능"하도록 제어할 수 있어 최소 오버헤드로 요구사항을 만족합니다.

**왜 다른 보기는 오답인가**
- A: VPC 피어링은 트랜지티브(전이적)가 아니므로, 100개 이상 계정 간 전체 연결을 위해서는 엄청난 수의 개별 피어링 연결이 필요해 비현실적입니다.
- B, D: 허브 계정을 통한 피어링/VPN 방식은 Transit Gateway 네이티브 라우팅보다 관리가 훨씬 복잡합니다.

> 💡 **시험 꿀팁**: **대규모(수백 개) 계정/VPC 간 통신**을 관리형으로 단순화하려면 **Transit Gateway + AWS RAM 공유**가 표준 정답이며, VPC 피어링은 비전이적이라 이런 규모에는 부적합합니다.

## QUESTION 182

**문제**: 애플리케이션 마이그레이션 중 완전관리형 서비스를 최대한 사용하려 함. 중요 대용량 문서 저장 요건: 1) 고내구성/고가용성, 2) 저장/전송 항상 암호화, 3) **암호화 키를 회사가 관리하고 주기적으로 교체**.

**보기**
- A. 파일 게이트웨이 모드 Storage Gateway + EBS 볼륨 암호화(KMS)(파일 게이트웨이는 S3 기반이지만 EBS 볼륨 암호화 설명은 개념이 맞지 않음).
- B. **S3 + 버킷 정책으로 HTTPS 연결 강제 + 서버 측 암호화(SSE-KMS)로 객체 암호화.**
- C. DynamoDB + SSL 연결 + KMS로 저장 객체 암호화(대용량 "문서" 저장에는 DynamoDB보다 S3가 적합).
- D. EBS 볼륨 연결된 인스턴스 배포 + EBS 암호화(EC2/EBS 프로비저닝과 관리가 필요해 "완전관리형" 요건에 덜 부합).

**정답: B**

**해설**
**Amazon S3**는 대용량 객체 저장에 최적화된 완전관리형, 고내구성(11 9's) 서비스입니다. 버킷 정책으로 `aws:SecureTransport` 조건을 사용해 HTTPS를 강제하면 전송 중 암호화를, **SSE-KMS**(고객 관리형 키, 자동/수동 키 교체 지원)를 사용하면 저장 시 암호화와 회사의 키 관리/교체 요건을 모두 만족합니다.

**왜 다른 보기는 오답인가**
- A: Storage Gateway는 온프레미스 하이브리드 접근이 필요할 때 쓰는 것으로, 이 시나리오처럼 순수 클라우드 완전관리형을 원할 때는 S3를 직접 쓰는 것이 더 적합합니다.
- C: DynamoDB는 키-값/문서 데이터베이스로, "큰 중요 문서"(파일) 저장에는 S3가 더 자연스럽습니다.
- D: EC2+EBS는 인스턴스 프로비저닝/관리가 필요해 "완전관리형 서비스를 최대한 사용"이라는 목표에 맞지 않습니다.

> 💡 **시험 꿀팁**: 대용량 문서를 **완전관리형**으로, **회사가 직접 관리/교체하는 키**로 암호화해야 할 때는 **S3 + SSE-KMS(고객 관리형 키) + 버킷 정책의 HTTPS 강제**가 표준 정답입니다.

## QUESTION 183

**문제**: ECS(Fargate, ALB 뒤, CPU 기반 오토스케일링) 공개 API. 최근 SQL 인젝션 공격 다수로 성능 저하 및 서비스 불가(최대 스케일까지 확장됨). 합법적 트래픭 허용 + 운영 효율 극대화하며 SQL 인젝션 차단 솔루션은?

**보기**
- A. 새 WAF 웹 ACL로 요청 모니터링만(차단 규칙 없음 — 실제 방어 효과 없음).
- B. WAF Bot Control(봇 트래픽 관리용, SQL 인젝션 자체를 타겟하지 않음).
- C. **새 WAF 웹 ACL 생성. SQL 데이터베이스 관리형 규칙 그룹과 일치하는 요청을 차단하는 규칙 추가. 나머지 트래픽은 허용. ALB에 웹 ACL 연결.**
- D. 빈 IP 세트 + Lambda로 로그 분석해 공격 IP를 수동 추가(반응형이라 느리고, 새로운 공격 IP마다 지연 발생).

**정답: C**

**해설**
AWS WAF에는 **SQL 데이터베이스(SQLi) 관리형 규칙 그룹**이 미리 정의되어 있어, 이를 웹 ACL에 추가하고 나머지 트래픽은 허용하도록 구성하면 SQL 인젝션 패턴을 즉시 자동으로 차단하면서도 정상 트래픽은 그대로 통과시킬 수 있습니다. 관리형 규칙이므로 운영 오버헤드도 최소입니다.

**왜 다른 보기는 오답인가**
- A: 모니터링만으로는 실제 공격을 막지 못합니다.
- B: Bot Control은 자동화된 봇 트래픽 관리 기능으로 SQL 인젝션 방어와는 목적이 다릅니다.
- D: 공격이 발생한 후 로그를 분석해 IP를 하나씩 차단하는 방식은 반응이 느리고, 공격자가 IP를 계속 바꾸면 무력화됩니다.

> 💡 **시험 꿀팁**: **SQL 인젝션 공격**을 막을 때는 AWS WAF의 **SQL 데이터베이스 관리형 규칙 그룹**을 사용하는 것이 즉각적이고 운영 부담 없는 표준 정답입니다.

## QUESTION 184

**문제**: IoT Core로 대기질 센서 데이터 수집, DynamoDB 저장. 비즈니스 연속성을 위해 **두 리전**에서 데이터 수집/저장 가능해야 함.

**보기**
- A. Route 53 별칭 장애 조치(IoT Core 데이터 엔드포인트 값 사용) + 데이터를 Aurora 글로벌 테이블로 마이그레이션(Aurora는 관계형 DB로 개념 오류, "글로벌 테이블"은 DynamoDB 용어).
- B. 각 리전 IoT Core 도메인 구성 + Route 53 지연 시간 기반 라우팅 + MemoryDB로 마이그레이션(지연시간 기반은 양쪽 다 활성 상태를 전제 — 두 리전 모두 지속 수집이 필요한 상황에 부적합할 수 있고 MemoryDB 마이그레이션도 불필요).
- C. **각 리전에 IoT Core 도메인 구성 생성. 도메인 구성 상태를 평가하는 Route 53 상태 확인 생성. 도메인 이름 값으로 장애 조치 라우팅 정책 생성. DynamoDB 테이블을 전역 테이블로 업데이트.**
- D. Route 53 지연 시간 기반 라우팅 + DynamoDB 스트림 및 리전 간 데이터 복제 수동 구성(DynamoDB 글로벌 테이블이라는 네이티브 기능을 두고 직접 구현 — 비효율).

**정답: C**

**해설**
**IoT Core의 도메인 구성**을 각 리전에 만들고 **Route 53 상태 확인 + 장애 조치 라우팅**으로 정상 리전으로 자동 전환하며, **DynamoDB 글로벌 테이블**(네이티브 다중 리전 복제 기능)로 데이터를 두 리전 모두에 저장하는 조합이 정확히 이 요구사항에 맞습니다.

**왜 다른 보기는 오답인가**
- A: Aurora는 관계형 데이터베이스로 DynamoDB 데이터의 대체재가 아니며, "Aurora 글로벌 테이블"이라는 표현도 개념적으로 부정확합니다(DynamoDB의 기능명입니다).
- B: MemoryDB로의 불필요한 마이그레이션이 포함되어 있고, 지연 시간 기반 라우팅은 이 시나리오의 요구(두 리전 모두 활성 상태로 데이터 수집)와 정확히 맞지 않을 수 있습니다.
- D: DynamoDB 스트림 기반 수동 복제는 이미 존재하는 네이티브 기능(글로벌 테이블)을 재구현하는 비효율적인 방법입니다.

> 💡 **시험 꿀팁**: DynamoDB의 **다중 리전 복제**는 항상 **글로벌 테이블(Global Tables)** 네이티브 기능을 사용하세요 — 스트림 기반 수동 복제는 불필요하게 복잡합니다. IoT Core의 다중 리전 장애 조치에는 **Route 53 상태 확인 + 장애 조치 라우팅**을 결합합니다.

## QUESTION 185

**문제**: Organizations 다중 계정. 재무 팀 계정(Lambda+DynamoDB, 기밀 데이터). 마케팅 팀(별도 계정)이 DynamoDB 테이블의 **특정 속성에만** 접근 가능해야 함. 적절한 접근 권한을 마케팅 팀에 부여하는 방법은?

**보기**
- A. 마케팅 팀 계정에 속성 접근 권한을 부여하는 SCP를 재무 팀 OU에 연결(SCP는 접근 권한을 부여할 수 없고, 상한선만 설정 가능 — 개념 오류).
- B. **재무 팀 계정에서 특정 DynamoDB 속성 조건(세밀한 액세스 제어)을 포함한 IAM 정책의 IAM 역할 생성. 마케팅 팀 계정과 신뢰 관계 구축. 마케팅 팀 계정에서 이 역할을 맡을 수 있는 IAM 역할 생성.**
- C. 리소스 기반 IAM 정책(DynamoDB 테이블에 직접 연결, 속성 조건 포함) + 마케팅 팀 계정에서 역할 생성(DynamoDB 테이블은 리소스 기반 정책을 직접 지원하지 않음).
- D. 재무 팀 계정에 IAM 역할 + 권한 경계(permission boundary)로 속성 제한(권한 경계는 역할 자체의 최대 권한 상한이지, 세밀한 속성 수준 조건 제어에 적합한 도구가 아님).

**정답: B**

**해설**
**크로스 계정 IAM 역할 + DynamoDB의 세밀한 액세스 제어(Fine-Grained Access Control, `dynamodb:LeadingKeys`/속성 조건)**를 결합한 IAM 정책으로, 재무 팀 계정에 역할을 만들고 마케팅 팀 계정이 이를 맡도록(assume) 신뢰 관계를 설정하는 것이 표준 크로스 계정, 속성 수준 접근 제어 패턴입니다.

**왜 다른 보기는 오답인가**
- A: SCP는 권한을 "부여"할 수 없고 최대 허용 범위(상한선)만 설정하는 도구입니다 — 개념적으로 틀렸습니다.
- C: **DynamoDB 테이블은 리소스 기반 정책을 직접 지원하지 않습니다**(S3와 다름).
- D: 권한 경계는 역할의 최대 권한 한도를 설정하는 도구로, 이 시나리오의 속성 수준 세밀한 제어와는 다른 목적입니다.

> 💡 **시험 꿀팁**: **DynamoDB는 리소스 기반 정책을 지원하지 않습니다.** 다른 계정에 DynamoDB 테이블의 특정 속성만 접근을 허용하려면 **크로스 계정 IAM 역할 + IAM 정책의 세밀한 액세스 제어 조건**을 사용하세요.

## QUESTION 186

**문제**: S3에 객체를 저장하는 애플리케이션, 두 리전에서 **동시** 사용. 두 버킷의 객체는 서로 동기화 상태 유지 필요. 최소 운영 오버헤드로. (3개 선택)

**보기**
- A. **S3 다중 리전 액세스 포인트 생성 + 애플리케이션이 이를 참조하도록 변경.**
- B. **두 S3 버킷 간 양방향 S3 CRR(Cross-Region Replication) 구성.**
- C. 각 S3 버킷에 객체를 저장하도록 애플리케이션 직접 수정(다중 리전 액세스 포인트를 쓰면 애플리케이션이 버킷을 직접 알 필요 없음 — 불필요).
- D. 수명 주기 규칙으로 복사(수명 주기 규칙은 이런 실시간 복제 용도가 아님).
- E. **각 S3 버킷에 대해 S3 버전 관리 활성화(CRR의 전제 조건).**
- F. Lambda로 수동 복사 이벤트 처리(CRR이라는 네이티브 기능을 두고 직접 구현 — 비효율).

**정답: A, B, E**

**해설**
**S3 CRR은 양쪽 버킷에 버전 관리가 활성화되어 있어야 동작**하므로(E), 양방향 CRR을 구성해 두 버킷의 객체를 동기화하고(B), 애플리케이션은 **S3 다중 리전 액세스 포인트**를 사용해 어느 리전에 있는지 신경 쓰지 않고 가장 가까운/활성 버킷에 자동 라우팅되도록 하는 것(A)이 최소 운영 오버헤드로 두 리전 동시 사용을 지원하는 표준 조합입니다.

**왜 다른 보기는 오답인가**
- C: 다중 리전 액세스 포인트를 사용하면 애플리케이션이 어떤 버킷에 쓰는지 직접 알 필요가 없어 이 단계가 불필요합니다.

- A. **가장 가까운 리전에 Direct Connect 게이트웨이 생성. Direct Connect 연결을 DXGW에 연결(attach).**
- B. DXGW로 다른 두 리전의 VPC 연결(DXGW를 통한 다른 리전 VPC 연결은 프라이빗 VIF를 통해서만 가능 — B 자체는 방법 설명이 불완전하지만 A+D 조합에서 이 부분이 자동으로 커버됨).
- C. 다른 두 리전으로 추가 Direct Connect 연결 설정(비용이 훨씬 큼 — 리전마다 새 DX 연결 필요).
- D. **프라이빗 VIF 생성. 기존 DX 연결과 연결된 VPC에서 프라이빗 VIF를 통해 Site-to-Site VPN 연결 설정(원격 리전 VPC 접근용, 실제로는 DXGW를 통한 프라이빗 VIF로 3개 VPC 모두에 접근).**
- E. 공용 VIF + Site-to-Site VPN(공용 VIF는 AWS 공용 서비스 접근용도로는 맞지만, VPC 내부 EC2 접근에는 프라이빗 VIF가 필요).
- F. VPC 피어링으로 리전 간 VPC 연결 + 프라이빗 VIF로 접근(피어링 관리가 추가되어 A+D 조합보다 복잡/비용 증가).

**정답: A, D**

**해설**
**Direct Connect Gateway**를 하나 생성해 기존 DX 연결에 연결(attach)하면(A), 이 DXGW를 통해 **하나의 DX 연결로 여러 리전의 여러 VPC**에 프라이빗 VIF를 통해 연결할 수 있습니다(D, 원격 VPC와의 가상 프라이빗 게이트웨이 연결). 이렇게 하면 리전마다 별도의 DX 연결을 만들 필요 없이 가장 저렴하게 3개 VPC 모두에 접근할 수 있습니다.

**왜 다른 보기는 오답인가**
- C: 각 리전에 별도의 물리적 DX 연결을 새로 구축하는 것은 비용이 훨씬 큽니다.
- E: 공용 VIF는 S3, DynamoDB 같은 AWS 공용 서비스 접근용이며, VPC 내부의 프라이빗 EC2 인스턴스 접근에는 프라이빗 VIF가 필요합니다.
- F: VPC 피어링을 추가하는 것은 DXGW의 네이티브 다중 리전 VPC 연결 기능을 두고 불필요한 복잡성을 더합니다.

> 💡 **시험 꿀팁**: **하나의 Direct Connect 연결로 여러 리전의 여러 VPC**에 가장 저렴하게 연결하려면 **Direct Connect Gateway + 프라이빗 VIF**를 사용하세요 — 리전마다 별도 DX 연결을 만드는 것보다 훨씬 경제적입니다.

## QUESTION 199

**문제**: Organizations로 수백 개 계정 관리. **OWASP Top 10** 웹 애플리케이션 취약점에 대한 기본 보호를, 조직 내 **모든 기존/신규 CloudFront 배포**에 WAF로 적용하려 함. (3개 선택)

**보기**
- A. **모든 계정에서 AWS Config 활성화(Firewall Manager의 준수 확인 등에 필요한 전제 조건 중 하나로 흔히 요구됨).**
- B. 모든 계정에서 GuardDuty 활성화(위협 탐지 서비스로 WAF 규칙 배포와 직접 관련 없음).
- C. **조직의 모든 기능(All Features) 활성화(Firewall Manager 사용의 전제 조건).**
- D. **AWS Firewall Manager를 사용해 모든 CloudFront 배포의 모든 계정에 WAF 규칙 배포.**
- E. Shield Advanced로 WAF 규칙 배포(Shield Advanced는 DDoS 보호 서비스로 WAF 규칙을 조직 전체에 배포하는 기능은 Firewall Manager의 역할).
- F. Security Hub로 WAF 규칙 배포(Security Hub는 보안 상태 통합 대시보드/알림 서비스로 규칙을 실제로 "배포"하는 기능이 없음).

**정답: A, C, D**

**해설**
조직 전체에 걸쳐 WAF 규칙을 중앙에서 배포/관리하는 서비스는 **AWS Firewall Manager**이며, 이를 사용하려면 **Organizations의 모든 기능 활성화**(C)가 전제 조건이고, 계정별 리소스 준수 상태 평가를 위해 **AWS Config 활성화**(A)도 필요합니다. 이 조건이 갖춰지면 Firewall Manager로 모든 계정의 모든 CloudFront 배포에 WAF 규칙(OWASP Top 10 등 관리형 규칙 그룹 포함)을 한 번에 배포할 수 있습니다(D).

**왜 다른 보기는 오답인가**
- B: GuardDuty는 위협 탐지 서비스로, WAF 규칙을 조직 전체에 배포하는 기능과는 무관합니다.
- E: Shield Advanced는 DDoS 보호에 특화되어 있으며, WAF 규칙을 조직 전체에 "배포"하는 역할은 Firewall Manager가 담당합니다.
- F: Security Hub는 보안 발견 사항을 통합해 보여주는 대시보드 서비스로, 실제로 WAF 규칙을 배포하는 기능이 없습니다.

> 💡 **시험 꿀팁**: **조직 전체에 걸쳐 WAF 규칙을 중앙 배포**하려면 **AWS Firewall Manager**가 정답이며, 이를 쓰기 위한 전제 조건으로 **Organizations 모든 기능 활성화 + AWS Config 활성화**가 필요하다는 점을 기억하세요.

## QUESTION 200

**문제**: 온프레미스 IdP와 SAML 2.0 페더레이션 ID 솔루션 구현. 설계자 본인은 연동 웹 포털을 통한 인증이 성공했으나, **테스트 사용자**는 같은 방식으로 AWS 환경에 접근하지 못함. ID 페더레이션이 올바르게 구성되었는지 확인해야 할 항목은? (3개 선택)

**보기**
- A. IAM 사용자의 권한 정책이 SAML 연동 사용을 허용(SAML 연동은 IAM 사용자가 아닌 IAM 역할을 통해 이루어짐 — 개념 오류).
- B. **연합 사용자/그룹의 신뢰 정책을 위해 생성된 IAM 역할이 SAML 공급자를 보안 주체(principal)로 설정했는지 확인.**
- C. 테스트 사용자가 회사 IdP의 AWSFederatedUsers 그룹에 없음(그룹 이름 자체가 필수 요건이 아니며, 실제로는 IdP의 SAML 어설션 매핑이 핵심 — 특정 그룹명에 종속되지 않음).
- D. **웹 포털이 SAML 공급자 ARN, IAM 역할 ARN, IdP의 SAML 어설션을 사용해 STS `AssumeRoleWithSAML` API를 호출하는지 확인.**
- E. 온프레미스 IdP의 DNS 호스트 이름이 AWS VPC에서 연결 가능한지 확인(SAML 페더레이션은 사용자의 브라우저가 IdP와 AWS 양쪽에 접근하는 구조이지, AWS VPC가 온프레미스 IdP에 직접 연결할 필요는 일반적으로 없음).
- F. **회사의 IdP가 사용자/그룹을 적절히 매핑하는 SAML 어설션과, 회사에서 적절한 권한을 가진 IAM 역할을 정의했는지 확인.**

**정답: B, D, F**

**해설**
SAML 2.0 페더레이션이 정상 작동하려면: ① IAM 역할의 **신뢰 정책이 SAML 공급자를 보안 주체로 신뢰**해야 하고(B), ② 웹 포털이 **`AssumeRoleWithSAML` API**를 SAML 공급자 ARN/역할 ARN/어설션과 함께 올바르게 호출해야 하며(D), ③ IdP 자체가 **올바른 SAML 어설션**(사용자를 적절한 역할에 매핑)을 발급하도록 구성되어 있어야 합니다(F). 이 세 가지 중 하나라도 어긋나면 특정 사용자만 인증에 실패할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: SAML 페더레이션 사용자는 IAM 사용자가 아니라 임시 자격 증명으로 IAM 역할을 수임하는 방식이므로, "IAM 사용자의 권한 정책"이라는 개념 자체가 맞지 않습니다.
- C: 특정 그룹 이름("AWSFederatedUsers")에 속해야 한다는 요건은 고정된 것이 아니며, 실제 매핑은 IdP의 SAML 어설션 구성에 달려 있습니다.
- E: SAML 페더레이션은 최종 사용자의 브라우저가 IdP와 AWS 각각에 접근하는 구조이며, AWS VPC가 온프레미스 IdP의 DNS에 직접 연결되어야 할 필요는 일반적으로 없습니다.

> 💡 **시험 꿀팁**: SAML 2.0 페더레이션 문제 해결 시 확인할 3대 핵심은 **① IAM 역할 신뢰 정책의 SAML 공급자 설정, ② 웹 포털의 `AssumeRoleWithSAML` 호출, ③ IdP의 올바른 SAML 어설션(사용자-역할 매핑)**입니다.
