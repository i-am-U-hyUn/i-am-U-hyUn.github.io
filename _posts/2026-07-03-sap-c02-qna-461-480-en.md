## QUESTION 461

**Question**: A company runs EC2 instances across multiple accounts, and a specific software license requires confirming, **in a cryptographically provable way**, which country/Region an instance is physically running in — not just trusting a Region setting value, but verifying it at the hardware level. What's the solution?

**Choices**
- A. Only check the instance's Region tag and metadata (tags/metadata are software-set values that could be tampered with, failing the strict "cryptographically provable" requirement).
- B. **Leverage the attestation feature provided by AWS Nitro System-based instances, verifying trusted hardware root-of-trust information — including physical execution location — via a cryptographic attestation document from the Nitro hardware the instance runs on.**
- C. Check only the Region parameter specified at instance launch in CloudTrail logs (CloudTrail only records the Region parameter a user specified in an API call — this doesn't cryptographically prove the actual physical execution location).
- D. Have the instance itself connect to an on-premises verification server in each Region and self-report its location (an instance self-reporting its own location is software-layer self-reporting, not hardware-level cryptographic attestation).

**Correct Answer: B**

**Explanation**
The **AWS Nitro System** uses a hardware-based security model, providing a **cryptographic attestation** scheme for the hardware an instance runs on via Nitro cards and the Nitro Security Chip (Nitro Enclaves' attestation feature is a representative example). This lets you perform trustworthy verification based on a hardware root of trust, rather than trusting software-layer setting values (tags, metadata).

**Why the other choices are wrong**
- A: Tags/metadata are software-set values that could be tampered with — not cryptographic attestation.
- C: CloudTrail only records API call parameters, not hardware-level proof of physical execution location.
- D: An instance self-reporting relies on trusting the software layer — different from hardware-based attestation.

> 💡 **Exam tip**: To **cryptographically, hardware-level prove** an instance's physical execution environment, verification based on **AWS Nitro System attestation** is the standard answer.

## QUESTION 462

**Question**: A company wants to centrally view the software inventory (installed applications, versions) of EC2 instances running across multiple AWS accounts, and quickly find all instances with a specific software (e.g., a vulnerable library version) installed — without connecting to each instance individually. How?

**Choices**
- A. SSH into each instance and manually check the list of installed packages (manual checking at a scale of hundreds to thousands of instances is very inefficient and time-consuming).
- B. **Use AWS Systems Manager Inventory to automatically collect each instance's installed application/version information via the SSM agent, and quickly search centrally for instances with specific software installed, via the Systems Manager console or an Athena query.**
- C. Track installed software with a Config rule (Config mainly tracks AWS resource configuration state; SSM Inventory is the dedicated feature for collecting the application inventory installed inside an instance).
- D. Check software inventory with Trusted Advisor (Trusted Advisor provides general best-practice checks and doesn't offer detailed in-instance software inventory collection).

**Correct Answer: B**

**Explanation**
**AWS Systems Manager Inventory** automatically collects metadata like applications, files, and network configuration from instances with the SSM agent installed, letting you view it centrally. The collected inventory data can be searched directly in the console or exported to S3 and queried via Athena, letting you quickly identify every instance with a specific vulnerable library version installed across multiple accounts.

**Why the other choices are wrong**
- A: Manual individual checking is very inefficient at scale.
- C: Config focuses on AWS resource configuration tracking; in-instance software inventory is SSM Inventory's dedicated domain.
- D: Trusted Advisor is a general best-practice check tool with no detailed software inventory collection feature.

> 💡 **Exam tip**: To **centrally collect/search installed software inventory** across many EC2 instances, **AWS Systems Manager Inventory** is the standard answer.

## QUESTION 463

**Question**: A company uses Amazon MQ (ActiveMQ engine) to handle messaging for a legacy JMS-based application, and wants automatic failover with no message loss if a broker instance fails, along with **higher availability than active-standby** (multiple nodes active simultaneously). What's the solution?

**Choices**
- A. Only use Amazon MQ's active/standby broker (active/standby has only one broker active at a time — different from this question's desired higher-availability configuration with "multiple nodes active simultaneously").
- B. **Use Amazon MQ for RabbitMQ's cluster deployment, configuring a cluster where multiple broker nodes operate active simultaneously (assuming the application is compatible with the RabbitMQ protocol).**
- C. Use a single broker instance with regular snapshot backups (a single broker has no automatic failover at all on failure, and snapshot restoration carries downtime and message-loss risk).
- D. Put an ALB in front of the broker and route to several independent broker instances (unlike a typical stateless web server, a message broker holds state [queues, messages], so simply load-balancing traffic across independent brokers via ALB can't guarantee message consistency or ordering).

**Correct Answer: B**

**Explanation**
Amazon MQ supports both ActiveMQ and RabbitMQ engines. Of these, **Amazon MQ for RabbitMQ's cluster deployment** can configure a cluster where multiple broker nodes operate **active simultaneously**, providing higher availability — the remaining nodes keep handling traffic even if one broker fails (the ActiveMQ engine centers on active/standby). This does require the application to be compatible with the RabbitMQ protocol (AMQP, etc.).

**Why the other choices are wrong**
- A: Active/standby has only one active at a time — different from this question's desired multi-active-node configuration.
- C: A single broker has no automatic failover, and snapshot restoration carries downtime/loss risk.
- D: A message broker holds state, so simple ALB distribution can't guarantee message consistency/ordering.

> 💡 **Exam tip**: For a message broker needing a **high-availability cluster with multiple nodes active simultaneously**, **Amazon MQ for RabbitMQ's cluster deployment** is the standard answer (assuming RabbitMQ protocol compatibility).

## QUESTION 464

**Question**: A company wants to enforce network policy in an EKS cluster so pods in one namespace can't communicate with pods in another. They learn that while the default Amazon VPC CNI plugin assigns VPC IPs directly to pods, enforcing a standard Kubernetes NetworkPolicy requires additional configuration. What's the solution?

**Choices**
- A. Separate each namespace into its own subnet and control between subnets with NACLs (Kubernetes pods are scheduled independent of subnet boundaries; physically separating subnets per namespace doesn't fit Kubernetes's network-policy model and isn't practical).
- B. **Enable network policy support in the Amazon VPC CNI plugin (configure the NetworkPolicy controller), so defining standard Kubernetes NetworkPolicy resources finely controls traffic between namespaces/pods.**
- C. Fully replace with a third-party CNI plugin (Calico, etc.) (viable, but since Amazon VPC CNI itself natively supports network-policy features now, if you're already using VPC CNI, enabling the native feature is simpler and more standard than a full replacement).
- D. Manually assign and manage individual security groups per pod (Security Groups for Pods is a viable feature, but for the goal of comprehensive, native Kubernetes policy enforcement between namespaces, NetworkPolicy is more suitable and simpler to manage).

**Correct Answer: B**

**Explanation**
The Amazon VPC CNI plugin **natively supports** network-policy features; enabling it lets you define standard **Kubernetes NetworkPolicy** resources (e.g., allowing ingress only from pods with a specific namespace label) to finely control traffic between namespaces/pods. This is the simplest and most standard way to implement standard Kubernetes-style network isolation in EKS with no full replacement to a third-party CNI needed.

**Why the other choices are wrong**
- A: Pods are scheduled independent of subnet boundaries, making per-namespace subnet separation impractical.
- C: A full third-party CNI replacement is viable but unnecessary since VPC CNI already natively supports policy features.
- D: Per-pod security groups are a viable alternative, but standard NetworkPolicy is more direct for namespace-to-namespace policy enforcement.

> 💡 **Exam tip**: To control traffic between namespaces/pods in EKS via **standard Kubernetes NetworkPolicy**, **enabling the Amazon VPC CNI's network-policy feature** is the standard answer.

## QUESTION 465

**Question**: A company's legacy on-premises application relies on a specific hardware security module (HSM)'s PKCS#11 interface for cryptographic operations, and they want to migrate it to AWS while keeping the application code (PKCS#11 call style) unchanged. What's the solution?

**Choices**
- A. Switch to AWS KMS and rewrite the application code to use KMS API calls (KMS is a strong managed key service, but doesn't natively support the PKCS#11 interface, requiring a major application code rewrite — contradicting the "no code changes" requirement).
- B. **Use AWS CloudHSM, configuring the existing application to communicate with CloudHSM's hardware security module via the standard PKCS#11 interface, using the PKCS#11 library CloudHSM provides, with no code changes.**
- C. Store the encryption key in Secrets Manager and rewrite the application to fetch it via API (Secrets Manager is a secret storage/retrieval service and doesn't provide a PKCS#11 standard interface — requires code rewriting).
- D. Keep the on-premises HSM as-is and move only the application server to AWS via VPN (keeping the on-premises HSM doesn't fit the goal of a full AWS migration and increases hybrid complexity).

**Correct Answer: B**

**Explanation**
**AWS CloudHSM** provides libraries supporting industry-standard cryptographic interfaces like **PKCS#11**, Java Cryptography Extension (JCE), and Microsoft CryptoNG (CNG). An existing on-premises application relying on PKCS#11 can simply change its connection configuration to CloudHSM's PKCS#11 library, letting it use CloudHSM's dedicated hardware security module with no change to the application's cryptographic call code itself.

**Why the other choices are wrong**
- A: KMS doesn't natively support the PKCS#11 standard interface, requiring code rewriting.
- C: Secrets Manager uses its own API rather than a PKCS#11 interface, requiring code changes.
- D: Keeping the on-premises HSM doesn't fit the full-migration goal.

> 💡 **Exam tip**: To migrate a **legacy application relying on the PKCS#11 interface** to AWS with no code changes, **AWS CloudHSM** (providing a PKCS#11 library) is the standard answer.

## QUESTION 466

**Question**: A company wants to automatically check, in its deployment pipeline, whether Lambda functions running across multiple accounts use a third-party library with a known vulnerability (e.g., an npm/pip package with a specific CVE) in their code dependencies, and **block the deployment itself** if a vulnerability is found. What's the solution?

**Choices**
- A. Scan Lambda functions with Amazon Inspector after deployment to check for vulnerabilities after the fact (Inspector's Lambda scanning is a valid, ongoing monitoring method, but this question explicitly requires preventive "blocking the deployment itself," which needs a pre-check integrated into the deployment pipeline).
- B. **Add a build stage to the CI/CD pipeline (CodePipeline/CodeBuild, etc.) that integrates a software composition analysis (SCA) tool, scanning code dependencies for known vulnerabilities (CVEs) before deployment, and failing the pipeline itself to block deployment if a vulnerability is found.**
- C. Minimize the Lambda function's execution role IAM permissions (minimizing IAM permissions is a good least-privilege practice, but isn't a feature for checking code-dependency vulnerabilities or blocking deployment).
- D. Monitor CloudWatch logs for error patterns after function deployment (log monitoring is an after-the-fact error-detection tool, a different purpose than pre-deployment vulnerability checking and blocking).

**Correct Answer: B**

**Explanation**
To block deployment proactively, you need to **integrate vulnerability scanning into the CI/CD pipeline**. Adding a third-party SCA (Software Composition Analysis) tool or related scanning logic to the build stage (CodeBuild) of AWS CodePipeline, checking dependencies for known CVEs before code is deployed, and **failing the build/pipeline itself** if a vulnerability is found so it doesn't proceed to the deployment stage, is the standard "shift-left" security approach.

**Why the other choices are wrong**
- A: Inspector's after-the-fact scanning is useful ongoing monitoring, but different from the "block deployment itself" preventive requirement.
- C: Minimizing IAM permissions is a different security principle, unrelated to code-dependency vulnerability checking.
- D: Log monitoring is an after-the-fact response tool.

> 💡 **Exam tip**: To **pre-check code dependencies for known vulnerabilities and block deployment itself** in a deployment pipeline, **integrating SCA (vulnerability scanning) into the CI/CD pipeline's build stage** is the standard answer.

## QUESTION 467

**Question**: A company wants an API Gateway REST API to route requests to **different backend Lambda function versions** (e.g., v2 under canary deployment or stable v1) based on a specific header value or query parameter combination. They want clients to explicitly select which version to use via a header — not simple random traffic splitting. What's the solution?

**Choices**
- A. Only use Lambda function alias weighted traffic shifting (alias weighting suits random-ratio-based traffic splitting but doesn't fit the requirement of deterministically choosing a specific version based on a specific header value).
- B. **Use API Gateway's request mapping template or Lambda proxy integration together with API Gateway stage variables, or a custom Lambda function (or a header-based routing configuration in API Gateway), to explicitly determine which Lambda alias/version to invoke based on a specific header value.**
- C. Distribute across two API Gateway endpoints via Route 53 weighted routing (DNS-based weighted routing doesn't support fine-grained conditional routing based on a header value and is closer to random-ratio-based distribution).
- D. Implement header-based routing using only CloudFront cache policies (a CloudFront cache policy is for determining the cache key and isn't itself a feature for deciding routing to different backend Lambda versions).

**Correct Answer: B**

**Explanation**
To deterministically call a different Lambda version based on a specific header value in API Gateway, you can leverage API Gateway's **stage variables** in the alias portion of the Lambda function ARN, or configure logic in front of the integration that checks the header value and selects the appropriate Lambda alias (a mapping template or a lightweight routing Lambda). This implements deterministic routing, like a client explicitly choosing v1/v2 via a header.

**Why the other choices are wrong**
- A: Alias weighting is random-ratio-based — a different mechanism than deterministic selection based on a header value.
- C: Route 53 weighted routing is DNS-layer random-ratio distribution and doesn't support header-based conditional routing.
- D: A CloudFront cache policy is for caching, not a backend routing decision mechanism.

> 💡 **Exam tip**: To **deterministically call a different Lambda version/alias based on a specific header value** in API Gateway, using stage variables or custom routing logic is the standard answer — distinguish this from random-ratio splitting (alias weighting).

## QUESTION 468

**Question**: A company regularly analyzes log files stored in an S3 bucket, and wants to confirm whether the log files' compression format (gzip) affects Athena query performance. They want to keep using compression, but in a way **Athena can split and read files in parallel (splittable)**. They learn standard gzip isn't splittable. What's the alternative?

**Choices**
- A. Don't use compression at all and store raw text (giving up compression increases storage cost and scanned data volume, raising query cost too — this sidesteps rather than solves the goal of splittable compression).
- B. **Use a splittable compression format like BZip2 or LZO (with indexing), or use a columnar format like Parquet/ORC (these formats support internal block-level compression enabling parallel reads).**
- C. Merge all log files into one very large gzip file (a single large gzip file is still non-splittable, and can actually reduce parallel-processing opportunity further, worsening performance).
- D. Just change the gzip-compressed file's extension to .txt (changing the extension doesn't change the actual compression format [or its splittability] and adds only the risk of Athena misinterpreting the file).

**Correct Answer: B**

**Explanation**
Standard **gzip** is a stream-compression method that can't be split and read in parallel (non-splittable) — a single large gzip file can't be processed in parallel by multiple workers; a single worker must read it sequentially from start to finish. To fix this, use a compression format like **BZip2** (inherently splittable), or more standardly, switch to a **columnar format like Parquet/ORC** (internally compressed block-by-block, enabling both parallel reads and column pruning) — the standard way to optimize Athena query performance.

**Why the other choices are wrong**
- A: Giving up compression increases cost and scan volume — not a fundamental fix.
- C: Merging into one large gzip file is still non-splittable and can actually reduce parallelism.
- D: Changing the extension doesn't change the actual file format.

> 💡 **Exam tip**: To have Athena **split and read compressed log files in parallel (splittable)**, using a splittable compression format like BZip2 or a **columnar format like Parquet/ORC** is the standard answer. Remember standard gzip isn't splittable.

## QUESTION 469

**Question**: A company wants to grant AWS resource access permissions based on Active Directory (AD) group membership, across multiple AWS accounts integrated with on-premises AD. They want to keep the existing AD infrastructure, centrally managing user provisioning/deprovisioning in AD, while providing SSO to the AWS console/CLI. How?

**Choices**
- A. Create separate IAM users in each AWS account and write a script to manually sync with AD (manual syncing risks AD changes not being reflected immediately, and management burden grows exponentially as accounts increase).
- B. **Integrate AWS IAM Identity Center with the existing on-premises AD via AWS Directory Service's AD Connector (or a trust relationship), automatically mapping permission sets for multiple AWS accounts based on AD group membership, providing SSO.**
- C. Create a Cognito user pool in each account and integrate individually with AD (Cognito is mainly for custom application authentication; IAM Identity Center is the standard for SSO to multiple AWS account consoles themselves).
- D. Fully retire AD and migrate all users to IAM Identity Center's built-in directory (contradicts the requirement to keep the existing AD infrastructure, and is an unnecessarily large migration).

**Correct Answer: B**

**Explanation**
**AWS IAM Identity Center** can integrate with an existing on-premises Active Directory (via AWS Directory Service's AD Connector or a bidirectional trust), letting AD's users/groups serve directly as the identity source. Configuring **permission sets** for multiple AWS accounts to automatically map based on AD **group membership** lets user provisioning/deprovisioning continue to be centrally managed in the existing AD, while providing SSO to the AWS console/CLI — the standard hybrid identity-management pattern.

**Why the other choices are wrong**
- A: A manual sync script carries high delay/inconsistency risk and grows management burden as accounts increase.
- C: Cognito specializes in custom application authentication; IAM Identity Center is standard for SSO across many AWS accounts.
- D: Retiring the existing AD is an unnecessarily large change contradicting the requirement to keep it.

> 💡 **Exam tip**: To provide **SSO access to multiple AWS accounts based on existing on-premises AD group membership**, **IAM Identity Center + AD integration (AD Connector/trust relationship)** is the standard answer.

## QUESTION 470

**Question**: A data science team needs SageMaker notebook instances to access training data, which is stored in S3, and regulations require access with **no internet traversal at all**. The notebook instance itself must also run in a private subnet isolated from the public internet. What's the solution?

**Choices**
- A. Place the SageMaker notebook instance in a public subnet and allow only specific IPs via a security group (placing it in a public subnet directly contradicts the "isolated from the public internet" requirement).
- B. **Create the SageMaker notebook instance with a VPC attachment in a private subnet, and configure a VPC endpoint for S3 (gateway or interface) in that VPC, so the notebook accesses S3 training data privately with no internet traversal.**
- C. Access S3 from the notebook instance via a NAT Gateway (going through a NAT Gateway ultimately uses an internet path, violating the strict "no internet traversal at all" requirement).
- D. Pre-copy training data to the notebook instance's local EBS volume for use (a one-time local copy is possible, but is an unscalable approach requiring manual re-copying for continuously updated training data, and differs from the core requirement of "S3 access").

Creating the SageMaker notebook instance attached to a VPC in a **private subnet** isolates it from the public internet. - A: A public subnet contradicts the isolation requirement.
- C: Going through a NAT Gateway is ultimately an internet path, violating "no internet traversal at all."
- D: A local copy doesn't scale and isn't a fundamental solution for continuously updated data.

> 💡 **Exam tip**: For a SageMaker notebook needing to **access S3 from a private subnet with no internet**, **private subnet placement + an S3 VPC endpoint** is the standard answer.

## QUESTION 471

**Question**: In an EKS cluster shared by multiple development teams, a company wants to force each team's workload to be scheduled only onto a specific node group (e.g., GPU nodes, Spot nodes, On-Demand nodes). How do you prevent Team A's pod from accidentally being scheduled onto Team B's expensive dedicated GPU nodes?

**Choices**
- A. Give each team a separate EKS cluster (differs from the premise of using a shared cluster and increases management burden as cluster count grows).
- B. **Set a taint on the nodes, and specify a matching toleration on pods that should use those nodes, additionally combined with node affinity, so a specific team's workload is scheduled only onto the designated node group and other workloads are excluded.**
- C. Only finely configure resource requests/limits (resource requests/limits only control the CPU/memory amount allocated to a pod — not a placement-control mechanism forcing scheduling onto a specific node group).
- D. Place each node group in a separate subnet and isolate via subnet routing (the Kubernetes scheduler places pods based on node labels/taints, not subnets, so subnet separation alone doesn't control scheduling itself).

**Correct Answer: B**

**Explanation**
Kubernetes **taints and tolerations** let you constrain a specific node so "only pods with a matching toleration can be scheduled here," and combining this with **node affinity** to steer a specific workload to always be scheduled only onto the designated (label-based) node group effectively prevents Team A's workload from accidentally landing on Team B's dedicated GPU nodes. This is the standard way to implement per-node-group workload isolation in Kubernetes environments, including EKS.

**Why the other choices are wrong**
- A: Providing a separate cluster differs from the shared-cluster premise and increases management burden.
- C: Resource requests/limits control resource allocation — a different mechanism than node-group placement control.
- D: The Kubernetes scheduler operates based on node labels/taints, not subnets, so subnet separation alone doesn't control scheduling.

> 💡 **Exam tip**: In EKS/Kubernetes, to **schedule a specific workload only onto a designated node group and exclude other workloads**, **taints/tolerations + node affinity** is the standard answer.

## QUESTION 472

**Question**: A company manages infrastructure with CloudFormation, and a specific stack update risks accidentally including a change that **deletes or replaces** a production database resource (an RDS instance). They want to prevent such a destructive change from being accidentally applied at stack-update time. What's the solution?

**Choices**
- A. Manually check the RDS console after a CloudFormation stack update to confirm the instance is still there (checking after the fact can't undo a deletion/replacement that already happened — not prevention).
- B. **Generate a CloudFormation change set to preview planned changes (including whether they're a delete or replacement) before actually applying, holding off or canceling execution if a destructive change is included. Additionally, set a stack policy or DeletionPolicy: Retain on the resource to protect against accidental deletion/replacement.**
- C. Manually update resources individually in the console every time instead of CloudFormation (manual individual updates give up IaC's benefits, still carry mistake risk, and actually reduce consistency).
- D. Only enable termination protection on all stacks (termination protection only prevents the entire stack from being deleted [delete-stack] — it's not fine-grained protection against an individual resource being replaced/deleted during a stack update; change-set review and resource-level policies are more direct).

**Correct Answer: B**

**Explanation**
A **CloudFormation change set** simulates which resources will be added/modified/**deleted/replaced** before actually updating the stack, letting you review a destructive change in advance and decide whether to proceed. Additionally, setting a **stack policy** on an important resource (RDS, etc.) to prohibit specific update actions, or setting `DeletionPolicy: Retain` (or `Snapshot`), provides an extra safeguard preventing actual resource deletion even if the resource's definition is accidentally removed or replaced in the stack.

**Why the other choices are wrong**
- A: Checking after the fact can't undo an already-occurred deletion/replacement — not prevention.
- C: Manual individual updates give up IaC's benefits and actually increase mistake risk and inconsistency.
- D: Termination protection only prevents deleting the entire stack — not fine-grained protection against individual resource replacement/deletion during an update.

> 💡 **Exam tip**: To **review and prevent destructive changes (delete/replace) in advance** during a CloudFormation stack update, **change set review + a stack policy/DeletionPolicy** is the standard answer.

## QUESTION 473

**Question**: As required by a regulated industry (healthcare), a company must enforce that every AWS resource processing data containing PHI (protected health information) is created/operated **only in a specific Region (the US)**, and wants this control managed at the organization level so it can't be accidentally bypassed. What's the standard way to enforce this at the Organizations level?

**Choices**
- A. Distribute a Region-restriction guideline document to each team (a document-based guideline has no enforcement power and can't prevent mistakes or intentional violations).
- B. **Configure a service control policy (SCP) in Organizations that denies resource creation outside a specific Region, so every user within the OU/account the SCP applies to is categorically blocked from creating any resource outside the allowed Region (the US).**
- C. Create a Config rule per Region to detect violating resources after the fact (after-the-fact detection only finds already-created violating resources — different from preventively blocking creation itself).
- D. Add a Region-restriction condition to each user's IAM policy only (IAM policies must be managed per individual user/role, which is less standard and less effective at bypass-prevention for consistent organization-wide enforcement and automatic application to new users than an SCP).

**Correct Answer: B**

**Explanation**
Configuring a **service control policy (SCP)** that explicitly denies resource-creation API calls outside the approved Region (the US) means **no IAM user or role** (including one with administrator permissions) within the OU/account the SCP applies to can create resources in a disallowed Region. This is the standard governance method for enforcing Region restrictions organization-wide, preventively and unbypassably.

**Why the other choices are wrong**
- A: A document-based guideline has no enforcement power.
- C: Config-rule-based detection is after-the-fact and doesn't block creation itself.
- D: Individual IAM policies must be managed per user, less favorable than an SCP for automatic application to new users or organization-wide consistency.

> 💡 **Exam tip**: To **categorically block resource creation outside a specific Region** organization-wide, an **Organizations Region-restriction SCP** is the standard answer.

## QUESTION 474

**Question**: A company runs order-processing microservices for a large e-commerce platform, and wants to prevent a problem — a specific downstream service (an inventory-check API) becoming intermittently slow or unresponsive — from **cascading throughout the entire order-processing system**. What resilience pattern can be implemented at the application code level?

**Choices**
- A. Only configure a timeout on the downstream service call (a timeout alone doesn't prevent wasting resources by continuing to send requests to a repeatedly failing downstream service — not a pattern that fundamentally prevents cascading failure).
- B. **Implement the circuit breaker pattern: when the downstream service's failure rate exceeds a threshold, immediately block requests to that service entirely for a period [open state] and return a fallback response, then gradually test recovery with a small number of requests in a half-open state.**
- C. Increase the retry count for the downstream service call to unlimited (unlimited retries actually send even more requests to an already-overloaded downstream service, worsening the situation, and also exhausts the caller's own resources, increasing cascading-failure risk).
- D. Re-consolidate all microservices into a single monolithic application (abandons the microservices architecture itself — an excessive redesign and not the solution this question calls for).

**Correct Answer: B**

**Explanation**
The **circuit breaker pattern** monitors a downstream service's failure rate, and when it exceeds a threshold, "opens" the circuit to immediately block requests to that service for a period, returning a **fallback response** instead (e.g., cached data, a default value, a graceful error message). This prevents wasting resources by continuing to send requests to a failing downstream service or accumulating wait times that propagate failure up to calling services. After a period, it transitions to a "half-open" state to test recovery with a small number of requests, closing the circuit again once normal.

**Why the other choices are wrong**
- A: A timeout alone doesn't stop repeated failing requests, not fundamentally preventing cascading failure.
- C: Unlimited retries actually worsen the situation and increase cascading-failure risk.
- D: Re-consolidating to a monolith is an excessive measure beyond this question's scope.

> 💡 **Exam tip**: To **prevent a downstream failure from cascading** in microservices, the application-level **circuit breaker pattern** is the standard answer.

## QUESTION 475

**Question**: A company wants to prevent a specific heavy analytical query (a long-running reporting query) on an Aurora PostgreSQL cluster from affecting production transaction-processing performance. They want to isolate these heavy queries onto separate compute resources, but without creating a separate replica for the underlying data or moving data. How?

**Choices**
- A. Create a separate read replica dedicated to analytical queries (viable, but the question explicitly states they want to handle this "without creating a separate replica or moving data," so this doesn't fit the condition).
- B. **Use Aurora's reader endpoint or a custom endpoint instead of the cluster endpoint to route analytical queries to a specific instance group, or separately add an Aurora Serverless v2 reader instance for query isolation using Amazon RDS Performance Insights, isolating the analytical workload from the transaction-processing instances within the same cluster.**
- C. Pause production transactions every time before running analytical queries (pausing transactions directly and negatively impacts service availability — impractical).
- D. Remove the analytical query from the application and stop running it (abandons the business requirement of analytical reporting itself — not a solution).

**Correct Answer: B**

**Explanation**
Aurora lets you create a **custom endpoint** within a cluster to route traffic only to a specific subset of instances (e.g., reader instances designated for analytics only). Routing heavy analytical queries to this custom endpoint isolates compute resources while still sharing the same cluster's storage (data), minimizing impact on the production transaction-processing instances. This is Aurora's standard feature for isolating workloads with no separate full replica created or data moved.

**Why the other choices are wrong**
- A: Creating a separate replica is the approach the question explicitly excludes.
- C: Pausing transactions directly harms service availability — impractical.
- D: Removing the analytical query abandons the business requirement.

## QUESTION 476

**Question**: A company wants to support Lambda function execution roles across multiple accounts needing temporary elevated permissions valid **only under specific conditions** (e.g., only within a specific VPC, or only during specific hours). ## QUESTION 480

**Question**: A company has multiple teams within an organization independently managing infrastructure with Terraform, and wants to **safely store the Terraform state file centrally, while preventing multiple people from modifying the same state simultaneously (locking)**. What's the standard backend configuration for this on AWS?

**Choices**
- A. Store the state file on each team member's local computer (local storage isn't shared among team members, loses the state file itself if a computer is lost, and offers no concurrent-modification prevention).
- B. **Use an S3 bucket as the Terraform state file's remote backend (with versioning enabled to preserve history), and configure a DynamoDB table together as the state-locking mechanism, preventing multiple users from modifying the same state simultaneously.**
- C. Store the state file content directly in an RDS database (Terraform's standard S3-backend ecosystem doesn't support using RDS as the state store — S3+DynamoDB is the officially documented standard combination).
- D. Commit the state file to a CodeCommit repository for version control (Git-based version control doesn't provide a concurrent-locking mechanism for the state file, risking conflict/corruption if multiple people run apply simultaneously).

**Correct Answer: B**

**Explanation**
The standard remote backend configuration for team collaboration in Terraform is the combination of an **S3 bucket** (storing the state file, with versioning preserving history and enabling recovery from mistakes) and a **DynamoDB table** (the state-locking mechanism). While someone runs `terraform apply`, a lock item is created in DynamoDB, preventing another user from attempting to modify the same state simultaneously (state locking). This is the officially recommended standard pattern for safely, centrally managing Terraform state in an AWS environment.

**Why the other choices are wrong**
- A: Local storage provides neither sharing, backup, nor locking.
- C: RDS isn't used as a state store in Terraform's standard S3-backend ecosystem.
- D: Git-based version control has no concurrent-locking mechanism, risking conflicts.

> 💡 **Exam tip**: For a team to **safely centrally store a Terraform state file and prevent concurrent modification (locking)**, the **S3 (state storage, versioning) + DynamoDB (state locking)** combination is the standard answer.
