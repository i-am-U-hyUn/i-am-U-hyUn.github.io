## 1. 왜 온톨로지인가

AI 경쟁력의 기준이 **데이터의 양**에서 **데이터를 연결해 맥락을 부여하는 능력**으로 옮겨 가고 있다. LLM을 기업에 도입할 때 가장 큰 걸림돌은 사실이 아닌 내용을 그럴듯하게 만들어내는 **환각(Hallucination)**인데, 원인은 기업 고유의 정보가 체계 없이 AI에 주어지기 때문이다.

온톨로지는 이 문제를 푸는 열쇠로 소개된다.

- **건축 비유**: 자재(데이터)를 아무리 쌓아도 설계도(온톨로지)가 없으면 건물이 아니라 자재 더미다.
- **지도 비유**: 위성 사진(Raw Data)만으로는 길을 못 찾는다. 도로명·건물 정보·교통 법규(온톨로지)가 입혀져야 내비게이션(AI)이 길을 안내할 수 있다.

## 2. 온톨로지란

온톨로지는 **현실 세계의 비즈니스를 디지털 공간에 복제(Digital Twin)하기 위한 규칙과 언어의 집합**이다. 팀 버너스 리의 표현을 빌리면 "사물과 사물 사이의 관계를 컴퓨터가 이해할 수 있는 언어로 정의한 것"이다.

엑셀, ERP, 로그처럼 흩어진 데이터를 **의미(Semantic)**라는 접착제로 묶어 하나의 지식 체계로 통합하는 것이 핵심이다.

### RDBMS vs 온톨로지 기반 지식 그래프

| 항목 | RDBMS (SQL) | 온톨로지 기반 지식 그래프 |
|---|---|---|
| **핵심 철학** | 저장 효율성, 정형화된 틀 | 데이터 연결과 맥락 |
| **구조** | 행과 열의 테이블 | 노드와 엣지의 네트워크 |
| **관계 처리** | JOIN, 연결이 복잡할수록 느려짐 | Index-free Adjacency, 관계를 바로 따라감 |
| **AI 활용** | 검색·조회 중심 | 다단계 추론에 적합 |
| **변경 대응** | 스키마가 바뀌면 전체 수정 | 노드나 관계를 추가해 확장 |

## 3. 팔란티어가 말하는 온톨로지

팔란티어의 온톨로지는 지식을 분류하는 사전을 넘어 **조직의 운영 세계를 그대로 옮긴 운영 레이어(operational digital twin)**에 가깝다. 데이터셋과 모델 위에 업무 의미를 올리고, 그 위에서 **조회뿐 아니라 변경(쓰기)까지 안전하게** 처리하게 만든다.

> 조직이 실제로 쓰는 **명사(대상)와 동사(행위)를 표준화**해 서로 다른 데이터와 시스템을 하나의 운영 모델로 묶고, 그 위에서 앱·워크플로·AI가 읽고, 추론하고, 행동하게 만드는 레이어
{: .prompt-tip }

### 3-1. 구성 요소: 객체 · 관계 · 행동

| 구성 요소 | 의미 | 예시 |
|---|---|---|
| **Object Type** | 현실의 대상(명사). 객체 하나는 타입의 인스턴스 1건, Object set은 조건으로 묶은 집합 | 시스템, 서비스, 장애, 변경 요청, 고객기관, 계약 |
| **Link Type** | 두 객체 타입 사이의 관계(그래프의 간선). 데이터셋 관점에서는 조인 정의와 비슷함 | 서비스 → 배포됨 → 클러스터, 변경 → 유발 → 장애 |
| **Action Type** | 한 번에 수행하는 객체·속성·링크의 생성·수정·삭제 묶음. 부수 효과 포함 가능 | 승인, 배포, 점검, 조치 |

Action Type이 있다는 점이 중요하다. 온톨로지가 대시보드용 의미층이 아니라 **운영 시스템처럼 쓰기를 통제**하는 구조라는 뜻이기 때문이다.

### 3-2. 일반 데이터 모델과 다른 점

ERD나 스타 스키마는 분석용 구조가 중심이다. 팔란티어 온톨로지는 여기에 더해 다음을 노린다.

- **의미의 표준화**: 부서마다 다른 용어를 객체·속성·관계로 합의해 고정
- **운영 앱의 기반**: 사용자가 테이블이 아니라 객체를 기준으로 탐색하고 업무 처리
- **쓰기 포함**: 액션으로 변경을 통제하고 감사·거버넌스에 맞춤
- **AI 실행 환경**: 데이터·로직·액션을 묶어 AI가 읽고 실행할 수 있게 함

### 3-3. 팔란티어식 구축 4단계

업무 관점(Top-down)과 데이터 관점(Bottom-up)을 같이 쓴다.

1. 운영 세계를 **명사와 동사로 분해**해 Object, Link, Action에 매핑
2. 데이터셋과 모델을 객체 타입·속성·링크·액션에 **매핑**
3. 개발 상태(Active, Experimental, Deprecated 등) 같은 메타데이터와 승인·감사 흐름으로 **거버넌스** 적용
4. 앱, 워크플로, AI 에이전트가 **객체 탐색과 액션**으로 바로 쓰게 함

### 3-4. LLM·에이전트와 결합할 때

LLM은 그럴듯한 답을 만들 수 있지만, 기업 운영에서는 **정확한 현재 상태(grounded state)**와 **허용된 행동(allowed actions)**이 더 중요하다.

| 개념 | 의미 |
|---|---|
| 온톨로지 | AI가 읽을 수 있는 기업 운영 상태 |
| 액션 타입 | AI가 실행할 수 있는 안전한 버튼(트랜잭션) |

이 조합이 챗봇을 넘어 **운영 에이전트**로 가는 관문이라는 설명이다.

## 4. 온톨로지가 핵심 자산이 되는 이유

| 이유 | 내용 |
|---|---|
| **단일 진실 공급원(SSoT)** | CRM의 "고객"과 ERP의 "고객"이 다른 대상을 가리키는 혼란을 개념 정의로 정리. MDM의 진화형 |
| **환각 완화** | LLM이 검증된 사실과 관계를 담은 지식 그래프를 참조해 답변. "LLM + Knowledge Graph"가 표준 패턴이 되는 이유 |
| **다단계 추론** | "특정 고객과 비슷한 계약 구조의 프로젝트 중 장애가 가장 적었던 사례는?"처럼 관계를 따라가는 질문에 답함 |
| **거버넌스** | "계약은 반드시 고객과 연결되어야 한다" 같은 규칙을 SHACL 같은 제약 언어로 검증 |

## 5. 구축은 어떻게 하나

온톨로지는 기술자가 혼자 만드는 산출물이 아니다. 전략, 도메인 지식, AI 활용 방향이 같이 들어가야 한다.

1. **핵심 개념과 관계 정의**: 해결할 문제를 기준으로, 모든 것을 담지 말고 최소한의 핵심 구조부터 설계
2. **전문가 설계 + LLM 자동화**: 뼈대(스키마)는 도메인 전문가가 설계하고, 문서·로그·DB에서 인스턴스를 뽑아 채우는 일은 LLM에 맡김
3. **그래프 DB로 구현**: Neo4j 기준으로 개념 → 노드 레이블, 관계 → 관계 타입, 속성 → 프로퍼티

> LLM에게 스키마까지 자동 생성을 맡기면 기존 데이터의 혼란이 그대로 구조화된다. 뼈대는 사람이, 살은 LLM이 붙이는 역할 분담이 포인트다.
{: .prompt-warning }

## 6. 정리

온톨로지를 만든다는 건 AI에게 회사의 조직도, 업무 매뉴얼, 의사결정 구조를 함께 가르치는 일이다.

- 흩어진 데이터를 관계 중심으로 통합하고
- AI의 판단 근거를 설명 가능한 구조로 제공하고
- 분석 결과를 실제 업무 행동(Action)으로 연결한다

팔란티어의 핵심은 특정 제품보다 **기업의 세계를 하나의 일관된 지식 모델로 정의하고 그 위에서 분석과 실행을 연결한다**는 철학에 있다. 원문은 개념 설명 위주라 실제 도입 사례나 효과 수치는 다루지 않는다.
