## QUESTION 141

**Question**: A company uses EC2 instances in an Auto Scaling group to process videos (30 minutes each) from an AWS Cloud. Instances scale based on the number of items in an SQS queue. A redrive policy (DLQ, maxReceiveCount=1) and a 1-hour visibility timeout are configured. Messages keep appearing in the dead-letter queue, but application logs show no errors. How to fix?

**Choices**
- A. Enable termination protection on the EC2 instances.
- B. Update the SQS visibility timeout to 3 hours.
- C. **Configure scale-in protection on instances that are processing.**
- D. Update the redrive policy and set maxReceiveCount to 0.

**Correct Answer: C**

**Explanation**
The real cause: during the 30-minute processing window, the Auto Scaling group **terminates the instance due to reduced load**. When terminated mid-processing, the message isn't deleted, its visibility timeout expires, it's redelivered, and with `maxReceiveCount=1` it goes straight to the DLQ. **Instance scale-in protection** excludes actively-processing instances from scale-in, fixing the root cause.

**Why the other choices are wrong**
- A: Termination protection only blocks manual/certain-event termination — it does not prevent Auto Scaling scale-in.
- B: A longer visibility timeout doesn't help if the instance itself is terminated by scale-in — not a root-cause fix.
- D: Setting maxReceiveCount to 0 is invalid or behaves differently than intended (e.g., sending messages to DLQ immediately).

> 💡 **Exam tip**: When an Auto Scaling group accidentally terminates an instance mid-way through a long-running job, the answer is almost always **Instance Scale-In Protection.**

## QUESTION 142

**Question**: A company built an API using a regional API Gateway endpoint calling Lambda functions with API Gateway's authorization mechanism. After a design review, a specific set of APIs was identified as not needing public access — they should be **accessible only from within the VPC**, and all APIs must be invoked as an authenticated user. Solution with minimal effort?

**Choices**
- A. Create an internal ALB + target group + attach the Lambda function.
- B. Remove the API Gateway DNS entry + create a Route 53 hosted zone + CNAME record.
- C. **Update the API Gateway endpoint from regional to private. Create an interface VPC endpoint in the VPC. Create a resource policy and attach it to the API. Call the API using the VPC endpoint.**
- D. Provision an EC2 instance inside the VPC running Apache to proxy Lambda calls.

**Correct Answer: C**

**Explanation**
API Gateway supports a **private endpoint type**, and combining it with an **interface VPC endpoint (PrivateLink)** plus a **resource policy** is the standard, minimal-effort way to restrict an API to VPC-only access.

**Why the other choices are wrong**
- A, D: Building a proxy via ALB or EC2/Apache requires far more configuration and ongoing management effort.
- B: DNS tricks alone cannot actually restrict network-level access to the VPC.

> 💡 **Exam tip**: To make an API Gateway API accessible **only from within a VPC**, use the combination of **a private API endpoint + an interface VPC endpoint + a resource policy.**

## QUESTION 143

**Question**: A weather service in eu-west-1 serves high-resolution weather maps stored in S3 alongside static HTML, fronted by CloudFront. The company recently expanded to serve us-east-1 users, who report the weather map view is sometimes slow. Which combination addresses the us-east-1 performance issue? (Choose two.)

**Choices**
- A. Configure a Global Accelerator endpoint for the S3 bucket in eu-west-1 + endpoint group for TCP 80/443 in us-east-1 + create a new S3 bucket in us-east-1 + S3 CRR from eu-west-1.
- B. **Use Lambda@Edge to modify requests from North America to use the us-east-1 S3 bucket.**
- C. Use Lambda@Edge to make North American requests use an S3 Transfer Acceleration endpoint in us-east-1.
- D. **Use Lambda@Edge to modify North American requests to use the us-east-1 S3 bucket, configure a Global Accelerator endpoint for us-east-1 as the CloudFront distribution's origin, and use Lambda@Edge to route requests to this new origin.**

**Correct Answer: B, D**

**Explanation**
The correct approach adds an **S3 bucket in us-east-1 (kept in sync via CRR)**, and uses **Lambda@Edge to dynamically route North American requests to the closer regional origin.** Dynamically switching CloudFront's origin per region at the edge is the standard use case for a **Lambda@Edge origin-request trigger.**

**Why the other choices are wrong**
- A: Attaching Global Accelerator directly to the S3 bucket itself isn't a typical pattern — combining it with CloudFront is more natural.
- C: S3 Transfer Acceleration speeds up uploads — it doesn't address content-download latency in this scenario.

> 💡 **Exam tip**: To have CloudFront dynamically select the **nearest regional origin**, use **Lambda@Edge (origin-request trigger)**, combined with **S3 Cross-Region Replication** to keep content synced across regional buckets.

## QUESTION 144

**Question**: WorkSpaces users can't establish new sessions. FSx for Windows File Server (10TB) is used as profile-sharing storage, and the file system has reached **maximum capacity.** Restore access for users, and also prevent recurrence.

**Choices**
- A. Remove old user profiles + migrate to FSx for Lustre.
- B. **Increase capacity via `update-file-system`. Monitor the FreeStorageCapacity CloudWatch metric. Use EventBridge to invoke a Lambda function to increase capacity as needed.**
- C. Monitor FreeStorageCapacity + use Step Functions to increase capacity.
- D. Remove old profiles + create a second FSx file system + redirect 50% of user profiles.

**Correct Answer: B**

**Explanation**
Satisfying both immediate fix (capacity increase) and prevention (monitoring+automation): **use the `update-file-system` API to increase capacity, monitor the FreeStorageCapacity CloudWatch metric, and trigger a Lambda function via EventBridge to automatically scale capacity when needed.**

**Why the other choices are wrong**
- A: FSx for Lustre isn't suited for Windows profile sharing (HPC-focused, no SMB support), and removing profiles is only a temporary fix.
- C: Step Functions adds unnecessary complexity for this auto-scaling workflow.
- D: Splitting profiles across a second file system only increases operational complexity.

> 💡 **Exam tip**: For FSx capacity management, use the **`update-file-system` API** to scale, and **CloudWatch FreeStorageCapacity + EventBridge + Lambda** for automation — the standard pattern.

## QUESTION 145

**Question**: Delivery confirmations (signatures/photos) are FTP-uploaded from handheld devices to a single EC2 instance, which queries a database, adds metadata, and stores results in S3. As the company scales, connection drops and memory issues occur. Handheld devices cannot be modified. Design a solution maximizing scalability.

**Choices**
- A. Create an AMI + Auto Scaling group of EC2 instances behind an ALB.
- B. AWS Transfer Family (FTP→EFS) + mount to existing EC2.
- C. **AWS Transfer Family (FTP→S3) + S3 event notification → SNS → Lambda to add metadata and update the delivery system.**
- D. Update handheld devices to upload directly to S3 (violates "cannot be modified") + SQS → Lambda.

**Correct Answer: C**

**Explanation**
Since devices can't be modified (FTP must be retained), create a managed FTP server via **AWS Transfer Family that writes directly to S3**, and use **S3 event notifications (via SNS) → Lambda** to serverlessly handle metadata addition and database updates — completely eliminating the single-EC2 bottleneck.

**Why the other choices are wrong**
- A: Merely scales out the existing single-EC2 architecture (where the FTP server itself is the bottleneck) without addressing the root cause.
- B: Storing to EFS and still processing via EC2 leaves the EC2 bottleneck in place.
- D: Violates the explicit constraint that handheld devices cannot be modified.

> 💡 **Exam tip**: To scale a **legacy FTP client that cannot be modified** into a serverless architecture, use **AWS Transfer Family (targeting S3) + S3 event notifications → Lambda** — the standard answer pattern.

## QUESTION 146

**Question**: An ECS (Fargate) + Aurora MySQL application must, per regulatory requirements, be recoverable to a **separate AWS Region** in case of failure, with **no data loss.** Solution with minimal operational overhead?

**Choices**
- A. **Provision an Aurora replica in another Region (Aurora Global Database).**
- B. Set up AWS DataSync for continuous replication to another Region.
- C. Set up AWS DMS for continuous replication to another Region.
- D. Use Amazon DLM to schedule snapshots every 5 minutes.

**Correct Answer: A**

**Explanation**
**Aurora Global Database** (a replica in another Region) is a managed, sub-second cross-Region replication feature native to Aurora — providing cross-Region DR with minimal operational overhead.

**Why the other choices are wrong**
- B: DataSync is for file/object data transfer, not relational database replication.
- C: Manually configuring continuous DMS replication carries far more operational overhead than Aurora Global Database.
- D: Snapshots every 5 minutes don't satisfy a "no data loss" (near-zero RPO) requirement.

> 💡 **Exam tip**: For **cross-Region disaster recovery of Aurora**, the answer is almost always **Aurora Global Database** — far less operational burden than manual DMS/DataSync replication.

## QUESTION 147

**Question**: A financial services company receives ~5,000 plaintext records every 15 minutes over HTTPS with server-side encryption directly into an S3 bucket, containing sensitive credit card PAN data. The company must automatically mask the PAN before sending data to another bucket for internal storage, remove/merge certain fields, and convert records to JSON. The design must also scale easily for future additional feeds.

**Choices**
- A. Lambda (extract→SQS) → Lambda (process→temp S3) → final Lambda converts to JSON once queue empties.
- B. Lambda (extract→SQS) → Fargate container auto-scales to process → scales down once queue empties.
- C. **Create a Glue crawler + custom classifier to build table definitions. On file arrival, a Lambda function starts a Glue ETL job that handles masking/removal/merging/transformation, outputting JSON, then sends results to the internal bucket.**
- D. Glue crawler + custom classifier + Athena queries + EMR ETL job.

**Correct Answer: C**

**Explanation**
**Glue ETL** is optimized for structured transformations like field masking, removal/merging, and format conversion (JSON), and crawler+classifier automatically recognizes schema — making it easy to extend for future new feed formats. Using Lambda merely as a trigger while delegating actual transformation to Glue ETL is best for management overhead and scalability.

**Why the other choices are wrong**
- A, B: Implementing transformation logic directly in Lambda or Fargate means reimplementing Glue's schema management/extensibility benefits.
- D: Spinning up an EMR cluster for every batch is excessively heavy for a 5,000-record/15-minute scale.

> 💡 **Exam tip**: When you need **field masking/removal/merging/format conversion** on structured data with future extensibility in mind, **Glue crawler (schema recognition) + Glue ETL job** is the standard answer.

## QUESTION 148

**Question**: Build a business continuity solution for an on-premises application (physical server, uses MySQL, EC2-compatible OS) with minimal operational overhead in case of failure.

**Choices**
- A. Install AWS Replication Agent + cutover to test instances (for regular drills, cutover on failure).
- B. **Install AWS Replication Agent (including on the MySQL server). Initialize AWS Elastic Disaster Recovery in the target Region. Define launch settings. Frequently perform failover/failback tests from the most recent point in time.**
- C. Create a DMS replication server + target Aurora MySQL DB cluster + SCT CDC task.
- D. Deploy Storage Gateway Volume Gateway + snapshots + restore volumes onto EC2.

**Correct Answer: B**

**Explanation**
**AWS Elastic Disaster Recovery (DRS)** is a managed DR service, purpose-built for exactly this scenario, providing continuous block-level replication and fast failover/failback with minimal operational overhead — even including heterogeneous/physical workloads.

**Why the other choices are wrong**
- A: Cutting over to plain test instances without initializing DRS isn't continuous replication with automated failover.
- C: DMS+SCT is for database (MySQL) migration/sync only — it doesn't cover DR for the entire application server (a physical server).
- D: Manual Storage Gateway-based snapshot/restore carries far more operational overhead than DRS.

> 💡 **Exam tip**: For **DR on AWS of an entire on-premises server** (application + database), the answer is almost always **AWS Elastic Disaster Recovery (DRS)** — distinguish it from DMS (database-only) and Storage Gateway (file/volume-only).

## QUESTION 149

**Question**: Provide secure, read-only access to a company's AWS account for an external auditor (using a single AWS account), following AWS security best practices.

**Choices**
- A. Create a resource policy on all resources in the company account granting access to the auditor's account + assign a unique external ID.
- B. **Create an IAM role in the company's AWS account that trusts the auditor's AWS account. Create an IAM policy with the needed permissions and attach it to the role. Assign a unique external ID to the role's trust policy.**
- C. Create an IAM user in the company account + attach the needed IAM policy + generate API access keys + share with the auditor.
- D. Create an IAM group with the needed permissions + create an IAM user per auditor + add them to the group.

**Correct Answer: B**

**Explanation**
**A cross-account IAM role (with an external ID in the trust policy) + a least-privilege policy** is the AWS-recommended pattern for granting access to external partners/auditors. The external ID prevents the "confused deputy" problem.

**Why the other choices are wrong**
- A: Attaching individual resource policies to every resource is inefficient and not a standard access pattern.
- C, D: Sharing long-lived access keys or IAM user credentials violates security best practices and makes revocation/auditing harder.

> 💡 **Exam tip**: When granting account access to an external auditor/partner, **IAM role + external ID** is always the answer; sharing IAM users/access keys is always wrong.

## QUESTION 150

**Question**: A latency-sensitive transaction platform uses DynamoDB (on-demand capacity) as its storage backend. Design a solution to improve performance while ensuring high availability, with minimal latency.

**Choices**
- A. Create a 2-node DAX cluster; configure the app to read and write through DAX.
- B. **Create a 3-node DAX cluster; configure the app to read through DAX and write directly to the DynamoDB table.**
- C. Create a 3-node DAX cluster; configure the app to read directly from DynamoDB and write through DAX.
- D. Create a single-node DAX cluster; configure the app to read through DAX and write directly to the DynamoDB table.

**Correct Answer: B**

**Explanation**
**DAX (DynamoDB Accelerator) is a cache — write acceleration is meaningless, only reads benefit.** For high availability, at least **3 nodes** (multi-AZ) are required, and writing **directly** to the DynamoDB table (bypassing DAX write-through overhead) is the standard pattern.

**Why the other choices are wrong**
- A: 2 nodes is insufficient for full high availability (3+ recommended minimum).
- C: Reading directly from DynamoDB bypasses DAX's low-latency caching benefit entirely.
- D: A single node doesn't satisfy the high-availability requirement at all.

> 💡 **Exam tip**: DAX is a **read-only cache** — the pattern is always "read through DAX, write directly to DynamoDB," and high availability requires **at least 3 nodes.**

## QUESTION 151

**Question**: A migrated application: frontend (static website, 2 EC2 behind an ALB), backend (Python, 3 large general-purpose on-demand EC2 behind another ALB). Monthly traffic is high overall but concentrated at lunchtime, with minimal traffic otherwise. Optimize infrastructure cost without hurting availability. (Choose two.)

**Choices**
- A. Change all EC2 instances to compute-optimized instances with the same core count.
- B. **Move the frontend to a static website hosted on Amazon S3.**
- C. Deploy the frontend via AWS Elastic Beanstalk, keeping the same instance type.
- D. Change all backend EC2 instances to Spot Instances.
- E. **Deploy the backend Python application on general-purpose burstable EC2 instances with the same core count.**

**Correct Answer: B, E**

**Explanation**
Moving the static frontend to **S3 static website hosting** (B) eliminates the need for EC2/ALB entirely. Since backend traffic is intermittent (lunchtime spike, minimal otherwise), switching from always-max-performance general-purpose instances to **burstable (T-family) instances** (E) is cheap at baseline and handles peaks via CPU credits.

**Why the other choices are wrong**
- A: Compute-optimized instances suit CPU-intensive workloads — unrelated to this scenario's "intermittent traffic" problem.
- C: Moving to Elastic Beanstalk with the same instance type yields no cost savings.
- D: Switching the backend (which must handle transactions reliably) to Spot risks interruption, violating "without hurting availability."

> 💡 **Exam tip**: For **intermittent/bursty** workloads, use **T-family burstable instances**; for static content, move to **S3 static hosting** — the standard cost-optimization pattern.

## QUESTION 152

**Question**: An EKS (EC2) + RDS MySQL ticketing platform, with new features being developed on Fargate. Rare peak demand tied to specific event dates. Most cost-effective setup?

**Choices**
- A. Standard RIs (baseline) + Spot (peak) + 1-year all-upfront RI for DB (sized to expected annual max load).
- B. **Compute Savings Plans (expected median load) + On-Demand Capacity Reservations scaled to peak event dates + 1-year no-upfront RI for DB (baseline load) + temporarily scale up read replicas during high usage.**
- C. EC2 Instance Savings Plans (baseline) + Spot (peak) + 1-year all-upfront RI for DB + manual DB scaling during high usage.
- D. Compute Savings Plans (baseline) + Spot (peak) + 1-year all-upfront RI for DB + manual DB scaling during high usage.

**Correct Answer: B**

**Explanation**
For rare but **date-predictable** peaks, **On-Demand Capacity Reservations** are safer than Spot (interruption risk). Cover DB baseline load with a **no-upfront 1-year RI** for flexibility, and **temporarily scale up read replicas** during peaks — the most cost-effective approach for predictable, event-driven traffic.

**Why the other choices are wrong**
- A, C, D: Ticketing platform peaks are critical traffic that can't tolerate failed transactions during an event, so using Spot for peaks risks interruption. Also, an "all-upfront" 1-year RI sized to the expected maximum is inefficient for rare peak scenarios.

> 💡 **Exam tip**: For **rare but date-predictable peaks** (events, sales), **On-Demand Capacity Reservations are safer than Spot.** Cover DB baseline with a no-upfront RI and handle peaks by **temporarily scaling read replicas.**

## QUESTION 153

**Question**: An Elastic Beanstalk (Aurora DB) application with CloudFront using the Beanstalk domain as origin. During weekly maintenance, the company wants visitors to see an **informational message** instead of a CloudFront error. An S3 bucket has already been created. What's the next combination of steps? (Choose three.)

**Choices**
- A. **Upload static informational content to the S3 bucket.**
- B. Create a new CloudFront distribution with S3 as the origin.
- C. **Set the S3 bucket as a second origin on the original distribution, configuring both the distribution and bucket to use an Origin Access Identity (OAI).**
- D. **During weekly maintenance, edit the default cache behavior to use the S3 origin; revert the change once maintenance completes.**
- E. During weekly maintenance, create a cache behavior for the S3 origin on a new distribution with path pattern \ and priority 0; delete it once maintenance completes.
- F. Configure Elastic Beanstalk to handle traffic for the S3 bucket.

**Correct Answer: A, C, D**

**Explanation**
Reuse the existing CloudFront distribution by **adding S3 as a second origin** (with OAI for secure access, C), pre-upload a **static informational page to S3** (A), and during maintenance windows, **switch the default cache behavior to the S3 origin** and revert afterward (D) — the minimal-change way to achieve the goal.

**Why the other choices are wrong**
- B: Creating a separate new distribution is unnecessarily complex and doesn't reuse the existing distribution's alternate domain name (CNAME) configuration.
- E: Creating a behavior on a new distribution repeats the same unnecessary separation as B.
- F: The concept of Elastic Beanstalk handling S3 traffic doesn't make sense.

> 💡 **Exam tip**: To temporarily show a **maintenance page** via CloudFront, the standard pattern is adding **S3 as a second origin (with OAI)** on the existing distribution and **temporarily switching the default cache behavior**, then reverting.

## QUESTION 154

**Question**: A Lambda function (invoked via a specific version ARN, using environment variables for image processing parameters) processes images. The company frequently tunes these parameters, and each new published version requires updating the custom application to call the new ARN — disruptive to users. Simplify with minimal operational overhead.

**Choices**
- A. Directly modify environment variables of published versions + test with $LATEST.
- B. Store image processing parameters in a DynamoDB table + modify Lambda to look them up.
- C. Hard-code parameters directly in the Lambda function code and remove environment variables.
- D. **Create a Lambda function alias. Update the client application to use the alias ARN. Once testing is done, reconfigure the alias to point to the new function version.**

**Correct Answer: D**

**Explanation**
A **Lambda alias** provides a fixed ARN while allowing the underlying version it points to be changed internally. Clients always call the alias ARN, so publishing a new version and repointing the alias requires zero client-side changes.

**Why the other choices are wrong**
- A: Published Lambda versions are immutable — environment variables cannot be modified directly.
- B: Adding a DynamoDB lookup introduces extra latency/cost per invocation and doesn't solve the root problem (changing ARNs).
- C: Hard-coding requires a code change and redeployment every time parameters are tuned — even more cumbersome.

> 💡 **Exam tip**: The problem of **frequently changing which Lambda version ARN to call** is almost always solved with a **Lambda alias** — clients always call the fixed alias ARN.

## QUESTION 155

**Question**: A global media company with a DynamoDB global table (spanning two continents), each deployment behind a public ALB. Public DNS is managed internally. The company wants the application available via its **apex domain.** Minimal-effort solution?

**Choices**
- A. Migrate public DNS to Route 53 + CNAME record for apex pointing to ALB + geolocation routing.
- B. Place an NLB in front of the ALB + CNAME record for apex pointing to the NLB's static IP + geolocation routing.
- C. **Create an AWS Global Accelerator with multiple endpoint groups targeting endpoints in the appropriate AWS Regions. Create a record for the apex domain in the existing public DNS using the accelerator's static IP addresses.**
- D. Create a Lambda-backed API Gateway API in one Region + Lambda round-robin routing + CNAME record for apex pointing to the API's URL.

**Correct Answer: C**

**Explanation**
The key constraint: **an apex (root) domain cannot have a CNAME record** — a standard DNS limitation. **AWS Global Accelerator provides fixed static IP addresses**, so registering these as an **A record** on the apex domain solves it. Since DNS is already managed **internally** (no need to migrate to Route 53), just add an A record to the existing DNS provider.

**Why the other choices are wrong**
- A: An apex domain cannot have a CNAME, and there's no need to migrate to Route 53 (unless using a Route 53 ALIAS record specifically, but this choice explicitly says CNAME).
- B: An NLB's IP may not be static (an EIP association would be needed), and it still mentions CNAME, violating the apex constraint.
- D: An unnecessarily complex custom routing solution that also violates the apex CNAME constraint.

> 💡 **Exam tip**: **An apex (root) domain cannot have a CNAME record.** For apex domain routing needing a static IP, the classic answer is **registering AWS Global Accelerator's fixed IP addresses as an A record.**

## QUESTION 156

**Question**: A company is developing a new serverless API using API Gateway and Lambda, with Lambda functions using several shared libraries and custom classes. Simplify deployment and optimize code reuse.

**Choices**
- A. Package shared libraries/custom classes into a Docker image, store in S3, create a Lambda layer using the Docker image as source, deploy the API's Lambda as a zip package configured to use the layer.
- B. Same as A but upload the Docker image to Amazon ECR instead of S3.
- C. Deploy shared libraries/custom classes as Docker containers on ECS Fargate, then use the deployed containers "as a Lambda layer" (not a real concept).
- D. **Package shared libraries, custom classes, and code for the API's Lambda functions all into a Docker image. Upload the image to Amazon ECR. Configure the API's Lambda functions to use this Docker image as the deployment package.**

**Correct Answer: D**

**Explanation**
Lambda supports using a **container image directly as its deployment package.** Bundling shared libraries and code into a single Docker image, uploading to ECR, and using it as the Lambda deployment package simplifies deployment to a single artifact and optimizes code/library reuse via image layer caching.

**Why the other choices are wrong**
- A, B: There is no such feature as using a Docker image as the "source" for a Lambda layer — layers use zip archives.
- C: Using an ECS/Fargate container "as a Lambda layer" is not a valid concept.

> 💡 **Exam tip**: Lambda supports using a **container image directly as the deployment package itself** (not as a layer source). To simplify complex Lambda deployments with many shared libraries, package everything into **one container image (via ECR).**

## QUESTION 157

**Question**: A manufacturing plant has IP cameras at the end of each assembly line and trained an ML model with SageMaker to detect defects from still images. The company wants to give local feedback to factory workers when defects are detected, even if the plant's internet connection drops. A local Linux server already hosts an API providing local feedback. How should the ML model be deployed?

**Choices**
- A. Set up a Kinesis Video Stream per camera to AWS + capture stills via EC2 + upload to S3 + call a SageMaker endpoint via Lambda (requires internet — violates requirement).
- B. **Deploy AWS IoT Greengrass to the local server. Deploy the ML model to Greengrass. Create Greengrass components to capture still images from cameras and run inference. Configure the component to call the local API when a defect is detected.**
- C. Order an AWS Snowball device; deploy a SageMaker endpoint, ML model, and EC2 instance to it, run inference there (excessively heavy).
- D. Deploy Amazon Monitron devices per camera (vibration/temperature sensing only — unsuitable for image-based defect detection).

**Correct Answer: B**

**Explanation**
Since the solution must work **even when internet connectivity is lost**, cloud-based inference (A, C) is unsuitable. **AWS IoT Greengrass** deploys the ML model to the edge (local server) and runs inference offline — exactly matching this scenario.

**Why the other choices are wrong**
- A: Calling a cloud-hosted SageMaker endpoint doesn't work when internet connectivity is lost.
- C: Using Snowball Edge as always-on inference infrastructure is excessively heavy and atypical.
- D: Amazon Monitron is dedicated hardware/service for vibration/temperature anomaly detection, not applicable to image-based defect detection.

> 💡 **Exam tip**: For edge scenarios needing **ML inference that must work offline** (no internet), the answer is **AWS IoT Greengrass** — deploying the model to local hardware for inference without a cloud connection.

## QUESTION 158

**Question**: A solutions architect needs to build a business case for migrating an on-premises data center to AWS, using a CMDB (Configuration Management Database) export from all company servers. Most cost-effective solution?

**Choices**
- A. Import CMDB data into the AWS Well-Architected Tool for analysis and recommendations (mismatched purpose — architecture review tool).
- B. **Use AWS Migration Evaluator to perform the analysis. Upload data from the CMDB export using a data import template.**
- C. Implement resource-matching rules and query CMDB data against AWS services in bulk using the AWS Price List Bulk API (building it yourself — inefficient).
- D. Use AWS Application Discovery Service to import CMDB data for analysis (a data-collection tool — unnecessary since CMDB data already exists).

**Correct Answer: B**

**Explanation**
**AWS Migration Evaluator** is a free service purpose-built for exactly this use case (generating a migration business case/TCO analysis from existing on-premises infrastructure data), and provides a **template-based import feature** for existing data like CMDB exports.

**Why the other choices are wrong**
- A: The Well-Architected Tool reviews best-practice adherence of an already-built architecture — not for building a migration business case.
- C: Building custom matching logic with the Price List Bulk API reinvents what Migration Evaluator already provides.
- D: Application Discovery Service is a tool for "collecting" data directly from on-premises servers — an unnecessary extra step when CMDB export data already exists.

> 💡 **Exam tip**: To build a migration business case/TCO analysis from existing **CMDB export data**, the answer is **AWS Migration Evaluator** (with its data import template) — distinguish it from Application Discovery Service, which is for collecting data from scratch.

## QUESTION 159

**Question**: A website running on EC2 instances behind an ALB (Auto Scaling group), with an AWS WAF web ACL attached. The site frequently faces application-layer attacks, each originating from a different IP address, causing sudden spikes in traffic to application servers. Mitigate this with minimal operational overhead.

**Choices**
- A. Create a CloudWatch alarm monitoring server access with a per-IP threshold, configuring the alarm action to add the IP to the web ACL's deny list.
- B. **Deploy AWS Shield Advanced in addition to AWS WAF. Add the ALB as a protected resource.**
- C. Create a CloudWatch alarm monitoring user IP addresses with a threshold, invoking a Lambda function to add deny rules to the application server subnet's route table for any triggering IP.
- D. Analyze access logs for patterns in attacking IP addresses; use Route 53 geolocation routing to block traffic from the countries hosting those IPs.

**Correct Answer: B**

**Explanation**
Since attacks come from **different IPs each time**, IP-based blocking (A, C) has limited effectiveness and requires ongoing manual/semi-automated response — high operational overhead. **AWS Shield Advanced** automatically provides sophisticated application-layer (L7) DDoS detection/mitigation, including DRT (DDoS Response Team) support, addressing ongoing application-layer attacks with minimal operational overhead.

**Why the other choices are wrong**
- A, C: Since IP addresses change every time, per-IP blocking is low-effectiveness and requires heavy ongoing manual response.
- D: Country-level blocking risks blocking legitimate users too, and is defeated if the attacker uses IPs from other countries.

> 💡 **Exam tip**: For **application-layer (L7) attacks originating from different IPs each time**, **AWS Shield Advanced** (sophisticated automated detection/mitigation) is the minimal-overhead answer, not IP-based blocking.

## QUESTION 160

**Question**: A critical application has its data layer (DynamoDB + Aurora MySQL, on an engine version supporting global databases) deployed in a single Region. The application layer is already deployed across two Regions. Company policy requires the data layer also be deployed across two Regions, with RTO/RPO of no more than a few minutes. Required steps? (Choose two.)

**Choices**
- A. **Add another Region to the Aurora MySQL DB cluster (Aurora Global Database).**
- B. Add another Region to each table in the Aurora MySQL cluster (conceptually wrong — Regions are added at the cluster level).
- C. Set up scheduled cross-Region backups for the DynamoDB tables and Aurora MySQL cluster (doesn't meet RPO — data loss possible between snapshots).
- D. **Convert the existing DynamoDB table to a global table by adding another Region to its configuration.**
- E. Use Amazon Route 53 Application Recovery Controller to automate database backup and recovery to a secondary Region (backup-based, doesn't meet RTO/RPO).

**Correct Answer: A, D**

**Explanation**
Since Aurora MySQL is already on an engine version supporting global databases, convert it to **Aurora Global Database** (add another Region, A), and convert DynamoDB to a **global table** (add another Region, D). Both are managed multi-Region replication features that keep RPO/RTO within minutes.

**Why the other choices are wrong**
- B: Region addition happens at the cluster level, not "per table" — a conceptual mismatch with how Aurora Global Database works.
- C, E: Scheduled backups or backup-based recovery automation can lose data depending on the snapshot cycle, failing the "few minutes" RPO requirement.

> 💡 **Exam tip**: For near-real-time cross-Region DR of a relational DB, use **Aurora Global Database**; for NoSQL (DynamoDB), use **Global Tables** — the standard answers. Remember that backup/snapshot-based approaches struggle to meet minutes-level RPO.
