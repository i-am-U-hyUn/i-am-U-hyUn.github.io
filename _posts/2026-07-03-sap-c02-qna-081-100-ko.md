## QUESTION 81

**문제**: 완전 서버리스 전자문서관리 시스템(eu-central-1)이 CloudFront(S3 오리진) 웹앱 + API Gateway **지역 엔드포인트** + Lambda + Aurora Serverless(메타데이터) + S3(문서)로 구성됩니다. 최대 고객과 PoC를 마쳤고 **유럽 밖에서의 지연 시간**을 개선해야 합니다. (2가지 선택)

**보기**
- A. **S3 버킷에서 Transfer Acceleration을 활성화**하고 웹앱이 가속화 서명 URL을 사용하도록 구성
- B. Global Accelerator를 만들어 CloudFront 배포에 연결
- C. **API Gateway 지역 엔드포인트를 엣지 최적화 엔드포인트로 변경**
- D. 전 세계 다른 두 위치에 전체 스택을 추가 프로비저닝 + Aurora 글로벌 데이터베이스
- E. Lambda와 Aurora Serverless 사이에 RDS 프록시 추가

**정답: A, C**

**해설**
문서 업로드(주로 서명된 URL을 통한 S3 직접 업로드)의 속도를 높이려면 **S3 Transfer Acceleration**을 사용하고, API 호출의 지연 시간을 줄이려면 **API Gateway를 엣지 최적화 엔드포인트로 전환**해 CloudFront의 엣지 네트워크를 API 호출에도 활용합니다.

**왜 다른 보기는 오답인가**
- B: **Global Accelerator는 CloudFront 배포에 연결하는 용도가 아닙니다**(ALB/NLB/EIP 등 다른 유형의 엔드포인트용이며, CloudFront는 이미 자체 엣지 네트워크를 갖추고 있습니다).
- D: 다른 위치에 전체 스택을 복제하고 Aurora 글로벌 데이터베이스까지 도입하는 것은 지금 단계(성장 초기)에 비해 지나치게 큰 재설계입니다.
- E: RDS 프록시는 연결 관리 문제를 해결하지, 지리적 지연 시간과는 무관합니다.

> 💡 **시험 꿀팁**: 지리적으로 먼 사용자를 위한 성능 개선은 **업로드(S3)에는 Transfer Acceleration, API 호출(API Gateway)에는 엣지 최적화 엔드포인트**로 구분해서 접근하세요.

## QUESTION 82

**문제**: 앱에서 언제든 업로드되는 사진·비디오가 S3 Standard에 저장되고 CloudFront로 제공됩니다. 대부분은 30일 후 드물게 액세스되지만, **일부는 30일 후에도 자주 액세스**됩니다. 밀리초 단위 조회 가용성을 유지하면서 가장 낮은 비용으로 스토리지를 최적화하려면?

**보기**
- A. **S3 Intelligent-Tiering을 구성**한다.
- B. 30일 후 S3 Glacier Deep Archive로 전환하는 수명 주기 정책 구성
- C. S3를 EC2에 탑재된 EFS로 교체
- D. Cache-Control 헤더를 30일로 설정

**정답: A**

**해설**
어떤 객체가 계속 자주 조회될지 미리 알 수 없는 **혼재된/예측 불가능한 접근 패턴**에는 **S3 Intelligent-Tiering**이 정답입니다. 실제 접근 패턴에 따라 객체별로 자동으로 계층을 이동시키면서도 항상 밀리초 단위 조회를 유지합니다.

**왜 다른 보기는 오답인가**
- B: Glacier Deep Archive는 조회에 수 시간이 걸려 밀리초 단위 조회 요구 사항을 만족하지 못하고, 30일 후에도 자주 조회되는 일부 객체를 고려하지 않습니다.
- C: EC2+EFS는 불필요한 컴퓨팅 비용을 추가하며 서버리스 S3+CloudFront 구조에 맞지 않습니다.
- D: Cache-Control 헤더는 브라우저/CDN 캐싱 기간을 조절할 뿐, S3 스토리지 클래스나 비용과는 무관합니다.

> 💡 **시험 꿀팁**: 일정 기간 후 접근 패턴이 **예측 불가능(일부는 계속 핫함)**하다면 수명 주기 정책으로 일괄 Glacier 전환하는 대신 **S3 Intelligent-Tiering**을 사용하세요. 밀리초 조회를 유지하면서 자동으로 비용을 최적화합니다.

## QUESTION 83

**문제**: 여러 스토리지 클래스에 파일·이미지를 저장 중이며 S3 비용이 작년에 크게 증가했습니다. 지난 12개월 데이터 추세를 검토하고 객체에 적합한 스토리지 클래스를 식별하려면?

**보기**
- A. 12개월 CUR 다운로드 + Trusted Advisor 권장 사항 검토
- B. S3 스토리지 클래스 분석 + QuickSight로 추세 분석
- C. **Amazon S3 Storage Lens를 사용**하고 **고급 지표를 포함하도록 기본 대시보드를 업그레이드**
- D. S3용 Access Analyzer + QuickSight로 가져오기

**정답: C**

**해설**
**Amazon S3 Storage Lens**는 조직 전체의 S3 사용량·비용 추세 분석, 스토리지 클래스 권장 사항, 고급 지표를 전용으로 제공하는 AWS 네이티브 분석 서비스로, 이 요구 사항에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: CUR+Trusted Advisor는 비용 데이터와 일반적인 모범 사례 권장은 제공하지만, Storage Lens만큼 S3 특화된 세밀한 스토리지 클래스별 추세 분석을 제공하지 않습니다.
- B: S3 스토리지 클래스 분석은 단일 버킷 범위의 (주로 Standard-IA 전환 후보 식별용) 더 좁은 기능으로, 이를 QuickSight로 수동 연동하는 것은 Storage Lens의 내장 고급 대시보드보다 번거롭습니다.
- D: **S3용 Access Analyzer는 버킷의 외부 노출(보안) 여부를 확인하는 도구**로, 비용/스토리지 클래스 분석과는 완전히 다른 목적입니다.

> 💡 **시험 꿀팁**: 조직 전체의 S3 사용 추세·스토리지 클래스 최적화 분석에는 **Amazon S3 Storage Lens**(고급 지표 티어)가 정답입니다. S3 Storage Class Analysis(단일 버킷, IA 중심)나 IAM Access Analyzer for S3(보안 노출 도구)와 혼동하지 마세요.

## QUESTION 84

**문제**: 클라우드 인프라를 코드로 정의해야 하며, 현재 단일 리전에 배포되어 있지만 향후 **여러 AWS 계정에 걸쳐 여러 리전**에 배포할 계획입니다.

**보기**
- A. CloudFormation 템플릿 + IAM 정책으로 여러 계정 제어
- B. Organizations + 마스터 계정에서 템플릿 배포 + Control Tower로 배포 관리
- C. **AWS Organizations + AWS CloudFormation StackSets**를 사용해, 필요한 IAM 권한이 있는 계정에서 템플릿 배포
- D. 중첩 스택으로 리전을 변경

**정답: C**

**해설**
**CloudFormation StackSets**는 동일한 템플릿을 **여러 계정과 여러 리전에 동시에** 배포하도록 설계된 기능이며, AWS Organizations와 통합되어 계정/OU 단위로 대상을 지정할 수 있어 이 요구 사항에 정확히 맞습니다.

**왜 다른 보기는 오답인가**
- A: 일반 CloudFormation 템플릿 + IAM 정책만으로는 계정 간 배포가 실제로 작동하지 않습니다(스택은 기본적으로 단일 계정·단일 리전 범위).
- B: Control Tower는 랜딩 존/계정 프로비저닝·거버넌스 도구이지, 템플릿 기반 다중 리전 배포 메커니즘 자체는 아닙니다(실제 배포는 StackSets가 담당).
- D: 중첩 스택은 **하나의** 스택·계정·리전 내에서 리소스를 모듈화하는 기능일 뿐, 계정/리전 간 배포 메커니즘이 아닙니다.

> 💡 **시험 꿀팁**: 동일한 인프라를 **여러 계정 + 여러 리전**에 동시에 배포하려면 **AWS Organizations + CloudFormation StackSets** 조합이 표준입니다.

## QUESTION 86

**문제**: 모놀리식 앱을 최신 설계로 리팩터링하며, CI/CD 파이프라인이 (1) **시간당 여러 번 릴리스**, (2) **최대한 빠른 롤백**을 지원해야 합니다.

**보기**
- A. AMI에 앱+설정 통합 → EC2 인스턴스 교체 방식 배포
- B. **CI/CD 파이프라인의 배포 대상을 보조 환경에서 스테이징하는 Elastic Beanstalk로 지정, 배포 시 스테이징-프로덕션 환경 URL을 교환**
- C. Systems Manager로 매 배포마다 인프라 재프로비저닝 + 가중 라우팅
- D. 사전 구축 AMI로 ASG 이벤트 중 롤아웃, 새 버전 인스턴스 추가 후 이전 버전 단계적 제거

**정답: B**

**해설**
Elastic Beanstalk의 **환경 URL 교환(스왑) 기반 블루/그린 배포**는 별도 스테이징 환경에 배포해 검증한 뒤 URL만 즉시 교환해 프로덕션으로 전환하며, 문제 발생 시 URL을 다시 교환하는 것만으로 **거의 즉각적인 롤백**이 가능해 두 요구 사항을 모두 만족합니다.

**왜 다른 보기는 오답인가**
- A: AMI를 매번 새로 빌드하는 것은 시간이 걸려 "시간당 여러 번 릴리스"에 적합하지 않습니다.
- C: 배포마다 인프라를 재프로비저닝하는 것은 훨씬 느리고 운영 부담이 큽니다.
- D: 롤링 배포 방식은 점진적이라 롤백도 같은 속도로 점진적이며, "최대한 빠른 롤백"에는 URL 교환 방식(B)만큼 즉각적이지 않습니다.

> 💡 **시험 꿀팁**: **초고빈도 릴리스 + 즉각적인 롤백**이 필요하면 **Elastic Beanstalk의 환경 URL 교환(블루/그린)** 배포 패턴을 떠올리세요. AMI 재구축이나 점진적 롤링 배포보다 빠릅니다.

## QUESTION 87

**문제**: EC2 앱(모두 동일 보안 그룹)이 Aurora DB 클러스터(자체 보안 그룹)에 **최소 권한**으로 접근해야 합니다. 필요한 보안 그룹 규칙 조합은? (2가지 선택)

**보기**
- A. EC2 보안 그룹에 **인바운드** 규칙 추가, DB 클러스터 보안 그룹을 소스로 지정
- B. **EC2 보안 그룹에 아웃바운드 규칙 추가, DB 클러스터 보안 그룹을 대상으로 지정(기본 Aurora 포트)**
- C. **DB 클러스터 보안 그룹에 인바운드 규칙 추가, EC2 보안 그룹을 소스로 지정(기본 Aurora 포트)**
- D. DB 클러스터 보안 그룹에 아웃바운드 규칙 추가, EC2 보안 그룹을 대상으로 지정
- E. DB 클러스터 보안 그룹에 아웃바운드 규칙 추가, EC2 보안 그룹을 임시 포트 대상으로 지정

**정답: B, C**

**해설**
"보안 그룹이 서로를 참조"하는 최소 권한 패턴입니다. EC2가 DB로 요청을 **보내는** 쪽이므로, EC2 측에는 **아웃바운드**(DB 보안 그룹을 대상으로, B)를, DB 측에는 **인바운드**(EC2 보안 그룹을 소스로, C)를 허용해야 합니다.

**왜 다른 보기는 오답인가**
- A: EC2의 보안 그룹에 "DB를 소스로 하는 인바운드"는 방향이 반대입니다(EC2가 요청을 시작하지, DB가 EC2로 먼저 연결하는 게 아닙니다).
- D, E: DB 측에 "EC2를 대상으로 하는 아웃바운드"도 방향이 반대입니다. 응답 트래픽은 보안 그룹이 **상태 저장(stateful)**이기 때문에 자동으로 허용되며, 별도의 아웃바운드 규칙을 명시할 필요가 없습니다.

> 💡 **시험 꿀팁**: EC2→DB 최소 권한 보안 그룹 구성은 **① EC2 쪽 아웃바운드(DB 보안 그룹 대상) + ② DB 쪽 인바운드(EC2 보안 그룹 소스)**입니다. 보안 그룹은 상태 저장형이라 응답 트래픽에 별도 규칙이 필요 없다는 점도 기억하세요.

## QUESTION 88

**문제**: 여러 사업부 계정(Organizations)에서 기존 태그(애플리케이션, 환경, 소유자)를 활용해 **중앙 집중식** 월별 비용 보고서와 임계값 초과 알림을 원합니다. 가장 비용 효율적인 방법은?

**보기**
- A. 각 계정에서 개별적으로 AWS Budgets 구성 + 각 계정에서 Cost Explorer로 보고서 생성
- B. **조직 마스터 계정에서 AWS Budgets를 구성**(태그별 그룹화 알림, SNS로 각 사업부에 전달), **마스터 계정에서 Cost Explorer로 월별 보고서 생성**
- C. 각 계정에서 개별적으로 AWS Budgets 구성 + 각 계정의 Billing and Cost Management 대시보드로 보고서 생성
- D. 마스터 계정에서 CUR 활성화 + 커스텀 Lambda로 예산 알림과 이메일 보고서 발송

**정답: B**

**해설**
**AWS Budgets와 Cost Explorer를 조직 마스터 계정에서 실행**하면 모든 구성원 계정의 데이터를 한 곳에서 집계·필터링할 수 있어, 각 계정마다 개별 설정하는 것보다 훨씬 중앙집중적이고 효율적입니다.

**왜 다른 보기는 오답인가**

애플리케이션을 크게 바꾸지 않으려면, RabbitMQ와 **프로토콜 호환**되는 **Amazon MQ**(코드 변경 불필요)로 메시징을 대체하고, 표준 Kubernetes를 그대로 실행하는 관리형 컨트롤 플레인인 **Amazon EKS**로 백엔드를 옮기는 것이 정답입니다. 웹 서버는 AMI+ASG+ALB로 기존 VM 방식을 유지합니다.

**왜 다른 보기는 오답인가**
- B: 웹 서버를 Lambda+API Gateway 기반으로 바꾸는 것은 애플리케이션의 대대적인 재설계라 "크게 바꾸지 않는다"는 조건에 정면으로 위배됩니다.
- C: EKS(관리형 컨트롤 플레인) 대신 EC2에 Kubernetes를 **직접 설치**하면, 온프레미스에서 겪던 것과 똑같은 컨트롤 플레인 관리 부담이 그대로 남습니다.
- D: **Amazon SQS는 RabbitMQ/AMQP와 프로토콜 호환이 되지 않는** 별도의 AWS 전용 API라, 애플리케이션 코드를 SQS에 맞게 다시 작성해야 합니다("크게 바꾸지 않는다"는 조건 위배).

> 💡 **시험 꿀팁**: **RabbitMQ**를 최소한의 코드 변경으로 옮기려면 (프로토콜 비호환인 SQS가 아니라) **Amazon MQ**를 사용하세요. **자체 관리 Kubernetes**를 최소 변경으로 옮기려면 (EC2에 직접 설치가 아니라) **Amazon EKS**(관리형 컨트롤 플레인)를 사용하세요.

## QUESTION 96

**문제**: KMS의 CMK로 새 S3 버킷 객체에 클라이언트 측 암호화를 구현합니다. IAM 정책에는 `s3:GetObject/GetObjectVersion/PutObject/PutObjectAcl`과 `kms:Decrypt`를 허용했습니다. 테스트 결과 기존 객체 **다운로드는 성공**하지만 새 객체 **업로드는 "금지됨" 오류**가 납니다. 어떤 KMS 작업을 추가해야 할까요?

**보기**
- A. **`kms:GenerateDataKey`**
- B. `kms:GetKeyPolicy`
- C. `kms:GetPublicKey`
- D. `kms:Sign`

**정답: A**

**해설**
클라이언트 측 암호화에서 **암호화(업로드)에는 `kms:GenerateDataKey`**(새 데이터 암호화 키 생성)가 필요하고, **복호화(다운로드)에는 `kms:Decrypt`**만 있으면 됩니다. 정책에 `kms:Decrypt`만 있고 `kms:GenerateDataKey`가 빠져 있어, 다운로드는 되지만 업로드(암호화용 키 생성이 먼저 필요)는 실패하는 것입니다.

**왜 다른 보기는 오답인가**
- B: `kms:GetKeyPolicy`는 키의 리소스 정책을 조회하는 관리용 작업으로, 실제 암복호화와는 무관합니다.
- C: `kms:GetPublicKey`는 **비대칭** KMS 키의 공개 키를 가져오는 작업으로, 일반적인 대칭 CMK 클라이언트 측 암호화 흐름과는 무관합니다.
- D: `kms:Sign`은 비대칭 키로 데이터에 **전자 서명**하는 작업으로, 객체 암호화와는 무관합니다.

> 💡 **시험 꿀팁**: KMS CMK로 클라이언트 측 암호화를 할 때, **암호화(업로드)=`kms:GenerateDataKey`**, **복호화(다운로드)=`kms:Decrypt`**로 나눠 기억하세요. 다운로드는 되는데 업로드만 안 된다면 거의 항상 `kms:GenerateDataKey` 누락입니다.

## QUESTION 97

**문제**: ALB 뒤 EC2 웹 앱의 보안 태세를 AWS WAF로 개선하려 하며, **정상 트래픽에 부정적 영향을 주면 안 됩니다.** Web ACL을 어떻게 구성해야 할까요?

**보기**
- A. **웹 ACL 규칙 동작을 Count로 설정 → WAF 로깅 활성화 → 가양성(false positive) 분석 → 규칙 수정 → 시간이 지나면서 Count에서 Block으로 전환**
- B. 속도 기반 규칙만 사용하고 임계값을 최대한 높게 설정
- C. 규칙 동작을 즉시 Block으로 설정, AWS 관리형 규칙 그룹만 사용
- D. 사용자 지정 규칙 그룹만 사용, 동작을 Allow로 설정 후 점차 Block으로 전환

**정답: A**

**해설**
AWS가 권장하는 표준 WAF 롤아웃 전략은 **"Count 모드로 먼저 배포 → 로깅으로 정상 트래픽 대비 가양성 분석 → 규칙 튜닝 → 확신이 서면 Block으로 전환"**입니다. 이 단계를 거쳐야 "정상 트래픽에 영향 없음"을 보장하면서 안전하게 보안을 강화할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 속도 기반 규칙만으로는 SQLi/XSS 등 다른 유형의 공격에 대한 보호가 부족해 보안 개선 범위가 좁습니다.
- C: 사전 검증 없이 바로 Block으로 설정하면 관리형 규칙이 이 앱의 특정 트래픽 패턴에 오탐(가양성)을 일으킬 경우 곧바로 정상 트래픽을 차단할 위험이 있습니다.
- D: AWS 관리형 규칙 그룹(이미 검증된 기본 보호)을 배제하고, "Allow"는 Count처럼 로깅·분석을 통한 안전한 테스트 단계에 해당하는 표준 동작이 아닙니다.

> 💡 **시험 꿀팁**: WAF 규칙을 새로 배포할 때 정상 트래픽에 영향을 주지 않으려면 **Count 모드 → 로그로 가양성 분석 → 규칙 튜닝 → Block 전환**의 점진적 롤아웃을 항상 기억하세요.

## QUESTION 98

**문제**: 많은 AWS 계정을 가진 조직에서, 온프레미스 네트워크 허용을 위한 공통 IP CIDR 대역 세트를 각 계정의 보안 그룹에 반영해야 합니다. 현재는 각 계정의 개발자가 수동으로 추가하고, 보안팀(별도 계정)이 변경 시 다른 계정 소유자에게 통지합니다. 최소 운영 오버헤드로 모든 계정에 공통 CIDR 세트를 배포하려면?

**보기**
- A. 보안팀 계정에 SNS 주제 + 모든 계정에 Lambda 배포, SNS 수신 시 각 계정의 보안 그룹을 업데이트하도록 구성
- B. 조직 내 각 계정마다 개별적으로 고객 관리형 접두사 목록 생성 + 소유자들에게 통지
- C. **보안팀 계정에 새 고객 관리형 접두사 목록 생성, 모든 내부 CIDR로 채움, AWS RAM으로 조직과 공유, 각 계정 소유자에게 새 접두사 목록 ID를 보안 그룹에서 허용하도록 통지**
- D. 각 계정에 IAM 역할 생성(보안 그룹 업데이트 권한) + 보안팀 계정의 Lambda가 역할을 수임해 각 계정의 보안 그룹을 직접 업데이트

**정답: C**

**해설**
(53번 문제와 동일한 패턴입니다.) **관리형 접두사 목록**을 한 곳(보안팀 계정)에서 만들어 **AWS RAM으로 조직 전체와 공유**하면, 각 계정은 최초 한 번만 접두사 목록 ID를 보안 그룹 규칙에 등록하면 되고, 이후 목록 내용이 바뀌어도 모든 곳에 자동 반영되어 추가 작업이 필요 없습니다.

**왜 다른 보기는 오답인가**
- A: 모든 계정에 커스텀 Lambda 동기화 로직을 배포·유지하는 것은 이미 존재하는 접두사 목록 공유 기능을 다시 만드는 불필요한 작업입니다.
- B: 각 계정에 **개별** 접두사 목록을 따로 만들면, 향후 변경 시 여전히 모든 계정을 일일이 업데이트해야 해 지금의 문제(모두에게 통지 후 수동 반영)가 그대로 반복됩니다.
- D: 모든 계정에 IAM 역할을 만들고 중앙 Lambda가 교차 계정으로 직접 수정하는 방식은 관리형 접두사 목록보다 훨씬 복잡하고 관리 부담이 큽니다.

> 💡 **시험 꿀팁**: (53번과 동일) 여러 계정에 공유해야 하는 CIDR 목록은 **관리형 접두사 목록 + AWS RAM 공유**로 중앙 관리하세요. 커스텀 Lambda 동기화나 계정별 개별 목록 생성보다 훨씬 운영 부담이 적습니다.

## QUESTION 99

**문제**: 새 재택근무 정책으로 직원이 VPN으로 접속합니다. 내부 앱은 여러 AWS 계정의 VPC에서 호스팅되며, 기본 계정의 VPC는 다른 계정들의 VPC와 **이미 피어링**되어 있습니다. 확장 가능한 AWS Client VPN 솔루션을 가장 비용 효율적으로 설계하려면?

**보기**
- A. 각 AWS 계정에 개별 클라이언트 VPN 엔드포인트 생성
- B. **기본 AWS 계정에 클라이언트 VPN 엔드포인트를 하나 생성**하고, 내부 앱 접근을 위한 필수 라우팅 구성
- C. 기본 계정에 클라이언트 VPN 엔드포인트 + 각 계정에 연결된 전송 게이트웨이 추가 프로비저닝
- D. 기본 계정에 클라이언트 VPN 엔드포인트 + 기존 Site-to-Site VPN과 연결

**정답: B**

**해설**
기본 계정의 VPC가 이미 다른 계정들의 VPC와 **직접 피어링**되어 있으므로, 기본 계정에 **클라이언트 VPN 엔드포인트를 하나만** 만들고 라우팅을 구성하면 기존 피어링 연결을 통해 다른 계정의 VPC에도 접근할 수 있습니다(피어링은 전이적이지 않지만, 이는 "A를 거쳐 C로" 가는 경우의 문제이며, 클라이언트 VPN이 종료되는 기본 VPC와 각 대상 VPC 사이의 **직접** 피어링은 정상 작동합니다). 엔드포인트는 시간당 비용이 발생하므로, 하나만 두는 것이 가장 저렴합니다.

**왜 다른 보기는 오답인가**
- A: 계정마다 별도 엔드포인트를 만드는 것은 이미 존재하는 피어링을 활용하면 불필요한 추가 비용입니다.
- C: 기존 피어링으로 이미 연결이 되는데 전송 게이트웨이까지 새로 만드는 것은 불필요한 비용·복잡성입니다(전이적 라우팅이 필요한 경우에만 TGW가 필요합니다).
- D: 클라이언트 VPN을 굳이 별도의 Site-to-Site VPN에 연결하는 것은 불필요한 우회 경로이며, Site-to-Site VPN은 애초에 물리 사무실 연결용입니다.

> 💡 **시험 꿀팁**: 계정 간 VPC가 **이미 직접 피어링**되어 있다면, 클라이언트 VPN 엔드포인트 하나를 허브 VPC에 만들고 라우팅만 구성하면 피어링된 VPC들에 모두 접근 가능합니다. 전이적 다단계 라우팅이 실제로 필요할 때만 전송 게이트웨이를 추가하세요.

## QUESTION 100

**문제**: 앱의 응답 시간이 일관성 없고 오류율이 크게 증가했습니다. 원인은 서드파티 서비스 호출 지연입니다. 현재 앱은 Lambda 함수를 **직접 동기 호출**해 서드파티 서비스를 부릅니다. 서드파티 호출을 분리하고 **모든 호출이 결국 완료되도록** 보장하려면?

**보기**
- A. **Amazon SQS 대기열로 이벤트를 저장하고 Lambda 함수를 호출**
- B. AWS Step Functions 상태 시스템으로 Lambda에 이벤트 전달
- C. Amazon EventBridge 규칙으로 Lambda에 이벤트 전달
- D. Amazon SNS 주제로 이벤트를 저장하고 Lambda 함수 호출

**정답: A**

**해설**
트리거와 서드파티를 호출하는 Lambda 사이에 **SQS**를 두면, 이벤트가 큐에 내구성 있게 저장되고 Lambda가 이를 처리하며(가시성 제한 시간, 재시도, DLQ 등 SQS의 내장 메커니즘 활용), 서드파티가 일시적으로 문제가 있어도 **결국 호출이 완료**되도록 보장하면서 호출자가 느린 서드파티를 기다리며 동기 대기하지 않게 됩니다.

**왜 다른 보기는 오답인가**
- B: Step Functions는 여러 단계로 구성된 워크플로 오케스트레이션이 주 목적이며, SQS가 제공하는 단순한 "내구성 있는 버퍼링+분리" 용도에는 SQS가 더 직접적으로 맞습니다.
- C: EventBridge는 이벤트 패턴 기반 라우팅에 유용하지만, "결국 완료됨"을 보장하는 큐 기반 내구성·재시도 시맨틱을 SQS만큼 제공하지 않습니다.
- D: **SNS는 발행-구독(pub/sub) 알림 서비스**로, 실패한 전송을 성공할 때까지 보관·재시도하는 SQS 같은 내구성 있는 큐잉 시맨틱을 제공하지 않습니다.

> 💡 **시험 꿀팁**: 신뢰할 수 없거나 느린 서드파티로의 동기 호출을 분리하고 **"결국에는 완료됨"**을 보장하려면, 트리거와 처리 Lambda 사이에 **Amazon SQS**를 두세요. SNS(팬아웃, 재시도 없음)나 EventBridge(라우팅 중심)와는 목적이 다릅니다.
