## QUESTION 241

**문제**: 한 온라인 교육 회사가 AWS 클라우드로 마이그레이션하고 있다. 이 회사는 PostgreSQL 데이터베이스에 학생 기록을 보관하며, 여러 AWS 리전에서 데이터를 항상 온라인으로 사용할 수 있는 솔루션이 필요하다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. PostgreSQL 데이터베이스를 Amazon EC2 인스턴스로 구성한 PostgreSQL 클러스터로 마이그레이션한다(EC2 상에서 직접 클러스터를 구축·운영해야 하므로 패치, 복제, 장애 조치를 모두 수동으로 관리해야 해 운영 오버헤드가 큼).
- B. PostgreSQL 데이터베이스를 다중 AZ가 활성화된 Amazon RDS for PostgreSQL DB 인스턴스로 마이그레이션한다(다중 AZ는 동일 리전 내 가용 영역 간 장애 조치만 제공하며 리전 간 복제는 지원하지 않음).
- C. **PostgreSQL 데이터베이스를 Amazon RDS for PostgreSQL DB 인스턴스로 마이그레이션한다. 다른 리전에 읽기 전용 복제본을 생성한다.**
- D. PostgreSQL 데이터베이스를 Amazon RDS for PostgreSQL DB 인스턴스로 마이그레이션한다. 다른 리전으로 복사할 DB 스냅샷을 설정한다(스냅샷 복사는 특정 시점 백업 방식이라 실시간에 가까운 "항상 온라인" 요구를 충족하지 못하고 수동 복원 절차가 필요함).

**정답: C**

**해설**
**Amazon RDS for PostgreSQL**은 엔진 패치, 백업, 장애 조치 등 데이터베이스 운영 작업을 관리형으로 처리해 주며, 여기에 **크로스 리전 읽기 전용 복제본**을 추가하면 다른 리전에서도 최신에 가까운 데이터를 상시 온라인 상태로 제공할 수 있습니다. 다중 AZ는 동일 리전 내 고가용성만 보장하므로 "여러 AWS 리전에서 항상 온라인"이라는 요구 사항에는 리전 간 복제 기능인 읽기 전용 복제본이 필요합니다.

**왜 다른 보기는 오답인가**
- A: EC2 기반 자체 클러스터는 복제·장애 조치·패치를 모두 수동 관리해야 해 운영 오버헤드가 가장 큽니다.
- B: 다중 AZ는 동일 리전 안에서만 동작하며 다른 리전으로 데이터를 복제하지 않습니다.
- D: 스냅샷 복사는 정기적인 백업/복원 방식이라 지속적인 다중 리전 온라인 가용성을 제공하지 못합니다.

> 💡 **시험 꿀팁**: "여러 리전에서 항상 온라인"이라는 조건이 나오면 **RDS 크로스 리전 읽기 전용 복제본**이 표준 정답이고, "동일 리전 내 고가용성"이면 **다중 AZ**가 정답입니다.

## QUESTION 242

**문제**: 한 회사가 7개의 Amazon EC2 인스턴스로 웹 애플리케이션을 호스팅하고 있다. 이 회사는 DNS 쿼리에 대한 응답으로 정상 상태인 모든 EC2 인스턴스의 IP 주소가 반환되기를 요구한다. 이 요구 사항을 충족하려면 어떤 라우팅 정책을 사용해야 하는가?

**보기**
- A. 단순 라우팅 정책(Simple routing policy)(단일 리소스에 대해 하나의 값만 반환하도록 설계되어 있어 다수의 IP를 동시에 반환하는 요구에 맞지 않음).
- B. 레이턴시 라우팅 정책(Latency routing policy)(가장 낮은 지연 시간을 기준으로 단일 최적 리전의 리소스로 라우팅하며, 정상 인스턴스 전체를 반환하지 않음).
- C. **다중값 라우팅 정책(Multivalue routing policy)**
- D. 지리적 위치 라우팅 정책(Geolocation routing policy)(사용자의 지리적 위치에 따라 트래픽을 분배할 뿐 정상 인스턴스 전체 목록을 반환하지 않음).

**정답: C**

**해설**
**Route 53 다중값 응답 라우팅 정책**을 사용하면 하나의 레코드에 최대 8개까지 값을 등록하고, 각 값을 상태 확인(health check)과 연동해 정상인 리소스의 IP 주소만 무작위 순서로 함께 반환할 수 있습니다. 이를 통해 클라이언트 측 부하 분산과 기본적인 장애 조치를 동시에 구현할 수 있어, 모든 정상 EC2 인스턴스의 IP를 DNS 응답에 포함해야 하는 요구 사항에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: 단순 라우팅은 레코드당 값을 여러 개 반환할 수는 있지만 상태 확인과 결합해 정상 리소스만 골라 반환하는 기능이 없습니다.
- B: 레이턴시 라우팅은 사용자에게 가장 빠른 응답을 주는 단일 리전(또는 리소스)을 선택하는 것이 목적입니다.
- D: 지리적 위치 라우팅은 사용자의 위치를 기준으로 트래픽을 분배하는 정책으로 전체 정상 인스턴스 반환과는 무관합니다.

> 💡 **시험 꿀팁**: "정상 상태인 모든 리소스의 IP를 DNS 응답에 포함"하라는 조건이 나오면 **다중값 응답 라우팅 정책**이 표준 정답입니다.

## QUESTION 243

**문제**: 한 의학 연구소가 새로운 연구와 관련된 데이터를 생성한다. 이 연구소는 온프레미스 파일 기반 애플리케이션을 사용하는 전국의 클리닉에 최소한의 지연 시간으로 데이터를 제공하고자 한다. 데이터 파일은 각 클리닉에 읽기 전용 권한이 부여된 Amazon S3 버킷에 저장되어 있다. 이 요구 사항을 충족하기 위해 솔루션 설계자는 무엇을 권장해야 하는가?

**보기**
- A. **각 클리닉의 온프레미스에 AWS Storage Gateway 파일 게이트웨이를 가상 머신(VM)으로 배포한다.**
- B. AWS DataSync를 사용해 각 클리닉의 온프레미스 애플리케이션으로 파일을 마이그레이션한다(파일을 아예 복사·이관하는 일회성/배치 방식이라 원본 S3와의 실시간 저지연 접근 및 지속적 동기화를 제공하지 않음).
- C. 각 클리닉의 온프레미스에 AWS Storage Gateway 볼륨 게이트웨이를 가상 머신(VM)으로 배포한다(블록 수준 스토리지를 제공하는 방식이라 파일 기반 애플리케이션의 파일 수준 접근 요구에 적합하지 않음).
- D. Amazon EFS 파일 시스템을 각 클리닉의 온프레미스 서버에 연결한다(EFS는 AWS VPC 내부용 파일 시스템이라 다수의 온프레미스 클리닉과 직접 연결하려면 복잡한 네트워크 구성과 추가 지연이 발생함).

**정답: A**

**해설**
**AWS Storage Gateway의 파일 게이트웨이**는 NFS/SMB 파일 인터페이스로 S3 버킷의 객체에 접근할 수 있게 해주며, 자주 액세스하는 데이터를 로컬 캐시에 저장해 온프레미스 애플리케이션이 저지연으로 파일을 읽을 수 있도록 합니다. 각 클리닉에 VM 형태로 배포하면 별도의 데이터 이관 없이 S3의 읽기 전용 권한 구조를 그대로 유지하면서 파일 기반 애플리케이션과 자연스럽게 연동됩니다.

**왜 다른 보기는 오답인가**
- B: DataSync는 데이터 전송·마이그레이션 도구로, 지속적인 실시간 접근보다는 일회성/주기적 동기화에 적합합니다.
- C: 볼륨 게이트웨이는 블록 스토리지(iSCSI)를 제공하므로 파일 기반 애플리케이션에는 맞지 않습니다.
- D: EFS는 VPC 내 EC2/온프레미스 VPN 연결을 전제로 하는 AWS 네이티브 파일 시스템이라 다수의 원격 클리닉 환경에는 파일 게이트웨이보다 복잡하고 지연도 커집니다.

> 💡 **시험 꿀팁**: "S3에 있는 데이터를 온프레미스 파일 기반 애플리케이션에서 저지연 파일 인터페이스로 접근"해야 한다는 조건에는 **Storage Gateway 파일 게이트웨이**가 표준 정답입니다.

## QUESTION 244

**문제**: 한 회사가 단일 Amazon EC2 인스턴스에서 실행되는 콘텐츠 관리 시스템을 사용하고 있다. 이 EC2 인스턴스에는 웹 서버와 데이터베이스 소프트웨어가 모두 포함되어 있다. 회사는 웹 사이트 플랫폼을 고가용성으로 만들고 사용자 수요에 맞춰 확장할 수 있어야 한다. 이 요구 사항을 충족하기 위해 솔루션 설계자는 무엇을 권장해야 하는가?

**보기**
- A. 데이터베이스를 Amazon RDS로 이동하고 자동 백업을 활성화한다. 동일한 가용 영역에서 다른 EC2 인스턴스를 수동으로 시작한다. 해당 가용 영역에 Application Load Balancer를 구성하고 두 인스턴스를 대상으로 설정한다(단일 가용 영역에만 리소스를 두므로 해당 AZ 장애 시 전체 서비스가 중단되어 고가용성을 보장하지 못하고, 자동 확장도 없음).
- B. 기존 EC2 인스턴스와 동일한 가용 영역에 읽기 전용 복제본이 있는 Amazon Aurora로 데이터베이스를 마이그레이션한다. 동일한 가용 영역에서 다른 EC2 인스턴스를 수동으로 시작한다. Application Load Balancer를 구성하고 두 EC2 인스턴스를 대상으로 설정한다(데이터베이스 성능은 개선되지만 여전히 단일 AZ 구성이며 Auto Scaling이 없어 확장성 요구를 충족하지 못함).
- C. **다른 가용 영역에 읽기 전용 복제본이 있는 Amazon Aurora로 데이터베이스를 이동한다. EC2 인스턴스에서 AMI를 생성한다. 두 가용 영역에 Application Load Balancer를 구성한다. 두 가용 영역에서 해당 AMI를 사용하는 Auto Scaling 그룹을 연결한다.**
- D. 데이터베이스를 별도의 EC2 인스턴스로 이동하고 Amazon S3로 백업을 예약한다. 원래 EC2 인스턴스에서 AMI를 생성한다. 두 가용 영역에 Application Load Balancer를 구성한다. 두 가용 영역에서 AMI를 사용하는 Auto Scaling 그룹을 연결한다(데이터베이스를 여전히 단일 EC2 인스턴스로 자체 운영하므로 관리형 DB의 자동 장애 조치를 활용하지 못해 데이터 계층의 고가용성이 취약함).

**정답: C**

**해설**
**Amazon Aurora**를 다른 가용 영역의 읽기 전용 복제본과 함께 구성하면 기본 인스턴스 장애 시 자동 장애 조치가 가능해 데이터 계층의 고가용성이 확보됩니다. 여기에 EC2 **AMI**를 만들어 두 가용 영역에 걸친 **Auto Scaling 그룹**과 **Application Load Balancer**를 연결하면, 웹 계층도 여러 AZ에서 자동으로 확장·복구되어 애플리케이션 전체가 고가용성과 탄력적 확장성을 모두 갖추게 됩니다.

**왜 다른 보기는 오답인가**
- A: 단일 AZ 내 수동 인스턴스 추가는 AZ 장애에 취약하고 Auto Scaling이 없어 확장성도 없습니다.
- B: Aurora로 DB 성능은 좋아지지만 여전히 단일 AZ, 수동 인스턴스 구성이라 고가용성과 확장성 모두 부족합니다.
- D: 데이터베이스가 자체 관리 EC2 인스턴스로 남아 있어 DB 계층의 자동 장애 조치가 없고, S3 백업만으로는 실시간 고가용성을 보장할 수 없습니다.

> 💡 **시험 꿀팁**: "고가용성 + 확장성"을 동시에 요구하면 **다중 AZ Aurora(또는 RDS 다중 AZ) + 다중 AZ ALB + Auto Scaling 그룹** 조합이 표준 정답입니다.

## QUESTION 245

**문제**: 한 회사가 AWS에서 애플리케이션을 시작하고 있다. 애플리케이션은 Application Load Balancer(ALB)를 사용해 단일 대상 그룹에 속한 최소 2개의 Amazon EC2 인스턴스로 트래픽을 보낸다. 인스턴스는 각 환경의 Auto Scaling 그룹에 속해 있다. 이 회사는 개발 환경과 프로덕션 환경이 필요하며, 프로덕션 환경에는 트래픽이 많은 기간이 있다. 개발 환경을 가장 비용 효율적으로 구성하는 솔루션은 무엇인가?

**보기**
- A. **개발 환경의 대상 그룹을 하나의 EC2 인스턴스만 대상으로 하도록 재구성한다.**
- B. ALB 밸런싱 알고리즘을 최소 미해결 요청(least outstanding requests) 방식으로 변경한다(트래픽 분배 방식을 바꾸는 것일 뿐이며 인스턴스 수나 리소스 사용량 자체를 줄이지 않아 비용 절감과 무관함).
- C. 두 환경 모두에서 EC2 인스턴스 크기를 줄인다(개발 환경뿐 아니라 트래픽이 많은 프로덕션 환경까지 축소해 성능 저하 위험이 있고, "개발 환경만" 비용 효율화하라는 요구에 맞지 않음).
- D. 개발 환경의 Auto Scaling 그룹에서 최대 EC2 인스턴스 수를 줄인다(비용 절감에 다소 도움은 되지만 대상 그룹이 여전히 최소 2개 인스턴스 이상을 유지하도록 설계되어 있다면 근본적인 리소스 축소 효과가 A보다 작음).

**정답: A**

**해설**

## QUESTION 246

**문제**: 한 회사가 여러 가용 영역의 Amazon EC2 인스턴스에서 웹 애플리케이션을 실행한다. EC2 인스턴스는 프라이빗 서브넷에 있다. 솔루션 설계자가 인터넷 연결 ALB를 구현하고 EC2 인스턴스를 대상 그룹으로 지정했지만, 인터넷 트래픽이 EC2 인스턴스에 도달하지 않는다. 솔루션 설계자는 이 문제를 해결하기 위해 아키텍처를 어떻게 재구성해야 하는가?

**보기**
- A. ALB를 Network Load Balancer로 교체한다. 인터넷 트래픽을 허용하도록 퍼블릭 서브넷에 NAT 게이트웨이를 구성한다(로드 밸런서 종류를 바꾸고 NAT 게이트웨이를 추가해도, 인바운드 트래픽이 로드 밸런서에 도달하지 못하는 근본 원인인 서브넷 구성 문제는 해결되지 않음).
- B. EC2 인스턴스를 퍼블릭 서브넷으로 이동한다. EC2 인스턴스의 보안 그룹에 0.0.0.0/0 아웃바운드 트래픽을 허용하는 규칙을 추가한다(인스턴스를 인터넷에 직접 노출시켜 불필요한 보안 위험을 초래하며, 아웃바운드 규칙 추가는 인바운드 도달 문제와 무관함).
- C. EC2 인스턴스 서브넷의 라우팅 테이블이 0.0.0.0/0 트래픽을 인터넷 게이트웨이로 보내도록 업데이트한다. EC2 인스턴스의 보안 그룹에 0.0.0.0/0 아웃바운드 트래픽을 허용하는 규칙을 추가한다(프라이빗 서브넷에서 나가는 아웃바운드 경로만 다룰 뿐, ALB로 들어오는 인바운드 트래픽이 인스턴스에 도달하지 못하는 문제와는 무관함).
- D. **각 가용 영역에 퍼블릭 서브넷을 생성한다. 퍼블릭 서브넷을 ALB와 연결한다. 프라이빗 서브넷으로 가는 경로를 포함하도록 퍼블릭 서브넷의 라우팅 테이블을 업데이트한다.**

**정답: D**

**해설**
**인터넷 연결(internet-facing) ALB**는 로드 밸런서 노드 자체가 반드시 **퍼블릭 서브넷**에 위치해야 인터넷에서 오는 요청을 받을 수 있습니다. 각 가용 영역에 퍼블릭 서브넷을 생성해 ALB를 연결하면 인바운드 트래픽이 ALB에 도달할 수 있게 되고, 이후 ALB가 대상 그룹인 프라이빗 서브넷의 EC2 인스턴스로 트래픽을 전달합니다. EC2 인스턴스 자체는 계속 프라이빗 서브넷에 두어 보안을 유지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 로드 밸런서 유형 변경과 NAT 게이트웨이 추가는 문제의 원인인 "ALB가 인터넷 트래픽을 받을 퍼블릭 서브넷이 없다"는 점을 해결하지 못합니다.
- B: EC2를 퍼블릭 서브넷으로 옮기면 보안 요구 사항(프라이빗 서브넷 유지)에 위배되고 근본 문제도 해결되지 않습니다.
- C: 아웃바운드 인터넷 접근을 위한 구성이며, ALB로 들어오는 인바운드 트래픽 문제와는 관련이 없습니다.

> 💡 **시험 꿀팁**: 인터넷 연결 ALB인데 트래픽이 도달하지 않는다면, 먼저 **ALB가 놓인 서브넷이 퍼블릭 서브넷인지**부터 확인하는 것이 표준 해법입니다.

## QUESTION 247

**문제**: 한 회사가 Amazon RDS for MySQL에 데이터베이스를 배포했다. 트랜잭션 증가로 인해 데이터베이스 지원 팀이 DB 인스턴스에 대한 느린 읽기를 보고하며 읽기 전용 복제본 추가를 권장한다. 이 변경 사항을 구현하기 전에 솔루션 설계자가 수행해야 하는 작업 조합은 무엇인가? (2개 선택)

## QUESTION 248

**문제**: 한 회사가 Amazon EC2 인스턴스에서 분석 소프트웨어를 실행한다. 이 소프트웨어는 Amazon S3에 업로드된 데이터를 처리하기 위한 사용자의 작업 요청을 받는다. 일부 제출된 데이터가 처리되지 않고 있다는 사용자 보고가 있으며, Amazon CloudWatch는 EC2 인스턴스의 CPU 사용률이 지속적으로 100%에 가깝다는 것을 보여준다. 회사는 시스템 성능을 개선하고 사용자 부하에 따라 시스템을 확장하고자 한다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. 인스턴스를 복제해 Application Load Balancer 뒤에 모든 인스턴스를 배치한다(단순히 인스턴스를 늘려 ALB로 분산하는 것만으로는 부하 변화에 자동으로 대응하는 확장 메커니즘이 없어 근본 해결책이 아님).
- B. Amazon S3용 VPC 엔드포인트를 생성하고 이를 참조하도록 소프트웨어를 업데이트한다(S3 접근 시 네트워크 경로를 최적화할 뿐, CPU 사용률이 높은 처리 병목이나 확장성 문제 자체는 해결하지 못함).
- C. EC2 인스턴스를 중지하고 CPU와 메모리가 더 강력한 인스턴스 유형으로 변경한 뒤 다시 시작한다(수직 확장(scale-up)은 일시적으로 성능을 개선할 수 있지만 상한이 있고, 부하에 따라 자동으로 규모를 조절하는 확장성을 제공하지 않음).
- D. **들어오는 요청을 Amazon SQS로 라우팅한다. 대기열 크기를 기준으로 EC2 Auto Scaling 그룹을 구성한다. 대기열에서 읽도록 소프트웨어를 업데이트한다.**

**해설**
**Amazon SQS**로 작업 요청을 버퍼링하면 순간적인 요청 폭주로 인한 처리 유실을 막을 수 있고, **대기열 메시지 수(ApproximateNumberOfMessagesVisible)를 기준으로 EC2 Auto Scaling 그룹을 확장/축소**하도록 구성하면 작업 부하에 비례해 처리 인스턴스 수가 자동으로 조절됩니다. 이렇게 큐 기반 디커플링 아키텍처로 전환하면 CPU 과부하 문제와 확장성 요구를 동시에 해결할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스를 늘리는 것 자체는 맞는 방향이지만 자동 확장 메커니즘이 없어 부하 변화에 대응하지 못합니다.
- B: S3 VPC 엔드포인트는 네트워크 성능/보안에 도움이 될 뿐 CPU 병목이나 확장성과는 무관합니다.
- C: 더 큰 인스턴스로 교체하는 수직 확장은 한계가 있고 자동 확장을 제공하지 않습니다.

> 💡 **시험 꿀팁**: "처리 요청이 몰려 인스턴스가 과부하이고 부하에 따라 확장이 필요하다"는 조건에는 **SQS로 디커플링 + 큐 길이 기반 Auto Scaling**이 표준 정답 패턴입니다.

## QUESTION 249

**문제**: 한 회사가 AWS 클라우드에서 호스팅되는 미디어 애플리케이션을 위한 공유 스토리지 솔루션을 구현하고 있다. 이 회사는 SMB 클라이언트로 데이터에 접근할 수 있어야 하며, 솔루션은 완전 관리형이어야 한다. 어떤 AWS 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. AWS Storage Gateway 볼륨 게이트웨이를 생성한다. 필요한 클라이언트 프로토콜을 사용하는 파일 공유를 만든다. 애플리케이션 서버를 파일 공유에 연결한다(볼륨 게이트웨이는 블록 스토리지(iSCSI)를 제공하는 게이트웨이 유형으로 SMB 파일 공유 기능이 없음).
- B. AWS Storage Gateway 테이프 게이트웨이를 생성한다. S3를 사용하도록 테이프를 구성한다. 애플리케이션 서버를 테이프 게이트웨이에 연결한다(가상 테이프 라이브러리를 이용한 백업/아카이브 용도이며 SMB로 실시간 파일 공유를 제공하지 않음).

- D. **Windows File Server용 Amazon FSx를 생성한다. 원본 서버에 파일 시스템을 연결한다. 애플리케이션 서버를 파일 시스템에 연결한다.**

**정답: D**

**해설**
**Amazon FSx for Windows File Server**는 SMB 프로토콜을 네이티브로 지원하는 완전 관리형 Windows 파일 시스템으로, Windows ACL, Active Directory 통합, 자동 백업 등을 AWS가 직접 관리해 줍니다. 미디어 애플리케이션이 SMB 클라이언트로 데이터를 공유해야 하면서 운영 부담 없는 완전 관리형 솔루션을 원하는 이번 요구 사항에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: 볼륨 게이트웨이는 블록 수준 스토리지(iSCSI)를 제공하며 SMB 파일 공유 기능이 없습니다.
- B: 테이프 게이트웨이는 백업/아카이브용 가상 테이프 라이브러리이며 실시간 파일 공유 용도가 아닙니다.
- C: EC2 Windows 인스턴스에 직접 파일 공유를 구성하면 SMB는 가능하지만 서버 운영·패치를 직접 해야 해 완전 관리형이 아닙니다.

> 💡 **시험 꿀팁**: "SMB로 완전 관리형 공유 스토리지"라는 조건에는 **Amazon FSx for Windows File Server**가 표준 정답입니다.

- B. Amazon Kinesis를 대상으로 사용한다. 항상 90일 동안 로그를 유지하도록 Kinesis 스트림을 구성한다(Kinesis 스트림은 스트리밍 데이터 처리용이며 장기 보관 및 계층화된 스토리지 비용 최적화에 적합하지 않음).
- C. AWS CloudTrail을 대상으로 사용한다. S3 버킷에 저장하도록 CloudTrail을 구성하고 S3 Intelligent-Tiering을 활성화한다(CloudTrail은 API 활동 감사용 서비스로, VPC 흐름 로그(네트워크 트래픽 로그) 자체를 캡처하는 대상이 될 수 없음).
- D. **Amazon S3를 대상으로 사용한다. S3 수명 주기 정책을 활성화해 90일 후 로그를 S3 Standard-IA로 전환한다.**

**정답: D**

**해설**
VPC 흐름 로그는 **Amazon S3**를 직접 전송 대상으로 지정할 수 있으며, **S3 수명 주기 정책**으로 생성 후 90일이 지난 객체를 자동으로 **S3 Standard-IA**로 전환하면 자주 액세스하는 기간에는 표준 스토리지의 성능을, 그 이후에는 저렴한 IA 스토리지 비용을 누릴 수 있어 이번 접근 패턴에 가장 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- A: CloudWatch Logs는 만료 후 로그를 완전히 삭제하는 보존 기간만 제공하며 스토리지 계층 전환 개념이 없습니다.
- B: Kinesis는 스트리밍 처리에 최적화되어 있고 장기 보관·계층형 비용 최적화 용도가 아닙니다.
- C: CloudTrail은 API 호출 감사 로그를 다루는 서비스로 VPC 흐름 로그의 대상이 될 수 없습니다.

> 💡 **시험 꿀팁**: "일정 기간 자주 접근하다가 그 이후 간헐적으로 접근"하는 패턴에는 **S3 + 수명 주기 정책으로 Standard-IA 전환**이 표준 정답 패턴입니다.

## QUESTION 251

**문제**: Amazon EC2 인스턴스가 새 VPC의 프라이빗 서브넷에 있다. 이 서브넷에는 아웃바운드 인터넷 액세스 권한이 없지만, EC2 인스턴스는 외부 공급업체로부터 월별 보안 업데이트를 다운로드할 수 있어야 한다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. 인터넷 게이트웨이를 생성해 VPC에 연결한다. 인터넷 게이트웨이를 기본 경로로 사용하도록 프라이빗 서브넷 라우팅 테이블을 구성한다(프라이빗 서브넷에 직접 인터넷 게이트웨이 경로를 부여하면 인스턴스가 퍼블릭 IP 없이는 여전히 인터넷에 접근할 수 없고, 보안상 프라이빗 서브넷을 사실상 퍼블릭화하는 셈이라 바람직하지 않음).
- B. **NAT 게이트웨이를 생성해 퍼블릭 서브넷에 배치한다. NAT 게이트웨이를 기본 경로로 사용하도록 프라이빗 서브넷 라우팅 테이블을 구성한다.**
- C. NAT 인스턴스를 생성해 EC2 인스턴스와 동일한 서브넷에 배치한다. NAT 인스턴스를 기본 경로로 사용하도록 프라이빗 서브넷 라우팅 테이블을 구성한다(NAT 인스턴스는 자체 EC2 관리·패치·확장을 직접 해야 해 완전 관리형인 NAT 게이트웨이보다 운영 부담이 크고 권장되지 않음).
- D. 인터넷 게이트웨이를 생성해 VPC에 연결한다. NAT 인스턴스를 생성해 EC2 인스턴스와 동일한 서브넷에 배치한다. 인터넷 게이트웨이를 기본 경로로 사용하도록 프라이빗 서브넷 라우팅 테이블을 구성한다(불필요하게 인터넷 게이트웨이와 NAT 인스턴스를 함께 사용하면서도 프라이빗 서브넷을 인터넷 게이트웨이로 직접 라우팅해 보안 원칙에 어긋나고 구성만 복잡해짐).

프라이빗 서브넷의 인스턴스가 인바운드 노출 없이 아웃바운드 인터넷 접근만 필요할 때는 **NAT 게이트웨이**를 퍼블릭 서브넷에 배치하고, 프라이빗 서브넷의 기본 경로(0.0.0.0/0)를 이 NAT 게이트웨이로 향하게 하는 것이 표준 패턴입니다. NAT 게이트웨이는 AWS가 완전 관리형으로 제공해 고가용성과 확장성을 자동으로 처리하므로, 인스턴스가 프라이빗 상태를 유지하면서도 외부 공급업체의 보안 업데이트를 안전하게 다운로드할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 프라이빗 서브넷에 인터넷 게이트웨이를 직접 연결하는 것은 아웃바운드 전용 접근이라는 목적에 맞지 않고 보안 원칙에도 어긋납니다.
- C: NAT 인스턴스는 동작은 가능하지만 자체 관리·패치·이중화가 필요해 NAT 게이트웨이보다 운영 부담이 크고 AWS가 일반적으로 권장하지 않습니다.
- D: 인터넷 게이트웨이와 NAT 인스턴스를 불필요하게 함께 사용하면서 프라이빗 서브넷을 인터넷 게이트웨이로 직접 라우팅해 목적에 맞지 않고 구성만 복잡해집니다.

> 💡 **시험 꿀팁**: "프라이빗 서브넷에서 아웃바운드 인터넷만 필요"하다는 조건에는 **퍼블릭 서브넷의 NAT 게이트웨이 + 프라이빗 서브넷 기본 경로 설정**이 표준 정답입니다.

**문제**: 솔루션 설계자가 고객 사례 파일을 저장할 시스템을 설계해야 한다. 파일은 핵심 회사 자산이며 중요하다. 파일 수는 시간이 지남에 따라 증가한다. 파일은 Amazon EC2 인스턴스에서 실행되는 여러 애플리케이션 서버에서 동시에 접근할 수 있어야 하며, 솔루션에는 중복성이 내장되어 있어야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

> 💡 **시험 꿀팁**: "여러 EC2 인스턴스에서 동일 파일에 동시 접근 + 자동 확장 + 내장 중복성"이 나오면 **Amazon EFS**가 표준 정답입니다.

- D: 서브넷 CIDR 기반 규칙도 해당 서브넷 내 모든 인스턴스를 허용하는 것이라 계층별 세밀한 제어가 되지 않습니다.

> 💡 **시험 꿀팁**: "애플리케이션 계층 간 최소 권한(세밀한 접근 제어)"이 조건으로 나오면 **보안 그룹 ID를 소스/대상으로 참조**하는 방식이 표준 정답입니다.

**문제**: 한 회사에 데이터베이스에 주문을 기록하고 결제를 처리하기 위해 서비스를 호출하는 전자 상거래 체크아웃 워크플로우가 있다. 사용자가 체크아웃 과정에서 시간 초과를 겪고 있으며, 체크아웃 양식을 다시 제출하면 동일한 거래에 대해 여러 개의 고유 주문이 생성된다. 중복 주문 생성을 방지하기 위해 솔루션 설계자는 이 워크플로우를 어떻게 리팩터링해야 하는가?

**보기**
- A. 웹 애플리케이션이 Amazon Kinesis Data Firehose로 주문 메시지를 보내도록 구성한다. 결제 서비스가 Kinesis Data Firehose에서 메시지를 검색해 주문을 처리하도록 설정한다(Data Firehose는 데이터를 S3/Redshift 등 대상으로 일괄 전달하는 스트리밍 적재 서비스로, 순차적이고 정확히 한 번 처리되는 주문 처리 보장을 제공하지 않음).
- B. 기록된 애플리케이션 경로 요청을 기반으로 AWS Lambda 함수를 호출하도록 AWS CloudTrail에 규칙을 생성한다. Lambda로 데이터베이스를 쿼리하고 결제 서비스를 호출해 주문 정보를 전달한다(CloudTrail은 API 활동 감사·기록용 서비스라 이를 트리거로 사용하는 방식은 안정적이고 순차적인 주문 처리를 보장하지 않음).
- C. 데이터베이스에 주문을 저장한다. 주문 번호가 포함된 메시지를 Amazon SNS로 보낸다. 결제 서비스가 SNS를 폴링해 메시지를 검색하고 주문을 처리하도록 설정한다(SNS는 폴링 방식의 대기열이 아닌 게시-구독 푸시 메시징 서비스이며, 메시지 중복 제거나 순서 보장 기능이 없어 재처리·중복 위험이 있음).
- D. **데이터베이스에 주문을 저장한다. 주문 번호가 포함된 메시지를 Amazon SQS FIFO 대기열로 보낸다. 결제 서비스가 메시지를 검색해 주문을 처리하고 대기열에서 메시지를 삭제하도록 설정한다.**

**정답: D**

**해설**
**Amazon SQS FIFO 대기열**은 메시지 그룹 ID 기준의 순서 보장과 **콘텐츠 기반 중복 제거(또는 명시적 중복 제거 ID)** 기능을 제공해, 동일한 거래에 대한 재제출 요청이 들어와도 동일한 주문이 중복 처리되지 않도록 막을 수 있습니다. 결제 서비스가 메시지를 처리한 뒤 대기열에서 삭제하는 방식은 "정확히 한 번" 처리에 가까운 안정적인 워크플로우를 보장해 체크아웃 시간 초과로 인한 중복 주문 문제를 근본적으로 해결합니다.

**왜 다른 보기는 오답인가**
- A: Kinesis Data Firehose는 데이터를 목적지로 일괄 전달하는 데 최적화되어 있으며 중복 제거나 순차 처리 보장이 목적이 아닙니다.
- B: CloudTrail은 API 호출 감사 로그를 다루는 서비스로, 이를 트리거로 쓰는 방식은 신뢰할 수 있는 주문 처리 파이프라인이 되지 못합니다.
- C: SNS는 발행-구독 푸시 모델이라 폴링 자체가 부자연스럽고, 표준 SNS/SQS 조합이 아니라면 메시지 중복 방지 기능이 없습니다.

> 💡 **시험 꿀팁**: "재시도/재제출로 인한 중복 처리를 방지"해야 한다는 조건에는 **Amazon SQS FIFO 대기열의 중복 제거 기능**이 표준 정답입니다.

- E: KMS 암호화는 데이터 기밀성 보호가 목적이며 삭제 방지나 버전 관리와는 관련이 없습니다.

> 💡 **시험 꿀팁**: "모든 버전 보존 + 우발적 삭제 방지"라는 조건이 함께 나오면 **S3 버전 관리 + MFA 삭제** 조합이 표준 정답입니다.

## QUESTION 258

**문제**: 한 회사에 매시간 수백 개의 1GB짜리 .csv 파일을 Amazon S3 버킷에 업로드하는 애플리케이션이 있다. 파일이 업로드될 때마다 회사는 이를 Apache Parquet 형식으로 변환해 출력 파일을 다른 S3 버킷에 저장해야 한다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. .csv 파일을 다운로드해 Parquet 형식으로 변환하고 출력 파일을 S3 버킷에 저장하는 AWS Lambda 함수를 생성한다. 각 S3 PUT 이벤트마다 Lambda 함수를 호출한다(1GB 크기의 파일을 Lambda 메모리/실행 시간 제한 안에서 직접 변환해야 해 동시성·타임아웃·메모리 관리를 세밀하게 신경 써야 하므로 운영 부담이 큼).
- B. .csv 파일을 읽어 Parquet 형식으로 변환하고 S3에 저장하는 Apache Spark 작업을 생성한다. 각 S3 PUT 이벤트마다 이 Spark 작업을 호출하는 Lambda 함수를 생성한다(Spark 클러스터를 별도로 프로비저닝·관리해야 하고 Lambda로 매번 호출·조율까지 해야 해 불필요한 복잡성과 운영 부담이 큼).
- C. .csv 파일이 업로드되는 S3 버킷에 대해 AWS Glue 테이블과 크롤러를 생성한다. Amazon Athena로 주기적으로 Glue 테이블을 쿼리하고, 쿼리 결과를 Parquet로 변환해 S3에 저장하는 Lambda 함수를 예약한다(업로드 이벤트가 아닌 주기적 스케줄에 의존해 실시간성이 떨어지고, 크롤러·Athena·Lambda를 조합한 과도하게 복잡한 파이프라인임).
- D. **.csv 파일을 Parquet 형식으로 변환해 출력 파일을 S3 버킷에 저장하는 AWS Glue ETL 작업을 생성한다. 각 S3 PUT 이벤트마다 이 ETL 작업을 호출하는 Lambda 함수를 생성한다.**

**정답: D**

**해설**
**AWS Glue ETL 작업**은 대용량 파일의 형식 변환(CSV → Parquet)을 서버리스 Spark 기반으로 완전 관리형으로 처리해 주며, 인프라 프로비저닝이나 클러스터 관리가 필요 없습니다. 여기에 **S3 PUT 이벤트로 Lambda 함수를 트리거해 Glue ETL 작업을 호출**하는 방식은 파일이 업로드될 때마다 자동으로 변환 파이프라인이 실행되도록 해, 대용량 파일 처리와 최소 운영 오버헤드 요구를 동시에 충족합니다.

**왜 다른 보기는 오답인가**
- A: 1GB 파일을 Lambda 내에서 직접 처리하면 메모리·실행 시간 제한, 동시성 관리 등 신경 써야 할 운영 부담이 큽니다.
- B: 별도의 Spark 클러스터를 직접 프로비저닝하고 관리해야 해 Glue ETL보다 복잡성과 오버헤드가 큽니다.
- C: 업로드 즉시 처리되지 않고 주기적 쿼리에 의존하는 구조라 실시간성이 떨어지고 파이프라인이 불필요하게 복잡합니다.

> 💡 **시험 꿀팁**: "S3에 파일이 올라올 때마다 대용량 형식 변환(예: CSV → Parquet)을 최소 오버헤드로 자동화"해야 한다는 조건에는 **S3 이벤트 → Lambda → AWS Glue ETL 작업**조합이 표준 정답입니다.

- B. 일일 스냅샷을 위해 RDS DB 인스턴스의 백업 기간을 구성한다. 각 RDS DB 인스턴스에 2년의 스냅샷 보존 정책을 할당한다. Amazon DLM을 사용해 스냅샷 삭제를 예약한다(Amazon DLM은 EBS 스냅샷 수명 주기 관리 도구로 RDS 스냅샷과는 호환되지 않아 RDS 스냅샷 삭제 예약에 사용할 수 없음).
- C. 만료 기간이 2년인 Amazon CloudWatch Logs에 자동 백업되도록 데이터베이스 트랜잭션 로그를 구성한다(트랜잭션 로그는 변경 사항만 기록할 뿐 데이터베이스 전체 상태의 일관된 스냅샷이 아니므로 특정 시점 전체 복원에 충분하지 않음).
- D. AWS DMS 복제 작업을 구성한다. 복제 인스턴스를 배포하고 CDC 작업을 구성해 데이터베이스 변경 사항을 S3로 스트리밍한다. 2년 후 삭제하도록 S3 수명 주기 정책을 구성한다(DMS는 데이터베이스 마이그레이션/복제를 위한 서비스이며 일관되고 복원 가능한 백업을 생성·관리하는 목적의 서비스가 아님).

**정답: A**

**해설**
**AWS Backup**은 백업 볼트에 백업을 중앙 집중식으로 저장하고, 백업 계획을 통해 일일 백업 일정과 2년 보존 기간(수명 주기)을 정책으로 정의할 수 있는 완전 관리형 서비스입니다. RDS DB 인스턴스를 이 백업 계획에 할당하면 AWS가 자동으로 일관된 스냅샷 기반 백업을 생성·보존·삭제해 주므로, "최소 2년 보존 + 일관되고 복원 가능한 일일 백업"이라는 요구 사항을 운영 부담 없이 충족합니다.

**왜 다른 보기는 오답인가**
- B: Amazon DLM은 EBS 볼륨 스냅샷 전용 도구로 RDS 스냅샷의 수명 주기 관리에는 사용할 수 없습니다.
- C: 트랜잭션 로그만으로는 데이터베이스의 전체 일관된 상태를 복원할 수 없어 요구되는 복원 가능성을 충족하지 못합니다.
- D: DMS는 마이그레이션과 CDC 복제에 초점을 맞춘 서비스이며, 정책 기반의 장기 백업 보존·관리 기능을 제공하지 않습니다.

> 💡 **시험 꿀팁**: "여러 리소스에 걸쳐 정책 기반의 장기(예: 수년) 백업 보존"이 요구되면 **AWS Backup의 백업 볼트 + 백업 계획**이 표준 정답입니다.

## QUESTION 260

**문제**: 한 회사의 규정 준수 팀이 파일 공유를 AWS로 이동해야 한다. 이 공유는 Windows Server SMB 파일 공유에서 실행되며, 자체 관리형 온프레미스 Active Directory가 파일 및 폴더에 대한 접근을 제어한다. 회사는 솔루션의 일부로 Windows File Server용 Amazon FSx를 사용하려 하며, 온프레미스 Active Directory 그룹이 AWS로 이동한 후에도 FSx for Windows File Server의 SMB 공유, 폴더, 파일에 대한 접근을 계속 제한할 수 있도록 해야 한다. 회사는 이미 Windows File Server용 FSx 파일 시스템을 생성했다. 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. Active Directory에 연결할 Active Directory 커넥터를 생성한다. Active Directory 그룹을 IAM 그룹에 매핑해 접근을 제한한다(IAM은 AWS 리소스에 대한 API 수준 접근을 관리하는 서비스이며, 파일·폴더 수준의 SMB 파일 시스템 권한 제어를 대체할 수 없음).
- B. 제한 태그 키와 규정 준수 태그 값을 가진 태그를 할당한다. Active Directory 그룹을 IAM 그룹에 매핑해 접근을 제한한다(태그는 리소스를 분류·관리하는 용도일 뿐 인증이나 파일 수준 접근 제어 메커니즘을 제공하지 않음).
- C. 접근 제한을 위해 FSx for Windows File Server에 직접 연결된 IAM 서비스 연결 역할을 생성한다(서비스 연결 역할은 AWS 서비스가 다른 AWS 리소스에 접근하도록 권한을 위임하는 용도이며, 온프레미스 AD 사용자·그룹 기반의 파일 접근 제어와는 무관함).
- D. **파일 시스템을 Active Directory에 연결(join)해 접근을 제한한다.**

**정답: D**

**해설**
**FSx for Windows File Server**를 기존 온프레미스 **Active Directory(자체 관리형 AD)**에 연결(도메인 조인)하면, 파일 시스템이 온프레미스 AD의 사용자·그룹 정보와 Windows NTFS ACL을 그대로 활용해 SMB 공유, 폴더, 파일 단위의 접근 제어를 수행할 수 있습니다. 이를 통해 회사는 기존에 구축해 둔 AD 기반 권한 체계를 그대로 클라우드로 확장해, AWS 마이그레이션 이후에도 동일한 규정 준수 접근 통제를 유지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: IAM은 AWS API/리소스에 대한 권한을 관리하는 체계로, SMB 파일 시스템의 파일·폴더 수준 권한(Windows ACL)을 대체하지 못합니다.
- B: 태그는 리소스 메타데이터일 뿐이며 인증이나 세밀한 파일 접근 제어 기능이 없습니다.
- C: IAM 서비스 연결 역할은 AWS 서비스 간 권한 위임을 위한 것으로 온프레미스 AD 통합과는 관련이 없습니다.

> 💡 **시험 꿀팁**: "온프레미스 AD 그룹으로 FSx의 SMB 파일/폴더 접근을 그대로 제어"해야 한다는 조건에는 **FSx 파일 시스템을 Active Directory에 조인**하는 것이 표준 정답입니다.
