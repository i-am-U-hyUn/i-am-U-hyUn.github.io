## QUESTION 1

**Question**: A company needs to design a hybrid DNS solution. Resources stored in VPCs use an Amazon Route 53 private hosted zone for the domain `cloud.example.com`. Requirements:
- On-premises systems must be able to resolve and connect to `cloud.example.com`
- All VPCs must be able to resolve `cloud.example.com`
- An AWS Direct Connect connection already exists between the on-premises network and an AWS Transit Gateway

Which architecture meets these requirements with the best performance?

**Choices**
- A. Associate the private hosted zone with all VPCs. Create a Route 53 **inbound** resolver in the shared services VPC. Connect all VPCs to the transit gateway, and create a forwarding rule on the on-premises DNS server pointing to the inbound resolver for `cloud.example.com`.
- B. Associate the private hosted zone with all VPCs. Deploy an Amazon EC2 conditional forwarder in the shared services VPC. Create a forwarding rule on the on-premises DNS server pointing to this forwarder.
- C. Associate the private hosted zone with the shared services VPC only. Create a Route 53 **outbound** resolver in the shared services VPC. Create a forwarding rule on the on-premises DNS server pointing to the outbound resolver.
- D. Associate the private hosted zone with the shared services VPC only. Create a Route 53 inbound resolver in the shared services VPC. Connect only the shared services VPC to the transit gateway and create the forwarding rule.

**Correct Answer: A**

**Explanation**
For on-premises to resolve records in a VPC's private hosted zone, you need a **Route 53 Resolver inbound endpoint** to receive queries flowing from on-premises into AWS. The on-premises DNS server sets up a conditional forwarding rule for `cloud.example.com` pointing to this inbound endpoint. At the same time, to satisfy "all VPCs must resolve it" with the best performance, the private hosted zone itself must be associated directly with every VPC — rather than adding an extra hop through the shared services VPC on every query.

**Why the other choices are wrong**
- B: An EC2 conditional forwarder is a self-managed solution you must operate yourself, carrying more operational overhead and lower availability than the managed Route 53 Resolver service.
- C: The outbound resolver is used when resources *inside* a VPC need to resolve *on-premises* DNS names — the opposite direction of what this question requires (on-premises → VPC).
- D: Limiting the hosted zone association and transit gateway connection to only the shared services VPC forces every other VPC to hop through it on each query, adding latency and failing the "best performance" requirement.

> 💡 **Exam tip**: Remember Route 53 Resolver direction as **inbound = receiving queries coming into AWS from on-premises**, **outbound = forwarding queries out from AWS to on-premises**.

## QUESTION 2

**Question**: A REST API runs on Amazon API Gateway with AWS Lambda integrations, has a Route 53 record `weather.example.com`, and stores data in Amazon DynamoDB. The company needs the API to be able to fail over to another AWS Region. Which solution fits?

**Choices**
- A. Deploy a new set of Lambda functions in a new Region. Update API Gateway to use an edge-optimized API endpoint targeting both Regions' Lambda functions. Convert the DynamoDB table into a global table.
- B. Deploy a new API Gateway API and Lambda functions in another Region. Change the Route 53 record to **Multivalue Answer** routing, add both API Gateway APIs, and enable target health monitoring. Convert DynamoDB into a global table.
- C. Deploy a new API Gateway API and Lambda functions in another Region. Change the Route 53 record to a **Failover** record and enable target health monitoring. Convert DynamoDB into a global table.
- D. Deploy a new API Gateway API in a new Region and turn the Lambda function into a "global function." Change the Route 53 record to Multivalue Answer. Convert DynamoDB into a global table.

**Correct Answer: C**

**Explanation**
"Failing over to another Region" describes an **active-passive** pattern: the primary Region normally handles all traffic, and only switches to the secondary Region on failure. Route 53's **Failover routing policy** (primary/secondary records plus health checks) is purpose-built for exactly this scenario. Synchronizing data across both Regions via a DynamoDB global table is also required.

**Why the other choices are wrong**
- A: A single edge-optimized endpoint targeting two Regions at once isn't an actual failover mechanism, and the traffic-switching logic is undefined.
- B: Multivalue Answer randomly mixes responses among healthy resources, meaning traffic could be spread across both Regions even under normal conditions — that contradicts the active-passive "only switch on failure" requirement.
- D: There's no such thing as a "global Lambda function," and the Multivalue Answer combination has the same flaw as B.

> 💡 **Exam tip**: **Failover routing policy** = active-passive (primary/secondary). **Multivalue Answer** = random response among multiple healthy resources (closer to load distribution). Whenever you see "only switch over on failure," think Failover routing policy.

## QUESTION 3

**Question**: A company manages multiple accounts under AWS Organizations with a single OU named `Production`. A deny-list SCP at the organization root restricts access to certain services. The company recently acquired a new business unit and invited its existing AWS account into the organization. After onboarding, the new unit's administrator finds they cannot update existing AWS Config rules to meet company policy, because the SCP blocks it. What option lets the administrator change and continue enforcing the current policy without extra long-term maintenance?

**Choices**
- A. Remove the root SCP restricting access to AWS Config. Create an AWS Service Catalog product for the company's standard AWS Config rules and deploy it org-wide, including to the new account.
- B. Create a temporary OU named `Onboarding` for the new account. Attach an SCP to the Onboarding OU that allows AWS Config actions. Once Config tuning is complete, move the new account to the Production OU. (The root SCP stays where it is.)
- C. Convert the root SCP from a deny-list to an allow-list style, and temporarily attach an SCP to the root that allows AWS Config actions for only the new account's principals.
- D. Create a temporary OU named `Onboarding` for the new account. Attach an SCP to the Onboarding OU that allows AWS Config actions. **Move the existing root SCP to the Production OU.** Once Config tuning is complete, move the new account to the Production OU.

**Correct Answer: D**

**Explanation**
The key concept here is **how SCPs are evaluated**: effective permissions are the **intersection** of every SCP that applies to an account (root → OU → account), and an explicit **Deny at a higher level can never be overridden by an Allow at a lower level.** As long as the deny SCP remains at the organization root, attaching any Allow SCP to the new Onboarding OU won't help — Config will still be blocked. The fix is to **move the deny SCP from the root to the Production OU**, so it simply never applies to the Onboarding OU in the first place. Once tuning is done, moving the account into Production reapplies the original restriction.

**Why the other choices are wrong**
- A: Removing the root SCP entirely eliminates the organization-wide restriction policy, undermining the original security goal (controlling access to restricted services).
- B: Nearly identical procedure to D, but it leaves the root SCP in place — per the SCP intersection rule, the Onboarding OU's Allow SCP still can't override the root's Deny, so the problem isn't actually solved. (This is the critical difference from D!)
- C: Rewriting the root SCP's fundamental style (deny-list → allow-list) has a large blast radius on the whole organization's policy and is a major structural change, not something that avoids "long-term maintenance."

> 💡 **Exam tip**: **SCPs evaluate as Deny-wins, intersection-based.** To carve out an exception for one OU/account, don't add an Allow underneath it — instead move the restrictive Deny SCP's **attachment point** so it only applies to what you actually want restricted.

## QUESTION 4

**Question**: An on-premises two-tier application (stateful, PostgreSQL backend) is being migrated to AWS using Amazon Aurora PostgreSQL, EC2 Auto Scaling, and Elastic Load Balancing. Which solution provides a consistent user experience while both tiers can scale?

**Choices**
- A. Enable Aurora Auto Scaling on Aurora **replicas**, use a **Network Load Balancer** with the **least outstanding requests** algorithm and sticky sessions enabled
- B. Enable Aurora Auto Scaling on the Aurora **writer**, use an Application Load Balancer with round-robin routing and sticky sessions enabled
- C. Enable Aurora Auto Scaling on Aurora **replicas**, use an **Application Load Balancer** with **round-robin routing** and sticky sessions enabled
- D. Enable Aurora Auto Scaling on the Aurora writer, use a Network Load Balancer with the least outstanding requests algorithm and sticky sessions enabled

**Correct Answer: C**

**Explanation**
Aurora Auto Scaling can only adjust the number of **read replicas**; the single **writer instance is never a scaling target.** So any option that says "Auto Scaling on the writer" (B, D) is wrong on its face. The application is also described as **stateful**, meaning it needs session stickiness — and cookie-based sticky sessions at Layer 7 are an **ALB** feature; an NLB operates at Layer 4 and doesn't support this kind of application-layer stickiness.

**Why the other choices are wrong**
- A: The scaling target (replicas) is correct, but "least outstanding requests" is an ALB-only routing algorithm that doesn't exist on an NLB.
- B: The premise itself is wrong — Aurora's architecture doesn't allow Auto Scaling on the writer.
- D: Same writer-scaling flaw as B, plus an inaccurate description of NLB routing algorithms.

> 💡 **Exam tip**: "Aurora Auto Scaling" only ever targets read replicas. Whenever you see a stateful application with a sticky-session requirement, think **ALB** (cookie-based) first, and don't confuse it with an NLB (Layer 4).

## QUESTION 5

**Question**: A company runs an on-premises metadata collection service. Legacy consumer devices (TVs, internet radios) don't support certain HTTP headers and error out when those headers appear in the response. Today, an on-premises load balancer strips the problematic headers from responses to legacy devices identified by their User-Agent header. The service has already been migrated to a set of Lambda functions, and the company wants to move to serverless while continuing to support legacy devices.

**Choices**
- A. Create a CloudFront distribution for the metadata service → create an ALB → configure CloudFront to forward requests to the ALB → configure the ALB to invoke the correct Lambda function per request type → create a **CloudFront Function** that strips problematic headers based on the User-Agent value
- B. Create an Amazon API Gateway REST API → integrate the correct Lambda per request type → modify the **default gateway response** to strip headers based on User-Agent
- C. Create an Amazon API Gateway **HTTP API** → integrate the correct Lambda per request type → build a **response mapping template** that strips headers based on User-Agent
- D. Same CloudFront + ALB setup as A → create a **Lambda@Edge** function that strips problematic headers from the end-user response

**Correct Answer: A**

**Explanation**
For a lightweight task like simply stripping response headers, AWS recommends **CloudFront Functions**. They're ultra-lightweight functions that run at the edge with sub-millisecond latency, cost less than Lambda@Edge, and are purpose-built for simple viewer-request/response operations like header manipulation or URL rewrites.

**Why the other choices are wrong**
- B: The "default gateway response" feature customizes API Gateway's own error responses (e.g., authentication failures) — it isn't meant for dynamically stripping headers from a normal, successful Lambda-integration response based on User-Agent.
- C: **API Gateway HTTP APIs, unlike REST APIs, do not support response mapping templates (VTL).** This choice assumes a feature that doesn't exist, making it wrong on its face.
- D: Lambda@Edge could technically do this, but it's heavier and more expensive than CloudFront Functions for such a simple header-stripping task. AWS's own guidance is to reserve Lambda@Edge for complex logic, external network calls, or origin-request processing, and use CloudFront Functions for simple viewer-level request/response handling.

> 💡 **Exam tip**: The **CloudFront Functions vs. Lambda@Edge** distinction shows up often. Simple/lightweight (header/URL manipulation, viewer stage) → CloudFront Functions. Complex logic, origin processing, external calls → Lambda@Edge. Also remember: **HTTP API does not support mapping templates** — a common trap in these questions.

## QUESTION 6

**Question**: A retail company (Account A) needs to let a business partner's IAM user, `User_DataProcessor`, in the partner's own account (Account B) access data files stored in Account A's S3 bucket. Which two actions are needed? (Choose two.)

**Choices**
- A. Turn on cross-origin resource sharing (CORS) for Account A's S3 bucket.
- B. Set an (incompletely configured) S3 bucket policy in Account A.
- C. In Account A, set the S3 bucket policy with `User_DataProcessor` (Account B's IAM user ARN) as the Principal, correctly allowing actions like `s3:GetObject` and `s3:ListBucket`.
- D. Grant `User_DataProcessor` (incomplete/misconfigured) IAM permissions in Account B.
- E. In Account B, correctly grant `User_DataProcessor` an IAM policy allowing `s3:GetObject`, `s3:ListBucket`, etc. on the relevant S3 resource.

> ⚠️ The IAM/S3 policy JSON snippets in the original PDF were garbled during scanning and could not be reliably reconstructed. The explanation below focuses on the core concept behind each choice.

**Correct Answer: C, E**

**Explanation**
For an IAM **user** (not a role) to access an S3 bucket owned by a different account, **both accounts must explicitly grant permission.** ① The account that owns the resource (Account A) must use a **bucket policy (resource-based policy)** naming the specific user in Account B as the Principal, and ② the account the requester actually belongs to (Account B) must also grant that user an **IAM policy (identity-based policy)** allowing the action. If either side is missing, access is denied.

**Why the other choices are wrong**
- A: CORS governs cross-origin requests made from a browser (fetching resources from a page on a different domain) — it has nothing to do with granting cross-account permissions.
- B, D: Both point in the right general direction (bucket policy, IAM policy respectively) but are presented as incomplete or misconfigured variants rather than the actual correct combination represented by C and E.

> 💡 **Exam tip**: For a different account's **IAM user** to access your S3 bucket, you need **both** a bucket policy (resource side) and an IAM policy (user's own side). (Note: if the other party accesses via an **assumed IAM role** instead, the requirements can differ.)

## QUESTION 7

**Question**: A web application running on EC2 is being refactored into container-based microservices. There are two environments, production and test. Load is variable but the min/max are known. What is the most cost-effective serverless architecture that minimizes operational complexity?

**Choices**
- A. Upload the container image as a Lambda function, configure a concurrency limit sized for the expected peak load, and configure two Lambda integrations in API Gateway — one for production, one for test.
- B. Upload the container image to ECR, configure two auto-scaling **ECS** clusters (production and test) using the **Fargate** launch type, and route traffic to each via separate ALBs.
- C. Same as B, but use **EKS** clusters instead of ECS.
- D. Upload the container image to Elastic Beanstalk with separate environments for production and test.

**Correct Answer: B**

**Explanation**
For a **continuous container workload with known min/max load**, **ECS on Fargate** — which auto-scales within a defined capacity range without any server management — is more cost-effective than Lambda's per-invocation billing model. Lambda also caps execution time at 15 minutes, and a static concurrency limit doesn't flexibly scale with actual traffic, making it less suited to an ongoing microservices workload.

**Why the other choices are wrong**
- A: A fixed concurrency limit doesn't scale flexibly with real traffic changes, and for a continuously-running microservice workload, it may not be as cost-effective as Fargate.
- C: EKS carries more Kubernetes control-plane management overhead than ECS, contradicting the "minimize operational complexity" requirement.
- D: Elastic Beanstalk still manages EC2 instances under the hood, so it carries more operational overhead than the truly server-management-free Fargate approach.

> 💡 **Exam tip**: When you see "continuous container workload with a known load range + minimal operational complexity," reach for **ECS on Fargate** first. Also remember EKS always carries more operational overhead than ECS.

## QUESTION 8

**Question**: A multi-tier web application runs on EC2 behind an ALB with an Auto Scaling group. The same setup is replicated in a backup Region, but the backup Region's ASG min/max is set to 0. RDS is Multi-AZ with a read replica in the backup Region. The company can't afford an active-active setup, but needs automatic failover to the backup Region with an RTO under 15 minutes.

**Choices**
- A. Use **latency-based routing** to split traffic across both ALBs, and a CloudWatch alarm (based on the 5XX metric) that triggers a Lambda function to promote the replica.
- B. Configure Route 53 with a health check and a **Failover routing policy**, normally using only the primary Region; on health-check failure, SNS notifies a Lambda function that promotes the replica and adjusts the ASG values, then traffic fails over to the backup Region's ALB.
- C. Keep the backup Region's ASG permanently sized the same as the primary Region's, with latency-based routing.
- D. Use AWS Global Accelerator with two equally-weighted endpoints, and a CloudWatch-alarm-triggered Lambda function to promote the replica.

**Correct Answer: B**

**Explanation**
An ASG min/max of **0** in the backup Region signals a **warm standby (close to pilot-light) pattern** — there are normally no running instances there at all. Under this design, any routing method that sends traffic to the backup Region under normal conditions (latency-based in A/C, weighted in D) causes errors, since there's nothing running to serve it. The correct approach uses only the primary Region under normal conditions and switches over **only on failure**, via a **Failover routing policy** plus health checks — with a Lambda function automating replica promotion and ASG capacity adjustment once a failure is detected.

**Why the other choices are wrong**
- A, D: Both route some traffic to the backup Region even under normal conditions, which structurally conflicts with an ASG min value of 0 (no running instances).
- C: Keeping the backup Region's ASG permanently matched to the primary Region's size effectively incurs active-active-level costs, contradicting the stated budget constraint.

> 💡 **Exam tip**: Whenever a question mentions "backup Region ASG min/max = 0," think **warm standby / pilot light**, and always pair it with a **Failover routing policy** (never latency-based or weighted routing).

## QUESTION 9

**Question**: A critical application runs on a single EC2 instance, using a single-node Redis cluster (ElastiCache) and an Amazon RDS for MariaDB instance. Which three actions provide automatic recovery from failure while minimizing downtime? (Choose three.)

**Choices (summarized)**
- A. Distribute traffic across multiple EC2 instances using an ELB, and configure an Auto Scaling group with a minimum capacity of 2.
- B. Configure the EC2 instances in Unlimited mode (relates to burstable-instance CPU credits, unrelated to high availability).
- C. Create a read replica in the same Availability Zone, and manually promote it on failure.
- D. **Modify the DB instance for a Multi-AZ deployment.**
- E. Create an ElastiCache Redis replication group, and configure the cluster to use an Auto Scaling group with 2 instances (an invalid pairing — Auto Scaling groups aren't attached to ElastiCache).
- F. **Create an ElastiCache Redis replication group and enable Multi-AZ on the cluster.**

**Correct Answer: A, D, F**

**Explanation**
This is the standard three-tier automatic-recovery pattern. ① Compute tier: an ELB plus an Auto Scaling group with a minimum capacity of 2+ for Multi-AZ redundancy (A). ② Database tier: RDS **Multi-AZ** deployment enables automatic failover (D). ③ Cache tier: a single-node Redis cluster has no automatic failover, so you must **create a replication group and enable Multi-AZ**, which automatically promotes a replica if the primary node fails (F).

**Why the other choices are wrong**
- B: Unlimited mode prevents burstable (T-family) instances from running out of CPU credits — unrelated to high availability or automatic recovery.
- C: A same-AZ replica offers no protection against an AZ-level failure, and "manual promotion" fails the "automatic" recovery requirement.
- E: ElastiCache replication group high availability comes from enabling Multi-AZ — attaching an EC2-style Auto Scaling group to a cache cluster isn't a real concept (cache nodes aren't managed by an ASG).

> 💡 **Exam tip**: A **single-node ElastiCache cluster has no automatic failover.** Whenever high availability is required, the answer must pair "create a replication group" with "enable Multi-AZ."

## QUESTION 10

**Question**: An e-commerce app runs on EC2 behind an ALB with RDS, and CloudFront caches static content with the ALB as its origin. After a recent deployment, the ALB intermittently returns 502 errors due to a malformed header (reloading the page fixes it). While the root cause is being fixed, the company wants to show visitors a custom error page instead of the default ALB error page, with minimal operational overhead. (Choose two.)

**Choices**
- A. Create an S3 bucket to host a static custom error page.
- B. Create a CloudWatch alarm on the ALB's failed-health-check metric that invokes a Lambda function to dynamically change the ALB's forwarding rules.
- C. Add a health check and failover target to the Route 53 record, redirecting DNS itself elsewhere.
- D. Create a CloudWatch alarm on the `ELB.InternalError` metric that invokes a Lambda function to modify the ALB's forwarding rules.
- E. Use CloudFront's **custom error response** feature to serve the S3-hosted page from A for specific error codes like 502.

**Correct Answer: A, E**

**Explanation**
CloudFront has a built-in **custom error response** feature that lets you serve a specific static page whenever the origin (the ALB) returns a given error code (502/503/504, etc.). This delivers a custom error page immediately with minimal operational overhead — no Lambda or alarms required. First, an **S3 bucket** (A) is needed to host the error page.

**Why the other choices are wrong**
- B, D: Using a CloudWatch alarm to trigger a Lambda function that dynamically rewrites ALB routing rules is far more complex to build and operate, failing the "minimal operational overhead" requirement.
- C: A Route 53 DNS failover redirects traffic entirely elsewhere — a bigger change than needed, and DNS TTL propagation delay makes it a poor fit for simply "show a custom error page temporarily."

> 💡 **Exam tip**: When origin errors (4XX/5XX) need to trigger a custom page, reach for CloudFront's built-in **Custom Error Response** feature first, before considering extra infrastructure like Lambda or alarms.

## QUESTION 11

**Question**: A company manages many AWS accounts through AWS Organizations. A dedicated infrastructure account owns the VPC and network. Individual accounts should not be able to manage the network themselves, but they must still be able to create AWS resources within the shared subnets. Which two actions are needed? (Choose two.)

**Choices**
- A. Create a transit gateway in the infrastructure account.
- B. **Enable resource sharing in the AWS Organizations management account.**
- C. Create a VPC in each account within the organization, matching the CIDR range and subnets of the infrastructure account's VPC, and peer each account's VPC with it.
- D. **In the infrastructure account's AWS Resource Access Manager (RAM), create a resource share**, selecting the specific Organizations OU to share the network with, and select each subnet to associate with the share.
- E. Share prefix lists instead of subnets via the RAM resource share.

**Correct Answer: B, D**

**Explanation**
This describes the classic **VPC Sharing** pattern. First, resource sharing must be enabled organization-wide from the management account (B). Then, the infrastructure account that owns the network shares **specific subnets** via AWS RAM to the target OU (D). Participating accounts can then create resources like EC2 or RDS inside the shared subnets, but cannot modify the underlying VPC, subnets, or routing.

**Why the other choices are wrong**
- A: A transit gateway is for routing and connectivity between multiple VPCs — a different goal from "centrally manage the network while other accounts only deploy resources into it" (which is what VPC Sharing addresses).
- C: Creating a separate VPC per account and peering them directly contradicts the requirement that "individual accounts cannot manage their own network."
- E: Sharing prefix lists is for referencing IP ranges in security group or route table rules — it doesn't let another account actually deploy resources into a shared subnet.

> 💡 **Exam tip**: Whenever you see "manage the network centrally, other accounts only deploy resources," think **VPC (subnet) Sharing via AWS RAM**. A Transit Gateway solves a different problem — connecting multiple VPCs/on-premises networks together.

## QUESTION 12

**Question**: A company wants to call a third-party SaaS application that runs inside a VPC on AWS via API calls, using private connectivity that never traverses the internet. The company's own VPC resources must not be reachable from outside, and permissions must follow least privilege. Which solution fits?

**Choices**
- A. Create an **AWS PrivateLink interface VPC endpoint**, connect it to the endpoint service provided by the SaaS application, and restrict access to the endpoint with a security group.
- B. Create an AWS Site-to-Site VPN connection between the company's VPC and the SaaS application, and restrict access through the VPN tunnel with network ACLs.
- C. Create a VPC peering connection between the company's VPC and the SaaS provider's VPC, updating route tables as needed.
- D. Have the company create its own **PrivateLink endpoint service**, and ask the SaaS provider to create an interface VPC endpoint pointing to it.

**Correct Answer: A**

**Explanation**
The company is the **consumer** of the SaaS service, so the consumer side should create an **interface VPC endpoint** connecting to the endpoint service that the SaaS provider exposes. PrivateLink provides one-directional, private connectivity that never traverses the internet, and it doesn't expose the company's VPC to the provider's network — satisfying the "resources must not be reachable from outside" requirement as well.

**Why the other choices are wrong**
- B: A VPN plus network ACLs isn't the standard pattern for this kind of SaaS integration, carries more operational overhead, and doesn't fit least-privilege design as cleanly as PrivateLink.
- C: VPC peering creates bidirectional network connectivity, which could make the company's VPC reachable from the other side too — violating the "not reachable from outside" requirement.
- D: The roles are reversed. Creating an endpoint service is what you do to expose *your own* service to others; since this scenario is about consuming *someone else's* service, the company should be the one creating the interface endpoint, not the endpoint service.

> 💡 **Exam tip**: **PrivateLink is one-directional and minimizes exposure.** If you're consuming a SaaS service, create an interface endpoint (A); if you're exposing your own service to others, create an endpoint service. Mixing up these roles flips the correct answer. VPC peering/Transit Gateway create bidirectional connectivity, making them a poor fit for this kind of minimal-exposure requirement.

## QUESTION 13

**Question**: On-premises servers and EC2 instances both need to be patched, and administrators need a single report showing patch status across all servers and instances. What action should be taken?

**Choices**
- A. Use **AWS Systems Manager** to manage patching for both on-premises servers and EC2 instances, and use Systems Manager to generate a patch compliance report.
- B. Use AWS OpsWorks to manage patching, and integrate OpsWorks with Amazon QuickSight to generate the report.
- C. Use an Amazon EventBridge rule to schedule AWS Systems Manager patch remediation, and use Amazon Inspector to generate the compliance report.
- D. Use AWS OpsWorks to manage patching, and use AWS X-Ray to publish patch status for the compliance report.

**Correct Answer: A**

**Explanation**
AWS Systems Manager can register on-premises servers as "managed instances" via a **hybrid activation**, letting you manage patches for both EC2 and on-premises with a single tool. Combining Patch Manager with the Compliance dashboard produces a unified report.

**Why the other choices are wrong**
- B: Pairing OpsWorks with QuickSight for a "patch compliance report" isn't a standard AWS pattern and adds unnecessary complexity.
- C: Scheduling patches via EventBridge is fine, but pairing it with Amazon Inspector (a vulnerability-scanning service) for compliance reporting is a mismatch — a common distractor pattern that bolts together unrelated services.
- D: AWS X-Ray is a distributed application tracing service and has nothing to do with patch status reporting.

> 💡 **Exam tip**: Remember that Systems Manager can include **on-premises servers as managed instances via hybrid activation**, and that patch compliance reporting is solved with **Patch Manager + Compliance**. Whenever X-Ray or Inspector show up in a choice like this, it's usually a mismatched-service distractor.

## QUESTION 14

**Question**: EC2 instances behind an ALB with an Auto Scaling group copy log files to S3 every 15 minutes. Some instances terminate before their next scheduled copy, causing log loss. How can you guarantee logs are copied to S3 exactly at termination time?

**Choices**
- A. Store the log-copy script without an SSM document. Use an ASG lifecycle hook plus an EventBridge rule to detect the `TERMINATING` transition → a Lambda function sends **ABANDON** to pause termination → runs the script directly → manually terminates the instance via the AWS SDK.
- B. Create an **SSM document (Run Command)** with the log-copy script. Use an ASG lifecycle hook plus an EventBridge rule to detect the `TERMINATING` transition → a Lambda function calls SSM `SendCommand` to run the document → once complete, sends **CONTINUE** to let termination proceed normally.
- C. Shorten the log upload interval to 5 minutes, and use EventBridge to detect the EC2 instance's actual termination and run the script.
- D. Create an SSM document. The lifecycle hook publishes a message to SNS → the SNS notification triggers `SendCommand` → once complete, sends **ABANDON**.

**Correct Answer: B**

**Explanation**
The AWS-recommended pattern pauses termination with an Auto Scaling **lifecycle hook (`EC2_INSTANCE_TERMINATING`)**, has an EventBridge rule detect this and invoke a Lambda function, which uses **SSM SendCommand** to run the log-copy document — and once the task finishes, calls **`CompleteLifecycleAction` with CONTINUE** to let the normal termination process proceed.

**Why the other choices are wrong**
- A: Sending ABANDON and then manually terminating via the AWS SDK is more complex and adds more moving parts than the standard lifecycle-hook completion flow.
- C: An EventBridge rule detecting "the EC2 instance has already terminated" fires too late — by then the instance is gone and its logs can't be copied. You need the lifecycle hook's `TERMINATING` (pre-termination pause) stage instead.
- D: If the custom action completed successfully, you should send `CONTINUE` to let the standard termination process proceed; `ABANDON` is generally the signal for a failure/skip scenario, not a fit for this flow.

> 💡 **Exam tip**: Memorize the "run cleanup logic right before an EC2 instance terminates" pattern as: **Lifecycle Hook (TERMINATING) → EventBridge → Lambda → SSM SendCommand → CompleteLifecycleAction(CONTINUE)**. ABANDON signals failure/skip, not successful completion.

## QUESTION 15

**Question**: DNS records live in a Route 53 private hosted zone in Account A, while the application and database run in Account B. A new VPC in Account B hosts a two-tier app, and a CNAME (`db.example.com`) for the RDS endpoint was created in Account A's hosted zone — but EC2 instances in the new VPC can't resolve `db.example.com`. The record set itself was created correctly. How should this be fixed? (Choose two.)

**Choices**
- A. Deploy the database directly on a separate EC2 instance in the new VPC and create a new record pointing to its private IP.
- B. SSH into the application-tier EC2 instances and manually add the RDS endpoint's IP address to `/etc/resolv.conf`.
- C. **In Account A, create a VPC association authorization** for Account B's new VPC.
- D. Create a new private hosted zone for the same domain in Account B, and configure "Route 53 replication" between accounts.
- E. **Associate Account B's new VPC with Account A's hosted zone**, then delete the authorization in Account A once done.

**Correct Answer: C, E**

**Explanation**
A Route 53 private hosted zone **can be associated with a VPC in a different account**, but it requires a two-step cross-account authorization flow. ① The account that owns the hosted zone (Account A) creates a **VPC association authorization** naming the target account and VPC (C). ② Account B then uses that authorization to **associate** its VPC with Account A's hosted zone (E). The root cause here is that the new VPC was never associated with the hosted zone in the first place — the record itself is fine.

**Why the other choices are wrong**
- A: Moving the database directly onto an EC2 instance is an unnecessary redesign unrelated to the actual root cause (missing VPC association).
- B: Manually editing resolv.conf on every instance doesn't scale and doesn't fix the underlying architectural gap.
- D: There is no such feature as "Route 53 replication," and maintaining a duplicate hosted zone for the same domain per account creates ongoing maintenance burden.

> 💡 **Exam tip**: To associate a private hosted zone with a **VPC in a different account**, you always need the two-step flow: "① owning account creates an authorization → ② target account performs the association." If the record looks correct but still won't resolve, suspect a missing association.

## QUESTION 16

**Question**: A blog site runs on EC2 behind an ALB with an Auto Scaling group, storing all content on Amazon EFS. After adding video posting, traffic grew 10x, and users report buffering and timeouts at peak hours. What is the most cost-effective and scalable fix?

**Choices**
- A. Reconfigure EFS to the **Max I/O** performance mode.
- B. Switch the site to use instance store volumes, copying content to the volume at startup and backing it up to S3 at shutdown.
- C. **Create a CloudFront distribution with an S3 origin, and migrate videos from EFS to Amazon S3.**
- D. Create a CloudFront distribution for all site content, pointing its origin at the ALB.

**Correct Answer: C**

**Explanation**
The root cause is continuing to serve large video files through the EC2/EFS combination. Large, frequently-requested static content like video is best moved to an **Amazon S3 + CloudFront** setup — the standard, most cost-effective, and highly scalable pattern for this kind of content.

**Why the other choices are wrong**
- A: Max I/O improves EFS's throughput mode, but every request still has to pass through EC2/EFS, so it doesn't resolve the underlying bottleneck.
- B: Instance store is ephemeral, risking data loss on instance stop/termination, and the manual sync logic is fragile and complex.
- D: If CloudFront's origin is the ALB (EC2), EC2 still has to serve the video on every cache miss — not as fundamental a fix as moving videos entirely to S3 (option C).

> 💡 **Exam tip**: If large static content (like video) served through EC2/EFS is causing a traffic bottleneck, the right pattern isn't "tune EFS" — it's **moving the content itself to S3 + CloudFront**.

## QUESTION 17

**Question**: A global company has a single 1 Gbps Direct Connect connection to a single Region (one private VIF, connected to one VPC). They want to add a redundant DX connection in the same Region, while also being able to extend the same connection pair to future Regions as the company expands. Which solution fits?

**Choices**
- A. Provision a **Direct Connect Gateway**, delete the existing private VIF from the existing connection, create a second DX connection, create a new private VIF on each connection, and connect both private VIFs to the Direct Connect Gateway.
- B. Connect a Direct Connect Gateway directly to the single VPC, keep the existing private VIF, create a second DX connection, and connect only the new VIF to that same VPC.
- C. Create a **public VIF** on the second connection and connect it to the single VPC.
- D. Provision a **Transit Gateway**, and connect both private VIFs to the Transit Gateway.

**Correct Answer: A**

**Explanation**
A **Direct Connect Gateway (DXGW)** is the AWS building block that lets a single (or redundant pair of) DX connection reach VPCs across **multiple Regions**. Whenever a scenario explicitly requires "expanding to future Regions," DXGW is the pattern to reach for.

**Why the other choices are wrong**
- B: Describing a DXGW as connecting "directly" to a VPC is inaccurate (it actually connects via a virtual private gateway or Transit Gateway), and leaving the existing VIF outside the DXGW while only routing the new VIF through it doesn't achieve "extend the same connection pair to multiple Regions."
- C: A public VIF is for accessing AWS public services like S3 or DynamoDB — connecting to private VPC resources requires a private VIF.
- D: A Transit Gateway is Region-scoped, so for a goal of "expand to multiple Regions," DXGW — which natively supports cross-Region connectivity — is the better fit.

> 💡 **Exam tip**: Whenever a scenario needs "one DX connection (pair) reaching VPCs across multiple Regions," think **Direct Connect Gateway**. Also remember the difference between public VIF (AWS public services) and private VIF (VPC resources).

## QUESTION 18

**Question**: A web app lets users upload short videos, which are stored on EBS and analyzed by third-party recognition software running on EC2 with an SQS worker fleet. The company wants to redesign the application to use AWS-managed services wherever possible, reducing operational overhead and eliminating the third-party software dependency.

**Choices**
- A. Run the web app on ECS containers and use spot instances in the ASG processing SQS; replace the custom software with **Amazon Rekognition** to classify videos.
- B. Store uploaded videos on **Amazon EFS**, keep the web app running on EC2, and process the SQS queue with a Lambda function that calls Amazon Rekognition.
- C. Host the web app on **Amazon S3**, store uploaded videos in **Amazon S3**, publish S3 event notifications to an SQS queue, and process the queue with a **Lambda** function that calls the Amazon Rekognition API to classify videos.
- D. Use AWS Elastic Beanstalk with an Auto Scaling web tier and a worker environment processing SQS, replacing the custom software with Rekognition.

**Correct Answer: C**

**Explanation**
The option that most fully achieves "reduce operational overhead using managed services wherever possible" is the fully serverless combination — with **no EC2/container management** for hosting, storage, event processing, or classification: **S3 (static hosting + storage) → S3 event notifications → SQS → Lambda → Amazon Rekognition**.

**Why the other choices are wrong**
- A: Still requires operating and managing ECS containers and a spot-instance ASG, retaining EC2/cluster management overhead.
- B: Videos are stored on EFS and the web app still runs on EC2, meaning more managed components than the fully serverless setup in C.
- D: Elastic Beanstalk still manages EC2 instances underneath, falling short of the "minimize server management" goal.

> 💡 **Exam tip**: For a media-processing pipeline where the requirement is "minimize operational overhead using managed services," look first at the fully serverless combo **S3 → S3 event notification → SQS → Lambda → Rekognition**. Any option that still has EC2/ECS/EKS/Elastic Beanstalk in the mix is usually a second-best choice.

## QUESTION 19

**Question**: A serverless application is built with CloudFront, API Gateway, and Lambda. The current deployment process generates a new Lambda version number and runs an AWS CLI script to update it; if the new version has a bug, another CLI script redeploys the previous working version to roll back. The company wants to reduce both the time it takes to deploy new versions of the application logic and the time it takes to detect and roll back errors. How can this be achieved?

**Choices**
- A. Create and deploy a nested AWS CloudFormation stack with a parent stack (CloudFront distribution and API Gateway) and a child stack containing the Lambda function. To change Lambda, create and deploy an AWS CloudFormation change set; on error, manually roll the change set back to the previous version.
- B. Use **AWS SAM with built-in AWS CodeDeploy** to deploy the new Lambda version, gradually shifting traffic to it (canary/linear), using pre-traffic and post-traffic test hooks to validate the code, and **automatically rolling back when a CloudWatch alarm fires**.
- C. Refactor the multiple AWS CLI scripts into a single script that deploys the new Lambda version; run a separate test script after deployment; manually roll back to the previous Lambda version if errors are detected.
- D. Create and deploy an AWS CloudFormation stack with a new API Gateway endpoint referencing the new Lambda version; manually switch the CloudFront origin to the new endpoint while monitoring for errors, and manually switch it back if problems are found.

**Correct Answer: B**

**Explanation**
**AWS SAM's built-in integration with AWS CodeDeploy** natively provides gradual (canary/linear) traffic shifting for Lambda deployments, pre/post-traffic test hooks to validate code, and **automatic rollback** when a CloudWatch alarm fires. This is the AWS standard pattern for automating away both deployment time and error-response time.

**Why the other choices are wrong**
- A, D: Manually creating, monitoring, and rolling back CloudFormation change sets or API Gateway endpoint switches still requires human intervention, falling short of the goal to reduce time meaningfully.
- C: Consolidating multiple scripts into one doesn't change the fact that it's fundamentally still a manual, script-driven process — far less automated than B.

> 💡 **Exam tip**: Whenever a question asks for automated Lambda deployment plus automatic rollback, reach for **AWS SAM + CodeDeploy** (canary/linear deployment, pre/post-traffic hooks, CloudWatch-alarm-triggered automatic rollback) as the first candidate.

## QUESTION 20

**Question**: A company needs to store a large volume of archived documents and make them available to employees over the corporate intranet, connecting via a Client VPN attached to the VPC. The data must not be publicly accessible. The documents are copies of originals archived elsewhere physically. Request volume is low, and availability and retrieval speed are not concerns. Which solution meets these requirements at the lowest cost?

**Choices**
- A. Create an S3 bucket, configure **S3 One Zone-Infrequent Access (S3 One Zone-IA)** as the default storage class, configure the bucket for website hosting, and create an **S3 interface endpoint**, restricting access to only that endpoint.
- B. Launch an EC2 instance running a web server, attach an Amazon EFS file system storing archived data on the EFS One Zone-IA storage class, and restrict access to the private network only via the instance's security group.
- C. Launch an EC2 instance running a web server, attach an Amazon EBS volume (Cold HDD, sc1) to store archived data, restricting access to the private network only.
- D. Create an S3 bucket, configure **S3 Glacier Deep Archive** as the default storage class, configure the bucket for website hosting, and create an S3 interface endpoint restricting access to only that endpoint.

**Correct Answer: A**

**Explanation**
Since the requirement states employees must be able to **use** the documents, the storage class needs to support immediate (millisecond-scale) retrieval. **S3 One Zone-IA** stores data in a single AZ to cut costs while still offering the same instant retrieval as S3 Standard, matching this requirement. Pairing it with an **S3 interface VPC endpoint** to restrict access to just that VPC also satisfies the "must not be publicly accessible" requirement.

**Why the other choices are wrong**
- B, C: Both require running an EC2 instance continuously, incurring ongoing compute costs that exceed a pure S3-based static hosting setup (option A).
- D: **S3 Glacier Deep Archive requires an asynchronous restore process that can take several hours (up to 48 hours)** before an object becomes retrievable — that conflicts with the requirement that documents must be "usable" on demand. Low request volume and "must be retrievable immediately" are two separate requirements, and it's important not to conflate them.

> 💡 **Exam tip**: **S3 Glacier storage classes offer the lowest storage cost but require time-delayed retrieval.** If a question implies "infrequently accessed, but still needs to be usable/retrievable right away," the answer is **S3 Standard-IA / One Zone-IA**, not Glacier. Glacier is only correct when the scenario explicitly states long-term archival with no need for immediate retrieval.
