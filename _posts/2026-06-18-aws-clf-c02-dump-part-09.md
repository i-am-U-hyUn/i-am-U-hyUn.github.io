## Q1. IAM 최소 권한 원칙

AWS IAM 사용자에게 최소한의 권한을 부여한다는 것은 무엇을 의미합니까?

- A. 단일 사용자에게만 권한을 부여합니다.
- B. AWS IAM 정책만 사용하여 권한을 부여합니다.
- C. 신뢰할 수 있는 사용자에게 관리자 액세스 정책 권한을 부여하는 것입니다.
- D. 주어진 작업을 수행하는 데 필요한 권한만 부여하는 것입니다.

**정답: D**

✅ **D. 주어진 작업을 수행하는 데 필요한 권한만 부여하는 것입니다.**: 최소 권한 원칙(Principle of Least Privilege)이란 사용자가 자신의 업무를 수행하는 데 꼭 필요한 최소한의 권한만 부여하는 보안 원칙입니다. 이를 통해 불필요한 권한 남용이나 보안 사고를 예방할 수 있습니다.

❌ **A. 단일 사용자에게만 권한을 부여합니다.**: 최소 권한은 권한을 받는 사용자의 수가 아니라, 부여되는 권한의 범위를 최소화하는 것을 의미합니다.

❌ **B. AWS IAM 정책만 사용하여 권한을 부여합니다.**: 권한 부여 메커니즘(정책 유형)에 대한 설명이며, 최소 권한의 정의와는 관련이 없습니다.

❌ **C. 신뢰할 수 있는 사용자에게 관리자 액세스 정책 권한을 부여하는 것입니다.**: 관리자 권한은 최소 권한 원칙에 정반대되는 개념으로, 필요 이상의 권한을 부여하는 것입니다.

💡 **시험 꿀팁**: 최소 권한 원칙(Least Privilege) = 필요한 권한만(Only what is needed) / IAM에서 기본값은 "모든 권한 거부"이며, 명시적으로 허용해야만 사용 가능합니다. "최소", "필요한 것만", "제한"이라는 키워드가 보이면 최소 권한 원칙을 떠올리세요.

## Q2. 프라이빗 하이브리드 연결 서비스

책임자는 하이브리드 클라우드 아키텍처를 조사하는 업무를 담당했습니다. 이 회사는 현재 공용 인터넷을 통해 AWS에 접속하고 있다. 프라이빗 하이브리드 연결을 용이하게 하는 서비스는 무엇입니까?

- A. Amazon Virtual Private Cloud(Amazon VPC) NAT 게이트웨이
- B. AWS Direct Connect
- C. Amazon S3(Simple Storage Service) 전송 가속화
- D. AWS 웹 애플리케이션 방화벽(AWS WAF)

**정답: B**

✅ **B. AWS Direct Connect**: AWS Direct Connect는 온프레미스 데이터 센터와 AWS 간에 전용 프라이빗 네트워크 연결을 제공하는 서비스입니다. 공용 인터넷을 우회하여 일관된 네트워크 성능과 높은 보안성을 제공하며, 하이브리드 클라우드 아키텍처의 핵심 구성 요소입니다.

❌ **A. Amazon VPC NAT 게이트웨이**: NAT 게이트웨이는 프라이빗 서브넷의 EC2 인스턴스가 인터넷으로 나가는 트래픽을 허용하는 서비스이며, 온프레미스와의 프라이빗 연결과는 관련이 없습니다.

❌ **C. Amazon S3 전송 가속화**: S3 Transfer Acceleration은 CloudFront 엣지 로케이션을 활용하여 S3 업로드/다운로드 속도를 높이는 기능이며, 하이브리드 연결 서비스가 아닙니다.

❌ **D. AWS WAF**: WAF(Web Application Firewall)는 웹 애플리케이션을 SQL 인젝션, XSS 등의 공격으로부터 보호하는 보안 서비스이며, 네트워크 연결 서비스가 아닙니다.

💡 **시험 꿀팁**: 온프레미스 ↔ AWS 프라이빗 연결 = **AWS Direct Connect** / 인터넷 기반 암호화 연결 = **AWS VPN** / "전용선", "프라이빗", "하이브리드"라는 키워드가 나오면 Direct Connect를 선택하세요.

## Q3. 단일 장애점 제거 설계 원칙

회사의 웹 애플리케이션은 현재 기본 구성요소에 대한 의존도가 매우 높기 때문에 하나의 구성요소가 실패하면 전체 웹 응용프로그램이 실패합니다. 어떤 AWS Cloud 설계 원칙을 적용하면 현재 설계 문제를 해결할 수 있습니까?

- A. 탄력성 구현, 수요 변화에 따라 애플리케이션을 스케일업 또는 스케일다운할 수 있습니다.
- B. 여러 EC2 인스턴스를 병렬로 실행하여 성능을 향상시킵니다.
- C. 구성 요소를 분리하고 다른 구성 요소가 고장 났을 때 개별 구성 요소가 작동할 수 있도록 함으로써 구성 요소를 분리하는 데 집중합니다.
- D. 시스템 내결함성을 높이기 위해 EC2 컴퓨팅 리소스를 두 배로 늘립니다.

**정답: C**

✅ **C. 구성 요소를 분리하고 다른 구성 요소가 고장 났을 때 개별 구성 요소가 작동할 수 있도록 함으로써 구성 요소를 분리하는 데 집중합니다.**: 느슨한 결합(Loose Coupling) 원칙을 적용하면 하나의 구성 요소 장애가 전체 시스템 장애로 전파되지 않습니다. SQS와 같은 메시지 큐나 마이크로서비스 아키텍처가 대표적인 구현 방법입니다.

❌ **A. 탄력성 구현**: 탄력성은 수요에 따른 용량 조정에 관한 것으로, 단일 장애점 문제를 해결하지는 않습니다.

❌ **B. 여러 EC2 인스턴스를 병렬로 실행**: 단순히 인스턴스를 늘리는 것은 성능 향상에는 도움되지만, 구성 요소 간 강한 의존성(단단한 결합) 문제를 해결하지 못합니다.

❌ **D. EC2 컴퓨팅 리소스를 두 배로 늘립니다.**: 리소스를 늘리는 것은 용량 문제를 해결하지만, 구성 요소 간의 의존성 문제(단일 장애점)를 해결하지 못합니다.

💡 **시험 꿀팁**: "하나가 실패하면 전체가 실패" = 단단한 결합(Tight Coupling) 문제 → 해결책은 **느슨한 결합(Loose Coupling)** / AWS에서는 SQS(메시지 큐), SNS, API Gateway 등을 활용하여 구성 요소를 분리합니다.

## Q4. AWS 계정 로그온 보안 강화 (두 개 선택)

고객이 AWS 계정 로그온에 대한 보안을 강화하려면 어떻게 해야 합니까? (두 개를 선택합니다.)

- A. AWS 인증서 관리자 구성
- B. MFA(Multi-Factor Authentication) 사용
- C. 액세스 관리를 위해 Amazon Cognito 사용
- D. 강력한 암호 정책 구성
- E. AWS 조직 지원

**정답: B, D**

✅ **B. MFA(Multi-Factor Authentication) 사용**: MFA는 암호 외에 추가 인증 수단(OTP, 하드웨어 토큰 등)을 요구하여 계정 탈취 위험을 크게 줄이는 핵심 보안 기능입니다. AWS 루트 계정과 IAM 사용자 계정 모두에 적용을 강력히 권장합니다.

✅ **D. 강력한 암호 정책 구성**: IAM 암호 정책을 통해 최소 길이, 복잡성 요구사항, 만료 기간 등을 설정하면 무차별 대입 공격(brute force)이나 사전 공격으로부터 계정을 보호할 수 있습니다.

❌ **A. AWS 인증서 관리자 구성**: AWS Certificate Manager(ACM)는 SSL/TLS 인증서를 관리하는 서비스로, 계정 로그온 보안 강화와는 관련이 없습니다.

❌ **C. Amazon Cognito 사용**: Cognito는 애플리케이션의 사용자 인증 및 액세스 제어를 위한 서비스이며, AWS 계정 자체의 로그온 보안 강화와는 다른 용도입니다.

❌ **E. AWS 조직 지원**: AWS Organizations는 여러 AWS 계정을 중앙에서 관리하는 서비스이며, 단일 계정의 로그온 보안 강화와는 직접적인 관련이 없습니다.

💡 **시험 꿀팁**: 계정 보안 강화 = **MFA + 강력한 암호 정책** / 루트 계정에는 반드시 MFA 활성화, 일상 작업에는 루트 계정 사용 금지가 AWS 모범 사례입니다. "로그인 보안", "계정 보호"가 키워드면 MFA를 먼저 떠올리세요.

## Q5. 다중 계정 중앙 관리 서비스

여러 계정에서 AWS 액세스를 중앙에서 관리하는 데 사용되는 AWS 서비스는 무엇입니까?

- A. AWS 서비스 카탈로그
- B. AWS 구성
- C. AWS Trusted Advisor
- D. AWS 조직

**정답: D**

✅ **D. AWS 조직(AWS Organizations)**: AWS Organizations는 여러 AWS 계정을 중앙에서 통합 관리할 수 있는 서비스입니다. 서비스 제어 정책(SCP)을 통해 계정별 권한을 제어하고, 통합 결제를 통해 비용을 한 번에 관리할 수 있습니다.

❌ **A. AWS 서비스 카탈로그**: AWS Service Catalog는 조직 내에서 승인된 IT 서비스 목록을 만들고 관리하는 서비스로, 다중 계정 액세스 중앙 관리와는 다릅니다.

❌ **B. AWS 구성(AWS Config)**: AWS Config는 리소스의 구성 변경 사항을 추적하고 규정 준수를 평가하는 서비스이며, 다중 계정 액세스 관리 서비스가 아닙니다.

❌ **C. AWS Trusted Advisor**: Trusted Advisor는 비용 최적화, 보안, 성능, 내결함성 등에 대한 권장 사항을 제공하는 서비스이며, 다중 계정 관리 서비스가 아닙니다.

💡 **시험 꿀팁**: 다중 계정 중앙 관리 = **AWS Organizations** / 핵심 기능: OU(조직 단위), SCP(서비스 제어 정책), 통합 결제(Consolidated Billing) / "여러 계정", "중앙 관리", "계정 그룹"이 키워드면 Organizations를 선택하세요.

## Q6. 비용 임계값 경고 알림 서비스

계정이 특정 금액에 근접할 때 고객이 경고 알림을 설정하는 데 사용할 수 있는 AWS 서비스는 무엇입니까?

- A. AWS 비용 및 사용량 보고서
- B. AWS 예산
- C. AWS 비용 탐색기
- D. AWS Trusted Advisor

**정답: B**

✅ **B. AWS 예산(AWS Budgets)**: AWS Budgets를 사용하면 실제 비용이나 예측 비용이 사용자가 설정한 임계값에 도달했을 때 이메일 또는 SNS 알림을 자동으로 받을 수 있습니다. 비용 예산, 사용량 예산, 예약 예산 등 다양한 유형의 예산을 설정할 수 있습니다.

❌ **A. AWS 비용 및 사용량 보고서**: Cost and Usage Report는 상세한 비용 및 사용량 데이터를 S3에 저장하는 리포팅 서비스이며, 알림 기능을 직접 제공하지 않습니다.

❌ **C. AWS 비용 탐색기**: Cost Explorer는 과거 비용 및 사용량 데이터를 시각화하고 분석하는 도구이며, 임계값 기반 알림 기능은 없습니다.

❌ **D. AWS Trusted Advisor**: Trusted Advisor는 비용 최적화 권장 사항을 제공하지만, 특정 금액 도달 시 경고 알림을 설정하는 기능은 제공하지 않습니다.

💡 **시험 꿀팁**: 비용 알림/경고 = **AWS Budgets** / 비용 분석/시각화 = **Cost Explorer** / 상세 비용 데이터 = **Cost and Usage Report** / "알림", "경고", "임계값"이 키워드면 AWS Budgets를 선택하세요.

## Q7. AWS Artifact 제공 항목

사용자가 AWS 아티팩트에서 액세스할 수 있는 항목은 무엇입니까?

- A. AWS 보안 및 컴플라이언스 문서
- B. 모든 AWS 리소스에 대한 구성 관리 세부 정보 다운로드
- C. AWS 서비스를 위한 교육 자료
- D. AWS 클라우드에 구축된 애플리케이션에 대한 보안 평가

**정답: A**

✅ **A. AWS 보안 및 컴플라이언스 문서**: AWS Artifact는 AWS의 보안 및 규정 준수 보고서(SOC, PCI, ISO 등)와 규정 준수 관련 계약을 온디맨드로 다운로드할 수 있는 셀프 서비스 포털입니다. 감사, 규제 대응, 규정 준수 증명에 활용됩니다.

❌ **B. 모든 AWS 리소스에 대한 구성 관리 세부 정보 다운로드**: 리소스 구성 관리는 AWS Config가 담당하는 영역입니다.

❌ **C. AWS 서비스를 위한 교육 자료**: 교육 자료는 AWS Training and Certification 또는 AWS Documentation에서 제공합니다.

❌ **D. AWS 클라우드에 구축된 애플리케이션에 대한 보안 평가**: 애플리케이션 보안 평가는 Amazon Inspector 또는 AWS Security Hub에서 제공합니다.

💡 **시험 꿀팁**: AWS Artifact = **규정 준수 보고서(Compliance Reports) + 계약서** 다운로드 포털 / SOC 1/2/3, PCI DSS, ISO 27001 등의 감사 보고서를 제공 / "감사", "컴플라이언스 문서", "규정 준수 증명"이 키워드면 AWS Artifact를 선택하세요.

## Q8. Well-Architected Framework 신뢰성 원칙

다음 중 신뢰성과 관련된 AWS의 잘 설계된 프레임워크 설계 원칙은 무엇입니까?

- A. 단일 가용성 영역에 구축
- B. 장애로부터 복구하는 능력
- C. 비용 최적화를 위한 설계
- D. 코드로 작업 수행

**정답: B**

✅ **B. 장애로부터 복구하는 능력**: AWS Well-Architected Framework의 신뢰성(Reliability) 원칙은 시스템이 장애를 자동으로 감지하고 복구할 수 있는 능력을 갖추는 것을 핵심으로 합니다. 여기에는 자동 복구, 수평 확장, 장애 격리 등이 포함됩니다.

❌ **A. 단일 가용성 영역에 구축**: 신뢰성 원칙은 오히려 여러 가용 영역(Multi-AZ)에 분산 배포하여 가용성을 높이는 것을 권장합니다. 단일 AZ는 신뢰성에 반하는 설계입니다.

❌ **C. 비용 최적화를 위한 설계**: 비용 최적화는 Well-Architected Framework의 6개 기둥 중 하나이지만, 신뢰성이 아닌 비용 최적화(Cost Optimization) 기둥에 해당합니다.

❌ **D. 코드로 작업 수행**: 이는 운영 우수성(Operational Excellence) 기둥의 원칙으로, Infrastructure as Code(IaC) 실천과 관련된 내용입니다.

💡 **시험 꿀팁**: AWS Well-Architected Framework 6개 기둥 = **운영 우수성(Operational Excellence), 보안(Security), 신뢰성(Reliability), 성능 효율성(Performance Efficiency), 비용 최적화(Cost Optimization), 지속 가능성(Sustainability)** / 신뢰성 = 장애 복구 + Multi-AZ + 자동 확장

## Q9. 임시 스토리지 유형

어떤 유형의 AWS 스토리지가 사용 후 삭제되고 인스턴스가 중지되거나 종료될 때 삭제됩니까?

- A. Amazon EBS
- B. Amazon EC2 인스턴스 저장소
- C. Amazon EFS
- D. 아마존 S3

**정답: B**

✅ **B. Amazon EC2 인스턴스 저장소(Instance Store)**: EC2 인스턴스 저장소는 호스트 서버에 물리적으로 연결된 임시 스토리지입니다. 인스턴스가 중지(stop), 종료(terminate), 또는 하드웨어 장애가 발생하면 데이터가 영구적으로 삭제됩니다. 임시 캐시나 버퍼 용도로 적합합니다.

❌ **A. Amazon EBS**: EBS(Elastic Block Store)는 인스턴스와 독립적으로 존재하는 영구 블록 스토리지입니다. 인스턴스가 중지되어도 데이터가 유지되며, 다른 인스턴스에 재연결할 수 있습니다.

❌ **C. Amazon EFS**: EFS(Elastic File System)는 여러 EC2 인스턴스가 동시에 접근할 수 있는 영구적인 관리형 파일 시스템입니다. 인스턴스 종료와 무관하게 데이터가 유지됩니다.

❌ **D. Amazon S3**: S3는 객체 스토리지 서비스로 EC2 인스턴스와 독립적이며, 매우 높은 내구성(99.999999999%, 11 9s)을 가진 영구 스토리지입니다.

💡 **시험 꿀팁**: 임시 스토리지(인스턴스 종료 시 삭제) = **EC2 인스턴스 저장소(Instance Store)** / 영구 블록 스토리지 = **EBS** / 관리형 파일 시스템 = **EFS** / 객체 스토리지(내구성 11 9s) = **S3** / "임시", "종료 시 삭제", "휘발성"이 키워드면 Instance Store를 선택하세요.

## Q10. AWS Cloud 사용의 이점

기존 사내 솔루션보다 AWS Cloud를 사용하면 어떤 이점이 있습니까?

- A. 사용자는 미래의 용량 요구에 대해 추측할 필요가 없습니다.
- B. 사용자는 기존 하드웨어 계약을 구매에 활용할 수 있습니다.
- C. 사용자는 트래픽에 상관없이 비용을 해결할 수 있습니다.
- D. 사용자는 AWS 보고서를 사용하여 감사를 피할 수 있습니다.

**정답: A**

✅ **A. 사용자는 미래의 용량 요구에 대해 추측할 필요가 없습니다.**: 클라우드의 핵심 이점 중 하나는 탄력성(Elasticity)입니다. 온프레미스 환경과 달리 AWS는 실제 수요에 맞게 용량을 즉시 확장하거나 축소할 수 있어 용량 과잉 구매나 부족 문제를 해결합니다.

❌ **B. 사용자는 기존 하드웨어 계약을 구매에 활용할 수 있습니다.**: AWS는 클라우드 기반 서비스로, 기존 하드웨어 계약과는 별개로 운영됩니다. 이는 AWS 사용의 이점이 아닙니다.

❌ **C. 사용자는 트래픽에 상관없이 비용을 해결할 수 있습니다.**: AWS는 사용한 만큼만 비용을 지불하는 종량제 모델이며, 트래픽에 따라 비용이 변동됩니다. 트래픽과 무관한 고정 비용은 클라우드의 특징이 아닙니다.

❌ **D. 사용자는 AWS 보고서를 사용하여 감사를 피할 수 있습니다.**: AWS는 감사를 피하는 수단을 제공하지 않으며, 오히려 AWS Artifact 등을 통해 규정 준수 감사를 지원합니다.

💡 **시험 꿀팁**: AWS 클라우드의 6대 이점: **가변 비용(종량제), 규모의 경제, 용량 추측 불필요, 속도 및 민첩성, 데이터 센터 유지비 절감, 글로벌 확장** / "추측 불필요", "필요에 따라 확장/축소"가 키워드면 탄력성/용량 관련 이점을 선택하세요.

## Q11. AWS 관리형 컴퓨팅 서비스

다음 중 AWS 관리 컴퓨팅 서비스는 무엇입니까?

- A. 아마존 SWF
- B. 아마존 EC2
- C. AWS 람다
- D. 아마존 오로라

**정답: C**

✅ **C. AWS 람다(AWS Lambda)**: AWS Lambda는 서버를 프로비저닝하거나 관리할 필요 없이 코드를 실행할 수 있는 완전 관리형 서버리스 컴퓨팅 서비스입니다. 인프라 관리를 AWS가 완전히 담당하므로 개발자는 코드 작성에만 집중할 수 있습니다.

❌ **A. 아마존 SWF(Simple Workflow Service)**: SWF는 분산 애플리케이션 구성 요소 간의 작업을 조율하는 워크플로우 서비스이며, 컴퓨팅 서비스가 아닙니다.

❌ **B. 아마존 EC2**: EC2는 가상 서버를 제공하지만, 사용자가 OS 패치, 보안 설정, 스케일링 등을 직접 관리해야 하는 IaaS(Infrastructure as a Service) 서비스입니다.

❌ **D. 아마존 오로라**: Amazon Aurora는 관계형 데이터베이스 서비스(RDS의 일종)로, 컴퓨팅이 아닌 데이터베이스 서비스입니다.

💡 **시험 꿀팁**: 완전 관리형(Fully Managed) 컴퓨팅 = **AWS Lambda(서버리스)** / EC2는 사용자 관리 필요(IaaS) / "서버리스", "관리형", "인프라 관리 불필요"가 키워드면 Lambda를 선택하세요. Lambda는 코드 실행 시간(ms 단위)만큼만 비용을 냅니다.

## Q12. 클라우드 애플리케이션 아키텍처 원칙

다음 중 클라우드 애플리케이션을 설계할 때 중요한 아키텍처 원칙은 무엇입니까?

- A. 데이터 및 백업을 동일한 영역에 저장합니다.
- B. 단단히 결합된 시스템 구성요소를 설계합니다.
- C. 멀티 스레딩을 피한다.
- D. 고장 설계

**정답: D**

✅ **D. 고장 설계(Design for Failure)**: "고장을 위한 설계"는 AWS 아키텍처의 핵심 원칙으로, 언제든 장애가 발생할 수 있다고 가정하고 이를 견딜 수 있도록 시스템을 설계하는 것입니다. 자동 복구, 이중화, 다중 AZ 배포 등이 이 원칙의 구현 방법입니다.

❌ **A. 데이터 및 백업을 동일한 영역에 저장합니다.**: 데이터와 백업을 동일 위치에 저장하면 해당 지역 장애 시 모두 손실될 수 있습니다. 올바른 방법은 다른 리전이나 AZ에 백업을 저장하는 것입니다.

❌ **B. 단단히 결합된 시스템 구성요소를 설계합니다.**: 단단한 결합(Tight Coupling)은 클라우드 설계 안티 패턴입니다. 느슨한 결합(Loose Coupling)을 통해 구성 요소 독립성을 높여야 합니다.

❌ **C. 멀티 스레딩을 피한다.**: 멀티 스레딩을 피하는 것은 클라우드 아키텍처 원칙과 무관하며, 오히려 병렬 처리를 통해 성능을 향상시키는 것이 권장됩니다.

💡 **시험 꿀팁**: 클라우드 아키텍처 핵심 원칙: **고장 설계(Design for Failure), 느슨한 결합(Loose Coupling), 탄력성(Elasticity), 자동화(Automation)** / "장애 대비", "복원력", "고가용성" 키워드가 보이면 "고장 설계" 원칙을 떠올리세요.

## Q14. 연간 1회 단기 워크로드 최적 가격 모델

24시간 동안 1년에 한 번 실행되는 무중단 워크로드에 가장 비용 효율적인 Amazon EC2 가격 모델은 무엇입니까?

- A. 주문형 인스턴스
- B. 예약된 인스턴스
- C. 스폿 인스턴스
- D. 전용 인스턴스

**정답: A**

✅ **A. 주문형 인스턴스(On-Demand Instance)**: 연간 단 한 번, 24시간만 실행되는 워크로드는 사용한 시간만큼만 비용을 지불하는 온디맨드 인스턴스가 가장 적합합니다. 장기 약정이나 선불 비용 없이 필요할 때만 실행하고 종료하면 됩니다.

❌ **B. 예약된 인스턴스(Reserved Instance)**: 예약 인스턴스는 1년 또는 3년 약정으로 지속적으로 사용할 때 최대 72% 할인을 받는 모델입니다. 연간 24시간만 사용하는 경우에는 약정 비용이 오히려 더 비쌀 수 있습니다.

❌ **D. 전용 인스턴스(Dedicated Instance)**: 전용 인스턴스는 물리적으로 격리된 하드웨어에서 실행되어 규정 준수 요건을 충족하지만, 비용이 매우 높아 연간 1회 24시간 워크로드에는 과도합니다.

💡 **시험 꿀팁**: EC2 가격 모델 선택 기준: **단기/불규칙 = On-Demand, 장기 안정적 = Reserved(최대 72% 할인), 중단 허용 저비용 = Spot(최대 90% 할인), 규정 준수 = Dedicated** / "1년에 한 번", "단기", "예측 불가"면 On-Demand를 선택하세요.

## Q15. 자동 스토리지 확장 MySQL 호환 데이터베이스 (두 개 선택)

다음 중 필요에 따라 자동으로 스토리지를 확장하는 MySQL 호환 데이터베이스를 실행할 수 있는 서비스는 무엇입니까? (두 개 선택)

- A. Amazon Elastic Compute 클라우드(Amazon EC2)
- B. MySQL용 Amazon RDS(Amazon Relational Database Service)
- C. 아마존 광선(Amazon Lightsail 또는 기타)
- D. 아마존 오로라

**정답: B, D**

✅ **B. MySQL용 Amazon RDS**: Amazon RDS for MySQL은 AWS의 완전 관리형 관계형 데이터베이스 서비스로 MySQL을 지원합니다. RDS Storage Auto Scaling 기능을 통해 스토리지가 자동으로 확장되며, 패치, 백업 등을 AWS가 관리합니다.

✅ **D. 아마존 오로라(Amazon Aurora)**: Aurora는 MySQL 및 PostgreSQL과 완전히 호환되는 AWS 자체 관계형 데이터베이스 엔진입니다. 스토리지가 10GB 단위로 최대 128TB까지 자동 확장되며, MySQL 대비 최대 5배 높은 성능을 제공합니다.

❌ **A. Amazon EC2**: EC2에 MySQL을 직접 설치하여 운영할 수는 있지만, 스토리지 자동 확장을 위해서는 별도의 EBS 볼륨 확장 작업이 필요하며 완전 관리형 서비스가 아닙니다.

❌ **C. 아마존 광선**: 이 문제에서 제시된 보기는 실제 AWS 데이터베이스 관련 서비스가 아니며, MySQL 호환 자동 확장 DB 서비스에 해당하지 않습니다.

💡 **시험 꿀팁**: MySQL 호환 DB 서비스 = **RDS for MySQL** 또는 **Amazon Aurora(MySQL 호환)** / Aurora는 MySQL보다 5배, PostgreSQL보다 3배 빠르며 스토리지 자동 확장(최대 128TB) / "MySQL 호환", "관리형", "자동 확장"이 키워드면 RDS 또는 Aurora를 선택하세요.

## Q16. 두 VPC 연결 기능

사용자가 두 개의 VPC를 함께 연결할 수 있는 Amazon VPC(Virtual Private Cloud) 기능은 무엇입니까?

- A. Amazon VPC 엔드포인트
- B. Amazon Elastic Compute Cloud(Amazon EC2) ClassicLink
- C. Amazon VPC 피어링
- D. AWS Direct Connect

**정답: C**

✅ **C. Amazon VPC 피어링(VPC Peering)**: VPC 피어링은 두 VPC 간에 프라이빗 IPv4 또는 IPv6 트래픽을 라우팅할 수 있도록 네트워크 연결을 설정하는 기능입니다. 같은 계정, 다른 계정, 다른 리전의 VPC 간에도 피어링 연결이 가능합니다.

❌ **A. Amazon VPC 엔드포인트**: VPC 엔드포인트는 인터넷을 통하지 않고 VPC에서 AWS 서비스(S3, DynamoDB 등)에 프라이빗으로 연결하기 위한 기능이며, VPC 간 연결 기능이 아닙니다.

❌ **B. Amazon EC2 ClassicLink**: ClassicLink는 EC2-Classic 인스턴스를 VPC에 연결하는 레거시 기능으로, 현재는 더 이상 권장되지 않으며 VPC 간 연결 기능이 아닙니다.

❌ **D. AWS Direct Connect**: Direct Connect는 온프레미스 데이터 센터와 AWS 간의 전용 프라이빗 연결을 제공하는 서비스이며, VPC 간 연결 기능이 아닙니다.

💡 **시험 꿀팁**: VPC ↔ VPC 연결 = **VPC 피어링(VPC Peering)** / VPC ↔ AWS 서비스 연결(인터넷 우회) = **VPC 엔드포인트** / VPC ↔ 온프레미스 = **Direct Connect 또는 VPN** / "두 VPC", "VPC 간"이 키워드면 VPC Peering을 선택하세요.

## Q17. 소프트웨어 버전 제어 서비스

소프트웨어 버전 제어의 주요 목적은 무엇입니까? (해당하는 AWS 서비스를 선택하시오.)

- A. Amazon CodeStar
- B. AWS 명령줄 인터페이스(AWS CLI)
- C. Amazon Cognito
- D. AWS CodeCommit

**정답: D**

✅ **D. AWS CodeCommit**: AWS CodeCommit은 Git 기반의 완전 관리형 소스 코드 버전 관리 서비스입니다. 팀이 코드를 안전하게 저장하고, 변경 이력을 추적하며, 협업할 수 있도록 지원합니다. GitHub, GitLab과 유사한 AWS 자체 코드 저장소입니다.

❌ **A. Amazon CodeStar**: CodeStar는 소프트웨어 개발 프로젝트를 빠르게 설정하고 전체 CI/CD 파이프라인을 관리하는 서비스로, 버전 제어 자체보다는 프로젝트 관리 도구에 가깝습니다.

❌ **B. AWS CLI**: AWS CLI는 명령줄 인터페이스를 통해 AWS 서비스를 관리하는 도구이며, 소스 코드 버전 관리 서비스가 아닙니다.

❌ **C. Amazon Cognito**: Cognito는 사용자 인증 및 액세스 제어를 위한 서비스로, 소프트웨어 버전 제어와 전혀 관련이 없습니다.

💡 **시험 꿀팁**: AWS 개발자 도구 정리: **CodeCommit(코드 저장소/버전관리), CodeBuild(빌드), CodeDeploy(배포), CodePipeline(CI/CD 파이프라인), CodeStar(프로젝트 관리)** / "버전 관리", "소스 코드 저장소", "Git"이 키워드면 CodeCommit을 선택하세요.

## Q18. 온프레미스와 AWS 비용 비교 도구

한 회사가 AWS로 애플리케이션을 이전하는 것을 고려하고 있다. 이 회사는 사내 워크로드를 실행하는 비용을 AWS 플랫폼에서 동일한 워크로드를 실행하는 비용과 비교하고자 합니다. 이 비교를 수행하는 데 사용할 수 있는 도구는 무엇입니까?

- A. AWS 가격 계산기
- B. AWS 총소유비용(TCO) 계산기
- C. AWS 청구 및 비용 관리 콘솔
- D. 비용 탐색기

**정답: B**

✅ **B. AWS 총소유비용(TCO) 계산기**: TCO(Total Cost of Ownership) 계산기는 온프레미스 인프라의 총 소유 비용과 AWS 클라우드에서 동일 워크로드를 운영하는 비용을 비교 분석하는 도구입니다. 하드웨어, 소프트웨어, 인력, 시설 비용 등을 포함하여 클라우드 전환의 경제적 이점을 수치로 보여줍니다.

❌ **A. AWS 가격 계산기**: AWS Pricing Calculator는 AWS 서비스의 예상 비용을 산출하는 도구이지만, 온프레미스 비용과의 비교 기능은 제공하지 않습니다.

❌ **C. AWS 청구 및 비용 관리 콘솔**: 이미 사용 중인 AWS 서비스의 실제 청구 내역을 확인하는 도구로, 마이그레이션 전 비용 비교 용도로는 적합하지 않습니다.

❌ **D. 비용 탐색기(Cost Explorer)**: Cost Explorer는 실제 AWS 사용량과 비용 데이터를 시각화하고 분석하는 도구로, 온프레미스와의 비교 기능은 없습니다.

💡 **시험 꿀팁**: 온프레미스 vs AWS 비용 비교 = **TCO 계산기** / AWS 서비스 예상 비용 산출 = **AWS Pricing Calculator** / 실제 사용 비용 분석 = **Cost Explorer** / "사내 vs 클라우드 비교", "마이그레이션 비용 분석"이 키워드면 TCO 계산기를 선택하세요.

## Q19. 엑사바이트 규모 데이터 마이그레이션 서비스

엑사바이트 규모의 데이터셋을 AWS로 마이그레이션하거나 전송할 수 있는 안전하고 빠르고 경제적인 방법을 제공하는 AWS 서비스는 무엇입니까?

- A. AWS 일괄 처리
- B. AWS 스노우볼
- C. AWS 마이그레이션 허브
- D. AWS Snowmobile

**정답: D**

✅ **D. AWS Snowmobile**: AWS Snowmobile은 최대 100PB(페타바이트) 용량의 데이터를 전송할 수 있는 대형 트럭 형태의 데이터 이전 서비스입니다. 엑사바이트(1EB = 1,000PB) 규모의 데이터를 이전할 때는 여러 대의 Snowmobile을 사용합니다. 물리적 운송을 통해 인터넷보다 훨씬 빠르고 경제적으로 대규모 데이터를 이전할 수 있습니다.

❌ **A. AWS 일괄 처리(AWS Batch)**: AWS Batch는 배치 컴퓨팅 워크로드를 실행하는 서비스로, 데이터 마이그레이션 서비스가 아닙니다.

❌ **B. AWS 스노우볼(AWS Snowball)**: Snowball은 80TB(Snowball Edge는 최대 210TB) 용량의 데이터 이전 장치로, 페타바이트 규모까지 지원하지만 엑사바이트 규모에는 Snowmobile이 더 적합합니다.

❌ **C. AWS 마이그레이션 허브**: AWS Migration Hub는 마이그레이션 프로젝트의 진행 상황을 추적하는 관리 도구이며, 실제 데이터 전송 서비스가 아닙니다.

💡 **시험 꿀팁**: AWS Snow 패밀리 용량 비교: **Snowcone(최대 14TB) < Snowball Edge(최대 210TB) < Snowmobile(최대 100PB)** / 엑사바이트(EB) 규모 = **Snowmobile(트럭)** / "엑사바이트", "초대용량", "물리적 운송"이 키워드면 Snowmobile을 선택하세요.

## Q20. AWS 가격 모델 설명 (두 개 선택)

다음 중 AWS 가격 모델을 가장 잘 설명한 항목은 무엇입니까? (두 개를 선택합니다.)

- A. 기간 고정
- B. 종량제
- C. 코로케이션
- D. 계획된
- E. 변동 비용

**정답: B, E**

✅ **B. 종량제(Pay-as-you-go)**: AWS의 핵심 요금 철학으로, 사용한 서비스와 리소스에 대해서만 비용을 지불합니다. 선불 비용 없이 실제 사용량에 따라 청구되므로 비용 예측과 최적화가 가능합니다.

✅ **E. 변동 비용(Variable Cost)**: AWS는 고정 비용(데이터 센터, 서버 구매 등) 대신 실제 사용량에 따라 변동하는 운영 비용(OpEx) 모델을 사용합니다. 사용량이 증가하면 비용도 증가하고, 감소하면 비용도 줄어듭니다.

❌ **A. 기간 고정**: AWS는 기간 약정이 필수가 아닌 유연한 요금 체계를 가집니다. 예약 인스턴스는 약정이 있지만 AWS의 기본 요금 모델은 기간 고정이 아닙니다.

❌ **C. 코로케이션**: 코로케이션은 사용자의 하드웨어를 데이터 센터 시설에 임대하여 운영하는 전통적 IT 모델로, AWS 클라우드 모델과 다릅니다.

❌ **D. 계획된**: 사전에 계획된 고정 비용 모델은 온프레미스 환경의 특징이며, AWS의 종량제/변동 비용 모델과 반대됩니다.

💡 **시험 꿀팁**: AWS 요금의 3대 원칙: **종량제(Pay-as-you-go), 예약 시 절약(Save when you reserve), 많이 쓸수록 할인(Pay less when using more)** / 클라우드 = 변동 비용(OpEx) vs 온프레미스 = 고정 비용(CapEx) / "사용한 만큼", "변동", "종량제"가 키워드입니다.
