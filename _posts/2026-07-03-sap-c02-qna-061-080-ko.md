## QUESTION 61

**문제**: 금융 회사가 매일 밤 SFTP로 재무 데이터를 받아 S3 데이터 레이크로 옮깁니다. 현재 퍼블릭 서브넷 EC2에서 자체 SFTP 서버를 운영하며 cron으로 파일을 이동합니다. 안정성과 확장성을 개선하려면?

**보기**
- A. EC2를 ASG로 옮기고 ALB 뒤에 배치
- B. **SFTP 서버를 AWS Transfer Family(AWS Transfer for SFTP)로 마이그레이션**
- C. Storage Gateway 파일 게이트웨이로 마이그레이션
- D. NLB 뒤에 EC2 배치

**정답: B**

**해설**
**AWS Transfer Family**는 완전관리형 SFTP 서비스로 S3와 네이티브로 통합되며, 자체 EC2 서버 관리가 필요 없어 안정성·확장성을 동시에 확보할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: **ALB는 L7(HTTP/HTTPS) 전용**이라 SFTP 프로토콜을 처리할 수 없습니다.
- C: 파일 게이트웨이는 NFS/SMB 프로토콜용이지 SFTP용이 아닙니다.
- D: NLB로 SFTP TCP 트래픽을 전달하는 것은 기술적으로 가능하지만, 여전히 자체 SFTP 서버 플릿을 패치·관리해야 해 "관리형으로 전환"이라는 목표를 달성하지 못합니다.

> 💡 **시험 꿀팁**: S3와 직접 통합되는 완전관리형 SFTP가 필요하면 **AWS Transfer Family**를 떠올리세요. 자체 EC2 기반 SFTP 서버를 계속 운영·패치하는 방식은 대부분 오답입니다.

## QUESTION 62

**문제**: 온프레미스 VMware에서 EC2로 앱을 마이그레이션하며, 소프트웨어와 구성 설정을 **그대로 보존**해야 합니다.

**보기**
- A. DataSync로 FSx for Windows에 VMware 데이터 저장소 복제 + VM Import/Export
- B. **vSphere 클라이언트로 OVF 이미지 내보내기 → S3에 저장 → VM Import용 IAM 역할 생성 → AWS CLI로 EC2 가져오기 명령 실행**
- C. Storage Gateway 파일 서비스로 CIFS 공유 내보내기 → 백업 복사본에서 AMI 생성
- D. Systems Manager 하이브리드 활성화 + AWS Backup 스냅샷으로 AMI 생성

**정답: B**

**해설**
**VM Import/Export**는 기존 VM 이미지(OS, 설치된 소프트웨어, 구성 포함)를 그대로 AMI/EC2 인스턴스로 가져오는 AWS 전용 서비스입니다. OVF로 내보내 S3에 올리고 CLI로 가져오기 명령을 실행하는 것이 표준 절차입니다.

**왜 다른 보기는 오답인가**
- A: DataSync+FSx는 **파일 데이터** 복제용이지, OS/설정을 포함한 전체 VM 이미지를 옮기는 표준 절차가 아닙니다.
- C: 백업 복사본에서 AMI를 만드는 것은 실제 AMI 생성 방식이 아닙니다.
- D: Systems Manager 하이브리드 활성화는 온프레미스 서버 **관리(패치 등)**용이지 VM 디스크 이미지를 가져오는 기능이 아닙니다.

> 💡 **시험 꿀팁**: 온프레미스 VM(OS·소프트웨어·설정 포함)을 그대로 AWS로 가져오려면 **VM Import/Export**(OVF 내보내기 → S3 업로드 → import 명령)를 떠올리세요.

## QUESTION 63

**문제**: 비디오 처리 Lambda 앱(S3 다운로드 → 처리 → S3 저장 → DynamoDB 메타데이터 업데이트)이 이미지 크기 증가로 **시간 초과가 잦습니다**(제한 시간은 이미 최대치). 인프라 관리를 원치 않으면서 호출 실패를 막으려면? (2가지 선택)

**보기**
- A. **애플리케이션 코드를 담은 Docker 이미지를 빌드해 ECR에 게시**
- B. **Fargate 호환 ECS 작업 정의 생성, 새 이미지 사용하도록 구성, S3 신규 파일 도착 시 Lambda가 ECS 작업을 호출하도록 조정**
- C. Step Functions Parallel 상태로 Lambda 호출 + 프로비저닝된 동시성 증가
- D. EC2 호환 유형의 ECS 작업 정의 생성
- E. EFS에 이미지 저장 + RDS로 메타데이터 이전

**정답: A, B**

**해설**
**Lambda의 최대 실행 시간(15분)**에 걸리는 것이 근본 원인이므로, 실제 처리 작업은 시간 제한이 없는 **ECS Fargate**(서버 관리 불필요)로 옮기고, Lambda는 S3 이벤트를 받아 **ECS 작업을 실행시키는 얇은 트리거** 역할만 하도록 재설계합니다.

**왜 다른 보기는 오답인가**
- C: Step Functions로 감싸도 Lambda 자체의 15분 제한 문제는 그대로이고, 프로비저닝된 동시성은 콜드 스타트 문제이지 실행 시간 문제가 아닙니다.
- D: **EC2 호환 유형**은 인스턴스/클러스터를 직접 관리해야 해 "인프라 관리를 원치 않는다"는 요구 사항에 어긋납니다.
- E: 스토리지 구조 변경은 근본 원인(Lambda 시간 초과)과 무관합니다.

> 💡 **시험 꿀팁**: 작업이 **Lambda의 15분 실행 제한**을 지속적으로 초과한다면, 인프라 관리 없이 처리하려면 **ECS Fargate**로 실제 작업을 옮기고 Lambda는 트리거 역할만 하도록 재설계하세요.

## QUESTION 64

**문제**: Control Tower로 랜딩 존을 배포한 조직에서, Production OU의 **유휴·미암호화 RDS 인스턴스를 감지**하는 정책이 필요합니다.

**보기**
- A. Control Tower **필수(Mandatory) 가드레일**을 켜서 Production OU에 적용
- B. **Control Tower의 "강력 권장(Strongly Recommended)" 가드레일 목록에서 적절한 가드레일을 활성화**해 Production OU에 적용
- C. 새 AWS Config 규칙을 직접 만들어 적용
- D. 사용자 지정 SCP 생성해 적용

**정답: B**

**해설**
Control Tower의 가드레일은 **필수(Mandatory, 항상 켜짐, 선택 불가)**와 **강력 권장(Strongly Recommended, 명시적으로 켜야 함)**으로 나뉩니다. "유휴·미암호화 RDS 감지" 같은 구체적인 탐지 항목은 강력 권장 목록에 있으므로, 이를 찾아 활성화해야 합니다.

**왜 다른 보기는 오답인가**
- A: 필수 가드레일은 고정된 기본 세트라 이런 특정 항목을 "켜는" 개념이 아닙니다.
- C: Control Tower를 쓰는 상황에서 이미 제공되는 가드레일 카탈로그를 두고 직접 Config 규칙을 새로 만드는 것은 표준적이지 않습니다.
- D: SCP는 권한(작업) 자체를 차단하는 것이지, "유휴·미암호화 상태"같은 리소스 **상태를 감지**하는 기능이 없습니다.

> 💡 **시험 꿀팁**: Control Tower 가드레일은 **필수(고정)**와 **강력 권장(직접 활성화 필요)**로 나뉩니다. 구체적인 탐지 요구 사항은 먼저 **강력 권장** 목록에서 찾아보세요.

## QUESTION 65

**문제**: 스타트업이 프라이빗 서브넷 EC2 플릿에 SSH로 접속해 트러블슈팅합니다. 온프레미스에서 보안 그룹으로 직접 SSH가 허용되어 있습니다. **SSH 접근 보안을 강화**하고 **엔지니어가 실행한 명령의 감사(audit)**가 필요합니다.

**보기**
- A. EC2 Instance Connect 설치, 포트 22 인바운드 규칙 제거
- B. 포트 22를 엔지니어 IP로만 제한 + CloudWatch 에이전트로 OS 감사 로그 전송
- C. 포트 22를 엔지니어 IP로 제한 + AWS Config/Firewall Manager로 보안 그룹 변경 자동 교정
- D. **`AmazonSSMManagedInstanceCore` 정책의 IAM 역할을 모든 EC2에 연결, 포트 22 인바운드 규칙 완전 제거, 엔지니어는 Systems Manager Session Manager로 원격 접속**

**정답: D**

**해설**
**Systems Manager Session Manager**는 포트 22를 아예 열지 않고도(IAM 권한 기반) 접속할 수 있어 SSH 공격 표면을 완전히 제거하며, 세션 내 실행된 활동을 CloudWatch Logs/S3에 **네이티브로 감사 로그**로 남겨 두 요구 사항을 동시에 만족합니다.

**왜 다른 보기는 오답인가**
- A: EC2 Instance Connect는 임시 SSH 키를 푸시하는 방식으로 **여전히 포트 22가 열려 있어야** 하고, Session Manager만큼의 내장 명령 감사 기능도 없습니다.
- B, C: 포트 22를 IP로 제한해도 **여전히 열려 있는 포트**라 D보다 보안 수준이 낮고, C는 SG 변경 자체를 감시할 뿐 엔지니어의 **명령 실행 내역**은 감사하지 못합니다.

> 💡 **시험 꿀팁**: 포트 22를 완전히 닫으면서 명령 실행 감사까지 원한다면 **Systems Manager Session Manager**(`AmazonSSMManagedInstanceCore` 역할)가 정답입니다. EC2 Instance Connect나 IP 제한 보안 그룹은 포트가 여전히 열려 있다는 한계가 있습니다.

## QUESTION 66

**문제**: Organizations로 개발자가 AWS를 실험하게 하는 회사가, 비용이 많이 드는 서비스 실행을 막고 개발자에게 **고정 월 예산**을 제공하려 합니다. (3가지 선택)

**보기**
- A. 고정 월 사용 한도를 설정하는 SCP 생성
- B. **AWS Budgets로 계정 생성 시 각 개발자 계정에 고정 월 예산 생성**
- C. **고가 서비스에 대한 액세스를 거부하는 SCP 생성**해 개발자 계정에 적용
- D. 고가 서비스를 거부하는 IAM 정책 생성해 적용
- E. 예산 도달 시 "모든 서비스를 종료"하는 예산 알림 작업 생성
- F. **예산 도달 시 SNS 알림을 보내고 Lambda 함수를 호출해 서비스를 종료하는 예산 알림 작업 생성**

**정답: B, C, F**

**해설**
**SCP는 비용/사용량 한도를 직접 설정할 수 없습니다**(권한 허용/거부만 가능). 따라서 예산 자체는 **AWS Budgets**(B)로 설정하고, 고가 서비스 접근 자체를 막는 것은 **SCP**(C)로, 예산 초과 시 자동 조치는 **SNS+Lambda**(F, 커스텀 종료 로직 구현) 조합으로 해결합니다.

**왜 다른 보기는 오답인가**
- A: SCP로 "월 사용 한도"를 설정하는 기능 자체가 존재하지 않습니다(카테고리 오류).
- D: 이 경우 IAM 정책보다 조직 차원에서 중앙 강제되는 **SCP**가 개발자 계정 전체에 일관되게 적용하기에 더 적합합니다.
- E: "예산 도달 시 모든 서비스를 자동 종료"하는 것은 AWS Budgets Actions의 실제 동작 방식이 아닙니다(F처럼 SNS+Lambda로 커스텀 구현해야 함).

> 💡 **시험 꿀팁**: **SCP는 비용을 제한할 수 없고 오직 권한만 제한**합니다. 예산 한도는 **AWS Budgets**, 고가 서비스 차단은 **SCP**, 예산 초과 시 자동 대응은 **SNS+Lambda** 조합으로 역할을 나눠 기억하세요.

## QUESTION 67

**문제**: Source 계정의 앱(Lambda + Aurora 재고 데이터, 자동 백업 구성됨)을 같은 Organization 내 새 Target 계정으로 마이그레이션합니다. 중요 데이터라 **다운타임을 최소화**해야 합니다.

**보기**
- A. Lambda 배포 패키지 다운로드해 재생성, **Aurora 자동 백업 스냅샷을 공유**
- B. Lambda 배포 패키지 다운로드해 재생성, **AWS RAM으로 Aurora DB 클러스터를 공유하고 Target 계정에 클론 생성 권한 부여**
- C. RAM으로 Lambda 함수와 Aurora 클러스터를 모두 공유
- D. RAM으로 Lambda 함수 공유 + Aurora 자동 백업 스냅샷 공유

**정답: B**

**해설**
**AWS RAM으로 Aurora DB 클러스터를 공유**하면 대상 계정에서 거의 즉시(패스트 클로닝) **클론**을 생성할 수 있어, 스냅샷 복원보다 다운타임이 훨씬 짧습니다. **Lambda 함수는 RAM으로 공유할 수 없는 리소스**이므로, 배포 패키지를 받아 새 계정에서 재생성해야 합니다.

**왜 다른 보기는 오답인가**
- A: 자동 백업 스냅샷 공유·복원은 클로닝보다 시간이 오래 걸려 다운타임이 커집니다.
- C, D: **Lambda 함수는 AWS RAM으로 공유할 수 있는 리소스 유형이 아닙니다.** 이 전제 자체가 틀렸습니다.

> 💡 **시험 꿀팁**: **AWS RAM은 Aurora DB 클러스터 공유(→클론 생성)를 지원**하지만 **Lambda 함수는 지원하지 않습니다.** Lambda는 배포 패키지를 다운로드해 대상 계정에서 재생성해야 합니다.

## QUESTION 68

**문제**: EC2의 Python 스크립트가 10분마다 S3 파일을 처리(평균 5분/파일)합니다. CloudWatch를 보니 EC2가 약 40% 유휴 상태입니다. 가용성·확장성을 높이고 장기 관리 부담을 줄이면서 가장 비용 효율적으로 해결하려면?

**보기**
- A. **데이터 처리 스크립트를 Lambda로 마이그레이션하고, S3 이벤트 알림으로 Lambda를 호출**해 객체를 처리
- B. SQS 대기열 생성 + 최소 크기 1인 EC2 ASG로 폴링 처리
- C. 컨테이너 이미지로 마이그레이션 후 EC2에서 컨테이너 실행, S3 폴링
- D. ECS Fargate 컨테이너 + Fargate RunTask API를 호출하는 별도 Lambda + S3 이벤트로 그 Lambda 호출

**정답: A**

**해설**
파일당 처리 시간(평균 5분)이 **Lambda의 15분 제한 안에 충분히 들어오므로**, S3 이벤트가 발생할 때마다 Lambda를 직접 호출하는 것이 가장 단순하고 저렴하며 확장성 있는 재설계입니다. 유휴 시간에 비용이 발생하는 EC2/컨테이너 인프라가 전혀 필요 없습니다.

**왜 다른 보기는 오답인가**
- B: 최소 용량 1의 EC2 ASG는 여전히 EC2 인스턴스가 상시 실행되어 유휴 비용이 발생하고 관리 부담도 남습니다.

**DynamoDB**는 초당 대량의 소규모 레코드 쓰기, 밀리초 단위의 저지연 조회, 그리고 **네이티브 TTL 기능**(별도 정리 작업 없이 지정 기간 후 자동 삭제)을 모두 기본 제공해, 이 요구 사항에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: 수백만 개의 개별 파일을 S3에서 "색인 검색"하는 것은 자연스럽지 않고 비효율적입니다.
- C: 관계형 DB는 이 정도 규모의 초당 쓰기를 자연스럽게 확장하기 어렵고, 수동 cron 삭제는 DynamoDB TTL보다 운영 부담이 큽니다.
- D: 배치+커스텀 메타데이터 검색 방식은 불필요하게 복잡하며 DynamoDB만큼 간단한 저지연 조회를 제공하지 못합니다.

> 💡 **시험 꿀팁**: **대량의 소규모 레코드 + 저지연 조회 + 시간 기반 자동 삭제**가 필요하면 **DynamoDB + 네이티브 TTL**을 기본으로 떠올리세요.

## QUESTION 76

**문제**: 여러 리전에 걸쳐 운영하는 전자상거래 사이트가 항상 가동되어야 하며, MySQL용 RDS에 데이터를 저장합니다. 데이터베이스에 **최고 수준의 가용성**을 제공하는 솔루션은?

**보기**
- A. RDS 자동 백업 구성, 중단 시 백업을 독립 인스턴스로 승격
- B. RDS **"전역 테이블"**(존재하지 않는 RDS 기능) + 읽기 전용 복제본, Lambda로 리전 간 복제본 수동 복사
- C. RDS "전역 테이블" + 자동 백업, Lambda로 리전 간 복제본 수동 복사
- D. **RDS 읽기 전용 복제본(교차 리전) 구성, 중단 시 이를 독립 인스턴스로 승격해 트래픽 전환, 승격된 인스턴스를 원본으로 새 복제본 재생성**

**정답: D**

**해설**
표준적인 **교차 리전 읽기 전용 복제본 승격** 패턴입니다. 평소 지속적으로 복제되는 읽기 전용 복제본을 대기 상태로 유지하다가, 리전 장애 시 이를 **독립 인스턴스로 승격**하고 트래픽을 전환한 뒤, 향후 대비를 위해 **새 복제본을 다시 생성**합니다.

**왜 다른 보기는 오답인가**
- A: **자동 백업**(지속 복제가 아님)을 복구에 사용하는 것은 이미 계속 최신 상태를 유지하는 읽기 전용 복제본보다 복구 시점 목표(RPO)와 속도가 떨어집니다.
- B, C: **"전역 테이블(Global Tables)"은 DynamoDB의 기능이지 RDS/MySQL에는 존재하지 않습니다.** 이 전제 자체가 틀렸고, Lambda로 매번 복제본을 수동 복사하는 것도 비효율적입니다.

> 💡 **시험 꿀팁**: **"전역 테이블(Global Tables)"은 DynamoDB 전용 기능**이며 RDS에는 없습니다. RDS/Aurora의 표준 교차 리전 DR 패턴은 **지속적인 읽기 전용 복제본 → 장애 시 승격 → 재복제**입니다.

## QUESTION 77

**문제**: Example Corp의 온프레미스와 VPC A는 Site-to-Site VPN으로 연결되어 있습니다. 인수한 AnyCompany의 VPC B와 VPC A는 피어링되어 있습니다(IP 대역 겹치지 않음). 온프레미스에서 **VPC B로도 연결**하려 합니다. NACL·보안 그룹은 이미 적절히 설정되어 있습니다. 최소 운영 노력으로는?

**보기**
- A. **전송 게이트웨이를 생성**하고 **Site-to-Site VPN, VPC A, VPC B를 모두 연결**, 모든 네트워크의 전송 게이트웨이 라우팅 테이블에 서로에 대한 경로 추가
- B. 온프레미스-VPC B 간 **별도의 새 Site-to-Site VPN**을 만들어 전송 게이트웨이에 연결
- C. VPN·VPC 라우팅 테이블 업데이트 + 세 네트워크 모두 BGP 전파 구성 (전송 게이트웨이 없이)
- D. 가상 프라이빗 게이트웨이 정의를 두 VPC를 포함하도록 수정

**정답: A**

**해설**
**VPC 피어링은 전이적(transitive)이지 않습니다.** VPC A와 B가 피어링되어 있고 온프레미스가 VPN으로 VPC A에 연결되어 있어도, 온프레미스가 A를 "거쳐" B로 갈 수는 없습니다. 온프레미스 VPN과 VPC A, VPC B를 모두 **하나의 전송 게이트웨이**에 연결하고 라우팅을 구성하면 이 문제를 해결할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 이미 존재하는 VPN 연결을 두고 **완전히 새로운 별도 VPN**을 또 만드는 것은 A보다 훨씬 큰 운영 노력이 듭니다.
- C: **VPC 피어링의 비전이적 특성은 라우팅 테이블이나 BGP 설정만으로는 극복할 수 없습니다.** 전송 게이트웨이 같은 별도의 허브가 필요합니다.
- D: "가상 프라이빗 게이트웨이를 두 VPC에 걸쳐 정의"하는 것은 실제로 존재하지 않는 구성입니다(VPN 게이트웨이는 VPC 하나에만 연결됨).

> 💡 **시험 꿀팁**: **VPC 피어링은 전이적이지 않습니다**(A-B, B-C가 피어링되어도 A가 C에 직접 접근 불가). 온프레미스 VPN + 여러 VPC를 모두 연결하며 전이적 라우팅이 필요하면 **전송 게이트웨이**가 정답입니다.

## QUESTION 78

**문제**: 레거시 SMTP 서비스(TLS 미지원, TCP 포트 25)에 의존하는 중요 앱을 마이그레이션했습니다. 앱은 **SMTP만** 사용할 수 있습니다. Amazon SES로 전환하기로 하고 도메인 검증과 발송 한도 해제까지 완료했습니다. 앱이 SES로 메일을 보내도록 수정하려면?

**보기**
- A. **"TLS 래퍼"**로 SES에 연결 + `ses:SendEmail` 권한의 **IAM 역할**을 EC2에 연결
- B. **STARTTLS**로 SES에 연결, **SES SMTP 자격 증명**을 발급받아 인증
- C. **SES API**로 메일 전송 + IAM 역할을 서비스 역할로 사용
- D. **AWS SDK**로 메일 전송 + IAM 사용자의 액세스 키로 인증

**정답: B**

**해설**
앱이 **SMTP만** 사용할 수 있으므로 SES의 **SMTP 인터페이스**를 써야 하며, SES SMTP 엔드포인트는 **STARTTLS**(연결 초기에 평문으로 시작해 TLS로 업그레이드)를 사용합니다("TLS 래퍼", 즉 처음부터 암시적 TLS와는 다른 방식입니다). 인증에는 IAM 역할이 아니라 IAM 자격 증명에서 파생된 전용 **SES SMTP 자격 증명**(사용자명/비밀번호)이 필요합니다.

**왜 다른 보기는 오답인가**
- A: SES SMTP는 "TLS 래퍼(암시적 TLS)"가 아니라 **STARTTLS**를 사용합니다. 또한 SMTP 인증에는 API 호출용 IAM 역할이 아니라 SMTP 전용 자격 증명이 필요합니다.
- C, D: 앱이 API/SDK를 아예 사용할 수 없다는 제약 조건과 정면으로 모순됩니다.

> 💡 **시험 꿀팁**: **SMTP만 사용 가능한 레거시 앱**이 Amazon SES를 쓰려면 반드시 **SES의 SMTP 인터페이스(STARTTLS) + 전용 SES SMTP 자격 증명**을 사용해야 합니다. API/SDK나 IAM 역할 기반 인증은 애초에 API 호출이 불가능한 앱에는 적용할 수 없습니다.

## QUESTION 79

**문제**: 여러 회사를 인수해 각기 다른 방식으로 청구·보고하던 계정들을 하나의 Organizations 조직으로 통합했지만, 팀별로 의미 있는 비용 보고서를 만들기 어렵습니다. 재무팀은 **자체 관리 애플리케이션**을 통해 모든 회사의 비용을 보고할 솔루션이 필요합니다.

**보기**
- A. **조직의 CUR(비용 및 사용 보고서) 생성, 태그·비용 카테고리 정의, Athena에 테이블 생성, 그 테이블 기반 QuickSight 데이터 세트 생성해 재무팀과 공유**
- B. 조직의 CUR 생성 + Cost Explorer에서 "특수 템플릿" 생성
- C. AWS Price List Query API로 지출 정보를 받는 QuickSight 데이터 세트 생성
- D. Price List Query API로 지출 수집 + Cost Explorer 특수 템플릿

**정답: A**

**해설**
재무팀이 "자체 관리 애플리케이션"으로 유연하게 다루려면 원시 상세 데이터가 필요합니다. **CUR(원시 데이터) → Athena(SQL 쿼리 계층) → QuickSight(또는 자체 앱 연동)** 파이프라인이 여러 회사의 통합된 데이터를 원하는 방식으로 그룹화·쿼리할 수 있는 유연한 기반을 제공합니다.

**왜 다른 보기는 오답인가**
- B: Cost Explorer의 내장 템플릿은 CUR+Athena+QuickSight 조합만큼 유연하지 않아 "자체 관리 애플리케이션"이 요구하는 커스텀 그룹화에 한계가 있습니다.

> 💡 **시험 꿀팁**: **AWS Price List Query API는 요금표(가격) 정보이지, 실제 사용/청구 데이터가 아닙니다.** 여러 계정을 아우르는 커스텀 비용 보고에는 **CUR(태그·비용 카테고리 정의) → Athena → QuickSight/자체 앱** 파이프라인이 표준입니다.

## QUESTION 80

**문제**: IoT 플랫폼: 여러 위치의 센서가 ALB 뒤 EC2의 Node.js API 서버로 데이터를 보내고, 4TB 범용 SSD RDS MySQL에 저장합니다. 센서 수가 계속 크게 늘고 있으며 API 서버는 계속 과부하, RDS는 쓰기 지연이 높습니다. 비용 효율적으로 영구히 해결하고 향후 성장에도 대응하려면? (2가지 선택)

**보기**
- A. MySQL 범용 SSD를 6TB로 늘려 IOPS 개선
- B. RDS MySQL 대신 Aurora + 읽기 전용 복제본으로 재설계
- C. **Amazon Kinesis Data Streams + AWS Lambda로 원시 데이터 수집·처리**
- D. AWS X-Ray로 분석·디버깅 + API 서버 추가
- E. **RDS MySQL 대신 Amazon DynamoDB로 데이터베이스 계층 재설계**

**정답: C, E**

**해설**
지속적으로 급증하는 IoT 데이터가 API 서버 과부하와 DB 쓰기 지연을 동시에 일으키고 있으므로, ① **Kinesis Data Streams**로 수집과 처리를 분리해(버퍼링 후 Lambda로 비동기 처리) API 서버의 직접적인 부하를 줄이고, ② **DynamoDB**처럼 대규모 쓰기에 특화된 NoSQL로 데이터베이스 계층을 재설계하는 것이 근본적이고 확장 가능한 해법입니다.

**왜 다른 보기는 오답인가**
- A: 볼륨 크기를 늘리는 것은 일시적인 미봉책일 뿐, 센서 수가 크게 늘어나는 근본적인 확장 문제를 해결하지 못합니다.
- B: Aurora + 읽기 복제본은 **읽기** 확장에는 좋지만, 문제는 명시적으로 **쓰기** 지연이므로 근본 해법이 아닙니다.
- D: X-Ray는 트레이싱/디버깅 도구이고, API 서버를 늘리는 것은 기존의 결함 있는 동기식 구조 위에 서버만 더하는 미봉책이라 다운스트림 DB 병목은 그대로입니다.

> 💡 **시험 꿀팁**: 지속적으로 급증하는 IoT/텔레메트리 수집이 API 계층과 관계형 DB의 쓰기 용량을 동시에 압도한다면, **① Kinesis Data Streams+Lambda로 수집·처리 분리 + ② DynamoDB로 데이터베이스 계층 전환**이 표준적인 영구 해법입니다. 단순히 읽기 복제본을 추가하거나 서버만 늘리는 것은 쓰기 병목을 해결하지 못합니다.
