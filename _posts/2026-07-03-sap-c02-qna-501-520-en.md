## QUESTION 501

**Question**: A company runs a mission-critical application on an Aurora MySQL cluster in us-east-1, with a strict requirement to recover service from another Region within an RPO of under 1 second and an RTO of under 1 minute even during a full Regional outage. A standard cross-Region read replica's asynchronous replication lag can exceed several seconds, risking failure to meet this requirement. What's the solution?

**Choices**
- A. Create a standard Aurora MySQL cross-Region read replica and manually promote it during an outage (a standard cross-Region replica's asynchronous replication can lag several seconds or more, making it hard to reliably guarantee a sub-1-second RPO).
- B. **Use Amazon Aurora Global Database, which uses dedicated infrastructure for storage-level replication to keep cross-Region replication lag typically under 1 second, and promote a secondary Region to a writable primary within minutes during a Regional outage.**
- C. Set up an ongoing AWS DMS replication task to sync to a separate Aurora cluster in another Region (viable, but requires operating separate replication instances and isn't designed to guarantee lag as low and consistent as Aurora Global Database's storage-level replication).
- D. Maintain independent Aurora clusters per Region and implement application-level dual writes (application-level dual writes make guaranteeing transactional consistency across two clusters extremely difficult and excessively complex to implement/operate).

**Correct Answer: B**

**Explanation**
**Amazon Aurora Global Database** consists of one primary Region and up to 5 secondary Regions, using **dedicated infrastructure for storage-level replication** rather than standard logical replication, typically keeping cross-Region replication lag under 1 second. During a full Regional outage, you can promote a secondary Region to a writable primary within minutes (via managed planned failover or unplanned failover) — the standard cross-Region DR solution for mission-critical workloads with strict RPO/RTO requirements.

**Why the other choices are wrong**
- A: A standard cross-Region read replica's asynchronous lag can exceed several seconds, failing to reliably guarantee a sub-1-second RPO.
- C: DMS ongoing replication is viable but carries heavier operational burden and doesn't guarantee as low a lag as Aurora Global Database.
- D: Application-level dual writes are a high-risk approach where guaranteeing transactional consistency is extremely difficult.

> 💡 **Exam tip**: For an Aurora workload with strict cross-Region DR requirements of **sub-1-second RPO and minute-scale RTO**, **Aurora Global Database** is the standard answer.

## QUESTION 502

**Question**: A company's EC2 instances in a private subnet frequently access an S3 bucket, currently routing through a NAT gateway to reach S3 over the internet — incurring substantial NAT gateway data-processing cost. They want traffic to reach S3 entirely within the AWS network without traversing the internet, while also reducing NAT gateway cost. What's the solution?

**Choices**
- A. Replace the NAT gateway with a larger instance type (NAT gateway has no instance-type concept, and the cost structure based on throughput isn't resolved by swapping types).
- B. Assign public IPs to all private-subnet instances to access directly via the internet gateway (assigning public IPs increases security exposure and contradicts the original purpose of designing a private subnet).
- C. **Create a Gateway VPC Endpoint for S3 in the VPC, so traffic destined for S3 routes directly within the AWS network via the route table, bypassing the NAT gateway and internet entirely (reducing NAT data-processing cost at no additional charge).**
- D. Move the S3 bucket to a different Region in the same account (moving Region is unrelated to whether traffic traverses NAT or the cost structure, and doesn't address the question's core requirement).

**Correct Answer: C**

**Explanation**
A **Gateway VPC Endpoint for S3** adds a route to the VPC's route table targeting the S3 prefix list, letting instances in a private subnet **reach S3 directly via an internal AWS network path**, with no internet gateway or NAT gateway involved. The gateway endpoint itself has no hourly or data-processing charge, so shifting S3 traffic that previously went through NAT to the endpoint reduces NAT data-processing cost while also improving security.

**Why the other choices are wrong**
- A: NAT gateway has no instance-type concept and this doesn't address the cost structure.
- B: Assigning public IPs increases security risk and contradicts the private-subnet design goal.
- D: Moving Region is unrelated to the question's core (NAT traversal and cost).

> 💡 **Exam tip**: To reach S3 **directly within the AWS network with no NAT gateway cost** from a private subnet, a **Gateway VPC Endpoint** is the standard answer.

## QUESTION 503

**Question**: A company shares AWS accounts across multiple business units (BUs) and wants to internally charge back costs to each BU based on actual usage. Resources are already tagged with a cost allocation tag indicating the BU, but they want to flexibly group costs across multiple tag values and services by BU and receive regular reports. What's the solution?

**Choices**
- A. **Use AWS Cost Categories to define rules combining dimensions like cost allocation tags, accounts, and services, grouping costs by BU, and continuously view them via this category in Cost Explorer or budget reports.**
- B. Create a completely separate AWS account per BU to split billing itself (account separation is a valid long-term strategy, but requires excessive restructuring for the immediate need to group billing in an already tag-differentiated shared-account environment).
- C. Analyze CloudTrail logs to manually estimate cost by API-call principal (CloudTrail only records API call history, providing no actual cost data or BU-grouping capability).
- D. Prefix every resource name with the BU name and manually parse the bill (manual parsing doesn't scale and fails to leverage the existing cost-allocation-tag asset).

**Correct Answer: A**

**Explanation**
**AWS Cost Categories** lets you combine dimensions — cost allocation tags, linked accounts, services, billing line items — into rules that map cost and usage data to desired business units (e.g., BU, project, team). Once defined, this category can be used continuously as a grouping dimension in Cost Explorer, Budgets, and the Cost and Usage Report (CUR), letting you flexibly generate BU-level chargeback reports even in an already-tagged shared-account environment.

**Why the other choices are wrong**
- B: Full account separation is valid but excessive for this question's immediate need (flexible grouping leveraging existing tags).
- C: CloudTrail provides no cost data.
- D: Manual parsing doesn't scale and is inefficient.

> 💡 **Exam tip**: To combine dimensions like cost allocation tags into **business-unit cost grouping and ongoing chargeback reporting**, **AWS Cost Categories** is the standard answer.

## QUESTION 504

**Question**: A company runs 50 VPCs (spread across multiple accounts), and as inter-VPC communication needs grow, the number of VPC peering connections has grown exponentially, becoming very hard to manage (peering doesn't support transitive routing, requiring a full mesh). They also want to share their Direct Connect connection to an on-premises data center across all VPCs. How do you simplify the network architecture?

**Choices**
- A. Consolidate all VPCs into one giant VPC (consolidating VPCs owned by different teams/accounts into one undermines isolation requirements and requires a massive redesign — impractical).
- B. Minimize peering connections by keeping only VPC pairs that absolutely must communicate, routing the rest around at the application level (a workaround design only makes the architecture more complex and doesn't solve the underlying scalability problem).
- C. Force all inter-VPC communication through API Gateway (API Gateway is a managed gateway in front of HTTP APIs, not a tool for replacing network-level routing between VPCs).
- D. **Adopt AWS Transit Gateway as a hub, connecting all VPCs and the Direct Connect connection to it in a hub-and-spoke architecture, so inter-VPC peering no longer needs individual management and routing is centrally managed, with Direct Connect shared across all connected VPCs.**

**Correct Answer: D**

**Explanation**
**AWS Transit Gateway** provides a **hub-and-spoke architecture** connecting many VPCs and on-premises networks (Direct Connect, VPN) to one central hub. Each VPC only needs to connect to the Transit Gateway once, and inter-VPC communication is centrally managed via the Transit Gateway's route tables. This means you don't need to exponentially add individual peering connections as the number of VPCs grows, and combined with a Direct Connect Gateway, the on-premises connection can be shared across all connected VPCs — greatly reducing network complexity at scale.

**Why the other choices are wrong**
- A: Consolidating VPCs undermines isolation requirements and exceeds a realistic redesign scope.
- B: A workaround design doesn't solve the underlying scalability problem.
- C: API Gateway isn't a network-level tool for inter-VPC routing.

> 💡 **Exam tip**: To manage communication among many VPCs and share Direct Connect **simply, with no peering**, an **AWS Transit Gateway** hub-and-spoke design is the standard answer.

## QUESTION 505

**Question**: A company is building a workflow in Step Functions to process tens of thousands of IoT sensor events per second. Each workflow execution is short (completing within seconds — simple validation, transformation, DynamoDB write), long-term detailed execution history isn't needed, and cost efficiency is paramount. What Step Functions workflow type fits this high-volume, short-duration case?

**Choices**
- A. Use a Standard workflow (Standard workflows are billed per state transition and are designed to retain full execution history long-term, making them cost-inefficient for tens of thousands of short executions per second).
- B. **Use an Express workflow, billed based on the number of requests, execution duration, and memory usage, to run high-volume short event-processing workflows cost-efficiently (asynchronous Express supports up to 5 minutes).**
- C. Implement all logic sequentially in a single giant Lambda function instead of Step Functions (viable, but the question explicitly asks about a Step Functions-based workflow type, and this sacrifices visual workflow management and built-in retry/error-handling benefits).
- D. Use only a standard SQS queue and skip Step Functions entirely (SQS alone provides no orchestration capability to express multi-step conditional logic and state management).

**Correct Answer: B**

**Explanation**
**Step Functions Express workflows** are optimized for short (up to 5 minutes), high-volume, event-driven workflows, billed based on **number of requests, execution duration, and memory usage** rather than state transitions. For short processing occurring tens of thousands of times per second, like IoT event processing, this is far more cost-efficient than Standard workflows, and detailed execution history can optionally be logged to CloudWatch Logs — fitting workloads that don't need long-term retention.

**Why the other choices are wrong**
- A: Standard's state-transition-based billing and long-term history retention make it costly for high-volume short executions.
- C: A single-function implementation sacrifices Step Functions' orchestration/visibility benefits.
- D: SQS alone can't express conditional orchestration.

> 💡 **Exam tip**: For **high-volume, short-duration** event-processing workflows, a **Step Functions Express workflow** is the standard answer.

## QUESTION 506

**Question**: A company operates separate backup tools and policies individually across resources scattered across multiple AWS services — EBS volumes, RDS databases, DynamoDB tables, EFS file systems — making management cumbersome. They want to manage backup frequency and retention across services with a single central policy, and have certain backups automatically copied to another Region/account for disaster recovery. What's the solution?

**Choices**
- A. **Use AWS Backup to consolidate backup frequency and retention across services like EBS/RDS/DynamoDB/EFS into a single central backup plan, and use backup copy rules to automatically copy specific backups to a separate vault in another Region/account.**
- B. Keep each service's native backup feature (EBS snapshots, RDS automated backups, etc.) as-is, but automate cross-Region copying with a Lambda script calling each service's API individually (viable, but requires maintaining separate scripts per service, contradicting this question's desire for "a single central policy").
- C. Periodically manually export all data to a single S3 bucket for unified management (this abandons service-native backup/restore features like RDS point-in-time recovery, and carries heavy manual operational burden).
- D. Use AWS Config to record resource change history as a substitute for backup (Config is a tool for recording configuration-change history and doesn't provide actual data backup/restore capability).

**Correct Answer: A**

**Explanation**
**AWS Backup** is a service that manages backups across multiple AWS services — EBS, RDS, DynamoDB, EFS, S3, and more — under **a single centralized backup plan**. Backup frequency, retention, and lifecycle (e.g., transition to cold storage) can be applied uniformly regardless of service type, based on tags or resource selection criteria, and configuring **backup copy rules** automatically copies created backups to a backup vault in another Region or account, also fulfilling disaster-recovery requirements.

**Why the other choices are wrong**
- B: Maintaining per-service individual scripts contradicts the desire for centralized policy management.
- C: Manual S3 export abandons service-native recovery features and carries heavy operational burden.
- D: Config doesn't provide backup/restore capability.

> 💡 **Exam tip**: To manage backups **across multiple AWS services with a single central policy and automatically copy them to another Region/account**, **AWS Backup** (backup plan + copy rules) is the standard answer.

## QUESTION 507

**Question**: A company stores a large volume of documents accumulated over years in S3, and suspects some contain sensitive personal information (PII) like national ID numbers or credit card numbers, but doesn't know exactly which objects contain what kind of sensitive data. They want to automatically scan the large S3 dataset to detect and classify sensitive data. What's the solution?

**Choices**
- A. Download every object and scan directly with regex scripts (developing/operating a custom script for large-scale data is a heavy development burden, requiring building detection logic for various sensitive-data patterns like credit cards and national IDs from scratch).
- B. Review document content using Amazon Comprehend's sentiment analysis feature (sentiment analysis analyzes positive/negative tone in text and isn't for detecting/classifying sensitive personal information [PII]).
- C. Only analyze storage usage patterns with S3 Storage Lens (Storage Lens provides storage usage/cost-optimization metrics only, with no capability to detect sensitive data within object content).
- D. **Use Amazon Macie to scan data stored in S3, automatically detecting and classifying various types of sensitive data (PII) — national ID numbers, credit card numbers, etc. — via machine learning and pattern matching, and review results in a dashboard.**

**Correct Answer: D**

**Explanation**
**Amazon Macie** is a fully managed service that scans data stored in S3 using **machine learning and managed data identifiers** to automatically detect and classify various types of sensitive data — personally identifiable information (PII), credit card numbers, credentials, and more. Findings, along with severity, are viewable in a dashboard, letting you understand sensitive-data exposure risk across large S3 datasets without developing your own scanning logic.

**Why the other choices are wrong**
- A: Developing custom regex scripts is a heavy burden and reinvents functionality Macie already provides.
- B: Comprehend's sentiment analysis is unrelated to PII detection.
- C: Storage Lens is a usage-metrics tool with no content-based sensitive-data detection.

> 💡 **Exam tip**: To automatically **detect/classify sensitive data like PII** stored in S3, **Amazon Macie** is the standard answer.

## QUESTION 508

**Question**: A company serves a real-time game server (TCP/UDP-based, dynamic uncacheable traffic) to global users, wanting them to connect to the nearest Region with low latency, and wanting requests to quickly and automatically fail over to another healthy Region if one Region fails. They determined CloudFront, optimized for static/cacheable content, doesn't fit this requirement. What's the solution?

**Choices**
- A. Use only Route 53 latency-based routing (DNS-based routing can have slower failover than an anycast-based approach leveraging the AWS network itself, due to DNS TTL and client/resolver caching).
- B. Assign a separate public IP per Region and implement logic in the client app to pick the fastest Region itself (client-side implementation carries high development complexity and requires reimplementing failover logic per application).
- C. **Use AWS Global Accelerator, routing users via fixed anycast IP addresses through the AWS global network to the nearest healthy Regional endpoint, and upon detecting a Regional failure, shifting traffic to another Region within seconds without waiting for DNS propagation.**
- D. Force a TCP/UDP origin onto CloudFront and use it as a proxy with no caching (CloudFront specializes in HTTP/HTTPS content delivery and isn't designed for arbitrary TCP/UDP traffic).

**Correct Answer: C**

**Explanation**
**AWS Global Accelerator** provides two fixed anycast IP addresses, routing user traffic via the AWS global network backbone to the nearest healthy endpoint (Region). It suits non-HTTP workloads including TCP/UDP traffic (like game servers), and if a Region or endpoint fails, it shifts traffic to a healthy Region within seconds at the AWS network level with no need to wait for DNS propagation — the standard solution better suited than CloudFront for uncacheable, dynamic, low-latency workloads.

**Why the other choices are wrong**
- A: DNS-based routing has relatively slow failover due to TTL/caching.
- B: Client-side implementation is complex and inefficient.
- D: CloudFront specializes in HTTP/HTTPS delivery, not arbitrary TCP/UDP game traffic.

> 💡 **Exam tip**: For **uncacheable TCP/UDP-based traffic** needing fixed anycast IPs, low latency, and fast Regional failover, **AWS Global Accelerator** is the standard answer.

## QUESTION 509

**Question**: A company's Lambda function connects directly to RDS for PostgreSQL. During traffic spikes, a large increase in Lambda concurrency causes each execution to open an individual database connection, exceeding RDS's maximum connection limit and causing "too many connections" errors. How do you fix this connection surge without modifying the Lambda code?

**Choices**
- A. Upgrade the RDS instance class to the largest size to raise the connection limit itself (simply upgrading to a bigger instance greatly increases cost and isn't a fundamental fix, since the same problem recurs if Lambda concurrency grows further).
- B. **Place Amazon RDS Proxy between Lambda and RDS, pooling and reusing the individual connection requests generated by many Lambda executions, keeping the actual number of connections to the database much lower.**
- C. Severely limit the Lambda function's concurrency (lowering concurrency eases the connection problem but greatly limits throughput, failing to handle traffic spikes).
- D. Switch RDS to Aurora Serverless v1, expecting the connection problem to resolve automatically (Aurora Serverless v1 also has a concurrent-connection limit, and switching alone doesn't fundamentally solve the connection-pooling problem).

**Correct Answer: B**

**Explanation**
**Amazon RDS Proxy** is a fully managed connection-pooling layer sitting between an application (including Lambda) and the database. It pools and reuses the short, frequent connection requests generated by many concurrent Lambda executions, keeping the actual number of physical connections opened to the database much lower. This lets you simply point the connection target at the RDS Proxy endpoint, with no Lambda code changes, preventing the database's maximum-connection limit from being exceeded even during traffic spikes.

**Why the other choices are wrong**
- A: Upgrading the instance only raises cost, and the problem recurs if concurrency grows further.
- C: Limiting concurrency sacrifices throughput and isn't a fundamental fix.
- D: Switching engines alone doesn't automatically solve connection pooling.

> 💡 **Exam tip**: For an **RDS connection surge** caused by Lambda's high concurrency, **Amazon RDS Proxy** (connection pooling) is the standard answer.

What's the solution?

**Choices**
- A. **Use AWS License Manager to create a license configuration defining the number of licenses owned and rules (e.g., per-core/vCPU licensing), track EC2 instances consuming this license across multiple accounts, and block new instance launches that would exceed the limit via rules.**
- B. Have each account administrator manually tally license usage in a spreadsheet (manual spreadsheet tallying can't provide real-time tracking/enforcement across multiple accounts and is error-prone).
- C. Indirectly avoid the licensing issue by restricting deployment to only approved products via Service Catalog (Service Catalog standardizes deployable products but doesn't provide fine-grained per-core/vCPU license quantity tracking and limit enforcement).

**Why the other choices are wrong**
- B: Manual spreadsheet tallying can't provide real-time tracking/enforcement and is error-prone.
- C: Service Catalog is a product-standardization tool with no fine-grained license tracking.

## QUESTION 512

**Question**: A company has built a Direct Connect dedicated connection between its on-premises data center and AWS, securing stable bandwidth and low latency. But there's no backup path in case the dedicated circuit or connected carrier line fails, raising concern about a single point of failure (SPOF). How do you improve resilience cost-efficiently without full redundancy?

**Choices**
- A. Build a second, fully identical redundant Direct Connect circuit (the most robust option, but costs nearly double, and other alternatives might be considered first for the "cost-efficient" condition).
- B. Pin all on-premises router traffic to AWS via static routes with no separate backup, operating as-is (with no backup path, this doesn't address the core SPOF concern at all).
- C. **Configure a Site-to-Site VPN as a backup to the Direct Connect connection, setting up routing (BGP) so traffic automatically fails over to the VPN path if Direct Connect fails, achieving resilience at lower cost than fully redundant Direct Connect.**
- D. Remove Direct Connect entirely and use only Site-to-Site VPN (using VPN alone abandons the stable bandwidth and low latency that were the original reasons for adopting Direct Connect).

**Correct Answer: C**

**Explanation**
The standard cost-efficient pattern for Direct Connect resilience is configuring a **Site-to-Site VPN as a backup** to the Direct Connect connection. Both paths advertise routes via BGP, with the generally more stable and (per-bandwidth) cheaper Direct Connect path given a lower BGP path cost (preferred path). If the Direct Connect circuit fails, BGP automatically shifts traffic to the VPN path — eliminating the single point of failure at far lower cost than building a fully redundant second Direct Connect.

**Why the other choices are wrong**
- A: Full redundancy is most robust but significantly raises cost, potentially not meeting the "cost-efficient" condition.
- B: Operating with no backup doesn't address the SPOF concern at all.
- D: VPN-only abandons the bandwidth/latency benefits that motivated adopting Direct Connect.

> 💡 **Exam tip**: To **cost-efficiently eliminate the single point of failure** for Direct Connect, the pattern of **configuring Site-to-Site VPN as a backup path with automatic BGP failover** is the standard answer.

## QUESTION 513

**Question**: A company managing 50 accounts via AWS Organizations wants to consistently deploy the same IAM role and a specific set of CloudWatch alarms for security logging across every account, with any newly created account automatically getting the same resources going forward. Instead of deploying manually to each account individually, how do you manage this centrally in one place?

**Choices**
- A. Ask each account administrator to deploy the same CloudFormation template file and create a stack individually (individual manual deployment makes maintaining consistency and applying to new accounts automatically harder as accounts grow — exactly what this question wants to avoid).
- B. **Use AWS CloudFormation StackSets to deploy a stack from one template, from the Organizations management (or delegated administrator) account, across all accounts and Regions in a target organizational unit (OU), and enable the automatic deployment option so newly added accounts in the OU automatically get the same stack deployed.**
- C. Remotely run a script on each account via Systems Manager Run Command (Run Command doesn't execute directly across account boundaries, and CloudFormation-based tooling is better suited for per-account resource provisioning like IAM roles).
- D. Run Terraform individually per account but share only the state file in central S3 (sharing just the state file provides no orchestration to automatically trigger deployment across accounts or apply automatically to new accounts).

**Correct Answer: B**

**Explanation**
**AWS CloudFormation StackSets** lets you **centrally deploy and manage stacks across multiple accounts and Regions** from a single CloudFormation template. Integrated with AWS Organizations, you can target a specific OU, and enabling the **automatic deployment** option means the stack is automatically deployed or removed as accounts are added to or removed from that OU. This keeps resources like security IAM roles or CloudWatch alarms consistent organization-wide, including automatically for new accounts.

**Why the other choices are wrong**
- A: Individual manual deployment makes consistency harder to maintain as accounts grow.
- C: Run Command isn't suited for cross-account resource-provisioning orchestration.
- D: Sharing only the Terraform state file provides no automatic-deployment orchestration.

> 💡 **Exam tip**: To deploy consistent resources across **multiple accounts/Regions** and have them auto-apply to new accounts, **CloudFormation StackSets** (with automatic deployment) is the standard answer.

**Question**: A company wants to proactively verify the resilience of its microservices architecture. They want to deliberately inject failure scenarios — a full AZ outage, increased API response latency for a specific service, EC2 instance termination — in a controlled environment resembling production, to experiment with whether the system withstands failure as designed. How do you run this kind of chaos engineering experiment as a managed service?

**Choices**
- A. **Use AWS Fault Injection Service (FIS) to inject various failures — AZ disruption, network latency, API throttling, instance termination — in a controlled way per defined experiment templates, and configure stop conditions for safety so an experiment auto-halts before causing serious real impact.**
- B. Wait for a real failure to happen by chance in production until a CloudWatch alarm triggers (waiting for a chance failure isn't a controlled experiment and doesn't fit the goal of proactive verification).
- C. Check the architecture for potential weaknesses with AWS Trusted Advisor (Trusted Advisor is a static best-practice check tool, not a feature for actually injecting failures to experiment with dynamic system resilience).
- D. Review all microservices' code to theoretically analyze failure scenarios (code review alone can't verify dynamic interactions and unexpected failure propagation in a real operating environment).

**Correct Answer: A**

**Explanation**

Configuring **stop conditions** linked to CloudWatch alarms automatically halts an experiment if it begins causing unexpectedly serious impact, letting you safely verify resilience.

**Why the other choices are wrong**
- B: Waiting for a chance failure isn't controlled proactive verification.
- C: Trusted Advisor is a static check tool with no actual failure-injection capability.
- D: Code review alone can't verify dynamic interactions in a real operating environment.

> 💡 **Exam tip**: To **inject real failures in a controlled way to experiment with system resilience** (chaos engineering), **AWS Fault Injection Service (FIS)** is the standard answer.

## QUESTION 515

**Question**: A company is building a pipeline to process clickstream events in real time, where multiple independent consumers (a real-time dashboard, an anomaly-detection ML model, data lake ingestion) must read the same event stream concurrently, each at its own pace, and must be able to replay unprocessed events in order after a consumer failure. What messaging/streaming service fits?

**Choices**
- A. Use an Amazon SQS standard queue, with each consumer pulling messages from the queue (SQS's default model deletes a message from the queue once consumed, unsuited to multiple independent consumers each replaying/reprocessing the same event, and requires additional setup like SNS for fan-out).
- B. Use only Amazon SNS to fan events out to multiple consumers (SNS suits pub-sub fan-out, but doesn't retain messages by default, providing no replay capability to reprocess in order from a specific point after a consumer failure).
- C. Implement a separate dedicated database-polling process per consumer (a self-built polling approach has poor real-time characteristics, heavy development/operational burden, and requires implementing ordering guarantees yourself).
- D. **Use Amazon Kinesis Data Streams, letting multiple consumers (dashboard, ML model, data lake ingestion) independently read the same stream with their own shard iterators, and reprocess events in order from a desired point within the configured retention period (up to 365 days).**

**Correct Answer: D**

**Explanation**
**Amazon Kinesis Data Streams** retains published records for the stream's configured **retention period** (default 24 hours, extendable up to 365 days), and lets multiple consumer applications each use independent shard iterators (or enhanced fan-out) to **read the same stream in parallel at their own pace**. Order is guaranteed within a partition key, and if a consumer falls behind due to failure or needs reprocessing, it can re-read (replay) from a desired point (sequence number) within the retention period and reprocess in order — precisely matching the requirement for multiple independent consumers plus replay.

**Why the other choices are wrong**
- A: SQS's delete-on-consume model doesn't suit multiple independent replays.
- B: SNS excels at fan-out but doesn't retain messages by default, providing no replay.
- C: A self-built polling approach has poor real-time characteristics and a heavy burden of implementing ordering yourself.

> 💡 **Exam tip**: When multiple independent consumers each need to read at their own pace **while preserving order and supporting replay**, **Amazon Kinesis Data Streams** is the standard answer.

How do you build a private CA hierarchy within AWS to manage certificates, without requesting from a public certificate authority each time?

**Choices**
- A. Have each service team generate self-signed certificates with OpenSSL and distribute them manually (manual generation/distribution/rotation for hundreds of services doesn't scale and makes building a consistent trust hierarchy difficult).
- B. Individually request certificates from a public CA for hundreds of internal services (a public CA suits issuing publicly trusted, domain-validated certificates, and is inefficient for issuing large volumes of internal-only mTLS certificates at low cost/high frequency).
- C. **Use AWS Certificate Manager Private CA (ACM Private CA) to build an internally trusted private certificate authority hierarchy, and automate programmatic issuance/distribution/rotation of certificates for a large number of internal services (integrable with App Mesh, etc. for automatic sidecar injection).**
- D. Skip certificate-based mTLS and use only a fixed shared API key for all inter-service communication (a shared API key doesn't provide the mutual authentication and fine-grained key rotation that mTLS offers).

**Correct Answer: C**

**Explanation**
**AWS Certificate Manager Private CA (ACM Private CA)** is a managed service letting you build your own internally trusted private certificate authority (root/intermediate CA) hierarchy. Integrated with a service mesh like AWS App Mesh, certificates can be automatically issued/injected into each service's sidecar proxy, letting you operate mTLS at scale across hundreds of services.

## QUESTION 519

**Question**: A company manages dozens of accounts via AWS Organizations, and wants to fundamentally block certain risky actions (e.g., creating resources outside a specific Region, disabling CloudTrail, using certain regulated services) organization-wide, regardless of any IAM user or role's permissions — even administrator access. How do you enforce this guardrail organization-wide without relying on each account's individual IAM policy settings?

**Choices**
- A. Distribute an organization-wide guideline document asking each account administrator to strongly comply with policy (a document-based guideline has no enforcement power and can't fundamentally prevent mistakes or exceptions set by individual account administrators).
- B. Manually review only a rule prohibiting attachment of the AdministratorAccess policy to IAM users in every account (even blocking administrator access, other delegated permissions could still allow risky actions, and manual per-account review doesn't scale).
- C. Individually configure IAM permission boundaries per account to limit each user's maximum permissions (permission boundaries apply per individual IAM principal within an account, not uniformly enforced organization-wide including the account's root user — requiring individual setup/maintenance per account).
- D. **Define a Service Control Policy (SCP) in AWS Organizations from the management account and apply it to the target OU, so specific actions are fundamentally blocked organization-wide for every IAM principal (including the root user) in every account under that OU, regardless of that account's own permission settings (acting as an upper bound on maximum allowable permissions).**

**Correct Answer: D**

**Explanation**
An **AWS Organizations Service Control Policy (SCP)** is a policy applied at the organization or specific-OU level, defining the **upper bound on the maximum permissions** that **every IAM user/role (even an account's root user)** within the target scope can have. An action explicitly denied by an SCP can never be performed, no matter how permissively (even with administrator access) that account's own IAM policy allows it — the standard way to implement an organization-wide, mandatory guardrail independent of per-account IAM settings.

**Why the other choices are wrong**
- A: A document-based guideline has no enforcement power.
- B: Blocking only administrator access doesn't prevent risky actions via other delegated permissions, and doesn't scale.
- C: Permission boundaries apply per individual principal within an account, not as a uniform organization-wide enforcement.

> 💡 **Exam tip**: To **fundamentally block specific actions organization-wide** regardless of per-account permission settings, an **AWS Organizations SCP** is the standard answer.

## QUESTION 520

**Question**: A company runs hundreds of EC2 instances, and suspects many are over-provisioned with instance types far larger than their actual CPU/memory utilization warrants — wasting cost. Instead of manually analyzing CloudWatch metrics one by one to judge the right size, they want automatic, concrete downsizing/type-change recommendations per instance based on historical utilization data. What's the solution?

**Choices**
- A. Only set up AWS Budgets alerts for budget overruns (Budgets only tells you whether spend exceeds budget, providing no per-resource utilization-based optimal-instance-type recommendation).
- B. Bulk-downsize every instance to the smallest type, scaling back up if problems arise (a blind bulk downsize ignoring actual utilization risks significant performance degradation or outages, and is unsystematic).
- C. **Use AWS Compute Optimizer to analyze each EC2 instance's historical CloudWatch utilization metrics (CPU, memory, etc.) via machine learning, automatically providing concrete per-instance right-sizing (downsizing or type-change) recommendations along with estimated cost savings.**
- D. Only collect installed-software inventory via Systems Manager Inventory as material for manual judgment (Inventory only collects installed software/configuration information and provides no utilization-based right-sizing analysis).

**Correct Answer: C**

**Explanation**
**AWS Compute Optimizer** analyzes historical CloudWatch utilization metrics (CPU, memory when the agent is installed, network, etc.) for EC2 instances, Auto Scaling groups, EBS volumes, Lambda functions, and more, using **machine learning** to determine whether a resource is over- or under-provisioned, and automatically presents concrete **instance-type-change recommendations along with estimated cost savings**. It's the standard tool for data-driven rightsizing decisions without manually analyzing hundreds of instances one by one.

**Why the other choices are wrong**
- A: Budgets only reports whether budget is exceeded, with no per-resource utilization analysis.
- B: A blind bulk downsize ignoring actual utilization is risky.
- D: Systems Manager Inventory is a software/configuration collection tool with no utilization analysis.

> 💡 **Exam tip**: To automatically get **rightsizing (downsizing) recommendations** for EC2 and other resources based on historical utilization, **AWS Compute Optimizer** is the standard answer.
