## QUESTION 41

**문제**: 회사의 애플리케이션은 데이터 수집을 위해 여러 SaaS(Software-as-a-Service) 소스와 통합된다. 현재는 Amazon EC2 인스턴스가 데이터를 수신해 Amazon S3 버킷에 업로드하고, 업로드가 완료되면 같은 인스턴스가 사용자에게 알림까지 보낸다. 회사는 애플리케이션 성능 저하를 발견했으며, 최소한의 운영 오버헤드로 성능을 개선하려고 한다.

**보기**
- A. EC2 인스턴스에 Auto Scaling 그룹을 구성하고, S3 업로드 완료 시 Amazon SNS 주제로 이벤트를 보내도록 S3 이벤트 알림을 구성한다(EC2가 SaaS 데이터 수신·업로드를 직접 처리하는 근본 구조는 그대로 두어 운영 부담과 병목이 남음).
- B. **각 SaaS 소스와 S3 버킷 간 데이터 전송을 위한 Amazon AppFlow 흐름을 생성한다. S3 업로드 완료 시 Amazon SNS 주제로 이벤트를 보내도록 S3 이벤트 알림을 구성한다.**
- C. 각 SaaS 소스마다 출력 데이터를 S3로 보내는 Amazon EventBridge 규칙을 만들고, S3 업로드 완료 시 이벤트를 보내는 두 번째 EventBridge 규칙을 만들어 SNS를 대상으로 지정한다(EventBridge는 SaaS 애플리케이션과의 데이터 전송 자체를 담당하는 서비스가 아니며, 이런 통합을 직접 구현하려면 별도 커넥터 개발이 필요해 운영·개발 부담이 큼).
- D. EC2 대신 Docker 컨테이너를 만들어 Amazon ECS에서 호스팅하고, S3 업로드 완료 시 CloudWatch Container Insights로 SNS 이벤트를 트리거한다(Container Insights는 컨테이너 성능 모니터링 도구일 뿐 S3 객체 이벤트를 감지해 알림을 보내는 기능이 없으며, 컴퓨팅 계층만 바꿔서는 SaaS 연동 병목이 해소되지 않음).

**정답: B**

**해설**
**Amazon AppFlow**는 Salesforce, SAP, ServiceNow, Slack 같은 SaaS 애플리케이션과 S3, Redshift 등 AWS 서비스 사이에서 데이터를 코드 작성 없이 안전하게 전송해 주는 완전관리형 통합 서비스입니다. EC2 인스턴스가 직접 데이터를 수신·업로드하던 구조를 AppFlow 흐름으로 대체하면 성능 병목이던 단일 인스턴스 처리 구간이 사라지고, S3 업로드 완료 이벤트를 SNS로 보내는 표준 알림 구성만 추가하면 되므로 운영 오버헤드도 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: Auto Scaling을 추가해도 EC2가 SaaS 데이터를 직접 처리하는 아키텍처 자체는 그대로라 근본적인 성능·운영 부담이 해결되지 않습니다.
- C: EventBridge는 AWS 서비스 간 이벤트 라우팅에 강점이 있을 뿐, SaaS 소스와의 데이터 전송 커넥터 역할은 하지 못해 별도 개발이 필요합니다.
- D: Container Insights는 컨테이너 리소스 모니터링 지표를 수집할 뿐 S3 객체 업로드 완료를 감지해 알림을 보내는 기능이 없습니다.

> 💡 **시험 꿀팁**: **SaaS 애플리케이션과 AWS 서비스 간 데이터 전송**을 코드 없이 최소 운영 오버헤드로 구성해야 한다면 **Amazon AppFlow**가 표준 정답입니다.

## QUESTION 42

**문제**: 회사는 단일 VPC의 여러 가용 영역, 여러 서브넷에서 고가용성 이미지 처리 애플리케이션을 실행한다. EC2 인스턴스끼리는 서로 통신하지 않지만, 각 인스턴스는 S3에서 이미지를 다운로드하고 단일 NAT 게이트웨이를 통해 S3에 이미지를 업로드한다. 회사는 지역 데이터 전송 요금을 가장 비용 효율적으로 피하고 싶다.

**보기**
- A. 각 가용 영역에 NAT 게이트웨이를 배포한다(가용 영역 간 NAT 트래픽 요금은 줄일 수 있어도, 트래픽이 여전히 NAT 게이트웨이를 거치므로 NAT 데이터 처리 요금 자체는 계속 발생).
- B. NAT 게이트웨이를 NAT 인스턴스로 교체한다(트래픽 경로가 여전히 NAT를 거쳐 S3로 나가므로 데이터 전송 요금 문제를 해결하지 못하고 인스턴스 관리 부담만 늘어남).
- C. **Amazon S3용 게이트웨이 VPC 엔드포인트를 배포한다.**
- D. EC2 인스턴스를 실행할 전용 호스트를 프로비저닝한다(과금 모델을 바꿀 뿐 네트워크 경로나 데이터 전송 요금 구조와는 무관).

**정답: C**

**해설**
**S3용 게이트웨이 VPC 엔드포인트**는 VPC 라우팅 테이블에 S3 프리픽스 목록을 대상으로 하는 경로를 추가해, NAT 게이트웨이나 인터넷 게이트웨이를 거치지 않고 VPC와 S3 사이를 AWS 네트워크 내부 경로로 직접 연결합니다. 이렇게 하면 NAT 게이트웨이의 데이터 처리 요금 자체가 발생하지 않게 되어, 추가 인프라 없이 가장 비용 효율적으로 지역 데이터 전송 요금 문제를 해결할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 각 AZ에 NAT 게이트웨이를 두면 AZ 간 데이터 전송은 줄일 수 있지만, 트래픽이 여전히 NAT를 통과하며 NAT 데이터 처리 요금이 그대로 발생합니다.
- B: NAT 인스턴스로 바꿔도 EC2와 S3 사이의 트래픽은 여전히 NAT를 경유하므로 요금 문제가 해결되지 않고 직접 관리 부담만 커집니다.
- D: 전용 호스트는 EC2 과금 모델(하드웨어 전용 할당)에 관한 옵션으로, 데이터 전송 요금과는 무관합니다.

> 💡 **시험 꿀팁**: **EC2와 S3 사이의 지역 데이터 전송 요금을 없애고 싶다**면 **S3용 게이트웨이 VPC 엔드포인트**가 표준 정답입니다.

## QUESTION 43

**문제**: 온프레미스 애플리케이션이 시간에 민감한 대량의 데이터를 생성해 Amazon S3에 백업하는데, 인터넷 대역폭 제한으로 사용자 불만이 발생하고 있다. 솔루션 설계자는 S3에 대한 적시 백업을 유지하면서 내부 사용자의 인터넷 연결에 대한 영향을 최소화하는 장기적인 솔루션을 설계해야 한다.

**보기**
- A. AWS VPN 연결을 설정하고 모든 트래픽을 VPC 게이트웨이 엔드포인트로 프록시한다(VPN은 결국 공용 인터넷 회선을 경유하는 방식이라 기존 인터넷 대역폭 병목을 그대로 공유하게 됨).
- B. **새 AWS Direct Connect 연결을 설정하고, 이 새 연결을 통해 백업 트래픽을 직접 연결한다.**
- C. AWS Snowball 디바이스를 매일 주문해 데이터를 담아 매일 AWS로 반환한다(디바이스 배송·처리에는 통상 수일이 걸려 매일 반복하는 것은 현실적으로 불가능하며 시간에 민감한 백업 요구에도 맞지 않음).
- D. AWS 지원 티켓을 제출해 계정의 S3 서비스 한도를 제거해 달라고 요청한다(문제의 원인은 S3 한도가 아니라 인터넷 대역폭이며, AWS 서비스 한도는 완전히 제거가 아니라 상향 조정만 가능).

**정답: B**

**해설**
**AWS Direct Connect**는 온프레미스 데이터센터와 AWS 사이에 공용 인터넷을 거치지 않는 전용 회선을 제공합니다. 백업 트래픽을 이 전용 연결로 옮기면 기존 인터넷 회선의 대역폭을 소비하지 않아 내부 사용자 경험에 영향을 주지 않으면서, 안정적이고 예측 가능한 대역폭으로 적시에 S3 백업을 완료할 수 있는 장기적인 해결책이 됩니다.

**왜 다른 보기는 오답인가**
- A: VPN은 암호화된 터널을 제공할 뿐 결국 인터넷 회선을 통과하므로 대역폭 경쟁 문제를 그대로 안고 갑니다.
- C: Snowball의 배송 및 처리 리드타임을 고려하면 매일 주문·반환하는 운영은 현실성이 없고, 시간에 민감한 데이터 요구에도 부적합합니다.
- D: S3 서비스 한도 조정은 대역폭 문제와 무관하며, AWS는 한도를 완전히 없애는 옵션을 제공하지 않고 상향 요청만 가능합니다.

> 💡 **시험 꿀팁**: **온프레미스-AWS 간 대용량 트래픽을 인터넷 대역폭 소모 없이 지속적으로** 처리해야 한다면 **AWS Direct Connect**가 표준 정답입니다.

## QUESTION 44

**문제**: 회사에 중요한 데이터가 담긴 Amazon S3 버킷이 있으며, 우발적인 삭제로부터 데이터를 보호해야 한다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 어떤 조치를 조합해야 하는가? (2개를 선택하세요.)

**보기**
- A. **S3 버킷에서 버전 관리(Versioning)를 활성화한다.**
- B. **S3 버킷에서 MFA 삭제(MFA Delete)를 활성화한다.**
- C. S3 버킷에 버킷 정책을 생성한다(버킷 정책은 누가 어떤 작업을 할 수 있는지에 대한 접근 권한 부여/제한 수단이며, 그 자체가 실수로 인한 삭제를 방지하는 전용 기능은 아님).
- D. S3 버킷에서 기본 암호화를 활성화한다(암호화는 저장된 데이터의 기밀성을 보호할 뿐, 삭제 권한이 있는 사용자의 삭제 자체를 막지는 못함).
- E. S3 버킷 객체에 수명 주기 정책을 생성한다(수명 주기 정책은 시간이 지남에 따라 객체를 다른 스토리지 클래스로 전환하거나 만료(삭제)시키는 자동화 도구로, 오히려 삭제를 유발할 수도 있는 기능이라 목적과 반대에 가까움).

**정답: A, B**

**해설**
**S3 버전 관리**를 활성화하면 객체를 덮어쓰거나 삭제해도 이전 버전이 버킷 내에 그대로 보존되어, 실수로 삭제된 객체를 이전 버전으로 복원할 수 있습니다. 여기에 **MFA 삭제**를 함께 활성화하면 객체 버전을 영구적으로 삭제하거나 버전 관리 상태를 변경할 때 계정 자격 증명 외에 추가 다단계 인증 코드를 요구해, 실수나 무단 삭제 자체를 어렵게 만듭니다. 두 기능을 조합해야 "보존"과 "삭제 방지"라는 두 측면을 모두 충족할 수 있습니다.

**왜 다른 보기는 오답인가**
- C: 버킷 정책은 리소스 기반 접근 권한을 정의하는 도구로, 삭제 방지를 위한 전용 메커니즘이 아닙니다.
- D: 기본 암호화는 데이터 열람을 통제할 뿐 삭제 자체를 막지는 못합니다.
- E: 수명 주기 정책은 오히려 일정 시점 이후 객체를 자동으로 삭제/전환하는 기능이라 우발적 삭제 방지 목적과 맞지 않습니다.

> 💡 **시험 꿀팁**: **S3의 우발적 삭제 방지**가 요구되면 **버전 관리 + MFA 삭제** 조합이 표준 정답입니다.

## QUESTION 45

**문제**: 회사의 데이터 수집 워크플로는 새 데이터 도착을 알리는 Amazon SNS 주제와, 데이터를 처리하고 메타데이터를 기록하는 AWS Lambda 함수로 구성된다. 네트워크 연결 문제로 워크플로가 간헐적으로 실패하며, 실패 시 회사가 수동으로 재실행하지 않는 한 Lambda가 해당 데이터를 수집하지 못한다. 향후 모든 데이터를 Lambda가 확실히 수집하도록 하려면 어떤 조치를 조합해야 하는가? (2개를 선택하세요.)

**보기**
- A. 여러 가용 영역에 Lambda 함수를 배포한다(Lambda는 기본적으로 AWS가 여러 AZ에 걸쳐 실행을 관리하는 서비스이며, 이 조치는 애초에 실패의 원인인 재시도·메시지 보존 문제와 관련이 없음).
- B. **Amazon SQS 대기열을 생성하고 SNS 주제를 구독하도록 구성한다.**
- C. Lambda 함수에 할당된 CPU와 메모리를 늘린다(리소스 부족이 아니라 네트워크 연결 실패가 원인이므로 문제 해결에 도움이 되지 않음).
- D. Lambda 함수의 프로비저닝된 동시성을 늘린다(콜드 스타트 지연을 줄이는 기능일 뿐 실패한 이벤트의 재처리·보존과는 무관).
- E. **SQS 대기열에서 메시지를 읽도록 Lambda 함수를 수정한다.**

**정답: B, E**

**해설**
SNS는 구독자가 메시지를 즉시 처리하지 못하면 재시도 후에도 결국 유실될 수 있는 푸시(push) 기반 알림 서비스입니다. **SNS 주제를 구독하는 SQS 대기열**을 추가하면 알림이 대기열에 안전하게 쌓여 처리 여부와 무관하게 보존되고, Lambda가 SNS를 직접 트리거로 쓰는 대신 **SQS를 폴링해 메시지를 읽도록** 수정하면 처리에 실패한 메시지도 대기열에 남아 자동으로 재시도됩니다. 이 조합으로 네트워크 문제에 따른 간헐적 실패에도 모든 데이터가 결국 처리되는 내결함성을 확보합니다.

**왜 다른 보기는 오답인가**
- A: Lambda의 다중 AZ 실행은 AWS가 자동으로 처리하는 부분이며, 이번 실패 원인인 메시지 유실/재시도 문제와는 관련이 없습니다.
- C: CPU/메모리 부족이 원인이 아니라 네트워크 연결 문제가 원인이므로 리소스 증설은 해결책이 아닙니다.
- D: 프로비저닝된 동시성은 콜드 스타트 지연 완화용 기능으로 메시지 보존·재시도와 무관합니다.

> 💡 **시험 꿀팁**: **SNS 기반 알림 처리가 간헐적으로 실패해 데이터가 유실**된다면 **SNS → SQS 구독 추가 + Lambda가 SQS를 폴링**하도록 바꾸는 것이 표준 정답입니다.

> 💡 **시험 꿀팁**: **특정 기간 동안 특정 가용 영역의 EC2 용량을 보장**받아야 한다면 **온디맨드 용량 예약(가용 영역 지정)**이 표준 정답입니다.

**보기**
- A. 전체 10년 동안 S3 Glacier에 기록을 저장하고, 접근 통제 정책으로 10년간 삭제를 거부한다(Glacier는 검색에 분 단위 이상이 소요되는 콜드 스토리지라 1년간 "즉시" 액세스해야 한다는 요구를 충족하지 못함).

Glacier Deep Archive는 여러 시설에 데이터를 중복 저장해 최대 복원력 요구도 함께 만족시킵니다.

- B: IAM 정책은 관리자/루트 사용자가 변경할 수 있는 권한 설정일 뿐이라, "누구도 삭제할 수 없음"이라는 강제적 불변성을 제공하지 못합니다.
- D: One Zone-IA는 단일 AZ 저장이라 복원력이 부족하고, 거버넌스 모드는 특정 권한을 가진 사용자가 보존 설정을 우회할 수 있어 완전한 삭제 방지가 아닙니다.

> 💡 **시험 꿀팁**: **관리자·루트 사용자를 포함해 누구도 삭제할 수 없는 저장**이 요구되면 **S3 Object Lock의 규정 준수(Compliance) 모드**가 표준 정답입니다(거버넌스 모드와 반드시 구분하세요).

- B. 퍼블릭 서브넷 인스턴스에 할당된 보안 그룹의 인바운드 트래픽을 거부하는 보안 그룹을 만들어 DB 인스턴스에 연결한다(보안 그룹은 허용(allow) 규칙만 지원하며 명시적 거부(deny) 규칙을 만들 수 없어 이 접근 방식 자체가 성립하지 않음).
- C. **프라이빗 서브넷 인스턴스에 할당된 보안 그룹의 인바운드 트래픽을 허용하는 보안 그룹을 만들어 DB 인스턴스에 연결한다.**
- D. 퍼블릭-프라이빗 서브넷 간, 프라이빗-데이터베이스 서브넷 간에 각각 VPC 피어링 연결을 생성한다(VPC 피어링은 서로 다른 VPC를 연결하는 기능이며, 같은 VPC 내 서브넷 간 접근 제어에는 사용할 수도 없고 적합하지도 않은 개념).

**정답: C**

**해설**
RDS 데이터베이스에 연결된 **보안 그룹**의 인바운드 규칙에서 소스를 IP 대역이 아니라 **프라이빗 서브넷 EC2 인스턴스에 연결된 보안 그룹**으로 지정하면, 해당 보안 그룹을 가진 인스턴스에서 오는 트래픽만 허용됩니다. 보안 그룹은 기본적으로 모든 인바운드 트래픽을 거부하는 상태에서 시작하므로, 프라이빗 서브넷의 보안 그룹만 명시적으로 허용하면 퍼블릭 서브넷 등 다른 어떤 소스에서도 DB에 접근할 수 없게 되어 요구 사항을 정확히 충족합니다.

**왜 다른 보기는 오답인가**

- B: 보안 그룹은 허용 규칙만 지원하고 거부 규칙 개념이 없으므로, "인바운드를 거부하는 보안 그룹"이라는 발상 자체가 AWS 보안 그룹의 동작 방식과 맞지 않습니다.
- D: VPC 피어링은 서로 다른 VPC 간 연결을 위한 기능으로, 동일 VPC 내부 서브넷 간 접근 제어와는 무관한 개념입니다.

> 💡 **시험 꿀팁**: **특정 서브넷의 인스턴스에서만 오는 트래픽을 허용**하려면 IP 대역이 아니라 **소스로 보안 그룹을 지정하는 보안 그룹 규칙**이 표준 정답입니다.

- B: 리전 API Gateway 사용자 지정 도메인은 API와 같은 리전의 ACM 인증서가 필요하며, us-east-1은 엣지 최적화(CloudFront 기반) 도메인 전용입니다.
- D: 인증서 리전이 잘못되었을 뿐 아니라, API Gateway 같은 AWS 리소스를 가리키려면 일반 A 레코드가 아닌 별칭(Alias) 레코드를 사용해야 합니다.

> 💡 **시험 꿀팁**: **API Gateway 리전 사용자 지정 도메인**을 구성할 때는 **API와 동일한 리전의 ACM 인증서** + **Route 53 별칭 레코드**가 표준 정답입니다(엣지 최적화 도메인만 us-east-1 인증서가 필요하다는 점과 구분하세요).

**왜 다른 보기는 오답인가**
- A: Data Pipeline + EMR은 배치 처리 지향적이라 지속적으로 유입되는 실시간 스트림 데이터를 다루기에는 운영 복잡성이 큽니다.
- B: 자체 EC2 Auto Scaling 계층으로 수집을 직접 구현하면 Kinesis 같은 관리형 스트리밍 서비스에 비해 운영 부담이 훨씬 커집니다.
- C: CloudFront는 콘텐츠 전송에 최적화된 CDN으로 스트림 수집 용도가 아니며, 객체별 Lambda 트리거 방식은 초당 대량 이벤트가 발생하는 클릭스트림 규모에 맞지 않습니다.

> 💡 **시험 꿀팁**: **대규모·다수 소스에서 발생하는 실시간 클릭스트림 데이터를 수집·저장·분석**해야 한다면 **Kinesis Data Streams + Kinesis Data Firehose + S3/Redshift** 조합이 표준 정답입니다.

## QUESTION 60

**문제**: 회사 웹 사이트가 HTTP와 HTTPS를 각각 별도로 처리하도록 구성된 ALB(Application Load Balancer) 뒤에 있다. 회사는 모든 요청이 HTTPS를 사용하도록 강제해 웹사이트로 전달하고 싶다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. HTTPS 트래픽만 허용하도록 ALB의 네트워크 ACL을 업데이트한다(이 방식은 HTTP 요청을 아예 차단해 버릴 뿐 HTTPS로 리디렉션하지 않아, HTTP로 접속한 사용자는 연결 자체가 실패하게 됨).
- B. URL의 HTTP를 HTTPS로 바꾸는 규칙을 만든다(ALB나 관련 AWS 서비스가 제공하는 표준 기능이 아니며 막연하고 구체성이 없는 접근).
- C. **ALB에 HTTP 트래픽을 HTTPS로 리디렉션하는 리스너 규칙을 생성한다.**
- D. ALB를 SNI(서버 이름 표시)를 사용하도록 구성된 Network Load Balancer로 교체한다(NLB는 TCP/UDP 계층에서 동작해 HTTP 요청 내용을 이해하지 못하므로, HTTP를 HTTPS로 리디렉션하는 애플리케이션 계층 기능을 기본적으로 제공하지 않음).

**정답: C**

**해설**
**Application Load Balancer의 리스너 규칙**에는 HTTP(80) 리스너에서 수신한 요청을 HTTPS(443)로 자동 리디렉션하는 내장 리디렉션 액션이 있습니다. HTTP 리스너에 "HTTPS로 리디렉션" 규칙을 추가하고 HTTPS 리스너와 인증서가 이미 구성되어 있다면, 사용자가 HTTP로 접속하더라도 자동으로 HTTPS URL로 리디렉션되어 모든 트래픽이 암호화된 연결을 사용하게 됩니다. ALB는 애플리케이션(7) 계층에서 동작하므로 이런 프로토콜 기반 리디렉션을 별도 코드 없이 처리할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 네트워크 ACL로 HTTP를 차단하면 리디렉션 없이 연결 자체가 실패해, HTTP로 접속을 시도한 사용자는 웹사이트에 아예 도달하지 못합니다.
- B: "URL을 바꾸는 규칙"은 AWS의 표준 기능으로 존재하지 않는 모호한 설명입니다.
- D: NLB는 4계층 로드밸런서로 HTTP 헤더나 URL을 이해하지 못해 HTTP-to-HTTPS 리디렉션 같은 애플리케이션 계층 기능을 제공하지 않습니다.

> 💡 **시험 꿀팁**: **ALB에서 HTTP 요청을 HTTPS로 강제 전환**하려면 **ALB 리스너 규칙의 리디렉션 액션**이 표준 정답입니다.
