## QUESTION 301

**문제**: 대학 연구소는 온프레미스 Windows 파일 서버에서 Amazon FSx for Windows File Server로 30TB의 데이터를 마이그레이션해야 한다. 연구소에는 대학의 다른 여러 부서와 공유하는 1Gbps 네트워크 회선이 있다. 연구소는 데이터 전송 성능을 최대화하는 마이그레이션 서비스를 사용하되, 다른 부서에 미치는 영향을 최소화하기 위해 사용 대역폭을 직접 제어할 수 있어야 한다. 마이그레이션은 향후 5일 이내에 완료되어야 한다. 이러한 요구 사항을 충족하는 AWS 솔루션은 무엇인가?

**보기**
- A. AWS Snowcone(오프라인 물리 배송 방식으로, 대역폭 제한이 아닌 네트워크 자체가 없는 상황에 적합하며 이미 네트워크 회선이 있는 이 사례에는 과도함)
- B. Amazon FSx File Gateway(온프레미스에서 FSx 파일을 캐싱해 접근하는 게이트웨이로, 대량 일회성 마이그레이션에 최적화된 기능이 아님)
- C. **AWS DataSync**
- D. AWS Transfer Family(SFTP/FTPS/FTP 프로토콜로 S3·EFS에 파일을 주고받는 서비스이며, Windows 파일 서버 간 대량 마이그레이션에 특화되지 않음)

**정답: C**

**해설**
**AWS DataSync**는 온프레미스 파일 시스템과 AWS 스토리지 간 데이터 전송을 자동화하고 가속화하는 관리형 서비스로, 전용 최적화 프로토콜을 사용해 네트워크 대역폭을 최대한 활용하면서도 태스크별로 **대역폭 제한(bandwidth throttling)**을 설정할 수 있습니다. 공유 네트워크 회선을 사용하는 다른 부서에 영향을 주지 않도록 대역폭 상한을 지정하면서도 5일이라는 짧은 기한 내에 30TB를 전송해야 하는 이 시나리오에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: Snowcone은 네트워크 연결이 열악하거나 없는 환경에서 물리적으로 데이터를 배송하는 용도이며, 이미 1Gbps 회선이 존재하고 대역폭 제어가 핵심 요구 사항인 이 상황과 맞지 않습니다.
- B: FSx File Gateway는 온프레미스 애플리케이션이 FSx 파일 공유에 저지연으로 캐시 접근하도록 돕는 것이 목적이며, 대량 데이터의 일회성 이전 및 대역폭 제어 기능을 제공하지 않습니다.
- D: Transfer Family는 SFTP/FTP류 프로토콜 기반 파일 교환에 초점을 맞춘 서비스로, 파일 서버 간 대규모 동기화 및 대역폭 스로틀링에는 DataSync만큼 적합하지 않습니다.

> 💡 **시험 꿀팁**: "공유 네트워크에서 **대역폭을 제어**하며 온프레미스와 AWS 스토리지 간 대량 데이터를 빠르게 옮겨야 한다"는 조건이 나오면 **AWS DataSync**가 표준 정답입니다.

## QUESTION 302

**문제**: 회사는 사용자가 모바일 기기에서 슬로우 모션 비디오 클립을 스트리밍할 수 있는 모바일 앱을 만들려고 한다. 현재 앱은 비디오 클립을 캡처해 원본(raw) 형식 그대로 Amazon S3 버킷에 업로드하고, 앱이 S3 버킷에서 직접 이 클립을 가져온다. 그러나 원본 형식 비디오의 용량이 커서 사용자가 모바일 기기에서 버퍼링과 재생 문제를 겪고 있다. 회사는 운영 오버헤드를 최소화하면서 앱의 성능과 확장성을 극대화하려고 한다. 이 요구 사항을 충족하는 솔루션 조합은 무엇인가? (2개 선택)

**보기**
- A. **콘텐츠 전송과 캐싱을 위해 Amazon CloudFront를 배포한다.**
- B. AWS DataSync를 사용해 다른 리전의 S3 버킷으로 비디오 파일을 복제한다(리전 간 재해복구/지연시간 개선용 복제이며, 원본 형식이 큰 비디오 재생 문제 자체를 해결하지 못함)
- C. **Amazon Elastic Transcoder를 사용해 비디오 파일을 보다 적절한 스트리밍 형식으로 변환한다.**
- D. 콘텐츠 전송과 캐싱을 위해 로컬 존에 Amazon EC2 인스턴스의 Auto Scaling 그룹을 배포한다(관리형 CDN인 CloudFront 대신 EC2 캐싱 계층을 직접 운영해야 하므로 운영 오버헤드가 큼)
- E. Amazon EC2 인스턴스의 Auto Scaling 그룹을 배포해 비디오 파일을 변환한다(관리형 트랜스코딩 서비스 대신 EC2 기반 변환 파이프라인을 직접 구축/운영해야 해 오버헤드가 큼)

**정답: A, C**

**해설**
원본 형식의 대용량 비디오가 버퍼링과 재생 문제의 근본 원인이므로, **Amazon Elastic Transcoder**로 비디오를 모바일 재생에 적합한 압축/해상도의 스트리밍 형식으로 변환하는 것이 먼저 필요합니다. 여기에 **Amazon CloudFront**를 앞단에 배포하면 변환된 파일을 엣지 로케이션에서 캐싱해 사용자에게 낮은 지연 시간으로 전달할 수 있고, S3에 직접 트래픽이 몰리는 것도 줄어들어 두 서비스 모두 완전관리형이므로 운영 오버헤드도 최소화됩니다.

**왜 다른 보기는 오답인가**
- B: DataSync에 의한 리전 간 복제는 재해복구나 지역별 지연시간 단축에는 유용하지만, 원본 파일 자체가 크다는 근본 문제나 콘텐츠 전송 최적화를 해결하지 못합니다.
- D: EC2 Auto Scaling 기반의 자체 캐싱 계층은 CloudFront 대비 인프라 관리, 패치, 확장 정책 설정 등 운영 부담이 훨씬 큽니다.
- E: 비디오 변환을 EC2 위에서 직접 구현하면 인코딩 파이프라인, 스케일링, 장애 처리를 모두 직접 관리해야 하므로 관리형 Elastic Transcoder보다 운영 오버헤드가 큽니다.

> 💡 **시험 꿀팁**: "대용량 미디어 파일 재생 성능"과 "운영 오버헤드 최소화"가 함께 나오면 **트랜스코딩(Elastic Transcoder/MediaConvert) + CloudFront** 조합이 표준 정답 패턴입니다.

## QUESTION 303

**문제**: 회사가 Amazon ECS 클러스터에 새 애플리케이션을 배포했고 ECS 태스크에 Fargate 시작 유형을 사용하고 있다. 실행 시점에 높은 트래픽이 예상되어 CPU 및 메모리 사용률을 모니터링하고 있지만, 사용률이 낮아지면 비용을 절감하고 싶어 한다. 솔루션 설계자는 무엇을 권장해야 하는가?

**보기**
- A. Amazon EC2 Auto Scaling을 사용해 과거 트래픽 패턴을 기반으로 특정 시간대에 조정한다(Fargate에는 EC2 Auto Scaling 개념이 적용되지 않으며 예측 기반 조정은 실제 사용률 변화에 즉각 대응하지 못함)
- B. AWS Lambda 함수로 CloudWatch 경보를 트리거해 ECS를 조정한다(직접 커스텀 스케일링 로직을 구현/유지보수해야 해 관리형 옵션보다 불필요하게 복잡함)
- C. 단순 조정 정책과 함께 Amazon EC2 Auto Scaling을 사용해 ECS 지표 위반이 CloudWatch 경보를 트리거할 때 조정한다(Fargate 태스크는 기반 EC2 인스턴스를 직접 관리하지 않으므로 EC2 Auto Scaling으로 태스크 수를 조정할 수 없음)
- D. **대상 추적 정책과 함께 AWS Application Auto Scaling을 사용해 ECS 지표 위반이 CloudWatch 경보를 트리거할 때 조정한다.**

**정답: D**

**해설**
Fargate 시작 유형에서는 기반 인프라를 관리하지 않으므로, ECS 서비스의 태스크 개수를 늘리거나 줄이려면 **AWS Application Auto Scaling**을 사용해야 합니다. 특히 **대상 추적(target tracking) 정책**은 CPU/메모리 사용률과 같은 CloudWatch 지표의 목표값을 지정하기만 하면 필요한 만큼 자동으로 태스크 수를 조정해 주므로, 트래픽 급증 시 확장하고 활용도가 낮을 때는 축소해 비용을 절감할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: EC2 Auto Scaling은 EC2 인스턴스 단위의 확장이며, Fargate는 서버리스 컴퓨팅이라 EC2 인스턴스 개념 자체가 없습니다.
- B: Lambda로 커스텀 스케일링 로직을 짜는 것은 가능하지만, Application Auto Scaling이 이미 제공하는 기능을 재구현하는 불필요한 복잡성을 추가합니다.
- C: Fargate 태스크는 EC2 인스턴스에 배치되지 않으므로 EC2 Auto Scaling 그룹으로는 애초에 ECS 태스크 수를 조정할 수 없습니다.

> 💡 **시험 꿀팁**: **ECS Fargate**의 태스크 수를 지표 기반으로 자동 확장/축소해야 한다면 **Application Auto Scaling의 대상 추적 정책**이 표준 정답입니다.

## QUESTION 304

**문제**: 한 회사가 최근 다른 AWS 리전에 재해 복구 사이트를 구축했다. 회사는 정기적으로 두 리전의 NFS 파일 시스템 간에 대량의 데이터를 주고받아야 한다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. **AWS DataSync를 사용한다.**
- B. AWS Snowball 디바이스를 사용한다(물리 디바이스 수동 취급·배송이 필요해 정기적/반복적 전송에는 적합하지 않음)
- C. Amazon EC2에서 SFTP 서버를 구축한다(전송을 수동으로 시작·모니터링해야 하며 운영 오버헤드가 큼)
- D. AWS Database Migration Service(AWS DMS)를 사용한다(관계형·비관계형 데이터베이스 마이그레이션용 서비스이며 NFS 파일 시스템 전송을 지원하지 않음)

**정답: A**

**해설**
**AWS DataSync**는 NFS, SMB 등 파일 기반 프로토콜을 네이티브로 지원하며, 온프레미스-AWS 간뿐 아니라 서로 다른 AWS 리전에 있는 파일 시스템 간에도 예약 실행과 자동 재시도, 데이터 검증을 포함한 전송 태스크를 구성할 수 있습니다. 정기적으로 반복되는 대량 NFS 데이터 동기화를 완전관리형으로 자동화할 수 있어 운영 오버헤드를 최소화한다는 요구에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- B: Snowball은 물리 디바이스를 주문·배송·반납하는 절차가 필요해 일회성 대량 이전에는 유리하지만 정기 반복 전송에는 맞지 않습니다.
- C: EC2에 SFTP 서버를 직접 구축하면 서버 운영, 보안 패치, 전송 스케줄링까지 모두 수동으로 관리해야 합니다.
- D: DMS는 데이터베이스 엔진 간 마이그레이션·복제에 특화된 서비스로, 파일 시스템(NFS) 데이터 전송을 지원하지 않습니다.

> 💡 **시험 꿀팁**: **리전 간 또는 온프레미스-AWS 간 NFS/SMB 파일 시스템의 정기적인 대량 데이터 전송**에는 **AWS DataSync**가 표준 정답입니다.

## QUESTION 305

**문제**: 회사는 AWS 클라우드에서 호스팅되는 게임 애플리케이션을 위한 공유 스토리지 솔루션을 설계하고 있다. SMB 클라이언트로 데이터에 접근할 수 있어야 하며, 솔루션은 완전관리형이어야 한다. 이 요구 사항을 충족하는 AWS 솔루션은 무엇인가?

**보기**
- A. 탑재 가능한 파일 시스템으로 데이터를 공유하는 AWS DataSync 태스크를 생성하고, 파일 시스템을 애플리케이션 서버에 마운트한다(DataSync는 데이터 전송 서비스이며 SMB 공유 스토리지 자체를 상시 제공하는 파일 시스템 서비스가 아님)
- B. Amazon EC2 Windows 인스턴스를 생성하고 Windows 파일 공유 역할을 설치·구성한 뒤 애플리케이션 서버를 연결한다(직접 구축한 인스턴스 기반 공유이므로 패치·고가용성·백업을 모두 자체 관리해야 해 완전관리형 요구에 위배)
- C. **Windows File Server용 Amazon FSx를 생성하고 애플리케이션 서버를 파일 시스템에 연결한다.**
- D. Amazon S3 버킷을 생성하고 IAM 역할로 접근 권한을 부여한 뒤 S3 버킷을 애플리케이션 서버에 마운트한다(S3는 객체 스토리지로 네이티브 SMB 프로토콜을 지원하지 않음)

**정답: C**

**해설**
**Amazon FSx for Windows File Server**는 SMB 프로토콜을 네이티브로 지원하는 완전관리형 Windows 파일 스토리지로, Active Directory 통합, 자동 백업, 고가용성 구성을 AWS가 직접 관리해 줍니다. 게임 애플리케이션 서버들이 SMB로 공유 스토리지에 접근해야 하면서 운영 부담 없는 완전관리형을 요구하는 이 시나리오에 정확히 맞습니다.

**왜 다른 보기는 오답인가**
- A: DataSync는 데이터를 이동/동기화하는 전송 서비스이지, 애플리케이션이 상시 마운트해 쓰는 공유 파일 시스템을 제공하지 않습니다.
- B: EC2에 직접 파일 서버를 구성하면 OS 패치, 장애 조치, 백업까지 모두 사용자가 관리해야 해 완전관리형 요구를 충족하지 못합니다.
- D: S3는 REST API 기반 객체 스토리지로 SMB 프로토콜 마운트를 네이티브로 지원하지 않습니다.

> 💡 **시험 꿀팁**: **SMB 기반 완전관리형 공유 파일 스토리지**가 필요하면 **Amazon FSx for Windows File Server**가 표준 정답입니다.

**문제**: 회사는 Amazon EC2 인스턴스에서 실행되는 지연 시간에 민감한 애플리케이션을 위해 인메모리 데이터베이스를 운영하려고 한다. 애플리케이션은 분당 10만 건 이상의 트랜잭션을 처리하며 높은 네트워크 처리량이 필요하다. 솔루션 설계자는 데이터 전송 비용을 최소화하는 비용 효율적인 네트워크 설계를 제공해야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

## QUESTION 307

**문제**: 주로 온프레미스에서 애플리케이션 서버를 운영하던 회사가 AWS로 마이그레이션하기로 했다. 회사는 온프레미스의 iSCSI 스토리지를 추가로 확장할 필요성을 최소화하려고 하며, 최근에 접근한 데이터만 로컬에 보관하기를 원한다. 이 요구 사항을 충족하려면 어떤 AWS 솔루션을 사용해야 하는가?

**보기**
- A. Amazon S3 File Gateway(NFS/SMB 기반 파일 인터페이스를 제공하는 게이트웨이로, iSCSI 블록 스토리지 확장 문제와는 직접 관련이 없음)
- B. AWS Storage Gateway 테이프 게이트웨이(백업/아카이브용 가상 테이프 인터페이스이며 iSCSI 블록 볼륨을 온디맨드로 캐싱하는 용도가 아님)
- C. AWS Storage Gateway 볼륨 게이트웨이 저장 볼륨(전체 데이터셋을 온프레미스에 저장하므로 iSCSI 스토리지 확장 필요성이 그대로 남음)
- D. **AWS Storage Gateway 볼륨 게이트웨이 캐시 볼륨**

**정답: D**

**해설**
**캐시 볼륨(cached volumes)** 구성은 전체 데이터를 Amazon S3에 저장하고, 자주 접근하는 데이터만 온프레미스 게이트웨이에 캐시로 보관합니다. iSCSI로 온프레미스에 연결되므로 기존 스토리지 확장 없이도 사실상 무제한에 가까운 S3 용량을 활용할 수 있어, "최근 접근 데이터만 로컬 보관 + iSCSI 확장 최소화"라는 요구에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: S3 File Gateway는 NFS/SMB 파일 인터페이스를 제공하는 것이지 iSCSI 블록 인터페이스가 아닙니다.
- B: 테이프 게이트웨이는 기존 백업 소프트웨어를 위한 가상 테이프 라이브러리(VTL) 용도로, 활성 데이터의 캐시 접근 패턴에 맞지 않습니다.
- C: 저장 볼륨(stored volumes)은 전체 데이터셋을 온프레미스에 유지하고 S3로 비동기 백업만 하므로, 로컬 스토리지 확장 부담이 그대로 남습니다.

> 💡 **시험 꿀팁**: "**최근 접근 데이터만 로컬에**, 나머지는 S3에" + "iSCSI" 조합이 나오면 **Storage Gateway 볼륨 게이트웨이의 캐시 볼륨**이 표준 정답입니다.

**문제**: 솔루션 설계자는 스토리지 비용을 최적화해야 하며, 더 이상 접근하지 않거나 거의 접근하지 않는 Amazon S3 버킷을 식별해야 한다. 최소한의 운영 오버헤드로 이 목표를 달성하는 솔루션은 무엇인가?

> 💡 **시험 꿀팁**: **S3 버킷의 접근 패턴·비용 최적화를 최소 오버헤드로 분석**해야 한다면 **S3 Storage Lens(고급 지표)**가 표준 정답입니다.

## QUESTION 310

**문제**: 회사가 AI/ML을 연구하는 고객에게 데이터셋을 판매한다. 데이터셋은 us-east-1 리전의 Amazon S3 버킷에 저장된 대용량 형식화 파일이다. 회사는 고객이 데이터셋 접근 권한을 구매하는 웹 애플리케이션을 Application Load Balancer 뒤의 여러 EC2 인스턴스에서 호스팅한다. 구매 후 고객은 파일 접근을 위한 S3 서명된 URL을 받는다. 고객은 북미와 유럽 전역에 분산되어 있다. 회사는 데이터 전송 비용을 줄이면서 성능은 유지하거나 개선하려고 한다. 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. 기존 S3 버킷에 S3 Transfer Acceleration을 구성하고, 고객 요청을 해당 엔드포인트로 안내하며 S3 서명된 URL을 계속 사용한다(주로 업로드 가속에 적합하며, 전 세계 분산 사용자에 대한 반복 다운로드 캐싱·전송비 절감 효과는 CloudFront보다 제한적)
- B. **기존 S3 버킷을 오리진으로 하는 Amazon CloudFront 배포를 생성하고, 고객 요청을 CloudFront URL로 전달하며 접근 제어를 CloudFront 서명된 URL로 전환한다.**
- C. S3 교차 리전 복제로 eu-central-1에 두 번째 버킷을 두고 가까운 리전으로 요청을 라우팅하며 S3 서명된 URL을 계속 사용한다(스토리지 중복 비용과 복제 지연이 추가되고, 리전 단위 라우팅만으로는 CloudFront만큼의 엣지 캐싱 효과를 얻지 못함)
- D. 웹 애플리케이션이 데이터셋을 최종 사용자에게 직접 스트리밍하도록 수정하고 애플리케이션에서 접근 제어를 구현한다(EC2를 통한 프록시 스트리밍은 오리진 대역폭 사용량과 데이터 전송 비용을 오히려 늘리고 운영 복잡도도 증가)

**정답: B**

**해설**
**Amazon CloudFront**를 S3 앞단에 배치하면 전 세계 엣지 로케이션에서 콘텐츠를 캐싱해 북미와 유럽에 흩어진 고객에게 낮은 지연 시간으로 파일을 전달할 수 있고, 반복 다운로드 시 오리진(S3)에서 나가는 데이터 전송량이 줄어 비용도 절감됩니다. 접근 제어는 **CloudFront 서명된 URL**로 전환해 기존과 동일하게 구매한 고객에게만 시간 제한된 접근 권한을 부여할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Transfer Accel­eration은 주로 클라이언트→S3 업로드 가속에 최적화되어 있어, 이 시나리오의 핵심인 전 세계 사용자에 대한 반복적인 다운로드 캐싱·비용 절감에는 CloudFront가 더 적합합니다.
- C: 리전별 복제 버킷을 유지하면 저장 비용이 두 배가 되고 복제 지연 문제가 생기며, CloudFront의 글로벌 엣지 캐싱만큼 세밀한 성능 최적화를 제공하지 못합니다.
- D: 애플리케이션 서버를 통해 파일을 스트리밍하면 모든 트래픽이 EC2와 ALB를 거치게 되어 오리진 대역폭 사용과 인프라 비용이 늘어나며 확장성도 떨어집니다.

> 💡 **시험 꿀팁**: **전 세계에 분산된 사용자에게 S3 콘텐츠를 저비용·저지연으로, 접근 제어까지 유지하며 배포**해야 한다면 **CloudFront + 서명된 URL/쿠키**가 표준 정답입니다.

## QUESTION 311

- B: SNS는 메시지를 지속 저장하지 않는 푸시 기반 서비스라 구독자(Lambda)가 실패하면 메시지가 유실될 수 있고, 유형별로 주제와 함수를 계속 추가해야 해 유지보수 부담이 커집니다.
- D: Kinesis Data Firehose와 OpenSearch 조합은 로그 분석/검색에 최적화된 파이프라인으로, 안정적인 순차 처리와 손실 방지가 필요한 트랜잭션성 견적 요청 처리에는 적합하지 않습니다.

> 💡 **시험 꿀팁**: "**메시지를 유형별로 분기**하면서 **손실 없이** 안정적으로 처리"해야 한다는 조건에는 **SNS 메시지 필터링 + 여러 SQS 대기열 구독**조합이 표준 정답입니다.

- D: 같은 리전 내 다른 가용 영역으로의 복사는 AZ 장애에는 대응할 수 있어도 리전 전체 장애 시 다른 리전에서 복구해야 한다는 요구를 충족하지 못합니다.

> 💡 **시험 꿀팁**: **EC2/EBS를 포함한 여러 리소스의 정기 백업과 크로스 리전 복사**를 운영 효율적으로 구성해야 한다면 **AWS Backup에 EC2 인스턴스를 리소스로 등록**하는 것이 표준 정답입니다.

- D: Client VPN 역시 개별 사용자 인증서/자격 증명 기반 연결이 필요해 대규모 소비자 앱에는 규모나 운영 측면에서 맞지 않습니다.

> 💡 **시험 꿀팁**: **대규모 사용자에게 승인된 콘텐츠만 안전하게 스트리밍**해야 한다면 **CloudFront + 서명된 URL/쿠키**가 표준 정답입니다.

## QUESTION 314

**문제**: 회사에는 접근 빈도가 낮은 패턴으로 글로벌 영업 팀이 사용하는 온프레미스 MySQL 데이터베이스가 있다. 영업팀은 데이터베이스 다운타임을 최소화해야 한다. 데이터베이스 관리자는 향후 사용자 증가를 예상하지만 특정 인스턴스 유형을 미리 선택하지 않고 이 데이터베이스를 AWS로 마이그레이션하려고 한다. 솔루션 설계자는 어떤 서비스를 추천해야 하는가?

- A. Amazon Aurora MySQL(고성능 프로비저닝형 관계형 DB이지만 인스턴스 클래스를 직접 선택해야 하며 자동 용량 조정 기능이 기본으로 없음)
- B. **Amazon Aurora Serverless for MySQL**

- C: Redshift Spectrum은 S3의 데이터를 Redshift SQL로 분석하는 용도로, 트랜잭션 처리용 MySQL 데이터베이스 마이그레이션과는 목적이 다릅니다.
- D: RDS for MySQL은 관리형 서비스지만 인스턴스 유형을 반드시 선택해야 하고, 트래픽이 늘어날 때 인스턴스 크기를 사람이 모니터링하고 조정해야 합니다.

> 💡 **시험 꿀팁**: "**인스턴스 유형을 미리 정하지 않고** 자동으로 늘었다 줄었다 하는 관계형 DB"가 필요하면 **Aurora Serverless**가 표준 정답입니다.

**문제**: 한 회사가 온프레미스 데이터 센터에서 여러 애플리케이션에 영향을 미치는 침해 사고를 겪었다. 공격자는 서버에서 실행 중이던 커스텀 애플리케이션의 취약점을 악용했다. 회사는 현재 이 애플리케이션을 Amazon EC2 인스턴스로 마이그레이션하는 중이며, EC2 인스턴스의 취약점을 능동적으로 스캔하고 결과를 상세히 담은 보고서를 전송하는 솔루션을 구현하려고 한다. 이 요구 사항을 충족하는 솔루션은 무엇인가?

- A. AWS Shield를 배포해 EC2 인스턴스의 취약점을 스캔하고 결과를 CloudTrail에 기록하는 Lambda 함수를 만든다(Shield는 DDoS 방어 서비스이며 소프트웨어 취약점 스캔 기능이 없음)

**해설**
**Amazon Inspector**는 EC2 인스턴스에 배포된 에이전트를 통해 소프트웨어 취약점, 의도치 않은 네트워크 노출 등을 능동적으로 스캔하고, 발견 사항을 상세히 기술한 평가 보고서를 생성합니다. Lambda 함수로 이 보고서의 생성과 배포를 자동화하면 회사가 원하는 대로 EC2 인스턴스의 취약점을 지속적으로 점검하고 결과를 관계자에게 전달하는 파이프라인을 구축할 수 있습니다.

- A: AWS Shield는 DDoS 공격으로부터 인프라를 보호하는 서비스로, 애플리케이션/OS 취약점 스캔 기능은 제공하지 않습니다.

- C: Amazon GuardDuty는 CloudTrail, VPC Flow Logs, DNS 로그 등을 분석해 이상 행위를 탐지하는 위협 탐지 서비스이며, 에이전트를 설치해 능동적으로 취약점을 스캔하는 방식이 아닙니다.

> 💡 **시험 꿀팁**: **EC2 인스턴스의 소프트웨어 취약점을 능동적으로 스캔하고 상세 보고서**를 받아야 한다면 **Amazon Inspector**가 표준 정답입니다.

- B: EventBridge로 온오프를 스케줄링하는 방식은 대기열 적체 상황에 실시간으로 반응하기 어렵고, 이를 위한 추가 모니터링/제어 로직을 직접 구축해야 합니다.
- D: Run Command는 관리자가 필요할 때 스크립트를 실행하는 운영 도구이며, SQS 메시지 발생에 따라 자동으로 스케일링되는 상시 처리 파이프라인이 아닙니다.

> 💡 **시험 꿀팁**: **SQS 메시지를 폴링·처리하는 EC2 스크립트의 비용을 줄이면서 확장성도 유지**하고 싶다면 **SQS를 트리거로 하는 Lambda 함수로 전환**하는 것이 표준 정답입니다.

> 💡 **시험 꿀팁**: **누가 무엇을 바꿨는지 추적(API 이력)**하려면 **CloudTrail**, **리소스 구성이 정책을 준수하는지 지속 감시**하려면 **AWS Config**를 함께 사용하는 것이 표준 정답 조합입니다.

**왜 다른 보기는 오답인가**
- B: STS로 일회성 SSH 키를 만드는 방식은 여전히 SSH 키 기반 접근이며, 키 배포·회수 로직을 직접 구현해야 해 관리 부담이 큽니다.
- C: 배스천 호스트에 여전히 공유 SSH 키를 사용한다면 보안팀이 지시한 "공유 키 완전 제거" 요구를 만족하지 못합니다.
- D: Cognito와 Lambda로 임시 SSH 키 발급 체계를 구축하는 것은 기술적으로 가능하지만 직접 설계·운영해야 하는 커스텀 솔루션이라 관리 오버헤드가 매우 큽니다.

> 💡 **시험 꿀팁**: **SSH 키 관리 부담 없이 EC2 인스턴스에 안전하게 접속**해야 한다면 **AWS Systems Manager Session Manager**가 표준 정답입니다.

## QUESTION 320

**문제**: 회사가 EC2 인스턴스 플릿으로 온프레미스 데이터 소스에서 데이터를 수집하고 있다. 데이터는 JSON 형식이며 수집 속도는 최대 1MB/s이다. EC2 인스턴스가 재부팅되면 처리 중이던 데이터가 손실된다. 회사의 데이터 과학 팀은 수집된 데이터를 거의 실시간으로 쿼리하려고 한다. 데이터 손실을 최소화하면서 확장 가능한 거의 실시간 쿼리를 제공하는 솔루션은 무엇인가?

**보기**
- A. **Amazon Kinesis Data Streams에 데이터를 게시하고 Kinesis Data Analytics로 데이터를 쿼리한다.**
- B. Amazon Redshift를 대상으로 하는 Amazon Kinesis Data Firehose에 데이터를 게시하고 Redshift로 쿼리한다(Firehose는 배치 버퍼링 후 전달하는 방식이라 완전한 실시간성이 떨어지고, 지속 가동되는 Redshift 클러스터 운영 부담도 있어 스트림 기반 즉시 분석에는 A가 더 적합)
- C. 수집 데이터를 EC2 인스턴스 스토어에 저장하고 S3를 대상으로 하는 Kinesis Data Firehose에 게시한 뒤 Athena로 쿼리한다(인스턴스 스토어는 인스턴스 중지/재부팅 시 데이터가 소실될 수 있어 "데이터 손실 최소화" 요구에 정면으로 위배)
- D. 수집 데이터를 EBS 볼륨에 저장하고 ElastiCache for Redis에 게시해 Redis 채널을 구독해 쿼리한다(Redis 채널 구독(Pub/Sub)은 구독 시점 이후 메시지만 전달하고 별도 영속 저장을 하지 않아 데이터 손실 위험이 있고 쿼리 모델로도 적합하지 않음)

**정답: A**

**해설**
**Amazon Kinesis Data Streams**는 데이터를 여러 가용 영역에 걸쳐 지정된 보존 기간 동안 내구성 있게 저장하므로, 프로듀서(EC2)가 재부팅되어도 스트림에 이미 게시된 데이터는 유실되지 않습니다. 여기에 **Kinesis Data Analytics**를 연결하면 SQL 기반으로 스트림 데이터를 거의 실시간으로 조회·집계할 수 있어, 데이터 손실 최소화와 실시간에 가까운 확장 가능한 쿼리라는 두 요구 사항을 함께 만족합니다.

**왜 다른 보기는 오답인가**
- B: Kinesis Data Firehose는 지정된 버퍼 크기/시간 간격으로 배치 전달하는 구조라 완전한 실시간 쿼리에는 지연이 발생하며, Redshift 클러스터도 상시 프로비저닝이 필요합니다.
- C: EC2 인스턴스 스토어는 인스턴스 재부팅/중지 시 데이터가 소실될 수 있는 임시 스토리지라, "데이터 손실 최소화"라는 핵심 요구를 직접적으로 위반합니다.
- D: Redis Pub/Sub 채널은 메시지를 영속적으로 저장하지 않는 발행-구독 모델이라, 구독자가 없거나 장애가 발생하면 메시지가 그대로 유실됩니다.

> 💡 **시험 꿀팁**: **재부팅에도 데이터를 잃지 않으면서 거의 실시간으로 쿼리**해야 한다면 **Kinesis Data Streams + Kinesis Data Analytics** 조합이 표준 정답입니다.
