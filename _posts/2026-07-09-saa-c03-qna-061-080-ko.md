## QUESTION 61

**문제**: 한 회사가 AWS에서 2계층 웹 애플리케이션을 개발하고 있다. 회사 개발자는 백엔드 Amazon RDS 데이터베이스에 직접 연결되는 Amazon EC2 인스턴스에 애플리케이션을 배포했다. 회사는 애플리케이션에 데이터베이스 자격 증명을 하드코딩해서는 안 되며, 정기적으로 데이터베이스 자격 증명을 자동으로 교체하는 솔루션을 구현해야 한다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. 인스턴스 메타데이터에 데이터베이스 자격 증명을 저장하고, Amazon EventBridge 규칙으로 RDS 자격 증명과 인스턴스 메타데이터를 동시에 갱신하는 예약된 Lambda 함수를 실행한다(자체 구축한 교체 파이프라인을 직접 운영·유지보수해야 해 운영 오버헤드가 큼).
- B. 암호화된 S3 버킷의 구성 파일에 자격 증명을 저장하고, EventBridge 규칙으로 RDS 자격 증명과 구성 파일을 동시에 갱신하는 Lambda 함수를 실행하며 S3 버전 관리로 이전 값 폴백을 보장한다(역시 직접 설계한 커스텀 교체 로직이 필요해 관리형 서비스 대비 운영 부담이 큼).
- C. **데이터베이스 자격 증명을 AWS Secrets Manager에 암호로 저장하고, 보안 암호에 대한 자동 순환을 켠 뒤 EC2 역할에 필요한 권한을 연결하여 접근 권한을 부여한다.**
- D. 데이터베이스 자격 증명을 AWS Systems Manager Parameter Store에 암호화된 파라미터로 저장하고 자동 회전을 켠 뒤 EC2 역할에 권한을 연결한다(Parameter Store는 Secrets Manager처럼 내장된 자동 순환 기능을 제공하지 않아 별도의 회전 로직을 직접 구현해야 함).

**정답: C**

**해설**
**AWS Secrets Manager**는 데이터베이스 자격 증명을 암호화된 보안 암호로 저장하고, Lambda 함수 기반의 내장 순환 기능을 통해 사람의 개입 없이 지정한 일정에 따라 자격 증명을 자동으로 교체합니다. 애플리케이션은 코드에 자격 증명을 하드코딩하는 대신 런타임에 Secrets Manager API를 호출해 최신 자격 증명을 가져오며, EC2 인스턴스 역할에 필요한 IAM 권한만 부여하면 되므로 별도의 교체 파이프라인을 직접 구축·운영할 필요가 없어 운영 오버헤드가 가장 낮습니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스 메타데이터는 자격 증명 저장소로 설계된 것이 아니며, 교체 로직 전체를 직접 만들고 유지보수해야 합니다.
- B: S3에 저장한 구성 파일 방식도 자체 구축한 동기화 로직이 필요해 관리형 자동 순환 대비 운영 부담이 큽니다.
- D: Parameter Store는 자격 증명 저장은 가능하지만 Secrets Manager와 달리 자동 순환 기능이 내장되어 있지 않아 별도의 커스텀 Lambda 순환 로직을 만들어야 합니다.

> 💡 **시험 꿀팁**: "DB 자격 증명 하드코딩 금지 + 자동 순환"이라는 조건이 나오면 **AWS Secrets Manager**가 표준 정답입니다.

## QUESTION 62

**문제**: 회사가 새로운 공개 웹 애플리케이션을 ALB(Application Load Balancer) 뒤에 배포하며, 외부 CA(인증 기관)가 발급한 SSL/TLS 인증서로 에지 암호화를 적용해야 한다. 인증서 만료 전 매년 교체가 필요하다. 솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. ACM을 사용해 SSL/TLS 인증서를 발급하고 ALB에 적용한 뒤 관리형 갱신으로 자동 교체한다(이미 외부 CA가 발급한 인증서를 사용해야 하는데 ACM에서 새로 발급받는 것은 요구 사항에 위배).
- B. ACM으로 인증서를 발급하고 키 자료를 가져와 ALB에 적용한 뒤 관리형 갱신으로 자동 교체한다(A와 마찬가지로 외부 CA 인증서 대신 ACM 발급 인증서를 사용하는 방식이라 요구 사항에 맞지 않음).
- C. ACM 사설 인증 기관을 이용해 루트 CA에서 새 SSL/TLS 인증서를 발급하고 ALB에 적용한 뒤 관리형 갱신으로 자동 교체한다(이미 신뢰할 수 있는 외부 공인 CA의 인증서가 있는데 사설 CA로 새로 발급하면 공개 웹 클라이언트가 신뢰하지 않는 인증서가 됨).
- D. **ACM을 사용해 외부 CA가 발급한 SSL/TLS 인증서를 가져와 ALB에 적용하고, EventBridge로 인증서 만료 알림을 받아 수동으로 교체한다.**

**정답: D**

**해설**
ACM은 자체 발급 인증서뿐 아니라 **외부 CA가 발급한 인증서를 가져와(import)** ALB 같은 통합 서비스에 배포하는 기능을 제공합니다. 다만 ACM의 **관리형 갱신(Managed Renewal)** 기능은 ACM이 직접 발급한 인증서에만 적용되며, 가져온(imported) 인증서는 자동 갱신 대상이 아니므로 만료 전에 **EventBridge(CloudWatch Events)**로 만료 알림을 받아 수동으로 새 인증서를 가져와 교체해야 합니다.

**왜 다른 보기는 오답인가**
- A: 외부 CA가 이미 발급한 인증서를 사용해야 하는 요구 사항과 달리 ACM에서 새 인증서를 발급받는 방식이라 부적합합니다.
- B: A와 동일한 이유로 부적합하며, ACM 발급 인증서에서 키 자료를 추출하는 절차 자체도 이 시나리오와 맞지 않습니다.
- C: ACM 사설 CA는 조직 내부용 사설 인증서를 발급하는 서비스로, 공개 웹 애플리케이션에서 일반 브라우저가 신뢰하는 공인 인증서를 대체할 수 없습니다.

> 💡 **시험 꿀팁**: 외부 CA가 발급한 인증서를 ALB에 적용해야 한다면 ACM으로 "가져오기(import)"하되, 가져온 인증서는 관리형 자동 갱신이 되지 않는다는(수동 갱신 필요) 점을 기억해야 합니다.

## QUESTION 63

**문제**: 회사가 700,000명 규모의 등록 기반을 보유한 문서 관리 애플리케이션을 운영하며, 평균 5MB인 PDF 파일을 JPG 이미지로 변환하는 제품을 만들려 한다. 원본 파일과 변환 파일을 모두 보관해야 하며, 시간이 지남에 따라 빠르게 증가할 수요를 수용할 수 있는 확장 가능한 솔루션이 필요하다. 어떤 솔루션이 이러한 요구 사항을 가장 비용 효율적으로 충족하는가?

**보기**
- A. **PDF 파일을 Amazon S3에 저장하고, S3 PUT 이벤트로 AWS Lambda 함수를 호출해 파일을 JPG로 변환한 뒤 다시 S3에 저장한다.**
- B. PDF 파일을 Amazon DynamoDB에 저장하고 DynamoDB 스트림으로 Lambda를 호출해 변환 후 다시 DynamoDB에 저장한다(DynamoDB는 아이템 크기 제한이 있어 대용량 바이너리 파일 저장소로 부적합하며 비용도 비효율적).
- C. EC2 인스턴스, EBS, Auto Scaling 그룹을 포함한 Elastic Beanstalk 애플리케이션에 PDF를 업로드하고 EC2 프로그램으로 변환한 뒤 EBS에 저장한다(항상 실행 중인 EC2 인스턴스와 EBS 비용이 발생해 서버리스 조합보다 비효율적).
- D. EC2, EFS, Auto Scaling 그룹을 포함한 Elastic Beanstalk 애플리케이션에 업로드하고 변환 후 EBS에 저장한다(C와 마찬가지로 상시 가동 인프라 비용이 들어 비용 효율성이 떨어짐).

**정답: A**

**해설**
**Amazon S3**는 대용량 파일을 저렴하게 저장할 수 있는 객체 스토리지이며, **S3 PUT 이벤트**로 **AWS Lambda**를 트리거하는 서버리스 아키텍처를 구성하면 PDF 업로드 즉시 자동으로 JPG 변환이 실행됩니다. 상시 가동되는 서버가 없어 요청량에 따라 자동으로 확장되고 유휴 시간에는 비용이 발생하지 않아, 700,000명 규모의 급증하는 수요에도 가장 비용 효율적으로 대응할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: DynamoDB는 아이템 크기 제한(최대 400KB)이 있어 평균 5MB인 PDF 파일을 직접 저장하기에 부적합합니다.
- C: EC2·EBS·Auto Scaling으로 구성된 상시 가동 인프라는 S3+Lambda 서버리스 조합보다 유휴 비용과 운영 부담이 큽니다.
- D: EFS를 사용해도 여전히 EC2 인스턴스를 상시 운영해야 하므로 C와 동일한 이유로 비효율적입니다.

> 💡 **시험 꿀팁**: "S3에 업로드되면 자동으로 파일을 변환·가공"해야 하는 요구에는 S3 이벤트 알림 + Lambda 조합이 표준 정답입니다.

## QUESTION 64

**문제**: 회사가 온프레미스에서 실행되는 Windows 파일 서버에 5TB 이상의 파일 데이터를 가지고 있으며, 사용자와 애플리케이션이 매일 데이터와 상호 작용한다. 회사는 Windows 워크로드를 AWS로 이전하는 중이며, 이 과정에서 AWS와 온프레미스 양쪽 파일 스토리지에 최소 지연 시간으로 접근할 수 있어야 한다. 운영 오버헤드를 최소화하고 기존 파일 접근 패턴을 크게 바꿀 필요가 없어야 하며, 회사는 AWS 연결에 Site-to-Site VPN을 사용한다. 솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. AWS에 FSx for Windows File Server를 배포하고 온프레미스 데이터를 그대로 옮긴 뒤 워크로드를 FSx를 사용하도록 재구성한다(온프레미스 워크로드도 여전히 저지연 접근이 필요한데 데이터를 통째로 AWS로 옮기면 온프레미스 접근 지연이 커지고 접근 패턴도 크게 바뀜).
- B. 온프레미스에 S3 파일 게이트웨이를 배포하고 데이터를 옮긴 뒤 온프레미스와 클라우드 워크로드 모두 S3 파일 게이트웨이를 사용하도록 재구성한다(S3 파일 게이트웨이는 S3를 NFS/SMB로 노출하는 용도로, Windows 고유의 파일 시스템 기능과 기존 접근 패턴을 그대로 유지하기 어려움).
- C. 온프레미스에 S3 파일 게이트웨이를 배포해 데이터를 S3로 옮기고, 워크로드 위치에 따라 S3 직접 접근 또는 S3 파일 게이트웨이를 사용하도록 재구성한다(B와 유사하게 Windows 파일 서버 고유 기능 및 기존 접근 패턴 유지에 한계가 있음).
- D. **AWS에 FSx for Windows File Server를 배포하고, 온프레미스에는 FSx 파일 게이트웨이를 배포해 온프레미스 데이터를 FSx 파일 게이트웨이로 옮긴다. 클라우드 워크로드는 FSx를, 온프레미스 워크로드는 FSx 파일 게이트웨이를 사용하도록 구성한다.**

**정답: D**

**해설**
**Amazon FSx for Windows File Server**는 완전관리형 Windows 파일 시스템을 AWS에 제공하고, **FSx File Gateway**는 온프레미스에서 이 FSx 파일 시스템에 대한 로컬 캐시 기반 접근을 제공해 자주 사용하는 데이터를 로컬에서 저지연으로 읽고 쓸 수 있게 합니다. 변경된 데이터는 백그라운드에서 FSx와 동기화되므로, 클라우드 워크로드는 FSx를 직접, 온프레미스 워크로드는 파일 게이트웨이를 통해 각각 최소 지연으로 접근할 수 있고 기존 SMB 기반 파일 접근 패턴도 그대로 유지됩니다.

**왜 다른 보기는 오답인가**
- A: 온프레미스 워크로드까지 FSx를 직접 쓰도록 재구성하면 VPN을 통한 매 요청이 원거리 왕복이 되어 저지연 요구를 충족하지 못하고 접근 패턴도 크게 바뀝니다.
- B: S3 파일 게이트웨이는 S3를 NFS/SMB로 노출하는 서비스로, Windows 고유의 파일 시스템 기능(ACL, 볼륨 섀도 복사본 등)을 요구하는 워크로드에는 적합하지 않습니다.
- C: B와 동일한 한계가 있으며, 워크로드 위치에 따라 접근 방식을 이원화해야 해 운영 복잡성도 커집니다.

> 💡 **시험 꿀팁**: "Windows 파일 서버를 AWS로 이전하면서 온프레미스에서도 저지연 접근이 필요하다"는 조건에는 FSx for Windows File Server + FSx File Gateway 조합이 표준 정답입니다.

## QUESTION 65

**문제**: 병원이 최근 Amazon API Gateway 및 AWS Lambda로 RESTful API를 배포해, PDF·JPEG 형식의 보고서를 업로드받는다. 병원은 보고서에서 보호되는 건강 정보(PHI)를 식별하도록 Lambda 코드를 수정해야 한다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. 기존 Python 라이브러리로 텍스트를 추출하고 PHI를 직접 식별한다(직접 구현한 텍스트 추출·식별 로직을 지속적으로 유지보수해야 해 운영 부담이 크고 의료 전용 개체 인식 정확도도 떨어짐).

> 💡 **시험 꿀팁**: "30일 후 접근 빈도는 줄지만 즉각적인 접근은 계속 필요"하다는 조건에는 S3 Standard-IA 전환이 표준 정답이며, 보관 기간 만료 시 정책에 명시된 삭제까지 챙겨야 합니다.

## QUESTION 67

**문제**: 회사가 여러 Amazon EC2 인스턴스에서 애플리케이션을 호스팅한다. 애플리케이션은 Amazon SQS 대기열의 메시지를 처리해 Amazon RDS 테이블에 쓰고 대기열에서 메시지를 삭제한다. RDS 테이블에서 가끔 중복 레코드가 발견되는데 SQS 대기열에는 중복 메시지가 없다. 메시지가 한 번만 처리되도록 솔루션 설계자는 무엇을 해야 하는가?

**보기**
- A. CreateQueue API 호출로 새 대기열을 만든다(기존 처리 로직의 중복 처리 원인과 무관하며 문제를 해결하지 못함).

**왜 다른 보기는 오답인가**

- B: 권한 설정은 누가 대기열에 접근할 수 있는지를 제어할 뿐 메시지 재노출 문제와는 무관합니다.
- C: ReceiveMessage의 대기 시간 설정(롱 폴링)은 빈 수신 응답을 줄이는 기능으로 가시성 제한 시간 만료로 인한 중복 수신 문제를 해결하지 못합니다.

> 💡 **시험 꿀팁**: SQS 표준 대기열에서 "처리 중 같은 메시지가 다시 수신되어 중복 처리"된다는 증상이 나오면 가시성 제한 시간(visibility timeout)을 늘리는 것이 표준 정답입니다.

**문제**: 솔루션 설계자가 회사의 온프레미스 인프라를 AWS로 확장하는 새로운 하이브리드 아키텍처를 설계하고 있다. 회사는 AWS 리전에 대해 일관되게 짧은 지연 시간과 고가용성 연결이 필요하다. 회사는 비용을 최소화해야 하며 기본 연결이 실패할 경우 더 느린 트래픽은 기꺼이 받아들인다. 솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 하는가?

- D: Direct Connect는 물리적 회선 구축이 필요한 서비스라 CLI 속성 설정만으로 백업 회선을 자동 생성할 수 없습니다.

> 💡 **시험 꿀팁**: "지연 시간은 중요하지만 비용도 최소화해야 하고, 장애 시 느린 트래픽은 감수 가능"하다는 조건에는 Direct Connect(주 회선) + Site-to-Site VPN(백업) 조합이 표준 정답입니다.

## QUESTION 69

**문제**: 회사가 ALB(Application Load Balancer) 뒤의 Amazon EC2 인스턴스에서 비즈니스 크리티컬 웹 애플리케이션을 실행하고 있으며, EC2 인스턴스는 Auto Scaling 그룹에 속해 있다. 애플리케이션은 단일 가용 영역에 배포된 Amazon Aurora PostgreSQL 데이터베이스를 사용한다. 회사는 다운타임과 데이터 손실을 최소화하면서 애플리케이션의 고가용성을 원한다. 최소한의 운영 노력으로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. EC2 인스턴스를 다른 AWS 리전에 배치하고 Route 53 상태 확인으로 트래픽을 리디렉션하며 Aurora PostgreSQL 교차 리전 복제를 사용한다(같은 리전 내 가용 영역 이중화로 충분한 상황에서 리전 단위 이중화는 과도하고 복잡성과 비용이 크게 증가).
- B. **여러 가용 영역을 사용하도록 Auto Scaling 그룹을 구성하고, 데이터베이스를 다중 AZ로 구성하며, 데이터베이스에 대한 Amazon RDS 프록시 인스턴스를 구성한다.**
- C. 하나의 가용 영역만 사용하도록 Auto Scaling 그룹을 구성하고 데이터베이스의 시간별 스냅샷을 생성해 장애 시 복구한다(단일 가용 영역 구성은 고가용성을 제공하지 못하며, 스냅샷 기반 복구는 다운타임과 데이터 손실이 커짐).
- D. 여러 리전을 사용하도록 Auto Scaling 그룹을 구성하고 애플리케이션 데이터를 S3에 쓴 뒤 S3 이벤트로 Lambda를 실행해 데이터베이스에 기록한다(불필요하게 복잡한 다중 리전 구조와 S3 경유 쓰기 경로가 추가되어 운영 부담과 지연이 커짐).

**정답: B**

**해설**
여러 가용 영역에 걸쳐 **Auto Scaling 그룹**을 구성하면 특정 AZ 장애 시에도 다른 AZ의 인스턴스가 트래픽을 계속 처리할 수 있고, **Aurora Multi-AZ** 구성은 장애 발생 시 몇 초 내에 대기 인스턴스로 자동 페일오버해 다운타임과 데이터 손실을 최소화합니다. 여기에 **Amazon RDS Proxy**를 추가하면 페일오버 시 애플리케이션 연결을 프록시가 대신 관리해 연결 재설정 지연을 줄이고 가용성을 한층 높이면서도, 모두 관리형 서비스로 제공되어 운영 노력이 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: 같은 리전 내 Multi-AZ로 충분한 고가용성을 얻을 수 있는데 굳이 다른 리전으로 인스턴스를 옮기고 교차 리전 복제까지 구성하는 것은 과도하고 운영 부담이 훨씬 큽니다.
- C: 단일 가용 영역 구성과 시간별 스냅샷 복구는 AZ 장애 시 서비스 중단과 상당한 데이터 손실 위험을 그대로 안고 갑니다.
- D: 다중 리전 Auto Scaling과 S3를 경유한 데이터베이스 쓰기는 불필요하게 복잡하고 지연이 커 요구 사항에 맞지 않습니다.

> 💡 **시험 꿀팁**: "다운타임과 데이터 손실 최소화 + 최소 운영 노력"이라는 조건에는 Multi-AZ Auto Scaling + Aurora Multi-AZ + RDS Proxy 조합이 표준 정답입니다.

## QUESTION 70

**문제**: 회사의 HTTP 애플리케이션이 NLB(Network Load Balancer) 뒤에 있고, NLB의 대상 그룹은 웹 서비스를 실행하는 여러 EC2 인스턴스로 구성된 Auto Scaling 그룹을 사용한다. 회사는 NLB가 애플리케이션에 대한 HTTP 오류를 감지하지 못한다는 것을 알게 되었고, 이런 오류는 EC2 인스턴스를 수동으로 재시작해야 한다. 회사는 사용자 정의 스크립트나 코드를 작성하지 않고 애플리케이션의 가용성을 개선해야 한다. 솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. NLB에서 HTTP 상태 확인을 활성화하고 회사 애플리케이션의 URL을 제공한다(NLB는 4계층(전송 계층) 로드 밸런서로 TCP 연결 성립 여부만 확인할 뿐, 애플리케이션 레벨의 HTTP 응답 코드 기반 상태 확인 기능을 제공하지 않음).
- B. EC2 인스턴스에 cron 작업을 추가해 1분마다 로컬 애플리케이션의 로그를 확인하고, HTTP 오류가 감지되면 애플리케이션을 재시작한다(커스텀 스크립트 작성이 필요해 요구 사항에 위배되며, 자동화 수준도 낮음).
- C. **NLB를 Application Load Balancer로 교체하고 회사 애플리케이션의 URL로 HTTP 상태 확인을 활성화하며, 비정상 인스턴스를 교체하도록 Auto Scaling 작업을 구성한다.**
- D. NLB의 UnhealthyHostCount 지표를 모니터링하는 CloudWatch 경보를 생성하고 ALARM 상태일 때 비정상 인스턴스를 교체하도록 Auto Scaling 작업을 구성한다(NLB는 애플리케이션 레벨 HTTP 오류를 인식하지 못하므로 UnhealthyHostCount 지표 자체가 HTTP 오류를 반영하지 못함).

**정답: C**

**해설**
**Application Load Balancer(ALB)**는 애플리케이션 계층(7계층)에서 동작하며, 지정한 URL 경로로 실제 HTTP 요청을 보내 응답 코드를 확인하는 **HTTP 상태 확인**을 지원합니다. 이를 Auto Scaling 그룹과 연동하면 상태 확인에 실패한 비정상 인스턴스를 자동으로 종료하고 새 인스턴스로 교체할 수 있어, 별도의 커스텀 스크립트 없이 애플리케이션 오류에 대한 가용성을 개선할 수 있습니다. 반면 NLB는 전송 계층에서 TCP 연결 성립 여부만 확인하므로 애플리케이션 자체의 HTTP 오류는 애초에 감지할 수 없습니다.

**왜 다른 보기는 오답인가**
- A: NLB는 애플리케이션 레벨의 HTTP 응답을 확인하는 상태 확인 기능을 제공하지 않으므로 URL을 지정해도 근본 문제가 해결되지 않습니다.
- B: cron 기반 로그 확인 및 재시작은 커스텀 스크립트를 작성해야 하므로 "코드 작성 없이"라는 요구 사항에 위배됩니다.
- D: UnhealthyHostCount는 NLB의 상태 확인 결과에 기반한 지표인데, NLB 자체가 HTTP 오류를 감지하지 못하므로 이 지표 역시 애플리케이션 오류를 반영하지 못합니다.

> 💡 **시험 꿀팁**: 로드 밸런서가 "애플리케이션(HTTP) 레벨 오류"를 감지해야 한다는 요구가 나오면 NLB가 아니라 ALB의 HTTP 상태 확인 + Auto Scaling 교체가 표준 정답입니다.

**문제**: 한 회사가 Amazon DynamoDB를 사용해 고객 정보를 저장하는 쇼핑 애플리케이션을 실행한다. 데이터 손상의 경우 솔루션 설계자는 15분의 RPO(복구 시점 목표)와 1시간의 RTO(복구 시간 목표)를 충족하는 솔루션을 설계해야 한다. 이러한 요구 사항을 충족하기 위해 솔루션 설계자는 무엇을 권장해야 하는가?

- A. DynamoDB 전역 테이블을 구성하고, 복구 시 애플리케이션이 다른 AWS 리전을 가리키도록 한다(전역 테이블은 변경 사항이 1초 이내에 모든 복제본 테이블로 전파되므로 잘못된 데이터(손상)까지 그대로 복제되어 데이터 손상 복구에는 적합하지 않음).

- C. DynamoDB 데이터를 매일 Amazon S3 Glacier로 내보내고, 복구 시 Glacier에서 데이터를 가져온다(일 단위 백업으로는 15분 RPO를 충족할 수 없고, Glacier의 검색 지연도 1시간 RTO에 불리).

**왜 다른 보기는 오답인가**
- A: 전역 테이블의 복제는 데이터 정합성이 아니라 지리적 분산과 지연 시간 감소가 목적이라, 손상된 데이터도 그대로 복제되어 손상 복구 수단이 되지 못합니다.
- C: 매일 한 번의 내보내기로는 최악의 경우 최대 24시간 분의 데이터 손실이 발생해 15분 RPO를 만족할 수 없고, Glacier에서의 데이터 가져오기 자체도 시간이 오래 걸립니다.
- D: DynamoDB는 EBS 볼륨을 사용하지 않는 완전관리형 서버리스 데이터베이스이므로 EBS 스냅샷이라는 개념 자체가 적용되지 않습니다.

> 💡 **시험 꿀팁**: DynamoDB에서 "짧은 RPO로 특정 시점 복구"가 필요하다는 조건이 나오면 지정 시간 복구(PITR)가 표준 정답입니다.

- C: 인터넷 게이트웨이를 통한 S3 접근은 인터넷으로 나가는 데이터 전송 요금이 그대로 부과되어 비용 절감 목적에 부합하지 않습니다.

> 💡 **시험 꿀팁**: "같은 리전의 VPC 내 EC2에서 S3로 나가는 데이터 전송 비용을 줄이고 싶다"는 조건에는 S3 VPC 게이트웨이 엔드포인트(무료, 인터넷/NAT 우회)가 표준 정답입니다.

## QUESTION 73

**문제**: 한 회사가 최근 프라이빗 서브넷의 Amazon EC2에서 Linux 기반 애플리케이션 인스턴스를 시작하고, VPC의 퍼블릭 서브넷에 있는 EC2 인스턴스에서 Linux 기반 배스천 호스트를 시작했다. 솔루션 설계자는 사내 네트워크에서 회사의 인터넷 연결을 통해 배스천 호스트 및 애플리케이션 서버에 연결해야 하며, 모든 EC2 인스턴스의 보안 그룹이 해당 액세스를 허용하는지 확인해야 한다. 솔루션 설계자는 이러한 요구 사항을 충족하기 위해 어떤 단계 조합을 취해야 하는가? (2개를 선택하세요.)

**보기**
- A. 배스천 호스트의 현재 보안 그룹을 애플리케이션 인스턴스의 인바운드 액세스만 허용하는 보안 그룹으로 교체한다(배스천 호스트는 사내 네트워크에서 오는 외부 트래픽을 받아야 하는데, 애플리케이션 인스턴스로부터의 인바운드만 허용하면 정작 필요한 외부 접속이 차단됨).
- B. 배스천 호스트의 현재 보안 그룹을 회사의 내부(사설) IP 범위에서만 인바운드 액세스를 허용하는 보안 그룹으로 교체한다(사내 네트워크에서 인터넷을 거쳐 배스천 호스트로 도달하는 트래픽의 발신지 IP는 인터넷으로 나갈 때 변환된 외부 공인 IP이지, 사내에서 쓰는 사설 IP 대역이 아니므로 이 조건으로는 접속이 차단됨).
- C. **배스천 호스트의 현재 보안 그룹을 회사의 외부 IP 범위에서만 인바운드 액세스를 허용하는 보안 그룹으로 교체한다.**
- D. **애플리케이션 인스턴스의 현재 보안 그룹을 배스천 호스트의 개인(프라이빗) IP 주소에서만 인바운드 SSH 액세스를 허용하는 보안 그룹으로 교체한다.**
- E. 애플리케이션 인스턴스의 현재 보안 그룹을 배스천 호스트의 공용(퍼블릭) IP 주소에서만 인바운드 SSH 액세스를 허용하는 보안 그룹으로 교체한다(같은 VPC 내부에서 통신할 때는 프라이빗 IP를 사용하는 것이 표준이며, 퍼블릭 IP를 기준으로 규칙을 설정하는 것은 불필요하고 VPC 내부 트래픽 처리 방식에도 맞지 않음).

**정답: C, D**

**해설**
접속 경로는 "사내 네트워크 → 인터넷 → 배스천 호스트(퍼블릭 서브넷) → 애플리케이션 인스턴스(프라이빗 서브넷)" 순서입니다. 사내 네트워크에서 인터넷을 거쳐 배스천 호스트에 도달하는 트래픽은 회사의 **외부(공인) IP 대역**에서 오는 것이므로, 배스천 호스트의 보안 그룹은 이 외부 IP 범위에서의 인바운드만 허용해야 합니다. 이후 배스천 호스트에서 애플리케이션 인스턴스로 접속할 때는 같은 VPC 내부 통신이므로 배스천 호스트의 **프라이빗 IP**가 발신지가 되며, 애플리케이션 인스턴스의 보안 그룹은 이 프라이빗 IP에서의 인바운드 SSH만 허용하도록 구성해야 합니다.

**왜 다른 보기는 오답인가**
- A: 배스천 호스트는 사내 네트워크로부터의 접속을 받아야 하는데, 애플리케이션 인스턴스로부터의 인바운드만 허용하는 규칙으로는 애초에 배스천 호스트에 접근할 수 없습니다.
- B: 사내에서 인터넷으로 나가는 트래픽은 NAT/공인 IP로 변환되므로, 배스천 호스트 입장에서 보이는 발신지 IP는 사설 IP 대역이 아니라 외부 공인 IP 대역입니다.
- E: 같은 VPC 안에서 배스천 호스트가 애플리케이션 인스턴스에 접속할 때는 프라이빗 IP를 사용하는 것이 정상 경로이며, 퍼블릭 IP 기준 규칙은 불필요합니다.

> 💡 **시험 꿀팁**: 배스천 호스트 아키텍처에서는 "배스천 호스트 = 외부(공인) IP 기준 인바운드 허용", "내부 인스턴스 = 배스천 호스트의 프라이빗 IP 기준 인바운드 허용"이라는 2단계 규칙이 표준 정답입니다.

## QUESTION 74

**문제**: 솔루션 설계자가 2계층 웹 애플리케이션을 설계하고 있다. 애플리케이션은 퍼블릭 서브넷의 Amazon EC2에서 호스팅되는 퍼블릭 웹 티어로 구성된다. 데이터베이스 계층은 프라이빗 서브넷의 Amazon EC2에서 실행되는 Microsoft SQL Server로 구성된다. 보안은 회사의 최우선 과제이다. 이 상황에서 보안 그룹을 어떻게 구성해야 하는가? (2개를 선택하세요.)

**보기**
- A. **0.0.0.0/0에서 포트 443의 인바운드 트래픽을 허용하도록 웹 계층에 대한 보안 그룹을 구성한다.**
- B. 0.0.0.0/0으로 포트 443의 아웃바운드 트래픽을 허용하도록 웹 계층에 대한 보안 그룹을 구성한다(보안 그룹은 상태 저장형(Stateful)이라 인바운드 요청에 대한 응답 트래픽은 아웃바운드 규칙 없이도 자동으로 허용되므로 별도 규칙이 불필요).
- C. **웹 계층에 대한 보안 그룹에서 오는 포트 1433의 인바운드 트래픽을 허용하도록 데이터베이스 계층에 대한 보안 그룹을 구성한다.**
- D. 데이터베이스 계층의 보안 그룹을 구성해 포트 443 및 1433의 아웃바운드 트래픽을 웹 계층의 보안 그룹으로 보낸다(B와 같은 이유로 상태 저장 특성상 응답 트래픽에 대한 아웃바운드 규칙은 불필요하며, DB가 웹 계층으로 나가는 별도 트래픽을 발생시킬 필요도 없음).
- E. 웹 계층에 대한 보안 그룹의 포트 443 및 1433에서 오는 인바운드 트래픽을 허용하도록 데이터베이스 계층에 대한 보안 그룹을 구성한다(DB 계층이 수신해야 하는 것은 SQL Server 포트인 1433뿐이며, 웹 계층이 사용하는 443 포트에서의 인바운드를 DB 계층에 허용할 이유가 없음).

**정답: A, C**

**해설**
인터넷의 사용자가 웹 애플리케이션에 접근하려면 웹 계층 보안 그룹에서 **0.0.0.0/0에서 오는 HTTPS(443) 인바운드**를 허용해야 합니다. 이후 웹 서버가 백엔드 **Microsoft SQL Server(포트 1433)**에 접근할 수 있도록, 데이터베이스 계층 보안 그룹에서는 웹 계층 보안 그룹을 소스로 지정해 포트 1433 인바운드만 허용하면 됩니다. 보안 그룹은 소스를 IP 대역이 아닌 다른 보안 그룹 ID로 지정할 수 있어, 웹 계층 인스턴스가 늘어나도 규칙을 개별 IP 단위로 관리할 필요가 없고 최소 권한 원칙도 지킬 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 보안 그룹은 상태 저장형(Stateful)이라 인바운드로 허용된 요청에 대한 응답은 아웃바운드 규칙 없이도 자동으로 나갈 수 있으므로 별도 아웃바운드 허용 규칙이 필요 없습니다.
- D: B와 같은 이유로 응답 트래픽에 대한 별도의 아웃바운드 허용이 불필요하며, DB가 먼저 웹 계층으로 나가는 트래픽을 만들 필요도 없습니다.
- E: 데이터베이스 계층이 열어야 할 포트는 SQL Server용 1433뿐이며, 웹 계층이 외부와 통신하는 443 포트를 DB 계층 인바운드에 포함시키는 것은 불필요하게 공격 표면을 넓힙니다.

> 💡 **시험 꿀팁**: 2계층 웹 아키텍처 보안 그룹 문제는 "웹 계층: 0.0.0.0/0에서 인바운드 443 허용", "DB 계층: 웹 계층 보안 그룹을 소스로 DB 포트만 인바운드 허용"이라는 최소 권한 2단 구성이 표준 정답입니다.

## QUESTION 75

**문제**: 한 회사가 애플리케이션의 성능을 개선하기 위해 다계층 애플리케이션을 온프레미스에서 AWS 클라우드로 이동하려고 한다. 애플리케이션은 RESTful 서비스를 통해 서로 통신하는 애플리케이션 계층들로 구성된다. 한 계층이 오버로드되면 트랜잭션이 삭제(유실)된다. 솔루션 설계자는 이러한 문제를 해결하고 애플리케이션을 현대화하는 솔루션을 설계해야 한다. 어떤 솔루션이 이러한 요구 사항을 충족하고 운영상 가장 효율적인가?

**보기**
- A. **Amazon API Gateway를 사용해 트랜잭션을 애플리케이션 계층인 AWS Lambda 함수로 전달하고, Amazon SQS를 애플리케이션 서비스 간 통신 계층으로 사용한다.**
- B. Amazon CloudWatch 지표로 성능 장애 시점의 서버 최대 사용률을 분석해 애플리케이션 서버의 EC2 인스턴스 크기를 늘린다(단순히 인스턴스를 확장하는 방식은 근본적인 과부하 시 트랜잭션 유실 문제를 해결하지 못하고 애플리케이션 현대화 요구도 충족하지 못함).
- C. Amazon SNS로 Auto Scaling 그룹의 EC2 애플리케이션 서버 간 메시징을 처리하고, CloudWatch로 SNS 대기열 길이를 모니터링해 확장·축소한다(SNS는 메시지를 구독자에게 즉시 푸시하는 알림 서비스로 메시지를 보관하는 대기열 개념이 없어 "대기열 길이" 모니터링 자체가 성립하지 않으며, 과부하 시 메시지가 유실될 수 있음).
- D. Amazon SQS로 Auto Scaling 그룹의 EC2 애플리케이션 서버 간 메시징을 처리하고, CloudWatch로 SQS 대기열 길이를 모니터링해 통신 오류가 감지되면 확장한다(EC2 기반 서버를 유지하는 구조라 서버리스 기반 A안보다 운영 오버헤드가 크고, 오류 발생 후 사후 대응하는 방식이라 사전 예방적이지 못함).

**정답: A**

**해설**
**Amazon API Gateway**로 RESTful 요청을 받아 **AWS Lambda** 기반 애플리케이션 계층으로 전달하면 서버 프로비저닝 없이 요청량에 따라 자동으로 확장되며, 계층 간 통신을 **Amazon SQS** 대기열로 비동기화하면 특정 계층이 일시적으로 과부하되어도 메시지가 대기열에 안전하게 쌓여 있다가 처리되므로 트랜잭션이 유실되지 않습니다. 서버리스 구성이라 인프라 관리 부담이 없어 운영 효율성도 가장 높습니다.

**왜 다른 보기는 오답인가**
- B: 단순 인스턴스 크기 조정은 일시적인 트래픽 급증에는 한계가 있고, 애플리케이션을 현대화(서버리스화)하려는 목적과도 맞지 않습니다.
- C: SNS는 발행-구독 기반 즉시 알림 서비스로 메시지를 큐에 저장하지 않아 소비자가 처리하지 못하면 메시지가 유실될 수 있으며, "대기열 길이" 모니터링이라는 개념 자체가 SNS에는 존재하지 않습니다.
- D: SQS를 메시징 계층으로 쓰는 방향은 맞지만, EC2 기반 서버를 계속 운영해야 해 완전 서버리스인 A안보다 운영 효율이 떨어집니다.

> 💡 **시험 꿀팁**: "계층 간 RESTful 통신에서 과부하 시 트랜잭션이 유실된다"는 조건에는 API Gateway + Lambda로 서버리스화하고 계층 사이를 SQS로 완충하는 구성이 표준 정답입니다.

## QUESTION 76

**문제**: 회사가 단일 공장에 있는 여러 기계에서 매일 10TB의 계측 데이터를 수신하며, 데이터는 공장 내 온프레미스 데이터 센터의 SAN(Storage Area Network)에 JSON 파일로 저장된다. 회사는 이 데이터를 Amazon S3로 전송해 중요한 실시간에 가까운 분석을 제공하는 여러 추가 시스템에서 액세스할 수 있기를 원한다. 데이터가 민감한 것으로 간주되기 때문에 안전한 전송이 중요하다. 가장 안정적인 데이터 전송을 제공하는 솔루션은 무엇인가?

**보기**
- A. 공용 인터넷을 통한 AWS DataSync(인터넷 구간을 그대로 경유하므로 전용 연결 대비 노출 위험과 지연 변동성이 크고, 매일 10TB 규모를 안정적으로 전송하기에도 대역폭이 불안정함).
- B. **AWS Direct Connect를 통한 AWS DataSync.**
- C. 공용 인터넷을 통한 AWS Database Migration Service(AWS DMS)(DMS는 관계형 데이터베이스 간 마이그레이션·복제에 특화된 서비스로 SAN의 JSON 파일을 S3로 옮기는 파일 전송 용도에 맞지 않으며, 공용 인터넷 경유라 보안성도 떨어짐).
- D. AWS Direct Connect를 통한 AWS DMS(DMS는 파일 기반 데이터를 S3로 옮기는 용도의 서비스가 아니라 데이터베이스 마이그레이션에 특화되어 있어 이 시나리오에 맞지 않음).

**정답: B**

**해설**
**AWS DataSync**는 온프레미스 스토리지와 AWS 스토리지 서비스(S3, EFS, FSx 등) 사이의 대용량 파일 데이터 이동을 자동화하며, 전송 중 자동 암호화와 무결성 검증을 내장해 민감한 데이터도 안전하게 옮길 수 있습니다. 여기에 **AWS Direct Connect**의 전용 회선을 조합하면 공용 인터넷을 거치지 않아 노출 위험이 없고, 대역폭과 지연 시간도 안정적으로 확보되어 매일 10TB 규모의 데이터를 안정적으로 전송할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 공용 인터넷 경로는 DataSync의 암호화 기능을 쓰더라도 대역폭 변동과 외부 네트워크 경유에 따른 노출 위험이 Direct Connect보다 큽니다.
- C: DMS는 관계형/NoSQL 데이터베이스 간 마이그레이션 및 지속적 복제에 특화된 서비스로, SAN에 있는 JSON 파일을 S3 객체로 옮기는 이 시나리오의 목적과 맞지 않습니다.
- D: Direct Connect를 사용하더라도 DMS 자체가 파일을 S3로 옮기는 용도의 서비스가 아니므로 적합하지 않습니다.

> 💡 **시험 꿀팁**: "온프레미스 파일 데이터를 안전하고 안정적으로 S3로 대량 전송"해야 한다는 조건에는 AWS DataSync, 특히 전용 회선인 Direct Connect와 결합한 구성이 표준 정답입니다.

## QUESTION 77

**문제**: 회사가 애플리케이션에 대한 실시간 데이터 수집 아키텍처를 구성해야 한다. 회사에는 데이터가 스트리밍될 때 이를 변환하는 API와 데이터를 위한 스토리지 솔루션이 필요하다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. EC2 인스턴스를 배포해 Amazon Kinesis 데이터 스트림으로 데이터를 전송하는 API를 직접 호스팅하고, Kinesis 데이터 스트림을 소스로 하는 Kinesis Data Firehose 전송 스트림을 만들어 Lambda로 변환한 뒤 S3로 보낸다(API를 EC2에서 직접 호스팅하면 서버 프로비저닝과 패치 등 운영 부담이 추가로 발생).
- B. EC2 인스턴스를 배포해 AWS Glue에 데이터를 전송하는 API를 호스팅하고 소스/대상 확인을 중지한 뒤 Glue로 변환해 S3로 보낸다(API를 직접 호스팅해야 해 운영 오버헤드가 크고, AWS Glue는 배치형 ETL에 최적화되어 있어 실시간 스트리밍 처리에는 적합하지 않음).
- C. **Amazon Kinesis 데이터 스트림으로 데이터를 보내도록 Amazon API Gateway API를 구성하고, Kinesis 데이터 스트림을 소스로 하는 Kinesis Data Firehose 전송 스트림을 생성해 Lambda 함수로 데이터를 변환한 뒤 Firehose 전송 스트림으로 데이터를 Amazon S3로 보낸다.**
- D. 데이터를 AWS Glue로 보내도록 API Gateway API를 구성하고 Lambda로 변환한 뒤 Glue로 S3에 보낸다(Glue는 실시간 스트리밍 수집·변환에 최적화된 서비스가 아니라 배치 ETL 작업에 적합해 실시간 요구 사항과 맞지 않음).

**정답: C**

**해설**
**Amazon API Gateway**는 서버 프로비저닝 없이 API를 완전관리형으로 제공하고, 이를 **Amazon Kinesis Data Streams**와 직접 통합하면 스트리밍 데이터를 실시간으로 수집할 수 있습니다. Kinesis Data Streams를 소스로 하는 **Kinesis Data Firehose** 전송 스트림을 구성하면 내장된 **Lambda** 변환 기능으로 스트리밍 중인 데이터를 변환하고, 그 결과를 자동으로 **Amazon S3**에 저장할 수 있어 API 호스팅부터 변환, 저장까지 전 구간이 관리형 서비스로 구성되어 운영 오버헤드가 최소화됩니다.

**왜 다른 보기는 오답인가**
- A: API를 EC2에 직접 호스팅하면 서버 운영·패치·확장 관리를 직접 해야 해 완전관리형인 API Gateway 대비 운영 부담이 큽니다.
- B: A와 마찬가지로 EC2에서 API를 직접 운영해야 하며, AWS Glue는 배치 지향 ETL 서비스라 실시간 스트리밍 변환에는 적합하지 않습니다.
- D: API Gateway로 API 자체는 관리형이지만, 데이터를 받는 대상이 AWS Glue라 실시간 스트리밍 수집에는 맞지 않고 별도 배치 처리 지연이 발생합니다.

> 💡 **시험 꿀팁**: "실시간 스트리밍 데이터를 수집·변환·저장"해야 한다는 조건에는 API Gateway + Kinesis Data Streams + Kinesis Data Firehose(Lambda 변환) + S3 조합이 표준 정답입니다.

## QUESTION 78

**문제**: 회사는 사용자 트랜잭션 데이터를 Amazon DynamoDB 테이블에 보관해야 한다. 회사는 데이터를 7년간 보관해야 한다. 이러한 요구 사항을 충족하는 가장 운영 효율성이 높은 솔루션은 무엇인가?

**보기**
- A. DynamoDB 지정 시간 복구를 사용해 테이블을 지속적으로 백업한다(PITR은 최근 35일 이내의 시점 복구만 지원해 7년 장기 보관 요구를 충족하지 못함).
- B. **AWS Backup을 사용해 테이블에 대한 백업 일정 및 보존 정책을 생성한다.**
- C. DynamoDB 콘솔을 사용해 테이블의 주문형 백업을 생성하고 백업을 Amazon S3 버킷에 저장한 뒤 S3 버킷에 대한 수명 주기 구성을 설정한다(수동으로 매번 온디맨드 백업을 생성하고 이를 S3로 옮기는 과정을 반복해야 해 자동화된 일정 관리를 제공하는 AWS Backup보다 운영 효율이 떨어짐).
- D. AWS Lambda 함수를 호출하는 Amazon EventBridge 규칙을 생성해 테이블을 백업하고 백업을 S3 버킷에 저장하도록 구성한 뒤 S3 수명 주기 구성을 설정한다(직접 만든 Lambda 백업 로직과 이벤트 규칙, S3 수명 주기까지 여러 컴포넌트를 개별적으로 구축·유지보수해야 해 운영 부담이 가장 큼).

**정답: B**

**해설**
**AWS Backup**은 DynamoDB를 포함한 여러 AWS 리소스에 대해 백업 일정과 **보존(retention) 정책**을 중앙에서 한 번에 구성하고, 온디맨드 백업을 자동으로 콜드 스토리지로 전환해 장기 보관 비용까지 절감할 수 있는 완전관리형 백업 서비스입니다. 7년이라는 장기 보관 요구도 보존 정책 하나로 설정할 수 있고, 여러 리소스의 백업 현황을 한 콘솔에서 모니터링할 수 있어 자체 구축 방식보다 운영 효율성이 가장 높습니다.

**왜 다른 보기는 오답인가**
- A: DynamoDB PITR은 최근 35일 이내 시점으로만 복원할 수 있어 7년 보관이라는 요구 사항 자체를 충족하지 못합니다.
- C: 온디맨드 백업 생성과 S3 이전, 수명 주기 설정을 수동/개별적으로 관리해야 해 자동화된 일정·보존 정책을 제공하는 AWS Backup보다 운영 부담이 큽니다.
- D: Lambda, EventBridge, S3 수명 주기까지 여러 컴포넌트를 직접 설계하고 유지보수해야 하므로 가장 많은 운영 오버헤드가 발생합니다.

> 💡 **시험 꿀팁**: "DynamoDB 데이터를 몇 년 단위로 장기 보관"해야 한다는 조건에는 AWS Backup의 백업 일정 및 보존 정책 구성이 표준 정답입니다(PITR은 35일 한도라는 점과 대비해서 기억).

## QUESTION 79

**문제**: 회사에서 데이터 저장을 위해 Amazon DynamoDB 테이블을 사용할 계획이며, 비용 최적화에 대해 우려하고 있다. 대부분의 아침에는 테이블을 사용하지 않는다. 저녁에는 읽기 및 쓰기 트래픽이 예측할 수 없는 경우가 많으며, 트래픽 급증이 발생하면 매우 빠르게 발생한다. 솔루션 아키텍트는 무엇을 추천해야 하는가?

**보기**
- A. **온디맨드 용량 모드로 DynamoDB 테이블을 생성한다.**
- B. 글로벌 보조 인덱스가 있는 DynamoDB 테이블을 생성한다(GSI는 추가적인 쿼리 패턴을 지원하기 위한 인덱스 기능일 뿐 용량 모드나 비용 최적화와는 직접적인 관련이 없음).
- C. 프로비저닝된 용량 및 Auto Scaling을 사용해 DynamoDB 테이블을 생성한다(Auto Scaling은 지표 변화에 반응해 용량을 조정하는 데 시간이 걸려, 매우 빠르게 발생하는 급격한 트래픽 급증에는 스로틀링 위험이 있고 예측 불가능한 트래픽에는 비효율적).
- D. 프로비저닝된 용량 모드로 테이블을 생성하고 전역 테이블로 구성한다(전역 테이블은 다중 리전 복제를 위한 기능으로 이 시나리오의 비용 최적화·트래픽 급증 대응 요구와는 무관하며, 프로비저닝 모드 자체도 예측 불가능한 트래픽에 부적합).

**정답: A**

**해설**
**DynamoDB 온디맨드 용량 모드**는 용량 계획 없이 실제 요청량에 따라 즉시 확장·축소되며, 사용한 읽기/쓰기 요청량만큼만 비용을 지불합니다. 아침에는 거의 사용하지 않고 저녁에 예측 불가능한 급격한 트래픽 급증이 발생하는 이 시나리오에서는 미리 용량을 프로비저닝해 둘 필요가 없는 온디맨드 모드가 유휴 시간의 낭비 비용을 없애면서도 급격한 트래픽 변화에 바로 대응할 수 있어 가장 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- B: GSI는 추가적인 액세스 패턴을 위한 보조 인덱스 기능으로, 이 문제의 핵심인 예측 불가능한 트래픽에 따른 비용 최적화와는 관련이 없습니다.
- C: Auto Scaling은 CloudWatch 경보 기반으로 용량을 조정하는 데 일정 시간이 걸리므로, 매우 빠르게 발생하는 트래픽 급증에는 스로틀링이 발생할 위험이 있습니다.
- D: 프로비저닝된 용량은 예측 가능한 트래픽에 적합하며, 전역 테이블은 다중 리전 복제 기능일 뿐 이 문제의 요구 사항(비용 최적화, 급격한 트래픽 대응)과는 무관합니다.

> 💡 **시험 꿀팁**: "트래픽 패턴이 예측 불가능하고 급증이 빠르게 발생"한다는 조건이 나오면 DynamoDB 온디맨드 용량 모드가 표준 정답입니다.

## QUESTION 80

**문제**: 한 회사는 최근 애플리케이션 마이그레이션 이니셔티브에 대한 지원을 위해 AWS 관리형 서비스 공급자(MSP) 파트너와 계약을 체결했다. 솔루션 설계자는 기존 AWS 계정의 Amazon 머신 이미지(AMI)를 MSP 파트너의 AWS 계정과 공유해야 한다. AMI는 Amazon EBS의 지원을 받으며 AWS KMS 고객 관리형 키를 사용해 EBS 볼륨 스냅샷을 암호화한다. 솔루션 설계자가 MSP 파트너의 AWS 계정과 AMI를 공유하는 가장 안전한 방법은 무엇인가?

**보기**
- A. 암호화된 AMI 및 스냅샷을 공개적으로 사용할 수 있도록 하고, MSP 파트너의 AWS 계정이 키를 사용할 수 있도록 키 정책을 수정한다(AMI를 퍼블릭으로 공개하면 의도한 파트너 계정 외 전 세계 누구나 AMI에 접근할 수 있게 되어 보안 요구에 정면으로 위배).
- B. **AMI의 launchPermission 속성을 수정해 MSP 파트너의 AWS 계정과만 AMI를 공유하고, MSP 파트너의 AWS 계정이 키를 사용할 수 있도록 키 정책을 수정한다.**
- C. AMI의 launchPermission 속성을 수정해 MSP 파트너의 AWS 계정과만 AMI를 공유하되, 암호화를 위해 MSP 파트너가 소유한 새 KMS 키를 신뢰하도록 키 정책을 수정한다(스냅샷은 이미 우리 계정의 키로 암호화되어 있어 파트너의 새 키를 신뢰할 필요가 없으며, 외부 계정 소유의 키를 신뢰하면 키 관리 권한이 뒤섞여 보안상 바람직하지 않음).
- D. 원본 계정에서 MSP 파트너의 AWS 계정에 있는 Amazon S3 버킷으로 AMI를 내보내고, MSP 파트너가 소유한 새 KMS 키로 S3 버킷을 암호화한 뒤 MSP 파트너의 AWS 계정에서 AMI를 복사하고 시작한다(불필요하게 복잡한 내보내기 절차가 추가되고, 파트너가 암호화 키를 소유하게 되어 공유 주체와 권한 관계가 역전됨).

**정답: B**

**해설**
EBS 기반 AMI를 다른 계정과 공유하려면 AMI의 **launchPermission** 속성에 대상 계정 ID를 추가해 특정 계정에게만 시작 권한을 부여해야 합니다. 스냅샷이 이미 우리 계정 소유의 **KMS 고객 관리형 키**로 암호화되어 있으므로, 새 키를 만들 필요 없이 기존 키 정책에 MSP 파트너 계정을 키 사용자로 추가해 해당 계정이 복호화 후 볼륨을 생성할 수 있도록 허용하면 됩니다. 이 방식은 AMI 공유 범위를 특정 계정으로 한정하고 암호화 키의 소유권도 그대로 우리 쪽에 유지되어 가장 안전합니다.

**왜 다른 보기는 오답인가**
- A: AMI를 퍼블릭으로 공개하면 MSP 파트너뿐 아니라 전 세계 누구나 AMI에 접근할 수 있어 "가장 안전한 방법"이라는 요구에 정면으로 반합니다.
- C: 파트너가 소유한 새 KMS 키를 신뢰하도록 설정하면 암호화 키에 대한 통제권이 파트너에게 넘어가는 셈이 되어, 원본 데이터 보안을 파트너의 키 관리 정책에 의존하게 되는 위험이 생깁니다.
- D: S3로 내보내고 파트너 소유 키로 암호화하는 절차는 단계가 불필요하게 많아지고, 결과적으로 파트너가 암호화를 통제하게 되어 공유 관계가 역전됩니다.

> 💡 **시험 꿀팁**: 고객 관리형 키로 암호화된 EBS 기반 AMI를 다른 계정과 공유할 때는 launchPermission으로 AMI를 공유하고, 기존 KMS 키 정책에 상대 계정을 키 사용자로 추가하는 방식(새 키로 바꾸지 않는 것)이 표준 정답입니다.
