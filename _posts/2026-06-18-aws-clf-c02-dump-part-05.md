## Q1. 여러 계정의 볼륨 할인 통합

AWS 계정이 여러 개인 기업이 사용량을 결합하여 볼륨 할인을 받을 수 있는 서비스는 무엇입니까?

- A. AWS 서버 마이그레이션 서비스
- B. AWS Organizations
- C. AWS 예산
- D. AWS Trusted Advisor
- E. Amazon QuickSight
- F. Amazon Forecast

**정답: B**

✅ **B. AWS Organizations**: AWS Organizations는 여러 AWS 계정을 중앙에서 관리할 수 있는 서비스입니다. 통합 결제(Consolidated Billing) 기능을 통해 모든 계정의 사용량을 합산하여 볼륨 기반 할인(계층형 요금제)을 적용받을 수 있습니다. 개별 계정보다 더 많은 사용량을 합산하므로 더 낮은 단가를 적용받게 됩니다.

❌ **A. AWS 서버 마이그레이션 서비스**: 온프레미스 서버를 AWS로 마이그레이션할 때 사용하는 서비스로, 계정 관리나 비용 할인과는 무관합니다.

❌ **C. AWS 예산**: 비용 임계값을 설정하고 초과 시 알림을 받는 서비스입니다. 볼륨 할인 기능은 제공하지 않습니다.

❌ **D. AWS Trusted Advisor**: AWS 모범 사례에 따라 비용 최적화, 보안, 성능 등을 점검해주는 서비스입니다. 여러 계정의 사용량을 통합하는 기능은 없습니다.

❌ **E. Amazon QuickSight**: 비즈니스 인텔리전스(BI) 시각화 도구로, 데이터 분석 및 대시보드 생성에 사용됩니다.

❌ **F. Amazon Forecast**: 머신러닝 기반의 수요 예측 서비스입니다.

💡 **시험 꿀팁**: AWS Organizations = 다중 계정 관리 + 통합 결제(Consolidated Billing) + 볼륨 할인. "여러 계정 통합", "볼륨 할인", "중앙 결제" 키워드가 나오면 AWS Organizations를 선택하세요!

## Q2. 온프레미스 서버에 애플리케이션 배포 (두 개 선택)

다음 중 사내에서 실행 중인 서버에 애플리케이션을 배포하는 데 사용할 수 있는 서비스는 무엇입니까? (두 개를 선택합니다.)

- A. AWS Elastic Beanstalk
- B. AWS OpsWorks
- C. AWS CodeDeploy
- D. AWS Batch
- E. AWS X-Ray

**정답: B, C**

✅ **B. AWS OpsWorks**: Chef 및 Puppet 기반의 구성 관리 서비스로, AWS 클라우드 환경뿐만 아니라 온프레미스 서버에도 애플리케이션을 배포하고 관리할 수 있습니다.

✅ **C. AWS CodeDeploy**: 애플리케이션 배포를 자동화하는 서비스로, Amazon EC2 인스턴스, Lambda 함수뿐만 아니라 온프레미스 서버에도 배포가 가능합니다.

❌ **A. AWS Elastic Beanstalk**: AWS 관리형 PaaS 서비스로, AWS 클라우드 환경(EC2, ECS 등)에만 배포 가능하며 온프레미스 서버는 지원하지 않습니다.

❌ **D. AWS Batch**: 대규모 배치 컴퓨팅 작업을 AWS 클라우드에서 실행하는 서비스입니다. 온프레미스 서버 배포와는 무관합니다.

❌ **E. AWS X-Ray**: 분산 애플리케이션의 디버깅 및 추적(Tracing)을 위한 서비스입니다. 배포 기능이 없습니다.

💡 **시험 꿀팁**: 온프레미스 서버 배포 가능 서비스 = **AWS CodeDeploy** + **AWS OpsWorks**. "온프레미스(on-premises)", "하이브리드 배포" 키워드가 나오면 이 두 서비스를 기억하세요!

## Q3. EC2 수급에 따라 조정되는 가격 모델

EC2 인스턴스의 수급에 따라 조정되는 Amazon EC2 가격 모델은 무엇입니까?

- A. 주문형 인스턴스 (On-Demand)
- B. 예약된 인스턴스 (Reserved Instances)
- C. 스폿 인스턴스 (Spot Instances)
- D. 컨버터블 예약 인스턴스 (Convertible Reserved Instances)

**정답: C**

✅ **C. 스폿 인스턴스**: AWS의 미사용 EC2 용량을 활용하는 방식으로, 수요와 공급에 따라 가격이 실시간으로 변동됩니다. 온디맨드 대비 최대 90%까지 저렴하지만, AWS가 용량을 회수할 경우 인스턴스가 중단될 수 있습니다.

❌ **A. 주문형 인스턴스**: 사용한 만큼 고정 요금(초/시간 단위)을 지불하는 방식입니다. 수요/공급과 무관하게 일정한 요금이 부과됩니다.

❌ **B. 예약된 인스턴스**: 1년 또는 3년 약정을 통해 할인된 요금을 제공합니다. 약정 기간 동안 고정된 요금이 적용됩니다.

❌ **D. 컨버터블 예약 인스턴스**: 예약 인스턴스의 한 종류로, 인스턴스 패밀리/OS/테넌시를 변경할 수 있습니다. 역시 고정된 약정 요금이 적용됩니다.

💡 **시험 꿀팁**: 스폿 인스턴스 = **수요/공급 기반 변동 요금** + 최대 90% 할인 + 언제든 중단 가능. "가격이 변동된다", "경매 방식", "수급에 따라"라는 표현이 나오면 스폿 인스턴스입니다!

## Q4. 대규모 단일 애플리케이션 재설계 원칙 (두 개 선택)

대규모 단일 애플리케이션을 재설계할 때 클라우드 아키텍처의 설계 원칙은 무엇입니까? (두 개를 선택합니다.)

- A. 수동 모니터링을 사용합니다.
- B. 고정 서버를 사용합니다.
- C. 느슨한 결합을 구현한다.
- D. 개별 부품에 의존한다.
- E. 확장성을 위한 설계.

**정답: C, E**

✅ **C. 느슨한 결합(Loose Coupling) 구현**: 마이크로서비스 아키텍처로 재설계할 때 핵심 원칙입니다. 각 컴포넌트가 독립적으로 동작하도록 하여 한 컴포넌트의 장애가 전체 시스템에 영향을 미치지 않도록 합니다. SQS, SNS 등을 활용하여 비동기 통신으로 의존성을 낮춥니다.

✅ **E. 확장성을 위한 설계(Design for Scalability)**: 트래픽 변화에 따라 자동으로 확장/축소할 수 있도록 설계하는 것은 클라우드 아키텍처의 핵심 원칙입니다. Auto Scaling, ELB 등을 활용합니다.

❌ **A. 수동 모니터링 사용**: 클라우드 모범 사례는 자동화된 모니터링(CloudWatch, CloudTrail 등)을 권장합니다. 수동 모니터링은 확장성이 없고 오류 가능성이 높습니다.

❌ **B. 고정 서버 사용**: 클라우드 설계 원칙은 탄력적(Elastic)이고 일회용(Disposable) 리소스를 권장합니다. 고정 서버는 온프레미스 사고방식입니다.

❌ **D. 개별 부품에 의존**: 단일 컴포넌트에 의존하면 단일 장애 지점(SPOF, Single Point of Failure)이 생깁니다. 클라우드 설계 원칙에 위배됩니다.

💡 **시험 꿀팁**: AWS Well-Architected Framework 5대 원칙 기억하기 - **운영 우수성, 보안, 안정성, 성능 효율성, 비용 최적화**. 모놀리식 → 마이크로서비스 재설계 시 핵심은 **느슨한 결합 + 수평 확장**!

## Q5. 1시간 이내 응답 최소 지원 계획

지원 사례에 대해 목표 응답 시간을 1시간까지 허용하는 최소 AWS 지원 계획은 무엇입니까?

- A. 기업 (Enterprise)
- B. 비즈니스 (Business)
- C. 개발자 (Developer)
- D. 기본 (Basic)

**정답: B**

✅ **B. 비즈니스(Business)**: Business 지원 계획은 프로덕션 시스템 다운 시 1시간 이내 응답을 보장합니다. 24/7 기술 지원, AWS Trusted Advisor 전체 점검, AWS Support API 접근이 포함됩니다.

❌ **A. 기업(Enterprise)**: 엔터프라이즈 계획도 1시간 이내 응답을 제공하지만, 비즈니스보다 상위 플랜입니다. "최소" 조건을 충족하는 것은 비즈니스입니다.

❌ **C. 개발자(Developer)**: 업무 시간 내 12~24시간 응답을 제공합니다. 1시간 이내 응답은 보장되지 않습니다.

❌ **D. 기본(Basic)**: 무료 지원 플랜으로 기술 지원 케이스를 열 수 없습니다. 문서와 커뮤니티 포럼만 이용 가능합니다.

💡 **시험 꿀팁**: AWS 지원 계획 응답 시간 암기 - **기본**: 없음 → **개발자**: 12~24시간(업무시간) → **비즈니스**: 1시간(프로덕션 다운) → **기업**: 15분(비즈니스 크리티컬). "1시간 = 비즈니스"를 외우세요!

## Q6. 컴플라이언스 및 인증 보고서 다운로드

AWS 컴플라이언스 및 인증 보고서는 어디에서 다운로드할 수 있습니까?

- A. AWS Artifact
- B. AWS Concierge
- C. AWS Certificate Manager
- D. AWS Trusted Advisor

**정답: A**

✅ **A. AWS Artifact**: AWS의 규정 준수 관련 문서를 제공하는 셀프서비스 포털입니다. ISO 인증, SOC 보고서, PCI DSS, HIPAA 등 다양한 컴플라이언스 보고서를 무료로 다운로드할 수 있습니다. 감사(Audit) 및 규정 준수 요구사항을 충족하는 데 활용됩니다.

❌ **B. AWS Concierge**: 엔터프라이즈 지원 플랜 고객에게 제공되는 전담 지원 서비스입니다. 컴플라이언스 문서 다운로드 기능은 없습니다.

❌ **C. AWS Certificate Manager(ACM)**: SSL/TLS 인증서를 프로비저닝, 관리, 배포하는 서비스입니다. 규정 준수 보고서와는 다릅니다.

❌ **D. AWS Trusted Advisor**: AWS 모범 사례 기반의 비용, 성능, 보안 권고 서비스입니다. 컴플라이언스 보고서를 제공하지 않습니다.

💡 **시험 꿀팁**: **AWS Artifact** = 컴플라이언스 보고서 저장소. "ISO", "SOC", "PCI DSS", "감사 보고서", "인증서 다운로드" 키워드가 나오면 무조건 Artifact! Certificate Manager(ACM)와 혼동 주의!

## Q7. 고객 워크로드의 맞춤형 서비스 상태 뷰

AWS에서 실행 중인 고객의 워크로드에 전원을 공급하는 특정 AWS 서비스의 상태에 대한 맞춤형 뷰를 제공하는 AWS 서비스는 무엇입니까?

- A. AWS 서비스 상태 대시보드 (Service Health Dashboard)
- B. AWS X-Ray
- C. AWS 개인 건강 대시보드 (Personal Health Dashboard)
- D. Amazon CloudWatch

**정답: C**

✅ **C. AWS 개인 건강 대시보드(Personal Health Dashboard)**: 고객이 실제로 사용 중인 AWS 서비스에 대한 맞춤형(Personalized) 상태 정보를 제공합니다. AWS 이벤트가 내 리소스에 미치는 영향을 알려주고, 예정된 유지보수 일정, 장애 알림 등을 제공합니다.

❌ **A. AWS 서비스 상태 대시보드**: 전체 AWS 서비스의 공개 상태를 보여주는 글로벌 뷰입니다. 특정 고객의 워크로드에 맞춘 맞춤형 뷰가 아닙니다.

❌ **B. AWS X-Ray**: 분산 애플리케이션의 요청을 추적하고 디버깅하는 서비스입니다. AWS 서비스 상태 정보를 제공하지 않습니다.

❌ **D. Amazon CloudWatch**: AWS 리소스의 지표(Metrics), 로그, 이벤트를 모니터링하는 서비스입니다. AWS 서비스 자체의 건강 상태 정보는 제공하지 않습니다.

💡 **시험 꿀팁**: **서비스 상태 대시보드** = 모든 고객 대상 공개 상태 / **개인 건강 대시보드** = 내 계정/리소스에 맞춤형 상태. "맞춤형(Personalized)", "내 리소스에 영향" 키워드 = 개인 건강 대시보드!

## Q8. AWS 통합 과금(Consolidated Billing)의 이점

다음 중 AWS 통합 과금 기능의 이점은 무엇입니까?

- A. 대량 가격 책정 자격 (Volume Pricing Qualification)
- B. 공유 액세스 권한
- C. 계정당 여러 청구서
- D. 태그 지정의 필요성

**정답: A**

✅ **A. 대량 가격 책정 자격(Volume Pricing Qualification)**: 통합 결제를 통해 여러 계정의 사용량을 합산하면 볼륨 티어 할인이 적용됩니다. 예를 들어 S3 스토리지 사용량이 개별 계정에서는 할인 임계값에 미치지 못하더라도, 통합하면 더 낮은 단가가 적용될 수 있습니다.

❌ **B. 공유 액세스 권한**: 통합 결제는 결제를 통합하는 것이지 리소스 접근 권한을 공유하는 기능이 아닙니다. 접근 권한 관리는 IAM으로 합니다.

❌ **C. 계정당 여러 청구서**: 통합 결제의 목적은 여러 계정의 청구서를 하나로 합치는 것입니다. 여러 청구서 생성은 이점이 아닌 단점입니다.

❌ **D. 태그 지정의 필요성**: 태그는 비용 할당을 위한 별도 기능입니다. 통합 결제가 태그를 필요로 하는 것은 이점이 아닙니다.

💡 **시험 꿀팁**: 통합 결제(Consolidated Billing) 3가지 이점 기억 - ① **볼륨 할인(대량 가격 책정)** ② **단일 청구서** ③ **Reserved Instance 및 Savings Plans 공유**. "볼륨 할인"이 가장 자주 출제됩니다!

## Q9. AWS 침투 테스트 수행 절차

AWS에서 침투 테스트를 수행할 때 고객이 수행해야 하는 단계는 다음 중 무엇입니까?

- A. Amazon Inspector를 사용하여 침투 테스트를 수행한 후 AWS 지원에 알립니다.
- B. 고객의 내부 보안팀에 요청하여 승인을 기다린 후 테스트를 실시한다.
- C. AWS 지원팀에 통보한 후 즉시 테스트를 수행합니다.
- D. AWS 지원 요청 및 승인 대기 후 테스트를 수행합니다.

**정답: D**

✅ **D. AWS 지원 요청 및 승인 대기 후 테스트를 수행합니다**: AWS의 침투 테스트 정책에 따르면, 고객은 자신이 소유한 AWS 리소스에 대해 침투 테스트를 수행하기 전에 AWS에 사전 승인을 요청해야 합니다. 무단으로 수행할 경우 AWS 이용 약관 위반이 될 수 있습니다.

❌ **A. Inspector 사용 후 통보**: 절차가 완전히 잘못되었습니다. 먼저 승인을 받아야 하며, Amazon Inspector는 취약점 평가 도구이지 침투 테스트 도구가 아닙니다.

❌ **B. 내부 보안팀 승인**: 내부 승인만으로는 부족합니다. AWS에도 사전 승인을 요청해야 합니다. AWS 인프라에 대한 테스트이므로 AWS의 동의가 필요합니다.

❌ **C. 통보 후 즉시 수행**: 통보만으로는 충분하지 않습니다. AWS의 명시적인 승인을 받은 후에 테스트를 진행해야 합니다.

💡 **시험 꿀팁**: 침투 테스트 순서 = **AWS에 사전 요청 → 승인 대기 → 테스트 수행**. 자신의 리소스라도 무단 테스트는 금지! Amazon Inspector는 "취약점 스캔" 도구, 침투 테스트 도구가 아님을 구분하세요.

## Q10. 미리 구성된 EC2 인스턴스 시작 기능

사용자가 미리 구성된 Amazon EC2 인스턴스를 시작할 수 있도록 지원하는 AWS 기능은 다음 중 무엇입니까?

- A. Amazon Elastic Block Store (Amazon EBS)
- B. Amazon Machine Image (AMI)
- C. Amazon EC2 Systems Manager
- D. Amazon AppStream 2.0

**정답: B**

✅ **B. Amazon Machine Image(AMI)**: AMI는 EC2 인스턴스를 시작하는 데 필요한 운영 체제, 애플리케이션 서버, 애플리케이션 등이 미리 구성된 이미지입니다. 원하는 AMI를 선택하면 동일한 구성의 인스턴스를 빠르게 시작할 수 있습니다.

❌ **A. Amazon EBS**: EC2 인스턴스에 연결하는 블록 스토리지 볼륨입니다. 인스턴스를 "시작"하는 기능이 아닙니다.

❌ **C. Amazon EC2 Systems Manager**: EC2 인스턴스의 운영 관리(패치, 명령 실행, 인벤토리 등)를 위한 서비스입니다. 미리 구성된 이미지로 인스턴스를 시작하는 기능이 아닙니다.

❌ **D. Amazon AppStream 2.0**: 데스크탑 애플리케이션을 스트리밍하는 서비스로, 일반 EC2 인스턴스 시작과는 다릅니다.

💡 **시험 꿀팁**: **AMI(Amazon Machine Image)** = EC2의 "골든 이미지" = OS + 설정 + 애플리케이션이 포함된 템플릿. "미리 구성된(pre-configured)", "템플릿", "골든 이미지" 키워드 = AMI!

## Q11. 대규모 사용자에게 공통 액세스 제어 적용

AWS 고객이 일반 액세스 제어를 대규모 사용자에게 어떻게 쉽게 적용할 수 있습니까?

- A. IAM 그룹에 IAM 정책을 적용합니다.
- B. IAM 역할에 IAM 정책을 적용합니다.
- C. 동일한 워크로드에 액세스할 수 있는 모든 IAM 사용자에게 동일한 IAM 정책을 적용합니다.
- D. IAM 정책을 Amazon Cognito 사용자 풀에 적용합니다.

**정답: A**

✅ **A. IAM 그룹에 IAM 정책을 적용합니다**: IAM 그룹은 동일한 권한이 필요한 사용자들을 묶는 논리적 단위입니다. 그룹에 정책을 한 번만 연결하면, 그룹에 속한 모든 사용자에게 자동으로 권한이 적용됩니다. 사용자가 추가/제거되어도 그룹 정책은 유지됩니다.

❌ **B. IAM 역할에 IAM 정책을 적용합니다**: IAM 역할은 임시 자격 증명을 부여하는 메커니즘으로, 주로 AWS 서비스나 외부 자격 증명 공급자가 사용합니다. 대규모 사용자 관리에는 그룹이 더 적합합니다.

❌ **C. 모든 IAM 사용자에게 동일한 정책 개별 적용**: 수동으로 각 사용자에게 정책을 적용하는 방식은 관리가 어렵고, 사용자 추가 시마다 반복 작업이 필요합니다. 비효율적이고 오류 가능성이 높습니다.

❌ **D. Amazon Cognito 사용자 풀에 적용**: Amazon Cognito는 외부 애플리케이션 사용자 인증을 위한 서비스입니다. AWS 내부 IAM 사용자 관리와는 다릅니다.

💡 **시험 꿀팁**: IAM 권한 관리 계층 기억 - **사용자(User)** < **그룹(Group)** < **역할(Role)**. "대규모 사용자", "여러 사용자에게 동일 권한" = IAM 그룹! 절대 개별 사용자에게 직접 정책 부여하지 말 것!

## Q12. 부하 변화에 따른 컴퓨팅 용량 조정 기술

부하 변화에 따라 컴퓨팅 용량을 조정할 수 있는 기술은 무엇입니까?

- A. 부하 분산 (Load Balancing)
- B. 자동 장애 조치 (Auto Failover)
- C. 라운드 로빈 (Round Robin)
- D. 자동 확장 (Auto Scaling)

**정답: D**

✅ **D. 자동 확장(Auto Scaling)**: Amazon EC2 Auto Scaling은 정의된 조건(CPU 사용률, 요청 수 등)에 따라 EC2 인스턴스 수를 자동으로 늘리거나 줄입니다. 트래픽이 증가하면 인스턴스를 추가(Scale Out)하고, 감소하면 제거(Scale In)하여 비용을 최적화합니다.

❌ **A. 부하 분산(Load Balancing)**: 들어오는 트래픽을 여러 인스턴스에 분산시키는 기술입니다. 용량 자체를 조정하지는 않습니다. ELB(Elastic Load Balancer)가 대표적입니다.

❌ **B. 자동 장애 조치(Auto Failover)**: 기본 시스템에 장애가 발생했을 때 백업 시스템으로 자동 전환하는 기술입니다. 용량 조정이 아닌 가용성 유지를 위한 기술입니다.

❌ **C. 라운드 로빈(Round Robin)**: 트래픽을 순서대로 각 서버에 분배하는 로드 밸런싱 알고리즘입니다. 용량을 조정하지 않습니다.

💡 **시험 꿀팁**: **Auto Scaling** = 수요에 따라 용량 자동 증감 (Scale Out/In). **Load Balancer** = 트래픽 분산. 두 개를 함께 사용하면 최적의 고가용성 아키텍처! "부하 변화", "용량 조정", "탄력성" = Auto Scaling!

## Q13. 글로벌 서비스로 분류되는 AWS 서비스 (두 개 선택)

지역 서비스가 아닌 글로벌 서비스로 정의되는 AWS 서비스는 무엇입니까? (두 개를 선택합니다.)

- A. Amazon Route 53
- B. Amazon EC2
- C. Amazon S3
- D. Amazon CloudFront
- E. Amazon DynamoDB

**정답: A, D**

✅ **A. Amazon Route 53**: DNS 서비스로 특정 리전에 종속되지 않는 글로벌 서비스입니다. 전 세계 엣지 로케이션에서 DNS 쿼리를 처리합니다.

✅ **D. Amazon CloudFront**: 전 세계 엣지 로케이션을 활용하는 CDN(콘텐츠 전송 네트워크) 서비스입니다. 특정 리전이 아닌 글로벌 인프라를 기반으로 동작합니다.

❌ **B. Amazon EC2**: 특정 리전 및 가용 영역(AZ)에 인스턴스를 프로비저닝하는 리전 서비스입니다.

❌ **C. Amazon S3**: 버킷은 특정 리전에 생성되지만 버킷 이름은 전역 고유(Globally Unique)해야 합니다. S3 자체는 리전 서비스로 분류됩니다.

❌ **E. Amazon DynamoDB**: 특정 리전에 테이블이 생성되는 리전 서비스입니다. (글로벌 테이블은 별도 기능이지만 서비스 자체는 리전 기반)

💡 **시험 꿀팁**: AWS 글로벌 서비스 목록 암기 - **IAM, Route 53, CloudFront, WAF(글로벌), AWS Organizations**. 나머지 대부분은 리전 서비스! "글로벌 서비스" 문제에서 Route 53과 CloudFront는 단골 정답입니다.

## Q14. 공유 책임 모델에서 고객 책임 (두 개 선택)

다음 중 공유 책임 모델에서 AWS 고객의 책임은 무엇입니까? (두 개를 선택합니다.)

- A. 미사용 애플리케이션 데이터의 암호화 확인
- B. AWS NTP 서버가 정확한 시간으로 설정되었는지 확인
- C. 사용자가 AWS 서비스 사용에 대한 보안 교육을 받았는지 확인
- D. 데이터 센터에 대한 액세스가 제한되는지 확인
- E. 하드웨어가 올바르게 처리되었는지 확인

**정답: A, C**

✅ **A. 미사용 애플리케이션 데이터의 암호화**: 데이터 암호화(미사용 데이터 및 전송 중 데이터)는 고객의 책임입니다. AWS는 암호화 도구(KMS, S3 서버 측 암호화 등)를 제공하지만, 실제 적용 여부는 고객이 결정합니다.

✅ **C. 사용자 보안 교육**: IAM 사용자 관리, 접근 권한 교육, 보안 인식 교육은 고객의 책임 영역입니다. AWS는 인프라 보안을 담당하지만 사용자 교육은 고객이 수행해야 합니다.

❌ **B. AWS NTP 서버 시간 설정**: AWS 인프라 수준의 설정으로 AWS의 책임입니다. 고객은 NTP 서버 자체를 관리하지 않습니다.

❌ **D. 데이터 센터 액세스 제한**: 물리적 보안(데이터 센터 출입 통제)은 AWS의 책임입니다. 고객은 데이터 센터에 접근할 수 없습니다.

❌ **E. 하드웨어 처리**: 서버, 네트워크 장비 등 물리적 하드웨어의 폐기 및 처리는 AWS의 책임입니다.

💡 **시험 꿀팁**: 공유 책임 모델 핵심 암기 - **AWS 책임**: 클라우드의 보안(Security OF the Cloud) = 물리적 인프라, 하드웨어, 네트워크. **고객 책임**: 클라우드에서의 보안(Security IN the Cloud) = 데이터, IAM, OS 패치, 암호화!

## Q15. 인스턴스를 수동으로 시작하는 AWS 서비스

리소스 요구 사항에 따라 인스턴스를 수동으로 시작하는 데 사용할 수 있는 AWS 서비스는 무엇입니까?

- A. Amazon EBS
- B. Amazon S3
- C. Amazon EC2
- D. Amazon ECS

**정답: C**

✅ **C. Amazon EC2(Elastic Compute Cloud)**: 가상 서버(인스턴스)를 필요에 따라 수동으로 시작하고 종료할 수 있는 컴퓨팅 서비스입니다. 인스턴스 유형, AMI, 스토리지, 네트워크 설정을 선택하여 원하는 사양의 서버를 즉시 프로비저닝할 수 있습니다.

❌ **A. Amazon EBS**: EC2에 연결하는 영구 블록 스토리지 서비스입니다. 인스턴스를 시작하는 서비스가 아닙니다.

❌ **B. Amazon S3**: 객체 스토리지 서비스로, 파일 및 데이터를 저장하는 데 사용합니다. 인스턴스(서버)를 시작하는 기능이 없습니다.

❌ **D. Amazon ECS(Elastic Container Service)**: 컨테이너 애플리케이션을 실행하고 관리하는 서비스입니다. 일반적인 가상 서버 인스턴스를 시작하는 것과는 다릅니다.

💡 **시험 꿀팁**: AWS 컴퓨팅 서비스 구분 - **EC2** = 가상 서버(VM), **ECS/EKS** = 컨테이너, **Lambda** = 서버리스. "서버 시작", "인스턴스", "가상 머신" = EC2! EBS는 스토리지, S3는 객체 저장소임을 혼동하지 마세요.

## Q16. 3년 중단 없는 워크로드의 비용 효율적인 가격 구조

한 회사가 3년 기간 동안 중단 없는 워크로드를 실행하는 애플리케이션을 마이그레이션하고 있습니다. 가장 비용 효율적인 솔루션을 제공하는 가격 구조는 무엇입니까?

- A. Amazon EC2 스폿 인스턴스
- B. Amazon EC2 전용 인스턴스
- C. Amazon EC2 온디맨드 인스턴스
- D. Amazon EC2 예약된 인스턴스

**정답: D**

✅ **D. Amazon EC2 예약된 인스턴스(Reserved Instances)**: 1년 또는 3년 약정으로 구매하면 온디맨드 대비 최대 72%까지 할인됩니다. 중단 없이 지속적으로 실행되는 워크로드(연중무휴 서버)에 가장 비용 효율적인 선택입니다.

❌ **A. 스폿 인스턴스**: 중단 없는 워크로드에는 부적합합니다. 스폿 인스턴스는 AWS가 용량이 필요할 때 언제든 중단할 수 있어 연속적인 실행을 보장할 수 없습니다.

❌ **B. 전용 인스턴스(Dedicated Instances)**: 물리적으로 격리된 하드웨어에서 실행되지만, 온디맨드보다 비용이 더 높습니다. 규정 준수 요구사항이 있을 때 사용합니다.

❌ **C. 온디맨드 인스턴스**: 약정 없이 사용한 만큼 지불하는 방식으로, 장기적으로 사용하면 예약 인스턴스보다 훨씬 비용이 높습니다.

💡 **시험 꿀팁**: 워크로드 유형별 최적 EC2 구매 옵션 - **중단 가능, 유연한 시간** = 스폿 / **예측 가능, 장기(1~3년)** = 예약 인스턴스 / **단기, 테스트** = 온디맨드 / **규정 준수, 물리 격리** = 전용. "3년", "중단 없음" = 예약 인스턴스!

## Q17. AWS 사용의 재정적 이점 (두 개 선택)

AWS를 사용함으로써 얻을 수 있는 재정적 이점은 다음과 같습니다. (두 가지를 선택하십시오.)

- A. 총소유비용(TCO) 절감
- B. 자본 지출 증가(CapEx)
- C. 운영비(OpEx) 절감
- D. 창업에 대한 지급 연기 계획
- E. 신생기업을 위한 비즈니스 크레딧 라인

**정답: A, C**

✅ **A. 총소유비용(TCO) 절감**: 온프레미스 데이터 센터 운영에는 하드웨어 구매, 유지보수, 부동산, 전기, 냉각, 인력 등 많은 비용이 포함됩니다. AWS 클라우드로 전환하면 이러한 총소유비용을 크게 절감할 수 있습니다.

✅ **C. 운영비(OpEx) 절감**: 클라우드에서는 사용한 만큼만 비용을 지불합니다. 과잉 프로비저닝 없이 필요한 리소스만 사용하므로 운영 비용을 최적화할 수 있습니다.

❌ **B. 자본 지출 증가(CapEx)**: AWS 클라우드 도입의 핵심 이점 중 하나는 CapEx(자본 지출, 서버 구매 등)를 OpEx(운영 지출, 사용 요금)로 전환하는 것입니다. CapEx가 증가하는 것은 클라우드 이점과 반대입니다.

❌ **D. 창업에 대한 지급 연기 계획**: AWS의 공식적인 재정적 이점으로 제공되는 항목이 아닙니다.

❌ **E. 신생기업을 위한 비즈니스 크레딧 라인**: AWS Activate 프로그램은 스타트업을 지원하지만, 이는 일반적인 AWS 클라우드 사용의 재정적 이점은 아닙니다.

💡 **시험 꿀팁**: AWS 6대 클라우드 이점 기억 - ① **CapEx → OpEx 전환** ② **규모의 경제** ③ **용량 추측 불필요** ④ **속도와 민첩성** ⑤ **데이터 센터 운영 비용 절감** ⑥ **글로벌 확장**. TCO 절감과 OpEx 절감은 핵심 이점!

## Q18. AWS 청구서의 가장 세부적인 데이터 도구

AWS 청구서에 대한 가장 세부적인 데이터를 볼 수 있는 AWS 비용 관리 도구는 무엇입니까?

- A. AWS 비용 탐색기 (Cost Explorer)
- B. AWS 예산 (Budgets)
- C. AWS 비용 및 사용량 보고서 (Cost and Usage Report)
- D. AWS 청구 대시보드 (Billing Dashboard)

**정답: C**

✅ **C. AWS 비용 및 사용량 보고서(Cost and Usage Report, CUR)**: AWS에서 가장 상세한 비용 데이터를 제공하는 보고서입니다. 시간별 또는 일별로 모든 AWS 서비스 사용량과 비용을 포함하며, S3에 저장하여 Athena, QuickSight 등으로 분석할 수 있습니다. 리소스 ID 수준까지 세분화된 데이터를 제공합니다.

❌ **A. AWS 비용 탐색기(Cost Explorer)**: 비용 데이터를 시각화하고 분석하는 도구입니다. 상세한 보고서보다는 트렌드 분석과 예측에 적합합니다.

❌ **B. AWS 예산(Budgets)**: 비용 임계값을 설정하고 초과 시 알림을 보내는 서비스입니다. 세부 데이터 조회보다는 예산 관리에 초점이 맞춰져 있습니다.

❌ **D. AWS 청구 대시보드**: 현재 월의 비용 요약을 보여주는 기본 대시보드입니다. 가장 세부적인 데이터가 아닌 요약 정보를 제공합니다.

💡 **시험 꿀팁**: AWS 비용 도구 비교 - **청구 대시보드** = 요약 / **Cost Explorer** = 시각화/트렌드 / **Budgets** = 알림 설정 / **CUR(비용 및 사용량 보고서)** = 가장 세부적, S3에 저장. "가장 세부적", "상세한 데이터" 키워드 = CUR!

## Q19. 새로운 RDS 클러스터 시작에 사용할 수 있는 기능 (두 개 선택)

AWS 고객이 새로운 Amazon RDS 클러스터를 시작하는 데 사용할 수 있는 기능은 다음 중 무엇입니까? (두 개를 선택합니다.)

- A. AWS Concierge
- B. AWS CloudFormation
- C. Amazon S3
- D. Amazon EC2 Auto Scaling
- E. AWS 관리 콘솔

**정답: B, E**

✅ **B. AWS CloudFormation**: 인프라를 코드(IaC)로 정의하는 서비스입니다. CloudFormation 템플릿에 RDS 클러스터 구성을 정의하면 자동으로 리소스를 프로비저닝합니다. 반복 가능하고 일관된 배포가 가능합니다.

✅ **E. AWS 관리 콘솔**: 웹 기반 GUI를 통해 RDS 클러스터를 직접 시작하고 구성할 수 있습니다. 가장 기본적이고 직관적인 방법입니다.

❌ **A. AWS Concierge**: 엔터프라이즈 지원 플랜의 계정 전담 지원 팀입니다. 직접 RDS 클러스터를 시작하는 기능이 아닙니다.

❌ **C. Amazon S3**: 객체 스토리지 서비스로 RDS 데이터베이스를 시작하는 기능이 없습니다. (RDS 스냅샷은 S3에 저장되지만, S3 자체로 RDS를 시작할 수 없습니다.)

❌ **D. Amazon EC2 Auto Scaling**: EC2 인스턴스 수를 자동 조정하는 서비스입니다. RDS 클러스터를 직접 시작하는 기능이 아닙니다.

💡 **시험 꿀팁**: AWS 리소스 프로비저닝 방법 - ① **AWS 관리 콘솔** (GUI) ② **AWS CLI** (명령줄) ③ **AWS SDK** (프로그래밍) ④ **CloudFormation** (IaC). "리소스 생성/시작" 방법을 묻는 문제에서 콘솔과 CloudFormation은 자주 등장하는 정답입니다!

## Q20. AWS 클라우드 아키텍처 설계 원칙

다음 중 AWS 클라우드 아키텍처 설계 원칙은 무엇입니까?

- A. 단일 장애 지점 구현
- B. 느슨한 결합 구현
- C. 단일 설계 구현
- D. 수직 확장 구현

**정답: B**

✅ **B. 느슨한 결합(Loose Coupling) 구현**: AWS Well-Architected Framework의 핵심 설계 원칙입니다. 컴포넌트 간 의존성을 최소화하여 한 부분의 변경이나 장애가 다른 부분에 영향을 주지 않도록 설계합니다. SQS 큐, SNS 토픽 등을 통해 비동기 통신을 구현합니다.

❌ **A. 단일 장애 지점 구현**: 클라우드 설계의 반대 원칙입니다. AWS는 단일 장애 지점(SPOF)을 제거하고 다중 AZ, 다중 리전 배포를 통해 고가용성을 확보할 것을 권장합니다.

❌ **C. 단일 설계 구현**: 모놀리식 단일 설계는 클라우드 설계 원칙에 위배됩니다. 마이크로서비스, 분산 아키텍처가 권장됩니다.

❌ **D. 수직 확장 구현**: 수직 확장(Scale Up, 더 큰 서버로 교체)보다 수평 확장(Scale Out, 서버 수 증가)이 클라우드 모범 사례입니다. 수직 확장에는 한계가 있고 중단 시간이 필요합니다.

💡 **시험 꿀팁**: AWS 클라우드 설계 원칙 핵심 키워드 - **느슨한 결합**, **수평 확장(Scale Out)**, **자동화**, **장애 대비 설계(Design for Failure)**, **탄력성**. "수직 확장"은 틀린 답, "수평 확장"이 올바른 클라우드 원칙입니다!
