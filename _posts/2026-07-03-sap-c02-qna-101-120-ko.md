## QUESTION 101

**문제**: 다중 계정 환경에서 영업 계정의 S3 버킷(페타바이트 규모, KMS 암호화)에 저장된 데이터를, 마케팅 계정의 QuickSight(이미 전용 IAM 서비스 역할 보유)가 접근해야 합니다. 최소 운영 오버헤드로 계정 간 보안 접근을 제공하려면?

> ⚠️ 원본 PDF에서 이 문제의 보기 A/B/C 텍스트 경계가 스캔 과정에서 서로 섞여 정확히 복원하지 못했습니다. 아래는 복원 가능한 범위 내에서 정리한 내용이며, 핵심은 정답 D의 논리에 있습니다.

**보기(요약)**
- A. 마케팅 계정에 새 S3 버킷 생성 + 영업 계정에서 S3 복제 규칙으로 객체 복사 + QuickSight 권한 업데이트
- B. S3 버킷 접근 권한을 마케팅 계정에 "부여하는" SCP 생성
- C. AWS RAM으로 영업 계정의 KMS 키를 마케팅 계정과 공유 + 버킷 정책 업데이트 + KMS 권한 부여(grant)로 복호화 허용 + QuickSight 권한 업데이트
- D. **영업 계정에 IAM 역할을 생성해 S3 버킷 접근 권한을 부여. 마케팅 계정이 그 역할을 수임(assume)해 S3 버킷에 접근. QuickSight 역할이 영업 계정의 새 IAM 역할과 신뢰 관계를 맺도록 업데이트.**

**정답: D**

**해설**
표준적인 **교차 계정 역할 수임(cross-account role assumption)** 패턴입니다. 리소스를 소유한 영업 계정에 필요한 권한을 가진 IAM 역할을 만들고, 마케팅 계정의 QuickSight 역할이 이를 **수임(Assume Role)**하도록 신뢰 관계를 설정합니다. 데이터를 복제하지 않고도(원본 그대로) 안전하게 접근할 수 있는 가장 표준적이고 운영 부담이 적은 방식입니다.

**왜 다른 보기는 오답인가**
- A: S3 복제로 데이터를 마케팅 계정에 **복사**하는 것은 페타바이트 규모에서 동기화 지연·이중 저장 비용이 발생하며, "접근 권한 부여"가 아니라 데이터 자체를 중복시키는 방식이라 목적에 맞지 않습니다.
- B: **SCP는 권한을 부여하는 기능이 아니라 상한선(제한)만 설정**합니다. "SCP로 접근 권한을 부여한다"는 개념 자체가 성립하지 않습니다.
- C: RAM으로 KMS 키를 공유하고 버킷 정책·KMS 권한 부여까지 별도로 관리하는 방식은 기술적으로는 가능할 수 있으나, 여러 리소스(키 공유, 버킷 정책, KMS grant)를 개별 관리해야 해 단일 IAM 역할 수임(D)보다 운영 복잡도가 높습니다.

> 💡 **시험 꿀팁**: 다른 계정의 암호화된 S3 데이터에 안전하게 접근해야 한다면, 데이터를 복제하거나 SCP로 "권한을 주려" 하지 말고 **리소스 소유 계정에 역할을 만들어 상대 계정이 수임(Assume Role)하게** 하는 것이 표준 패턴입니다. SCP는 절대 권한을 부여하지 못한다는 점(57, 32번 참고)을 기억하세요.

## QUESTION 102

**문제**: 온프레미스 Microsoft SQL Server Always On 클러스터를 AWS 관리형 데이터베이스 서비스(다른 엔진, 예: MySQL)로 **이기종(heterogeneous) 마이그레이션**하려 합니다.

**보기**
- A. 백업 및 복원 유틸리티로 SQL Server를 MySQL용 RDS로 마이그레이션
- B. Snowball Edge로 S3에 전송 + SQL Server의 "BULK INSERT" S3 통합 기능으로 RDS MySQL에 로드
- C. **AWS Schema Conversion Tool(SCT)로 스키마를 MySQL용 RDS로 변환한 뒤, AWS DMS로 데이터 마이그레이션**
- D. DataSync로 S3에 전송 + SQL Server의 S3 통합 기능으로 RDS MySQL에 로드

**정답: C**

**해설**
서로 다른 데이터베이스 엔진 간의 **이기종 마이그레이션**에는 항상 **AWS Schema Conversion Tool(스키마 변환)** + **AWS DMS(실제 데이터 이전)** 조합을 사용합니다.

**왜 다른 보기는 오답인가**
- A: 백업/복원 유틸리티는 **동종(homogeneous)** 마이그레이션(SQL Server → SQL Server)에만 통합니다. 다른 엔진(MySQL)으로는 백업 파일 형식 자체가 호환되지 않습니다.
- B, D: "BULK INSERT와 SQL Server의 S3 통합" 기능은 **SQL Server 전용** 기능이며, RDS for MySQL에는 이런 기능이 존재하지 않습니다. 존재하지 않는 기능 조합을 전제로 한 오답입니다.

> 💡 **시험 꿀팁**: 서로 **다른 데이터베이스 엔진 간(이기종) 마이그레이션**에는 항상 **SCT(스키마 변환) + DMS(데이터 이전)** 조합을 떠올리세요. 백업/복원이나 엔진 고유 기능은 동일 엔진 간 마이그레이션에만 유효합니다.

## QUESTION 103

**문제**: 출판사 디자인 팀(개발 계정)이 정적 자산을 테스트한 뒤 프로덕션 계정의 S3 버킷에 업로드해야 합니다. 웹 앱의 다른 부분은 위험에 노출되지 않아야 합니다. (3가지 선택)

**보기**
- A. **프로덕션 계정에서 S3 버킷에 대한 읽기·쓰기 IAM 정책 생성**
- B. 개발 계정에서 S3 버킷에 대한 IAM 정책 생성
- C. **프로덕션 계정에 역할 생성, 새 정책 연결, 개발 계정을 신뢰할 수 있는 엔터티로 정의**
- D. 개발 계정에 역할 생성, 프로덕션 계정을 신뢰할 수 있는 엔터티로 정의
- E. **개발 계정에 디자인 팀 IAM 그룹 생성, 프로덕션 계정의 역할에 대한 `sts:AssumeRole`을 허용하는 정책 연결**
- F. 개발 계정에 디자인 팀 그룹 생성, 개발 계정 자체의 역할에 대한 `sts:AssumeRole` 허용

**정답: A, C, E**

**해설**
리소스(S3 버킷)를 소유한 **프로덕션 계정**에 좁은 범위의(해당 버킷만 대상으로 한) 정책(A)과, 개발 계정을 신뢰하는 역할(C)을 만들고, **개발 계정**의 디자인 팀 그룹에는 그 역할을 수임할 수 있는 권한(E)만 부여합니다. 이렇게 하면 디자인 팀은 딱 그 S3 버킷에만 접근할 수 있고, 프로덕션의 다른 리소스는 노출되지 않습니다.

**왜 다른 보기는 오답인가**
- B: 개발 계정에서 프로덕션 리소스에 대한 정책을 만드는 것은 이 방식의 정상적인 흐름이 아닙니다.
- D: 신뢰 관계 방향이 반대입니다. 역할은 **리소스를 소유한 프로덕션 계정**에 있어야 하고, 그 역할이 개발 계정을 신뢰해야 합니다.
- F: 개발 계정 **자체의** 역할을 수임하는 것은 계정 경계를 넘지 못해 프로덕션 접근과 무관합니다.

> 💡 **시험 꿀팁**: 교차 계정 접근의 표준 패턴은 **① 리소스를 소유한 계정에 좁은 범위의 정책+역할(상대 계정을 신뢰) 생성, ② 요청하는 계정에서는 그 역할에 대한 `sts:AssumeRole` 권한만 부여**입니다. 신뢰 방향을 반대로 두면 작동하지 않습니다.

## QUESTION 104

**문제**: Elastic Beanstalk 파일럿 앱을 비용 절감을 위해 **단일 인스턴스 환경**으로 개발 중이며, CPU 사용률이 자주 85%를 넘어 병목이 생깁니다. 프로덕션 출시 전 최소 운영 오버헤드로 완화하려면?

**보기**
- A. 새 Elastic Beanstalk 애플리케이션 생성 + 부하 분산 환경 유형 선택
- B. 두 번째 환경 생성 + 트래픽 분할 배포 정책
- C. **기존 환경의 용량 구성을 부하 분산 환경 유형으로 수정**, 모든 AZ 선택, CPU 85% 초과 시 확장 규칙 추가
- D. "환경 재구축" 작업으로 부하 분산 옵션 선택

**정답: C**

**해설**
Elastic Beanstalk는 **기존 환경의 용량 구성을 그 자리에서 수정**해 단일 인스턴스 → 부하 분산(Auto Scaling) 유형으로 전환할 수 있습니다. 새 애플리케이션이나 새 환경을 만들 필요 없이 가장 적은 운영 부담으로 전환 가능합니다.

**왜 다른 보기는 오답인가**
- A: 완전히 새로운 애플리케이션을 만드는 것은 기존 환경을 그냥 수정하는 것보다 불필요한 중복입니다.
- B: 트래픽 분할 배포 정책은 **새 애플리케이션 버전 테스트용** 기능이지, 용량/확장 문제 해결용이 아닙니다.
- D: "환경 재구축"은 환경을 처음부터 다시 만드는 더 파괴적인 작업으로, 단순 설정 변경보다 과합니다.

> 💡 **시험 꿀팁**: Elastic Beanstalk 환경을 단일 인스턴스에서 부하 분산형으로 바꾸려면 **기존 환경의 용량 구성을 직접 수정**하세요. 새 애플리케이션/환경 생성이나 재구축은 불필요합니다.

## QUESTION 105

**문제**: 금융 회사가 자체 관리 MySQL(과도한 I/O)을 쓰는 앱을 EC2(ELB+ASG)에서 운영합니다. 평소엔 잘 작동하지만 **매달 말 3일간**(월말 보고) 느려집니다. 데이터베이스 성능 영향을 최소화하며 월말 부하를 처리하려면?

**보기**
- A. 더 큰 인스턴스 + 모든 EBS를 GP2로 변경
- B. **데이터베이스를 Amazon RDS로 일회성 마이그레이션하고, 월말 부하 처리를 위한 추가 읽기 전용 복제본을 생성**
- C. CloudWatch+Lambda로 EBS 볼륨 유형·크기·IOPS를 동적으로 변경
- D. 월말 전 스냅샷 생성 → 최대 PIOPS 볼륨으로 교체 → 이후 되돌리기

**정답: B**

**해설**
근본 문제는 자체 관리 MySQL 하나가 쓰기와 무거운 보고성 읽기를 동시에 처리해야 한다는 점입니다. **관리형 RDS로 옮기고 읽기 전용 복제본을 추가**하면, 월말 보고성 쿼리를 복제본으로 분산시켜 프라이머리(쓰기)의 성능에 영향을 주지 않으면서 부하를 처리할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스·볼륨을 키우는 것은 근본적인 "쓰기+보고 동시 처리" 구조 문제를 해결하지 못하는 미봉책입니다.
- C: EBS 유형·크기를 동적으로 바꾸는 커스텀 자동화는 복잡하고, 근본 원인(단일 DB의 이중 역할)을 해결하지 못합니다.
- D: 매달 스냅샷/볼륨 교체를 수동으로 반복하는 것은 매우 번거롭고 위험한 운영 프로세스입니다.

> 💡 **시험 꿀팁**: 자체 관리 DB가 **주기적으로 예측 가능한 보고성 부하**(월말 등)에 시달린다면, **관리형 서비스로 마이그레이션 + 읽기 전용 복제본 추가**로 보고 쿼리를 분리하는 것이 표준 해법입니다.

## QUESTION 106

**문제**: 복잡한 종속성이 있는 안정적인 Java 앱이 온프레미스 VM에서 실행 중입니다. 기술 스택을 현대화하며 AWS로 마이그레이션하되 **서버 관리 오버헤드**와 **코드 변경**을 모두 최소화하려면?

**보기**
- A. **AWS App2Container로 AWS Fargate의 Amazon ECS로 마이그레이션**, ECR에 이미지 저장, ECS 작업 실행 역할에 ECR 접근 권한 부여, ALB로 상호작용
- B. Lambda에서 실행되는 컨테이너로 코드 마이그레이션 + API Gateway
- C. App2Container로 **EKS 관리형 노드 그룹**으로 마이그레이션
- D. Lambda 컨테이너 + ALB

**정답: A**

**해설**
**AWS App2Container**는 기존 VM에서 실행 중인 복잡한 Java(또는 .NET) 앱을 **최소한의 코드 변경**으로 자동 컨테이너화해주는 전용 도구입니다. 여기에 **Fargate**(서버/클러스터 관리가 필요 없는 완전관리형 컨테이너)를 결합하면 "서버 관리 오버헤드 최소화"까지 동시에 만족합니다.

**왜 다른 보기는 오답인가**
- B, D: 앱 코드를 Lambda의 실행 모델(콜드 스타트, 상태 비저장 호출 등)에 맞게 옮기는 것은 App2Container보다 훨씬 큰 변경을 요구합니다.
- C: App2Container는 맞지만, **EKS 관리형 노드 그룹**은 여전히 EC2 인스턴스(노드) 자체를 관리해야 해 Fargate(A)보다 서버 관리 부담이 큽니다.

> 💡 **시험 꿀팁**: 기존 복잡한 VM 기반 앱을 **최소 코드 변경**으로 컨테이너화하려면 **AWS App2Container**를 먼저 떠올리고, **서버 관리까지 최소화**하려면 EKS(관리형 노드 그룹, 여전히 EC2 관리 필요)가 아니라 **Fargate**와 결합하세요.

## QUESTION 107

**문제**: 비동기 HTTP 앱이 us-east-1에서 Lambda + 퍼블릭 API Gateway로 운영됩니다. 다른 리전으로의 장애 조치를 지원하도록 재설계하려면?

**보기**
- A. us-west-2에 API Gateway만 새로 만들고 트래픽을 여전히 us-east-1의 Lambda로 전달 + Route 53 장애 조치
- B. API Gateway와 Lambda 사이에 SQS 추가
- C. us-west-2에 Lambda 배포 + API Gateway 생성, Global Accelerator + ALB로 두 엔드포인트 관리

**문제**: 유럽 온프레미스 데이터센터 + eu-west-1/us-east-1 두 리전 AWS. 온프레미스에서 **두 리전 중 아무 곳의 VPC로든** 라우팅 가능해야 하고, **두 리전의 VPC 간 직접 라우팅**도 지원해야 하며, **단일 장애점이 없어야** 합니다. 이미 2개의 1Gbps Direct Connect 연결(서로 다른 DX 위치 DX-A, DX-B)이 있습니다. 각 리전에는 해당 리전의 모든 VPC를 라우팅하는 단일 Transit Gateway가 있습니다.

**보기**
- A. DX-A/DX-B에서 **프라이빗 VIF**로 하나의 Direct Connect Gateway에 연결, 양쪽 리전 TGW를 DXGW와 연결, TGW끼리 피어링
- B. DX-A에서 전송 VIF로 DXGW1 생성(eu-west-1 TGW 연결), DX-B에서 별도 전송 VIF로 DXGW2 생성(us-east-1 TGW 연결), **두 DXGW끼리 피어링**
- C. DX-A/DX-B 모두 전송 VIF로 하나의 DXGW에 연결, 양쪽 TGW 연결, **DXGW가 TGW 간 트래픽을 라우팅하도록 구성**

- C: DXGW와 양쪽 TGW 연결까지는 맞지만, **"DXGW가 TGW 간 트래픽을 라우팅하도록 구성"한다는 것은 실제로 작동하지 않습니다.** DXGW는 온프레미스-리전 연결만 담당하며, 리전 간(TGW 간) 직접 라우팅에는 반드시 **TGW 피어링**이 별도로 필요합니다.

**정답: B**

**해설**
업무 시간 외에만 필요 없는 개발·테스트 리소스에는 **저녁에 중지, 아침에 시작**하는 간단한 스케줄 자동화가 표준입니다. **두 개의 별도 EventBridge 규칙**(저녁-중지, 아침-시작)과 각각 간단한 태그 기반 Lambda 함수로 구성하는 것이 가장 단순합니다(프로덕션은 별도 태그이므로 이 스케줄 대상에서 제외됨).

**왜 다른 보기는 오답인가**
- A: 하나의 함수에 요일·시간 조건 로직을 모두 넣어 시작/중지를 판단하게 하는 것은 B의 "역할별로 나뉜 두 개의 단순한 규칙"보다 더 복잡한 단일 로직입니다.
- C, D: "마지막 백업에서 복원"하는 것은 단순히 중지된 인스턴스를 **시작**하는 것보다 훨씬 느리고 무거운 작업이며, 매시간 실행도 하루 두 번(아침/저녁)이면 충분한 이 시나리오에는 불필요합니다.

> 💡 **시험 꿀팁**: 업무 시간에만 필요한 개발·테스트 리소스 비용 절감에는 **저녁-중지 / 아침-시작, 각각 별도의 EventBridge 규칙 + 단순 태그 기반 Lambda** 조합이 표준입니다. 하나의 함수에 복잡한 조건 로직을 넣거나 "백업에서 복원" 같은 무거운 작업을 쓰지 마세요.

## QUESTION 120

**문제**: SaaS 회사가 여러 리전, 동일 프로덕션 계정에 API Gateway REST API + Lambda 통합을 배포했습니다. 계층형 가격제: 프리미엄 고객은 초당 최대 3,000회 호출(API 키로 식별). 여러 리전의 여러 프리미엄 고객이 피크 시간에 여러 API 메서드에서 **429 오류**를 받습니다. 로그를 보니 **Lambda는 호출되지 않았습니다.** 원인은?

**보기**
- A. Lambda 함수의 동시성 제한 도달
- B. Lambda의 리전별 동시성 제한 기능
- C. **API Gateway 계정 수준의 초당 호출 한도 도달**
- D. API Gateway의 메서드별 기본 초당 호출 제한 도달

**정답: C**

**해설**
Lambda가 **아예 호출되지 않았다**는 점이 핵심 단서입니다. Lambda 동시성 문제였다면 호출 시도 자체는 로그에 남았을 것입니다. API Gateway에는 계정(리전) 단위의 전체 초당 호출 한도가 있으며, 이는 **개별 고객의 사용량 계획(usage plan) 한도와는 별개**입니다. 여러 프리미엄 고객이 동시에, 각자는 자신의 3,000회/초 한도 내에 있음에도 영향을 받았다는 것은, 그 계정(리전)의 **누적 트래픽이 계정 수준 한도를 초과**했다는 신호입니다.

**왜 다른 보기는 오답인가**
- A, B: Lambda 동시성 문제라면 Lambda **호출 시도** 자체는 발생했어야 합니다. "Lambda가 호출되지 않았다"는 로그와 모순됩니다.
- D: "메서드별 기본 제한"은 API Gateway의 계층 중 더 좁은 단위이며, 여러 고객·여러 메서드·여러 리전에 걸쳐 동시다발적으로 발생한 증상은 더 상위의 **계정 수준** 한도 소진에 더 부합합니다.

> 💡 **시험 꿀팁**: API Gateway의 조절(throttling)은 **① 계정 수준(리전 전체 합산) → ② 스테이지 수준 → ③ 사용량 계획(API 키별)** 세 계층으로 나뉩니다. 여러 고객이 동시에 429를 받고 **Lambda가 아예 호출되지 않았다**면, 개별 고객의 사용량 계획이 아니라 **계정 수준 한도**를 의심하세요.
