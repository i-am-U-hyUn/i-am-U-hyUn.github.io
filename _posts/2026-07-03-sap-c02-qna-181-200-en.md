## QUESTION 181

**Question**: Organizations multi-account setup, 3 OUs (100+ accounts each), each account has a single VPC (same Region, non-overlapping CIDRs). VPCs **within the same OU** must be able to communicate, but not across OUs. Minimal operational overhead?

**Choices**
- A. CloudFormation StackSets to set up VPC peering between accounts in each OU (managing N:N peering across so many accounts is extremely complex).
- B. Create a dedicated networking account per OU + share the VPC via AWS RAM + peer the networking account with every other account in the OU (managing 100+ peering connections to one hub is more complex than the alternative).
- C. **Provision a transit gateway in an account per OU. Share the transit gateway organization-wide via AWS RAM. Create a transit gateway VPC attachment for each VPC.**
- D. Dedicated networking account + VPN connections + third-party routing software (very heavy management burden).

**Correct Answer: C**

**Explanation**
**Transit Gateway + AWS RAM** is the standard way to simplify many-to-many VPC connectivity in a managed fashion at scale (100+ accounts per OU). Creating a transit gateway per OU and controlling routing tables lets you enforce "communication only within the same OU," meeting the requirement with minimal overhead.

**Why the other choices are wrong**
- A: VPC peering is not transitive, so connecting 100+ accounts fully would require an impractically large number of individual peering connections.
- B, D: Hub-account-based peering/VPN is far more complex to manage than Transit Gateway's native routing.

> 💡 **Exam tip**: To simplify communication between **hundreds of accounts/VPCs** in a managed way, **Transit Gateway + AWS RAM sharing** is the standard answer — VPC peering is non-transitive and unsuitable at this scale.

## QUESTION 182

**Question**: During application migration, the company wants to use fully managed services as much as possible. Requirements for storing large critical documents: 1) high durability/availability, 2) always encrypted at rest and in transit, 3) **encryption keys managed and periodically rotated by the company.**

**Choices**
- A. Storage Gateway in File Gateway mode + EBS volume encryption via KMS (File Gateway is S3-backed, but describing "EBS volume encryption" is conceptually mismatched).
- B. **Use Amazon S3 with a bucket policy enforcing HTTPS for connections, and server-side encryption with AWS KMS for object encryption.**
- C. DynamoDB + SSL connection + KMS encryption of stored objects (S3 better suits storing large "documents" than DynamoDB).
- D. Deploy an instance with an attached EBS volume + EBS volume encryption via KMS (requires EC2/EBS provisioning/management, less aligned with "fully managed").

**Correct Answer: B**

**Explanation**
**Amazon S3** is a fully managed, highly durable (11 9's) service optimized for storing large objects. Enforcing HTTPS via a bucket policy condition (`aws:SecureTransport`) covers in-transit encryption, while **SSE-KMS** (customer-managed keys, supporting automatic/manual rotation) covers at-rest encryption and the company's key management/rotation requirement.

**Why the other choices are wrong**
- A: Storage Gateway suits hybrid on-premises access needs — for a purely cloud, fully managed scenario like this, using S3 directly is more appropriate.
- C: DynamoDB is a key-value/document database; S3 is more natural for storing "large critical documents" (files).
- D: EC2+EBS requires instance provisioning/management, conflicting with the goal of "using fully managed services as much as possible."

> 💡 **Exam tip**: For large documents needing **fully managed** storage encrypted with **keys the company manages/rotates itself**, the standard answer is **S3 + SSE-KMS (customer-managed key) + a bucket policy enforcing HTTPS.**

## QUESTION 183

**Question**: A public API runs as ECS tasks (Fargate, behind an ALB, CPU-based auto scaling). Recently, numerous SQL injection attacks degraded performance and made the app unavailable (scaled to maximum). Implement a solution to block SQL injection attacks while allowing legitimate traffic and maximizing operational efficiency.

**Choices**
- A. Create a new WAF web ACL just monitoring HTTP/HTTPS requests to the ALB (no blocking rule — no actual defense).
- B. Create a new AWS WAF Bot Control implementation (for managing bot traffic, doesn't specifically target SQL injection).
- C. **Create a new AWS WAF web ACL. Add a rule blocking requests matching the SQL database managed rule group. Allow all other traffic not matching that rule. Attach the web ACL to the ALB in front of the ECS tasks.**
- D. Empty IP set + Lambda scraping logs to manually add attacking IPs (reactive and slow, and new attacking IPs each cause a delay).

**Correct Answer: C**

**Explanation**
AWS WAF has a pre-built **SQL database (SQLi) managed rule group** — adding it to a web ACL and allowing all other traffic immediately and automatically blocks SQL injection patterns while letting legitimate traffic pass. Being a managed rule, operational overhead is minimal.

**Why the other choices are wrong**
- A: Monitoring alone doesn't actually block attacks.
- B: Bot Control manages automated bot traffic — a different purpose than defending against SQL injection.
- D: Blocking IPs one-by-one after analyzing logs post-attack is slow, and defeated if the attacker keeps changing IPs.

> 💡 **Exam tip**: To block **SQL injection attacks**, use AWS WAF's **SQL database managed rule group** — the immediate, low-operational-overhead standard answer.

## QUESTION 184

**Question**: IoT Core collects air quality sensor data, stored in DynamoDB. For business continuity, data collection/storage must work across **two Regions.**

**Choices**
- A. Route 53 alias failover (using IoT Core data endpoint values) + migrate data to "Aurora global tables" (Aurora is relational — a conceptual error; "global tables" is DynamoDB terminology).
- B. IoT Core domain configuration per Region + Route 53 latency-based routing + migrate to MemoryDB (latency-based routing assumes both sides active — may be mismatched if continuous dual-Region ingestion is needed, and migrating to MemoryDB is unnecessary).
- C. **Create an IoT Core domain configuration in each Region. Create a Route 53 health check evaluating domain configuration status. Create a failover routing policy using the domain configuration's domain name values. Update the DynamoDB table to a global table.**
- D. Route 53 latency-based routing + manually configure DynamoDB Streams and cross-Region data replication (reimplementing a native feature — global tables — manually is inefficient).

**Correct Answer: C**

**Explanation**
Creating an **IoT Core domain configuration** in each Region, with **Route 53 health checks + failover routing** to automatically switch to the healthy Region, and using **DynamoDB Global Tables** (native multi-Region replication) to store data in both Regions, exactly matches this requirement.

**Why the other choices are wrong**
- A: Aurora is a relational database, not a substitute for DynamoDB data, and "Aurora global tables" is conceptually incorrect (that's a DynamoDB feature name).
- B: Includes an unnecessary migration to MemoryDB, and latency-based routing may not exactly match this scenario's need (both Regions active for ingestion).
- D: Manually replicating via DynamoDB Streams reimplements a feature (Global Tables) that already exists natively — inefficient.

> 💡 **Exam tip**: Always use **DynamoDB Global Tables** (native) for **multi-Region replication** — manual Streams-based replication is unnecessarily complex. For IoT Core multi-Region failover, combine **Route 53 health checks + failover routing.**

## QUESTION 185

**Question**: Organizations multi-account setup. The Finance team's account (Lambda+DynamoDB, confidential data). The Marketing team (separate account) needs access to **only specific attributes** of the DynamoDB table. How should the solutions architect grant appropriate access to Marketing?

**Choices**
- A. Attach an SCP granting attribute access to the Marketing account, applied to the Finance team's OU (SCPs cannot grant access — only set a ceiling; a conceptual error).
- B. **In the Finance account, create an IAM role with an IAM policy containing conditions for specific DynamoDB attributes (fine-grained access control). Establish a trust relationship with the Marketing account. Create an IAM role in the Marketing account with permission to assume this role.**
- C. A resource-based IAM policy (attached directly to the DynamoDB table, with attribute conditions) + create a role in the Marketing account (DynamoDB tables don't directly support resource-based policies).
- D. Create an IAM role in the Finance account + use an IAM permission boundary to restrict attribute access (permission boundaries cap a role's maximum permissions — not the right tool for fine-grained attribute-level conditions).

**Correct Answer: B**

**Explanation**
Combining a **cross-account IAM role** with an IAM policy using **DynamoDB's Fine-Grained Access Control** (`dynamodb:LeadingKeys`/attribute conditions) — creating the role in the Finance account and setting up trust so the Marketing account can assume it — is the standard cross-account, attribute-level access control pattern.

**Why the other choices are wrong**
- A: SCPs cannot "grant" permissions — they only set a maximum allowed ceiling. Conceptually wrong.
- C: **DynamoDB tables do not directly support resource-based policies** (unlike S3).
- D: Permission boundaries set a role's maximum permission limit — a different purpose than this scenario's attribute-level fine-grained control.

> 💡 **Exam tip**: **DynamoDB does not support resource-based policies.** To allow another account access to only specific attributes of a DynamoDB table, use a **cross-account IAM role + IAM policy with fine-grained access control conditions.**

## QUESTION 186

**Question**: An application storing objects in S3, used **simultaneously** across two Regions. Objects in both buckets must stay synchronized. Minimal operational overhead. (Choose three.)

**Choices**
- A. **Create an S3 Multi-Region Access Point + modify the application to reference it.**
- B. **Configure bidirectional S3 Cross-Region Replication (CRR) between the two S3 buckets.**
- C. Directly modify the application to store objects in each S3 bucket (unnecessary when using a multi-region access point, since the app doesn't need to know about individual buckets).
- D. Create S3 lifecycle rules to copy objects from one bucket to the other (lifecycle rules aren't for this kind of real-time replication).
- E. **Enable S3 versioning on each S3 bucket (a CRR prerequisite).**
- F. Invoke a Lambda function via event notifications on each bucket to manually copy objects (reimplementing the native CRR feature — inefficient).

**Correct Answer: A, B, E**

**Explanation**
Since **S3 CRR requires versioning enabled on both buckets** (E), configure bidirectional CRR to keep objects in both buckets synchronized (B), and have the application use an **S3 Multi-Region Access Point** so it doesn't need to care which Region it's in — automatically routed to the nearest/active bucket (A). This is the standard minimal-overhead combination for simultaneous dual-Region usage.

**Why the other choices are wrong**
- C: With a Multi-Region Access Point, the application doesn't need direct knowledge of which bucket it's writing to — this step is unnecessary.
- D: Lifecycle rules manage storage class transitions/expiration, not real-time replication.
- F: Manually implementing copying via Lambda when the native CRR feature exists is unnecessarily complex.

> 💡 **Exam tip**: For an S3-based application used **simultaneously across two Regions**, **bidirectional CRR (versioning required) + Multi-Region Access Point** is the standard minimal-overhead combination.

## QUESTION 187

**Question**: An on-premises IoT platform (MQTT server, collecting telemetry every 5 minutes, storing metadata in a MongoDB cluster). A periodic job (120-600 seconds) aggregates telemetry/metadata for an always-running web application generating reports. Migrate to AWS while reducing operational overhead. (Choose three.)

**Choices**
- A. Connect to IoT devices using Lambda (IoT Core is the standard for MQTT device connections).
- B. **Configure IoT devices to publish to AWS IoT Core.**
- C. Write metadata to a self-managed MongoDB database on EC2 instances (self-managed increases operational overhead).
- D. **Write metadata to Amazon DocumentDB (MongoDB compatible).**
- E. **Use an AWS Step Functions state machine with Lambda tasks to prepare reports, writing reports to Amazon S3, serving reports via Amazon CloudFront (S3 origin).**
- F. Use an Amazon EKS cluster with EC2 instances to prepare reports, serving via the EKS cluster's ingress controller (requires maintaining an always-running cluster, increasing operational overhead).

**Correct Answer: B, D, E**

**Explanation**
**AWS IoT Core** (B) is the standard for device connectivity. Since MongoDB compatibility is needed, moving to fully managed **Amazon DocumentDB** (D) instead of self-managed reduces operational burden. The periodic (120-600 second, intermittent) job is handled serverlessly via **Step Functions + Lambda**, with resulting reports served via **S3+CloudFront** (E), efficiently serving without needing always-running infrastructure (the web application).

**Why the other choices are wrong**
- A: Lambda itself doesn't handle MQTT device connections directly — IoT Core plays that role.
- C: Maintaining self-managed MongoDB on EC2 carries more operational overhead than managed DocumentDB.
- F: Maintaining an always-running EKS cluster carries more operational overhead than serverless (E), given the intermittent (120-600s) job plus always-on web service characteristics.

> 💡 **Exam tip**: For MQTT device connectivity use **IoT Core**; to replace self-managed MongoDB use **DocumentDB**; for intermittent jobs plus result publishing, **Step Functions+Lambda+S3+CloudFront** (serverless) is the standard minimal-overhead combination.

## QUESTION 188

**Question**: A global manufacturer plans to migrate most applications to AWS. However, some applications must remain in **specific countries/the central on-premises data center** due to data regulation or single-digit-millisecond latency requirements, and some are hosted at **factory sites with limited network infrastructure.** Developers need a consistent experience building once and deploying to on-premises, cloud, or hybrid architectures, using the same familiar tools/APIs/services.

**Choices**
- A. Migrate everything to the nearest compliant AWS Region + Direct Connect (doesn't address the special-case regulation/latency apps).
- B. AWS Snowball Edge Storage Optimized devices kept on-premises for regulation/latency apps + deploy AWS Wavelength for factory sites (Snowball is a data-transfer device, not persistent production infrastructure; Wavelength targets telecom 5G network edges — mismatched for limited-network factories).
- C. **Install AWS Outposts for regulation/latency-requirement applications. Use AWS Snowball Edge Compute Optimized devices to host workloads at limited-network factory sites.**
- D. Migrate regulation/latency apps to AWS Local Zones (Local Zones are still an extension of AWS Region infrastructure, mismatched with "remain in the company's central data center") + deploy Wavelength for factory sites.

**Correct Answer: C**

**Explanation**
**AWS Outposts** installs AWS hardware directly on-premises, providing the identical API/tools/services locally — letting regulation-bound or ultra-low-latency workloads stay on-premises with an "AWS-identical experience." For network-limited factories, **Snowball Edge Compute Optimized** performs local compute and syncs only when possible.

**Why the other choices are wrong**
- A: Simply moving regulation/latency-bound workloads to the nearest AWS Region contradicts the premise that they "cannot move to AWS" in the first place.
- B: Snowball Edge is primarily a data-transfer/temporary-compute device, not typically kept as persistent production infrastructure, and Wavelength is a telecom-network-edge (5G)-specific service, mismatched with "network-limited factories."
- D: AWS Local Zones are still an extension of AWS-managed infrastructure, mismatched with "must remain in the company's central on-premises data center," and Wavelength doesn't fit this scenario either.

> 💡 **Exam tip**: For workloads that **must stay on-premises** due to data regulation/ultra-low latency, **AWS Outposts** (installing AWS infrastructure locally) is the answer, and for compute at **network-limited remote sites**, **Snowball Edge Compute Optimized** is the standard.

## QUESTION 189

**Question**: An online ordering app (ECS, DynamoDB, public ALB) faces increasing malicious attacks. Prevent attacks and ensure business continuity (minimal disruption) during attacks, most cost-effectively. (Choose two.)

**Choices**
- A. **Create a CloudFront distribution with the ALB as origin. Add a custom header with a random value to the CloudFront domain. Configure the ALB to forward traffic only when the header/value matches (blocking direct ALB access).**
- B. Deploy in two Regions + Route 53 weighted routing (unrelated to attack defense directly, and doubles cost).
- C. ECS task auto scaling + a DAX cluster (doesn't stop the attack itself, only adds cost).
- D. ElastiCache to reduce DynamoDB overhead (unrelated to attack defense).
- E. **Deploy an AWS WAF web ACL with appropriate rule groups. Attach it to the CloudFront distribution.**

**Correct Answer: A, E**

**Explanation**
Blocking direct access to the ALB via **CloudFront + custom header validation** (A, preventing origin bypass) and attaching **AWS WAF** to CloudFront (E) to filter known attack patterns prevents attacks cost-effectively while still serving legitimate traffic.

**Why the other choices are wrong**
- B: Multi-Region deployment significantly increases cost and doesn't stop application-layer attacks itself.
- C, D: Auto scaling or caching only helps "absorb" attack-induced load rather than preventing the attack, and only adds cost.

> 💡 **Exam tip**: To block **direct access to an origin (ALB), forcing traffic through CloudFront only**, use the **custom header validation** pattern; to stop application-layer attacks themselves, combine **CloudFront + AWS WAF** — the low-cost standard answer.

## QUESTION 190

**Question**: CloudFront (S3 static content) + ALB (EC2 dynamic content) + Route 53 web application. During high-traffic periods, the ALB intermittently returns **HTTP 503**. The company wants a custom error page displayed **immediately** when this occurs. Minimal operational overhead?

**Choices**
- A. Route 53 failover routing (ALB health check → failover to S3 bucket endpoint) (DNS-based failover may not reflect "immediately" due to caching/TTL).
- B. Second CloudFront+S3 deployment + Route 53 failover routing (active-passive) (same DNS-switching delay issue).
- C. **Create a CloudFront origin group (primary origin: ALB, secondary origin: an S3 bucket configured for static website hosting). Set up origin failover for the CloudFront distribution. Update the S3 static website to incorporate the custom error page.**
- D. Create a CloudFront function validating each HTTP response code from the ALB + read and serve the error page from S3 (possible, but more complex than the native origin failover feature, adding function execution overhead).

**Correct Answer: C**

**Explanation**
CloudFront's **Origin Group Origin Failover** feature switches **immediately at the CloudFront edge** to the secondary origin (S3's static error page) when the primary origin (ALB) returns a specified failure status code (including 503) — no need to wait for DNS propagation, exactly meeting the "immediate display" requirement.

**Why the other choices are wrong**
- A, B: Route 53-based failover is affected by DNS caching/TTL, making "immediate" hard to guarantee.
- D: Implementing this directly via a CloudFront function reinvents the already-existing native origin failover feature — unnecessarily complex.

> 💡 **Exam tip**: To show **immediate fallback content when an origin error (503, etc.) occurs** in CloudFront, use **CloudFront Origin Group Origin Failover** — much faster than Route 53 DNS-based failover.

## QUESTION 191

**Question**: Migrate a Docker container application (using NFSv4 file shares) to AWS. Design a secure, scalable containerized solution requiring no provisioning or management of underlying infrastructure.

**Choices**
- A. **Deploy containers using ECS with the Fargate launch type. Use EFS for shared storage. Reference the EFS file system ID, container mount point, and EFS authorization IAM role in the ECS task definition.**
- B. Fargate ECS + FSx for Lustre (uses its own Lustre protocol, not NFSv4 — mismatched requirement).
- C. ECS with EC2 launch type (with Auto Scaling) + EFS (requires provisioning/managing EC2 instances — violates "no underlying infrastructure management").
- D. ECS with EC2 launch type + EBS Multi-Attach (requires EC2 management + Multi-Attach's same-AZ constraint).

**Correct Answer: A**

**Explanation**
**Fargate** is a serverless container runtime requiring zero underlying infrastructure (EC2) provisioning/management, and **Amazon EFS** natively supports the NFS protocol (including NFSv4) as a fully managed file system. Configuring the ECS task definition to directly reference an EFS volume exactly meets the requirements.

**Why the other choices are wrong**
- B: FSx for Lustre uses its own Lustre client/protocol, not NFS, mismatching the "NFS version 4" requirement.
- C, D: EC2 launch type requires instance provisioning/management, violating the core "no underlying infrastructure management" requirement.

> 💡 **Exam tip**: To migrate an **NFS-based containerized workload serverlessly**, **Fargate + EFS** (referenced directly in the task definition) is the standard answer. Remember FSx for Lustre doesn't use the NFS protocol.

## QUESTION 192

**Question**: An EC2 (Auto Scaling)+ALB application (api.example.com). A major business logic update is planned; during a testing period, **only 10% of customers** should receive the new logic, and each customer must keep using the **same version** throughout the test (sticky per customer). How to deploy?

**Choices**
- A. Second ALB + new Auto Scaling group + Route 53 weighted routing (routing between two ALBs may not guarantee per-user version stickiness due to DNS caching).
- B. **Create a second target group referenced by the ALB, deploy the new logic to it. Update the ALB listener rule to use weighted target groups. Configure ALB target group stickiness.**
- C. New launch configuration + AutoScalingRollingUpdate policy (MaxBatchSize=10) (a full-replacement rolling approach — a different concept than a 10%-held A/B test; eventually everything gets rolled over).
- D. Second Auto Scaling group + change the ALB routing algorithm to LOR + ALB session stickiness (LOR is a load-balancing algorithm among instances within a target group, not a mechanism for splitting traffic between two versions).

**Correct Answer: B**

**Explanation**
**ALB weighted target groups** let a listener rule distribute traffic in an exact ratio (90%/10%) between two target groups (existing/new logic), and enabling **target group stickiness** ensures a customer, once assigned to a group, keeps using the same version throughout the test.

**Why the other choices are wrong**
- A: Using Route 53 weighted routing between two separate ALBs risks users landing on different ALBs across requests due to DNS caching, weakening the "keep same version" guarantee.
- C: A rolling update eventually replaces every instance sequentially with the new version — a different concept than a canary/A-B test holding 10% steady.
- D: LOR (Least Outstanding Requests) is a load-balancing algorithm among instances within a target group, not a feature for splitting traffic ratio between two versions.

> 💡 **Exam tip**: To split ALB traffic **by an exact percentage across two versions** while **pinning each user to their assigned version**, the standard answer is **weighted target groups + target group stickiness.**

## QUESTION 193

**Question**: WorkSpaces + FSx for Windows File Server (user profiles, DNS alias, connected to self-managed AD). Login times spike as more users adopt WorkSpaces. Investigation reveals performance degradation of the file system, which was created on **HDD storage (16MBps throughput).** Improve performance during a defined maintenance window, with minimal management effort.

**Choices**
- A. Use AWS Backup for a point-in-time backup + restore to a new file system (SSD, 32MBps) + adjust DNS alias + delete original (unnecessarily complex, requires creating a new file system).
- B. **Disconnect users from the file system. In the FSx console, update storage capacity to 32MBps and storage type to SSD. Reconnect users.**
- C. Migrate to a new file system using DataSync (unnecessarily complex separate migration task).
- D. Use Windows PowerShell shadow copies (a backup/restore feature unrelated to solving the performance problem).

**Correct Answer: B**

**Explanation**
**Amazon FSx for Windows File Server supports directly (in-place) updating the storage type (HDD→SSD) and throughput capacity** on an existing file system. No need to create a new file system or migrate data — just change the values in the console, making it the least management effort way to improve performance.

**Why the other choices are wrong**
- A: Creating a new file system via backup/restore is unnecessarily complex and time-consuming.
- C: Migration via DataSync also requires a separate new file system and data transfer, requiring more effort.
- D: Shadow copies restore previous file versions — unrelated to the storage performance problem.

> 💡 **Exam tip**: **FSx for Windows File Server's storage type/throughput capacity can be updated in-place** on the existing file system — remember you can change it directly in the console without creating a new file system or migrating.

## QUESTION 194

**Question**: An application reading/writing a single S3 bucket must be modified to deploy across **two Regions.** Minimal operational overhead solution?

**Choices**
- A. CloudFront distribution with S3 as origin + deploy app to second Region + access S3 data via Global Accelerator (CloudFront/Global Accelerator don't directly solve this scenario's multi-Region write-sync problem).

- C: One-way CRR only causes data written in the second Region to never reflect back to the original bucket, creating inconsistency.

## QUESTION 195

**Question**: An online gaming platform is being rehosted on AWS. Requires HPC processing, with a frequently-changing leaderboard. A Node.js game display app runs on compute-optimized Ubuntu instances. Game state is tracked in an on-premises Redis instance. Design a migration strategy optimizing application performance.

**Choices**
- A. m5.large Spot Instance Auto Scaling group + ElastiCache for Redis (general-purpose instances mismatch the HPC requirement, and Spot's interruption risk is unsuitable for a game service).
- B. c5.large Spot Instance Auto Scaling group + OpenSearch cluster (Redis is better suited to real-time sorted-set operations for leaderboards than OpenSearch, and Spot still carries interruption risk).
- C. **c5.large On-Demand Instance Auto Scaling group behind an ALB + Amazon ElastiCache for Redis cluster maintaining the leaderboard.**
- D. m5.large On-Demand Instance Auto Scaling group + DynamoDB table for the leaderboard (general-purpose instances mismatch "Compute Optimized," and Redis is better optimized for sorted-set ranking operations than DynamoDB).

**Correct Answer: C**

**Explanation**
The stated "Compute Optimized" requirement calls for the **c5 (compute-optimized) instance family**, and for game-service stability, **On-Demand** (not interruption-risky Spot) is appropriate. For the leaderboard (frequently-changing sorted data), **ElastiCache for Redis** with its **Sorted Set** structure specialized for real-time ranking operations is the natural managed replacement for the on-premises Redis.

**Why the other choices are wrong**
- A, D: m5 is a general-purpose instance family, mismatching the "compute-optimized" requirement.
- A, B: Spot Instances risk interruption, unsuitable for a production workload like a game service where continuous availability matters.
- D: DynamoDB could implement a leaderboard, but it's not as optimized for real-time ranking operations as Redis's Sorted Set, and migrating the existing Redis-based architecture as-is is more natural.

> 💡 **Exam tip**: When "Compute Optimized" is explicitly stated, choose **C-family instances**, and for production stability, choose **On-Demand** (not Spot). For real-time leaderboards/rankings, **ElastiCache for Redis (Sorted Set)** is the standard answer.

## QUESTION 196

**Question**: Employees submit timesheets via mobile (concentrated on Fridays), stored in a format the payroll manager can use for monthly reports. Infrastructure must be highly available and scale with incoming data/report request rates, minimizing operational overhead. (Choose two.)

**Choices**
- A. Deploy the app on load-balanced EC2 On-Demand instances across multiple AZs + scheduled EC2 Auto Scaling ahead of Friday (server management needed, more overhead than serverless).
- B. Deploy in containers via load-balanced Amazon ECS across multiple AZs + scheduled Service Auto Scaling ahead of Friday (better than A, but still requires container/cluster management).
- C. **Deploy the frontend on S3 (served by CloudFront). Deploy the backend using API Gateway with Lambda proxy integration.**
- D. Store timesheet data in Redshift + generate reports via QuickSight using Redshift as the data source (Redshift requires an always-provisioned cluster — excessive operational burden/cost for an intermittent workload).
- E. **Store timesheet data in S3. Generate reports using Athena and QuickSight with S3 as the data source.**

**Correct Answer: C, E**

**Explanation**
For intermittent (Friday-concentrated) traffic, a **fully serverless** setup (S3+CloudFront frontend, API Gateway+Lambda backend) automatically scales up/down without managing scheduled Auto Scaling — the lowest operational overhead (C). Monthly reports handled via **S3+Athena (serverless query)+QuickSight** (E), requiring no always-on cluster, similarly minimize management burden.

**Why the other choices are wrong**
- A, B: EC2/ECS-based approaches require directly setting up/managing scheduled Auto Scaling, more overhead than fully serverless.
- D: Redshift requires an always-provisioned cluster, inefficient in cost/operations for an intermittent workload like monthly reporting.

> 💡 **Exam tip**: For **intermittent/bursty** traffic, use **fully serverless (S3+CloudFront, API Gateway+Lambda)**; for intermittent report generation, **S3+Athena+QuickSight** (no always-on cluster needed) — the minimal-overhead standard combination.

## QUESTION 197

**Question**: Sensitive data stored in S3. **Log all activity** on the objects and retain logs for 5 years. The security team must receive an email notification whenever there's an attempt to **delete data.** Most cost-effective combination? (Choose three.)

**Choices**
- A. **Configure AWS CloudTrail to log S3 data events.**
- B. Configure S3 server access logging on the bucket (access logging has lower granularity and is hard to use as a real-time notification trigger).
- C. Configure S3 to send object delete events to Amazon SES (SES is an email-sending API, not an event routing/trigger service — conceptual error).
- D. **Configure S3 to send object delete events to an EventBridge event bus that publishes to an SNS topic.**
- E. Configure S3 to send logs to Amazon Timestream (a time-series database — cost-inefficient for long-term log archiving compared to S3).
- F. **Configure a new S3 bucket to store logs with an S3 lifecycle policy.**

**Correct Answer: A, D, F**

**Explanation**
**CloudTrail's S3 data event logging** (A) captures all object-level activity, **S3 event notifications → EventBridge → SNS** (D) sends email notifications on delete events, and storing logs in **S3 with a lifecycle policy** (F, e.g., transitioning to cheaper storage classes, expiring after 5 years) is the most cost-effective combination.

**Why the other choices are wrong**
- B: Server access logging has lower granularity and isn't suited for real-time event-driven notification.

## QUESTION 200

**Question**: A SAML 2.0 federated identity solution was implemented with an on-premises IdP. The architect's own authentication via the federated web portal succeeds, but a **test user** cannot access AWS the same way. What should be checked to verify identity federation is correctly configured? (Choose three.)

**Choices**
- A. The IAM user's permission policy allows SAML federation use (SAML federation works through IAM roles, not IAM users — a conceptual error).
- B. **Verify that the IAM role created for the trust policy of federated users/groups sets the SAML provider as the principal.**
- C. The test user isn't in the company IdP's AWSFederatedUsers group (the group name itself isn't a mandatory requirement — the real key is the IdP's SAML assertion mapping, not dependency on a specific group name).
- D. **Verify the web portal calls the STS `AssumeRoleWithSAML` API using the SAML provider ARN, IAM role ARN, and the IdP's SAML assertion.**
- E. Verify the on-premises IdP's DNS hostname is reachable from the AWS VPC (SAML federation is structured so the user's browser reaches both the IdP and AWS — the AWS VPC generally doesn't need direct connectivity to the on-premises IdP).
- F. **Verify the company's IdP defines a SAML assertion that properly maps users/groups, and that the company has defined an IAM role with appropriate permissions.**

**Correct Answer: B, D, F**

**Explanation**
For SAML 2.0 federation to work correctly: ① the IAM role's **trust policy must trust the SAML provider as principal** (B), ② the web portal must correctly call the **`AssumeRoleWithSAML` API** with the SAML provider ARN/role ARN/assertion (D), and ③ the IdP itself must be configured to issue a **correct SAML assertion** (mapping the user to the appropriate role) (F). A mismatch in any of these three can cause authentication failure for specific users only.

**Why the other choices are wrong**
- A: SAML-federated users aren't IAM users — they assume an IAM role via temporary credentials, so "the IAM user's permission policy" is a conceptual mismatch.
- C: There's no fixed requirement to belong to a specific group name ("AWSFederatedUsers") — the actual mapping depends on the IdP's SAML assertion configuration.
- E: SAML federation is structured so the end user's browser reaches the IdP and AWS separately — the AWS VPC generally doesn't need direct connectivity to the on-premises IdP's DNS.

> 💡 **Exam tip**: When troubleshooting SAML 2.0 federation, check these three core items: **① the IAM role's trust policy setting the SAML provider, ② the web portal's `AssumeRoleWithSAML` call, and ③ the IdP's correct SAML assertion (user-to-role mapping).**
