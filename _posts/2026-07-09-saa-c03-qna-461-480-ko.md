## QUESTION 461

**문제**: 한 자동차 부품 제조업체는 공장 내 생산 라인에서 실시간으로 생성되는 센서 데이터를 초저지연으로 처리해야 합니다. 공장은 통신 환경이 불안정한 지역에 위치해 있어 리전으로의 네트워크 연결이 간헐적으로 끊길 수 있으며, 그런 상황에서도 EC2, EBS, 컨테이너 서비스 등 AWS 네이티브 서비스를 현장에서 계속 실행해야 합니다. 이 회사는 AWS 콘솔, API, 도구를 그대로 사용하면서 온프레미스에서 컴퓨팅을 처리하고자 합니다. 어떤 솔루션이 이 요구 사항을 충족합니까?

**보기**
- A. **AWS Outposts 랙을 공장 현장에 설치하여 온프레미스에서 AWS 네이티브 서비스를 실행한다.**
- B. AWS Direct Connect 전용선을 통해 가장 가까운 리전과 연결한다(리전 연결에 의존하므로 네트워크 단절 시 현장에서 컴퓨팅을 계속 실행할 수 없고, 지연 시간도 완전히 해소되지 않는다).
- C. 가장 가까운 AWS Local Zone을 이용해 컴퓨팅 자원을 배치한다(Local Zone은 AWS가 대도시 권역에 직접 운영하는 인프라로, 공장 부지 내부에 위치시킬 수는 없다).
- D. AWS Storage Gateway 볼륨 게이트웨이를 현장에 배치한다(스토리지 캐싱만 제공할 뿐 EC2 컴퓨팅이나 컨테이너 서비스를 현장에서 실행할 수는 없다).

**정답: A**

**해설**: **AWS Outposts**는 AWS가 설계한 랙이나 서버를 고객의 데이터센터, 공장 등 온프레미스 환경에 물리적으로 설치해, 리전과 동일한 API, 콘솔, 도구로 EC2, EBS, ECS/EKS 등의 서비스를 로컬에서 실행할 수 있게 해줍니다. 네트워크가 일시적으로 끊기더라도 로컬 컴퓨팅이 계속 동작하며, 초저지연이 필요한 공장 자동화 워크로드에 적합합니다.

**왜 다른 보기는 오답인가**
- B: Direct Connect는 온프레미스와 리전 간 전용 네트워크 연결을 제공하지만, 실제 처리는 여전히 리전에서 이루어지므로 연결이 끊기면 처리가 중단되고 초저지연 요구도 완전히 만족시키지 못합니다.
- C: Local Zone은 AWS가 특정 대도시 권역에 구축한 확장 인프라로, 고객 사업장 내부에 직접 배치되는 것이 아니어서 공장 현장 컴퓨팅 요구에는 맞지 않습니다.
- D: Storage Gateway는 스토리지 캐싱 및 하이브리드 스토리지 용도이며, EC2 인스턴스나 컨테이너 워크로드 자체를 실행하는 컴퓨팅 서비스가 아닙니다.

> 💡 **시험 꿀팁**: "AWS 네이티브 서비스를 온프레미스에서 그대로 실행"이라는 표현이 나오면 거의 항상 AWS Outposts가 정답입니다.

## QUESTION 462

**문제**: 한 OTT 스트리밍 서비스는 CloudFront를 통해 프리미엄 회원 전용 동영상 파일들을 배포하고 있습니다. 로그인한 프리미엄 회원은 세션 동안 수십 개의 서로 다른 동영상 파일에 접근할 수 있어야 하는데, 동영상마다 개별적으로 서명된 URL을 발급하는 방식은 애플리케이션 로직을 복잡하게 만들고 있습니다. 로그인 시 한 번의 인증으로 여러 리소스에 대한 접근 권한을 부여하고 싶습니다. 어떤 방법이 가장 적합합니까?

**보기**
- A. 각 동영상 파일에 대해 CloudFront 서명된 URL을 개별적으로 발급한다(파일마다 매번 서명을 생성해야 하므로 다수의 리소스에 접근해야 하는 시나리오에서는 관리 부담이 크다).
- B. **로그인 시 CloudFront 서명된 쿠키를 발급하여 여러 restricted 동영상 파일에 대한 접근을 한 번에 허용한다.**
- C. S3 버킷 정책을 수정하여 각 최종 사용자에게 IAM 자격 증명을 발급한다(최종 사용자는 IAM 보안 주체가 아니며, 사용자 수만큼 IAM 자격 증명을 관리하는 것은 확장성이 없다).
- D. CloudFront Origin Access Control(OAC)만 설정한다(OAC는 S3 오리진에 대한 접근을 CloudFront로만 제한할 뿐, 최종 사용자별 인증이나 세분화된 접근 제어를 제공하지 않는다).

**정답: B**

**해설**: **CloudFront 서명된 쿠키(signed cookies)**를 사용하면 사용자가 로그인할 때 쿠키를 한 번 발급하고, 이후 여러 개의 제한된 콘텐츠에 URL 구조를 바꾸지 않고도 접근할 수 있습니다. 이는 다수의 파일에 동일한 접근 정책을 적용해야 하는 스트리밍 서비스에 적합하며, 개별 URL마다 서명을 생성해야 하는 번거로움을 없애줍니다.

**왜 다른 보기는 오답인가**
- A: 서명된 URL은 파일 단위로 발급되므로 다수의 동영상에 접근해야 하는 세션에서는 매번 URL을 새로 생성해야 해 비효율적입니다.
- C: 최종 사용자는 IAM 사용자가 아니며, 사용자 수만큼 IAM 자격 증명을 발급/관리하는 것은 운영상 불가능에 가깝습니다.
- D: OAC는 S3와 CloudFront 사이의 접근을 제한하는 기능일 뿐, 최종 사용자 인증이나 개별 콘텐츠 접근 제어를 대체하지 못합니다.

> 💡 **시험 꿀팁**: "여러 파일에 대한 접근을 한 번에" 요구 사항이 등장하면 서명된 URL이 아니라 서명된 쿠키를 떠올리세요.

## QUESTION 463

**문제**: 한 이커머스 회사는 Amazon RDS for MySQL을 사용 중인데, 최근 특정 시간대에 응답 지연이 심해졌다는 고객 불만이 접수되고 있습니다. CloudWatch의 CPU 사용률과 메모리 지표는 정상 범위 내에 있지만, 어떤 SQL 쿼리가 병목의 원인인지 특정할 수 없는 상황입니다. 솔루션 아키텍트는 데이터베이스 부하를 유발하는 실제 쿼리를 식별하고 싶습니다. 어떤 서비스를 사용해야 합니까?

**보기**
- A. CloudWatch의 기본 CPU/메모리 지표를 더 세밀한 간격으로 모니터링한다(호스트 수준 지표만 제공할 뿐, 어떤 SQL 쿼리가 부하를 유발하는지는 알려주지 않는다).
- B. RDS 이벤트 구독을 설정하여 인스턴스 상태 변경 알림을 받는다(인스턴스 재부팅, 장애조치 등 이벤트 알림용으로, 쿼리 수준의 성능 분석과는 무관하다).
- C. **Amazon RDS Performance Insights를 활성화하여 대기 이벤트와 상위 SQL 쿼리를 분석한다.**
- D. VPC Flow Logs를 활성화해 네트워크 트래픽 패턴을 분석한다(IP 트래픽 흐름을 기록할 뿐 데이터베이스 내부의 SQL 실행 정보는 제공하지 않는다).

**정답: C**

**해설**: **Amazon RDS Performance Insights**는 데이터베이스 부하를 시각화하고, 대기 이벤트(wait events)별로 분해해 어떤 SQL 문이 가장 많은 부하를 유발하는지 식별할 수 있게 해줍니다. 인스턴스 수준의 CPU/메모리 지표로는 알 수 없는 쿼리 단위의 병목 원인을 정확히 짚어낼 수 있어 이 시나리오에 가장 적합합니다.

**왜 다른 보기는 오답인가**
- A: CPU/메모리 지표는 이미 정상이라고 명시되어 있으며, 애초에 쿼리 단위 분석 기능이 없습니다.
- B: RDS 이벤트 구독은 장애조치, 백업 완료 등 운영 이벤트를 알려주는 기능으로 쿼리 성능 진단과 관련이 없습니다.
- D: VPC Flow Logs는 네트워크 인터페이스 수준의 IP 트래픽을 기록하는 기능으로 SQL 실행 내역과는 관련이 없습니다.

> 💡 **시험 꿀팁**: "어떤 쿼리가 문제인지 알고 싶다"는 문구가 나오면 RDS Performance Insights를 떠올리세요.

## QUESTION 464

**문제**: 한 물류 회사는 수백만 대의 IoT 배송 추적 장치로부터 초 단위로 이벤트를 수신해 짧은 시간 내에 처리를 완료해야 하는 워크플로를 구축하려고 합니다. 각 실행은 몇 초 이내에 끝나지만 처리량이 매우 높으며, 비용 효율성이 중요한 요소입니다. 워크플로 실행 이력은 필요하지만 완벽한 정확히 한 번(exactly-once) 실행 보장까지는 필요하지 않습니다. 어떤 Step Functions 워크플로 유형을 선택해야 합니까?

**보기**
- A. Standard Workflows를 사용한다(장시간 실행과 정확히 한 번 실행 보장에 최적화되어 있어 상태 전환당 과금되므로, 초당 대량의 단기 실행에는 비용 효율이 떨어진다).
- B. Amazon Simple Workflow Service(SWF)를 사용한다(레거시 서비스로 AWS가 신규 워크로드에는 Step Functions 사용을 권장하며 관리형 기능이 상대적으로 제한적이다).
- C. Lambda와 DynamoDB로 상태 머신을 직접 구현한다(운영 오버헤드와 개발 복잡도가 크게 늘어나며 재시도, 이력 관리 등을 직접 구현해야 한다).
- D. **Express Workflows를 사용한다.**

**정답: D**

**해설**: **Step Functions Express Workflows**는 최소 한 번(at-least-once) 실행 모델을 기반으로 하며, 초당 수십만 건의 이벤트를 짧은 실행 시간 동안 저비용으로 처리하도록 설계되었습니다. 과금이 실행 시간과 요청 수 기준으로 이루어져 고빈도·단기 실행 워크로드에 Standard Workflows보다 훨씬 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- A: Standard Workflows는 상태 전환 단위로 과금되고 정확히 한 번 실행을 보장하도록 설계되어 있어, 장시간 실행이나 감사 추적이 중요한 워크로드에 적합하지만 대량의 단기 이벤트 처리에는 비용이 크게 늘어납니다.
- B: SWF는 Step Functions 이전의 레거시 오케스트레이션 서비스로 신규 구축에는 권장되지 않습니다.
- C: 직접 구현 방식은 관리형 서비스의 이점을 포기하고 재시도, 상태 추적 등을 모두 직접 처리해야 하므로 운영 부담이 큽니다.

> 💡 **시험 꿀팁**: "고빈도·단기 실행·비용 효율"이라는 키워드 조합은 Express Workflows, "장시간·정확히 한 번 실행"은 Standard Workflows를 가리킵니다.

## QUESTION 465

**문제**: 한 대기업은 여러 사업부가 각각 다른 AWS 계정에서 수십 개의 VPC를 운영하고 있으며, 최근 IP 주소 대역이 중복되어 VPC 피어링과 Transit Gateway 연결에 문제가 생기고 있습니다. 네트워크 팀은 조직 전체의 IP 주소 할당 현황을 중앙에서 계획하고, 사용률을 모니터링하며, 중복 할당을 사전에 방지하고 싶어 합니다. 어떤 서비스를 사용해야 합니까?

**보기**
- A. **Amazon VPC IP Address Manager(IPAM)를 사용해 여러 계정과 VPC의 IP 주소를 중앙에서 계획하고 모니터링한다.**
- B. VPC 피어링을 구성해 VPC 간 연결을 확장한다(VPC 간 네트워크 연결 자체를 위한 기능일 뿐, IP 주소 계획이나 중복 방지 기능은 제공하지 않는다).
- C. AWS Transit Gateway를 도입해 모든 VPC를 하나의 허브로 연결한다(다대다 연결을 단순화하는 데는 유용하지만 IP 주소 할당 현황을 관리하는 기능은 아니다).
- D. 스프레드시트로 각 계정의 CIDR 블록을 수동으로 추적한다(계정과 VPC 수가 많아질수록 오류 발생 가능성이 커지고 실시간성이 떨어진다).

**정답: A**

**해설**: **Amazon VPC IP Address Manager(IPAM)**는 여러 AWS 계정과 리전에 걸쳐 IP 주소 공간을 중앙에서 계획, 추적, 모니터링할 수 있게 해주는 관리형 기능입니다. CIDR 중복을 사전에 방지하고 사용률을 시각화할 수 있어 대규모 멀티 계정 환경의 IP 관리 문제를 해결하는 데 가장 적합합니다.

**왜 다른 보기는 오답인가**
- B: VPC 피어링은 이미 존재하는 VPC 간 네트워크 트래픽을 연결하는 기능으로, IP 주소 계획 문제 자체를 해결하지 못합니다.
- C: Transit Gateway는 여러 VPC와 온프레미스 네트워크를 허브 형태로 연결하는 서비스로, IP 주소 중복 방지나 사용률 모니터링 기능은 없습니다.
- D: 수동 추적 방식은 계정과 VPC 수가 늘어날수록 확장성이 없고 실수가 발생하기 쉽습니다.

> 💡 **시험 꿀팁**: "여러 계정/VPC의 IP 주소를 중앙에서 계획·모니터링"이라는 표현은 VPC IPAM을 가리키는 전형적인 신호입니다.

## QUESTION 466

**해설**: **S3 Multi-Region Access Points**는 여러 리전에 걸친 버킷들을 하나의 글로벌 엔드포인트로 통합해, AWS 글로벌 네트워크를 기반으로 요청을 지연 시간이 가장 짧은 리전으로 자동 라우팅합니다. 또한 리전 장애 시에도 장애 조치(failover) 제어를 통해 다른 리전으로 트래픽을 전환할 수 있어, 단일 엔드포인트로 다중 리전을 운영해야 하는 요구 사항에 정확히 부합합니다.

**왜 다른 보기는 오답인가**
- A: Route 53 지연 시간 기반 라우팅은 DNS 수준에서 리전을 선택할 수 있지만, 버킷별 엔드포인트를 계속 개별 관리해야 하고 장애 조치 로직을 추가로 구현해야 합니다.
- B: CloudFront는 콘텐츠 캐싱과 배포에 강점이 있지만 다중 오리진 간 자동 최적 라우팅과 장애 조치까지 매끄럽게 처리하는 것은 Multi-Region Access Points의 핵심 기능입니다.
- D: Transfer Acceleration은 CloudFront 엣지를 이용해 단일 버킷으로의 전송 속도를 높이는 기능일 뿐 다중 리전 라우팅과는 관련이 없습니다.

> 💡 **시험 꿀팁**: "단일 엔드포인트로 여러 리전 버킷에 자동 라우팅"이라는 표현은 S3 Multi-Region Access Points를 가리키는 핵심 신호입니다.

## QUESTION 474

**문제**: 한 스타트업은 신규 SaaS 제품의 백엔드 데이터베이스를 구축하려고 하는데, 트래픽 패턴이 매우 불규칙합니다. 어떤 날은 거의 트래픽이 없다가 마케팅 캠페인이 진행되는 날에는 갑자기 부하가 급증하며, 이런 패턴을 사전에 예측하기 어렵습니다. 트래픽이 없을 때 불필요한 비용을 지불하지 않으면서도 갑작스러운 트래픽 증가에 자동으로 대응할 수 있는 관계형 데이터베이스가 필요합니다. 어떤 솔루션이 적합합니까?

- A: 고정 프로비저닝 인스턴스는 트래픽이 없을 때도 동일한 비용이 발생하며, 급증하는 트래픽에는 수동 또는 별도 스케일링 절차가 필요합니다.
- C: 읽기 복제본은 읽기 부하 분산에는 유용하지만 쓰기 컴퓨팅 용량이나 전체적인 가변 부하 문제를 해결하지 못합니다.
- D: ElastiCache는 읽기 성능을 개선하는 캐싱 계층일 뿐, 데이터베이스 자체의 가변적인 컴퓨팅 용량 문제를 해결하는 솔루션이 아닙니다.

> 💡 **시험 꿀팁**: "예측 불가능하고 간헐적인(intermittent) 트래픽"이라는 키워드는 Aurora Serverless v2를 가리키는 대표적인 신호입니다.

- B. 네트워크 ACL은 스테이트풀하므로 인바운드 규칙만 설정해도 리턴 트래픽이 자동으로 허용된다(사실과 반대로, 네트워크 ACL은 스테이트리스이므로 인바운드와 아웃바운드 규칙을 모두 명시적으로 설정해야 한다).
- C. 보안 그룹과 네트워크 ACL 모두 스테이트풀하므로 결과적으로 리턴 트래픽에 대한 별도 규칙이 필요 없다(네트워크 ACL은 스테이트리스로 동작하므로 이 설명은 옳지 않다).
- D. **보안 그룹은 스테이트풀하여 리턴 트래픽이 자동으로 허용되지만, 네트워크 ACL은 스테이트리스이므로 인바운드와 아웃바운드 규칙을 모두 명시적으로 설정해야 한다.**

**정답: D**

**해설**: **보안 그룹**은 인스턴스 수준에서 동작하는 스테이트풀(stateful) 방화벽으로, 인바운드 요청이 허용되면 그에 대한 응답(리턴) 트래픽은 아웃바운드 규칙과 무관하게 자동으로 허용됩니다. 반면 **네트워크 ACL**은 서브넷 수준에서 동작하는 스테이트리스(stateless) 방화벽으로, 인바운드 규칙과 아웃바운드 규칙을 각각 독립적으로 평가하므로 응답 트래픽을 허용하려면 아웃바운드 규칙(흔히 에페메럴 포트 범위 포함)을 별도로 명시해야 합니다.

**왜 다른 보기는 오답인가**
- A: 보안 그룹이 스테이트리스라는 설명은 반대로 되어 있으며, 실제로는 스테이트풀하기 때문에 별도 아웃바운드 규칙 없이도 응답 트래픽이 허용됩니다.
- B: 네트워크 ACL이 스테이트풀하다는 설명이 잘못되었으며, 실제로는 스테이트리스이기 때문에 인바운드/아웃바운드를 모두 명시해야 합니다.
- C: 네트워크 ACL은 스테이트리스이므로 "모두 스테이트풀"이라는 전제 자체가 틀렸습니다.

> 💡 **시험 꿀팁**: 보안 그룹 = 스테이트풀(리턴 트래픽 자동 허용), 네트워크 ACL = 스테이트리스(양방향 규칙 모두 필요)로 암기하세요.

## QUESTION 477

**문제**: 한 모바일 게임 회사는 사용자가 회원 가입을 하지 않고도 게임을 체험할 수 있는 게스트 모드를 제공하려고 합니다. 게스트 사용자도 앱 내에서 S3에 저장된 리소스를 다운로드하거나 DynamoDB에 진행 상황을 저장할 수 있어야 하지만, 장기 자격 증명을 클라이언트에 내장하는 것은 보안상 허용되지 않습니다. 인증되지 않은 사용자에게도 제한된 임시 AWS 자격 증명을 부여하고 싶습니다. 어떤 서비스를 사용해야 합니까?

**보기**
- A. **Amazon Cognito Identity Pools를 사용해 인증되지 않은 자격 증명(unauthenticated identities)을 허용하도록 구성한다.**
- B. Amazon Cognito User Pools만 단독으로 사용한다(회원 가입/로그인 관리와 JWT 토큰 발급에 초점이 맞춰져 있어, 인증되지 않은 게스트에게 임시 AWS 자격 증명을 부여하는 기능은 제공하지 않는다).
- C. IAM 사용자 자격 증명을 앱에 하드코딩한다(장기 자격 증명이 클라이언트에 노출되어 심각한 보안 위험을 초래한다).
- D. 모바일 클라이언트에서 STS AssumeRole API를 직접 호출한다(역할을 위임하려면 이미 인증된 자격 증명이나 신원이 필요한데, 이 시나리오는 애초에 인증되지 않은 게스트를 위한 것이므로 적합하지 않다).

**정답: A**

**해설**: **Amazon Cognito Identity Pools(연동 자격 증명)**는 인증되지 않은 자격 증명을 허용하도록 구성하면, 로그인하지 않은 게스트 사용자에게도 IAM 역할을 기반으로 한 제한된 임시 자격 증명(STS 토큰)을 발급할 수 있습니다. 이를 통해 게스트도 안전하게 S3나 DynamoDB 같은 AWS 리소스에 최소 권한으로 접근할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: User Pools는 사용자 디렉터리와 인증(로그인/회원가입) 기능에 특화되어 있으며, AWS 리소스에 접근하기 위한 임시 자격 증명 발급은 Identity Pools의 역할입니다.
- C: 장기 IAM 자격 증명을 클라이언트 앱에 내장하는 것은 유출 위험이 매우 크고 AWS 모범 사례에 위배됩니다.
- D: STS AssumeRole은 이미 신뢰할 수 있는 자격 증명이나 신원이 있어야 호출할 수 있는데, 게스트는 애초에 인증된 신원이 없으므로 이 방식이 성립하지 않습니다.

> 💡 **시험 꿀팁**: "인증되지 않은 게스트 사용자에게 임시 AWS 자격 증명"이라는 요구는 Cognito Identity Pools의 unauthenticated identities 기능을 가리킵니다.

## QUESTION 478

**문제**: 한 보안팀은 조직 내 수백 개의 S3 버킷 중 퍼블릭 액세스가 실수로 열리는 경우가 반복적으로 발생하는 것을 발견했습니다. 담당자가 매번 수동으로 확인하고 수정하는 방식은 대응 속도가 느리고 누락이 발생하기 쉽습니다. 규정 준수 위반이 탐지되면 사람의 개입 없이 자동으로 문제를 교정하는 체계를 구축하고 싶습니다. 어떤 조합이 적합합니까?

**보기**
- A. CloudWatch 이벤트로 알림만 받고 담당자가 콘솔에서 수동으로 수정한다(사람이 직접 개입해야 하므로 대응 속도가 느리고 실수나 누락이 발생할 수 있어 자동화 요구를 충족하지 못한다).
- B. **AWS Config 규칙으로 비준수 리소스를 탐지하고, Systems Manager Automation 문서를 연결해 자동으로 교정하도록 구성한다.**
- C. AWS Trusted Advisor의 점검 결과를 주기적으로 검토한다(모범 사례 위반 여부를 알려주는 권고 기능일 뿐 자동 교정 조치를 수행하지는 않는다).
- D. AWS CloudTrail 로그를 분석해 사후에 감사한다(이미 발생한 이벤트를 기록하고 추적하는 사후 감사 도구로, 실시간 자동 교정 기능은 없다).

**정답: B**

**해설**: **AWS Config 규칙**은 리소스 구성을 지속적으로 평가해 비준수 상태를 탐지하며, 여기에 **Systems Manager Automation 문서**를 교정 조치(remediation action)로 연결하면 비준수 리소스가 발견되는 즉시 사람의 개입 없이 자동으로 원하는 상태로 되돌릴 수 있습니다. 이는 반복적인 설정 오류를 신속하고 일관되게 교정해야 하는 요구 사항에 가장 적합한 조합입니다.

**왜 다른 보기는 오답인가**
- A: 알림 후 수동 조치는 사람이 개입해야 하므로 자동 교정이라는 목표를 충족하지 못하고 대응이 지연됩니다.
- C: Trusted Advisor는 모범 사례 대비 점검 결과를 보여주는 권고 도구로 자동 교정 기능은 없습니다.
- D: CloudTrail은 API 호출 이력을 기록하는 사후 감사 도구로, 실시간으로 리소스를 교정하는 기능은 제공하지 않습니다.

> 💡 **시험 꿀팁**: "규정 위반을 자동으로 교정"이라는 요구 사항은 AWS Config 규칙 + Systems Manager Automation 조합을 가리킵니다.

## QUESTION 479

**문제**: 한 연구 기관은 대용량 공개 데이터셋을 S3 버킷에 저장해 전 세계 연구자들이 자유롭게 다운로드할 수 있도록 제공하고 있습니다. 그러나 다운로드 요청이 급증하면서 데이터 전송 비용이 기관 예산을 초과하고 있습니다. 데이터셋 자체는 계속 공개적으로 유지하되, 데이터를 실제로 내려받는 사용자가 전송 비용을 부담하도록 하고 싶습니다. 어떤 기능을 사용해야 합니까?

**보기**
- A. 버킷을 프라이빗으로 전환하고 사전 서명된 URL을 배포한다(버킷 소유자 계정이 여전히 데이터 전송 비용을 부담하며, 공개 데이터셋의 개방성과 배포 편의성도 떨어진다).
- B. CloudFront 배포를 앞단에 구성해 캐싱한다(캐싱으로 오리진 요청은 줄어들 수 있지만 배포 자체의 데이터 전송 비용은 여전히 버킷/배포 소유자 계정이 부담한다).
- C. **S3 버킷에 Requester Pays를 활성화해 다운로드하는 사용자가 데이터 전송 비용을 부담하도록 한다.**
- D. S3 Transfer Acceleration을 활성화한다(전송 속도를 높여주는 기능일 뿐 비용을 요청자에게 전가하는 기능은 아니다).

**정답: C**

**해설**: **S3 Requester Pays**를 버킷에 활성화하면, 버킷 소유자는 스토리지 비용만 부담하고 데이터를 다운로드하는 요청자가 자신의 AWS 계정으로 데이터 전송 비용을 지불하게 됩니다. 요청자는 요청 시 자신의 계정 정보를 명시해야 하므로, 공개 데이터셋을 계속 개방적으로 제공하면서도 급증하는 전송 비용 부담을 다운로드하는 쪽으로 옮길 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 버킷을 프라이빗으로 바꾸고 서명된 URL을 발급해도 전송 비용은 여전히 버킷 소유자가 부담하며, 공개 데이터셋의 접근 편의성도 떨어집니다.
- B: CloudFront 캐싱은 오리진으로의 반복 요청을 줄여 비용을 절감하는 데 도움이 되지만, 배포를 통한 데이터 전송 비용 자체는 여전히 소유자 계정에 청구됩니다.
- D: Transfer Acceleration은 업로드/다운로드 속도를 개선하는 기능으로 비용 부담 주체를 바꾸지는 않습니다.

> 💡 **시험 꿀팁**: "다운로드하는 사용자가 전송 비용을 부담"하게 하려면 S3 Requester Pays를 떠올리세요.

## QUESTION 480

**문제**: 한 회사는 메모리에 대용량 캐시와 세션 상태를 유지하는 상태 저장(stateful) 분석 애플리케이션을 EC2에서 운영하고 있습니다. 이 인스턴스를 야간에 잠시 내렸다가 아침에 다시 사용하려고 하는데, 매번 인스턴스를 중지 후 재시작하면 메모리 내용이 사라져 애플리케이션이 캐시를 처음부터 다시 채우는 데 오랜 시간이 걸립니다. 인스턴스를 재개할 때 메모리 상태를 그대로 유지한 채 빠르게 복구하고 싶습니다. 어떤 기능을 사용해야 합니까?

**보기**
- A. 인스턴스를 중지(Stop)했다가 다시 시작한다(중지 시 RAM의 내용이 모두 사라지므로 재시작 후 애플리케이션이 메모리 상태를 처음부터 다시 구성해야 하는 콜드 부팅이 발생한다).
- B. 인스턴스를 종료(Terminate)하고 새 인스턴스를 시작한다(루트 볼륨 설정에 따라 EBS까지 삭제될 수 있으며, 메모리 상태는 당연히 전혀 보존되지 않는다).
- C. Auto Scaling으로 새 인스턴스를 교체 투입한다(완전히 새로운 인스턴스이므로 기존 메모리 상태가 전혀 보존되지 않는다).
- D. **EC2 Hibernate를 사용해 인스턴스를 최대 절전 모드로 전환하고, 재개 시 메모리 상태를 그대로 복원한다.**

**정답: D**

**해설**: **EC2 Hibernate**를 사용하면 인스턴스를 최대 절전 모드로 전환할 때 RAM의 내용이 EBS 루트 볼륨에 저장되고, 인스턴스를 다시 시작하면 저장된 메모리 상태가 그대로 복원되어 운영체제 부팅, 애플리케이션 재시작, 캐시 재구성 과정을 생략할 수 있습니다. 이는 메모리 상태를 유지한 채 빠르게 재개해야 하는 상태 저장 워크로드에 정확히 맞는 기능입니다.

**왜 다른 보기는 오답인가**
- A: 일반적인 중지(Stop)는 RAM 내용을 보존하지 않으므로 재시작 시 콜드 부팅과 동일하게 메모리 상태를 다시 구성해야 합니다.
- B: 종료는 인스턴스 자체를 삭제하는 작업으로 메모리 상태 보존과는 전혀 무관하며 손실 위험이 가장 큽니다.
- C: Auto Scaling으로 교체된 인스턴스는 완전히 새로운 인스턴스이므로 이전 인스턴스의 메모리 상태를 이어받을 수 없습니다.

> 💡 **시험 꿀팁**: "메모리 상태를 유지한 채 빠르게 재개"라는 요구 사항은 EC2 Hibernate를 가리키는 핵심 키워드입니다.
