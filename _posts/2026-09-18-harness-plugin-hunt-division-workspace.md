같이 이 사이드 프로젝트를 만들던 동료가 어느 날 `develop` 브랜치에 커밋 3개를 올렸다. 커밋 메시지는 "개발 자동화 하네스 초기 구성" — Parser, StoreAPI, FlowLayout, Frontend, QA 이렇게 역할이 나뉜 에이전트 5개와, 그걸 조율하는 오케스트레이터 스킬이 통째로 들어와 있었다. `CLAUDE.md`에는 "이 프로젝트에서 개발 요청이 오면 무조건 이 오케스트레이터를 써라"는 트리거까지 박혀 있었다.

궁금했다. "이걸 실제로 돌리면 여러 에이전트가 알아서 역할을 나눠서 일을 하나?" 확인해보고 싶어서 부문(워크스페이스)별로 화면을 분리하는 기능을 이 오케스트레이터한테 맡겨보기로 했다.

## 1. 스킬은 있는데 도구가 없다

새로 받은 스킬 파일을 로컬 세션에서 바로 불러보려 했더니 "Unknown skill" 에러가 났다. 세션이 시작될 때 스킬 목록이 고정되는 구조라, 방금 pull 받은 스킬은 세션을 새로 열어야 인식된다는 걸 알게 됐다.

그런데 세션을 새로 열어 스킬이 인식된 뒤에도 진짜 문제는 따로 있었다. 오케스트레이터 스킬 문서를 열어보니 `TeamCreate`, `TaskCreate`라는 도구로 에이전트 팀을 구성하라고 적혀 있는데, 그 이름의 도구 자체가 이 환경에 없었다. 전체 도구 목록을 뒤져봐도 안 나온다. 대신 "팀원(teammate)에게 메시지 보내기" 같은 주변 개념만 존재했다 — 팀이라는 개념은 있는데, 그 팀을 새로 만드는 진입점만 빠져 있는 상태였다.

## 2. 마켓플레이스를 뒤지다 다른 회사를 만났다

프로젝트의 `.claude/settings.json`에는 이런 설정이 있었다.

```json
{
  "enabledPlugins": {
    "harness@harness-marketplace": true
  }
}
```

"플러그인이 활성화만 되어 있고 설치가 안 된 거구나" 싶어서 마켓플레이스 출처를 찾아 나섰다.

- 이 repo의 git 히스토리 전체를 뒤져도 `harness-marketplace`가 어디서 왔는지 안 나왔다. 동료 컴퓨터에만 등록해둔 설정이었던 모양이다.
- 로컬 전역 설정(`known_marketplaces.json`)에도 없었다.
- 심지어 Anthropic 공식 플러그인 카탈로그(3,000개가 넘는 플러그인)를 통째로 내려받아 이름으로 검색해봐도 없었다.

검색 엔진에 "Harness marketplace"라고 쳐봤더니, 전혀 다른 회사가 튀어나왔다. CI/CD 소프트웨어 딜리버리 플랫폼으로 유명한 **Harness.io**였다. "하네스"라는 흔한 영어 단어를 프로젝트 이름으로 써서 생긴 완전한 우연의 일치였는데, 잠깐이지만 이 회사 마켓플레이스를 설치해야 하나 진지하게 고민했다.

결국 답은 공식 지원 문서에 있었다. Claude 플러그인 사용법 문서와 Cowork 시작 가이드를 찾아 읽어보니, **멀티에이전트 "팀" 기능은 Cowork 환경에서만 동작한다**고 적혀 있었다. 로컬 CLI에서 플러그인을 아무리 뒤져도 안 나왔던 이유가 그거였다.

## 3. Cowork에 넘겼더니, 진짜로 일이 됐다

Cowork을 열고, GitHub repo와 브랜치를 명시한 뒤 요구사항을 프롬프트로 정리해서 넘겼다.

요구사항의 핵심은 세 가지였다.

- DB는 쪼개지 않는다. 부문 1/2/3이 프로세스 데이터를 공유하되, "이 프로세스는 몇 부문 것"이라는 매핑만 따로 둔다.
- 플로우차트 그래프는 **항상 전체 데이터로 조립**한다. 부문별로 미리 걸러서 조립하면, 부문 경계를 넘나드는 프로세스 연결(handoff)이 있을 때 그래프 조립 단계에서 그 연결선이 끊겨버릴 수 있어서다.
- 부문 경계(어떤 프로세스가 몇 부문 소속인지)는 아직 모른다. 나중에 회의로 정해질 예정이라, 지금은 빈 뼈대만 만들어둔다.

Cowork은 이 오케스트레이터가 정의한 에이전트 경계(Store/FlowLayout/Frontend/QA)를 그대로 지키면서, `division_roots`라는 신규 컬렉션과 `resolveDivisionProcessIds`라는 리졸버 함수를 만들었다. 리졸버는 부문에 등록된 id가 상위(macro) 프로세스면 하위 프로세스까지 재귀적으로 펼치고, 순환 참조가 있어도 안전하게 막도록 짜여 있었다. 기존 그래프 조립 함수는 건드리지 않고, 조립이 끝난 결과에만 후처리로 필터를 씌우는 방식이라 처음 요구했던 "핸드오프 연결 안 끊김" 조건도 잘 지켰다.

다만 Cowork 자신의 리눅스 VM 샌드박스에서는 실제 서버를 띄워 검증하지 못했다고 보고했다. esbuild 네이티브 바이너리가 그 VM 아키텍처와 안 맞고, 컴파일된 서버를 직접 실행해도 마운트된 폴더의 동기 파일 입출력에서 멈춰버린다는 것이었다. "실제 PC에서 확인해보라"는 권고와 함께 작업을 마무리했다.

## 4. AI 보고서는 참고 자료지, 사실이 아니다

Cowork은 작업을 마치면서 "리졸버·필터 로직을 9개 케이스로 단위 테스트했고 전부 통과했다"고 보고했다. 그런데 그 테스트 코드 자체를 같이 받은 게 아니라 결과만 문장으로 전달받은 상황이라, 이 주장을 그대로 믿고 넘어가지 않았다. 대신 로컬 PC에서 직접 서버를 띄우고, 실제 API를 호출해서 눈으로 확인했다.

```
필터 없음(전체) 노드: 20개, 엣지: 24개   ← 기존 동작 그대로
division-1(미배정 상태) 노드: 0개, 엣지: 0개   ← 에러 아니고 정상적인 빈 상태
```

여기서 실제로 버그를 하나 발견했다. 프로세스를 업로드해서 특정 부문에 걸어둔 다음 그 프로세스를 삭제해봤더니, `division_roots`에 죽은 참조가 그대로 남아있었다. 기존 코드에는 프로세스 삭제 시 그 프로세스가 발신하던 엣지, 하위 스텝, Pain Point 같은 "고아 데이터"를 같이 정리하는 로직이 이미 있었는데, 새로 추가된 `division_roots`만 그 목록에서 빠져 있었다. 기존 패턴 그대로 삭제할 때 부문 목록에서도 참조를 지우는 함수 하나 추가해서 고쳤다.

Cowork의 보고서에는 "`db.ts`, `store.firestore.ts` 이 두 파일은 내가 시작하기 전부터 이미 크게 바뀌어 있었고, 나는 손대지 않았다"는 일종의 책임회피성 메모도 있었다. 실제로 로컬에서 그 두 파일의 git diff를 확인해보니 아무 변경사항도 없었다. Cowork 혼자 쓰던 리눅스 VM 안에서만 보였던 뭔가였던 것 같은데, 그냥 믿고 넘어갔으면 있지도 않은 파일 충돌을 붙잡고 헤맸을 거다.

그 밖에도 Cowork이 권한 문제로 못 지운 stale `.git/index.lock` 파일과, 검증용으로 만들었다가 옮겨둔 임시 스크립트를 정리하는 건 결국 사람이 직접 해야 했다.

## 5. "그냥 부문별로 업로드하면 되는 거 아니야?"

기능이 다 만들어졌다고 생각했는데, 실제로 써보려니 이상했다. Cowork이 만든 방식은 관리자가 API로 부문 소속 프로세스 id 목록을 직접 입력하는 방식이었다. 그런데 정작 원했던 건 훨씬 단순했다. 부문을 선택하고 문서를 업로드하면, 그 문서에서 만들어진 프로세스가 알아서 그 부문 것으로 잡히길 바랐다.

코드를 다시 열어봤다. 업로드 API에는 부문이라는 개념 자체가 없었다. 업로드 = 문서 파싱 = 프로세스 생성이었고, 부문 배정은 완전히 별개의 수동 작업이었다.

이 부분은 직접 채워 넣었다. 업로드 API가 `division` 파라미터를 받아서, 파싱이 끝나면 그 프로세스 id를 해당 부문 목록에 자동으로 추가하도록 했다(이미 들어있으면 중복 추가하지 않는다). 실제로 테스트 문서 하나를 1부문 선택 상태에서 업로드해보면 이렇게 바뀐다.

```
업로드 전:  1부문 process_ids: []
업로드 후:  1부문 process_ids: ["S00"]   ← 사람이 손대지 않아도 자동으로 추가됨
```

화면 UI도 처음엔 부문마다 버튼 탭을 나열하는 방식이었는데, 협업 툴에서 흔히 보던 좌상단 드롭다운 워크스페이스 전환 방식으로 바꿨다. 클릭하면 현재 부문 이름이 보이고, 눌러서 목록에서 다른 부문으로 전환하는 식이다.

이 UI는 브라우저를 직접 열어서 클릭해가며 검증했다. 드롭다운이 열리고 닫히는 것, 부문을 바꿨을 때 캔버스와 문서함·히스토리 화면이 같이 갱신되는 것까지는 잘 됐는데, 부문 목록이 저장 순서 그대로 나와서 1·2·3 순서가 뒤죽박죽인 사소한 문제가 하나 나왔다. id 기준으로 정렬 한 줄만 추가해서 마무리했다.

## 마무리

"하네스 엔지니어링 한번 써보자"로 시작한 일이었는데, 막상 겪어보니 절반은 이 하네스가 로컬에선 아예 안 되고 Cowork에서만 돌아간다는 걸 알아내는 일이었고, 나머지 절반은 Cowork이 돌리고 나온 결과를 믿지 않고 다시 확인하는 일이었다.

Cowork이 만들어준 결과물을 그대로 커밋하지 않길 잘했다. 로컬에서 직접 재현해보지 않았으면 있지도 않은 파일 충돌을 걱정했을 거고, 삭제할 때 고아 데이터 남는 버그도 못 잡았을 거다. 부문 배정을 관리자가 API로 일일이 입력해야 하는 워크플로우도 그대로 나갔을 거고. 오케스트레이터가 아무리 정교해도, 그 결과물이 실제로 쓸 만한지 판단하는 건 여전히 사람 몫이다.
