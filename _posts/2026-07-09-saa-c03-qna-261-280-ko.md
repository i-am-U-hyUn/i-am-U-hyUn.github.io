## QUESTION 261

**문제**: 한 회사가 전 세계 고객을 대상으로 소매 웹 사이트를 배포했습니다. 웹 사이트는 여러 가용 영역의 Auto Scaling 그룹에서 실행되는 Amazon EC2 인스턴스에서 동작하며, 앞단에는 Elastic Load Balancer가 있습니다. 회사는 고객이 웹 사이트에 접속할 때 사용하는 디바이스에 따라 서로 다른 버전의 콘텐츠를 제공하려고 합니다. 이 요구 사항을 충족하려면 솔루션 설계자는 어떤 작업 조합을 수행해야 합니까? (2개 선택)

**보기**
- A. **여러 버전의 콘텐츠를 캐싱하도록 Amazon CloudFront를 구성한다.**
- B. 트래픽을 다른 인스턴스로 전달하도록 Network Load Balancer에서 호스트 헤더를 구성한다(NLB는 L4 로드밸런서로 호스트 헤더 기반 라우팅 자체를 지원하지 않음).
- C. **User-Agent 헤더를 기반으로 사용자에게 특정 객체를 전달하도록 Lambda@Edge 함수를 구성한다.**
- D. AWS Global Accelerator를 구성하고 NLB로 요청을 전달한 뒤, 다른 EC2 인스턴스로 호스트 기반 라우팅을 수행하도록 NLB를 구성한다(Global Accelerator는 성능/가용성 개선용이며 NLB는 호스트 기반 라우팅을 지원하지 않아 디바이스별 콘텐츠 요구를 다루지 못함).
- E. AWS Global Accelerator를 구성하고 NLB로 요청을 전달한 뒤, 다른 EC2 인스턴스로 경로 기반 라우팅을 수행하도록 NLB를 구성한다(NLB는 경로 기반 라우팅도 지원하지 않으며 디바이스 유형과 무관한 접근 방식).

**정답: A, C**

**해설**
**Lambda@Edge**를 CloudFront 뷰어 요청 이벤트에 연결하면 요청의 **User-Agent 헤더**를 검사해 모바일/데스크톱/태블릿 등 디바이스 유형을 판별하고, 그에 맞는 객체를 반환하도록 응답을 즉시 커스터마이징할 수 있습니다. 이렇게 생성된 디바이스별 콘텐츠는 **CloudFront**가 에지 로케이션에 각각 캐싱해 두므로, 이후 동일 디바이스 유형의 요청은 성능 저하 없이 빠르게 제공됩니다. 즉 A(다중 버전 캐싱)와 C(디바이스 판별 로직)가 결합되어야 요구 사항이 완성됩니다.

**왜 다른 보기는 오답인가**
- B: Network Load Balancer는 OSI 4계층에서 동작하므로 호스트 헤더 같은 애플리케이션 계층 정보를 기반으로 라우팅할 수 없습니다.
- D: Global Accelerator는 네트워크 성능·가용성 향상이 목적이며, NLB 역시 호스트 기반 라우팅 기능이 없어 디바이스별 콘텐츠 제공과 무관합니다.
- E: 마찬가지로 NLB는 경로 기반 라우팅을 지원하지 않으며, 이 조합은 디바이스 유형 판별과 아무 관련이 없습니다.

> 💡 **시험 꿀팁**: "**디바이스/User-Agent에 따라 다른 콘텐츠**"라는 요구가 나오면 **Lambda@Edge(판별) + CloudFront(캐싱)** 조합이 표준 정답입니다.

## QUESTION 262

**문제**: 회사가 다중 계층 웹 애플리케이션에 Amazon ElastiCache를 사용할 계획입니다. 솔루션 설계자는 ElastiCache 클러스터용 캐시 VPC와 애플리케이션의 EC2 인스턴스용 앱 VPC를 생성했으며, 두 VPC 모두 us-east-1 리전에 있습니다. 애플리케이션의 EC2 인스턴스가 ElastiCache 클러스터에 접근할 수 있도록 해야 합니다. 이 요구 사항을 가장 비용 효율적으로 충족하는 솔루션은 무엇입니까?

**보기**
- A. **두 VPC 간에 피어링 연결을 생성하고 양쪽 VPC의 라우팅 테이블에 피어링 경로를 추가한다. ElastiCache 클러스터의 보안 그룹에서 애플리케이션 보안 그룹의 인바운드 트래픽을 허용하도록 구성한다.**
- B. 전송(Transit) VPC를 생성하고 캐시 VPC 및 앱 VPC의 라우팅 테이블이 전송 VPC를 경유하도록 업데이트한다. ElastiCache 클러스터의 보안 그룹에서 인바운드를 허용한다(추가 VPC와 라우팅 인프라가 필요해 불필요한 비용과 복잡성이 발생).
- C. 두 VPC 간 피어링 연결을 생성하고 라우팅 테이블도 구성하지만, 인바운드 규칙은 피어링 연결의 보안 그룹에 설정한다(VPC 피어링 연결 자체에는 보안 그룹을 연결할 수 없으므로 성립하지 않는 구성).
- D. 전송 VPC를 생성해 트래픽을 경유시키고, 인바운드 규칙을 전송 VPC의 보안 그룹에 구성한다(B와 마찬가지로 불필요한 전송 VPC 비용이 추가됨).

**정답: A**

**해설**
**VPC 피어링**은 두 VPC 간 트래픽을 직접 라우팅하는 무료(데이터 전송 요금만 발생) 연결 방식으로, 별도의 중계 인프라가 필요 없습니다. 피어링 연결을 만들고 양쪽 라우팅 테이블에 상대 VPC 대역으로 가는 경로를 추가한 뒤, **ElastiCache 클러스터의 보안 그룹**에서 애플리케이션 보안 그룹의 인바운드를 허용하면 앱 VPC의 EC2 인스턴스가 별도 비용 없이 캐시 VPC의 ElastiCache에 접근할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: Transit VPC를 새로 구성하려면 추가 EC2/VPN 리소스가 필요해 이 단순한 2-VPC 연결 시나리오에는 과도한 비용과 복잡성을 더합니다.
- C: VPC 피어링 연결(peering connection) 자체는 보안 그룹을 가질 수 있는 리소스가 아니므로, 이 옵션이 설명하는 구성은 애초에 적용할 수 없습니다.
- D: B와 동일하게 불필요한 Transit VPC 리소스 비용이 추가되며, 이 요구 사항에는 과도한 설계입니다.

> 💡 **시험 꿀팁**: **같은 리전 내 두 VPC를 저비용으로 연결**해야 한다면 우선적으로 **VPC 피어링**을 떠올리세요. 피어링 연결 자체에는 보안 그룹을 붙일 수 없다는 점도 기억해 두면 오답 함정을 피할 수 있습니다.

## QUESTION 263

**문제**: 회사가 여러 마이크로서비스로 구성된 애플리케이션을 컨테이너 기술로 AWS에 배포하려고 합니다. 유지 관리와 확장에 드는 지속적인 노력을 최소화해야 하며, 회사는 추가 인프라를 직접 관리할 수 없습니다. 이 요구 사항을 충족하려면 솔루션 설계자는 어떤 작업 조합을 수행해야 합니까? (2개 선택)

**보기**
- A. **Amazon Elastic Container Service(ECS) 클러스터를 배포한다.**
- B. 여러 가용 영역에 걸친 EC2 인스턴스에 Kubernetes 제어 평면을 직접 배포한다(제어 평면 운영·패치·고가용성 구성을 회사가 직접 관리해야 해 요구 사항에 위배).
- C. EC2 시작 유형으로 ECS 서비스를 배포하고 원하는 태스크 수를 2 이상으로 지정한다(여전히 EC2 인스턴스 프로비저닝·패치·용량 관리가 필요함).
- D. **Fargate 시작 유형으로 ECS 서비스를 배포하고 원하는 태스크 수를 2 이상으로 지정한다.**
- E. 여러 가용 영역에 걸친 EC2 인스턴스에 Kubernetes 작업자 노드를 배포하고 마이크로서비스별로 2개 이상의 복제본을 지정한다(작업자 노드용 EC2까지 직접 관리해야 하므로 인프라 관리 부담이 큼).

**정답: A, D**

**해설**
**AWS Fargate**는 컨테이너를 실행할 EC2 인스턴스나 클러스터를 프로비저닝·패치·확장할 필요가 없는 서버리스 컴퓨팅 엔진입니다. **ECS 클러스터**를 생성하고 그 위에 **Fargate 시작 유형**으로 서비스를 배포하면, AWS가 기반 인프라를 전담 관리하므로 회사는 태스크 정의와 원하는 태스크 수만 지정하면 됩니다. 이는 "추가 인프라를 관리할 수 없다"는 제약과 "유지 관리/확장 노력 최소화" 요구를 동시에 만족합니다.

**왜 다른 보기는 오답인가**
- B: 자체 관리형 Kubernetes 제어 평면은 고가용성 구성과 업그레이드를 회사가 직접 책임져야 해 관리형 서비스의 장점을 잃습니다.
- C: EC2 시작 유형은 여전히 인스턴스 크기 조정, 패치, 용량 계획 등의 운영 부담이 남아 있어 Fargate보다 효율이 떨어집니다.
- E: 작업자 노드용 EC2까지 직접 배포·확장해야 하므로 "추가 인프라 관리 불가" 요구 사항과 정면으로 충돌합니다.

> 💡 **시험 꿀팁**: "**컨테이너 + 인프라 관리 최소화**" 조합이 나오면 **ECS(또는 EKS) + Fargate**가 표준 정답입니다.

## QUESTION 264

**문제**: 회사가 Amazon Route 53으로 트래픽을 전달받는 10개 이상의 EC2 인스턴스로 웹 애플리케이션을 운영 중이며, 이따금 접속 시 시간 초과 오류가 발생합니다. 네트워킹 팀은 일부 DNS 쿼리가 비정상 인스턴스의 IP 주소를 반환해 시간 초과가 발생함을 확인했습니다. 이 시간 초과 오류를 해결하려면 솔루션 설계자는 무엇을 구현해야 합니까?

**보기**
- A. 각 EC2 인스턴스에 대해 Route 53 단순 라우팅 정책 레코드를 생성하고 상태 확인을 연결한다(상태가 나쁜 레코드를 배제할 뿐, 정상 인스턴스로 트래픽을 자동 분산하는 로드밸런싱 기능이 없음).
- B. 각 EC2 인스턴스에 대해 Route 53 장애 조치 라우팅 정책 레코드를 생성하고 상태 확인을 연결한다(1차/2차 페일오버 구조에 적합할 뿐, 다수 인스턴스 간 정상 노드로의 부하 분산에는 적합하지 않음).
- C. EC2 인스턴스를 오리진으로 하는 Amazon CloudFront 배포를 생성하고 상태 확인을 EC2 인스턴스에 연결한다(CloudFront는 CDN으로서 캐싱·전송 최적화가 목적이며 백엔드 상태 기반 트래픽 분산을 직접 수행하지 않음).
- D. **상태 확인이 포함된 Application Load Balancer(ALB)를 EC2 인스턴스 앞에 생성하고, Route 53이 ALB를 가리키도록 구성한다.**

**정답: D**

**해설**
**Application Load Balancer**는 등록된 대상에 대해 주기적으로 상태 확인을 수행하고, 비정상 인스턴스를 자동으로 트래픽 분산 대상에서 제외합니다. Route 53의 레코드가 개별 EC2 인스턴스가 아닌 **ALB**를 가리키도록 구성하면, DNS 쿼리는 항상 ALB의 주소를 반환하고 실제 라우팅 결정은 ALB가 실시간 상태 확인 결과에 따라 내리므로 비정상 인스턴스로 인한 시간 초과가 근본적으로 사라집니다.

**왜 다른 보기는 오답인가**
- A: 레코드별 상태 확인은 문제 인스턴스를 DNS 응답에서 제외할 수는 있지만, 정상 인스턴스 간 부하를 고르게 분산하는 로드밸런싱 기능은 제공하지 않습니다.
- B: 장애 조치 라우팅은 기본/보조 두 엔드포인트 간 전환에 최적화된 정책으로, 다수의 동등한 인스턴스에 대한 상시 부하 분산 용도가 아닙니다.
- C: CloudFront는 콘텐츠 전송 가속과 캐싱에 특화된 서비스로, 오리진의 상태를 기준으로 트래픽을 여러 백엔드에 분산하는 로드밸런서 기능은 제공하지 않습니다.

> 💡 **시험 꿀팁**: "**여러 인스턴스 중 비정상 노드로 트래픽이 가서 타임아웃**"이라는 패턴이 나오면 **Route 53을 ALB로 향하게 하고 ALB가 상태 확인/분산을 담당**하는 구조가 표준 정답입니다.

## QUESTION 265

**문제**: 솔루션 설계자가 웹, 애플리케이션, 데이터베이스 계층으로 구성된 고가용성 애플리케이션을 설계해야 합니다. HTTPS 콘텐츠 전송은 전송 시간을 최소화하면서 가능한 한 에지에 가깝게 이루어져야 합니다. 이 요구 사항을 충족하면서 가장 안전한 솔루션은 무엇입니까?

**보기**
- A. 퍼블릭 서브넷의 여러 중복 EC2 인스턴스로 퍼블릭 ALB를 구성하고, 퍼블릭 ALB를 오리진으로 하는 CloudFront로 HTTPS 콘텐츠를 제공한다(EC2 인스턴스가 퍼블릭 서브넷에 직접 노출되어 공격 표면이 커짐).
- B. 프라이빗 서브넷의 여러 중복 EC2 인스턴스로 퍼블릭 ALB를 구성하고, EC2 인스턴스를 오리진으로 하는 CloudFront로 HTTPS 콘텐츠를 제공한다(CloudFront가 ALB를 거치지 않고 EC2를 직접 오리진으로 지정해 로드밸런싱 이점을 잃고 인스턴스가 사실상 노출됨).
- C. **프라이빗 서브넷의 여러 중복 EC2 인스턴스로 퍼블릭 ALB를 구성하고, 퍼블릭 ALB를 오리진으로 하는 CloudFront로 HTTPS 콘텐츠를 제공한다.**
- D. 퍼블릭 서브넷의 여러 중복 EC2 인스턴스로 퍼블릭 ALB를 구성하고, EC2 인스턴스를 오리진으로 하는 CloudFront로 HTTPS 콘텐츠를 제공한다(퍼블릭 서브넷 노출과 EC2 직접 오리진 지정이 겹쳐 보안상 가장 취약).

**정답: C**

**해설**
**퍼블릭 ALB는 인터넷 요청을 받는 진입점 역할**을 하고, 실제 연산을 수행하는 EC2 인스턴스는 **프라이빗 서브넷**에 두어 외부에서 직접 접근할 수 없게 합니다. 여기에 **CloudFront가 ALB를 오리진으로 지정**해 HTTPS 콘텐츠를 에지 로케이션에서 전송하면, 전송 지연은 최소화하면서도 EC2 인스턴스를 인터넷에 전혀 노출하지 않는 가장 안전한 구조가 완성됩니다.

**왜 다른 보기는 오답인가**
- A: EC2 인스턴스가 퍼블릭 서브넷에 있어 잘못된 보안 그룹 설정이나 라우팅 실수만으로도 인터넷에 직접 노출될 위험이 있습니다.
- B: CloudFront가 ALB의 로드밸런싱을 우회해 EC2를 직접 오리진으로 삼으면 개별 인스턴스의 퍼블릭 엔드포인트가 필요해져 보안과 가용성 모두에서 불리합니다.
- D: 퍼블릭 서브넷 배치와 EC2 직접 오리진 지정이 동시에 적용되어 네 옵션 중 보안이 가장 취약합니다.

> 💡 **시험 꿀팁**: "**HTTPS 콘텐츠를 에지에서 안전하게 전송**"하는 표준 패턴은 **CloudFront → 퍼블릭 ALB(진입점) → 프라이빗 서브넷 EC2(백엔드)**입니다.

**보기**
- A. **AWS Global Accelerator에서 액셀러레이터를 구성하고, 애플리케이션이 수신하는 포트에 대한 리스너를 추가해 각 리전의 리전 엔드포인트에 연결한다. ALB를 엔드포인트로 등록한다.**

- C: S3를 오리진으로 하는 구성은 정적 콘텐츠 전송에는 적합하지만, 동적인 애플리케이션 상태 모니터링과는 관련이 없습니다.

> 💡 **시험 꿀팁**: "**여러 리전에 걸친 엔드포인트의 상태 확인 + 가장 가까운 정상 엔드포인트로 라우팅**"이 필요하면 **AWS Global Accelerator**가 표준 정답입니다.

> 💡 **시험 꿀팁**: "**거의 실시간 수집 + 형식 변환/암호화 + 최소 운영**" 조합이 나오면 **Kinesis Data Firehose + Kinesis Data Analytics**가 표준 정답입니다.

- D: 관계형 모델을 NoSQL로 바꾸는 것은 쿼리와 스키마 전체를 다시 설계해야 하는 대규모 마이그레이션으로, 최소 변경과 거리가 멉니다.

> 💡 **시험 꿀팁**: "**엔드포인트만 바꿔서 연결 부하를 줄이고 싶다**"는 조건이면 **RDS Proxy**, "**애플리케이션 로직까지 바꿔 캐싱하겠다**"면 **ElastiCache**로 구분해서 기억하세요.

> 💡 **시험 꿀팁**: "**같은 SQL을 그대로, 읽기 전용 부하만 분리**"하고 싶다면 **RDS 읽기 복제본**이 표준 정답입니다.

- B. 서버 측 암호화를 사용해 S3에 업로드되는 데이터를 암호화한다(S3에 도달한 이후, 즉 저장 시점에 암호화가 적용되므로 "업로드되기 전" 암호화 요구를 충족하지 못함).
- C. S3 업로드 시 SSE-S3 서버 측 암호화를 강제하는 버킷 정책을 만든다(마찬가지로 데이터가 S3에 도착한 뒤 암호화되는 방식이라 업로드 이전 암호화 요건에 부합하지 않음).
- D. 기본 AWS KMS 키로 S3 버킷을 암호화하는 옵션을 활성화한다(SSE-KMS 역시 S3 서버 측에서 저장 시 암호화가 적용되는 방식으로 동일한 이유로 부적합).

**정답: A**

**해설**
**클라이언트 측 암호화**는 데이터를 S3로 전송하기 전에 클라이언트(또는 그 앞단)에서 직접 암호화하는 방식으로, S3는 이미 암호화된 상태의 데이터만 수신합니다. 이 방식은 암호화 키를 고객이 직접 관리하므로 S3가 평문 데이터나 키에 접근할 수 없고, HTTPS를 통한 전송과 결합하면 "업로드 이전 암호화"와 "전송 중 암호화" 요구를 모두 만족합니다.

**왜 다른 보기는 오답인가**
- B: 서버 측 암호화는 S3가 데이터를 수신한 이후 저장 시점에 암호화를 적용하는 방식이라 "업로드되기 전에 암호화"라는 조건을 충족하지 못합니다.
- C: 버킷 정책으로 SSE-S3를 강제해도 암호화 시점은 S3 내부(저장 시)이므로 B와 동일한 이유로 부적합합니다.
- D: SSE-KMS도 결국 S3 서버 측에서 수행되는 저장 시 암호화이며, 업로드 이전 암호화 요건과는 무관합니다.

> 💡 **시험 꿀팁**: "**S3에 도달하기 전에 이미 암호화되어 있어야 한다**"는 표현이 나오면 서버 측 암호화가 아니라 **클라이언트 측 암호화**를 골라야 합니다.

## QUESTION 271

**문제**: 솔루션 설계자가 야간 배치 처리 작업이 원하는 EC2 용량에 도달하기까지 자동 조정에 1시간이 걸리는 것을 관찰했습니다. 최대 용량은 매일 밤 동일하고, 배치 작업은 항상 오전 1시에 시작됩니다. 솔루션 설계자는 원하는 EC2 용량에 빠르게 도달하고, 배치 작업 완료 후에는 Auto Scaling 그룹이 다시 축소될 수 있는 비용 효율적인 솔루션이 필요합니다. 무엇을 해야 합니까?

**보기**
- A. Auto Scaling 그룹의 최소 용량을 늘린다(최소 용량을 높이면 배치 작업이 없는 시간에도 불필요한 인스턴스가 상시 유지되어 비용이 늘어남).
- B. Auto Scaling 그룹의 최대 용량을 늘린다(최대치를 늘려도 도달 속도 자체는 빨라지지 않으며 오히려 과도한 확장의 여지만 커짐).
- C. **원하는 컴퓨팅 수준으로 확장하도록 예약된 확장(scheduled scaling)을 구성한다.**
- D. 매 조정 작업마다 더 많은 EC2 인스턴스를 추가하도록 조정 정책을 변경한다(반응형 정책은 여전히 지표 임계값을 넘어야 트리거되므로 예측 가능한 정시 배치 시작에는 예약된 확장만큼 즉각적이지 않음).

**정답: C**

**해설**
배치 작업이 매일 정확히 오전 1시에 시작되고 필요한 용량도 매일 동일하다면, 이는 **예측 가능한 스케줄** 패턴입니다. **예약된 확장(Scheduled Scaling)**을 구성하면 지정한 시각에 Auto Scaling 그룹의 원하는 용량을 즉시 목표치로 설정할 수 있어, 지표가 임계값을 넘기를 기다릴 필요 없이 배치 작업 시작과 동시에 필요한 용량을 확보합니다. 작업이 끝난 뒤에는 다시 별도의 예약(또는 동적 조정)으로 축소해 비용을 절감할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 최소 용량 증가는 배치 시간 외에도 인스턴스를 상시 유지시켜 비용 효율성 요구에 위배됩니다.
- B: 최대 용량을 늘리는 것은 확장 상한을 높일 뿐, 목표 용량에 도달하는 속도를 개선하지 않습니다.
- D: 조정 폭을 키워도 여전히 CPU 등 지표가 임계값을 넘어야 확장이 시작되는 반응형 구조라서, 정시에 즉시 확장되는 예약된 확장보다 느립니다.

> 💡 **시험 꿀팁**: "**매일 정해진 시각에 정해진 용량**"이 필요한 패턴은 반응형 정책이 아니라 **예약된 확장(Scheduled Scaling)**이 표준 정답입니다.

## QUESTION 272

**문제**: 회사가 ALB 뒤의 EC2 플릿에서 동적 웹 사이트를 운영하며, 전 세계 고객을 위해 여러 언어를 지원해야 합니다. 아키텍처는 us-west-1 리전에서만 실행되어 다른 지역 사용자에게 높은 요청 지연이 발생하고 있습니다. 사용자 위치와 무관하게 빠르고 효율적으로 요청을 처리해야 하지만, 회사는 여러 리전에 기존 아키텍처를 다시 구축하고 싶어하지 않습니다. 솔루션 설계자는 무엇을 해야 합니까?

**보기**
- A. 기존 아키텍처를 S3 버킷 기반 웹 사이트로 교체하고, S3를 오리진으로 하는 CloudFront 배포에서 Accept-Language 헤더 기반 캐시 동작을 구성한다(동적 웹 사이트를 정적 S3 호스팅으로 바꾸는 것은 애플리케이션 특성 자체를 변경하는 과도한 재설계).
- B. **ALB를 오리진으로 하는 CloudFront 배포를 생성하고, Accept-Language 요청 헤더를 기준으로 캐시하도록 캐시 동작을 구성한다.**
- C. ALB와 통합되는 API Gateway API를 HTTP 통합 유형으로 생성하고, Accept-Language 헤더 기반 API 캐시를 활성화한다(불필요한 API Gateway 계층이 추가되며 CloudFront만큼 전역 에지 캐싱 이점을 제공하지 못함).

**왜 다른 보기는 오답인가**
- A: 동적 웹 사이트를 정적 S3 사이트로 바꾸는 것은 애플리케이션의 근본 성격을 바꾸는 대규모 재작성입니다.
- C: API Gateway 계층을 추가하면 구성만 복잡해질 뿐, CloudFront가 제공하는 전역 에지 캐싱만큼의 지연 개선 효과를 얻기 어렵습니다.
- D: 여러 리전에 EC2와 NGINX, Route 53 지리 라우팅까지 새로 구축해야 하므로 "기존 아키텍처 재구축 회피"라는 명시적 제약을 위반합니다.

> 💡 **시험 꿀팁**: "**리전은 그대로 두고 전역 지연만 줄이고 싶다**"면 기존 오리진 앞에 **CloudFront**를 추가하고, 필요한 요청 헤더(예: Accept-Language)를 캐시 키에 포함시키는 것이 표준 정답입니다.

## QUESTION 273

**문제**: 빠르게 성장하는 전자상거래 회사가 단일 AWS 리전에서 워크로드를 실행하고 있습니다. 솔루션 설계자는 다른 리전을 포함하는 재해 복구(DR) 전략을 세워야 하며, 대기 시간을 최소화하면서 DR 리전의 데이터베이스를 최신 상태로 유지해야 합니다. DR 리전의 나머지 인프라는 축소된 용량으로 상시 실행되다가 필요 시 확장되어야 합니다. 가장 낮은 RTO로 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. 파일럿 라이트 배포와 Amazon Aurora 글로벌 데이터베이스를 사용한다(파일럿 라이트는 재해 시 인프라를 새로 확장해야 해 웜 스탠바이보다 RTO가 큼).
- B. **웜 스탠바이 배포와 Amazon Aurora 글로벌 데이터베이스를 사용한다.**
- C. 파일럿 라이트 배포와 RDS Multi-AZ DB 인스턴스를 사용한다(파일럿 라이트의 RTO 한계에 더해 Multi-AZ는 단일 리전 내 가용성 기능이라 리전 간 DR 요구를 충족하지 못함).
- D. 웜 스탠바이 배포와 RDS Multi-AZ DB 인스턴스를 사용한다(RDS Multi-AZ는 동일 리전 내 대기 인스턴스 구조로 다른 리전으로의 복제 자체가 불가능함).

**정답: B**

**해설**
**Amazon Aurora 글로벌 데이터베이스**는 리전 간 복제 지연이 보통 1초 미만으로, 성능 저하 없이 DR 리전의 데이터베이스를 거의 실시간으로 최신 상태로 유지합니다. 여기에 **웜 스탠바이** 방식을 적용하면 DR 리전에 축소된 용량의 인프라가 이미 가동 중이므로, 재해 발생 시 별도로 인프라를 처음부터 배포해야 하는 파일럿 라이트보다 훨씬 빠르게(즉 더 낮은 RTO로) 전체 트래픽을 처리할 수 있는 수준까지 확장할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 파일럿 라이트는 최소한의 코어 요소만 유지하다가 재해 시 나머지 인프라를 새로 프로비저닝해야 하므로 웜 스탠바이보다 RTO가 깁니다.
- C: 파일럿 라이트의 RTO 문제에 더해, RDS Multi-AZ는 동일 리전 내 가용 영역 간 장애 조치 기능이라 리전 단위 재해에는 애초에 대응할 수 없습니다.
- D: RDS Multi-AZ는 리전 간 복제를 지원하지 않으므로, 다른 리전의 DR 사이트로 데이터베이스를 최신 상태로 유지하는 요구 사항 자체를 충족할 수 없습니다.

> 💡 **시험 꿀팁**: "**리전 간 DR + 최저 RTO**"가 나오면 대기 인프라를 미리 켜 두는 **웜 스탠바이**를, 데이터베이스 복제에는 리전 간 복제가 가능한 **Aurora 글로벌 데이터베이스**를 선택하세요. RDS Multi-AZ는 리전 간 DR에 쓸 수 없다는 점이 핵심 함정입니다.

## QUESTION 274

**문제**: 회사가 EC2 인스턴스에서 애플리케이션을 실행하며, RTO 4시간 미만의 재해 복구(DR) 솔루션이 필요합니다. 또한 정상 운영 중에는 가능한 한 적은 AWS 리소스를 사용해야 합니다. 운영상 가장 효율적인 방식으로 이 요구 사항을 충족하는 솔루션은 무엇입니까?

**보기**
- A. AMI를 생성해 EC2 인스턴스를 백업하고 보조 리전에 복사한 뒤, AWS Lambda와 사용자 지정 스크립트로 보조 리전의 인프라 배포를 자동화한다(커스텀 스크립트 기반 자동화는 코드 유지보수 부담이 크고 IaC 도구만큼 운영 효율적이지 않음).
- B. **AMI를 생성해 EC2 인스턴스를 백업하고 보조 리전에 복사한 뒤, AWS CloudFormation으로 보조 리전의 인프라 배포를 자동화한다.**
- C. 보조 리전에서 EC2 인스턴스를 항상 활성 상태로 실행한다(정상 운영 중에도 리소스를 상시 사용하는 핫 스탠바이 방식이라 "최소 리소스 사용" 조건에 위배).
- D. 보조 가용 영역에서 EC2 인스턴스를 항상 활성 상태로 실행한다(같은 리전 내 AZ 이중화일 뿐 리전 단위 재해에는 대응할 수 없으며, 역시 상시 리소스를 사용함).

**정답: B**

**해설**
평상시에는 EC2 인스턴스의 **AMI**만 생성해 보조 리전에 복사해 두고 실제 컴퓨팅 리소스는 가동하지 않으면, 정상 운영 중 리소스 사용을 최소화할 수 있습니다. 재해 발생 시에는 **AWS CloudFormation** 템플릿으로 해당 AMI를 기반 삼아 필요한 스택 전체(EC2, 네트워킹 등)를 코드 한 번 실행으로 신속하게 재현할 수 있어, 반복 가능하고 검증된 방식으로 4시간 미만의 RTO를 달성할 수 있습니다. CloudFormation은 관리형 IaC 서비스이므로 커스텀 스크립트보다 운영 효율성도 높습니다.

**왜 다른 보기는 오답인가**
- A: Lambda와 사용자 지정 스크립트 조합은 동작은 하지만, 스크립트 자체의 유지보수·오류 처리를 회사가 직접 책임져야 해 선언적 IaC인 CloudFormation보다 운영 효율이 떨어집니다.
- C: 보조 리전 EC2를 상시 가동하는 것은 사실상 핫 스탠바이로, 정상 운영 중 리소스를 최소화해야 한다는 요구 사항에 정면으로 배치됩니다.
- D: 가용 영역 이중화는 리전 전체 장애에는 대응하지 못하며, C와 마찬가지로 상시 리소스 사용 문제도 그대로 남습니다.

## QUESTION 275

**문제**: 회사가 내부 브라우저 기반 애플리케이션을 ALB 뒤의 EC2 Auto Scaling 그룹(여러 가용 영역)에서 운영하며, 근무 시간에는 최대 20개까지 확장되지만 야간에는 2개로 축소됩니다. 오전 중반까지는 문제없이 동작하지만, 하루가 시작될 때마다 애플리케이션이 느리다는 직원 불만이 있습니다. 불만을 해결하면서 비용도 최소화하려면 조정 방식을 어떻게 바꿔야 합니까?

**보기**
- A. 사무실이 열리기 직전에 원하는 용량을 20으로 설정하는 예약 작업을 구현한다(매일 고정된 값으로 즉시 20까지 늘려 근무 시간 초반 지연은 줄일 수 있으나, 실제 수요와 무관하게 고정 용량을 강제해 수요가 적은 날에도 과도하게 프로비저닝될 수 있음).
- B. 더 낮은 CPU 임계값에서 트리거되는 단계 조정(step scaling) 정책을 구현하고 휴지 기간을 줄인다(임계값을 낮추는 방향은 맞지만 계단별 조정 폭을 세밀하게 튜닝해야 하는 부담이 있고, 목표 지표 하나로 지속 조정되는 대상 추적만큼 매끄럽게 반응하지 않음).
- C. **더 낮은 CPU 임계값에서 트리거되는 대상 추적(target tracking) 정책을 구현하고 휴지 기간을 줄인다.**
- D. 사무실이 열리기 직전에 최소 및 최대 용량을 모두 20으로 설정하는 예약 조치를 구현한다(최소 용량 자체를 20으로 고정하면 실제 수요가 적어도 축소가 불가능해져 비용 최소화 요구에 위배).

**왜 다른 보기는 오답인가**
- A: 매일 동일한 시각에 20개로 고정 확장하면 실제 수요와 무관하게 리소스가 낭비될 수 있고, 수요 변화에 유연하게 대응하지 못합니다.
- B: 단계 조정도 임계값을 낮추면 도움이 되지만, 트래픽 증가 폭별 단계 설정을 세밀하게 튜닝해야 해 대상 추적보다 구성과 유지보수 부담이 큽니다.
- D: 최소 용량 자체를 20으로 고정하면 근무 외 시간에도 축소가 불가능해져 비용 최소화라는 목표에 정면으로 위배됩니다.

> 💡 **시험 꿀팁**: "**성능도 개선하고 비용도 최소화**"해야 한다는 조건에서는 고정 예약보다, 임계값과 휴지 기간을 조정한 **대상 추적(Target Tracking)** 정책이 대체로 더 나은 정답입니다.

## QUESTION 276

**문제**: 회사가 Auto Scaling 그룹의 여러 EC2 인스턴스에 배포된 다중 계층 애플리케이션을 운영하며, 데이터 계층은 Oracle 전용 PL/SQL 기능을 사용하는 Amazon RDS for Oracle 인스턴스입니다. 트래픽이 꾸준히 증가하면서 EC2 인스턴스는 과부하되고 RDS 인스턴스는 스토리지가 부족해지고 있습니다. Auto Scaling 그룹에는 조정 지표가 없고 최소 정상 인스턴스 수만 정의되어 있습니다. 트래픽은 안정되기 전까지 예측 불가능한 속도로 계속 증가할 전망입니다. 시스템이 자동으로 확장되도록 하려면 솔루션 설계자는 무엇을 해야 합니까? (2개 선택)

- A. **RDS for Oracle 인스턴스에서 스토리지 Auto Scaling을 구성한다.**
- B. Auto Scaling 스토리지를 사용하기 위해 데이터베이스를 Amazon Aurora로 마이그레이션한다(Oracle 전용 PL/SQL 기능을 사용 중이라 마이그레이션 자체가 크고 번거로운 작업이며, RDS for Oracle도 이미 스토리지 Auto Scaling을 지원하므로 불필요함).
- C. 저장 공간 부족에 대해 RDS for Oracle에서 경보를 구성한다(경보는 알림만 줄 뿐 스토리지를 자동으로 확장하지 않음).
- D. **평균 CPU를 조정 지표로 사용하도록 Auto Scaling 그룹을 구성한다.**
- E. 평균 여유 메모리를 조정 지표로 사용하도록 Auto Scaling 그룹을 구성한다(EC2의 여유 메모리는 CloudWatch 기본 제공 지표가 아니라 CloudWatch 에이전트를 별도로 설치해야 해 CPU 사용률보다 구성 부담이 큼).

**RDS 스토리지 Auto Scaling**을 활성화하면 스토리지 사용량이 임계치에 근접할 때 RDS가 자동으로 볼륨을 확장해, 트래픽 증가에 따른 스토리지 부족 문제를 별도 개입 없이 해결합니다. 컴퓨팅 계층에서는 EC2 인스턴스의 **평균 CPU 사용률**을 조정 지표로 지정하면, Auto Scaling 그룹이 부하 증가를 감지해 자동으로 인스턴스를 추가할 수 있습니다. CPU 사용률은 CloudWatch가 기본 제공하는 지표라 추가 설정 없이 바로 사용할 수 있는 것도 장점입니다.

- B: PL/SQL과 같은 Oracle 전용 기능에 의존하는 애플리케이션을 Aurora로 옮기는 것은 코드 전반의 재작성이 필요한 대규모 작업이며, RDS for Oracle도 이미 스토리지 Auto Scaling을 지원하므로 굳이 마이그레이션할 이유가 없습니다.
- C: CloudWatch 경보는 임계치 초과를 알릴 뿐이며, 스토리지를 자동으로 늘려주는 조치를 스스로 수행하지 않습니다.
- E: 여유 메모리는 EC2의 기본 CloudWatch 지표에 포함되지 않아 CloudWatch 에이전트 설치라는 추가 작업이 필요하므로, 바로 사용 가능한 CPU 사용률에 비해 구성 부담이 큽니다.

> 💡 **시험 꿀팁**: RDS의 스토리지 문제는 **스토리지 Auto Scaling**으로, EC2 컴퓨팅 계층의 확장은 기본 제공 지표인 **평균 CPU 사용률** 기반 조정 정책으로 해결하는 것이 표준 정답입니다.

**보기**
- A. **매월 1일에 DynamoDB 테이블을 백업하는 AWS Backup 계획을 생성하고, 6개월 후 백업을 콜드 스토리지로 전환하는 수명 주기 정책을 지정하며, 각 백업의 보존 기간을 7년으로 설정한다.**
- B. 매월 1일에 DynamoDB 온디맨드 백업을 생성하고, 6개월 후 S3 Glacier Flexible Retrieval로 전환한 뒤 7년 지난 백업을 삭제하는 S3 수명 주기 정책을 만든다(DynamoDB 온디맨드 백업은 DynamoDB 자체 백업 저장소에 남아 있는 리소스로, S3 수명 주기 정책을 직접 적용할 대상이 아님).
- C. AWS SDK로 온디맨드 백업 생성 스크립트를 작성해 매월 1일 EventBridge 규칙으로 실행하고, 6개월 이상 백업을 콜드 스토리지로 전환하고 7년 이상 백업을 삭제하는 두 번째 스크립트를 매월 2일에 실행한다(직접 스크립트로 백업 생명주기 전체를 관리해야 해 운영 부담과 오류 가능성이 크며 AWS Backup의 관리형 기능을 활용하지 못함).
- D. AWS CLI로 온디맨드 백업을 생성하고 Cron 표현식 기반 EventBridge 규칙으로 매월 1일에 실행하며, 6개월 후 콜드 스토리지 전환과 7년 후 삭제를 명령에 직접 지정한다(CLI 명령 자체에는 수명 주기 자동 전환/삭제 기능이 없어 별도의 스케줄링 로직을 추가로 구현해야 함).

**정답: A**

**해설**
**AWS Backup**은 백업 계획(backup plan)에 매월 1일이라는 일정을 지정하면 DynamoDB 테이블의 전체 백업을 자동으로 수행합니다. 백업 계획의 **수명 주기 정책**으로 "6개월 후 콜드 스토리지로 전환"을 지정하면 사용 빈도가 낮아진 백업의 저장 비용을 낮추면서도 필요 시 복원이 가능하고, **보존 기간을 7년**으로 설정하면 규정 준수 요구대로 정확히 7년간 유지된 뒤 자동 만료됩니다. 이 모든 과정이 AWS Backup 콘솔/정책만으로 완결되어 별도의 스크립트나 커스텀 자동화가 필요 없습니다.

**왜 다른 보기는 오답인가**
- B: DynamoDB 온디맨드 백업은 DynamoDB가 자체적으로 관리하는 백업 리소스이며, S3 객체가 아니므로 S3 수명 주기 정책을 곧바로 적용할 수 없습니다.
- C: 백업 생성부터 콜드 전환, 만료 삭제까지 전부 커스텀 스크립트로 구현해야 해 유지보수 부담과 실패 위험이 AWS Backup 대비 훨씬 큽니다.
- D: CLI로 백업을 생성하는 것은 가능하지만, "6개월 후 전환/7년 후 삭제"라는 수명 주기 로직 자체는 CLI 명령에 내장되어 있지 않아 추가 자동화가 필요합니다.

> 💡 **시험 꿀팁**: "**정기 백업 + 일정 기간 후 저비용 전환 + 장기 보존**" 요구 사항에는 커스텀 스크립트가 아니라 **AWS Backup의 백업 계획 + 수명 주기 정책**이 표준 정답입니다.

## QUESTION 280

**문제**: 회사가 웹 사이트에 Amazon CloudFront를 사용 중이며, CloudFront 배포에서 로깅을 활성화해 로그를 S3 버킷에 저장하고 있습니다. 회사는 이 로그에 대해 고급 분석을 수행하고 시각화를 구축해야 합니다. 솔루션 설계자는 이 요구 사항을 충족하기 위해 무엇을 해야 합니까?

**보기**
- A. Amazon Athena의 표준 SQL 쿼리로 S3 버킷의 CloudFront 로그를 분석하고, AWS Glue로 결과를 시각화한다(Glue는 ETL/데이터 카탈로그 서비스로 대시보드형 시각화 기능을 제공하지 않음).
- B. **Amazon Athena의 표준 SQL 쿼리로 S3 버킷의 CloudFront 로그를 분석하고, Amazon QuickSight로 결과를 시각화한다.**
- C. Amazon DynamoDB의 표준 SQL 쿼리로 S3 버킷의 CloudFront 로그를 분석하고, AWS Glue로 결과를 시각화한다(DynamoDB는 S3에 있는 로그 파일을 표준 SQL로 직접 쿼리하는 서비스가 아니며 Glue도 시각화 도구가 아님).
- D. Amazon DynamoDB의 표준 SQL 쿼리로 S3 버킷의 CloudFront 로그를 분석하고, Amazon QuickSight로 결과를 시각화한다(DynamoDB로 S3의 로그 파일을 직접 SQL 쿼리하는 것은 불가능하며 별도의 적재 과정이 필요함).

**정답: B**

**해설**
**Amazon Athena**는 서버 프로비저닝 없이 S3에 저장된 CloudFront 로그를 표준 SQL로 바로 쿼리할 수 있는 서버리스 쿼리 서비스입니다. Athena의 쿼리 결과를 **Amazon QuickSight**와 연결하면 별도의 인프라 구축 없이 대화형 대시보드와 시각화를 손쉽게 만들 수 있어, 전담 개발팀 없이도 비용 효율적이고 확장 가능한 로그 분석 체계를 구성할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: AWS Glue는 ETL 작업과 데이터 카탈로그 관리에 쓰이는 서비스로, 쿼리 결과를 대시보드로 시각화하는 기능은 제공하지 않습니다.
- C, D: DynamoDB는 키-값/문서 기반 NoSQL 데이터베이스로, S3에 있는 로그 파일을 표준 SQL로 직접 쿼리할 수 없으며 사전에 데이터를 적재하는 별도 과정이 필요해 요구 사항에 맞지 않습니다.

> 💡 **시험 꿀팁**: "**S3에 쌓인 로그를 SQL로 분석하고 대시보드로 시각화**"하고 싶다면 **Athena(쿼리) + QuickSight(시각화)** 조합이 표준 정답입니다.
