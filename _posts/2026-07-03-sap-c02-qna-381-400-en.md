## QUESTION 381

**Question**: A broadcaster needs to provide real-time 4K video rendering/transcoding to viewers in a specific metro area, and even the nearest AWS Region's round-trip latency is too far for the real-time broadcast requirement (single-digit milliseconds). They only need to serve that one city and don't want to build a separate data center. What's the solution?

**Choices**
- A. Deploy in the nearest Region and cache with CloudFront (CloudFront caching is effective for static content delivery, but doesn't move a dynamic compute workload like real-time rendering/transcoding itself closer to that city).
- B. **Use AWS Local Zones to place compute/storage infrastructure like EC2 and EBS in that metro area, while keeping other management functions [control plane, etc.] in the parent Region.**
- C. Build their own data center in that city and connect to AWS via Direct Connect (directly contradicts the "don't want to build their own data center" requirement).
- D. Use AWS Wavelength, deployed at a telecom network edge (Wavelength specializes in ultra-low latency to mobile end users over a telecom's 5G network; Local Zones is better suited for the goal of general low-latency compute infrastructure in a specific metro area as in this scenario).

**Correct Answer: B**

**Explanation**
**AWS Local Zones** is an infrastructure deployment option that places AWS compute, storage, database, and other services near a metro area, providing single-digit-millisecond ultra-low latency to users there with no separate data center build needed. You use the same APIs/tools/console as the parent Region, keeping management functions in the parent Region while placing only the compute resources that need real-time processing in the Local Zone.

**Why the other choices are wrong**
- A: CloudFront is effective for static content caching but doesn't relocate a dynamic compute workload like real-time rendering/transcoding.
- C: Building their own data center is explicitly the approach this question says they don't want.
- D: Wavelength targets mobile users at a telecom network edge; Local Zones is the standard for this scenario's goal (general low-latency infrastructure in a specific metro area).

> 💡 **Exam tip**: For **single-digit-millisecond ultra-low-latency compute in a specific metro area** with no desire to build a data center, **AWS Local Zones** is the standard answer.

## QUESTION 382

**Question**: A data warehouse workload generates a huge amount of storage I/O (millions of reads/writes per second) on Aurora PostgreSQL, and standard Aurora's per-I/O-request billing model causes **large monthly cost swings**, making budgeting difficult. Without changing the workload's compute/storage requirements, how do you improve cost predictability?

**Choices**
- A. Fully migrate the data warehouse to Redshift (a migration itself is a large undertaking; the question asks how to improve the existing Aurora workload's cost structure).
- B. **Switch to Aurora I/O-Optimized storage configuration, replacing per-I/O-request billing with a flat-rate structure for compute+storage, making the cost of an I/O-heavy workload predictable.**
- C. Add more read replicas to distribute I/O (adding replicas doesn't reduce overall I/O request volume, and actually adds per-replica I/O charges that could increase total cost).
- D. Switch to Aurora Serverless v2 for auto-scaling (Serverless v2 also bills for compute capacity and isn't a feature that changes the per-I/O-request billing structure itself — the I/O cost predictability problem remains separately).

**Correct Answer: B**

**Explanation**
**Aurora I/O-Optimized** is an alternative pricing structure that charges a **higher but flat** rate for compute and storage instead of the standard per-I/O-request billing. For I/O-intensive workloads (high, variable request volume), this configuration can lower total cost while significantly improving the **predictability** of monthly bills.

**Why the other choices are wrong**
- A: A full migration to Redshift is a large undertaking beyond the scope of improving the existing Aurora workload this question asks about.
- C: Adding replicas doesn't reduce I/O requests themselves and can actually add per-replica I/O charges.
- D: Serverless v2 is a compute auto-scaling feature and doesn't itself change the I/O billing structure.

> 💡 **Exam tip**: For an I/O-heavy Aurora workload needing **cost predictability**, **Aurora I/O-Optimized** storage configuration is the standard answer.

## QUESTION 383

**Question**: For Lambda functions and IoT device firmware it deploys, a company wants to **cryptographically verify before deployment that the code went through an approved build process and hasn't been tampered with**. Unsigned or invalid-signature code must be categorically refused for deployment/execution. What's the solution?

**Choices**
- A. Strictly restrict access to the code repository via IAM (access control is valid, but isn't a feature that verifies the cryptographic integrity of the deployed artifact itself or technically blocks deployment/execution of unsigned code).
- B. **Use AWS Signer to configure code-signing jobs for the Lambda function code and IoT firmware, and enforce, via Lambda's code-signing configuration or IoT's signed job, that unsigned or invalid-signature code is refused for deployment/installation.**
- C. Manually compare checksums of the deployment package uploaded to S3 (manual checksum comparison isn't an automated enforcement mechanism and doesn't provide a feature for automatically rejecting unsigned code in the deployment pipeline).
- D. Have a staff member visually review code at CodePipeline's approval stage (manual visual review isn't cryptographic integrity verification, doesn't scale, and carries high risk of mistakes).

**Correct Answer: B**

**Explanation**
**AWS Signer** is a fully managed service for generating and managing **digital signatures** for Lambda function code or IoT device firmware. Using Lambda's **code-signing configuration** means that when a function is deployed, code that isn't signed by a trusted signing profile, or has an invalid signature, is **automatically refused** for deployment. For IoT, a **signed job** can enforce that a device verifies the signature before installing firmware — cryptographically guaranteeing that only untampered code that went through the approved build process gets deployed/executed.

**Why the other choices are wrong**
- A: IAM access control only restricts repository access — a different layer than cryptographic integrity verification of the deployed artifact itself.
- C: Manual checksum comparison isn't automated enforcement and isn't integrated into the deployment pipeline.
- D: Manual visual review doesn't scale and can't substitute for cryptographic verification.

> 💡 **Exam tip**: To **cryptographically verify code signing and enforce a categorical block on deploying unsigned code** for Lambda functions or IoT firmware, **AWS Signer** (Lambda code-signing configuration / IoT signed jobs) is the standard answer.

## QUESTION 384

**Question**: A company wants to perform an **initial bulk transfer** of petabytes of data from an on-premises NFS file server to S3, and after that transfer completes, **continuously incrementally sync** ongoing changes (new/modified files) still happening on-premises (the on-premises system keeps running until full cutover). How do you handle both the initial bulk transfer and the ongoing incremental sync with one tool?

**Choices**
- A. Use Snowball Edge for the initial transfer and a separate rsync script for ongoing incremental sync (requires combining two different tools, and the incremental-sync part carries the burden of implementing/maintaining a custom script).
- B. **Use AWS DataSync: run the initial bulk transfer task, then repeatedly/on a schedule re-run the same DataSync task to efficiently (detecting only changed files) continuously sync incremental changes afterward.**
- C. Use DataSync for the initial transfer, then switch to Storage Gateway File Gateway for ongoing incremental sync (switching requires a different management scheme and access approach, contradicting the "handle everything with one tool" requirement).
- D. Fully re-copy all data from scratch every time (a full re-copy is very inefficient for petabyte-scale data, wasting enormous bandwidth and time).

**Correct Answer: B**

**Explanation**
**AWS DataSync** supports not just an initial bulk data transfer, but also incremental sync — re-running the same task afterward **efficiently detects and transfers only changed files**. With a single tool, you can handle both the initial bulk transfer and subsequent continuous incremental sync (reflecting only changes), keeping data between on-premises and S3 continuously up to date until a full cutover.

**Why the other choices are wrong**
- A: Combining two different tools contradicts the "handle everything with one tool" goal and carries the burden of maintaining a custom script.
- C: Switching tools partway through also contradicts the requirement to use one integrated tool.
- D: Fully re-copying every time is very inefficient for petabyte-scale data.

> 💡 **Exam tip**: To handle both an **initial bulk transfer and subsequent continuous incremental sync** from on-premises to S3 with one tool, **AWS DataSync** (re-running to efficiently transfer only changes) is the standard answer.

## QUESTION 385

**Question**: A company must **guarantee** the EC2 capacity it needs is available in a specific Availability Zone during traffic spikes (wanting to avoid "insufficient capacity" errors caused by other customers' demand), while also getting a cost discount for long-term usage. What combination meets both requirements together?

**Choices**
- A. Purchase only Savings Plans (Savings Plans provide a rate discount but don't guarantee physical capacity availability in a specific AZ — discount and capacity assurance are different mechanisms).
- B. **Reserve the needed capacity in a specific AZ via an On-Demand Capacity Reservation, and separately purchase a Savings Plan (or Reserved Instance) matching this reserved capacity, combining capacity assurance with a rate discount.**
- C. Purchase only a (Region-scoped) Reserved Instance (a Region-scoped RI provides a rate discount but doesn't guarantee physical capacity in a specific AZ — an AZ-scoped Capacity Reservation is needed for capacity assurance).
- D. Pre-secure needed capacity with Spot Instances (Spot Instances can be reclaimed anytime if capacity runs short — the opposite of "must guarantee" availability).

**Correct Answer: B**

**Explanation**
A **Capacity Reservation** physically reserves EC2 capacity in a specific AZ, guaranteeing that capacity is definitely usable when needed, regardless of other customers' demand. Since a Capacity Reservation itself doesn't provide a rate discount, purchasing a matching **Savings Plan** (or Reserved Instance) alongside it lets you get **capacity assurance** via the reservation and a **cost discount** via the commitment, simultaneously.

**Why the other choices are wrong**
- A, C: Savings Plans and a Region-scoped Reserved Instance are just rate-discount mechanisms — they don't guarantee physical capacity in a specific AZ.
- D: Spot Instances carry reclamation risk, conflicting with the "must guarantee" requirement.

> 💡 **Exam tip**: To **guarantee capacity in a specific AZ while also getting a cost discount**, combining a **Capacity Reservation + a Savings Plan (or Reserved Instance)** is the standard answer.

## QUESTION 386

**Question**: An enterprise runs a Control Tower landing zone, and a team wants not just the preventive guardrail "S3 buckets cannot be made public," but also a detective guardrail that "detects and alerts the security team if a public bucket is accidentally created." How do you understand the distinction between these two guardrail types in Control Tower's guardrail system?

**Choices**
- A. Both preventive and detective guardrails are implemented purely via SCPs (an SCP is a mechanism used for preventive control [blocking a specific API call itself]; after-the-fact detection and notification, a detective control, isn't an SCP's role — a conceptual error).
- B. **Control Tower implements preventive guardrails via SCPs and detective guardrails via AWS Config rules. A preventive guardrail (e.g., "cannot disable public access block") categorically blocks a specific action itself, while a detective guardrail (e.g., "identify whether an S3 bucket allows public access") continuously scans for non-compliant resources and flags them as non-compliant.**
- C. Both guardrail types are implemented purely via GuardDuty (GuardDuty specializes in threat/anomaly detection; Control Tower's guardrail system is based on SCPs and Config rules, not GuardDuty).
- D. Detective guardrails take priority over preventive guardrails and are always checked first (the two guardrail types differ in purpose and timing, not priority — a preventive guardrail blocks at the moment of the action, while a detective guardrail continuously evaluates after the fact; these are separate mechanisms, not compared by priority).

**Correct Answer: B**

**Explanation**
**AWS Control Tower**'s guardrails fall into two broad types. A **preventive guardrail** internally uses an **SCP** to categorically block a specific action (e.g., disabling public access block) at the moment of the API call itself. A **detective guardrail** internally uses an **AWS Config rule** to continuously evaluate whether existing resources comply, identifying and flagging non-compliant resources on a dashboard. Using both layers together implements multi-layered governance combining prevention and after-the-fact detection.

**Why the other choices are wrong**
- A, C: These don't accurately reflect each guardrail type's actual underlying mechanism (SCP vs. Config rule).
- D: The two guardrails aren't compared by priority — they're separate, complementary mechanisms differing in purpose (prevention vs. detection) and timing.

> 💡 **Exam tip**: In Control Tower guardrails, remember that **preventive guardrails are SCP-based (blocking the action itself)** and **detective guardrails are AWS Config rule-based (after-the-fact non-compliance identification)**.

## QUESTION 387

**Question**: A large enterprise's network team wants to centrally own/manage all VPC networking (subnets, routing, NAT gateways, etc.), but each application team should be able to freely deploy its own resources (EC2, RDS, etc.) within that network from its own account. How do you implement this without creating a separate VPC per account?

**Choices**
- A. Create a VPC in the network team's account and grant each application team a full administrator IAM role on that account (delegating full admin permissions violates least privilege, and lets application teams change network resources too — contradicting the goal of "network managed centrally only").
- B. **Use VPC sharing (based on AWS RAM), sharing subnets from the network team's owning account with other application team accounts. Each application team deploys its own resources into the shared subnet, while ownership and management of the network configuration itself [subnets, routing, etc.] remains with the network team's account.**
- C. Create an individual VPC per application team account and connect them all via Transit Gateway (the question explicitly wants this implemented "without creating a separate VPC per account," so this contradicts the requirement).
- D. Move all applications into the network team's single account (contradicts the requirement for each team to deploy resources from its own account — mismatches the account structure itself).

**Correct Answer: B**

**Explanation**
**VPC sharing (based on AWS Resource Access Manager)** lets the account owning a VPC (and its subnets) — the network team — share it with other accounts in the organization (application teams). Accounts it's shared with can deploy their own resources (EC2, RDS, etc.) into that subnet, but **management permissions over the network infrastructure itself — creating/deleting subnets, route tables, NACLs — remain solely with the owning account (the network team)**. This is the standard multi-account networking pattern satisfying both centralized network management and per-team resource-deployment autonomy.

**Why the other choices are wrong**
- A: Delegating full admin permissions violates least privilege and loses centralized control over the network.
- C: Creating a separate VPC per account is exactly what the question explicitly excludes.
- D: Merging all applications into a single account conflicts with the existing per-team account separation structure.

> 💡 **Exam tip**: To have a network **centrally owned/managed while multiple accounts deploy their own resources into it**, **VPC sharing (AWS RAM)** is the standard answer.

## QUESTION 388

**Question**: A company needs to manage thousands of different schedules (one-time execution at a specific date/time, recurring execution accounting for time zones, etc.), and managing this large volume as individual EventBridge rules (cron/rate expressions) is cumbersome, plus non-UTC time zones must be calculated manually. What service more easily manages a large volume of flexible schedules?

**Choices**
- A. Keep using standard EventBridge rules (cron expressions) but just create more rules (there's a quota on the number of EventBridge rules per account/Region, and you'd still have to handle large-scale schedule management and time-zone conversion yourself).
- B. **Use Amazon EventBridge Scheduler, which centrally manages schedules scaling up to millions, natively supports timezone-aware recurring/one-time schedules, and can also be configured with a flexible retry policy.**
- C. Set up individual cron jobs (crontab) on each EC2 instance (instance-based cron isn't a serverless managed approach, depends on the instance's own availability, and is hard to manage centrally at scale).
- D. Implement every schedule using only Step Functions' Wait state (Step Functions is optimized for workflow orchestration and isn't a dedicated scheduling service for managing thousands of independent, large-scale schedules).

**Correct Answer: B**

**Explanation**
**Amazon EventBridge Scheduler** offers scalability to create/manage millions of schedules, and natively supports **timezone-aware one-time and recurring schedules**, eliminating the need to manually calculate UTC conversions. It also lets you configure a flexible retry policy and a flexible time window per schedule, making it far more scalable and easier to manage than individual EventBridge rules for a large volume of differing schedules.

**Why the other choices are wrong**
- A: Standard EventBridge rules have a per-account rule-count quota and require manually calculating time zones — cumbersome.
- C: Instance-based cron isn't serverless and doesn't fit large-scale centralized management.
- D: Step Functions is a workflow orchestration tool, not a dedicated service for managing a large volume of independent schedules.

> 💡 **Exam tip**: To manage a **large volume (up to millions) of flexible schedules (including timezone-aware)**, **Amazon EventBridge Scheduler** is the standard answer.

## QUESTION 389

**Question**: A company wants to grant access to an S3-based data lake, mapped directly and finely (down to the directory-prefix level) to **identities in its existing identity provider (e.g., Okta, Microsoft Entra ID) users/groups**, without pre-creating IAM roles/policies one by one. How do you implement this without creating additional IAM roles as data users grow?

**Choices**
- A. Pre-create a corresponding IAM role individually for each user in the identity provider (requires pre-creating an IAM role per user, directly contradicting "without creating additional IAM roles," and doesn't scale).
- B. **Use S3 Access Grants to dynamically grant fine-grained access permissions (read/write, etc.) at the S3 bucket/prefix level to users/groups from an existing identity provider integrated with IAM Identity Center. Users obtain temporary credentials via credential federation, scoped to their granted access.**
- C. Share the same single broad IAM role across all data users (all users get the same broad permissions, contradicting the fine-grained access control requirement and violating least privilege).
- D. List every individual user's ARN in the bucket policy (listing many individual users directly in a bucket policy can hit policy size limits, and isn't a dynamic integration with the identity provider — heavy manual maintenance burden).

**Correct Answer: B**

**Explanation**
**S3 Access Grants** is a feature that dynamically grants access to S3 data directly mapped to **identities of users/groups in an identity provider** (Okta, Entra ID, etc. integrated with IAM Identity Center), rather than to a pre-defined IAM role. When the data owner grants read/write permission to a specific identity at the bucket/prefix level, users obtain **temporary credentials** scoped to that grant via credential federation. As new data users are added, there's no need to create a new IAM role — you simply grant permission to the identity on the identity-provider side — highly scalable.

**Why the other choices are wrong**
- A: Pre-creating an IAM role per user doesn't scale and contradicts the requirement.
- C: Sharing the same broad role across everyone violates fine-grained access control and least privilege.
- D: Listing individual users in a bucket policy runs into policy size limits and heavy manual maintenance burden.

> 💡 **Exam tip**: To **dynamically grant fine-grained S3 data access mapped directly to an existing identity provider's identities**, with no additional IAM roles created, **S3 Access Grants** is the standard answer.

## QUESTION 390

**Question**: A manufacturing plant needs to analyze IoT sensor data in real time to detect anomalies, but the plant's internet connectivity is **intermittently disconnected**. Machine-learning inference and basic data processing must continue running locally even while disconnected, and they want automatic sync with the cloud once connectivity is restored. What's the solution?

**Choices**
- A. Assume internet connectivity is always stable and do all processing only in the cloud (Lambda/Kinesis) (processing stops entirely when connectivity drops — doesn't account for the "intermittent disconnection" requirement at all).
- B. **Deploy AWS IoT Greengrass on the plant's edge devices/gateway, running machine-learning inference and data-processing logic locally, continuing to operate locally during a connectivity drop, and automatically syncing with AWS IoT Core once connectivity is restored.**
- C. Build a completely separate on-premises server farm at the plant, operating independently of AWS (requires building/operating entirely separately with no AWS service/tool integration — heavy management burden, and doesn't address the automatic cloud-sync requirement either).
- D. Add a battery-backed 4G modem to each sensor to just improve connection stability (can somewhat improve connection stability, but can't fully eliminate the underlying premise of "intermittent disconnection," and is a different approach than the question's core requirement of having local processing capability itself).

**Correct Answer: B**

**Explanation**
**AWS IoT Greengrass** is software that runs locally on edge devices, enabling **local inference** using a machine-learning model deployed from the cloud, along with data processing and messaging, regardless of internet connectivity. It keeps operating normally locally during a connectivity drop, and once connectivity is restored, **automatically syncs** the accumulated data and state **with AWS IoT Core**. This is the standard service providing continuous local processing capability in an edge environment with intermittent connectivity.

**Why the other choices are wrong**
- A: Relying solely on the cloud means processing stops entirely when connectivity drops.
- C: A completely separate on-premises infrastructure requires building/operating it yourself with no AWS integration — heavy burden, and doesn't address cloud sync either.
- D: Just improving connection stability can't fully eliminate intermittent disconnection itself and is a different approach than securing local processing capability.

> 💡 **Exam tip**: For an edge environment with **intermittent internet connectivity** needing local processing (including inference) plus automatic sync on reconnection, **AWS IoT Greengrass** is the standard answer.

**Choices**

## QUESTION 392

**Question**: A company currently running an application in Region A wants to gradually migrate it to a new Region B. Instead of cutting over all traffic overnight, they want to **gradually increase the traffic percentage to Region B over several weeks** while monitoring for issues. Assuming the application is deployed in both Regions, what's the solution?

**Choices**
- A. Use a Route 53 failover routing policy (failover routing is an active-passive structure that switches only when one side is completely down — a different purpose than this question's desired "gradual ratio-based traffic shift").
- B. **Use a Route 53 weighted routing policy, assigning weights to Region A's and Region B's endpoints, and gradually increasing Region B's weight over several weeks to adjust the traffic ratio.**
- C. Use AWS Global Accelerator's traffic dial to gradually adjust, in percentage increments, the traffic ratio to registered endpoint groups (Region A, Region B) (Global Accelerator is also a valid approach, maintaining a static Anycast IP while finely adjusting the inter-Region ratio via the traffic dial — also a standard consideration when this scenario needs precise traffic-dial adjustment and a fixed IP).
- D. Completely delete Region A's DNS record and switch immediately to Region B (an immediate full cutover directly contradicts the "gradually over several weeks" requirement).

**Correct Answer: B**

**Explanation**
**Route 53 weighted routing** assigns relative weights to multiple endpoints (Region A, Region B), distributing traffic according to that ratio. Gradually increasing Region B's weight over several weeks (e.g., 10% → 30% → 50% → 100%) while monitoring lets you implement a safe, gradual Regional migration where you can immediately revert the weight if a problem occurs. (Note: Global Accelerator's traffic dial is a similar-purpose alternative, but weighted routing is most commonly presented as the standard DNS-based gradual-shift method for this scenario.)

**Why the other choices are wrong**
- A: Failover routing is optimized for switching during a complete outage — a different purpose than gradual ratio adjustment.
- D: An immediate full cutover directly contradicts the gradual-migration requirement.

> 💡 **Exam tip**: To shift traffic between two Regions **gradually over several weeks by adjusting the ratio**, **Route 53 weighted routing** is the standard answer.

## QUESTION 393

**Question**: A company runs a self-managed Apache Cassandra cluster (wide-column NoSQL, requiring high write throughput and low latency), and wants to reduce the operational burden of cluster patching/scaling/failure recovery, while keeping the existing Cassandra Query Language (CQL)-based application code unchanged. What's the solution?

**Choices**
- A. Fully migrate to DynamoDB (DynamoDB is a strong NoSQL service, but uses its own API rather than CQL, requiring a major rewrite of the existing CQL-based application code).
- B. **Migrate to Amazon Keyspaces (for Apache Cassandra, serverless), keeping the existing CQL driver and application code largely as-is, while moving to a fully managed service with no server provisioning/patching/scaling.**
- C. Keep the Cassandra cluster on EC2 as-is but just upgrade to a larger instance type (the operational burden [patching, scaling, failure recovery, etc.] still has to be self-managed, failing to achieve the fundamental goal of reducing operational burden).
- D. Migrate to RDS for PostgreSQL, modeling the wide-column data with JSONB columns (switching to a relational database requires fully rewriting CQL-based code and the data model, and doesn't match Cassandra-level write throughput/latency characteristics).

**Correct Answer: B**

**Explanation**
**Amazon Keyspaces (for Apache Cassandra)** is a **serverless, fully managed** wide-column NoSQL database service compatible with the Cassandra Query Language (CQL) API. It lets you move to a service where AWS handles server provisioning, patching, scaling, and failure recovery, while keeping most of the existing CQL-based driver and application code as-is — meeting both requirements in this question (reduced operational burden + preserved code).

**Why the other choices are wrong**
- A: DynamoDB uses its own API, not CQL, requiring a major application code rewrite.
- C: As long as you keep your own EC2 cluster, patching/scaling/failure-recovery burden remains.
- D: Switching to a relational database requires a full redesign of the data model and code, with different performance characteristics too.

> 💡 **Exam tip**: To eliminate the operational burden of a self-managed **Apache Cassandra** deployment while keeping existing CQL code, **Amazon Keyspaces** is the standard answer.

## QUESTION 394

**Question**: After a Regional disaster, they successfully failed over and are operating the application in the DR Region. The original primary Region has now recovered, and they want to safely **fail back to the original Region**. What approach is needed to prevent losing data that changed during the DR period (e.g., new transactions that occurred in the DR Region during the outage) when failing back?

**Choices**
- A. Immediately re-switch DNS to the original primary Region as soon as it recovers (switching immediately with none of the data changes made in the DR Region during the DR period reflected back to the original Region causes data loss — a premature switch with no reverse sync).
- B. **Before failback, configure reverse replication from the DR Region (currently active) to the original primary Region, fully syncing the changes that occurred during the DR period into the original Region, confirm the two Regions' data match, and then fail back traffic to the original Region.**
- C. Ignore data changes made during the DR period and restore the original Region from a backup taken at the moment of the disaster (causes serious data loss — all transactions/data changes processed in the DR Region since the disaster are lost).
- D. Never fail back — permanently use the DR Region as the new primary (could be a valid option in general, but the question explicitly wants failback to the original Region, so this doesn't fit this scenario's requirement).

**Correct Answer: B**

**Explanation**
The key to a safe **failback** is configuring **reverse replication** from the Region that was active during the DR event (the Region currently holding the actual data) to the original primary Region, syncing all data changes that occurred during the DR period so they're fully reflected in the original Region too. Only after confirming the two Regions' data match can you safely switch traffic back to the original Region — skipping this order results in losing data generated during the DR period.

**Why the other choices are wrong**
- A: Switching immediately with no reverse sync loses data from the DR period.
- C: Restoring from a disaster-moment backup causes serious data loss of everything changed since then.
- D: The question explicitly requires failback to the original Region, so this option doesn't fit the scenario.

> 💡 **Exam tip**: To **safely fail back to the original Region** after a DR event, the standard answer is to first **fully sync data via reverse replication** from the currently active Region to the original Region, then switch traffic.

## QUESTION 395

**Question**: A company wants to issue public SSL/TLS certificates for use with both CloudFront and an ALB, and wants renewal to be **fully automated** to prevent service outages from expiration. They don't want to manage the certificate private key themselves or perform manual renewal work. What's the solution?

**Choices**
- A. Purchase a certificate from a third-party certificate authority and manually renew/redeploy it every year (requires a manual purchase/renewal/redeployment process, contradicting "fully automated," and carries risk of missing a renewal).
