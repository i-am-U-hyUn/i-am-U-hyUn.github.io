## Q1. 스폿 인스턴스 활용 시점

기업은 언제 스폿 인스턴스를 사용하는 것이 유리합니까?

- A. 애플리케이션을 실행해야 할 때 유연성이 있는 경우
- B. 미션 크리티컬 워크로드가 있는 경우
- C. 전용 용량이 필요한 경우
- D. 인스턴스를 중지하지 않아야 하는 경우

**정답: A**

✅ **A. 애플리케이션을 실행해야 할 때 유연성이 있는 경우**: 스폿 인스턴스는 AWS가 여유 용량을 경매 방식으로 제공하는 것으로, 온디맨드 대비 최대 90%까지 저렴합니다. 단, AWS가 용량을 회수할 경우 인스턴스가 중단될 수 있으므로, 중단 가능성을 허용할 수 있는 유연한 워크로드(배치 처리, 데이터 분석, 테스트 등)에 적합합니다.

❌ **B. 미션 크리티컬 워크로드가 있는 경우**: 스폿 인스턴스는 AWS가 언제든지 회수할 수 있어 중단 위험이 있으므로, 중단 불가한 미션 크리티컬 워크로드에는 온디맨드 또는 예약 인스턴스를 사용해야 합니다.

❌ **C. 전용 용량이 필요한 경우**: 전용 용량이 필요한 경우에는 전용 인스턴스(Dedicated Instance) 또는 전용 호스트(Dedicated Host)를 사용해야 하며, 스폿 인스턴스는 전용 용량을 보장하지 않습니다.

❌ **D. 인스턴스를 중지하지 않아야 하는 경우**: 스폿 인스턴스의 가장 큰 특징은 AWS가 필요 시 인스턴스를 회수(중단)할 수 있다는 것입니다. 따라서 절대 중단되어서는 안 되는 워크로드에는 부적합합니다.

💡 **시험 꿀팁**: 스폿 인스턴스 = 저렴 + 중단 가능 + 유연한 워크로드 (배치처리, CI/CD, 빅데이터 분석). 온디맨드 = 중단 불가 + 일반 워크로드. 예약 인스턴스 = 1년/3년 약정 + 최대 72% 할인. 전용 호스트 = 물리 서버 독점 사용.

## Q2. TCO 분석 포함 요소 (두 개 선택)

AWS로 사내 데이터센터를 이전하는 방안을 검토 중이다. 총소유비용(TCO) 분석에는 어떤 요소가 포함되어야 합니까? (두 개를 선택합니다.)

- A. Amazon EC2 인스턴스 가용성
- B. 데이터 센터의 전력 소비량
- C. 구형 서버 교체에 드는 인건비
- D. 애플리케이션 개발 시간
- E. 데이터베이스 엔진 용량

**정답: B, C**

✅ **B. 데이터 센터의 전력 소비량**: TCO(총소유비용) 분석에서 온프레미스 데이터센터의 전력 비용은 핵심 항목입니다. 서버 운영에 필요한 전력과 냉각 비용은 클라우드 전환 시 절감할 수 있는 대표적인 비용 요소입니다.

✅ **C. 구형 서버 교체에 드는 인건비**: 온프레미스 환경에서는 노후화된 서버를 주기적으로 교체해야 하며, 이에 따른 하드웨어 구매비와 설치/교체 인건비가 발생합니다. 이는 클라우드 전환 시 제거되는 직접 비용으로 TCO 분석의 핵심 구성 요소입니다.

❌ **A. Amazon EC2 인스턴스 가용성**: EC2 인스턴스 가용성은 TCO 비용 분석 항목이 아니라 가용성(SLA) 지표에 해당합니다. TCO 분석은 비용 절감 요소를 비교하는 것이므로 이 항목은 해당되지 않습니다.

❌ **D. 애플리케이션 개발 시간**: 애플리케이션 개발 시간은 TCO의 인프라 비용 비교와 직접적인 관련이 없으며, 소프트웨어 개발 비용은 온프레미스와 클라우드 전환 여부와 관계없이 발생합니다.

❌ **E. 데이터베이스 엔진 용량**: 데이터베이스 엔진 용량은 TCO 비용 분석에서 고려하는 인프라 운영 비용(전력, 인건비, 시설비)이 아닌 기술 사양에 해당합니다.

💡 **시험 꿀팁**: TCO(Total Cost of Ownership) 분석 = 온프레미스 숨겨진 비용 발굴! 핵심 항목: 전력/냉각 비용, 하드웨어 구매/교체 비용, 시설 임대비, IT 인건비(유지보수), 라이선스 비용. AWS TCO 계산기를 사용해 온프레미스 vs 클라우드 비용 비교 가능.

## Q3. AWS Lambda 요금 부과 방식

AWS 람다에 대한 AWS 요금은 어떻게 부과됩니까?

- A. 사용자가 시간당 지불할 최대 가격에 입찰합니다.
- B. 사용자는 1년, 3년 또는 5년 선불 지급 기간을 선택합니다.
- C. 사용자가 파일 시스템 또는 데이터베이스에서 필요한 영구 스토리지 비용을 지불합니다.
- D. 사용자는 요청 수와 사용된 계산 리소스에 따라 비용을 지불합니다.

**정답: D**

✅ **D. 사용자는 요청 수와 사용된 계산 리소스에 따라 비용을 지불합니다**: AWS Lambda는 완전한 서버리스 서비스로, 함수가 실행될 때만 비용이 청구됩니다. 요금은 함수 호출 횟수(요청 수)와 실행 시간(GB-초 단위의 컴퓨팅 리소스)을 기반으로 계산됩니다. 매월 100만 건의 무료 요청과 40만 GB-초의 무료 컴퓨팅 시간이 제공됩니다.

❌ **A. 사용자가 시간당 지불할 최대 가격에 입찰합니다**: 입찰 방식은 EC2 스폿 인스턴스에 해당하는 설명입니다. Lambda는 입찰 없이 사용량 기반으로 자동 청구됩니다.

❌ **B. 사용자는 1년, 3년 또는 5년 선불 지급 기간을 선택합니다**: 선불 약정 방식은 EC2 예약 인스턴스(Reserved Instances)에 해당합니다. Lambda는 약정 없이 사용한 만큼만 지불합니다.

❌ **C. 사용자가 파일 시스템 또는 데이터베이스에서 필요한 영구 스토리지 비용을 지불합니다**: Lambda 자체는 영구 스토리지를 제공하지 않으며, 영구 스토리지는 S3, EFS, RDS 등 별도 서비스를 사용합니다. Lambda 요금에 스토리지 비용은 포함되지 않습니다.

💡 **시험 꿀팁**: Lambda = 서버리스 + 사용한 만큼만 지불 + 유휴 비용 없음. 요금 구성: ① 요청 수 (매월 100만 건 무료) + ② 실행 시간 GB-초 (40만 GB-초 무료). "서버를 관리하지 않고 코드만 실행" = Lambda의 핵심 가치!

## Q4. Security Group의 역할

Security Group은 관련 Amazon Elastic Compute Cloud(Amazon EC2) 인스턴스 보안을 지원하는 기능을 무엇입니까?

- A. Amazon EC2 인스턴스의 가상 방화벽 역할을 수행합니다.
- B. AWS ID 및 IAM(Access Management) 정책을 사용하는 보안 AWS 사용자 계정
- C. AWS Shield로 DDoS 보호 제공
- D. Amazon CloudFront를 사용하여 Amazon EC2 인스턴스를 보호합니다.

**정답: A**

✅ **A. Amazon EC2 인스턴스의 가상 방화벽 역할을 수행합니다**: Security Group은 EC2 인스턴스 수준에서 인바운드 및 아웃바운드 트래픽을 제어하는 가상 방화벽입니다. 허용(Allow) 규칙만 설정 가능하며 거부(Deny) 규칙은 없고, 상태 저장(Stateful) 방식으로 동작하여 인바운드 허용 시 응답 트래픽은 자동으로 허용됩니다.

❌ **B. AWS ID 및 IAM 정책을 사용하는 보안 AWS 사용자 계정**: IAM(Identity and Access Management)은 AWS 서비스와 리소스에 대한 접근 권한을 관리하는 서비스입니다. Security Group과는 다른 보안 레이어로, 사용자/역할/정책을 관리합니다.

❌ **C. AWS Shield로 DDoS 보호 제공**: AWS Shield는 DDoS(분산 서비스 거부) 공격으로부터 AWS 리소스를 보호하는 별도의 관리형 서비스입니다. Security Group과는 다른 서비스입니다.

❌ **D. Amazon CloudFront를 사용하여 Amazon EC2 인스턴스를 보호합니다**: Amazon CloudFront는 CDN(콘텐츠 전송 네트워크) 서비스로, 콘텐츠를 엣지 위치에서 캐시하여 빠르게 전달합니다. EC2 인스턴스를 직접 보호하는 방화벽 기능은 없습니다.

💡 **시험 꿀팁**: Security Group vs NACL 차이 암기! Security Group = 인스턴스 레벨 + 허용 규칙만 + Stateful(상태 저장). NACL = 서브넷 레벨 + 허용/거부 규칙 + Stateless(상태 비저장). "방화벽" 키워드 = Security Group!

## Q5. 다운타임 가장 낮은 재해 복구 시나리오

다운타임 가능성이 가장 낮은 재해 복구 시나리오는 무엇입니까?

- A. 백업 및 복원
- B. 파일럿 조명
- C. 웜 스탠바이
- D. 다중 사이트 액티브-액티브

**정답: D**

✅ **D. 다중 사이트 액티브-액티브**: 멀티 사이트 액티브-액티브 방식은 여러 리전에 동일한 환경이 동시에 운영되는 방식으로, 재해 발생 시 트래픽을 즉시 다른 리전으로 전환할 수 있어 다운타임이 거의 없습니다(RTO: 거의 0). 비용은 가장 높지만 가용성과 복구 속도가 가장 뛰어납니다.

❌ **A. 백업 및 복원**: 백업 및 복원(Backup & Restore)은 데이터를 정기적으로 백업하고 재해 시 복원하는 방식입니다. 복원에 수 시간이 소요될 수 있어 다운타임이 가장 길고 RTO가 가장 높습니다.

❌ **B. 파일럿 조명**: 파일럿 라이트(Pilot Light)는 핵심 시스템만 최소한으로 클라우드에서 실행하고, 재해 시 나머지를 신속히 확장하는 방식입니다. 백업/복원보다는 빠르지만 액티브-액티브보다 다운타임이 깁니다.

❌ **C. 웜 스탠바이**: 웜 스탠바이(Warm Standby)는 축소된 규모로 대기 환경을 운영하다가 재해 시 빠르게 확장하는 방식입니다. 파일럿 라이트보다 빠르지만 액티브-액티브보다 다운타임이 존재합니다.

💡 **시험 꿀팁**: DR 전략 RTO/RPO 순서 암기! (다운타임 낮음 → 높음 순): 액티브-액티브 > 웜 스탠바이 > 파일럿 라이트 > 백업 & 복원. 비용은 반대 순서! "다운타임 최소" = 액티브-액티브, "비용 최소" = 백업 & 복원.

## Q6. AWS 클라우드 마이그레이션 비용 편익 분석 도구

기업이 AWS 클라우드로 마이그레이션하는 데 필요한 비용 편익 분석을 수행하는 데 도움이 되는 것은 무엇입니까?

- A. 비용 탐색기
- B. AWS 총소유비용(TCO) 계산기
- C. AWS 가격 계산기
- D. AWS Trusted Advisor

**정답: B**

✅ **B. AWS 총소유비용(TCO) 계산기**: AWS TCO 계산기는 온프레미스 데이터센터 운영 비용과 AWS 클라우드 비용을 비교하여 마이그레이션의 비용 편익을 분석하는 도구입니다. 서버 수, 스토리지, 네트워크 등의 정보를 입력하면 3~5년간의 비용 비교 보고서를 제공하여 마이그레이션 결정에 활용할 수 있습니다.

❌ **A. 비용 탐색기**: AWS 비용 탐색기(Cost Explorer)는 이미 발생한 AWS 사용 비용과 사용량을 시각화하고 분석하는 도구입니다. 마이그레이션 전 비용 편익 분석이 아닌, 기존 AWS 비용을 모니터링하고 최적화하는 데 사용됩니다.

❌ **C. AWS 가격 계산기**: AWS 가격 계산기(Pricing Calculator)는 AWS 서비스별 예상 비용을 계산하는 도구로, 특정 AWS 아키텍처의 예상 비용을 산출합니다. TCO 계산기와 달리 온프레미스 vs 클라우드 비교 분석 기능은 없습니다.

❌ **D. AWS Trusted Advisor**: AWS Trusted Advisor는 기존 AWS 환경의 비용 최적화, 보안, 성능, 내결함성, 서비스 한도를 점검하고 권고사항을 제공하는 도구입니다. 마이그레이션 전 비용 편익 분석 용도가 아닙니다.

💡 **시험 꿀팁**: 도구별 용도 구분 암기! TCO 계산기 = "온프레미스 vs 클라우드" 비용 비교 (마이그레이션 결정). AWS 가격 계산기 = "AWS 서비스 예상 비용" 산출. 비용 탐색기 = "현재 AWS 비용" 분석 및 예측. Trusted Advisor = "AWS 환경 모범 사례" 점검.

## Q7. 예약 인스턴스 비용 이점 계정 간 공유

다음 중 예약 인스턴스의 비용 이점을 AWS 계정 간에 공유할 수 있는 기능은 무엇입니까?

- A. AWS 계정 간 AWS 비용 탐색기
- B. 연결된 계정 및 통합 청구
- C. Amazon Elastic Compute Cloud(Amazon EC2) 예약된 인스턴스 활용률 보고서
- D. AWS 계정 간의 Amazon EC2 인스턴스 사용량 보고서

**정답: B**

✅ **B. 연결된 계정 및 통합 청구**: AWS Organizations의 통합 청구(Consolidated Billing) 기능을 통해 마스터 계정에서 예약 인스턴스를 구매하면, 연결된 멤버 계정들도 해당 예약 인스턴스의 할인 혜택을 자동으로 공유받을 수 있습니다. 이를 통해 여러 계정에 걸쳐 예약 인스턴스 활용률을 극대화하고 비용을 절감할 수 있습니다.

❌ **A. AWS 계정 간 AWS 비용 탐색기**: 비용 탐색기는 비용 데이터를 시각화하고 분석하는 도구로, 예약 인스턴스 할인을 계정 간에 공유하는 기능은 없습니다.

❌ **C. Amazon EC2 예약된 인스턴스 활용률 보고서**: 이 보고서는 예약 인스턴스가 얼마나 효율적으로 사용되고 있는지 모니터링하는 도구입니다. 비용 이점을 공유하는 기능이 아닌 활용률을 추적하는 보고서입니다.

❌ **D. AWS 계정 간의 Amazon EC2 인스턴스 사용량 보고서**: 사용량 보고서는 인스턴스 사용 현황을 모니터링하는 도구로, 예약 인스턴스 할인 혜택을 공유하는 기능이 아닙니다.

💡 **시험 꿀팁**: AWS Organizations + 통합 청구(Consolidated Billing)의 핵심 혜택 3가지: ① 단일 청구서로 모든 계정 관리, ② 예약 인스턴스 및 Savings Plans 할인 공유, ③ 볼륨 할인(사용량 합산으로 더 높은 할인율 적용). "계정 간 비용 공유" = 통합 청구!

## Q8. 여러 AWS 계정 청구 통합 서비스

한 회사가 여러 AWS 계정을 보유하고 있으며 청구 프로세스를 단순화하고 통합하고자 합니다. 이를 달성할 AWS 서비스는 무엇입니까?

- A. AWS 비용 및 사용량 보고서
- B. AWS 조직
- C. AWS 비용 탐색기
- D. AWS 예산

**정답: B**

✅ **B. AWS 조직**: AWS Organizations는 여러 AWS 계정을 중앙에서 관리하는 서비스입니다. 통합 청구(Consolidated Billing) 기능을 통해 여러 계정의 청구를 하나의 마스터 계정으로 통합하고, 단일 청구서를 통해 모든 계정의 비용을 관리할 수 있습니다. 또한 서비스 제어 정책(SCP)을 통해 계정별 권한도 중앙 관리할 수 있습니다.

❌ **A. AWS 비용 및 사용량 보고서**: AWS Cost and Usage Report(CUR)는 상세한 비용 및 사용량 데이터를 S3에 저장하여 분석할 수 있는 보고서 서비스입니다. 청구 프로세스를 통합하는 기능은 없습니다.

❌ **C. AWS 비용 탐색기**: 비용 탐색기는 AWS 사용 비용을 시각화하고 분석하는 도구입니다. 여러 계정의 청구를 통합하는 기능은 없으며, Organizations와 함께 사용하면 계정별 비용 분석이 가능합니다.

❌ **D. AWS 예산**: AWS Budgets는 비용 또는 사용량이 임계값을 초과할 때 알림을 보내는 예산 관리 도구입니다. 청구 프로세스를 통합하는 기능은 없습니다.

💡 **시험 꿀팁**: "여러 계정 관리" = AWS Organizations! Organizations의 두 가지 핵심 기능: ① 통합 청구 (Consolidated Billing) — 단일 청구서, ② 서비스 제어 정책 (SCP) — 계정별 권한 제한. "청구 통합" + "중앙 관리" 키워드가 나오면 항상 AWS Organizations를 선택!

## Q9. 전 세계 사용자 짧은 지연 시간 서비스

한 회사가 전 세계에 퍼져 있는 최종 사용자를 위한 단일 AWS 영역에서 호스팅되는 애플리케이션을 설계하고 있습니다. 이 회사는 최종 사용자에게 애플리케이션 데이터에 대한 짧은 지연 시간 액세스를 제공하고자 합니다. 다음 중 이 요구 사항을 충족하는 데 도움이 되는 서비스는 무엇입니까?

- A. Amazon CloudFront
- B. AWS Direct Connect
- C. Amazon Route 53 글로벌 DNS
- D. Amazon S3 전송 가속화

**정답: A**

✅ **A. Amazon CloudFront**: Amazon CloudFront는 AWS의 글로벌 CDN(콘텐츠 전송 네트워크) 서비스입니다. 전 세계 400개 이상의 엣지 로케이션(POP)에 콘텐츠를 캐시하여, 단일 리전에 호스팅된 애플리케이션의 데이터를 전 세계 사용자에게 짧은 지연 시간으로 제공할 수 있습니다. 정적 및 동적 콘텐츠 모두 지원합니다.

❌ **B. AWS Direct Connect**: Direct Connect는 온프레미스 데이터센터와 AWS 간의 전용 네트워크 연결을 제공하는 서비스입니다. 전 세계 최종 사용자에게 낮은 지연 시간을 제공하는 CDN 서비스가 아닙니다.

❌ **C. Amazon Route 53 글로벌 DNS**: Route 53은 글로벌 DNS 서비스로 도메인 이름을 IP 주소로 변환하고 트래픽 라우팅을 담당합니다. 콘텐츠를 캐시하여 지연 시간을 줄이는 CDN 기능은 없으며, 지리 기반 라우팅은 가능하지만 캐싱은 지원하지 않습니다.

❌ **D. Amazon S3 전송 가속화**: S3 Transfer Acceleration은 S3 버킷과 클라이언트 간의 파일 전송 속도를 높이는 기능으로, CloudFront의 엣지 네트워크를 활용합니다. 하지만 S3 객체 전송에 특화되어 있으며, 일반 애플리케이션 데이터의 글로벌 배포에는 CloudFront가 더 적합합니다.

💡 **시험 꿀팁**: "전 세계 낮은 지연 시간" + "콘텐츠 배포" = CloudFront(CDN)! CloudFront 핵심: 엣지 로케이션에 캐시 → 오리진 서버 부하 감소 + 사용자 지연 시간 감소. CloudFront는 S3, EC2, ALB, Lambda@Edge 등을 오리진으로 사용 가능.

## Q10. 자본 비용을 운영 비용으로 교환하는 구현 모델

다음 중 고객이 자본 IT 비용을 운영 비용과 완전히 교환할 수 있는 구현 모델은 무엇입니까?

- A. 사내(온프레미스)
- B. 하이브리드
- C. 클라우드
- D. 서비스형 플랫폼

**정답: C**

✅ **C. 클라우드**: 클라우드 컴퓨팅의 핵심 가치 중 하나는 자본 지출(CapEx: Capital Expenditure)을 운영 비용(OpEx: Operational Expenditure)으로 전환하는 것입니다. 서버, 데이터센터 같은 인프라에 대한 대규모 선행 투자(CapEx) 없이, 사용한 만큼만 지불하는 종량제(OpEx) 방식으로 완전히 전환할 수 있습니다.

❌ **A. 사내(온프레미스)**: 온프레미스 환경은 하드웨어 구매, 데이터센터 구축 등에 대규모 자본 지출(CapEx)이 필요합니다. CapEx를 OpEx로 전환하는 것이 불가능합니다.

❌ **B. 하이브리드**: 하이브리드 모델은 온프레미스와 클라우드를 혼합 사용하는 방식으로, 여전히 온프레미스 부분에서 자본 지출이 발생합니다. CapEx를 완전히 OpEx로 전환할 수 없습니다.

❌ **D. 서비스형 플랫폼(PaaS)**: PaaS는 클라우드 제공 모델의 한 유형으로, CapEx를 OpEx로 전환하는 데 기여하지만, "구현 모델"이라는 관점에서는 클라우드가 더 정확한 답입니다. PaaS는 클라우드의 서비스 유형(IaaS/PaaS/SaaS) 중 하나입니다.

💡 **시험 꿀팁**: 클라우드의 6대 장점 암기! ① CapEx → OpEx 전환, ② 규모의 경제 혜택, ③ 용량 추측 불필요, ④ 속도와 민첩성 향상, ⑤ 데이터센터 운영 비용 절감, ⑥ 몇 분 만에 전 세계 배포. "자본 비용" + "운영 비용" 키워드 = 클라우드의 CapEx→OpEx 전환!

## Q11. AWS 자산 관리가 온프레미스보다 쉬운 이유

AWS의 자산 관리가 물리적 데이터 센터의 자산 관리보다 어떻게 더 쉽습니까?

- A. AWS는 사용자가 유지관리할 수 있는 Configuration Management Database를 제공합니다.
- B. AWS는 고객을 대신하여 인프라 검색 검색을 수행합니다.
- C. Amazon EC2는 자산 보고서를 자동으로 생성하여 고객이 지정한 Amazon S3 버킷에 저장합니다.
- D. 사용자는 몇 번의 API 호출로 안정적으로 자산 메타데이터를 수집할 수 있습니다.

**정답: D**

✅ **D. 사용자는 몇 번의 API 호출로 안정적으로 자산 메타데이터를 수집할 수 있습니다**: AWS는 모든 인프라를 API로 제어할 수 있으므로, 몇 번의 API 호출만으로 모든 리소스(EC2 인스턴스, S3 버킷, RDS 등)의 메타데이터를 프로그래밍 방식으로 즉시 조회할 수 있습니다. 온프레미스에서는 물리적 자산을 일일이 수작업으로 추적해야 하는 것과 대조적입니다. AWS Config 서비스를 통해 자산 변경 이력도 자동 추적됩니다.

❌ **A. AWS는 사용자가 유지관리할 수 있는 Configuration Management Database를 제공합니다**: AWS는 CMDB를 직접 제공하지 않습니다. AWS Config가 구성 변경을 추적하지만, 전통적인 CMDB는 ServiceNow 같은 서드파티 도구를 사용합니다.

❌ **B. AWS는 고객을 대신하여 인프라 검색 검색을 수행합니다**: AWS가 고객의 인프라 검색을 대신 수행하지는 않습니다. 고객이 AWS API 또는 콘솔을 통해 직접 자산을 조회합니다. AWS Systems Manager Inventory 같은 서비스가 있지만 AWS가 "대신" 수행하는 것은 아닙니다.

❌ **C. Amazon EC2는 자산 보고서를 자동으로 생성하여 고객이 지정한 S3 버킷에 저장합니다**: Amazon EC2가 자동으로 자산 보고서를 S3에 저장하는 기능은 존재하지 않습니다. 이런 기능은 AWS Systems Manager나 별도의 자동화 스크립트를 통해 구현해야 합니다.

💡 **시험 꿀팁**: AWS의 자산 관리 핵심 서비스: AWS Config (구성 변경 추적 + 규정 준수 평가), AWS Systems Manager Inventory (EC2 인스턴스 소프트웨어 목록 수집), AWS Organizations (다중 계정 리소스 통합 관리). API 기반 관리 = 자동화 + 프로그래밍적 제어 = 클라우드의 핵심 장점!

## Q12. Amazon RDS 전역 중복 데이터베이스 기능

Amazon RDS의 어떤 기능이 전역적으로 중복되는 데이터베이스를 만드는 데 도움이 됩니까?

- A. 스냅샷
- B. 자동 패치 및 업데이트
- C. 영역 간 읽기 복제본
- D. 프로비저닝된 IOPS

**정답: C**

✅ **C. 영역 간 읽기 복제본**: Amazon RDS의 크로스 리전 읽기 복제본(Cross-Region Read Replica)은 다른 AWS 리전에 데이터베이스 복제본을 생성하여 전역적으로 중복된 데이터베이스 환경을 구성합니다. 이를 통해 재해 복구(DR)에 활용하거나, 전 세계 여러 리전의 사용자에게 낮은 지연 시간으로 읽기 쿼리를 처리할 수 있습니다.

❌ **A. 스냅샷**: RDS 스냅샷은 특정 시점의 데이터베이스 백업을 생성하는 기능입니다. 다른 리전으로 복사할 수 있지만, 실시간으로 전역 중복 환경을 제공하는 기능이 아닙니다.

❌ **B. 자동 패치 및 업데이트**: 자동 패치는 데이터베이스 엔진의 보안 패치와 업데이트를 자동으로 적용하는 기능입니다. 전역 중복성과는 관련이 없습니다.

❌ **D. 프로비저닝된 IOPS**: 프로비저닝된 IOPS(Provisioned IOPS)는 데이터베이스 스토리지의 I/O 성능을 보장하는 기능입니다. 전역 중복성이 아닌 성능 최적화에 관련된 기능입니다.

💡 **시험 꿀팁**: RDS 고가용성 vs 글로벌 중복 구분! 다중 AZ(Multi-AZ) = 같은 리전 내 고가용성 + 자동 장애 조치 (읽기 쿼리 불가). 크로스 리전 읽기 복제본 = 다른 리전에 복제 + 읽기 성능 향상 + 글로벌 DR. "전역(Global)" + "중복" 키워드 = 크로스 리전 읽기 복제본!

## Q13. 부서별 AWS 비용 식별 방법 (두 개 선택)

부서별로 AWS 비용을 식별하는 데 사용할 수 있는 방법은 무엇입니까? (두 개를 선택합니다.)

- A. AWS 계정 루트 사용자에 대해 멀티 팩터 인증을 사용합니다.
- B. 각 부서에 대해 별도의 계정을 만듭니다.
- C. 가능하면 예약된 인스턴스를 사용합니다.
- D. 태그를 사용하여 각 인스턴스를 특정 부서와 연결합니다.
- E. 구매 주문을 사용하여 청구서 결제

**정답: B, D**

✅ **B. 각 부서에 대해 별도의 계정을 만듭니다**: 부서별로 별도의 AWS 계정을 생성하면 각 계정의 비용이 완전히 분리되어 명확하게 추적됩니다. AWS Organizations를 사용하면 여러 계정을 중앙에서 관리하면서도 부서별 비용을 독립적으로 파악할 수 있습니다.

✅ **D. 태그를 사용하여 각 인스턴스를 특정 부서와 연결합니다**: AWS 리소스에 태그(Key-Value 쌍)를 적용하면 비용 탐색기와 비용 배분 태그 기능을 통해 부서별 비용을 분류하고 추적할 수 있습니다. 예: `Department: Finance`, `Department: Engineering` 태그를 적용하면 청구서에서 부서별 비용을 확인 가능합니다.

❌ **A. AWS 계정 루트 사용자에 대해 멀티 팩터 인증을 사용합니다**: MFA(Multi-Factor Authentication)는 보안 강화를 위한 인증 방법으로, 비용 추적 및 부서별 비용 식별과는 관련이 없습니다.

❌ **C. 가능하면 예약된 인스턴스를 사용합니다**: 예약 인스턴스는 비용을 절감하는 구매 방법이지, 부서별 비용을 식별하고 배분하는 방법이 아닙니다.

❌ **E. 구매 주문을 사용하여 청구서 결제**: 구매 주문(PO) 방식은 청구서 결제 방법의 하나로, 부서별 비용을 식별하거나 배분하는 기능이 아닙니다.

💡 **시험 꿀팁**: 비용 배분(Cost Allocation) 두 가지 전략: ① 계정 분리 (Account-level separation) — AWS Organizations 활용, ② 태그 기반 분리 (Tag-based) — 비용 배분 태그 활성화 후 Cost Explorer에서 부서별 필터링. 실무에서도 이 두 방법을 함께 사용하는 것이 권장됩니다!

## Q14. AWS 공유 책임 모델에서 고객 책임

AWS 공유 책임 모델에서 고객 책임에는 다음 중 어떤 것이 포함됩니까?

- A. 모든 제품과 서비스를 실행하는 하드웨어, 소프트웨어, 시설 및 네트워크의 보안.

❌ **D. 산업 인증 및 독립적인 타사 증명 획득**: AWS 인프라에 대한 ISO, SOC, PCI DSS 등의 규정 준수 인증 획득은 AWS의 책임입니다. 고객은 자신의 애플리케이션에 대한 규정 준수를 책임집니다.

💡 **시험 꿀팁**: 공유 책임 모델 핵심 구분! AWS 책임(클라우드 자체) = 물리적 보안, 하이퍼바이저, 글로벌 인프라, 관리형 서비스 보안. 고객 책임(클라우드 내부) = 운영 체제, 애플리케이션, 데이터, IAM, 암호화, Security Group 설정. EC2 = 고객이 OS 관리. Lambda/RDS(관리형) = AWS가 OS 관리, 고객은 데이터/접근 권한 관리.

## Q15. AWS 보안 모범 사례 실시간 지침 서비스

AWS 보안 모범 사례에 대한 실시간 지침을 제공하는 관리형 AWS 서비스는 무엇입니까?

- A. AWS X-Ray
- B. AWS Trusted Advisor
- C. Amazon CloudWatch
- D. AWS 시스템 매니저

**정답: B**

✅ **B. AWS Trusted Advisor**: AWS Trusted Advisor는 AWS 환경을 모범 사례와 비교하여 실시간으로 권고사항을 제공하는 관리형 서비스입니다. 5개 카테고리(비용 최적화, 성능, 보안, 내결함성, 서비스 한도)에 대한 검사를 수행하며, 보안 그룹의 위험한 포트 개방, S3 버킷 공개 접근, IAM 모범 사례 미준수 등의 보안 문제를 실시간으로 알려줍니다.

❌ **C. Amazon CloudWatch**: CloudWatch는 AWS 리소스와 애플리케이션의 모니터링 서비스로, 지표(Metrics), 로그(Logs), 이벤트(Events), 알람(Alarms)을 제공합니다. 보안 모범 사례 지침이 아닌 운영 모니터링에 특화되어 있습니다.

❌ **D. AWS 시스템 매니저**: AWS Systems Manager는 EC2 인스턴스와 온프레미스 서버를 중앙에서 관리하는 서비스로, 패치 관리, Run Command, Session Manager 등의 기능을 제공합니다. 보안 모범 사례 실시간 지침이 아닌 운영 자동화 도구입니다.

💡 **시험 꿀팁**: Trusted Advisor 5가지 검사 카테고리 암기: ① 비용 최적화 (미사용 리소스 감지), ② 성능 (성능 개선 권고), ③ 보안 (보안 취약점 감지), ④ 내결함성 (가용성 향상 방안), ⑤ 서비스 한도 (한도 초과 경고). "모범 사례 권고" + "실시간 지침" = Trusted Advisor!

## Q16. EC2 인스턴스 탄력성을 추가하는 기능

변화하는 워크로드 수요를 처리하기 위해 Amazon EC2 인스턴스에 탄력성을 추가하는 기능은 무엇입니까?

- A. 리소스 그룹
- B. 라이프사이클 정책
- C. 애플리케이션 로드 밸런서
- D. Amazon EC2 자동 확장

**정답: D**

✅ **D. Amazon EC2 자동 확장**: Amazon EC2 Auto Scaling은 수요 변화에 따라 EC2 인스턴스 수를 자동으로 늘리거나(Scale Out) 줄이는(Scale In) 서비스입니다. CPU 사용률, 요청 수 등의 지표를 기반으로 최소/최대 인스턴스 수 범위 내에서 자동으로 확장/축소하여 비용 효율적이고 고가용성 환경을 구성합니다. 이것이 바로 클라우드의 "탄력성(Elasticity)" 개념입니다.

❌ **A. 리소스 그룹**: AWS 리소스 그룹은 태그나 CloudFormation 스택을 기반으로 관련 AWS 리소스를 그룹화하여 관리하는 기능입니다. 수요에 따른 자동 확장 기능이 아닙니다.

❌ **B. 라이프사이클 정책**: 라이프사이클 정책은 주로 S3 객체나 EBS 스냅샷의 자동 관리(전환, 삭제 등)에 사용됩니다. EC2 인스턴스의 탄력적 확장과는 관련이 없습니다.

❌ **C. 애플리케이션 로드 밸런서**: ALB(Application Load Balancer)는 HTTP/HTTPS 트래픽을 여러 EC2 인스턴스에 분산하는 서비스입니다. 트래픽 분산은 담당하지만 인스턴스 수를 자동으로 늘리거나 줄이는 탄력성 기능은 없습니다. 실제로 Auto Scaling과 함께 사용됩니다.

💡 **시험 꿀팁**: 탄력성(Elasticity) = Auto Scaling! Auto Scaling + ALB 조합이 표준 아키텍처. Auto Scaling 3가지 정책: ① 동적 확장 (지표 기반 자동), ② 예약 확장 (일정 기반), ③ 예측 확장 (ML 기반 예측). "탄력성" + "자동" + "수요 변화" 키워드 = EC2 Auto Scaling!

## Q17. 고객이 책임지는 클라우드 보안 측면 (두 개 선택)

AWS 공유 책임 모델에서 고객은 클라우드 보안의 어떤 측면을 책임집니까? (두 개를 선택합니다.)

- A. 시각화 관리
- B. 하드웨어 관리
- C. 암호화 관리

✅ **E. 방화벽 관리**: Security Group(인스턴스 레벨)과 NACL(서브넷 레벨)을 통한 가상 방화벽 규칙 관리는 고객의 책임입니다. 어떤 포트와 프로토콜을 허용할지 고객이 직접 설정해야 합니다.

❌ **B. 하드웨어 관리**: 물리적 서버, 네트워크 장비, 스토리지 하드웨어의 유지보수와 보안은 AWS의 책임입니다. 고객은 물리적 하드웨어에 접근하거나 관리할 수 없습니다.

❌ **D. 시설물 관리**: 데이터센터 건물, 물리적 접근 통제, 환경 제어(냉각, 전력) 등 시설 관리는 AWS의 책임입니다. AWS는 데이터센터 위치조차 공개하지 않을 정도로 물리적 보안을 철저히 관리합니다.

💡 **시험 꿀팁**: 고객 책임(클라우드 IN 보안) 핵심 항목: 데이터 암호화, IAM/접근 관리, OS 패치, 애플리케이션 보안, 네트워크 설정(Security Group/NACL), 방화벽 규칙. AWS 책임(클라우드 OF 보안): 물리적 보안, 하드웨어, 하이퍼바이저, 글로벌 인프라, 관리형 서비스.

## Q18. 온프레미스 애플리케이션의 AWS 클라우드 스토리지 연결 서비스

사내 애플리케이션이 표준 파일 스토리지 프로토콜을 통해 AWS 클라우드 스토리지를 원활하게 사용할 수 있도록 지원하는 AWS 하이브리드 스토리지 서비스는 무엇입니까?

- A. AWS Direct Connect
- B. AWS 스노우볼
- C. AWS 스토리지 게이트웨이
- D. AWS Snowball Edge

**정답: C**

✅ **C. AWS 스토리지 게이트웨이**: AWS Storage Gateway는 온프레미스 애플리케이션과 AWS 클라우드 스토리지를 연결하는 하이브리드 스토리지 서비스입니다. NFS, SMB, iSCSI 등 표준 파일 스토리지 프로토콜을 지원하므로, 기존 온프레미스 애플리케이션을 수정하지 않고도 클라우드 스토리지(S3, Glacier 등)를 원활하게 사용할 수 있습니다. 파일 게이트웨이, 볼륨 게이트웨이, 테이프 게이트웨이 세 가지 유형이 있습니다.

❌ **A. AWS Direct Connect**: Direct Connect는 온프레미스와 AWS 간의 전용 네트워크 연결 서비스입니다. 네트워크 연결 품질(대역폭, 지연 시간)을 개선하지만, 스토리지 프로토콜을 통한 클라우드 스토리지 접근을 지원하는 하이브리드 스토리지 서비스가 아닙니다.

❌ **B. AWS 스노우볼**: AWS Snowball은 대량의 데이터를 물리적 장치를 통해 AWS로 오프라인 전송하는 데이터 마이그레이션 서비스입니다. 표준 파일 프로토콜을 통한 지속적인 하이브리드 스토리지 연결이 아닌 일회성 대용량 데이터 이전에 사용됩니다.

❌ **D. AWS Snowball Edge**: Snowball Edge는 Snowball에 컴퓨팅 기능이 추가된 장치로, 네트워크 연결이 어려운 원격/엣지 환경에서 로컬 데이터 처리와 스토리지에 사용됩니다. 하이브리드 스토리지 프로토콜 연결 서비스가 아닙니다.

💡 **시험 꿀팁**: AWS Storage Gateway 유형 암기! ① 파일 게이트웨이 (File GW) = NFS/SMB로 S3에 파일 저장, ② 볼륨 게이트웨이 (Volume GW) = iSCSI 블록 스토리지 → S3/EBS, ③ 테이프 게이트웨이 (Tape GW) = 가상 테이프로 S3/Glacier 백업. "온프레미스 + 표준 프로토콜 + 클라우드 스토리지" = Storage Gateway!

## Q19. 공유 책임 모델에서 AWS의 책임

공유 책임 모델에서 AWS의 책임은 무엇입니까?

- A. 취약한 포트에 대한 트래픽을 차단하도록 네트워크 ACL 업데이트
- B. Amazon EC2 인스턴스에서 실행되는 운영 체제 패치 적용.
- C. 기본 EC2 호스트에서 펌웨어 업데이트.
- D. 취약한 포트에 대한 트래픽을 차단하기 위해 Security Group 규칙 업데이트

**정답: C**

✅ **C. 기본 EC2 호스트에서 펌웨어 업데이트**: EC2 인스턴스가 실행되는 물리적 호스트 서버(베어메탈 서버)의 펌웨어 업데이트는 AWS의 책임입니다. 고객은 가상 머신(EC2 인스턴스) 내부만 관리하며, 그 아래에 있는 물리적 하드웨어와 하이퍼바이저 레이어는 모두 AWS가 관리합니다.

❌ **A. 취약한 포트에 대한 트래픽을 차단하도록 네트워크 ACL 업데이트**: NACL(네트워크 접근 제어 목록) 규칙 설정은 고객의 VPC 내 네트워크 보안 설정으로, 고객의 책임입니다. AWS는 NACL 기능을 제공하지만 규칙 구성은 고객이 해야 합니다.

❌ **B. Amazon EC2 인스턴스에서 실행되는 운영 체제 패치 적용**: EC2 인스턴스 내 운영 체제(OS) 패치는 고객의 책임입니다. 공유 책임 모델에서 EC2의 경우 AWS는 하이퍼바이저까지 관리하고, 게스트 OS부터는 고객이 관리합니다.

❌ **D. 취약한 포트에 대한 트래픽을 차단하기 위해 Security Group 규칙 업데이트**: Security Group 규칙 설정은 고객의 책임입니다. AWS는 Security Group 기능을 제공하지만, 어떤 트래픽을 허용/차단할지는 고객이 직접 구성해야 합니다.

💡 **시험 꿀팁**: EC2 공유 책임 경계선! AWS 책임(하이퍼바이저 아래): 물리 서버, 물리 네트워크, 물리 스토리지, 데이터센터, 펌웨어, 하이퍼바이저. 고객 책임(하이퍼바이저 위): 게스트 OS, OS 패치, 애플리케이션, 보안 그룹, NACL, 데이터 암호화. "펌웨어" + "물리 호스트" = AWS 책임!

## Q20. 다중 AZ RDS 배포 아키텍처 원칙

다중 가용성 영역 모드에서 Amazon RDS(Relational Database Service) 인스턴스를 배포할 때 사용되는 아키텍처 원칙은 무엇입니까?

- A. 느슨한 결합을 구현합니다.
- B. 고장을 위한 설계.
- C. 자동화할 수 있는 모든 것을 자동화합니다.
- D. 서버가 아닌 서비스를 사용합니다.

**정답: B**

✅ **B. 고장을 위한 설계**: 다중 AZ(Multi-AZ) RDS 배포는 "고장을 위한 설계(Design for Failure)" 원칙을 구현합니다. 기본 DB 인스턴스와 대기(Standby) 인스턴스를 서로 다른 가용 영역에 배치하여, 한 AZ에서 장애가 발생해도 자동으로 다른 AZ의 대기 인스턴스로 장애 조치(Failover)됩니다. 단일 장애점(SPOF)을 제거하여 고가용성을 보장합니다.

❌ **A. 느슨한 결합을 구현합니다**: 느슨한 결합(Loose Coupling)은 컴포넌트 간 의존성을 최소화하여 독립적으로 확장하고 장애를 격리하는 원칙입니다. SQS, SNS 등을 통한 메시지 기반 아키텍처가 대표적이며, 다중 AZ RDS와는 직접적인 관련이 없습니다.

❌ **C. 자동화할 수 있는 모든 것을 자동화합니다**: 자동화 원칙은 반복 작업을 자동화하여 인적 오류를 줄이는 것으로, Infrastructure as Code(IaC), 자동 패치, 자동 백업 등이 해당됩니다. 다중 AZ 자체가 자동화 원칙의 구현이라기보다는 가용성 원칙의 구현입니다.

❌ **D. 서버가 아닌 서비스를 사용합니다**: "서버 대신 서비스" 원칙은 EC2 인스턴스를 직접 관리하는 대신 관리형 서비스(RDS, Lambda, SQS 등)를 사용하는 것입니다. 다중 AZ RDS 자체는 이미 관리형 서비스이지만, 다중 AZ 구성은 "고장을 위한 설계" 원칙을 더 직접적으로 나타냅니다.

💡 **시험 꿀팁**: AWS Well-Architected Framework의 핵심 설계 원칙: ① 고장을 위한 설계 (단일 장애점 제거, 다중 AZ), ② 느슨한 결합 (SQS/SNS로 컴포넌트 분리), ③ 탄력성 (Auto Scaling), ④ 자동화 (IaC, Auto Scaling), ⑤ 서비스 활용 (관리형 서비스 사용). "다중 AZ" + "자동 장애 조치" = 고장을 위한 설계!
