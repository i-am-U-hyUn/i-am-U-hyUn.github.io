## 들어가며

지금 회사 Business Operations 조직에서 **Process Innovation(PI)**을 전담하면서, 사내 프로세스 개선 안건을 접수·추적·평가하는 **PI 웹 포털**을 기획부터 개발, 운영까지 직접 맡고 있다.

이 글에는 회사 내부 안건 내용, 부서명, 실제 통계 수치는 전혀 담지 않았다. 아래 화면 캡처와 수치는 전부 **가상의 예시 데이터로 만든 목업**이고, 다루는 내용은 어디까지나 **구조와 기술적 선택**에 대한 이야기다.

> 안건 상세, 담당자 이름, 실제 만족도 수치 등은 보안상 전부 제외했습니다. 아래 이미지는 설명을 돕기 위한 목업입니다.

## 1. 왜 이런 도구가 필요했나

PI 안건은 보통 이런 흐름으로 굴러간다.

1. 부서에서 개선 요청(안건)을 접수한다.
2. 담당자(Owner)가 배정되고 개선 활동이 진행된다.
3. 완료되면 개선계획서를 제출하고, 요청 부서가 만족도를 평가한다.

안건 수가 늘어나면서 스프레드시트 한 장으로 관리하던 방식은 금방 한계에 부딪혔다.

- 안건마다 **열람 권한**이 달라야 하는데(관리자는 전체, 실무자는 본인 관련 건만), 시트 공유 설정만으로는 세밀하게 제어하기 어려웠다.
- Status는 "진행중"인데 개선계획서가 안 올라오거나, 완료됐는데 만족도 평가가 비어 있는 안건을 사람이 일일이 찾아 리마인드해야 했다.
- 분야별·부서별 현황을 한눈에 보려면 매번 피벗 테이블을 새로 만져야 했다.

세 가지 모두 "자동화하면 사라질 반복 작업"이라 직접 포털을 만들기로 했다.

## 2. 왜 Google Apps Script인가

사내 표준 협업 도구가 이미 Google Workspace였고, 데이터 원본도 스프레드시트였다. 별도 서버·DB를 구축하는 대신 **Google Apps Script(GAS)로 스프레드시트를 그대로 데이터 계층 삼아** 웹앱을 얹는 방식을 선택했다.

| 고려사항 | 판단 |
|---|---|
| 인프라 | 서버 프로비저닝·배포 파이프라인 없이 스크립트 배포만으로 운영 가능 |
| 데이터 | 현업 담당자들이 이미 시트에 편하게 데이터를 채우고 있어, 별도 입력 화면 강제가 불필요 |
| 인증 | 회사 Google 계정 기반이라 별도 회원가입/비밀번호 관리가 필요 없음 |
| 제약 | 실행 시간 6분 제한, 동시 실행 쿼터 등 GAS 고유 한계는 감수 |

사내용 소규모 도구에는 무거운 백엔드보다 **이미 있는 인프라(Workspace)를 그대로 활용하는 쪽**이 개발 속도와 유지보수 부담 모두에서 유리했다.

## 3. 아키텍처

![PI 포털 아키텍처 개요](/assets/img/posts/pi-portal/architecture.svg)
_실제 서비스 URL, 프로젝트 식별자, 안건 데이터는 표기하지 않았다._

- **프론트엔드**: 하나의 `Index.html`로 과제 현황판 / 신규 안건 접수 / 현황 요약 세 개 탭을 구성

- **데이터 계층**: Google Sheets — 안건 목록, 권한 목록, 설문/제출 로그를 시트별로 분리
- **외부 연동**: Gmail(인증·알림), Directory API(계정↔이름 매핑), Vertex AI Gemini(자동 분류)

## 4. 핵심 기능

### 4-1. 이메일 OTP + 열람 권한 분리

로그인은 사내 이메일로 6자리 OTP를 받는 방식이다. 인증 후에는 계정에 따라 보이는 데이터 범위가 달라진다.

- **전체 권한 계정**: 모든 안건 열람
- **일반 계정**: 본인이 요청자·Owner·이해관계자로 등록된 안건만 필터링해서 노출

로직을 단순화하면 이렇다.

```js
function getListSheetData(email) {
  // STEP 1: 관리자 목록에 등록된 계정이면 전체 안건 열람 가능
  if (isFullAccessAccount(email)) {
    return { access: 'full', data: getAllRows() };
  }

  // STEP 2: 그 외에는 요청자 / Owner / 이해관계자 항목에
  //         본인 이름이 포함된 안건만 필터링
  const myName = resolveDisplayName(email); // Google 조직도 API로 이메일 → 표시 이름 조회
  const rows = getAllRows().filter(row =>
    [row.requester, row.owner, row.stakeholders].join(',').includes(myName)
  );

  return rows.length ? { access: 'partial', data: rows } : { access: 'none' };
}
```

이메일에서 실명을 바로 알 수 없기 때문에, Google People API로 먼저 표시 이름을 조회한 뒤(실패 시 관리 콘솔 API로 폴백) 안건의 담당자 칸과 대조하는 두 단계 구조로 짰다.

### 4-2. Gemini 기반 안건 자동 분류

안건이 쌓이면서 "이 안건은 어떤 분야인가"를 매번 사람이 태깅하는 것도 병목이 됐다. Vertex AI Gemini에 안건의 요청 내용(Request)과 배경(Context)을 넘겨, 미리 정의한 카테고리 중 하나로 자동 분류하도록 했다.

분류 기준은 하나의 축이 아니라 **3대 지표**를 종합해 판단하도록 프롬프트를 설계했다.

| 지표 | 질문 |
|---|---|
| 목적성 (Goal Alignment) | 이 카테고리의 조치가 없으면 문제 해결이 불가능한가? |
| 리소스 비중 (Resource Center of Gravity) | 이 영역 리소스 투입이 프로젝트 성패를 좌우하는가? |
| 기대 효과 (Impact) | 이 카테고리 관점의 성과 지표가 직접적으로 개선되는가? |

여러 카테고리에 걸쳐 있는 애매한 안건은 각 카테고리별로 3개 지표 점수를 합산해 최고점 카테고리 하나로 수렴시켰다. `temperature: 0`으로 고정해 같은 입력이면 같은 분류 결과가 나오도록 결정성을 확보했다.

### 4-3. 미제출 자동 알림

- 매주 금요일: Status가 "진행중"인데 개선계획서가 비어 있는 안건 → Owner에게 자동 메일
- 매일: Status가 "완료"인데 만족도 설문이 비어 있는 안건 → 요청자에게 자동 메일

담당자 이름으로 이메일 주소를 역조회해야 해서, 이름↔이메일 매핑 결과를 스크립트 캐시에 저장해 API 호출을 줄였다.

## 6. 개발하며 부딪힌 것들

- **6분 실행 제한**: 행이 수백 개를 넘어가면서 전체 스캔 로직이 느려졌다. `getValues()`로 시트를 한 번에 통째로 읽고 메모리에서 필터링하는 방식으로 바꿔 API 호출 수를 줄였다.
- **필터로 숨긴 행 문제**: 시트에 필터가 걸려 있으면 `getLastRow()`가 숨겨진 행까지는 제대로 못 잡는 경우가 있어서, 마지막 행을 여유 있게 잡고 값이 채워진 실제 마지막 행을 역방향으로 찾아내는 방식으로 우회했다.
- **이름 기반 매칭의 한계**: 이메일이 아니라 표시 이름으로 담당자를 매칭하다 보니 동명이인·이름 표기 차이 이슈가 있었다. People API 우선, 실패 시 관리 콘솔 API로 폴백하고 결과를 캐싱해 안정성과 속도를 함께 잡았다.

## 마치며

PI 담당자로서 프로세스를 진단하고 개선안을 설계하는 일과, 그 개선안을 돌아가게 만드는 도구를 직접 코드로 짜는 일은 완전히 다른 근육을 쓴다. 이 포털을 만들면서 "안건 관리"라는 하나의 프로세스 자체를 진단하고 재설계해본 셈인데, 결국 PI든 개발이든 본질은 같았다 — **반복되는 병목을 찾아서 없애는 것.**
