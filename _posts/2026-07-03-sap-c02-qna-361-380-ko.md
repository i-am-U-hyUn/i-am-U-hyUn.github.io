## QUESTION 361

**문제**: 회사가 재택근무 직원들에게 내부 웹 애플리케이션(HR 시스템, 사내 위키 등) 접근을 제공해야 하는데, 기존 VPN 방식은 모든 트래픽을 터널링해 성능 저하와 관리 복잡성을 유발한다. **VPN 클라이언트 설치 없이**, 브라우저에서 직접 애플리케이션 단위로 접근하며, 매 요청마다 사용자 신원과 디바이스 상태를 확인하는 제로 트러스트 방식을 구현하고 싶다. 솔루션은?

**보기**
- A. 기존 Site-to-Site VPN의 대역폭만 증설(VPN 자체의 아키텍처(전체 네트워크 터널링)는 그대로 유지되어 "VPN 클라이언트 없이 애플리케이션 단위 제로 트러스트 접근"이라는 요구를 충족하지 못함).
- B. **AWS Verified Access를 사용해, IAM Identity Center 및 디바이스 신뢰 데이터 공급자와 통합된 접근 정책을 애플리케이션별로 정의하고, 사용자가 VPN 클라이언트 없이 브라우저로 직접 접근하되 매 요청마다 신원/디바이스 상태를 평가.**
- C. 각 애플리케이션 앞에 API Gateway를 두고 API 키로만 접근 제어(API 키만으로는 세밀한 신원/디바이스 상태 기반의 제로 트러스트 정책을 구현할 수 없고, 매 요청 단위의 동적 평가도 어려움).
- D. 모든 내부 애플리케이션을 퍼블릭 인터넷에 노출하고 Cognito로만 인증(내부 애플리케이션을 퍼블릭에 노출하는 것은 공격 표면을 크게 늘리며, 디바이스 상태 평가 같은 제로 트러스트의 핵심 요소가 빠져 있음).

**정답: B**

**해설**
**AWS Verified Access**는 VPN 없이 제로 트러스트 원칙에 따라 내부 애플리케이션에 대한 접근을 제어하는 서비스입니다. **IAM Identity Center**(신원) 및 서드파티 디바이스 신뢰 데이터 공급자(디바이스 상태)와 통합해, 애플리케이션별로 세밀한 접근 정책(예: "회사 관리 기기 + MFA 인증된 사용자만")을 정의할 수 있으며, 사용자는 브라우저로 애플리케이션에 직접 접근하되 **매 요청마다** 신원과 디바이스 상태를 지속적으로 평가받습니다. 이는 전체 네트워크를 터널링하는 기존 VPN보다 세밀하고 안전한 접근 모델입니다.

**왜 다른 보기는 오답인가**
- A: VPN 대역폭 증설은 근본적인 아키텍처(전체 네트워크 터널링)를 바꾸지 않아 제로 트러스트 요구를 충족하지 못합니다.
- C: API 키만으로는 신원/디바이스 상태에 대한 동적 제로 트러스트 평가를 구현할 수 없습니다.
- D: 내부 애플리케이션의 퍼블릭 노출은 공격 표면을 늘리며, 디바이스 상태 평가 같은 핵심 제로 트러스트 요소가 빠져 있습니다.

> 💡 **시험 꿀팁**: VPN 클라이언트 없이 **애플리케이션 단위의 제로 트러스트 접근**(신원 + 디바이스 상태 기반)이 필요하면 **AWS Verified Access**가 표준 정답입니다.

## QUESTION 362

**문제**: 프로덕션 RDS MySQL 데이터베이스를 메이저 버전(예: 5.7 → 8.0)으로 업그레이드해야 하는데, 애플리케이션 호환성 문제가 발견될 경우 **즉시 원래 버전으로 되돌릴 수 있어야** 하며, 업그레이드로 인한 다운타임과 리스크를 최소화하고 싶다. 솔루션은?

**보기**
- A. 프로덕션 인스턴스에서 직접 인플레이스(in-place) 메이저 버전 업그레이드 수행(직접 업그레이드는 되돌리기가 매우 어렵거나 불가능하며, 문제 발생 시 스냅샷 복원 등 복잡하고 시간이 오래 걸리는 롤백 절차가 필요함).
- B. **RDS 블루/그린 배포(Blue/Green Deployments)를 사용해, 업그레이드된 새 버전의 그린 환경을 프로덕션(블루)과 동기화된 상태로 별도로 생성해 충분히 테스트한 뒤, 문제가 없으면 빠르게 전환(switchover)하고, 문제가 있으면 그린 환경을 폐기하고 블루 환경을 그대로 유지.**
- C. 읽기 복제본을 새 버전으로 업그레이드한 뒤 프라이머리로 승격(읽기 복제본은 프라이머리와 다른 엔진 버전을 유지하는 것 자체가 기술적으로 제한적이며, 안전한 사전 격리 테스트와 빠른 롤백을 위한 전용 매커니즘이 아님).
- D. 애플리케이션을 잠시 중단하고 수동으로 덤프/복원한 뒤 새 버전에 임포트(수동 덤프/복원은 대규모 데이터베이스에서 다운타임이 매우 길고, 문제 발생 시 롤백도 복잡함).

**정답: B**

**해설**
**RDS 블루/그린 배포**는 프로덕션(블루) 환경과 동기화(논리적 복제)되는 업그레이드된 새 버전의 격리된 **그린 환경**을 생성해, 프로덕션에 영향을 주지 않고 충분히 테스트할 수 있게 해줍니다. 테스트 결과가 만족스러우면 **빠른 전환(switchover)**으로 그린 환경을 새로운 프로덕션으로 만들고, 문제가 발견되면 그린 환경을 폐기하고 기존 블루 환경을 그대로 유지하면 되므로, 메이저 버전 업그레이드의 리스크와 다운타임을 모두 최소화하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 인플레이스 업그레이드는 되돌리기가 어렵고 문제 발생 시 대응이 매우 복잡합니다.
- C: 읽기 복제본을 다른 메이저 버전으로 운영하는 것은 제약이 많고, 사전 테스트/빠른 롤백을 위한 전용 메커니즘이 아닙니다.
- D: 수동 덤프/복원은 대규모 데이터에서 다운타임이 매우 길어집니다.

> 💡 **시험 꿀팁**: RDS/Aurora의 **메이저 버전 업그레이드를 안전하게(사전 테스트 + 빠른 롤백 가능) 수행**하려면 **블루/그린 배포(Blue/Green Deployments)**가 표준 정답입니다.

## QUESTION 363

**문제**: 회사가 S3에 저장된 수십억 개의 객체 중 특정 조건(예: 2023년 이전 생성, 특정 접두사)에 맞는 객체들에 새로운 태그를 일괄로 부여하거나 다른 버킷으로 복사해야 한다. 객체 수가 너무 많아 개별 API 호출로 처리하는 것은 비현실적이다. 솔루션은?

**보기**
- A. 각 객체를 나열(List)한 뒤 Lambda 함수를 반복 호출해 개별적으로 태그 지정/복사(수십억 개의 개별 API 호출을 자체적으로 관리(재시도, 진행 상황 추적, 속도 제한 등)해야 해서 매우 비효율적이고 오류 발생 시 복구가 어려움).
- B. **S3 Batch Operations를 사용해, S3 인벤토리 리포트나 CSV 매니페스트를 입력으로 대상 객체 목록을 지정하고, 태그 지정(PUT object tagging) 또는 복사(Copy) 작업을 대규모로 실행하며 진행 상황과 실패 항목을 자동으로 추적.**
- C. 모든 객체를 애플리케이션으로 다운로드해 로컬에서 처리한 뒤 다시 업로드(수십억 개 객체를 다운로드/재업로드하는 것은 시간과 비용이 막대하며 매우 비효율적).
- D. S3 라이프사이클 정책으로 태그를 자동 부여(라이프사이클 정책은 스토리지 클래스 전환이나 만료 처리를 위한 것이며, 임의의 조건에 따라 커스텀 태그를 일괄 부여하거나 다른 버킷으로 복사하는 기능은 제공하지 않음).

**정답: B**

**해설**
**S3 Batch Operations**는 수십억 개에 달하는 대규모 객체 집합에 대해 태그 지정, 복사, ACL 변경, Object Lock 보존 설정, Lambda 함수 호출 등의 작업을 **대규모로 실행**할 수 있는 관리형 기능입니다. S3 인벤토리 리포트나 CSV 매니페스트로 대상 객체 목록을 지정하면, 작업의 진행 상황을 추적하고 실패한 항목에 대한 보고서를 자동으로 생성해, 개별 API 호출을 직접 관리할 필요 없이 대규모 객체 작업을 안정적으로 수행할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 자체적으로 수십억 건의 API 호출을 관리하는 것은 재시도/추적/속도 제한 로직을 직접 구현해야 해서 매우 비효율적입니다.
- C: 전체 객체를 다운로드/재업로드하는 것은 시간과 비용 면에서 비현실적입니다.
- D: 라이프사이클 정책은 스토리지 클래스 전환/만료용이며 임의의 일괄 태그 지정이나 복사 기능은 제공하지 않습니다.

> 💡 **시험 꿀팁**: S3의 **대규모 객체 집합(수십억 개)에 대한 일괄 태그 지정/복사/기타 작업**을 안정적으로 수행하려면 **S3 Batch Operations**가 표준 정답입니다.

## QUESTION 364

**문제**: Python으로 작성된 Lambda 함수가 큰 머신러닝 라이브러리를 임포트하면서 콜드 스타트 지연이 발생한다. 이 함수는 SnapStart를 지원하지 않는 런타임이다(SnapStart는 현재 Java, Python, .NET 일부 런타임에 한정 지원되며, 이 시나리오는 특정 미지원 런타임/구성을 가정). 트래픽이 예측 가능한 패턴(업무 시간에 집중)을 보이는 경우, 콜드 스타트를 없애기 위한 대안은?

**보기**
- A. 함수 코드를 완전히 재작성해 라이브러리 의존성을 제거(핵심 머신러닝 기능 자체를 포기해야 할 수 있어 기능 요구사항과 상충할 위험이 큼).
- B. **Application Auto Scaling과 연동해 예측 가능한 트래픽 패턴(예: 업무 시간 시작 전)에 맞춰 스케줄 기반으로 프로비저닝된 동시성(Provisioned Concurrency)의 양을 사전에 조정.**
- C. 함수를 컨테이너 이미지 기반으로 전환(컨테이너 이미지 기반 Lambda는 오히려 이미지 크기가 커질 경우 콜드 스타트가 더 길어질 수 있으며, 이 자체가 콜드 스타트를 없애는 기능은 아님).
- D. 함수의 제한 시간(timeout)을 최대로 늘림(제한 시간은 실행 가능한 최대 시간을 늘릴 뿐이며 콜드 스타트 지연 자체와는 무관함).

**정답: B**

**해설**
**프로비저닝된 동시성(Provisioned Concurrency)**은 미리 초기화된 실행 환경을 유지해 콜드 스타트를 원천적으로 제거합니다. 트래픽이 업무 시간에 집중되는 등 **예측 가능한 패턴**을 보인다면, Application Auto Scaling의 **예약된 작업(scheduled scaling)**과 연동해 트래픽이 몰리기 직전에 프로비저닝된 동시성 양을 늘리고, 트래픽이 적은 야간/주말에는 줄여 불필요한 상시 비용을 최소화하면서도 콜드 스타트 없는 응답성을 확보할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 라이브러리 의존성 제거는 핵심 기능 자체를 포기해야 할 위험이 있는 근본적인 재설계입니다.
- C: 컨테이너 이미지 전환 자체는 콜드 스타트를 없애는 기능이 아니며, 이미지 크기에 따라 오히려 악화될 수 있습니다.
- D: 제한 시간(timeout) 조정은 콜드 스타트 지연과 무관한 별개의 설정입니다.

> 💡 **시험 꿀팁**: SnapStart를 사용할 수 없는 런타임에서 **예측 가능한 트래픽 패턴**에 맞춰 콜드 스타트를 없애려면 **스케줄 기반 프로비저닝된 동시성(Provisioned Concurrency + Application Auto Scaling 예약 작업)**이 표준 정답입니다.

## QUESTION 365

**문제**: 멀티테넌트 SaaS 회사가 공유된 AWS 인프라(동일 EC2/RDS/Lambda를 여러 고객이 함께 사용)의 비용을 **개별 고객 테넌트별로 정확하게 배분**하고 싶다. 리소스 자체가 계정이나 태그로 명확히 분리되어 있지 않고, 대신 애플리케이션 로그에 테넌트 식별자가 기록된다. 솔루션은?

**보기**
- A. 모든 리소스에 테넌트 ID 태그를 붙이고 Cost Explorer로 태그별 비용 확인(리소스 자체가 여러 테넌트에 의해 공유되고 있어 리소스 단위 태깅만으로는 개별 테넌트별 세분화된 사용량 기반 배분이 불가능 — 공유 리소스 내부의 테넌트별 실제 사용 비율을 반영하지 못함).

## QUESTION 369

**Organizations 선언적 정책(declarative policies)**은 SCP처럼 IAM 권한을 제어하는 것이 아니라, 특정 AWS 서비스의 **기본 동작/설정 자체**(예: EC2 인스턴스 메타데이터 옵션을 IMDSv2 필수로)를 조직 차원에서 선언적으로 정의하고, 개별 계정에서 이 설정이 임의로 변경되는 것을 원천적으로 방지합니다. 새로 생성되는 계정에도 자동으로 적용되어, "설정값 자체에 대한 중앙 집중식 선언적 강제"라는 요구에 정확히 맞는 비교적 최신 기능입니다.

**왜 다른 보기는 오답인가**
- A: Config 규칙 기반 탐지는 사후 발견일 뿐이며, 설정 변경 자체를 사전에 막지 못합니다.
- C: SCP도 관련 API 호출을 조건부로 거부하도록 구성할 수 있지만, 서비스 기본 설정값 자체를 선언적으로 통일하는 목적에는 선언적 정책이 더 직접적이고 간단합니다.
- D: 문서 기반 가이드라인은 강제력이 전혀 없습니다.

> 💡 **시험 꿀팁**: 조직 전체에서 **특정 서비스의 기본 설정값 자체를 선언적으로 통일하고 개별 계정의 변경을 원천 차단**하려면 **Organizations 선언적 정책(declarative policies)**이 표준 정답입니다.

**문제**: 회사가 Amazon OpenSearch Service 도메인에 중요한 로그/검색 데이터를 저장하고 있으며, 리전 재해 시 다른 리전에서 빠르게 서비스를 재개할 수 있어야 한다. 스냅샷 기반 백업/복원은 RPO가 너무 길다고 판단된다. 솔루션은?

## QUESTION 371

**문제**: Lambda 함수가 S3 이벤트에 의해 비동기(asynchronous)로 호출되는데, 함수 실행이 **성공했을 때는 결과를 SQS 큐로**, **실패했을 때는 다른 SQS 큐(DLQ 역할)로** 자동 라우팅하고 싶다. 함수 코드 내부에 성공/실패 처리 로직과 재시도 로직을 직접 구현하고 싶지 않다. 솔루션은?

**보기**
- A. 함수 코드 끝에서 try-catch로 성공/실패를 판단해 각각 다른 SQS로 직접 메시지 발행(함수 코드 내부에 이 로직을 직접 구현해야 해서 "코드에 직접 구현하고 싶지 않다"는 요구에 반하며, 함수 자체의 타임아웃/크래시 같은 상황은 이 방식으로 포착하지 못함).
- B. **Lambda 함수의 대상(destinations) 설정에서, 비동기 호출의 성공 시(OnSuccess) 대상과 실패 시(OnFailure) 대상을 각각 다른 SQS 큐로 지정해, Lambda 서비스가 실행 결과에 따라 자동으로 라우팅하도록 구성.**
- C. EventBridge 규칙을 만들어 Lambda 실행 완료 이벤트를 감지해 분기 처리(비동기 호출 완료를 감지하는 표준적인 방법이 아니며, Lambda가 기본 제공하는 destinations 기능을 두고 불필요하게 복잡한 우회 경로를 만드는 것).
- D. Step Functions로 Lambda 호출을 감싸고 성공/실패 상태에 따라 분기(가능한 방법이지만, 단순 성공/실패 라우팅만 필요한 경우 Step Functions 워크플로우 전체를 도입하는 것은 이 문제의 요구에 비해 과도하게 복잡함).

**정답: B**

**해설**
**Lambda 대상(destinations)** 기능은 함수를 코드 수정 없이, 비동기 호출의 **성공(OnSuccess) 또는 실패(OnFailure)** 결과에 따라 지정된 대상(SQS, SNS, EventBridge, 다른 Lambda 함수)으로 **자동으로 라우팅**합니다. 이를 활용하면 함수 자체의 타임아웃이나 크래시로 인한 실패까지 포함해, 실행 결과에 따른 후속 처리(성공 큐/실패 큐로 분리)를 함수 코드에 별도 로직을 구현하지 않고도 선언적으로 구성할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 함수 코드 내부에 직접 구현해야 해서 요구사항에 반하며, 함수 자체의 크래시/타임아웃은 코드 내부 try-catch로 포착할 수 없습니다.
- C: Lambda가 기본 제공하는 destinations 기능이 있음에도 EventBridge로 우회하는 것은 불필요하게 복잡합니다.
- D: 단순 성공/실패 분기만 필요한 경우 Step Functions 전체 도입은 과도합니다.

> 💡 **시험 꿀팁**: Lambda **비동기 호출의 성공/실패 결과에 따라 자동으로 다른 대상(SQS 등)으로 라우팅**하려면 함수 코드 수정 없이 **Lambda 대상(destinations)** 기능이 표준 정답입니다.

## QUESTION 373

**문제**: 금융 회사가 Direct Connect 이중화 구성(두 개의 개별 연결)을 갖추고 있으며, 실제 장애가 발생하기 전에 **정기적으로 백업 경로로의 페일오버가 실제로 정상 작동하는지** 프로덕션 트래픽에 미치는 영향 없이 테스트하고 싶다. 물리적으로 회선을 강제로 차단하는 위험한 수동 테스트 대신 사용할 수 있는 기능은?

- B. **Direct Connect 콘솔의 연결 테스트(Direct Connect failover test) 기능을 사용해, 특정 가상 인터페이스의 BGP 세션을 소프트웨어적으로 일정 시간 동안 다운시켜 트래픽이 실제로 대체 경로로 전환되는지 안전하게 검증.**

- D: 모니터링은 사후 감지 수단이며 사전 능동적 검증 기능이 아닙니다.

> 💡 **시험 꿀팁**: Direct Connect의 **페일오버가 실제로 작동하는지 안전하게 사전 검증**하려면 물리적 개입 없이 **Direct Connect 연결 테스트(failover test)** 기능이 표준 정답입니다.

**해설**
**Auto Scaling 그룹의 인스턴스 갱신(Instance Refresh)** 기능은 새로운 시작 템플릿 버전(패치된 새 AMI 포함)을 대상으로, **최소 정상 비율**(교체 중에도 유지할 최소 서비스 용량)과 **워밍업 시간**을 설정해 인스턴스를 점진적으로(배치 단위로) 교체합니다. CloudWatch 알람을 롤백 트리거로 연결하면, 교체 도중 지표가 임계값을 벗어날 경우 **자동으로 갱신을 중단**해 안전하게 롤아웃할 수 있어, 이 문제의 모든 요구(점진적 교체, 서비스 중단 없음, 자동 롤백)를 충족하는 표준 기능입니다.

**왜 다른 보기는 오답인가**
- A: 시작 템플릿만 업데이트하면 기존 실행 중인 인스턴스는 교체되지 않은 채 남아 있습니다.
- C: 전체 동시 종료는 서비스 중단을 유발해 요구사항에 반합니다.
- D: 별도 그룹 병행 운영은 가능하지만 Instance Refresh보다 수동 관리 부담이 큽니다.

> 💡 **시험 꿀팁**: Auto Scaling 그룹의 인스턴스를 **점진적으로, 서비스 중단 없이, 문제 시 자동 롤백되도록** 새 AMI로 교체하려면 **인스턴스 갱신(Instance Refresh)**(최소 정상 비율 + 알람 기반 롤백)이 표준 정답입니다.

**문제**: 글로벌 전자상거래 회사가 DynamoDB 글로벌 테이블로 여러 리전에서 **동시에 쓰기(active-active)**가 가능한 장바구니 서비스를 운영 중이다. 드물게 같은 상품 항목이 서로 다른 리전에서 거의 동시에 수정될 때 어떤 값이 최종적으로 반영되는지 이해하고 싶다. DynamoDB 글로벌 테이블의 충돌 해결 방식은?

- B. **DynamoDB 글로벌 테이블은 "마지막 쓰기 우선(last writer wins)" 방식을 사용하며, 각 리전의 쓰기에 내부 타임스탬프를 부여해 여러 리전에서 동시에 발생한 쓰기 중 가장 최근 타임스탬프를 가진 쓰기가 최종적으로 모든 리전에 반영.**

**해설**
**DynamoDB 글로벌 테이블**은 여러 리전에서의 동시 쓰기 충돌을 **"마지막 쓰기 우선(last writer wins)"** 방식으로 자동 해결합니다. 각 리전에서 발생한 쓰기에는 내부적으로 타임스탬프가 부여되며, 동일한 항목에 대해 여러 리전에서 거의 동시에 쓰기가 발생하면 **가장 최근 타임스탬프를 가진 쓰기가 승리**해 최종적으로 모든 리전에 결과적 일관성(eventual consistency)으로 수렴합니다. 이는 애플리케이션 개입 없이 자동으로 이루어지는 내장 충돌 해결 메커니즘입니다.

- C: 값을 병합하는 기능은 제공되지 않으며, 하나의 값만 최종 채택됩니다.
- D: 애플리케이션에 오류를 반환하지 않고 내부적으로 자동 해결됩니다.

> 💡 **시험 꿀팁**: DynamoDB 글로벌 테이블의 **다중 리전 동시 쓰기 충돌**은 애플리케이션 개입 없이 **마지막 쓰기 우선(last writer wins, 타임스탬프 기준)** 방식으로 자동 해결된다는 점을 기억하세요.

- B. **AWS CloudHSM을 사용해, 고객 전용의 단일 테넌트 FIPS 140-2 Level 3 검증 하드웨어 보안 모듈 클러스터를 프로비저닝하고, 키 생성/저장/사용에 대한 완전한 관리 통제권을 직접 보유.**
- C. 온프레미스 HSM을 그대로 유지하고 AWS 워크로드는 별도로 운영(하이브리드 이원화는 관리 복잡도를 늘리며, 문제는 AWS 내에서 이 요구를 충족하는 방법을 묻고 있고 CloudHSM이 이를 직접 해결).
- D. S3 서버 측 암호화(SSE-S3)만 사용(SSE-S3는 AWS 관리형 키를 사용하며 전용 HSM에 대한 고객의 직접적인 통제권이나 FIPS 140-2 Level 3 전용 하드웨어 요구사항을 충족하지 못함).

**정답: B**

**해설**
**AWS CloudHSM**은 **FIPS 140-2 Level 3** 검증을 받은 전용(single-tenant) 하드웨어 보안 모듈(HSM) 클러스터를 고객이 직접 프로비저닝하고 완전히 통제할 수 있게 해주는 서비스입니다. 다른 고객과 하드웨어를 공유하지 않으며, 키 생성부터 저장, 사용까지 고객이 직접 관리하는 전용 하드웨어 기반 키 관리가 필요한 PCI DSS 같은 엄격한 규제 요구사항에 적합합니다.

**왜 다른 보기는 오답인가**
- A: AWS KMS의 기본 HSM은 강력한 보안을 제공하지만 멀티 테넌트 방식이며, 이 문제가 요구하는 "전용 하드웨어에 대한 완전한 통제권"이라는 엄격한 요구에는 CloudHSM이 더 적합합니다.
- C: 온프레미스 HSM 유지는 문제의 범위(AWS 내에서의 해결)를 벗어나며 불필요하게 복잡합니다.
- D: SSE-S3는 AWS 관리형 키를 사용해 고객의 직접적인 하드웨어 통제권을 제공하지 않습니다.

> 💡 **시험 꿀팁**: **FIPS 140-2 Level 3 검증 전용(single-tenant) HSM에 대한 완전한 관리 통제권**이 필요한 엄격한 규제 요구사항에는 **AWS CloudHSM**이 표준 정답입니다.

## QUESTION 380

**문제**: 아키텍트가 새로 설계한 애플리케이션 아키텍처가 회사가 정한 RTO(4시간) 및 RPO(1시간) 목표를 실제로 만족하는지 **정량적으로 평가**하고 싶다. 단순히 아키텍처 다이어그램을 검토하는 것이 아니라, 실제 AWS 리소스 구성을 분석해 잠재적 취약점(단일 장애 지점 등)을 식별하고 목표 대비 실제 달성 가능한 RTO/RPO를 추정하며 개선 권장 사항을 받고 싶다. 솔루션은?

**보기**
- A. Well-Architected Tool로 신뢰성 기둥에 대한 설문에 수동으로 답변(Well-Architected Tool은 정성적인 설문 기반 셀프 평가 방식이며, 실제 리소스 구성을 분석해 정량적인 RTO/RPO 달성 가능성을 추정하는 전용 기능은 아님).
- B. **AWS Resilience Hub에 애플리케이션(관련 리소스 목록)을 정의하고 RTO/RPO 목표를 설정한 뒤 복원력 평가(assessment)를 실행해, 실제 리소스 구성 기반으로 목표 달성 가능 여부를 분석하고 단일 장애 지점 등 취약점과 구체적인 개선 권장 사항을 받음.**
- C. AWS Trusted Advisor의 내결함성 카테고리 검사 결과만 확인(Trusted Advisor는 일반적인 모범 사례 검사를 제공하지만, 특정 애플리케이션에 대해 사용자가 설정한 RTO/RPO 목표 대비 정량적으로 평가하는 전용 기능은 아님).
- D. 애플리케이션을 실제로 여러 번 장애 상황에 노출시켜(프로덕션에서 무작위 테스트) 경험적으로 RTO/RPO를 측정(프로덕션에 반복적으로 실제 장애를 일으키는 것은 매우 위험하며, 사전 정량 평가 없이 바로 실제 장애 테스트부터 시작하는 것은 순서가 바뀐 접근).

**정답: B**

**해설**
**AWS Resilience Hub**는 애플리케이션을 구성하는 AWS 리소스를 정의하고 원하는 **RTO/RPO 목표**를 설정하면, 실제 리소스 구성(Multi-AZ 여부, 백업 설정, 아키텍처 패턴 등)을 분석해 **목표를 실제로 달성할 수 있는지 정량적으로 평가**합니다. 단일 장애 지점 같은 복원력 취약점을 식별하고, 목표 달성을 위한 구체적인 개선 권장 사항(예: "이 RDS를 Multi-AZ로 전환하세요")을 제공하는, 복원력 평가에 특화된 서비스입니다.

**왜 다른 보기는 오답인가**
- A: Well-Architected Tool은 정성적 설문 기반 셀프 평가이며, 실제 리소스 구성 분석 기반의 정량적 RTO/RPO 평가 기능은 Resilience Hub가 제공합니다.
- C: Trusted Advisor는 일반적인 모범 사례 점검이며 애플리케이션별 RTO/RPO 목표 대비 정량 평가 전용 기능이 아닙니다.
- D: 프로덕션에서의 반복적 실제 장애 테스트는 매우 위험하며, 사전 평가 없이 바로 실행하는 것은 순서가 잘못되었습니다(Resilience Hub 평가 이후 FIS 같은 도구로 검증하는 것이 올바른 순서).

> 💡 **시험 꿀팁**: 애플리케이션이 목표 **RTO/RPO를 실제로 달성할 수 있는지 리소스 구성 기반으로 정량 평가**하고 개선 권장 사항을 받으려면 **AWS Resilience Hub**가 표준 정답입니다.
