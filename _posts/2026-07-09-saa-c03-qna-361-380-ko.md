## QUESTION 361

**문제**: 한 회사가 자주 접근하지 않는 로그 데이터를 S3에 대량으로 저장하고 있다. 데이터는 생성 후 30일 동안만 가끔 조회되고, 이후에는 규정 준수 목적으로 7년간 보관만 하면 된다. 운영 부담과 비용을 최소화하는 솔루션은 무엇인가?

**보기**
- A. **S3 수명 주기 정책을 구성하여 객체 생성 30일 후 S3 Glacier Deep Archive로 전환한다.**
- B. 객체를 처음부터 S3 Glacier Deep Archive에 저장하고 필요 시 신속 검색 옵션으로 조회한다(30일간의 잦은 조회 요구에는 조회 비용과 지연이 커서 부적합).
- C. 매일 배치 작업으로 30일 지난 객체를 찾아 수동으로 다른 버킷에 복사한다(직접 스크립트를 운영해야 해 운영 부담이 큼).
- D. 모든 데이터를 S3 Standard에 7년간 그대로 보관한다(저장 비용이 불필요하게 높아짐).

**정답: A**

**해설**
**S3 수명 주기 정책(Lifecycle Policy)**은 객체의 생성 시점을 기준으로 스토리지 클래스 전환을 자동화합니다. 30일간은 S3 Standard에서 빠르게 조회하고, 그 이후 자동으로 **S3 Glacier Deep Archive**로 전환하면 장기 규정 준수 보관 비용을 최소화하면서도 별도의 운영 스크립트 없이 완전관리형으로 처리할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: Glacier Deep Archive는 검색 시간이 길고 신속 검색 비용이 비싸, 초기 30일의 잦은 조회 요구와 맞지 않습니다.
- C: 수동 스크립트 운영은 관리 부담을 늘리며 S3가 기본 제공하는 자동화 기능을 활용하지 못합니다.
- D: S3 Standard는 자주 조회되지 않는 장기 보관 데이터에 비용 효율적이지 않습니다.

> 💡 **시험 꿀팁**: "일정 기간 후 접근 빈도가 급격히 줄고 장기 보관만 필요"하다는 조건이 나오면 **S3 수명 주기 정책 + Glacier Deep Archive**가 표준 정답입니다.

## QUESTION 362

**문제**: 한 회사가 두 개의 VPC(VPC A, VPC B)를 운영하며, 각 VPC 내 여러 서브넷의 EC2 인스턴스들이 서로 통신해야 한다. 또한 향후 수십 개의 VPC가 추가로 연결될 예정이며, 중앙에서 라우팅을 관리하고 싶다. 확장성을 고려한 최적의 솔루션은 무엇인가?

**보기**
- A. 모든 VPC 쌍마다 개별적으로 VPC Peering 연결을 생성한다(VPC 수가 늘어날수록 연결 수가 기하급수적으로 증가해 관리가 어려움).
- B. **AWS Transit Gateway를 생성하고 모든 VPC를 Transit Gateway에 연결하여 중앙에서 라우팅을 관리한다.**
- C. 각 VPC에 NAT 게이트웨이를 배치하고 인터넷을 경유해 통신하도록 구성한다(불필요하게 인터넷을 경유하며 보안과 비용 측면에서 비효율적).
- D. VPN Gateway를 통해 모든 VPC를 온프레미스 데이터센터에 연결한 뒤 온프레미스를 경유해 통신하게 한다(불필요한 홉이 추가되고 온프레미스 인프라에 대한 의존성이 커짐).

**정답: B**

**해설**
**AWS Transit Gateway**는 다수의 VPC와 온프레미스 네트워크를 허브 앤 스포크 구조로 연결하는 중앙 라우팅 허브입니다. VPC가 수십 개로 늘어나도 각 VPC는 Transit Gateway 하나에만 연결하면 되므로, VPC Peering처럼 연결 수가 기하급수적으로 늘지 않고 중앙에서 라우팅 테이블을 관리할 수 있어 확장성이 뛰어납니다.

**왜 다른 보기는 오답인가**
- A: VPC Peering은 VPC 수가 n개일 때 최대 n(n-1)/2개의 연결이 필요해, 수십 개로 확장 시 관리가 매우 복잡해집니다.
- C: 인터넷을 경유하는 통신은 지연과 보안 노출을 늘리며, VPC 간 사설 통신 요구에 맞지 않습니다.
- D: 온프레미스를 경유하는 통신은 불필요한 홉과 대역폭 제약을 추가합니다.

> 💡 **시험 꿀팁**: "여러 VPC를 확장 가능하게 중앙에서 연결"해야 한다는 조건이 나오면 **Transit Gateway**가 표준 정답입니다.

## QUESTION 363

**문제**: 한 회사가 운영 중인 RDS MySQL 데이터베이스에서 읽기 트래픽이 급증하여 데이터베이스 성능이 저하되고 있다. 쓰기 성능에는 영향을 주지 않으면서 읽기 처리량을 확장하려면 어떤 솔루션이 적합한가?

**보기**
- A. RDS 인스턴스를 Multi-AZ로 전환한다(Multi-AZ는 고가용성을 위한 대기 인스턴스이며 읽기 트래픽 분산에는 사용되지 않음).
- B. 더 큰 인스턴스 클래스로 수직 확장한다(비용이 크게 증가하고 트래픽 급증에 유연하게 대응하기 어려움).
- C. **RDS 읽기 전용 복제본(Read Replica)을 여러 개 생성하고 애플리케이션의 읽기 쿼리를 복제본으로 분산시킨다.**
- D. 데이터베이스 앞에 ElastiCache를 두지 않고 애플리케이션 서버에 로컬 캐시를 구현한다(로컬 캐시는 인스턴스마다 별도로 존재해 일관성 문제가 발생하고 확장성이 떨어짐).

**정답: C**

**해설**
**RDS Read Replica**는 원본 데이터베이스의 읽기 전용 복제본을 생성해 읽기 트래픽을 여러 인스턴스로 분산시킵니다. 쓰기는 항상 원본(primary)에서만 처리되므로 쓰기 성능에는 영향을 주지 않으면서, 읽기 위주의 부하를 수평으로 확장할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Multi-AZ의 대기 인스턴스는 장애 조치(failover) 전용이며 일반적으로 읽기 트래픽을 처리하지 않습니다.
- B: 수직 확장은 단일 인스턴스의 한계를 근본적으로 해결하지 못하고 비용 대비 효율이 낮습니다.
- D: 로컬 캐시는 인스턴스별로 분산되어 있어 캐시 일관성을 보장하기 어렵고 관리가 복잡해집니다.

> 💡 **시험 꿀팁**: "읽기 트래픽만 증가, 쓰기 성능은 유지"라는 조건이 나오면 **RDS Read Replica**가 표준 정답입니다.

## QUESTION 364

**문제**: 한 회사가 EC2 기반 웹 애플리케이션을 운영 중이며, 트래픽이 하루 중 특정 시간대에 예측 가능하게 급증한다. 이 회사는 트래픽 패턴에 따라 자동으로 인스턴스 수를 조정하면서 목표 CPU 사용률을 일정하게 유지하고 싶다. 가장 적합한 솔루션은 무엇인가?

**보기**
- A. 수동으로 트래픽 급증 시간대에 맞춰 인스턴스를 추가/제거하는 운영 스크립트를 작성한다(수동 개입이 필요해 운영 부담이 크고 예측 오차에 취약함).
- B. 고정된 개수의 대형 인스턴스를 항상 실행해 최대 트래픽에 대비한다(평상시 리소스 낭비로 비용이 크게 증가함).
- C. Auto Scaling 그룹에 특정 시간에만 작동하는 예약 조정(Scheduled Scaling)만 사용한다(예측 가능한 패턴에는 도움이 되지만 예상치 못한 변동에는 대응하지 못함).
- D. **Auto Scaling 그룹에 목표 추적 조정 정책(Target Tracking Scaling Policy)을 구성하여 평균 CPU 사용률을 목표 값으로 유지하도록 한다.**

**정답: D**

**해설**
**목표 추적 조정 정책(Target Tracking Scaling Policy)**은 지정한 지표(예: 평균 CPU 사용률)가 목표 값을 유지하도록 Auto Scaling 그룹이 자동으로 인스턴스 수를 늘리거나 줄입니다. 예측 가능한 패턴뿐 아니라 예상치 못한 트래픽 변화에도 실시간으로 대응할 수 있어 운영 부담 없이 일정한 성능을 유지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 수동 스크립트는 운영 부담이 크고 실시간 변동에 정확히 대응하기 어렵습니다.
- B: 고정된 대형 인스턴스 운영은 평상시 과도한 비용을 발생시킵니다.
- C: 예약 조정만으로는 예측하지 못한 트래픽 스파이크에 대응할 수 없습니다.

> 💡 **시험 꿀팁**: "목표 지표를 일정하게 유지하며 자동 확장/축소"라는 조건이 나오면 **목표 추적 조정 정책**이 표준 정답입니다.

## QUESTION 365

**문제**: 한 스타트업이 이벤트 기반 아키텍처로 이미지 업로드 시 자동으로 썸네일을 생성하는 기능을 구축하려 한다. 서버를 직접 프로비저닝하거나 관리하지 않고, 업로드 이벤트가 발생할 때만 코드를 실행하고 싶다. 가장 적합한 조합은 무엇인가?

**보기**
- A. **S3에 이미지가 업로드되면 이벤트 알림을 트리거로 하여 AWS Lambda 함수가 실행되어 썸네일을 생성하고 다시 S3에 저장한다.**
- B. EC2 Auto Scaling 그룹을 구성하여 이미지 업로드 요청이 있을 때마다 인스턴스를 시작한다(인스턴스 시작에 시간이 걸리고 상시 관리가 필요해 서버리스 요구에 맞지 않음).
- C. ECS 클러스터에서 상시 실행되는 컨테이너가 S3를 주기적으로 폴링하여 새 이미지를 확인한다(폴링 방식은 비효율적이며 상시 실행 중인 컨테이너를 직접 관리해야 함).
- D. API Gateway를 통해 사용자가 직접 썸네일 생성 API를 호출하도록 요구한다(업로드 이벤트 기반 자동화 요구에 맞지 않고 클라이언트 구현 부담이 커짐).

**정답: A**

**해설**
**S3 이벤트 알림 + Lambda**는 대표적인 서버리스 이벤트 기반 아키텍처입니다. S3에 객체가 업로드되는 이벤트를 트리거로 Lambda 함수가 자동 실행되어 썸네일 생성 같은 작업을 처리하며, 서버 프로비저닝이나 상시 실행 중인 인프라 없이 사용한 만큼만 비용을 지불합니다.

**왜 다른 보기는 오답인가**
- B: EC2 인스턴스는 시작 시간이 걸리고 상시 관리가 필요해 완전한 서버리스 요구에 맞지 않습니다.
- C: 폴링 방식은 실시간성이 떨어지고 상시 실행 컨테이너에 대한 관리 부담이 발생합니다.
- D: 클라이언트가 직접 호출하는 방식은 업로드 시점에 자동으로 반응하는 이벤트 기반 요구를 충족하지 못합니다.

> 💡 **시험 꿀팁**: "S3 업로드 시 자동으로 실행되는 서버 없는 처리"라는 조건이 나오면 **S3 이벤트 알림 + Lambda**가 표준 정답입니다.

## QUESTION 366

**문제**: 한 회사가 정적 웹사이트를 S3에서 호스팅하고 있으며, 전 세계 사용자에게 낮은 지연 시간으로 콘텐츠를 제공하고 싶다. 동시에 S3 버킷은 퍼블릭 액세스를 완전히 차단한 상태로 유지해야 한다. 어떤 솔루션이 이 요구 사항을 충족하는가?

**보기**
- A. S3 버킷 정책을 수정해 모든 사용자에게 퍼블릭 읽기 권한을 부여한다(퍼블릭 액세스 차단 요구에 정면으로 위배됨).
- B. **CloudFront 배포를 생성하고 오리진 액세스 제어(OAC)를 구성하여 CloudFront만 S3 버킷에 접근할 수 있도록 하고, 버킷의 퍼블릭 액세스는 차단한다.**
- C. 각 대륙의 리전에 S3 버킷을 복제하고 Route 53 지연 시간 기반 라우팅으로 가장 가까운 버킷으로 연결한다(버킷을 퍼블릭으로 열어야 하며 복제 관리 부담도 커짐).
- D. EC2 인스턴스를 여러 리전에 배치해 S3 콘텐츠를 프록시하도록 구성한다(불필요한 인프라와 운영 부담이 추가됨).

**정답: B**

**해설**
**CloudFront + 오리진 액세스 제어(OAC)**를 사용하면 CloudFront 엣지 로케이션을 통해 전 세계에 낮은 지연으로 콘텐츠를 배포하면서도, S3 버킷은 CloudFront의 요청만 허용하도록 제한해 퍼블릭 액세스를 완전히 차단할 수 있습니다. 이는 정적 웹사이트 호스팅의 표준 보안 아키텍처입니다.

**왜 다른 보기는 오답인가**
- A: 퍼블릭 읽기 권한 부여는 버킷을 완전히 차단해야 한다는 요구와 정반대입니다.
- C: 버킷을 리전마다 복제하려면 결국 퍼블릭 액세스가 필요해지고, 복제 동기화 관리 부담이 커집니다.
- D: EC2 프록시는 CloudFront가 기본 제공하는 캐싱과 엣지 배포 이점을 활용하지 못하고 운영 부담만 늘립니다.

> 💡 **시험 꿀팁**: "S3는 완전히 비공개로 유지하면서 전 세계에 콘텐츠 배포"라는 조건이 나오면 **CloudFront + OAC**가 표준 정답입니다.

## QUESTION 367

**문제**: 한 회사의 A 계정에 있는 Lambda 함수가 B 계정의 S3 버킷에 접근해야 한다. 장기 액세스 키를 발급하지 않고 최소 권한 원칙을 지키면서 이를 구현하려면 어떤 방법이 적합한가?

**보기**
- A. B 계정에서 IAM 사용자를 생성하고 액세스 키를 발급해 A 계정의 Lambda 환경 변수에 하드코딩한다(장기 자격 증명을 저장/관리해야 해 보안 위험이 크고 요구에 위배됨).
- B. A 계정의 Lambda 실행 역할에 B 계정 리소스에 대한 전체 관리자 권한을 직접 부여한다(최소 권한 원칙에 위배되고 과도한 권한 부여).

- B: 전체 관리자 권한 부여는 필요 이상의 권한으로 최소 권한 원칙을 위반합니다.
- D: 버킷을 퍼블릭으로 여는 것은 인증되지 않은 누구나 접근 가능하게 만들어 보안상 허용될 수 없습니다.

> 💡 **시험 꿀팁**: "다른 계정의 리소스에 최소 권한으로, 장기 키 없이 접근"이라는 조건이 나오면 **교차 계정 IAM 역할(AssumeRole)**이 표준 정답입니다.

## QUESTION 370

**문제**: 한 회사의 주문 처리 시스템에서, 주문 서비스가 결제 서비스와 배송 서비스에 동시에 이벤트를 전달해야 하며 각 서비스는 독립적으로 이벤트를 소비해야 한다. 서비스 간 결합도를 낮추고 확장 가능한 아키텍처는 무엇인가?

**보기**
- A. 주문 서비스가 결제 서비스와 배송 서비스의 API를 직접 순차 호출한다(서비스 간 강한 결합이 발생하고 하나의 서비스 장애가 전체 흐름에 영향을 줌).
- B. **주문 서비스가 SNS 주제(Topic)에 이벤트를 게시하고, 결제 서비스와 배송 서비스는 각각 SQS 대기열을 구독하여 독립적으로 이벤트를 소비한다.**
- C. 모든 서비스가 하나의 공유 데이터베이스 테이블을 폴링하여 새 주문을 확인한다(폴링 방식은 지연이 크고 데이터베이스에 불필요한 부하를 유발함).
- D. 주문 서비스가 결제 서비스에만 이벤트를 보내고, 결제 서비스가 처리 후 배송 서비스를 호출하는 체인 방식을 사용한다(서비스 간 순차적 의존성이 생겨 결합도가 높아지고 장애 전파 위험이 커짐).

**정답: B**

**해설**
**SNS 팬아웃(Fan-out) 패턴**은 하나의 SNS 주제에 이벤트를 게시하면 여러 구독자(SQS 대기열)가 동시에 독립적으로 메시지를 받아 처리할 수 있게 합니다. 각 서비스가 자신의 대기열에서 메시지를 소비하므로 서비스 간 결합도가 낮아지고, 하나의 서비스 처리 지연이 다른 서비스에 영향을 주지 않아 확장성이 높습니다.

**왜 다른 보기는 오답인가**
- A: 직접 순차 호출은 서비스 간 강한 결합을 만들고 장애 전파 위험이 큽니다.
- C: 폴링 방식은 실시간성이 떨어지고 데이터베이스에 불필요한 부하를 줍니다.
- D: 체인 방식의 순차 호출은 서비스 간 의존성을 높여 하나가 실패하면 전체 흐름이 지연되거나 실패합니다.

> 💡 **시험 꿀팁**: "하나의 이벤트를 여러 서비스가 독립적으로 소비"해야 한다는 조건이 나오면 **SNS + SQS 팬아웃 패턴**이 표준 정답입니다.

## QUESTION 371

**문제**: 한 회사가 여러 EC2 인스턴스에서 공유해야 하는 파일 시스템이 필요하며, 리눅스 기반 인스턴스들이 동시에 읽고 쓸 수 있어야 하고 트래픽에 따라 자동으로 용량이 확장/축소되어야 한다. 가장 적합한 스토리지는 무엇인가?

- B. S3 버킷을 각 인스턴스에 마운트하여 파일 시스템처럼 사용한다(S3는 객체 스토리지로 파일 시스템 프로토콜을 기본 지원하지 않아 일반적인 공유 파일 시스템 용도에 적합하지 않음).
- C. **Amazon EFS를 생성하고 여러 가용 영역의 EC2 인스턴스에 마운트하여 공유 파일 시스템으로 사용한다.**

**정답: C**

**해설**
**Amazon EFS(Elastic File System)**는 여러 가용 영역의 다수 EC2 인스턴스가 동시에 마운트하여 읽고 쓸 수 있는 완전관리형 NFS 파일 시스템입니다. 저장하는 데이터양에 따라 용량이 자동으로 확장/축소되며 별도의 프로비저닝 없이 다중 인스턴스 동시 접근을 지원합니다.

**왜 다른 보기는 오답인가**
- A: EBS는 기본적으로 한 번에 하나의 인스턴스에만 연결되는 블록 스토리지입니다(멀티 어태치는 제한적인 특수 사례).
- B: S3는 객체 스토리지로, 파일 시스템 마운트 및 POSIX 호환 접근을 기본 지원하지 않습니다.
- D: 직접 구축한 NFS 서버는 단일 장애점이 되고 별도의 운영 부담이 큽니다.

> 💡 **시험 꿀팁**: "여러 EC2 인스턴스가 동시에 읽고 쓰는 공유 파일 시스템 + 자동 확장"이라는 조건이 나오면 **Amazon EFS**가 표준 정답입니다.

## QUESTION 372

**문제**: 한 회사가 재해 복구(DR) 전략을 수립하려 한다. 목표는 평소에는 최소한의 비용만 지출하되, 재해 발생 시 수 분 내에 서비스를 복구할 수 있어야 한다는 것이다. 가장 적합한 DR 전략은 무엇인가?

**정답: C**

**해설**

**왜 다른 보기는 오답인가**
- A: 백업/복원은 비용이 가장 낮지만 복구 시간이 가장 길어 수 분 내 복구 요구에 맞지 않습니다.
- B: 액티브-액티브는 복구 시간이 거의 없지만 평소 비용이 가장 높습니다.
- D: DR 전략 부재는 재해 시 복구 시간을 예측할 수 없고 데이터 손실 위험이 큽니다.

> 💡 **시험 꿀팁**: "평소 낮은 비용 + 재해 시 수 분 내 복구"라는 균형 잡힌 조건이 나오면 **파일럿 라이트** 전략이 표준 정답입니다.

**문제**: 한 회사가 API Gateway로 구성한 REST API 뒤에서 여러 마이크로서비스를 운영하고 있다. 특정 클라이언트가 API를 과도하게 호출해 다른 클라이언트의 서비스 품질에 영향을 주는 것을 방지하고 싶다. 가장 적합한 방법은 무엇인가?

**보기**
- A. 모든 클라이언트에 대해 API Gateway 자체를 완전히 비활성화하고 새로운 API를 구축한다(과도한 조치이며 문제 해결과 무관함).
- B. **API Gateway에서 사용량 계획(Usage Plan)과 API 키를 구성하여 클라이언트별로 요청 제한(Throttling)과 할당량(Quota)을 설정한다.**
- C. 모든 마이크로서비스의 EC2 인스턴스 수를 무제한으로 늘려 트래픽을 흡수한다(비용이 급증하고 근본적인 클라이언트별 제어가 되지 않음).
- D. 클라이언트의 요청을 코드 레벨에서 IP 주소로 판별해 각 마이크로서비스에 개별적으로 제한 로직을 구현한다(마이크로서비스마다 중복 구현해야 해 유지보수 부담이 크고 일관성이 떨어짐).

**정답: B**

**해설**
**API Gateway의 사용량 계획(Usage Plan)과 API 키**를 사용하면 클라이언트(API 키)별로 초당 요청 수 제한(Throttling)과 기간별 호출 할당량(Quota)을 설정할 수 있습니다. 이를 통해 특정 클라이언트의 과도한 호출이 다른 클라이언트에게 영향을 주지 않도록 API Gateway 계층에서 중앙집중적으로 제어할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: API Gateway를 비활성화하는 것은 문제 해결과 무관하며 서비스 자체를 중단시킵니다.
- C: 인스턴스를 무제한으로 늘리는 것은 비용만 증가시킬 뿐 특정 클라이언트의 과도한 호출 자체를 제어하지 못합니다.
- D: 각 마이크로서비스에 개별 구현하는 것은 코드 중복과 유지보수 부담을 크게 늘립니다.

> 💡 **시험 꿀팁**: "클라이언트별로 API 호출을 제한"해야 한다는 조건이 나오면 **API Gateway 사용량 계획(Usage Plan) + API 키**가 표준 정답입니다.

## QUESTION 380

**문제**: 한 회사가 EC2에서 실행 중인 레거시 애플리케이션을 컨테이너로 전환하려 하지만, 팀에 Kubernetes 운영 경험이 없고 AWS가 관리하는 오케스트레이션 플랫폼을 원한다. 또한 향후 온프레미스 환경에도 동일한 오케스트레이션 도구를 일관되게 사용하고 싶다. 가장 적합한 선택은 무엇인가?

**보기**
- A. 자체적으로 Kubernetes 클러스터를 EC2 위에 처음부터 구축하고 운영한다(Kubernetes 운영 경험이 없는 팀에 부담이 크고 관리형 서비스의 이점을 활용하지 못함).
- B. ECS를 사용하되 향후 온프레미스 확장 계획은 고려하지 않는다(ECS는 AWS 전용 오케스트레이터로 온프레미스 일관성 요구를 충족하지 못함).
- C. **Amazon EKS(Elastic Kubernetes Service)를 사용하여 관리형 Kubernetes 컨트롤 플레인을 활용하고, 필요 시 EKS Anywhere 또는 유사 도구로 온프레미스에서도 동일한 Kubernetes 기반 오케스트레이션을 사용한다.**
- D. 컨테이너화를 포기하고 EC2에서 레거시 애플리케이션을 그대로 유지한다(컨테이너 전환이라는 목표 자체를 달성하지 못함).

**정답: C**

**해설**
**Amazon EKS**는 AWS가 관리하는 Kubernetes 컨트롤 플레인을 제공하여 팀이 Kubernetes의 표준 API와 생태계를 그대로 사용하면서도 컨트롤 플레인 운영 부담을 AWS에 맡길 수 있습니다. Kubernetes는 오픈소스 표준이므로 온프레미스나 다른 환경에서도 동일한 도구와 워크플로를 일관되게 사용할 수 있어, 향후 하이브리드 확장 요구에도 적합합니다.

**왜 다른 보기는 오답인가**
- A: 자체 구축 Kubernetes는 컨트롤 플레인까지 팀이 직접 운영해야 해, 경험이 없는 팀에는 부담이 매우 큽니다.
- B: ECS는 AWS 전용 오케스트레이터로 온프레미스에서 동일하게 사용할 수 없습니다.
- D: 컨테이너 전환을 포기하는 것은 문제의 핵심 목표를 달성하지 못합니다.

> 💡 **시험 꿀팁**: "관리형 Kubernetes + 온프레미스와 일관된 오케스트레이션"이라는 조건이 나오면 **Amazon EKS**가 표준 정답입니다.
