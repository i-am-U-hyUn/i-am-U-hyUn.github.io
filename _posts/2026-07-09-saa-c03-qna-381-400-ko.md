## QUESTION 381

**문제**: 한 스타트업이 새로운 추천 알고리즘을 적용한 애플리케이션 v2를 출시하려고 합니다. 전체 트래픽을 한 번에 전환하는 대신, 사용자 트래픽의 10%만 새 버전으로 보내 성능과 오류율을 검증한 뒤 점진적으로 비율을 늘리고 싶어합니다. 별도의 로드밸런서 없이 DNS 계층에서 트래픽 비율을 손쉽게 제어할 수 있는 방법을 찾고 있습니다.

**보기**
- A. **Amazon Route 53의 가중치 기반 라우팅 정책(Weighted Routing Policy)을 사용해 v1과 v2 레코드에 90:10 비율의 가중치를 부여한다.**
- B. Route 53의 지연 시간 기반 라우팅 정책을 사용해 지연 시간이 낮은 리전으로만 트래픽을 보낸다. (지연 시간 기준으로 리전을 선택할 뿐 특정 비율로 트래픽을 분산하도록 설계된 기능이 아님)
- C. Route 53의 장애 조치(Failover) 라우팅 정책을 구성해 v1 장애 시에만 v2로 전환되도록 한다. (장애 발생 시에만 전환되며 상시 비율 분산에는 적합하지 않음)
- D. Application Load Balancer를 새로 생성하고 리스너 규칙으로 v1과 v2 대상 그룹에 요청을 반씩 분배한다. (요청 비율을 세밀하게 조정하기 어렵고 DNS 계층이 아닌 로드밸런서 계층의 솔루션이라 요구사항인 "DNS 계층 제어"에 부합하지 않음)

**정답: A**

**해설**: **Route 53의 가중치 기반 라우팅 정책**은 동일한 도메인 이름에 대해 여러 리소스 레코드에 상대적인 가중치를 부여하여, 지정한 비율대로 트래픽을 분산시킬 수 있습니다. v1과 v2에 각각 90과 10의 가중치를 부여하면 약 90%와 10%의 비율로 트래픽이 분산되며, 이후 v2의 안정성이 검증되면 가중치 값만 조정해 점진적으로 트래픽 비율을 늘려나갈 수 있어 A/B 테스트나 카나리 배포에 적합합니다.

**왜 다른 보기는 오답인가**
- B: 지연 시간 기반 라우팅은 사용자에게 가장 낮은 네트워크 지연 시간을 제공하는 리전으로 트래픽을 보내는 정책으로, 버전 간 비율 분산 목적과는 무관합니다.
- C: 장애 조치 라우팅은 주 리소스에 장애가 발생했을 때 보조 리소스로 전환하는 액티브-패시브 구성에 사용되며, 상시 일정 비율로 트래픽을 나누는 용도가 아닙니다.
- D: ALB 리스너 규칙으로도 가중치 기반 분산이 가능하지만 새 로드밸런서를 추가로 생성해야 하며, 문제에서 요구한 "DNS 계층에서 손쉽게 제어"라는 조건에는 맞지 않습니다.

> 💡 **시험 꿀팁**: 특정 비율로 트래픽을 나눠 배포/테스트하고 싶다는 키워드가 나오면 Route 53 가중치 기반 라우팅을 먼저 떠올리세요.

## QUESTION 382

**문제**: 한 금융 회사는 프라이빗 서브넷에 있는 EC2 인스턴스들이 인터넷을 거치지 않고 Amazon S3 버킷에 접근해 대용량 로그 파일을 저장하도록 구성해야 합니다. 보안팀은 인터넷 게이트웨이나 NAT 게이트웨이를 통한 아웃바운드 경로를 최대한 배제하고, 데이터가 AWS 네트워크 내부에만 머물기를 원합니다. 추가 비용도 최소화하고 싶습니다.

**보기**
- A. NAT 게이트웨이를 퍼블릭 서브넷에 생성하고 프라이빗 서브넷의 라우팅 테이블에서 이를 통해 S3로 나가도록 설정한다. (트래픽이 결국 퍼블릭 인터넷 경로의 NAT 게이트웨이를 거치며 시간당 요금과 데이터 처리 요금이 추가로 발생함)
- B. **S3용 VPC 게이트웨이 엔드포인트(Gateway Endpoint)를 생성하고 프라이빗 서브넷의 라우팅 테이블에 엔드포인트로 향하는 경로를 추가한다.**
- C. VPC 피어링을 통해 S3 전용 VPC를 새로 만들고 피어링 연결로 접근한다. (S3는 VPC 리소스가 아니므로 VPC 피어링 대상이 될 수 없음)
- D. AWS Direct Connect를 구성해 온프레미스를 거치지 않고 S3에 접근하도록 한다. (Direct Connect는 온프레미스와 AWS 간의 전용 네트워크 연결 서비스로, VPC 내부에서 S3 접근 경로 문제 해결과는 무관하며 구축 비용과 기간이 큼)

**정답: B**

**해설**: **S3용 VPC 게이트웨이 엔드포인트**를 사용하면 인터넷 게이트웨이, NAT 디바이스, VPN 연결 없이도 VPC 내부에서 Amazon S3와 같은 AWS 서비스로 직접, 안정적으로 통신할 수 있습니다. 게이트웨이 엔드포인트는 라우팅 테이블에 대상 경로를 추가하는 방식으로 동작하며 별도의 시간당 요금이 없어 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- A: NAT 게이트웨이는 프라이빗 서브넷이 인터넷 상의 리소스와 통신할 때 필요하지만, S3는 AWS 관리형 서비스이므로 게이트웨이 엔드포인트로 더 저렴하고 안전하게 접근할 수 있어 NAT를 거칠 필요가 없습니다.
- C: VPC 피어링은 VPC와 VPC 간 연결에 사용되는 기능으로, S3와 같은 리전 서비스에는 적용되지 않습니다.
- D: Direct Connect는 온프레미스 데이터센터와 AWS 리전을 연결하는 전용선 서비스로, VPC 내부 라우팅 문제와는 관련이 없고 도입 비용과 시간이 큽니다.

> 💡 **시험 꿀팁**: "NAT 없이 S3/DynamoDB에 프라이빗하게 접근"이라는 문구가 나오면 VPC 게이트웨이 엔드포인트를 떠올리세요.

## QUESTION 383

**문제**: 한 글로벌 이커머스 기업이 서울 리전에서 Amazon Aurora MySQL을 운영 중이며, 리전 전체 장애에 대비해 도쿄 리전에 재해 복구(DR) 사이트를 구성하려 합니다. 복구 시점 목표(RPO)는 1초 수준으로 매우 짧아야 하며, 리전 간 복제 지연을 최소화하면서 운영 부담은 줄이고 싶습니다.

**보기**
- A. Aurora 읽기 복제본을 도쿄 리전에 생성하고 애플리케이션에서 주기적으로 mysqldump를 이용해 백업을 옮긴다. (수동 덤프 방식은 복제 지연이 크고 RPO를 1초 수준으로 맞출 수 없음)
- B. AWS DMS를 이용해 서울 리전 Aurora에서 도쿄 리전 Aurora로 지속적 복제(CDC) 작업을 구성한다. (DMS 지속적 복제는 가능하지만 별도 복제 인스턴스 운영과 모니터링이 필요해 운영 부담이 크고 Aurora 전용 복제 기능보다 지연이 큼)
- C. **Aurora Global Database를 구성하여 도쿄 리전에 보조 클러스터를 두고 전용 인프라 기반 복제를 사용한다.**
- D. 서울 리전 Aurora의 스냅샷을 매일 도쿄 리전으로 수동 복사하여 신규 클러스터를 복원한다. (하루 단위 스냅샷 복사는 RPO가 최대 24시간에 달해 요구사항을 충족하지 못함)

**정답: C**

**해설**: **Aurora Global Database**는 하나의 Aurora 클러스터를 여러 리전에 걸쳐 확장할 수 있게 해주며, 전용 인프라를 사용한 스토리지 기반 복제로 일반적으로 1초 미만의 지연 시간으로 데이터를 복제합니다. 리전 장애 시에는 보조 리전의 클러스터를 몇 분 이내에 쓰기 가능한 상태로 승격할 수 있어 낮은 RPO와 RTO가 모두 필요한 재해 복구 시나리오에 적합합니다.

**왜 다른 보기는 오답인가**
- A: 수동 덤프/복원 방식은 자동화되어 있지 않고 지연 시간이 커서 초 단위 RPO를 만족할 수 없습니다.
- B: DMS는 이기종 또는 동종 데이터베이스 마이그레이션과 복제에 유용하지만, Aurora Global Database의 전용 복제 인프라만큼 낮은 지연을 보장하지 않고 별도의 복제 인스턴스를 관리해야 합니다.
- D: 스냅샷 기반 복사는 정기적인 배치 작업으로, 실시간에 가까운 복제가 불가능해 RPO 요구사항에 크게 미달합니다.

> 💡 **시험 꿀팁**: Aurora에서 "리전 간, 초 단위 RPO, 낮은 지연"이라는 키워드가 함께 나오면 Aurora Global Database가 정답일 확률이 높습니다.

## QUESTION 384

**문제**: 한 물류 회사는 Amazon SQS 표준 큐를 통해 주문 처리 메시지를 백엔드 워커에게 전달합니다. 그런데 일부 메시지가 데이터 형식 오류로 인해 워커에서 계속 처리에 실패하고, 큐에 재삽입되기를 반복하며 정상 메시지 처리 속도를 떨어뜨리고 있습니다. 실패한 메시지만 별도로 격리해 분석할 수 있는 방법이 필요합니다.

**보기**
- A. 큐의 가시성 제한 시간(Visibility Timeout)을 늘려서 워커가 메시지를 처리할 시간을 더 확보한다. (가시성 제한 시간을 늘려도 근본적으로 처리에 실패하는 메시지 자체는 계속 큐에 남아 반복 재시도됨)
- B. 큐의 메시지 보존 기간(Retention Period)을 최대값인 14일로 늘려 메시지가 삭제되지 않도록 한다. (보존 기간을 늘려도 실패 메시지가 정상 메시지 처리를 방해하는 문제는 해결되지 않음)
- C. Amazon Kinesis Data Streams로 큐를 대체하고 샤드 단위로 실패 메시지를 구분한다. (Kinesis는 스트리밍 데이터 처리에 적합하지만 개별 메시지 재시도 실패를 자동으로 격리하는 DLQ와 같은 기능을 기본 제공하지 않으며 아키텍처 전면 교체가 필요함)
- D. **SQS 재처리 정책(Redrive Policy)을 설정하고 최대 수신 횟수(Max Receive Count)를 초과한 메시지를 데드레터 큐(DLQ)로 이동시킨다.**

**정답: D**

**해설**: **SQS 데드레터 큐(DLQ)**는 재처리 정책의 최대 수신 횟수를 초과할 때까지 정상 처리되지 못한 메시지를 자동으로 별도의 큐로 옮겨 격리하는 기능입니다. 이를 통해 문제가 있는 메시지가 원본 큐에서 반복적으로 재시도되며 정상 메시지 처리를 지연시키는 것을 방지하고, 개발팀은 DLQ에 쌓인 메시지만 따로 분석해 원인을 파악할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 가시성 제한 시간 조정은 처리 시간을 늘려줄 뿐, 데이터 자체에 오류가 있어 계속 실패하는 메시지를 근본적으로 격리하지 못합니다.
- B: 메시지 보존 기간은 메시지가 큐에서 삭제되기까지의 최대 시간일 뿐이며, 실패 메시지의 반복 재시도 문제와는 무관합니다.
- C: Kinesis Data Streams는 실시간 스트리밍 데이터 처리용 서비스로, 메시지 큐잉 모델과 다르며 요구사항에 맞는 DLQ 격리 기능을 기본으로 제공하지 않습니다.

> 💡 **시험 꿀팁**: "반복 실패하는 메시지를 격리"라는 표현이 나오면 SQS 데드레터 큐(DLQ)와 Max Receive Count 설정을 떠올리세요.

## QUESTION 385

**문제**: 한 다국적 기업이 50개의 AWS 계정과 5개의 리전에 걸쳐 동일한 보안 로깅 및 IAM 역할 구성을 담은 CloudFormation 템플릿을 배포하려고 합니다. 각 계정과 리전에 수동으로 콘솔에 접속해 스택을 개별 생성하는 방식은 시간이 오래 걸리고 실수 위험이 커서, 중앙에서 한 번에 관리하고 배포할 수 있는 방법을 원합니다.

**보기**
- A. **AWS CloudFormation StackSets를 사용해 관리 계정에서 대상 계정과 리전 목록을 지정하여 스택을 한 번에 생성·업데이트한다.**
- B. AWS Systems Manager Automation을 이용해 각 계정에 SSH로 접속한 뒤 스택을 순차적으로 생성하는 스크립트를 실행한다. (계정별로 개별 인증과 접속이 필요해 중앙 집중식 관리가 어렵고 CloudFormation 스택 생성을 위한 표준 방식이 아님)
- C. 각 계정에 동일한 템플릿 파일을 이메일로 전달하고 계정 관리자가 개별적으로 콘솔에서 배포하도록 요청한다. (수동 프로세스로 일관성을 보장하기 어렵고 규모가 커질수록 관리가 불가능해짐)
- D. AWS Organizations의 서비스 제어 정책(SCP)에 템플릿 내용을 포함시켜 배포한다. (SCP는 계정이 사용할 수 있는 최대 권한을 제어하는 정책이며 리소스를 배포하는 기능이 아님)

**정답: A**

> 💡 **시험 꿀팁**: "여러 계정과 여러 리전에 동일한 스택을 배포"라는 문구가 나오면 CloudFormation StackSets를 정답으로 고려하세요.

**문제**: 한 온라인 쇼핑몰이 Amazon CloudFront를 통해 웹 애플리케이션을 배포하고 있는데, 최근 로그에서 SQL 삽입(SQL Injection) 및 크로스 사이트 스크립팅(XSS) 시도가 다수 발견되었습니다. 보안팀은 이러한 공통적인 웹 공격 패턴을 애플리케이션 코드 수정 없이 엣지 레벨에서 필터링하고 싶어합니다.

- C: 보안 그룹은 네트워크 계층(IP, 포트)에서 동작하는 상태 저장 방화벽으로, 애플리케이션 계층의 요청 본문에 포함된 공격 패턴을 검사할 수 없습니다.
- D: Amazon Inspector는 워크로드의 알려진 취약점과 노출을 진단하는 서비스로, 실시간 웹 트래픽을 필터링하는 기능은 제공하지 않습니다.

> 💡 **시험 꿀팁**: "SQL 삽입/XSS 차단"이라는 문구는 거의 항상 AWS WAF의 관리형 규칙 그룹을 가리킵니다.

**문제**: 한 의료 데이터 관리 기업은 규제 기관으로부터 원본 데이터가 저장된 리전과 별개의 리전에도 자동으로 동기화된 사본을 보관해야 한다는 컴플라이언스 요구사항을 받았습니다. 데이터는 S3 버킷에 저장되어 있으며, 객체가 업로드될 때마다 사람이 개입하지 않고 자동으로 다른 리전에 복제되어야 합니다.

## QUESTION 389

**문제**: 한 미디어 스트리밍 회사는 Auto Scaling 그룹으로 운영되는 웹 서버들이 사용자의 로그인 세션 정보를 로컬 메모리에 저장하고 있어, 스케일 인 시 세션이 유실되거나 로드밸런서가 다른 인스턴스로 요청을 보낼 때 사용자가 다시 로그인해야 하는 문제를 겪고 있습니다. 서버를 완전히 무상태(stateless)로 만들어 어떤 인스턴스가 요청을 처리하더라도 세션이 유지되도록 개선하고자 합니다.

**보기**
- A. **Amazon ElastiCache for Redis를 도입해 세션 데이터를 인메모리 캐시에 외부화하고 모든 웹 서버가 이를 공유하도록 구성한다.**
- B. 각 웹 서버의 로컬 디스크에 세션 파일을 저장하고 인스턴스 간 rsync로 주기적으로 동기화한다. (동기화 지연이 발생하며 인스턴스가 늘어날수록 동기화 복잡도와 지연이 커져 세션 일관성을 보장하기 어려움)

- D. Amazon RDS Multi-AZ 인스턴스를 세션 저장용으로 사용해 모든 세션 읽기/쓰기를 RDS에서 처리한다. (관계형 DB는 세션과 같이 빈번하고 단순한 키-값 조회에는 지연 시간과 비용 면에서 비효율적임)

- B: 로컬 파일 동기화 방식은 실시간성이 떨어지고 인스턴스 수가 늘어날수록 관리가 복잡해져 확장성 있는 해결책이 아닙니다.
- C: 스티키 세션은 임시방편으로 특정 인스턴스에 세션을 고정시킬 뿐, 해당 인스턴스가 종료되면 세션이 그대로 유실되어 근본적인 해결책이 되지 못합니다.
- D: RDS는 관계형 데이터 저장에 적합하지만, 세션과 같이 짧은 TTL과 높은 읽기/쓰기 빈도를 가진 데이터에는 인메모리 캐시보다 지연 시간이 크고 비용 효율이 떨어집니다.

> 💡 **시험 꿀팁**: "세션 외부화로 서버를 무상태로 만들기"라는 요구사항은 ElastiCache(Redis/Memcached)를 가리키는 대표적인 신호입니다.

**문제**: 한 이커머스 플랫폼의 주문 처리 과정은 재고 확인, 결제 승인, 배송 요청, 알림 발송 등 여러 단계로 구성되어 있으며 각 단계는 서로 다른 Lambda 함수로 구현되어 있습니다. 특정 단계에서 일시적인 오류가 발생하면 자동으로 재시도하고, 각 단계의 실행 상태를 시각적으로 추적할 수 있는 오케스트레이션 방법이 필요합니다.

**보기**
- A. Amazon SNS 주제를 만들어 각 Lambda 함수가 다음 단계의 Lambda를 순서대로 트리거하도록 구독을 설정한다. (SNS는 단순 발행-구독 메시징 서비스로 재시도 정책, 상태 추적, 분기 로직과 같은 워크플로우 기능을 제공하지 않음)
- B. **AWS Step Functions로 각 단계를 상태 머신의 상태(State)로 정의하고, 재시도(Retry) 및 오류 처리(Catch) 규칙을 구성한다.**
- C. Amazon EventBridge 규칙을 여러 개 만들어 각 Lambda의 완료 이벤트가 다음 Lambda를 호출하도록 체이닝한다. (이벤트 체이닝만으로는 전체 워크플로우의 실행 상태를 한눈에 시각화하거나 세밀한 재시도/타임아웃 정책을 표준화하여 관리하기 어려움)
- D. 하나의 대형 Lambda 함수 안에 모든 단계 로직을 순차적으로 작성해 하나의 실행 단위로 처리한다. (단일 함수는 실행 시간 제한에 취약하고 단계별 재시도, 병렬 처리, 상태 추적이 어려워 유지보수성이 크게 떨어짐)

**정답: B**

**해설**: **AWS Step Functions**는 여러 Lambda 함수나 AWS 서비스를 순서대로, 또는 병렬로 실행하는 워크플로우를 상태 머신 형태로 정의할 수 있는 서비스입니다. 각 단계마다 재시도 횟수, 백오프 간격, 오류 발생 시 대체 경로(Catch)를 선언적으로 설정할 수 있고, 콘솔에서 각 실행의 진행 상태를 시각적으로 추적할 수 있어 주문 처리와 같은 다단계 워크플로우 오케스트레이션에 적합합니다.

**왜 다른 보기는 오답인가**
- A: SNS는 메시지를 구독자에게 전달하는 발행-구독 서비스일 뿐, 단계별 재시도 정책이나 실행 상태 시각화와 같은 워크플로우 오케스트레이션 기능이 없습니다.
- C: EventBridge로 이벤트를 체이닝할 수는 있지만, 전체 흐름을 하나의 워크플로우로 정의하고 상태를 추적하는 기능은 Step Functions만큼 체계적이지 않습니다.
- D: 모든 로직을 하나의 함수에 넣으면 실행 시간 제한에 걸리기 쉽고, 특정 단계만 재시도하거나 병렬화하는 것이 불가능해 확장성과 가시성이 떨어집니다.

> 💡 **시험 꿀팁**: "여러 단계, 재시도, 시각적 워크플로우 추적"이라는 키워드 조합은 AWS Step Functions를 가리킵니다.

**왜 다른 보기는 오답인가**

- D: CloudTrail은 API 호출 이력을 기록하는 감사 로그 서비스일 뿐이며, 이를 정책 준수 여부로 해석하려면 별도의 분석 로직을 직접 구축해야 해 자동화된 지속적 평가라 보기 어렵습니다.

> 💡 **시험 꿀팁**: "리소스 구성이 정책을 지속적으로 준수하는지 자동 평가"라는 요구사항은 AWS Config를 가리키는 핵심 키워드입니다.

**문제**: 한 회사가 프라이빗 서브넷의 EC2 인스턴스들이 소프트웨어 업데이트를 위해 아웃바운드로만 인터넷에 연결될 수 있도록 구성하려 합니다. 인프라팀은 고가용성을 보장하면서도 NAT 관련 인스턴스의 패치, 확장, 장애 조치를 직접 관리하는 운영 부담을 최소화하고 싶어합니다.

- A. 퍼블릭 서브넷에 EC2 기반의 NAT 인스턴스를 직접 구성하고 소스/대상 확인(Source/Destination Check)을 비활성화한다. (NAT 인스턴스는 인스턴스 유형에 따른 대역폭 제한이 있고, 패치·장애 조치·스케일링을 직접 관리해야 해 운영 부담이 큼)

- C: VPC 피어링으로 인터넷 경로를 공유하는 것은 지원되지 않는 구성이며, 아웃바운드 인터넷 접근이라는 목적에 맞는 표준 솔루션이 아닙니다.

> 💡 **시험 꿀팁**: "운영 부담 최소화 + 프라이빗 서브넷의 아웃바운드 인터넷 접근"이라는 조합은 NAT 인스턴스가 아닌 관리형 NAT 게이트웨이를 가리킵니다.

> 💡 **시험 꿀팁**: "노드 간 초저지연, 고대역폭 통신이 필요한 HPC/긴밀 결합 워크로드"라는 표현은 클러스터 배치 그룹을 가리킵니다.

## QUESTION 394

**문제**: 한 회사의 보안 정책상 프라이빗 서브넷에 있는 EC2 인스턴스에 대해 22번(SSH) 및 3389번(RDP) 포트를 인바운드로 전혀 열지 않아야 합니다. 그럼에도 관리자는 필요할 때 해당 인스턴스에 셸로 접속해 문제를 진단하고 명령을 실행할 수 있어야 하며, 베스천 호스트를 별도로 운영하고 싶지는 않습니다.

**보기**
- A. 퍼블릭 서브넷에 베스천 호스트를 구성하고 그곳을 경유해 SSH로 프라이빗 인스턴스에 접속한다. (베스천 호스트 자체를 구축, 패치, 보안 관리해야 하는 추가 운영 부담이 발생하며 22번 포트를 완전히 닫으라는 요구사항과도 상충함)

**왜 다른 보기는 오답인가**
- A: 베스천 호스트 방식은 여전히 SSH 포트를 열어야 하고, 베스천 호스트 자체의 보안 패치와 관리라는 추가 운영 부담이 발생합니다.
- C: EC2 Instance Connect는 임시 자격 증명을 사용하긴 하지만 결국 22번 포트를 통한 SSH 연결을 전제로 하므로, 포트를 전혀 열지 않는다는 요구사항에 부합하지 않습니다.
- D: VPN 연결 역시 결국 인스턴스의 SSH/RDP 포트를 대상 네트워크에 열어야 접속이 가능하며, VPN 인프라 구축이라는 별도의 운영 부담이 추가됩니다.

> 💡 **시험 꿀팁**: "포트를 전혀 열지 않고 셸 접속"이라는 요구사항은 Systems Manager Session Manager를 가리키는 결정적 단서입니다.

**문제**: 한 회사가 하나의 도메인(api.example.com) 아래에서 주문, 결제, 회원 서비스라는 세 개의 독립적인 마이크로서비스를 각각 다른 대상 그룹으로 라우팅하고 싶어합니다. 예를 들어 /orders로 시작하는 요청은 주문 서비스로, /payments로 시작하는 요청은 결제 서비스로 전달되어야 하며, 각 서비스는 독립적으로 스케일링됩니다.

- B: Network Load Balancer는 전송 계층(4계층)에서 동작하므로 URL 경로 정보를 인식하지 못해 경로 기반 라우팅을 구현할 수 없습니다.

> 💡 **시험 꿀팁**: "하나의 도메인, 여러 마이크로서비스, URL 경로별 라우팅"이라는 조합은 ALB의 경로 기반 라우팅을 가리킵니다.

**문제**: 한 금융 회사가 특정 금융 규제에 따라 거래 기록 문서를 일정 보존 기간 동안 어느 누구도—심지어 루트 계정 관리자라도—수정하거나 삭제할 수 없는 방식으로 Amazon S3에 저장해야 합니다. 규제 감사관은 이 불변성(Immutability)이 기술적으로 강제되는지 확인하고자 합니다.

- A. S3 버킷 정책에서 삭제(DeleteObject) 및 덮어쓰기 API 호출을 명시적으로 거부(Deny)하는 규칙을 추가한다. (버킷 정책은 IAM 권한을 가진 사용자가 정책 자체를 수정하면 우회될 수 있어 기술적으로 강제되는 진정한 불변성을 보장하지 못함)

- C: 라이프사이클 정책은 스토리지 비용 절감을 위한 자동 계층 전환 기능으로, 객체의 삭제/수정을 막는 목적과는 다릅니다.

> 💡 **시험 꿀팁**: "규제 요건상 삭제/수정이 기술적으로 불가능한 WORM 저장"이라는 표현은 S3 Object Lock(특히 준수 모드)을 가리킵니다.

> 💡 **시험 꿀팁**: "위임 관리자가 부여할 수 있는 권한의 상한선 제한"이라는 요구사항은 IAM 권한 경계(Permissions Boundary)를 가리키는 핵심 키워드입니다.

**문제**: 한 제조업체가 온프레미스 데이터센터에서 운영 중인 Oracle 데이터베이스를 Amazon RDS for PostgreSQL로 마이그레이션하려 합니다. 서비스는 24시간 운영되어야 하므로 다운타임을 최소화해야 하고, 스키마 변환과 지속적 데이터 복제(CDC)를 통해 최종 전환(cutover) 시점까지 온프레미스와 대상 데이터베이스 간 데이터를 최신 상태로 유지하고 싶어합니다.

**보기**
- A. mysqldump와 유사한 pg_dump/pg_restore 도구로 데이터베이스 전체를 한 번에 덤프하고 복원한다. (전체 덤프/복원 방식은 복원 작업 동안 서비스가 중단되어야 해 다운타임을 최소화하려는 요구사항에 맞지 않고, 이기종 마이그레이션 시 스키마 변환도 지원하지 않음)
- B. AWS Snowball Edge로 데이터베이스 파일을 물리적으로 복사해 리전으로 배송한다. (물리적 배송은 일회성 대용량 데이터 이전에 적합하지만 지속적 복제(CDC)를 통한 실시간 동기화를 제공하지 않아 다운타임 최소화 요구사항을 충족하지 못함)
- C. **AWS Schema Conversion Tool(SCT)로 스키마를 변환하고 AWS Database Migration Service(DMS)로 지속적 복제(CDC)를 사용해 마이그레이션한다.**
- D. Amazon S3에 데이터베이스 백업 파일을 업로드한 뒤 RDS의 네이티브 백업 복원 기능으로 복원한다. (동종 엔진 간 네이티브 백업/복원과 달리 Oracle에서 PostgreSQL로의 이기종 마이그레이션에는 스키마 변환이 필요하며, 이 방식은 지속적 동기화도 지원하지 않아 다운타임이 커짐)

**정답: C**

**해설**: **AWS Schema Conversion Tool(SCT)**은 Oracle과 같은 소스 데이터베이스의 스키마를 PostgreSQL과 같은 대상 엔진에 맞게 자동으로 변환해주며, **AWS Database Migration Service(DMS)**는 전체 데이터 적재(Full Load) 이후 지속적 복제(Change Data Capture, CDC)를 통해 온프레미스에서 발생하는 변경 사항을 대상 데이터베이스에 실시간으로 반영합니다. 이를 통해 실제 전환 시점까지 서비스 중단을 최소화하면서 두 데이터베이스 간 데이터를 동기화된 상태로 유지할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: pg_dump/pg_restore와 같은 전체 덤프 방식은 복원이 완료될 때까지 서비스를 중단해야 하며, 이기종 데이터베이스 간 스키마 차이를 자동으로 처리해주지 않습니다.
- B: Snowball Edge는 네트워크 대역폭이 부족한 환경에서 대용량 데이터를 물리적으로 옮기는 데 유용하지만, 일회성 이전이라 지속적인 실시간 동기화를 지원하지 않습니다.
- D: 네이티브 백업/복원 기능은 보통 동일 엔진 간 마이그레이션에 사용되며, Oracle에서 PostgreSQL로의 이기종 전환에는 별도의 스키마 변환과 지속적 복제 과정이 필요합니다.

> 💡 **시험 꿀팁**: "이기종 DB 마이그레이션 + 최소 다운타임 + 지속적 복제"라는 조합은 SCT와 DMS(CDC)를 함께 가리킵니다.

## QUESTION 400

**문제**: 한 스타트업의 재무팀은 매달 AWS 청구서가 예상치 못하게 급증하는 경우가 있어, 서비스별·팀별 비용 사용 패턴을 시각적으로 분석하고, 특정 예산 금액을 초과할 것으로 예상되면 담당자에게 사전에 이메일 알림을 받고 싶어합니다. 별도의 커스텀 리포팅 시스템을 구축하지 않고 AWS 콘솔에서 바로 사용할 수 있는 방법을 원합니다.

**보기**
- A. Amazon CloudWatch 지표(Metrics)만으로 EC2 사용률을 모니터링해 비용 급증을 예측한다. (CloudWatch 지표는 리소스의 성능/사용률 지표를 제공할 뿐 서비스별 비용 데이터를 직접 시각화하거나 예산 알림을 보내는 기능은 아님)
- B. AWS Trusted Advisor의 비용 최적화 검사 결과만 매주 수동으로 확인한다. (Trusted Advisor는 특정 모범 사례에 대한 점검 결과를 제공할 뿐, 세부적인 사용 패턴 시각화나 사전 예산 초과 알림 기능은 제공하지 않음)
- C. 매월 청구서(Invoice) PDF를 다운로드해 스프레드시트로 수동 집계하고 팀별로 이메일을 전달한다. (수동 집계 방식은 시간이 오래 걸리고 사전 알림이 불가능해 비용 급증을 사전에 방지하기 어려움)
- D. **AWS Cost Explorer로 서비스별·태그별 비용 추이를 시각화하고, AWS Budgets에서 예산과 임계치를 설정해 초과 예상 시 이메일 알림을 받도록 구성한다.**

**정답: D**

**해설**: **AWS Cost Explorer**는 서비스별, 계정별, 태그별로 과거 및 예측 비용 사용 패턴을 그래프로 시각화하여 분석할 수 있는 도구이며, **AWS Budgets**는 사용자가 정의한 예산 임계치에 실제 비용 또는 예상 비용이 도달하거나 초과할 것으로 예상될 때 이메일이나 SNS 알림을 자동으로 보내주는 기능을 제공합니다. 두 서비스를 함께 사용하면 별도의 커스텀 리포팅 시스템 없이도 AWS 콘솔에서 비용 가시성 확보와 사전 예방적 알림을 모두 구현할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: CloudWatch 지표는 CPU 사용률과 같은 운영 지표를 다루는 서비스로, 비용 데이터 자체를 시각화하거나 예산 알림을 제공하지 않습니다.
- B: Trusted Advisor는 유휴 리소스나 예약 인스턴스 활용과 같은 비용 최적화 권고 사항을 점검할 뿐, 세부 비용 추이 시각화나 예산 초과 사전 알림 기능은 없습니다.
- C: 수동으로 청구서를 집계하는 방식은 시간이 오래 걸리고 실시간성이 없어 비용 급증을 사전에 감지하고 예방하기 어렵습니다.

> 💡 **시험 꿀팁**: "비용 시각화 + 예산 초과 사전 알림"이라는 조합은 AWS Cost Explorer와 AWS Budgets를 함께 가리킵니다.
