## QUESTION 261

**Question**: An on-premises VMware environment runs hundreds of large VMs (some stateful legacy apps). Migrate to AWS with **minimal downtime**, rehosting with no application code changes. What's the way to move a large number of servers with minimal operational overhead?

**Choices**
- A. Migrate the entire servers using AWS Database Migration Service (DMS) (DMS is for database migration only, not for moving an entire server including its OS/application — a conceptual error).
- B. **Set up AWS Application Migration Service (MGN) for continuous block-level replication of source servers into AWS. At cutover, launch up-to-date EC2 instances with a short downtime window.**
- C. Manually export each VM as an AMI and upload individually to EC2 (handling hundreds manually carries very high operational overhead, and without continuous replication, changes made up to the cutover point aren't captured, lengthening downtime).
- D. Use AWS Server Migration Service (SMS) with periodic snapshot-based replication (SMS is a legacy service already superseded by MGN, and the longer the snapshot interval, the greater the downtime and data-loss risk at cutover).

**Correct Answer: B**

**Explanation**
**AWS Application Migration Service (MGN)** installs an agent on source servers to maintain an up-to-date copy in AWS via **continuous block-level replication**, stopping the source only briefly at the actual cutover point before launching the EC2 instance — minimizing downtime. Even stateful legacy apps can be rehosted as-is with no OS/application changes, making MGN the standard tool for large-scale server migration.

**Why the other choices are wrong**
- A: DMS migrates databases (schema/data) — a different purpose than rehosting an entire server, OS included.
- C: Manual AMI export/upload is extremely burdensome at a scale of hundreds of servers, and without continuous replication, downtime at cutover is also longer.
- D: SMS is a legacy service AWS recommends replacing with MGN, and its periodic-snapshot (rather than continuous) approach is unfavorable for minimizing downtime.

> 💡 **Exam tip**: For rehosting a large number of servers with **minimal downtime and no code changes**, the standard answer is **AWS Application Migration Service (MGN)** — continuous block-level replication combined with a short cutover.

## QUESTION 262

**Question**: GuardDuty is enabled and managed individually across 50 AWS accounts in an organization, making it hard for the security team to get a unified view of threats. They want to view **GuardDuty findings from all accounts centrally** from a single security account, with new accounts automatically included. What minimizes operational overhead?

**Choices**
- A. In each account individually, forward GuardDuty findings via EventBridge to an SQS queue in the security account (requires configuring/maintaining an EventBridge rule individually per account — heavy operational burden, and new accounts aren't auto-included).
- B. **Designate the security account as the GuardDuty delegated administrator. Integrate with Organizations so GuardDuty is automatically enabled for all existing/new member accounts and findings are viewed centrally.**
- C. Individually deploy a Lambda in each account that exports GuardDuty findings to S3 + query centrally via Athena from the security account (requires deploying/maintaining Lambda per account, with no automatic inclusion of new accounts — heavy operational overhead).
- D. From the master account, manually send GuardDuty invitations to each member account (manual invite/accept processes become inefficient as the number of member accounts grows; the Organizations delegated-administrator approach is superior for auto-including new accounts).

**Correct Answer: B**

**Explanation**
Integrating GuardDuty with Organizations and designating a **delegated administrator** account means GuardDuty is **automatically enabled** not just for existing member accounts but for **any new accounts added to the organization going forward**, and the delegated administrator account can view findings from all accounts in one central console. This is the most operationally efficient approach, requiring no per-account configuration at all.

**Why the other choices are wrong**
- A, C: Configuring/maintaining EventBridge rules or Lambda functions individually per account becomes more burdensome as the account count grows, and doesn't apply automatically to new accounts.
- D: Manual invitations are inferior to the Organizations delegated-administrator approach both in auto-including new accounts and in operational efficiency.

> 💡 **Exam tip**: To manage security findings across many accounts **centrally and automatically for new accounts too**, the standard answer is the combination of **GuardDuty (or Security Hub, Macie, etc.) + an Organizations delegated administrator**.

## QUESTION 263

**Question**: A manufacturing plant has an on-premises application that **frequently reads and writes with low latency** to a local file server. They also want these files backed up to the cloud for disaster recovery. What's the solution that minimizes on-premises infrastructure investment?

**Choices**
- A. Keep using the on-premises NAS and back it up to S3 every night via AWS DataSync (the burden of scaling/maintaining the NAS hardware itself remains, which doesn't meet the "minimize on-premises infrastructure investment" requirement).
- B. **Deploy Storage Gateway's File Gateway to provide low-latency access via a local cache while storing files as objects in S3.**
- C. Install FSx for Windows File Server directly on-premises (FSx is a fully managed service that runs in AWS, not something installable on-premises — a conceptual error).
- D. Periodically physically ship on-premises file server data via Snowball Edge (periodic physical shipment is unrelated to a near-real-time, low-latency access requirement, and only adds operational complexity).

**Correct Answer: B**

**Explanation**
**Storage Gateway's File Gateway** is deployed on-premises as a virtual appliance, providing low-latency access to frequently accessed files via a **local cache**, while the actual data is stored as objects in **S3**, automatically backing it up to the cloud. This preserves the existing file workflow without requiring additional on-premises hardware investment (e.g., expanding a NAS).

**Why the other choices are wrong**
- A: Continuing to operate/scale an on-premises NAS conflicts with the requirement to minimize on-premises investment.
- C: FSx for Windows File Server is a managed service that runs in an AWS Region — it cannot be installed directly on-premises.
- D: Periodic physical shipment via Snowball Edge is closer to batch backup and doesn't satisfy the "frequent, low-latency read/write" requirement.

> 💡 **Exam tip**: For on-premises workloads that need to **keep low-latency file access while automatically backing up to the cloud**, **Storage Gateway File Gateway (local cache + S3 storage)** is the standard answer.

## QUESTION 264

**Question**: A globally used application's Aurora MySQL database has writes concentrated in one Region, but needs **lower read latency across multiple Regions**, and must resume writes in another Region with a **1-minute RTO** in the event of a Regional outage. What's the solution?

**Choices**
- A. Run independent Aurora clusters in multiple Regions and implement application-level dual writes (application-level dual writing is very difficult to keep consistent, with high implementation/operational complexity).
- B. A primary-Region Aurora cluster + a standard cross-Region Aurora read replica in another Region (cross-Region Aurora read replicas use ordinary asynchronous replication, and promotion can take several minutes or more — hard to meet a 1-minute RTO).
- C. **Set up Aurora Global Database with a read-only replica in the secondary Region, and use fast recoverability to promote the secondary Region to a writable Region during a failure.**
- D. Migrate the entire database to DynamoDB global tables (even without explicit relational schema/query requirements, a full migration away from the existing Aurora MySQL database — which must be kept — to DynamoDB would impose a very heavy application-rewrite burden).

**Correct Answer: C**

**Explanation**
**Aurora Global Database** uses dedicated replication infrastructure to keep a read-only replica in the secondary Region with **sub-second lag**, lowering global read latency, and during a Regional outage it can **typically promote the secondary Region to writable in under a minute**, meeting the strict RTO requirement.

**Why the other choices are wrong**
- A: Application-level dual writes make conflict resolution and consistency extremely difficult, carrying high operational risk.
- B: Promoting an ordinary cross-Region Aurora read replica is far slower than Global Database's fast-recovery feature.
- D: Fully switching to DynamoDB when the existing relational workload must be preserved is an excessive redesign not called for by the requirements.

> 💡 **Exam tip**: For an Aurora workload that needs both **reduced global read latency and fast Regional-failure recovery with a short RTO**, **Aurora Global Database** is the standard answer.

## QUESTION 265

**Question**: A single EKS cluster runs workloads for multiple teams, requiring **network/resource isolation** between teams, and each pod must use **least-privilege AWS credentials**. Achieve this without splitting the cluster per team, minimizing operational overhead. How?

**Choices**
- A. Deploy all teams' workloads into a single namespace and grant AWS permissions via an EC2 instance profile (no namespace separation means no isolation, and an instance profile means every pod on the node shares the same permissions — violates least privilege).
- B. **Configure a separate namespace and NetworkPolicy per team, and use IAM Roles for Service Accounts (IRSA) to map each team's service account to a least-privilege IAM role.**
- C. Create a brand-new, separate EKS cluster per team (contradicts the requirement to operate a single cluster without splitting it, and also increases operational overhead).
- D. Attach the same broad-permission IAM role to the node for use by all pods (every pod ends up with the same broad permissions, directly violating least privilege).

**Correct Answer: B**

**Explanation**
Kubernetes **namespaces** create a logical boundary per team, and **NetworkPolicy** controls traffic between namespaces to implement network isolation, while **IRSA (IAM Roles for Service Accounts)** allows least-privilege IAM roles to be granted at the granularity of a **pod (service account)** rather than the node. This is the standard way to achieve strong isolation and least privilege simultaneously without splitting the cluster.

**Why the other choices are wrong**
- A, D: Instance (node)-level IAM roles mean every pod running on that node shares the same permissions, which doesn't fit a scenario requiring per-pod least privilege.
- C: The question explicitly states the goal is to avoid splitting the cluster while minimizing operational overhead, so splitting clusters contradicts the requirement.

> 💡 **Exam tip**: In EKS, when you need **least-privilege AWS credentials per pod**, use **IRSA (IAM Roles for Service Accounts)**; for **network isolation** between teams/workloads, combine **namespaces + NetworkPolicy** — the standard answer.

## QUESTION 266

**Question**: Dozens of microservices spread across multiple AWS accounts, each in a different VPC, need to communicate with each other. They want to simplify service discovery and access control **at the application layer, without managing network connectivity like VPC peering or Transit Gateway**. What's the solution?

**Choices**
- A. Connect all VPCs via Transit Gateway + apply individual security group rules per service (the question explicitly wants to reduce network-connectivity management burden, so a traditional TGW-based networking approach contradicts the requirement).
- B. **Use Amazon VPC Lattice to build a service network, connecting services to it regardless of account/VPC boundaries, and apply application-layer routing and access-control (authentication/authorization) policies.**
- C. Expose all services via API Gateway private endpoints and individually create an interface endpoint in each consumer VPC (requires creating/managing an endpoint per service individually — heavy operational burden at a scale of dozens, with no unified service-network concept).
- D. Consolidate all microservices into a single VPC (rather than simplifying communication while preserving account/VPC boundaries, this requires restructuring the entire architecture — a much heavier lift).

**Correct Answer: B**

**Explanation**
**Amazon VPC Lattice** manages service-to-service communication across VPC/account boundaries at the **application layer (L7)**, letting you connect services to a single logical **service network** without complex VPC peering or Transit Gateway setups, and centrally define authentication/authorization-based access-control policies. This is the modern standard approach for simplifying communication among microservices scattered across many accounts/VPCs.

**Why the other choices are wrong**
- A: Managing everything through the traditional network layer (TGW, security groups) is exactly the approach this question wants to avoid.
- C: Creating and managing API Gateway private endpoints individually per service still carries heavy operational burden at a scale of dozens of services.
- D: Ignoring the account/VPC boundaries the organization needs to maintain and merging everything into one VPC is an unrealistic, large-scale redesign.

> 💡 **Exam tip**: To simplify communication among microservices scattered across many accounts/VPCs **without network-layer management overhead**, at the application layer, **Amazon VPC Lattice** is the standard answer.

## QUESTION 267

**Question**: Across 30 accounts managed under Organizations, each team purchases Savings Plans/Reserved Instances individually, leading to uneven utilization and poor overall cost savings. They want to **share purchased commitments** organization-wide to maximize utilization. What can be done without buying anything additional?

**Choices**
- A. Cancel all existing commitments across accounts and repurchase consolidated ones from the master account (canceling/repurchasing already-purchased commitments can incur financial loss and penalty risk — unnecessary).
- B. **Enable Reserved Instance/Savings Plans sharing at the Organizations management account so all accounts in the organization share each other's commitment discounts.**
- C. Have each account purchase additional Reserved Instances of the same type to individually raise utilization (violates the "without additional purchases" requirement and actually increases cost).
- D. Set up AWS Budgets alerts on each account's Reserved Instance utilization (monitoring/alerting alone doesn't fix the root cause — that commitments aren't shared across accounts).

**Correct Answer: B**

**Explanation**
Enabling Organizations' **Reserved Instance/Savings Plans sharing** feature automatically applies unused commitment discounts from one account to matching usage in other accounts within the organization, **maximizing commitment utilization organization-wide with no additional purchases**.

**Why the other choices are wrong**
- A: Canceling and repurchasing existing commitments incurs unnecessary cost/penalty risk.
- C: Additional purchases are explicitly excluded by the question, and don't address the root cause of poor utilization.
- D: Setting up alerts is only a monitoring measure — it doesn't fix the structural problem of commitments not being shared across accounts.

> 💡 **Exam tip**: To raise Reserved Instance/Savings Plans utilization across a multi-account environment **without additional purchases**, enabling **Organizations' commitment sharing (RI/Savings Plans sharing)** is the standard answer.

## QUESTION 268

**Question**: For a mission-critical RDS PostgreSQL workload, the recovery target during a Regional outage is **within a few hours** (not a strict sub-minute figure), while minimizing steady-state cost — a pilot light DR architecture. What combination is appropriate?

**Choices**
- A. Run a DR-Region RDS instance of the same size as production at all times (this is a hot standby/multi-site approach rather than pilot light, conflicting with the steady-state cost-minimization requirement).
- B. **Keep a minimally sized RDS read replica running in the DR Region. On failure, promote the read replica to a writable primary and scale up the instance size as needed. Use Route 53 health-check-based failover to switch traffic.**
- C. Only copy nightly RDS snapshots to the DR Region, and create a new instance from a snapshot during a failure (a snapshot-only approach is cheaper than pilot light but risks losing up to a day of data, and including instance-creation time could take several hours — more of a backup/restore approach than "pilot light" as intended here).
- D. Keep no resources at all in the DR Region, and on failure provision the entire stack (network+DB+app) from scratch via CloudFormation on demand (a cold standby approach — building everything from scratch generally takes longer than pilot light, which could jeopardize the RTO target).

**Correct Answer: B**

**Explanation**
A **pilot light** approach keeps a minimally sized core component (here, an RDS read replica) running at all times in the DR Region to keep steady-state costs low, while allowing a **read replica promotion** alone to quickly establish a writable environment during a failure. Combined with **Route 53 health-check-based failover**, the entire recovery — including DNS cutover — can be achieved within the target RTO (a few hours).

**Why the other choices are wrong**
- A: Running a same-size instance at all times is closer to hot standby/multi-site, which conflicts with pilot light's cost-saving intent.
- C: A snapshot-only approach is closer to cold standby, and is worse than promoting a read replica both in terms of potential data loss and recovery time.
- D: Cold standby with no pre-provisioned resources generally has a longer RTO than pilot light, since the entire stack must be built from scratch.

> 💡 **Exam tip**: A **pilot light DR** pattern keeps a minimally sized core component (e.g., an RDS read replica) running at all times, recovers quickly via **promotion + scale-up** during a failure, and switches traffic via **Route 53 failover** — the standard pattern.

## QUESTION 269

**Question**: A genomics company needs to batch-process petabytes of genomic data. Each job has different CPU/memory requirements, and thousands of parallel jobs must run, while **minimizing the operational burden of job scheduling and infrastructure management**. What's the appropriate service?

**Choices**
- A. Directly configure an EC2 Auto Scaling group and implement a custom job queue/scheduler (implementing/operating job queuing, prioritization, retry logic, etc. yourself is very heavy overhead).
- B. **Use AWS Batch to configure a compute environment (a mix of On-Demand/Spot), a job queue, and job definitions, specifying the CPU/memory needed per job, and delegate scheduling to the fully managed service.**
- C. Run an Amazon EMR cluster continuously to process jobs via Hadoop/Spark (EMR is optimized for distributed data-processing frameworks; AWS Batch is better suited for flexibly scheduling diverse batch jobs with varying resource needs, and running continuously is also cost-inefficient).
- D. Implement each job as an individual Lambda function (Lambda's maximum execution time and resource limits make it unsuitable for long-running, petabyte-scale batch jobs).

**Correct Answer: B**

**Explanation**
**AWS Batch** automatically provisions the optimal compute resources (which can mix On-Demand and Spot) based on job volume and resource requirements, and handles job queuing and scheduling in a fully managed way. It's optimized for running thousands of parallel batch jobs with varying CPU/memory requirements with no operational burden.

**Why the other choices are wrong**
- A: Implementing your own queue/scheduler reinvents functionality AWS Batch already provides — very heavy operational burden.
- C: EMR specializes in distributed data-processing frameworks like Hadoop/Spark, and a continuously running cluster is cost-inefficient for a variable batch workload.
- D: Lambda's maximum execution time (15 minutes) makes it unsuitable for long-running, large-scale batch jobs.

> 💡 **Exam tip**: To run **large-scale parallel batch jobs** with widely varying resource requirements with no operational burden, **AWS Batch** (automatic compute-environment provisioning + fully managed job queue/scheduling) is the standard answer.

## QUESTION 270

**Question**: RDS databases scattered across multiple AWS accounts use credentials that the security team wants to **rotate automatically from a central location**, while each application account queries only the secrets it needs, following least privilege. How do you centralize this without running a separate Secrets Manager instance per account?

**Choices**
- A. Create/rotate Secrets Manager secrets individually in each account and manually sync them (requires per-account management, contradicting the centralization requirement, and manual syncing is highly error-prone).
- B. **Store secrets in a security (central) account and use a Secrets Manager resource policy to allow cross-account access to each application account's IAM role. Manage the rotation Lambda function in the central account.**
- C. Encrypt all database passwords with a single KMS key and store them in S3, with each application reading directly from S3 (storing secrets, encrypted or not, in S3 is an anti-pattern that forfeits Secrets Manager's automatic rotation, auditing, and fine-grained access control).
- D. Switch to Systems Manager Parameter Store SecureString and implement rotation logic individually in each account (Parameter Store's native rotation isn't as integrated as Secrets Manager's, requiring you to build rotation logic yourself, and per-account implementation also contradicts the centralization requirement).

**Correct Answer: B**

**Explanation**
Storing secrets in a **central security account's Secrets Manager** and using a **resource-based policy** to grant cross-account read access only to specific IAM roles in each application account lets secrets be managed centrally in one place while each account queries only what it needs, at least privilege. The rotation Lambda function also only needs to be managed once, in the central account, minimizing operational overhead.

**Why the other choices are wrong**
- A: Managing secrets individually per account and syncing manually directly contradicts the centralization requirement and carries high operational risk.
- C: Storing secrets directly in S3 forfeits Secrets Manager's key benefits — automatic rotation, fine-grained access control, and audit logging.
- D: Parameter Store SecureString is a viable alternative, but Secrets Manager's integrated automatic rotation for RDS credentials is more robust, and per-account implementation contradicts the centralization intent.

> 💡 **Exam tip**: To **centrally manage secrets while sharing them at least privilege** across multiple accounts, **a central account's Secrets Manager + resource-policy-based cross-account access** is the standard answer.

## QUESTION 271

**Question**: A financial company wants to build a Direct Connect connection between its on-premises data center and AWS with **maximum resiliency** — no single point of failure (circuit, device, or location). What configuration does AWS recommend?

**Choices**
- A. A single circuit at a single Direct Connect location (a single location and single circuit is vulnerable to both location and circuit failure — no resiliency at all).
- B. Two circuits through two different devices at a single Direct Connect location (a failure of the single location affects both circuits — no location-level resiliency).
- C. **At each of two different Direct Connect locations, two circuits through two different devices at that location (4 circuits total, 2 locations, device redundancy within each location).**
- D. Two circuits at a single Direct Connect location, backed up only by an internet-based VPN (relies on a single location, and VPN's lower bandwidth/higher latency compared to Direct Connect means it isn't a full substitute — falls short of the maximum-resiliency model).

**Correct Answer: C**

**Explanation**
The **maximum resiliency** model defined by the AWS Direct Connect Resiliency Toolkit calls for multiple circuits, each through a **different device**, at **two or more different Direct Connect locations**. This way, connectivity is maintained via the remaining paths even if an entire location fails, a specific device fails, or a specific circuit fails.

**Why the other choices are wrong**
- A, B: Relying on a single location means a failure at that location itself (power outage, disaster, etc.) severs connectivity entirely — falling short of the maximum-resiliency bar.
- D: An internet-based VPN can be a valid backup path, but it's not a full substitute for a single Direct Connect location given the bandwidth/latency requirements of a financial workload, and it still relies on that single location.

> 💡 **Exam tip**: Direct Connect's **maximum resiliency** model standardly calls for **2+ different locations × multiple circuits through different devices at each location**. A single-location-based configuration makes the location itself a single point of failure (SPOF).

## QUESTION 272

**Question**: A large enterprise wants to quickly provision a standardized account (including logging, security guardrails, and baseline networking) for every new project. Development teams should be able to self-service the request, while governance ensures accounts can only be created within a pre-approved configuration scope. What's the solution?

**Choices**
- A. An administrator manually creates each AWS account and runs individual CloudFormation stacks to apply the standard configuration (a manual process that contradicts self-service and doesn't scale).
- B. **Configure AWS Control Tower's Account Factory, and register pre-approved account templates as AWS Service Catalog products for development teams to request via self-service.**
- C. Grant each dev team administrator permissions in the Organizations management account to create and configure accounts directly (delegating broad management-account permissions violates least privilege and makes enforcing guardrails difficult).
- D. Let dev teams create AWS accounts individually, with the security team auditing after the fact and requesting fixes if issues are found (a reactive rather than preventive-guardrail approach — high governance risk and inefficient).

**Correct Answer: B**

**Explanation**
**AWS Control Tower's Account Factory** automatically provisions standardized accounts that include logging, security guardrails, and baseline networking. Publishing this as an **AWS Service Catalog** product lets development teams request accounts via **self-service** within a pre-approved scope, while maintaining governance so nothing deviates from centrally defined guardrails and standards.

**Why the other choices are wrong**
- A: Having an administrator handle everything manually each time isn't self-service and doesn't scale as requests grow.
- C: Delegating broad management-account permissions to each team violates least privilege and makes it hard to enforce standard guardrails.
- D: A post-hoc audit approach only catches problems after they occur — riskier than preventive governance that restricts scope up front.

> 💡 **Exam tip**: To provide many teams with **standardized, guardrail-compliant accounts quickly via self-service**, the combination of **Control Tower's Account Factory + Service Catalog** is the standard answer.

## QUESTION 273

**Question**: Multiple departments load data with different schemas into an S3 data lake, and schemas frequently change over time (columns added, types changed). The analytics team needs to query via Athena, but also needs **fine-grained column/row-level access control** per dataset. What data-catalog/governance solution minimizes operational burden?

**Choices**
- A. Each department builds its own Hive metastore on EC2 to manage schemas (requires building/operating your own — heavy overhead, and fine-grained access control must also be implemented from scratch).
- B. **Use AWS Glue crawlers to automatically detect schema changes and reflect them in the Glue Data Catalog, and use AWS Lake Formation's fine-grained permissions (column/row level) to control dataset access.**
- C. Move all source data into RDS and force it into a unified relational schema (forcing frequently changing, semi-structured/varied data into a unified relational schema is unsuitable, and migration effort is heavy).
- D. Control access to each dataset using only separate S3 bucket policies (S3 bucket policies only allow bucket/object-level control and don't support fine-grained column/row-level access control).

**Correct Answer: B**

**Explanation**
**AWS Glue crawlers** periodically and automatically detect schema changes in S3 data, keeping the **Glue Data Catalog** up to date without manual schema management. **AWS Lake Formation** builds on this catalog to centrally define **column-level and row-level** access-control policies, exposing analytics teams querying via Athena only to the parts of each dataset they need.

**Why the other choices are wrong**
- A: Running your own Hive metastore means building/maintaining functionality the Glue Data Catalog already provides in a fully managed way — heavy operational burden.
- C: Forcing varied, frequently changing data into a relational DB schema hurts flexibility and incurs heavy migration cost.
- D: S3 bucket policies only support object/bucket-level control, not the column/row-level fine-grained access control the question requires.

> 💡 **Exam tip**: When a data lake needs **automatic schema management + fine-grained column/row-level access control**, the standard answer is **Glue Data Catalog (auto-updated via crawlers) + Lake Formation (fine-grained permissions)**.

## QUESTION 275

**Question**: A company's commercial software license is billed based on the **socket/core count of a specific physical server**, and the license agreement requires the ability to **verify the physical characteristics (sockets, cores, host ID) of the virtualized environment**. How do you meet this on EC2 while optimizing license cost?

**Choices**
- A. Use standard On-Demand EC2 instances with no other action (standard instances on shared hardware make it hard to clearly control/verify physical-server-level socket/core information, potentially failing to meet the license agreement's requirement).
- B. **Use Amazon EC2 Dedicated Hosts to get an entire physical server allocated exclusively, verify the host's socket/core information, and apply the existing license as-is (BYOL, Bring Your Own License).**
- C. Use Dedicated Instances (dedicated instances guarantee hardware isn't shared with other accounts, but offer less visibility/control over physical details like a specific host's socket/core ID than a Dedicated Host).
- D. Purchase Savings Plans to get a discount that also covers licensing costs (Savings Plans is a compute-usage discount program and doesn't address the socket/core-based software licensing requirement itself).

**Correct Answer: B**

**Explanation**
**Dedicated Hosts** allocate an entire physical server exclusively to you, providing visibility into that host's **socket count, core count, and host ID**. This lets you bring an existing commercial software license billed by socket/core into the cloud as-is (BYOL), meeting the license agreement's requirements while optimizing cost.

**Why the other choices are wrong**
- A: Standard instances on shared hardware don't allow control at the physical socket/core level, making them unsuitable for this kind of license requirement.
- C: Dedicated Instances guarantee no hardware sharing, but don't provide the same level of detailed visibility (socket/core/host ID) into a specific physical host as a Dedicated Host.
- D: Savings Plans is just a compute-billing discount mechanism, unrelated to socket/core-based license compliance.

> 💡 **Exam tip**: For a **BYOL license** requirement billed by socket/core count, **EC2 Dedicated Hosts** — which provide visibility into physical server details (sockets, cores, host ID) — is the standard answer.

## QUESTION 276

**Question**: A remote research station needs to move **petabytes** of collected sensor data to AWS, but internet bandwidth is extremely limited (slow satellite internet), so online transfer would take months. They also want to perform some **preprocessing (local compute)** on the data while transferring it. What's the solution?

**Choices**
- A. Use S3 Transfer Acceleration to speed up internet transfer (with base bandwidth already extremely limited, Transfer Acceleration still can't make up the time needed for petabyte-scale transfer).
- B. **Deploy an AWS Snowball Edge Compute Optimized device on-site to preprocess data locally (EC2/Lambda-compatible compute), then physically ship the device to AWS for automatic loading into S3.**
- C. Install a DataSync agent on the on-site server to continuously sync to S3 over the internet (even with DataSync, the fundamental time constraint of a petabyte-scale transfer over limited satellite bandwidth isn't solved, and it has no local preprocessing capability).
- D. Build a server similar to EC2 on-site to preprocess and send only the results over the internet (building/operating your own hardware is a heavy burden, with no integrated management with AWS, adding operational overhead).

**Correct Answer: B**

**Explanation**
**AWS Snowball Edge Compute Optimized** combines large-capacity storage with built-in EC2/Lambda-compatible **compute** capability, allowing on-site data preprocessing even in a bandwidth-constrained environment, before **physically shipping** the device to AWS to load the data into S3. This is the standard way to address both the bandwidth constraint and the on-site preprocessing requirement simultaneously.

**Why the other choices are wrong**
- A: Transfer Acceleration only optimizes the network path — it doesn't overcome the fundamental limits of the constrained bandwidth itself.
- C: DataSync still relies on the internet connection, so it remains unsuitable for petabyte-scale transfer over extremely limited satellite bandwidth, and it has no local compute feature.
- D: Building your own server carries heavy hardware procurement/operational burden and doesn't provide fully managed integration with AWS (e.g., automatic loading into S3).

> 💡 **Exam tip**: When you need **petabyte-scale data transfer plus on-site preprocessing in an extremely bandwidth-constrained environment**, **AWS Snowball Edge (Compute Optimized)** is the standard answer.

## QUESTION 277

**Question**: A loan-approval workflow needs to call several microservices along with a **manual human approval step** (which can take days). **Choices**
- A. Chain the steps via SQS queues, with Lambda polling/processing sequentially (an SQS+Lambda chain doesn't natively provide multi-day waiting states or visual tracking of the overall workflow status — heavy implementation burden).
- B. **Define a state machine in AWS Step Functions to model each microservice call step, and use a task token for the human-approval step to pause the workflow, resuming it via SendTaskSuccess/SendTaskFailure from the approval system.**
- C. Build Apache Airflow directly on EC2 for workflow orchestration (requires building/operating your own server — contradicts the "no server management" requirement).
- D. Have each microservice call the next one directly in a chain (a choreography rather than orchestration approach, lacking central visibility for overall status tracking/retries/long waits, and scattering failure-handling logic across services, raising complexity).

**Correct Answer: B**

**Explanation**
**AWS Step Functions** is a fully managed service that lets you define each step as a visual state machine, with declarative retry/error handling on failure. In particular, for long-running steps involving human intervention, the **task token** pattern lets you pause the workflow and have an external system resume it via the `SendTaskSuccess`/`SendTaskFailure` API once approval is complete (waiting for up to a year) — well suited to an approval process that can take days.

**Why the other choices are wrong**
- A: An SQS+Lambda chain is fine for processing individual messages, but doesn't natively provide long-running human-intervention steps or visual tracking of overall workflow status, leaving much to implement yourself.

## QUESTION 278

**Question**: A compliance requirement mandates that backup data stored across multiple Regions be encrypted with the **same key material** (rather than re-encrypting with a separate key per Region), while still allowing fast, local encryption/decryption in each Region. What's the solution?

**Choices**
- A. Create an independent KMS key per Region, and for backups, decrypt in the source Region and re-encrypt with the destination Region's key (each Region uses different key material, violating the "same key material" requirement, and decrypting/re-encrypting each time adds processing cost and latency).
- B. **Create a KMS multi-Region key as the primary key, and create replica keys in each Region needed. Since they share the same key ID/key material, encryption/decryption can happen locally in each Region without cross-Region re-encryption.**
- C. Create a KMS key in only one Region, and always have resources in other Regions call across Regions to that key's Region for encryption/decryption (cross-Region API calls have high latency, and an outage in the key's Region would affect encryption/decryption in every other Region too — violating the "locally in each Region" requirement).
- D. Build an independent CloudHSM cluster in each Region and manually export/import keys between clusters (manual key movement carries heavy operational burden and security risk, far more cumbersome than KMS multi-Region key's native replication).

**Correct Answer: B**

**Explanation**
A **KMS multi-Region key** lets you create a primary key and then create **replica keys** in other Regions that **share the same key material**, so each Region has an independent key ID but uses **identical cryptographic material**. Data encrypted in one Region can therefore be decrypted directly using the replica key in another Region with no re-encryption, and since each Region calls its API locally, latency is minimized too.

**Why the other choices are wrong**
- A: Using independent keys (different key material) per Region and re-encrypting doesn't meet the "same key material" requirement and adds processing overhead.
- C: Relying on a single-Region key and always calling across Regions incurs high latency and makes that Region's outage a single point of failure affecting every other Region.
- D: Manually moving keys between CloudHSM clusters is far more complex and operationally risky than KMS multi-Region key's native replication.

> 💡 **Exam tip**: When you need **local encryption/decryption in multiple Regions using the same key material with no re-encryption**, **KMS multi-Region keys + replica keys** is the standard answer.

## QUESTION 279

**Question**: In a hybrid environment, on-premises servers need to resolve domains in a VPC's private hosted zone, and conversely, EC2 instances in the VPC need to resolve domains managed by an on-premises DNS server (bidirectional hybrid DNS resolution). Assuming connectivity via VPN/Direct Connect, what's the solution?

**Choices**
- A. Change all on-premises servers' DNS settings to point directly at the Route 53 public hosted zone's name servers (a private hosted zone can't be resolved via public name servers, and this doesn't address the requirement to resolve on-premises' own domains either — a conceptual error).
- B. **Configure a Route 53 Resolver outbound endpoint with a conditional forwarding rule to send queries from the VPC to the on-premises DNS server, and an inbound endpoint so on-premises can query the VPC's private hosted zone.**
- C. Deploy an identical hosts file to every EC2 instance and on-premises server, hardcoding domains (continuously syncing a hosts file across hundreds/thousands of machines is operationally near-impossible).
- D. Switch the VPC to use only a public hosted zone instead of a private one (exposing a private domain publicly is undesirable for security, and it doesn't match the question's premise of hybrid resolution for a private zone in the first place).

**Correct Answer: B**

**Explanation**
**Route 53 Resolver** provides bidirectional endpoints for hybrid DNS resolution. An **outbound endpoint + a conditional forwarding rule** lets VPC resources forward queries for specific on-premises domains to the on-premises DNS server, while an **inbound endpoint** lets on-premises servers query records in the VPC's Route 53 private hosted zone. This combination is the standard bidirectional hybrid DNS architecture, assuming VPN/Direct Connect connectivity.

**Why the other choices are wrong**
- A: A private hosted zone isn't resolvable via public name servers, and this doesn't address the requirement for the VPC side to resolve on-premises' own domains either.
- C: Continuously syncing a hosts file at scale is practically unworkable operationally.
- D: Exposing private data publicly violates the security requirement, and contradicts the question's premise of keeping a private zone in the first place.

> 💡 **Exam tip**: For **bidirectional DNS resolution** between on-premises and a VPC in a hybrid environment, the standard answer is **Route 53 Resolver's outbound endpoint (conditional forwarding) + inbound endpoint**.

## QUESTION 280

**Question**: A global online gaming service processes **UDP-based** real-time game traffic through an EC2 fleet behind an NLB. After a recent large-scale DDoS attack caused an outage, leadership wants advanced DDoS protection including **cost protection** and **dedicated response-team support**. What's the solution that also routes global users over the optimal path while protecting the service?

**Choices**
- A. Protect the NLB with CloudFront + AWS WAF in front (CloudFront is optimized for HTTP/HTTPS content delivery and doesn't support UDP traffic, so it doesn't fit a UDP-based real-time gaming traffic scenario).
- B. **Register the NLB as an endpoint with AWS Global Accelerator to route global traffic over the optimal path via an Anycast IP, and subscribe to AWS Shield Advanced to protect the Global Accelerator/NLB (including DDoS cost protection and DRT support).**
- C. Distribute traffic to per-Region NLBs via Route 53 geoproximity routing + rely only on the default AWS Shield Standard (Shield Standard is basic free protection and doesn't include cost protection or dedicated response-team [DRT] support, falling short of the requirement).
- D. Put API Gateway in front of the NLB to apply request-rate limiting (API Gateway is for REST/HTTP APIs and WebSockets, and can't handle UDP-based real-time gaming traffic — a conceptual error).

**Correct Answer: B**

**Explanation**
**AWS Global Accelerator** routes users to the nearest edge of the AWS global network via a fixed Anycast IP, providing an optimal path and low latency for both TCP and UDP traffic, and can register an NLB as an endpoint. Applying **AWS Shield Advanced** on top provides large-scale DDoS attack protection for the Global Accelerator/NLB, plus **financial protection against scaling costs** incurred by DDoS, and 24/7 support from the **DDoS Response Team (DRT)** — meeting all of leadership's requirements.

**Why the other choices are wrong**
- A: CloudFront specializes in HTTP(S) content delivery and can't handle UDP gaming traffic.
- C: Shield Standard is the baseline network/transport-layer DDoS protection given to all AWS customers, but advanced features like cost protection and dedicated DRT support are only available with Shield Advanced.
- D: API Gateway isn't a service for handling UDP-based real-time traffic.

> 💡 **Exam tip**: When you need to route **UDP or other non-HTTP traffic** over the globally optimal path while getting **DDoS cost protection + DRT support**, the standard answer is **Global Accelerator (Anycast IP, TCP/UDP support) + Shield Advanced**. Remember CloudFront is HTTP(S)-only.
