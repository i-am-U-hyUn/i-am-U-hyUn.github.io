## QUESTION 141

**문제**: 한 회사가 사용자에게 글로벌 속보, 지역 경보, 날씨 업데이트를 제공하는 웹 기반 포털을 운영한다. 포털은 정적 콘텐츠와 동적 콘텐츠를 혼합하여 각 사용자에게 개인화된 화면을 제공한다. 콘텐츠는 ALB(Application Load Balancer) 뒤의 Amazon EC2 인스턴스에서 실행되는 API 서버를 통해 HTTPS로 제공된다. 회사는 이 콘텐츠를 전 세계 사용자에게 가능한 한 빠르게 제공하고자 한다. 모든 사용자의 지연 시간을 최소화하려면 애플리케이션을 어떻게 설계해야 하는가?

**보기**
- A. **단일 AWS 리전에 애플리케이션 스택을 배포하고, ALB를 오리진으로 지정한 Amazon CloudFront를 사용하여 정적 및 동적 콘텐츠를 모두 제공한다.**
- B. 두 AWS 리전에 애플리케이션 스택을 배포하고, Amazon Route 53 지연 시간 라우팅 정책으로 가장 가까운 리전의 ALB에서 모든 콘텐츠를 제공한다(다중 리전 구축과 데이터 동기화 부담이 추가되며, CloudFront 캐싱만으로 해결 가능한 문제에 과도한 인프라 복제).
- C. 단일 리전에 배포하고, CloudFront로 정적 콘텐츠만 제공하고 ALB에서 동적 콘텐츠를 직접 제공한다(동적 콘텐츠 경로가 오리진 리전까지 그대로 왕복해야 해 원거리 사용자의 지연이 그대로 남음).
- D. 두 AWS 리전에 배포하고, Amazon Route 53 지리적 위치 라우팅 정책으로 가장 가까운 리전에서 ALB의 모든 콘텐츠를 제공한다(지리적 위치 라우팅은 사용자의 실제 위치와 무관하게 정해진 지리적 매핑으로 라우팅되어 반드시 최저 지연 리전으로 연결된다는 보장이 없고, 다중 리전 운영 부담도 발생).

**정답: A**

**해설**
**Amazon CloudFront**는 ALB를 오리진으로 사용할 수 있어서, 정적 콘텐츠는 엣지 로케이션에서 캐싱하고 동적 콘텐츠 요청도 CloudFront의 최적화된 백본 네트워크를 통해 오리진(ALB)까지 빠르게 전달합니다. 단일 리전만으로도 전 세계 사용자에게 낮은 지연 시간을 제공할 수 있어, 다중 리전을 구축하는 방식보다 단순하고 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- B: 다중 리전에 스택을 복제하고 데이터까지 동기화해야 해 CloudFront 하나로 해결 가능한 문제에 비해 운영 복잡성과 비용이 크게 늘어납니다.
- C: 동적 콘텐츠를 ALB에서 직접 제공하면 원거리 사용자는 여전히 오리진 리전까지의 왕복 지연을 그대로 겪습니다.
- D: 지리적 위치 라우팅은 사용자를 특정 리전에 고정 매핑하는 방식이라 실제 최저 지연 경로를 보장하지 않으며, 다중 리전 운영 부담도 그대로 남습니다.

> 💡 **시험 꿀팁**: 정적+동적 콘텐츠를 전 세계에 빠르게 제공해야 한다면 단일 리전 + **CloudFront(ALB를 오리진으로)** 조합이 표준 정답입니다.

## QUESTION 142

**문제**: 게임 회사가 고가용성 아키텍처를 설계하고 있다. 애플리케이션은 수정된 Linux 커널에서 실행되며 UDP 기반 트래픽만 지원한다. 최상의 사용자 경험을 위해 프런트엔드 계층이 지연 시간이 짧은 가장 가까운 엣지 로케이션으로 트래픽을 라우팅하고, 애플리케이션 엔드포인트 진입을 위한 고정 IP 주소를 제공해야 한다. 솔루션 설계자는 이러한 요구 사항을 충족하기 위해 무엇을 해야 하는가?

**보기**
- A. Amazon Route 53을 구성해 요청을 Application Load Balancer로 전달하고, AWS Application Auto Scaling의 애플리케이션에 AWS Lambda를 사용한다(ALB는 HTTP/HTTPS 계층 로드밸런서로 UDP 트래픽을 지원하지 않음).
- B. Amazon CloudFront를 구성해 요청을 Network Load Balancer로 전달하고, AWS Application Auto Scaling 그룹의 애플리케이션에 AWS Lambda를 사용한다(CloudFront는 HTTP/HTTPS 기반 CDN으로 UDP 트래픽 프록시 및 고정 진입 IP 제공 목적에 맞지 않음).
- C. **AWS Global Accelerator를 구성해 요청을 Network Load Balancer로 전달하고, EC2 Auto Scaling 그룹의 애플리케이션에 Amazon EC2 인스턴스를 사용한다.**
- D. Amazon API Gateway를 구성해 요청을 Application Load Balancer로 전달하고, EC2 Auto Scaling 그룹의 애플리케이션에 Amazon EC2 인스턴스를 사용한다(API Gateway와 ALB 모두 HTTP(S) 기반이라 UDP 트래픽을 처리할 수 없음).

**정답: C**

**해설**
**AWS Global Accelerator**는 AWS 글로벌 네트워크의 엣지에서 TCP/UDP 패킷을 프록시하여 가장 가까운 엣지 로케이션으로 트래픽을 라우팅하고, 두 개의 고정 애니캐스트 IP 주소로 애플리케이션에 진입할 수 있게 해줍니다. **Network Load Balancer**는 4계층에서 UDP를 포함한 트래픽을 처리할 수 있으므로, Global Accelerator + NLB + EC2 Auto Scaling 조합이 UDP 기반 게임 트래픽에 고정 IP와 최단 경로 라우팅을 동시에 제공하는 표준 아키텍처입니다.

**왜 다른 보기는 오답인가**
- A, D: ALB와 API Gateway는 모두 HTTP/HTTPS(7계층) 트래픽에 특화되어 있어 UDP 기반 게임 트래픽을 처리할 수 없습니다.
- B: CloudFront는 캐시 가능한 HTTP(S) 콘텐츠 가속에 특화된 CDN으로, UDP 트래픽 프록시나 고정 IP 제공이라는 요구 사항에 부합하지 않습니다.

> 💡 **시험 꿀팁**: **UDP/TCP 비HTTP 트래픽 + 고정 IP + 엣지 기반 최단 경로**라는 조건이 나오면 **AWS Global Accelerator(+ NLB)**가 표준 정답입니다.

## QUESTION 143

**문제**: 회사가 기존 온프레미스 모놀리식 애플리케이션을 AWS로 마이그레이션하려 한다. 프런트엔드 코드와 백엔드 코드는 최대한 그대로 유지하되, 애플리케이션을 더 작은 단위로 나누어 서로 다른 팀이 각각 관리하도록 하려 한다. 운영 오버헤드를 최소화하면서 확장성이 뛰어난 솔루션은 무엇인가?

**보기**
- A. AWS Lambda에서 애플리케이션을 호스팅하고 Amazon API Gateway와 통합한다(기존 코드베이스를 Lambda 함수 단위로 재작성해야 해 "코드를 최대한 유지"라는 요구와 충돌하며, 이벤트 기반/서버리스 워크로드에 더 적합).
- B. AWS Amplify를 사용해 애플리케이션을 호스팅하고, AWS Lambda와 통합된 Amazon API Gateway API에 연결한다(Amplify는 주로 프런트엔드 웹/모바일 호스팅에 초점이 맞춰져 있어 기존 백엔드 코드를 유지한 채 여러 팀이 독립적으로 관리하는 분리 구조에는 적합하지 않음).
- C. Amazon EC2 인스턴스에서 애플리케이션을 호스팅하고, Auto Scaling 그룹의 EC2 인스턴스를 대상으로 ALB를 설정한다(인스턴스 프로비저닝/패치 등 인프라 관리가 그대로 필요해 컨테이너 서비스 대비 운영 오버헤드가 큼).
- D. **Amazon Elastic Container Service(Amazon ECS)에서 애플리케이션을 호스팅하고, Amazon ECS를 대상으로 하는 Application Load Balancer를 설정한다.**

**정답: D**

**해설**
**Amazon ECS**는 기존 애플리케이션 코드를 컨테이너 이미지로 패키징해 그대로 옮길 수 있으면서도, 관리형 오케스트레이션으로 운영 오버헤드를 줄여주는 서비스입니다. 애플리케이션을 여러 개의 독립된 ECS 서비스(마이크로서비스)로 분리하면 팀마다 자신의 서비스를 독립적으로 배포·확장할 수 있고, ALB를 ECS 앞에 두면 여러 태스크에 트래픽을 분산해 확장성과 가용성을 확보할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Lambda는 이벤트 기반/서버리스 워크로드에 적합하며, 기존 모놀리식 코드를 최대한 유지하며 마이그레이션하는 데는 재작성 부담이 큽니다.
- B: Amplify는 프런트엔드 중심 호스팅 플랫폼으로, 백엔드를 여러 독립 애플리케이션으로 나누어 관리하는 유연성을 제공하지 않습니다.
- C: EC2 기반 구성은 인프라 프로비저닝과 패치 등을 직접 관리해야 해 ECS 대비 운영 부담이 더 큽니다.

> 💡 **시험 꿀팁**: **기존 코드를 최대한 유지하며 여러 팀이 독립적으로 관리하는 확장 가능한 마이크로서비스**로 나누고 싶다면 **Amazon ECS + ALB**가 표준 정답입니다.

## QUESTION 144

**문제**: 한 회사가 최근 글로벌 전자상거래 애플리케이션의 데이터 저장소로 Amazon Aurora를 사용하기 시작했다. 대규모 월별 보고서가 실행될 때 전자상거래 애플리케이션의 성능이 저하되며, CloudWatch 지표를 확인해보니 이때 ReadIOPS와 CPUUtilization 지표가 급증한다. 가장 비용 효율적인 솔루션은 무엇인가?

**보기**
- A. 월별 보고를 Amazon Redshift로 마이그레이션한다(별도의 데이터 웨어하우스 클러스터 구축과 ETL 파이프라인이 필요해 비용과 운영 부담이 큼).
- B. **월별 보고를 Aurora 복제본으로 마이그레이션한다.**
- C. Aurora 데이터베이스를 더 큰 인스턴스 클래스로 마이그레이션한다(인스턴스 업그레이드는 지속적인 비용 증가를 유발하며, 보고서 실행 시에만 발생하는 일시적 부하에는 비효율적).
- D. Aurora 인스턴스에서 프로비저닝된 IOPS를 늘린다(Aurora는 스토리지 자동 확장형 구조로 프로비저닝된 IOPS를 늘려도 근본 원인인 프라이머리 인스턴스의 읽기 경합을 해결하지 못함).

**정답: B**

**해설**
**Aurora 복제본**은 프라이머리 인스턴스와 동일한 스토리지 볼륨을 공유하면서 읽기 전용 쿼리를 처리할 수 있는 인스턴스입니다. 월별 보고서처럼 무거운 읽기 작업을 Aurora 복제본으로 돌리면 프라이머리 인스턴스의 ReadIOPS와 CPU 부담을 분산시켜 전자상거래 트랜잭션 처리 성능에 미치는 영향을 최소화하면서도, 기존 인스턴스를 그대로 유지하므로 추가 비용이 가장 적습니다.

**왜 다른 보기는 오답인가**
- A: Redshift 마이그레이션은 별도의 웨어하우스 구축과 데이터 파이프라인 구성이 필요해 "가장 비용 효율적" 조건에 맞지 않습니다.
- C: 인스턴스 클래스를 키우면 상시 더 높은 비용을 지불해야 하며, 월별 한 번의 스파이크에는 과도한 해결책입니다.
- D: 프로비저닝된 IOPS를 늘리는 것은 스토리지 계층의 처리량을 늘릴 뿐, 읽기 쿼리가 프라이머리 인스턴스의 컴퓨팅 자원을 경합하는 근본 문제는 해결하지 못합니다.

> 💡 **시험 꿀팁**: **Aurora에서 읽기 위주 보고서/분석 작업이 프라이머리 성능에 영향**을 준다면 **Aurora 복제본으로 읽기 부하 분리**가 표준 정답입니다.

## QUESTION 145

**문제**: 회사가 단일 Amazon EC2 온디맨드 인스턴스에서 웹 사이트 분석 애플리케이션을 호스팅한다. PHP로 작성된 분석 소프트웨어와 MySQL 데이터베이스, 웹 서버가 모두 하나의 EC2 인스턴스에서 실행된다. 바쁜 시간대에 성능이 저하되고 5xx 오류가 발생하며, 회사는 애플리케이션을 원활하게 확장하고자 한다. 가장 비용 효율적으로 이 요구 사항을 충족하는 솔루션은 무엇인가?

**보기**
- A. 데이터베이스를 Amazon RDS for MySQL로 마이그레이션하고, 웹 애플리케이션 AMI를 생성해 두 번째 EC2 온디맨드 인스턴스를 시작한 뒤 ALB로 각 EC2 인스턴스에 로드를 분산한다(Auto Scaling이 구성되지 않아 트래픽 변화에 자동으로 대응하지 못하고 수동으로 용량을 조정해야 함).
- B. 데이터베이스를 Amazon RDS for MySQL로 마이그레이션하고, 웹 애플리케이션 AMI를 생성해 두 번째 EC2 온디맨드 인스턴스를 시작한 뒤 Route 53 가중 라우팅으로 두 인스턴스에 로드를 분산한다(가중 라우팅은 고정된 비율로 트래픽을 분배할 뿐 부하에 따라 자동으로 확장되지 않음).
- C. 데이터베이스를 Amazon Aurora MySQL로 마이그레이션하고, Lambda 함수로 EC2 인스턴스를 중지하고 인스턴스 유형을 변경하며, CPU 사용률이 75%를 초과하면 이 Lambda를 호출하는 CloudWatch 경보를 생성한다(인스턴스를 중지했다가 유형을 바꿔 재시작하는 수직 확장 방식은 전환 중 다운타임이 발생하고 트래픽 급증에 실시간으로 대응하기 어려움).

- C: 인스턴스를 중지하고 유형을 변경하는 수직 확장 방식은 전환 시간 동안 서비스가 중단되며 실시간 트래픽 급증에 적절히 대응하기 어렵습니다.

Lambda 함수의 비동기 호출이 실패하면 **온-페일러 목적지(on-failure destination)**로 SQS 대기열을 지정해 실패한 이벤트 정보를 안전하게 보관할 수 있습니다. Lambda 함수가 이 대기열의 메시지를 처리하도록 구성하면, 네트워크 문제 등으로 최초 처리가 실패하더라도 이벤트가 유실되지 않고 나중에 자동으로 재처리되어 수동 재실행 없이도 결국 모든 알림이 처리됩니다.

- B: 리소스(CPU/메모리) 부족이 원인이 아니라 네트워크 연결 문제가 원인이므로 이 조치는 문제를 해결하지 못합니다.
- C: SNS의 재시도 횟수를 늘려도 결국 전송 정책이 소진되면 DLQ 없이는 메시지가 삭제되므로 유실 가능성이 남습니다.

> 💡 **시험 꿀팁**: **비동기 처리 실패 시 이벤트 유실 방지**가 필요하면 **Lambda의 온-페일러 목적지로 SQS(DLQ) 구성**이 표준 정답입니다.

**문제**: 회사에 이벤트 데이터를 생성하는 서비스가 있으며, AWS를 사용해 이벤트 데이터를 수신하는 대로 처리하려 한다. 데이터는 처리 전반에 걸쳐 유지되어야 하는 특정 순서로 작성된다. 운영 오버헤드를 최소화하는 솔루션은 무엇인가?

> 💡 **시험 꿀팁**: **이벤트/메시지의 처리 순서를 반드시 유지**해야 한다면 **SQS FIFO 대기열**이 표준 정답입니다.

- B. Amazon CloudWatch 대시보드를 생성하여 지표를 시각화하고 문제에 신속하게 대응한다(대시보드는 지표를 시각화할 뿐 조건에 따라 자동으로 경보를 발생시키는 기능이 없어 오경보 감소 요구를 충족하지 못함).
- C. Amazon CloudWatch Synthetics 카나리아를 생성하여 애플리케이션을 모니터링하고 경보를 발생시킨다(Synthetics는 외부 엔드포인트의 가용성/응답을 점검하는 용도로, 인스턴스 내부의 CPU·디스크 지표 조합 조건 판단에는 적합하지 않음).
- D. 가능한 경우 여러 지표 임계값으로 단일 Amazon CloudWatch 지표 경보를 생성한다(단일 지표 경보는 하나의 지표·조건만 평가하도록 설계되어 있어 CPU와 IOPS라는 서로 다른 지표를 AND 조건으로 결합해 판단할 수 없음).

**정답: A**

**해설**
**CloudWatch 복합 경보**는 여러 개의 개별 지표 경보 상태(ALARM/OK)를 AND/OR 논리로 조합해 하나의 최종 경보 상태를 만들어내는 기능입니다. "CPU 사용률 경보"와 "읽기 IOPS 경보"를 각각 만든 뒤 두 경보가 동시에 ALARM 상태일 때만 최종 경보가 발생하도록 AND 조건의 복합 경보를 구성하면, CPU만 단독으로 튀는 정상적인 상황은 무시하고 실제 문제 상황(CPU와 IOPS가 동시에 높은 경우)에만 알림을 받아 오경보를 크게 줄일 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 대시보드는 지표를 시각적으로 보여줄 뿐이며, 조건을 판단해 자동으로 알림을 발생시키는 경보 기능이 아닙니다.
- C: Synthetics 카나리아는 외부에서 애플리케이션 엔드포인트의 가용성을 주기적으로 점검하는 용도로, 인스턴스 내부 지표 조합 조건에는 적합하지 않습니다.
- D: 단일 지표 경보는 하나의 지표에 대해서만 임계값을 평가하도록 설계되어 있어, 서로 다른 두 지표를 AND로 결합한 조건을 표현할 수 없습니다.

> 💡 **시험 꿀팁**: **여러 지표가 동시에 특정 조건을 만족할 때만 경보를 울려 오경보를 줄이고 싶다**면 **CloudWatch 복합 경보(Composite Alarm)**가 표준 정답입니다.

- E: AWS Config는 리소스 구성 변경을 감지·기록하는 사후 모니터링 도구일 뿐, 위반 행위 자체를 사전에 차단하지 못합니다.

> 💡 **시험 꿀팁**: **특정 리전만 허용 + 인터넷 차단**과 같은 예방적 거버넌스 요구에는 **Control Tower 가드레일**과 **Organizations SCP**의 조합이 표준 정답입니다.

## QUESTION 153

**문제**: 회사가 인기 있는 노래 클립으로 만든 벨소리를 판매한다. 파일은 최소 128KB이며 Amazon S3 Standard에 저장되고, 수백만 개의 파일 중 90일보다 오래된 벨소리는 다운로드가 드물다. 가장 많이 액세스하는 파일은 계속 쉽게 사용할 수 있도록 유지하면서 스토리지 비용을 절약하려면 어떤 조치를 취해야 하는가?

**해설**
최근 생성된 벨소리는 자주 다운로드되므로 **S3 Standard**에 두어 빠른 접근을 유지하고, 90일이 지나 다운로드가 드물어진 파일은 **S3 수명 주기 정책**을 통해 자동으로 **S3 Standard-IA**로 전환하면 스토리지 비용을 낮추면서도 필요할 때는 여전히 빠르게 검색할 수 있습니다. 별도의 수동 개입 없이 사전 정의된 규칙만으로 접근 패턴에 맞춰 비용을 최적화하는 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A: 신규 파일은 접근 빈도가 높아 IA로 시작하면 빈번한 검색 요금이 발생해 오히려 비효율적입니다.
- B: Intelligent-Tiering은 접근 패턴이 불확실할 때 유용하지만, 이미 "90일" 기준이 명확한 이 상황에서는 모니터링 요금이 추가로 드는 대신 얻는 이점이 적습니다.
- C: S3 인벤토리는 객체 목록과 상태를 보고하는 도구로, 스토리지 클래스를 자동으로 전환하지 못해 수동 작업이 필요합니다.

> 💡 **시험 꿀팁**: **특정 기간이 지나면 접근 빈도가 뚜렷하게 줄어드는 패턴**에는 **S3 수명 주기 정책으로 Standard → Standard-IA 자동 전환**이 표준 정답입니다.

## QUESTION 154

**문제**: 회사가 의료 시험 결과를 Amazon S3 리포지토리에 저장해야 한다. 일부 과학자는 새 파일을 추가할 수 있어야 하고, 다른 모든 사용자는 읽기 전용 액세스로 제한되어야 한다. 어떤 사용자도 저장소의 파일을 수정하거나 삭제할 수 없어야 하며, 모든 파일은 생성일로부터 최소 1년 동안 보관되어야 한다. 어떤 솔루션이 이러한 요구 사항을 충족하는가?

**보기**
- A. 거버넌스 모드에서 1년의 법적 보유 기간으로 S3 Object Lock을 사용한다(거버넌스 모드는 특별 권한을 가진 일부 사용자가 객체를 삭제·수정할 수 있어 "어떤 사용자도 수정·삭제 불가"라는 요구를 완전히 충족하지 못함).
- B. **보존 기간이 365일인 규정 준수(Compliance) 모드에서 S3 Object Lock을 사용한다.**
- C. IAM 역할을 사용하여 모든 사용자가 S3 버킷의 객체를 삭제하거나 변경하지 못하도록 제한하고, S3 버킷 정책으로 IAM 역할만 허용한다(권한 정책은 설정 실수나 정책 변경으로 우회될 수 있어 WORM을 원천적으로 강제하는 Object Lock만큼 강력한 보장을 제공하지 못함).
- D. 객체가 추가될 때마다 AWS Lambda 함수를 호출하도록 S3 버킷을 구성하고, 저장된 객체의 해시를 추적해 수정된 객체를 표시하는 기능을 구성한다(변경 사실을 사후에 탐지·표시할 뿐이며 변경이나 삭제 자체를 막지는 못함).

**정답: B**

**해설**
**S3 Object Lock의 규정 준수(Compliance) 모드**는 보존 기간이 만료되기 전까지 루트 사용자를 포함한 어떤 사용자도 객체 버전을 덮어쓰거나 삭제할 수 없도록 강제하는 WORM(Write Once, Read Many) 메커니즘입니다. 보존 기간을 365일로 설정하면 생성일로부터 최소 1년간 파일이 보호되며, 과학자들은 새 파일을 계속 추가할 수 있지만 어떤 사용자도 기존 파일을 수정·삭제할 수 없다는 요구를 정확히 충족합니다.

**왜 다른 보기는 오답인가**
- A: 거버넌스 모드는 특수 권한을 가진 사용자가 보존 설정을 변경하거나 객체를 삭제할 수 있어 요구 사항에 위배됩니다.
- C: IAM/버킷 정책만으로는 정책 변경이나 관리자 실수로 삭제·수정이 가능해 Object Lock 수준의 강제성을 제공하지 못합니다.
- D: 해시 추적은 변경을 사후에 감지하는 방법일 뿐, 애초에 변경·삭제 자체를 막는 예방적 통제가 아닙니다.

> 💡 **시험 꿀팁**: **어떤 사용자도(관리자 포함) 예외 없이 객체를 삭제·수정하지 못하게** 해야 한다면 **S3 Object Lock의 규정 준수(Compliance) 모드**가 표준 정답입니다.

**해설**
**API 키 기반 사용량 계획**을 도입하면 정품 사용자에게만 배포된 키가 있어야 API를 호출할 수 있어, 키가 없는 봇넷의 무차별 요청을 API Gateway 단계에서 걸러낼 수 있습니다. 여기에 **AWS WAF**로 봇 시그니처, 요청 비율, IP 평판 등을 기준으로 한 규칙을 만들어 API Gateway에 연결하면, 애플리케이션 계층에서 악성 트래픽을 자동으로 차단해 Lambda까지 도달하기 전에 걸러낼 수 있습니다. 두 조치를 함께 사용하면 정상적인 공개 API 접근성은 유지하면서 사기성 요청만 효과적으로 차단할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: Lambda 내부에서 걸러내는 방식은 이미 API Gateway를 통과해 Lambda가 호출된 이후의 대응이라 비용·부하가 이미 발생한 뒤이며, IP 목록 유지 관리도 번거롭습니다.
- D: 비공개 API로 전환하면 "공개적으로 접근 가능한" 서비스라는 요구 사항 자체를 훼손합니다.
- E: 불특정 다수를 대상으로 하는 공개 API에서 사용자별 IAM 역할을 개별적으로 생성·관리하는 것은 현실적으로 확장 불가능합니다.

> 💡 **시험 꿀팁**: **공개 서버리스 API에 대한 봇/사기성 트래픽 차단**에는 **API 키 기반 사용량 계획 + AWS WAF** 조합이 표준 정답입니다.

## QUESTION 160

**문제**: 전자상거래 회사가 AWS 클라우드에서 분석 애플리케이션을 호스팅하며, 이 애플리케이션은 매월 약 300MB의 데이터를 JSON 형식으로 생성한다. 회사는 데이터 백업을 위한 재해 복구 솔루션을 평가하고 있으며, 데이터는 필요한 경우 밀리초 단위로 접근할 수 있어야 하고 30일 동안 보관되어야 한다. 이러한 요구 사항을 가장 비용 효율적으로 충족하는 솔루션은 무엇인가?

**보기**
- A. Amazon OpenSearch Service(Amazon Elasticsearch Service)(검색·분석 엔진으로, 이미 별도의 분석 애플리케이션이 있는 상황에서 백업용 데이터 저장소로 사용하기에는 목적이 맞지 않고 비용도 더 높음).
- B. Amazon S3 Glacier(검색(retrieval)에 최소 수 분이 걸릴 수 있어 밀리초 단위 액세스 요구를 충족하지 못함).
- C. **Amazon S3 Standard**
- D. Amazon RDS for PostgreSQL(관계형 데이터베이스는 구조화된 데이터를 조회·갱신하는 용도로, 단순 백업 데이터를 일정 기간 보관하는 재해 복구 목적에는 과도하고 비용도 더 높음).

**정답: C**

**해설**
매월 약 300MB의 소규모 JSON 데이터를 30일간 백업용으로 보관하면서 필요 시 밀리초 단위로 즉시 조회할 수 있어야 하는 요구에는 **Amazon S3 Standard**가 가장 적합합니다. S3 Standard는 자주 접근되는 데이터를 위한 스토리지 클래스로 밀리초 단위의 낮은 지연 시간을 제공하며, 데이터 양이 작고 30일이라는 짧은 보관 기간을 고려하면 별도의 검색 지연이 있는 아카이브 스토리지나 무거운 데이터베이스·검색 서비스보다 훨씬 비용 효율적입니다.

**왜 다른 보기는 오답인가**
- A: OpenSearch Service는 로그 분석, 실시간 모니터링 등에 특화된 검색·분석 엔진으로, 단순 백업 데이터 저장 용도로는 불필요하게 무겁고 비용도 큽니다.
- B: S3 Glacier는 장기 저비용 보관에는 적합하지만, 데이터 검색에 최소 수 분 이상 걸릴 수 있어 밀리초 단위 액세스 요구를 충족하지 못합니다.
- D: RDS for PostgreSQL은 관계형 데이터를 저장·질의하는 데이터베이스 서비스로, 단순 파일 백업의 재해 복구 저장소로 사용하기에는 과도하고 비용도 더 높습니다.

> 💡 **시험 꿀팁**: **소규모 데이터의 단기(수십 일) 백업 + 밀리초 단위 즉시 액세스**가 필요하다면 별도의 아카이브나 DB 없이 **Amazon S3 Standard**가 가장 비용 효율적인 표준 정답입니다.
