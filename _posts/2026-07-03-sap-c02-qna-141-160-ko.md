## QUESTION 141

**문제**: Auto Scaling 그룹의 EC2 인스턴스로 30분 걸리는 비디오 처리를 하며, SQS 대기열 메시지 수에 따라 확장/축소된다. 리드라이브 정책(DLQ, maxReceiveCount=1), 가시성 제한 시간 1시간. 배달 못한 편지 대기열에 메시지가 쌓이는데 애플리케이션 로그에는 오류가 없다. 해결 방법은?

**보기**
- A. EC2 인스턴스에 종료 방지 기능을 켠다.
- B. SQS 가시성 제한 시간을 3시간으로 늘린다.
- C. **처리 중인 인스턴스에 축소 보호를 구성한다.**
- D. 리드라이브 정책의 maxReceiveCount를 0으로 설정한다.

**정답: C**

**해설**
문제의 진짜 원인은 처리 도중(30분 소요) Auto Scaling 그룹이 **부하 감소를 이유로 해당 인스턴스를 종료**시켜버리는 것입니다. 인스턴스가 종료되면 메시지 처리가 완료되지 못하고 가시성 제한 시간이 끝난 후 재수신되며, `maxReceiveCount=1`이라 즉시 DLQ로 이동합니다. **인스턴스 축소 보호(scale-in protection)**를 활성화하면 처리 중인 인스턴스가 축소 대상에서 제외되어 문제를 근본적으로 해결합니다.

**왜 다른 보기는 오답인가**
- A: 종료 방지는 수동 종료나 특정 이벤트를 막을 뿐, Auto Scaling의 축소(scale-in) 자체를 막지 못합니다.
- B: 가시성 제한 시간을 늘려도 인스턴스가 축소로 종료되면 여전히 처리가 중단됩니다 — 근본 원인 해결이 아닙니다.
- D: maxReceiveCount를 0으로 설정하는 것은 유효하지 않거나 즉시 DLQ로 보내는 등 의도와 다르게 동작합니다.

> 💡 **시험 꿀팁**: Auto Scaling 그룹이 **처리 중인 긴 작업의 인스턴스를 실수로 종료**하는 시나리오는 **인스턴스 축소 보호(Instance Scale-In Protection)**가 정답인 경우가 많습니다.

## QUESTION 142

**문제**: 리전 엔드포인트의 API Gateway(Lambda 통합), 특정 API 세트는 **VPC 내부에서만** 접근 가능해야 하며, 모든 API는 인증된 사용자만 호출 가능해야 한다. 최소 노력으로 만족하는 솔루션은?

**보기**
- A. 내부 ALB + 대상 그룹 + Lambda 연결.
- B. API Gateway DNS 항목 제거 + Route 53 호스팅 영역 + CNAME.
- C. **API Gateway 엔드포인트를 리전 → 프라이빗으로 변경. VPC에 인터페이스 VPC 엔드포인트 생성. 리소스 정책을 API에 연결. VPC 엔드포인트로 API를 호출.**
- D. VPC 내부 EC2 + Apache 서버로 Lambda 프록시.

**정답: C**

**해설**
API Gateway는 **프라이빗 엔드포인트 유형**을 지원하며, **인터페이스 VPC 엔드포인트(PrivateLink)**와 **리소스 정책**을 결합하면 API를 VPC 내부에서만 호출 가능하도록 손쉽게 제한할 수 있습니다. 이것이 최소 노력의 표준 방법입니다.

**왜 다른 보기는 오답인가**
- A, D: ALB나 EC2/Apache로 우회 프록시를 만드는 것은 훨씬 큰 구성 노력과 관리 부담이 필요합니다.
- B: DNS 트릭만으로는 실제 네트워크 접근을 VPC로 제한할 수 없습니다.

> 💡 **시험 꿀팁**: API Gateway를 **VPC 내부에서만** 호출 가능하게 만들려면 **프라이빗 API 엔드포인트 + 인터페이스 VPC 엔드포인트 + 리소스 정책** 조합이 정답입니다.

## QUESTION 143

**문제**: eu-west-1의 S3+정적 콘텐츠를 CloudFront로 서비스하는 날씨 지도 서비스. us-east-1로 신규 확장했는데 us-east-1 사용자가 느리다고 보고한다. 해결 조합은? (2개 선택)

**보기**
- A. Global Accelerator + S3 CRR로 us-east-1에 새 버킷.
- B. **(D의 일부처럼) Lambda@Edge로 북미 요청을 us-east-1 S3 버킷으로 수정.**
- C. Lambda@Edge로 S3 Transfer Acceleration 엔드포인트 사용.
- D. **Lambda@Edge로 북미 요청을 us-east-1 S3로 수정 + us-east-1용 Global Accelerator 엔드포인트를 CloudFront 오리진으로 구성 + Lambda@Edge로 새 오리진 사용.**

**정답: B, D**

**해설**
정답은 **us-east-1에 S3 버킷을 추가로 두고(CRR로 동기화), Lambda@Edge를 사용해 북미(us-east-1) 사용자의 요청을 가까운 리전의 버킷/오리진으로 라우팅**하는 조합입니다. CloudFront의 엣지에서 지역별로 오리진을 동적으로 바꾸는 데는 **Lambda@Edge의 오리진 요청(origin-request) 트리거**가 표준 해법입니다.

**왜 다른 보기는 오답인가**
- A: Global Accelerator를 S3 버킷 자체에 직접 붙이는 방식은 일반적인 패턴이 아니며, CloudFront와 결합하는 것이 더 자연스럽습니다.
- C: S3 Transfer Acceleration은 업로드 가속 기능이지, 이 시나리오의 콘텐츠 다운로드 지연 문제 해결과는 맞지 않습니다.

> 💡 **시험 꿀팁**: CloudFront가 지역별로 **가까운 오리진**을 동적으로 선택하게 하려면 **Lambda@Edge(오리진 요청 트리거)**를 사용하고, 콘텐츠 자체는 **S3 Cross-Region Replication**으로 각 리전에 복제해두는 조합이 표준입니다.

## QUESTION 144

**문제**: WorkSpaces에서 새 세션을 만들 수 없는 문제. FSx for Windows File Server를 프로필 공유 스토리지(10TB)로 사용 중이며, 파일 시스템이 **최대 용량**에 도달했다. 사용자 재접속 가능하게 하고, 재발 방지도 필요.

**보기**
- A. 오래된 프로필 제거 + FSx for Lustre로 마이그레이션.
- B. **`update-file-system`으로 용량 증설. FreeStorageCapacity CloudWatch 지표 모니터링. EventBridge → Lambda로 필요 시 자동 증설.**
- C. FreeStorageCapacity 지표 + Step Functions로 증설.
- D. 오래된 프로필 제거 + 두 번째 FSx 생성 + 프로필 50% 리디렉션.

**정답: B**

**해설**
즉시 문제 해결(용량 증설)과 재발 방지(모니터링+자동화)를 모두 충족하는 것은 **`update-file-system` API로 용량을 늘리고, CloudWatch의 FreeStorageCapacity 지표를 모니터링하다가 EventBridge로 Lambda를 호출해 필요할 때 자동으로 용량을 늘리는** 구성입니다.

**왜 다른 보기는 오답인가**
- A: FSx for Lustre는 프로필 공유(Windows용)에 적합하지 않으며(HPC 중심, SMB 미지원), 프로필 제거는 임시방편일 뿐입니다.
- C: Step Functions는 이 자동 확장 워크플로에 불필요하게 복잡합니다.
- D: 프로필 리디렉션으로 파일 시스템을 나누는 것은 운영 복잡도만 증가시킵니다.

> 💡 **시험 꿀팁**: FSx 용량 관리는 **`update-file-system` API**로 증설하고, **CloudWatch FreeStorageCapacity + EventBridge + Lambda**로 자동화하는 것이 표준 패턴입니다.

## QUESTION 145

**문제**: 배송 확인(서명/사진)을 핸드헬드 장치가 FTP로 단일 EC2 인스턴스에 업로드, 인스턴스가 DB 조회 후 메타데이터 추가, S3에 보관. 확장하면서 연결 끊김/메모리 문제 발생. 핸드헬드 장치는 수정 불가. 확장성 극대화 솔루션은?

**보기**
- A. AMI 생성 + ALB 뒤 Auto Scaling 그룹.
- B. AWS Transfer Family(FTP→EFS) + 기존 EC2에 마운트.
- C. **AWS Transfer Family(FTP→S3) + S3 이벤트 → SNS → Lambda로 메타데이터 추가 및 전달 시스템 업데이트.**
- D. 핸드헬드 장치를 S3 직접 업로드로 변경(장치 수정 불가라 제외) + SQS → Lambda.

**정답: C**

**해설**
장치는 수정 불가(FTP 유지 필요)이므로, **AWS Transfer Family로 관리형 FTP 서버를 만들어 S3로 직접 저장**하고, **S3 이벤트 알림(SNS) → Lambda**로 메타데이터 추가와 DB 업데이트를 서버리스로 자동 처리하면 단일 EC2 병목이 완전히 제거됩니다.

**왜 다른 보기는 오답인가**
- A: 기존 단일 EC2 아키텍처(FTP 서버 자체의 병목)를 그대로 확장할 뿐, 근본 원인을 해결하지 못합니다.
- B: EFS에 저장 후 다시 EC2로 처리하는 구조는 여전히 EC2 병목을 남깁니다.
- D: 핸드헬드 장치를 수정할 수 없다는 제약을 위반합니다.

> 💡 **시험 꿀팁**: **레거시 FTP 클라이언트(수정 불가)를 서버리스로 확장**해야 할 때는 **AWS Transfer Family(S3 대상) + S3 이벤트 → Lambda**가 표준 정답 패턴입니다.

## QUESTION 146

**문제**: ECS(Fargate) + Aurora MySQL 애플리케이션. 규제 요구사항으로 재해 시 **다른 리전**으로 복구해야 하며 **데이터 손실이 없어야** 함. 최소 운영 오버헤드로 만족하는 솔루션은?

**보기**
- A. **다른 리전에 Aurora 복제본(Aurora Global Database)을 프로비저닝한다.**
- B. AWS DataSync로 지속적 복제.
- C. AWS DMS로 지속적 복제.
- D. Amazon DLM으로 5분마다 스냅샷.

**정답: A**

**해설**
**Aurora Global Database**(다른 리전 Aurora 복제본)는 관리형으로 리전 간 복제 지연이 1초 미만 수준이며, 최소 운영 오버헤드로 크로스 리전 재해 복구를 제공하는 Aurora의 네이티브 기능입니다.

**왜 다른 보기는 오답인가**
- B: DataSync는 파일/객체 데이터 전송용이지 관계형 DB 복제용이 아닙니다.
- C: DMS로 지속 복제를 직접 구성하는 것은 Aurora Global Database보다 운영 오버헤드가 훨씬 큽니다.
- D: 5분 간격 스냅샷은 RPO(데이터 손실 없음)를 만족하지 못합니다.

> 💡 **시험 꿀팁**: Aurora의 **크로스 리전 재해 복구**는 거의 항상 **Aurora Global Database**가 정답이며, DMS/DataSync 같은 수동 복제 구성보다 운영 부담이 훨씬 적습니다.

## QUESTION 147

**문제**: 신용카드 파트너로부터 15분마다 평문 5,000개 레코드를 HTTPS+서버측 암호화로 S3에 수신. PAN(카드번호)을 자동 마스킹 후 다른 버킷으로 전송해야 하고, 필드 제거/병합 후 JSON 변환 필요. 향후 확장 가능해야 함.

**보기**
- A. Lambda(추출→SQS) → Lambda(처리→S3 임시) → 대기열 비면 최종 Lambda로 JSON 변환.
- B. Lambda(추출→SQS) → Fargate 컨테이너로 처리 → 대기열 비면 축소.
- C. **Glue 크롤러+사용자 지정 분류자로 테이블 정의. 파일 전송 시 Lambda가 Glue ETL 작업 실행(처리/변환/마스킹). 출력 JSON. 완료 후 내부 버킷으로 전송.**
- D. Glue 크롤러 + Athena 쿼리 + EMR ETL.

**정답: C**

**해설**
**Glue ETL**은 필드 마스킹, 제거/병합, 포맷 변환(JSON) 같은 구조화된 변환 작업에 최적화되어 있으며, 크롤러+분류자로 스키마를 자동 인식해 향후 새로운 피드 형식에도 쉽게 확장 가능합니다. Lambda로 트리거만 하고 실제 변환은 Glue ETL에 위임하는 것이 관리 오버헤드와 확장성 면에서 최선입니다.

**왜 다른 보기는 오답인가**
- A, B: Lambda나 Fargate로 변환 로직을 직접 구현하면 Glue의 스키마 관리/확장성 이점을 재구현해야 하는 추가 부담이 생깁니다.
- D: EMR 클러스터를 매번 띄우는 것은 5,000개 레코드/15분 규모에 비해 과도하게 무겁습니다.

> 💡 **시험 꿀팁**: 정형 데이터의 **필드 마스킹/제거/병합/포맷 변환**이 필요하고 향후 확장성도 중요할 때는 **Glue 크롤러(스키마 인식) + Glue ETL 작업**이 표준 정답입니다.

## QUESTION 148

**문제**: 온프레미스 애플리케이션(물리 서버, MySQL 사용, EC2 호환 OS)의 장애 대비 비즈니스 연속성 솔루션을 최소 운영 오버헤드로 구축.

**보기**
- A. AWS Replication Agent + 테스트 인스턴스 컷오버(정기 훈련용, 장애 시 컷오버).
- B. **AWS Replication Agent 설치(MySQL 서버 포함) + 대상 리전에서 AWS Elastic Disaster Recovery 초기화 + 시작 설정 정의 + 최근 시점부터 자주 장애 조치/폴백 테스트.**
- C. DMS 복제 서버 + Aurora MySQL 대상 클러스터 + SCT CDC 작업.
- D. Storage Gateway Volume Gateway + 스냅샷 + EC2에서 볼륨 게이트웨이 복원.

**정답: B**

**해설**
**AWS Elastic Disaster Recovery(DRS)**는 물리서버/이기종 워크로드를 포함해 최소 운영 오버헤드로 지속적인 블록 수준 복제와 신속한 장애 조치/폴백을 제공하는, 이 시나리오에 정확히 맞는 관리형 재해 복구 서비스입니다.

**왜 다른 보기는 오답인가**
- A: DRS를 초기화하지 않고 단순 테스트 인스턴스로 컷오버하는 방식은 지속적 복제와 자동화된 장애 조치가 아닙니다.
- C: DMS+SCT는 데이터베이스(MySQL) 마이그레이션/동기화 전용이며, 애플리케이션 서버 전체(물리서버)의 DR을 포괄하지 않습니다.
- D: Storage Gateway 기반 수동 스냅샷/복원 방식은 DRS보다 운영 오버헤드가 훨씬 큽니다.

- B. 공유 라이브러리를 Docker 이미지 + ECR 업로드 + Lambda 계층으로 사용 + zip 패키지.
- C. Fargate(ECS) 컨테이너에 공유 라이브러리 배포 + 이를 Lambda 계층처럼 사용(불가능한 개념).
- D. **공유 라이브러리, 사용자 지정 클래스, 코드 전체를 Docker 이미지에 배포. ECR에 업로드. Lambda 함수가 이 Docker 이미지를 배포 패키지로 사용하도록 구성.**

**정답: D**

**해설**
Lambda는 **컨테이너 이미지를 배포 패키지로 직접 사용**할 수 있습니다. 공유 라이브러리와 코드를 하나의 Docker 이미지에 모두 담아 ECR에 올리고 이를 Lambda의 배포 패키지로 사용하면, 배포가 단일 아티팩트로 단순화되고 코드/라이브러리 재사용도 이미지 레이어 캐싱으로 최적화됩니다.

**왜 다른 보기는 오답인가**
- A, B: Lambda 계층(layer)의 소스로 Docker 이미지를 지정하는 기능 자체가 존재하지 않습니다 — Lambda 계층은 zip 아카이브를 사용합니다.
- C: ECS/Fargate 컨테이너를 Lambda 계층으로 쓴다는 개념 자체가 성립하지 않습니다.

> 💡 **시험 꿀팁**: Lambda는 **컨테이너 이미지를 배포 패키지 자체로 직접 사용**할 수 있습니다(계층의 "소스"로 쓰는 게 아님). 공유 라이브러리가 많은 복잡한 Lambda 배포를 단순화하려면 **하나의 컨테이너 이미지(ECR)로 전체를 패키징**하는 것이 정답입니다.

## QUESTION 158

**문제**: 온프레미스 데이터센터의 AWS 마이그레이션 비즈니스 사례 작성. 모든 서버의 CMDB(구성 관리 데이터베이스) 내보내기 데이터를 사용. 가장 비용 효율적인 솔루션은?

**보기**
- A. AWS Well-Architected Tool로 CMDB 데이터 가져오기(용도 불일치 — 아키텍처 검토 도구).

- C. 리소스 매칭 규칙 구현 + CMDB + AWS Price List Bulk API로 직접 대량 쿼리(직접 구축, 비효율).

**정답: B**

**해설**

- C: Price List Bulk API로 직접 매칭 로직을 구축하는 것은 Migration Evaluator가 이미 제공하는 기능을 재발명하는 것입니다.

> 💡 **시험 꿀팁**: 기존 **CMDB 내보내기 데이터**를 활용해 마이그레이션 비즈니스 사례/TCO를 만들 때는 **AWS Migration Evaluator**(데이터 가져오기 템플릿 지원)가 정답이며, Application Discovery Service는 "처음부터 데이터를 수집"해야 할 때 쓰는 도구임을 구분하세요.

## QUESTION 159

**문제**: ALB+Auto Scaling 그룹 웹사이트, AWS WAF 웹 ACL 연결. 애플리케이션 계층 공격이 자주 발생하며 매번 다른 IP 주소에서 시작됨. 최소 운영 오버헤드로 완화하는 솔루션은?

**보기**
- A. CloudWatch 경보(IP별 임계값) + 웹 ACL 거부 목록에 자동 추가.
- B. **AWS WAF에 더해 AWS Shield Advanced 배포. ALB를 보호 리소스로 추가.**
- C. CloudWatch 경보 + Lambda로 서브넷 라우팅 테이블에 거부 규칙 추가.
- D. 액세스 로그 분석 + Route 53 지리적 위치 라우팅으로 국가 차단.

**정답: B**

**해설**
공격이 **매번 다른 IP**에서 오므로 IP 기반 차단(A, C)은 효과가 제한적이고 지속적인 수동/반자동 대응이 필요해 운영 오버헤드가 큽니다. **AWS Shield Advanced**는 정교한 애플리케이션 계층(L7) DDoS 탐지/완화를 자동으로 제공하며, DRT(DDoS 대응팀) 지원까지 포함해 최소 운영 오버헤드로 지속적인 애플리케이션 계층 공격에 대응합니다.

**왜 다른 보기는 오답인가**
- A, C: IP 주소가 매번 바뀌므로 개별 IP 차단 방식은 효과가 낮고, 지속적인 수동 대응 부담이 큽니다.
- D: 국가 단위 차단은 정상 사용자까지 차단할 위험이 크고, 공격자가 다른 국가의 IP를 사용하면 무력화됩니다.

> 💡 **시험 꿀팁**: **매번 다른 IP에서 오는 애플리케이션 계층(L7) 공격**에는 IP 기반 차단보다 **AWS Shield Advanced**(정교한 자동 탐지/완화)가 최소 운영 오버헤드로 대응하는 정답입니다.

## QUESTION 160

**문제**: 단일 리전에 데이터 계층(DynamoDB + Aurora MySQL, 글로벌 데이터베이스 지원 버전) 배포된 중요 애플리케이션. 애플리케이션 계층은 이미 두 리전에 배포됨. 회사 정책상 데이터 계층도 두 리전 배포 필요. RTO/RPO는 몇 분 이내. 필요한 단계는? (2개 선택)

**보기**
- A. **Aurora MySQL DB 클러스터에 다른 리전 추가(Aurora Global Database).**
- B. Aurora MySQL 클러스터의 각 테이블에 다른 리전 추가(개념 오류 — 리전은 클러스터 단위).
- C. DynamoDB+Aurora에 예약된 교차 리전 백업 설정(RPO 요건 미충족 — 분 단위 손실 발생 가능).
- D. **기존 DynamoDB 테이블에 다른 리전을 추가해 글로벌 테이블로 전환.**
- E. Route 53 Application Recovery Controller로 백업/복구 자동화(백업 기반 방식이라 RTO/RPO 미충족).

**정답: A, D**

**해설**
Aurora MySQL은 이미 글로벌 데이터베이스를 지원하는 엔진 버전이므로 **Aurora Global Database**로 전환(다른 리전 추가, A)하면 되고, DynamoDB는 **글로벌 테이블**로 전환(다른 리전 추가, D)하면 됩니다. 둘 다 관리형 다중 리전 복제 기능으로 RPO/RTO를 분 단위로 유지합니다.

**왜 다른 보기는 오답인가**
- B: 리전 추가는 클러스터 단위로 이루어지며 "각 테이블"이라는 개념은 Aurora Global Database의 동작 방식과 맞지 않습니다.
- C, E: 예약된 백업이나 백업 기반 복구 자동화는 스냅샷 주기에 따라 데이터 손실이 발생할 수 있어 "몇 분 이내 RPO" 요건을 만족하지 못합니다.

> 💡 **시험 꿀팁**: 관계형 DB의 실시간에 가까운 크로스 리전 DR은 **Aurora Global Database**, NoSQL(DynamoDB)은 **글로벌 테이블**이 표준 정답이며, 백업/스냅샷 기반 방식은 분 단위 RPO를 만족시키기 어렵다는 점을 기억하세요.
