## QUESTION 41

**문제**: DynamoDB를 사용하는 앱의 RCU/WCU를 예상 최대 부하에 맞췄습니다. 최대 부하는 주 1회 4시간 동안 발생하며 평균의 2배이고, 나머지 시간은 평균 부하입니다. 읽기보다 쓰기가 많습니다. 테이블 비용을 최소화하려면?

**보기**
- A. **피크 기간엔 Application Auto Scaling**으로 용량을 늘리고, **평균 부하에 맞춰 예약 용량(Reserved RCU/WCU)을 구매**한다.
- B. 테이블을 온디맨드 용량 모드로 구성한다.
- C. DAX를 구성하고, 새로운 최대 부하에 맞춰 프로비저닝된 읽기 용량을 줄인다.
- D. DAX를 구성하고, 테이블을 온디맨드 용량 모드로 구성한다.

**정답: A**

**해설**
부하 패턴이 예측 가능(대부분 평균 부하 + 주 1회 짧은 피크)하므로, **예약 용량(Reserved Capacity)**으로 평균 부하 부분을 할인된 요금으로 확보하고, **Application Auto Scaling**으로 짧은 피크 기간만 용량을 늘리는 것이 가장 저렴합니다. 이는 온디맨드보다 대체로 저렴한 조합입니다.

**왜 다른 보기는 오답인가**
- B: 온디맨드 모드는 요청당 과금이라, 이렇게 예측 가능하고 지속적인 부하 패턴에는 예약 용량+Auto Scaling 조합보다 대체로 비용이 높습니다.
- C, D: **DAX는 읽기 전용 캐시**입니다. 이 문제는 "쓰기가 읽기보다 많다"는 조건이므로 DAX는 애초에 도움이 되지 않습니다.

> 💡 **시험 꿀팁**: 예측 가능한 기본 부하 + 주기적인 짧은 피크 패턴의 DynamoDB 워크로드에는 **예약 용량(기본 부하) + Application Auto Scaling(피크)** 조합이 온디맨드보다 저렴한 경우가 많습니다. DAX는 읽기 워크로드에만 효과가 있다는 점도 기억하세요.

## QUESTION 42

**문제**: 온프레미스 미디어 처리 앱을 마이그레이션합니다. 웹 서버가 파일을 NAS에 저장하고 메시지 큐로 처리 서버에 알립니다. 각 파일 처리는 최대 1시간까지 걸립니다. 대기 파일 수는 업무 시간에 훨씬 많고 그 외엔 급감합니다. 가장 비용 효율적인 마이그레이션은?

**보기**
- A. SQS + 대기열 메시지 시 **Lambda 함수**를 호출해 처리, S3에 저장
- B. Amazon MQ + 새 EC2 인스턴스를 그때그때 생성해 처리, EFS에 저장
- C. Amazon MQ + Lambda 함수로 처리, EFS에 저장
- D. **SQS** + **EC2 Auto Scaling 그룹**이 큐를 처리(**큐 길이 기반 확장**), **S3**에 저장

**정답: D**

**해설**
파일 처리에 **최대 1시간**이 걸릴 수 있는데, **Lambda의 최대 실행 시간은 15분**이라 A·C처럼 Lambda로 처리하는 방식은 애초에 기술적으로 불가능합니다. 단순 점대점 큐 용도에는 Amazon MQ보다 **SQS**가 더 간단하고 저렴하며, **SQS 큐 길이 기반으로 EC2 Auto Scaling 그룹을 확장**하면 업무 시간대의 급증한 부하와 이후의 급감을 자연스럽게 따라갈 수 있습니다.

**왜 다른 보기는 오답인가**
- A, C: 최대 1시간 걸리는 작업에 Lambda(최대 15분 제한)를 쓰는 것 자체가 기술적으로 불가능합니다.
- B: 기존 프로토콜 브로커 마이그레이션 등에 적합한 Amazon MQ는 이런 단순 큐 용도엔 SQS보다 비용·복잡도 면에서 불리하고, 큐 길이 기반 자동 확장이 아니라 수동으로 인스턴스를 생성하는 방식도 비효율적입니다.

> 💡 **시험 꿀팁**: 작업 처리 시간이 **15분을 넘을 가능성**이 있다면 Lambda는 애초에 후보에서 제외하세요(최대 실행 시간 제한). 단순 점대점 큐에는 Amazon MQ보다 **SQS**가 기본 선택지입니다.

## QUESTION 43

**문제**: OpenSearch Service 클러스터(데이터 노드 10개)가 S3 Standard에서 데이터를 로드합니다. 데이터는 읽기 전용 분석을 위해 클러스터에 1개월 머물고, 이후 인덱스가 삭제됩니다. 규정 준수를 위해 **모든 입력 데이터의 사본은 계속 보관**해야 합니다. 가장 비용 효율적인 솔루션은?

**보기**
- A. 모든 데이터 노드를 UltraWarm으로 교체, 데이터 로드 시 S3 Standard → **Glacier Deep Archive**로 즉시 전환
- B. **데이터 노드를 2개로 축소**, **UltraWarm 노드 추가**, 수집 시 UltraWarm으로 전환하도록 인덱스 구성, **S3 수명 주기 정책으로 1개월 후 Glacier Deep Archive로 전환**
- C. 데이터 노드를 2개로 축소, UltraWarm 추가, 콜드 스토리지 노드까지 추가, **1개월 후 S3에서 입력 데이터를 삭제**
- D. 데이터 노드를 2개로 축소, **인스턴스 지원 데이터 노드**를 추가, 데이터 로드 시 즉시 Glacier Deep Archive로 전환

**정답: B**

**해설**
**UltraWarm**은 자주 조회되지 않는 "웜" 데이터를 S3 기반으로 저렴하게 저장하는 OpenSearch Service 스토리지 계층으로, 비싼 핫 데이터 노드 수를 줄이면서도 1개월 분석 요구 사항을 충족할 수 있습니다. 규정 준수를 위해 **모든 입력 데이터는 삭제가 아니라 보관**해야 하므로, S3 수명 주기 정책으로 1개월 후 가장 저렴한 장기 보관 클래스인 **Glacier Deep Archive로 전환**해야 합니다.

**왜 다른 보기는 오답인가**
- A: 모든 노드를 UltraWarm으로 바꾸는 것은 신규 수집 데이터를 위한 핫 노드가 없어져 표준 아키텍처(핫+웜 혼합)에 맞지 않습니다.
- C: 콜드 스토리지까지 추가한 것은 과합니다. 결정적으로 **1개월 후 S3의 입력 데이터를 삭제**하는 것은 "모든 입력 데이터 사본 보관"이라는 규정 준수 요구 사항을 정면으로 위반합니다.
- D: UltraWarm 대신 **인스턴스 지원 데이터 노드**를 쓰면 웜/저빈도 조회 데이터에 대해 UltraWarm보다 비용이 훨씬 높습니다.

> 💡 **시험 꿀팁**: OpenSearch Service의 **UltraWarm**은 S3 기반의 저비용 "웜" 데이터 계층입니다. 규정 준수로 데이터를 영구 보관해야 한다면, **S3 수명 주기 정책으로 삭제가 아니라 Glacier Deep Archive로 전환**해야 한다는 점을 놓치지 마세요.

## QUESTION 44

**문제**: Organizations의 10개 계정(Prod/NonProd OU)마다 AWS Config가 구성되어 있고, 소스 `0.0.0.0/0`인 보안 그룹 인바운드 규칙이 생성되면 EventBridge → SNS로 알림을 보냅니다. NonProd OU의 모든 계정에서 보안팀은 **이런 규칙을 아예 만들 수 없도록** 만들어야 합니다. 최소 운영 오버헤드로는?

**보기**
- A. EventBridge 규칙을 수정해 Lambda가 규칙을 제거하고 SNS에 게시하도록 한다.
- B. NonProd OU에 `vpc-sg-open-only-to-authorized-ports` AWS Config 관리형 규칙을 추가한다.
- C. `aws:SourceIp`가 `0.0.0.0/0`이 **아닐 때** `ec2:AuthorizeSecurityGroupIngress`를 **허용**하는 SCP를 구성한다.
- D. **`aws:SourceIp`가 `0.0.0.0/0`일 때 `ec2:AuthorizeSecurityGroupIngress`를 거부하는 SCP**를 NonProd OU에 적용한다.

**정답: D**

**해설**
"아예 만들 수 없도록"이라는 것은 **사전 예방(preventive) 통제**를 의미합니다. 기존의 EventBridge+SNS 알림이나 AWS Config 규칙(B)은 문제가 생긴 **뒤에** 감지하는 **사후(detective) 통제**일 뿐입니다. 특정 위험한 작업 패턴을 원천 차단하려면 **조건(Condition) 키를 포함한 명시적 Deny SCP**가 정답입니다.

**왜 다른 보기는 오답인가**
- A: 생성된 후 Lambda로 제거하는 방식이라 여전히 사후 대응(감지→제거)이며, 그 사이의 취약 시간이 존재합니다.
- B: AWS Config 관리형 규칙은 기본적으로 **감지** 기능이며, 자동 교정을 붙이더라도 SCP만큼 즉각적인 사전 차단은 아닙니다.
- C: "허용" SCP 방식으로 우회 조건을 표현하는 것은 SCP의 동작 방식(32번 문제 참고)과 맞지 않으며, 원하는 위험 패턴을 직접적으로 차단하는 명시적 Deny(D)만큼 확실하지 않습니다.

> 💡 **시험 꿀팁**: 어떤 작업을 조직/OU 차원에서 **진짜로 막고 싶다면** (사후 감지가 아니라) **조건 키를 포함한 명시적 Deny SCP**를 사용하세요. EventBridge/Lambda 교정이나 Config 규칙은 이미 일어난 일을 감지·교정하는 사후 통제일 뿐입니다.

## QUESTION 45

**문제**: 온프레미스 Git 저장소가 웹훅으로 AWS의 함수를 호출합니다. 현재는 ALB 뒤 Auto Scaling 그룹의 EC2에서 웹훅 로직을 실행합니다. 서버리스로 전환하고 싶고, 최소 운영 오버헤드가 필요합니다.

**보기**
- A. 웹훅마다 개별 **Lambda 함수 URL**을 생성해 Git 서버가 각각을 호출하도록 한다.
- B. **API Gateway HTTP API**를 생성하고, 각 웹훅 로직을 **별도의 Lambda 함수**로 구현한다. Git 서버가 API Gateway 엔드포인트를 호출하게 한다.
- C. 웹훅 로직을 AWS App Runner에 배포하고 앞에 ALB를 둔다.
- D. 웹훅 로직을 컨테이너화해 ECS Fargate에서 실행하고, API Gateway REST API로 연결한다.

**정답: B**

**해설**
**API Gateway HTTP API**(REST API의 고급 기능이 필요 없다면 더 저렴·간단) 뒤에 웹훅마다 별도의 **Lambda 함수**를 두는 조합이, 흩어진 개별 함수 URL을 관리하는 것보다 훨씬 중앙집중적이고 관리하기 쉬우며, 컨테이너 기반 방식보다 운영 부담이 훨씬 적습니다.

**왜 다른 보기는 오답인가**
- A: 웹훅이 늘어날수록 개별 함수 URL을 각각 관리해야 해, 하나의 API Gateway로 통합 관리하는 것보다 확장성이 떨어집니다.
- C: App Runner + ALB는 컨테이너 기반이라 완전한 서버리스(이벤트 기반 Lambda)만큼 가볍지 않고 인프라(ALB)도 추가로 필요합니다.
- D: 컨테이너화 + ECS Fargate + REST API는 이미지 빌드, ECS 서비스 관리 등 운영 부담이 훨씬 큽니다.

> 💡 **시험 꿀팁**: EC2/ALB 기반 웹훅 처리를 저운영 서버리스로 전환할 때는 **API Gateway(HTTP API) + 웹훅별 Lambda 함수** 조합이 표준입니다. 흩어진 Lambda 함수 URL이나 컨테이너 기반(App Runner/ECS)보다 운영 부담이 적습니다.

## QUESTION 46

**문제**: 1,000대의 온프레미스 서버(VMware 클러스터)를 마이그레이션합니다. CPU 세부정보, RAM 사용량, OS 정보, **실행 중인 프로세스** 등을 수집한 뒤 쿼리·분석해야 합니다.

**보기**
- A. **에이전트리스(Agentless) Discovery Connector** 배포 + Migration Hub + AWS Glue ETL + S3 Select로 쿼리
- B. VM 성능 정보만 수동 내보내기 + Migration Hub 수동 업데이트 + QuickSight로 쿼리
- C. 커스텀 스크립트 + `put-resource-attributes` CLI로 Migration Hub에 수동 저장 + 콘솔에서 직접 쿼리
- D. **각 서버에 AWS Application Discovery Agent 배포** + Migration Hub에서 데이터 탐색 구성 + **Amazon Athena로 S3 데이터에 사전 정의된 쿼리 실행**

**정답: D**

**해설**
**실행 중인 프로세스**까지 수집해야 한다는 조건이 핵심입니다. **에이전트리스** 방식(vCenter API 기반, VM 외부에서 수집)은 게스트 OS 내부의 프로세스 정보를 볼 수 없어 이 요구 사항을 만족하지 못합니다. 반드시 **각 서버에 설치하는 Application Discovery Agent**(에이전트 기반)를 써야 하며, 수집된 데이터는 Migration Hub를 거쳐 S3에 저장되고 **Amazon Athena**로 서버리스 SQL 쿼리·분석이 가능합니다.

**왜 다른 보기는 오답인가**
- A: 에이전트리스 커넥터는 게스트 내부의 프로세스 정보를 수집할 수 없어 요구 사항 자체를 만족하지 못합니다.
- B, C: 수동으로 정보를 내보내거나 CLI로 직접 데이터를 밀어넣는 방식은 자동화된 에이전트 기반 수집만큼 완전하지도 효율적이지도 않습니다.

> 💡 **시험 꿀팁**: **실행 중인 프로세스**처럼 게스트 OS 내부의 상세 정보가 필요하면 반드시 (에이전트리스가 아닌) **에이전트 기반 Application Discovery Agent**를 사용해야 합니다. 수집된 데이터는 보통 **Amazon Athena**로 S3에서 바로 쿼리합니다.

## QUESTION 47

**문제**: VPC에 연결된 Lambda 함수로 구성된 서버리스 앱이 외부 공급자의 신규 서비스와 통합해야 합니다. 외부 공급자는 허용 목록에 등록된 **퍼블릭 IPv4 주소**에서 오는 요청만 지원하며, 회사는 **단일 공인 IP**를 사전에 제공해야 합니다.

**보기**
- A. **NAT 게이트웨이를 배포**하고 **탄력적 IP를 연결**한 뒤, VPC가 이 NAT 게이트웨이를 사용하도록 구성한다.
- B. "외부 전용 인터넷 게이트웨이(Egress-only IGW)"에 탄력적 IP를 연결한다.
- C. 인터넷 게이트웨이에 탄력적 IP를 연결하고 Lambda 함수가 이 IGW를 사용하도록 구성한다.
- D. 인터넷 게이트웨이 + 탄력적 IP + 퍼블릭 라우팅 테이블의 기본 경로 구성

**정답: A**

**해설**

- A, E: 이는 "소스 계정이 밀어넣는(push)" 방향의 대안 조합에 해당하는 요소들로, 이 문제에서 정답으로 제시된 "대상이 끌어오는" 방향(B/D/F)과 섞어 쓸 수 없습니다.
- C: 소스 계정에서 IAM 정책을 만드는 것도 "push" 방향에 속하는 요소라, "pull" 방향인 정답 조합과 일치하지 않습니다.

> 💡 **시험 꿀팁**: 교차 계정 S3 복사는 **"대상이 끌어오기"**(대상 계정 IAM 정책 + 소스 버킷 정책으로 읽기 허용 + 대상 계정에서 sync 실행) 또는 **"소스가 밀어넣기"**(반대 방향) 중 **한 방향으로 일관되게** 구성해야 합니다. 두 방향의 요소를 섞으면 안 됩니다.

## QUESTION 60

**문제**: CloudFormation으로 배포된 Lambda 기반 앱이 있습니다. 최근 프로덕션 릴리스에서 몇 분간 중단이 발생했습니다. **카나리 릴리스**를 지원하도록 배포 프로세스를 조정하려면?

**보기**
- A. 새로 배포되는 Lambda 함수 버전마다 **별칭(Alias)을 생성**하고, **AWS CLI `update-alias` 명령의 라우팅 구성 파라미터**로 트래픽을 분산한다.
- B. 새 CloudFormation 스택에 앱을 배포하고 Route 53 가중 라우팅으로 분산한다.
- C. 새로 배포된 함수마다 버전을 생성하고, `update-function-configuration` 명령의 라우팅 구성 파라미터로 분산한다.
- D. AWS CodeDeploy를 구성하고 `CodeDeployDefault.OneAtATime` 배포 구성으로 분산한다.

**정답: A**

**해설**
Lambda의 네이티브 카나리 배포 메커니즘은 **Lambda 별칭(Alias) + 가중 라우팅 구성**입니다. `update-alias` CLI 명령에 라우팅 구성 파라미터를 지정하면 새 버전과 기존 버전 간에 트래픽 비율을 점진적으로 조정할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 스택 전체를 새로 배포하고 DNS로 분산하는 것은 단순한 Lambda 버전 트래픽 전환에 비해 훨씬 무겁고 복잡한 방식입니다.
- C: `update-function-configuration`은 함수의 **설정값**(메모리, 타임아웃 등)을 바꾸는 명령이며, 트래픽 라우팅을 위한 파라미터는 없습니다. 이 명령에는 그런 기능이 존재하지 않습니다.
- D: `CodeDeployDefault.OneAtATime`은 **EC2/온프레미스** 배포용 구성(인스턴스를 하나씩 순차 배포)이지, Lambda의 카나리 배포 구성(예: `LambdaCanary10Percent5Minutes`)이 아닙니다.

> 💡 **시험 꿀팁**: Lambda의 네이티브 카나리 배포는 **별칭(Alias) + 가중 라우팅 구성**(`update-alias --routing-config` 또는 SAM+CodeDeploy의 `LambdaCanary*`/`LambdaLinear*` 구성)으로 이루어집니다. `OneAtATime`은 EC2용 개념이고, `update-function-configuration`은 설정 변경용이라는 점을 헷갈리지 마세요.
