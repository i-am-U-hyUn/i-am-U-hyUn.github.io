## QUESTION 1

**문제**: 회사는 여러 대륙에 걸쳐 도시의 온도, 습도 및 대기압에 대한 데이터를 수집한다. 회사가 매일 각 사이트에서 수집하는 데이터의 평균 볼륨은 500GB이며, 각 사이트에는 고속 인터넷 연결이 있다. 이 회사는 이러한 모든 글로벌 사이트의 데이터를 단일 Amazon S3 버킷에 최대한 빨리 집계하려고 하며, 솔루션은 운영 복잡성을 최소화해야 한다. 어떤 솔루션이 이러한 요구 사항을 충족하는가?

**보기**
- A. **대상 S3 버킷에서 S3 Transfer Acceleration을 켜고, 멀티파트 업로드를 사용하여 사이트 데이터를 대상 S3 버킷에 직접 업로드한다.**
- B. 각 사이트의 데이터를 가장 가까운 리전의 S3 버킷에 업로드한 뒤 S3 교차 리전 복제로 대상 버킷에 객체를 복사(중간 버킷과 복제 지연이 추가되어 "최대한 빨리"라는 요구와 운영 단순성 모두에 불리).
- C. AWS Snowball Edge를 매일 예약해 데이터를 전송(오프라인 물리 배송 방식은 매일 반복하기에는 리드타임이 크고, 이미 고속 인터넷이 있는 상황에는 과도한 방식).
- D. EC2 인스턴스와 EBS 볼륨에 저장 후 스냅샷을 리전 간 복사해 복원(스냅샷 복사/복원 절차가 다단계이고 지연이 커서 신속성 요구에 부합하지 않음).

**정답: A**

**해설**
**S3 Transfer Acceleration**은 클라이언트와 S3 버킷 사이의 업로드 경로를 CloudFront의 엣지 로케이션과 AWS의 최적화된 백본 네트워크로 우회시켜 장거리 대용량 업로드 속도를 크게 높여줍니다. 이미 각 사이트에 고속 인터넷이 있는 상황에서 **멀티파트 업로드**와 결합하면 별도의 중계 인프라 없이 각 사이트에서 대상 버킷으로 직접, 빠르고 운영이 단순한 방식으로 데이터를 집계할 수 있습니다.

**왜 다른 보기는 오답인가**
- B: 리전별 중간 버킷 업로드 후 교차 리전 복제 및 원본 삭제까지 거치는 다단계 파이프라인은 운영 복잡성을 오히려 높이고 지연도 늘어납니다.
- C: Snowball Edge는 네트워크 대역폭이 부족한 오프라인 대량 이전에 적합하며, 매일 반복되는 실시간에 가까운 집계 요구에는 맞지 않습니다.
- D: EBS 스냅샷 생성-복사-복원의 다단계 프로세스는 매일 반복하기에 운영 부담이 크고 신속성도 떨어집니다.

> 💡 **시험 꿀팁**: 여러 글로벌 사이트에서 **하나의 S3 버킷으로 빠르게 업로드**해야 한다는 조건이 나오면 **S3 Transfer Acceleration + 멀티파트 업로드**가 표준 정답입니다.

## QUESTION 2

**문제**: 회사는 Amazon S3 버킷에 JSON 형식으로 저장된 독점 애플리케이션 로그를 분석해야 한다. 쿼리는 간단하고 주문형(ad-hoc)으로 실행되며, 솔루션 설계자는 기존 아키텍처에 대한 최소한의 변경과 최소한의 운영 오버헤드로 이 요구 사항을 충족해야 한다.

**보기**
- A. Amazon Redshift로 모든 콘텐츠를 한 곳에 로드하고 SQL 쿼리를 실행(데이터 웨어하우스 클러스터 프로비저닝과 ETL이 필요해 최소 변경/최소 오버헤드 요구에 과도함).
- B. Amazon CloudWatch Logs에 로그를 저장하고 콘솔에서 SQL 쿼리 실행(CloudWatch Logs Insights는 로그 쿼리용이며 S3에 이미 있는 JSON 객체에 대한 표준 SQL 분석 용도로는 적합하지 않음).
- C. **Amazon S3와 함께 Amazon Athena를 직접 사용하여 필요에 따라 쿼리를 실행한다.**
- D. AWS Glue로 로그를 분류하고 Amazon EMR의 임시 Spark 클러스터로 SQL 쿼리 실행(클러스터 프로비저닝과 운영 부담이 커서 간단한 주문형 쿼리에는 과도함).

**정답: C**

**해설**
**Amazon Athena**는 S3에 저장된 데이터에 대해 서버나 인프라 프로비저닝 없이 표준 SQL로 바로 쿼리할 수 있는 서버리스 대화형 쿼리 서비스입니다. JSON으로 저장된 로그도 Athena의 JSON 관련 함수로 파싱할 수 있어, 기존 아키텍처를 바꾸지 않고 S3 위에 Athena만 얹으면 간단한 주문형 쿼리 요구를 최소 오버헤드로 충족할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Redshift는 클러스터 운영이 필요한 데이터 웨어하우스로, 간단한 주문형 쿼리에는 오버헤드가 큽니다.
- B: CloudWatch Logs Insights는 CloudWatch에 수집된 로그 전용이며, S3에 있는 JSON 객체를 표준 SQL로 분석하는 목적에는 맞지 않습니다.
- D: Glue + EMR/Spark 조합은 대규모 ETL/배치 처리에 적합하지만 간단한 쿼리 요구에는 구성과 운영 부담이 지나칩니다.

> 💡 **시험 꿀팁**: **S3에 있는 데이터를 서버 없이 SQL로 바로 조회**하고 싶다는 요구에는 거의 항상 **Amazon Athena**가 정답입니다.

## QUESTION 3

**문제**: 회사는 AWS Organizations로 여러 부서의 여러 AWS 계정을 관리한다. 관리 계정에는 프로젝트 보고서가 담긴 S3 버킷이 있으며, 이 버킷에 대한 접근을 조직 내 계정 사용자로만 최소한의 운영 오버헤드로 제한하려고 한다.

**보기**
- A. **조직 ID를 참조하는 `aws:PrincipalOrgID` 전역 조건 키를 S3 버킷 정책에 추가한다.**
- B. 부서별 OU를 만들고 `aws:PrincipalOrgPaths` 조건 키를 사용(OU 경로 단위 제어가 필요할 때 유효하지만, 이 문제는 조직 전체 사용자만 허용하면 되므로 OU를 별도로 설계하는 것은 불필요한 복잡성 추가).
- C. CloudTrail로 계정 생성/초대/탈퇴 이벤트를 모니터링하고 그때마다 버킷 정책을 수동 업데이트(이벤트 기록 도구일 뿐이며 수동 갱신은 운영 오버헤드가 큼).
- D. 접근이 필요한 각 사용자에 태그를 지정하고 `aws:PrincipalTag` 조건 키를 사용(사용자마다 개별 태깅이 필요해 최소 운영 오버헤드 조건에 위배).

**정답: A**

**해설**
**`aws:PrincipalOrgID`** 전역 조건 키를 사용하면 조직의 모든 계정 ID를 일일이 나열하지 않고도, 요청자가 지정한 AWS Organizations 조직에 속한 IAM 주체인지 한 번의 조건으로 검증할 수 있습니다. 버킷 정책에 이 조건 키 하나만 추가하면 되므로 신규 계정이 추가되어도 정책을 갱신할 필요가 없어 운영 오버헤드가 가장 낮습니다.

**왜 다른 보기는 오답인가**
- B: `PrincipalOrgPaths`는 특정 OU 경로 단위로 세밀하게 제어할 때 유용하지만, 조직 구성원 전체를 허용하면 되는 이 요구에는 OU 설계라는 불필요한 단계가 추가됩니다.
- C: CloudTrail은 감사 로그 기록 서비스로, 조건에 따라 자동으로 접근을 제어하는 기능이 없어 수동 정책 갱신이 반복적으로 필요합니다.
- D: 사용자별 태그 부착과 유지 관리는 사용자 수가 늘어날수록 운영 부담이 커집니다.

> 💡 **시험 꿀팁**: **"조직 내 모든 계정 사용자에게만" + "최소 운영 오버헤드"** 조합이 나오면 **`aws:PrincipalOrgID`** 전역 조건 키가 표준 정답입니다.

## QUESTION 4

**문제**: VPC의 EC2 인스턴스에서 실행되는 애플리케이션이 S3 버킷에 저장된 로그를 처리한다. EC2 인스턴스는 인터넷 연결 없이 S3 버킷에 접근해야 한다. Amazon S3에 대한 프라이빗 네트워크 연결을 제공하는 솔루션은?

**보기**
- A. **S3 버킷에 대한 게이트웨이 VPC 엔드포인트를 생성한다.**
- B. CloudWatch Logs로 로그를 스트리밍하고 S3로 내보낸다(요구 사항인 "S3에 대한 프라이빗 연결 자체"를 제공하지 않으며 우회적인 방법).
- C. EC2에 인스턴스 프로파일을 생성해 S3 액세스를 허용(권한 부여 방법일 뿐 네트워크 경로 문제는 해결하지 못함).
- D. S3 엔드포인트 접근용 프라이빗 링크가 있는 API Gateway API 생성(불필요하게 복잡하며 S3 직접 접근을 위한 표준 방법이 아님).

**정답: A**

**해설**
**S3용 게이트웨이 VPC 엔드포인트**는 VPC 라우팅 테이블에 S3 프리픽스 목록을 대상으로 하는 경로를 추가해, 인터넷 게이트웨이나 NAT 없이도 AWS 네트워크 내부 경로로 S3에 직접 접근할 수 있게 해줍니다. 추가 비용 없이 프라이빗 연결을 제공하는 가장 단순한 표준 방법입니다.

**왜 다른 보기는 오답인가**
- B: 로그를 CloudWatch로 보내는 것은 S3 접근 경로 문제와 무관한 별개의 흐름입니다.
- C: 인스턴스 프로파일은 IAM 권한을 부여할 뿐이며, 네트워크 상으로 인터넷을 거치지 않는 경로를 제공하지는 않습니다.
- D: API Gateway 프라이빗 링크는 S3 접근을 위한 표준 경로가 아니며 불필요하게 복잡합니다.

> 💡 **시험 꿀팁**: **인터넷 없이 프라이빗 서브넷에서 S3에 접근**해야 한다면 **게이트웨이 VPC 엔드포인트**가 표준 정답입니다.

## QUESTION 5

**문제**: 회사는 사용자 업로드 문서를 EBS 볼륨에 저장하는 단일 EC2 인스턴스로 웹 애플리케이션을 운영하다가, 확장성과 가용성을 위해 다른 가용 영역에 두 번째 EC2 인스턴스와 EBS 볼륨을 추가해 ALB 뒤에 배치했다. 그 결과 사용자가 새로고침할 때마다 문서의 일부만 보이고 전체를 한 번에 볼 수 없는 문제가 발생했다. 모든 문서를 한 번에 볼 수 있게 하려면?

**보기**
- A. 두 EBS 볼륨에 모든 문서가 포함되도록 데이터를 복사(일회성 동기화일 뿐 이후 신규 업로드마다 다시 어긋나는 근본적이지 않은 해결책).
- B. 문서가 있는 서버로 사용자를 안내하도록 ALB 구성(ALB는 특정 문서 위치를 인식해 라우팅하는 기능을 기본 제공하지 않음).
- C. **두 EBS 볼륨의 데이터를 Amazon EFS로 옮기고, 새 문서도 EFS에 저장하도록 애플리케이션을 수정한다.**
- D. 두 서버 모두에 요청을 보내 올바른 서버에서 문서를 반환하도록 ALB 구성(ALB의 표준 라우팅 기능이 아니며 구현이 사실상 불가능에 가까움).

**정답: C**

**해설**
문제의 근본 원인은 **EBS가 단일 AZ에서만 접근 가능한 블록 스토리지**라서 두 인스턴스가 저장소를 공유하지 못하는 데 있습니다. **Amazon EFS**는 다중 AZ에서 여러 EC2 인스턴스가 동시에 마운트해 공유할 수 있는 NFS 기반 파일 스토리지이므로, 기존 데이터를 EFS로 옮기고 이후 저장 위치를 EFS로 통일하면 어떤 인스턴스로 요청이 가더라도 모든 문서에 접근할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: 이후에도 각 서버에 독립적으로 신규 업로드가 발생하면 다시 불일치가 생기는 임시방편입니다.
- B: ALB는 문서 존재 위치 기반 라우팅 기능을 제공하지 않습니다.
- D: 두 서버 모두에 요청을 보내 올바른 응답만 취사선택하는 구성은 ALB의 표준 기능이 아니며 비현실적입니다.

> 💡 **시험 꿀팁**: **여러 AZ의 EC2가 동일한 파일을 공유**해야 하는 문제에는 **Amazon EFS**가 표준 정답입니다(EBS는 단일 AZ 전용이라는 점을 기억하세요).

## QUESTION 6

**문제**: 회사는 NFS로 온프레미스 NAS에 대용량 비디오 파일(1MB~500GB, 총 70TB, 더 이상 증가 없음)을 저장하고 있으며 Amazon S3로 마이그레이션하려 한다. 가능한 한 최소한의 네트워크 대역폭을 사용하면서 최대한 빨리 마이그레이션해야 한다.

**보기**
- A. S3 버킷 생성 후 AWS CLI로 모든 파일을 네트워크로 직접 복사(네트워크 대역폭을 그대로 사용하므로 "최소한의 대역폭" 요구에 위배).
- B. **AWS Snowball Edge 작업을 생성해 디바이스로 오프라인 전송한 뒤 AWS로 반송해 S3로 가져온다.**
- C. 온프레미스에 S3 파일 게이트웨이를 배포하고 퍼블릭 엔드포인트로 연결(네트워크를 통한 전송이라 대역폭을 계속 소비하며, 70TB 규모의 1회성 이전에는 비효율적).
- D. Direct Connect를 새로 구축하고 S3 파일 게이트웨이 사용(신규 전용선 구축 자체가 시간과 비용이 크고, 네트워크 경유라는 점도 동일).
- (참고) 총 데이터가 70TB로 Snowball Edge(최대 약 80~100TB) 한 대로 처리 가능한 규모입니다.

**정답: B**

**해설**
**AWS Snowball Edge**는 네트워크 대역폭을 전혀 사용하지 않고 물리 디바이스로 대용량 데이터를 오프라인 이동시키는 서비스입니다. 총 70TB, 개별 파일 최대 500GB 규모는 Snowball Edge 한 대의 용량 범위 내에 들어오며, 이후 데이터가 더 늘어나지 않는 일회성 이전이라는 조건과도 맞아, "최소 대역폭 + 최대한 빠른 이전"이라는 상충되어 보이는 두 요구를 동시에 만족시키는 표준 솔루션입니다.

**왜 다른 보기는 오답인가**
- A: 네트워크를 통한 직접 복사는 대역폭을 그대로 소비하여 조건에 위배됩니다.
- C, D: S3 파일 게이트웨이는 지속적인 하이브리드 접근에는 유용하지만, 네트워크 경유 전송이라는 점에서 최소 대역폭 조건을 만족하지 못하며, 이번처럼 더 이상 늘어나지 않는 데이터의 일회성 대량 이전에는 Snowball Edge가 더 적합합니다.

> 💡 **시험 꿀팁**: **네트워크 대역폭을 쓰지 않고 대용량 데이터를 한 번에 옮기고 싶다**는 조건에는 **AWS Snowball(Edge)**가 표준 정답입니다.

> 💡 **시험 꿀팁**: **기존 SMB/NFS 접근 방식을 유지하며 온프레미스 저장 공간을 S3로 확장**하려면 **S3 파일 게이트웨이 + 수명 주기 정책**이 표준 정답입니다.

- D. 정적/동적 콘텐츠마다 별도 도메인과 별도 서비스(CloudFront/Global Accelerator)를 사용(단일 도메인으로 통합 가능한 것을 굳이 이원화해 운영 복잡성 증가).

**정답: A**

**해설**
**Amazon CloudFront**는 S3(정적)와 ALB(동적)를 모두 오리진으로 지정할 수 있는 CDN으로, 정적 콘텐츠는 엣지에서 캐싱하고 동적 콘텐츠 요청은 오리진(ALB)으로 최적화된 경로를 통해 전달합니다. Route 53에서 사용자 도메인을 CloudFront 배포로 연결하면 하나의 배포와 하나의 도메인으로 정적/동적 콘텐츠 모두의 성능을 개선하고 지연을 줄일 수 있습니다.

**왜 다른 보기는 오답인가**
- B, C: Global Accelerator는 TCP/UDP 기반의 비-HTTP 워크로드나 다중 리전 장애 조치에 강점이 있는 서비스로, 이미 CloudFront로 처리 가능한 이 HTTP 시나리오에 추가하는 것은 불필요한 복잡성입니다.
- D: 정적/동적을 굳이 별도 도메인으로 분리할 필요 없이 CloudFront 하나로 통합 가능하며, 이원화는 운영 복잡성만 늘립니다.

> 💡 **시험 꿀팁**: **S3(정적) + ALB(동적)를 하나의 도메인으로 빠르게 서비스**하려면 **CloudFront가 두 오리진을 모두 포함**하는 구성이 표준 정답입니다.

- A. **SQS 대기열을 생성하고, 이미지가 S3에 업로드될 때 SQS로 알림을 보내도록 S3 버킷을 구성한다.**
- B. **SQS 대기열을 Lambda 함수의 호출 소스로 사용하도록 구성하고, 메시지가 성공적으로 처리되면 대기열에서 삭제한다.**
- C. Lambda가 새 업로드를 위해 S3를 직접 모니터링하고, 메모리 내 텍스트 파일에 처리 여부를 기록(Lambda는 상태를 메모리에 유지할 수 없고 실행 간 보장도 없어 내구성/상태 비저장 요구 위반).
- D. EC2 인스턴스를 띄워 SQS를 모니터링하고 텍스트 파일에 기록 후 Lambda 호출(EC2 상시 운영이 필요해 서버리스·상태 비저장이라는 목표에 부합하지 않고 불필요한 인프라 추가).
- E. EventBridge로 S3를 모니터링하고 업로드 시 이메일과 함께 SNS 주제에 알림(사람의 개입을 전제로 한 알림 흐름이라 완전 자동화된 이미지 처리 파이프라인에 부합하지 않음).

**정답: A, B**

**해설**
**S3 이벤트 알림 → SQS → Lambda** 조합은 각 단계가 독립적으로 내구성 있게 동작하는 서버리스 파이프라인입니다. 이미지가 업로드되면 S3가 자동으로 SQS에 메시지를 보내고(A), Lambda가 이 SQS를 호출 소스로 사용해 메시지를 처리한 뒤 성공 시에만 큐에서 삭제합니다(B). 이 구조는 상태를 어디에도 별도로 저장할 필요 없이(상태 비저장) 처리 실패 시에도 메시지가 큐에 남아 재처리가 가능한 내구성을 확보합니다.

**왜 다른 보기는 오답인가**
- C: Lambda의 메모리는 실행 간 지속이 보장되지 않아 처리 여부 추적을 메모리에 의존하면 데이터가 유실될 수 있습니다.
- D: 상시 EC2 인스턴스가 필요해 서버리스·상태 비저장 아키텍처라는 목표와 맞지 않습니다.
- E: 이메일 알림 기반 흐름은 사람의 수동 처리를 전제로 해 완전 자동화된 이미지 압축 파이프라인에 부합하지 않습니다.

> 💡 **시험 꿀팁**: **S3 업로드를 트리거로 한 서버리스 자동 처리**에는 **S3 이벤트 → SQS → Lambda**(또는 직접 S3 → Lambda) 패턴이 표준 정답입니다.

## QUESTION 19

**문제**: 3계층 웹 애플리케이션에서 웹 서버는 퍼블릭 서브넷에, 애플리케이션/DB 서버는 프라이빗 서브넷에 있다. 검사 VPC에 배포한 AWS Marketplace의 타사 가상 방화벽 어플라이언스로, 트래픽이 웹 서버에 도달하기 전에 모든 트래픽을 검사하도록 최소 운영 오버헤드로 통합하려면?

**보기**
- A. 퍼블릭 서브넷에 NLB를 만들어 어플라이언스로 트래픽 라우팅(NLB만으로는 여러 AZ의 어플라이언스로 트래픽을 대칭적으로 안전하게 왕복시키는 구조를 표준적으로 제공하지 않음).
- B. 퍼블릭 서브넷에 ALB를 만들어 어플라이언스로 라우팅(ALB는 HTTP/HTTPS 계층 로드밸런서로, IP 패킷 단위의 어플라이언스 트래픽 검사 통합에는 적합하지 않음).
- C. 검사 VPC에 Transit Gateway를 배포하고 라우팅 테이블로 패킷을 흘려보냄(구성이 가능은 하지만 Gateway Load Balancer만큼 어플라이언스 확장·상태 유지 연동에 최적화되어 있지 않아 운영 오버헤드가 더 큼).
- D. **검사 VPC에 Gateway Load Balancer를 배포하고, Gateway Load Balancer 엔드포인트로 수신 패킷을 받아 어플라이언스로 전달한다.**

**정답: D**

**해설**
**Gateway Load Balancer(GWLB)**는 방화벽, 침입 탐지/방지 시스템 같은 타사 가상 어플라이언스를 투명하게 트래픽 경로에 끼워 넣기 위해 설계된 서비스입니다. **GWLB 엔드포인트**를 애플리케이션 VPC에 배치하면 웹 서버로 향하는 모든 트래픽이 먼저 이 엔드포인트를 거쳐 검사 VPC의 어플라이언스로 전달되고, 검사 후 다시 원래 경로로 돌아갑니다. 어플라이언스의 확장, 상태 유지, 다중 AZ 구성을 GWLB가 대신 관리해주므로 운영 오버헤드가 가장 낮습니다.

**왜 다른 보기는 오답인가**
- A, B: NLB/ALB는 각각 전통적인 4계층/7계층 로드밸런싱에 최적화되어 있으며, IP 패킷을 어플라이언스에 투명하게 왕복시키는 인라인 검사 아키텍처를 표준적으로 지원하지 않습니다.
- C: Transit Gateway로 라우팅을 구성하는 것도 가능하지만, 어플라이언스의 확장성과 상태 유지까지 고려하면 Gateway Load Balancer 전용 설계보다 운영 부담이 큽니다.

> 💡 **시험 꿀팁**: **타사 가상 방화벽/IDS 어플라이언스를 트래픽 경로에 투명하게 삽입**해야 한다면 **Gateway Load Balancer(+ GWLB 엔드포인트)**가 표준 정답입니다.

## QUESTION 20

**문제**: 회사가 동일 리전의 테스트 환경으로 대량의 프로덕션 데이터(EBS에 저장)를 복제하는 기능을 개선하려 한다. 복제된 데이터를 수정해도 프로덕션에 영향이 없어야 하고, 데이터에 접근하는 소프트웨어는 일관되게 높은 I/O 성능을 요구하며, 복제에 필요한 시간을 최소화해야 한다.

**보기**
- A. 프로덕션 EBS 스냅샷을 만들어 테스트 환경 EC2의 **인스턴스 스토어 볼륨**에 복원(인스턴스 스토어는 휘발성이라 인스턴스 중지/종료 시 데이터가 소실되어 내구성 요구에 부적합).
- B. 프로덕션 EBS에 **다중 연결(Multi-Attach)**을 활성화하고 스냅샷을 만든 뒤, 테스트 환경 EC2에 프로덕션 EBS 볼륨을 직접 연결(다중 연결은 동일 볼륨을 공유하는 것이라 테스트 환경에서의 수정이 프로덕션에 직접 영향을 줘 요구 사항에 위배).
- C. 프로덕션 EBS 스냅샷을 만들고 새 EBS 볼륨을 생성·초기화한 뒤 그 볼륨에 스냅샷을 복원(초기화한 빈 볼륨에 스냅샷을 복원하는 순서가 잘못되었으며, 초기 읽기 시 지연이 발생하는 지연 초기화 문제도 그대로 남음).
- D. **프로덕션 EBS 스냅샷을 만들고, EBS 빠른 스냅샷 복원(Fast Snapshot Restore)을 켠 뒤 새 EBS 볼륨으로 복원해 테스트 환경 EC2에 연결한다.**

**정답: D**

**해설**
**EBS 빠른 스냅샷 복원(FSR)**을 활성화하면 스냅샷에서 새 볼륨을 생성할 때 발생하는 초기 지연 초기화(lazy loading) 문제 없이, 처음부터 볼륨의 최대 성능(IOPS/처리량)을 즉시 사용할 수 있습니다. 스냅샷은 프로덕션 볼륨과 완전히 분리된 새 볼륨을 만드는 것이므로 테스트 환경에서의 수정이 프로덕션에 영향을 주지 않으면서도, 복제 소요 시간과 초기 I/O 성능 저하 문제를 동시에 해결합니다.

**왜 다른 보기는 오답인가**
- A: 인스턴스 스토어는 휘발성 스토리지로 인스턴스 중지 시 데이터가 사라져 내구성 요구를 충족하지 못합니다.
- B: EBS 다중 연결로 같은 볼륨을 공유하면 테스트 환경의 수정이 곧바로 프로덕션에 반영되어 격리 요구에 정면으로 위배됩니다.
- C: 새 볼륨을 초기화한 뒤 나중에 스냅샷을 복원하는 순서 자체가 부적절하며, 빠른 스냅샷 복원 없이는 초기 성능 저하 문제도 해결되지 않습니다.

> 💡 **시험 꿀팁**: **스냅샷에서 복원한 새 볼륨이 처음부터 최대 성능**을 내야 한다면 **EBS 빠른 스냅샷 복원(Fast Snapshot Restore)**이 표준 정답입니다.
