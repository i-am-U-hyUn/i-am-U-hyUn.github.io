## QUESTION 201

**Question**: An Aurora MySQL application (mostly INSERT operations) experiences connection overload. Credentials are currently stored in a text-based configuration file. Design a solution that handles the current connection load while keeping credentials secure and automatically rotating them regularly.

**Choices**
- A. **Deploy an Amazon RDS Proxy layer in front of the DB instance. Store connection credentials as a secret in AWS Secrets Manager.**
- B. Deploy RDS Proxy + store in Parameter Store (Parameter Store lacks the integrated automatic rotation Secrets Manager provides).
- C. Create an Aurora replica + Secrets Manager (replicas are for scaling reads, unrelated to solving connection overload for this mostly-INSERT workload).
- D. Aurora replica + Parameter Store (also unrelated to the write-connection problem, and lacks automatic rotation).

**Correct Answer: A**

**Explanation**
**RDS Proxy** significantly reduces the number of connections to the database via connection pooling, solving the connection overload problem, while **AWS Secrets Manager** securely stores database credentials and natively supports **automatic rotation.** This combination is the standard solution satisfying both requirements.

**Why the other choices are wrong**
- B: Parameter Store can also store securely, but doesn't offer as integrated an automatic rotation feature as Secrets Manager.
- C, D: Aurora replicas are for distributing read workloads and don't solve the connection overload problem for a mostly-**write (INSERT)** workload like this one.

> 💡 **Exam tip**: For **database connection overload**, use **RDS Proxy** (connection pooling); for **secure credential storage + automatic rotation**, use **Secrets Manager** — the standard combination. Aurora replicas scale reads, not a fix for connection count issues.

## QUESTION 202

**Question**: A DR solution for an e-commerce site (t3.large EC2, multi-AZ Auto Scaling, RDS MySQL) with **RPO 30 seconds, RTO 10 minutes**, failing over to a secondary environment. Most cost-effective solution?

**Choices**
- A. Provision DR-Region infrastructure via IaC + RDS cross-Region read replica + AWS Backup (cross-Region) + a cron every 30 seconds backing up + restore EC2 from the latest backup + Route 53 geolocation routing (backup-based recovery is unlikely to meet a 10-minute RTO given EC2 restore/boot time).
- B. **Provision DR-Region infrastructure via IaC + RDS cross-Region read replica + configure AWS Elastic Disaster Recovery to continuously replicate EC2 + run EC2 at minimal capacity in the DR Region + Route 53 failover routing + increase the Auto Scaling group's desired capacity.**
- C. AWS Backup (cross-Region) + a cron every 30 seconds + IaC provisioning + manual restore + Route 53 simple routing (manual intervention makes meeting the 10-minute RTO difficult).
- D. IaC + Aurora Global Database + continuous EC2 replication via DRS + run EC2 Auto Scaling group at **full capacity** always in the DR Region + Route 53 failover (always running at full capacity is excessively costly).

**Correct Answer: B**

**Explanation**
**AWS Elastic Disaster Recovery (DRS)** continuously (second-level) replicates EC2, and keeping only **minimal capacity** (pilot light/warm standby) in the DR Region, scaling up the Auto Scaling group's capacity only on failure, meets the 30-second RPO/10-minute RTO while being far cheaper than always running full capacity. RDS uses a **read replica** promoted for fast database failover.

**Why the other choices are wrong**
- A, C: 30-second-interval backup/cron-based approaches can preserve data, but restoring/booting EC2 from backups from scratch easily exceeds a 10-minute RTO.
- D: Always running EC2 at full capacity in the DR Region is excessive standing cost, mismatched with "most cost-effective."

> 💡 **Exam tip**: For EC2 DR with short RPO/RTO, continuous replication via **AWS Elastic Disaster Recovery (DRS)** is the answer, and for cost optimization, keep the DR Region at **minimal capacity (pilot light)**, scaling only upon failure.

## QUESTION 203

**Question**: A one-time migration of an on-premises 60TB MySQL database to Aurora MySQL in us-east-1. Limited internet bandwidth means transfer would take a month. Fastest migration solution?

**Choices**
- A. Request a 1Gbps Direct Connect connection + migrate with DMS (setting up a new DX connection itself takes a long time).
- B. Use AWS DataSync over the existing internet connection to accelerate transfer + AWS Application Migration Service to migrate (still depends on limited bandwidth, unsuitable for 60TB).
- C. **Order an AWS Snowball Edge device. Load data into an S3 bucket via the S3 interface. Migrate from S3 to Aurora MySQL using AWS DMS.**
- D. Order a Snowball device + load via the S3 adapter for Snowball + Application Migration Service (Application Migration Service is a server-migration tool, not a database migration tool — a conceptual error).

**Correct Answer: C**

**Explanation**
If limited bandwidth would take a month to transfer 60TB, physically shipping data via **AWS Snowball Edge** is far faster. Once loaded into S3 via Snowball, complete the migration from S3 to Aurora MySQL with **AWS DMS.**

**Why the other choices are wrong**
- A: Setting up a new Direct Connect connection can itself take weeks, mismatching "fastest time."
- B: Even with DataSync, it still depends on the limited internet connection, not resolving the fundamental bottleneck.
- D: AWS Application Migration Service is a server (compute) migration tool, not a database migration tool — DMS is correct.

> 💡 **Exam tip**: To move **large amounts of data (tens of TB) over limited bandwidth**, the standard answer is **Snowball Edge (physical transfer) → S3 → DMS (migrate to DB).**

## QUESTION 204

**Question**: An application on 20 EC2 instances (persistent, multiple EBS volumes) needs backups maintained in a separate Region. Recovery of EC2 instances and their configuration must happen within **1 business day with no more than one day of data loss.** The company has limited staff and needs a backup solution optimizing operational efficiency and cost. A CloudFormation template for provisioning the necessary network configuration in the secondary Region already exists.

**Choices**
- A. Create a second CloudFormation template (recreating EC2 instances) + use a Systems Manager Automation Runbook for daily multi-volume snapshots + copy snapshots to the secondary Region + on failure, launch the template and restore EBS volumes from snapshots (a workable approach but with more moving parts than AWS Backup).
- B. Use Amazon Data Lifecycle Manager (DLM) for daily multi-volume EBS snapshots + on failure, launch the template and use DLM to restore volumes (DLM automates snapshot creation/retention, but AWS Backup better integrates cross-Region copy and instance/config restoration).
- C. **Use AWS Backup to create a scheduled daily backup plan for the EC2 instances. Configure the backup job to copy backups to a vault in the secondary Region. On failure, launch the CloudFormation template + restore instance volumes/configuration from the backup vault + shift traffic to the secondary Region.**
- D. Deploy identically-sized/configured EC2 instances in the secondary Region always-on + configure daily AWS DataSync to copy data from primary to secondary (maintaining always-on duplicate infrastructure is much more costly — mismatched with "limited staff, cost-optimized").

**Correct Answer: C**

**Explanation**
**AWS Backup** provides scheduled backups (covering multiple attached EBS volumes) and **cross-Region copy** as one integrated managed service, meeting a one-day RPO with minimal operational burden even for limited staff. On failure, using the prepared CloudFormation template to set up networking and restoring from the backup vault also meets the 1-business-day RTO.

**Why the other choices are wrong**
- A, B: Directly managing snapshots via DLM or Systems Manager Runbooks involves more components than AWS Backup's integrated backup plan/cross-Region copy, increasing operational burden.
- D: Maintaining identical always-on infrastructure in the secondary Region is far too costly, mismatching "limited staff, cost-optimized."

> 💡 **Exam tip**: To simplify **cross-Region backup/recovery of EC2+EBS** in a managed way with limited staff, **AWS Backup** (scheduled backup plan + cross-Region copy) is the standard answer.

## QUESTION 205

**Question**: A static-content website (large file upload/download) uses S3+CloudFront. All data must be **encrypted both in transit and at rest.** (Choose three.)

**Choices**
- A. **Turn on S3 server-side encryption for the S3 bucket used by the web application (encryption at rest).**
- B. Add an "aws:SecureTransport": "true" policy attribute to read/write operations in the S3 ACL (the condition belongs on a bucket policy, not an ACL — somewhat conceptually inaccurate).
- C. **Create a bucket policy denying unencrypted operations (HTTP) on the S3 bucket used by the web application (enforcing in-transit encryption).**
- D. Configure encryption at rest in CloudFront using SSE-KMS (CloudFront itself isn't storage, so "encryption at rest in CloudFront" doesn't make sense — at-rest encryption belongs to the origin, S3).
- E. **Configure CloudFront to redirect HTTP requests to HTTPS (in-transit encryption, the user-to-CloudFront leg).**
- F. Use the RequireSSL option when generating pre-signed URLs (no such option exists in the S3 pre-signed URL API — the SecureTransport condition on a bucket policy is the standard method).

**Correct Answer: A, C, E**

**Explanation**
At-rest encryption is handled by **S3 server-side encryption** (A). In-transit encryption must be enforced on two legs: the **CloudFront-to-user leg** via HTTP→HTTPS redirect (E), and the **application-to-S3 leg** via a bucket policy denying non-HTTPS requests (C).

**Why the other choices are wrong**
- B: The SecureTransport condition standardly belongs on a **bucket policy**, not an ACL (C correctly expresses this).
- D: CloudFront isn't content storage, so "encryption at rest in CloudFront" isn't a valid concept.
- F: No "RequireSSL" option exists in the S3 pre-signed URL generation API.

> 💡 **Exam tip**: To enforce **end-to-end encryption** in an S3+CloudFront architecture, you need: ① S3 server-side encryption (at rest), ② CloudFront's HTTP→HTTPS redirect (user-to-CF leg, in transit), and ③ a bucket policy's `aws:SecureTransport` condition (app-to-S3 leg, in transit).

## QUESTION 206

**Question**: A serverless architecture where Lambda accesses RDS SQL Server. Separate development/production environments. Developers can access dev DB credentials. **Production DB credentials must be encrypted with a key accessible only to the IT security team's IAM user group**, and this key must be **rotated regularly.** What should be done in the production environment?

**Choices**
- A. Parameter Store SecureString (KMS customer-managed key) + attach Lambda role + restrict access to IT security team only (Parameter Store itself lacks built-in automatic rotation of the credential value).
- B. KMS default (AWS-managed) Lambda key encryption + store credentials in environment variables (a default key is hard to restrict via a custom policy limited to a specific IAM group).
- C. Store credentials in environment variables + encrypt with a KMS customer-managed key (environment variables themselves have no automatic rotation mechanism).
- D. **Store database credentials in Secrets Manager as a secret associated with a KMS customer-managed key. Attach a role with secret access permission to each Lambda function. Restrict access to the customer-managed key to only the IT security team.**

**Correct Answer: D**

**Explanation**
**AWS Secrets Manager** natively supports storing credentials and **automatic rotation**, and restricting the key policy of the **KMS customer-managed key** used for encryption to the IT security team's IAM group precisely satisfies "only the security team can access this key."

**Why the other choices are wrong**
- A, C: Parameter Store or environment variables can securely store the value, but don't provide the integrated **automatic rotation** feature Secrets Manager offers.
- B: KMS default (AWS-managed) keys have limited ability to customize the key policy (restricting to a specific IAM group).

> 💡 **Exam tip**: When you need **both regular automatic credential rotation and encryption-key access restricted to a specific group**, the standard answer is **Secrets Manager (automatic rotation) + a KMS customer-managed key (access restricted via key policy).**

## QUESTION 207

**Question**: Migrating a legacy on-premises .NET application (load-balanced web servers + app servers + SQL Server). Use AWS managed services where possible, **without wanting to rewrite the application.** Solve scaling issues and **minimize licensing costs as the application scales.** Most cost-effective solution?

**Choices**
- A. **Deploy the web/app tiers on EC2 in Auto Scaling groups behind an Application Load Balancer. Change platforms for the SQL Server database to Amazon Aurora PostgreSQL with Babelfish turned on.**
- B. Use DMS to create server images + deploy EC2 instances based on on-premises import + NLB + DynamoDB as the database tier (switching to NoSQL requires rewriting the relational SQL Server application — violates "no rewrite").
- C. Containerize + provision an EKS cluster + NLB + RDS for SQL Server as the database (RDS for SQL Server still incurs full SQL Server licensing costs — fails the cost-minimization goal).
- D. Decompose application functions into Lambda functions + API Gateway + migrate data to S3 + query with Athena (requires extensive rewriting — violates "no rewrite").

**Correct Answer: A**

**Explanation**
**Babelfish for Aurora PostgreSQL** provides a compatibility layer understanding SQL Server's T-SQL protocol/syntax, letting SQL Server be replaced with Aurora PostgreSQL (open-source based, no licensing cost) without significant application code changes. Lifting-and-shifting the web/app tiers to EC2 Auto Scaling groups also solves the scalability problem.

**Why the other choices are wrong**
- B: Switching to DynamoDB (NoSQL) requires rewriting the relational data model and query logic, violating "no rewrite."
- C: Continuing to use RDS for SQL Server keeps SQL Server licensing costs unchanged, failing the "minimize licensing cost" goal.
- D: A full redesign via Lambda/API Gateway directly contradicts the premise of migrating without rewriting.

> 💡 **Exam tip**: To migrate **eliminating SQL Server licensing costs without rewriting the application**, **Babelfish for Aurora PostgreSQL** (T-SQL compatibility layer) is the standard answer.

## QUESTION 208

**Question**: A SaaS API (us-east-1 EKS+ALB) uses some non-standard REST methods (LINK, UNLINK, LOCK, UNLOCK). Users outside the US report long, inconsistent response times. Minimal operational overhead solution?

**Choices**
- A. Add a CloudFront distribution (ALB origin) (CloudFront is an HTTP-method-aware CDN and may not support non-standard REST methods like LINK — potentially unsuitable here).
- B. API Gateway edge-optimized endpoint (ALB as target) (API Gateway REST APIs are also optimized for standard HTTP methods, with limited support for non-standard ones).
- C. **Add an accelerator in AWS Global Accelerator. Configure the ALB as origin.**
- D. Deploy the API additionally in eu-west-1 and ap-southeast-2 + add a Route 53 latency-based routing record (a multi-Region deployment has far more operational overhead — data/state sync, etc.).

**Correct Answer: C**

**Explanation**
**AWS Global Accelerator** accelerates traffic at the **TCP/UDP layer over AWS's global backbone network**, regardless of HTTP method or protocol content — so it works fine with this API's non-standard REST methods, improving worldwide response times with minimal configuration change (just adding the accelerator).

**Why the other choices are wrong**
- A, B: CloudFront and API Gateway both operate at the HTTP layer, optimized for the standard HTTP method set, and may not fully support non-standard methods like LINK/UNLINK/LOCK/UNLOCK.
- D: Fully redeploying the application across multiple Regions has far more operational overhead (data sync, deployment pipelines, etc.) than Global Accelerator.

> 💡 **Exam tip**: To improve global performance for an **API using non-standard HTTP methods**, or any TCP/UDP-based workload, use **AWS Global Accelerator** (network-layer acceleration) instead of HTTP-layer services like CloudFront/API Gateway.

## QUESTION 209

**Question**: Millions of home sensors across the US connect via MQTT to a custom MQTT broker on a single EC2 instance (domain iot.example.com), storing data in DynamoDB. Data volume overloads the broker, causing data loss. Improve reliability.

**Choices**
- A. ALB+Auto Scaling group for the MQTT broker + Route 53 alias record (still scaling a self-managed MQTT broker, leaving operational burden and reliability limits vs. a managed service).
- B. **Set up AWS IoT Core to receive sensor data. Create and configure a custom domain to connect to AWS IoT Core. Update the Route 53 DNS record to the IoT Core Data-ATS endpoint. Configure an IoT rule to store the data.**
- C. NLB+MQTT broker as target + Global Accelerator + Route 53 multi-value response (still limited by the underlying self-managed single/few-broker architecture).
- D. Set up AWS IoT Greengrass (Greengrass is for edge/local gateway use — IoT Core is more appropriate for the cloud ingestion hub role for millions of home sensors).

**Correct Answer: B**

**Explanation**
**AWS IoT Core** is purpose-built to reliably handle millions of device connections in a managed way, with native MQTT protocol support. Replacing the self-managed single-EC2 broker with IoT Core fundamentally resolves the scalability/reliability problem, a **custom domain** preserves the existing `iot.example.com` endpoint, and an **IoT rule** connects storage to DynamoDB as before.

**Why the other choices are wrong**
- A, C: Scaling a self-managed MQTT broker via ALB/NLB/Global Accelerator still carries the limitations and management burden of a single piece of broker software — not a fundamental reliability improvement.
- D: IoT Greengrass is an edge (local) compute/gateway service; IoT Core is more suited to the cloud hub role for millions of remote home sensors connecting directly.

> 💡 **Exam tip**: For a large-scale ingestion hub where **millions of IoT devices connect via MQTT**, **AWS IoT Core** (custom domain + IoT rules) is the standard answer instead of a self-managed broker.

## QUESTION 210

**Question**: Linux EC2 instances, SSH key-pair-based access, each system needs a unique key pair. Implement a policy that automatically rotates all EC2 key pairs on request and stores keys in a securely encrypted location. **Less than 1 minute of downtime** allowed during key rotation.

**Choices**
- A. **Store all keys in Secrets Manager. Define a Secrets Manager rotation schedule invoking a Lambda function to generate a new key pair. Replace the public key on the EC2 instance. Update the private key in Secrets Manager.**
- B. Store all keys as strings in Parameter Store (SecureString) + define a Systems Manager maintenance window invoking Lambda (Parameter Store lacks the integrated automatic rotation scheduling that Secrets Manager offers).
- C. "Import" EC2 key pairs into KMS + configure automatic key rotation (KMS manages symmetric/asymmetric encryption keys, not a service for storing/rotating EC2 SSH key pairs themselves — a conceptual error).
- D. Add all EC2 instances to Fleet Manager + use a Systems Manager maintenance window to run Run Command generating/replacing new key pairs (a workable method, but doesn't clearly satisfy the "securely encrypted storage location" requirement as well as Secrets Manager).

**Correct Answer: A**

**Explanation**
**AWS Secrets Manager** securely encrypts and stores secrets (here, SSH keys) and supports a **rotation schedule** that automatically invokes a Lambda function to generate new key pairs. Updating the new public key into the EC2 instance's `authorized_keys` (replacing the old) and updating the private key in Secrets Manager implements automatic key rotation with short downtime.

**Why the other choices are wrong**
- B: Parameter Store can store values but lacks the fully integrated automatic rotation scheduling that Secrets Manager provides.
- C: AWS KMS manages encryption keys (for data encryption) — it isn't a service for "importing/rotating" EC2 SSH key pairs this way.
- D: Achievable via Fleet Manager/Run Command, but Secrets Manager is the purpose-built service better matching the "securely encrypted storage location" requirement.

> 💡 **Exam tip**: When both **automatic regular rotation of SSH keys (or other secrets) and secure encrypted storage** are needed, the standard answer is **AWS Secrets Manager's rotation schedule + Lambda.**

## QUESTION 211

**Question**: Planning to migrate a VMware ESXi environment (thousands of VMs) to AWS. No configuration management database exists, and knowledge of the VMware portfolio is limited. Provide an **accurate inventory** so the company can plan a cost-effective migration. Minimal operational overhead?

**Choices**
- A. Deploy Migration Evaluator to each VM via Systems Manager Patch Manager (Migration Evaluator uses an agentless collector; deploying via Patch Manager isn't how it works — a conceptual error).
- B. Manually export the VMware portfolio to a .csv + check disk utilization directly (manual work carries heavy operational overhead).
- C. **Deploy the Migration Evaluator agentless collector to the ESXi hypervisor. Review collected data, identify inactive servers, and remove them from the migration list. Import the data into Migration Hub.**
- D. Deploy an Application Migration Service agent to each VM + import data into Redshift for analysis + visualize with QuickSight (agent-based deployment across thousands of VMs itself is a heavy operational burden, and the goal is migration execution, not upfront inventory assessment).

**Correct Answer: C**

**Explanation**
**AWS Migration Evaluator's agentless collector** installs once at the ESXi hypervisor level to automatically collect utilization data across the entire VM portfolio. Since no per-VM agent installation is needed, operational overhead stays minimal even at a scale of thousands, and the collected data can identify inactive servers to exclude from migration before managing the portfolio through **Migration Hub.**

**Why the other choices are wrong**
- A: Migration Evaluator is fundamentally agentless — describing deployment via Patch Manager mismatches how it actually operates.
- B: Manually checking each server carries very heavy operational overhead at thousands-of-VM scale.
- D: Application Migration Service is a tool for the actual migration execution stage; Migration Evaluator better suits upfront portfolio assessment/inventory purposes. Also, installing an agent on every single VM is itself a heavy burden at this scale.

> 💡 **Exam tip**: For upfront assessment of a **large-scale VMware VM inventory**, **Migration Evaluator's agentless collector** (installed directly at the ESXi hypervisor, no per-VM agent needed) is the minimal-overhead standard answer.

## QUESTION 212

**Question**: Microservices (Lambda) write to an on-premises SQL database that supports only a limited number of concurrent connections. Excessive Lambda invocations crash the database. A Direct Connect connection exists. Design a solution protecting the database from crashes.

**Choices**
- A. **Write data to an SQS queue. Configure Lambda to read from the queue and write to the existing database. Set reserved concurrency for the Lambda function lower than the number of connections the database supports.**
- B. Migrate to a new Amazon Aurora Serverless DB cluster (the target is still an on-premises SQL database, so protecting without migrating is what's needed — leaving the on-premises DB as-is is more appropriate here).
- C. Create an RDS Proxy DB instance (RDS Proxy is for Amazon RDS instances and cannot be used with an **on-premises** SQL database — a conceptual error).
- D. Publish data to an SNS topic + invoke Lambda + configure provisioned concurrency equal to the database's connection count (SNS doesn't buffer/throttle processing rate like a queue does — less suitable than SQS).

**Correct Answer: A**

**Explanation**
Using an **SQS queue as a buffer** and setting Lambda's **reserved concurrency** lower than the number of connections the database supports keeps the number of Lambda instances polling the queue always within the DB's connection limit, preventing crashes from overload.

**Why the other choices are wrong**
- B: Migrating to Aurora Serverless doesn't match this scenario where the target is still an on-premises DB (migration itself isn't a stated requirement).
- C: **RDS Proxy is exclusive to Amazon RDS (and Aurora) instances** and cannot be used with an on-premises SQL server.
- D: SNS is an immediate fan-out publish-subscribe model, unsuitable for buffering/throttling messages to match processing rate like SQS.

> 💡 **Exam tip**: To **protect a downstream database (especially on-premises or connection-limited) from excessive concurrent Lambda invocations**, the standard answer is **an SQS buffer + Lambda reserved concurrency limit** (kept within the DB's connection limit). Remember RDS Proxy cannot be used with an on-premises database.

## QUESTION 213

**Question**: Grafana running on a single EC2 instance monitors AWS workload health. The company invested time building dashboards it wants preserved. Dashboards must be highly available (no more than 10 minutes downtime), with minimal ongoing maintenance. Minimal operational overhead solution?

**Choices**
- A. Migrate to CloudWatch dashboards + recreate existing Grafana dashboards (the platform itself changes, so existing Grafana dashboards can't be kept as-is and must be rebuilt — more effort).
- B. **Create an Amazon Managed Grafana workspace. Configure a new CloudWatch data source. Export dashboards from the existing Grafana instance. Import the dashboards into the new workspace.**
- C. A Grafana-preinstalled AMI + store existing dashboards on Amazon EFS + create an Auto Scaling group (min/desired/max=1) + an ALB across multiple AZs (maintaining self-managed infrastructure carries much more operational overhead).
- D. Configure AWS Backup to back up the EC2 running Grafana hourly + restore from the latest snapshot in an alternate AZ if needed (restore takes time, causing downtime hard to keep under the "no more than 10 minutes" strict availability requirement).

**Correct Answer: B**

**Explanation**
**Amazon Managed Grafana** is a fully managed service requiring no infrastructure management at all and providing high availability by default. The existing Grafana dashboards can be moved as-is to the new workspace via **export/import**, preserving the invested dashboards while minimizing management burden.

**Why the other choices are wrong**
- A: Switching to CloudWatch dashboards means the existing Grafana dashboards can't be kept and must be rebuilt from scratch.
- C: A self-managed EC2-based HA setup requires directly maintaining multiple components (AMI/EFS/ASG/ALB), carrying heavy operational overhead.
- D: A backup/restore approach takes time to restore on failure, making it hard to meet the strict "no more than 10 minutes downtime" availability requirement.

> 💡 **Exam tip**: To move a self-managed Grafana setup to high availability with minimal operational overhead, migrate to **Amazon Managed Grafana** (fully managed), moving existing dashboards via **export/import** — the standard answer.

## QUESTION 215

**Question**: Designing the AWS account structure for a company with multiple teams (all in the same Region). A VPC connected to the on-premises network is needed. Expected on-premises traffic is under **50Mbps.** Most cost-effective combination? (Choose two.)

**Choices**
- A. Deploy a CloudFormation template provisioning a VPC+subnets to each account (a separate VPC per account means separate on-premises connections per account too — much more expensive).
- B. **Deploy a CloudFormation template provisioning a VPC+subnets to a shared services account. Share the subnets with other accounts via AWS RAM.**
- C. Use Transit Gateway + Site-to-Site VPN to connect to on-premises + share the transit gateway via RAM (Transit Gateway's hourly cost may be excessive for traffic under 50Mbps).
- D. **Use AWS Site-to-Site VPN for on-premises network connectivity.**
- E. Use AWS Direct Connect for on-premises network connectivity (Direct Connect's fixed cost is far pricier than VPN for low traffic like 50Mbps).

**Correct Answer: B, D**

**Explanation**
Since multiple teams work in the **same Region**, creating the VPC/subnets once in a **shared services account** and **sharing subnets via AWS RAM** (B) is much cheaper than creating a separate VPC per account. Since traffic is low (**under 50Mbps**), **Site-to-Site VPN** (D, low-cost, traffic-based) is most economical at this scale compared to Direct Connect or Transit Gateway's high fixed costs.

**Why the other choices are wrong**
- A: A separate VPC per account also requires a separate on-premises connection (VPN/DX) per account, increasing cost.
- C: Transit Gateway has hourly and data processing charges, overkill/excessive cost for a single-Region, sub-50Mbps scenario.
- E: Direct Connect's high fixed monthly cost is inefficient compared to VPN for 50Mbps of low traffic.

> 💡 **Exam tip**: When multiple teams work in the **same Region**, sharing a **shared services account's VPC/subnets via AWS RAM** is cheaper than per-account VPCs, and for **low-traffic (tens of Mbps) on-premises connectivity**, **Site-to-Site VPN** is more cost-effective than Direct Connect/Transit Gateway.

## QUESTION 216

**Question**: Organizations (100+ accounts, routed via a central Transit Gateway, single Region). Each account has both an internet gateway and NAT gateway. Central, managed, rule-based filtering is needed for **all outbound internet traffic** across the organization. Max 25Gbps per AZ.

**Choices**
- A. New outbound-only VPC + attach existing TGW + NAT gateway + open-source proxy on an EC2 Auto Scaling group for rule-based filtering (self-managed proxy carries heavy management burden and questionable scalability at 25Gbps).
- B. **Create a new outbound-only VPC. Attach the existing TGW to the new VPC. Configure a new NAT gateway. Use AWS Network Firewall for rule-based filtering. Create Network Firewall endpoints in each AZ. Modify all default routes to point to the Network Firewall endpoints.**

Placing Network Firewall and the existing Transit Gateway in a **centralized (hub-and-spoke) VPC**, with every account's default route passing through this central firewall, allows centrally managing outbound traffic from a single point across 100+ accounts.

**Why the other choices are wrong**

> 💡 **Exam tip**: To centrally, rule-based filter **all outbound internet traffic** for a large organization (100+ accounts), **a centralized VPC + Transit Gateway + AWS Network Firewall** is the standard answer, offering better scalability and manageability than a self-managed proxy.

## QUESTION 220

**Question**: IoT sensors monitoring citywide traffic patterns stream to Kinesis Data Streams, read by multiple applications. Consumers experience throttling and periodic `ReadProvisionedThroughputExceeded` errors. What actions should resolve this? (Choose three.)

**Choices**
- A. **Reshard the stream to increase the number of shards.**
- B. Adjust polling frequency (if meant as "increasing" it, this would actually worsen the situation — this standalone item isn't part of the correct set as phrased).
- C. **Use consumers with the Enhanced Fan-Out feature.**
- D. Reshard the stream to decrease the number of shards (reducing shards would decrease throughput, worsening the problem).
- E. **Use error retry and exponential backoff mechanisms in consumer logic.**

**Why the other choices are wrong**

> 💡 **Exam tip**: When multiple consumers hit **`ReadProvisionedThroughputExceeded`** errors on Kinesis Data Streams, combine ① **increasing shard count (resharding)**, ② **Enhanced Fan-Out** (dedicated throughput per consumer), and ③ **retry with exponential backoff** — the standard answer.
