## QUESTION 281

**Question**: An on-premises Oracle database needs to migrate to Aurora PostgreSQL (a heterogeneous engine migration). Oracle-specific code such as stored procedures should be converted automatically as much as possible, and **application downtime during the actual data cutover** should be minimized. What's the standard approach?

**Choices**
- A. Migrate schema and data all at once using only AWS DMS (DMS has limited automatic conversion capability for schema objects — especially code like stored procedures; SCT paired with DMS is the standard for heterogeneous migrations).
- B. **Use AWS Schema Conversion Tool (SCT) to convert the Oracle schema and code into PostgreSQL-compatible form, then use AWS DMS to perform a full load plus continuous replication (CDC), keeping data current up to cutover, and switch traffic during a short cutover window.**
- C. Export Oracle data as text (similar to mysqldump) and manually import it into PostgreSQL (a manual approach is error-prone at scale and has no way to continuously capture changes during the cutover, leading to large downtime).
- D. Rehost to RDS for Oracle first instead of Aurora PostgreSQL, and revisit later (the question explicitly requires an engine switch to Aurora PostgreSQL, so this doesn't meet the goal).

**Correct Answer: B**

**Explanation**
**AWS SCT** converts Oracle's schema and application code such as stored procedures/functions into PostgreSQL-compatible code as automatically as possible (parts that can't auto-convert are flagged in a conversion report). Then **AWS DMS** performs an initial **full load** of all data, and continues replicating subsequent changes via **CDC (change data capture)** to keep source and target in sync, allowing the application to switch to the target during only a short cutover window — minimizing downtime.

**Why the other choices are wrong**
- A: DMS is strong at data migration, but its automatic conversion of code objects like stored procedures is more limited than SCT's. SCT (schema/code conversion) + DMS (data migration) is the standard combination for heterogeneous migrations.
- C: Manual export/import is inefficient and error-prone at large data volumes, and without continuous replication, downtime up to cutover grows large.
- D: The question's goal is explicitly to move to Aurora PostgreSQL, so rehosting to RDS for Oracle doesn't meet the requirement.

> 💡 **Exam tip**: For **heterogeneous migrations** between different database engines, the standard answer is **SCT (schema/code conversion) + DMS (full load + continuous CDC replication)** — also the standard pattern for minimizing downtime.

## QUESTION 282

**Question**: A SaaS company serves its API through an EC2 fleet behind an NLB, and wants hundreds of customer AWS accounts to access this API **without going over the public internet**. What structure keeps operational overhead from growing as the customer count grows?

**Choices**
- A. VPC peering connections between each customer VPC and the SaaS VPC (peering is non-transitive and can run into CIDR overlap issues, and managing individual peering connections at a scale of hundreds of customers is a very heavy operational burden).
- B. **Create and publish a VPC endpoint service (a PrivateLink service) based on the NLB, and allow customers to connect by creating an interface endpoint in their own VPC.**
- C. Expose the SaaS API to the public internet and add security group rules allowing only customer IPs (directly contradicts the requirement to avoid the public internet).
- D. Connect individually with every customer via private virtual interfaces over a Direct Connect gateway (setting up physical/dedicated-circuit-based Direct Connect per customer is far more costly and time-consuming than a multi-customer SaaS connectivity scenario calls for).

**Correct Answer: B**

**Explanation**
Creating and publishing a **VPC endpoint service (AWS PrivateLink)** targeting the NLB lets customers connect to the SaaS API without traversing the public internet, simply by creating an **interface endpoint** in their own VPC. There's no CIDR overlap concern, and the SaaS provider doesn't need any additional network configuration per new customer, so operational overhead barely grows as the customer count increases.

**Why the other choices are wrong**
- A: VPC peering fails when CIDRs overlap, and managing individual peering with hundreds of customers doesn't scale.
- C: Public exposure violates the core requirement of avoiding the public internet.
- D: Direct Connect is dedicated-circuit-based, making it unsuitable in cost and setup time for connecting many SaaS customers.

> 💡 **Exam tip**: For a SaaS provider to **expose a service to many customer VPCs, scalably and without the public internet**, an **NLB-based VPC endpoint service (AWS PrivateLink)** is the standard answer.

## QUESTION 283

**Question**: A financial regulator requires certain transaction records to be retained in a way that **cannot be deleted or modified by any means** for a set period (WORM, Write Once Read Many), similar to SEC 17a-4-style compliance. No one — not even an administrator account — should be able to delete them during the retention period. How do you implement this in S3?

**Choices**
- A. Deny the DeleteObject API to all users via an S3 bucket policy (an administrator can still modify or delete the bucket policy itself, so this doesn't guarantee true immutability).
- B. **Enable S3 Versioning, then set S3 Object Lock to Compliance mode and specify the required retention period.**
- C. Set S3 Object Lock to Governance mode (Governance mode allows a user with special permission [s3:BypassGovernanceRetention] to bypass the retention setting and delete the object, so it doesn't fully meet the "not even an administrator" requirement).
- D. Use a lifecycle policy to transition to Glacier Deep Archive after a period (this only changes storage class — it doesn't inherently prevent deletion/modification).

**Correct Answer: B**

**Explanation**
**S3 Object Lock** protects objects with a WORM model on a versioning-enabled bucket. Setting it to **Compliance mode** means **no user, including the root account,** can delete the object or weaken its retention setting before the retention period ends — meeting strict regulatory requirements like SEC 17a-4.

**Why the other choices are wrong**
- A: A bucket policy can itself be changed/deleted by a user with sufficient IAM permissions, so it doesn't guarantee the fundamental immutability the regulation requires.
- C: Governance mode has an exception allowing a specially privileged user to bypass the retention setting, so Compliance mode is more appropriate for the strict "no one can delete" requirement.
- D: Changing storage class is a cost-optimization feature, unrelated to preventing deletion/modification.

> 💡 **Exam tip**: For **WORM compliance where no one — not even an administrator — can delete or modify data**, **S3 Versioning + S3 Object Lock Compliance mode** is the standard answer. Remember Governance mode can be bypassed, unlike Compliance mode.

## QUESTION 284

**Question**: Multiple business units each generate events (order creation, inventory changes, etc.) in their own AWS accounts, and these need to flow into a **central event bus** so several consumer applications (in other accounts) can subscribe only to the events they care about. How do you build an event-driven architecture without tight coupling between accounts?

**Choices**
- A. Have each business-unit account publish SNS messages directly to consumer accounts, managing separate SNS topic subscriptions per consumer account (managing an individual connection per business-unit/consumer pair grows into a complex N:M relationship as accounts increase).
- B. **Create a custom EventBridge event bus in a central account, and set a resource policy allowing each business-unit account to publish events to this central bus. Consumer applications subscribe by filtering only the event patterns they care about via rules.**
- C. Write all events into an RDS table in one account and have consumer applications periodically poll it (polling lacks real-time-ness, and there's no built-in event-routing capability for interest-based filtering).
- D. Have each business unit create its own SQS queue, with consumer applications individually subscribing to every queue they need (managing a queue per business-unit/consumer combination doesn't scale, and there's no event-pattern-based filtering).

**Correct Answer: B**

**Explanation**
Placing a custom **Amazon EventBridge** event bus in a central account, and allowing each business-unit account to publish events to it via a **resource-based policy**, loosely couples publishers and consumers — neither needs to know about the other. Consumer applications can selectively subscribe to only the events they care about using **event-pattern-based rules**, simplifying an N:M relationship into a single event bus — the standard event-driven architecture.

**Why the other choices are wrong**
- A, D: Managing an individual connection (SNS subscription, SQS queue) per publisher-consumer pair grows management complexity exponentially as accounts increase.
- C: A polling-based approach doesn't provide the real-time-ness and loose coupling an event-driven architecture aims for, and event-pattern filtering would have to be built manually.

> 💡 **Exam tip**: To **collect events from multiple accounts centrally and selectively distribute them by interest**, the standard answer is **a central account's EventBridge custom event bus (with a resource policy allowing cross-account publishing) + rule-based subscriptions**.

## QUESTION 285

**Question**: Some of a company's archived data needs to be **retrieved instantly (millisecond-level)** during quarterly audits, while other regulatory archive data is accessed **once a year and can tolerate up to about 12 hours** to retrieve. Both datasets are accessed very infrequently. What storage strategy minimizes cost?

**Choices**
- A. Store both datasets in S3 Glacier Deep Archive (Deep Archive's restore time can take 12+ hours, which doesn't meet the instant-retrieval requirement for the audit dataset).
- B. **Store the data needing instant retrieval in S3 Glacier Instant Retrieval, and the regulatory archive data that can wait up to 12 hours in S3 Glacier Deep Archive.**
- C. Store both datasets in S3 Standard-IA (Standard-Infrequent Access) (given the extremely low access frequency and long-term archival purpose, not using the cheaper Glacier-family storage classes misses a cost-optimization opportunity).
- D. Store both datasets in S3 Glacier Flexible Retrieval (formerly Glacier) and use Expedited retrieval for urgent needs (Expedited still has at least a few minutes of latency and costs more, while Glacier Instant Retrieval is more suitable and cheaper for millisecond-level instant access).

**Correct Answer: B**

**Explanation**
For data accessed very infrequently but needing **millisecond-level instant retrieval**, **S3 Glacier Instant Retrieval** delivers Standard-IA-level retrieval performance at Glacier-level low storage cost — ideal. For regulatory archive data accessed **once a year and tolerant of up to 12 hours** of retrieval wait, the cheapest storage option, **S3 Glacier Deep Archive**, fits best. Splitting storage classes per each dataset's access pattern is the standard cost-minimization strategy.

**Why the other choices are wrong**
- A: Deep Archive can take 12+ hours to restore, unsuitable for the dataset needing instant retrieval.
- C: Standard-IA has higher storage cost than the Glacier family, missing a cost-optimization opportunity for such infrequently accessed data.
- D: Glacier Flexible Retrieval's Expedited tier is also worse than Glacier Instant Retrieval in both latency and cost for an instant-retrieval requirement.

> 💡 **Exam tip**: For infrequently accessed data with **different retrieval-time requirements**, don't lump it into one storage class — split by requirement: **instant retrieval → Glacier Instant Retrieval**, **long-wait tolerant → Glacier Deep Archive** — the standard cost-optimized answer.

## QUESTION 286

**Question**: A startup's new application has almost no traffic initially, but during marketing campaigns it repeatedly spikes **unpredictably and sharply (within seconds)** and then drops back down. They want the database capacity to auto-scale finely and quickly to match traffic, while costing almost nothing when idle. What's the solution?

**Choices**
- A. An Aurora Provisioned cluster + Application Auto Scaling to adjust the number of read replicas (adding/removing read replicas happens on the order of minutes, too slow to respond to second-scale traffic spikes, and the primary's own capacity doesn't auto-scale).
- B. **Configure the cluster as Aurora Serverless v2, set to automatically scale compute capacity up/down finely on a per-second basis.**
- C. Fully switch to DynamoDB on-demand mode (if the relational data model and query patterns need to be preserved, a full migration to DynamoDB imposes a heavy application-rewrite burden, and the question presupposes a relational database).
- D. Run a fixed, large-instance-class Aurora Provisioned cluster continuously (paying for a large instance's cost even during near-zero-traffic periods, contradicting the "cost almost nothing when idle" requirement).

**Correct Answer: B**

**Explanation**
**Aurora Serverless v2** automatically scales compute capacity (ACUs) up and down **finely, on a per-second basis**, based on actual application load, dropping to minimum capacity when there's no traffic, incurring almost no cost. This is a relational database solution precisely suited to workloads with unpredictable, sharp traffic swings.

**Why the other choices are wrong**
- A: Adding/removing read replicas is too slow to respond to second-scale sudden changes, and the primary instance handling writes doesn't auto-scale its own capacity.
- C: Fully switching to DynamoDB when the relational model/queries must be preserved is an excessive redesign.
- D: Running a fixed large instance continuously incurs high cost even during traffic-free periods, contradicting the cost-minimization requirement.

> 💡 **Exam tip**: For a relational workload with **unpredictable, sharp (second-scale) traffic swings**, needing both fine-grained auto-scaling and low idle cost, **Aurora Serverless v2** is the standard answer.

## QUESTION 287

**Question**: A large organization wants to **centrally inspect** outbound/east-west traffic (intrusion detection/prevention, domain filtering, etc.) across dozens of VPCs, and wants to continue using its existing third-party firewall appliance. What's a scalable, centralized traffic-inspection architecture?

**Choices**
- A. Deploy a third-party firewall instance individually in each VPC and force traffic through it via route tables (requires per-VPC deployment/management, contradicting the "centralized" requirement and adding heavy operational burden).
- B. **Create a central inspection VPC, place the third-party firewall appliance behind a Gateway Load Balancer (GWLB), place a GWLB endpoint in each spoke VPC, and configure Transit Gateway with routing so all traffic passes through the central inspection VPC.**
- C. Deploy only AWS Network Firewall individually in each VPC (doesn't meet the requirement to keep using the existing third-party firewall appliance, and per-VPC deployment isn't centralized).
- D. Configure fine-grained NACL rules in each VPC as a substitute for traffic inspection (NACLs only provide stateless IP/port-based filtering and don't offer deep packet inspection features like intrusion detection/prevention or domain filtering).

**Correct Answer: B**

**Explanation**
**Gateway Load Balancer (GWLB)** scalably deploys virtual appliances like third-party firewalls and transparently forwards traffic through them. Placing the GWLB and the third-party appliance in a central **inspection VPC**, placing a **GWLB endpoint** in each spoke VPC, and configuring Transit Gateway with routing so all outbound/east-west traffic passes through the central inspection VPC achieves a scalable, centralized traffic-inspection architecture while preserving the existing third-party firewall investment.

**Why the other choices are wrong**
- A: Deploying/managing individually per VPC isn't centralized and doesn't scale well.
- C: Ignoring the requirement to keep using the existing third-party firewall appliance and fully replacing it with AWS Network Firewall doesn't meet the requirement (though if AWS Network Firewall were used instead of a third party, a central inspection VPC without GWLB would be viable).
- D: NACLs only support stateless IP/port filtering and can't substitute for deep inspection features like intrusion detection/prevention.

> 💡 **Exam tip**: To use an existing **third-party firewall appliance** to **centrally and scalably inspect traffic** across many VPCs, the standard answer is **Gateway Load Balancer + a central inspection VPC + GWLB endpoints + Transit Gateway routing**.

## QUESTION 288

**Question**: A production RDS MySQL database needs **automatic failover**, and the application must keep using the same endpoint without change during failover. Additional cost should be minimized. What's the solution?

**Choices**
- A. A Single-AZ RDS instance + nightly snapshot backups (Single-AZ has no automatic failover capability at all, and recovery from a snapshot requires manual restoration — doesn't meet the "automatic" requirement at all).
- B. **Switch to a Multi-AZ RDS deployment, maintaining a synchronously replicated standby instance. On failure, RDS automatically fails over to the standby, and the application keeps using the same DB endpoint.**
- C. Create a read replica, and on failure have an operator manually promote it to primary and update the application's connection string (requires manual intervention, contradicting "automatic" failover, and also requires an endpoint change, contradicting "no endpoint change").
- D. Switch to Aurora Global Database, keeping a read-only replica in a secondary Region (cross-Region Global Database is overly complex and costly for this single-Region automatic-failover requirement, and doesn't match the premise of an RDS MySQL environment to begin with).

**Correct Answer: B**

**Explanation**
An **RDS Multi-AZ** deployment automatically maintains a synchronously replicated standby instance in a separate Availability Zone, and if the primary fails, **RDS automatically** fails over to the standby. The DB endpoint (DNS name) stays unchanged throughout, requiring no application-side changes. This is the most appropriate and cost-effective way to meet a standard automatic-failover requirement within a single Region.

**Why the other choices are wrong**
- A: Single-AZ has no automatic failover, and recovery is entirely manual.
- C: Promoting a read replica requires a manual action and a connection-string (endpoint) change, violating both the "automatic" and "no endpoint change" requirements.
- D: Aurora Global Database is a cross-Region disaster-recovery solution — excessive for this question's scope of automatic AZ-failure failover within a single Region, and would also require an engine switch (MySQL → Aurora).

> 💡 **Exam tip**: For RDS high availability with **automatic failover and no endpoint change** within a single Region, **Multi-AZ deployment** is the standard answer. Remember read replicas are for scaling, not automatic failover.

## QUESTION 289

**Question**: A very cost-sensitive, large-scale image-rendering batch job is designed to resume from its last checkpoint if interrupted (fault-tolerant). Process it **as cheaply as possible**, while ensuring there's enough time to safely save in-progress work before an instance is reclaimed (interrupted). What's the solution?

**Choices**
- A. Build the Auto Scaling group using only On-Demand instances (using only On-Demand for a fault-tolerant, cost-sensitive batch workload misses the cost savings Spot offers).
- B. **Configure an EC2 Auto Scaling group (or Spot Fleet) using Spot Instances, and add logic to handle the EC2 Spot interruption notice (2-minute advance warning) to save a checkpoint before reclamation.**
- C. Purchase a 1-year Reserved Instance commitment (a long-term commitment for unpredictable batch workload volume risks wasted idle capacity, and the savings are smaller than Spot's).
- D. Secure dedicated hardware via a Dedicated Host and run the bulk job (Dedicated Hosts are meant for special purposes like license compliance, and are actually more expensive than On-Demand — unsuitable for simple batch cost optimization).

**Correct Answer: B**

**Explanation**
**Spot Instances** are up to 90% cheaper than On-Demand, ideal for fault-tolerant (checkpoint-resumable) batch workloads. EC2 gives a **2-minute interruption notice** before reclaiming a Spot instance, so implementing logic that detects this notice and saves the in-progress work (checkpoint) lets you process large batch jobs at low cost with no data loss.

**Why the other choices are wrong**
- A: Using only On-Demand fails to capture the significant cost savings Spot offers for a fault-tolerant batch workload.
- C: A long-term Reserved Instance commitment doesn't fit variable batch job volume and doesn't save as much as Spot.
- D: Dedicated Hosts serve special requirements like licensing/compliance and would actually cost more than On-Demand for simple cost-optimized batch work.

> 💡 **Exam tip**: For a **fault-tolerant (checkpoint-resumable), cost-sensitive batch workload**, the standard answer is **Spot Instances + checkpoint-saving logic triggered by the 2-minute interruption notice**.

## QUESTION 290

**Question**: The compliance team wants to continuously audit whether **the same security best practices** (e.g., S3 public access blocked, no unencrypted EBS volumes) are being followed across all of the organization's accounts, and get a single view of violations. The same audit rules must automatically apply to new accounts too. What's the solution?

**Choices**
- A. Manually create AWS Config rules in each account individually and compile results into a spreadsheet report (requires manual setup/compilation per account — heavy operational burden, and doesn't apply automatically to new accounts).
- B. **Deploy an AWS Config organization conformance pack from the management account (or a delegated administrator account) to automatically apply the same rule set to all existing and new accounts in the organization, and aggregate compliance status centrally.**
- C. Use only Trusted Advisor's default free-tier checks (the free tier's security checks are limited, and it offers no custom rule definitions or organization-wide automatic deployment).
- D. Deploy a Lambda function in each account to periodically scan resources and alert via SNS on violations (heavy implementation/maintenance burden, and per-account deployment means new accounts aren't automatically covered).

**Correct Answer: B**

**Explanation**
An **AWS Config organization conformance pack**, deployed once from the management account (or a delegated administrator), **automatically applies** the same rule set (a bundle of managed rules) to **every existing account and any future account** added to the organization, with compliance status aggregated centrally in a dashboard. This is the standard way to automate consistent compliance auditing across a multi-account environment.

**Why the other choices are wrong**
- A: Manual per-account setup and manual compilation is a heavy operational burden and doesn't apply automatically to new accounts.
- C: Trusted Advisor's free tier has limited checks and no ability to automatically deploy custom rules organization-wide.
- D: Building/deploying your own Lambda scanner reinvents functionality AWS Config already provides, creating unnecessary operational burden.

> 💡 **Exam tip**: To **automatically apply the same compliance rules to new accounts too and audit centrally** across a multi-account environment, **AWS Config's organization conformance pack** is the standard answer.

## QUESTION 291

**Question**: Dozens of VPCs each run their own NAT Gateway, and outbound internet costs (NAT Gateway hourly charges + data-processing charges) are billed far higher than expected. How do you reduce NAT-related costs while preserving each VPC's outbound traffic requirements?

**Choices**
- A. Keep each VPC's NAT Gateway as-is but downsize its "instance type" (NAT Gateway is a managed service with no instance-type concept, and its cost is based on uptime and data processed — this option doesn't even make sense).
- B. **Place one NAT Gateway (or a small, redundant pair) in a central egress VPC, and route each spoke VPC's outbound traffic to this central NAT Gateway via Transit Gateway.**
- C. Remove NAT Gateways from all VPCs and assign public IPs directly to instances in private subnets (directly exposing private-subnet resources with public IPs is a direct violation of security best practices).
- D. Reintroduce EC2-based NAT instances individually in each VPC (an EC2-based NAT instance carries operational burden — you must handle patching, redundancy, etc. yourself — and scales worse under heavy traffic than a managed NAT Gateway).

**Correct Answer: B**

**Explanation**
The core driver of the cost increase is the hourly NAT Gateway charge being duplicated across every VPC. Placing only a small number of NAT Gateways in a **central egress VPC**, and using **Transit Gateway** to funnel multiple spoke VPCs' outbound traffic to this central NAT Gateway, significantly reduces the NAT Gateway's own hourly charges while still meeting each VPC's outbound internet access requirement (weigh this against Transit Gateway's own data-processing charges).

**Why the other choices are wrong**
- A: NAT Gateway is a fully managed service with no user-selectable instance type — the concept itself doesn't apply.
- C: Directly exposing private resources with public IPs is a direct violation of security best practices.
- D: Running your own NAT instances requires handling patching, redundancy, and scaling yourself, carrying more operational burden and lower throughput limits than a managed NAT Gateway.

> 💡 **Exam tip**: To **reduce NAT Gateway costs** across many VPCs, centralizing via **a central egress VPC's NAT Gateway + Transit Gateway routing** is the standard answer — but also weigh the trade-off against Transit Gateway's own data-processing costs.

## QUESTION 292

**Question**: Several independent consumer applications need to read the same Kinesis Data Stream in real time (within seconds of latency each), but as the number of consumers grows, **each consumer experiences delays from competing for the shared 2MB/s-per-shard throughput**. How do you guarantee dedicated throughput per consumer?

**Choices**
- A. Significantly increase the number of shards to raise overall stream throughput (increasing shards raises total throughput, but all consumers [polling] still share the 2MB/s per shard, so the same contention problem recurs as more consumers are added).
- B. **Use Kinesis Data Streams' Enhanced Fan-Out to register each consumer, providing each with dedicated 2MB/s-per-shard throughput delivered via HTTP/2 push.**
- C. Create a separate Kinesis Data Stream per consumer and have the producer duplicate-publish the same data to each stream (requires the producer to implement/maintain duplicate-publishing logic, increasing complexity and cost, and requires a producer change every time a new consumer is added).
- D. Switch to SQS and have each consumer subscribe to its own queue (SQS isn't suited to standard publish-subscribe fan-out at this scale, and lacks Kinesis-style ordered stream replay, so it doesn't fit the requirement).

**Correct Answer: B**

**Explanation**
**Enhanced Fan-Out** delivers data to each registered consumer via **HTTP/2 push** rather than polling, guaranteeing each consumer **dedicated 2MB/s per shard**. So as the number of consumers grows, there's no throughput contention between them, and each consumer receives data with latency typically under about 70ms.

**Why the other choices are wrong**
- A: Standard (polling) consumers still share per-shard throughput, so the same contention problem recurs if consumer count grows alongside shard count.
- C: Duplicating the stream per consumer and having the producer publish redundantly is operationally and financially costly, and doesn't scale well.
- D: SQS doesn't fit this scenario's requirement for multiple consumers to replay an ordered stream.

> 💡 **Exam tip**: In Kinesis Data Streams, when **multiple consumers need dedicated, low-latency real-time throughput without contention**, **Enhanced Fan-Out** is the standard answer.

## QUESTION 293

**Question**: A company wants to share an AMI built from a KMS-encrypted EBS snapshot with **another AWS account** (a partner) so they can launch their own EC2 instances from it. How do you implement this while preserving confidentiality of the underlying data?

**Choices**
- A. Make the AMI public so anyone can use it (public sharing exposes it to the whole world, not just the partner — directly violating the confidentiality requirement).
- B. Decrypt the snapshot and create a new, unencrypted snapshot/AMI to share (removing encryption violates the confidentiality requirement and security best practices).
- C. **Explicitly share the AMI (and its underlying snapshot) with the partner's account ID, and modify the key policy of the KMS key used to encrypt the snapshot to grant the partner account permission to use (decrypt with) that key.**
- D. Skip AMI sharing and instead document the AMI's contents as text so the partner can rebuild it from scratch (faithfully reproducing the original AMI is difficult, and this doesn't achieve the stated goal of "sharing the AMI" at all).

**Correct Answer: C**

**Explanation**
To share a KMS-encrypted-snapshot-based AMI with another account, you must both **share the AMI itself with the target account ID** and **modify the key policy of the KMS key** that encrypted the snapshot to grant the target account the necessary permissions (e.g., `kms:Decrypt`). Both steps are required for the partner account to actually be able to launch an instance from the AMI successfully.

**Why the other choices are wrong**
- A: Public sharing exposes the AMI to everyone, not just the partner, violating confidentiality.
- B: Sharing with encryption removed abandons the data-protection requirement entirely.
- D: Documenting and rebuilding doesn't achieve the goal of sharing the original AMI and is impractical.

> 💡 **Exam tip**: When **sharing a KMS-encrypted AMI/snapshot with another account**, remember both steps are required: ① share the AMI with the target account, and ② **modify the KMS key policy to grant the target account usage permission**.

## QUESTION 294

**Question**: A compliance requirement mandates that backups of production data also be stored in a **separate account and Region** from the original (so backups remain safe even in a ransomware attack or account compromise). This needs to be managed centrally across multiple AWS services (EBS, RDS, DynamoDB, etc.). What's the solution?

**Choices**
- A. Use each service's (EBS, RDS, DynamoDB) own snapshot/backup feature and write scripts to individually copy each to another Region (requires building/maintaining separate scripts per service — heavy operational burden and hard to manage centrally).
- B. **Use AWS Backup to centrally define a backup plan spanning multiple services, and configure cross-account/cross-Region copy rules to automatically copy backups to a separate backup account/Region.**
- C. Manually export each service's data at the application level to S3 in a separate account (a manual, per-service approach is inefficient for automation, consistent retention policy enforcement, and central monitoring).
- D. Only strengthen IAM policies in the production account to prevent backup deletion (this is permission hardening within the same account, and if the account itself is compromised this defense can be bypassed too — doesn't meet the core "store in a separate account" requirement).

**Correct Answer: B**

**Explanation**
**AWS Backup** lets you centrally define a single **backup plan** spanning multiple AWS services like EBS, RDS, and DynamoDB, and setting **cross-account/cross-Region copy rules** automatically copies backups to a separate, isolated backup account and Region. This keeps the separate-account backups safe even if the original account is compromised by ransomware or a breach, while managing backups across multiple services from a single console.

**Why the other choices are wrong**
- A, C: Building individual scripts/manual processes per service is inefficient, reinventing the centralized policy management, automation, and monitoring AWS Backup already provides.
- D: Hardening IAM policies within the same account alone doesn't eliminate the risk if the account itself is compromised, failing to meet the core requirement of storing backups in a separate account.

> 💡 **Exam tip**: To **centrally manage backups across multiple AWS services and automatically isolate copies to a separate account/Region**, **AWS Backup's backup plan + cross-account/cross-Region copy rules** is the standard answer.

## QUESTION 295

**Question**: A Lambda function written in Java has significant **cold-start latency** due to JVM initialization and class loading, causing unstable response times for an API with intermittent traffic. They want to reduce cold starts **without using Provisioned Concurrency** (i.e., no additional standing cost). What's the solution?

**Choices**
- A. Increase the function's memory to the maximum to boost CPU performance (more memory can improve execution performance, but doesn't fundamentally solve the JVM-initialization cold-start problem).
- B. **Enable Lambda SnapStart, which caches an encrypted snapshot of an already-initialized execution environment at deployment time, and quickly restores the execution environment from this snapshot on invocation.**
- C. Set Provisioned Concurrency to a constantly high maximum (the question explicitly requires no additional standing cost, and Provisioned Concurrency incurs standing charges, contradicting the requirement).
- D. Rewrite the function in Node.js (a rewrite could be a viable fix, but if the requirement is to keep the existing Java codebase while just improving cold starts, SnapStart is the more direct solution).

**Correct Answer: B**

**Explanation**
**Lambda SnapStart** (supported for Java-based runtimes) creates and caches an **encrypted snapshot** of a fully initialized execution environment at deployment time, and quickly restores the execution environment from this snapshot on an actual invocation, greatly reducing cold-start latency from JVM initialization and similar steps. Unlike Provisioned Concurrency, it doesn't keep a standing execution environment warm, so it incurs no additional standing cost.

**Why the other choices are wrong**
- A: Increasing memory can improve execution performance but doesn't shorten the initialization process itself, the root cause of cold starts.
- C: Provisioned Concurrency is effective but incurs standing cost, violating the "no additional standing cost" requirement.
- D: A full runtime rewrite is a possible fix, but SnapStart is the more direct, lower-risk solution when the existing codebase must be preserved.

> 💡 **Exam tip**: To reduce **cold starts in Java (etc.) Lambda functions** **without additional standing cost**, **Lambda SnapStart** is the standard answer. Remember the contrast with Provisioned Concurrency's standing cost.

## QUESTION 296

**Question**: A financial trading firm serves client applications using a custom TCP-based binary protocol (non-HTTP). They need a **fixed static IP address** for client-side firewall allow-listing, and want to route global clients over the optimal network path. What's the solution?

**Choices**
- A. Use Amazon CloudFront for a static IP (CloudFront specializes in HTTP/HTTPS content delivery, doesn't support arbitrary TCP binary protocols, and its wide range of edge IPs doesn't fit a fixed-IP allow-listing requirement).
- B. **Use AWS Global Accelerator to assign a fixed Anycast static IP address in front of the application; clients connecting to this IP are routed via the AWS global network to the nearest optimal endpoint.**
- C. Use Route 53 geoproximity routing with each Region's ALB's dynamic IP (ALB's IP can change over time, failing to meet the fixed-IP allow-listing requirement; also, while ALB supports TCP listeners, an NLB is more suited to an arbitrary custom TCP application).
- D. Place an EC2 instance with an Elastic IP in each Region and have clients manually pick the nearest Region (requires clients to manually choose a Region, failing the automatic-optimal-routing requirement, and also requires allow-listing a different IP per Region — cumbersome).

**Correct Answer: B**

**Explanation**
**AWS Global Accelerator** provides a **fixed Anycast static IP address** for TCP/UDP traffic; clients need only connect to this single IP, and AWS's global backbone network automatically routes them to the **nearest optimal endpoint** (NLB, ALB, EC2, etc.). Since it supports arbitrary TCP protocols beyond HTTP, it fits precisely a non-HTTP financial protocol scenario requiring a fixed-IP allow list.

- A: CloudFront is dedicated to HTTP(S) content delivery — it doesn't support custom TCP binary protocols and doesn't provide a fixed IP.

> 💡 **Exam tip**: For a **non-HTTP TCP/UDP protocol** needing a **fixed static IP plus globally optimal routing**, **AWS Global Accelerator** is the standard answer.

## QUESTION 297

What's the solution?

**Choices**
- A. Use only default scheduling with no placement constraints (default scheduling may not guarantee even distribution across AZs, and offers no fine-grained control over the Fargate Spot/On-Demand ratio).
- B. **Attach both the Fargate and Fargate Spot capacity providers to the ECS service, and in the capacity provider strategy, set base (the guaranteed minimum) to Fargate and weight (the remaining proportion) to Fargate Spot. The service spreads tasks across AZs by default.**
- C. Run all tasks on Fargate Spot only (running everything on Spot with no guaranteed baseline risks significant availability loss during a large-scale simultaneous Spot reclamation — failing the "minimum guaranteed capacity" requirement).

## QUESTION 299

**Question**: A central platform team wants to delegate self-service IAM role creation to developers, but must prevent developers from **escalating their own privileges** (e.g., granting themselves administrator access). How do you preserve developer flexibility while categorically blocking privilege escalation?

**Choices**
- A. Grant developers only IAM role-creation permissions (iam:CreateRole, iam:AttachRolePolicy, etc.) with no other control, trusting them (with no technical safeguard against privilege escalation, this leaves open the risk of a developer intentionally or accidentally creating a role with an administrator policy attached).
- B. **Attach a permissions boundary alongside the developers' IAM role-creation permission, so that any role a developer creates can never exceed the maximum permissions defined by that boundary.**
- C. Block developers' IAM console access entirely and have the platform team create all roles on their behalf (completely removes developer self-service flexibility, contradicting the "preserve flexibility" requirement).
- D. Use an SCP to block iam:CreateRole entirely across all accounts (blocking role creation altogether prevents developers from achieving the goal of self-service role creation at all).

**Correct Answer: B**

**Explanation**
An **IAM permissions boundary** is an advanced feature that defines the **maximum allowed permissions ceiling** for IAM roles/users a developer can create. Granting developers role-creation permission while enforcing (via policy condition) that a specific permissions boundary must always be attached means that no matter how broad a permission (even an administrator policy) a developer tries to attach to a role, its actual effective permissions can never exceed the boundary. This is the standard pattern for achieving both self-service flexibility and prevention of privilege escalation.

**Why the other choices are wrong**
- A: Relying on trust alone with no technical control leaves the privilege-escalation risk fully open.
- C: Completely removing developer self-service directly contradicts the flexibility requirement.
- D: Blocking role creation entirely via SCP prevents developers from creating roles at all, failing to achieve the self-service goal.

> 💡 **Exam tip**: To **delegate IAM role/policy creation to users while preventing privilege escalation**, enforcing a **permissions boundary** alongside it is the standard answer.

## QUESTION 300

**Question**: A company wants to use an API that a third-party SaaS vendor provides via PrivateLink, from resources inside its VPC. The application code is already hardcoded to the SaaS's public domain name (e.g., api.saas-vendor.com), and they want requests to this domain to automatically route through PrivateLink with no code changes. What's the solution?

**Choices**
- A. Create only a VPC interface endpoint and modify the application code everywhere to use the endpoint's unique DNS name (requires a code change, contradicting the "no code changes" requirement).
- B. **Create the VPC interface endpoint with the private DNS option enabled, so the SaaS's original public domain name automatically resolves to the endpoint's private IP inside the VPC.**
- C. Create a record with the same name as the SaaS domain in a Route 53 public hosted zone, overriding it to the endpoint's IP (you can't override a public domain owned by the SaaS vendor yourself — this amounts to DNS spoofing and is technically infeasible/inappropriate).
- D. Add an override record for this domain only on the on-premises DNS server (since the scenario is about VPC-internal resources using it, changing on-premises DNS has no effect on the VPC-internal traffic path).

**Correct Answer: B**

**Explanation**
Enabling the **private DNS** option when creating a VPC interface endpoint has AWS automatically configure a Route 53 private hosted zone so that the service's **original public domain name** resolves, inside the VPC, to the interface endpoint's private IP address. This means the application can keep using its existing hardcoded public domain name, while the actual traffic automatically routes through PrivateLink with no code changes.

**Why the other choices are wrong**
- A: Modifying code to use the endpoint-specific DNS name violates the core "no code changes" requirement.
- C: You cannot — and should not attempt to — override a public domain owned by another organization (the SaaS vendor) yourself.
- D: Changing on-premises DNS settings has no effect on name resolution for resources inside the VPC.

> 💡 **Exam tip**: To have an existing public domain name **automatically resolve to a private IP with no application code changes** while using a PrivateLink interface endpoint, enabling the **private DNS** option when creating the endpoint is the standard answer.
