## QUESTION 201

**문제**: 회사가 모바일 앱 사용자를 대상으로 하는 마케팅 커뮤니케이션 서비스를 개발하고 있다. 회사는 SMS(문자 메시지)로 사용자에게 확인 메시지를 보내야 하며, 사용자는 SMS 메시지에 회신할 수 있어야 한다. 회사는 분석을 위해 응답을 1년 동안 보관해야 한다. 이러한 요구 사항을 충족하려면?

**보기**
- A. Amazon Connect 통화 흐름을 생성해 SMS 메시지를 보내고, AWS Lambda로 응답을 처리한다(Connect는 콜센터/음성 중심 서비스로 양방향 SMS 캠페인·여정 관리에 특화되어 있지 않음).
- B. **Amazon Pinpoint 여정(journey)을 구축하고, 분석 및 보관을 위해 이벤트를 Amazon Kinesis 데이터 스트림으로 보내도록 Amazon Pinpoint를 구성한다.**
- C. Amazon SQS로 SMS 메시지를 배포하고 Lambda로 응답을 처리한다(SQS는 단순 메시지 대기열일 뿐 양방향 SMS 발신·수신, 캠페인 관리, 장기 보관 기능을 제공하지 않음).
- D. Amazon SNS FIFO 주제를 생성하고, 분석 및 보관을 위해 Kinesis 데이터 스트림을 SNS 주제에 구독시킨다(SNS는 SMS 양방향 회신을 자체적으로 관리하는 기능이 없고, SNS의 구독 대상도 SQS·Lambda·HTTP(S) 등이며 Kinesis 데이터 스트림을 직접 구독 대상으로 붙일 수 없음).

**정답: B**

**해설**
**Amazon Pinpoint**는 SMS 발송뿐 아니라 고객의 회신을 받아 처리하는 양방향 메시징과, 캠페인/여정(journey) 기반의 자동화된 커뮤니케이션 흐름을 기본 제공하는 관리형 마케팅 서비스입니다. Pinpoint 여정으로 확인 메시지 발송과 회신 수집을 구성하고, 발생하는 이벤트를 **Amazon Kinesis 데이터 스트림**으로 전달하도록 설정하면 이후 분석 파이프라인이나 S3 등으로 연계해 1년간 응답 데이터를 안정적으로 보관할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: Amazon Connect는 콜센터 통화 흐름 및 옴니채널 컨택센터에 초점이 맞춰져 있어, 이 시나리오의 대규모 SMS 캠페인·여정 관리 목적에는 Pinpoint보다 적합하지 않습니다.
- C: SQS는 메시지를 전달·버퍼링하는 대기열 서비스일 뿐이며, SMS 발신/양방향 회신 처리와 캠페인 관리 기능이 없어 별도로 모두 구현해야 합니다.
- D: SNS는 회신 수집·여정 관리 기능이 없고, 구독 대상으로 Kinesis 데이터 스트림을 직접 지정할 수 없어 아키텍처 자체가 성립하지 않습니다.

> 💡 **시험 꿀팁**: **양방향 SMS + 캠페인/여정 자동화**가 요구되면 **Amazon Pinpoint**가 표준 정답이며, 분석·보관을 위한 이벤트 전달에는 **Kinesis 데이터 스트림** 연동이 함께 따라옵니다.

## QUESTION 202

**문제**: 회사가 데이터를 Amazon S3 버킷으로 이동할 계획이다. 데이터는 S3에 저장될 때 암호화되어야 하며, 암호화 키는 매년 자동으로 순환(rotate)되어야 한다. 최소한의 운영 오버헤드로 이 요구 사항을 충족하는 솔루션은?

**보기**
- A. 데이터를 S3 버킷으로 이동하고 SSE-S3(S3 관리형 키)로 서버 측 암호화를 사용하며, SSE-S3의 기본 제공 키 순환 동작에 의존한다(SSE-S3는 AWS가 내부적으로 키를 관리·순환하지만 사용자가 순환 주기를 지정하거나 확인할 수 없어 "매년"이라는 요구를 충족한다고 보장할 수 없음).
- B. **AWS KMS 고객 관리형 키를 생성하고 자동 키 순환을 활성화한 뒤, 이 키를 사용하도록 S3 버킷의 기본 암호화를 설정하고 데이터를 이동한다.**
- C. AWS KMS 고객 관리형 키를 생성해 S3 버킷의 기본 암호화로 설정하고, 매년 수동으로 키를 교체한다(수동 교체는 담당자의 실수나 누락 위험이 있고 운영 부담이 크므로 "최소 오버헤드" 요구에 위배).
- D. S3로 이동하기 전에 고객 키 자료로 데이터를 암호화하고, 키 자료 없이 생성한 KMS 키에 그 자료를 가져와 자동 키 순환을 활성화한다(업로드 전 암호화는 SSE가 아닌 클라이언트 측 암호화이며, 가져온 키 자료를 사용하는 KMS 키는 애초에 AWS의 자동 키 순환을 지원하지 않음).

**정답: B**

**해설**
**AWS KMS 고객 관리형 키(CMK)**는 자동 키 순환 기능을 켜면 매년(365일마다) 새로운 암호화 자료를 자동으로 생성해 별도 작업 없이 키를 순환시킵니다. 이 키를 S3 버킷의 **기본 암호화(default encryption)** 설정에 지정하면, 방법을 따로 지정하지 않고 업로드되는 모든 객체가 저장 시점(SSE)에 자동으로 암호화되어, "저장 시 암호화 + 매년 자동 키 순환 + 최소 운영 오버헤드"라는 세 조건을 모두 만족합니다.

**왜 다른 보기는 오답인가**
- A: SSE-S3는 AWS 소유·관리 키를 사용해 무료로 암호화되지만, 키 순환 주기를 사용자가 지정하거나 통제할 수 없어 "매년"이라는 명시적 요구를 보장하지 못합니다.
- C: 매년 수동 교체는 순환을 자동화하지 않아 운영 부담이 크고, 교체를 잊거나 지연하면 요구 사항을 놓칠 위험이 있습니다.
- D: 업로드 전에 데이터를 암호화하는 방식은 서버 측 암호화(SSE)가 아닌 클라이언트 측 암호화(CSE)이며, 키 자료를 가져온(import) KMS 키는 AWS의 자동 순환 기능 자체를 지원하지 않습니다.

> 💡 **시험 꿀팁**: **"S3 저장 시 암호화" + "키의 자동/정기 순환"** 조합에는 **KMS 고객 관리형 키 + 자동 키 순환 + S3 기본 암호화**가 표준 정답입니다.

## QUESTION 203

**문제**: 금융 회사에서 고객이 문자로 재정 고문과의 약속을 요청하면, EC2에서 실행되는 웹 애플리케이션이 요청을 받아 Amazon SQS 대기열에 게시한다. 또 다른 EC2 애플리케이션이 회의 초대·확인 이메일을 보내고, 예약 성공 후 DynamoDB에 회의 정보를 저장한다. 회사가 성장하면서 고객이 회의 초대장을 받는 데 시간이 더 오래 걸린다고 보고한다. 이 문제를 해결하려면?

**보기**
- A. DynamoDB 앞에 DynamoDB Accelerator(DAX) 클러스터를 추가한다(DAX는 DynamoDB 읽기 지연을 줄이는 인메모리 캐시로, 초대 이메일 발송 애플리케이션의 처리 지연 문제와는 무관함).
- B. 약속 요청을 수락하는 웹 애플리케이션 앞에 API Gateway를 추가한다(요청 수집 단계는 문제의 병목이 아니며, 지연이 발생하는 곳은 초대장 발송 처리 단계임).
- C. CloudFront 배포를 추가해 오리진을 약속 요청 웹 애플리케이션으로 설정한다(정적 콘텐츠 캐싱은 요청 접수 단계를 빠르게 할 뿐, 초대장 발송 애플리케이션의 처리 용량 부족은 해결하지 못함).
- D. **회의 초대를 보내는 애플리케이션에 Auto Scaling 그룹을 추가하고, SQS 대기열 깊이(백로그)에 따라 확장되도록 구성한다.**

**정답: D**

**해설**
초대장 지연의 원인은 요청을 접수하는 앞단이 아니라, **SQS 대기열에서 메시지를 꺼내 이메일을 발송하는 뒤단 애플리케이션의 처리 용량 부족**입니다. 이 애플리케이션을 **Auto Scaling 그룹**으로 구성하고 **SQS 대기열의 메시지 수(백로그)** 지표에 따라 인스턴스 수를 조정하면, 요청량이 늘어도 초대장 처리 속도를 유지할 수 있어 전달 지연 문제를 근본적으로 해결합니다.

**왜 다른 보기는 오답인가**
- A: DAX는 DynamoDB 읽기 캐시이며, 이메일 발송 처리량이나 지연과는 관련이 없습니다.
- B: API Gateway는 요청 수집 계층에 추가되는 것으로, 병목이 이미 있는 발송 처리 단계에는 영향을 주지 않습니다.
- C: CloudFront는 콘텐츠 전송을 가속화하는 CDN으로, 백엔드 처리 애플리케이션의 확장 문제를 해결하지 못합니다.

> 💡 **시험 꿀팁**: **SQS를 소비하는 워커(worker) 애플리케이션이 병목**이라면, **대기열 깊이(ApproximateNumberOfMessages) 기반 Auto Scaling**이 표준 정답입니다.

## QUESTION 204

**문제**: 온라인 소매 회사가 5천만 명 이상의 활성 고객과 하루 25,000건 이상의 주문을 처리하며, 구매 데이터는 S3에, 추가 고객 데이터는 RDS에 저장한다. 여러 팀이 분석을 위해 모든 데이터를 사용할 수 있어야 하며, 세분화된 권한 관리와 최소한의 운영 오버헤드가 필요하다. 이 요구를 충족하는 솔루션은?

**보기**
- A. 구매 데이터를 RDS에 직접 마이그레이션하고 RDS 액세스 제어로 접근을 제한한다(대규모 반정형 구매 데이터를 RDS로 옮기는 것 자체가 비효율적이며, 여러 팀이 분석 도구로 자유롭게 조회할 수 있는 방법이 명시되지 않음).
- B. Lambda로 RDS 데이터를 주기적으로 S3에 복사하고, Glue 크롤러와 Athena로 쿼리하며 S3 버킷 정책으로 접근을 제한한다(S3 버킷 정책은 버킷/객체 단위로만 제어되어 테이블·컬럼 수준의 세분화된 권한 관리가 어렵고, 별도 배치 복사 로직을 직접 운영해야 함).
- C. **AWS Lake Formation으로 데이터 레이크를 구성하고, RDS에 대한 AWS Glue JDBC 연결을 생성해 Lake Formation에 S3 버킷을 등록한 뒤 Lake Formation 액세스 제어로 접근을 제한한다.**
- D. Redshift 클러스터를 생성하고 Lambda로 S3·RDS 데이터를 주기적으로 복사한 뒤 Redshift 액세스 제어로 접근을 제한한다(클러스터 프로비저닝·운영이 필요하고 주기적 복사 파이프라인을 직접 구축·관리해야 해 운영 오버헤드가 큼).

**정답: C**

**해설**
**AWS Lake Formation**은 S3를 중심으로 데이터 레이크를 구성하고, AWS Glue의 크롤러·ETL·카탈로그 기능을 그대로 활용하면서 **테이블·컬럼·행 수준의 세분화된 권한 부여/취소** 모델을 제공합니다. RDS는 Glue JDBC 연결로 데이터 레이크에 통합하고 S3는 Lake Formation에 위치를 등록하기만 하면, 별도의 데이터 복제 파이프라인 없이 여러 팀에 중앙 집중식·세분화된 접근 제어를 최소 오버헤드로 제공할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: RDS로 구매 데이터를 옮기는 것은 불필요한 마이그레이션이며, RDS 액세스 제어만으로는 세분화된 분석용 권한 관리를 제공하기 어렵습니다.
- B: S3 버킷 정책은 세밀한(테이블/컬럼 단위) 권한 관리에 한계가 있고, 주기적 복사를 위한 Lambda 스케줄링을 직접 유지 관리해야 합니다.
- D: Redshift 클러스터 운영과 주기적 데이터 적재 파이프라인을 모두 직접 구축·관리해야 하므로 운영 오버헤드가 가장 큽니다.

> 💡 **시험 꿀팁**: **여러 데이터 소스(S3+RDS 등)를 통합해 팀별 세분화된 권한으로 분석**하게 하려면 **AWS Lake Formation**이 표준 정답입니다.

## QUESTION 205

**문제**: 회사가 온프레미스에서 정적 문서로 구성된 마케팅 웹 사이트를 운영하며 SFTP로 문서를 업로드한다. 이를 AWS로 옮겨 CloudFront를 오리진으로 사용하려 한다. 가장 비용 효율적이고 탄력적인 오리진 아키텍처는?

**보기**
- A. Amazon Lightsail 가상 서버에서 웹 서버를 구성하고 SFTP로 콘텐츠를 업로드한다(가상 서버 운영·패치 등 추가 관리 오버헤드와 비용이 정적 콘텐츠 호스팅 대비 불필요하게 발생).
- B. EC2 Auto Scaling 그룹과 ALB를 구성하고 SFTP로 콘텐츠를 업로드한다(단순 정적 문서 제공에 EC2·ASG·ALB까지 두는 것은 과도한 복잡성과 비용을 초래).
- C. **프라이빗 S3 버킷을 생성하고, CloudFront 원본 액세스 자격(OAI/OAC)에서만 접근을 허용하도록 S3 버킷 정책을 구성한 뒤 AWS CLI로 콘텐츠를 업로드한다.**
- D. 퍼블릭 S3 버킷을 생성하고 SFTP용 AWS Transfer Family를 구성해 S3 버킷을 정적 웹 사이트 호스팅용으로 설정한 뒤 SFTP로 업로드한다(AWS Transfer Family 사용에 따른 추가 비용과 복잡성이 발생하고, 퍼블릭 버킷 노출은 보안상 바람직하지 않음).

**정답: C**

**해설**
**프라이빗 S3 버킷**은 정적 문서 호스팅에 서버 관리가 필요 없는 가장 비용 효율적이고 내구성 높은 스토리지입니다. 버킷을 비공개로 유지한 채 **CloudFront 원본 액세스(OAI/OAC)**를 통해서만 접근을 허용하는 버킷 정책을 적용하면, 콘텐츠는 CloudFront를 거쳐서만 안전하게 제공되고 S3 직접 접근은 차단됩니다. AWS CLI로 업로드하면 SFTP 서버 같은 별도 인프라 없이도 손쉽게 콘텐츠를 관리할 수 있습니다.

- A: Lightsail 가상 서버는 OS 패치·웹 서버 관리 등 추가 운영 부담과 비용이 S3 정적 호스팅보다 큽니다.
- B: 정적 문서 제공에 ASG+ALB까지 필요하지 않으며, 불필요한 복잡성과 비용만 추가됩니다.
- D: AWS Transfer Family for SFTP는 별도의 비용과 관리가 필요하고, 퍼블릭 버킷으로 웹 사이트를 호스팅하는 것은 프라이빗 버킷+OAI 방식보다 보안이 취약합니다.

> 💡 **시험 꿀팁**: **CloudFront 오리진으로 정적 콘텐츠를 가장 저렴하고 안전하게 제공**하려면 **프라이빗 S3 + CloudFront OAI/OAC**가 표준 정답입니다.

## QUESTION 207

**문제**: 회사가 비동기 API로 사용자 요청을 수집해 요청 유형별 마이크로서비스로 라우팅한다. API Gateway가 프런트엔드를 제공하고, Lambda가 DynamoDB에 요청을 저장한 뒤 처리 마이크로서비스로 전달한다. DynamoDB 처리량을 예산 한도까지 프로비저닝했음에도 가용성 문제가 발생해 사용자 요청이 유실되고 있다. 기존 사용자에게 영향을 주지 않고 이 문제를 해결하려면?

- A. API Gateway에서 서버 측 조절(스로틀링) 제한을 추가한다(요청을 조절·거부하는 방식은 오히려 정상 사용자 요청까지 유실시켜 "기존 사용자에게 영향 없이"라는 조건에 정면으로 위배).
- B. DAX와 Lambda로 DynamoDB에 대한 쓰기를 버퍼링한다(DAX는 읽기 지연을 줄이는 캐시로 설계되어 있으며 쓰기 버퍼링 용도가 아니어서 이 문제(쓰기 처리량 초과로 인한 유실)를 해결하지 못함).

**해설**

**왜 다른 보기는 오답인가**

- B: DAX는 읽기 가속용 인메모리 캐시이며 쓰기 버퍼링을 위한 서비스가 아닙니다.
- C: 보조 인덱스는 조회 효율을 높일 뿐 쓰기 처리량 초과로 인한 요청 유실과는 관련이 없습니다.

> 💡 **시험 꿀팁**: **다운스트림 저장소(DynamoDB 등)의 처리량 한계로 요청이 유실**된다면, **SQS로 버퍼링해 쓰기 속도를 분리**하는 것이 표준 정답입니다.

- C. 수집·이행용 SQS 대기열을 각각 프로비저닝하고 EC2가 폴링하도록 구성하되, 대기열의 알림을 기반으로 ASG를 조정한다(대기열 사용은 옳은 방향이지만, 단순 알림 기반 조정은 인스턴스당 처리 부담을 반영하지 못해 세밀한 확장 제어가 어려움).
- D. **수집·이행용 SQS 대기열을 각각 프로비저닝하고 EC2가 폴링하도록 구성하며, 인스턴스당 백로그(backlog per instance) 지표를 만들어 이를 기준으로 ASG를 조정한다.**

**정답: D**

**해설**
주문 수집과 이행처럼 **처리 속도가 다른 두 단계**는 각각 별도의 **SQS 대기열**로 분리해 서로 영향을 주지 않고 확장할 수 있어야 합니다. 여기에 **인스턴스당 백로그(대기열 메시지 수 ÷ 실행 중인 인스턴스 수)**를 커스텀 CloudWatch 지표로 만들어 이를 기준으로 ASG를 조정하면, 실제 처리 대기량에 정확히 비례해 필요한 만큼만 인스턴스를 늘리거나 줄일 수 있어 데이터 손실 없이 리소스 활용을 최적화할 수 있습니다.

**왜 다른 보기는 오답인가**
- A: CPU 사용률은 큐 기반 워크로드의 실제 처리 지연을 정확히 반영하지 못하며, 최대치 기준 최소 용량 고정은 평시 리소스 낭비를 유발합니다.
- B: SQS를 통한 분리·안정적 메시지 처리가 빠져 있어, 이행 단계가 밀릴 때 데이터가 유실될 위험이 남습니다.
- C: 대기열을 도입한 것은 맞지만, 단순 알림 기반 조정은 인스턴스별 실제 부하를 반영하지 못해 D만큼 정교하지 않습니다.

> 💡 **시험 꿀팁**: **SQS를 폴링하는 워커의 Auto Scaling**에는 **인스턴스당 백로그(backlog per instance) 커스텀 지표**를 기준으로 조정하는 것이 표준 정답입니다.

## QUESTION 212

**문제**: 회사가 다른 팀이 접근할 수 있도록 데이터베이스를 하루 한 번 S3로 내보낸다. 내보낸 객체 크기는 2~5GB이며, 접근 패턴은 가변적이고 빠르게 바뀐다. 데이터는 즉시 사용 가능해야 하고 최대 3개월간 접근 가능해야 하며, 검색 시간을 늘리지 않으면서 가장 비용 효율적이어야 한다. 어떤 S3 스토리지 클래스를 사용해야 하는가?

- A. **S3 Intelligent-Tiering**

> 💡 **시험 꿀팁**: **접근 패턴을 예측할 수 없고 자주 바뀌는 데이터**에는 **S3 Intelligent-Tiering**이 표준 정답입니다(자동으로 계층을 오가며 검색 지연/요금이 없다는 점이 핵심).

## QUESTION 218

**문제**: 회사에 탄력적 IP가 있는 퍼블릭 서브넷의 EC2에서 실행되는 웹 서버가 있다. EC2에는 기본 보안 그룹이 할당되어 있고, 기본 네트워크 ACL은 모든 트래픽을 차단하도록 수정되었다. 포트 443으로 어디서든 웹 서버에 접근할 수 있도록 해야 한다. 이를 위한 단계 조합은? (2개 선택)

- D. 소스 0.0.0.0/0에서 대상 0.0.0.0/0으로 인바운드/아웃바운드 TCP 포트 443을 모두 허용하도록 네트워크 ACL을 업데이트한다(클라이언트의 응답 트래픽은 서버가 443번에서 클라이언트의 임시 포트(에페메럴 포트)로 되돌아가는 것이라, 아웃바운드도 443으로 고정하면 실제 응답 트래픽의 목적지 포트와 맞지 않아 규칙이 성립하지 않음).
- E. **소스 0.0.0.0/0에서 인바운드 TCP 포트 443을 허용하고, 대상 0.0.0.0/0으로 아웃바운드 TCP 포트 32768-65535(임시 포트 범위)를 허용하도록 네트워크 ACL을 업데이트한다.**

**정답: A, E**

**해설**
포트 443으로 어디서나 접근을 허용하려면 **보안 그룹(상태 저장)**과 **네트워크 ACL(상태 비저장)** 두 계층 모두에서 트래픽을 허용해야 합니다. 보안 그룹은 상태 저장이므로 인바운드 443 허용 규칙(A) 하나만으로 응답 트래픽까지 자동 허용됩니다. 반면 네트워크 ACL은 상태 비저장이라 요청과 응답을 각각 별도 규칙으로 허용해야 하는데, 클라이언트가 보낸 요청은 목적지 포트 443(인바운드 허용 필요)이고, 서버의 응답은 출발지 포트 443에서 클라이언트의 임시 포트(대상 아웃바운드 32768-65535 허용 필요)로 돌아갑니다. 따라서 A와 E를 함께 적용해야 실제로 양방향 통신이 성립합니다.

**왜 다른 보기는 오답인가**
- B: 아웃바운드 목적지 기준 규칙은 외부에서 들어오는 인바운드 요청 자체를 허용하지 않습니다.
- C: 인바운드 허용만으로는 부족하며, 상태 비저장인 NACL에서는 응답을 위한 아웃바운드 규칙이 별도로 필요합니다.
- D: 아웃바운드를 443으로 고정하면 실제 응답 트래픽의 목적지 포트(클라이언트의 임시 포트)와 일치하지 않아 규칙이 의도대로 동작하지 않습니다.

> 💡 **시험 꿀팁**: **네트워크 ACL은 상태 비저장**이므로, 특정 포트에 대한 인바운드 허용과 함께 **응답용 임시 포트(32768-65535) 범위의 아웃바운드 허용**을 반드시 짝지어 구성해야 한다는 점을 기억하세요.

- A. Auto Scaling 그룹에서 실행되는 T3 인스턴스로 교체하고 콘솔에서 변경한다(T3는 버스터블 성능 인스턴스로 CPU 크레딧 소진 시 성능이 저하될 수 있어 지속적인 인메모리 작업 부하에 적합하지 않고, 콘솔에서의 수동 변경은 IaC(CloudFormation) 운용 방식과도 어긋남).
- B. Auto Scaling 그룹을 사용하도록 CloudFormation 템플릿을 수정하고, 필요 시 원하는/최대 용량을 수동으로 늘린다(수동 용량 조정은 근본 원인인 인스턴스 유형(메모리 부족)을 해결하지 못하고 운영 개입이 반복적으로 필요함).
- C. CloudFormation 템플릿을 수정해 R5 인스턴스로 교체하고, CloudWatch의 내장 EC2 메모리 지표로 향후 용량 계획을 추적한다(EC2의 기본 제공 CloudWatch 지표에는 메모리 사용률이 포함되지 않아, 별도의 CloudWatch 에이전트 없이는 애초에 이 지표 자체를 얻을 수 없음).
- D. **CloudFormation 템플릿을 수정해 R5 인스턴스로 교체하고, EC2에 CloudWatch 에이전트를 배포해 사용자 지정 애플리케이션 지연 시간 지표를 생성한다.**

**정답: D**

**해설**
인메모리 작업 위주의 상태 저장 애플리케이션에는 범용 M5보다 **메모리 최적화 R5 인스턴스**가 적합합니다. 여기에 **CloudWatch 에이전트**를 배포해 OS 수준 메모리 사용률과 애플리케이션의 사용자 지정 지연 시간 지표를 수집하면, EC2 기본 지표만으로는 알 수 없는 실제 병목을 파악해 향후 용량 계획에 활용할 수 있습니다. 인스턴스 유형 교체와 세밀한 모니터링을 CloudFormation을 통해 코드로 관리하는 것이 가장 운영 효율적인 방식입니다.

**왜 다른 보기는 오답인가**
- A: T3는 버스터블 인스턴스로 CPU 크레딧이 소진되면 성능이 급격히 떨어질 수 있어 지속적인 고부하 인메모리 작업에 부적합하며, 콘솔 수동 변경은 IaC 운영 방식에도 맞지 않습니다.
- B: 인스턴스 수를 늘리는 것만으로는 상태 저장 애플리케이션의 메모리 부족이라는 근본 원인을 해결하지 못합니다.
- C: EC2의 기본 제공 CloudWatch 지표에는 메모리 사용률이 포함되어 있지 않으므로("내장 EC2 메모리 지표"라는 전제 자체가 성립하지 않음), CloudWatch 에이전트 없이는 이 지표를 얻을 수 없습니다.

> 💡 **시험 꿀팁**: **EC2 메모리 사용률은 기본 CloudWatch 지표에 포함되지 않는다**는 점과, **메모리 집약적 워크로드에는 R 계열 인스턴스**가 표준 정답이라는 점을 함께 기억하세요.

## QUESTION 220

**문제**: 솔루션 설계자가 API Gateway로 사용자 요청을 받는 새 API를 설계 중이다. 요청량은 매우 가변적이며 몇 시간 동안 요청이 없을 수도 있다. 데이터 처리는 비동기식이지만 요청 후 몇 초 이내에 완료되어야 한다. 최저 비용으로 API를 호출할 컴퓨팅 서비스는?

**보기**
- A. AWS Glue 작업(Glue는 배치성 ETL 작업에 최적화된 서비스로 작업 시작에 수 분이 걸릴 수 있어, 몇 초 내 완료해야 하는 API 요청 처리 방식에 맞지 않음).
- B. **AWS Lambda 함수**
- C. Amazon EKS에서 호스팅되는 컨테이너화된 서비스(항상 실행 중인 클러스터/노드 비용이 발생해, 몇 시간씩 요청이 없는 간헐적 워크로드에는 비용 효율적이지 않음).
- D. Amazon EC2와 함께 Amazon ECS에서 호스팅되는 컨테이너화된 서비스(요청이 없는 동안에도 EC2 인스턴스가 계속 실행되며 비용이 발생해, 간헐적이고 가변적인 트래픽에는 비효율적임).

**정답: B**

**해설**
**AWS Lambda**는 API Gateway와 통합되어 요청이 들어올 때만 실행되고, 사용한 컴퓨팅 시간에 대해서만 과금되는 완전 서버리스 컴퓨팅입니다. 요청량이 급증하면 자동으로 동시 실행 수가 늘어나 몇 초 이내 처리 요구를 충족하고, 요청이 몇 시간 동안 없을 때는 비용이 전혀 발생하지 않아 가변적이고 간헐적인 트래픽 패턴에 가장 저렴한 선택입니다.

**왜 다른 보기는 오답인가**
- A: Glue는 대규모 데이터 처리·변환용 배치 서비스로, 작업 시작 지연이 있어 몇 초 내 응답이 필요한 API 트리거 용도에 적합하지 않습니다.
- C, D: EKS나 EC2 기반 ECS는 요청이 없는 시간에도 클러스터/인스턴스가 계속 실행되며 비용이 발생해, 몇 시간씩 요청이 없을 수 있는 이 워크로드에는 비효율적입니다.

> 💡 **시험 꿀팁**: **가변적이고 간헐적인 요청량 + API Gateway 트리거 + 최저 비용**이라는 조합에는 **AWS Lambda**가 표준 정답입니다.
