## Q1. AWS 클라우드로 이전 시 비용 절감

회사가 온프레미스 리소스 대신 AWS 클라우드에서 새 애플리케이션 워크로드를 구축하려 합니다. AWS 클라우드를 사용하면 어떤 비용을 줄일 수 있습니까?

- A. 사용자 지정 Java 또는 Node.js 코드 작성 비용
- B. 보안 침투 테스트
- C. 새 애플리케이션을 지원하는 데 필요한 하드웨어
- D. 타사 애플리케이션에 대한 특정 테스트 케이스 작성

**정답: C**

✅ **C. 새 애플리케이션을 지원하는 데 필요한 하드웨어**: AWS는 물리적 인프라를 운영하고 유지 관리하므로 고객은 물리적 서버 및 하드웨어를 구매, 설치, 유지 관리할 필요가 없습니다. 하드웨어에 대한 대규모 초기 자본 지출이 없어집니다.

❌ **A. 사용자 지정 Java 또는 Node.js 코드 작성 비용**: AWS는 애플리케이션 코드를 작성해 주지 않습니다. 클라우드나 온프레미스를 사용하든 개발 비용은 고객의 책임입니다.

❌ **B. 보안 침투 테스트**: 침투 테스트는 여전히 고객의 책임이며 AWS와 조율이 필요할 수 있습니다. 클라우드로 이전해도 이 비용이 없어지지 않습니다.

❌ **D. 타사 애플리케이션에 대한 테스트 케이스 작성**: 애플리케이션 테스트는 고객의 책임입니다. AWS는 애플리케이션을 위한 테스트 케이스 작성 또는 실행 비용을 부담하지 않습니다.

💡 **시험 꿀팁**: AWS 클라우드 = 하드웨어에 대한 CapEx 없음. 자본 지출(서버 구매)을 운영 지출(종량제)로 전환합니다. 핵심 키워드: "하드웨어 비용 제거".

## Q2. AWS Marketplace에서 사용자가 할 수 있는 작업 (2개 선택)

AWS Marketplace에서 사용자가 수행할 수 있는 작업은 무엇입니까? (2개 선택)

- A. 미사용 Amazon EC2 스팟 인스턴스 판매
- B. 다른 AWS 사용자에게 솔루션 판매
- C. AWS에서 실행되는 타사 소프트웨어 구매
- D. AWS 보안 및 규정 준수 문서 구매
- E. AWS Snowball 주문

**정답: B, C**

✅ **B. 다른 AWS 사용자에게 솔루션 판매**: AWS Marketplace를 통해 독립 소프트웨어 공급업체 및 개인이 다른 AWS 고객에게 소프트웨어 솔루션, SaaS 제품, AMI를 목록에 올리고 판매할 수 있습니다.

✅ **C. AWS에서 실행되는 타사 소프트웨어 구매**: AWS Marketplace는 AWS에서 실행되도록 사전 구성된 타사 공급업체의 소프트웨어를 찾아 구매하고 배포할 수 있는 디지털 카탈로그입니다.

❌ **A. 미사용 EC2 스팟 인스턴스 판매**: 스팟 인스턴스 용량은 가용 용량에 따라 AWS가 완전히 관리합니다. 개별 고객은 미사용 스팟 인스턴스를 Marketplace에 목록에 올리거나 판매할 수 없습니다.

❌ **D. AWS 보안 및 규정 준수 문서 구매**: AWS 규정 준수 문서(SOC 보고서, PCI DSS 증명 등)는 AWS Marketplace가 아닌 AWS Artifact를 통해 이용할 수 있습니다.

❌ **E. AWS Snowball 주문**: AWS Snowball은 AWS 관리 콘솔 또는 AWS Snow Family 콘솔을 통해 주문하며, AWS Marketplace를 통해 주문하지 않습니다.

💡 **시험 꿀팁**: AWS Marketplace = AWS에서 실행되는 소프트웨어 구매/판매(AMI, SaaS, 데이터). AWS Artifact = 규정 준수 문서. AWS Snow Family 콘솔 = Snowball 디바이스 주문.

## Q3. AWS의 하이브리드 클라우드 아키텍처의 의미

사용자가 AWS에서 하이브리드 클라우드 아키텍처를 구축할 때 무엇을 의미합니까?

- A. 모든 리소스가 온프레미스 인프라를 사용하여 실행됩니다.
- B. 일부 리소스는 온프레미스에서 실행되고 일부는 코로케이션 센터에서 실행됩니다.
- C. 모든 리소스가 AWS 클라우드에서 실행됩니다.
- D. 일부 리소스는 온프레미스에서 실행되고 일부는 AWS 클라우드에서 실행됩니다.

**정답: D**

✅ **D. 일부 리소스는 온프레미스에서 실행되고 일부는 AWS 클라우드에서 실행됩니다**: 하이브리드 클라우드 아키텍처는 온프레미스(또는 프라이빗 클라우드) 인프라와 퍼블릭 클라우드 서비스(AWS)를 결합합니다. 기업은 민감한 워크로드를 온프레미스에 유지하면서 확장성과 다른 서비스를 위해 AWS를 활용할 수 있습니다.

❌ **A. 모든 리소스가 온프레미스 인프라를 사용하여 실행됩니다**: 이것은 완전한 온프레미스(프라이빗) 아키텍처를 설명하며, 하이브리드 클라우드가 아닙니다.

❌ **B. 일부 리소스는 온프레미스에서 실행되고 일부는 코로케이션 센터에서 실행됩니다**: 이것은 전통적인 분산 데이터 센터 모델을 설명하지만 클라우드 공급자가 포함되지 않으므로 하이브리드 클라우드가 아닙니다.

❌ **C. 모든 리소스가 AWS 클라우드에서 실행됩니다**: 이것은 완전히 클라우드 네이티브 또는 "올인" 클라우드 아키텍처를 설명하며, 하이브리드 모델이 아닙니다.

💡 **시험 꿀팁**: 하이브리드 클라우드 = 온프레미스 + AWS 클라우드 함께 사용. 하이브리드를 지원하는 서비스: AWS Direct Connect, AWS VPN, AWS Outposts, AWS Storage Gateway.

## Q4. 시간 경과에 따른 리소스 변경 사항을 식별하는 서비스

사용자가 시간 경과에 따른 리소스 변경 사항을 식별할 수 있게 해주는 AWS 서비스는 무엇입니까?

- A. Amazon Detective
- B. AWS Config
- C. AWS Service Catalog
- D. AWS IAM

**정답: B**

✅ **B. AWS Config**: AWS Config는 시간 경과에 따른 AWS 리소스의 구성 변경 사항을 지속적으로 기록하고 추적합니다. 리소스 구성의 기록을 제공하여 무엇이 변경되었는지, 언제 변경되었는지, 누가 변경했는지 확인할 수 있습니다.

❌ **A. Amazon Detective**: Amazon Detective는 로그 데이터를 분석하여 보안 조사 결과의 근본 원인을 조사하고 식별하는 데 도움이 되는 보안 서비스입니다. 일반적인 리소스 구성 추적이 아닌 보안 조사에 중점을 둡니다.

❌ **C. AWS Service Catalog**: AWS Service Catalog는 조직이 승인된 IT 서비스의 카탈로그를 만들고 관리할 수 있게 합니다. 거버넌스 및 배포 표준화에 사용되며, 시간 경과에 따른 리소스 변경 사항을 추적하지 않습니다.

❌ **D. AWS IAM**: AWS IAM은 사용자 권한 및 액세스 제어를 관리합니다. 누가 변경할 수 있는지 제어하지만, 시간 경과에 따른 리소스 구성 변경 사항을 추적하지 않습니다.

💡 **시험 꿀팁**: AWS Config = 구성 기록 + 규정 준수 감사 + "무엇이 언제 변경되었는지". CloudTrail = 누가 API 호출을 했는지. Config = 리소스가 어떻게 생겼는지와 어떻게 변경되었는지.

## Q5. AWS를 사용하여 TCO(총소유비용) 절감 방법

AWS를 사용하여 총소유비용(TCO)을 어떻게 줄일 수 있습니까?

- A. 대규모 자본 지출을 최소화함으로써
- B. 타사 라이선스 비용에 대한 책임이 없어짐으로써
- C. 운영 비용을 지출하지 않음으로써
- D. AWS가 애플리케이션을 관리함으로써

**정답: A**

✅ **A. 대규모 자본 지출을 최소화함으로써**: AWS는 종량제 모델을 사용하여 물리적 하드웨어를 선불로 구매할 필요를 없앱니다. 이를 통해 대규모 자본 지출(CapEx)을 더 작고 예측 가능한 운영 지출(OpEx)로 전환하여 TCO 절감의 주요 원동력이 됩니다.

❌ **B. 타사 라이선스 비용에 대한 책임이 없어짐으로써**: 타사 소프트웨어 라이선스 비용(Oracle, Windows 등)은 라이선스 포함 옵션을 사용하지 않는 한 여전히 고객의 책임입니다. AWS는 타사 라이선스 비용을 없애주지 않습니다.

❌ **C. 운영 비용을 지출하지 않음으로써**: AWS로 이전해도 운영 비용이 없어지지 않습니다. 컴퓨팅, 스토리지, 데이터 전송에 대한 비용을 여전히 지불합니다. 모델이 CapEx에서 OpEx로 전환되는 것이지, 제로 비용이 아닙니다.

❌ **D. AWS가 애플리케이션을 관리함으로써**: AWS는 공유 책임 모델에 따라 기본 인프라를 관리하지만, 애플리케이션 관리, 배포, 운영은 고객의 책임으로 남습니다.

💡 **시험 꿀팁**: AWS를 통한 TCO 절감 = CapEx에서 OpEx로 전환. 핵심 용어: 선불 하드웨어 비용 없음, 데이터 센터 유지 관리 없음, 규모의 경제, 사용한 만큼만 지불.

## Q6. AWS 공유 책임 모델에서 고객의 책임

AWS 공유 책임 모델에 따르면 AWS 클라우드에서 고객의 책임은 무엇입니까?

- A. AWS에서 인터넷까지의 네트워크 연결 보장
- B. AWS 클라우드 인프라 내의 결함 패치 및 수정
- C. 클라우드 데이터 센터의 물리적 보안 보장
- D. Amazon EBS 볼륨 백업 보장

**정답: D**

✅ **D. Amazon EBS 볼륨 백업 보장**: 고객은 Amazon EBS 볼륨 백업을 포함한 자신의 데이터를 책임집니다. AWS는 도구(스냅샷, AWS Backup)를 제공하지만, 백업 생성 및 관리 책임은 고객에게 있습니다.

❌ **A. AWS에서 인터넷까지의 네트워크 연결 보장**: AWS는 데이터 센터에서의 인터넷 연결을 포함한 글로벌 네트워크 인프라를 유지 관리합니다.

❌ **B. AWS 클라우드 인프라 내의 결함 패치 및 수정**: AWS는 기본 인프라(하드웨어, 하이퍼바이저, 네트워킹)를 패치하고 유지 관리합니다. 고객은 자신의 OS와 애플리케이션을 패치합니다.

❌ **C. 클라우드 데이터 센터의 물리적 보안 보장**: AWS 시설의 물리적 보안은 전적으로 AWS의 책임("클라우드의 보안")입니다. 고객은 AWS 데이터 센터의 물리적 보안에 접근하거나 책임을 지지 않습니다.

💡 **시험 꿀팁**: 공유 책임 = AWS는 "클라우드의 보안"(하드웨어, 시설, 네트워크), 고객은 "클라우드에서의 보안"(데이터, OS 패치, IAM, 백업, 암호화). EBS 백업 = 고객의 역할.

## Q7. AWS 클라우드의 이점 (2개 선택)

AWS 클라우드의 이점은 무엇입니까? (2개 선택)

- A. 고정 월 비용 요금
- B. 용량 요구 사항을 추정할 필요 없음
- C. 시장 출시 시간 단축
- D. 초기 자본 지출 증가
- E. 클라우드 데이터 센터에 대한 물리적 접근

**정답: B, C**

✅ **B. 용량 요구 사항을 추정할 필요 없음**: AWS를 사용하면 수요에 따라 리소스를 확장하거나 축소할 수 있습니다. 인프라를 과잉 프로비저닝하거나 부족하게 프로비저닝할 필요 없이 필요에 따라 용량을 조정하고 사용한 만큼만 지불합니다.

✅ **C. 시장 출시 시간 단축**: AWS는 사용 가능한 서비스(데이터베이스, AI/ML, 네트워킹)를 제공하여 개발 및 배포 시간을 크게 줄이고 조직이 제품 및 기능을 더 빠르게 출시할 수 있게 합니다.

❌ **A. 고정 월 비용 요금**: AWS 요금은 동적이고 사용량 기반(종량제)이며 고정 월 요금이 아닙니다. 청구서는 실제 리소스 소비에 따라 달라집니다.

❌ **D. 초기 자본 지출 증가**: AWS의 주요 이점 중 하나는 대규모 선불 자본 지출의 제거입니다. AWS는 초기 CapEx를 증가시키는 것이 아니라 감소시킵니다.

❌ **E. 클라우드 데이터 센터에 대한 물리적 접근**: AWS 데이터 센터는 고객이 접근할 수 없습니다. 물리적 보안은 전적으로 AWS가 관리합니다.

💡 **시험 꿀팁**: 클라우드 컴퓨팅의 6가지 이점: CapEx를 OpEx로 전환, 대규모 경제 이점, 용량 추정 불필요, 속도 및 민첩성 향상, 데이터 센터 운영 비용 절감, 몇 분 만에 글로벌 확장.

## Q8. 온프레미스와 클라우드 TCO 비교 시 고려해야 할 비용 (2개 선택)

온프레미스 인프라와 클라우드 아키텍처의 TCO(총소유비용)를 비교할 때 어떤 비용을 고려해야 합니까? (2개 선택)

- A. 클라우드의 애플리케이션 거래에 대한 신용카드 처리 수수료
- B. 온프레미스 데이터 센터에서 서버 하드웨어 구매 및 설치 비용
- C. OS 설치, 패치, 백업, 재해 복구를 포함한 인프라 관리 비용
- D. 타사 침투 테스트 비용
- E. 지속적인 회사 전체 캠페인 관련 광고 비용

✅ **B. 온프레미스 데이터 센터에서 서버 하드웨어 구매 및 설치 비용**: 하드웨어 조달, 설치, 최종 교체는 AWS로 마이그레이션할 때 사라지는 중요한 온프레미스 비용입니다. 이는 모든 TCO 비교에서 핵심 CapEx 항목입니다.

✅ **C. OS 설치, 패치, 백업, 재해 복구를 포함한 인프라 관리 비용**: 온프레미스 인프라 관리에는 일상적인 작업을 위한 전담 IT 직원과 도구가 필요합니다. AWS는 관리형 서비스를 통해 이러한 운영 부담을 크게 줄입니다.

❌ **A. 클라우드의 애플리케이션 거래에 대한 신용카드 처리 수수료**: 결제 처리 수수료는 온프레미스와 클라우드 간의 인프라 비교와 관련 없는 사업 운영 비용입니다.

❌ **D. 타사 침투 테스트 비용**: 침투 테스트는 온프레미스 또는 클라우드 인프라 사용 여부에 관계없이 적용되는 보안 관행이며, TCO 비교에서 차별화되는 비용 요소가 아닙니다.

❌ **E. 광고 비용**: 광고 비용은 인프라 TCO와 전혀 무관한 사업 비용입니다.

💡 **시험 꿀팁**: TCO 비교 = 하드웨어 비용, 인력/운영 비용, 시설 비용(전력, 냉각, 공간), 소프트웨어 라이선스를 찾으세요. 관련 없는 사업 비용(마케팅, 결제 처리)은 무시하세요.

AWS 공유 책임 모델에서 고객의 책임은 무엇입니까?

- B. 네트워크 인프라

- D. 하드웨어의 물리적 보안

❌ **A. 가상화 인프라**: AWS는 "클라우드의 보안"의 일환으로 하이퍼바이저 및 가상화 계층을 관리합니다. 고객은 가상화 인프라에 대한 접근 권한이나 책임이 없습니다.

💡 **시험 꿀팁**: 고객 = "클라우드에서" — 데이터 분류, IAM/사용자 관리, OS 패치(EC2), 애플리케이션 보안, 암호화, 네트워크 트래픽(보안 그룹/NACL). AWS = "클라우드의" — 물리적, 네트워크 인프라, 하이퍼바이저.

## Q11. 전 세계 사용자의 지연 시간 감소

회사가 전 세계 사용자의 지연 시간을 줄이는 방법은 무엇입니까?

- A. 모든 사용자에게 중앙에 있는 AWS 리전 사용
- B. 사용 중인 AWS 리전의 두 번째 가용 영역 사용
- C. 사용 중인 AWS 리전에서 캐싱 활성화
- D. 엣지 로케이션을 사용하여 모든 사용자에게 콘텐츠를 더 가깝게 가져오기

**정답: D**

✅ **D. 엣지 로케이션을 사용하여 콘텐츠를 모든 사용자에게 더 가깝게 가져오기**: Amazon CloudFront는 전 세계 400개 이상의 엣지 로케이션 네트워크를 사용하여 최종 사용자와 지리적으로 가까운 위치에서 콘텐츠를 캐싱하고 제공합니다. 이를 통해 전 세계 방문자의 지연 시간을 대폭 줄입니다.

❌ **A. 모든 사용자에게 중앙에 있는 AWS 리전 사용**: 단일 중앙 AWS 리전은 해당 리전에서 멀리 있는 사용자에게 높은 지연 시간을 초래합니다. 모든 전 세계 사용자와 동일하게 가까운 단일 리전은 없습니다.

❌ **B. 사용 중인 리전의 두 번째 가용 영역 사용**: 추가 가용 영역은 리전 내 가용성과 내결함성을 향상시키지만, 지리적으로 분산된 전 세계 사용자의 지연 시간을 줄이지 않습니다.

❌ **C. 사용 중인 리전에서 캐싱 활성화**: 리전 캐싱은 해당 리전 근처의 사용자 성능을 향상시킬 수 있지만, 멀리 있는 사용자는 여전히 높은 지연 시간을 겪습니다. CloudFront 엣지 로케이션이 글로벌 지연 시간을 해결하기 위해 특별히 설계되었습니다.

💡 **시험 꿀팁**: 글로벌 지연 시간 감소 = CloudFront + 엣지 로케이션. 엣지 로케이션은 리전/AZ와 별도로 최종 사용자 가까이에 콘텐츠를 캐싱하기 위해 존재합니다. CloudFront = CDN(콘텐츠 전달 네트워크).

## Q12. 온프레미스 데이터 센터에서 마이그레이션 후 직원 생산성 향상

온프레미스 데이터 센터에서 마이그레이션한 후 AWS 클라우드가 직원 생산성을 어떻게 높일 수 있습니까?

- A. 사용자가 인프라 프로비저닝을 기다릴 필요가 없습니다.
- B. AWS 클라우드 인프라가 온프레미스 데이터 센터 인프라보다 훨씬 빠릅니다.
- C. AWS가 사용자를 대신하여 애플리케이션 구성 관리를 담당합니다.
- D. 사용자가 보안 및 규정 준수 문제를 처리할 필요가 없습니다.

**정답: A**

✅ **A. 사용자가 인프라 프로비저닝을 기다릴 필요가 없습니다**: 온프레미스 인프라 프로비저닝은 수 주 또는 수 개월이 걸릴 수 있습니다(하드웨어 주문, 배송, 설치). AWS를 사용하면 콘솔이나 API를 통해 수 분 안에 리소스를 프로비저닝할 수 있어 개발자와 팀이 더 빠르고 효율적으로 작업할 수 있습니다.

❌ **B. AWS 클라우드 인프라가 온프레미스보다 훨씬 빠릅니다**: AWS 인프라가 고도로 최적화되어 있지만, 주요 생산성 향상은 원시 속도가 아니라 민첩성(빠른 프로비저닝 및 확장 능력)에 있습니다.

❌ **D. 사용자가 보안 및 규정 준수 문제를 처리할 필요가 없습니다**: 보안 및 규정 준수는 공유 책임입니다. 고객은 자신의 보안 구성, IAM 정책, 규정 준수 요구 사항을 여전히 관리해야 합니다.

💡 **시험 꿀팁**: AWS 생산성 이점 = 민첩성(수개월이 아닌 수분 만에 프로비저닝). 더 이상 하드웨어를 기다릴 필요 없음. 콘솔/CLI/API를 통한 셀프 서비스 프로비저닝 = 더 빠른 가치 실현.

## Q13. AWS 계정을 빠르고 자동으로 생성하고 관리하는 서비스

AWS 계정을 빠르고 자동으로 생성하고 관리할 수 있는 AWS 서비스는 무엇입니까?

- A. AWS QuickSight
- B. Amazon Lightsail
- C. AWS Organizations
- D. Amazon Connect

**정답: C**

✅ **C. AWS Organizations**: AWS Organizations는 여러 AWS 계정을 중앙에서 프로그래밍 방식으로 생성하고 관리할 수 있게 합니다. 계정 생성 자동화, 거버넌스 정책(SCP) 적용, 통합 청구 활성화, 계정을 조직 단위(OU)로 구성할 수 있습니다.

❌ **A. AWS QuickSight**: AWS QuickSight는 비즈니스 인텔리전스(BI) 및 데이터 시각화 서비스입니다. 대시보드 및 보고서를 만드는 데 사용하며, AWS 계정 관리에 사용하지 않습니다.

❌ **B. Amazon Lightsail**: Amazon Lightsail은 예측 가능한 요금으로 소규모 애플리케이션 및 웹사이트를 배포하기 위한 단순화된 클라우드 플랫폼입니다. 계정 관리에 사용하지 않습니다.

❌ **D. Amazon Connect**: Amazon Connect는 고객 전화 통화 및 상호작용을 처리하는 클라우드 기반 콜센터 서비스입니다. AWS 계정 관리에 아무런 역할을 하지 않습니다.

💡 **시험 꿀팁**: AWS Organizations = 다중 계정 관리, 통합 청구, SCP(서비스 제어 정책), 자동화된 계정 생성. AWS Landing Zone 및 Control Tower의 기반입니다.

## Q14. 고가용성을 달성하기 위한 Amazon RDS 기능

고가용성을 달성하는 데 사용할 수 있는 Amazon RDS 기능은 무엇입니까?

- A. 다중 가용 영역
- B. Amazon 예약 인스턴스
- C. 프로비저닝된 IOPS 스토리지
- D. 향상된 모니터링

**정답: A**

✅ **A. 다중 가용 영역**: Amazon RDS Multi-AZ는 다른 가용 영역에 동기식 대기 복제본을 자동으로 생성합니다. 기본 인스턴스에 장애가 발생하면 RDS는 자동으로 대기 인스턴스로 페일오버하여 고가용성과 데이터 내구성을 제공합니다.

❌ **B. Amazon 예약 인스턴스**: 예약 인스턴스는 특정 인스턴스 유형 사용 약정 대가로 상당한 할인을 제공하는 요금 모델입니다. 가용성 또는 중복성에 영향을 미치지 않습니다.

❌ **C. 프로비저닝된 IOPS 스토리지**: 프로비저닝된 IOPS(io1/io2)는 I/O 집약적 워크로드에 대해 일관된 고성능 스토리지를 제공합니다. 이는 성능을 향상시키지만 직접적으로 고가용성이나 자동 페일오버를 제공하지 않습니다.

❌ **D. 향상된 모니터링**: 향상된 모니터링은 RDS 인스턴스에 대한 실시간 OS 수준 지표를 제공합니다. 운영 가시성에 도움이 되지만 고가용성에 기여하지는 않습니다.

💡 **시험 꿀팁**: RDS 고가용성 = 다중 AZ 배포(동기식 복제, 자동 페일오버). RDS 읽기 복제본 = 성능/읽기 확장(비동기식, 고가용성 페일오버 아님). 이 두 가지는 다른 기능입니다.

## Q15. 악의적인 목적으로 사용되는 AWS 리소스 신고 위치

AWS 리소스가 악의적인 목적으로 사용되고 있다는 것을 어디에 신고해야 합니까?

- A. AWS Trust & Safety 팀
- B. AWS Shield
- C. AWS Support
- D. AWS 개발자 포럼

**정답: A**

✅ **A. AWS Trust & Safety 팀**: AWS Trust & Safety 팀은 스팸, 악성 소프트웨어 호스팅, DDoS 공격, 피싱 및 기타 악의적인 활동을 포함한 AWS 리소스 남용을 신고하기 위한 지정 연락처입니다. reportphishing@amazon.com 또는 AWS 남용 신고 양식을 통해 신고할 수 있습니다.

❌ **B. AWS Shield**: AWS Shield는 자신의 리소스를 보호하는 관리형 DDoS 보호 서비스입니다. 타사에 의한 남용을 신고하는 채널이 아닙니다.

❌ **C. AWS Support**: AWS Support는 기술적 문제, 청구 질문, 서비스 관련 문제를 처리합니다. AWS 리소스의 악의적인 사용은 일반 지원이 아닌 Trust & Safety 팀에 신고해야 합니다.

❌ **D. AWS 개발자 포럼**: AWS 개발자 포럼은 기술적 질문 및 지식 공유를 위한 커뮤니티 토론 게시판입니다. 남용 또는 악의적인 활동 신고에 적합한 채널이 아닙니다.

💡 **시험 꿀팁**: AWS 남용 신고 = AWS Trust & Safety 팀(abuse@amazonaws.com). 스팸, 악성 소프트웨어, 피싱, 포트 스캔, AWS IP에서 발생하는 DDoS를 다룹니다. AWS Support 아님, AWS Shield 아님.

## Q16. AWS 관리 콘솔에서 모든 사용자 계정 변경 사항을 추적하는 서비스

AWS 관리 콘솔에서 모든 사용자 계정 변경 사항을 추적하려면 어떤 AWS 서비스를 활성화해야 합니까?

- A. AWS CloudTrail
- B. Amazon Simple Notification Service (Amazon SNS)
- C. VPC Flow Logs
- D. AWS CloudHSM

**정답: A**

✅ **A. AWS CloudTrail**: AWS CloudTrail은 관리 콘솔, CLI, SDK를 통해 취해진 작업을 포함하여 AWS 계정 전반의 모든 API 호출 및 사용자 활동을 기록합니다. 누가 무엇을 언제 어디서 했는지에 대한 완전한 감사 추적을 제공합니다.

❌ **B. Amazon Simple Notification Service (Amazon SNS)**: Amazon SNS는 구독자에게 알림 및 메시지를 보내는 메시징 서비스입니다. 자체적으로 계정 변경 사항을 기록하거나 추적하지 않습니다.

❌ **C. VPC Flow Logs**: VPC Flow Logs는 VPC의 네트워크 인터페이스를 드나드는 IP 트래픽에 대한 정보를 캡처합니다. 네트워크 트래픽을 추적하며, 사용자 계정 작업 또는 API 호출이 아닙니다.

❌ **D. AWS CloudHSM**: AWS CloudHSM은 암호화 키 관리 및 암호화에 사용되는 하드웨어 보안 모듈 서비스입니다. 보안 하드웨어 서비스이며, 감사 또는 로깅 서비스가 아닙니다.

💡 **시험 꿀팁**: CloudTrail = API 감사 로그(누가 어떤 API를 언제 어디서 호출했는지). 거버넌스, 규정 준수, 보안 감사를 위한 1위 도구. 기본적으로 90일 동안 활성화되며, 장기 S3 보존을 위해 Trail을 생성합니다.

## Q17. AWS 클라우드 설계 모범 사례

AWS 클라우드 설계 모범 사례는 무엇입니까?

- A. 컴포넌트 간 강한 결합
- B. 단일 장애 지점
- C. 고가용성
- D. 리소스 과잉 프로비저닝

**정답: C**

✅ **C. 고가용성**: 고가용성은 핵심 AWS Well-Architected Framework 원칙입니다. 컴포넌트 장애에도 불구하고 계속 운영되는 시스템 설계 — 여러 AZ 사용, 로드 밸런서, Auto Scaling, 중복성을 통해 — 는 AWS의 기본 모범 사례입니다.

❌ **A. 컴포넌트 간 강한 결합**: 강한 결합은 컴포넌트들이 서로 크게 의존한다는 것을 의미하며, 복원력이 감소합니다. AWS 모범 사례는 한 컴포넌트의 장애가 전파되지 않도록 느슨한 결합 아키텍처(SQS, SNS, API Gateway 사용)를 옹호합니다.

❌ **B. 단일 장애 지점**: 단일 장애 지점이 있다는 것은 하나의 컴포넌트 장애가 전체 시스템을 중단시킬 수 있다는 것을 의미합니다. AWS 모범 사례는 중복성과 다중 AZ 배포를 통해 단일 장애 지점을 명시적으로 제거할 것을 권장합니다.

❌ **D. 리소스 과잉 프로비저닝**: 과잉 프로비저닝은 비용을 낭비하며 클라우드의 가치 제안에 반합니다. AWS는 적절한 크기 조정 및 Auto Scaling을 통해 실제 수요에 맞게 용량을 조정할 것을 권장합니다.

💡 **시험 꿀팁**: AWS Well-Architected Framework 기둥: 운영 우수성, 보안, 안정성, 성능 효율성, 비용 최적화, 지속 가능성. 고가용성은 안정성에 해당합니다. 피해야 할 것: 강한 결합, SPOF, 과잉 프로비저닝.

## Q18. 선불 비용 절감을 위한 AWS 클라우드 전환 예시

AWS 클라우드로 전환하여 선불 비용을 줄이는 예시는 무엇입니까?

- A. 대규모 변동 비용을 낮은 자본 투자로 대체함으로써
- B. 대규모 자본 투자를 낮은 변동 비용으로 대체함으로써
- C. 최고 수요를 충족하기 위해 고정 수준으로 컴퓨팅 및 스토리지를 프로비저닝함으로써
- D. 가상 서버의 반복적인 확장을 더 간단한 고정 확장 모델로 대체함으로써

**정답: B**

✅ **B. 대규모 자본 투자를 낮은 변동 비용으로 대체함으로써**: 이것은 클라우드 컴퓨팅의 근본적인 재정적 이점 중 하나입니다. 하드웨어의 대규모 선불 구매(CapEx) 대신 AWS를 사용하면 사용한 만큼만 지불(가변/운영 지출/OpEx)하여 초기 투자를 대폭 줄입니다.

❌ **A. 대규모 변동 비용을 낮은 자본 투자로 대체함으로써**: 이것은 반대입니다. AWS는 자본 투자(CapEx)를 줄이는 것이지, 변동 비용을 줄이는 것이 아닙니다. 온프레미스는 높은 CapEx를 가지는 경향이 있고, AWS는 변동(사용량 기반) 비용을 도입합니다.

❌ **C. 최고 수요를 충족하기 위해 고정 수준으로 컴퓨팅 및 스토리지 프로비저닝**: 최고 수요를 위한 고정 프로비저닝은 낭비로 이어지는 온프레미스 접근 방식입니다. AWS는 실제 수요에 맞게 동적 확장을 권장합니다.

❌ **D. 가상 서버의 반복적인 확장을 더 간단한 고정 확장 모델로 대체**: AWS는 동적/탄력적 확장을 촉진하며, 고정 확장이 아닙니다. Auto Scaling은 수요에 따라 자동으로 용량을 조정합니다.

💡 **시험 꿀팁**: 핵심 클라우드 경제 문구: "자본 지출(CapEx)을 운영 지출(OpEx)로 전환". CapEx = 서버 선불 구매. OpEx = 월별 종량제. 이것은 항상 "선불/초기 비용 절감"에 대한 올바른 답입니다.

## Q19. 3계층 웹 애플리케이션에서 가용성을 높이는 서비스 (2개 선택)

일반적인 3계층 웹 애플리케이션 설계 시 가용성을 높이고 영향을 줄이는 AWS 서비스 및/또는 기능은 무엇입니까? (2개 선택)

- A. Amazon EC2 인스턴스에 대한 AWS Auto Scaling
- B. 서비스 상태를 확인하는 Amazon VPC 서브넷 ACL
- C. 여러 가용 영역에 분산된 리소스
- D. AWS Server Migration Service(SMS)를 사용하여 Amazon EC2 인스턴스를 다른 리전으로 이동
- E. 여러 AWS 접속 지점에 분산된 리소스

**정답: A, C**

✅ **A. Amazon EC2 인스턴스에 대한 AWS Auto Scaling**: Auto Scaling은 수요에 따라 EC2 인스턴스 수를 자동으로 조정합니다. 인스턴스에 장애가 발생하면 Auto Scaling이 자동으로 교체하여 가용성을 유지하고 개별 인스턴스 장애의 영향을 줄입니다.

✅ **C. 여러 가용 영역에 분산된 리소스**: 리전 내 여러 AZ에 리소스(EC2, RDS, 로드 밸런서)를 분산시키면 하나의 AZ 장애가 전체 애플리케이션을 중단시키지 않아 가용성이 크게 향상됩니다.

❌ **B. Amazon VPC 서브넷 ACL로 서비스 상태 확인**: 네트워크 ACL(NACL)은 보안 필터링을 위해 서브넷 수준에서 인바운드 및 아웃바운드 트래픽을 제어합니다. 서비스 상태를 확인하거나 애플리케이션 가용성을 향상시키는 데 사용하지 않습니다.

❌ **D. AWS SMS를 사용하여 EC2 인스턴스를 다른 리전으로 이동**: AWS Server Migration Service는 온프레미스 서버를 AWS로 마이그레이션하는 데 사용하며, 가용성을 위해 실행 중인 EC2 인스턴스를 리전 간에 이동하는 데 사용하지 않습니다.

❌ **E. 여러 AWS 접속 지점에 분산된 리소스**: AWS 접속 지점(엣지 로케이션)은 콘텐츠 전달을 위해 CloudFront가 사용하며, EC2와 같은 컴퓨팅 리소스를 분산하는 데 사용하지 않습니다.

💡 **시험 꿀팁**: 웹 앱의 고가용성 = 다중 AZ 배포 + Auto Scaling + Elastic Load Balancer(ELB). 이 조합이 CLF-C02에서 테스트되는 클래식 "고가용성 및 확장 가능한" 아키텍처 패턴입니다.

## Q20. AWS 클라우드 모범 사례에 부합하는 클라우드 설계 원칙

AWS 클라우드 모범 사례에 부합하는 클라우드 설계 원칙은 무엇입니까?

- A. 애플리케이션 컴포넌트 간 고정 의존성 생성
- B. 단일 인스턴스에 서비스 집계
- C. 단일 가용 영역에 애플리케이션 구축
- D. 여러 리소스에 컴퓨팅 부하 분산

**정답: D**

✅ **D. 여러 리소스에 컴퓨팅 부하 분산**: 이것은 AWS의 핵심 설계 원칙입니다 — 수평 확장 및 부하 분산. 여러 인스턴스, 서비스, 가용 영역에 워크로드를 분산시키면 병목 현상을 제거하고 성능을 향상시키며 내결함성이 향상됩니다.

❌ **A. 애플리케이션 컴포넌트 간 고정 의존성 생성**: 고정/강한 의존성은 복원력과 확장성을 감소시킵니다. AWS 모범 사례는 SQS, SNS, API Gateway를 사용하여 컴포넌트를 분리하는 느슨한 결합을 권장합니다.

❌ **B. 단일 인스턴스에 서비스 집계**: 모든 것을 하나의 인스턴스에 통합하면 단일 장애 지점이 생성되고 확장성이 제한됩니다. AWS는 마이크로서비스 및 분산 아키텍처를 권장합니다.

❌ **C. 단일 가용 영역에 애플리케이션 구축**: 단일 AZ 사용은 잠재적 장애 지점을 만듭니다. AWS 모범 사례는 하나의 AZ에 장애가 발생하더라도 가용성을 보장하기 위해 다중 AZ 배포를 권장합니다.

💡 **시험 꿀팁**: AWS 설계 원칙: 느슨한 결합, 수평 확장(인스턴스 추가), 고가용성을 위한 다중 AZ, 장애를 위한 설계(무언가 고장날 것을 가정), 관리형 서비스 사용. 피해야 할 것: 모놀리식, 단일 AZ, 강한 결합, 단일 장애 지점.
